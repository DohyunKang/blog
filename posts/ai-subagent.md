서브에이전트는 메인 에이전트가 일부 작업을 따로 떼어 새 컨텍스트에서 시키고 결과 요약만 받아 오는 구조인데, 일이 병렬로 나뉘고 결과가 요약으로 충분할 때만 이득이었다.

## 쉬운 말로 먼저

에이전트 하나가 혼자 일하면 읽은 파일, 검색 결과, 로그가 전부 자기 대화에 쌓인다. [컨텍스트](#/post/ai-context)가 금방 무거워진다. 그래서 "이 부분은 다른 에이전트가 따로 조사하고 결론만 알려줘" 하는 방식이 생겼다. 맡는 쪽이 서브에이전트, 이런 에이전트가 여러 개 협업하는 구조 전체를 멀티에이전트라고 부른다. 사람 팀에 비유하면 팀장이 조사 한 건을 팀원에게 시키고 보고서 한 장만 받는 것과 비슷하다. 다만 비유일 뿐이고, 실제로는 모델 호출이 하나 더 도는 것이다.

[에이전트 루프](#/post/ai-agent-loop)가 도구를 부르며 도는 구조라면, 서브에이전트는 그 루프 안에서 "다른 루프를 하나 더 시작하는 도구"처럼 쓰이는 경우가 많다. 도구 호출 자체는 [도구 사용](#/post/ai-tool-use) 글에 따로 정리했다.

## 원리: 맥락을 가르는 것

Claude Code 문서가 설명하는 서브에이전트는 이렇다.

- 각자 자기 컨텍스트 윈도우, 시스템 프롬프트, 도구 권한, 권한 설정을 가진다.
- 메인 대화의 기록을 보지 못한다. 메인이 작업을 요약한 위임 메시지를 써서 넘겨줄 뿐이다.
- 끝나면 최종 결과만 메인으로 돌아온다. 중간에 읽은 파일 내용이나 검색 결과는 메인에 들어오지 않는다.
- 사용량 한도는 메인 대화와 같이 쓴다. 따로 공짜가 아니다.

핵심은 마지막 두 가지다. 지저분한 중간 과정은 서브에이전트의 창에서 끝나고, 메인은 결론만 받는다. 그래서 [컨텍스트 윈도우](#/post/ai-context-window)가 덜 찬다. 이건 [압축](#/post/ai-compaction)과 목적이 같지만 방식이 다르다. 압축은 이미 쌓인 걸 줄이는 것이고, 서브에이전트는 처음부터 메인에 안 쌓이게 한다.

Anthropic 컨텍스트 엔지니어링 글이 서브에이전트 결과를 1,000~2,000 토큰 정도 요약으로 받는다고 쓴 것도 같은 맥락이다. 이 숫자는 이전 글에서 읽은 것이다.

## 병렬화와 오케스트레이터-워커

Anthropic의 "Building effective agents"는 비슷해 보이는 두 패턴을 나눈다.

| | 병렬화 | 오케스트레이터-워커 |
|---|---|---|
| 나누는 주체 | 코드가 미리 정해 둠 | 중앙 모델이 입력을 보고 그때 정함 |
| 하위 작업 | 미리 정의됨 (섹션 나누기, 같은 일 여러 번 돌려 투표) | 사전에 예측하기 어려움 |
| 어울리는 일 | 독립적인 조각, 속도 | 여러 파일을 고치는 코딩 같은 일 |

서브에이전트 구조는 대부분 오른쪽이다. 오케스트레이터(lead)가 일을 쪼개고 워커(서브에이전트)에게 맡긴다. 워커끼리 동시에 돌리면 병렬화 효과도 같이 얻는다.

Anthropic이 쓴 멀티에이전트 리서치 시스템 글에서 구체적인 수치가 나온다. 리드 에이전트는 Claude Opus 4, 서브에이전트는 Claude Sonnet 4로 구성했고, 같은 내부 리서치 평가에서 Opus 4 단독보다 90.2% 더 좋았다. 이득은 여러 갈래를 넓게 찾아야 하는 질문(breadth-first)에서 컸다. 리드가 서브에이전트 3~5개를 동시에 띄우고 각 서브에이전트도 도구를 3개 이상 동시에 부르게 해서, 복잡한 질의의 조사 시간이 최대 90% 줄었다고 한다. 둘 다 Anthropic 내부 평가라서 내가 재현한 건 아니다.

## 비용: 이게 제일 중요했다

같은 글의 토큰 수치는 이렇다.

| 구조 | 채팅 대비 토큰 |
|---|---|
| 에이전트 | 약 4배 |
| 멀티에이전트 | 약 15배 |

BrowseComp 평가에서는 토큰 사용량 하나가 성능 차이의 80%를 설명했다고 한다. 도구 호출 수와 모델 선택까지 합치면 95%다. 이걸 거꾸로 읽으면, 멀티에이전트가 좋아지는 이유 상당 부분이 "토큰을 더 많이 쓰니까"일 수 있다는 얘기다. 구조가 똑똑해서가 아니라 더 많이 읽고 더 많이 시도해서 좋아졌을 수 있다. 이는 글에 나온 결론이 아니라 읽으면서 든 추측이다. 글도 일의 가치가 늘어난 토큰 비용을 감당할 만해야 한다고 적는다.

[AI 원가](#/post/app-cost) 관점에서는 이렇게 정리했다. 서브에이전트를 하나 더 띄우면 그 서브에이전트의 입력·출력 토큰이 전부 요금이다. 메인 컨텍스트가 줄어든 만큼 아끼는 게 아니라 새로 쓰는 것이다. [토큰 아끼는 법](#/post/claude-tokens)에서 쓸 때도 이 점이 먼저 걸렸다. 다만 서브에이전트마다 모델을 다르게 지정할 수 있어서(Claude Code 문서 기준 `model` 필드에 sonnet, opus, haiku, fable, 전체 모델 ID, inherit) 단순 조사는 작은 모델에 맡기는 식의 절약은 가능하다.

## 언제 쓰면 안 되나

Anthropic 글은 안 맞는 경우를 직접 적는다. 모든 에이전트가 같은 컨텍스트를 필요로 하거나 서로 의존이 많은 일이다. 코딩은 리서치보다 병렬로 쪼갤 부분이 적고, 에이전트가 실시간으로 조율하는 건 아직 서툴다고 한다.

반대편 글도 읽었다. Cognition의 "Don't Build Multi-Agents"는 두 원칙을 든다.

- 컨텍스트를 공유하라. 개별 메시지가 아니라 전체 에이전트 기록(trace)을.
- 행동에는 암묵적인 결정이 담겨 있다. 결정이 서로 충돌하면 결과가 나쁘다.

예시는 Flappy Bird 복제다. 서브에이전트 하나는 슈퍼마리오 같은 배경을 만들고, 다른 하나는 게임과 어울리지 않는 새를 만든다. 마지막 에이전트가 이 둘을 맞춰야 한다. 원래 작업 설명을 둘 다에게 줘도 완전히 해결되지 않는다고 한다. 실제 대화는 여러 턴이고 도구 호출이 해석을 바꾸기 때문이다. 대안으로 단일 스레드 에이전트(컨텍스트가 이어짐), 이력을 줄여 주는 별도 압축 모델, 그리고 제한적인 서브에이전트를 든다. Claude Code의 서브에이전트는 주로 명확한 질문에 답하고 코드를 병렬로 쓰지 않아서 충돌이 적다고 이 글이 평가한다.

두 글이 같은 말을 하는 건 아니다. Anthropic은 맞는 일(조사)에는 멀티에이전트가 크게 낫다고 하고, Cognition은 쓰기·결정이 얽힌 일에는 조심하라고 한다. 나는 "읽기·조사는 나누고, 쓰기·결정은 한 곳에서" 정도로 받아들였다. 두 글을 읽고 직접 내린 요약이다.

문서가 정리한 선택 기준도 비슷하다.

- 서브에이전트: 출력이 길어서 메인에 두기 싫을 때, 도구 권한을 제한하고 싶을 때, 일이 독립적이고 요약으로 돌려줄 수 있을 때.
- 메인 대화: 자주 주고받으며 다듬어야 할 때, 여러 단계가 컨텍스트를 많이 공유할 때, 빠른 작은 수정일 때, 지연이 중요할 때(서브에이전트는 빈 상태로 시작하니 맥락을 모으는 시간이 든다).

## 쓸 때 걸리는 것들

위임 설명이 부실하면 일이 겹친다. Anthropic 글에 이런 사례가 있다. 어떤 서브에이전트는 2021년 자동차 반도체 위기를 조사하고, 다른 둘은 2025년 공급망을 똑같이 조사했다. 각 서브에이전트에게 목표, 출력 형식, 출처 지침, 작업 경계를 분명히 줘야 한다는 결론이다. 이건 서브에이전트에 넘기는 [프롬프트](#/post/ai-prompt)가 곧 전부라는 뜻이다. 서브에이전트는 메인의 대화를 못 보기 때문이다.

또 하나는 규모 조절이다. 초기 버전은 단순한 질문에도 서브에이전트를 50개 띄웠다고 한다. 해결은 규칙을 프롬프트에 박는 것이었다. 단순한 사실 찾기는 에이전트 1개에 도구 호출 3~10번, 직접 비교는 서브에이전트 2~4개에 각 10~15번, 복잡한 조사는 10개 이상까지 쓸 수 있다는 식이다.

## 흔한 오해

- 서브에이전트를 쓰면 토큰이 줄어든다: 메인 컨텍스트는 줄지만 전체 토큰은 늘어나는 경우가 많다. 위 15배 수치가 그 예다.
- 에이전트가 많을수록 똑똑하다: 일이 의존적이면 오히려 충돌한다.
- 서브에이전트도 내 대화를 안다: 일반 서브에이전트는 모른다. 메인 대화를 상속하는 건 포크(fork) 방식이다. 문서에는 포크가 부모 대화를 상속한다고만 나온다.
- 서브에이전트는 무한히 중첩된다: 문서 기준 기본값은 메인 아래 3층까지이고 환경변수로 바꿀 수 있다. 동시 실행 기본 상한은 20개다.

<details>
<summary>자세한 풀이: Claude Code 서브에이전트 파일 구조</summary>

문서에 나오는 서브에이전트는 YAML 프런트매터가 붙은 마크다운 파일이고, 본문이 시스템 프롬프트가 된다. 필수 필드는 `name`과 `description`뿐이다. Claude는 `description`을 보고 언제 위임할지 정한다. 이름을 직접 부르거나 `@`로 언급해도 되고, `claude --agent <name>`으로 세션 전체를 그 에이전트로 돌릴 수도 있다.

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices. Use proactively after code changes.
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

위 예시는 문서에 있는 것을 그대로 옮긴 것이고, 내가 실행해 본 건 아니다.

도구 제한은 `tools`(허용 목록)와 `disallowedTools`(차단 목록)로 한다. 차단이 먼저 적용되고 둘 다에 적힌 도구는 빠진다. 내장 서브에이전트로는 Explore(읽기 전용, 코드 검색), Plan(읽기 전용, 계획 모드 조사), general-purpose(모든 도구)가 있다. 저장 위치가 겹치면 조직 관리 설정 > `--agents` 플래그 > 프로젝트 `.claude/agents/` > 사용자 `~/.claude/agents/` > 플러그인 순으로 우선한다. 모델은 호출 때 지정한 값, 파일의 `model`, 환경변수 `CLAUDE_CODE_SUBAGENT_MODEL`, 메인 모델 순서로 정해진다.

서브에이전트마다 새 인스턴스가 만들어진다. 이어서 시키려면 `SendMessage`로 에이전트 ID나 이름을 지정해 재개한다. 재개된 에이전트는 전체 기록을 유지한다. Explore와 Plan은 한 번 쓰고 끝이라 재개할 수 없다고 문서에 나온다.

[하네스](#/post/ai-harness) 관점에서 보면, 서브에이전트를 띄우고 결과를 돌려받고 한도를 지키는 건 모델이 아니라 이 바깥 코드의 일이다. 이 연결은 내가 붙인 해석이다.
