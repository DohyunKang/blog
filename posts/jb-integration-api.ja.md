統合実装の単元は、独立したシステムをどのように接続し、その間を介してデータをどのような形式でやり取りするかを問います。用語が多く見えても、「中間で何者かが何を代行しているか」と整理すれば、ほとんどが解けます。

## この単元で問われること

単元は大きく 3 つの塊に分けられます。

| 塊 | 核心的な質問 | よく出てくる用語 |
|---|---|---|
| モジュール連携 | システム同士をどのように繋ぐか | 直接連携、間接連携、EAI、ESB |
| インターフェース | 何をどのようにやり取りするかの約束は何か | インターフェース仕様、送受信項目、エラー処理 |
| データフォーマット | やり取りする文書の形状は | JSON, XML |

試験では「次の説明に該当する用語は？」といった定義のマッチング問題が多いです。そのため、用語を一つずつ一行の定義とセットにして暗記しておくのが先です。試験日程と受験料は公式サイトで確認してください。

## 連携が必要な理由

企業には ERP、CRM、給与計算などのシステムが個別に動いています。ウィキペディアの EAI 項目では、このような状態を互いに孤立した「自動化の島」と表現し、EAI をそれらの間でのデータと業務フローを共有できるようにするミドルウェアとして説明しています。

システムが二つや三つの場合のみなら、互いに直接繋げば済みます。問題は数が増えた時です。直接繋ぐ線はシステム数が増えるにつれて急速に増え、一つのシステムの形式が変わると、そのシステムと接続されているすべての線を修正する必要があります。中間に一つを挟む構造は、この負担を減らすために登場しました。

## 連携構造の 3 つ

| 構造 | 形状 | 特徴 |
|---|---|---|
| ポイントツーポイント (Point-to-Point) | システム同士が 1 対 1 で直接接続 | シンプルだが、接続が増えると管理が困難になる |
| ハブアンドスポーク (Hub & Spoke) | 中央のハブに各システムが接続 | 中央から統制する。ハブが詰まると全体に影響を受ける |
| バス (Bus) | 共通バスに各システムが接続される | システムがバスに挿入される形で繋がっている |

ウィキペディアの EAI 項目には 2 つのトポロジーが登場します。ハブアンドスポークは EAI が中央にあり、アプリケーションがスポークとして接続される構造で、バスは EAI がバスそのものか、既存のメッセージ指向ミドルウェア内のモジュールとして回る構造です。ポイントツーポイントは EAI を使わず直接繋ぐ方式であり、比較用に覚えておけば十分です。

[詳しく → ソフトウェアアーキテクチャ](#/post/jb-architecture-pattern)

## EAI

EAI (Enterprise Application Integration) は、企業内の複数のアプリケーションを接続し、データと業務プロセスを共有できるようにする方式です。文書に登場する構成要素は以下の通りです。

- ハブまたはバス：中央でメッセージのやり取りを行う部分
- アダプター：各アプリケーションをハブに取り付け、データを共通形式に変換する部分
- 統合モジュール：特定のイベントを購読して通知を処理する部分

パターンは 2 つに分けられます。仲介 (Mediation) は、一つのアプリケーションでイベントが発生すると、EAI がブローカーとして関連するアプリケーションに変更を伝える方式です。連合 (Federation) は、EAI が外部要求の窓口となり、内部のアプリケーションと代わりに通信する方式です。

複数のシステムにわたる作業の一貫性は、2 段階コミットや補償トランザクションで整えられていると言われています。

[詳しく →正規化とトランザクション](#/post/jb-normalization-transaction)

## ESB

ESB (Enterprise Service Bus) は、サービス指向アーキテクチャ (SOA) でアプリケーションを接続する通信システムであり、異なるシステムを統合することが主な用途です。ウィキペディアでは、ESB を EAI のバスモデルを実装する一般的な方式として紹介しています。理想的には、アプリケーション同士が直接接触していたことを代替し、すべての通信がバスを経由するようにします。

ESB の核心的な機能は 4 つに整理できます。

| 機能 | 行うこと |
|---|---|
| ルーティング | メッセージを適切なサービスに送り、フローを監視・制御する。内容やルールに応じて分岐して送ることができる |
| 変換 | 受け取る側が読み取れる形式に変えてメッセージを変換する |
| プロトコル変換 | 異なる通信規約を使用するサービス同士を繋ぐ |
| メッセージキューイング | メッセージとイベントを並べて順番に伝える |

<details>
<summary>EAI と ESB を一言で区別する</summary>

EAI は「企業内のアプリケーションを統合する」という目的に近い言葉であり、ESB はそれをサービスバスという形状で実装した方式に近い言葉です。試験ではハブ中心であれば EAI のハブアンドスポーク、サービス指向構造とバスが登場すれば ESB 側と読み替えるのが概ね合っています。ただし問題文によって両者を同じカテゴリにまとめる場合もあるため、選択肢に両方の用語が同時に登場する場合は説明文を最後まで読むのが安全です。

</details>

## インターフェース仕様

システム同士を連携させるためには約束が必要であり、その約束を記述した文書がインターフェース仕様です。通常含まれる内容は以下の通りです。

- どのシステムが送信し、どのシステムが受信するか
- 送受信する項目の名前、データ型、長さ、必須かどうか
- 呼び出し方式と周期（リアルタイムかバッチか）
- エラーが発生した際の処理方法

項目の解釈が一つでも異なると連携が即座に破綻するため、このドキュメントは短くても漏れなく記述することが重要です。試験では、仕様にどのような項目が含まれるかを問う問題や、連携後にデータが正しくやり取りされたかを確認するテスト段階と組み合わされます。

[詳細 → ソフトウェアテスト](#/post/jb-testing)

## データフォーマット：JSON と XML

送受信されるデータの形式は、JSON と XML が代表的です。同じ注文情報を両方の方式で記述すると以下のようになります。

```json
{"orderId": 101, "items": [{"sku": "A1", "qty": 2}], "paid": true}
```

```xml
<order id="101"><item sku="A1" qty="2"/><paid>true</paid></order>
```

上記の 2 つを Python で直接読み込んでみたところ、JSON は `json.loads` を使用して辞書型に変換され、`items[0].qty` が 2 となり、XML は `ElementTree` を使用して読み込み、`item` の `qty` 属性が 2 として出力されました。閉じタグが一致しない XML（`<a><b></a>`）は、パース段階でエラーが発生しました。

### JSON

json.org では、JSON を「人間が読み書きしやすく、機械が解釈・生成しやすい、言語に依存しない軽量なテキストデータ交換形式」と説明しています。構造は 2 つあります。

- オブジェクト：名前のペアと値の集合。中括弧で囲み、名の後にコロンを付け、ペアはカンマで区切ります。順序のない集合です。
- アレイ：値を順序通りに集めたもの。角括弧で囲み、カンマで区切ります。

値は文字列（ダブルクォート）、数値、true/false、null、そしてオブジェクトとアレイ（ネスト可能）です。

### XML

W3C の XML 1.0 ドキュメントによると、XML は SGML の制限された部分集合であり、ウェブ上で構造化データをやり取りしやすく処理することを目的としています。試験で問われる概念は主に 2 つです。

| 概念 | 意味 |
|---|---|
| 正則 (well-formed) | ルート要素が一つであり、要素が適切にネストされているなど文法規則に従ったドキュメント |
| 有効 (valid) | 正則であり、関連付けられた DTD で定められた構造も満たすドキュメント |

開始タグと終了タグはペアをなし、属性は開始タグ内の名義 - 値のペアで、順序には意味がなく、同じタグ内では名前が重複することはできません。DTD は許可される要素と属性の構造を定義する部分です。

<details>
<summary>JSON と XML の比較表</summary>

| 項目 | JSON | XML |
|---|---|---|
| 構造 | オブジェクトとアレイ | タグで囲まれた要素ツリー |
| 属性 | なし、名義 - 値で表現 | 開始タグの属性 |
| 構造検証 | ドキュメント自体の規則は文法レベル | DTD で有効性検証が可能 |
| 形式 | 短く記述する傾向 | タグが繰り返されるため長め |

文字数の違いは上記の例のように同じ情報を記述すれば一目でわかりますが、どちらが常に優れているとは限りません。試験では両形式の定義と構造の違いを区別して問われます。

</details>

## よく出るパターン

- 用語マッチング：説明文を与えられ、EAI、ESB、ハブ＆スポーク、バスのうちから選ぶ
- 機能区分：ルーティング、変換、プロトコル変換、メッセージキューイングの説明に合うものを探す
- フォーマット読み取り：JSON または XML の例題を与えられ、値を読み取るか正しい文法を選ぶ
- 正則と有効の区別：DTD の有無で分かれる問題

解き方は単純です。文中に「中央」「ハブ」があればハブ＆スポーク、「サービス」「バス」に変換・ルーティングが現れれば ESB と読み取ります。フォーマットは中括弧なら JSON、タグなら XML とまずフィルタして詳細に入ります。過去問はキューネットなどの公式公開資料で直接解くのがおすすめです。
