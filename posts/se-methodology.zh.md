[概述](#/post/cs-sw-engineering) 中仅简要提及了瀑布模型和敏捷开发。本文将深入探讨方法论究竟规定了什么，以及瀑布、螺旋、Scrum、XP 和 Kanban 之间的具体区别。

## 方法论规定的内容

方法论最终确定了三点：将工作划分为何种单位、验证与修正的频率、以及谁对什么负责。阶段名称（需求、设计、实现、测试）几乎相同。差异在于：该阶段是只执行一次，还是多次短周期执行，亦或是完全摒弃阶段框架而视为流程。

| | 执行次数 | 验证周期 | 核心关注点 |
|---|---|---|---|
| 瀑布模型 | 一次 | 阶段结束时 | 计划与文档 |
| 螺旋模型 | 多次 | 每轮循环时 | 风险 |
| Scrum | 每个 Sprint | 每个 Sprint | 固定周期与角色 |
| XP | 极短 | 以代码为单位持续进行 | 编码实践 |
| Kanban | 无固定周期 | 每项任务完成时 | 流程与进行中数量 |

## 瀑布模型：原始论文截然不同

“瀑布”这一名称及自上而下的图示源自 1970 年 Winston Royce 的论文。然而，根据维基百科的整理，Royce 并未直接推荐这种顺序方式。他指出测试仅位于末端的结构既危险又会导致失败，并增加了若干降低风险的步骤。他最终绘制的模型中包含了从代码测试回溯到设计、再从设计回溯到需求的反馈机制。同时也涵盖了充分保留文档、规划测试以及让客户参与等内容。

因此，“瀑布 = 不可回头的模型”这一形象更多是单张插图传播的结果，而非原始论文的本意。在需求固定且变更较少的工作中，该模式至今仍适用。

## 螺旋模型：风险决定顺序

Barry Boehm 于 1986 年提出的螺旋模型以风险为中心。每轮循环需完成四项任务：

1. 明确利益相关者的目标
2. 寻找并评估实现该目标的替代方案
3. 识别所选方案的潜在风险并加以消除
4. 获得利益相关者的批准并就下一轮达成共识

若风险较大，则制作原型；若风险较小，也可采用瀑布式方法。维基百科的解释中提到一种观点：将瀑布视为螺旋模型的特例。即当需求稳定且风险较低时，只需一轮循环的螺旋模型便等同于瀑布模型。反之，若需求不稳定却反复多次执行瀑布流程，虽看似螺旋模型，但 Boehm 警告这实则危险。螺旋模型的核心不在于“重复”，而在于“根据风险选择下一步行动”。

## Scrum：固定周期与三项承诺

[Scrum 指南](https://scrumguides.org/scrum-guide.html) 建立在经验主义之上，由透明度（工作与过程可见）、检查（频繁验证）和适应（发现问题立即修正）三大支柱支撑。Sprint 是时长不超过一个月的固定周期，结束后立即开始下一个 Sprint。

指南中值得注意的一点是：每项产出物都附带一项承诺。

| 产出物 | 附带承诺 |
|---|---|
| 产品待办列表 (Product Backlog) | 产品待办事项 (Product Goal) |
| Sprint 待办列表 (Sprint Backlog) | Sprint 目标 (Sprint Goal) |
| 增量 (Increment) | 完成定义 (Definition of Done) |

不满足“完成定义”的项目不得计入增量。这是防止将“几乎完成”视为进度的机制。Sprint 目标仅固定单一目标，允许为实现该目标的具体任务进行调整。在角色中，产品负责人（Product Owner）是单人而非委员会，且唯有此人有权取消 Sprint。但这仅限于 Sprint 目标不再适用时。

<details>
<summary>Scrum 指南中的价值观与角色职责</summary>

价值观包括承诺、专注、开放、尊重和勇气五项。整个 Scrum 团队对每个 Sprint 产生有价值且有用的增量负责。开发人员创建 Sprint 待办列表、遵守完成定义并每日调整计划。Scrum Master 进行教练以确保 Scrum 正常运行，清除障碍并确保事件按时结束。

## XP：深入代码层面

若 Scrum 规定周期与角色，则 XP（极限编程）规定编码方式。根据维基百科的整理，其价值观包括沟通、简单、反馈、勇气、尊重（第二版新增），实践法则有十二项。

- **快速反馈**：结对编程、计划游戏、测试驱动开发、全员参与
- **持续流动**：持续集成、重构、小版本发布
- **共同理解**：编码规范、集体代码所有权、简单设计、系统隐喻
- **以人为本**：可持续的开发速度

Scrum 和 XP 并非竞争关系，而是处于不同的层次。Scrum 讨论的是“如何组织工作”，而 XP 则关注“如何编写代码”，因此两者经常结合使用。测试驱动开发和持续集成分别在 [测试与质量](#/post/se-testing) 以及 [版本管理与 CI/CD](#/post/se-cicd) 中单独讨论。

## 看板：无固定周期，计数管理

[看板指南](https://kanbanguides.org/english/)将看板定义为“优化价值流经过程的策略”。其实践包含三个方面：定义工作流程并使其可视化、积极管理进行中项、以及改进流程。

不同于 Sprint 等固定周期，这里设定的是以下内容：

- 开始时间点、结束时间点及中间状态
- 如何控制进行中项数量（WIP）
- 服务水平期望值（SLE）：基于历史周期时间预测的指标，例如“85% 的项目将在 N 天内完成”

通过控制 WIP，自然就会形成拉式（pull）系统。只有当进行中项数量降至设定水平以下、出现空位时，才启动新工作。看板指南强调必须使用四个测量指标：WIP（已开始但未完成的项目数）、吞吐量（单位时间内完成的项目数）、工作项年龄（进行中项目自开始以来流逝的时间）以及周期时间（从开始到结束所花费的时间）。

### 减少 WIP 会带来什么变化

为了直观地理解指南中关于控制 WIP 的理由，我用 Python 运行了一个非常简单的模型。团队容量为每天 3 人日，共有 20 个每项需 3 人日的工作项。工作项的容量被平均分配给进行中项，且仅允许在 WIP 限额范围内同时启动新项目。

```python
def run(wip, n=20, size=3, cap=3):
    remaining = {}
    start, done = {}, {}
    nxt, day = 0, 0
    while len(done) < n:
        while len(remaining) < wip and nxt < n:   # 자리가 나야 시작
            remaining[nxt] = size; start[nxt] = day; nxt += 1
        day += 1
        share = cap / len(remaining)              # 진행 중인 항목에 용량을 똑같이 나눔
        for i in list(remaining):
            remaining[i] -= share
            if remaining[i] <= 1e-9:
                del remaining[i]; done[i] = day
    ct = [done[i] - start[i] for i in range(n)]
    return day, sum(ct) / n, n / day

for w in (1, 3, 6, 20):
    d, ct, th = run(w)
    print(w, d, round(ct, 2), round(th, 2))
```

执行结果如下：

| WIP 限制 | 总耗时 | 平均周期时间 | 吞吐量 |
|---|---|---|---|
| 1 | 20 天 | 1.00 天 | 1.00 个/天 |
| 3 | 20 天 | 2.90 天 | 1.00 个/天 |
| 6 | 20 天 | 5.60 天 | 1.00 个/天 |
| 20 | 20 天 | 20.00 天 | 1.00 个/天 |

吞吐量和总耗时保持不变，但周期时间几乎与 WIP 成正比地增加。虽然全部完成的时间相同，但如果将 WIP 设为 20，则所有项目都将在最后一天才完成；而逐个处理时，第一个项目只需一天即可交付。当 WIP 为 3 时平均值为 2.9 天，这是因为随着最后剩余项目减少，WIP 降至 3 以下的区间所致。该模型未考虑容量浪费或任务切换成本。实际上，同时启动的项目越多，切换成本越高，吞吐量也会下降，但这超出了当前代码所展示的范围。

## 常见误解

- Scrum 就是敏捷吗？Scrum 是践行敏捷原则的框架之一。Kanban 和 XP 也属于同一阵营。
- Kanban 就是使用看板板吗？指南指出，看板板是将工作流程定义可视化的结果产物。若仅张贴看板板而缺乏流程定义和 WIP 控制，则难以称之为 Kanban。
- 螺旋模型是瀑布模型的多次重复吗？据称 Boehm 本人曾明确表示反对这种看法。
- 瀑布模型没有反馈吗？Royce 的最终模型中实际上包含了反馈回路。
