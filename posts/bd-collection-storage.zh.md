## 收集来源与数据形态

首先从两个方面进行区分：数据来源是哪里，以及数据的形态是什么。

| 标准 | 分类 | 示例 |
| --- | --- | --- |
| 来源 | 内部数据 | 公司数据库中的订单表、客户表、服务日志 |
| 来源 | 外部数据 | 公共数据、社交媒体、网页 |
| 形态 | 结构化 | 行列固定的表格（RDB、CSV） |
| 形态 | 半结构化 | 有结构但非固定表格（JSON、XML、日志） |
| 形态 | 非结构化 | 文本正文、图像、视频、音频 |

内部数据易于获取且质量在一定程度上可控；外部数据虽然容易获取，但格式和质量参差不齐，需要花费成本进行整理。考试中常出现要求根据示例判断“是内部还是外部”、“是结构化还是半结构化”的题型。只要牢牢记住"JSON 属于半结构化”这一点，就能答对一半的题目。

收集包含个人信息的數據时需注意的事项，已在 [详情 → 大数据概览与应用](#/post/bd-overview) 中单独整理。

## 收集方式：批处理与流处理

收集方式主要分为一次性批量获取和实时持续接收两类。

批处理是在指定时间将数据集中后统一获取，例如每天复制一次整个订单表。这种方式实现简单，适合大规模数据处理，但在两次批处理之间产生的变化无法感知。

流处理是即时接收产生的数据，适用于传感器数值、点击日志等持续生成的数据。该领域的代表性工具是 Apache Kafka。Kafka 的介绍文档将事件流处理定义为：从数据库、传感器、应用等来源实时收集数据，长期存储，按需或延迟处理，并发送至其他系统。相关术语在考试中也很重要。

| 术语 | 含义 |
| --- | --- |
| 主题 (topic) | 用于存储事件的命名集合，类似于文件夹 |
| 生产者 (producer) | 发送事件的一方 |
| 消费者 (consumer) | 读取事件的一方，必要时可重新读取 |
| 分区 (partition) | 对主题进行划分的单元。相同键的事件进入同一分区，且在该分区内保持顺序 |
| 保留 (retention) | 针对每个主题设定的、删除旧事件的持续时间 |

核心在于发送方和接收方通过主题相互隔离。因此，即使收集器变慢也不会阻塞发送方，同时可以有多个消费者。

[详情 → 异步处理与队列](#/post/be-async-queue) 从后端视角对相同结构进行了阐述。

## ETL 与网络爬虫

ETL 是抽取 (Extract)、转换 (Transform)、加载 (Load) 的缩写。即从来源提取数据，将其转换为可用格式，然后加载到目的地。顺序至关重要。若先加载后转换，则称为 ELT。考试中常询问 ETL 三个字母分别代表什么，以及在哪个阶段进行去重和格式统一。答案是转换阶段。

我亲自运行了一个小示例：读取 CSV 文件、删除重复项、填充缺失价格，然后存入 SQLite 并使用 SQL 进行聚合。

```python
import pandas as pd, sqlite3, io

src = pd.read_csv(io.StringIO("id,name,price\n1,a,1000\n2,b,\n3,a,1000\n3,a,1000\n"))
# Extract: 위에서 읽은 src
# Transform: 중복 제거, 빈 값 처리
t = src.drop_duplicates().assign(price=lambda x: x.price.fillna(0).astype(int))
# Load: DB에 적재
con = sqlite3.connect(":memory:")
t.to_sql("product", con, index=False)
print(pd.read_sql("select name, sum(price) s, count(*) n from product group by name", con).to_dict("records"))
print(len(src), len(t))
```

输出结果为 `[{'name': 'a', 's': 2000, 'n': 2}, {'name': 'b', 's': 0, 'n': 1}]` 和 `4 3`。行数从 4 行变为 3 行。将原本价格为空的 b 填充为 0 是为了演示示例。实际上是否将空值填充为 0 取决于分析目的，相关内容在 [详情 → 数据预处理](#/post/bd-preprocessing) 中已讨论。

网络爬虫是一种通过程序自动下载网页并提取所需部分的数据收集方式。适用于获取外部数据中未以结构化形式提供的内容。从考试角度看，只需掌握“自动收集 Web 文档”这一定义，以及常识性的“若有公开 API，则优先使用 API 而非爬虫，更稳定”即可。由于各网站的利用条款和采集范围限制不同，实际操作前务必先查阅相关规定。

## 存储：选择适合数据形态的容器

存储技术需根据数据形态和使用方式进行选择。

| 存储库 | 适合的数据类型 | 特点 |
| --- | --- | --- |
| RDB | 结构化、关系明确的数据 | 先定义模式，使用 SQL 查询。事务性强（[详情 → 关系型数据库与 SQL](#/post/db-rdb-sql)） |
| NoSQL | 半结构化、非结构化、模式频繁变化的数据 | 种类繁多（[详情 → NoSQL 类型与选择](#/post/db-nosql)） |
| 分布式文件系统 (HDFS) | 超大文件 | 分割后存储于多台服务器 |

### HDFS

从 Hadoop 官方文档的 HDFS 设计说明中，仅摘录了与考试相关的部分。

- NameNode（主节点）负责管理文件命名空间（namespace），以及每个块位于哪个 DataNode。
- DataNode 负责实际存储数据块，并响应读写请求。
- 采用“一次写入、多次读取”（write-once-read-many）模型。关闭后仅支持追加（append）和截断（truncate）操作。
- 优先考虑高吞吐量而非低延迟，专为批处理设计。
- 块大小较大。文档通常提及 128MB，但可为每个文件单独设置。
- 副本数通常为 3 个，创建文件时设定，后续可修改。
- 将计算移至数据侧比移动数据更利于减少网络负担。

只需记住“NameNode 管理元数据，DataNode 存储实际数据”这一表述即可避免混淆。此外，HDFS 并非用于频繁修改小文件，而是用于一次性写入并多次读取大文件，这一点可用于排除错误选项。

### NoSQL

NoSQL 并非单一技术，而是一类技术的集合。通常分为键值型、文档型、列族型和图型四类。各类的使用场景已在上述链接中说明，此处仅重点介绍文档型。

MongoDB 将数据以 BSON 文档形式存储，并指出同一集合中的文档无需具有相同的字段或数据类型。添加字段时无需重写现有文档或执行迁移。设计上支持在值内嵌套文档或数组，遵循“共同访问的数据应一起存储”的原则；必要时也可通过模式验证强制结构约束。考试中常将“模式灵活”列为 NoSQL 的典型特征，本文档即为依据。

<details>
<summary>RDB 与 NoSQL 如何选择（总结）</summary>

- 若重视表间关系与数据一致性，则选择 RDB。
- 若结构各异或频繁变化，则选择文档型等 NoSQL。
- 并非只能二选一，同一服务内可混合使用。
- 考试通常以“从特征描述中选出正确项”的形式出现，因此可记忆：RDB 对应固定模式、SQL、事务；NoSQL 对应灵活模式、水平扩展。
</details>

## 质量管理：检查四项指标

在写入数据前需评估其质量。概念上包括完整性（是否存在缺失值）、唯一性（是否存在重复）、有效性（是否在允许范围或格式内）和一致性（相同对象是否一致表示）等项目。不同资料对名称的称呼略有差异，需根据选项含义进行判断。

已亲自验证这四项在代码中各仅需一行实现：

```python
import pandas as pd, io

raw = io.StringIO("""id,age,city,amount,date
1,25,Seoul,1200,2026-01-03
2,,Busan,800,2026-01-04
2,,Busan,800,2026-01-04
3,41,seoul,-50,2026-01-05
4,200,Daegu,3000,2026/01/06
5,33,Incheon,,2026-01-07
""")
df = pd.read_csv(raw)

print(df.isna().mean().round(2).to_dict())          # 완전성: 열별 결측 비율
print(df.duplicated().sum())                         # 유일성: 중복 행 수
print(df['city'].str.lower().str.strip().value_counts().to_dict())  # 일관성: 표기 통일 후 집계
print(((df.age < 0) | (df.age > 120)).sum(), (df.amount < 0).sum())  # 유효성: 범위 밖
d = pd.to_datetime(df['date'], errors='coerce', format='%Y-%m-%d')
print(d.isna().sum())                                # 유효성: 날짜 형식 불일치
```

输出结果如下：

| 检查项 | 结果 |
| --- | --- |
| 列缺失比例 | age 0.33, amount 0.17, 其余 0 |
| 重复行 | 1 |
| 统一 city 拼写后聚合 | seoul 2, busan 2, daegu 1, incheon 1 |
| 超出年龄范围 / 负金额 | 1 / 1 |
| 日期格式不一致 | 1 |

`Seoul`与`seoul`在视觉上代表同一城市，但若直接聚合会视为不同值；统一为小写后，seoul 才被正确计为 2。这属于一致性问题。年龄 200 和负金额虽存在数值，但逻辑不合理，因此不属于完整性问题，而是有效性问题。日期 `2026/01/06`因与其他行的分隔符不同而被判定为格式不匹配。

此处需特别区分：本阶段旨在发现问题并计数；如何处理缺失值或异常值属于预处理环节。

## 常见题型

- 以结构化、半结构化、非结构化数据为例进行分类（如 JSON、XML、日志属于半结构化）。

- HDFS 中 NameNode 与 DataNode 的角色，以及大块存储和副本的必要性。
- RDB 与 NoSQL 的特征对比。
- 将质量管理各项的名称与其含义进行关联。

## 解题技巧

术语问题要从选项中先抓住关键词。看到“实时”就选流处理（Streaming），看到“管理元数据”就选 NameNode，看到“模式灵活”就选 NoSQL，看到“相同即一致”就选一致性。历年真题每年选项会略有变化，因此建议按概念分别整理成“出现这个词就选这个”的速记单，能节省时间。
