가상 메모리는 주소 변환 표(페이지 테이블) 위에 세워진 장치라서, 그 표가 얼마나 크고 얼마나 느린지를 따라가면 TLB, 다단계 테이블, 페이지 교체, 스래싱이 차례로 나온다. 운영체제 전체 그림은 [개요](#/post/cs-os)에서 봤고, 여기서는 메모리 쪽만 안으로 들어간다.

## 변환이 하는 일

프로세스가 내는 주소는 가상 주소이고, 이걸 물리 주소로 바꾸는 일은 매 메모리 접근마다 일어난다. 페이징에서는 주소를 두 토막으로 쪼갠다. 앞부분이 가상 페이지 번호(VPN), 뒷부분이 페이지 안 위치(오프셋)다. VPN으로 페이지 테이블을 찾아 물리 프레임 번호(PFN)를 얻고, 오프셋은 그대로 붙인다.

OSTEP이 쓰는 작은 예시(64바이트 주소 공간, 페이지 16바이트)를 그대로 돌려 봤다. 페이지 0, 1, 2, 3이 프레임 3, 7, 5, 2에 놓여 있다고 두면 이렇다.

| 가상 주소 | VPN | 오프셋 | PFN | 물리 주소 |
|---|---|---|---|---|
| 0 | 0 | 0 | 3 | 48 |
| 21 | 1 | 5 | 7 | 117 |
| 50 | 3 | 2 | 2 | 34 |

```python
PAGE = 16
pt = {0: 3, 1: 7, 2: 5, 3: 2}
def tr(va):
    vpn, off = divmod(va, PAGE)
    return pt[vpn] * PAGE + off
print(tr(0), tr(21), tr(50))   # 48 117 34
```

페이지 테이블은 프로세스마다 하나씩 있다. 표의 한 칸(PTE)에는 프레임 번호 말고도 몇 가지 비트가 들어간다. OSTEP 설명으로는 이런 것들이다.

- valid: 이 번역이 유효한가. 안 쓰는 영역을 invalid로 표시해 두면 물리 프레임을 안 줘도 되고, 거기에 접근하면 OS로 trap이 걸린다.
- 보호(read/write/execute): 허용되지 않은 방식으로 접근하면 역시 trap.
- present: 지금 RAM에 있는가, 디스크로 내려갔는가.
- dirty: 메모리에 올라온 뒤 수정됐는가.
- reference(accessed): 최근에 접근됐는가. 페이지 교체에서 쓰인다.

## 표가 너무 크다

32비트 주소 공간에 페이지가 4KB라면 주소는 20비트 VPN과 12비트 오프셋으로 나뉜다. 번역이 2^20개, 약 백만 개이고, PTE를 4바이트로 잡으면 프로세스 하나의 페이지 테이블이 4MB다. OSTEP은 프로세스 100개면 400MB가 번역 정보만으로 든다고 짚는다.

```python
print(2**32 // 4096, (2**32 // 4096) * 4)   # 1048576 4194304
```

대부분의 주소 공간은 비어 있다. 코드와 힙은 한쪽 끝, 스택은 반대쪽 끝에 있고 가운데는 invalid인데도 선형 테이블은 그 칸을 다 들고 있다. 페이지를 키우면 표는 줄지만(4배 키우면 정확히 4배 준다) 페이지 안에서 쓰지 않고 버려지는 공간, 즉 내부 단편화가 커진다. 그래서 대부분의 시스템은 4KB나 8KB 같은 작은 페이지를 쓴다.

이 문제를 푸는 방식(다단계 테이블, 세그먼트 혼합)은 아래 접기에 적었다.

<details>
<summary>다단계 페이지 테이블, 그리고 세그먼트와 섞은 방식</summary>

다단계 테이블은 페이지 테이블 자체를 페이지 크기로 잘라서, 통째로 invalid인 조각은 아예 할당하지 않는다. 어느 조각이 있는지는 페이지 디렉터리가 들고 있고, 디렉터리 항목(PDE)은 최소한 valid 비트와 프레임 번호를 가진다. PDE가 valid라는 건 그 조각 안에 valid인 PTE가 하나 이상 있다는 뜻이다.

장점은 표 공간이 실제로 쓰는 주소 공간에 비례한다는 것, 그리고 표의 조각이 페이지 하나에 딱 들어맞아서 OS가 다음 빈 페이지를 가져다 쓰면 된다는 것이다. 대가도 있다. TLB 미스가 나면 디렉터리와 PTE를 각각 읽어야 해서 메모리를 두 번 읽는다. OSTEP은 이걸 시간과 공간의 맞바꿈이라 부른다.

이보다 먼저 나온 방식이 세그먼트와 페이징의 혼합이다. 주소 윗비트로 세그먼트(코드, 힙, 스택)를 고르고, 세그먼트마다 base와 bounds를 두어 그 세그먼트 전용 선형 테이블을 가리킨다. bounds에는 그 세그먼트의 최대 유효 페이지 수가 들어가서 사이의 빈 구간이 표를 차지하지 않는다. 하지만 힙이 크면서 듬성듬성 쓰이면 낭비가 남고, 표가 제각각 길이가 되어 빈 공간 찾기가 어려운 외부 단편화가 다시 생긴다. 이런 이유로 다단계 쪽이 이어졌다고 한다.
</details>

## 느리다: TLB

변환을 하려면 페이지 테이블을 읽어야 하고, 그 테이블도 메모리에 있다. 접근 하나가 메모리를 두 번 건드리게 된다. 이걸 줄이려고 하드웨어에 최근 번역을 담아 두는 작은 캐시가 있다. TLB(translation-lookaside buffer)다.

흐름은 단순하다. 주소가 오면 VPN으로 TLB를 먼저 본다. 있으면(히트) 곧바로 물리 주소를 만든다. 없으면(미스) 페이지 테이블을 읽어 번역을 얻고 TLB에 채운 다음 다시 시도한다.

TLB가 잘 듣는 이유는 지역성이다. 시간 지역성은 방금 쓴 걸 또 쓴다는 것, 공간 지역성은 x 근처를 쓰면 그 다음도 근처라는 것이다. OSTEP 예시는 정수 배열 10개를 차례로 읽는 경우다. 원소들이 한 페이지에 촘촘히 박혀 있어서 결과가 miss, hit, hit, miss, hit, hit, hit, miss, hit, hit이고 히트율이 70%다. 처음 읽는 배열인데도 히트가 나온다.

평균 접근 시간은 히트율에 따라 이렇게 움직인다. 숫자는 설명용 가정이다(TLB 조회 1, 메모리 접근 100, 미스 때 테이블 읽기 한 번 더).

```python
mem, tlb = 100, 1
for hr in (0.99, 0.9, 0.5):
    print(hr, tlb + hr * mem + (1 - hr) * 2 * mem)
# 0.99 102.0 / 0.9 111.0 / 0.5 151.0
```

프로세스를 바꿀 때 TLB가 문제다. 앞 프로세스의 번역은 다음 프로세스에겐 의미가 없다. 한 방법은 컨텍스트 스위치마다 TLB를 비우는 것이다. 안전하지만 프로세스가 다시 돌 때마다 미스를 새로 겪는다. 그래서 일부 하드웨어는 TLB 항목에 ASID(주소 공간 식별자)를 붙여 프로세스끼리 TLB를 같이 쓰게 한다. ASID는 PID처럼 쓰이지만 비트 수가 더 적다(OSTEP 예로 8비트 대 32비트). 스위치 자체가 어떻게 일어나는지는 [프로세스와 스레드](#/post/os-process-thread), TLB가 속한 계층 구조는 [메모리 계층과 캐시](#/post/ca-memory-hierarchy)에서 이어 본다.

## 메모리가 모자라면: 교체 정책

present 비트가 0인 페이지에 접근하면 페이지 폴트가 난다. OS가 디스크에서 그 페이지를 가져와야 하는데 빈 프레임이 없으면 하나를 내보내야 한다. 누굴 내보내느냐가 교체 정책이고, 개요에서 FIFO와 LRU를 간단히 비교했으니 여기서는 기준점인 최적 정책과 실제 구현에서 쓰는 근사를 본다.

최적 정책은 앞으로 가장 늦게 쓰일 페이지를 내보내는 것이다. Belady가 보인 바로는 미스가 가장 적다. 미래를 알아야 하니 실제로 만들 수는 없고, 새 정책이 얼마나 좋은지 재는 자(기준선)로 쓴다.

OSTEP이 쓰는 참조열 0,1,2,0,1,3,0,3,1,2,1을 프레임 3개로 돌렸다.

```python
def opt(refs, f):
    mem = []; h = 0
    for i, r in enumerate(refs):
        if r in mem: h += 1; continue
        if len(mem) == f:
            def nxt(p):
                try: return refs.index(p, i + 1)
                except ValueError: return 10**9
            mem.remove(max(mem, key=nxt))
        mem.append(r)
    return h

def fifo(refs, f):
    mem = []; h = 0
    for r in refs:
        if r in mem: h += 1; continue
        if len(mem) == f: mem.pop(0)
        mem.append(r)
    return h

def lru(refs, f):
    mem = []; h = 0
    for r in refs:
        if r in mem: h += 1; mem.remove(r)
        elif len(mem) == f: mem.pop(0)
        mem.append(r)
    return h

def clock(refs, f):
    fr = [None] * f; use = [0] * f; hand = 0; h = 0
    for r in refs:
        if r in fr: h += 1; use[fr.index(r)] = 1; continue
        while fr[hand] is not None and use[hand]:
            use[hand] = 0; hand = (hand + 1) % f
        fr[hand] = r; use[hand] = 1; hand = (hand + 1) % f
    return h

t = [0,1,2,0,1,3,0,3,1,2,1]
print([fn(t, 3) for fn in (opt, fifo, lru, clock)])   # [6, 4, 6, 4]
```

11번 접근 중 히트가 최적 6번(54.5%), FIFO 4번(36.4%), LRU 6번, 클록 4번이다. FIFO의 36.4%는 OSTEP이 같은 예시에서 든 수치와 같다. 페이지 0을 여러 번 썼는데도 FIFO는 먼저 들어왔다는 이유만으로 내보낸다.

LRU는 가장 오래 안 쓴 페이지를 내보낸다. 접근 기록을 매번 정렬해 두는 건 비싸서 실제 시스템은 근사를 쓴다. 하드웨어가 페이지에 접근할 때마다 use 비트를 1로 세우고, 0으로 내리는 건 OS 몫이다. 클록 알고리즘은 페이지들을 원형 리스트로 놓고 시계바늘을 돌린다. 바늘이 가리킨 페이지의 use가 1이면 0으로 내리고 다음으로 넘어가고, 0이면 그 페이지를 내보낸다. 전체를 매번 훑지 않아도 되는 게 장점이다. 위 참조열에서는 클록이 FIFO와 같은 4번이었는데, 이 짧은 입력 하나로 우열을 말할 수는 없다.

한 가지 더 있다. 수정된(dirty) 페이지는 내보내려면 디스크에 써야 하고 그게 비싸다. 안 바뀐(clean) 페이지는 프레임을 그냥 재사용하면 된다. 그래서 일부 VM 시스템은 clean 쪽을 우선 내보낸다. 이게 dirty 비트가 있는 이유다.

## 스래싱

루프를 도는 프로그램에서 정책이 얼마나 극단적으로 갈리는지 돌려 봤다. 페이지 5개를 0,1,2,3,4 순서로 20번 반복하는 100번 접근이다.

```python
loop = list(range(5)) * 20
for f in (3, 4, 5):
    print(f, lru(loop, f), fifo(loop, f), opt(loop, f))
# 3 0 0 48
# 4 0 0 72
# 5 95 95 95
```

프레임이 5개면 히트가 95번(처음 5번만 미스)인데, 4개로 한 칸만 줄여도 LRU와 FIFO는 히트가 0이다. 매번 바로 다음에 쓸 페이지를 방금 내보낸 셈이다. 같은 입력에서 최적은 4개일 때 72번 히트한다. 활발히 쓰는 페이지 집합(워킹 셋)이 메모리에 안 들어가면 성능이 서서히 나빠지는 게 아니라 벼랑에서 떨어지듯 나빠질 수 있다는 것을 보여 준다.

이렇게 메모리 요구가 물리 메모리를 넘어서 계속 페이징만 하는 상태가 스래싱이다. OSTEP이 소개하는 대응은 두 가지다. 옛 시스템은 일부 프로세스를 아예 돌리지 않아서 남은 프로세스들의 워킹 셋이 메모리에 들어가게 했다(admission control). 요즘 일부 Linux는 메모리가 넘칠 때 메모리를 많이 쓰는 프로세스를 골라 죽이는 out-of-memory killer를 돌린다. 뭐든 한꺼번에 어설프게 하느니 덜 하더라도 제대로 하는 편이 낫다는 쪽의 선택이다.

## 흔한 오해

- 페이지 크기는 클수록 좋다: 표와 TLB 부담은 줄지만 내부 단편화가 커진다. 큰 페이지(예로 4MB)를 필요한 구간에만 쓰는 구조를 지원하는 CPU도 있는데, 그 주된 목적은 표 공간이 아니라 TLB 부담을 줄이는 것이라고 OSTEP은 적는다.
- 프레임을 늘리면 항상 낫다: 개요의 Belady 현상처럼 FIFO에선 아닐 수 있다.
- LRU면 충분하다: 위 루프 예에서 LRU는 프레임이 한 칸 모자란 순간 히트 0이었다. 접근 패턴에 따라 달라진다.
- 스와핑은 느리니 쓰지 않는 게 낫다: 한 번 내려간 페이지가 다시 필요 없으면 문제없고, 문제는 계속 오가는 스래싱이다.
