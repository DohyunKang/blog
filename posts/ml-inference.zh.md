推理优化是一系列旨在让在已训练模型上生成问答的过程变得更快速、更便宜的技术集合。总结一下，KV 缓存（KV Cache）、批处理（batching）、流式处理（streaming）和投机解码（speculative decoding）其实是紧密相连的一个整体。

## 从定义开始

推理（inference）是使用已完成训练的模型的阶段。训练是一次性大规模运行就结束了，而推理则随着用户的使用持续进行。对于服务提供商而言，这是持续产生的成本。（[详情 → 预训练](#/post/ml-pretraining)）

LLM 不会一次性生成答案。它会先生成一个 token，将该 token 作为输入再次运行模型，然后再生成下一个 token。这个过程会一直重复直到最后一个 token 生成完毕。这种慢速和高成本的根源大多来自这种循环结构。（[详情 → Transformer](#/post/ml-transformer)）

## 推理的两个阶段

处理一个请求分为两个阶段。

| 阶段 | 操作内容 | 性质 |
|---|---|---|
| 预填充（prefill） | 一次性处理整个输入提示词（prompt） | 并行计算 token，计算量大 |
| 解码（decode） | 逐个生成 token | 每次生成一个 token，每次都需要从内存中读取模型权重和缓存 |

预填充阶段影响用户看到第一个字符之前的时间，而解码阶段影响后续字符输出的速度。优化技术通常针对两者之一，尤其是针对解码阶段的瓶颈。解码往往比计算更耗时，因为大部分时间花在从内存读取数据上。

## KV 缓存

Transformer 的注意力机制在生成新 token 时会使用之前所有 token 的 key 和 value 值。这些值对每个 token、每层都是确定的，且已生成的 token 的值不会改变。因此，我们不需要每次都重新计算，而是将其存储起来以便重用。这就是 KV 缓存。

- 如果没有缓存，每次生成 token 时都需要重新计算前面的所有内容。
- 如果有缓存，只需计算新生成的一个 token，其余部分直接从缓存读取。
- 代价是占用 GPU 内存。对话越长、并发请求越多，所需空间就越大。

（[详情 → 提示词缓存](#/post/ai-prompt-caching)）是一项在服务端利用请求间 KV 状态重用的功能。

<details>
<summary>KV 缓存有多大（计算示例）</summary>

单个 token 所占的大小由以下公式给出：

```text
2(key와 value) x 층 수 x 어텐션 헤드 수 x 헤드 차원 x 자료형 바이트
```

这是基于假设值的计算，并非实际模型。若为 32 层、32 个 head、head 维度 128、fp16（2 字节），则一个 token 占用 524,288 字节（0.5MB）。一次包含 4,096 个 token 的对话将占用 2GB。若同时处理 10 个请求，仅缓存就需要 20GB。（已用 Python 计算验证。）

最近的一些模型采用了减少 key/value head 数量的结构，从而减小了这一大小。
</details>

## 批处理与连续批处理

GPU 在处理单个请求时会有大量闲置部分。由于解码阶段从内存读取权重的成本很高，因此将多个请求捆绑在一起一次性读取并计算可以提高效率。这就是批处理（batching）。

问题在于每个请求的回答长度不同。如果以固定大小的组运行，先完成的请求会空出位置，而系统仍需等待最长的请求完成，新请求则需等到当前批次结束才能加入。

Orca 论文（OSDI 2022）通过基于迭代（iteration）的调度解决了这一问题。每次运行模型时，调度器都会介入：将已完成的请求立即输出，并将等待中的新请求填入空位。这种方式通常被称为连续批处理（continuous batching）。论文页面中并未出现该术语，但根据上下文可理解为相同思路。论文报告称，在 GPT-3 175B 模型上，相比具有相同延迟水平的 NVIDIA FasterTransformer，其吞吐量提升了 36.9 倍。

```text
고정 배치:   [요청A ████████████]
             [요청B ████░░░░░░░░]  <- 끝났지만 자리가 빈 채로 대기
연속 배치:   [요청A ████████████]
             [요청B ████][요청C ████████]  <- 빈자리에 바로 새 요청
```

## PagedAttention

要扩大批处理规模，就必须容纳更多的 KV 缓存，但无法预先知道每个请求的缓存大小。如果按最大长度预留空间，会导致大量未使用空间的浪费；又因各请求大小不一，还会产生内存碎片（fragmentation）。

vLLM 论文（SOSP 2023）提出的 PagedAttention 借鉴了操作系统的虚拟内存和分页机制。它将缓存划分为小块，按需分配，且不再要求块在内存中连续。相同提示词的请求之间还可以共享块。论文指出，这种方法几乎消除了浪费，并在与现有系统（FasterTransformer、Orca）对比时，在相同延迟下将吞吐量提升了 2~4 倍。对于长序列、大模型和复杂解码场景，差异尤为明显。（[详情 → vLLM](#/post/repo-vllm)）

## 流式处理

流式输出（Streaming）并非旨在减少模型的总生成时间，而是为了降低用户的感知等待时间。它不会等到整个回答全部生成完毕才发送，而是随着新 Token 的生成立即将其流式输出。由于解码过程本身就是一个 Token 一个 Token 产生的机制，因此这种结构上是自然的。

- 用户感知的延迟主要是首 Token 到达的时间（TTFT）。如果预填充（Prefill）阶段耗时过长，TTFT 就会增加。
- 后续 Token 之间的间隔则取决于解码速度。
- 即使总生成时间相同，采用流式输出也会让用户感觉快得多。

## 投机性解码 (Speculative Decoding)

解码速度慢是因为模型一次只能生成一个 Token。投机性解码（speculative decoding）利用一个小而快的模型先预测多个 Token，然后由一个大模型一次性并行验证这些预测。对于预测正确的部分，直接采纳大模型运行一次的结果；一旦遇到预测错误的地方，则从该点开始使用大模型的值重新生成。

Leviathan 等论文报告称，在 T5-XXL 模型上，该方法比现有实现快约 2~3 倍，且无需重新训练模型或修改结构，输出分布也保持不变。换言之，这是一种在不牺牲质量的前提下加速获取答案的方法。

要使预测准确，小模型的预测能力需与大模型相似。对于简单部分（如结构化句子、重复代码），推测往往准确；而在困难部分则容易出错。

<details>
<summary>一次能生成多少个 Token？（计算示例）</summary>

假设每个 Token 的推测正确概率为 0.8，且一次推测 4 个 Token，则在运行大模型时获得的 Token 数量的期望值为 $1 + 0.8 + 0.8^2 + 0.8^3 + 0.8^4 \approx 3.36$ 个。这是一个理论假设值；由于运行小模型本身也需要时间，实际的速度提升会低于此数值。在验证过程中具体遵循何种规则来接受或拒绝推测结果，需查阅论文中的公式，本文此处不作展开。
</details>

## 服务中常用的相关概念

- **量化 (Quantization)**：将权重以较小的数值格式存储，从而减少内存占用和读取时间。代价是精度略有下降。（[详情 → 本地模型](#/post/ml-local-models)）
- **模型并行 (Model Parallelism)**：将无法放入单个 GPU 的模型拆分部署到多个 GPU 上。
- **前缀缓存 (Prefix Cache)**：对于具有相同前缀的请求，复用其 KV 缓存。

实际的服务架构将在另一篇文章中继续介绍。（[详情 → AI 服务基础设施](#/post/infra-ai-serving)）

## 常见误区

- 流式输出并不意味着模型计算得更快，它只是优先展示已生成的部分。
- 投机性解码并非牺牲答案质量的捷径。根据论文，其输出分布保持不变。
- 增大批量大小（Batch Size）并不总是有益的。虽然吞吐量会提升，但单个请求的等待时间可能会增加。
- KV 缓存独立于模型大小也会占用大量内存。这就是为什么即使模型已加载，在处理长对话时仍可能出现内存不足的原因。
