サーバーを起動するまでは何とかできたが、起動後に「今、正常に動いているか」を確認するには別途準備が必要だった。その準備とは、モニタリング、ログ、アラートである。

## 三つのシグナル

稼働中のシステムから引き出せる情報は大きく三種類に分けられる。OpenTelemetry のドキュメントもこの三つを「シグナル (signal)」と呼んでいる。

| シグナル | 一言定義 | 答える質問 |
|---|---|---|
| メトリクス | 時間経過とともに記録される数値（リクエスト数、エラー率、メモリ使用量など） | 現在の状態はどうなのか、普段と違うのか |
| ログ | 起こった出来事の一件一件の記録 | その時何が起きたのか |
| トレース | 一つのリクエストが複数のサービスを通過した経路 | どこで遅れたのか、どこで失敗したのか |

OpenTelemetry はトレースを「アプリケーションを通過するリクエストの経路」、メトリクスを「ランタイムで測定された値」、ログを「イベントの記録」と説明している。

通常の手順は以下の通りだ。まずメトリクスのグラフが異常を示し、次にトレースで範囲を絞り込み、最後にログから原因となる文章を見つける。数字は安価で速いが理由がわからない一方、ログには理由があるものの量が多すぎて見つけにくい。そのため、一つだけ使うのではなく三つを併用する。

## メトリクス：何を観測するか

観測すべき項目が多すぎるため基準が必要だが、Google SRE の本に登場する「四つのゴールデンシグナル」が最も引用されている。

| シグナル | 意味 |
|---|---|
| レイテンシ (latency) | 一つのリクエストを処理するのに要する時間。成功と失敗を別々に観測する |
| トラフィック | システムに入ってくるリクエスト量（例：1 秒あたりのリクエスト数） |
| エラー | 失敗したリクエストの割合。500 エラーだけでなく、200 レスポンスでも内容が間違っている場合や、遅すぎて失敗とみなす場合も含まれる |
| 飽和 (saturation) | 最も逼迫しているリソースがどの程度使用されているか |

失敗を別々に観測させる理由は、早々に失敗するリクエストがあることで平均レイテンシが低下し、状況が良そうに見えるようにするためである。飽和については 100% に達する前から性能が低下するシステムが多いため、目標使用率を設定しておくよう推奨されている。

### 平均ではなくパーセンタイル

レイテンシは平均値で見ると誤解を招く。以下のコードは、1,000 のリクエストのうち 980 が 100ms 前後で処理され、20 が 3 秒かかった状況を模倣したものである。

```python
import random
lat = sorted([random.gauss(100, 20) for _ in range(980)] + [3000] * 20)
avg = sum(lat) / len(lat)
p50 = lat[len(lat) // 2]
p99 = lat[int(len(lat) * 0.99) - 1]
print(round(avg), round(p50), round(p99))   # 실행 결과 예: 156 99 3000
```

平均は 156ms で問題なさそうに見えるが、p99 は 3,000ms である。これは 50 のリクエストのうち 1 つが 3 秒待たされたことを意味する。p50 は中央値であり、p99 は 99% のリクエストがこの時間以内で完了したことを示す値だ。レイテンシのアラートは平均ではなく、p95 や p99 などの尾部の値に設定するのが望ましい。

## ログ：人間が読むものから機械が探すものへ

ログを `print("エラー発生")` のように単なる文句として残しておくと、後で検索できない。最近では JSON などの構造化形式で保存し、リクエストごとに ID を付与する。エラーをどの階層でキャッチし、何を記録するかについては [詳細 → エラー処理とロギング](#/post/be-error-logging) で別途記述している。

```python
import json, time, uuid

def log(level, msg, **kw):
    print(json.dumps({"ts": round(time.time(), 3), "level": level,
                      "msg": msg, **kw}, ensure_ascii=False))

rid = "req-" + uuid.uuid4().hex[:6]
log("info", "order created", request_id=rid, user_id=42, took_ms=120)
log("error", "payment failed", request_id=rid, upstream="pay-api", took_ms=3000)
```

実行すると各行に JSON が一つずつ出力される。`request_id` で検索すれば、そのリクエストが通過した痕跡のみをまとめて確認できる。サービスが複数に分割されている場合、この ID をサービス間で渡す必要があるが、それがトレースの基本的な考え方である。

ログで注意すべき点は三つある。

- パスワード、トークン、キー、個人情報を残さない。一度ログに記録されると複数の場所に複製される。キー管理については [詳細 → シークレット・環境変数の管理](#/post/cloud-secrets) で扱っている。
- レベルを区別する。正常なフローは info、人間が見るべきものは error である。すべて error とすると真のエラーが埋もれてしまう。
- 量を考慮する。ログは保存容量と検索コストがそのまま費用になるため、リクエストごとに全文を記録すると請求書が先に届く。

## トレース：一つのリクエストへの地図

トレースとは、一つのリクエストを複数の区間 (span) に分割し、それぞれに要した時間を記録したものである。API サーバーが DB を呼び出し、外部決済 API を呼び出すようなリクエストであれば span が三つ程度生まれ、そのうちどこが遅かったかが一目でわかる。単一のサーバーで構成されるサービスではログとメトリクスだけで大半の問題は解決できるが、複数のサービスが存在するか、サーバーレス関数が連携する場合にトレースの価値が高まる。サーバーレスについては [詳細 → サーバーレス](#/post/cloud-serverless) にある。

OpenTelemetry はこの三つのシグナルを収集する方法をベンダー中立な標準として定めたプロジェクトである。アプリに一度埋め込んでおけば、送信先（ストレージやダッシュボード）を変えてもアプリのコードを変更する必要がないのが利点だという。

<details>
<summary>収集方式の二つ（折りたたみ）</summary>

- プル (pull): モニタリングサーバーが定期的にアプリの指標アドレスを訪れて読み取る。Prometheus が代表的である。
- プッシュ (push): アプリやエージェントが収集サーバーに直接送信する。短い寿命を持つ作業やサーバーレスではこちらの方が自然だ。

どちらの場合でも、アプリは「数値を暴露する」ことしかせず、保存・グラフ・通知などは別のツールが担当する構造が一般的です。
</details>

## 通知設計

モニタリングで最も難しいのは収集ではなく、通知でした。通知が多すぎるとすべて無視され、少なすぎると障害をユーザーから聞かされます。

Google SRE の本と Prometheus ドキュメントで共通して言われていることは似ています。

- 原因ではなく症状に通知を送る。「CPU 90%」よりも「エラー率の急増、応答の遅れ」がユーザーが実際に直面する問題です。CPU が上がってもユーザーが感じなければ緊急に知らせる必要はありません。
- 呼び出し（ページ）は緊急性があり、人間が対応が必要な時に行います。機械的に処理できることは通知ではないと SRE の本は言っています。
- メール通知は蓄積するとノイズになりやすいため、すぐに緊急性がない問題はダッシュボードで見ることを推奨します。
- 通知は可能な限り少なく、ユーザーが困っている箇所だけにします。通知には関連するダッシュボードのリンクを付けて、どの構成要素の問題か即座に確認できるようにします。
- 一時的な揺らぎは許容範囲を持たせます（条件が一定時間続く場合のみ鳴らす）。
- 容量が限界に近づいている場合は、現在ユーザーへの影響がなくても通知します。すぐに障害になる可能性があるためです。
- バッチ処理は実行周期の 2 倍以上を基準とします。一度失敗しても人間が対応できない場合は、より頻繁に回す方が良いでしょう。

同じドキュメントには、モニタリングシステム自体も監視すべきという内容もあります。通知サーバーが死んでいれば静かではなく「目が見えない」状態であるため、外部からサービスを確認するブラックボックスチェックを別途設けることを推奨します。

| 区分 | ホワイトボックス | ブラックボックス |
|---|---|---|
| 見る場所 | システム内部（メトリクス、ログ） | ユーザーが確認できる外部動作 |
| 強み | すぐに発火する問題、再試行で隠れた失敗、デバッグ | 実際に機能していないこと |
| 弱み | 内部指標が多いためノイズが発生しやすい | まだ発生していない問題は予測できない |

両方使うのが普通で、呼び出しはブラックボックス・症状側に送ります。

## 障害発生時の基本手順

障害対応は原因を見つけることよりも被害を減らすことが先です。ここからはドキュメントから読んだ内容ではなく、一般的な運用手順を記したものであり、チームによって異なる場合があります。

1. 影響範囲の確認：誰が、どの程度、いつから不具合があるか。
2. 直近の変更確認：直前のデプロイや設定変更があった場合はロールバックが最も早いです。デプロイ関連は [詳細 → CI/CD](#/post/cloud-cicd) とリンクしています。
3. 緩和：ロールバック、トラフィックの削減、インスタンスの増加など。原因は後で探っても構いません。
4. 原因分析：メトリクスから時点を特定し、トレースで区間を絞り込み、ログから文脈を見つけます。
5. 事後整理：同じことが繰り返されないよう通知・テスト・ドキュメントを改善します。人を責めるような文章ではなく、構造を改善する内容に書きます。

インスタンスを増やす方法は [詳細 → オートスケーリング](#/post/infra-autoscaling) で別途見ています。

## よくある誤解

- モニタリングと観測可能性（observability）は同じ意味ではありません。モニタリングは事前に定義された指標を確認することであり、観測可能性とは初めて見る問題でも信号を調べて説明できる程度を指します。ただしこの区別はドキュメントによって定義が少しずつ異なるため、この稿ではその程度に留めます。
- 指標を多く作るほど良いわけではありません。誰も見ないグラフはコストだけがかかります。
- ダッシュボードがあれば通知が必要ないわけではありません。人は 24 時間画面を見ていないからです。
- 平均遅延が問題なければサービスは良好だという考え方は、上記のコードが反例となります。
- 通知が多いほど安全だということも逆です。鳴ったらすべて無視すれば、通知がないのと同じです。
