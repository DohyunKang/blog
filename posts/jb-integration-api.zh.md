整合实施单元探讨如何将分离的系统连接起来，以及它们之间以何种格式交换数据。虽然术语繁多，但若归纳为“中间由谁代为处理”，大部分问题即可迎刃而解。

## 本单元考察内容

本单元主要分为三个部分。

| 部分 | 核心问题 | 常用术语 |
|---|---|---|
| 模块关联 | 如何将系统连接起来 | 直接关联、间接关联、EAI、ESB |
| 接口 | 如何约定交换内容 | 接口规范、收发项目、错误处理 |
| 数据格式 | 交换内容的形态 | JSON, XML |

考试中常有“下列描述对应的术语是？”这类定义匹配题。因此，首先应将每个术语与单行定义配对记忆。考试日程和报名费可在官方网站查询。

## 需要关联的原因

公司内 ERP、CRM、薪资等系统各自独立运行。维基百科的 EAI 条目将这种状态称为相互孤立的“自动化孤岛”，并解释 EAI 是用于共享其间数据与业务流程的中间件。

当系统只有两三个时，可直接互联即可。问题在于数量增加时。直接连接的线路会随系统数量增加而迅速增多；一旦某个系统的格式变更，就需要调整所有与其相连的线路。引入中间节点的结构正是为了减轻这一负担。

## 三种关联结构

| 结构 | 形态 | 特点 |
|---|---|---|
| 点对点 (Point-to-Point) | 系统间一对一直接连接 | 简单但连接增多后管理困难 |
| 星型 (Hub & Spoke) | 各系统连接至中央枢纽 | 由中央进行控制。若枢纽受阻，整体将受影响 |
| 总线 (Bus) | 各系统接入公共总线 | 系统以插入总线的方式互联 |

维基百科 EAI 条目中提及两种拓扑结构：星型结构中 EAI 位于中央，应用程序作为 spoke（分支）连接；总线结构中 EAI 本身即为总线或现有消息中间件内的模块。点对点则是无 EAI 的直接连接方式，可作为对比了解。

## EAI

EAI（Enterprise Application Integration，企业应用集成）是一种连接企业内部多个应用程序、实现数据与业务流程共享的方式。文档中提到的组件如下：

- 枢纽或总线：负责在中央进行消息交换的部分
- 适配器：将各应用程序接入枢纽，并将数据转换为统一格式的部分
- 集成模块：订阅特定事件并处理通知的部分

模式分为两类：仲裁（Mediation）是指当某个应用程序产生事件时，EAI 作为 broker（中介）向相关应用程序传递变更；联邦（Federation）是指 EAI 充当外部请求的入口，代为与内部应用程序通信。

跨多个系统操作的一致性通常通过两阶段提交或补偿事务来实现。

[详情 → 规范化与事务](#/post/jb-normalization-transaction)

## ESB

ESB（Enterprise Service Bus，企业服务总线）是面向服务架构（SOA）中用于连接应用程序的通信系统，其主要用途是集成不同系统。维基百科将 ESB 介绍为实现 EAI 总线模型的常见方式。理想情况下，原本应用程序间的直接接触被替代，所有通信均通过总线进行。

ESB 的核心功能可归纳为四项：

| 功能 | 作用 |
|---|---|
| 路由 | 将消息发送至合适的服务，并监控和控制流程。可根据内容或规则进行分流发送 |
| 转换 | 将消息转换为接收方可读的格式 |
| 协议转换 | 使使用不同通信协议的服务能够互通 |
| 消息队列 | 对消息和事件进行排队并按顺序传递 |

<details>
<summary>用一句话区分 EAI 与 ESB</summary>

EAI 的说法更接近“集成企业内部应用程序”这一目的，而 ESB 则是以“服务总线”这一形态实现该目标的方式。考试中，若出现以枢纽为中心的描述，多指向 EAI 的星型结构；若涉及面向服务架构和总线，则多指向 ESB。不过，题目表述可能将两者归为同一类别，因此当选项中同时出现这两个术语时，建议通读解释句子以确保准确判断。

</details>

## 接口规范

系统间进行关联需要约定，而记录这些约定的文档即为接口规范。通常包含以下内容：

- 发送方与接收方的系统
- 交换项的名称、数据类型、长度及是否必填
- 调用方式与频率（实时或批量）
- 出错时的处理方法

若任一项目被误解，整个集成流程便会随之失效，因此即便文档简短，也必须详尽无遗。在考试中，可能会询问规范中包含哪些项目，或将此与验证数据在集成后是否正确流转的测试环节相结合。

## 数据格式：JSON 与 XML

交换数据的常见格式为 JSON 和 XML。以相同的订单信息为例，两种方式的表示如下：

```json
{"orderId": 101, "items": [{"sku": "A1", "qty": 2}], "paid": true}
```

```xml
<order id="101"><item sku="A1" qty="2"/><paid>true</paid></order>
```

用 Python 直接读取上述两段代码后发现：JSON 可通过 `json.loads` 解析为字典，其中 `items[0].qty` 的值为 2；XML 则需通过 `ElementTree` 解析，其 `item` 元素的 `qty` 属性值同样为 2。若 XML 的结束标签不匹配（如 `<a><b></a>`），则在解析阶段就会报错。

### JSON

json.org 将 JSON 描述为一种轻量级的文本数据交换格式，旨在让人类易于读写，同时让机器易于解析和生成，且与语言无关。其结构包含两种类型：

- **对象**：由名称 - 值对组成的集合，用花括号包裹，名称后跟冒号，各对之间用逗号分隔。顺序无关紧要。
- **数组**：按顺序排列的值集合，用方括号包裹，元素间用逗号分隔。

值可以是字符串（使用双引号）、数字、true/false、null，以及对象和数组（支持嵌套）。

### XML

根据 W3C 的 XML 1.0 规范，XML 是 SGML 的一个受限子集，其目标是便于在网络上交换和处理结构化数据。考试中常考的概念有两个：

| 概念 | 含义 |
|---|---|
| 正形 (well-formed) | 遵循语法规则的文档，例如只有一个根元素且元素正确嵌套 |
| 有效 (valid) | 不仅正形，还满足关联 DTD 所定义的结构的文档 |

起始标签与结束标签必须成对出现；属性是起始标签内的名称 - 值对；顺序无意义；同一标签内不能出现同名属性。DTD 用于定义允许的元素和属性结构。

<details>
<summary>JSON 与 XML 对比表</summary>

| 项目 | JSON | XML |
|---|---|---|
| 结构 | 对象与数组 | 由标签包裹的元素树 |
| 属性 | 无，以名称 - 值对表示 | 起始标签的属性 |
| 结构验证 | 仅基于文档自身的语法规则 | 可通过 DTD 进行有效性验证 |
| 篇幅 | 通常较短 | 因标签重复而较长 |

虽然如上文示例所示，相同信息在不同格式下的长度差异一目了然，但并不能断言哪种格式始终更优。考试中会分别考查两种格式的定义与结构差异。

</details>

## 常见题型

- **术语匹配**：给出描述句子，从 EAI、ESB、Hub-and-Spoke（轮辐式）、Bus（总线）中选择正确项
- **功能区分**：在路由、转换、协议转换、消息队列中，找出与描述相符的功能
- **格式识别**：给出 JSON 或 XML 示例，要求读取值或选择正确的语法
- **正形与有效辨析**：根据是否存在 DTD 来判断文档是仅“正形”还是“有效”

解题方法很简单：若句子中出现“中央”、“Hub"等词，则对应 Hub-and-Spoke；若出现“服务”、“Bus"及转换、路由相关描述，则指向 ESB。遇到格式判断时，先根据花括号识别为 JSON，根据标签识别为 XML，再深入细节分析。建议直接通过 큐넷（Korea Computer Federation）等官方公开资料进行练习。
