加密、哈希和电子签名看似相似，但解决的问题却不同。加密是为了隐藏信息并能在之后还原；哈希则是为了验证一致性且不可还原；签名则是为了确认是谁创建的以及内容是否被篡改。

## 先区分这三种概念

| 工具 | 可还原吗 | 密钥 | 主要用途 |
|---|---|---|---|
| 对称加密 | 可以 | 一个（相同密钥） | 隐藏数据 |
| 非对称加密/签名 | 加密可还原 | 公钥 + 私钥 | 密钥交换、签名验证 |
| 哈希 | 不可还原 | 无 | 完整性校验、密码存储 |

之前被这些术语搞混了，但问一个问题后就理清了：是否需要原文（加密），还是只需确认是否一致（哈希），或是需要确认发送者身份（签名）。

## 对称加密

用同一个密钥加锁和解锁。速度快。无论是文件还是通信，真正处理大量数据隐藏的场景几乎都依赖对称加密。目前的标准是 AES，现在通常采用同时提供加密和篡改检测的 AEAD 模式（如 AES-GCM、ChaCha20-Poly1305）。RFC 8446 指出 TLS 1.3 已移除了非 AEAD 的加密方式。

其缺点只有一个：双方如何安全地共享同一个密钥。如果在互联网上直接发送密钥，就失去了隐藏的意义。

## 非对称加密

密钥是一对。公钥可以分发给任何人，私钥只有本人持有。用公钥加密的内容只能用私钥解密。因此，即使与初次见面的对方也能建立秘密通信渠道。

但缺点是速度慢。因此实际应用中会混合使用：通过非对称方式协商出对称密钥，之后正文内容再用该对称密钥加密。TLS 也是这种结构。RSA、椭圆曲线（ECDH、ECDSA 等）是典型代表。

<details>
<summary>密钥交换的实际实现（Diffie-Hellman 系列）</summary>

在 TLS 1.3 中，并不是向对方“发送”密钥，而是双方各自生成临时的密钥对，仅交换公开值，从而计算出相同的秘密值。这是基于即使中间人截获了所有公开值，也无法推算出该秘密值的数学原理。由于是临时密钥，会话结束后即被丢弃；即使后来服务器的长期密钥被盗，过去的通信也无法破解。这被称为前向安全性（forward secrecy）。RFC 8446 指出 TLS 1.3 的基于公钥的密钥交换全部具备此特性（仅使用 PSK 的模式和 0-RTT 数据除外）。
</details>

## 哈希

无论输入是什么，都会输出固定长度的值。相同的输入总是产生相同的输出，且无法从输出反推输入。只要输入中有一个字符不同，结果就会完全改变。

```python
import hashlib
hashlib.sha256(b"hello").hexdigest()
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
hashlib.sha256(b"hellp").hexdigest()
# fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7
```

上述两个值是直接计算得出的。下载文件后核对校验和就是这种用途。如果值相同，说明文件未被篡改。

此外还有一点：哈希可以在“无密钥”的情况下由任何人计算。因此若要防止篡改，需使用混合了密钥的 HMAC。只有知道密钥的一方才能生成正确的值。

## 密码不能仅用哈希存储

SHA-256 设计得很快，而用于密码存储时，这种速度反而成了问题。一旦数据库被盗，攻击者可以每秒尝试海量候选密码；且相同密码会产生相同哈希，导致预先计算的表（彩虹表）也有效。

因此需要增加两项措施：

- **盐值（Salt）**：为每个用户添加不同的随机值。即使密码相同，生成的哈希也不同，从而使预计算表失效。盐值并非秘密，可以明文存储在哈希旁边。
- **慢速哈希**：使用故意消耗大量时间和内存的函数。

OWASP 密码存储最佳实践指南给出的优先级如下：首选 Argon2id（最小 m=19456KiB, t=2, p=1），次选 scrypt，老旧系统可用 bcrypt（工作因子至少 10，密码长度限制为 72 字节），若需符合 FIPS 规定则使用 PBKDF2-HMAC-SHA256 迭代 60 万次。盐值应为每个密码单独随机生成，大多数库会自动处理，建议不要手动创建。

```python
import hashlib, os, hmac
salt = os.urandom(16)
h = hashlib.pbkdf2_hmac("sha256", b"pw", salt, 600000)
hmac.compare_digest(h, hashlib.pbkdf2_hmac("sha256", b"pw", salt, 600000))  # True
```

运行后得到 32 字节的输出，相同盐值和迭代次数时结果一致。使用 `compare_digest` 进行比较是为了防止通过比较时间泄露信息。在实际服务中，推荐使用 Argon2id 库实现（本代码为 PBKDF2 示例，故仅作验证）。

<details>
<summary>胡椒（pepper）</summary>

与盐值不同，胡椒是一个所有密码共用的秘密值。它应存放在数据库之外（如密钥存储库或 HSM）。根据 OWASP 的解释，仅靠胡椒并不能提供完整安全，而是作为数据库单独泄露时的辅助防御手段。可在哈希前混合，或在哈希后将其作为 HMAC 的密钥使用。若胡椒泄露，必须更换，届时受影响的用户需重新设置密码。
</details>

## 电子签名

这是哈希值与非对称密钥的结合体。如果对文档进行哈希并用私钥签名，接收方则使用公钥进行验证。如果验证通过，则可以确认两点：该文档由该私钥的持有者创建，且在签名后文档内容未被篡改。

为了便于记忆，可以记住“加密与解密的方向是相反的”：加密是用公钥锁住、用私钥打开；而签名则是用私钥生成（盖章）、用公钥验证。软件分发、JWT 签名以及证书都基于这一原理。

然而，如何确认公钥确实属于那个人呢？这就引出了证书和认证机构（CA）。证书是由 CA 对“此域名的公钥是以下内容”这一声明进行签名的结果。浏览器会维护一份受信任的 CA 列表，并沿着证书链向上追溯以完成验证。

## TLS 所做的事情

HTTPS 中的"S"指的就是这个。上述工具按顺序全部使用。RFC 8446 中整理的 TLS 1.3 流程大致如下：

1. 客户端发送 ClientHello，其中包含临时密钥交换值（key_share）和支持的签名算法。
2. 服务器通过 ServerHello 返回其 key_share。此时双方计算出相同的共享秘密值，此后的消息将使用加密传输。
3. 服务器发送证书、CertificateVerify（用私钥生成的签名）以及 Finished 消息，以此证明其真实身份。
4. 当客户端也发送 Finished 后，后续数据将通过协商好的对称密钥进行传输。

基本握手过程需要往返一次。如果已经建立过一次连接，理论上可以在第一次传输中通过 0-RTT 携带数据，但 RFC 明确指出这些数据不具备前向安全性。与 TLS 1.2 相比，静态 RSA 密钥交换、压缩以及过时的加密算法已被移除。

总结来说：利用非对称加密（密钥协商与签名）来验证身份并生成密钥；利用对称加密（AEAD）快速加密正文内容；利用哈希和 HMAC 来防止数据篡改。

## 常见误解

- 哈希不是加密，其目的也不是可逆还原。如果说“将密码‘加密’存储”，这实际上意味着可以还原，因此这种说法反而具有危险性。
- 编码（如 Base64）也不是加密，任何人都可以解码。
- Salt（盐值）并非秘密，其用途是防止相同输入产生相同的输出。
- 不应自行创建加密算法，而应使用经过验证的库和标准算法。
- HTTPS 图标上的锁并不代表网站内容绝对安全，它仅表示通信内容未被中间人窃读，且域名匹配正确。
