인덱스는 테이블과 별개로 값을 정렬해 둔 구조라서, 조건에 맞는 행을 처음부터 훑지 않고 바로 찾아가게 해 준다. 대신 쓸 때마다 같이 고쳐야 하니 공짜는 아니다.

## 인덱스가 뭔지

테이블에서 `WHERE email = '...'` 같은 조건으로 한 행을 찾는다고 하자. 인덱스가 없으면 DB는 첫 행부터 끝까지 다 읽는다. 풀 스캔이다. 행이 열 개면 아무 문제가 없지만 이십만 개, 이천만 개가 되면 얘기가 달라진다.

인덱스는 책 뒤에 붙은 찾아보기와 비슷하다. 단어를 가나다순으로 정렬해 두고 옆에 페이지 번호를 적어 둔 것. SQLite 문서도 비슷하게 설명한다. 인덱스는 색인할 컬럼 값과 원래 행의 rowid를 정렬된 순서로 담은 별도의 구조고, 값이 같으면 rowid로 순서를 가른다. 정렬돼 있으니 이진 탐색이 되고, 그래서 찾는 시간이 행 수 N에 비례하지 않고 log N에 비례한다. 문서는 천만 행 테이블에서 이 차이가 백만 배쯤 된다고 어림한다.

[자세히 → 관계형 DB와 SQL 기본](#/post/db-rdb-sql)에서 테이블·키 이야기를 먼저 보고 오면 이 글이 더 편하다. 기본 키(primary key)는 대부분의 DB에서 인덱스가 자동으로 붙는다고 알고 있는데, 이 부분은 DB마다 구현이 달라서 쓰는 DB 문서로 확인해야 한다.

## B-Tree가 어떻게 생겼나

인덱스 구조로 제일 흔한 건 B-Tree다. Use The Index, Luke는 인덱스를 "이중 연결 리스트 + 검색 트리" 조합으로 소개한다. 맨 아래층(리프)에는 정렬된 인덱스 항목들이 줄줄이 연결돼 있고, 그 위에 "이 범위는 이쪽 칸"이라고 알려 주는 안내 층이 쌓여 있다. 균형 트리라서 어느 값을 찾든 위에서 아래까지 내려가는 깊이가 같다.

직관만 잡으면 이렇다.

```
        [ 50 | 100 ]              <- 루트: 어느 구간인지만 알려 줌
       /     |     \
 [10|30]  [60|80]  [120|150]      <- 중간층
   |        |         |
 리프: 10 20 30 | 55 60 70 80 | 120 130 150 ...  (정렬된 채로 서로 연결)
```

61을 찾는다면 루트에서 "50과 100 사이"로, 중간층에서 "60~80 칸"으로, 리프에서 61 근처로 내려간다. 세 번 내려가면 끝이다. 한 칸에 담기는 항목이 많을수록 층이 얕아진다. 예를 들어 한 노드에 100갈래라고 치면 3층만으로 100만 개 리프를 가리킬 수 있다(산수일 뿐 실제 DB의 숫자는 아니다). 데이터가 천 배 늘어도 층은 한두 개 늘어나는 정도라는 게 포인트다.

리프가 서로 연결돼 있고 정렬돼 있어서 범위 조회(`BETWEEN`)와 정렬(`ORDER BY`)에도 이 구조가 도움이 된다. 시작점을 찾은 다음 옆으로 쭉 읽으면 되기 때문이다.

<details>
<summary>자세한 풀이: 한 건 찾는 비용과 여러 건 찾는 비용</summary>

SQLite 문서의 설명대로면 인덱스로 한 행을 찾는 데 이진 탐색이 두 번 필요하다. 인덱스에서 rowid를 찾는 것, 그 rowid로 원래 테이블에서 행을 찾는 것. 조건에 맞는 행이 K개면 비용은 대략 (K+1)·log N이다. 첫 건은 탐색으로 찾고, 나머지는 인덱스에서 다음 항목으로 넘어가며 읽기 때문이다.

그래서 K가 커져서 테이블의 큰 비율이 되면 얘기가 달라진다. 인덱스로 한 건씩 테이블을 오가는 것보다 그냥 통째로 훑는 게 나을 수 있고, DB는 통계를 보고 그쪽을 고르기도 한다. 이 선택 기준의 정확한 계산식은 DB마다 다르다.

</details>

## 직접 돌려 봤다

SQLite(3.50.4)에서 사용자 테이블에 20만 행을 넣고 이메일 한 건을 찾아 봤다. 이메일은 모두 다르고, 도시와 나이는 무작위다.

```python
import sqlite3, random, time
c = sqlite3.connect(':memory:')
c.execute("create table users(id integer primary key, email text, city text, age int)")
random.seed(1)
cities = ['서울','부산','대구','인천','광주']
c.executemany("insert into users(email,city,age) values(?,?,?)",
    [(f"u{i}@ex.com", random.choice(cities), random.randint(18,70)) for i in range(200000)])

q = "select * from users where email='u123456@ex.com'"
for r in c.execute("explain query plan " + q): print(r[3])
c.execute("create index idx_email on users(email)")
for r in c.execute("explain query plan " + q): print(r[3])
```

결과는 이랬다.

| | 실행 계획 | 걸린 시간(1회 측정) |
|---|---|---|
| 인덱스 전 | `SCAN users` | 약 4.17ms |
| 인덱스 후 | `SEARCH users USING INDEX idx_email (email=?)` | 약 0.019ms |

한 번만 잰 값이라 정확한 배수는 의미가 없고, 풀 스캔에서 인덱스 탐색으로 바뀌었다는 것과 시간이 두 자릿수 이상 줄었다는 것만 본다. 컴퓨터마다 다르다.

## 실행 계획으로 확인하기

위 코드에서 `explain query plan`이 실행 계획을 보여 준 것이다. 인덱스를 만들었다고 쿼리가 꼭 그걸 쓰는 건 아니라서, 만든 뒤에 계획을 보는 습관이 필요하다.

PostgreSQL 문서 기준으로 `EXPLAIN`은 쿼리를 실행하지 않고 DB가 고른 계획을 보여 준다. 읽을 때 눈에 들어오는 건 몇 개다.

- `Seq Scan`: 테이블 전체를 읽는다(SQLite에서는 `SCAN`).
- `Index Scan`: 인덱스로 찾은 뒤 테이블에서 행을 가져온다. 한 건처럼 선택도가 높은 조건에서 주로 고른다고 문서에 나온다.
- `cost`: 시작 비용과 전체 비용으로, 단위는 임의다. 시간(ms)이 아니다.
- `rows`: 그 단계가 내보낼 것으로 추정한 행 수다. 추정이라 틀릴 수 있다.

`EXPLAIN ANALYZE`는 쿼리를 진짜로 실행해서 실제 시간과 실제 행 수를 같이 보여 준다. 추정 행 수와 실제 행 수가 크게 어긋나면 통계가 낡았다는 신호로 읽는다고 한다. 실제로 실행하니 `UPDATE`·`DELETE`에 쓸 땐 `BEGIN`/`ROLLBACK`으로 감싸라고 문서가 알려 준다. 나는 PostgreSQL을 직접 돌리지 않았고 이 부분은 문서만 읽었다.

## 인덱스가 도움이 안 되는 경우

같은 테이블로 몇 가지 쿼리의 계획을 봤다. 이메일 인덱스가 이미 있는 상태다.

| 쿼리 | 실행 계획 |
|---|---|
| `email = 'u123456@ex.com'` | 인덱스 탐색 |
| `email like '%123456@ex.com'` | `SCAN users` (풀 스캔) |
| `lower(email) = '...'` | `SCAN users` (풀 스캔) |

앞이 와일드카드인 `LIKE '%...'`는 정렬된 순서의 시작점을 알 수 없어서 인덱스를 못 쓴다. 사전에서 "끝이 사랑으로 끝나는 단어"를 찾는 것과 같다. 컬럼에 함수를 씌운 `lower(email)`도 인덱스는 원본 값 기준으로 정렬돼 있어서 안 맞는다. 이건 SQLite에서 확인한 것이고, DB마다 예외(함수 기반 인덱스 등)가 있다.

그 밖에 일반적으로 알려진 경우도 있다. 값이 몇 종류 안 되는 컬럼(성별처럼)은 인덱스를 타도 조건에 맞는 행이 너무 많아서 이득이 작다. 테이블이 아주 작으면 그냥 훑는 게 빠르다.

## 여러 컬럼 인덱스는 왼쪽부터

`city`와 `age`를 같이 조건으로 거는 쿼리가 많다면 두 컬럼을 묶은 인덱스를 만들 수 있다.

```python
q4 = "select * from users where city='서울' and age=30"
c.execute("create index idx_city_age on users(city, age)")
```

| 쿼리 | 만들기 전 | 만든 뒤 |
|---|---|---|
| `city='서울' and age=30` | `SCAN users` | `SEARCH ... USING INDEX idx_city_age (city=? AND age=?)` |
| `city='서울'` | `SCAN users` | `SEARCH ... USING INDEX idx_city_age (city=?)` |
| `age=30` | `SCAN users` | `SCAN users` (인덱스 못 씀) |
| `select city, age ... where city='서울' and age=30` | | `SEARCH ... USING COVERING INDEX idx_city_age` |

두 번째 줄, 세 번째 줄이 규칙을 보여 준다. 왼쪽 컬럼(`city`)만 조건이면 이 인덱스를 쓰지만, 오른쪽 컬럼(`age`)만 조건이면 못 쓴다. 전화번호부가 성, 이름 순으로 정렬돼 있어서 이름만으로는 못 찾는 것과 같다. SQLite 문서도 맨 왼쪽 컬럼이 가장 큰 정렬 기준이고 다음 컬럼은 동점을 가르는 용도라고 설명한다. 같은 문서가 "한쪽이 다른 쪽의 앞부분이면 두 인덱스를 다 두지 말고 짧은 쪽을 지우라"는 요령도 적는다. `(city, age)`가 있으면 `(city)` 인덱스는 필요가 없다는 얘기다.

네 번째 줄의 `COVERING INDEX`는 쿼리가 필요한 컬럼이 전부 인덱스 안에 있어서 원래 테이블을 아예 안 열어 보는 경우다. 문서는 이게 점근적으로 빨라지는 게 아니라 상수 배(2배쯤) 정도의 이득이라고 한다.

## 읽을 땐 빠르고 쓸 땐 느리다

인덱스는 정렬된 채로 유지돼야 하니 행을 넣고, 고치고, 지울 때마다 인덱스도 같이 고쳐야 한다. 같은 SQLite로 20만 행을 넣는 시간을 비교했다. 테이블 컬럼은 세 개(a, b, c)고, 하나는 인덱스 없이, 하나는 세 컬럼 모두에 인덱스를 둔 경우다.

| | 20만 건 INSERT (1회 측정) |
|---|---|
| 인덱스 0개 | 약 120ms |
| 인덱스 3개 | 약 403ms |

세 배쯤 느려졌다. 이것도 한 번 잰 값이고 환경에 따라 다르다. 그래서 "자주 찾는 컬럼에만" 만든다. 인덱스는 저장 공간도 따로 차지한다. 쓰기가 아주 많은 테이블에 인덱스를 잔뜩 거는 건 손해일 수 있다. 쓰기 정합성이 걸린 이야기는 [자세히 → 트랜잭션과 격리 수준](#/post/db-transaction)과도 이어지고, 테이블 설계 쪽은 [자세히 → 정규화와 모델링](#/post/db-normalization)에서 다룬다.

## 흔한 오해

- 인덱스를 만들면 무조건 빨라진다: 위 `LIKE '%...'`나 함수를 씌운 조건처럼 안 타는 경우가 있다. 만든 뒤에 계획을 봐야 한다.
- 컬럼마다 인덱스를 걸어 두면 안전하다: 쓰기가 느려지고 공간도 쓴다. 컬럼 세 개에 걸었더니 INSERT가 세 배쯤 걸렸다.
- 여러 컬럼 인덱스는 순서가 상관없다: 왼쪽부터 쓰인다. `(city, age)`는 `age`만 조건일 땐 소용이 없었다.
- 인덱스가 있으면 DB가 반드시 그걸 쓴다: DB가 통계를 보고 풀 스캔이 낫다고 판단하면 안 쓴다.
- 인덱스는 B-Tree뿐이다: 아니다. 벡터 검색에 쓰는 HNSW 같은 다른 구조도 있다. [자세히 → 벡터 DB](#/post/db-vector)에서 나온다.
