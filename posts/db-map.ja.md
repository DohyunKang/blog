DB 学習はテーブルと SQL から始まり、高速検索の仕方、同時書き込みの仕方、スキーマ設計の仕方、他の種類の DB、キャッシュ、複数サーバーへの拡張まで続きます。一つずつ別々に見るとどこに属するか混乱してしまうので、まずは 8 つを一行ずつ記述し、さらに知りたいことはリンクから進めるようにしました。順序は「基本 → 高速化 → 安全性 → スキーマ → 種類 → 拡張」です。

## 関係を一覧

```
관계형 DB (테이블 + 키 + SQL)
 ├─ 읽기를 빠르게   → 인덱스 (DB 안에서 찾는 비용을 줄임)
 ├─ 동시에 써도 안전하게 → 트랜잭션·격리 수준
 └─ 테이블을 어떻게 나누나 → 정규화·모델링
관계형이 아닌 저장 방식 → NoSQL, 임베딩을 담는 벡터 DB
DB까지 가지 않게 → 캐시(Redis)
DB 한 대가 모자랄 때 → 복제·샤딩
```

## 1. 基本

**リレーショナル DB と SQL**: データを複数のテーブルに分けて格納し、キーで結びつける方式と、そのテーブルから行を取得・変更する言語です。2 つのテーブルと数行のクエリがあれば、基礎は実際に触ってみることができます。
[詳しく → リレーショナル DB と SQL の基本](#/post/db-rdb-sql)

## 2. 高速化、安全性、適切な形状で

**インデックス**: 値をソートした別々の構造体であるため、条件に一致する行を最初から順次走査せず、即座に見つけ出します。代わりに毎回同時に更新する必要があり、どこに作成するかを選ぶのが仕事です。
[詳しく → インデックス](#/post/db-index)

**トランザクションと隔離レベル**: 複数のクエリをすべて成功させるか、すべて失敗させるようにまとめる単位がトランザクションであり、同時に実行中の塊同士が互いにどの程度見えるようにするかを決めるのが隔離レベルです。ロックとデッドロックもここから生まれます。
[詳しく → トランザクションと隔離レベル](#/post/db-transaction)

**正規化とモデルリング**: 同じ事実を一つの場所にしか書かないというルールであり、1NF〜3NF はそれを段階に分けたものです。ERD と非正規化についても同じ記事で確認できます。
[詳しく → 正規化とモデルリング](#/post/db-normalization)

## 3. リレーショナル以外のストレージ

**NoSQL**: SQL を捨てたものではなく、データの書き込み形状に合わせて保存方式を変えたものの集合です。Key-Value、Document、Column、Graph の 4 つの形状があり、分散化が加わると CAP 定理の話になります。
[詳しく → NoSQL の種類と選択](#/post/db-nosql)

**ベクトル DB**: エンベッディングを蓄積し、クエリに近いものを素早く見つけてくれる DB です。精度を少し犠牲にして速度を買う近似的検索構造であり、pgvector などの選択肢と専用 DB を比較します。エンベッディング自体は [エンベッディングとベクトル検索](#/post/ai-embedding)、検索結果を LLM に付与する側は [RAG](#/post/ai-rag)にあります。
[詳しく → ベクトル DB](#/post/db-vector)

## 4. 規模が大きくなると

**キャッシュと Redis**: 頻繁に読み取るデータを近くに複製しておくのがキャッシュであり、Redis はその複製をキー・バリューで保持するサーバーです。難しいのは複製がオリジナルと異なった場合の処理です。インデックスが DB 内の探索コストを減らすなら、キャッシュはそもそも DB にアクセスさせません。
[詳しく → キャッシュと Redis](#/post/db-cache-redis)

**レプリケーションとシャーディング**: 単一 DB で耐えられなくなったら、読み取りについては同じデータを複数台に複製するレプリケーションで、書き込みと容量についてはデータを分割するシャーディングに分けます。分割するほど一貫性と利便性を犠牲にします。
[詳しく → レプリケーションとシャーディング](#/post/db-scaling)

## どこから読むか

初めての場合は上から下へ読むのが良いでしょう。すでに SQL を知っている状態でサービスが遅くなった場合なら、インデックス → キャッシュ → レプリケーションとシャーディングの順序が問題解決の順序と似ています。データをどのように分割するか悩んでいる場合は、正規化と NoSQL を一緒に見て比較すると良いでしょう。
