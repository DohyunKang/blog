CSR, SSR, SSG 는「誰が、いつ HTML を生成するか」だけが異なり、どちらが良いかというよりは、ページごとのデータの更新頻度によって使い分けるべきです。

## まず一行ずつ

ブラウザが画面を描画するには結局 HTML が必要です。その HTML を生成するタイミングは 3 つに分かれます。ブラウザが画面を描画する順序については [詳しく → ブラウザが画面を描画する過程](#/post/fe-browser-render) に別途書いておきました。

| | 誰が | いつ | ブラウザが最初にするもの |
|---|---|---|---|
| CSR (Client-Side Rendering) | ブラウザの JavaScript | ページを開いた後 | ほぼ空の HTML + JS |
| SSR (Server-Side Rendering) | サーバー | リクエストが来るたびに | 完成した HTML |
| SSG (Static Site Generation) | ビルド過程 | デプロイする前に一度 | 事前に用意しておいた HTML ファイル |

web.dev のレンダリング記事も同じように分類しています。CSR はブラウザが JavaScript でロジック・データの取得・テンプレート・ルーティングを担当する方式であり、SSR はサーバーが各リクエストに対して完成した HTML を生成する方式で、静的レンダリングはビルド時に URL ごとに HTML ファイルを一つずつ用意しておく方式です。

## CSR: 空の枠を受け取ってブラウザが埋める

CSR でサーバーから渡される HTML は大まかにこの形です。

```html
<body>
  <div id="root"></div>
  <script src="/app.js"></script>
</body>
```

ブラウザが `app.js` をダウンロードして実行し、必要であれば API を呼び出してデータを取得した後、それを `#root` の中身で埋めます。画面にコンテンツが表示されるタイミングは「JS のダウンロード → 実行 → データ要求 → 描画」の後にずれ込みます。

良い点はロードした後の移動が速く、アプリのように滑らかであることです。サーバーは静的ファイルのみを提供すればよいので運用も単純です。悪い点は最初の画面が遅くなりやすいことです。web.dev は JS が大きくなるほど TBT や INP などのインタラクション指標が悪化し、モバイルで速く保ちにくいと述べています。検索エンジンが JS を実行しなければコンテンツが表示されない可能性もあることも知られています。

## SSR: リクエストが来るたびにサーバーが HTML を生成する

SSR はリクエストが来るとサーバーがデータを取得して HTML を完成させて返します。ブラウザは JS が到着する前にも即座にコンテンツを描画できます。web.dev は SSR が通常 FCP が速く、クライアント側の JS が減ると説明しています。逆に各リクエストごとにサーバーが処理を行うため TTFB（最初のバイトが届くまでの時間）が増える可能性があります。

ログインユーザーごとの画面やリアルタイムに近いデータのように、各リクエストで内容が変わるページに適しています。

[詳しく → リクエストが処理される流れ](#/post/be-request-flow) でサーバー側の処理順序を確認できます。

## SSG: ビルド時に事前に用意しておく

SSG は `next build` などのビルド段階でページをすべて HTML ファイルとして用意しておきます。リクエストが来るとサーバーは計算なしにそのファイルをそのまま返します。そのためファイルを CDN にアップロードしやすく、TTFB と FCP が一定して速いです。web.dev も CDN 親和性が高いと述べています。

欠点はコンテンツが変われば再度ビルドが必要であることです。ページ数が数万に増える場合やユーザーごとに異なる内容の場合などは現実的ではないと言われています。ブログ記事、ドキュメント、紹介ページのように一度作ればしばらく変わらない場所に適しています。ファイルを近くから提供する話は [詳しく → CDN とキャッシュ戦略](#/post/infra-cdn-cache) に続きます。

## ハイドレーション: SSR・SSG から派生する概念

SSR や SSG で HTML を受け取ると画面は即座に表示されますが、ボタンを押しても何も起きない区間があります。HTML にはイベントハンドラが付いていないためです。この HTML に JS がイベントと状態を付与して生きたアプリにする過程がハイドレーションです。Next.js のドキュメントでは「静的 HTML にイベントハンドラを付けてインタラクティブにする React のプロセス」と定義しています。

React の `hydrateRoot` はサーバーがすでに作成した HTML の上に React を貼り付けます。

```js
import { hydrateRoot } from 'react-dom/client';

hydrateRoot(document.getElementById('root'), <App />);
```

（このコードはドキュメントの例を移したものなので、実際に実行していません。）

ここで守るべき条件があります。React のドキュメントではクライアントが最初に描画した結果とサーバーから送られた HTML が一致している必要があると述べています。ズレると開発中は警告が表示され、復旧する場合もありますが保証がないため最悪の場合はイベントハンドラが誤った要素に付く可能性があるとして書かれています。ズレる一般的な原因としてドキュメントに含まれるものは以下のものです。

- レンダリング中に `typeof window !== 'undefined'` で分岐するコード
- レンダリング中に `window.matchMedia` などのブラウザ固有の API を使うコード
- サーバーとクライアントで異なるデータを描画する場合

時間とともに必然的に変化する値については、`suppressHydrationWarning` で警告を抑制できますが、これは一度きりの適用に留まります。

ハイドレーションにもコストがかかります。web.dev は、FCP（First Contentful Paint）が改善されても TBT（Total Blocking Time）や INP（Interaction to Next Paint）が悪化する可能性があるとしています。画面は表示されているのにスクリプトが実行中であるため、ユーザー入力が無視される状態が発生するからです。サーバーから HTML が送信され、クライアント側で同じ UI コードを再度実行するため、「二度手間」と指摘されています。

## 混在させる方式：ISR とサーバーコンポーネント

現実的には、3 つの選択肢のうち 1 つだけを使うことは稀です。

ISR（Incremental Static Regeneration）は、SSG の「変更があったら再ビルド」の問題を軽減する手法です。Next.js のドキュメントに基づくと動作は以下の通りです。ビルド時に作成されたページはキャッシュから即座に除外されます。`revalidate = 60` と設定すれば、60 秒経過した後の最初のリクエストには古いページをそのまま返し、同時にバックグラウンドで新しいページを作成します。すべて準備が整うと、その次のリクエストから新しいページが返されます。ドキュメントでは `revalidate` の値を 1 秒ではなく 1 時間程度に高く設定することを推奨しており、細かく変更したい場合は `revalidatePath` や `revalidateTag` などのオンデマンド方式を使うよう指示されています。リアルタイムデータが必要な場合は動的レンダリングへ移行するよう勧められています。

Next.js の App Router はコンポーネント単位で混在させます。レイアウトとページはデフォルトでサーバーコンポーネントであり、状態管理やクリックイベントが必要となる部分のみ `'use client'` を付与したクライアントコンポーネントを使用します。初回のロードでは、サーバーコンポーネントの結果（RSC Payload）とクライアントコンポーネントを用いて HTML を事前に生成して送信し、ブラウザがその HTML を即座に表示した後、JS によってクライアントコンポーネントのみをハイドレーションします。以降のページ遷移では RSC Payload を事前に受け取ってキャッシュに保存しておき、クライアントコンポーネントはサーバー HTML に依存せずブラウザ上で描画します。ドキュメントによれば、この方法によりブラウザへ送信される JS の量を削減できるとのことです。状態管理に関連する話は [詳細 → 状態管理](#/post/fe-state) を参照してください。

## 選択の基準

質問順に見てみると以下のようになります。

| 質問 | 方向性 |
|---|---|
| コンテンツが訪問者と無関係で、頻繁に変更されないか | SSG（変更周期がある場合は ISR） |
| リクエストごと、またはユーザーごとにコンテンツが変わるか | SSR |
| ログイン後のダッシュボードのようにアプリに近いもので、検索露出は重要でないか | CSR |
| 1 ページ内に静的部分とインタラクション部分が混在するか | サーバーコンポーネント + クライアントコンポーネント |

パフォーマンスに関する考慮事項については、[詳細 → フロントエンドパフォーマンス](#/post/fe-performance) で指標と共に確認すると理解しやすいです。

## よくある誤解

- SSR は CSR より常に速い：初回表示（FCP）は速いが、サーバーが各リクエストで処理を行うため TTFB（Time to First Byte）は増える可能性があり、ハイドレーションが完了する前にはクリックしても反応しない。
- SSG は静的なのでデータを使えない：ビルド時にデータを取得して HTML に埋め込んでいるだけである。ただし、ビルド後の値の変更は反映されない。ISR がその隙間を埋める。
- ハイドレーションすると HTML を再描画する：既存の HTML に React を追加するため、サーバーと同じ結果を出すという前提がある。再描画ではないため、不一致になると問題となる。
- フレームワークを使えばこの選択は気にしなくてよい：Next.js はルートごとに静的・動的を分け、コンポーネント単位でサーバー・クライアントを切り分けるため、選択肢が消えるのではなくコード内部に組み込まれる。

<details>
<summary>詳細な解説：指標用語</summary>

- TTFB: リクエストを送信してからレスポンスの最初のバイトが到着するまでの時間。
- FCP: 画面に最初のコンテンツ（文字や画像）が描画される時点。
- TBT: メインスレッドがブロックされ、入力に対して反応しなかった時間の合計。
- INP: ユーザーがクリックまたは入力した際、次の画面変化までにかかる反応速度。

web.dev の記事では、SSR と静的レンダリングはクライアント側 JS を削減するため TBT や INP に有利であると報告しており、CSR はバンドルサイズが大きくなるほど最も影響を受けるとまとめている。この記事の図表には TTI という古い指標も登場するが、本稿での比較は TBT・INP を基準としている。

</details>

<details>
<summary>詳細な解説：プリレンダリングとストリーミング</summary>

プリレンダリング（prerendering）とは、CSR アプリをビルド時に一度実行して最初の HTML だけを抽出して保存する方式である。FCP は改善されるが、実際にインタラクションを行うには JS の必要がある。前述の SSG と多くの共通点を持つが、web.dev は両者を区別して説明している。

web.dev はハイドレーションコストを削減する方法として、ストリーミング SSR と段階的・部分的ハイドレーションを挙げている。ただし、部分的ハイドレーションは実装が難しいと記載されている。Next.js のドキュメントには、サーバーコンポーネントがコンテンツを段階的にクライアントにストリーミングするという記述がある。

</details>

<details>
<summary>詳細な解説：ISR のレスポンス状態を確認</summary>

Next.js のドキュメントによると、ISR が有効化されたページのレスポンスには `x-nextjs-cache` ヘッダーが付与され、その値は 4 つあります。

- `HIT`: キャッシュから返す
- `STALE`: キャッシュから返しつつバックグラウンドで再構築中
- `MISS`: キャッシュに存在しないため新規レンダリング
- `REVALIDATED`: オンデマンドで再構築される

注意点もドキュメントに記載されています。静的エクスポート（static export）では ISR は機能せず、複数のインスタンスを起動するとデフォルトのファイルキャッシュが各インスタンスごとに独立するため、オンデマンド再検証はコールされたインスタンスのみが対象となります。

</details>
