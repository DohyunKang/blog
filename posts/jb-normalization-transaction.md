정규화는 같은 사실이 여러 곳에 적혀서 생기는 문제를 표를 쪼개 없애는 일이고, 트랜잭션은 여러 작업을 전부 되거나 전부 안 되게 묶는 일이다. 정보처리기사 데이터베이스 단원에서 이 둘은 거의 매번 나온다. 시험 일정과 응시료는 쓰지 않고, 필요하면 공식 사이트에서 확인하면 된다.

## 정규화가 왜 필요한지

표 하나에 학생, 과목, 담당 교수를 다 넣었다고 해 보자. 교수 이름이 학생 수만큼 반복해서 적힌다. 이런 중복에서 이상현상(anomaly)이 생긴다. 시험에서는 세 가지를 구분해서 묻는다.

| 이상현상 | 언제 생기나 | 예 |
| --- | --- | --- |
| 삽입 이상 | 원하지 않는 값이 같이 있어야 넣을 수 있다 | 수강생이 없는 새 과목은 행을 만들 수 없다 |
| 삭제 이상 | 한 행을 지웠더니 다른 정보도 같이 사라진다 | 마지막 수강생을 지우니 과목 정보가 없어진다 |
| 갱신 이상 | 중복된 값을 일부만 고쳐서 모순이 생긴다 | 교수 이름을 두 행만 바꿔서 한 과목에 이름이 둘이다 |

정규화는 이걸 막으려고 함수적 종속성을 기준으로 표를 나누는 과정이다. 데이터베이스 기본 개념은 [자세히 → 데이터베이스 기본과 데이터 모델](#/post/jb-db-concept)에 따로 정리했다.

## 함수적 종속성부터

정규형 문제는 결국 종속성을 읽을 수 있느냐다. A를 알면 B가 하나로 정해질 때 B는 A에 함수적으로 종속된다고 하고 A → B로 쓴다. 학번 → 이름처럼 쓴다.

- 완전 함수 종속: 기본키 전체를 알아야 값이 정해진다. 복합키 (학번, 과목)에서 성적이 그렇다.
- 부분 함수 종속: 복합키의 일부만 알아도 값이 정해진다. (학번, 과목)에서 학번만으로 이름이 정해지면 이름은 부분 종속이다.
- 이행 함수 종속: A → B, B → C라서 A → C가 거치는 경로로 성립한다. 학번 → 학과, 학과 → 학과장이면 학번 → 학과장은 이행 종속이다.

## 정규형 순서

정규형은 앞 단계를 만족한 상태에서 다음 조건을 더 붙이는 구조다.

| 정규형 | 추가 조건 | 없애는 것 |
| --- | --- | --- |
| 제1정규형(1NF) | 모든 속성이 원자값 | 한 칸에 값 여러 개 |
| 제2정규형(2NF) | 부분 함수 종속 제거 | 복합키 일부에 종속된 속성 |
| 제3정규형(3NF) | 이행 함수 종속 제거 | 일반 속성을 거친 종속 |
| BCNF | 모든 결정자가 후보키 | 후보키가 아닌 결정자 |
| 제4정규형(4NF) | 다치 종속 제거 | 서로 무관한 다중값 속성 조합 |
| 제5정규형(5NF) | 조인 종속 제거 | 후보키를 통하지 않는 조인 종속 |

외우기는 이렇게 했다. 1NF는 칸 하나에 값 하나, 2NF는 키 일부에 매달린 속성 치우기, 3NF는 키가 아닌 속성을 거쳐 가는 종속 치우기, BCNF는 결정자는 전부 후보키여야 한다.

<details>
<summary>예제로 보는 2NF와 3NF 분해</summary>

수강(학번, 과목, 이름, 학과, 학과장, 성적) 표가 있고 기본키는 (학번, 과목)이라고 하자.

1. 학번 → 이름, 학과가 성립한다. 키 일부에 종속된 부분 종속이다. 2NF로 가려면 분리한다.
   - 학생(학번, 이름, 학과, 학과장)
   - 수강(학번, 과목, 성적)
2. 학생 표에서 학과 → 학과장이 성립한다. 학번 → 학과 → 학과장 이행 종속이다. 3NF로 가려면 또 분리한다.
   - 학생(학번, 이름, 학과)
   - 학과(학과, 학과장)

분해할 때는 다시 조인했을 때 원래 데이터가 그대로 복원되어야 한다(무손실 조인). 함수적 종속성도 잃지 않아야 한다(종속성 보존). 풀이할 때 이 두 조건을 확인하는 습관을 들였다.
</details>

## 반정규화

정규화를 많이 하면 표가 쪼개져서 조회할 때 조인이 늘어난다. 성능이 문제가 되면 일부러 중복을 허용하는 반정규화를 한다. 시험에서는 정규화의 반대 개념이라는 점, 조회 성능을 올리는 대신 무결성을 더 신경 써야 한다는 점을 묻는다. 물리 설계 쪽 이야기는 [자세히 → DB 물리 설계와 분산 DB](#/post/jb-physical-design)로 이어진다.

## 트랜잭션과 ACID

트랜잭션은 하나의 논리적 작업 단위다. 계좌 이체는 출금과 입금이 둘 다 되어야 의미가 있어서, SQL 문 두 개를 하나로 묶는다. 이 묶음이 지켜야 할 네 가지 성질이 ACID다.

| 성질 | 뜻 | 보장하는 쪽 |
| --- | --- | --- |
| 원자성(Atomicity) | 전부 실행되거나 전혀 실행되지 않는다 | 회복 기법 |
| 일관성(Consistency) | 실행 전후에 제약 조건이 지켜진다 | 무결성 제약 |
| 격리성(Isolation) | 실행 중 중간 결과를 다른 트랜잭션이 못 본다 | 동시성 제어 |
| 지속성(Durability) | 커밋한 결과는 장애가 나도 남는다 | 로그 |

원자성을 SQLite로 직접 돌려 봤다. 잔액이 0 미만이면 안 되는 제약을 걸고, 이체 도중 제약을 어기게 했다.

```python
import sqlite3
c = sqlite3.connect(":memory:", isolation_level=None)
c.execute("create table acct(id integer primary key, bal int check(bal>=0))")
c.execute("insert into acct values(1,1000),(2,0)")
try:
    c.execute("begin")
    c.execute("update acct set bal=bal-300 where id=1")
    c.execute("update acct set bal=bal+300 where id=2")
    c.execute("update acct set bal=bal-900 where id=1")  # 700-900 < 0
    c.execute("commit")
except sqlite3.IntegrityError as e:
    c.execute("rollback")
    print("rollback:", e)
print(c.execute("select * from acct").fetchall())
```

실행하면 `rollback: CHECK constraint failed: bal>=0`이 나오고 잔액은 `[(1, 1000), (2, 0)]`로 처음 상태 그대로다. 앞의 두 UPDATE가 성공했는데도 롤백하니 같이 사라졌다. 이게 원자성이다. 이 흐름의 SQL 문법(COMMIT, ROLLBACK, SAVEPOINT)은 [자세히 → SQL 응용](#/post/jb-sql-basic)에서 이어진다.

## 동시성 제어와 격리 수준

여러 트랜잭션이 동시에 돌 때 격리가 깨지면 이런 현상이 생긴다.

- 갱신 손실: 두 트랜잭션이 같은 값을 읽고 각자 고쳐서 한쪽 결과가 덮어써진다.
- 더티 리드(Dirty Read): 커밋 안 된 다른 트랜잭션의 값을 읽는다.
- 반복 불가능 읽기(Non-repeatable Read): 같은 행을 두 번 읽었는데 그 사이 다른 트랜잭션이 고쳐서 값이 다르다.
- 팬텀 리드(Phantom Read): 같은 조건으로 두 번 조회했는데 새 행이 생겨서 결과 행 수가 다르다.

표준 격리 수준 네 단계와 허용 현상은 PostgreSQL 문서의 표로 확인했다.

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| Read Uncommitted | 허용 | 허용 | 허용 |
| Read Committed | 방지 | 허용 | 허용 |
| Repeatable Read | 방지 | 방지 | 허용 |
| Serializable | 방지 | 방지 | 방지 |

표는 SQL 표준 기준이고 실제 제품은 다르게 구현한다. 예를 들어 PostgreSQL은 Read Uncommitted를 지정해도 내부에서는 Read Committed처럼 동작하고, Repeatable Read에서도 팬텀이 생기지 않는다. SQLite는 기본적으로 모든 트랜잭션이 직렬 가능(SERIALIZABLE) 수준이다. 시험 답은 표준 표를 기준으로 쓰면 된다.

격리 수준이 높을수록 안전한 대신 동시에 처리할 수 있는 양이 줄어든다. 시험에서는 이 트레이드오프가 자주 나온다.

### 동시성 제어 기법

| 기법 | 핵심 |
| --- | --- |
| 로킹 | 데이터에 잠금을 걸어 접근을 제어한다. 공유(읽기)·전용(쓰기) 잠금이 있다 |
| 2단계 로킹(2PL) | 잠금을 늘리기만 하는 확장 단계와 풀기만 하는 축소 단계로 나눈다. 직렬 가능성을 보장한다 |
| 타임스탬프 | 시작 시각 순서로 작업 순서를 정한다 |
| 낙관적 검증 | 일단 실행하고 커밋 직전에 충돌을 검증한다 |
| 다중 버전(MVCC) | 데이터의 여러 버전을 두어 읽기가 쓰기를 막지 않게 한다 |

<details>
<summary>교착상태와 2PL 정리</summary>

2PL은 직렬 가능성은 보장하지만 교착상태(deadlock)는 막지 못한다. T1이 A를 잡고 B를 기다리고, T2가 B를 잡고 A를 기다리면 서로 영원히 기다린다. 대응은 크게 세 방향으로 정리했다.

- 예방: 필요한 잠금을 한 번에 요청하거나 자원에 순서를 둔다.
- 회피: 요청을 받을 때마다 교착이 생길지 검사해서 안전할 때만 허용한다.
- 탐지와 회복: 대기 그래프에 사이클이 생기면 교착으로 보고 희생자 트랜잭션을 하나 롤백한다.

SQLite 문서에는 WAL 모드에서 읽기 트랜잭션이 쓰기로 올라가려는데 그 사이 다른 연결이 커밋하면 `SQLITE_BUSY_SNAPSHOT`이 난다고 나온다. 그래서 쓸 예정이면 `BEGIN IMMEDIATE`로 처음부터 쓰기 잠금을 잡으라고 한다. 시험 범위는 아니지만 잠금과 스냅샷이 실제로 어떻게 보이는지 이해하는 데 도움이 됐다.
</details>

## 회복

장애가 나면 원자성과 지속성을 지키기 위해 로그를 쓴다. 로그에는 트랜잭션 ID, 대상 데이터, 변경 전 값(Before Image)과 변경 후 값(After Image)이 들어간다.

| 기법 | 동작 |
| --- | --- |
| REDO | 커밋된 트랜잭션을 로그의 후행 값으로 다시 실행한다 |
| UNDO | 커밋 안 된 트랜잭션을 로그의 선행 값으로 되돌린다 |
| 즉시 갱신 | 커밋 전에도 DB에 바로 반영한다. 장애 시 REDO·UNDO가 모두 필요할 수 있다 |
| 지연 갱신 | 커밋 때 반영한다. 보통 REDO만 있으면 된다 |
| 체크포인트 | 특정 시점까지 반영을 확정해 두어 복구 범위를 줄인다 |
| 그림자 페이징 | 로그 대신 페이지 복사본을 두고 커밋 때 바꿔 끼운다 |

체크포인트 문제는 로그를 보고 "이 트랜잭션은 REDO, 저 트랜잭션은 UNDO"를 가르는 유형이 많다. 체크포인트 이전에 커밋된 트랜잭션은 이미 반영돼서 할 일이 없고, 체크포인트 이후에 커밋된 건 REDO, 장애 시점에 커밋 못 한 건 UNDO로 푼다.

## 자주 나오는 유형과 푸는 순서

- 이상현상 구분: 삽입·삭제·갱신 중 어느 상황인지 행을 지우고 넣어 보며 확인한다.
- 정규형 판별: 기본키를 먼저 정하고, 종속성을 화살표로 쓴 뒤, 부분 종속 → 이행 종속 → 결정자 순으로 본다.
- ACID 짝 맞추기: 원자성은 회복, 격리성은 동시성 제어, 지속성은 로그와 짝으로 외운다.
- 격리 수준 표: 낮은 수준일수록 허용 현상이 늘어나는 구조로 표를 빈칸 채우듯 그린다.
- 회복 기법: 체크포인트와 커밋 시점을 선으로 그려 REDO·UNDO를 나눈다.

기출문제 원문은 옮기지 않았다. 최근 기출은 공식 사이트나 기출 제공 서비스에서 직접 풀어 보는 게 맞다.
