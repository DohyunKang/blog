GraphRAG 는 문서から LLM でエンティティと関係を抽出し知識グラフを作成し、互いに近いエンティティのグループ（コミュニティ）ごとにサマリーを事前に用意しておき、質問時に使用する RAG です。Microsoft Research が 2024 年に論文とブログで公開し、オープンソースライブラリもあります。

## 通常の RAG の弱点

[RAG](#/post/ai-rag) は、質問と似たチャンク数個を検出して [LLM](#/post/ai-llm) に提示する方式です。特定の事実を問う質問には適しています。しかし GraphRAG の論文は、RAG が「文書全体の質問」に失敗すると述べています。例示された質問は「このデータセットの主要なトピックは何ですか」です。このような質問は検索問題ではなく、クエリ中心のサマライゼーション（query-focused summarization）の問題であるというのが論文の見解です。逆に既存のサマライゼーション手法は、RAG が扱うテキスト量まで拡張できないとのことです。

Microsoft のブログは 2 つの弱点を指摘しています。

- 複数の文書に散らばった情報を共通属性でつなぐこと（「点を繋ぐ」）が苦手です。
- 大規模な文書コレクション全体を理解する必要がある質問には弱いです。ベクトル類似度検索のため、「上位 5 つのトピック」と問うと、データの実際の内容ではなく「トピック」という単語が含まれた文章がヒットしてしまいます。

ブログでは、2023 年 6 月のロシア・ウクライナニュース記事データセットである VIINA を示しています。「Novorossiya とは何ですか」という質問にはどちらも正しく答えましたが、「Novorossiya は何をしたか」という質問については通常の RAG が答えられず、GraphRAG は根拠の抽出と共に答えました。このデータはモデル学習時点以降の資料であるため選ばれたとのことです。

## GraphRAG が行うこと

公式ドキュメントは GraphRAG を「構造的で階層的な RAG」と紹介しています。インデックス化（indexing）段階の流れは以下の通りです。

```
[색인 단계, 미리 한 번 — LLM이 많이 쓰인다]
문서 → TextUnit(청크) → 엔티티·관계·주장 추출 → 지식그래프
     → Leiden 방식으로 계층 군집화(커뮤니티) → 커뮤니티별 요약을 아래에서 위로 생성

[질문 단계]
Global: 커뮤니티 요약들 → 요약마다 부분 답 → 부분 답을 합쳐 최종 답
Local : 특정 엔티티 → 이웃 엔티티·관련 개념으로 퍼져 나가며 찾음
```

| 段階 | 行うこと | 関連記事 |
|---|---|---|
| チャンク分割 | 入力コーパスを TextUnit に分割する | [RAG](#/post/ai-rag) |
| 抽出 | エンティティ・関係・主要主張を LLM で抽出する | [知識グラフ](#/post/ai-knowledge-graph), [オントロジー・トリプル](#/post/ai-ontology-triple) |
| クラスタリング | グラフを Leiden アルゴリズムで階層的クラスタリングする | [グラフ DB](#/post/ai-graph-db) |
| サマライゼーション | 各コミュニティと構成要素のサマリーを下から作成する | |

通常の RAG は「似た文章断片」を検出しますが、GraphRAG は「接続されたエンティティのグループとそのサマリー」を検出するという点が異なります。チャンクはベクトルで検索する際に [埋め込み](#/post/ai-embedding) が使われる一方、グラフはエンティティ間の接続を辿ります。

## 4 つの質問方式

公式ドキュメントが分類する検索方式是以下の通りです。

| 方式 | 適した質問 |
|---|---|
| Global Search | コーパス全体に対する大きな質問。コミュニティサマリーを利用します |
| Local Search | 特定のエンティティに関する質問。近隣と関連概念に広がります |
| DRIFT Search | Local と似ていますが、コミュニティ情報が文脈として加わります |
| Basic Search | 通常の top-k ベクトル検索。通常の RAG で十分な質問用です |

ドキュメントが Basic Search を併記している点が目立ちます。すべての質問にグラフが必要ないという解釈ができます。

## 論文で得られた結果

論文は、約 100 万トークンのデータセットでグローバル理解（global sensemaking）に関する質問をテストしました。通常の RAG ベースラインと比較して、回答の包括性（comprehensiveness）と多様性（diversity）が大幅に向上したと報告しています。ブログでも同様に、LLM エバリュエーターが包括性・多様性・根拠提示の面で GraphRAG を一貫してより良い方へ選んだと述べられています。一方、SelfCheckGPT で測った忠実性（faithfulness）は通常の RAG と似ており、ブログでは評価フレームワークはまだ開発中であると書かれています。回答は出典テキストを引用して原文と比較できます。

## 何时使用，何时普通 RAG 就足够了

ここからは上記資料の性質から読み取れる区別です。

| 状況 | 選択 |
|---|---|
| 「この契約書の解約条項は何ですか」などの特定の事実質問 | 通常の RAG |
| 1 つの文書か小規模でそのまま投入できる場合 | 通常の RAG（または単にコンテキストに入れる、[コンテキストウィンドウ](#/post/ai-context-window)） |
| 「資料全体の主要トピック・流れは何ですか」 | GraphRAG Global |
| 複数の文書に散らばる人物・組織・事象の関係を繋ぐ必要がある質問 | GraphRAG Local/DRIFT |
| 頻繁に変更される文書 | 通常の RAG が軽量（インデックスを再実行する負担が少ない） |

最後の行は後述するコストの話につながる推論であり、公式ドキュメントがそう言っているわけではありません。

## コストと複雑さ

GitHub リポジトリの案内文には、GraphRAG インデックスは「高コストな作業となり得る」と記載されており、文書全体を読み込みプロセスとコストを理解した上で小さく始めるよう推奨しています。この文章を作成する際に確認した公式ドキュメントの最初のページやブログ記事には具体的な費用の数字はありませんでした。インデックスでは LLM がすべてのテキストに対してエンティティ抽出とサマリーを実行するという構造上、通常の RAG の 1 回の埋め込み呼び出しよりもはるかに多くの呼び出しが必要になるのは避けられないことです。

公式ドキュメントでは、プロンプトをデータに合わせて手動で調整することを「強く推奨」しています。デフォルト値のままでは最適な結果が得られない可能性があるためです。また、`graphrag init --force` を実行すると設定とプロンプトを上書きしてしまうため、バックアップを取るよう注意喚起もあります。

## よくある誤解

- GraphRAG が通常の RAG を代替する：文書自体に Basic Search を選択肢として用意しています。質問の種類によって分岐します。
- グラフ DB が必要である：この文章で確認した公式ドキュメントのインデックス段階にはグラフ DB の言及はありませんでした。グラフ DB とは何かについては [グラフ DB](#/post/ai-graph-db) の記事で別途扱います。
- ハルシネーションが解消される：論文やブログで報告された忠実度指標は、通常の RAG と同程度のレベルでした ([ハルシネーション](#/post/ai-hallucination))。

<summary>詳細な解説：コミュニティサマリーによる全質問への回答プロセス</summary>

論文の要約を基準にすると、質問が来ると各コミュニティサマリーが部分的な回答を作成し、それらの部分回答を再度サマリーして最終的な回答を導き出します。サマリーは質問の前に事前に作成されているため、質問ごとに原文全体を読むのではなく、サマレイヤーのみを読み込めば済みます。クラスタリングが階層的であるため、大きな束（大きなトピック）から小さな束（詳細なトピック）まで、どの高さのサマリーを使用するかを選択できます。公式ドキュメントもサマリーは下から上で作成されると説明しています。
