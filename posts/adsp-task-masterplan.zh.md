## 如何寻找课题

寻找课题的方式主要有两种：

| | 自下而上 (Bottom-up) | 自上而下 (Top-down) |
|---|---|---|
| 出发点 | 已有待解决的问题 | 未知问题，从数据入手 |
| 适用场景 | 分析对象明确时 | 寻求新洞察时 |
| 流程 | 问题探索 → 问题定义 → 解决方案探索 → 可行性评估 | 假设生成 → 实验 → 实际环境测试 → 假设验证 |
| 工具 | 商业模式、外部参考模型 | 探索性数据分析、无监督学习、原型制作 |

自上而下的问题探索可进一步分为两类：基于内部业务/产品/客户视角的商业模式，以及借鉴相似行业的外部参考模型。探索结果应整理为分析用例（包含问题描述及解决后的预期效果）。随后将此类用案例转化为数据分析问题并进行评估。在最后的可行性评估阶段，需同时考量经济可行性与数据及技术应用的可行性。

在分析规划阶段，需提前考虑以下三点：可用数据、合适的用例、以及针对障碍因素（成本、准确度、组织能力、变革管理）的预先计划。关于“可用人力”的资料并未纳入上述三点，若出现在选项中需格外留意。

## 优先级：紧迫性与难度

无法一次性完成所有找到的课题，因此需要确定执行顺序。判断标准基于两个维度：

| 维度 | 观察内容 |
|---|---|
| 紧迫性 | 战略重要性、目标价值。是现在需要还是将来需要？ |
| 难度 | 数据获取/存储/处理成本、分析应用成本、分析水平 |

将这两个维度相乘，可得到四个象限：

| 紧迫性 | 难度 | 备注 |
|---|---|---|
| 当前 | 简单 | 最优先 |
| 当前 | 困难 | 若优先考虑紧迫性则为第二顺位 |
| 未来 | 简单 | 若优先考虑难度则为第二顺位 |
| 未来 | 困难 | 最后处理 |

中间两个象限的顺序取决于是优先考虑紧迫性还是难度。一份整理资料（IT Wiki）指出，按紧迫性优先排序为 III → IV → II → I，按难度优先排序为 III → II → IV → I。但该资料的编号用法因资料而异，建议以属性特征记忆而非死记数字。因此，背诵时应记住“当前且简单为第一顺位，未来且困难为最后”，若题目中出现四象限图，应先确认轴的名称而非直接套用编号。

核心标准是紧迫性。难度可根据公司实际情况进行调整。对于当前需要但难度较高的课题，也可通过减少数据量或缩小分析范围来降低难度后优先处理。

## 主计划与路线图

主计划是对已确定的课题何时、按何种顺序执行所做的规划。制定优先级时需考虑的因素包括：战略重要性、业务成果（ROI）及执行难易度。

在确定应用范围与方式时，需审视以下三点：

| 要素 | 区分水平的提问 |
|---|---|
| 业务内嵌化 | 是仅提供报告/界面，还是融入业务流程与系统实现自动利用？ |
| 分析数据 | 仅使用内部数据，还是扩展至外部及非结构化数据？ |
| 技术 | 沿用现有系统与技术方案，还是引入新的分析或大数据技术？ |

实施路线图分为三个阶段：

1. **数据分析体系引入**：发掘分析机会、定义课题、制定路线图
2. **数据分析有效性验证**：算法设计、架构设计、试点执行
3. **数据分析推广与深化**：变革管理、系统构建、相关系统升级

先通过试点确认效果，再逐步推广，这一顺序至关重要。诸如“个人信息匿名化”等项目不属于上述考量要素。

## 治理体系

分析治理是指组织为确保持续开展分析工作并将其融入业务而建立的管理体系。其包含五个组成部分。

| 要素 | 内容 |
|---|---|
| Organization(组织) | 分析规划与管理组织的定位与形态 |
| Process(流程) | 课题发掘、规划、执行与管理流程 |
| System(系统) | 用于分析的 IT 系统与工具 |
| Data(数据) | 标准化、质量与安全治理（数据治理） |
| Human Resource(人力资源) | 人员招募、角色定义与培训体系 |

数据治理是分析治理中的一个要素。将两者混为一谈的说法是错误的。

分析组织架构分为三种类型：

| 类型 | 特征 | 弱点 |
|---|---|---|
| 集中型 | 由专职组织负责全公司分析工作 | 可能与业务部门职能重叠 |
| 功能中心型 | 无独立组织，由业务部门直接进行分析 | 难以开展全公司层面的核心分析 |
| 分散型 | 将分析人员配置到业务部门 | 但有利于最佳实践的共享 |

课题管理遵循以下顺序：课题发掘（创意发掘 → 课题候选提案 → 课题确定）与课题执行（团队组建 → 执行 → 过程管理 → 结果分享与改进）。成果与经验汇入资源池（pool），供后续课题复用。

## 准备度与成熟度

组织的当前分析水平可从两个维度进行诊断。

准备度考察六个领域：分析业务、人员与组织、分析方法、分析数据、分析文化、IT 基础设施。成熟度则从“引入 → 应用 → 推广 → 优化”四个阶段出发，分别针对业务、组织·能力、IT 部门进行评估。

将准备度与成熟度各分为高/低两类，可组合出四种类型：

| 类型 | 准备度 | 成熟度 | 方向 |
|---|---|---|---|
| 准备型 | 低 | 低 | 从分析准备工作开始 |
|  정착형 (定居型) | 低 | 高 | 已开展分析，需系统化地加以巩固 |
| 引入型 | 高 | 低 | 准备充分，可立即引入 |
| 扩散型 | 高 | 高 | 持续推广深化 |

定居型与引入型容易混淆。不应仅凭名称判断，而应依据“准备度与成熟度哪一项更高”来区分：定居型的成熟度高，引入型的准备度高。

## 项目管理十大领域

分析课题也属于项目范畴，因此按 PMBOK 知识领域进行管理。以 PMBOK 第 6 版为标准，共包含十个领域：

| 领域 | 工作内容 |
|---|---|
| 整合 | 协调项目整体要素 |
| 范围 | 定义并控制项目包含的工作内容 |
| 进度 | 估算并控制作业顺序与所需时间 |
| 成本 | 估算并控制预算 |
| 质量 | 确保交付物符合标准 |
| 资源 | 获取并管理团队与资源 |
| 沟通 | 管理向利益相关者传递的信息流 |
| 风险 | 识别、分析、应对与监控风险 |
| 采购 | 从外部供应商获取物资与服务 |
| 干系人 | 识别受影响人员并促使其参与 |

PMBOK 第 7 版（2021）已用八个绩效领域替代了上述知识领域。考试教材所依据的版本，需结合教材说明一并确认。

## 常见题型

- 自上而下与自下而上的区分：若“问题先给出”则为自上而下；若“先看数据”则为自下而上。
- 优先级选项选择：当前·简单者优先，未来·困难者置后；中间选项需确认其依据是紧迫性还是难度。
- 在应用范围、方式三个要素中找出缺失项：业务内化、分析数据、技术。若混入其他无关项则为错误答案。
- 匹配数据治理五大构成要素与三种组织架构类型的特征。
- 类似定居型与引入型，根据准备度与成熟度的高低组合推断类型名称。
- 路线图顺序：体系引入 → 有效性验证（试点）→ 推广与深化。

解题时先观察选项关键词。“试点”对应第 2 阶段，“变革管理”对应第 3 阶段，“创意发掘”对应第 1 阶段，通常可迅速锁定答案。历年真题建议直接在官网或教材中练习。
