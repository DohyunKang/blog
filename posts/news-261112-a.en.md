## What it is
A Python framework that automatically builds a layer on top of a company's databases that says what the numbers mean. That layer is called an ontology: a machine-readable map of concepts and how they relate. [More → Ontology and triples](#/post/ai-ontology-triple)

The first paragraph of the README sums up the problem. Agents can query databases, but a revenue number answered fast is worth nothing if it's wrong. So they need a context layer that says where data lives, what it means, whether to use it, and where it came from.

From the user's side it's a text-to-SQL tool. Text-to-SQL turns a question like "how many orders shipped last week?" into SQL and runs it. The difference is that the model doesn't guess SQL from table names alone. It looks up definitions people have checked first.

## How it works
The ontology holds three things.

- Terms: business concepts like Customer or Invoice Line, with descriptions and synonyms, mapped to real columns.
- SQL attributes: reviewed SQL expressions such as a margin or a rolling total. The agent reuses them, so a metric is computed the same way every time.
- Relationships: how tables join, inferred from keys and from the data itself.

The flow has three stages: generate, certify, answer. Generation reads schemas, samples column values, extracts terms per table, infers joins, and stores it all in Postgres, with embeddings for search in pgvector. Embeddings turn text into number vectors so similar meanings can be found. [More → Embeddings and vector search](#/post/ai-embedding)

Certification is the human part. You test the draft with real questions, fix definitions, and certify the ones that are right. I liked that it doesn't just trust the auto-generated map.

When answering, it extracts the intent and entities, finds candidate terms, columns, and SQL attributes by embedding search, writes SQL, checks filter values and the query against the database, repairs the SQL if a check fails, then runs it. The answer comes with its SQL and the steps taken. In the README example, asking about one product's revenue in Pennsylvania in June 2015 returned $588.80 along with a six-table join.

What caught my eye most was the case where it can't answer. The sample database has no ad spend data, so when asked for return on ad spend, the MCP tool `check_answerable` says first that no term covers "ad spend", and the agent asks back. Much better than inventing a column that sounds right.

## Hooking it up
There's a separate MCP server, so it plugs into Cursor or Claude Desktop with a few lines of config. All tools are read-only and run with the user's own permissions. [More → MCP](#/post/ai-mcp) It also ships three skills for coding agents (setup, management, querying). [More → Skills](#/post/ai-skills) Questions sent to the REST API come back as an SSE stream.

The default models are NVIDIA NIM's Nemotron 3.5 family, split into four roles: reasoning, lighter steps, embedding, and reranking. Each role can be swapped for any OpenAI-compatible endpoint, according to the README. It connects to 10 database engines, including PostgreSQL, MySQL, Snowflake, Databricks, and DuckDB.

## For beginners
For a PM, the idea that lands is pinning the definition of "revenue" in one place. Teams computing revenue differently is an old problem. This turns the fix into a dictionary the agent reads. For someone starting out in development, the Next.js + FastAPI + Postgres/pgvector + MCP setup looks like a good example of applying RAG to SQL. [More → RAG](#/post/ai-rag)

The README has warnings too. Internal ports 3001 and 3002 either have no auth or trust a user header forwarded by the frontend, so keep them on a private network. By default it sends requests to the NVIDIA API catalog. It isn't accepting outside contributions right now. Benchmark results like BIRD point to a separate repo, and I didn't check the numbers.
