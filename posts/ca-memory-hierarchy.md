CPU는 빠른데 메모리는 느리다. 이 차이를 숨기려고 작고 빠른 저장소를 큰 저장소 앞에 겹겹이 둔 것이 메모리 계층이고, 그 중간 층들이 캐시다. [운영체제 개요](#/post/cs-os)에서 가상 메모리와 페이지 폴트를 다뤘는데, 이 글은 그보다 아래인 하드웨어 쪽에서 같은 문제를 본다.

## 계층이라는 모양

위로 갈수록 빠르고 작고 비싸다. 아래로 갈수록 느리고 크고 싸다.

| 층 | 대략의 성격 |
|---|---|
| 레지스터 | CPU 안, 가장 빠르고 개수가 아주 적다 |
| L1, L2, L3 캐시 | CPU 안팎의 SRAM, 층이 내려갈수록 크고 느리다 |
| 주기억장치(RAM) | 프로그램이 실제로 올라가는 곳 |
| 디스크(SSD, HDD) | 전원이 꺼져도 남는 대용량 저장소 |

레지스터는 [CPU와 명령어](#/post/ca-cpu)에서 본 것처럼 명령어가 직접 읽고 쓰는 곳이다. 그 아래 층들은 프로그램이 직접 고르지 않고 하드웨어가 알아서 채우고 비운다. 그래서 코드에는 캐시가 안 보이는데 속도에는 크게 보인다.

## 왜 캐시가 통하나: 지역성

작은 캐시가 큰 메모리의 속도를 흉내 낼 수 있는 건 프로그램의 접근 패턴이 고르지 않기 때문이다. 이 성질을 지역성(locality of reference)이라고 부른다.

- 시간 지역성: 한 번 쓴 데이터를 곧 다시 쓸 가능성이 높다. 반복문의 변수가 그렇다.
- 공간 지역성: 어떤 주소를 쓰면 근처 주소도 곧 쓸 가능성이 높다. 배열을 앞에서부터 훑는 경우가 그렇다.

공간 지역성 때문에 캐시는 필요한 1바이트만 가져오지 않고 블록 단위로 가져온다. 이 블록을 캐시 라인이라고 부른다. 위키피디아의 CPU 캐시 문서는 예로 Pentium 4와 K8의 L1 데이터 캐시가 64바이트 라인을 쓴다고 적는다. 아래 시뮬레이션도 64바이트로 맞췄다.

## 적중과 미스, 그리고 평균 접근 시간

CPU가 찾는 데이터가 캐시에 있으면 적중(hit), 없으면 미스(miss)다. 미스가 나면 아래 층에서 가져와야 해서 오래 걸린다. 적중률이 h일 때 평균 접근 시간은 보통 이렇게 쓴다.

평균 접근 시간 = 적중 시간 + (1 − h) × 미스 때 추가로 드는 시간

적중이 1 단위, 미스가 100 단위 더 든다고 가정하고 계산해 봤다(숫자는 가정이고, 실제 기계 값이 아니다).

| 적중률 | 평균 접근 시간 |
|---|---|
| 99% | 2 |
| 95% | 6 |
| 90% | 11 |

적중률이 9%p 떨어졌을 뿐인데 평균 시간은 5배 넘게 늘었다. 캐시 이야기에서 적중률 몇 퍼센트에 다들 예민한 이유가 이 식에 있다.

<details>
<summary>평균 접근 시간 계산 풀이</summary>

적중 시간 1, 미스 추가 시간 100으로 두고 파이썬으로 계산했다.

```python
for h in (0.99, 0.95, 0.9):
    print(h, 1 + (1 - h) * 100)
# 0.99 2.0 / 0.95 6.0 / 0.9 11.0
```

(실제 출력은 부동소수점 때문에 2.000000000000001처럼 나온다.)
</details>

## 캐시 안에서 어디에 넣나

메모리 주소를 캐시의 어느 자리에 넣을지 정하는 방식이 세 가지다.

- 직접 사상(direct-mapped): 한 주소가 들어갈 자리가 딱 하나다. 단순하고 빠르지만 같은 자리를 쓰는 주소끼리 서로를 계속 내쫓을 수 있다.
- 집합 연관(set-associative): N군데 중 아무 데나 넣는다. N-way라고 부른다.
- 완전 연관(fully associative): 아무 자리나 된다. 미스율은 가장 좋지만 항목이 적을 때만 현실적이다.

위키피디아 문서에 따르면 2-way는 두 배 크기의 직접 사상 캐시와 비슷한 적중률을 내고, 4-way를 넘으면 이득이 작다고 한다.

쓰기는 두 가지 정책이 있다. 쓰기 통과(write-through)는 캐시에 쓸 때마다 메모리에도 쓴다. 쓰기 되돌림(write-back)은 캐시 라인에만 쓰고 '바뀐 라인(dirty)' 표시를 해 둔 뒤, 그 라인이 밀려날 때 메모리에 쓴다.

## 직접 시뮬레이션해 보기

작은 캐시(1KB, 라인 64바이트)를 파이썬으로 흉내 내고 접근 패턴을 바꿔 봤다. 라인이 가득 차면 가장 오래 안 쓴 것을 내보내는 방식이다.

```python
def sim(addrs, size=1024, line=64, ways=1):
    sets = size // line // ways
    st = [[] for _ in range(sets)]
    hit = 0
    for a in addrs:
        b = a // line
        s = b % sets
        if b in st[s]:
            hit += 1
            st[s].remove(b); st[s].append(b)
        else:
            if len(st[s]) >= ways:
                st[s].pop(0)
            st[s].append(b)
    return hit / len(addrs)

print(sim([i * 4 for i in range(4096)]))      # 0.9375
print(sim([i * 64 for i in range(4096)]))     # 0.0
```

4바이트짜리 정수를 순서대로 읽으면 라인 하나(64바이트)에 16개가 들어 있어서, 첫 접근만 미스이고 뒤 15개는 적중이다. 15/16이 0.9375다. 반대로 64바이트씩 건너뛰며 읽으면 매번 새 라인이라 적중이 0이었다. 같은 개수만큼 읽어도 순서에 따라 이만큼 갈린다.

같은 캐시에서 주소 0과 1024를 번갈아 1000번 읽는 경우도 돌렸다. 두 주소가 같은 자리로 매핑돼서 직접 사상은 적중률 0.0, 2-way는 0.998이 나왔다. 위에서 말한 서로 내쫓기(충돌 미스)가 실제로 이렇게 생긴다.

## 2차원 배열을 행으로 읽나 열로 읽나

배열 방향에 따른 차이도 같은 시뮬레이터로 봤다. 64x64 정수 배열을 행 우선으로 저장한다고 놓고, 4KB 4-way 캐시로 돌렸다.

| 순회 방식 | 적중률 |
|---|---|
| 행 단위(저장 순서대로) | 0.9375 |
| 열 단위(건너뛰며) | 0.0 |

위키피디아의 지역성 문서도 C가 행 우선으로 저장하기 때문에 행 단위 순회가 연속 메모리를 읽어 효율이 좋고, 열 단위는 멀리 떨어진 곳을 오가서 미스가 늘어난다고 설명한다. 행렬이 캐시에 다 들어갈 만큼 작으면 차이가 줄어든다고도 한다.

<details>
<summary>실제 컴퓨터에서 재 본 시간</summary>

numpy로 5000x5000 int32 배열(행 우선 저장)의 행 합과 열 합을 각각 5번 재고 가장 빠른 값을 골랐다. 내 PC에서 행 쪽이 약 0.029초, 열 쪽이 약 0.086초로 3배쯤 차이 났다. 이 값은 이 PC와 numpy 구현에 묶인 결과라 다른 환경에서는 달라질 수 있다.

```python
import numpy as np, time
a = np.ones((5000, 5000), dtype=np.int32)
def best(f):
    r = []
    for _ in range(5):
        t = time.perf_counter(); f(); r.append(time.perf_counter() - t)
    return min(r)
rows = best(lambda: [a[i].sum() for i in range(5000)])
cols = best(lambda: [a[:, j].sum() for j in range(5000)])
print(rows, cols, cols / rows)
```
</details>

## 흔한 오해

- 캐시가 클수록 무조건 빠르다: 커질수록 찾는 데 시간이 더 들어서 층을 나눠 둔 것이다.
- 캐시는 프로그래머와 상관없다: 하드웨어가 알아서 관리하지만, 접근 순서를 바꾸는 것만으로 적중률이 달라진다는 걸 위에서 확인했다.
- RAM과 가상 메모리의 디스크 교체는 캐시와 다른 이야기다: 방향은 같다. RAM을 디스크의 캐시처럼 보는 시각도 가능하고, 페이지 교체 정책은 캐시 교체 정책과 같은 질문이다.
