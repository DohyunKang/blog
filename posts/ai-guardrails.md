가드레일은 LLM 서비스가 해서는 안 되는 말과 행동을 막아 두는 안전장치를 통틀어 부르는 말이다. 프롬프트에 "하지 마"라고 적는 것도 가드레일이고, 모델 앞뒤에 검사 코드를 붙이는 것도, 모델이 쓸 수 있는 도구의 권한을 줄이는 것도 가드레일이다.

## 왜 필요한가

[LLM](#/post/ai-llm)은 지시문과 데이터를 둘 다 글자로 받는다. 개발자가 쓴 지시와 사용자가 보낸 글, 웹페이지에서 가져온 내용이 한 덩어리의 텍스트로 모델에 들어간다. 그래서 데이터 안에 지시처럼 생긴 문장이 섞여 있으면 모델이 그걸 따를 수 있다. 가드레일이 필요한 이유가 대부분 여기서 나온다.

기업이 서비스를 운영할 때 걱정하는 건 크게 세 가지다.

| 걱정 | 무슨 일이 생기나 | OWASP 항목 |
|---|---|---|
| 프롬프트 인젝션 | 입력이 모델의 동작을 의도와 다르게 바꾼다 | LLM01 |
| 민감정보 유출 | 개인정보·내부 문서·키 같은 게 답변에 섞여 나간다 | LLM02 |
| 과도한 권한의 에이전트 | 모델이 필요 이상의 도구와 권한으로 피해를 낸다 | LLM06 |

OWASP는 웹 보안 Top 10으로 유명한 곳인데, LLM 애플리케이션용 Top 10도 따로 낸다. 2025년판에는 위 셋 말고도 공급망, 데이터·모델 오염, 부적절한 출력 처리(LLM05), 시스템 프롬프트 유출(LLM07), 벡터·임베딩 약점(LLM08), 잘못된 정보(LLM09), 무제한 소비(LLM10)가 들어 있다. 이 글은 위 표의 세 가지에 집중한다.

## 프롬프트 인젝션

OWASP의 정의는 입력이 LLM의 동작이나 출력을 의도하지 않은 방향으로 바꾸는 것이다. 사람 눈에 안 보이는 입력이어도 모델이 읽을 수 있으면 해당된다. 두 갈래가 있다.

| 유형 | 누가 넣나 | 예 |
|---|---|---|
| 직접 | 서비스 사용자 본인이 입력창에 | 챗봇에 "앞의 지시는 무시해" 같은 문장을 보낸다 |
| 간접 | 모델이 읽어 오는 외부 내용 안에 | 웹페이지, 메일 본문, 업로드 파일, 도구 결과에 지시문이 들어 있다 |

탈옥(jailbreak)은 직접 인젝션의 한 형태로, 모델의 안전 규칙을 아예 우회하려는 시도다.

Anthropic 문서는 두 갈래의 위협 모델이 다르다고 설명한다. 직접 쪽은 사용자가 공격자다. 간접 쪽은 사용자는 믿을 만하지만 모델이 읽는 제3자 콘텐츠에 공격 문장이 들어 있다. [RAG](#/post/ai-rag)로 문서를 끌어오거나 [도구 호출](#/post/ai-tool-use)로 웹을 읽는 서비스일수록 간접 쪽 비중이 커진다.

OWASP는 영향이 서비스 맥락과 모델이 가진 권한 크기에 따라 달라진다고 적는다. 시스템 프롬프트 유출, 틀린 출력, 연결된 시스템에서의 명령 실행까지 범위가 넓다. 그리고 이 문제를 완전히 막는 방법은 없고 피해를 줄이는 쪽이라고 분명히 말한다.

## 민감정보 유출

OWASP가 말하는 민감정보는 개인정보, 금융·건강 기록, 기업 기밀, 인증 정보, 법률 문서 등이다. 모델이 학습한 내용이나, 서비스가 프롬프트에 붙여 준 내부 문서가 답변으로 새어 나오는 것이 문제다.

OWASP가 드는 대응은 다음과 같다.

- 학습·입력 데이터에서 민감정보를 가리거나 지운다(마스킹, 패턴 기반 삭제)
- 사용자와 프로세스에 필요한 데이터만 접근시킨다(최소 권한)
- 모델이 접근할 수 있는 외부 데이터 소스를 제한한다
- 사용자에게 민감정보를 입력하지 말라고 안내하고, 데이터 보관·사용 정책을 공개한다
- 시스템 초기 설정을 사용자가 바꾸거나 읽지 못하게 한다

같은 페이지에 이런 문장도 있다. 출력 종류를 제한하는 시스템 프롬프트 지시는 프롬프트 인젝션으로 우회될 수 있으니 그것만 믿으면 안 된다. 그래서 "답변에 이런 건 쓰지 마"라는 문장보다, 애초에 모델 손에 그 데이터가 안 들어가게 하는 쪽이 앞선다.

## 과도한 권한의 에이전트

[에이전트](#/post/ai-agent-loop)는 모델이 도구를 골라 쓰면서 일을 진행한다. OWASP는 모델의 출력이 예상 밖이거나 모호하거나 조작되었을 때 피해를 내는 것을 과도한 권한(Excessive Agency)이라고 부른다. 원인은 환각, 직접·간접 인젝션, 오염된 확장 기능이나 다른 에이전트 등 다양하다. 문서가 꼽는 뿌리는 세 가지다.

| 뿌리 | 뜻 | 방향 |
|---|---|---|
| 과도한 기능 | 서비스에 필요 없는 도구까지 붙어 있다 | 도구 수와 기능을 줄인다 |
| 과도한 권한 | 필요보다 넓은 접근 권한, 또는 모든 걸 하는 공용 계정으로 실행 | 읽기 전용 등 최소 범위, 사용자 본인 권한으로 실행 |
| 과도한 자율 | 영향이 큰 행동을 검증이나 승인 없이 실행 | 사람 승인 |

특히 셸 실행처럼 범위가 열려 있는 도구보다 목적이 좁은 전용 도구를 쓰라는 권고가 눈에 띈다. 허용 여부 판단은 모델에게 맡기지 말고 연결된 시스템 쪽에서 권한 검사로 강제하라고 한다. [MCP](#/post/ai-mcp)로 외부 도구를 붙일 때도 같은 기준이 적용된다.

## 방어는 겹겹이

공식 가이드들을 나란히 놓으면 방어가 네 층으로 정리된다.

```
사용자 입력 → [1 입력 검사] → 모델 → [2 출력 검사] → 도구 실행 → [3 권한 최소화] → [4 사람 승인] → 실제 반영
```

| 층 | 하는 일 | 근거 |
|---|---|---|
| 1 입력 검사 | 알려진 공격 패턴 필터, 가벼운 모델로 위험 입력 사전 분류, 입력 길이 제한 | Anthropic, OpenAI, OWASP |
| 2 출력 검사 | 기대한 형식인지 코드로 검증, 관련성·근거성 평가, 모더레이션, 출력 토큰 제한 | OWASP, OpenAI |
| 3 권한 최소화 | 필요한 도구만, 읽기 전용, 샌드박스, 비밀값은 아예 안 보여 주기 | OWASP, Anthropic |
| 4 사람 승인 | 영향이 큰 행동과 고위험 분야의 결과는 사람이 확인 | OWASP, OpenAI |

### 1. 입력 검사

Anthropic 문서는 사용자 입력이 메인 모델에 가기 전에 가벼운 모델로 먼저 걸러 보라고 한다. 응답을 "위험한가, 아닌가" 같은 단순 분류로 제한하고 구조화된 출력으로 받아서 코드가 분기하게 하는 식이다. 알려진 인젝션 패턴을 필터링하는 입력 검증, 거절하는 방법까지 적어 둔 시스템 프롬프트도 같이 쓰라고 한다. OpenAI 가이드는 입력 길이를 제한하면 인젝션 위험이 줄고, 자유 입력 대신 검증된 드롭다운을 쓸 수 있으면 그쪽이 낫다고 한다.

간접 인젝션 쪽은 구조가 핵심이다. Anthropic 문서의 권고를 추리면 이렇다.

- 외부 콘텐츠는 시스템 프롬프트나 일반 사용자 메시지가 아니라 도구 결과(tool_result) 칸에만 넣는다
- 그 콘텐츠가 무엇이고 어디서 왔는지 도구 설명이나 결과 구조에 밝힌다
- 도구·문서·검색 결과는 신뢰할 수 없는 데이터이고 지시를 바꿀 수 없다고 시스템 프롬프트에 명시한다
- 외부 문자열은 JSON으로 감싸서 데이터와 지시의 경계를 분명하게 한다
- 도구가 돌려준 내용도 같은 방식의 가벼운 모델 검사를 거친 뒤에 모델에 전달한다

### 2. 출력 검사

OWASP는 기대하는 출력 형식을 정해 두고 결정적인 코드로 맞는지 확인하라고 한다. 응답이 질문과 관련 있는지, 제공된 자료에 근거했는지도 점검 대상이다. 근거 없는 답을 걸러 내는 일은 [환각](#/post/ai-hallucination) 대응과도 겹친다. OpenAI는 모더레이션 API(무료)와 출력 토큰 상한을 권하고, 가능하면 모델이 새로 쓴 글 대신 검증된 백엔드 콘텐츠(예: 가장 맞는 도움말 문서)를 돌려주라고 한다.

### 3. 권한 최소화

앞 절의 과도한 권한 표가 곧 이 층이다. Anthropic도 성공한 인젝션의 피해를 최소로 만들기 위해 모델이 필요 없는 비밀값에 접근하지 못하게 하고, 도구는 샌드박스에서 돌리고, 권한 범위를 좁게 잡으라고 한다. OWASP는 여기에 사용자 인증 범위로 실행하기, 확장 기능 활동의 로그·모니터링, 속도 제한을 더한다.

### 4. 사람 승인

OWASP는 위험이 큰 행동에 사람 승인(human-in-the-loop)을 두라고 한다. OpenAI 가이드는 고위험 분야와 코드 생성에서 사람이 출력을 검토해야 하고, 검토자가 시스템의 한계를 알고 원본 자료로 확인할 수 있어야 한다고 한다. 메일 발송, 결제, 삭제처럼 되돌리기 어려운 동작이 대표적인 승인 대상이다.

## 운영하면서 같이 할 것

- 배포 전에 일부러 공격 문장이 든 문서·메일·도구 결과로 시험한다. Anthropic은 자기 에이전트를 직접 레드팀하라고 하고, OpenAI와 OWASP도 적대적 테스트를 권한다. 이런 시험은 [평가](#/post/ai-evals)의 한 종류로 묶어 반복하기 좋다.
- 출력을 주기적으로 분석해서 인젝션이 성공한 흔적을 찾고, 프롬프트와 필터를 고쳐 나간다(Anthropic의 지속 모니터링).
- 같은 우회를 반복하는 사용자는 제한하거나 차단한다(Anthropic의 반복 위반자 대응).
- 사용자 계정을 요구하고 사용자별 안정적인 식별자를 API에 같이 보내서, 남용이 생기면 조직 전체가 아니라 해당 사용자로 추적한다(OpenAI의 safety_identifier).
- 신고 창구를 두고 사람이 응답한다.

이런 조각들을 서비스 코드에 묶어 두는 틀을 [하네스](#/post/ai-harness)라고 부르기도 하는데, 가드레일은 그 안에서 모델 앞뒤와 도구 호출 지점에 놓이는 부품에 가깝다.

## 흔한 오해

- 시스템 프롬프트에 "무시하지 마"라고 쓰면 막힌다: 도움은 되지만 OWASP가 완전한 방법은 없다고 못 박는다. 프롬프트는 여러 층 중 하나다.
- 모델이 좋아지면 가드레일이 필요 없다: Anthropic 문서조차 Claude가 원래 이런 공격에 저항력이 있다고 하면서도 추가 단계를 권한다.
- 입력만 막으면 된다: 간접 인젝션은 입력창을 거치지 않고 도구 결과나 문서로 들어온다. 출력과 권한 쪽 층이 따로 필요하다.
- 가드레일은 모델의 일이다: 권한 판단을 모델에게 맡기지 말고 연결된 시스템에서 강제하라는 게 OWASP의 입장이다.

<details>
<summary>자세한 풀이: 간접 인젝션이 왜 어려운가</summary>

모델은 지시와 데이터를 입력 형식으로 완전히 분리해서 받지 않는다. 시스템 프롬프트, 사용자 메시지, 도구 결과가 모두 토큰 열로 들어간다. 그래서 외부 콘텐츠 안의 지시문이 정말 사용자가 시킨 것인지 모델이 스스로 판별해야 하는데, 이 판별이 확률적이라 100%가 될 수 없다.

Anthropic이 권하는 구조 분리(tool_result에만 넣기, 출처 명시, JSON 인코딩)는 이 판별을 쉽게 만들어 주는 장치다. 인용 부호나 태그를 닫아서 지시 영역으로 빠져나오는 경로를 JSON 이스케이프가 막아 준다는 설명이 문서에 있다. 이 장치들이 확률을 낮추더라도 0으로 만들지는 못하기 때문에, 성공했을 때의 피해를 줄이는 권한 최소화와 사람 승인이 뒤에 남는다. 방어 층이 여럿인 이유가 이것이다.

</details>
