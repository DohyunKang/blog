브라우저는 HTML과 CSS를 받아 DOM, CSSOM, 렌더 트리, 레이아웃, 페인트 순서로 화면을 만들고, 이 중 어느 단계가 다시 도느냐가 화면 변경의 비용을 갈랐다.

## 주소를 치고 나서

화면을 그리기 전에 HTML부터 받아야 한다. MDN 문서 기준으로 순서는 이렇다. DNS로 호스트 이름을 IP로 바꾸고, TCP 연결을 맺고(3-way handshake), HTTPS면 TLS 협상을 거친다. 그다음 HTTP GET을 보내고 첫 HTML 조각이 오면 그때부터 해석을 시작한다. 첫 패킷이 도착하기까지 걸린 시간이 TTFB다. 이 앞단은 네트워크 이야기라 [자세히 → 네트워크](#/post/cs-network)에 따로 있다. 여기서는 HTML 첫 조각이 도착한 뒤부터 본다.

## 전체 흐름

| 단계 | 하는 일 | 결과물 |
|---|---|---|
| 파싱(HTML) | 글자를 토큰으로 쪼개 노드 트리로 만든다 | DOM |
| 파싱(CSS) | 규칙을 일반 → 구체 순으로 쌓아 트리로 만든다 | CSSOM |
| 스타일 결합 | DOM과 CSSOM을 합쳐 보이는 노드만 고른다 | 렌더 트리 |
| 레이아웃 | 각 박스의 위치와 크기를 계산한다 | 박스 모델 |
| 페인트 | 박스를 픽셀로 그린다(글자, 색, 테두리, 그림자) | 레이어별 비트맵 |
| 합성 | 레이어를 겹쳐 화면에 올린다 | 화면 |

이 중 앞에서 다섯 개가 이른바 크리티컬 렌더링 패스다. web.dev 문서는 이 경로를 최적화한다는 말을 "이 단계들에 쓰는 시간을 줄이는 것"이라고 설명한다.

## DOM과 CSSOM

HTML은 토큰으로 쪼개져 `<html>`을 뿌리로 하는 노드 트리가 된다. 이게 DOM이다. CSS도 따로 트리가 되는데 이게 CSSOM이다. 브라우저 기본 스타일시트에서 시작해 일반적인 규칙에서 구체적인 규칙으로 덮어 가는 구조라서 트리라고 부른다.

둘은 별개 객체다. DOM은 내용이 뭔지, CSSOM은 그 내용에 어떤 스타일 규칙이 걸리는지를 가진다. 그래서 HTML만 있어도 DOM은 만들 수 있지만, 화면에 그리려면 둘이 만나야 한다.

파싱 중에 `<script>`를 만나면 사정이 달라진다. MDN 문서에 따르면 `async`나 `defer`가 없는 스크립트는 내려받고 실행하는 동안 HTML 파싱을 멈춘다. CSS는 HTML 파싱을 멈추지는 않지만 계산된 스타일을 읽는 JavaScript는 막는다. 그래서 스크립트는 보통 `defer`를 붙이거나 문서 끝에 둔다.

```html
<!-- 파싱을 멈추고 내려받아 실행 -->
<script src="a.js"></script>
<!-- 병렬로 내려받고, 끝나는 대로 실행(순서 보장 없음) -->
<script src="b.js" async></script>
<!-- 병렬로 내려받고, 파싱이 끝난 뒤 문서 순서대로 실행 -->
<script src="c.js" defer></script>
```

참고로 파서 뒤쪽에서는 프리로드 스캐너가 앞서 달리며 CSS, JS, 폰트, 이미지를 미리 받아 둔다. 파싱이 스크립트에 막혀 있어도 다운로드는 그전부터 시작될 수 있다.

## 렌더 트리

DOM과 CSSOM을 합치면 렌더 트리가 된다. 뿌리에서 시작해 화면에 보이는 노드만 방문하면서 맞는 CSS 규칙을 붙이고, 계산된 스타일을 가진 노드로 내보낸다.

안 보이는 노드는 빠진다. `<head>`, `<script>`, `<meta>` 같은 것과 `display: none`인 요소가 그렇다. 여기서 많이 헷갈리는 게 `visibility: hidden`이다. 이건 렌더 트리에 남는다. 자리는 차지하고 안 보이기만 한다. `display: none`은 렌더 트리에서 빠지니까 레이아웃에도 참여하지 않는다.

## 레이아웃

렌더 트리를 뿌리부터 돌면서 각 요소의 정확한 위치와 크기를 뷰포트 기준으로 계산한다. 퍼센트 같은 상대값이 픽셀로 바뀌는 단계다. web.dev 예시가 직관적이다. 부모가 뷰포트의 50%이고 그 안의 자식이 부모의 50%면 자식은 뷰포트 폭의 25%가 된다.

처음 계산하는 것을 레이아웃이라 하고, 그 뒤에 다시 계산하는 것을 리플로우라 부른다(MDN). 같은 계산인데 이름만 시점으로 나뉜다.

## 페인트와 합성

레이아웃이 끝나면 박스를 픽셀로 바꾼다. 글자, 색, 테두리, 그림자, 이미지가 이때 그려진다. 스타일에 따라 비용이 다르다. web.dev는 단색은 싸고 드롭 섀도는 계산이 비싸다고 적는다.

그 뒤 합성 단계가 있다. `opacity`, 3D `transform`, `will-change`가 걸린 요소나 `<video>`, `<canvas>`는 별도 레이어로 올라가 GPU에서 합성될 수 있다. 레이어를 나눠 두면 한 레이어만 다시 그릴 수 있지만, 레이어는 메모리를 쓰니까 남발하면 안 된다고 MDN은 말한다. 스타일, 레이아웃, 페인트를 포함해 메인 스레드 작업이 16.67ms 안에 끝나야 스크롤과 애니메이션이 부드럽다는 기준도 같은 문서에 나온다.

## 리플로우와 리페인트

DOM이나 CSSOM이 바뀌면 브라우저는 이 과정 일부를 다시 해서 어떤 픽셀을 다시 그릴지 정한다. 두 용어를 나눠 보면 이렇다.

| | 리플로우 | 리페인트 |
|---|---|---|
| 뜻 | 크기·위치를 다시 계산 | 모양만 다시 그림 |
| 지오메트리 | 바뀜 | 안 바뀜 |
| 뒤따르는 단계 | 리페인트와 합성까지 | 해당 레이어의 페인트·합성 |
| 예 | 요소 추가·삭제, 너비·글자 크기 변경 | 배경색, 글자색 변경 |

MDN은 리플로우가 일어나면 리페인트와 재합성이 뒤따른다고 적는다. 그래서 리플로우가 더 비싸다. 위 표의 예는 "지오메트리가 바뀌느냐"는 정의에서 끌어낸 것이고, 어떤 속성이 정확히 어느 쪽인지의 전체 목록은 MDN도 이 문서에서는 주지 않았다. 목록이 필요하면 따로 찾아봐야 한다.

MDN이 드는 실제 사례 하나는 이미지다. `width`와 `height` 없이 `<img>`를 두면 일단 자리 없이 레이아웃을 하고, 이미지가 도착해 실제 크기를 알게 되면 레이아웃부터 다시 한다. 속성으로 크기를 미리 적어 두면 자리가 잡혀 있어서 리플로우가 필요 없다.

```html
<!-- 크기 없음: 로딩되면 리플로우 -->
<img src="a.jpg" alt="설명">
<!-- 크기 있음: 자리가 미리 잡힘 -->
<img src="a.jpg" alt="설명" width="800" height="600">
```

## 흔한 오해

- 렌더 트리는 DOM이다: 다르다. 렌더 트리는 DOM에서 안 보이는 것을 뺀 것에 계산된 스타일을 붙인 것이다.
- `display: none`과 `visibility: hidden`은 같다: 앞은 렌더 트리에서 빠지고, 뒤는 자리를 차지한 채 남는다.
- CSS는 파싱과 상관없다: HTML 파싱을 막지는 않지만 스타일을 읽는 스크립트는 막고, 렌더 트리 자체가 CSSOM이 있어야 만들어진다.
- 화면이 떴으니 다 끝났다: MDN은 화면이 로드된 것처럼 보여도 메인 스레드가 큰 스크립트로 바쁘면 스크롤과 탭에 반응이 없을 수 있다고 한다. 이걸 재는 지표가 TTI다.
- 크기를 안 바꾸면 비용이 없다: 색 하나 바꾸는 것도 리페인트는 일어난다. 다만 리플로우보다 싸다.

성능 쪽 이야기는 [자세히 → 프론트엔드 성능](#/post/fe-performance)에서, 서버에서 HTML을 만들어 보내느냐 브라우저가 만드느냐의 문제는 [자세히 → 렌더링 방식](#/post/fe-rendering-modes)에서 이어진다.

<details>
<summary>자세한 풀이: 한 번 더 도는 경우를 JS로 보기</summary>

개념으로만 아는 것과 달리, 코드에서는 아래처럼 읽기와 쓰기가 섞이면 같은 일이 여러 번 일어날 수 있다. 이 부분은 일반적으로 알려진 패턴이다.

```js
const items = document.querySelectorAll('.item');

// 읽기와 쓰기를 번갈아 하는 경우
items.forEach((el) => {
  const w = el.offsetWidth;      // 레이아웃 값을 읽음
  el.style.width = (w + 10) + 'px'; // 레이아웃이 바뀜
});

// 읽기를 먼저 몰아서 하고, 쓰기를 나중에 하는 경우
const widths = [...items].map((el) => el.offsetWidth);
items.forEach((el, i) => {
  el.style.width = (widths[i] + 10) + 'px';
});
```

첫 방식은 값을 읽을 때마다 브라우저가 최신 레이아웃을 맞춰 줘야 해서 레이아웃이 반복될 수 있다. 두 번째는 읽기를 모아서 그 횟수를 줄이는 방식이다.
