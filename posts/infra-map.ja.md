サービス運営を進めていくと、ロードバランサー、CDN、キャッシュ、レートリミット、オートスケーリングといった用語が同時に登場します。これらはすべて、ユーザーから DB へのリクエスト経路のどこかに配置された装置であり、その経路を基準にまずは各項目について一行ずつ記述しました。さらに詳しく知りたい場合は、以下のリンクに進んでください。

## 全体像を見る

```
사용자 → DNS → CDN(엣지 캐시) → 로드밸런서 → 앱 서버 → 캐시 → DB
                                   ↑               ↑
                          레이트 리밋(문 앞에서 제한)   오토스케일링(서버 수 조절)
앱 서버 → (LLM API를 부르는 서비스라면) 큐·캐시·타임아웃을 한 겹 더
```

## 1. まず全体の流れを確認する

**リクエストが通る道**: アドレスバーで Enter を押すと、DNS から DB まで複数の地点を通過しますが、遅い箇所は通常一か所か二か所程度であるため、どこで時間が失われているかを最初に確認する必要があります。
[詳しく → リクエストが通る道](#/post/infra-request-journey)

## 2. 先頭で受け取り・分割する

**CDN とキャッシュ階層**: オリジナルサーバーの応答をユーザーに近い場所に複製して保存するキャッシュ。複製版をいつまで信頼すべきかを `Cache-Control` ヘッダーで決めることが、実際に気をつけるべき点です。
[詳しく → CDN とキャッシュ階層](#/post/infra-cdn-cache)

**ロードバランサー**: 複数のサーバーの前でリクエストを振り分け、故障したサーバーには送らないようにブロックします。振り分け方よりも、故障したサーバーをいかに素早く除外するかが重要だと感じました。
[詳しく → ロードバランサー](#/post/infra-load-balancer)

## 3. 混雑時に耐える

**レートリミットとトラフィック制御**: サーバーが処理できないリクエストを入り口で返却する装置。どのアルゴリズムを採用するかによって、突発的な負荷（バースト）を受け入れる場合もあれば、境界から突破される場合もあります。
[詳しく → レートリミットとトラフィック制御](#/post/infra-rate-limit)

**オートスケーリングと拡張**: サーバーを増やす方法は垂直・水平の二通りあり、自動で増やしたい場合はサーバーが状態を保持していない必要があります。
[詳しく → オートスケーリングと拡張](#/post/infra-autoscaling)

## 4. AI サービスの場合

**AI サービスのサービング構造**: LLM API を呼び出すサービスは遅く、時折失敗し、呼び出しごとにコストがかかるため、リクエスト経路の中間にキュー・キャッシュ・タイムアウトをそれぞれ一層ずつ設ける必要があります。
[詳しく → AI サービスのサービング構造](#/post/infra-ai-serving)
