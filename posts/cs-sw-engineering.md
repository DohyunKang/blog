소프트웨어 공학은 코드를 잘 짜는 법보다 "무엇을 어떤 순서로 만들고, 어떻게 확인하고, 어떻게 고쳐 나갈지"를 다루는 분야다. 큰 줄기만 정리했다.

## 소프트웨어 공학이 뭔지

프로그램이 작으면 혼자 머릿속으로 관리해도 된다. 사람이 늘고 기간이 길어지면 문제가 달라진다. 뭘 만들어야 하는지 서로 다르게 이해하고, 고치다가 다른 데가 깨지고, 납기가 밀린다. 소프트웨어 공학은 이런 문제를 줄이려고 만든 방법들의 묶음이다.

크게 다섯 덩어리로 나뉘더라. 전체 진행 방식(개발 방법론), 만들 것을 정하는 일(요구사항), 그걸 그림으로 옮기는 일(설계·UML), 제대로 됐는지 보는 일(테스트), 바뀌는 코드를 관리하는 일(형상관리). 순서도 대체로 이렇다.

| 단계 | 하는 일 | 결과물 |
|---|---|---|
| 요구사항 | 뭘 만들지 듣고 정리 | 요구사항 명세 |
| 설계 | 구조·화면·데이터 결정 | UML, 설계서 |
| 구현 | 코드 작성 | 소스 |
| 테스트 | 요구대로 되는지 확인 | 테스트 결과 |
| 유지보수 | 고치고 덧붙임 | 새 버전 |

## 개발 방법론: 폭포수와 애자일

방법론은 위 단계를 어떻게 돌리느냐의 차이다.

폭포수 모델은 단계를 위에서 아래로 한 번씩 순서대로 간다. 요구사항을 다 끝내고 설계, 설계를 다 끝내고 구현. 앞 단계가 끝나야 다음으로 넘어가서 문서와 계획이 분명한 대신, 중간에 요구가 바뀌면 되돌리기 어렵다. 결과물이 마지막에 가서야 보인다는 것도 약점이다.

애자일은 반대로 짧게 만들어 보여 주고 고치는 쪽이다. 애자일 선언의 원칙 12개를 읽어 보면 방향이 분명하다. 요구가 개발 후반에 바뀌어도 환영하고, 동작하는 소프트웨어를 몇 주 단위로 자주 내놓고, 업무 담당자와 개발자가 매일 함께 일하고, 동작하는 소프트웨어를 진척의 기준으로 삼는다. 주기적으로 돌아보며 방식을 고치는 것도 포함된다.

| | 폭포수 | 애자일 |
|---|---|---|
| 진행 | 단계를 한 번씩 순서대로 | 짧은 주기를 반복 |
| 요구 변경 | 어렵고 비쌈 | 받아들이는 게 전제 |
| 결과물 확인 | 거의 끝에 | 매 주기마다 |
| 문서 | 많음 | 필요한 만큼 |
| 잘 맞는 곳 | 요구가 고정된 일 | 요구가 자주 바뀌는 일 |

애자일을 실제로 돌리는 틀 중 가장 흔한 게 스크럼이다. [스크럼 가이드](https://scrumguides.org/scrum-guide.html) 기준으로 정리하면 이렇다.

- 스프린트: 한 달 이하의 고정 기간. 모든 이벤트가 이 안에 들어간다.
- 이벤트: 스프린트 계획, 데일리 스크럼(15분), 스프린트 리뷰, 회고.
- 역할: 프로덕트 오너(백로그 관리, 한 사람), 스크럼 마스터(방해물 제거), 개발자.
- 산출물: 프로덕트 백로그, 스프린트 백로그, 인크리먼트(쓸 수 있는 결과물).

폭포수가 나쁘고 애자일이 좋다는 식으로 알면 현실에서 틀린다. 요구가 고정되고 되돌리기 비싼 일(예: 하드웨어에 들어가는 펌웨어)이면 계획 중심이 맞을 때가 있다. 나머지 모델로 나선형(위험 분석을 반복), 프로토타입 등이 있는데 이름과 특징만 알아 두면 됐다.

## 요구사항

요구사항은 시스템이 해야 할 일과 지켜야 할 조건이다. 두 종류로 나눈다.

- 기능 요구사항: "회원은 이메일로 로그인할 수 있어야 한다"처럼 시스템이 하는 일.
- 비기능 요구사항: "로그인 응답은 1초 안에" "개인정보는 암호화" 같은 품질·제약.

좋은 요구사항은 하나의 문장에 하나의 뜻이고, 확인할 수 있어야 한다. "빠르게"는 확인이 안 되고 "1초 안에"는 된다. 요구사항 단계의 실수는 뒤로 갈수록 고치는 비용이 커져서, 이 단계에서 서로 같은 걸 이해하고 있는지 맞추는 게 제일 중요하다고 하더라.

<details>
<summary>요구사항을 가져오는 방법과 검증</summary>

도출은 인터뷰, 설문, 현재 업무 관찰, 프로토타입 시연 같은 방법으로 한다. 받은 요구는 분석해서 충돌하는 것을 걸러내고, 명세서로 적고, 마지막에 이해관계자가 검토한다. 요구 하나하나에 번호를 붙여 두면 나중에 설계·테스트와 연결해 추적할 수 있다(추적 표).
</details>

## UML

UML은 설계를 그림으로 그리는 표준 표기법이다. 종류가 많지만 자주 나오는 건 몇 개다.

| 다이어그램 | 보여 주는 것 | 언제 |
|---|---|---|
| 유스케이스 | 사용자가 시스템으로 하는 일 | 요구사항 정리 |
| 클래스 | 클래스와 관계 | 구조 설계 |
| 시퀀스 | 객체 사이 메시지 순서 | 한 기능의 흐름 |
| 상태 | 상태가 바뀌는 조건 | 주문·결제 같은 상태 있는 것 |
| 액티비티 | 작업 흐름 | 업무 절차 |

구조를 보여 주는 그림(클래스 등)과 동작을 보여 주는 그림(시퀀스, 상태 등)으로 나눠 외우면 덜 헷갈렸다. 모든 걸 다 그릴 필요는 없고, 말로 설명하기 어려운 부분만 그리는 게 낫다.

## 테스트

테스트는 만든 것이 요구대로 동작하는지, 어디서 깨지는지를 찾는 일이다. 단위(함수·클래스 하나), 통합(모듈을 묶어서), 시스템(전체), 인수(사용자·고객이 받아들일 만한지) 순으로 범위가 넓어진다.

자동화 테스트는 "테스트 피라미드"로 비율을 설명한다. [Martin Fowler의 글](https://martinfowler.com/articles/practical-test-pyramid.html) 기준으로 단위 테스트는 빠르니까 가장 많이, 데이터베이스 등 외부와 붙는 통합 테스트는 적당히, UI 전체를 도는 테스트는 아주 적게 둔다. 이걸 뒤집으면 느리고 유지가 비싼 "아이스크림 콘"이 되고, 같은 걸 여러 층에서 중복해서 확인하지 말고 가능한 한 낮은 층으로 내리라고 한다.

테스트는 블랙박스(내부 코드 안 보고 입력·출력만)와 화이트박스(코드 구조를 보고 경로를 확인)로도 나눈다. 블랙박스에서는 경계값 분석이 대표적이다. 값이 0, 1, 최대 같은 경계에서 오류가 잘 나기 때문이다.

단위 테스트는 이런 모양이다. 파이썬 `unittest`로 짜서 직접 돌려 4개가 통과하는 것까지 확인했다.

```python
import unittest

def discount(price, is_member):
    if price < 0:
        raise ValueError("price")
    return int(price * 0.9) if is_member else price

class T(unittest.TestCase):
    def test_member(self):
        self.assertEqual(discount(10000, True), 9000)
    def test_guest(self):
        self.assertEqual(discount(10000, False), 10000)
    def test_zero(self):          # 경계값
        self.assertEqual(discount(0, True), 0)
    def test_negative(self):      # 예외 경우
        with self.assertRaises(ValueError):
            discount(-1, True)

unittest.main()
```

<details>
<summary>테스트 용어 몇 개</summary>

- 회귀 테스트: 고친 뒤 예전에 되던 게 안 깨졌는지 다시 확인.
- 스텁·목: 테스트에서 진짜 의존 대상(DB, 외부 API)을 대신하는 가짜.
- 검증(Verification)은 "제대로 만들었나"(명세에 맞는가), 확인(Validation)은 "맞는 걸 만들었나"(사용자 요구에 맞는가).
</details>

## 형상관리

코드는 계속 바뀌는데, 누가 언제 무엇을 바꿨는지 모르면 문제가 생겨도 되돌릴 수 없다. 형상관리(SCM)는 소스·문서 같은 산출물의 변경을 기록하고 통제하는 일이다. 버전 관리(되돌리기·이력), 변경 통제(누가 승인), 빌드·배포 관리가 포함된다. 요즘은 Git이 사실상 표준이다.

## 흔한 오해

- 애자일은 문서도 계획도 없이 한다? 원칙에도 좋은 설계와 기술적 탁월함이 들어 있다. 문서를 줄이는 것이지 없애는 게 아니다.
- 테스트는 개발이 끝나고 한다? 요구사항 단계에서 이미 "어떻게 확인할지"를 같이 적어 두는 게 좋다.
- UML은 다 그려야 한다? 필요한 만큼만 그린다.
