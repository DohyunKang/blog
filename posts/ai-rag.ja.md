RAG は、質問が入ると関連するドキュメントをまず検索してプロンプトに追加し、モデルがそれを見て回答させる方式です。モデルを再学習させずに、モデルが知らない内容についても回答させることができます。

## なぜ必要なのか

[LLM](#/post/ai-llm) は、学習が終了した時点までの知識しか持っていません。昨日変更された社内規定や自社のドキュメントについては当然ながら知りません。「知らない」と正直に言うのが望ましいですが、 그럴듯하게 ( 그럴듯하게 → あり得そうなように ) 作り上げてしまうことがあります ([幻覚 → ハルシネーション](#/post/ai-hallucination))。

とはいえ、ドキュメントをすべてプロンプトに入れることもできません。[コンテキストウィンドウ](#/post/ai-context-window) には制限があり、長くなるほどコストも増大し、中間の内容は利用されにくい傾向もあります。「Lost in the Middle」という論文では、関連情報が入力のはじめや終わりにある場合の性能が高く、中央にある場合は大きく低下すると報告されています。長い文脈をサポートするモデルでも同様だということです。

したがって、必要な部分だけを選んで入れるのが RAG です。用語は 2020 年の Lewis らによる論文 "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" から来ています。同論文では、モデルの重치に含まれる知識をパラメトリックメモリ、ウィキペディアベクトルインデックスのような外部に置かれた知識を非パラメトリックメモリと呼び、両者を組み合わせる方式を提案しています。私の言葉で簡略化すれば「暗記した知識 + 広げられる本」です。

## フロー

一度見るとこのようになります。

```
[준비 단계, 미리 한 번]
문서 → 청킹(조각내기) → 임베딩(숫자 벡터로) → 벡터 DB에 저장

[질문이 올 때마다]
질문 → 임베딩 → 비슷한 청크 검색(top-k) → 프롬프트에 붙임 → 모델이 답변
```

| ステップ | 行うこと | 覚えておく点 |
|---|---|---|
| チャンキング | ドキュメントを適切なサイズに分割する | 検索の単位となります |
| エンベッディング | チャンクを意味を持つベクトルに変換する | [詳細 → エンベッディング](#/post/ai-embedding) |
| 検索 | 質問ベクトルに近いチャンクを探します | トップ k 件のみを取得します |
| プロンプト注入 | 「以下の資料だけを見て回答してください」というようにチャンクを追加します | [詳細 → プロンプト](#/post/ai-prompt) |
| 回答 | モデルが資料を読み書きします | 出典を併記すると確認が容易です |

プロンプト注入部分は大まかにこのようになります。

```
다음 자료만 근거로 질문에 답하라. 자료에 없으면 모른다고 답하라.

[자료 1] ...청크...
[자료 2] ...청크...

질문: ...
```

「資料にない場合は知らない」という一行は意外にも重要です。これがなければ、モデルは資料にない部分を自らの知識で埋めてしまいます。

## チャンクサイズ

チャンクをどのように分割するかは検索品質に直接影響を与えます。Anthropic の Contextual Retrieval という記事でも、チャンクサイズ・境界・重複 (overlap) が検索性能に影響を与える旨が書かれています。

- 大きすぎると、1 つのチャンクに複数の主題が混ざり合いエンベッディングが曖昧になり、プロンプトのスペースも多く消費します。
- 小さすぎると、文脈なしで前後から文が切断され意味が失われます。
- 重複を設けると、境界で切断された内容を隣接するチャンクが受け取ります。その代わり重複が増加します。

「何トークンが最適か」という数字は見つかりませんでした。記事でも使用ケースごとに実験することをお勧めしています。ドキュメントの種類（規定、会話、コード）によって分割基準は異なり、「タイトルや段落単位で分割する方が文字数で分割するよりも良い」という話をよく耳にしますが、これは私が直接確認したわけではありません。

## 再順位付けとハイブリッド検索

最初の実験から得られたトップ k 件が常に良いわけではありません。そのため、以下の 2 つがよく組み合わせられます。

ハイブリッド検索は、エンベッディング検索（意味ベース）と BM25（単語一致ベース）を併用するものです。エンベッディングは意味が似ていればよく見つかりますが、「TS-999」のようなエラーコードや固有用語の正確な一致を見逃す可能性があります。BM25 は逆です。両方の結果をランク融合 (rank fusion) で統合し、重複を除去します。

再順位付け (reranking) は、まず広く検索した後に、再順位モデルが質問とチャンクを同時に見てスコアを再計算し、上位のみを残すステップです。最初の実験は速く大まかであれば、再順位付けは遅くかつ精緻です。その代わり遅延が若干増えるため、何件を再順位付けるかはコストと速度のトレードオフとなります。

Anthropic の記事には数字があります。これは「トップ 20 チャンク内に正解がない割合（検索失敗率）」という基準です。

| 方式 | 失敗率 | ベースとの比較 |
|---|---|---|
| ベースエンベッディング | 5.7% | ベース |
| チャンクにコンテキスト文を付けてエンベッディング | 3.7% | 35% 減少 |
| 上記方式 + コンテキスト BM25 | 2.9% | 49% 減少 |
| 上記方式 + 再順位付け | 1.9% | 67% 減少 |

これはその記事の独自実験条件（データセット、再順位モデルは Cohere）から得られた値です。私のデータでも同様に減少するとは保証できません。方向性は参考になります。

ここで出たコンテキスト追加は、チャンクが「売上は前四半期より 3% 増加」といったように会社名や期間が抜けて切断される問題を防止するため、チャンクの前に短い説明文を付加する方式です。

## 失敗する場合

RAG が間違える点は、 대체로 ( 대체로 → おおむね ) モデルではなくフロントエンドにあります。

- 필요한 청크가 검색 결과에서 나오지 않습니다. 이는 가장 흔한 문제이며, 위 실패율을 나타내는 바로 그 지표입니다.
- 청크가 잘려서 맥락이 손실됩니다. 위의 회사명 예시가 그렇습니다.
- 찾기는 했지만 내용이 묻혀 있어 모델이 사용하지 않습니다. 앞의 'Lost in the Middle' 논의가 이쪽을 가리킵니다.
- 여러 문서를 합쳐야 하는 질문 (비교, 집계 등) 의 경우 상위 몇 개의 청크만으로는 부족합니다.
- 문서가 낡았거나 서로 모순됩니다. 검색은 잘 되지만 자료가 틀린 경우입니다. 이는 RAG 로 해결할 수 없습니다.
- 자료를 제공해도 모델이 자신의 지식으로 답하거나 자료를 잘못 읽습니다.

따라서 답변이 틀렸을 때 "모델 탓"부터 하지 말고, 어떤 청크가 프롬프트에 포함되었는지를 먼저 확인하는 것이 순서 같습니다.

## 파인튜닝과 무엇이 다른가

둘 다 "모델이 우리 것을 알게 하는 방법"으로 묶이지만 수행하는 작업은 다릅니다.

| | RAG | 파인튜닝 |
|---|---|---|
| 바뀌는 것 | 모델이 보는 입력 | 모델의 가중치 |
| 잘 맞는 것 | 자주 바뀌는 지식, 사내 문서, 출처 필요 | 말투, 출력 형식, 일관된 행동 |
| 지식 갱신 | 문서를 고치면 끝 | 다시 학습 |
| 출처 표시 | 청크를 그대로 보여 줄 수 있다 | 어렵다 |

검색해서 읽은 실무 글들은 대체로 "지식 문제라면 RAG, 행동 문제라면 파인튜닝"으로 정리하고, 둘을 섞어 사용하기도 한다고 합니다. 다만 이는 업체나 개인 블로그가 대부분이라 의견에 가깝고, 같은 과제로 둘을 비교한 통제된 실험은 찾지 못했습니다.

## 흔한 오해

- RAG 를 쓰면 환각이 사라진다: 줄어들 뿐입니다. 검색이 틀리거나 모델이 자료를 무시하면 똑같이 지어냅니다.
- 파인튜닝하면 문서 내용을 외운다: 사실을 안정적으로 외우게 하는 용도로는 약하다는 것이 실무 글들의 공통된 이야기였습니다. 저도 직접 해 보지는 못했습니다.
- 벡터 DB 만 있으면 RAG 다: DB 는 저장 장치일 뿐이며, 품질은 청킹, 검색 방식, 재순위화에서 갈립니다.
- 컨텍스트가 길어졌으니 RAG 는 필요 없다: 지식 베이스가 작으면 (Anthropic 글 기준 대략 20 만 토큰, 500 페이지 미만) 통째로 넣는 것이 가장 간단하다고 그 글도 말합니다. 그보다 크면 여전히 필요합니다.

<details>
<summary>자세한 풀이: 의미 검색이 어떻게 찾는지</summary>

임베딩은 글을 수백~수천 차원의 숫자 목록으로 바꾼 것입니다. 뜻이 비슷한 글은 벡터 공간에서 가깝게 놓이도록 학습된 모델이 만듭니다. 질문도 같은 모델로 벡터로 바꾸고, 저장된 청크 벡터 중 가까운 것 (코사인 유사도 등) 을 고릅니다. 청크가 많으면 하나씩 비교하지 않고 근사 최근접 탐색 인덱스를 사용합니다.

BM25 는 단어가 얼마나 자주, 얼마나 희귀하게 나오는지를 보는 점수 함수입니다. 흔한 단어가 점수를 독차지하지 않게 빈도에 상한을 두고 문서 길이도 보정한다고 합니다. 뜻은 몰라도 같은 글자가 있으면 찾는다는 점이 임베딩과 보완 관계입니다.
