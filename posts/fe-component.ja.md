コンポーネントは、データの流れに合わせて画面を分割した断片であり、設計とは「どこでどう分割するか」よりも、「どこで止めるか」「状態を誰が保持するか」に近い。

## コンポーネントとは何か

コンポーネントとは、画面の一部を 1 つの関数として実装したものです。入力を渡すと、それに応じた画面の断片を返します。ボタンや検索ボックス、商品行といった小さな要素もあれば、それらをまとめた表全体もコンポーネントになります。本稿の例は React を基準にしていますが、Vue や Svelte も言葉は違えど同じ考え方をしています。

入力は props として渡されます。React のドキュメントでは「props はコンポーネントの『唯一の引数』である」と記載されています。また、コンポーネントが props を直接変更してはいけません。値を変更したい場合は state を使用します。props はレンダリングのたびに新しく受け取られる読み取り専用のスナップショットです。

```jsx
function Avatar({ person, size = 100 }) {
  return <img src={person.imageUrl} width={size} height={size} />;
}
```

デフォルト値（`size = 100`）は、値が存在しない場合や `undefined` の場合にのみ使用されます。`size={0}` や `size={null}` を渡すとデフォルト値は適用されません。最初は混乱しやすいですが、ドキュメントには明記されています。

## どのように分割するか

ドキュメントの「Thinking in React」では、アイデアを箱に描きながら始めるよう指示しています。各箱に名前をつけ、中に含まれる箱を子要素とします。分割すべきかどうかは以下の 3 つの視点で判断します。コード（関数やオブジェクトを作成する際の基準）、CSS（別々のクラスを与える必要があるか）、デザイン（レイヤーが独立して動く必要があるか）です。

基準は単純です。コンポーネントは 1 つのことに集中することが理想であり、大きくなったら小さく分割します。分割する際は、データモデルの 1 つの断片を 1 つのコンポーネントに対応させるようにしてください。ドキュメントの商品表の例は以下の通りです。

```text
FilterableProductTable
├─ SearchBar
└─ ProductTable
   ├─ ProductCategoryRow
   └─ ProductRow
```

表の見出しは別々に抽出しません。ただし、ソートなどの機能が追加され見出しが複雑化した場合に初めて `ProductTableHeader` として抽出すると、ドキュメントでは述べています。「事前に分割せず、大きくなった時に分割する」という趣旨で読み取れます。これは [結合度・凝集度](#/post/be-coupling-cohesion) や [SOLID](#/post/cs-solid) の単一責任の原則と同様です。

## 合成 (composition)

再利用のためにオプションを付け続けるアプローチと、中身を決めるのは外側から行うアプローチがあります。後者を合成と呼びます。タグ間に挿入された内容は `children` という prop として渡されます。

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

<Card>
  <Avatar person={me} />
</Card>
```

`Card` は中にアバターが来るのか、テキストが来るのか分かりません。分からないためどこでも使用可能です。逆に、`showAvatar`、`showTitle`、`showFooter` といったブール型の props が増え始めると、合成に切り替えるべきタイミングのシグナルとなります。
`{...props}` で受け取った props をそのまま子要素に渡すスプレッド演算子もあります。ドキュメントでは「節制して使いなさい。各コンポーネントで使っているなら何か間違っている」と述べています。便利ですが、何が下流へ伝わっているか見えなくなります。

## データは下向き、イベントは上向き

React ではデータは上から下へのみ流れます。親が state を持ち、props として子に渡し、子が値を変更したい場合は親が渡した関数を呼び出します。ドキュメントでは、双方向バインディングよりもコードが少し長くなると認めています。代わりに、データの流れが視覚的に明確になります。

```jsx
<SearchBar
  filterText={filterText}
  onFilterTextChange={setFilterText}
/>
```

state をどこに置くかはドキュメントで順序が示されています。その state で画面を描画するコンポーネントをすべて見つけ、それらの最も近い共通の親要素に置きます。これが状態の引き上げ (lifting state up) です。各 state には所有者は 1 人である必要があります (single source of truth)。すべての state を 1 か所に集めるという意味ではなく、情報のそれぞれに対して所有者を 1 つに定めるという意味です。グローバルな状態に関する話は [状態管理](#/post/fe-state) で続きます。

state は最小限に抑えます。ドキュメントでは以下の 3 つを問います。時間が経っても変わらないか、親が props として渡すか、他の state や props から計算できるかです。いずれかに該当すれば state ではありません。商品リストは props であり、検索語でフィルタリングしたリストは計算で得られるため、state は検索語とチェックボックスの値の 2 つだけです。

## 制御と非制御

ドキュメントのアコーディオンの例がこの区別をよく示しています。パネルが開いているか (`isActive`) をパネル自体が保持している場合は非制御 (uncontrolled) です。親が `isActive` を渡す場合は制御 (controlled) です。

| | 非制御 | 制御 |
|---|---|---|
| 状態の所有者 | コンポーネント自身 | 親 |
| 書き込み | 容易で設定が少ない | 親から props を渡す必要がある |
| 柔軟性 | 親が介入できない | 複数のコンポーネントを連携させて動かせる |

「一度に 1 つしか開いてはいけない」というルールが生じる瞬間、パネルは単独では決定できなくなり、その時点で制御に変更します。ドキュメントでも実際には両方が混在しており、必要に応じて切り替えると述べています。最初からすべて制御で作る必要はありません。

## コンテナ/プレゼンテーション

データを扱うコンポーネント（コンテナ）と、プロップスを受け取って描画するだけのコンポーネント（プレゼンテーション）に分けるパターンがあります。この名前は Dan Abramov の記事で広まりました。その記事の冒頭には、現在はこのような分け方を推奨しないという更新メモが添えられています。「コードベースに自然に合えば有用だが、教条的に強制するのはあまり見たくない」という趣旨であり、状態ロジックを分離しようとした目的は、フック（hook）によって任意の境界なしで実現できるからです。

したがって、このパターンは「ファイルを 2 つに分けろ」という考えよりも、「描画コードとデータを扱うコードを混ぜない」という考え方で捉えたいと思います。現在はカスタムフックを使ってロジックを抽出する方が一般的です。

## 過剰な抽象化

コンポーネントを作成する際に最も頻繁に犯すミスは、事前に一般化してしまうことです。ボタンが 2 ヶ所で使われるから `GenericButton` を作ってしまい、3 つ目のケースが出たらプロップスを一つ追加し、10 個くらいになると `variant`, `size`, `iconLeft`, `iconRight`, `loading`, `as` が付いた怪物になってしまいます。使う人はどのような組み合わせになるか分からず、作る人も修正が恐ろしくなります。

点検時に投げかける質問は以下の通りです。

- 同じような形状が 3 回以上出てきたか。2 回ならコピーしても問題ない。
- プロップスが追加されたときに互いに影響を与えているか。そうなら合成して分割する時だ。
- このコンポーネントの名前を一文で説明できるか。「～も～もする」なら 2 つに分けるべきだ。
- 逆に、あまりに細かく分割してファイルを 3 つ開かないと一行が理解できないか。

分割する側のミスと統合する側のミスはどちらも存在するため、どちらが正解か言いにくいですが、後で統合するよりも後で分割する方が概ね簡単だという話は多いです。

## よくある誤解

- コンポーネントは小さいほど良い：基準はサイズではなく責任である。1 行でも理由が必要であり、100 行でも一つの事柄なら問題ない。
- プロップスを替えて値を更新する：プロップスは読み取り専用である。変更されるべき値は state に置く。
- state は多く置いた方が楽：計算可能な値を state に置くと、2 つの値がずれてバグが発生する。
- コンテナ/プレゼンテーションを必ず守らなければならない：作成者自身が強制しないように整理した。
- 再利用されるコンポーネントが良いコンポーネントである：再利用は結果であり、使われない汎用コンポーネントは荷物だ。

<details>
<summary>詳しい解説：状態の引き上げを一度追ってみる</summary>

ドキュメントのアコーディアン例に従うと順序は以下の通りです。最初は各 `Panel` に `isActive` state を持っており、2 つのパネルが同時に開きます。1 つだけ開くには 1) パネルから state を削除し、2) 親 `Accordion` で値を直接受け取り、3) 親に state を追加してイベントハンドラも一緒に渡す必要があります。

```jsx
function Accordion() {
  const [activeIndex, setActiveIndex] = useState(0);
  return (
    <>
      <Panel title="About" isActive={activeIndex === 0} onShow={() => setActiveIndex(0)}>...</Panel>
      <Panel title="Etymology" isActive={activeIndex === 1} onShow={() => setActiveIndex(1)}>...</Panel>
    </>
  );
}

function Panel({ title, children, isActive, onShow }) {
  return (
    <section>
      <h3>{title}</h3>
      {isActive ? <p>{children}</p> : <button onClick={onShow}>Show</button>}
    </section>
  );
}
```

パネルはこれで開くか否かを自ら決めず、親が渡した値を描画し、押された事実のみを知らせます。このコードはドキュメントの例を簡略化して記述したもので、私が実際に実行していません。アクセシビリティの観点（ボタン代わりに `aria-expanded` など）については [ウェブアクセシビリティ](#/post/fe-accessibility) で別途見ています。
