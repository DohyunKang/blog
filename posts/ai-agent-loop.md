에이전트는 모델이 도구를 쓰고, 결과를 보고, 다음에 뭘 할지 스스로 정하는 일을 끝날 때까지 반복하는 구조였다. 이름은 거창한데 뼈대는 while 문이다.

## 에이전트가 뭔지

Anthropic의 "Building effective agents" 글은 둘을 이렇게 나눈다. 워크플로우는 LLM과 도구를 "미리 정해 둔 코드 경로"로 엮은 시스템이고, 에이전트는 LLM이 "스스로 자기 작업 과정과 도구 사용을 지휘"하는 시스템이다. 같은 글에서 에이전트를 실제로 구현하면 대개 "환경의 피드백을 받으며 도구를 쓰는 LLM이 루프를 도는 것" 정도라고 한다.

쉽게 말하면 이렇다. 단계가 코드에 박혀 있으면 워크플로우, 다음 단계를 모델이 고르면 에이전트다. 둘 사이에 칼로 자른 듯한 선이 있다기보다 모델에게 얼마나 맡기느냐의 정도 차이로 읽었다. 도구가 뭔지는 [자세히 → 도구 호출](#/post/ai-tool-use)에 따로 적었다.

| | 워크플로우 | 에이전트 |
|---|---|---|
| 다음 단계를 정하는 쪽 | 코드 | 모델 |
| 단계 수 | 미리 안다 | 돌려 봐야 안다 |
| 예측 가능성 | 높다 | 낮다 |
| 비용·지연 | 적고 안정적 | 늘고 들쭉날쭉 |

## 루프는 어떻게 도나

Anthropic 문서(How tool use works)가 설명하는 기본 모양은 이렇다. 도구를 내 코드가 실행하는 경우, 내 앱이 루프를 돌려야 한다. 모델이 직접 코드를 실행하지 못하기 때문이다.

1. 도구 목록과 사용자 메시지를 담아 요청을 보낸다.
2. 모델이 `stop_reason: "tool_use"`와 함께 도구 호출 요청(`tool_use` 블록)을 돌려준다.
3. 내 코드가 그 도구를 실행하고 결과를 `tool_result`로 만든다.
4. 지금까지의 대화, 모델의 응답, 결과를 합쳐 다시 요청을 보낸다.
5. `stop_reason`이 `"tool_use"`인 동안 2번부터 반복한다.

`end_turn`, `max_tokens`, `stop_sequence`, `refusal` 중 하나가 나오면 루프를 빠져나온다. 모델이 최종 답을 냈거나, 다른 이유로 멈췄다는 뜻이다. 문서 표현으로는 모델은 "구조화된 요청을 내보낼 뿐"이고 실행은 내 코드(또는 Anthropic 서버)가 한다.

이걸 관찰, 생각, 행동으로 부르기도 한다. 도구 결과가 관찰, 그걸 보고 다음을 정하는 게 생각, 도구를 부르는 게 행동이다. 이 방식의 이름이 ReAct(Yao 등, 2022)다. 논문 초록 기준으로 추론(reasoning)과 행동(acting)을 번갈아 하게 하는 프롬프트 방식이고, HotpotQA·FEVER에서 chain-of-thought만 쓸 때보다 환각과 오류 전파가 줄었다고 보고한다. 숫자 하나 더, ALFWorld와 WebShop에서는 모방·강화학습 방법보다 성공률이 절대치로 각각 34%p, 10%p 높았다고 한다. 다만 이건 2022년 논문의 실험 조건이고 지금 모델에 그대로 맞는 수치는 아니다.

## 직접 돌려 본 최소 루프

모델 호출은 규칙 함수로 대신하고 구조만 확인했다. 실제 모델이 아니라서 판단 능력은 볼 수 없고, 루프 모양과 종료만 본다.

```python
def fake_model(messages):
    last = messages[-1]
    if last["role"] == "user":
        return {"stop_reason": "tool_use", "tool": "add", "args": {"a": 2, "b": 3}}
    if last["role"] == "tool":
        return {"stop_reason": "end_turn", "text": f"답은 {last['content']}"}

TOOLS = {"add": lambda a, b: a + b}

def run(task, max_steps=5):
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        r = fake_model(messages)
        if r["stop_reason"] != "tool_use":
            return r["text"], step + 1
        try:
            out = TOOLS[r["tool"]](**r["args"])
        except Exception as e:
            out = f"error: {e}"
        messages.append({"role": "assistant", "content": r})
        messages.append({"role": "tool", "content": out})
    return "중단: 최대 단계 도달", max_steps
```

실행하니 `run("2+3은?")`은 두 번째 단계에서 "답은 5"로 끝났다. 모델이 계속 도구만 부르도록 바꾼 경우(`max_steps=3`)는 3단계에서 "최대 단계 도달"로 멈췄다. 이 상한이 없으면 같은 코드가 끝나지 않는다.

## 언제 끝나나

종료는 두 갈래다.

- 모델이 "다 했다"고 판단해서 도구 호출 없이 답을 낸다(`end_turn`).
- 바깥에서 끊는다. 최대 반복 횟수, 토큰·시간 예산, 사람의 확인 같은 것이다.

Anthropic 글도 통제를 유지하는 방법으로 최대 반복 횟수 같은 종료 조건을 든다. 에이전트가 막혔거나 중요한 지점에서는 사람에게 확인을 받으며 진행할 수도 있다고 한다. 앞쪽만 믿으면 모델이 "다 했다"고 착각하는 경우를 못 막으니, 바깥에서 끊는 장치는 따로 있어야 한다는 게 내가 이해한 포인트다.

서버가 도구를 대신 실행하는 경우(web_search 같은 것)에는 서버 안에서 루프가 돌고, 반복 한도에 걸리면 `pause_turn`으로 돌아온다. 이때는 일이 끝난 게 아니니 그 대화를 그대로 다시 보내서 이어 가라고 문서에 적혀 있다.

## 계획과 맥락

루프가 길어지면 두 가지가 문제가 된다. 하나는 계획이다. 한 번에 정해 놓고 따라가는 방식도 있고, 한 단계마다 보고 다시 정하는 방식도 있다. 위 글에서 에이전트가 "계획하고 독립적으로 작동한다"고 하고, 매 단계 환경에서 "ground truth"(도구 결과, 코드 실행 결과)를 얻어 진행 상황을 판단해야 한다고 한다. 나는 이걸 "머릿속 계획보다 실제로 돌려 본 결과를 믿어야 한다"로 이해했다.

다른 하나는 맥락이다. 단계마다 도구 결과가 쌓이니 창이 점점 찬다. 이건 [자세히 → 컨텍스트](#/post/ai-context)와 [자세히 → 압축](#/post/ai-compaction)에서 다룬 문제와 같다. 긴 일을 맡기려면 루프 바깥에서 하네스가 이 부분을 관리해야 한다. 하네스는 [자세히 → 하네스](#/post/ai-harness)에 정리했다.

## 실패 모드

문서와 글에서 확인한 것과, 내가 추론한 것을 나눠 적는다.

확인한 것
- 오류가 쌓인다: Anthropic 글이 "자율성은 더 높은 비용과 오류가 누적될 가능성을 뜻한다"고 한다. 단계마다 틀릴 확률이 조금씩 있으면 단계가 길수록 전체 성공률은 내려간다는 얘기다.
- 비용과 지연: 에이전트 시스템은 더 나은 성과를 얻는 대신 지연과 비용을 치르는 경우가 많다고 한다.
- 권고: 샌드박스에서 충분히 테스트하고 적절한 가드레일을 두라고 한다. 이건 [자세히 → 가드레일](#/post/app-guardrails)과도 이어진다.

내가 추론한 것
- 같은 도구를 같은 인자로 반복해서 부르는 헛바퀴.
- 도구 오류 메시지를 보고도 같은 실수를 되풀이하는 것.
- 중간에 목표를 잊거나 목표가 슬금슬금 바뀌는 것.

위 세 가지는 직접 재현해 본 게 아니라 구조상 그럴 것 같다고 생각한 것이다. 맞다면 해결은 대체로 반복 상한, 같은 호출 감지, 오류를 모델이 읽기 좋게 돌려주기 정도일 텐데, 이것도 확인한 처방은 아니다.

## 워크플로우로 충분할 때

같은 글이 가장 강하게 말하는 건 "가장 단순한 해법부터 시작하고, 필요할 때만 복잡도를 더하라"다. 검색과 예시를 붙인 LLM 호출 한 번으로 충분한 경우가 많다고 한다. 기준은 대략 이렇게 읽었다.

| 상황 | 맞는 쪽 |
|---|---|
| 단계가 정해져 있고 예측이 중요 | 워크플로우 |
| 몇 단계 걸릴지 모르는 열린 문제 | 에이전트 |
| 모델 판단을 믿을 수 있는 환경 | 에이전트 |

워크플로우의 대표 패턴으로 글은 다섯 가지를 든다. 프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-워커, 평가자-최적화. 여러 에이전트로 나누는 얘기는 [자세히 → 서브에이전트](#/post/ai-subagent)에 이어 적는다. 에이전트 앱을 실제로 설계할 때 고려할 것은 [자세히 → 에이전트 설계](#/post/app-agent-design)에 있다.

## 흔한 오해

- 에이전트는 별도의 특별한 모델이다: 아니다. 같은 LLM을 루프 안에서 도구와 함께 쓰는 방식이다. 다만 도구를 잘 쓰도록 학습된 모델이 더 잘 돌긴 한다(Anthropic 문서가 trained-in 도구 스키마를 언급한다).
- 에이전트가 항상 워크플로우보다 낫다: 비용·지연·오류 누적이 있어서 좁고 정해진 일에는 워크플로우가 낫다.
- 루프를 돌리면 모델이 알아서 끝낸다: 종료 조건은 바깥에서도 걸어 두는 게 안전하다.
- 모델이 도구를 실행한다: 모델은 요청만 내보낸다. 실행은 내 코드나 서버가 한다.

<details>
<summary>자세한 풀이: stop_reason별 처리</summary>

문서에서 읽은 범위만 적는다.

- `tool_use`: 도구를 실행하고 결과를 붙여 계속한다. 도구 호출이 여러 개일 수 있다(병렬 호출).
- `end_turn`: 최종 답. 루프를 끝낸다.
- `max_tokens`: 답이 잘렸다. 최종 답이 아니므로 내 앱이 처리해야 한다.
- `stop_sequence`, `refusal`: 다른 이유로 멈춘 것. 마찬가지로 앱이 처리한다.
- `pause_turn`: 서버 쪽 루프가 반복 한도에 걸렸다. 응답을 포함해 다시 보내 이어 간다.
