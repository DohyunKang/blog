今朝の GitHub トレンド(daily)に NVIDIA/SkillEvaluator が載っていた。今日のスター 323、合計 3,705(11月19日朝に確認)。コーディングエージェント用のスキルやプラグインを渡すと形式とセキュリティを検査し、最後に「このスキルを入れたらエージェントは本当に仕事がうまくなるのか」を数字で出してくれるツールだ。README と `docs/` のいくつかの文書、arXiv の要旨を読んだ。自分では動かしていない。

## どんなものか
スキルは、エージェントが必要なときに読み込む説明書のフォルダだ。SKILL.md に指示と例、補助スクリプトが付く。[詳しく → スキル](#/post/ai-skills) 最近スキル集のレポがよくトレンドに上がるが、そのスキルが役に立つかは使った人の感覚頼りだった。SkillEvaluator はそれを3段階に分けて調べる。

1. Tier 1(検証):形式、バージョン、個人情報、ライセンス、隠れた Unicode 文字、秘密鍵の漏れ、スクリプトの安全性などの静的検査。README によると 500 以上のルールと検出パターンがあり、モデルのキーなしで動く。品質は100点満点で、既定の合格ラインは70点。
2. Tier 2(重複):埋め込みでスキル内の指示同士、または他のスキルと重なっていないかを見る。埋め込みは文の意味を数値ベクトルにして近さを測る方法だ。
3. Tier 3(実地評価):同じ課題を Docker サンドボックスで、スキルありとなしで1回ずつエージェントにやらせる。その差が Skill Lift。

Tier 1 の中に Harness Check が別にあるのが面白かった。Claude Code、Codex、OpenCode、Copilot CLI などは、スキルを読むフォルダや説明文の長さの上限がそれぞれ違う。だから「説明が 1,024 の上限を 4 超えていて Copilot CLI では読み込まれない」といったことを、エージェントを動かさずに教えてくれる。スキルが効かない理由が中身ではなくこういうところにあることは、けっこう多そうだ。

## Skill Lift の測り方
Tier 3 は試行ごとに6つの信号を0〜1で付ける。セキュリティ、スキルを見つけて使えたか(skill_execution)、効率よく使えたか、正解と合うか(accuracy)、目標を達成したか(goal_accuracy)、やるべき行動をしたか(behavior_check)。トークン効率は報告だけで点数には入らない。一部は LLM が採点役になる。[詳しく → 評価(Evals)](#/post/ai-evals)

式は単純で、`Skill Lift = スキルありの総合点 - スキルなしの総合点`。ただし両方が走った課題と、両方で採点された信号だけで比べる。+0.05 以上で PASS、-0.10 以下で FAIL、その間は NEUTRAL。課題数が少ないとぶれるので、課題単位で引き直すブートストラップで95%区間も出す。課題が1つだけなら区間は出さない。幅ゼロの区間が確定した結果に見えてしまうから、と書いてある。

文書に「まだ確かめられていないこと」という節があるのがよかった。人間の採点との一致を調べた研究はない。合格ライン 0.50 や lift の区切りは根拠のある値ではなく決めた慣例。比較が「スキルあり vs なし」なので、スキルの中身のおかげか、指示が1つ増えたおかげかは区別できない。最後の点は、読みながら自分も気になっていたところだ。

## 論文の数字
同じ方法をまとめた論文(arXiv 2608.20614、8月提出)がある。要旨によると、実際のスキル145個で構造検査の点と LLM 採点の点の相関は 0.14 と低かった。静的検査と実際の効果は別のものを見ているということだ。本番スキル58個、対になった課題947件で平均 Skill Lift は 0.2134、72.8% の課題で lift が正だった。差が一番大きかったのは正解率よりも、スキルを見つけて使い、手順に従う部分だったそうだ。文書を読むだけでは見えない部分だ、というのが論文の主張。

## 入門者にとって
PM なら、「スキルを入れればよくなるだろう」を「同じ課題で入れた場合と入れない場合を比べた」に変える枠組みが使える。エージェントの説明書に A/B テストをかけるようなものだ。課題が10件未満なら不十分とみなす既定値も目安になる。

開発の入門者なら、まず Tier 1 だけ試すのが気楽だ。`pip install skillevaluator` のあと `skillevaluator quality-check ./my-skill` はキーも GPU も Docker もなしで動く。`harness-check` も同じ。Tier 3 はモデルのキーと Docker が必要で、モデル利用料がかかることがあると書いてある。サポートは Experimental で、NVIDIA の公式サポートはない。よく使うスキルの話は以前の記事と合わせて読むといい。[詳しく → よく使う Claude スキル集](#/post/claude-popular-skills)
