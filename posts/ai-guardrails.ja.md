ガードレイルとは、LLM サービスがしてはならない言葉や行動を防ぐための安全装置を総称したものです。プロンプトに「しないでください」と書くことも、モデルの前後に検証コードを追加することも、モデルが利用可能なツールの権限を制限することも、すべてガードレイルです。

## なぜ必要なのか

[LLM](#/post/ai-llm) は指示とデータをどちらもテキストとして受け取ります。開発者が書いた指示やユーザーが送信した文章、ウェブページから取得された内容が、モデルには一つの大きなテキストブロックとして入力されます。そのため、データの中に指示のように見える文が含まれていれば、モデルはそれに従ってしまいます。ガードレイルが必要になる理由は、ほとんどここから生まれます。

企業がサービス運営を気にするのは主に 3 つです。

| 懸念点 | 何が起こるか | OWASP カテゴリ |
|---|---|---|
| プロンプトインジェクション | 入力がモデルの動作や出力を意図した方向とは異なるように変更する | LLM01 |
| 機密情報の漏洩 | 個人情報・内部文書・鍵などが回答に混じって流出する | LLM02 |
| 権限の過剰なエージェント | モデルが不必要なツールや権限を使って被害を与える | LLM06 |

OWASP はウェブセキュリティ「Top 10」で有名な組織ですが、LLM アプリケーション向けの Top 10 も別途発表しています。2025 年版には上記 3 つに加え、サプライチェーン、データ・モデル汚染、不適切な出力処理 (LLM05)、システムプロンプトの漏洩 (LLM07)、ベクトル・埋め込みの弱点 (LLM08)、誤情報 (LLM09)、無制限な消費 (LLM10) が含まれています。本稿では上記表の 3 つに焦点を当てます。

## プロンプトインジェクション

OWASP の定義では、入力が LLM の動作や出力を意図しない方向に変化させることです。人間の目には見えない入力であっても、モデルが読み込めれば該当します。2 つのパターンがあります。

| 種類 | 誰が入力するか | 例 |
|---|---|---|
| 直接 | サービスのユーザー自身が入力欄に | チャットボットに「前の指示は無視して」といった文章を送る |
| 間接 | モデルが読み込む外部コンテンツの中に | ウェブページ、メール本文、アップロードされたファイル、ツールの結果などに指示文が含まれている |

脱獄 (jailbreak) は直接インジェクションの一種で、モデルの安全ルールを完全に回避しようとする試みです。

Anthropic のドキュメントでは、2 つの脅威モデルが異なることを説明しています。直接系はユーザーが攻撃者です。間接系ではユーザーは信頼できるものの、モデルが読み込む第三者のコンテンツに攻撃文が含まれています。[RAG](#/post/ai-rag) で文書を引き寄せたり、[ツール呼び出し](#/post/ai-tool-use) でウェブを読み取るサービスほど、間接系の割合が大きくなります。

OWASP は影響がサービスのコンテキストとモデルが持つ権限の大きさに依存すると述べています。システムプロンプトの漏洩、誤った出力、接続されたシステムでのコマンド実行まで範囲は広いです。そしてこの問題を完全に防ぐ方法はなく、被害を減らす方向であると明確に言っています。

## 機密情報の漏洩

OWASP が言う機密情報とは、個人情報、金融・健康記録、企業秘密、認証情報、法律文書などです。モデルが学習した内容や、サービスがプロンプトに付与した内部文書が回答として漏れるのが問題です。

OWASP が提案する対策は以下の通りです。

- 学習データや入力データから機密情報を特定して削除する（マスキング、パターンベースの削除）
- ユーザーとプロセスに必要なデータのみへのアクセスを許可する（最小権限）
- モデルがアクセスできる外部データソースを制限する
- ユーザーに機密情報の入力を行わないよう案内し、データの保存・利用ポリシーを公開する
- システムの初期設定をユーザーが変更したり閲覧したりできないようにする

同じページには以下のような文章もあります。出力の種類を制限するシステムプロンプト指示はプロンプトインジェクションで迂回される可能性があるため、それだけを信じてはいけません。したがって、「回答にこれを書かないで」という文句よりも、そもそもモデルの手元に入らないようにする方が優先されます。

## 権限の過剰なエージェント

[エージェント](#/post/ai-agent-loop) は、モデルがツールを選定して使用しながら作業を進めます。OWASP は、モデルの出力が予期せぬものや曖昧なもの、あるいは改ざんされた場合に被害を与えることを「過度な権限 (Excessive Agency)」と呼びます。原因は幻覚、直接・間接インジェクション、汚染された拡張機能、または他のエージェントなど多岐にわたります。ドキュメントで挙げられている根本原因は 3 つです。

| 根本原因 | 意味 | 方向性 |
|---|---|---|
| 過剰な機能 | サービスに必要なツールだけでなく不要なツールも付随している | ツールの数と機能を削減する |
| 過剰な権限 | 必要以上に広いアクセス権限、または何でもできる共有アカウントで実行 | 読み取り専用などの最小範囲、ユーザー自身の権限で実行 |
| 過剰な自律性 | 影響の大きい行動を検証や承認なしに実行する | 人間の承認 |

特にシェル実行のように範囲が開放されているツールよりも、目的が狭い専用ツールの使用を推奨する指摘が目立ちます。許可有無の判断はモデルに任せず、接続されたシステム側で権限チェックによって強制すべきです。[MCP](#/post/ai-mcp) で外部ツールを追加する場合も同様の基準が適用されます。

## 防御は層をなす

公式ガイドを並べると、防御は 4 つの層に整理される。

```
사용자 입력 → [1 입력 검사] → 모델 → [2 출력 검사] → 도구 실행 → [3 권한 최소화] → [4 사람 승인] → 실제 반영
```

| 層 | 行うこと | 根拠 |
|---|---|---|
| 1 入力検査 | 既知の攻撃パターンのフィルタ、軽量モデルによる危険入力の事前分類、入力長さ制限 | Anthropic, OpenAI, OWASP |
| 2 出力検査 | 期待する形式かコードで検証、関連性・根拠性の評価、モデレーション、出力トークン制限 | OWASP, OpenAI |
| 3 権限最小化 | 必要なツールのみ、読み取り専用、サンドボックス、機密値はそもそも見せない | OWASP, Anthropic |
| 4 人間承認 | 影響の大きい行動と高リスク分野の結果は人間が確認 | OWASP, OpenAI |

### 1. 入力検査

Anthropic のドキュメントでは、ユーザー入力がメインモデルに到達する前に軽量モデルでまずふるいを通すよう述べている。応答を「危険か、否か」といった単純な分類に制限し、構造化された出力を受け取ってコードが分岐させるような仕組みだ。既知のインジェクションパターンをフィルタリングする入力検証や、拒絶する方法まで記したシステムプロンプトも併せて使うよう述べている。OpenAI のガイドでは、入力長さを制限するとインジェクションリスクが減り、自由な入力ではなく検証済みのドロップダウンを使う方がよいと述べている。

間接インジェクションについては構造が核心だ。Anthropic ドキュメントの勧告を要約すると以下のようになる。

- 外部コンテンツはシステムプロンプトや通常のユーザーメッセージではなく、ツール結果 (tool_result) の欄に入れるのみ
- そのコンテンツが何でありどこから来たのか、ツール説明や結果構造に明記する
- ツール・ドキュメント・検索結果は信頼できないデータであり、指示を変えることはないとシステムプロンプトに明示する
- 外部文字列は JSON で包んで、データと指示の境界を明確にする
- ツールが返した内容も、同様の軽量モデル検査を経てからモデルに渡す

### 2. 出力検査

OWASP は期待する出力形式を定め、決定的なコードで合致しているか確認するよう述べている。応答が質問に関連しており、提供された資料に基づいているかもチェック対象だ。根拠のない回答をフィルタリングすることは [幻覚](#/post/ai-hallucination) 対策とも重なる。OpenAI はモデレーション API（無料）と出力トークン上限を推奨し、可能であればモデルが新たに書いた文章の代わりに検証済みのバックエンドコンテンツ（例：最も適切なヘルプドキュメント）を返すよう述べている。

### 3. 権限最小化

前節の過剰な権限付与がまさにこの層だ。Anthropic も成功したインジェクションの被害を最小限にするために、モデルに必要な機密値へのアクセスを防ぎ、ツールはサンドボックス内で実行し、権限範囲を狭く取るよう述べている。OWASP はこれに加え、ユーザー認証範囲での実行、拡張機能活動のログ・モニタリング、速度制限を追加する。

### 4. 人間承認

OWASP はリスクの高い行動には人間承認 (human-in-the-loop) を設けるよう述べている。OpenAI のガイドでは高リスク分野とコード生成において人間が出力を検証する必要があり、検証者がシステムの限界を知り、元資料で確認できる必要があると述べている。メール送信、決済、削除のように取り返しのつかない動作が典型的な承認対象だ。

## 運用時に併せて行うこと

- デプロイ前に意図的に攻撃文が含まれるドキュメント・メール・ツール結果で試験する。Anthropic は自分のエージェントを直接レッドチーム化し、OpenAI と OWASP も敵対的テストを推奨する。こうした試験は [評価](#/post/ai-evals) の一種としてまとめ、反復して行うのがよい。
- 出力を定期的に分析してインジェクションが成功した痕跡を見つけ、プロンプトとフィルタを見直す（Anthropic の継続的モニタリング）。
- 同じ迂回を繰り返すユーザーは制限またはブロックする（Anthropic の反復違反者対応）。
- ユーザーアカウントを要求し、ユーザー固有の安定した識別子を API に併せて送ることで、悪用が発生しても組織全体ではなく該当ユーザーを追跡できる（OpenAI の safety_identifier）。
- 報告窓口を設置し、人間が対応する。

こうした断片をサービスコードにまとめる枠組みは [ハネス](#/post/ai-harness) と呼ばれることもあるが、ガードレールはその中でモデルの前後とツール呼び出し地点に置かれる部品に近い。

## よくある誤解

- システムプロンプトに「無視しないで」と書くと詰む：助けにはなるが OWASP は完全な方法はないと釘を刺す。プロンプトは複数の層の一つだ。
- モデルが良くなればガードレールは不要：Anthropic のドキュメントですら Claude が元々こうした攻撃に抵抗力があると述べているにもかかわらず、追加段階を推奨する。
- 入力だけをブロックすればよい：間接インジェクションは入力窓を経由せず、ツール結果やドキュメントから入ってくる。出力と権限の層も別途必要だ。
- ガードレールはモデルの仕事：権限判断をモデルに委ねず、接続されたシステムで強制すべきだと OWASP の立場だ。

<details>
<summary>詳しい解説：なぜ間接インジェクションが難しいのか</summary>

モデルは、指示とデータを入力形式で完全に分離して受け取らない。システムプロンプト、ユーザーメッセージ、ツール結果がすべてトークン列として入ってくるため、外部コンテンツ内の指示が本当にユーザーからのものかどうかをモデル自身が判断しなければならない。この判定は確率的であり、100% にはならない。

Anthropic が推奨する構造的分離（tool_result へのみの配置、出典の明示、JSON エンコーディング）は、この判定を容易にする装置である。引用符やタグを閉じて指示領域から抜け出す経路を JSON エスケープが塞ぐという説明が文書にある。これらの装置が確률을低下させてもゼロにはできないため、成功時の被害を減らす権限最小化と人間による承認を後方に残す。防御層が複数ある理由はこれである。

</details>
