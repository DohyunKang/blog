One request is sent by the client, passes through a chain of middleware handled by the server's framework, the router selects the appropriate handler, and the response generated by the handler via the database returns along the same path back.

## In Simple Terms First

An analogy with ordering at a restaurant makes it easy to understand. The customer (client) places an order (request). The entrance staff writes it down on the waiting list (logging), checks if it's a reservation (authentication), and decides which kitchen staff should receive it (routing). The staff member searches the warehouse (DB) to prepare the dish, and the plate (response) leaves the hall.

Backend code handles this intermediate process. Since the browser only sends requests and receives responses, the middle part remains invisible.

## Shape of Requests and Responses

An HTTP request consists of a method (GET, POST, etc.), resource path, protocol version, optional headers, and an optional body. A response includes a protocol version, status code with a short message, headers, and an optional body. Here is an example from MDN:

```http
GET /users/1 HTTP/1.1
Host: example.com

HTTP/1.1 200 OK
Content-Type: application/json
```

When you enter an address in the address bar, the browser either opens a new TCP connection or reuses an existing one to send the above request. If the response is HTML, the browser parses it and requests scripts, CSS, and images mentioned there. This explains why multiple requests go to the server even after pressing Enter once. The side where the screen is drawn is covered separately in [How the Browser Renders the Screen → Rendering](#/post/fe-browser-render).

A proxy may also be inserted between the client and server. MDN states that a proxy can handle caching, filtering, load balancing, authentication, and logging. How many such layers exist before the server is discussed in [The Journey Until the Request Reaches the Server](#/post/infra-request-journey).

## Inside the Server

When a request arrives at the server process, the framework (Express, FastAPI, Spring, etc.) receives it and converts it into request and response objects. The subsequent steps are generally as follows:

| Step | Action | Example |
|---|---|---|
| Middleware | Common processing that all (or some) requests pass through | Logging, authentication, JSON parsing, CORS |
| Routing | Selecting a handler based on method and path | `GET /users/:id` |
| Handler | Actual business logic | Fetch user |
| Data Access | Calling DB, cache, or external APIs | Executing SQL |
| Response | Creating status code, headers, and body | `200` + JSON |
| Error Handling | Collecting exceptions from anywhere and responding | `500` |

Parts like `:id` in the path are placeholders, and the router extracts their actual values to pass them to the handler. How API paths are designed is covered in [REST API](#/post/be-api-rest).

## Middleware Forms a Chain

According to the Express documentation definition, middleware is a function that can access the request (`req`), response (`res`), and the next middleware (`next`). It can execute code, modify `req` and `res`, end the request-response cycle, or pass control to the next handler. If the response is not ended, `next()` must be called; otherwise, the request simply stops.

They execute in the defined order. Handlers for the same path are also checked sequentially, so if a response is sent earlier, subsequent ones are not executed. That's why authentication middleware should be placed before routes; incorrect ordering creates paths that bypass authentication.

Types are categorized based on Express into those attached to the entire app, those attached to a router, error-handling ones (with four arguments: `(err, req, res, next)`), built-in (`express.json`, etc.), and third-party modules. Error-handling middleware must declare all four arguments, including `next` even if unused; otherwise, it's treated as regular middleware, and the documentation notes that errors won't be caught.

Thinking of this structure like onion layers makes it easier to understand. The request enters from the outer layer inward, and the response exits from the inside outward. This is why logging middleware can write "one line on entry, one line on exit."

## Mini Framework I Built Itself

Reading only concepts leaves things vague, so I tried mimicking routing and middleware chains using only Python's standard library. Actual frameworks are much more complex, but the skeleton is the same.

<details>
<summary>Code (Execution Verified)</summary>

```python
import re

class App:
    def __init__(self):
        self.middlewares = []
        self.routes = []          # (method, regex, handler)

    def use(self, fn):
        self.middlewares.append(fn)

    def route(self, method, path):
        regex = re.compile("^" + re.sub(r":(\w+)", r"(?P<\1>[^/]+)", path) + "$")
        def deco(fn):
            self.routes.append((method, regex, fn))
            return fn
        return deco

    def handle(self, method, path, body=None):
        req = {"method": method, "path": path, "body": body, "params": {}}

        def dispatch(req):
            for m, rx, fn in self.routes:
                hit = rx.match(req["path"])
                if m == req["method"] and hit:
                    req["params"] = hit.groupdict()
                    return fn(req)
            return {"status": 404, "body": "not found"}

        chain = dispatch
        for mw in reversed(self.middlewares):
            chain = (lambda mw, nxt: lambda r: mw(r, nxt))(mw, chain)
        try:
            return chain(req)
        except Exception as e:
            return {"status": 500, "body": f"error: {e}"}

app = App()
DB = {"1": "kim", "2": "lee"}
log = []

def logger(req, nxt):
    log.append(f"-> {req['method']} {req['path']}")
    res = nxt(req)
    log.append(f"<- {res['status']}")
    return res

def auth(req, nxt):
    if req["path"].startswith("/admin"):
        return {"status": 401, "body": "login required"}
    return nxt(req)

app.use(logger)
app.use(auth)

@app.route("GET", "/users/:id")
def get_user(req):
    name = DB[req["params"]["id"]]
    return {"status": 200, "body": {"id": req["params"]["id"], "name": name}}

for args in [("GET", "/users/1"), ("GET", "/users/9"), ("GET", "/nope"), ("GET", "/admin/x")]:
    print(args, app.handle(*args))
print("\n".join(log))
```

Execution result:

```
('GET', '/users/1') {'status': 200, 'body': {'id': '1', 'name': 'kim'}}
('GET', '/users/9') {'status': 500, 'body': "error: '9'"}
('GET', '/nope') {'status': 404, 'body': 'not found'}
('GET', '/admin/x') {'status': 401, 'body': 'login required'}
-> GET /users/1
<- 200
-> GET /users/9
-> GET /nope
<- 404
-> GET /admin/x
<- 401
```

</details>

Three things stand out in the results:

- The route `/admin/x` is interrupted by the authentication middleware before reaching the handler, resulting in a 401 response. However, since the logger acts as an outer wrapper, it logs both entry and exit points.
- `/nope` returns a 404 because there is no matching route. A 404 is not an error; it is a normal response from the router indicating "no match found."
- Reading a non-existent key in the DB for `/users/9` triggered an exception, which was caught externally and converted to a 500 response. However, the log only shows `-> GET /users/9` without the corresponding `<-` line. This is because the exception bypassed the logger during exit, causing the exit log to be missing. In this code, the logger does not catch exceptions; similarly, in actual services, a single-line gap in error logs may occur for the same reason. The importance of where to handle errors lies here. Methods for aggregating errors continue in [Error Handling and Logging](#/post/be-error-logging).

In this code, `9` refers to a non-existent user, which should return a 404, but a 500 was returned instead. This happens if the handler does not distinguish between "not found" and "server error."

## Where Does DB Fit In?

Handlers may use SQL directly or go through service layers or repository layers. The reasons and methods for dividing these layers are explained in [Layered Architecture](#/post/be-layered-architecture). Since DB calls typically consume the largest portion of request time, they are the first place to suspect when performance slows down. Information on optimizing queries is available in [Indexes](#/post/db-index).

If a handler performs long-running tasks (e.g., sending emails, video conversion) within the request, the client must wait continuously. For such cases, it's better to enqueue the task and respond immediately; see [Async Tasks and Queues](#/post/be-async-queue).

## Common Misconceptions

- It is easy to assume that a single request corresponds to a single server. However, as explained by MDN, servers can be multiple machines sharing the load, and clients often don't know which specific server they're connecting to.
- If a response is sent in middleware but `next()` is still called, subsequent handlers may attempt to send another response, causing an error. Once a response is finalized, it should not be passed further.
- Status codes are contractual agreements set by the server; sending a 200 status with a body saying "failed" will still work technically. However, since clients, proxies, and monitoring tools rely on status codes, it's better to send the correct code.
- It is easy to assume that order doesn't matter. As in the demo above, middleware executes in the exact order they are registered.
