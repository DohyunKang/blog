API 키나 비밀번호 같은 시크릿은 완벽하게 숨기는 것보다, 새는 순간 바로 폐기하고 새로 발급할 수 있는 구조를 만들어 두는 게 관리의 핵심이었다.

## 시크릿이 뭔지

시크릿은 "이걸 아는 쪽이 나로 인정받는" 값이다. API 키, 액세스 토큰, DB 비밀번호, 개인 키(SSH·TLS), 웹훅 서명 값이 다 여기 들어간다. 로그인 비밀번호와 다른 점은 사람이 아니라 프로그램이 쓴다는 것이다. 사람이 기억해서 치는 게 아니라 코드나 설정 파일 어딘가에 놓여 있고, 그래서 새는 경로가 많다.

키가 새면 남이 내 계정으로 요청을 보낼 수 있다. 클라우드 키라면 서버를 마음대로 띄우고 요금이 청구된다. AI API 키라면 호출 비용이 내 카드로 나간다. 그래서 키 관리는 보안이기도 하지만 비용 문제이기도 하다.

## 어디서 새나

흔한 유출 경로를 모아 보면 거의 비슷하다.

| 경로 | 어떻게 새나 |
|---|---|
| 깃 저장소 | `.env`나 설정 파일을 그대로 커밋, 코드에 키를 직접 적음 |
| 깃 기록 | 나중에 지워도 이전 커밋에 그대로 남아 있음 |
| 로그 | 요청 헤더나 설정 전체를 출력하다 키가 같이 찍힘 |
| 채팅·문서 | 슬랙, 이슈, 위키에 "이거 써" 하고 붙여 넣음 |
| 클라이언트 코드 | 프런트 번들이나 앱에 키를 넣어 배포하면 누구나 열어 볼 수 있음 |
| CI/CD | 파이프라인 변수가 로그에 노출되거나, 오래 쓰는 큰 권한 키를 파이프라인에 둠 |

깃은 특히 주의가 필요하다. GitHub의 secret scanning은 모든 브랜치의 전체 기록과 이슈·PR 본문, 위키까지 훑는다고 문서에 나온다. 반대로 말하면 이 정도 범위에 키가 남아 있을 수 있다는 뜻이다. 그리고 공개 저장소에 올린 키는 사람이 보기 전에 자동으로 긁어 가는 도구들이 있다는 얘기를 흔히 듣는데,

## 원칙 네 가지

OWASP의 Secrets Management Cheat Sheet가 정리한 내용 중 핵심만 추렸다.

1. 중앙에서 관리한다. 팀마다 방식이 다르면 사고가 났을 때 어디에 뭐가 있는지 찾기 어렵다. 저장·인증·감사 로그를 한곳에서 표준화하라고 한다.
2. 최소 권한을 준다. 시크릿마다 누가 읽고 바꿀 수 있는지를 세밀하게 나눈다. 엔지니어 전원이 전부 볼 수 있으면 안 된다.
3. 주기적으로 돌린다(회전, rotation). 훔친 키의 수명을 짧게 만드는 방법이다. 가능하면 자동화한다. 사용자 비밀번호는 예외로, 침해가 의심될 때 위주로 바꾼다고 한다.
4. 가능하면 짧게 쓰고 버리는 값(동적 시크릿)을 쓴다. 세션이나 배포마다 새로 발급하고 임대 시간을 짧게 둔다. 앱을 재시작한다고 이미 훔쳐 간 키가 취소되는 건 아니고, 취소는 만료나 명시적 폐기로만 된다.

이 네 가지가 서로 이어진다. 회전이 쉬우려면 키를 쓰는 곳이 한 군데에 모여 있어야 하고, 권한이 좁아야 새도 피해가 작다. 환경변수와 `.env`, 시크릿 매니저가 어떻게 이어지는지는 [자세히 → 환경변수와 시크릿 관리](#/post/cloud-secrets)에 따로 정리했다.

## 저장은 어디에

단계로 보면 대략 이렇게 올라간다.

| 단계 | 방식 | 비고 |
|---|---|---|
| 0 | 코드에 직접 적기 | 쓰면 안 된다 |
| 1 | `.env` 파일 + `.gitignore` | 개인 개발·작은 프로젝트의 최소선 |
| 2 | 배포 환경의 환경변수·플랫폼 시크릿 | 코드와 분리됨 |
| 3 | 시크릿 매니저(클라우드 제공 서비스, Vault 등) | 권한·감사·회전을 같이 해결 |

`.env`는 로컬 개발에는 편하지만 파일이 곧 비밀이라, 저장소에는 `.env.example`처럼 이름만 있는 파일을 올리고 진짜 값은 올리지 않는 식으로 나눠 둔다. 그리고 `.gitignore`는 아직 추적하지 않은 파일에만 작동한다. 이미 커밋한 파일은 `.gitignore`에 넣어도 계속 추적된다. 이게 흔한 실수라서 아래 오해 항목에 다시 적었다.

OWASP는 CI/CD에도 같은 원칙을 적용하라고 한다. 파이프라인을 운영 환경만큼 조심해서 다루고, 오래 쓰는 큰 키를 파이프라인에 두지 말고, 가능하면 시크릿을 쓰는 쪽이 직접 시크릿 매니저에서 가져가게 해서 파이프라인이 값을 아예 만지지 않게 하라는 식이다. 배포 쪽 흐름은 [자세히 → CI/CD](#/post/cloud-cicd)에 있다.

## 새어 버렸다면

순서가 중요하다. 먼저 하는 일이 "지우기"가 아니라 "폐기"다.

OWASP는 대응 순서를 이렇게 적는다. 노출된 시크릿을 즉시 폐기하고, 새 값으로 회전하고(가급적 자동으로), 코드와 로그 같은 노출 위치에서 지우고, 누가 언제 접근했는지 기록을 남긴다. GitHub 문서도 같다. 먼저 키를 회전하고, 기록에서 지우는 건 선택이다. 키를 폐기하고 나면 기록에 남은 값은 이미 못 쓰는 값이라 굳이 기록을 고치지 않아도 되는 경우가 많다고 한다.

그래도 기록에서 지워야 한다면 GitHub 문서의 주의점이 꽤 많다.

- 기록을 다시 쓰면 해당 커밋과 그 이후 커밋의 해시가 다 바뀐다.
- 다른 사람의 로컬 복제본이나 포크는 그대로라서, 그쪽에서 다시 올리면 값이 되살아날 수 있다.
- GitHub의 캐시된 화면이나 PR이 옛 커밋을 해시로 계속 보여 줄 수 있어서, 이럴 땐 GitHub Support에 정리를 요청해야 한다.

즉 "지웠으니 괜찮다"가 아니다. 그래서 키 폐기가 먼저고, 기록 정리는 그다음이다.

<details>
<summary>자세한 풀이: git-filter-repo로 기록에서 지울 때</summary>

GitHub 문서 기준으로 정리한 순서다.

1. 키를 먼저 폐기·회전한다.
2. 열린 PR을 먼저 병합하거나 닫는다. 닫은 PR의 diff 화면이 기록 수정 후 사라질 수 있다.
3. `git-filter-repo` 2.47 이상에서 `--sensitive-data-removal` 옵션을 쓴다.
4. 파일 하나를 통째로 지우려면 `--invert-paths --path <경로>`, 문자열만 바꾸려면 `--replace-text <파일>`을 쓴다. 파일이 이동·이름 변경된 적이 있으면 옛 경로도 같이 적는다.
5. 도구가 만드는 `changed-refs` 파일로 영향받는 PR 수를 확인한다. 이 단계를 넘기면 되돌릴 수 없다고 한다.
6. `git push --force --mirror origin`으로 올린다. `refs/pull/` 쪽은 실패하는데, 이건 GitHub Support가 처리한다.
7. 공동 작업자는 다시 복제하거나, 옛 기록에서 만든 브랜치를 병합이 아니라 rebase로 옮겨야 한다. 병합하면 오염된 기록이 돌아온다.

브랜치 보호가 force push를 막고 있으면 잠깐 풀어야 하고, 커밋 서명은 무효가 된다.

</details>

## 막는 장치들

사고 후 대응만 있는 건 아니다. 올리기 전에 막는 장치가 있다.

- push protection: GitHub에서 push를 하는 순간 하드코딩된 시크릿이 있는지 검사해서 저장소에 닿기 전에 막는다. 제휴사 패턴, 개인 키나 DB 연결 문자열 같은 일반 패턴, 직접 정의한 정규식, 그리고 비밀번호 같은 비정형 값을 문맥으로 찾는 AI 탐지(공개 프리뷰)를 본다. 다만 쓰기 권한이 있으면 사유를 대고 우회할 수 있고, 우회는 감사 로그에 남는다. 저장소 단위로 켜는 방식은 기본이 꺼져 있다고 문서에 적혀 있다.
- secret scanning: 이미 올라간 것을 전체 기록에서 찾아 알림을 준다. 제휴 서비스의 키는 해당 서비스에 바로 알려서, 서비스가 알아서 폐기하기도 한다.
- 로컬 커밋 전 검사: 도구마다 다르지만 원리는 비슷하게, 커밋 직전에 패턴을 훑는다. 아래 코드는 그 원리만 보여 주는 장난감이다.

<details>
<summary>코드: 정규식으로 키 모양 찾기 (직접 실행해서 확인함)</summary>

아래 키는 AWS 문서에 나오는 예시 형태와 임의의 더미 문자열이다. 진짜 키가 아니다.

```python
import re

PATTERNS = {
    "AWS 액세스 키 ID": re.compile(r"\bAKIA[0-9A-Z]{16}\b"),
    "개인 키 헤더": re.compile(r"-----BEGIN (?:RSA |EC )?PRIVATE KEY-----"),
    "대입문 속 비밀값": re.compile(
        r"""(?i)(?:api[_-]?key|secret|token|password)\s*[:=]\s*['"][^'"\s]{12,}['"]"""
    ),
}

def scan(text):
    hits = []
    for no, line in enumerate(text.splitlines(), 1):
        for name, pat in PATTERNS.items():
            if pat.search(line):
                hits.append((no, name))
    return hits

FAKE_AWS = "AKIA" + "IOSFODNN7EXAMPLE"  # AWS 문서의 공개 예시값(실제 키 아님)
sample = '''import boto3
AWS_KEY = "{FAKE_AWS}"
api_key = "dummy-not-a-real-key-123456"
url = os.environ["DB_URL"]
timeout = "30"
'''.replace("{FAKE_AWS}", FAKE_AWS)
for no, name in scan(sample):
    print(no, name)
```

실행하면 2번 줄(AWS 키 모양)과 3번 줄(대입문 속 비밀값)만 잡히고, 환경변수에서 읽는 4번 줄과 짧은 값인 5번 줄은 안 잡혔다. 이 정규식은 모양만 보기 때문에 놓치는 것도 많고(모양이 없는 임의의 비밀번호), 아무 문자열이나 잡는 오탐도 생긴다. 실제 도구는 패턴이 훨씬 많고, 키가 아직 유효한지 확인하는 기능도 붙는다.

</details>

## 흔한 오해

- `.gitignore`에 넣었으니 안전하다: 아직 추적하지 않은 파일에만 효과가 있다. 이미 커밋한 파일은 계속 추적된다.
- 커밋을 지웠으니 끝났다: 기록, 포크, 다른 사람의 복제본, 캐시에 남을 수 있다. 폐기가 먼저다.
- 비공개 저장소니까 괜찮다: 접근 권한이 있는 사람이 늘거나 저장소를 공개로 바꾸는 순간 같이 노출된다. 코드에 키를 적는 습관 자체가 문제다.
- 환경변수면 안전하다: 코드 밖에 둔다는 것뿐이다. 로그에 찍히거나 프로세스 정보로 새는 건 별개 문제다. 시크릿 매니저는 권한·감사·회전을 더해 준다.
- 프런트 코드에 넣고 난독화하면 된다: 클라이언트에 내려가는 값은 누구나 볼 수 있다고 보는 게 맞다. 서버를 거치게 만들어야 한다.
- 회전은 귀찮으니 한 번 발급해서 오래 쓴다: 오래 쓸수록 유출 후 피해 기간이 길어진다. 자동화가 어려우면 최소한 폐기 절차는 미리 정해 둔다.
