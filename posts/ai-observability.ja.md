観測性 (Observability) は、サービスから外部へ出力される記録を確認することで、内部で何が起こったかを推測できるようにする仕組みです。LLM サービスでは、ユーザーの 1 つのリクエストがプロンプトの組み立て、検索、モデル呼び出し、ツール実行などの複数の段階に分割されるため、これらの段階を一つにまとめて残すトレーシングが中核となります。

## 通常のログだけではなぜ足りないのか

Web サーバーのログは、リクエストが到達し、200 を返したことを示します。LLM の機能では、200 が返されても回答が間違っている可能性があります。エラーがないため、ログには何も痕跡が残らないのです。

その理由は 2 つあります。

- **出力が一様ではない**。同じ入力に対して異なる回答が返されるため、再現できない報告については、実際にやり取りされたプロンプトとレスポンスが残されている必要があります。この変動性が評価が必要な理由でもあります ([LLM 評価](#/post/ai-evals))。
- **1 つのリクエストが複数の段階を通過する**。[エージェントループ](#/post/ai-agent-loop) が動作すると、モデル呼び出しが 5 回、[ツール呼び出し](#/post/ai-tool-use) が 3 回など、1 つのリクエスト内に含まれます。ログが羅列されていても、どの行がどのリクエストの何番目の段階か紐付けられていないと読み解くことができません。

## trace と span

OpenTelemetry ドキュメントの定義を訳すと以下のようになります。trace はリクエストがアプリケーションを通過した全経路であり、同じ trace ID を持つ span 群で構成されています。span はその中の作業の一つです。名前、親 span の ID（最上位は空）、開始・終了時刻、属性 (attributes)、イベント、ステータスを有します。子 span は親の ID を格納するため階層構造が生まれます。

LLM リクエスト 1 つを図示するとこのようになります。

```
trace  (사용자 질문 1건)
└─ span: 에이전트 실행            ← 전체 12.4초
   ├─ span: 검색                  ← 0.6초
   ├─ span: 모델 호출 #1          ← 3.1초, 도구 요청이 나옴
   ├─ span: 도구 실행 (주문 조회) ← 0.9초
   └─ span: 모델 호출 #2          ← 7.2초, 최종 답
```

各セルにかかった時間が表示されているため、遅いリクエストが遅い箇所がすぐにわかります。上記の数字は形状を示すために作成した例です。

span の属性は名前のペアと値のペアであり、OpenTelemetry は標準的な属性名を定めたものをシマンティック規約 (semantic conventions) と呼びます。同じ名前を使用すれば、ツールが異なっても同じ形式で読み取れます。

## 何を記録するか

LLM 側で残す内容は概ね以下の通りです。

| 項目 | なぜ必要なのか |
|---|---|
| プロンプト (入力メッセージ) | その時モデルが実際に受け取った内容を確認して原因を特定するため |
| レスポンス (出力メッセージ) |どのような回答が返されたか、後で確認できるようにするため |
| モデル名・パラメータ | モデルを変更した後に変化があったかを比較するため |
| トークン数 (入力・出力) | コスト計算の材料となるため |
| 遅延時間 | span の開始・終了時刻から得られる |
| ツール名・引数・結果 | エージェントが不適切なツールを選択したか確認するため |
| 終了理由 | 長さ制限で切断されたかなど |
| ユーザー・セッション ID、バージョン、タグ | 特定のユーザーやデプロイバージョンでフィルタリングするため |

コストはトークン数にモデルごとの単価を掛けた値であるため、別途記録するよりもトークン数を残しておいて後から計算する方が容易です。モデル呼び出しの単価は変更される可能性があるため、記録時点の単価も同様に保持すべきかはツールごとに異なる場合があります。

## OpenTelemetry の GenAI 規約

OpenTelemetry には、このような属性名を整理した GenAI シマンティック規約が存在します。現在は opentelemetry.io のドキュメントページから別リポジトリ (semantic-conventions-genai) に移行中です。このリポジトリの README は、GenAI クライアント、MCP、プロバイダーごとの規約について span・metric・event を扱っていると紹介しています。

移行前の属性レジストリページに記載されていたいくつかの名前を見ると、概要がつかめます。

| 属性 | 意味 |
|---|---|
| `gen_ai.operation.name` |どのような作業か。`chat`, `embeddings`, `execute_tool`, `invoke_agent`, `retrieval` などが値として返される |
| `gen_ai.request.model` | リクエストを送信したモデル名 |
| `gen_ai.usage.input_tokens` | 入力トークン数 (キャッシュされた入力トークンを含める必要があると記載されている) |
| `gen_ai.usage.output_tokens` | 出力トークン数 |
| `gen_ai.response.finish_reasons` | 生成が停止した理由 |
| `gen_ai.tool.name` | エージェントが使用したツールの名前 |
| `gen_ai.input.messages` / `gen_ai.output.messages` | モデルに入力された会話と出力されたメッセージ |

operation の名前に `execute_tool`, `invoke_agent`, `retrieval` があるため、モデル呼び出しだけでなくツール・エージェント・検索の段階も同じ枠組みで残すことを意図した規約です。該当ページではこれらの値は現在開発 (development) ステージとして表示されており、名前が変更される可能性があります。

## 代表的なツール

OpenTelemetry は規格および SDK であり、ログを収集・可視化する側は別の製品です。公式ドキュメントから概念を読み取った内容を以下に記します。

LangSmith では `run` と `trace` という用語を使います。`run` は LLM の呼び出し、プロンプトの組み立て、ドキュメント検索などの単一の作業単位であり、OpenTelemetry の `span` と比較されます。`trace` は一つの作業における `run` の集まりで、`trace ID` で束縛されます。複数のターンにわたる対話は一つの `trace` が一つのターンとなり、`thread_id` メタデータで束縛してスレッドとして扱います。各 `run` にはスコア（フィードバック）を付与でき、タグとスコア値で構成されます。

Langfuse では `trace` の下に `observation` があり、その種類として `span`、`generation`、`event` があります。LLM の呼び出し、ツール呼び出し、検索ステップなどが observation です。一度のチャットが一つの `trace` であり、複数の `trace` を束縛する単位は `session` です。収集機能は OpenTelemetry の上に構築されており、SDK がバッチで集めてバックグラウンドに送信します。短いアプリケーションについては終了前に `flush()` を呼び出すことでデータを失わないようにするとドキュメントに記載されています。

用語の違いはあるものの構造は同じです。一つのリクエスト（`trace`）に対して段階（`span`/`run`/`observation`）が階層として付加され、そこに入出力やメタデータが付与されます。

## 評価・回帰と続く部分

ログを蓄積しておくと、評価側で利用する余地が生じます。

- サービス内で異常だった `trace` を評価セットの事例に移動させます。評価記事でも運用ログを良い評価事例の材料として捉えていると述べています。
- プロンプトやモデルを変更した後、同じ種類の `trace` における遅延、トークン数、失敗率がどのように変化したかを比較します。これが回帰を検出する根拠となります。
- 応答にスコアを付与します。LangSmith は `run` 単位でフィードバックを付与する構造を持っています。人間の「いいね」「いいねしない」か自動採点かに関わらず、どの `trace` に対するスコアであるかを紐付けることで、低いスコアの要因となった段階を開示できます。
- [ガードレール](#/post/ai-guardrails) が何かを阻止した際も、その事実を `span` やイベントとして残しておけば、どれほど頻繁にトリガーされるかを計測できます。

まとめると、評価はスコアを作成し、観測可能性はそのスコアの要因がどこにあるかを開示します。

## 個人情報マスキング

プロンプトと応答をそのまま残すことが観測可能性の核心的な価値ですが、それが 곧 위험です。ユーザー入力には名前、連絡先、内部ドキュメントの内容が含まれる可能性があります。OpenTelemetry の属性レジストリの `gen_ai.input.messages` および `gen_ai.output.messages` 項目にも、ユーザー情報や個人識別情報（PII）が含まれる可能性についての警告が付けられています。

Langfuse はマスキング機能を別途用意しています。データがアプリケーションを離れる前に、入力・出力・メタデータを隠す用途です。Python SDK ではエクスポート時に `span` を受け取り属性を削除または変更するフック（`mask_otel_spans`）の使用を推奨しており、JS/TS SDK では `LangfuseSpanProcessor` に `mask` 関数を渡します。OpenTelemetry 単体での構成の場合も、アプリケーション内の span プロセッサや Collector の redaction・transform プロセッサでマスキング可能であるとしています。ドキュメントに記載されている制約もあります。この関数は高速かつ決定的であり、例外が発生したり不正な値を返したりするとそのバッチ全体を破棄します。

<details>
<summary>マスキング設計時に検討すべき点</summary>

- マスキングの位置：アプリケーション内でマスキングすれば外部に漏れず、Collector でマスキングすれば一元管理できます。
- 何をマスキングするか：メールアドレスや電話番号などのパターン、入力本文全体、ユーザー ID のハッシュ値など選択肢があります。
- 本文を残さない選択肢もあります：トークン数、遅延、ツール名などのメタデータのみを残せばリスクは大幅に減りますが、原因を特定する手がかりも減少します。
- 保存期間：LangSmith SaaS のドキュメントでは収集後 180 日間の保存と記載されています。使用するツールの保存期間を確認しておきます。

</details>

## よくある誤解

- ログを多く出力すれば観測可能性がある：段階が `trace ID` で束縛されていなければリクエスト単位で読み込めません。
- 観測可能性があれば品質が保証される：ログは事後に確認するもので、防ぐのはガードレールであり、スコア付けは評価の一部です。
- プロンプトと応答をすべて残すのが良い：個人情報が混じるため、何を残すべきかを決定する必要があります。
- OpenTelemetry は可視化画面である：規格および SDK であり、画面は LangSmith や Langfuse などの別ツールや他のバックエンドが担当します。
