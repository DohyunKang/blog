트랜잭션은 여러 SQL을 "전부 되거나 전부 안 되거나"로 묶는 단위이고, 격리 수준은 동시에 도는 트랜잭션끼리 서로의 중간 상태를 얼마나 보게 둘지 정하는 설정이다.

## 트랜잭션이 뭔지

계좌이체를 생각하면 쉽다. A 계좌에서 30원을 빼고 B 계좌에 30원을 더하는 쿼리 두 개가 필요하다. 첫 번째만 실행되고 서버가 죽으면 돈 30원이 사라진다. 이 두 쿼리를 하나로 묶어 "둘 다 반영하거나, 둘 다 없던 일로 하자"고 하는 것이 트랜잭션이다.

```sql
BEGIN;
UPDATE acc SET bal = bal - 30 WHERE id = 1;
UPDATE acc SET bal = bal + 30 WHERE id = 2;
COMMIT;   -- 문제가 생기면 COMMIT 대신 ROLLBACK
```

`COMMIT`을 하면 묶음 전체가 확정되고, `ROLLBACK`을 하면 `BEGIN` 이후의 변경이 전부 취소된다. 직접 돌려 봤다. 파이썬 sqlite3로 A에서 30을 뺀 뒤 일부러 예외를 내고 롤백했더니 잔액이 `[(1, 100), (2, 0)]` 그대로였다. 중간에 죽어도 반쪽 상태가 남지 않는다.

## ACID

트랜잭션이 지켜 주는 성질 네 가지를 앞글자로 ACID라고 부른다.

| 글자 | 이름 | 한마디 |
|---|---|---|
| A | Atomicity (원자성) | 전부 되거나 전부 안 된다 |
| C | Consistency (일관성) | 끝난 뒤에도 제약조건(PK, FK, CHECK 등)이 깨지지 않는다 |
| I | Isolation (격리성) | 동시에 도는 트랜잭션이 서로 간섭하지 않는 것처럼 보인다 |
| D | Durability (지속성) | 커밋된 건 장애가 나도 남는다 |

원자성과 지속성은 비교적 이해하기 쉽다. 헷갈린 건 일관성과 격리성이다. 일관성은 DB가 마법처럼 비즈니스 규칙을 알아서 지켜 준다는 뜻이 아니다. 내가 선언한 제약조건을 트랜잭션 끝에 어기지 못하게 막아 준다는 정도로 이해했다. 격리성은 "완전히 간섭 없음"에서 "조금은 보임"까지 단계가 있고, 그 단계가 격리 수준이다. 여기서부터가 이 글의 본론이다.

## 동시에 돌 때 생기는 문제

트랜잭션이 하나씩만 돌면 문제가 없다. 여러 개가 동시에 돌면 이상한 일이 생길 수 있고, PostgreSQL 문서는 네 가지로 정의한다.

- 더티 리드(dirty read): 아직 커밋 안 된 다른 트랜잭션의 변경을 읽는다.
- 반복 불가능 읽기(nonrepeatable read): 같은 행을 두 번 읽었는데 그 사이 다른 트랜잭션이 커밋해서 값이 달라져 있다.
- 팬텀 읽기(phantom read): 같은 조건으로 두 번 조회했는데 그 사이 커밋된 다른 트랜잭션 때문에 조건에 맞는 행의 집합 자체가 달라져 있다.
- 직렬화 이상(serialization anomaly): 동시에 커밋된 결과가, 그 트랜잭션들을 한 줄로 세워 하나씩 돌린 어떤 순서와도 맞지 않는다.

[자세히 → 인덱스](#/post/db-index)가 조회 속도 얘기라면, 이쪽은 "같은 데이터를 동시에 건드릴 때 무엇이 보이는가" 얘기다.

## 격리 수준

SQL 표준은 격리 수준을 네 단계로 정하고, 단계마다 위 현상 중 무엇을 허용하는지가 다르다. 표준 기준은 이렇다.

| 격리 수준 | 더티 리드 | 반복 불가능 읽기 | 팬텀 읽기 | 직렬화 이상 |
|---|---|---|---|---|
| Read Uncommitted | 가능 | 가능 | 가능 | 가능 |
| Read Committed | 불가 | 가능 | 가능 | 가능 |
| Repeatable Read | 불가 | 불가 | 가능 | 가능 |
| Serializable | 불가 | 불가 | 불가 | 불가 |

위로 갈수록 느슨하고 빠르고, 아래로 갈수록 엄격하고 비싸다. 다만 이건 표준의 최소 요구이고, 실제 DB는 구현마다 다르다. PostgreSQL 문서 표를 보면 이렇다.

- Read Uncommitted는 이름만 받아 주고 실제로는 Read Committed처럼 동작한다. 그래서 더티 리드가 일어나지 않는다.
- Repeatable Read는 표준보다 강하다. 팬텀 읽기도 막는다. 직렬화 이상은 남는다.
- 기본값은 Read Committed다. 문서에 "각 문장이 새로운 스냅샷을 본다"고 나온다.

MySQL(InnoDB)이나 다른 DB는 같은 이름이어도 동작이 다를 수 있다. 이 글에서는 확인한 PostgreSQL 기준으로만 적었다.

## 수준마다 어떻게 다른지 (PostgreSQL)

Read Committed에서는 `SELECT`가 "쿼리가 시작되기 전에 커밋된 데이터"만 본다. 한 트랜잭션 안에서 같은 `SELECT`를 두 번 하면 그 사이에 다른 트랜잭션이 커밋했을 때 결과가 달라질 수 있다.

Repeatable Read는 트랜잭션의 첫 문장에서 스냅샷을 고정한다. 이후 `SELECT`는 계속 같은 데이터를 본다. 대신 내가 고치려는 행을 다른 트랜잭션이 먼저 바꿔 커밋했다면 이런 에러가 난다.

```
ERROR:  could not serialize access due to concurrent update
```

문서는 이럴 때 "현재 트랜잭션을 중단하고 처음부터 전부 다시 시도하라"고 안내한다.

Serializable은 Repeatable Read에 더해, 결과가 순차 실행과 달라질 수 있는 의존 관계까지 감지해서 한쪽을 롤백한다. 이 수준을 쓰면 애플리케이션이 재시도를 준비해야 하고, 직렬화 실패는 SQLSTATE `40001`로 돌아온다고 문서에 나온다.

정리하면 높은 수준을 쓸수록 "실패하고 다시 하기"가 애플리케이션 몫으로 넘어온다. 엄격함의 값은 성능만이 아니라 재시도 코드이기도 하다.

## 격리 수준만으로는 안 막히는 것: 갱신 손실

격리 수준 얘기를 하다 보면 놓치기 쉬운 게 갱신 손실(lost update)이다. 코드가 값을 읽어 와서 계산한 뒤 덮어쓰는 방식일 때 생긴다. 파이썬으로 재현해 봤다. 잔액이 100인 계좌에서 두 연결이 각각 30과 50을 빼려 한다. 기대값은 20이다.

```python
x = a.execute("select bal from acc where id=1").fetchone()[0]   # 100
y = b.execute("select bal from acc where id=1").fetchone()[0]   # 100
a.execute("update acc set bal=? where id=1", (x - 30,))
b.execute("update acc set bal=? where id=1", (y - 50,))
# 결과: 50 (기대값 20)
```

둘 다 100을 읽고 각자 계산해서 덮어썼기 때문에 앞의 갱신 30이 사라졌다. 이 실험은 sqlite3로 했다(PostgreSQL은 설치하지 않아서 돌려 보지 않았다). 일반적인 읽기-계산-쓰기 패턴의 문제를 보여 주려는 용도다. 해결은 계산을 DB에게 넘기는 것이다.

```python
a.execute("update acc set bal = bal - 30 where id=1")
b.execute("update acc set bal = bal - 50 where id=1")
# 결과: 20
```

`bal = bal - 30`은 DB가 읽고 쓰는 걸 한 문장 안에서 처리하니 덮어쓰기가 안 난다.

## 락: 비관적과 낙관적

읽은 값을 기반으로 애플리케이션에서 판단해야 하는 경우엔 락을 쓴다. 두 가지 방식이 있다.

비관적 락은 "충돌이 날 것 같으니 먼저 잠그자"는 쪽이다. PostgreSQL에서는 `SELECT ... FOR UPDATE`를 쓴다. 문서에 따르면 읽은 행은 현재 트랜잭션이 끝날 때까지 다른 트랜잭션이 잠그거나 수정하거나 삭제할 수 없고, 그런 시도는 끝날 때까지 기다리게 된다.

```sql
BEGIN;
SELECT bal FROM acc WHERE id = 1 FOR UPDATE;   -- 이 행을 잠근다
UPDATE acc SET bal = bal - 30 WHERE id = 1;
COMMIT;
```

낙관적 락은 "웬만하면 충돌 안 나니 일단 하고, 저장할 때 확인하자"는 쪽이다. 보통 행에 `version` 컬럼을 두고, 읽을 때의 버전과 같을 때만 갱신한다.

```python
def save(conn, body, ver):
    return conn.execute(
        "update doc set body=?, ver=ver+1 where id=1 and ver=?", (body, ver)
    ).rowcount

save(a, 'A', 1)   # 1  (성공)
save(b, 'B', 1)   # 0  (이미 ver이 2라서 갱신된 행이 없음 -> 충돌)
```

`rowcount`가 0이면 누군가 먼저 바꿨다는 뜻이니 다시 읽고 다시 시도하면 된다. 실제로 돌려 보니 A는 1, B는 0이 나왔다.

| | 비관적 락 | 낙관적 락 |
|---|---|---|
| 방식 | 읽을 때 잠금 | 저장할 때 버전 확인 |
| 충돌이 잦을 때 | 기다리니 안정적 | 재시도가 많아 낭비 |
| 충돌이 드물 때 | 잠금 비용만 든다 | 가볍다 |
| 주의점 | 오래 잡으면 대기·데드락 | 재시도 코드가 필요 |

어느 쪽이 낫다기보다 충돌이 얼마나 잦은지로 고르는 문제로 이해했다.

## 데드락

락을 쓰면 데드락(교착)이 생길 수 있다. 트랜잭션 1이 계좌 11111을 수정한 뒤 22222를 수정하려 하고, 트랜잭션 2가 22222를 수정한 뒤 11111을 수정하려 하면 서로 상대가 쥔 락을 기다리며 영원히 멈춘다.

PostgreSQL 문서는 데드락을 자동으로 감지해 관련 트랜잭션 중 하나를 중단시킨다고 한다. 어느 쪽이 중단될지는 예측하면 안 된다고도 적는다. 예방법으로는 "여러 객체의 락을 항상 같은 순서로 잡기"를 제일 먼저 든다. 위 예시도 두 트랜잭션이 같은 순서로 갱신했다면 데드락이 없었다고 한다. 순서를 맞추기 어려우면 데드락으로 중단된 트랜잭션을 재시도하는 방법도 있다. 또 락을 잡은 채 사용자 입력을 기다리는 식으로 트랜잭션을 오래 열어 두는 건 좋지 않다고 문서가 경고한다.

여기서도 결론은 재시도다. 직렬화 실패도, 낙관적 락 충돌도, 데드락도 "처음부터 다시"로 수습한다.

## 흔한 오해

- 트랜잭션으로 묶으면 동시성 문제가 사라진다: 묶는 건 원자성이다. 동시성은 격리 수준과 락이 맡고, 기본값 Read Committed에서는 앞의 갱신 손실 같은 패턴이 그대로 일어날 수 있다.
- Serializable만 쓰면 다 해결된다: 막긴 하지만 실패하는 트랜잭션이 생기고, 재시도 코드가 없으면 에러가 사용자에게 그대로 간다.
- 격리 수준 이름은 DB마다 같은 뜻이다: 표준은 최소 요구일 뿐이고 구현은 다르다. PostgreSQL만 해도 Read Uncommitted가 Read Committed로 동작한다.
- 락을 걸면 느려지니 쓰지 않는 게 낫다: 충돌이 잦은 곳에서는 락이 오히려 재시도 폭풍을 막는다.

<details>
<summary>자세한 풀이: 스냅샷과 MVCC는 왜 나오나</summary>

PostgreSQL 문서가 Read Uncommitted를 Read Committed로 매핑하는 이유로 든 말이 "PostgreSQL의 다중 버전 동시성 제어(multiversion concurrency control) 구조에 맞는 유일한 합리적 방식"이다. 행을 덮어쓰지 않고 버전별로 두고, 각 트랜잭션이 자기 기준 시점의 버전을 읽게 하는 구조라서 읽기가 쓰기를 막지 않는다. 그래서 "더러운" 중간 값을 읽을 방법이 없다.

내가 위에서 sqlite3로 확인한 것도 비슷한 맥락이다. 쓰기 연결이 커밋하기 전에 읽기 연결로 조회하면 100이 그대로 나왔고, 커밋 후에는 999가 나왔다. 다만 sqlite의 동작 방식은 PostgreSQL과 다르니 격리 수준 비교용으로는 쓰지 않았다.

</details>

<details>
<summary>자세한 풀이: 용어 정리</summary>

- 커밋(commit): 트랜잭션의 변경을 확정한다.
- 롤백(rollback): 트랜잭션의 변경을 취소한다.
- 스냅샷: 특정 시점 기준으로 보이는 데이터의 모습.
- 직렬화(serializable): 동시에 돌았더라도 결과가 한 줄로 세워 돌린 것과 같음.

</details>
