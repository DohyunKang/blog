状态管理是决定屏幕需要记住哪些值以及谁来修改这些值的工作。相比选择库，首先对值的类型进行分类更为重要。

## 什么是状态 (State)

状态 (state) 是指随着时间推移会发生变化，且一旦变化就需要同步更新屏幕的数值。输入框中的文字、已打开的菜单、登录用户、从服务器获取的列表等都属于状态。简单来说，屏幕是接收状态后渲染出的结果；因此，当屏幕显示异常时，通常也是状态出了问题。

[详见 → 组件设计](#/post/fe-component) 中会讨论到，如今的前端开发倾向于将界面拆分为组件。一旦拆分，就会产生“这个值由哪个组件持有”的问题。状态管理就是收集这个问题的答案而命名的概念。

## 将状态分为三类

起初我以为所有状态都是一样的，但考虑到它们的特性差异，进行分类处理更为方便。

| 类型 | 示例 | 通常位置 | 特征 |
|---|---|---|---|
| 局部状态 (Local State) | 输入中的文字、模态框是否打开 | 组件内部 | 无需其他地方知晓 |
| 共享（全局）状态 | 登录用户、主题、购物车 | 公共父级、Context、Store | 多个屏幕共同读写 |
| 服务器状态 (Server State) | 文章列表、商品信息 | 服务器为源头，客户端为副本 | 异步操作、可被他人修改、可能过期 |

判断依据主要有两点：“谁需要知道这个值”以及“原始数据在哪里”。如果原始数据在服务器，则为服务器状态；若不在服务器且仅由单个组件使用，则为局部状态；若多个组件共同使用，则为共享状态。

## 从局部开始并向上提升

React 文档的基本方针是：先将状态放在最近的地方，当需要时再将其提升。如果两个组件必须始终保持同步变化，应清除它们各自的状态，移至最近的公共父组件，并通过 props 向下传递。这种做法被称为“状态提升” (lifting state up)。文档指出，这是 React 代码中最常见的操作之一。

文档中的手风琴示例易于理解：如果每个面板都单独持有 `isActive`，则两个面板可以同时打开；而若父组件仅持有唯一的 `activeIndex`，则从结构上保证了“只能有一个打开”。文档也提到，提升状态后，所存储值的性质往往会发生变化。

```js
const [activeIndex, setActiveIndex] = useState(0);
<Panel isActive={activeIndex === 0} onShow={() => setActiveIndex(0)} />
```

由此引出的术语是受控组件与非受控组件。如果由自身状态驱动变化，则为非受控；如果通过 props 接收重要值来驱动变化，则为受控。非受控虽然编写方便，但难以与其他部分协调；受控则更加灵活，但需要父组件进行配置。文档指出，这种区分并非严格，一个组件也可以混合使用两者。

此外还有一条原则：每个值都应指定一个唯一的拥有组件（single source of truth）。这并不意味着要将所有状态集中到一个地方，而是指不要将同一份值复制到两个地方。

## 确定状态的形状

除了决定状态存放的位置外，其结构形态同样会影响是否会出现 bug。React 文档的“选择状态结构”部分列举了五点建议：

- 将共同变化的值组合在一起。不要分别存储 `x` 和 `y`，而应使用单一的 `position`。
- 避免产生矛盾的结构。例如 `isSending` 和 `isSent` 两个布尔值不能同时为 true；应在 `status` 中存储 `'typing' | 'sending' | 'sent'` 中的一个互斥状态。
- 不存储可计算的值。例如 `fullName` 应在渲染时通过 `firstName + ' ' + lastName` 计算得出，而非将 props 复制到 state 中，否则当 props 变化时 state 不会随之更新。
- 不在多处存放相同数据。应使用 `selectedId` 并在列表中查找，而不是直接存储 `selectedItem` 对象。
- 避免深层嵌套。修改上层结构往往需要复制整个上层路径，既繁琐又容易出错；基于 id 查找的扁平化结构更为优越。

这些建议的核心思想是一致的：尽可能减少状态的数量，其余部分通过计算得出。

## 单独看待服务器状态

过去一段时间，许多人习惯将来自服务器的数据直接存入全局 Store 并使用。但 TanStack Query 文档对此持不同观点。它定义服务器状态为：不属于我所有的远程数据；读写需要异步 API；可能在不知情的情况下被他人修改；也可能在我的应用中过期。因此，它认为这类数据不适合使用管理局部状态的库。

如果将原本由该库承担的任务转移过来，则包括：获取、缓存、同步、更新、合并相同请求（去重）、判断是否过期并在后台重新获取、清理未使用的数据、分页等。若要自行实现这些功能，工作量相当巨大。若将服务器状态交由此类工具管理，全局 Store 中将仅保留真正的客户端值，体积会大幅减小。以上是对文档内容的理解和整理，在实际项目中具体能减少多少比例，我尚未亲自验证。

[详见 → CSR·SSR·SSG](#/post/fe-rendering-modes)，正如所见，根据渲染方式的不同，服务器数据有时会从一开始就包含在 HTML 中，因此获取服务器状态的方式也会随之改变。

## 何时使用全局状态库

从局部开始并逐步向上提升时，难免会遇到需要跨越多层传递 props 的情况。此时大致有以下几种选择：

| 选项 | 适用场景 |
|---|---|
| 直接提升 (Lift Up) | 仅需在两三层之间解决时 |
| Context | 如主题、登录用户等变化不频繁且作用范围较广的值 |
| 外部存储 (Redux, Zustand 等) | 多处频繁读写，且希望缩小更新范围时 |
| 服务器状态工具 | 数据源位于服务器的数据 |

外部存储的核心结构其实很简单：一个值、一个读取函数、一个修改函数以及订阅者列表。下面的代码是用纯 JavaScript 实现的该结构，并已在 Node.js 环境中直接运行验证。

```js
function createStore(init) {
  let s = init; const ls = new Set();
  return {
    get: () => s,
    set: (f) => { const n = f(s); if (Object.is(n, s)) return; s = n; ls.forEach(l => l()); },
    sub: (l) => { ls.add(l); return () => ls.delete(l); },
  };
}
const st = createStore({ count: 0 });
let calls = 0;
const un = st.sub(() => calls++);
st.set(s => ({ count: s.count + 1 }));  // 알림
st.set(s => s);                         // 같은 값이라 알림 없음
un();
st.set(s => ({ count: s.count + 1 }));  // 구독 해제 후라 알림 없음
console.log(st.get(), calls);           // { count: 2 } 1
```

仅在值发生变化时才通知订阅者这一点至关重要。各类库减少不必要重渲染的方法正是基于此原理的演进。这与 [详见 → 前端性能](#/post/fe-performance) 中的内容紧密相关。

## 常见误区

- 所有状态都应放在全局以便管理：文档持相反观点。应就近存放，仅在需要时提升。
- 从服务器获取的数据也是状态：它们可能过期，且存在独立的数据源，因此管理方式不同。
- 使用库就能解决设计问题：存在冗余或矛盾的状态结构，无法通过任何库修复。
- Redux 是标准，必须无条件使用：它只是选项之一，选择依据应是项目规模和更新模式。

<summary>详细解析：派生值与冗余状态示例</summary>

以购物车为例，只需将 `items`（商品数组）作为状态，而 `totalPrice` 和 `count` 应在渲染时从 `items` 中计算得出。若将这些值单独设为 state，删除商品时需同时更新三者，遗漏任一都会导致视图不一致。

选中的项目同理。若保存 `selectedItem` 对象，当修改 `items` 中某项名称时，选中项仍保留旧名称；而仅保存 `selectedId`，则始终能在最新列表中查找，绝不会出错。本例是将文档原则迁移至其他场景的演示。
