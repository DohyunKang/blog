サンプリングとは、モデルが計算した次の単語の確率表から実際に一つの単語を抽出する方法であり、温度（temperature）や top-p はその抽出をどの程度保守的に行うかを決定する値です。しかし最近では Claude 側ではこれらの値を使用できなくなっており、概念と現状についてまとめておきます。

## まず一言で

同じ質問を二回行ったのに答えが異なっていたことがあります。モデルが故障したわけではなく、元々そのような仕組みになっています。[LLM](#/post/ai-llm) は文章を書く際に、次のトークンごとに「どのトークンがどれほど妥当か」というスコアを計算し、そのスコアを確率に変換した後、その確率に従って一つを選択します。この最後の「選択」がサンプリングです。

したがって、温度（temperature）、top-p、top-k はモデルの知識や賢さを変える値ではありません。既に計算された確率表をどのように抽出するかという点だけを操作するものです。

## 原理：スコアから一つの単語が出るまで

モデルが出すスコアはロジット（logit）と呼ばれます。各単語一つずつにあり、まだ確率ではありません。これを softmax という関数に入力すると、合計が 1 になる確率になります。流れは以下の通りです。

| ステップ | 行うこと | 操作する値 |
|---|---|---|
| 1 | 各単語のスコア（ロジット）を計算 | モデル自体 |
| 2 | スコアを温度で割る | temperature |
| 3 | softmax で確率表を作成する | |
| 4 | 確率が低い候補を切り捨てる | top-k, top-p |
| 5 | 残った候補から確率に従って一つを選ぶ | |

文字単位ではなくトークン単位で、このプロセスを各トークンごとに繰り返します。一つの答えに数百回もサンプリングを行うため、途中で一度だけ異なる結果が出ると後の文がすべて変わってしまいます。同じ質問に対して答えが分かれる理由はここにあります。

## 温度

温度は 2 ステップでスコアを割る値です。低いとスコアの差がより開き、1 位が確率のほとんどを独占し、高いと差が縮まって確率が均等に広がります。0 に近いとほぼ常に 1 位しか選ばれません（グリディッドという呼び方があります）。

実際に数字を確認するために簡単な Python を実行してみました（下の折りたたみ部分）。候補は六つでスコアを `[3.0, 2.5, 1.5, 1.0, 0.5, -1.0]` に設定し、温度のみを変えました。

| 温度 | 1 位 | 2 位 | 3 位 | 残りの合計 |
|---|---|---|---|---|
| 0.2 | 92.4% | 7.6% | 0.1% | 0% |
| 1.0 | 48.4% | 29.4% | 10.8% | 11.5% |
| 2.0 | 32.9% | 25.6% | 15.5% | 26.0% |

温度 0.2 では事実上決まった答えであり、2.0 では最下位候補でも約 4.5% の確率で選ばれます。この表を目で見てみると「温度が高いと創造的」という言葉の意味が理解できました。創造的というよりは、確率が低い単語を選ぶ機会が増えるということです。

## top-k と top-p

温度を上げるとたまに意味のない単語が選ばれることがあります。そのため、尾部を切り捨てる仕組みが別にあります。

- top-k: 確率が高い順に k 個だけ残し、それ以外は捨てます。k=2 の場合、上記の例では 1 位と 2 位のみが残ります。単純ですが、状況に関係なく数が固定されていることが弱点です。1 位が 99% の場所でも k 個を残し、候補が同点に近い場所では切り捨てが多すぎます。
- top-p（nucleus sampling）: 確率が高い順に加えていき、合計が p に達したらそこで止めます。候補の数は状況に応じて変わります。1 位に自信がある場合は一两个だけ残り、あいまいな場合は複数残ります。

top-p は Holtzman らが 2019 年の論文で提案しました。論文によると確率が最も高い方だけを続けて選ぶと文章が退屈で反復的になり、これを避けるために確率分布の「動的な核（nucleus）」のみから選び、信頼度の低い尾部を切り捨てます。同じモデルでもデコーディング方式だけで品質が大きく変わることもこの論文の主張です。

上記の例（温度 1.0）で top-p を 0.9 にすると、1〜3 位の合計が 88.6% でまだ 0.9 に達していないため 4 位まで残り、5 位と 6 位は切り捨てられます。残った候補の確率は再び合計が 1 になるように調整されます。

<details>
<summary>詳しい解説：実際に実行したコード</summary>

```python
import math, random

def softmax(logits, T=1.0):
    z = [x / T for x in logits]
    m = max(z)                       # 오버플로 방지
    e = [math.exp(x - m) for x in z]
    s = sum(e)
    return [x / s for x in e]

def top_k(p, k):
    keep = set(sorted(range(len(p)), key=lambda i: -p[i])[:k])
    q = [p[i] if i in keep else 0 for i in range(len(p))]
    s = sum(q)
    return [x / s for x in q]

def top_p(p, P):
    order = sorted(range(len(p)), key=lambda i: -p[i])
    keep, c = set(), 0
    for i in order:
        keep.add(i)
        c += p[i]
        if c >= P:
            break
    q = [p[i] if i in keep else 0 for i in range(len(p))]
    s = sum(q)
    return [x / s for x in q]

logits = [3.0, 2.5, 1.5, 1.0, 0.5, -1.0]
p = softmax(logits, 1.0)
print(top_k(p, 2))      # [0.622, 0.378, 0, 0, 0, 0]
print(top_p(p, 0.9))    # [0.509, 0.309, 0.114, 0.069, 0, 0]
```

実行結果では温度別の確率は T=0.2 で `[0.924, 0.076, 0.001, 0, 0, 0]`、T=1.0 で `[0.484, 0.294, 0.108, 0.066, 0.04, 0.009]`、T=2.0 で `[0.329, 0.256, 0.155, 0.121, 0.094, 0.045]` でした。温度をまず 0.7 に下げ、top-p 0.9 を適用すると `[0.622, 0.305, 0.073, 0, 0, 0]` が得られました。つまり温度と top-p を併用すると効果が相乗します。

上記のコードは概念を確認するために作った玩具です。

## いつどのように調整するか

OpenAI API の Chat Completions に関するドキュメントでは、`temperature` パラメータは 0 から 2 の間の値で説明されています。高い値（例：0.8）は出力をよりランダムにし、低い値（例：0.2）はより集中して決定的な結果をもたらすと記載されています。`top_p` は温度の代替手段であり、値が 0.1 の場合、確率質量上位 10% に含まれるトークンのみが考慮されるとのことです。「両方のパラメータを同時に変更せず、片方だけを変更するよう」推奨されています。これは、前述した通り両者が同方向の効果を持つため重ね合わせることができないと解釈しましたが（この理由は文書には明記されていません）、これが理由であるかどうかは確認していません。

一般的に経験則として知られている内容は以下の通りです。これは公式ドキュメントで確認した内容ではなく、広く知られている一般的な方法です。

| 目的 | 低い値 | 高い値 |
|---|---|---|
| 要約、抽出、分類、コード生成 | O | |
| ブレインストーミング、命名、ライティング | | O |
| 同じ入力に対して同じ出力が必要なテスト | O | |

## よくある誤解

温度を 0 にすると常に同じ答えが返ってくるのか？ほぼそうだが保証はできない。私はこれを直接検証していません。サーバー側の計算（浮動小数点の順序、バッチ処理など）によって完全に一致しない可能性があるという話は多いですが、この記事で出典を確認したわけではありません。

温度を下げることで [ハルシネーション](#/post/ai-hallucination) が減るのか？いいえ、そうではありません。温度は確率分布からどのようにサンプルを取り出すかを変えるだけで、モデルが知らないことを知らせることはできません。1 位候補が正しくない答えであれば、低い温度はその誤った答えをより確実に出力します。

温度を高くすると賢くなるのか？いいえ、単に多様化するだけです。また、[推論モデル](#/post/ai-reasoning) のように長い思考プロセスを経るモデルでは、これらの値がどのように動作するかはモデルによって異なります。

## Claude はこれらの値を廃止しています

ここで驚きました。サンプリングパラメータを調整するのは当然のことだと思っていたのですが、Anthropic のドキュメントにあるモデルサポート終了ページ（API parameter deprecations）を見ると、`temperature`、`top_p`、`top_k` が API バージョン `2026-10-21` で削除されたことが記載されています。このバージョンでリクエストを送信すると、これらの値を送った瞬間に 400 エラーが発生します。ドキュメントが推奨する代替手段は「除外し、プロンプトでモデルの振る舞いを誘導すること」です。

まとめると以下のようになります。

| 状況 | 動作（ドキュメント基準） |
|---|---|
| API バージョン 2026-10-21 | 3 つの値すべてを削除、送信すると 400 エラー |
| 旧バージョン + Claude 4.7 以降のモデル | デフォルト値以外の値を送ると 400 エラー |
| 旧バージョン + その他のモデル | このドキュメントには別途記載はありません |

あるブログ（Enjoy Agentic Industries）では、旧バージョンが引き続き動作しており終了日が公表されていないと書かれています。これは公式文書ではなく二次資料なので参考程度にとどめました。同じブログでは、Claude Sonnet 4.6 などの旧モデルで低い温度を使って結果を安定化させるコードは、新バージョンではその効果が失われるため、旧バージョンに留めるよう推奨しています。

私が理解したことは、今後は「同じ答えを出させたい」という要求は、温度ではなくプロンプトや [構造化出力](#/post/ai-structured-output) 側で解決する必要があるということです。他の提供元（OpenAI など）も前述の通り、これらの値をドキュメントに残しています。モデルや提供元ごとのサポート状況は異なるため、使用前に該当するモデルのドキュメントを確認するのが適切です。モデルごとの違いについては [AI モデルマップ](#/post/ai-models) で続報があります。入力量に関する他の制限についても [コンテキストウィンドウ](#/post/ai-context-window) の記事にあります。
