통합 구현 단원은 따로 떨어진 시스템을 어떻게 이어 붙이고, 그 사이에서 데이터를 어떤 모양으로 주고받느냐를 묻는다. 용어가 많아 보여도 "누가 중간에서 무엇을 대신해 주느냐"로 정리하면 대부분 풀린다.

## 이 단원에서 묻는 것

단원은 크게 세 덩어리로 나뉜다.

| 덩어리 | 핵심 질문 | 자주 나오는 용어 |
|---|---|---|
| 모듈 연계 | 시스템을 어떻게 이을까 | 직접 연계, 간접 연계, EAI, ESB |
| 인터페이스 | 무엇을 어떻게 주고받기로 약속했나 | 인터페이스 명세, 송수신 항목, 오류 처리 |
| 데이터 포맷 | 주고받는 글의 모양은 | JSON, XML |

시험에서는 "다음 설명에 해당하는 용어는?" 같은 정의 매칭이 많다. 그래서 용어 하나하나를 한 줄 정의와 짝지어 외워 두는 게 먼저다. 시험 일정과 응시료는 공식 사이트에서 확인하면 된다.

## 연계가 필요한 이유

회사에는 ERP, CRM, 급여 같은 시스템이 따로 돌아간다. 위키백과의 EAI 항목은 이런 상태를 서로 고립된 "자동화의 섬"이라고 표현하고, EAI를 그 사이의 데이터와 업무 흐름을 공유하게 해 주는 미들웨어로 설명한다.

시스템이 두세 개일 때는 서로 직접 이으면 된다. 문제는 숫자가 늘 때다. 직접 잇는 선은 시스템 수가 늘수록 빠르게 많아지고, 한 시스템의 형식이 바뀌면 그 시스템과 연결된 모든 선을 손봐야 한다. 중간에 하나를 두는 구조는 이 부담을 줄이려고 나왔다.

## 연계 구조 세 가지

| 구조 | 모양 | 특징 |
|---|---|---|
| 점대점(Point-to-Point) | 시스템끼리 일대일로 직접 연결 | 단순하지만 연결이 늘면 관리가 어렵다 |
| 허브 앤 스포크(Hub & Spoke) | 중앙 허브에 각 시스템이 연결 | 중앙에서 통제한다. 허브가 막히면 전체가 영향받는다 |
| 버스(Bus) | 공통 버스에 각 시스템이 붙음 | 시스템이 버스에 꽂는 방식으로 이어진다 |

위키백과 EAI 항목에는 두 가지 토폴로지가 나온다. 허브 앤 스포크는 EAI가 가운데에 있고 애플리케이션이 스포크로 연결되는 구조, 버스는 EAI가 버스 자체이거나 기존 메시지 지향 미들웨어 안의 모듈로 도는 구조다. 점대점은 EAI 없이 직접 잇는 방식으로 비교용으로 알아 두면 된다.

[자세히 → 소프트웨어 아키텍처](#/post/jb-architecture-pattern)

## EAI

EAI(Enterprise Application Integration)는 기업 안의 여러 애플리케이션을 연결해 데이터와 업무 프로세스를 공유하게 하는 방식이다. 문서에 나온 구성 요소는 이렇다.

- 허브 또는 버스: 중앙에서 메시지를 주고받게 하는 부분
- 어댑터: 각 애플리케이션을 허브에 붙이고, 데이터를 공통 형식으로 바꿔 주는 부분
- 통합 모듈: 특정 이벤트를 구독해서 알림을 처리하는 부분

패턴은 둘로 나뉜다. 중재(Mediation)는 한 애플리케이션에서 이벤트가 생기면 EAI가 브로커로서 관련 애플리케이션에 변경을 전달하는 방식이다. 연합(Federation)은 EAI가 외부 요청의 창구가 되어 안쪽 애플리케이션과 대신 통신하는 방식이다.

여러 시스템에 걸친 작업의 일관성은 2단계 커밋이나 보상 트랜잭션으로 맞춘다고 한다.

[자세히 → 정규화와 트랜잭션](#/post/jb-normalization-transaction)

## ESB

ESB(Enterprise Service Bus)는 서비스 지향 아키텍처(SOA)에서 애플리케이션을 연결하는 통신 시스템이고, 서로 다른 시스템을 통합하는 게 주된 용도다. 위키백과는 ESB를 EAI의 버스 모델을 구현하는 흔한 방식으로 소개한다. 이상적으로는 애플리케이션끼리 직접 접촉하던 걸 대신해서 모든 통신이 버스를 지나가게 한다.

ESB의 핵심 기능은 네 가지로 정리된다.

| 기능 | 하는 일 |
|---|---|
| 라우팅 | 메시지를 알맞은 서비스로 보내고 흐름을 감시·제어한다. 내용이나 규칙에 따라 갈라 보낼 수 있다 |
| 변환 | 받는 쪽이 읽을 수 있는 형식으로 메시지를 바꾼다 |
| 프로토콜 변환 | 서로 다른 통신 규약을 쓰는 서비스끼리 통하게 한다 |
| 메시지 큐잉 | 메시지와 이벤트를 줄 세워 순서대로 전달한다 |

<details>
<summary>EAI와 ESB를 한 줄로 구분하기</summary>

EAI는 "기업 내 애플리케이션을 통합한다"는 목적에 가까운 말이고, ESB는 그걸 서비스 버스라는 모양으로 구현한 방식에 가까운 말이다. 시험에서는 허브 중심이면 EAI의 허브 앤 스포크, 서비스 지향 구조와 버스가 나오면 ESB 쪽으로 읽으면 대체로 맞았다. 다만 문제 문장에 따라 둘을 같은 범주로 묶어 내기도 하니, 보기에 두 용어가 같이 나오면 설명 문장을 끝까지 읽는 편이 안전하다.

</details>

## 인터페이스 명세

시스템끼리 연계하려면 약속이 필요하고, 그 약속을 적은 문서가 인터페이스 명세다. 보통 들어가는 내용은 다음과 같다.

- 어느 시스템이 보내고 어느 시스템이 받는지
- 주고받는 항목의 이름, 자료형, 길이, 필수 여부
- 호출 방식과 주기(실시간인지 일괄인지)
- 오류가 났을 때 처리 방법

항목 하나가 다르게 해석되면 연계가 그대로 깨지기 때문에, 이 문서는 짧아도 빠짐없이 쓰는 게 중요하다. 시험에서는 명세에 어떤 항목이 들어가는지 묻거나, 연계 후 데이터가 잘 오갔는지 확인하는 테스트 단계와 엮어 낸다.

## 데이터 포맷: JSON과 XML

주고받는 데이터의 모양은 JSON과 XML이 대표다. 같은 주문 정보를 두 방식으로 쓰면 이렇다.

```json
{"orderId": 101, "items": [{"sku": "A1", "qty": 2}], "paid": true}
```

```xml
<order id="101"><item sku="A1" qty="2"/><paid>true</paid></order>
```

위 두 줄을 파이썬으로 직접 읽어 봤더니 JSON은 `json.loads`로 딕셔너리가 되어 `items[0].qty`가 2로, XML은 `ElementTree`로 읽어 `item`의 `qty` 속성이 2로 나왔다. 닫는 태그가 맞지 않는 XML(`<a><b></a>`)은 파싱 단계에서 오류가 났다.

### JSON

json.org는 JSON을 사람이 읽고 쓰기 쉽고 기계가 해석하고 만들기 쉬운, 언어에 독립적인 가벼운 텍스트 데이터 교환 형식이라고 설명한다. 구조는 두 가지다.

- 객체: 이름과 값의 쌍을 모은 것. 중괄호로 감싸고 이름 뒤에 콜론을 붙이며 쌍은 쉼표로 구분한다. 순서가 없는 집합이다.
- 배열: 값을 순서대로 모은 것. 대괄호로 감싸고 쉼표로 구분한다.

값은 문자열(큰따옴표), 숫자, true/false, null, 그리고 객체와 배열(중첩 가능)이다.

### XML

W3C의 XML 1.0 문서에 따르면 XML은 SGML의 제한된 부분집합이고, 웹에서 구조화된 데이터를 주고받고 처리하기 쉽게 만드는 게 목표다. 시험에서 걸리는 개념은 두 가지다.

| 개념 | 뜻 |
|---|---|
| 정형(well-formed) | 루트 요소가 하나이고 요소가 올바르게 중첩되는 등 문법 규칙을 지킨 문서 |
| 유효(valid) | 정형이면서, 연결된 DTD가 정한 구조까지 만족하는 문서 |

시작 태그와 끝 태그가 짝을 이루고, 속성은 시작 태그 안의 이름-값 쌍이며 순서는 의미가 없고 같은 태그 안에서 이름이 겹칠 수 없다. DTD는 허용되는 요소와 속성 구조를 정의하는 부분이다.

<details>
<summary>JSON과 XML 비교표</summary>

| 항목 | JSON | XML |
|---|---|---|
| 구조 | 객체와 배열 | 태그로 감싼 요소 트리 |
| 속성 | 없음, 이름-값으로 표현 | 시작 태그의 속성 |
| 구조 검증 | 문서 자체 규칙은 문법 수준 | DTD로 유효성 검증 가능 |
| 모양 | 짧게 쓰는 편 | 태그가 반복되어 긴 편 |

글자 수 차이는 위 예시처럼 같은 정보를 쓰면 바로 보이지만, 어느 쪽이 항상 낫다고 정해진 건 아니다. 시험에서는 두 형식의 정의와 구조 차이를 구분해서 묻는다.

</details>

## 자주 나오는 유형

- 용어 매칭: 설명 문장을 주고 EAI, ESB, 허브 앤 스포크, 버스 중 고르기
- 기능 구분: 라우팅, 변환, 프로토콜 변환, 메시지 큐잉 중 설명에 맞는 것 찾기
- 형식 읽기: JSON이나 XML 예시를 주고 값 읽기, 올바른 문법 고르기
- 정형과 유효 구분: DTD 유무로 갈리는 문제

풀이 방식은 단순하다. 문장에 "중앙", "허브"가 있으면 허브 앤 스포크, "서비스", "버스"에 변환·라우팅이 나오면 ESB로 읽는다. 포맷은 중괄호면 JSON, 태그면 XML로 먼저 거르고 세부로 들어간다. 기출 문제는 큐넷 등 공식 공개 자료에서 직접 풀어 보는 게 좋다.
