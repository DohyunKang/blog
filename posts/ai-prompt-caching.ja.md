プロンプトキャッシングは、毎回繰り返される前半部分を一度処理しておき、次のリクエストで再利用する機能であり、その核心は「先頭から完全に一致していなければならない」という一点にあります。

## 定義から

LLM API は、対話が進行するたびにシステムプロンプト、ツール定義、これまでの対話を丸ごと再送信します。（[詳細 → コンテキスト](#/post/ai-context)）このうち毎回同じ部分は非常に大きいです。プロンプトキャッシングとは、その同じ前半部分の処理結果をサーバーが一時的に保持しておき、再び同じ前半部分が来る際、最初から計算するのではなくそれを引き出すことです。

出力は変わりません。Anthropic のドキュメントも OpenAI のドキュメントも、キャッシュが出力生成に影響を与えないと記述しています。変わるのは入力を処理する時間と入力料金です。

## 原理：接頭辞（prefix）一致

OpenAI ドキュメントの説明によると、サーバーが保存するのはトークンの文字ではなく、前半部分を処理して作成した KV ステートです。モデル内部の計算中間値と理解しました。この中間値は前方のトークンによって後方の値が決まる構造であるため、前半部分と同じ場合のみ再利用可能です。（この構造の説明は私の解釈であり、ドキュメントでは「全体プロンプトの先頭部分が一致していなければならない」としか記されていません。）

したがってルールは単純です。

- 先頭から何トークンも異なる区間までがキャッシュに合致します。
- 途中で一つでも異なれば、その後はすべて再計算します。
- イメージも内容に含まれます。同じイメージが同じ位置にある必要があります。

Anthropic はプロンプトを `tools` → `system` → `messages` の順に連結したものを一つの接頭辞とみなします。ツール定義が先頭にあるため、ツールの一つを変更するとその後のすべてが無効になるという意味です。

```text
[도구 정의][시스템 프롬프트][문서/예시][지난 대화......][이번 질문]
|<------------ 매번 같음 (캐시) ------------>|<-- 달라짐 -->|
```

## 費用と遅延の利点

Anthropic ドキュメントの倍率（基本入力単価に対する）は以下の通りです。

| 項目 | 倍率 |
|---|---|
| 5 分キャッシュ書き込み | 1.25 倍 |
| 1 時間キャッシュ書き込み | 2 倍 |
| キャッシュ読み取り（ヒット） | 基本 0.1 倍（モデルにより 0.05 倍、0.025 倍の場合もある） |

書き込みは少し高く、読み取りははるかに安いです。計算してみました。前半部分が 20,000 トークンで、同じ前半部分を使って 10 回リクエストすると仮定します。単価を 1 と置くと以下のようになります。

| | 計算 | 入力費用（トークン×倍率） |
|---|---|---|
| キャッシュなし | 20,000 × 10 | 200,000 |
| 5 分キャッシュ | 20,000×1.25 + 20,000×0.1×9 | 43,000（約 21.5%） |

2 番目のリクエストからすでに利益があります。一度書き、一度読みしても 1.25 + 0.1 = 1.35 倍となり、そのまま 2 回送る 2 倍よりも安いです。ただしこれは接頭辞部分だけの計算であり、今回の質問のような後半部分と出力料金は含まれていません。

遅延についてはドキュメントに「最初のトークンにかかる時間が短縮され、長い文書ほど大きくなる」とあります。具体的な何秒短縮したという数値は両方のドキュメントのどこにもなく記載しません。OpenAI 側のドキュメントも遅延の数値を与えていません。

さらに一つ、Anthropic ドキュメントによるとキャッシュヒット分は速度制限（rate limit）から除外されます。OpenAI 側は逆にキャッシュされたトークンも速度制限にカウントすると記述しています。会社によって異なるため、使用する方のドキュメントを確認する必要があります。

原価の観点については [詳細 → コスト設計](#/post/app-cost) でさらに扱っています。

## キャッシュを壊す行動

前半部分と同じである必要があるため、壊れるケースもそこから出ます。

- システムプロンプトの最上段に現在時刻やリクエスト ID を入れる。リクエストごとに変わるため後方がすべて無効になります。
- ツール定義をリクエストごとに追加したり削除したり順序を変える。ツールは先頭にあるためです。
- 過去の対話を要約したり切り取って再送信する。前半部分が変化します。（[詳細 → コンテキスト圧縮](#/post/ai-compaction)）
- イメージを途中で挿入したり削除したりする。Anthropic の表ではイメージの追加・削除は tools や system キャッシュも無効にします。
- `tool_choice` の値を変える。同じ表で tools と system キャッシュが無効になります。

OpenAI ドキュメントの助言も同じ方向です。変わらない内容は先頭に、変わる内容（時刻、ユーザー固有データ）は後方に置きます。ツールを削除する代わりに `tool_choice: "none"` や `allowed_tools` を使うように也说います。

## TTL：キャッシュがどれほど生きるか

キャッシュは永続ではありません。Anthropic はデフォルト 5 分であり、使用するたびに無料で延長されます。`ttl: "1h"` を指定すれば 1 時間となり、書き込み単価は 2 倍です。5 分ごとに一度はリクエストが来る流れであれば 5 分キャッシュが、間隔が 5 分以上で 1 時間以内であれば 1 時間キャッシュが正しいとドキュメントが案内しています。

OpenAI のアプローチは異なります。ドキュメントによると、GPT-5.6 以降のモデルではデフォルトで最低 30 分間保持され、`prompt_cache_options.ttl` を用いて最大 12 時間に延長できます（ただし書き込みコストが増加します）。それ以前のモデルでは `in_memory`（非アクティブ時 5〜10 分程度）と `24h` の選択がありました。この点で最も混乱したのは、モデルの世代によってルールが異なることです。

## API での使用方法

Anthropic では 2 つの方法があります。トップレベルに 1 つの `cache_control` を指定する自動方式（対話が進むにつれてキャッシュの有効期限も順次更新される）と、各ブロックごとに直接指定する明示的アプローチ（最大 4 カ所まで）です。ドキュメントの Python 例を簡略化して転記すると以下のようになります。

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-5-5",   # 문서 예시의 모델 이름
    max_tokens=1024,
    system=[
        {"type": "text", "text": "You are an AI assistant tasked with analyzing legal documents."},
        {
            "type": "text",
            "text": "Here is the full text of a complex legal agreement: [...]",
            "cache_control": {"type": "ephemeral"},  # 여기까지를 캐시
        },
    ],
    messages=[{"role": "user", "content": "What are the key terms and conditions in this agreement?"}],
)
print(response.usage)
```

このコードはドキュメントの例を転記したものです。

キャッシュヒットの有無は、レスポンスの `usage` で確認します。

- `cache_creation_input_tokens`: 今回はキャッシュに使用されたトークン数
- `cache_read_input_tokens`: キャッシュから読み取ったトークン数
- `input_tokens`: キャッシュ未使用のトークン（最後の表示以降）

全体の入力トークンはこれら 3 つを合計した値です。最初の 2 つが 0 の場合はキャッシュヒットしておらず、通常は後者の最小長さに満たないためです。この場合エラーも発生しません。単にキャッシュがヒットしないだけなので、`usage` を確認する習慣が必要です。

OpenAI ではコードはほとんど不要です。ドキュメントで言及されているモデルではデフォルトで有効になっており、レスポンスの `cached_tokens` でヒットを確認します。

<details>
<summary>詳細解説：最小長さと確認ウィンドウ (lookback)</summary>

Anthropic ではモデルごとにキャッシュ可能な最小長さが異なります。ドキュメントの表によると、512 トークン（Opus 5.5, Sonnet 5.5, Haiku 5.5 など）、1,024 トークン（Sonnet 5, Sonnet 4.6 など）、2,048 トークン（Opus 4.7 など）、4,096 トークン（Opus 4.6, Haiku 4.5 など）に分かれます。モデルが頻繁に変わるため、使用する際は表を再度確認する必要があります。OpenAI では GPT-5.6 以降の基準で 1,024 トークンです。

Anthropic はキャッシュをブレークポイント（表示位置）のみで使用します。リクエストが来るたびにその地点のハッシュを確認し、存在しない場合は前方から最大 20 カ所まで遡って以前のリクエストで使用した項目を探します。対話が一度に 20 カ所以上長くなる場合、さらに前方にキャッシュを追加するよう案内されています。各リクエストで変わるブロック（例：タイムスタンプ）にキャッシュを配置するとハッシュが一致せず、毎回書き込み料のみが発生します。

プリウォーミング（pre-warming）も可能です。`max_tokens: 0` を指定して送信すると、出力なしでキャッシュのみ使用できるようです。ストリーミング、拡張思考、構造化出力などとは併用できません。私はこの機能を実際に試したことはありません。

思考（thinking）ブロックは直接キャッシュを設定することはできませんが、以前のアシスタントターンの一部としてキャッシュされます。一部の最新モデルでは思考ブロックをデフォルトで保持してキャッシュを継続し、旧モデルでは特定のユーザー入力が入ると切り離され、その地点から無効になるとドキュメントに記載されています。
</details>

GPT-5.6 以前のモデルでは、同じ接頭辞を共有するリクエストに対して同じ `prompt_cache_key` を指定することで同じキャッシュを使用するように助けるようです。これは保証ではなく、ルーティングに影響を与える程度のものです。混雑しているグループではキーあたり分間 15 件程度が適切で、それ以上ならキーを分割するようドキュメントに記載されています。GPT-5.6 以降はオプションであり、ユーザーごとのキャッシュ集計を別に行うか、他のユーザーがキャッシュヒットの有無から情報を窺うのを防ぐために使用するとのことです。私はこれを直接試したことはありません。

## よくある誤解

- キャッシュにするとコンテキストウィンドウも縮小する：違います。料金が減るだけでウィンドウはそのままです。（[詳細 → コンテキストウィンドウ](#/post/ai-context-window)）
- 同じ質問なら同じ回答がキャッシュで返ってくる：違います。保存するのは入力処理の結果であり、回答は毎回新たに生成されます。
- キャッシュを設定すれば常に機能する：最小長さより短ければエラーなくキャッシュヒットしません。
- キャッシュは永続的ではない：5 分、1 時間、長くても数時間の単位であり、手動で削除することもできません（OpenAI ドキュメント基準）。
- 書き込みコストはない：Anthropic では 1.25 倍または 2 倍です。一度だけ使用してプロンプトを終わらせる場合、むしろ損になります。

エージェントのように同じツールリストと指示文を持ち続けて回る場合、この効果が大きいです。ハネスがどのようにプロンプトを積み上げるかがヒット率を左右しているようです。（[詳細 → ハネス](#/post/ai-harness)）
