规范化是为了防止因重复数据而产生的异常现象，即拆分表；而反规范化、分区以及超级/子类型则是为了性能对已经拆分过的模型进行的调整。SQLD 第 1 课中既有概念题，也有给出情境并询问“该如何修改”的题目，因此我不仅整理了定义，还将适用场景一并归纳总结。

考试日程和报名费用可在官网确认。本文仅涵盖课程核心概念及高频题型。

## 为什么需要规范化

如果在同一张表中为每位员工记录部门名称，当部门名称变更时，必须修改所有对应员工的记录。若遗漏任何一个，该部门就会拥有两个不同的名称。这类问题被称为异常（anomaly），通常分为三类：

| 异常类型 | 情况描述 |
|---|---|
| 插入异常 | 没有员工的新部门无法录入系统 |
| 更新异常 | 修改部门名称时若只更新了部分行，会导致数据不一致 |
| 删除异常 | 删除最后一名员工时，部门信息也随之丢失 |

规范化的目的是通过遵循函数依赖关系来拆分表。函数依赖是指"A 的值确定后，B 的值也唯一确定”的关系（A → B）。例如，确定了员工编号，员工姓名也就唯一确定，因此存在“员工编号 → 员工姓名”的依赖。

## 1~3 范式

以维基百科关于规范化的定义为准，三个阶段的解读如下：

| 范式 | 条件 | 违反时的处理方式 |
|---|---|---|
| 第一范式 | 每个单元格仅包含单个值，无重复组或多值 | 将重复的值移至独立表 |
| 第二范式 | 当主键为复合键时，非键属性必须完全依赖于整个主键（消除部分依赖） | 将部分依赖的属性移至独立表 |
| 第三范式 | 非键属性不依赖于其他非键属性（消除传递依赖） | 将传递依赖的属性移至独立表 |

记忆时可抓住关键词：第一范式对应原子值，第二范式对应部分依赖，第三范式对应传递依赖。

以选课表为例，主键为（学号，课程代码）。若“课程名称”仅依赖于“课程代码”，则构成部分依赖，违反第二范式；若存在“学号 → 学院代码 → 学院名称”这样的非键属性间相互决定的情况，则构成传递依赖，违反第三范式。

<details>
<summary>解题步骤（遇到题目时）</summary>

1. 首先确认主键。
2. 若某个单元格包含多个值，则违反第一范式。
3. 若主键为复合键，检查每个非键属性是否仅由主键的一部分决定。若是，则违反第二范式。
4. 若非键属性之间存在"A 决定 B"的关系，则违反第三范式。
5. 将违反范式的属性与其决定因素（左侧属性）一同移至新表，原表中保留决定因素作为外键。

若主键为单一属性，则不会产生部分依赖，因此自动满足第二范式。这一点常在选择题中作为考点。
</details>

虽然还存在 BCNF、第四范式、第五范式等概念，但本单元主要围绕第三范式进行考察。具体的出题范围请以官网课程说明为准。

## 用代码验证规范化效果

将员工表和部门表分离后，部门名称只存储在一个地方。以下是使用 sqlite 直接运行的结果：

```sql
CREATE TABLE dept(dept_id INT PRIMARY KEY, dept_name TEXT);
CREATE TABLE emp(emp_id INT PRIMARY KEY, emp_name TEXT,
                 dept_id INT REFERENCES dept);
INSERT INTO dept VALUES (10, '영업');
INSERT INTO emp VALUES (1, '가', 10), (2, '나', 10);

UPDATE dept SET dept_name = '영업1' WHERE dept_id = 10;

SELECT e.emp_name, d.dept_name
FROM emp e JOIN dept d USING (dept_id);
```

结果显示为 `('가', '영업1')`, `('나', '영업1')`。仅修改了一行数据，但两名员工的记录均得到更新。然而，若需同时查看员工和部门名称，则必须进行连接（join）操作。反规范化的讨论由此展开。

## 反规范化

进行规范化后，表的数量增加，查询时的连接操作也随之增多。当连接操作成为性能瓶颈时，故意允许数据重复即为反规范化。维基百科的规范化文档中并无专门的“反规范化”条目，仅通过链接指向独立文档。通常而言，反规范化是通过牺牲一定的数据冗余来减少连接操作。

考试中常要求对方法进行分类说明：

| 类别 | 方法 | 示例 |
|---|---|---|
| 表 | 表合并 | 将 1:1 或 1:N 关系的表合并为一张 |
| 表 | 表分割 | 按列（垂直分割）或按行（水平分割） |
| 表 | 添加表 | 聚合表、历史表、分片表 |
| 列 | 添加重复列 | 为避免连接而复制名称列 |
| 列 | 添加派生列 | 预先计算并存储合计值或计数 |
| 关系 | 添加冗余关系 | 为减少多步连接而额外保留一层关系 |

在实施反规范化之前，了解以下优化手段也很有必要：通常优先调整索引、使用视图或重写查询；若上述方法仍无法满足需求，再考虑进行反规范化。

反规范化的代价是数据一致性。对于复制的列，当源数据变更时必须同步更新，这通常由应用程序或触发器负责。因此，该方法主要应用于以读操作为主的查询密集型业务场景。

## 超级类型与子类型

当实体具有共同属性并按类别划分时，公共部分构成超类型，而各类别部分构成子类型。例如，客户可分为个人客户和法人客户。在逻辑模型中这样表示，而在转换为物理模型时，需从三种方式中选择一种。

| 转换方式 | 形状 | 适用场景 |
|---|---|---|
| 一对一关系 | 将超类型和子类型分别作为表，并以 1:1 连接 | 当子类型具有大量特有属性且需要单独查询时 |
| 超类型 + 子类型合并（单表） | 在一个表中包含区分列和所有属性 | 当无需区分子类型、需联合查询且处理速度重要时 |
| 按子类型分离 | 每个子类型对应一个表，公共属性重复存储 | 当各子类型几乎独立使用时 |

合并方式虽无连接操作因而速度快，但会保留不必要的列为 NULL 并导致表体积增大。反之，若采用分离方式，则表结构更轻量，但在需要整体查看时则需使用连接或 UNION 操作。考试中常出现“给定查询模式，应选择哪种转换”这类题目。记住每种方式的优缺点一对即可轻松应对。

[详情 → 实体与属性](#/post/sqld-entity-attr)中关于实体分类的内容可帮助理解超类型/子类型的来源。

## 分区（Partitioning）

将大表划分为小片段进行管理的方法。Oracle 文档将分区描述为将表或索引划分为更小的单元——即“分区”；在应用程序层面，分区表与普通表外观一致，无需更改 SQL。某一行属于哪个分区由分区键决定。

| 方式 | 依据 | 示例 |
|---|---|---|
| 范围 (Range) | 值的范围 | 按月划分的订单数据 |
| 列表 (List) | 指定值列表 | 按地区划分的数据 |
| 哈希 (Hash) | 哈希值均匀分布 | 无自然范围的数据 |
| 复合 (Composite) | 组合上述方式使用 | 在范围内应用哈希 |

其效果主要体现在三个方面：性能方面，仅读取所需分区的“分区剪枝（pruning）”是关键；文档示例显示，在一个按周划分、共包含两年数据（104 个分区）的订单表中查询一周时，仅需读取 104 个分区中的 1 个。管理方面，可按分区进行备份或加载；可用性方面，即使某个分区被阻塞，其余分区仍可正常使用。

考试中常出现类似“只有当查询条件中包含分区键时才有效”这类判断题。由于剪枝机制依赖于键条件运作，理解这一点即可避免混淆。只需记住分区方式的名称及其依据即可。

<details>
<summary>水平分割与分区是同一概念吗？</summary>

表水平分割是以行为基准，将表本身物理拆分为多个独立表；而分区在逻辑上仍视为单一表，仅对存储进行划分。水平分割要求应用程序明确知道查看哪个表，而分区则无需修改 SQL 即可访问。考试中更多考察的是两者的效果差异，而非单纯区分概念。
</details>

## 从索引视角看性能建模

设计索引时，在建模阶段需考虑以下几点：

- 为常用于查询条件和连接操作的列建立索引，外键列是典型代表。
- 取值种类极少的列效果不佳，应选择选择度（cardinality）较高的列。
- 索引虽能加速查询，但在 INSERT、UPDATE、DELETE 操作时需同步更新，因此会产生写入开销。
- 复合索引中列的顺序至关重要；若前列未用于条件匹配，则难以有效利用。

在上述员工示例中，为 `emp(dept_id)` 创建索引后，查看 sqlite 的执行计划显示为：  
`SEARCH emp USING INDEX ix_emp_dept (dept_id=?)`  
这表明通过外键列进行查询时命中了索引。

```sql
CREATE INDEX ix_emp_dept ON emp(dept_id);
EXPLAIN QUERY PLAN SELECT * FROM emp WHERE dept_id = 10;
```

关于索引内部结构，请参见 [详情 → 索引](#/post/db-index)；将规范化作为数据库通用概念讨论的文章见 [详情 → 规范化](#/post/db-normalization)。本文仅涵盖考试中涉及的内容。

## 常见题型总结

| 类型 | 解题思路 |
|---|---|
| 判断给定表属于第几范式 | 依次检查主键、部分依赖 → 传递依赖 |
| 确定规范化后的表结构 | 将决定者与依赖属性成对分离 |
| 反规范化技术分类 | 根据操作对象是表、列还是关系来划分 |
| 查询缓慢的情况分析 | 按顺序考虑索引、视图、反规范化 |
| 选择超类型/子类型转换方式 | 依据查询模式（联合查看 or 单独查看）决定 |
| 分区效果评估 | 关注分区键条件、剪枝机制、管理单元划分

选择项中常见的错误模式是像“规范化越多，性能就越好”这样的绝对化断言。只需记住：规范化是为了保持一致性，而查询性能可能会因为 JOIN 增多反而变得不利，就可以排除这类选项。
