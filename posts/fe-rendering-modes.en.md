CSR, SSR, and SSG differ only in *who* and *when* the HTML for the screen is generated. Rather than declaring one superior, the choice depends on how frequently data changes per page.

## First, line by line

For a browser to render a screen, it ultimately needs HTML. There are three points at which this HTML can be generated. The order in which the browser renders the screen is detailed separately in [detailed → How the browser renders pages](#/post/fe-browser-render).

| | Who | When | What the browser receives first |
|---|---|---|---|
| CSR (Client-Side Rendering) | Browser's JavaScript | After the page loads | Nearly empty HTML + JS |
| SSR (Server-Side Rendering) | Server | Every time a request arrives | Completed HTML |
| SSG (Static Site Generation) | Build process | Once, before deployment | Pre-generated HTML files |

web.dev categorizes rendering in a similar way. CSR is an approach where the browser handles logic, data fetching, templating, and routing via JavaScript; SSR is where the server generates completed HTML for each request; and static rendering involves creating one HTML file per URL during the build process.

## CSR: Receiving an empty shell and letting the browser fill it

In CSR, the HTML provided by the server looks roughly like this.

```html
<body>
  <div id="root"></div>
  <script src="/app.js"></script>
</body>
```

The browser downloads and executes `app.js`, fetches data from APIs if needed, and then fills the contents of `#root`. The moment content appears on the screen is delayed until after "JS download → execution → data request → rendering".

The advantages are fast navigation after the initial load and a smooth, app-like experience. Since the server only needs to serve static files, operations are simple. The disadvantage is that the first screen can be slow to load. web.dev notes that as JavaScript grows, interaction metrics like TBT (Total Blocking Time) and INP (Interaction to Next Paint) degrade, making it difficult to maintain performance on mobile devices. It is also known that search engines may not display content if they do not execute JavaScript.

## SSR: The server generates HTML for each incoming request

With SSR, when a request arrives, the server fetches data and sends back completed HTML. The browser can render content immediately even before the JavaScript arrives. web.dev explains that SSR typically results in faster FCP (First Contentful Paint) and reduced client-side JavaScript. Conversely, since the server must work for every request, TTFB (Time to First Byte) can increase.

This approach suits pages where content changes per request, such as user-specific screens for logged-in users or data that is nearly real-time.

You can see the server-side processing order in [detailed → Request processing flow](#/post/be-request-flow).

## SSG: Pre-generating everything during the build

SSG generates all pages as HTML files during a build step like `next build`. When a request arrives, the server simply serves that file without computation. This makes it easy to host files on a CDN, resulting in consistent and fast TTFB and FCP. web.dev also notes that this is CDN-friendly.

The downside is that content must be rebuilt whenever it changes. It is considered impractical for sites with tens of thousands of pages or content that varies by user. It suits places where content remains unchanged for a while after creation, such as blog posts, documentation, or landing pages. The discussion on serving files from nearby locations continues in [detailed → CDN and caching strategies](#/post/infra-cdn-cache).

## Hydration: A concept arising from SSR and SSG

When receiving HTML via SSR or SSG, the screen appears immediately, but there may be sections where nothing happens when buttons are pressed. This is because event handlers are not attached to the HTML. Hydration is the process of attaching JavaScript events and state to this HTML to make it a living app. Next.js documentation defines it as "React's process of attaching event handlers to static HTML to enable interactivity."

React's `hydrateRoot` attaches React on top of HTML already generated by the server.

```js
import { hydrateRoot } from 'react-dom/client';

hydrateRoot(document.getElementById('root'), <App />);
```

(This code is an example from the documentation and has not been executed directly.)

There are conditions to observe here. The React documentation states that the result drawn by the client initially must match the HTML sent by the server. If they differ, warnings appear during development; while recovery is possible in some cases, there is no guarantee, and in severe instances, event handlers may be attached to incorrect elements. Common causes for mismatches include:

- Code that branches using `typeof window !== 'undefined'` during rendering
- Code using browser-specific APIs like `window.matchMedia` during rendering
- Cases where data is rendered differently on the server versus the client

Values that change inevitably over time, like the clock, can trigger a warning using `suppressHydrationWarning`, but this only works for one level of depth.

Hydration also incurs costs. web.dev notes that even if FCP improves, TBT and INP may worsen. This happens because the screen appears fully loaded, but while scripts are still running, the page remains unresponsive. There is also criticism that since the server sends HTML and the client re-executes the same UI code, the work is effectively done twice.

## Mixing Approaches: ISR and Server Components

In practice, it's rare to use only one of the three approaches.

ISR (Incremental Static Regeneration) is a method to reduce the "rebuild on change" issue inherent in SSG. According to Next.js documentation, here is how it works: pages created during build are immediately served from cache. If `revalidate = 60`, the first request after 60 seconds receives the stale page as-is, while simultaneously a new page is built in the background. Once the new page is ready, subsequent requests serve the fresh version. The documentation recommends setting the `revalidate` value higher than 1 second (e.g., to 1 hour) and suggests using on-demand methods like `revalidatePath` or `revalidateTag` for precise updates. For real-time data needs, it advises switching to dynamic rendering.

Next.js App Router mixes these at the component level. Layouts and pages are by default server components, while parts requiring state or click events use client components marked with `'use client'`. On the initial load, the server component result (RSC Payload) and client components are pre-rendered into HTML and sent; the browser displays this HTML immediately, then hydrates only the client components via JS. For subsequent page navigations, the RSC Payload is fetched in advance and cached, while client components are rendered in the browser without relying on server HTML. The documentation states that this approach reduces the amount of JS sent to the browser. Further discussion on state management can be found [here → State Management](#/post/fe-state).

## Criteria for Selection

Here is how to decide based on a series of questions:

| Question | Leans Towards |
|---|---|
| Is the content identical regardless of the visitor and rarely changes? | SSG (use ISR if there are periodic changes) |
| Does the content differ per request or per user? | SSR |
| Is it more like an app (e.g., a dashboard after login) where search exposure is not critical? | CSR |
| Are static and interactive parts mixed within a single page? | Server Components + Client Components |

For performance considerations, refer to [Frontend Performance](#/post/fe-performance) for metrics and indicators to better understand the trade-offs.

## Common Misconceptions

- **SSR is always faster than CSR:** While the first screen (FCP) is faster, TTFB can increase because the server processes each request, and the page remains unresponsive until hydration completes.
- **SSG cannot use dynamic data:** SSG fetches data during build and embeds it in HTML. However, values that change after the build are not reflected; ISR fills this gap.
- **Hydration means re-rendering HTML:** Hydration attaches React to existing HTML, assuming the server and client produce the same result. If they diverge, problems arise because it's not a redraw but a reconciliation.
- **Using a framework eliminates the need to choose:** With Next.js, static and dynamic routing are separated by route, and server/client components are split at the component level. This doesn't eliminate the choice; rather, it brings the decision into your codebase.

<summary>Detailed Explanation: Metric Terminology</summary>

- **TTFB**: Time from sending a request until the first byte of the response arrives.
- **FCP**: The moment the first content (text or image) is rendered on the screen.
- **TBT**: Cumulative time the main thread is blocked, preventing responsiveness to input.
- **INP**: Response speed from user interaction (click or input) until the next visual change occurs.

web.dev reports that SSR and static rendering reduce client-side JS, benefiting TBT and INP, while CSR is most affected as bundles grow larger. The diagram in this article includes an older metric called TTI, but comparisons in the text are based on TBT and INP.

</details>

<details>
<summary>Detailed Explanation: Pre-rendering and Streaming</summary>

Pre-rendering refers to running a CSR app once during build to extract only the initial HTML. While this improves FCP, JavaScript is still required for true interactivity. This overlaps significantly with SSG, but web.dev distinguishes between the two in its explanations.

web.dev lists streaming SSR and progressive/partial hydration as methods to reduce hydration costs. However, it notes that partial hydration is difficult to implement. Next.js documentation mentions that server components stream content progressively to the client.

</details>

<details>
<summary>Detailed explanation: Viewing ISR response status</summary>

According to the Next.js documentation, pages with ISR enabled include an `x-nextjs-cache` header in their responses, which can have one of four values:

- `HIT`: Served from cache
- `STALE`: Served from cache while being regenerated in the background
- `MISS`: Not in cache, so it's freshly rendered
- `REVALIDATED`: Regenerated on-demand

The documentation also notes some important caveats. ISR does not work with static exports, and when running multiple instances, each instance has its own file cache; therefore, on-demand revalidation only applies to the instance that received the request.

</details>
