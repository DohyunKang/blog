컨텍스트는 모델이 답을 만들 때 한 번에 볼 수 있는 글 전체이고, 넓다고 다 좋은 게 아니라 거기에 뭘 올려 두느냐가 품질과 비용을 갈랐다.

## 컨텍스트가 뭔지

컨텍스트 윈도우는 모델이 답을 만들 때 참고할 수 있는 텍스트 전체다. Anthropic 문서는 이걸 모델의 "작업 기억(working memory)"이라고 부른다. 학습에 쓴 방대한 데이터와는 다른 얘기다. 학습 데이터는 모델 안에 이미 녹아 있는 것이고, 컨텍스트는 지금 요청에 실려 가는 것이다.

여기에 들어가는 것은 생각보다 많다. 시스템 프롬프트, 지금까지 주고받은 대화, 도구 정의, 도구가 돌려준 결과, 첨부한 이미지와 문서가 다 들어가고, 모델이 쓰는 답변(생각 토큰 포함)도 윈도우를 차지한다. 내가 친 한 줄은 일부일 뿐이다.

크기는 토큰으로 센다. 문서 기준으로 최근 Claude 모델 대부분이 1M 토큰 창을 가지고, 이전 세대 일부는 200k다. 다만 숫자는 모델마다 다르고 자주 바뀌어서, 쓸 때 모델 비교표를 다시 보는 게 맞다.

## 왜 길수록 문제가 되나

비용 쪽은 단순하다. API는 매 턴마다 지금까지의 대화를 통째로 다시 보낸다. 대화가 열 턴 쌓이면 열한 번째 요청은 앞의 열 턴을 전부 입력으로 다시 낸다. 그래서 길어질수록 요청 한 번의 입력 토큰이 늘고, 그만큼 요금과 지연이 늘어난다. 프롬프트 캐싱을 쓰면 단가가 줄지만, 문서에 따르면 캐시된 부분도 윈도우는 그대로 차지한다. 바뀌는 건 내는 돈이지 자리가 아니다.

품질 쪽이 더 헷갈린다. 창이 크면 많이 넣어도 되는 줄 알았는데 그렇지 않았다. Anthropic 문서는 "더 많은 컨텍스트가 자동으로 더 좋은 건 아니다. 토큰이 늘수록 정확도와 재현율이 떨어지는데 이걸 context rot이라 한다"고 적는다. 근거로 볼 만한 연구도 둘 찾았다.

- Liu 등의 "Lost in the Middle"(2023): 관련 정보가 입력의 앞이나 끝에 있을 때 성능이 좋고, 가운데에 있으면 떨어졌다. 입력이 길어질수록 전반적으로 성능이 내려가는 경향도 보고한다.
- Chroma의 "Context Rot"(2025): 18개 모델을 비교했더니 입력이 길어질수록 성능이 고르지 않게 떨어졌고, 단어 반복 같은 쉬운 과제에서도 그랬다.

다만 둘 다 특정 실험 조건에서 나온 결과다. 모델이 새로 나오면 수치는 달라질 수 있고, Chroma 쪽도 "왜 그런지"의 원인은 확실히 모른다고 한다. 그래서 "길면 무조건 나쁘다"가 아니라 "길수록 불안정해질 수 있다" 정도로 받아들였다.

Anthropic 엔지니어링 글은 이걸 "주의 예산(attention budget)"으로 설명한다. 토큰이 하나 늘 때마다 예산이 조금씩 닳는다는 비유다. 비유일 뿐 내부 구조를 증명한 말은 아니다.

## 컨텍스트 엔지니어링은 뭔가

같은 글에서 컨텍스트 엔지니어링은 프롬프트 엔지니어링의 "자연스러운 다음 단계"로 나온다. 정의는 추론 때 들어갈 토큰 집합을 가장 알맞게 고르고 유지하는 전략들이다.

내가 이해한 차이는 이렇다.

| | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|---|---|---|
| 다루는 것 | 지시문을 어떻게 쓸까 | 지금 이 모델 눈앞에 뭐가 있어야 하나 |
| 시점 | 한 번 쓰고 끝 | 매 턴, 루프 안에서 계속 |
| 대상 | 문장 | 지시, 대화 기록, 도구, 검색 결과, 메모 전부 |

챗 한 번이면 프롬프트 잘 쓰는 걸로 거의 충분하다. 에이전트처럼 모델이 도구를 부르며 루프를 도는 경우엔 턴마다 새 결과가 쌓이니까, 뭘 남기고 뭘 버릴지가 일이 된다. 그래서 이름이 따로 생긴 것 같다.

## 예시: 실제로 하는 일들

Anthropic 글이 드는 방법 몇 가지.

- 압축(compaction): 창이 거의 찼을 때 대화를 요약해서 새 창으로 이어 간다. 결정 사항과 풀리지 않은 버그는 남기고 중복된 도구 출력은 버린다.
- 바깥 메모: 에이전트가 NOTES.md나 할 일 목록 같은 걸 창 밖에 적어 두고 필요할 때 다시 불러온다.
- 하위 에이전트: 좁은 일은 깨끗한 창을 가진 하위 에이전트에게 맡기고, 결과는 요약(글에서는 1,000~2,000 토큰 정도)만 받는다.
- 필요할 때 가져오기(just-in-time): 파일을 미리 다 읽어 넣지 않고 경로 같은 식별자만 들고 있다가 도구로 열어 본다. 느린 대신 창이 가볍다. 글은 둘을 섞는 방식을 권한다(CLAUDE.md는 미리, 나머지는 그때그때).

## 하네스와의 관계

하네스(harness)는 모델을 감싸서 루프를 돌리는 쪽 코드와 환경을 말한다. 도구 호출을 실행하고, 결과를 다시 모델에 넣고, 기록을 잘라 내거나 요약하는 부분이다. 컨텍스트 엔지니어링의 앞선 방법들(압축, 메모, 하위 에이전트)은 결국 하네스가 구현한다. 모델은 자기에게 주어진 창만 볼 수 있으니, 창에 뭘 채울지는 하네스가 정한다. 그래서 둘의 관계는 "컨텍스트 엔지니어링은 하는 일, 하네스는 그 일을 하는 장치" 정도로 정리했다.

주의할 점: 위에서 읽은 Anthropic의 컨텍스트 엔지니어링 글에는 "하네스"라는 단어가 없었다. 문서 쪽에 "Effective harnesses for long-running agents"라는 별도 글 링크가 있는데, 여기서 쓰는 하네스 정의는 내 이해다.

## 흔한 오해

- 창이 1M이니 다 넣으면 된다: 들어간다는 것과 잘 쓴다는 것은 다르다. 위 연구들이 그 차이를 보여 준다.
- 컨텍스트 엔지니어링이 프롬프트 엔지니어링을 대체한다: 대체가 아니라 확장이다. 지시문 쓰기는 그대로 필요하다.
- 압축하면 안전하다: 요약에서 빠진 건 돌아오지 않는다. 뭘 남길지가 곧 설계다.
- 캐싱하면 창 걱정이 없다: 캐시는 요금을 줄일 뿐 자리를 줄이지 않는다.

문서가 설명하는 한 턴의 흐름은 이렇다. 입력 단계에는 이전 대화 전부와 이번 사용자 메시지가 들어간다. 출력 단계에서 나온 답은 다음 턴의 입력이 된다. 도구를 쓰면 도구 요청과 결과가 같은 식으로 쌓인다.

생각(thinking) 토큰은 `max_tokens` 안에 포함되고 출력 토큰으로 과금된다. 이전 턴의 생각 블록을 유지할지는 모델마다 다르다. 최신 모델은 기본으로 유지하고(그래서 입력으로 다시 과금되고 창도 차지), 일부 이전 모델은 자동으로 뗀다. 이 부분은 모델 목록이 계속 바뀌니 쓸 때 문서의 모델별 표를 다시 봐야 한다.

일부 모델은 남은 토큰 예산을 스스로 알 수 있는 "컨텍스트 인식" 기능이 있고, 모델에 따라 없고 대신 task budget(베타)을 쓴다고 문서에 나온다.
