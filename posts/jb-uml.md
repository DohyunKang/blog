UML은 소프트웨어를 그림으로 그리는 표준 표기법이고, 정보처리기사에서는 다이어그램 종류 구분과 클래스 관계 기호, 유스케이스·시퀀스 읽기가 핵심 단원이다. 이 글은 시험 대비용 정리다. 요구사항을 뽑는 단계는 [자세히 → 요구사항 확인과 분석](#/post/jb-requirements)에서 먼저 다뤘다.

## UML이 뭔지

UML(Unified Modeling Language)은 시스템을 모델로 그리는 표준 언어다. OMG가 1997년에 표준으로 채택해 관리하고 있고, ISO/IEC가 2005년에 ISO/IEC 19501로 냈다. 이후 정식 버전은 2.5.1(2017년 12월 채택)이다.

UML 2는 다이어그램을 14가지로 정의한다. 외울 때는 둘로 나누는 게 편하다.

| 구분 | 무엇을 그리나 | 다이어그램 7개 |
|---|---|---|
| 구조(Structure) | 시스템이 어떤 부품으로 이뤄졌나(정적) | 클래스, 컴포넌트, 복합체 구조, 배치, 객체, 패키지, 프로파일 |
| 행위(Behavior) | 시간에 따라 어떻게 움직이나(동적) | 유스케이스, 액티비티, 상태 머신, 시퀀스, 커뮤니케이션, 상호작용 개요, 타이밍 |

행위 쪽의 시퀀스·커뮤니케이션·상호작용 개요·타이밍 네 개는 따로 묶어 상호작용(interaction) 다이어그램이라고 부르기도 한다.

시험에서는 "이 그림은 어떤 다이어그램인가", "정적 모델과 동적 모델 중 어느 쪽인가" 같은 구분 문제로 나오기 쉬워서, 위 표의 왼쪽·오른쪽 소속만 정확히 들고 있으면 된다. 배치 다이어그램이 구조 쪽이라는 점, 유스케이스가 행위 쪽이라는 점이 헷갈리는 지점이다.

## 유스케이스 다이어그램

시스템을 쓰는 사람과 시스템이 해 주는 일을 한 장에 그린다.

- 액터(actor): 사용자나 외부 시스템. 보통 막대 사람 모양이다.
- 유스케이스: 시스템이 제공하는 기능 하나. 원이나 타원으로 그린다.
- 시스템 경계: 유스케이스들을 감싸는 네모. 시스템의 범위를 보여 준다.

유스케이스 사이 관계는 점선 화살표에 이름표를 붙인다.

| 관계 | 의미 | 화살표 방향 |
|---|---|---|
| include | 기본 유스케이스가 공통 기능을 정상 흐름에서 가져다 씀 | 기본 → 포함되는 쪽 |
| extend | 조건이 맞을 때 기본 기능에 선택 동작을 덧붙임 | 확장하는 쪽 → 기본 |
| 일반화 | 자식이 부모를 확장·재정의 | 자식 → 부모(삼각형 머리) |

include는 로그인 확인처럼 늘 거치는 부분, extend는 "비밀번호 오류" 같은 가끔 끼어드는 부분으로 기억하면 방향이 덜 헷갈린다. extend는 화살표가 기본 쪽을 향한다.

## 클래스 다이어그램

구조 다이어그램 중 가장 많이 쓰이는 그림이다. 클래스는 세 칸 상자(이름·속성·연산)로 그리고, 멤버 앞에 접근 기호를 붙인다.

| 기호 | 접근 |
|---|---|
| + | public |
| - | private |
| # | protected |
| ~ | package |

다중성(multiplicity)은 관계선 끝에 적는다. 1은 정확히 하나, 0..1은 없거나 하나, 0..* 또는 *는 0개 이상, 1..*는 1개 이상이다. 이어서 관계 여섯 가지가 이 단원의 중심이다.

| 관계 | 말로 하면 | 모양 |
|---|---|---|
| 연관(association) | 클래스끼리 구조적으로 이어짐 | 실선 |
| 집약(aggregation) | has-a, 부분이 따로 존재 가능 | 전체 쪽에 빈 마름모 |
| 합성(composition) | 더 강한 has-a, 전체가 죽으면 부분도 사라짐 | 전체 쪽에 채운 마름모 |
| 일반화(generalization) | is-a, 상속 | 실선 + 부모 쪽 빈 삼각형 |
| 실체화(realization) | 인터페이스를 구현 | 점선 + 인터페이스 쪽 빈 삼각형 |
| 의존(dependency) | 한쪽이 바뀌면 다른 쪽이 영향받는 약한 관계 | 점선 + 열린 화살표(사용하는 쪽 → 쓰이는 쪽) |

헷갈리는 건 집약과 합성, 그리고 일반화와 실체화다. 마름모가 비었는지 채워졌는지는 생명주기를 같이 가느냐로 갈린다. 삼각형은 둘 다 빈 삼각형이고, 선이 실선이면 상속, 점선이면 구현이다. 선 모양이 먼저, 머리 모양이 다음이라고 순서를 정해 두면 덜 틀린다.

다만 위 관계가 시험지에서 어떤 용어로 나오든(영문이든 한글이든) 정의 문장 하나씩만 붙여 외워 두면 된다. 코드로 옮기는 감각은 [자세히 → 객체지향과 언어 코드 읽기](#/post/jb-oop-lang)와 이어진다.

## 시퀀스 다이어그램

객체들이 메시지를 주고받는 순서를 위에서 아래로 시간 흐름에 맞춰 그린다.

- 라이프라인: 객체나 프로세스를 나타내는 세로선. 아래에 X가 있으면 객체가 사라진 것이다.
- 메시지: 가로 화살표에 메시지 이름을 단다. 채운 화살촉은 동기(호출한 쪽이 끝날 때까지 기다림), 열린 화살촉은 비동기(기다리지 않고 계속 진행), 점선은 응답(반환)이다.
- 활성 박스(activation bar): 라이프라인 위의 가는 사각형. 그 객체가 메시지를 처리 중인 구간이다. 자기 자신을 부르면 박스가 겹쳐 쌓인다.
- 조합 프래그먼트(combined fragment): 병렬, 조건 분기, 선택 동작 같은 흐름을 묶어서 표현하는 박스다.

문제는 보통 그림을 보고 "몇 번째 메시지가 어떤 종류인지", "어느 객체가 호출을 받는지"를 묻는 식이라, 화살촉 모양과 점선 응답을 구분하는 연습이 가장 직접적이다.

온라인 주문 한 건을 예로 들면 같은 내용이 그림마다 다르게 보인다.

- 유스케이스: 액터 "고객"과 "결제 대행사"가 있고, 유스케이스는 "주문하기", "결제하기". "주문하기"가 "로그인 확인"을 include하고, "쿠폰 적용"이 "결제하기"를 extend한다. 시스템 경계 안에 유스케이스가 들어가고 액터는 밖에 둔다.
- 클래스: 주문(Order)과 주문항목(OrderItem)은 항목이 주문 없이 의미가 없으니 합성으로 그리고, 주문과 고객(Customer)은 연관으로 둔다. 다중성은 고객 1에 주문 0..*이다. 결제 방식 인터페이스를 카드 결제 클래스가 구현하면 점선+빈 삼각형이다.
- 시퀀스: 고객 → 주문 서비스로 "주문 요청"(동기), 주문 서비스 → 결제로 "결제 요청", 점선으로 "결제 결과" 응답이 돌아온다. 알림을 기다리지 않고 보낸다면 열린 화살촉 비동기 메시지로 그린다.

같은 시스템도 "누가 무엇을 하나"는 유스케이스, "무엇이 무엇을 가졌나"는 클래스, "누가 누구에게 언제 말하나"는 시퀀스가 맡는다. 문제를 읽을 때 질문이 이 셋 중 어디에 속하는지 먼저 정하면 풀이가 빨라진다.

## 객체지향 분석에서 쓰는 감각

객체지향 분석은 요구사항에서 객체 후보(명사)와 그 행동(동사)을 뽑아 클래스로 정리하는 일이다. 유스케이스로 기능 범위를 잡고, 클래스 다이어그램으로 정적 구조를 정하고, 시퀀스로 시나리오를 검증하는 순서가 자연스럽다. 이 단계에서 정한 구조가 이어서 나오는 [자세히 → 소프트웨어 아키텍처](#/post/jb-architecture-pattern)와 [자세히 → 디자인 패턴](#/post/jb-design-pattern)의 재료가 된다.

## 흔한 헷갈림

- 집약과 합성은 둘 다 마름모다: 빈 마름모는 부분이 따로 살 수 있고, 채운 마름모는 전체와 같이 사라진다.
- 일반화와 실체화의 삼각형은 같다: 실선이면 상속, 점선이면 구현이다.
- include와 extend의 화살표 방향이 같다: 반대다. include는 기본에서 포함되는 쪽으로, extend는 확장하는 쪽에서 기본으로 간다.
- 배치·컴포넌트 다이어그램은 행위 쪽이다: 둘 다 구조 쪽이다.
- 시험 일정이나 문제 유형 비율은 이 글에서 다루지 않는다. 일정·접수는 공식 사이트에서 확인한다.
