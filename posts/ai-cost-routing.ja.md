LLM API の料金は、使用したトークン数に単価を掛けた値です。したがって、コスト削減の手法も「掛け算の両側」から整理できます。単価が低いモデルを使う、割引を受けながら呼ぶ、あるいはトークン自体を減らすといった方法があります。

## 料金の計算方法

[LLM](#/post/ai-llm) API は入力トークンと出力トークンを別々にカウントします。単価は通常 100 万トークン (MTok) を基準としており、出力の方が入力を高価に設定されています。以下は Anthropic の公式価格ページの標準価格です（2026-11-04 に確認した値で、価格は変動します）。

| モデル | 入力 | 出力 | バッチ入力 | バッチ出力 |
|---|---|---|---|---|
| Claude Opus 5.5 | $4 | $20 | $2 | $10 |
| Claude Sonnet 5.5 | $2 | $10 | $1 | $5 |
| Claude Haiku 5.5 (プロンプト 10 万トークン以下) | $0.10 | $0.50 | $0.05 | $0.25 |

同じページ基準で、Opus と Haiku では入力が 40 倍、出力も 40 倍の差があります。モデルを一つ変えるだけで、桁が一位ではなく二位動く計算になります。モデルごとの特徴は [AI モデルマップ](#/post/ai-models) に別途整理しています。

コスト感を把握するために仮定を立てます。1 日 1,000 件、リクエストあたり入力 2,000 トークン・出力 500 トークンとします。

```
하루 입력 = 1,000 × 2,000 = 200만 토큰
하루 출력 = 1,000 × 500  =  50만 토큰
```

この数字に上記の表を掛け合わせると以下のようになります。

| モデル | 1 日コスト | 30 日 |
|---|---|---|
| Opus 5.5 | $8 + $10 = $18 | $540 |
| Sonnet 5.5 | $4 + $5 = $9 | $270 |
| Haiku 5.5 | $0.2 + $0.25 = $0.45 | $13.5 |

入力トークン数は、プロンプトに [コンテキスト](#/post/ai-context) をどれだけ埋めるかで決まります。対話が長くなるほど、ドキュメントを多く追加するほど、リクエストあたりの入力が膨らみます。[コンテキストウィンドウ](#/post/ai-context-window) が大きいということは「多く入れることができる」という意味であり、「無料」という意味ではありません。

## モデルルーティング

リクエストごとに難易度は異なります。分類、短い抽出、形式変換などは小さなモデルでも可能ですが、長い推論やコード作成には大きなモデルが必要です。ルーティングは、入ってきたリクエストを見てどのモデルに送るかを決定するフロントエンドです。

```
요청 → [라우터: 난이도 판단] ─ 쉬움 → 작은 모델 (Haiku급)
                            └ 어려움 → 큰 모델 (Sonnet·Opus급)
```

上記の仮定で、リクエストの 80% を Haiku、20% を Sonnet に送ると、1 日コストは以下のようにになります。

```
0.8 × $0.45 + 0.2 × $9 = $0.36 + $1.80 = $2.16
```

すべて Sonnet の場合は $9 だったので、4 分の 1 の水準です。大きなモデルの比重がコストの大部分を占めていることもわかります。20% しか送っていないのに、コストの 80% がそこから出ています。

ルーティングを作成する方法はいくつかあります。

- ルール：入力長、リクエストの種類（分類か作文か）、ユーザーグレードなどで分けます。最も単純でデバッグも容易です。
- 小さなモデルに判断させる：リクエストを見て「簡単/難しい」のみを答えるようにします。この呼び出し自体がコストになるため、非常に安いモデルである必要があります。
- まず小さなモデル、失敗したら大きなモデル：小さなモデルで答えを出し、形式チェックや信頼度チェックに合格しない場合、大きなモデルに再度送ります。失敗した試行のコストがかかるのが欠点です。

ルーティングが難しいリクエストを簡単なものと間違えて送ると品質が低下します。コストだけを見て変更してもこれを察知できないため、変更するたびに [評価セット](#/post/ai-evals) でスコアを比較する必要があります。

## キャッシング

反復される前半部分の処理結果を再利用するプロンプトキャッシングは、入力側の単価を大幅に下げます。価格ページの Sonnet 5.5 の行におけるキャッシュヒット価格は $0.10/MTok で、標準入力の $2 の 20 分の 1 です。一方、キャッシュに使用するリクエストは $2.50/MTok（5 分間のキャッシュ基準）で、標準よりやや高価です。原理と使い方は [プロンプトキャッシング](#/post/ai-prompt-caching) の記事に整理しているので、ここではコスト手段としての位置づけのみ記載します。システムプロンプトや長いドキュメントのように、各リクエストごとに同じく付随する部分が大きいほど効果は大きいです。

同じ質問がそのまま繰り返されるサービスであれば、回答自体を保存しておく方法もあります。これはモデルを呼ばないためコストは 0 です。ただし質問が完全に一致する必要があり、ユーザーによって表現が変わるサービスでは命中率が低くなります。

## バッチ API

即座に答えが必要な作業ではなく、バッチとして送信します。上記表のバッチ列がそれであり、Anthropic のページでは入力と出力ともに 50% の割引と記載されています。OpenAI のバッチガイドでも同期 API に比べて 50% のコスト割引であるとされ、24 時間以内に完了し（実際にはより早く終了するケースが多い）、評価実行、大規模データ分類、コンテンツ埋め込みなどの作業に適しているとしています。

夜間の分類、ドキュメントの大規模要約、評価セットの回すような人が待機しない作業が該当します。ユーザーが画面前で待機しているリクエストには使用できません。価格ページには、この割引がキャッシュのような他の価格調整と重ねて適用される旨の記載もあります。

Sonnet 5.5 の場合、バッチ処理を適用すると単価は $9 から $4.5 に下がります。

## 出力量を削減する

出力の単価が入力単価の約 5 倍（Sonnet 5.5 では $10 対 $2）であるため、出力トークンを 1 つ減らすことが入力トークンを 1 つ減らすことよりも価値があります。

- 業務に合わせて `max_tokens` の最大出力長を制限します。
- プロンプトで形式を厳格に指定します。「単語一つで分類」「JSON のみ出力」などです。
- 不要な序論や要約を付加しないよう指示します。

単に長さを減らすと回答が途切れてしまう可能性があるため、切断しても問題ない作業に適用します。

## 呼び出し自体を削減する

モデルを呼ばなくても済む場合は、呼ばないのが最も安いです。

- ルールや通常のコードで処理可能なこと（正規表現、条件分岐、DB 照会など）はモデルに委ねません。
- 同じ入力の結果を保存して再利用します。
- 複数の項目を一度に処理できる場合はバッチ化します。システムプロンプトが各リクエストごとに重複課金されるのを防ぎます。
- [エージェントループ](#/post/ai-agent-loop) は 1 つのリクエストでモデルを複数回呼び出します。反復回数の上限を設けないと、想定以上のコストになる可能性があります。
- [RAG](#/post/ai-rag) で文書を丸ごと追加するのではなく、必要な断片だけ追加すれば入力トークンが削減されます。

## オープンソースモデルを自走させる場合

オープンソースモデルを自分の GPU で実行すれば、トークン単価はなくなります。代わりに GPU 費用が固定費として発生します。クラウド GPU は時間課金ですが、自機の場合は購入費用と電気代です。どちらを使うかに関わらずコストが発生します。

したがって、比較は以下のようになります。

```
API 비용      = 월 토큰 수 × 단가            (쓴 만큼 늘어남)
자체 운영 비용 = GPU 월 비용 + 운영 인력·시간   (거의 고정)

손익분기 월 토큰 ≈ 자체 운영 월 비용 ÷ API 토큰당 단가
```

自走運用の月間コストが決まれば、それを上記の単価で割って、月間何トークン以上使うとから自走運用が安くなるかを計算できます。ただし、この計算で見落としがちなのが、GPU がアイドル状態にある時間、サービングソフトウェアの設定や修正に要する時間、モデル性能が API の大規模モデルに劣る可能性です。1 日数百件程度の使用量では上記の表のように Haiku 級でも月間十数ドルで、GPU の固定費を上回らないケースが多いでしょう。逆にトラフィックが大きく安定しており、小規模モデルでも十分な作業であれば自走運用が適している可能性があります。どちらが転換点かは、実際の GPU 料金と処理量を代入して直接計算する必要があります。

<details>
<summary>詳細な解説：上記の計算を一覧で確認</summary>

仮定：1 日 1,000 件、リクエストあたり入力 2,000 トークン・出力 500 トークン、30 日間。

| 構成 | 1 日 | 30 日 |
|---|---|---|
| すべて Sonnet 5.5 | $9 | $270 |
| すべて Sonnet 5.5 バッチ | $4.5 | $135 |
| 80% Haiku + 20% Sonnet | $2.16 | $64.8 |
| すべて Haiku 5.5 | $0.45 | $13.5 |

ルーティングとバッチ処理は併用可能です。ルーティング後、非同期可能なリクエストのみをバッチで実行する方式です。キャッシュは入力単価を別途下げるため、上記の表よりもさらにコストを下げることも可能です。

</details>

## どこから削減するか

順序は概ね以下の通りが無難です。まずどのリクエストが多くのトークンを消費するかログで計測します。次に呼び出し自体と出力長を削減し、反復処理の前半部分が大きい場合はキャッシュを活用し、人が待たない作業はバッチ処理に移し、最後にルーティングを追加します。モデルを変更するのは品質への影響が最も大きいため、評価セットがある場合に実施します。

## よくある誤解

- 安いモデルなら常に有利：小規模モデルが間違えて再試行・再リクエストが増えると、節約分が消えます。
- キャッシュは書き込みさえすれば常に安価：キャッシュに書き込むリクエストは標準より高く、再度読み込まれない場合は損です。
| 入力長が長くても料金は変わらない：入力はトークン数に応じて課金され、長さが増すほど線形に増加します。
- 自走 GPU は無料：トークン単価はなくても固定費が発生します。
