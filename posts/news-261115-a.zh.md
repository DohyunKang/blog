## 是什么
一个用 AI 做代码审查的命令行工具。README 说，这是阿里巴巴内部用了两年的审查助手，后来开源了。它读取 Git diff，把改动的文件交给 LLM 代理，返回精确到行的审查评论。代理能读整个文件、搜索代码库，所以也能看到 diff 之外的上下文。代理就是模型一边用工具一边自己决定下一步做什么的方式。[详细 → 代理循环](#/post/ai-agent-loop)

用 `npm install -g @alibaba-group/open-code-review` 安装，配置好模型提供方，然后运行 `ocr review` 就行。还有不看 diff、直接扫整个目录的 `ocr scan`。

## 怎么运行
有意思的是它对设计的说法。README 说，给 Claude Code 这类通用代理加个技能去做审查，会出问题：改动一大就只看一部分文件，指出的行号和实际代码对不上，提示词稍微一改质量就忽高忽低。原因是整个流程只靠语言来指挥，没有强制的机制。

所以不能出错的步骤交给普通代码，而不是模型。

1. 选文件：用代码决定审哪些文件、过滤哪些，让模型没机会漏掉。
2. 打包：把相关文件归成一个单元，比如 `message_en.properties` 和 `message_zh.properties`。每个包由上下文相互隔离的子代理分别处理。[详细 → 子代理](#/post/ai-subagent)
3. 匹配规则：用模板引擎只挑出适合该文件的审查规则放进去，减少模型要读的信息。
4. 定位和复查：模型之外另有模块，一个校正评论指向的行，一个重新检查评论内容。

模型只在中间做判断，比如还要去找哪些上下文。工具列表也是根据真实使用记录，分析每个工具被调用多少次、重复多少次之后精简的。[详细 → 工具使用](#/post/ai-tool-use)

它有两种运行模式，这点也挺显眼。默认是 OCR 自己调用配置好的模型 API。委托模式(Delegation Mode)下，OCR 只负责选文件和整理规则，审查本身由我平时用的编程代理用它自己的模型来做。README 写着这时不需要单独的 OCR API 密钥。

## 为什么火
有一张表很显眼。它用50个开源仓库里的200个真实 PR，以人工标出的1,505个问题作为标准答案来比较(AACR-Bench，项目自己做的基准)。同样用 Claude-4.8-Opus,OCR 的精确率37.8%、召回率11.7%,每次审查352K token、1分6秒。Claude Code 是精确率15.93%、召回率12.70%、2,062K token、5分38秒。精确率是指出的问题里真问题的比例，召回率是真问题里被找到的比例。README 也承认召回率低是为了减少误报而做的取舍。表里的 OCR 是 v1.3.1,比现在的 v1.13.9 旧很多，而且是项目自己测的数字，我没有复现。[详细 → 评估(evals)](#/post/ai-evals)

发版也很勤。11月10日、12日、13日接连发了 v1.13.7~v1.13.9,12日的版本加入了 GitHub Copilot CLI 集成。

在 Reddit 和 YouTube 上传播得怎么样，没能确认。

## 从入门者角度看
站在 PM 的角度，"别全交给模型，不能出错的部分用代码固定下来"这个设计很有感触。代理质量不稳定的时候，与其再去打磨提示词，不如看看哪一步该挪到模型之外。审查里误报一多，人最后就不看了，所以宁可少找一点也要准，这个选择也说得通。

开发入门的话，可以先在自己的小项目里对一个提交跑 `ocr review --commit <哈希>` 试试。如果已经在用 Claude Code 这类代理，可以用委托模式不配密钥接上试试。对找安全漏洞的工具感兴趣的话，这篇也可以一起看。[详细 → Codex Security](#/post/news-261113-a)
