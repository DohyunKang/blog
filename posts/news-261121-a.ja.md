## どういうものか
CLI はマウスの代わりに文字でコマンドを打ってプログラムを使うやり方だ。エージェントはもともとテキストを読み書きする側なので、ボタンを探して押すよりコマンドを打つほうがずっと向いている。エージェントがツールを選んで呼ぶ流れは前にまとめた。[詳しく → ツール呼び出し](#/post/ai-tool-use)

CLI-Anything は二つに分かれる。一つは Claude Code のプラグインで、`/cli-anything ./gimp` のようにプログラムのソースフォルダを渡すと、エージェントがそのプログラム用の CLI を作る。もう一つは作り済みの CLI を集めた CLI-Hub。`pip install cli-anything-hub` のあと `cli-hub install gimp` のように入れる。リポジトリ内のレジストリファイル二つに、それぞれ 79 件と 24 件が登録されていた。

できた CLI はこう使う。README の例をそのまま書くと、`cli-anything-libreoffice document new -o report.json --type writer` で文書を作り、見出しや表をコマンドで足して、`export render output.pdf` で本物の LibreOffice を画面なしで動かして PDF を出す。どのコマンドにも `--json` を付ければ結果が JSON で返り、エージェントがそのまま読める。コマンドなしで起動すると対話モード(REPL)に入って一行ずつ打てる。

## 中でどう作るのか
`/cli-anything` を呼ぶと 7 段階が回る。ソース分析、コマンド構成の設計、実装、テスト計画、テスト作成、ドキュメント化、インストール用パッケージ作成の順。最後にその CLI の使い方を書いた SKILL.md もできる。スキルはエージェントが必要なときに取り出して読む説明書だ。[詳しく → スキル](#/post/ai-skills)

HARNESS.md が実質的な設計書で、最初の段階が面白かった。

1. GUI の裏にあるエンジンを探す。画面は殻で、実際の仕事は内側のライブラリがやる。文書は動画編集ソフト Shotcut の裏にある MLT を例に挙げている。
2. ボタンのクリックやメニューの一つ一つが、結局どの関数呼び出しなのか対応を取る。
3. プロジェクトファイルの形式(XML、JSON など)を把握する。
4. プログラムに取り消し(undo)があれば、それがそのままコマンドの単位になる。取り消しができるには操作が一つずつのコマンドに分かれている必要があるので、それを CLI のコマンドに移す。

原則の中で目に付いたのは、必ず本物のプログラムを呼ぶこと。GIMP の代わりに Python の画像ライブラリで真似したりせず、プロジェクトファイルを作ったらレンダリングは本物のアプリに任せる。アプリが入っていなければテストはスキップではなく失敗扱いになると書いてある。「終了コードが 0 だからといって書き出せたと信じるな」という項目もある。PDF ならファイルの先頭が `%PDF-` か、音声なら音量が 0 でないかまで確かめろということだ。こうした確認を合わせて、README にはテスト 2,464 件通過とある。

## 入門者の立場から
PM の立場では「このプログラムはエージェントが使えるか」を問う基準が一つ増えたと言える。画面の代わりにコマンドと JSON で扱えれば、自動化が壊れにくい。ただ README 自身が限界を書いている。性能の高い最新モデルがないとまともな CLI はできず、ソースコードのないプログラムでは品質が大きく落ち、一度で全部できなければ `/cli-anything:refine` を何度か回す必要があるそうだ。

開発入門者なら、HARNESS.md を機能設計の練習用の文書として読んでもよさそう。「見るコマンドを先に作って、変えるコマンドはその後」という順番は、エージェントでなくてもそのまま通じる話だ。エージェントがツールを使う別のやり方である MCP と比べると違いがよく見える。[詳しく → MCP](#/post/ai-mcp)
