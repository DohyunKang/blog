Evals 는 LLM 機能が正しく動作しているかを検証するための試験紙と採点方式のセットです。入力データセット（評価用データ）、正解の基準、採点方法が 1 セットをなし、プロンプトやモデルを変更するたびに同じ試験紙で再度問題を解いて点を比較します。

## なぜ必要なのか

一般的なソフトウェアは同じ入力で同じ出力が出るため、ユニットテストで十分です。[LLM](#/post/ai-llm) はそうではありません。OpenAI の評価ガイドでは、生成 AI は非決定論的であるため従来の方式のテストでは不十分であり、その変動の中で精度・性能・信頼性を測る構造化されたテストを evals と説明しています。

企業が LLM 機能をサービスに導入すると変化が多いです。[プロンプト](#/post/ai-prompt) の 1 行、モデルバージョン、[RAG](#/post/ai-rag) の検索設定、ツールリストがすべて回答を変えます。ある箇所を修正して A クエリが良くなったのに B クエリが悪化したかどうかは、目で数件見るだけでは分かりにくいです。OpenAI ガイドもこのような「感覚での判断 (vibe-based evals)」や、リリース後に評価を追加することをアンチパターンとして挙げています。

そのため、評価は開発の初期段階に置きます。両方のガイドとも、評価を一度行って終わらせるのではなく、継続的に回すものとしています。

## 全体の流れ

OpenAI ガイドの 5 ステップを簡略化すると以下のようになります。

```
목표 정의 → 데이터셋 수집 → 지표 정의 → 실행·비교 → 지속 평가
   │            │              │           │           │
 성공이 뭔가   입력+정답 모음   어떻게 채점  점수 비교   변경마다 재실행,
                                                       세트 키우기
```

Anthropic のドキュメントでは、成功基準から設定するよう指示しています。良い基準は具体的 (Specific) で、測定可能 (Measurable)、達成可能 (Achievable)、関連性がある (Relevant) である必要があります。ドキュメントの対比例は以下の通りです。

| 悪い基準 | 良い基準 |
|---|---|
| 感情分類を良くする必要がある | 1 万件の多様なツイート保持セットで F1 0.85 以上、現在のベースラインより 5% の改善 |
| 有害な回答があってはならない | 1 万回の試行のうち、コンテンツフィルターが有害と判定した出力が 0.1% 未満 |

基準が 1 つだけの 경우는稀であり、ドキュメントもほとんどのユースケースでは複数の基準（タスク忠実度、一貫性、関連性、トーン、個人情報保護、文脈活用、遅延、価格など）を同時に見る必要があると記しています。

## 評価データセット

試験紙に相当する部分です。2 つのドキュメントが共有する原則はいくつかあります。

- 実際のサービスに導入される入力分布に似せるようにします。学術指標や業務と無関係なデータだけで構成すると、点数と実際の品質が乖離します（Anthropic: task-specific, OpenAI: プロダクショントラフィックと合わないデータセットはアンチパターン）。
- 一般的なケース、境界ケース、攻撃的・敵対的な入力を混ぜます。Anthropic ドキュメントで挙げている境界ケースには、関連がないか存在しない入力、過度に長い入力、不適切な入力、人間同士でも判断が分かれる曖昧なケースが含まれます。
- 出典を混ぜます。OpenAI ガイドでは合成データ、ドメインデータ、人間が作成したもの、運用ログ、過去データを挙げます。ログをすべて残しておけば後で良い評価事例の材料になるとも言います。
- 合成で作成した事例については、専門家がラベルを付けることを推奨します。
- Anthropic は、品質の高い人間による採点数件よりも、信号が少し弱くても自動採点される問題が多い方がよい（volume over quality）としています。

データの 1 行は概ね以下のようになります。OpenAI Evals ドキュメントの例でも入力 (`ticket_text`) と人間が付けた正解 (`correct_label`) を 1 つの項目に置いています。

| id | 入力 | 正解基準 |
|---|---|---|
| refund-1 | " 환불 기간이 어떻게 되나요?" | 答えに"7 일"が含まれる |
| refund-2 | " 그냥 다 환불해 주세요" | 무조건 보장한다는 표현이 없다 |
| edge-1 | (빈 입력) | 되묻거나 거절한다 |

## 採点方法の 3 つ

Anthropic ドキュメントでは「最も速く、信頼でき、拡張性の高い方法を選べ」と述べ、順に 3 つを提示しています。

| 方式 | 長所 | 限界 | 例 |
|---|---|---|---|
| コード検査 | 最も速く、信頼性が高く、拡張が容易 | 微妙な判断には硬直的 | 完全一致、キーワードの有無 |
| 人間による査収 | 最も柔軟で品質が高い | 遅く、高価 | 専門家のスコア付け |
| LLM 採点 (LLM-as-judge) | 速く柔軟で複雑な判断も可能 | 信頼性を先に確認する必要がある | トーン 1〜5 点、情報漏洩の有無（はい/いいえ） |

OpenAI ガイドの分類も同様です。指標ベース（完全一致、ROUGE/BLEU、関数呼び出し精度、実行して確認する text2sql など）は速く回帰テストに適していますがニュアンスを見逃す可能性があります。人間評価は品質が最も高いですが遅く、評価者間で意見が分かれることがあります。モデル採点はさらに安く拡張可能です。

### コード検査

正解が決まっている部分はコードで記述する。形式の遵守、必須文句、禁止文句、数字範囲などである。[構造化された出力](#/post/ai-structured-output) を使用する機能であれば、JSON がスキーマに合致しているかどうか自体が最もコストのかからないチェック手段となる。以下は実際に実行して確認した最小限の例である。

```python
cases = [
    {"id": "refund-1", "output": "환불은 7일 이내 가능합니다.", "must": ["7일"], "banned": ["보장합니다"]},
    {"id": "refund-2", "output": "언제든 100% 환불을 보장합니다.", "must": ["7일"], "banned": ["보장합니다"]},
]
def check(c):
    return all(m in c["output"] for m in c["must"]) and not any(b in c["output"] for b in c["banned"])
res = {c["id"]: check(c) for c in cases}
print(res, sum(res.values()) / len(res))
# {'refund-1': True, 'refund-2': False} 0.5
```

### LLM による評価

人間が読み込んで判断すべき項目（トーン、要約の忠実度など）については、別のモデルに評価を依頼する。Anthropic のドキュメントで示されているヒントは 3 つある。

- ルーブリックを具体的に記述する。例："答えの最初の文節に 'Acme Inc.' が含まれており、含まれていない場合は自動的に incorrect とする"など。ある使用事例に対して複数のルーブリックが必要になる場合もある。
- 出力を固定する。'correct'/'incorrect'のみ、または 1〜5 点などのスコアリングを行う。純粋な記述式評価は、迅速かつ大量にレビューするのは難しい。
- 評価モデルがまず推論を行わせるようにする。ドキュメントでは、thinking を有効にした評価モデルを使用すると、特に複雑な判断において評価性能が向上すると記載されている。

同じドキュメントの評価プロンプトは以下のようになる。

```
Grade this answer based on the rubric:
<rubric>{rubric}</rubric>
<answer>{answer}</answer>
Output 'correct' or 'incorrect' in <result> tags.
```

また、Anthropic は評価対象の出力を生成したモデルとは別のモデルで評価を行うことが一般的に良い方法であると述べている。

<details>
<summary>詳細な解説：OpenAI ガイドにおける LLM 評価の推奨事項</summary>

- 評価形式にはペア比較、単一回答評価、正解参照評価がある。
- 可能な限り高性能なモデルを評価に使用し、スコア付け前に根拠を示させる。
- 質問を選択式に変換できる場合は変換する。ガイドでは、LLM が自由文を書くことよりも選択肢間の区別を行う方が優れていると報告しており、ペア比較・分類・基準別評価を推奨している。
- 明確で詳細なルーブリックを使用する。
- 評価モデルが人間ラベルと一貫性を保つことを確認した上で、規模を拡大する。
- ガイドも完璧な戦略は存在せず、専門家ラベルは高コストであると認めている。

</details>

## 人間による検証はどこで使うか

人間による評価は高価であるため、すべてを人間に任せることはできない。代わりに基準点（ベンチマーク）としての役割を果たす。OpenAI ガイドでは、人間の注釈を正解（ground truth）とし、自動評価器をそれに合わせて検証・補正することを推奨している。この補正ステップをスキップすることもアンチパターンとして記載されている。人間による評価を行う際の推奨事項には、複数回のレビュー、各スコア段階での例示の提供、数値スコアとともにパス/フェイル基準の設定、複数のレビュアーによる合意投票などが含まれる。

まとめると役割は分担される。

```
사람 검수   → 소수 샘플로 "정답 기준"을 만들고 채점기를 보정
LLM 채점    → 보정된 기준으로 대량 채점
코드 검사   → 형식·금지어처럼 확정적인 것은 항상 먼저
```

## 回帰テスト

回帰とは、修正した結果、以前に機能していたものが動かなくなってしまうことを指す。評価セットがそれを検知する装置となる。OpenAI Evals のドキュメントでは、モデルをアップロードしたり新しいモデルを試す際に、性能が期待水準を維持しているかを確認するために評価が必須であると述べており、継続的な評価フェーズでは変更ごとに評価を実行し、セットを継続的に拡大することを推奨している。

運用方法は単純である。

| 時点 | 行うこと |
|---|---|
| プロンプト・モデル・検索設定を変更する直前 | 現在のスコアを基準線として記録 |
| 変更後 | 同じセットで再実行し、スコアを比較 |
| サービス側で失敗事例が発見された場合 | その入力を評価セットに追加 |

OpenAI ガイドでは、指標ベースの評価は迅速であり回帰テストに適しているため、毎回回すのはコードチェックが中心となり、LLM 評価や人間検証は大きな変更時に追加する構成が自然であると述べている。

## 構造が複雑化した場合

OpenAI ガイドでは、非決定性が構造の各層に侵入するため、評価もその各ポイントで行う必要があると述べている。

| 構造 | 評価すべき項目 |
|---|---|
| シングルターン | 指示に従う（衝突するユーザープロンプトに対する抵抗を含む）、機能的正確性 |
| ワークフロー | 各ステップを個別に同じ基準で評価 |
| シングルエージェント | ツールの適切な選択、引数の正確な渡しが適切か |
| マルチエージェント | 引き継ぎのタイミングを認識するか（ハンドオフの精度） |

[エージェントループ](#/post/ai-agent-loop) が回る機能であれば、最終的な答えだけでなく、中間のツール選択も評価対象となる。

## よくある落とし穴

両方のガイドに直接記載されている事項のみを集めると以下のようになる。

- 評価モデルの位置偏り：ペア比較において、応答が配置された順序によって好みが変化することがある。OpenAI ガイドでは、ペア比較やパス/フェイル形式が信頼性を高めると述べている。
- 評価モデルの長さ偏り：判定モデルがより長い応答を好む傾向があるため、応答の長さを制御するよう指示している。
- 自動評価器を人間に合わせていない：自動スコアが高くても人間の判断と食い違う可能性がある。
- 学術指標のみを使用：perplexity や BLEU などの一般的な指標だけでは、我々の業務品質を測定できない。
- 実際の入力とは異なるデータセットや境界事例の欠落：スコアは良いが、サービス側で失敗する。
- 同じモデルが生成し、同じモデルで評価：Anthropic は別のモデルで評価することを推奨している。
- 遅れて追加された評価：リリース後に追加すると基準線が存在しない。

## よくある誤解

- 点数が高いと幻覚がない：これは評価セットが扱う範囲内でのみ言えることである。セットに含まれていない入力はそのまま残る（[幻覚](#/post/ai-hallucination)）。
- 評価はモデル会社が実施するもの：ベンチマーク（MMLU など）はモデル同士の比較に用いられ、当サービスに適したものは各自が作成したタスク別評価である。OpenAI ガイドはこの 2 つを区別している。
- 評価は一度で十分：変更ごとや失敗事例が蓄積するたびにセットを拡張する。
- 評価ですべてを防げるわけではない：評価は測定であり、出力の遮断ではない。実行中に防ぐのは [ガードレール](#/post/ai-guardrails) の役割である。
- 評価とファインチューニングは別物：OpenAI ガイドでは、評価が一貫して性能を測れるようになった場合、そのデータを改善に利用するよう示唆しており、例として強化学習によるファインチューニングを挙げている（[ファインチューニング](#/post/ai-finetuning)）。

<summary>参考：OpenAI Evals プラットフォームの発表</summary>

OpenAI のドキュメントには、Evals プラットフォームを停止する旨の発表がある。既存ユーザーに対しては 2026 年 10 月 31 日から読み取り専用となり、11 月 30 日に終了予定であり、代替手段として Datasets が案内されている。ツールが変わっても上記の構造（データ項目、採点基準、実行後の比較）はそのままであるため、概念の整理には影響がない。Evals ドキュメントの流れは、データスキーマとテスト基準を定義し、正解ラベルを含む JSONL をアップロードし、モデルとプロンプトテンプレートを用いて run を作成し、run の通過/失敗数を確認する順序である。例で使用されている採点器は `string_check`（完全一致 `eq`、部分一致 `like`）である。
