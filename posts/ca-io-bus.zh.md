CPU 能够快速执行指令，而磁盘、网卡和键盘相比之下则慢得多。关于输入/输出（I/O）的讨论，几乎都归结于如何掩盖这种速度差异。CPU 内部的运作详见 [CPU 与指令](#/post/ca-cpu)，内存方面的速度差异则在 [内存层次结构与缓存](#/post/ca-memory-hierarchy) 中介绍，本文仅关注 CPU 外部的设备及其之间的连接。

## 设备看起来只有几个寄存器

OSTEP（教材）通过一个虚拟标准设备进行讲解。设备由两部分组成：向系统展示的接口和其背后的内部结构。内部结构既可以是简单的单个芯片，也可以是包含小型 CPU 和内存、运行固件的复杂设备。操作系统无需了解内部结构，只需处理接口即可。

接口被简化为三个寄存器：

| 寄存器 | 用途 |
|---|---|
| 状态 (status) | 读取以确认设备当前是否忙碌 |
| 命令 (command) | 写入以启动设备执行相应操作 |
| 数据 (data) | 向设备写入要发送的数据，或读取接收到的数据 |

基本流程包含四个步骤：在状态显示忙碌时等待，向数据寄存器写入，向命令寄存器写入，然后再次等待直到状态不再显示忙碌。这种持续读取状态并等待的方式称为轮询（polling），而 CPU 直接搬运数据的方式称为程序化 I/O（PIO）。这种方式虽然简单且能工作，但如果设备较慢，CPU 会花费大量时间仅用于读取状态寄存器。

## 如何访问寄存器

CPU 访问设备寄存器的方法主要有两种。一种是专用的输入/输出指令，例如 x86 架构中的 `in` 和 `out`，它们通过端口号来指代设备。这些指令通常是特权指令，只有操作系统可以使用，因为普通程序直接操作磁盘会导致问题。

另一种是内存映射 I/O（Memory-Mapped I/O）。它将设备寄存器模拟为内存地址，对相应地址执行加载/存储操作时，硬件会将这些操作视为对设备的访问而非内存。其优势在于无需额外的专用指令。OSTEP 指出，目前这两种方式并无明显优劣之分，均被广泛使用。

由于每个设备的寄存器和流程各不相同，整个操作系统无法掌握所有细节。因此，设备的具体实现被封装在设备驱动程序中，而上层如文件系统则仅发出“读取/写入块”等通用请求。关于文件系统与 I/O 的内容，将在 [文件系统与输入/输出](#/post/os-filesystem) 中讨论。

## 等待的成本：轮询与中断

若使用中断代替轮询，操作系统在发出请求后会挂起该进程并转而执行其他任务。当设备完成操作时，硬件会触发中断，CPU 随即跳转到预设的中断服务程序（ISR）。处理程序完成请求后唤醒被挂起的进程。在此期间，CPU 已执行了其他进程，从而实现了计算与 I/O 的重叠。

那么中断是否总是更优？OSTEP 认为并非如此。中断处理和上下文切换同样消耗资源。如果设备非常快，仅需几次轮询即可完成操作，此时轮询反而更高效。因此，存在一种混合模式：先短暂轮询，若未完成则切换到中断方式。当数据包大量涌入（如网络场景）时，过多的中断可能导致操作系统陷入仅处理中断而无法完成其他任务的“活锁”状态，此时偶尔采用轮询直接控制流程更为合适。此外，还有一种名为 coalescing 的优化技术，可将多个中断合并后一次性通知。

<details>
<summary>轮询与阻塞等待对 CPU 的使用量（直接运行测试）</summary>

模拟了一个会在 1 秒后报告“完成”的慢速设备。一侧持续循环调用非阻塞 `recv`（即轮询），另一侧则使用阻塞 `recv` 让内核挂起进程。需要注意的是，阻塞方式并不等同于中断机制，但其结构相似：操作系统挂起进程，并在事件发生时将其唤醒。

```python
import socket, time, threading

def device(sock, delay):
    time.sleep(delay)
    sock.send(b"done")

def run(mode, delay=1.0):
    a, b = socket.socketpair()
    threading.Thread(target=device, args=(b, delay), daemon=True).start()
    c0, t0 = time.process_time(), time.perf_counter()
    if mode == "poll":
        a.setblocking(False)
        n = 0
        while True:
            n += 1
            try:
                a.recv(4); break
            except BlockingIOError:
                pass
    else:
        a.recv(4); n = 1
    return mode, n, time.process_time() - c0, time.perf_counter() - t0

for m in ("poll", "block"):
    mode, n, cpu, wall = run(m)
    print(f"{mode:5s} 확인 {n:>9,}회  CPU {cpu:.2f}s  경과 {wall:.2f}s")
```

这是在 Windows 上使用 Python 3.13 运行的结果。轮询模式进行了约 58 万次检查，消耗 CPU 时间 0.98 秒；阻塞模式每次调用仅消耗 0.00 秒 CPU 时间。两者总耗时均为 1.00 秒，等待时间相同，区别在于是否在此期间使用 CPU。具体次数随执行情况而变化。
</details>

## 数据传输：DMA

即使通过中断减少了等待时间，在 PIO 模式下仍需由 CPU 逐字将数据复制到设备。对于大块数据，CPU 会花费大量时间在简单的复制操作上。为此引入了 DMA（直接内存访问）。DMA 引擎是一种专用硬件，能够在无需 CPU 干预的情况下直接在内存与设备之间进行数据传输。

顺序如下：操作系统会告知 DMA 引擎数据位于内存的何处、需要传输多少数据以及应发送至哪个设备。至此部分由操作系统完成，随后的数据传输则由引擎执行。传输结束后，引擎会通过中断进行通知。从 OSTEP 的时间线图来看，在 PIO（程序输入/输出）模式下，当进程 1 进行复制时 CPU 会被占用；而在 DMA 模式下，该时间段内可运行进程 2。

DMA 并非免费。由于设置引擎和处理结束中断需要成本，因此在极小的数据传输场景中，PIO 可能反而更高效。

<details>
<summary>PIO 与 DMA 盈亏平衡点计算（基于假设数值，已执行）</summary>

此处并未测量实际硬件，而是基于以下假设数值进行计算：传输一个单词（8 字节）需要 20 个周期，DMA 设置与中断处理共需 2000 个周期。

```python
BLOCK = 4096
WORD = 8
COPY_CYCLES = 20
SETUP_CYCLES = 2000

dma = SETUP_CYCLES
for size in (64, 512, 4096, 65536):
    p = (size // WORD) * COPY_CYCLES
    print(f"{size:>6}B  PIO {p:>7}  DMA {dma}  ->", "PIO가 유리" if p < dma else "DMA가 유리")
```

结果显示：在 64B 时，PIO 为 160 而 DMA 为 2000（PIO 更优）；在 512B 时，PIO 为 1280 而 DMA 为 2000（PIO 更优）；在 4096B 时，PIO 为 10240 而 DMA 为 2000（DMA 更优）；在 65536B 时，PIO 为 163840 而 DMA 为 2000（DMA 更优）。盈亏平衡点取决于所假设的数值，实际值因设备和 CPU 而异。
</details>

## 总线与地址

总线是 CPU、内存和设备之间用于交换数据与信号的连接通道。根据 OSTEP 中现代系统的图示，CPU 通过内存控制器直接与内存相连，并通过高性能 PCIe 直接连接至显卡；其余设备则需经过由 DMI（Direct Media Interface）连接的 I/O 芯片。在此芯片之下，硬盘通过 eSATA 连接，而键盘、鼠标等低速设备则通过 USB 连接。网络卡或 NVMe 存储设备等高性能设备通常也采用 PCIe 接口。总体而言，速度越快的设备越靠近 CPU，而速度较慢的设备则需经过更远的层级结构中的芯片。

由于使用 DMA 的设备可直接使用内存地址，因此引入了额外的“地址”概念。Linux 内核文档将地址划分为三类：供内核使用的虚拟地址、用于管理如设备寄存器等资源的中断 CPU 物理地址，以及设备在 MMIO（内存映射 I/O）和 DMA 中使用的总线地址。总线地址可能因主机桥接器或 IOMMU（输入输出内存管理单元）的转换而与 CPU 物理地址不同。IOMMU 是一种将设备所见的地址翻译为实际 RAM 地址的设备，简单系统中可能不存在此类组件。

Linux 中的 DMA 映射分为两类：相干映射在驱动初始化时创建并长期使用，使硬件所见内容（CPU 与设备）保持一致，适用于描述符环等需持续同步的结构；流式映射则专为单次传输创建并在完成后释放，常用于网络或文件系统缓冲区。若 CPU 在此期间访问该缓冲区，则需进行同步调用。

## GPU 连接于何处

GPU 同样作为设备连接至总线。不过，在 CUDA 文档的模型中，与 CPU 直接相连的内存称为主机内存（Host Memory），而与 GPU 相连的内存称为设备内存（Device Memory）。程序从 CPU 启动，通过 CUDA API 在两者之间复制数据、执行内核（即在 GPU 上运行的代码），并等待其完成。CPU 与 GPU 可并行运行。在支持的相关系统中，得益于统一的虚拟地址空间，仅凭地址即可判断某块内存属于 GPU 还是系统内存；若使用 Unified Memory（统一内存），运行时或硬件会根据需要自动迁移数据。文档指出，通过 PCIe 或 NVLink 直接读取 CPU 内存的方式，并不能替代将数据放置于合适位置的做法。

综上所述，使用 GPU 时的“数据复制”成本本质上就是经过总线的成本。这也解释了为何将模型部署在 GPU 上可避免每次重复复制数据。关于推理方面的内容，请参阅 [推理优化](#/post/ml-inference)。

## 常见误解

- 使用 DMA 时 CPU 完全不参与：传输本身由引擎执行，但启动时的设置和结束时的中断处理仍由 CPU 完成。
- 中断总是优于轮询：在高速设备或中断密集的场景下，轮询可能更为合适。
- 设备地址与内存地址完全无关：在内存映射 I/O（MMIO）中，设备寄存器会出现在同一地址空间中。
- CPU 所见的物理地址与设备使用的地址始终相同：若存在桥接器或 IOMMU，则两者可能不同。
