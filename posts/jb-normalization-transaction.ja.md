正規化は、同じ事柄が複数の箇所に記載されていることで生じる問題を解決するためにテーブルを分割する作業であり、トランザクションは複数の作業をすべて成功させるか、すべて失敗させるように束ねる作業である。情報処理技術者試験のデータベース分野において、これら 2 つはほぼ毎回出題される。試験日程や受験料については記載せず、必要であれば公式サイトで確認すればよい。

## なぜ正規化が必要なのか

1 つのテーブルに学生、科目、担当教員をすべて含めたと仮定しよう。教員の名前は学生の人数分繰り返して記述されることになる。このような重複から異常現象（anomaly）が発生する。試験ではこれら 3 つを区別して問われる。

| 異常現象 | いつ発生するか | 例 |
| --- | --- | --- |
| 挿入異常 | 望まない値も一緒に存在しなければ挿入できない | 受講生がいない新しい科目は行を作成できない |
| 削除異常 | 1 つの行を削除すると他の情報も同時に消えてしまう | 最後の受講生を削除すると科目情報が消失する |
| 更新異常 | 重複した値の一部だけを修正して矛盾が生じる | 教員名を 2 つの行だけ変更して、1 つの科目に 2 つの名前が現れる |

正規化はこれを防ぐために、関数従属性を基準にしてテーブルを分割するプロセスである。データベースの基本概念については [詳しく → データベース基本とデータモデル](#/post/jb-db-concept) で別途まとめている。

## 関数従属性から

正規形の問題は結局、従属性を読み取れるかどうかにかかっている。A が分かれば B が一意に定まる場合、B は A に関数的に従属しているとされ、A → B と書く。学籍番号 → 名前のように書く。

- 完全関数従属: 基本キー全体を知ることで値が定まる。複合キー（学籍番号、科目）における成績がそうだ。
- 部分関数従属: 複合キーの一部を知るだけで値が定まる。（学籍番号、科目）において学籍番号だけで名前が定まれば、名前は部分従属である。
- 推移関数従属: A → B, B → C なので、A → C が通る経路として成立する。学籍番号 → 学科、学科 → 学科長であれば、学籍番号 → 学科長は推移従属である。

## 正規形の順序

正規形は前の段階を満足した状態に次の条件を追加していく構造である。

| 正規形 | 追加条件 | 排除するもの |
| --- | --- | --- |
| 第 1 正規形 (1NF) | すべての属性が原子値 | 1 つのセルに複数の値 |
| 第 2 正規形 (2NF) | 部分関数従属の排除 | 複合キーの一部に従属する属性 |
| 第 3 正規形 (3NF) | 推移関数従属の排除 | 一般属性を介した従属 |
| BCNF | すべての決定子が候補キーであること | 候補キーではない決定子 |
| 第 4 正規形 (4NF) | 多値従属の排除 | 互いに無関係な多重値属性の組み合わせ |
| 第 5 正規形 (5NF) | 結合従属の排除 | 候補キーを通らない結合従属 |

暗記はこうした。1NF はセル 1 つに値 1 つ、2NF はキーの一部にぶら下がった属性を整理し、3NF はキーではない属性を介する従属を整理し、BCNF は決定子はすべて候補キーでなければならない。

<details>
<summary>例題から見る 2NF と 3NF の分解</summary>

受講（学籍番号、科目、名前、学科、学科長、成績）というテーブルがあり、基本キーが（学籍番号、科目）と仮定しよう。

1. 学籍番号 → 名前、学科 が成立する。これはキーの一部に従属する部分従属である。2NF にするには分割する必要がある。
   - 学生（学籍番号、名前、学科、学科長）
   - 受講（学籍番号、科目、成績）
2. 学生テーブルにおいて 学科 → 学科長 が成立する。学籍番号 → 学科 → 学科長 という推移従属である。3NF にするにはさらに分割する必要がある。
   - 学生（学籍番号、名前、学科）
   - 学科（学科、学科長）

分解する際には、再度結合したときに元のデータがそのまま復元されるようにしなければならない（ロスレス結合）。関数従属性も失ってはならない（従属性保存）。解説する際はこの 2 つの条件を確認する癖をつけること。
</details>

## 非正規化

正規化を多く行うとテーブルが細分化され、照会時に結合が増える。パフォーマンスが問題となる場合、意図的に重複を許容する非正規化を行う。試験では正規化の反対概念である点、照会パフォーマンスを向上させる代わりに整合性をより注意深く扱う必要がある点を問う。物理設計に関する話は [詳しく → DB 物理設計と分散 DB](#/post/jb-physical-design) に続いている。

## トランザクションと ACID

トランザクションは 1 つの論理的な作業単位である。口座振替は出金と入金、両方が完了して初めて意味を持つため、SQL ステートメント 2 つを 1 つに束ねる。この束ね物が守らなければならない 4 つの性質が ACID である。

| 性質 | 意味 | 保証する側 |
| --- | --- | --- |
| 原子性 (Atomicity) | すべて実行されるか、全く実行されない | 回復手法 |
| 一貫性 (Consistency) | 実行前後に制約条件が守られる | 整合性制約 |
| 隔離性 (Isolation) | 実行中の中間結果を他のトランザクションが見られない | 同時性制御 |
| 持続性 (Durability) | コミットした結果は障害があっても残る | ログ |

原子性を SQLite で実際に動かしてみた。残高が 0 未満になる制約をかけ、振替中にその制約を破るようにした。

```python
import sqlite3
c = sqlite3.connect(":memory:", isolation_level=None)
c.execute("create table acct(id integer primary key, bal int check(bal>=0))")
c.execute("insert into acct values(1,1000),(2,0)")
try:
    c.execute("begin")
    c.execute("update acct set bal=bal-300 where id=1")
    c.execute("update acct set bal=bal+300 where id=2")
    c.execute("update acct set bal=bal-900 where id=1")  # 700-900 < 0
    c.execute("commit")
except sqlite3.IntegrityError as e:
    c.execute("rollback")
    print("rollback:", e)
print(c.execute("select * from acct").fetchall())
```

実行すると `rollback: CHECK constraint failed: bal>=0` というエラーが出力され、残高は `[(1, 1000), (2, 0)]` と最初の状態のままです。前述の 2 つの UPDATE が成功したにもかかわらずロールバックされたため、それらも同時に消えてしまいました。これが原子性です。このフローの SQL 構文 (COMMIT, ROLLBACK, SAVEPOINT) は [詳細 → SQL アプリケーション](#/post/jb-sql-basic) で続きます。

## 同時実行制御と隔離レベル

複数のトランザクションが同時に実行されている際に隔離が破れると、このような現象が発生します。

- **更新の喪失 (Lost Update)**: 2 つのトランザクションが同じ値を読み取り、それぞれ修正しますが、片方の結果が上書きされます。
- **ディティリード (Dirty Read)**: コミットされていない他のトランザクションの値を読み取ります。
- **非反復可能読み取り (Non-repeatable Read)**: 同じ行を 2 回読みましたが、その間に他のトランザクションが修正したため値が異なります。
- **ファントムリード (Phantom Read)**: 同じ条件で 2 回照会しましたが、新しい行が生成されたため結果の行数が異なります。

標準の隔離レベルの 4 つの段階と許可される現象は、PostgreSQL ドキュメントの表で確認できます。

| 隔離レベル | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| Read Uncommitted | 許可 | 許可 | 許可 |
| Read Committed | 防止 | 許可 | 許可 |
| Repeatable Read | 防止 | 防止 | 許可 |
| Serializable | 防止 | 防止 | 防止 |

この表は SQL 標準に基づくものであり、実際の製品では異なる実装が行われます。例えば、PostgreSQL は `Read Uncommitted` を指定しても内部では `Read Committed` のように動作し、`Repeatable Read` でもファントムが発生しません。SQLite はデフォルトですべてのトランザクションをシリアライズ可能 (SERIALIZABLE) レベルとしています。試験の解答は標準表を基準にすればよいでしょう。

隔離レベルが高いほど安全ですが、同時に処理できる量が減少します。試験ではこのトレードオフが頻出します。

### 同時実行制御手法

| 手法 | 核心 |
| --- | --- |
| ロッキング | データにロックを掛けてアクセスを制御します。共有 (読み取り)・独占 (書き込み) ロックがあります |
| 2 段階ロッキング (2PL) | ロックを増やす拡張フェーズと、ロックを解放する縮小フェーズに分けます。シリアライズ可能性を保証します |
| タイムスタンプ | 開始時刻の順序で作業順序を決定します |
| 楽観的検証 | まず実行し、コミットの直前に衝突を検証します |
| 多値バージョン (MVCC) | データの複数のバージョンを保持することで、読み取りが書き込みを妨げないようにします |

<details>
<summary>デッドロックと 2PL のまとめ</summary>

2PL はシリアライズ可能性を保証しますが、デッドロック (deadlock) を防ぐことはできません。T1 が A をロックして B を待ち、T2 が B をロックして A を待つ場合、互いに永遠に待ち合わせ状態になります。対策は主に 3 つの方向に整理できます。

- **予防**: 必要なロックを一度に要求するか、リソースに順序を設けます。
- **回避**: 要求ごとにデッドロックが発生する可能性があるか検査し、安全な場合のみ許可します。
- **検出と回復**: 待機グラフにサイクルが生成されたらデッドロックとして扱い、サクリファイスとなるトランザクションを 1 つロールバックします。

SQLite ドキュメントでは、WAL モードで読み取りトランザクションが書き込みへ進もうとする際、その間に他の接続がコミットすると `SQLITE_BUSY_SNAPSHOT` エラーが発生すると記載されています。したがって、書き込みを行う場合は `BEGIN IMMEDIATE` を使用して最初から書き込みロックを取得するよう推奨されています。試験範囲ではありませんが、ロックとスナップショットが実際にどのように見えるかを理解する上で役立ちました。
</details>

## 回復

障害が発生した際、原子性と持続性を保つためにログを使用します。ログにはトランザクション ID、対象データ、変更前の値 (Before Image) と変更後の値 (After Image) が含まれます。

| 手法 | 動作 |
| --- | --- |
| REDO | コミットされたトランザクションをログの後続の値として再度実行します |
| UNDO | コミットされていないトランザクションをログの先行の値に戻します |
| 即時更新 | コミット前でも DB に即座に反映します。障害時には REDO と UNDO の両方が必要になる可能性があります |
| 遅延更新 | コミット時に反映します。通常、REDO だけで十分です |
| チェックポイント | 特定の時点までの反映を確定させており、復旧範囲を縮小します |
| シャドウページング | ログの代わりにページの複製を置き、コミット時に切り替えます |

チェックポイントの問題は、ログを見て「このトランザクションは REDO、あのトランザクションは UNDO」と区別するタイプが多いです。チェックポイント以前にコミットされたトランザクションは既に反映されているため作業が不要で、チェックポイント以後にコミットされたものは REDO、障害時点でコミットできなかったものは UNDO で解決します。

## よく出るパターンと解法順序

- 이상 현상 구분: 삽입·삭제·갱신 중 어느 상황인지 행을 지우고 넣어 보며 확인한다.
- 정규형 판별: 기본키를 먼저 정하고, 종속성을 화살표로 표기한 뒤, 부분 종속 → 이행 종속 → 결정자 순으로 분석한다.
- ACID 짝 맞추기: 원자성은 회복, 격리성은 동시성 제어, 지속성은 로그와 짝지어 외운다.
- 격리 수준 표: 낮은 수준일수록 허용되는 현상이 늘어나는 구조로 표를 빈칸 채우듯 그린다.
- 회복 기법: 체크포인트와 커밋 시점을 선으로 그려 REDO·UNDO 를 구분한다.
