ロードバランサーは、複数のサーバーの前に立ち、流入するリクエストを振り分けると同時に、故障したサーバーには送らないように遮断してくれる装置です。サーバーを増やしてもクライアントが知る必要があるのは単一のアドレスだけである理由就在这里にあります。

## ロードバランサーが行うこと

サーバーが 1 つしかない場合、そのサーバーがダウンするとサービスも同時に停止します。2 つに増やすと、どのリクエストをどのサーバーに送るかを決定する必要があります。この役割を担うのがロードバランサーです。主な業務は大きく 2 つあります。

- リクエストを複数のサーバーに分散させる
- サーバーの状態を確認し、正常なサーバーへのみ送信する

AWS のドキュメントも同様の説明をしています。ロードバランサーはクライアントからのリクエストを受け取り、登録されたターゲット（target）宛てに送ると同時に、ターゲットの状態を継続的に監視しており、異常が検知されればトラフィックを遮断し、正常に戻れば再度送信します。リクエストがサービス全体でどの経路を辿るかは [詳細 → リクエストが通る道のり](#/post/infra-request-journey) で整理されており、ここではその中でロードバランサーの項目に焦点を当てます。

## L4 と L7

ロードバランサーは、どのレイヤー（階層）で動作するかによって分類されます。ネットワークレイヤーの名前が馴染みがない場合は [詳細 → ネットワーク基礎](#/post/cs-network) を先に読むと良いでしょう。

| 区分 | L4 (トランスポートレイヤー) | L7 (アプリケーションレイヤー) |
|---|---|---|
| 観測対象 | IP、ポート、TCP 接続 | HTTP パス、ホスト、ヘッダー、クッキー |
| 分散単位 | 1 つの接続 | 1 つのリクエスト |
| 可能なこと | 接続のみを素早く分散させる | `/api` は A サーバー群、`/img` は B サーバー群といったルールによる分散 |
| AWS の名称 | Network Load Balancer | Application Load Balancer |

AWS ドキュメントの基準では、NLB はプロトコル、送信元 IP・ポート、宛先 IP・ポート、TCP シーケンス番号を用いて flow hash を生成しターゲットを選択し、一度確立した TCP 接続は終了するまで同じターゲットへ送ります。ALB はリスナー規則を優先順で評価してどの規則を使用するかを決定し、その規則のターゲットグループ内でターゲットを選択します。デフォルトのアルゴリズムはラウンドロビンです。

L7 はリクエストの内容を読み取れるため賢く機能しますが、それだけ処理負荷も増えます。どちらが優れているという話よりも、パスごとにサーバーを分ける必要があるかどうかの方が基準となります。接続のみを素早く分散できれば L4 でよく、アドレス規則が必要なら L7 です。

## 分散アルゴリズム

リクエストをどのように分散するかはアルゴリズムによって決まります。nginx のドキュメントに紹介されている方式を基準に整理しました。

| 方式 | 動作 |
|---|---|
| ラウンドロビン | 順番に回して送る（nginx デフォルト） |
| 重み (weight) | サーバーごとに割り当て量を異ならせる。`weight=3` の場合、5 件中 3 件がそのサーバーへ行く |
| 最小接続 (least_conn) | 現在処理中の接続数が最も少ないサーバーへ送る |
| IP ハッシュ (ip_hash) | クライアントの IP でハッシュを生成し、同じユーザーは同じサーバーへ送る |
| 最小時間 (least_time) | 平均応答時間が短くかつ接続数も少ないサーバーを選択する |

ラウンドロビンは単純なため、サーバー性能とリクエストの負荷が似ている場合に適しています。問題は、各リクエストにかかる時間がバラバラな場合です。重いリクエストが特定のサーバーに集中しても、ラウンドロビンはそれを認識せず単に順番を守ります。

### 実際に試してみたもの

違いを目で確認したいという目的で、非常に単純なシミュレーションを作成しました。リクエストは秒間約 60 件流入し、そのうち 5% は 1.5 秒かかる重いリクエストで、残りは 0.02 秒です。サーバー 0 番を他のサーバーより 4 倍遅く設定しました。各サーバーが同時に保持しているリクエスト数の最大値を観測しました。

<details>
<summary>シミュレーションコード (Python で実行して確認)</summary>

```python
import heapq, random, itertools

class RoundRobin:
    def __init__(self, n):
        self.cycle = itertools.cycle(range(n))
    def pick(self, active):
        return next(self.cycle)

class LeastConn:
    def pick(self, active):
        return min(range(len(active)), key=lambda i: active[i])

def simulate(lb, n_servers=3, n_req=3000, seed=1):
    rnd = random.Random(seed)
    active = [0] * n_servers
    done = []  # (finish_time, server)
    peak = [0] * n_servers
    t = 0.0
    for _ in range(n_req):
        t += rnd.expovariate(60)           # 초당 약 60개 도착
        while done and done[0][0] <= t:
            _, s = heapq.heappop(done)
            active[s] -= 1
        s = lb.pick(active)
        active[s] += 1
        peak[s] = max(peak[s], active[s])
        # 요청 처리 시간: 대부분 짧고 가끔 아주 김, 0번 서버는 4배 느림
        dur = (1.5 if rnd.random() < 0.05 else 0.02) * (4 if s == 0 else 1)
        heapq.heappush(done, (t + dur, s))
    return peak

print("round robin peak:", simulate(RoundRobin(3)))
print("least conn  peak:", simulate(LeastConn()))
```

</details>

結果は以下の通りでした。

```
round robin peak: [16, 7, 6]
least conn  peak: [7, 6, 6]
```

ラウンドロビンでは遅い 0 番サーバーにリクエストが 16 件まで蓄積しましたが、最小接続では 7 件で抑えられました。同じサーバー 3 つですが、遅いサーバーを混ぜるとこのような差が出ます。ただしこれは私が任意の数値で動かした玩具モデルであり、実際のサービス数値ではありません。方向性だけを見ていただければ結構です。

なお、AWS Classic Load Balancer は TCP リスナーにはラウンドロビン、HTTP/HTTPS リスナーには最小処理中リクエスト (least outstanding requests) を使用するという記載があります。リクエストが長い場合は接続数を基準にする方式がデフォルトとなる 셈 です。

## ヘルスチェック

どれだけ適切に分散しても、故障したサーバーへ送ってしまっては意味がありません。そのためロードバランサーはサーバーが生きているか継続的に確認します。方法は 2 つに分けられます。

- アクティブ (active): ロードバランサーが定期的に `/health` などのアドレスを直接叩いて確認する
- パッシブ (passive): 実際のリクエストを送信して失敗した場合、そのサーバーを異常と表示する

nginx のオープンソースドキュメントに記載されているのは手動方式です。`max_fails` は `fail_timeout` の時間内に連続して何回失敗すればサーバーを「失敗」とみなすかを決定する値で、デフォルトは 1 です。`max_fails=3 fail_timeout=30s` に設定すると、30 秒以内に 3 回失敗した場合、そのサーバーを 30 秒間停止します。時間が経過すると実際のクライアントリクエストを通じて少しずつ試行し、成功すれば再び稼働しているとみなします。手動方式は、失敗したリクエストが少なくとも一度はユーザーに到達してしまう点が問題です。

ヘルスチェック用のアドレスでどこまで確認するかは悩ましいところです。プロセスが起動しているかどうかだけを確認すると、データベースが切断されても正常と判定され、データベースまで確認するとデータベースを一度揺さぶるだけでサーバー全体が一括して落ちる可能性があります。どちらが正しいか断定するよりも、サービスごとに設定すべき問題のように見えます。

## セッション固定

ログイン状態をサーバーのメモリに保持していると問題が発生します。リクエストが A サーバーから B サーバーへ渡る瞬間に、B はそのユーザーを認識しません。nginx のドキュメントでも、ラウンドロビンや最小接続では同じクライアントが同じサーバーに行くことを保証しないと記載されています。

解決策は 2 つあります。

1. セッション固定 (sticky session): 同じユーザーを同じサーバーに継続して送ります。nginx の `ip_hash` がその一例で、ドキュメントの基準では該当サーバーが使えない場合を除き、同じクライアントは同じサーバーへ向かいます。AWS ALB にも sticky 設定があることが知られています。
2. サーバーをステートレスにします: セッションを Redis などの外部ストレージに置けば、どのサーバーに行っても同じ情報を読み取れます。[詳細 → Redis とキャッシュ](#/post/db-cache-redis) を参照してください。

セッション固定は簡単ですが副作用があります。IP ハッシュを使用すると、企業のような共有 IP の背後にいる多くの人が一つのサーバーに集中し、そのサーバーが落ちるとそこに付着していたセッションが失われます。サーバーの増減が頻繁であればステートレスな方が都合が良いです。この話は [詳細 → オートスケーリングと拡張](#/post/infra-autoscaling) で続きます。

## 複数のゾーンに適用する場合

AWS のドキュメントには、利用可能な領域 (AZ) ごとにロードバランサーノードが生成されるとあります。ALB は少なくとも 2 つの AZ をオンにする必要があります。この際、cross-zone 設定が分散比率を変えます。ドキュメントの例では、A ゾーンにターゲット 2 つ、B ゾーンにターゲット 8 つがある場合です。

| 設定 | A ゾーンの各ターゲット | B ゾーンの各ターゲット |
|---|---|---|
| cross-zone オン | 10% | 10% |
| cross-zone オフ | 25% | 6.25% |

各ノードがクライアントトラフィックの 50% をそれぞれ受け取る状態において、オフにすると自分のゾーン内でのみ分割するため、ターゲットが少ないゾーンのサーバーがより多くのリクエストを受け取ります。ドキュメントの基準では ALB はロードバランサーレベルで常にオンになっており、NLB はデフォルトでオフになっています。

## よくある誤解

- ロードバランサーを置けば高可用性が自動的に生まれると思われがちです。ロードバランサー自体が単一の場合、そこが単一障害点 (SPOF) になります。AWS はロードバランサーノードを複数の AZ に配置することでこの問題を軽減すると説明しています。
- ラウンドロビンであれば負荷が均等に分かれると思われがちです。リクエストの数は選別しますが、リクエストの重みは選別しません。上記のシミュレーションはその例です。
- ロードバランサーがあれば速度が速くなると思われることもあります。サーバーを複数台使えるようにするだけであり、1 つのリクエストの処理時間はそのままです。片寄りを防げば遅延を減らすことはできますが。
- ロードバランサーとレートリミットは別のものです。リクエストを分割することと、過剰なリクエストを防ぐことは別であり、後者は [詳細 → レートリミットとトラフィック制御](#/post/infra-rate-limit) で扱います。
