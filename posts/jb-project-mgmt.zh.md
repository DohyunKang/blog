项目管理部分看似范围广泛，但考试中主要涉及几类计算问题：进度管理对应 CPM 和 PERT，成本管理对应 COCOMO，人员管理对应布鲁克斯定律（Brooks's Law），运营管理对应 ITIL 术语。考试日程和报名费请查阅官方网站，此处仅整理核心概念与解题步骤。

## 先看整体框架

| 问题 | 工具 | 解法 |
|---|---|---|
| 需要多长时间？ | CPM | 沿前驱关系寻找最长路径 |
| 不知道活动耗时 | PERT | 利用乐观、最可能、悲观三个值计算期望值 |
| 人力成本多少？ | COCOMO | 将代码规模（KLOC）代入公式 |
| 增加人手能加快吗？ | 布鲁克斯定律 | 沟通路径数量会增加 |
| 如何运营服务？ | ITIL | 包括事件、问题、变更等管理活动 |

若衡量规模的输入值（需求）发生波动，这些计算结果也会随之变化。前一步骤承接自 [需求确认与分析](#/post/jb-requirements)。

## 进度：CPM

CPM（关键路径法）将活动间的前驱关系绘制成图，并将最长路径定为关键路径。关键路径上的活动浮动时间（float, slack）为 0，任何一天的延误都会导致整体进度推迟；非关键路径上的活动则存在浮动时间。

计算需进行两次遍历：

1. **正向计算**：从前往后，求出每个活动的最早开始时间（ES）和最早结束时间（EF = ES + 持续时间）。若有多个前驱活动，取结束最晚的那个作为基准。
2. **反向计算**：从后往前，以项目总结束时间为起点，逆推最迟结束时间（LF）和最迟开始时间（LS = LF - 持续时间）。若有多个后续活动，取开始最早的那个作为基准。
3. **浮动时间 = LS - ES**。若为 0，则该活动属于关键活动。

例如，选取 6 个活动进行手动演算。括号内为持续时间（天），箭头前方为前驱活动。

| 活动 | 持续时间 | 前驱 |
|---|---|---|
| A | 3 | - |
| B | 4 | A |
| C | 2 | A |
| D | 5 | B, C |
| E | 3 | C |
| F | 2 | D, E |

```python
tasks = {"A": (3, []), "B": (4, ["A"]), "C": (2, ["A"]),
         "D": (5, ["B", "C"]), "E": (3, ["C"]), "F": (2, ["D", "E"])}
es, ef = {}, {}
for t in tasks:                       # 전진
    d, pre = tasks[t]
    es[t] = max([ef[x] for x in pre], default=0)
    ef[t] = es[t] + d
end = max(ef.values())
ls, lf = {}, {}
for t in reversed(list(tasks)):       # 후진
    succ = [s for s in tasks if t in tasks[s][1]]
    lf[t] = min([ls[s] for s in succ], default=end)
    ls[t] = lf[t] - tasks[t][0]
for t in tasks:
    print(t, es[t], ef[t], ls[t], lf[t], "여유", ls[t] - es[t])
print("전체", end)
# A 0 3 0 3 여유 0
# B 3 7 3 7 여유 0
# C 3 5 5 7 여유 2
# D 7 12 7 12 여유 0
# E 5 8 9 12 여유 4
# F 12 14 12 14 여유 0
# 전체 14
```

关键路径为 A-B-D-F，总工期为 14 天。即使活动 C 延迟 2 天、活动 E 延迟 4 天，也不会影响整体进度。考题通常询问“关键路径长度”或“某活动的浮动时间”。

<details>
<summary>解题时常见错误</summary>

- 正向计算中，若有多个前驱活动，应取最大的 EF 值而非求和。上例中 D 的开始时间为 7，是因为 B（7）与 C（5）中取较大者。
- 反向计算中，若有多个后续活动，应取最小的 LS 值。上例中 C 的 LF 为 7，是因为 D（LS 7）与 E（LS 9）中取较小者。
- 可能存在多条关键路径。切勿仅找一条即止，需检查所有浮动时间为 0 的活动。

</details>

## 进度：PERT

当无法确定活动耗时时，PERT 采用三个值进行估算：乐观时间 o、最可能时间 m、悲观时间 p。期望时间 te = (o + 4m + p) / 6，标准差为 (p - o) / 6。整条路径的期望时间为各活动期望时间之和；路径的标准差则为各活动标准差平方和的平方根。

```python
o, m, p = 2, 4, 12
print((o + 4*m + p) / 6)   # 5.0
print((p - o) / 6)         # 1.666...
```

若乐观值为 2、最可能值为 4、悲观值为 12，则期望时间为 5 天。结果偏大是因为悲观侧尾部较长。记忆要点：CPM 将持续时间视为确定值，而 PERT 将其视为概率分布。

## 成本：COCOMO

COCOMO 是基于代码规模估算工作量（人月）的模型。基本（Basic）模型的公式如下：

- 工作量 E = a × (KLOC)^b （人月）
- 开发周期 D = 2.5 × E^c （月）
- 平均人数 P = E / D

系数 a、b、c 因项目类型而异。

| 类型 | a | b | c |
|---|---|---|---|
| 有机型（Organic） | 2.4 | 1.05 | 0.38 |
| 半分离型（Semi-detached） | 3.0 | 1.12 | 0.35 |
| 嵌入型（Embedded） | 3.6 | 1.20 | 0.32 |

即使代码规模同为 10 KLOC，类型不同也会导致结果差异。

```python
for name, a, b, c in (("조직형", 2.4, 1.05, 0.38),
                      ("반분리형", 3.0, 1.12, 0.35),
                      ("내장형", 3.6, 1.20, 0.32)):
    e = a * 10**b
    d = 2.5 * e**c
    print(name, round(e, 1), round(d, 1), round(e / d, 1))
# 조직형 26.9 8.7 3.1
# 반분리형 39.5 9.1 4.4
# 내장형 57.1 9.1 6.3
```

工作量从有机型的 26.9 人月到嵌入型的 57.1 人月相差超过一倍，但开发周期均在 9 个月左右，差异不大。这是因为周期公式中的指数 c 较小，因此工作量增加时周期增长缓慢。考试通常以“10 KLOC 有机型项目的工作量”等形式出题，故优先记忆系数。若无法使用计算器，切勿对 b 指数进行近似估算，而应直接使用题目给定数值。

<details>
<summary>基本·中间·详细模型区分</summary>

基础模型是最简单的形式，仅考虑规模和类型。中间（Intermediate）模型在此基础上乘以努力调整系数（EAF），该系数反映了成本因素（如产品、人力、环境等多项内容）。a·b·c 的用法相同。虽然详细模型以分阶段细化著称，但在考试中，基础模型的公式和系数才是重点。

</details>

还有一个类似的概念是功能点法，即不计算代码行数而是统计功能数量。这仅仅是衡量“规模”的标准不同，“规模 → 努力”的逻辑流程保持一致。

## 人：布鲁克斯法则

布鲁克斯法则指出，在延期的软件项目中增加人力投入反而会导致项目更晚完成。其原因有三：工作无法完全拆分为独立的模块、新加入的成员需要先学习从而占用原有团队成员的时间、人员增加会导致沟通路径迅速增多。n 人之间的沟通路径数量为 n(n-1)/2。

```python
print(10*9//2, 50*49//2)  # 45 1225
```

例如，10 人时有 45 条路径，50 人时则有 1,225 条。考试中常考的问题是“当有 n 人时的沟通路径数量”。

## 服务运营：ITIL

ITIL 是 IT 服务管理的最佳实践集合。第三版以服务生命周期为中心，将内容分为五本关于过程和功能的书籍；第四版（2019）则结合了敏捷、DevOps 和精益理念，范围从仅限于 IT 扩展到了更广泛的非 IT 服务管理领域。考试中会出现区分各项单独管理活动含义的题目。

| 术语 | 一句话解释 |
|---|---|
| 事件管理 (Incident Management) | 快速将服务从故障或中断状态恢复至正常运行 |
| 问题管理 (Problem Management) | 找出事件的根源并防止其重复发生 |
| 变更 (Change) 管理 | 控制变更以管理服务受到的影响。第四版名称为 change enablement |

记住：事件（Incident）对应“先恢复”，问题（Problem）对应“找原因”。变更管理与 [版本控制和构建·部署](#/post/jb-build-release) 中的版本变更控制名称相似容易混淆，但 ITIL 侧重于服务运营视角。

## 常见误区

- CPM 中时间最长的路径是临界路径，而非最短路径。因为最长路径决定了整个项目的工期。
- COCOMO 模型中的努力与工期不成正比。即使将努力翻倍，工期也仅按指数 c 增加。
- “增加人手就能缩短工期”的计算仅在任务可拆分为独立模块时成立，而软件工作通常不符合这一条件。
- 事件和问题是不同的概念：事件重在恢复，问题重在消除根源。
