DB 공부는 테이블과 SQL에서 시작해서, 빠르게 찾는 법, 동시에 쓰는 법, 모양 잡는 법, 다른 종류의 DB, 캐시, 서버를 여러 대로 늘리는 법까지 이어진다. 한 글씩 따로 보면 서로 어디에 붙는지 헷갈려서, 여덟 가지를 한 줄씩만 먼저 적고 더 알고 싶은 건 링크로 넘어가게 했다. 순서는 기본 → 빠르게 → 안전하게 → 모양 → 종류 → 확장 순이다.

## 한눈에 보는 관계

```
관계형 DB (테이블 + 키 + SQL)
 ├─ 읽기를 빠르게   → 인덱스 (DB 안에서 찾는 비용을 줄임)
 ├─ 동시에 써도 안전하게 → 트랜잭션·격리 수준
 └─ 테이블을 어떻게 나누나 → 정규화·모델링
관계형이 아닌 저장 방식 → NoSQL, 임베딩을 담는 벡터 DB
DB까지 가지 않게 → 캐시(Redis)
DB 한 대가 모자랄 때 → 복제·샤딩
```

## 1. 기본

**관계형 DB와 SQL**: 데이터를 표 여러 개로 나눠 담고 키로 잇는 방식과, 그 표에서 행을 꺼내고 바꾸는 언어. 표 두 개와 쿼리 몇 줄이면 기본은 직접 만져 볼 수 있다.
[자세히 → 관계형 DB와 SQL 기본](#/post/db-rdb-sql)

## 2. 빠르게, 안전하게, 알맞은 모양으로

**인덱스**: 값을 정렬해 둔 별도의 구조라서 조건에 맞는 행을 처음부터 훑지 않고 바로 찾는다. 대신 쓸 때마다 같이 고쳐야 해서 어디에 만들지 고르는 게 일이다.
[자세히 → 인덱스](#/post/db-index)

**트랜잭션과 격리 수준**: 여러 쿼리를 전부 되거나 전부 안 되게 묶는 단위가 트랜잭션이고, 동시에 도는 덩어리끼리 서로를 얼마나 보게 둘지 정하는 게 격리 수준이다. 락과 데드락도 여기서 나온다.
[자세히 → 트랜잭션과 격리 수준](#/post/db-transaction)

**정규화와 모델링**: 같은 사실은 한 곳에만 적어 두자는 규칙이고, 1NF~3NF는 그걸 단계로 나눈 것이다. ERD와 반정규화도 같은 글에서 본다.
[자세히 → 정규화와 모델링](#/post/db-normalization)

## 3. 관계형 밖의 저장소

**NoSQL**: SQL을 버린 게 아니라 데이터를 쓰는 모양에 맞춰 저장 방식을 바꾼 것들의 묶음이다. Key-Value, Document, Column, Graph 네 가지 모양이 있고 분산이 끼면 CAP 이야기가 나온다.
[자세히 → NoSQL 종류와 선택](#/post/db-nosql)

**벡터 DB**: 임베딩을 모아 두고 질의와 가까운 것을 빨리 찾아 주는 DB다. 정확도를 조금 내주고 속도를 사는 근사 검색 구조이고, pgvector 같은 선택지와 전용 DB를 비교한다. 임베딩 자체는 [임베딩과 벡터 검색](#/post/ai-embedding), 검색 결과를 LLM에 붙이는 쪽은 [RAG](#/post/ai-rag)에 있다.
[자세히 → 벡터 DB](#/post/db-vector)

## 4. 커지면

**캐시와 Redis**: 자주 읽는 데이터를 가까운 곳에 복사해 두는 것이 캐시이고, Redis는 그 복사본을 키-값으로 들고 있는 서버다. 어려운 건 복사본이 원본과 달라졌을 때 처리하는 쪽이다. 인덱스가 DB 안의 탐색 비용을 줄인다면 캐시는 아예 DB에 가지 않게 한다.
[자세히 → 캐시와 Redis](#/post/db-cache-redis)

**복제와 샤딩**: DB 한 대로 버티다 한계가 오면 읽기는 같은 데이터를 여러 대에 복사하는 복제로, 쓰기와 용량은 데이터를 쪼개는 샤딩으로 나눈다. 나눌수록 일관성과 편의를 내놓게 된다.
[자세히 → 복제와 샤딩](#/post/db-scaling)

## 어디서부터 읽나

처음이면 위에서 아래로 읽으면 된다. 이미 SQL은 아는 상태에서 서비스가 느려진 경우라면 인덱스 → 캐시 → 복제와 샤딩 순서가 문제 푸는 순서와 비슷하다. 데이터를 어떻게 쪼갤지 고민이면 정규화와 NoSQL을 같이 보면 비교가 된다.
