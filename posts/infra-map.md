서비스를 운영하다 보면 로드밸런서, CDN, 캐시, 레이트 리밋, 오토스케일링 같은 말이 한꺼번에 나온다. 전부 요청이 사용자에게서 DB까지 가는 길 어딘가에 놓인 장치라서, 그 길을 기준으로 한 줄씩만 먼저 적었다. 더 알고 싶은 건 아래 링크로 넘어가면 된다.

## 한눈에 보는 관계

```
사용자 → DNS → CDN(엣지 캐시) → 로드밸런서 → 앱 서버 → 캐시 → DB
                                   ↑               ↑
                          레이트 리밋(문 앞에서 제한)   오토스케일링(서버 수 조절)
앱 서버 → (LLM API를 부르는 서비스라면) 큐·캐시·타임아웃을 한 겹 더
```

## 1. 먼저 전체 길 보기

**요청 하나가 거치는 길**: 주소창에 엔터를 치면 DNS부터 DB까지 여러 군데를 거치는데, 느린 곳은 대개 한두 군데라서 어디서 시간이 새는지 먼저 봐야 한다.
[자세히 → 요청 하나가 거치는 길](#/post/infra-request-journey)

## 2. 앞에서 받아 나누기

**CDN과 캐싱 계층**: 원본 서버의 응답을 사용자 가까운 곳에 복사해 두는 캐시. 복사본을 언제까지 믿을지를 `Cache-Control` 헤더로 정하는 게 실제로 신경 쓸 일이다.
[자세히 → CDN과 캐싱 계층](#/post/infra-cdn-cache)

**로드밸런서**: 서버 여러 대 앞에서 요청을 나눠 주고 죽은 서버로는 보내지 않게 막아 준다. 나누는 방식보다 죽은 서버를 얼마나 빨리 빼느냐가 더 중요해 보였다.
[자세히 → 로드밸런서](#/post/infra-load-balancer)

## 3. 몰릴 때 버티기

**레이트 리밋과 트래픽 제어**: 서버가 감당 못 할 요청을 문 앞에서 돌려보내는 장치. 어떤 알고리즘으로 세느냐에 따라 버스트를 받아 주기도 하고 경계에서 뚫리기도 한다.
[자세히 → 레이트 리밋과 트래픽 제어](#/post/infra-rate-limit)

**오토스케일링과 확장**: 서버를 늘리는 방법은 수직·수평 두 가지고, 자동으로 늘리려면 서버가 상태를 들고 있지 않아야 한다.
[자세히 → 오토스케일링과 확장](#/post/infra-autoscaling)

## 4. AI 서비스라면
