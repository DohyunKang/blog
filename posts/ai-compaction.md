컴팩션은 창이 차 가는 대화를 요약으로 바꿔 끼우는 것이고, 메모리는 요약에서 빠져도 되돌릴 수 있게 창 밖에 적어 두는 것이다. 둘은 경쟁하는 게 아니라 같이 쓰는 쪽에 가까웠다.

## 컴팩션이 뭔지

모델은 한 번에 볼 수 있는 양이 정해져 있다. [컨텍스트 윈도우](#/post/ai-context-window)가 그 크기다. 그런데 모델은 상태를 기억하지 못해서 매 요청마다 지금까지의 대화를 다시 보내야 한다([자세히 → 세션과 대화 기록](#/post/ai-session)). 대화가 길어지면 보낼 양이 늘고, 언젠가 창이 찬다.

컴팩션(compaction)은 이때 오래된 턴을 요약 하나로 바꿔서 창을 비우는 방법이다. Anthropic 문서는 컴팩션을 "오래된 턴을 서버에서 Claude가 쓴 요약으로 대체하는 것"이라고 설명한다. 요약 코드를 직접 짤 필요가 없다는 점이 강조된다. 이유도 적혀 있다. 대화가 길어질수록 응답 품질이 떨어지니까 활성 컨텍스트를 작게 유지하려는 것이다. 왜 품질이 떨어지는지는 [컨텍스트 글](#/post/ai-context)에 정리해 뒀다.

쉽게 말하면 회의록 쓰기와 비슷하다. 세 시간짜리 회의를 처음부터 다시 읽을 순 없으니 결정 사항만 한 장으로 적고 그 한 장으로 회의를 이어 간다.

## 컴팩션이 도는 방식

Anthropic 문서에서 확인한 방식은 세 갈래다.

| | 누가 시점을 정하나 | 특징 |
|---|---|---|
| 요청 시 컴팩션(on demand) | 내 앱이 요청을 보낼 때 | 요약 블록을 받아 `messages` 맨 앞에 넣는다. 최근 턴은 원문 그대로 남길 수 있고, 백그라운드로 돌릴 수도 있다 |
| 토큰 임계값 컴팩션(threshold) | API가 입력 토큰이 정해 둔 기준에 닿을 때 | 일반 요청에 파라미터 하나만 붙이면 된다. 요약은 그 요청 안에서 돈다 |
| 직접 만든 요약기 | 내 코드 | 요약 호출·프롬프트·기록 다시 쓰기를 전부 내가 한다 |

문서는 되도록 요청 시 컴팩션을 쓰라고 권한다. 두 방식 모두 문서에 베타로 표시돼 있고, 요청 시 컴팩션은 베타 헤더 `compact-2026-09-04`와 최상위 `compaction` 파라미터를 쓴다. 이 숫자와 이름은 바뀔 수 있어서 쓸 때 문서를 다시 봐야 한다. 요약 프롬프트를 내가 직접 쓸 수도 있다는 항목이 있는데, 기본 요약이 뒤에 필요한 걸 빠뜨릴 때 쓰라고 한다.

## 요약에서 뭘 남기나

컴팩션을 잘하는 건 요약을 짧게 쓰는 게 아니라 뭘 남길지 고르는 일이다. Anthropic 엔지니어링 글은 이렇게 적는다.

- 남기는 것: 설계 결정, 풀리지 않은 버그, 구현 세부. Claude Code는 최근에 연 파일 다섯 개도 같이 가져간다.
- 버리는 것: 중복된 도구 출력과 메시지. 이미 한참 전에 부른 도구의 원본 결과는 다시 볼 일이 거의 없다.
- 튜닝 순서: 먼저 놓치는 게 없도록 재현율을 최대로 하고, 그다음에 쓸데없는 걸 쳐 내며 정밀도를 올린다.

글에는 가장 가벼운 형태의 컴팩션으로 "도구 결과 지우기(tool result clearing)"가 나온다. 요약하지 않고 오래된 도구 결과만 규칙으로 지운다. 문서에는 이걸 따로 [컨텍스트 편집(context editing)](https://platform.claude.com/docs/en/build-with-claude/context-editing)이라는 기능으로 두고, 컴팩션과 구분해 설명한다. 이 기능 쪽은 이번에 열어 보지 않았다.

## 메모리: 창 밖에 적어 두기

컴팩션은 한 번 요약하면 빠진 건 돌아오지 않는다. 그래서 중요한 것은 아예 창 밖에 적어 둔다. Anthropic 글은 이걸 구조화된 노트(structured note-taking, 에이전트형 메모리)라고 부른다. 에이전트가 주기적으로 창 밖 메모리에 노트를 쓰고 나중에 다시 불러온다. 예로 Claude Code의 할 일 목록, 직접 만든 에이전트의 NOTES.md, 그리고 Claude가 포켓몬을 하며 컨텍스트가 리셋돼도 훈련 진행과 전략 메모를 이어 간 사례가 나온다.

Anthropic이 제공하는 메모리 도구(memory tool)는 이걸 파일 기반으로 해 준다. 문서에서 확인한 구조는 이렇다.

- Claude가 `/memories` 디렉터리의 파일을 만들고 읽고 고치고 지운다. 명령은 `view`, `create`, `str_replace`, `insert`, `delete`, `rename`이다.
- 클라이언트 쪽 도구라서 Claude는 요청만 하고, 실제 파일 처리는 내 앱이 한다. 저장 위치(디스크, DB 등)와 보관 정책도 내가 정한다.
- 메모리 도구가 있으면 API가 시스템 프롬프트에 "작업 전에 먼저 메모리 디렉터리를 본다", "컨텍스트가 언제든 리셋될 수 있다고 가정하라"는 지시를 자동으로 넣는다.
- 경로 조작(`../`)을 막는 검증은 내가 직접 구현해야 한다고 경고한다.

메모리 문서는 컴팩션과 같이 쓰는 걸 권한다. 컴팩션은 클라이언트 관리 없이 활성 컨텍스트를 작게 유지하고, 메모리는 요약을 거쳐도 남아야 하는 정보를 보존한다는 역할 분담이다.

이렇게 쓰면 [RAG](#/post/ai-rag)와 비슷해 보이는데, 결이 다르다. RAG는 외부 문서에서 관련 조각을 찾아 [임베딩](#/post/ai-embedding) 검색으로 넣어 주는 쪽이고, 여기서 말하는 메모리는 에이전트가 자기 작업을 스스로 적어 두는 쪽이다. 메모리를 검색 DB에 넣는 구현도 가능하겠지만 이번에 읽은 문서에서는 파일 방식만 확인했다.

## 트레이드오프

| | 컴팩션 | 메모리(노트) |
|---|---|---|
| 잘 맞는 일 | 주고받음이 많은 대화형 작업 | 마일스톤이 있는 반복 개발 |
| 장점 | 대화 흐름이 이어진다 | 적은 부담으로 오래 남는다 |
| 위험 | 지나치게 공격적이면 사소해 보이지만 중요한 맥락이 사라진다 | 뭘 적을지, 낡은 노트를 어떻게 정리할지를 관리해야 한다 |

엔지니어링 글 자체는 노트 방식의 단점을 따로 적지 않는다.

긴 작업에서는 이 방법들을 섞어 쓴다. 하위 에이전트에게 좁은 일을 맡기고 요약만 받는 방법도 있다([자세히 → 서브에이전트](#/post/ai-subagent)). 이 루프를 돌리고 컴팩션 시점과 메모리 읽기·쓰기를 실제로 실행하는 쪽이 [하네스](#/post/ai-harness)다.

## 흔한 오해

- 컴팩션하면 원본이 어딘가 남는다: 요약으로 바꿔 끼운 뒤 내 쪽 기록에서 원문을 지우면 모델은 요약만 본다. 원문을 따로 저장해 둘지는 앱이 정한다.
- 메모리는 모델이 알아서 쌓아 둔다: 메모리 도구는 클라이언트 구현이 있어야 돌아간다. 저장소가 없으면 기억도 없다.
- 컨텍스트가 크면 컴팩션이 필요 없다: 창이 커도 품질과 비용 문제는 남는다. [프롬프트 캐싱](#/post/ai-prompt-caching)은 요금만 줄이고 자리는 그대로다([컨텍스트 글](#/post/ai-context) 참고).
- 컴팩션과 컨텍스트 편집은 같은 것: 전자는 요약, 후자는 규칙으로 특정 도구 결과·생각 블록을 지운다.

<details>
<summary>자세한 풀이: 요청 시 컴팩션 흐름</summary>

문서의 목차에서 읽은 순서를 정리하면 이렇다. ① 요약을 요청한다 ② 받은 요약 블록을 `messages` 맨 앞에 두고 요약된 메시지를 대신한다 ③ 이후 요청은 그 블록부터 이어 간다. 대화가 다시 길어지면 컴팩션 블록으로 시작하는 대화를 한 번 더 요약할 수 있다("compact again").

최근 몇 턴을 원문 그대로 남기는 옵션도 있다. 요약이 오래된 부분만 맡고 마지막 몇 턴은 그대로 가는 방식이다. 백그라운드 컴팩션은 대화를 멈추지 않고 요약 요청을 따로 돌리다가 완료되면 블록을 끼워 넣는다. 생각(thinking) 블록을 다시 보내는 경우 보존된 생각과의 호환 조건이 따로 있다.

각 하위 페이지(keep-recent-turns, background, thinking-blocks)는 이번에 열지 않았고, 개요 페이지의 설명만 읽었다.
