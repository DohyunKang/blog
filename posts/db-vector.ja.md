ベクター DB は埋め込みベクトルを保存しておき、照会ベクトルと最も近いもの k 個を素早く抽出するデータベースです。通常の DB が「値が同じ行」を探すのであれば、ベクター DB は「値が似ている行」を探します。

## 何を保存するか

保存するのは数値の配列です。文章一つを埋め込みモデルに入力すると数百〜数千個の数値リストが出力され、これを本文 ID や出典などの付加情報（メタデータ）と一緒に格納しておきます。埋め込みとは何かについては [詳しく → 埋め込み](#/post/ai-embedding) を参照してください。

用途のほとんどは検索です。質問を埋め込んで類似した文書断片を見つけ、それを LLM に添付する RAG が代表的な例です。[詳しく → RAG](#/post/ai-rag)

## 全部比較してもダメなのか

データ量が少なければ可能です。照会ベクトルを保存された全ベクトルと一つずつ比較して得点順に切り取れば正確です。これを全件探索 (brute force, exact search) と呼びます。問題は、データ量に比例して遅くなる点です。

メモリも考慮する価値があります。1536 次元のベクトルを float32(4 バイト) で保存すると一つあたり約 6KB となり、100 万個だと約 6GB です (計算値)。インデックス構造は別途さらに容量を使います。ベクターが数十万個程度で照会も間欠的であれば全件探索でも十分という話をよく見かけます。「十分」の限界はハードウェアや次元によって異なるため、実際に確認する必要があります。

## 近似最近傍探索 (ANN)

データ量が増えるとインデックスを作成します。ベクターインデックスは正確に最も近いものを保証せず、「ほぼ近いもの」をはるかに速く見つけます。これを近似最近傍探索 (Approximate Nearest Neighbor, ANN) と呼びます。通常の DB インデックスは結果が正確であるという前提ですが ([詳しく → インデックス](#/post/db-index))、ベクターインデックスは最初から精度の一部を犠牲にして高速化するという点で異なります。

精度は再現率 (recall) で測定します。本当に近い上位 10 件中、インデックスが何個見つけたかの比率です。再現率 0.95 は 10 件中平均 9.5 件正解という意味です。

代表的な手法は二つあります。

| | IVF(IVFFlat) | HNSW |
|---|---|---|
| アイデア | ベクトルをクラスタ（リスト）に分割し、照会与近いクラスタ数個のみ走査する | 層状に積み重ねた近傍グラフで上層から大きく → 下層へ絞り込む |
| 作成方法 | データがある状態でクラスタを作成する (学習段階) | 空のテーブルでも作成可能 |
| 速度・再現率 | 相対的に低い | 相対的に高い |
| ビルド時間・メモリ | 少ない | 多い |

上記表の pgvector に関する比較は pgvector README の説明を翻訳したものです。HNSW は 2016 年の Malkov & Yashunin の論文で登場し、緑色の基準（※注：原文の「緑色」は文脈に依存する可能性あり）に従うと上層から開始する探索と距離規模別のリンク分離により探索コストが対数規模で増加するとされています。跳び越しリスト (skip list) に似ているという説明もあります。

### IVF を自作してみる

原理が理解しにくかったので numpy で玩具を作成して試しました。64 次元ベクトル 2 万個を 100 クラスタに分割し、照会ごとに近いクラスタ `probes` 個のみ走査します。

```python
import numpy as np
rng = np.random.default_rng(0)
N, D, K, C = 20000, 64, 10, 100
centers = rng.normal(size=(C, D))
X = centers[rng.integers(0, C, N)] + 0.5 * rng.normal(size=(N, D))
X /= np.linalg.norm(X, axis=1, keepdims=True)
Q = X[rng.choice(N, 200, replace=False)] + 0.1 * rng.normal(size=(200, D))
Q /= np.linalg.norm(Q, axis=1, keepdims=True)

def exact(q):                       # 전수 탐색: 전부 비교
    return np.argsort(-(X @ q))[:K]

# k-means로 군집 만들기 (10번만 반복)
cent = X[rng.choice(N, 100, replace=False)].copy()
for _ in range(10):
    lab = np.argmax(X @ cent.T, axis=1)
    for c in range(100):
        m = X[lab == c]
        if len(m): cent[c] = m.mean(0)
    cent /= np.linalg.norm(cent, axis=1, keepdims=True)
lab = np.argmax(X @ cent.T, axis=1)
lists = [np.where(lab == c)[0] for c in range(100)]

def ivf(q, probes):                 # 가까운 군집 probes개만 훑기
    cs = np.argsort(-(cent @ q))[:probes]
    ids = np.concatenate([lists[c] for c in cs])
    return ids[np.argsort(-(X[ids] @ q))[:K]]
```

実行結果は以下の通りです (自分の PC で直接実行)。

| probes | recall@10 | 平均で走査したベクトル数 |
|---|---|---|
| 1 | 0.95 | 231 / 20000 |
| 3 | 1.00 | 631 / 20000 |
| 10 | 1.00 | 2036 / 20000 |

クラスタ一つだけ走査しても全体の約 1% を見るだけで再現率 0.95 が得られました。データを明確なクラスタにすることで実際の条件よりも容易な状況です。実際のデータからこれが出るとは限らず、`probes` を増やすほど再現率が上がり走査量が増える傾向だけを見ておけばよいです。照会速度については測定していません。

<details>
<summary>pgvector には同じ調整機構はどこにあるか</summary>

pgvector は PostgreSQL の拡張です。README に従ってインデックスは以下のように作成します。

```sql
CREATE INDEX ON items USING hnsw (embedding vector_l2_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX ON items USING ivfflat (embedding vector_l2_ops) WITH (lists = 100);
```

- HNSW: `m`(デフォルト 16)、`ef_construction`(デフォルト 64) はビルド時、`hnsw.ef_search`(デフォルト 40) は照会時の値です。大きく設定すると再現率が上がり速度が低下します。
- IVFFlat: `lists` はクラスタ数です。README では 100 万行までは行数/1000、それ以上は行数の平方根を起点として推奨しています。`ivfflat.probes`(デフォルト 1) は上記玩具の `probes` と同じ役割を果たします。
- 距離演算子: `<->` L2、`<#>` 負の内積、`<=>` コサイン距離。
- インデックスを作成できる次元は `vector` タイプでは 2,000 まで、`halfvec` では 4,000 までです。

</details>

## フィルターが加わると難しくなる

実際のサービスでは、「このユーザーのドキュメントのみ」、「2024 年以降のみ」といった条件が追加されます。ベクターインデックスではこれが思った以上に難しいです。pgvector の README は、近似インデックスにおいてフィルタはインデックス探索後に適用されると説明しています。例えば、条件に合う行が 10% で `ef_search` が 40 の場合、候補 40 つの平均で 4 つしか残りません。これは要求された k 個を満たせないことを意味します。

対処法としていくつかの案が文書に挙げられています。条件に合う行が少ない場合は正確な（全数）探索が適しており、値の種類が少ない場合は部分インデックス、多い場合はパーティショニングを検討すべきとあります。0.8.0 以降では、条件を満たす結果が十分に集まるまでインデックスを継続的に走査する反復スキャン (iterative index scan) も存在します。

Qdrant の文書は別のアプローチです。フィルタリング用のペイロードインデックスを事前に作成しておくと、HNSW グラフにフィルタを考慮したエッジが追加される構造となるため、ペイロードインデックスはデータを投入する前に作成し、後から追加すると HNSW を再構築しなければならないと記載されています。同じ問題を各 DB で異なる方法で解決しています。

<details>
<summary>strict order と relaxed order</summary>

pgvector の反復スキャンには 2 つのモードがあります。`strict_order` は結果を正確な距離順に維持し、`relaxed_order` は順序が少しずれる代わりに再現性が良いです。無限に走査するのではなく、`hnsw.max_scan_tuples`(デフォルト 20,000) で停止します。

</details>

## pgvector か専用 DB か

すでに PostgreSQL を使用しているなら pgvector が最も手間がかかりません。ベクターの隣に通常の列があり、フィルタを SQL で使用でき JOIN も可能で、トランザクションやバックアップもそのまま利用できます ([詳細 → 関係型 DB と SQL](#/post/db-rdb-sql))。サービスの数が増えないことも大きな利点です。

専用 DB(Qdrant, Pinecone, Milvus, Weaviate など) はベクター検索が本業であるため、フィルタリング構造や量子化、分散処理などの機能がベクターに最適化されています。その代わり、1 つのサービスをさらに運用する必要があり、元データ DB とベクター DB の間でデータを同期させる作業が発生します。

私が理解した選択基準は以下の通りです。

| 状況 | 推奨方向 |
|---|---|
| すでに PostgreSQL を使用し、ベクター数が多くない、フィルタ・JOIN が多い | pgvector |
| ベクター数が非常に多く、検索がサービスの核心である | 専用 DB の検討 |
| 数千程度、プロトタイプ段階 | 全数探索やファイルレベルでも十分 |

これは一般的な基準であり、数字の境界はデータとクエリ方式によって異なるため、実際に確認する必要があります。キー値ストレージやドキュメント DB などの他の種類との位置関係は [詳細 → NoSQL](#/post/db-nosql) に、規模が大きくなった際に DB をどのように拡張するかは [詳細 → スケーリング](#/post/db-scaling) にあります。

## よくある誤解

- ベクター DB がないと RAG ができないわけではありません。規模が小さい場合は全数探索でも可能です。RAG を小さく試すのは [詳細 → RAG の自作](#/post/app-rag-build) にあります。
- ベクターインデックスの結果は正確な最近傍ではありません。近似であるため見落としがあり、再現率と速度を同時に見て設定を決定します。
- エンベッディングモデルを変更すると既存のベクターをそのまま使うことはできません。モデルごとに座標系が異なるため、新たにエンベッディングしてインデックスも再作成する必要があります（これは一般的に知られたことで、今回は文書で別途確認しませんでした）。
- ベクター検索がキーワード検索を完全に代替するわけではありません。固有名詞や正確な用語についてはキーワード側の方が適している場合があります。
