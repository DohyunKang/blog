LLM アプリの評価とは、「この答えが良いか」を感覚で判断するのではなく、事前に定められた問題と採点基準に基づいて数値化し、改善のたびに同じ尺度で比較することです。

## なぜ別途評価が必要なのか

通常のコードは入力が同じであれば出力も同じであるため、テストケースが 1 行で済みます。一方、LLM アプリでは答えが毎回少しずつ異なり、「正解」と「不正解」の境界も曖昧です。そのため、プロンプトを 1 行修正して何回か実行し、「まあいいだろう」と進んでしまうことが容易です。

問題は、修正した方が良くなった一方で、別の部分が静かに悪化してしまうケースです。評価が存在しなければ、そのことはユーザーが最初に気づきます。Hamel Husain の記事は、評価を軽視してプロンプトやモデルだけを触る状況を「ハムスター捕獲式な回帰（打って逃げる）」へと繋がると警告しています。評価とは、そのハムスターを目に見えるようにする装置なのです。

## まず成功基準から

Anthropic のドキュメントでは、評価を作成する前に成功基準を定めるよう述べています。良い基準の条件は、具体的で、測定可能で、達成可能であり、アプリの目的に合致していることです。「性能が良い」ではなく、「感情分類が正確である」といったように記述すべきです。通常、1 つの数値だけでは不十分なので、複数の軸を組み合わせて評価します。ドキュメントの例示には、F1 スコア 0.85 以上、無害な出力 99.5%、応答の 95% が 200ms 以内といったものがあります。

この段階で決めるべきことは多岐にわたります。基準がないと、どのような質問を収集すべきか、どの採点器を使用すべきかも定まりません。

## ゴールデンセット

ゴールデンセットとは、入力と「正解または通過条件」をペアにして集めた問題の集合です。評価の骨格であり、ここで品質がほぼ決定されます。

Anthropic のドキュメントで言及されている設計原則は 3 つあります。

- タスクに合わせてください。実際の使用分布に似せるようにし、不自然な入力、長すぎる入力、曖昧な入力、有害な入力などの境界ケースも含めます。
- 可能であれば自動採点できるようにしてください。
- 質よりも量を優先してください。信号がやや弱くても自動採点可能な問題が多い方が、人手で採点する少量の問題よりも優れているという立場です。

問題をどこから入手するかについて、Hamel の記事では LLM を使って合成入力を生成して使用し、新たな失敗が見つかるたびに追加することを推奨しています。実際のログから失敗した事例をゴールデンセットに移すのが最も価値があるように思われます。

## 採点方法の 3 つ

| 方法 | どのように行うか | 向いている場所 | 弱点 |
|---|---|---|---|
| コードによる採点 | 文字列一致、包含関係、正規表現、埋めベクトル類似度、ROUGE などの指標 | 分類、数値・形式の確認 | 表現の多様な記述式回答 |
| LLM による採点 | 他の LLM が基準に基づいてスコアや合格判定を行う | トーン、要約品質、記述式 | 採点器自体が間違える可能性がある |
| 人間による採点 | 人間が直接読み、判断する | 基準策定時、採点器の検証 | 遅く、高価である |

Anthropic ドキュメントの例示評価 5 つは、この表にそのまま当てはまります。ツイート感情分類は正規化された文字列一致、FAQ 一貫性は SBERT 埋めベクトルのコサイン類似度、要約は ROUGE-L、カスタマー対応トーンは LLM が 1〜5 点で評価する方式、医療チャットボットの個人情報検出は LLM が yes/no で答える方式です。

順序は安い方からが正しいです。Hamel もユニットテストのような高速で安価な検査を先に置き、モデルベースの評価はその上に載せるよう述べています。モデル評価から始めるとより高価で遅くても得られるものは少ないからです。

## 小規模での試行

コードによる採点だけでゴールデンセットと回帰確認がどのように動作するか、実際にコードを書いて実行してみました。モデル呼び出しは意図的に偽の関数に置き換えました。評価枠組みの構造を確認したいだけです。

```python
golden = [
    {"id": 1, "q": "환불 기한이 며칠이야?", "must": ["7일"], "must_not": ["30일"]},
    {"id": 2, "q": "배송비는 얼마야?", "must": ["3,000원"], "must_not": []},
    {"id": 3, "q": "오늘 날씨 어때?", "must": ["모르"], "must_not": []},
]

def check(case, out):
    return all(m in out for m in case["must"]) and not any(m in out for m in case["must_not"])

def run(app):
    res = {c["id"]: check(c, app(c["q"])) for c in golden}
    return res, sum(res.values()) / len(res)

r1, s1 = run(app_v1)   # 프롬프트 고치기 전
r2, s2 = run(app_v2)   # 고친 뒤
print("회귀:", [i for i in r1 if r1[i] and not r2[i]])
print("개선:", [i for i in r1 if not r1[i] and r2[i]])
```

偽アプリ v1 は天気に関する質問に対して捏造した回答（「晴れています」）を行い、v2 は天気を知らないと言いつつ返金期限を 30 日と誤ります。実行結果は以下の通りでした。

```
v1 {1: True, 2: True, 3: False} 0.67
v2 {1: False, 2: True, 3: True} 0.67
회귀: [1]
개선: [3]
```

両バージョンのスコアはどちらも 0.67 です。平均値だけを見ると「変化なし」ですが、実際には一つ修正して一つ壊しているのです。そのため、単一のスコアだけでなく、各問題の結果を前バージョンと並べて表示し、回帰（以前は正解だったのに今は不正解になったもの）を別途抽出することが重要だと感じました。

## LLM-as-judge

記述式回答は文字列一致では採点できないため、別の LLM に採点を任せる方式が用いられます。これを LLM-as-judge と呼びます。Zheng 他による論文（MT-Bench, Chatbot Arena）では、GPT-4 などの強力なモデルが人間の嗜好と 80% 以上一致しており、これは人間同士の一致率と同程度であると報告しています。同じ論文の要約では、限界として位置バイアス、長文偏向、自己強化バイアスを名称のみ挙げています。

実務上のガイドラインはドキュメントごとに似通っています。

- 生成したモデルとは別のモデルで評価を行う (Anthropic)。
- 評価者の出力を狭く制限する。数字のみ、または yes/no のみを出させ、評価対象の答えは `<response>` などのタグで囲む (Anthropic)。
- できるだけ高性能なモデルを評価器として使用する (Hamel)。
- 評価器を人間の判断と比較して補正し、定期的に再確認する。評価器自体を管理すべきシステムである (Hamel)。

<details>
<summary>詳細な解説：評価プロンプトの形式</summary>

Anthropic のドキュメントの例を参考にすると、おおよそこのようなテンプレートになります。

```
아래 <response>가 다음 기준을 만족하는지 판단해라.
기준: 환불 기한을 정확히 말하고, 정책에 없는 약속을 하지 않는다.
<response>
{{답변}}
</response>
yes 또는 no만 출력해라.
```

yes/no のように二値で開始させる方が管理しやすいです。Hamel も当初は単純な「良い/悪い」ラベルから始め、細かいスコアを扱うのは難しいと述べています。5 点評価尺度を使えば、3 点と 4 点の境界が曖昧になり、評価器同士でも人間同士でも意見が割れます。

評価器が正しいか確認するには、人間がラベル付けした少数の事例に評価器を適用して比較します。Hamel は不均衡なデータにおいて単純な一致率や精度はマイノリティクラスの失敗を見逃すため、精密度と再現率を見るよう推奨しています。例えば悪い答えが 5% のみで、すべて「良い」と判定しても 95% は正解になります。

</details>

## 評価を回すタイミング

評価は一度作るだけで終わるのではなく、変更するたびに実行する必要があります。プロンプト、モデルバージョン、検索設定（[RAG を自作する場合](#/post/app-rag-build) のチャンクサイズや top-k など）、ツール定義が変われば実行します。この反復がリグレッションテストです。コード変更ごとに自動で実行できる部分（形式チェック、禁語チェック）と、時間がかかってデプロイ前までには実行する部分（LLM 評価、人間確認）を分けるのが現実的です。

モデルベースの評価は呼び出しごとにコストがかかるため、ゴールデンセットが大きくなるほど評価コストもアプリの原価の項目の一つになります。この部分は [AI サービスの原価](#/post/app-cost) で続けます。

## 何を測るか

| 見たいもの | 測定方法の例 |
|---|---|
| 正解が決まっているタスク（分類、抽出） | 精度、F1、完全一致率 |
| 形式 | JSON パース成功率、スキーマ通過率（[構造化出力](#/post/ai-structured-output) を参照） |
| 生成 | 根拠文書にない主張の割合（[ハルシネーション](#/post/ai-hallucination) を参照） |
| セーフティ | 拒否すべき入力に対する拒否率、流出試行のブロック率（[ガードレール](#/post/app-guardrails) を参照） |
| 応答速度 | レイテンシ分布 |
| コスト | リクエストあたりのトークン数、リクエストあたりの金額 |

一つの数字にまとめず、軸ごとに個別に見ます。上記の実験のように平均に隠れてしまうものがあるためです。

## よくある落とし穴と誤解

- 感覚だけで確認すること。Hamel が最初の落とし穴として挙げるのがこれです。
- 自社の製品の失敗様式とは無関係な汎用評価ツールやスコアに依存すること（同じ記事）。
- 自動評価が人間レビューを代替するという信念。Hamel は「人を排除できる」というツールの主張には懐疑的であり、データを継続して読むよう促しています。学ぶことがなくなるまで読むのが止まる基準だと言います。
- 合格率 100% を目標とするという信念。許容失敗率は製品が決める分だという立場です。
- ゴールデンセットに簡単な問題しかないという思い込み。スコアは高いのに実際の使用では間違え続けます。
- 評価問題をプロンプトの例示そのままに入れること。これだと評価が試験漏洩のようになり、スコアの意味を失います。
- 評価を指標数字を上げるゲームにしてしまうこと。数字が上がってもユーザーの不満が変わらなければ、ゴールデンセットは現実を反映できていません。

[プロンプトインジェクション](#/post/sec-prompt-injection) などの攻撃事例は評価問題に別途集めておけば、防御が崩壊したかすぐにわかります。
