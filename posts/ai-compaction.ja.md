コンパクションは、会話のウィンドウが埋まりそうな状態を要約に置き換える仕組みであり、メモリとは要約から除外された内容をウィンドウの外に記録しておき、必要に応じて取り戻せるようにするものです。両者は競合するものではなく、むしろ協調して動作する側面が強いです。

## コンパクションとは何か

モデルは一度に表示できる量が制限されています。その大きさが [コンテキスト ウィンドウ](#/post/ai-context-window) です。しかしモデルは状態を記憶できないため、各リクエストごとにこれまでの対話を再度送信する必要があります（[詳細 → セッションと会話履歴](#/post/ai-session)）。対話が長くなると送信するデータ量が増え、やがてウィンドウが埋まります。

コンパクション (compaction) はその際、古いターンを一つの要約に置き換えてウィンドウを空にする方法です。Anthropic のドキュメントではコンパクションを「サーバー上の古いターンを Claude が作成した要約で置き換えること」と説明しています。要約コードを手動で作成する必要がない点が強調されています。その理由も記載されています。対話が長くなるほど応答品質が低下するため、アクティブなコンテキストを小さく維持しようとするのです。なぜ品質が低下するのかは [コンテキスト記事](#/post/ai-context) にまとめられています。

簡単に言えば会議録の作成に似ています。3 時間の会議を最初から読み直すことはできないので、決定事項だけを 1 ページに書き留め、その 1 ページを持って会議を進めます。

## コンパクションが動作する仕組み

Anthropic のドキュメントで確認した方法は 3 つあります。

| | 誰がタイミングを決めるか | 特徴 |
|---|---|---|
| リクエスト時のコンパクション (on demand) | アプリ側がリクエストを送信する際 | 要約ブロックを受け取り `messages` の先頭に追加します。最新のターンは原文のまま残すことも、バックグラウンドで実行することも可能です |
| トークン閾値コンパクション (threshold) | API が入力トーク数が設定した基準に達した時 | 通常のリクエストにパラメータを一つ追加するだけで済みます。要約はそのリクエスト内で処理されます |
| 自作の要約器 | アプリ側のコード | 要約呼び出し、プロンプト、記録の書き換えをすべて自分で行います |

ドキュメントでは、可能な限り「リクエスト時のコンパクション」の使用を推奨しています。両方の方法はドキュメント上でベータ版として表示されており、リクエスト時のコンパクションはベータヘッダー `compact-2026-09-04` と最上位の `compaction` パラメータを使用します。この番号や名称は変更される可能性があるため、使用前にドキュメントを再確認する必要があります。自作で要約プロンプトを使用する項目もありますが、デフォルトの要約が後続に必要な情報を漏らす場合に使用するとあります。

## 要約では何を残すか

コンパクションを適切に行うことは、要約を短く書くことではなく、何を残すべきかを選択することです。Anthropic のエンジニアリング記事には以下のように記載されています。

- 残すもの：設計決定、未解決のバグ、実装の詳細。Claude Code は最近に開いたファイルも 5 つ一緒に持ち込みます。
- 捨てるもの：重複したツール出力とメッセージ。すでに長時間前に呼び出されたツールの元の結果を再度見ることはほとんどありません。
- チューニング順序：まず見落としがないように再現性を最大化し、次に不要なものを排除して精度を高めます。

記事には最も軽量な形式のコンパクションとして「ツール結果の削除 (tool result clearing)」が挙げられています。要約せず、古いツールの結果だけを規則に基づいて削除します。ドキュメントではこれを [コンテキスト編集 (context editing)](https://platform.claude.com/docs/en/build-with-claude/context-editing) という別機能として扱い、コンパクションとは区別して説明しています。この機能については今回は触れません。

## メモリ：ウィンドウの外に記録する

コンパクションは一度要約すると元には戻りません。そのため重要なのは、そもそもウィンドウの外に記録しておくことです。Anthropic の記事ではこれを「構造化されたノート取り (structured note-taking, エージェント型メモリ)」と呼んでいます。エージェントが定期的にウィンドウ外のメモリにノートを記録し、後で読み返します。例えば Claude Code のタスクリスト、自作エージェントの NOTES.md、そしてポケモンをしながらコンテキストがリセットされてもトレーニングの進行や戦略メモを引き継いだ事例などが挙げられています。

Anthropic が提供するメモリツール (memory tool) はこれをファイルベースに実装しています。ドキュメントで確認した構造は以下の通りです。

- Claude が `/memories` ディレクトリのファイルを生成し、読み込み、修正、削除を行います。コマンドは `view`, `create`, `str_replace`, `insert`, `delete`, `rename` です。
- クライアントサイドのツールであるため、Claude はリクエストのみを行い、実際のファイル処理はアプリ側が行います。保存場所（ディスク、DB など）と保持ポリシーも自分で設定します。
- メモリツールがあれば、API がシステムプロンプトに「作業前にまずメモリディレクトリを確認する」「コンテキストがいつでもリセットされる可能性があると考えてください」という指示を自動的に追加します。
- 相対パス操作 (`../`) を防ぐ検証は自分で実装しなければならないと警告されています。

メモリドキュメントは、コンパクションと併せて使用することを推奨します。コンパクションはクライアント側の管理なしでアクティブなコンテキストを小さく保つ役割を持ち、メモリは要約を行っても保持すべき情報を保存するという役割分担です。

このように使うと [RAG](#/post/ai-rag) と似て見えるかもしれませんが、仕組みは異なります。RAG は外部ドキュメントから関連する断片を検出し、[埋め込み](#/post/ai-embedding) 検索によって投入する一方、ここで言うメモリはエージェントが自身のタスクを自ら記録しておくものです。メモリを検索 DB に格納する実装も可能ですが、今回読んだドキュメントではファイル方式のみを確認しました。

## トレードオフ

| | コンパクション | メモリ (ノート) |
|---|---|---|
| 向いている用途 | 頻繁なやり取りを行う対話型タスク | マイルストーンのある反復開発 |
| 利点 | 対話の流れが維持される | 少ない負荷で長期間保持される |
| リスク | 過剰に攻撃的になると、些細に見えても重要な文脈が失われます | 何を書くべきか、古くなったノートをどう整理するかを管理する必要があります |

エンジニアリング記事自体は、ノート方式の欠点を別に記載していません。

長期的なタスクではこれらの方法を組み合わせて使用します。サブエージェントに狭い範囲の仕事を任せて要約のみを受け取る方法もあります ([詳細 → サブエージェント](#/post/ai-subagent))。このループを回し、コンパクション時点とメモリの読み書きを実際に実行するのは [ハネス](#/post/ai-harness) です。

## よくある誤解

- コンパクションすると元文がどこかに残る：要約に置き換えた後、自らの記録から原文を削除すれば、モデルは要約のみを見ています。原文を別途保存するかどうかはアプリが決めます。
- メモリはモデルが勝手に蓄積する：メモリツールはクライアント側の実装が必要であり動作します。ストレージがないと記憶もありません。
- コンテキストが大きければコンパクションは不要：ウィンドウが大きくなっても品質やコストの問題は残ります。[プロンプトキャッシング](#/post/ai-prompt-caching) は料金を削減するだけでスペースは変わりません ([コンテキスト記事](#/post/ai-context) を参照)。
- コンパクションとコンテキスト編集は同じもの：前者は要約であり、後者はルールに基づいて特定のツール結果や思考ブロックを削除します。

ドキュメントの目次から読み取った順序を整理すると以下のようになります。① 要約をリクエストする ② 受け取った要約ブロックを `messages` の先頭に置き、要約されたメッセージで置換する ③ 以降のリクエストはそのブロックから続きます。対話が再び長くなると、コンパクションブロックから始まる対話を再度要約できます ("compact again")。

最近の数ターンを原文のまま残すオプションもあります。要約は古い部分のみを担当し、最後の数ターンはそのまま流れる方式です。バックグラウンドコンパクションは対話を中断せず、要約リクエストを別途実行して完了するとブロックを挿入します。思考 (thinking) ブロックを再送信する場合は、保持された思考との互換性条件が別途あります。
