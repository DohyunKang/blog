通过调用 LLM API 来提供答案的服务，与普通 Web 服务不同：单个请求可能需要数秒才能完成，偶尔会失败，并且每次调用都会产生费用。因此，在请求路径的中间，通常会叠加一层层机制来处理队列、缓存、流式传输、超时和成本限制等问题。

## 普通 API 与 LLM API 有何不同

正如 [单个请求所经过的路径](#/post/infra-request-journey) 中所述，普通的 Web 请求通常会经过 DNS、CDN、负载均衡器、服务器和数据库，几十毫秒即可完成。如果涉及 LLM，服务器则需要额外等待一个外部 API。这种等待时间往往比其他阶段长得多，因为答案不是一次性生成的，而是逐个生成 token。

用表格来总结两者的差异如下：

| | 普通 API | LLM 调用 |
|---|---|---|
| 耗时 | 几十毫秒 | 几秒到几分钟不等 |
| 响应大小 | 几乎固定 | 随生成内容而变化 |
| 相同输入 | 相同输出 | 通常每次略有不同 |
| 调用成本 | 几乎为零 | 按输入和输出 token 计费 |
| 限制 | 取决于服务器配置 | 由厂商设定的每分钟请求数和 token 限制 |

正如 [什么是 LLM](#/post/ai-llm) 中所述，模型通过不断拼接下一个 token 来工作，因此响应时间会随着输出长度成比例增加。从服务器角度看，这是一个长时间占用单个连接的请求。

## 将结构浓缩在一页

从服务侧常见的分层结构按顺序绘制出来大致如下：

```
사용자
  │  (스트리밍으로 받음)
  ▼
[ 우리 서버 ]
  ├─ 1. 인증·사용자별 한도 확인      ← 내 서비스의 레이트 리밋
  ├─ 2. 캐시 조회                    ← 같은 질문이면 여기서 끝
  ├─ 3. 큐 / 동시 호출 제한          ← 업스트림을 한 번에 너무 못 부르게
  ├─ 4. LLM API 호출                 ← 타임아웃·재시도·스트리밍
  └─ 5. 사용량 기록                  ← 토큰 수, 비용, 요청 ID
```

每一层解决的问题各不相同。下面逐一介绍。

## 1. 限制：厂商限制与自身限制

以 Anthropic 文档为准，Messages API 的限制针对每个模型分别设定，包括每分钟请求数（RPM）、每分钟输入 token（ITPM）和每分钟输出 token（OTPM）。一旦超过其中任何一项限制，就会收到 429 错误；如果响应中包含 `retry-after` 头，则需等待该时间段后再重试。限制机制并非基于固定时间段的 token 桶重置，而是持续填充容量。关于速率限制和流量控制的算法本身，请参考 [速率限制与流量控制](#/post/infra-rate-limit)。

以下是几个值得注意的点：

- 限制取决于组织的使用等级（tier）。文档中有按等级划分的表格，但由于数字随模型和时间变化，此处不再列出。
- 大多数模型中，从缓存读取的输入 token 不计入 ITPM。因此使用缓存可以在相同限制下处理更多内容。
- 并非所有 429 错误都是暂时的。如果达到月度支出上限，会收到相同的 429 `rate_limit_error`，但缺少 `retry-after` 头，且将持续失败直到下个月月初。SDK 的自动重试也无济于事。可通过检查 `error.details.error_code` 是否为 `enforced_spend_limit_reached` 来区分。
- 如果触达自己设定的支出上限，收到的不是 429 而是 400。

因此，服务需要两种类型的限制：一种是避免超过厂商设定的限制，另一种是防止单个用户耗尽自己的配额。后者厂商不会代为处理。

## 2. 缓存：对相同问题不再重复调用

最便宜的调用是不进行调用的情况。响应缓存通过将问题（以及模型和设置）哈希化作为键来存储结果。我们直接沿用 [缓存与 Redis](#/post/db-cache-redis) 的方式，但在 LLM 场景下有一些附加条件：

- 由于相同输入可能产生不同输出，因此仅适用于“可以接受相同答案”的问题，例如 FAQ 类问题、翻译或分类等。
- 包含用户个人信息的响应不会将用户信息加入键中，或者直接不缓存。

这里有一个名称相似但实质不同的概念：厂商提供的提示词缓存（prompt caching）。它不是存储响应，而是复用长提示词前部分的处理结果。根据文档，默认生存期为 5 分钟，每次命中时更新。许多模型的读取单价是基础输入单价的 0.1 倍，写入则是 5 分钟版本的 1.25 倍。只有前缀完全匹配才能命中。详细信息请参考 [提示词缓存](#/post/ai-prompt-caching)。

| | 响应缓存（自有服务器） | 提示词缓存（厂商提供） |
|---|---|---|
| 存储内容 | 完整答案 | 提示词前部分的处理结果 |
| 命中后效果 | 完全不调用 LLM | 仍会调用，但输入单价和限制降低 |
| 条件 | 相同问题 | 前缀在字符级别完全一致 |

## 3. 队列与并发限制

当用户请求突然激增时，上游会瞬间涌出大量请求，导致触发限流。因此，服务端需要限制同时发出的调用数量。简单的做法是使用信号量（Semaphore），更复杂的方案则采用消息队列配合工作线程。这是 [异步处理与消息队列](#/post/be-async-queue) 中讨论的结构，但在 LLM 场景下还有一个额外原因：对于耗时较长的任务，不应试图在请求内部完成，而应将任务放入队列并向用户显示“处理中”，这样更便于连接管理。

Anthropic 也提供了此类用途的 Message Batches API。文档将其介绍为降低长请求中断风险的方法，并说明结果需通过轮询获取。这是一种适合非实时大批量任务的方案。

## 4. 流式传输与超时

LLM 响应通常较长，若等待其完全生成完毕再返回，用户将面临空白屏幕。因此，应设置 `stream: true`，通过服务器发送事件（SSE）接收数据并实时推送。文档中描述的响应顺序为 `message_start`、多个 `content_block_delta` 以及最后的 `message_stop`，中间可能夹杂 `ping` 事件。

流式传输不仅关乎感知速度。文档明确指出，对于超过 10 分钟的长请求或 `max_tokens` 较大的请求，不应使用非流式方式发送，因为网络可能会断开空闲连接。官方 SDK 表示，若非流式请求预计会超过 10 分钟，将在验证阶段予以拦截。

此外还有一点：即使收到 HTTP 200 状态码，仍可能发生错误。文档中的示例显示，事件流中可能出现 `overloaded_error`。此时常规的基于状态码的错误处理机制将失效，因此读取流体的代码必须直接处理 `error` 事件。

超时问题可分为两类看待：建立连接所需的时间，以及获取完整响应所需的总时间。对于流式传输而言，“等待下一片数据片段”的时长是更有意义的参考指标。具体阈值因服务而异，此处不列出具体数值。

## 5. 重试与失败处理

文档中列出的错误代码里，服务器暂时无法处理的包括 429、500、504 和 529。其中 529 表示 API 整体过载，500 则是 Anthropic 内部错误，建议采用指数退避策略进行重试。相反，400、401、403 和 413 表明请求本身存在问题，重新发送不会产生不同结果，因此需要区分哪些情况应重试、哪些不应重试。

官方 SDK 默认会对连接错误、429 及 5xx 错误进行最多 2 次指数退避重试；若响应中包含 `retry-after` 头，则遵循该值等待后再试。可通过 `max_retries` 参数进行调整。若自行实现逻辑，只需遵循上述规则即可；但若在使用 SDK 的同时又在自身代码中包裹重试逻辑，需注意重试次数会成倍增加的问题。

<details>
<summary>详细解析：结合并发限制 + 缓存 + 重试的小型示例</summary>

此处使用一个模拟函数替代真实 API，该函数有 40% 概率抛出过载错误（模拟 529），利用信号量将并发调用限制为 3 个，并集成了响应缓存与指数退避重试机制。代码已直接执行。

```python
import asyncio, random, hashlib

class Busy(Exception): pass

calls = 0
async def fake_llm(prompt):
    """진짜 API 대신 쓰는 가짜. 40%는 과부하, 가끔 느림."""
    global calls
    calls += 1
    await asyncio.sleep(random.choice([0.05, 0.05, 0.05, 0.3]))
    if random.random() < 0.4:
        raise Busy("529")
    return f"answer({prompt})"

cache = {}
sem = asyncio.Semaphore(3)  # 동시에 3개까지만 업스트림으로

async def ask(prompt, retries=4, timeout=0.2):
    key = hashlib.sha256(prompt.encode()).hexdigest()
    if key in cache:
        return cache[key]
    async with sem:
        for n in range(retries + 1):
            try:
                out = await asyncio.wait_for(fake_llm(prompt), timeout)
                cache[key] = out
                return out
            except (Busy, asyncio.TimeoutError):
                if n == retries:
                    return "잠시 후 다시 시도해 주세요"
                await asyncio.sleep(min(2 ** n * 0.05, 1) * random.random())

async def main():
    random.seed(1)
    prompts = ["a", "b", "a", "c", "a", "b"] * 3
    res = await asyncio.gather(*(ask(p) for p in prompts))
    print(len(prompts), "요청 / 업스트림 호출", calls, "/ 캐시 항목", len(cache))
    print(sorted(set(res)))
asyncio.run(main())
```

执行结果如下：

```
18 요청 / 업스트림 호출 40 / 캐시 항목 3
['answer(a)', 'answer(b)', 'answer(c)', '잠시 후 다시 시도해 주세요']
```

共发出 18 次请求，但仅有 3 个不同的问题；而上游调用却达到了 40 次。原因有二：模拟函数频繁失败导致触发重试；同时到达的多个相同问题因缓存中尚无对应值，全部被转发至上游。这种现象被称为“缓存踩踏”（cache stampede）。当前代码并未对此进行防护，若要解决，需引入机制将同一键下的并发调用合并处理。此外，对于已耗尽重试次数的请求，系统会返回提示信息，而这些提示也出现在结果集合中。在实际服务中，此类信息不应存入缓存（上述代码仅缓存成功响应）。

延迟时间与概率均为模拟值，与实际 API 行为无关，本示例旨在验证架构是否有效运作。

</details>

<summary>详细解析：错误代码对照表</summary>

以下是从 Anthropic 错误文档中整理的摘要：

| 代码 | 含义 | 重新发送是否有效 |
|---|---|---|
| 400 | 请求格式或内容问题（包括达到设定的支出上限） | 无效 |
| 401 / 403 | 密钥问题 / 无权限 | 无效 |
| 413 | 请求体过大 | 无效 |
| 429 | 超出限用额度或月度支出上限 | 若存在 `retry-after` 则按该值等待，否则可能无效 |
| 500 | Anthropic 内部错误 | 采用指数退避重试 |
| 504 | 处理超时 | 建议改用流式传输 |
| 529 | API 过载 | 稍后重试 |

所有响应均包含 `request-id` 头，错误正文中也包含 `request_id`。文档建议在与支持团队联系时一并保留这些信息，因此最好将其记录在日志中。

## 6. 成本管控与监控

由于每个请求的 Token 都涉及费用，仅记录服务器上的请求数量是不够的。响应中包含输入和输出 Token 的使用量，因此需要按用户和功能分别记录这些数据，以便追踪成本来源。文档指出，可通过检查响应中的 `cache_creation_input_tokens` 和 `cache_read_input_tokens` 是否非零来判断缓存命中情况。

管控手段大致包括以下几类：

- 由服务直接设置按用户和套餐划分的每日 Token 上限。
- 将简单问题分配给小模型，复杂问题才使用大模型。
- 在控制台中自行降低支出上限（作为防止超过月度上限的安全机制）。
- 将无需实时处理的任务改为批处理执行。

计算成本的方法详见 [AI 服务成本结构](#/post/app-cost)。虽然可通过增加服务器解决某些瓶颈（参见 [自动扩展与扩容](#/post/infra-autoscaling)），但 LLM 调用受限于厂商配额，因此增加服务器数量并不能线性提升处理能力。这一点让我感到与普通服务的最大不同。

## 常见误解

- 遇到 429 错误时只需等待并重试：因月度支出上限导致的 429 错误不会包含 `retry-after` 头，将持续失败。
- 使用流式传输即可通过状态码判断错误：即使收到 200 状态码，流中仍可能出现错误事件。
- 使用了提示词缓存就不需要响应缓存：两者作用机制不同。前者旨在降低输入成本，后者则减少调用次数。
- 增加服务器数量就能提升处理能力：若瓶颈在于厂商配额，则服务器数量无关紧要。
- 设置较大的 `max_tokens` 会消耗更多配额：根据文档，OTPM 仅统计实际生成的 Token。不过，在不使用流式传输时设置较大值可能导致连接问题。
