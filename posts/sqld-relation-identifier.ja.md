SQLD 모델링 과목에서 관계와 식별자는 거의 매 회차 나오는 단원이며, 용어를 "무엇을 기준으로 나눈 이름인지"로 정리해 두면 보기가 달라져도 풀립니다.

## 이 단원에서 나오는 것

엔터티와 속성을 정했으면 그다음은 엔터티끼리 어떻게 이어지는지, 그리고 각 엔터티의 행을 무엇으로 구분하는지입니다. 앞 단원은 [엔터티와 속성](#/post/sqld-entity-attr)에 있고, 모델링 전체 흐름은 [데이터 모델링의 이해](#/post/sqld-modeling)에 있습니다.

| 구분 | 기준 | 나오는 용어 |
|---|---|---|
| 관계 | 몇 개가 이어지나 | 1:1, 1:N, M:N (관계 차수) |
| 관계 | 꼭 있어야 하나 | 필수, 선택 (선택성) |
| 관계 | 부모 PK 가 자식 PK 에 들어가나 | 식별 관계, 비식별 관계 |
| 식별자 | 어떤 역할이냐 | 주식별자, 보조식별자 |
| 식별자 | 어디서 왔냐 | 내부식별자, 외부식별자 |
| 식별자 | 한 컬럼이냐 | 단일, 복합 |
| 식별자 | 원래 있던 거냐 | 본질식별자, 인조식별자 |

시험은 이 표의 각 줄이 "무슨 기준의 분류인지"를 묻는 경우가 많습니다. 기준만 기억하면 낯선 문장도 풀립니다.

## 관계의 기본

관계는 두 엔터티 사이에서 업무상 연결이 있다는 뜻입니다. 사원과 부서처럼 "소속된다"는 동사로 읽히면 관계입니다. 읽는 방향이 둘이라서, 부서 쪽에서는 "부서는 여러 사원을 가진다", 사원 쪽에서는 "사원은 한 부서에 소속된다"로 양쪽에서 문장을 만들어 봅니다. 한쪽 문장만으로는 차수를 잘못 잡기 쉽습니다.

### 관계 차수 (몇 개가 이어지나)

- 1:1 : 한쪽 행 하나에 상대 행이 최대 하나
- 1:N : 한쪽 행 하나에 상대 행이 여러 개, 반대로는 최대 하나
- M:N : 양쪽 다 여러 개

ER 도식에서 쓰는 까마귀발 표기는 선 끝에 동그라미는 0, 세로 막대는 1, 갈퀴는 많음을 뜻합니다. 각 끝에 기호가 두 개 붙는데 안쪽이 최소, 바깥쪽이 최대입니다 ([Wikipedia: Entity–relationship model](https://en.wikipedia.org/wiki/Entity%E2%80%93relationship_model)).

M:N 은 물리 테이블로 바로 만들 수 없어서 가운데에 교차 (연결) 엔터티를 하나 둬서 1:N 두 개로 푹니다. 학생과 수강 과목이 M:N 이면 "수강" 엔터티를 만들고 학생 PK 와 과목 PK 를 가져옵니다. 시험에서 "M:N 관계는 어떻게 해소하나"가 나오면 답은 이 교차 엔터티입니다.

### 선택성 (꼭 있어야 하나)

차수가 최대 개수라면 선택성은 최소 개수입니다. 최소가 0 이면 선택 (optional), 1 이면 필수 (mandatory) 입니다.

- 사원은 반드시 한 부서에 소속된다 : 사원 쪽 필수
- 부서는 사원이 없어도 만들 수 있다 : 부서 쪽 선택

이 선택성이 나중에 FK 컬럼이 NULL 을 허용하느냐로 이어집니다. 필수면 FK 는 NOT NULL, 선택이면 NULL 허용입니다. 아래에서 다시 나옵니다.

## 관계를 읽는 순서

문제에서 관계 문장이 주어지면 이 순서로 읽습니다.

1. 양쪽 방향으로 문장을 만든다.
2. 각 방향의 최대 (하나/여러 개) 를 적는다 → 차수
3. 각 방향의 최소 (없어도 되나/꼭 있나) 를 적는다 → 선택성
4. 자식이 부모 없이 존재할 수 있나 → 식별/비식별 판단으로 넘어간다

<details>
<summary>예: 주문과 주문상품</summary>

- 주문 → 주문상품 : 주문은 상품 줄을 여러 개 가진다 (최대 N). 줄이 하나도 없는 주문은 없다고 보면 최소 1.
- 주문상품 → 주문 : 상품 줄은 반드시 한 주문에 속한다 (최대 1, 최소 1).

그래서 1:N 이고 자식 쪽은 필수다. 주문 없이 주문상품 줄만 있을 수는 없으니, 뒤에 나올 식별 관계 후보가 됩니다. 업무 규칙이 바뀌면 최소 개수도 바뀐다는 점은 기억해 둡니다. "주문은 상품 없이도 먼저 만들 수 있다"면 주문 쪽 최소는 0 입니다.
</details>

## 식별자

식별자는 엔터티 안에서 행 하나를 딱 하나로 가리키는 속성 (또는 속성 묶음) 입니다. 모델링에서는 식별자, 물리 테이블에서는 키라고 부르는 경우가 많고, 시험에서도 이 둘을 같은 흐름으로 다룹니다.

### 주식별자의 조건

주식별자가 되려면 보통 다음 네 가지를 만족해야 한다고 정리합니다.

| 특성 | 뜻 |
|---|---|
| 유일성 | 행마다 값이 달라야 한다 |
| 최소성 | 꼭 필요한 최소한의 속성만 묶는다 |
| 불변성 | 한 번 정해지면 바뀌지 않는다 |
| 존재성 | NULL 이면 안 된다, 반드시 값이 있다 |

특히 불변성이 자주 함정입니다. 전화번호나 이메일은 유일해 보여도 바뀔 수 있어서 주식별자 후보로는 불안합니다. 최소성은 "이미 유일한데 속성을 더 붙이면 안 된다"로 외웁니다.

### 분류 기준별로 나눠 보기

- 代表性（主キー vs 副キー）：他のエンティティとの関係において、主として使用される場合は主キー、行を区別するが主としては使用されない場合は副キーです。
- 自己生成（内部識別子 vs 外部識別子）：自身のエンティティ内で作成されたものは内部、他のエンティティから取得したものは外部です。
- 属性数（単一 vs 複合）：1 つの属性の場合は単一、2 つ以上の場合には複合です。
- 代替の有無（本質的 vs 人工的）：業務で本来使用されていたものは本質的、便宜のために新たに作成されたものは人工的です。

<details>
<summary>本質的識別子と人工的識別子をさらに</summary>

人工的識別子は、シリアル番号のようにシステムが生成した値です。値には業務上の意味がなく変化しないため、FK（Foreign Key）が 1 つの列で終わるという利点があります。一方、値に意味がないため、同じ業務データが重複して入力されても防ぐことができない場合があり、そのため本来の業務キーに対してユニーク制約を別途設けることが多いです。この長所と短所は、surrogate key の説明でも同様の方向で整理されています ([Wikipedia: Surrogate key](https://en.wikipedia.org/wiki/Surrogate_key))。

複合識別子が長くなると、子テーブルに行くほど PK がさらに長くなります。そのため実務では人工的識別子を併用することもありますが、試験ではこれを「複合識別子を単一的人工的識別子に置き換える」と表現します。
</details>

## 識別関係と非識別関係

この単元の核心です。基準は一つ、親の PK が子の PK に含まれるかどうかです。

| 区分 | 親の PK が子で | 子の存在 | ERD の線 |
|---|---|---|---|
| 識別関係 | 子の PK の一部となる | 親が存在しなければ存在しない | 実線 |
| 非識別関係 | 子の一般属性 (FK) となる | 親がなくても可能 | 点線 |

識別関係では、親の PK が子の PK の一部となり、子行は必ず親の一つに接続されます。注文と注文商品が代表的な例として使われます。注文商品は注文番号と行番号を組み合わせて PK とし、注文が存在しなければ存在できません ([Wikipedia: Weak entity](https://en.wikipedia.org/wiki/Weak_entity))。

```sql
-- 식별 관계: 부모 PK(order_no)가 자식 PK에 포함
CREATE TABLE orders (
  order_no INTEGER PRIMARY KEY,
  memo     TEXT
);
CREATE TABLE order_item (
  order_no INTEGER NOT NULL REFERENCES orders(order_no),
  line_no  INTEGER NOT NULL,
  item     TEXT,
  PRIMARY KEY (order_no, line_no)
);

-- 비식별 관계: 부모 PK(dept_id)는 일반 컬럼으로 FK, NULL 허용 = 선택
CREATE TABLE dept (dept_id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE emp (
  emp_id  INTEGER PRIMARY KEY,
  dept_id INTEGER REFERENCES dept(dept_id),
  name    TEXT
);
```

上記の DDL を SQLite で実際に実行しました。存在しない注文番号 (9) で `order_item` を挿入すると外鍵制約違反でブロックされ、`dept_id` が NULL の社員は挿入できました。識別関係では親がなければ子が生まれず、選択的・非識別関係では親なしでも子が可能であることがそのまま確認できます。（SQLite は `PRAGMA foreign_keys=ON` をオンにしないと外鍵をチェックしません。）

### 非識別関係は二つに分かれる

非識別関係では、FK の NULL 許容の有無でさらに分類します。

- 必須的・非識別：FK が NOT NULL、子は必ず親を持つ
- 選択的・非識別：FK が NULL を許容、親がなくても子が存在できる

前述の選択性はここで FK の NULL 可否に変化します。試験では「親なしで子が生成可能」という文句が出れば、選択的・非識別関係と結びつければよいです。

### どっちに分類するか

- 親がなければ子は意味がない（注文と注文商品）：識別関係
- 子が独立して使用され、親を参照するだけ（社員と部署）：非識別関係
- 子が複数の親の PK を持つようになると PK が長くなるため、非識別として扱い人工的識別子を使用する選択肢もあります

<details>
<summary>識別関係を使う際に起きること</summary>

識別関係が複数段階にわたる場合、最下位のエンティティの PK に最上級の親の PK まですべて反映されます。JOIN 時に多くの列を合わせる必要があり、インデックスも大きくなります。逆に、PK を見るだけでどの親の下にあるデータか分かり、親の削除時に子も一緒に整理される業務に適しています。長所と短所の分岐点であり、試験では一つの正解を問うのではなく、「識別関係の特徴」で選択肢を区別させることが多いです。
</details>

## よく出るパターン

| 類型 | 解法方向 |
|---|---|
| 関係の次数を求める | 双方向の文句で最大数を記入する |
| M:N の解消方法 | 交差（接続）エンティティを置き、1:N を二つに分ける |
| 識別子条件の選び方 | 一意性、最小性、不変性、存在性の四つと比較する |
| 識別子の分類区分 | 「どのような基準で分類しているか」から確認する（代表性、生成位置、属性数、代替の有無） |
| 識別/非識別の判断 | 親の PK が子の PK に含まれる場合は識別、一般属性の場合は非識別 |
| ERD の表記 | 実線/点線、カラス足、丸 (0)/棒 (1) の読み取り |

誤りを含む文句を選ぶ問題は、一般的に用語を意図と異なるものに変えて出題されます。例えば「非識別関係では親の PK が子の PK の一部となる」といったように定義そのものを逆転させるようなものです。定義を一文ずつ暗記しておけば回避できます。実際に解く際は、過去問の原文を覚えるよりも、上記の表の基準を文章で説明する方が効果的です。試験日程・受験料は公式サイトで確認してください。

## 混同しやすい点

- 次数と選択性は異なります。次数は「最大」、選択性は「最小」です。
- 識別子と FK は異なります。FK は他のエンティティを指す属性であり、それが PK の一部になると識別関係、または非識別関係となります。
- 人工識別子を設ければ業務キーは不要か？いいえ。業務上で一意である必要がある値はユニーク制約で別途守ります。
- 複合識別子は複数の属性を持ちますが、「最小」の条件も引き続き適用されます。除外しても一意であれば不要な属性です。
