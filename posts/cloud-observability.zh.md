虽然服务器已经成功启动，但要确认“它是否正常运行”，还需要额外的准备工作。这些准备工作包括监控、日志和告警。

## 三种信号

从运行中的系统中可以获取的信息大致分为三类。OpenTelemetry 文档也将这三者称为“信号（signal）”。

| 信号 | 一句话定义 | 回答的问题 |
|---|---|---|
| 指标 (Metrics) | 随时间变化的数值（如请求数、错误率、内存使用量） | 当前状态如何？与平时相比有何不同？ |
| 日志 (Logs) | 每一个发生事件的记录 | 当时发生了什么？ |
| 追踪 (Traces) | 单个请求经过多个服务的路径 | 哪里变慢了？哪里出错了？ |

OpenTelemetry 将追踪定义为“穿过应用程序的请求路径”，指标定义为“运行时测量的值”，日志定义为“事件的记录”。

通常的顺序是这样的：首先由指标图表提示异常，然后通过追踪缩小范围，最后在日志中找到原因语句。数字虽然便宜且快速，但缺乏原因；日志虽有原因，但数量庞大难以查找。因此不能只使用其中一种，而是三者结合使用。

## 指标：该看什么

可选的指标太多，因此需要标准。Google SRE 书中的“四个黄金信号”被引用最多。

| 信号 | 含义 |
|---|---|
| 延迟 (Latency) | 处理单个请求所需的时间。需分别查看成功和失败的情况 |
| 流量 (Traffic) | 进入系统的需求量（如每秒请求数） |
| 错误 (Errors) | 失败请求的比例。不仅包括 HTTP 500，也包括返回 200 但内容错误的情况，或因响应过慢而被视为失败的案例 |
| 饱和度 (Saturation) | 最紧张的资源已使用到何种程度 |

单独关注错误的原因是：快速失败的请求会降低平均延迟，从而让系统状况看起来更好。由于许多系统在达到 100% 饱和度之前性能就会下降，因此建议设定目标利用率。

### 不要只看平均值，要看百分位

仅看平均值会具有误导性。以下代码模拟了 1,000 个请求中，980 个在 100ms 左右完成，20 个耗时 3 秒的场景：

```python
import random
lat = sorted([random.gauss(100, 20) for _ in range(980)] + [3000] * 20)
avg = sum(lat) / len(lat)
p50 = lat[len(lat) // 2]
p99 = lat[int(len(lat) * 0.99) - 1]
print(round(avg), round(p50), round(p99))   # 실행 결과 예: 156 99 3000
```

平均值为 156ms，看似正常，但 p99 高达 3,000ms。这意味着在 50 个请求中有 1 个需要等待 3 秒。p50 是中位数，p99 表示 99% 的请求在此时间内完成。延迟告警应基于 p95、p99 等尾部值，而非平均值。

## 日志：从人类可读转向机器可解析

如果仅以 `print("错误发生")` 这样的文本形式记录日志，后续将无法有效检索。如今通常采用 JSON 等结构化格式，并为每个请求附加唯一 ID。关于在哪个层级捕获错误以及保留哪些内容，详见 [深入探讨 → 错误处理与日志记录](#/post/be-error-logging)。

```python
import json, time, uuid

def log(level, msg, **kw):
    print(json.dumps({"ts": round(time.time(), 3), "level": level,
                      "msg": msg, **kw}, ensure_ascii=False))

rid = "req-" + uuid.uuid4().hex[:6]
log("info", "order created", request_id=rid, user_id=42, took_ms=120)
log("error", "payment failed", request_id=rid, upstream="pay-api", took_ms=3000)
```

执行后每行输出一个 JSON 对象。通过 `request_id` 搜索，可以汇总查看单个请求的完整轨迹。当服务被拆分为多个部分时，需要在各服务间传递此 ID，这正是追踪的基本理念。

日志中需注意三点：

- 不得记录密码、令牌、密钥或个人信息。一旦写入日志，这些信息会被复制到多处。密钥管理详见 [深入探讨 → 秘密与环境变量管理](#/post/cloud-secrets)。
- 区分日志级别。正常流程使用 info，需人工关注的内容使用 error。若全部记为 error，真正的错误将被淹没。
- 控制日志量。日志的存储容量和检索成本直接转化为费用，若每个请求都记录完整正文，账单会很快反映出来。

## 追踪：单个请求的地图

追踪是将单个请求划分为多个段（span），并记录每段耗时。例如，API 服务器调用数据库和外部支付 API 的请求会产生约三个 span，其中哪一段耗时最长一目了然。对于单一服务器的服务，仅靠日志和指标通常已足够；而当服务被拆分为多个部分或涉及无服务器函数时，追踪的价值才真正凸显。关于无服务器的相关内容，详见 [深入探讨 → 无服务器](#/post/cloud-serverless)。

OpenTelemetry 是一个旨在以中立方式标准化这三种信号收集方法的项目。其优势在于：只需在应用程序中集成一次，即使更换数据存储或仪表盘，也无需修改应用代码。

<details>
<summary>两种采集方式（折叠）</summary>

- 拉取 (Pull)：监控服务器定期查询应用程序的指标地址并读取数据。Prometheus 是典型代表。
- 推送 (Push)：应用程序或代理直接向收集服务器发送数据。对于生命周期较短的任务或无服务器架构，这种方式更为自然。

无论哪种方式，应用通常只负责“暴露数字”，而将存储、图表和通知交由专用工具处理。
</details>

## 通知设计

监控中最困难的部分往往不是数据收集，而是通知。通知过多会导致被全部忽略，过少则无法及时获知故障。

Google SRE 书籍与 Prometheus 文档中的共同观点如下：

- 针对症状而非原因发出通知。“CPU 使用率 90%"不如“错误率激增、响应缓慢”更能反映用户实际遇到的问题。即使 CPU 升高，若用户无感知，则无需紧急处理。
- 调用（page）仅在情况紧急且需要人工介入时进行。SRE 书籍指出，若可通过自动化机制处理，则不应发出调用通知。
- 电子邮件通知容易因堆积产生噪音，对于非紧急问题，建议通过仪表盘查看。
- 通知应尽可能精简，仅针对用户受影响的环节。通知中应附带相关仪表盘链接，以便直接查看是哪个组件导致的问题。
- 对短暂波动应给予缓冲时间（仅在条件持续一定时间后才触发）。
- 即使当前尚未影响用户，也应发出容量接近极限的警报，因为这预示着即将发生故障。
- 对于批处理任务，应以超过两次执行周期的时间为基准。若一次失败无需人工干预，则更频繁地重试更为妥当。

同一文档中还提到，监控系统本身也需要被监控。若通知服务器宕机，系统不会安静，而是如同“失明”一般，因此建议额外设置外部探测服务（黑盒检查）来验证其状态。

| 分类 | 白盒 (Whitebox) | 黑盒 (Blackbox) |
|---|---|---|
| 观测位置 | 系统内部（指标、日志） | 用户可见的外部行为 |
| 优势 | 能提前发现即将爆发的故障、揭示被重试掩盖的失败、便于调试 | 反映当前实际未工作的状态 |
| 劣势 | 内部指标繁多易产生噪音 | 无法预测尚未发生的问题 |

通常两者结合使用，调用通知主要针对黑盒和症状层面。

## 发生故障时的基本流程

故障应对的首要任务是减少损害，而非立即寻找原因。以下内容并非来自文档，而是通用的运维流程，具体步骤可能因团队而异。

1. 确认影响范围：谁受影响、受影响的程度、从何时开始出现问题。
2. 检查最近变更：若存在最近的部署或配置更改，回滚通常是最快的解决方案。部署相关操作可参考 [详情 → CI/CD](#/post/cloud-cicd)。
3. 缓解措施：执行回滚、减少流量、增加实例等。原因可在后续分析。
4. 根因分析：从指标中定位时间点，通过追踪（trace）缩小范围，在日志中查找具体语句。
5. 事后复盘：修改通知、测试和文档以防止类似问题重复发生。撰写时应聚焦于改进系统结构，而非指责个人。

关于增加实例的方案，可参考 [详情 → 自动扩缩容](#/post/infra-autoscaling)。

## 常见误区

- 监控（monitoring）与可观测性（observability）并非同一概念。监控是指观察预先定义的指标；可观测性则指即使面对未知问题，也能通过信号进行分析并给出解释的能力。不过不同文档对此定义略有差异，本文仅做简要说明。
- 创建更多指标并不总是有益的。无人查看的图表只会增加成本。
- 拥有仪表盘并不意味着就不需要通知。人类无法全天候盯着屏幕。
- 平均延迟尚可并不代表服务良好，上述代码即为反例。
- 通知越多越安全也是错误的观点。若每次响起都被忽略，则与没有通知无异。
