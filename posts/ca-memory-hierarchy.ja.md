CPU は速いが、メモリは遅い。この差を隠蔽するために、小さな高速な記憶装置を大きな記憶装置の前に重ねて配置したものがメモリエアーシングであり、その中間層がキャッシュとなる。[OS の概要](#/post/cs-os) では仮想メモリとページフォールトについて触れたが、この記事ではそれより下位にあるハードウェア側から同じ問題を扱う。

## 「階層」という形状

上に行くほど速く、小さく、高価である。下に行くほど遅く、大きく、安価である。

| 層 | 大まかな性質 |
|---|---|
| レジスタ | CPU 内部で最も速く、数が非常に少ない |
| L1, L2, L3 キャッシュ | CPU 内外の SRAM で、階層が下がるほど大きくて遅い |
| メインメモリ (RAM) | プログラムが実際にロードされる場所 |
| ディスク (SSD, HDD) | 電源を切っても残る大容量記憶装置 |

レジスタは [CPU と命令](#/post/ca-cpu) で見たように、命令が直接読み書きする場所である。それより下の層はプログラムが直接指定せず、ハードウェアが自動的に埋めたり空にしたりする。そのためコード上ではキャッシュが見えないが、速度には大きく影響する。

## なぜキャッシュが機能するか：局所性

小さなキャッシュが大きなメモリの速度を模倣できるのは、プログラムのアクセスパターンが一様ではないからである。この性質は「局所性 (locality of reference)」と呼ばれる。

- 時間的局所性：一度使用したデータをすぐに再び使う可能性が高い。ループ変数が該当する。
- 空間的局所性：あるアドレスを使用すると、その近傍のアドレスもすぐに使う可能性が高い。配列を先頭から順に走査する場合が該当する。

空間的局所性のため、キャッシュは必要な 1 バイトだけでなく、ブロック単位で取得する。このブロックをキャッシュラインと呼ぶ。ウィキペディアの CPU キャッシュに関する文書では、Pentium 4 と K8 の L1 データキャッシュが 64 バイトのラインを使用していると例示している。以下のシミュレーションも 64 バイトに合わせている。

## ヒットとミス、そして平均アクセス時間

CPU が探しているデータがキャッシュにある場合はヒット (hit)、ない場合はミス (miss) となる。ミスが発生すると下位の層から取得するため時間が掛かる。ヒット率が h の場合、平均アクセス時間は通常以下のように表される。

平均アクセス時間 = ヒット時間 + (1 − h) × ミス時に追加でかかる時間

ヒットを 1 ユニット、ミスを 100 ユニット多くかかると仮定して計算してみた（数字は仮定であり、実際の機械値ではない）。

| ヒット率 | 平均アクセス時間 |
|---|---|
| 99% | 2 |
| 95% | 6 |
| 90% | 11 |

ヒット率がわずか 9%p 低下するだけで、平均時間は 5 倍近く増加した。キャッシュの話において、何パーセントのヒット率に皆が敏感になるのかは、この式にある。

<details>
<summary>平均アクセス時間の計算解説</summary>

ヒット時間 1、ミス追加時間 100 と仮定して Python で計算した。

```python
for h in (0.99, 0.95, 0.9):
    print(h, 1 + (1 - h) * 100)
# 0.99 2.0 / 0.95 6.0 / 0.9 11.0
```

(実際の出力は浮動小数点のため 2.000000000000001 のように表示される。)
</details>

## キャッシュ内の配置方法

メモリアドレスをキャッシュのどの位置に配置するかを決める方式には三種類ある。

- 直接マッピング (direct-mapped)：一つのアドレスが入る場所はただ一つである。単純で速いが、同じ場所を使用するアドレス同士が互いに追い出す可能性がある。
- セット関連 (set-associative)：N の場所のいずれかに入れる。これを N-way と呼ぶ。
- 完全関連 (fully associative)：どの場所でもよい。ミス率は最も良いが、項目が少ない場合のみ現実的である。

ウィキペディアの文書によると、2-way は直接マッピングのキャッシュの 2 倍のサイズと似たヒット率を示し、4-way を超えると効果は小さいという。

書き込みには二つのポリシーがある。書き込み通過 (write-through) はキャッシュに書き込むたびにメモリにも書き込む。書き込み遅延 (write-back) はキャッシュラインのみを書き込み、「変更されたライン (dirty)」のフラグを立てておき、そのラインが追い出される際にメモリに書き込む。

## 直接シミュレーションしてみる

小さなキャッシュ（1KB、ライン 64 バイト）を Python で模倣し、アクセスパターンを変えてみた。ラインが満杯になると、最も長く使用されていないものを排出する方式である。

```python
def sim(addrs, size=1024, line=64, ways=1):
    sets = size // line // ways
    st = [[] for _ in range(sets)]
    hit = 0
    for a in addrs:
        b = a // line
        s = b % sets
        if b in st[s]:
            hit += 1
            st[s].remove(b); st[s].append(b)
        else:
            if len(st[s]) >= ways:
                st[s].pop(0)
            st[s].append(b)
    return hit / len(addrs)

print(sim([i * 4 for i in range(4096)]))      # 0.9375
print(sim([i * 64 for i in range(4096)]))     # 0.0
```

4 バイトの整数を順に読み込むと、ライン一つ（64 バイト）に 16 個収まるため、最初のアクセスのみがミスで、その後の 15 個はヒットとなる。15/16 は 0.9375 である。逆に 64 バイトずつ飛ばして読み込むと、毎回新しいラインになるためヒット率は 0 となった。同じ数だけ読み込んでも順序によってこのように差が出る。

同じキャッシュでアドレス 0 と 1024 を交互に 1000 回読み込む場合も試した。両アドレスは同じ位置にマッピングされるため、直接マッピングではヒット率 0.0、2-way では 0.998 が得られた。前述の互いに追い出す（衝突ミス）現象が実際にこのように生じる。

## 二次元配列を行方向で読むか列方向で読むか

配列の方向による違いも同じシミュレーターで確認した。64x64 の整数配列を行優先で保存すると仮定し、4KB 4-way キャッシュで動作させた。

| 巡回方式 | ヒット率 |
|---|---|
| 行単位（保存順） | 0.9375 |
| 列単位（スキップして） | 0.0 |

ウィキペディアの「局所性」の文書でも、C は行優先で保存されているため、行単位の巡回は連続したメモリを読み取って効率が良く、列単位は遠く離れた場所を行き来してミスが増えるという説明があります。行列がキャッシュに収まるほど小さい場合は差が小さくなるとも言われています。

<details>
<summary>実際にコンピュータで計測した結果</summary>

numpy で 5000x5000 の int32 配列（行優先保存）の行合計と列合計をそれぞれ 5 回計算し、最も速い値を選びました。私の PC では行側が約 0.029 秒、列側が約 0.086 秒で、約 3 倍の差がありました。この値は特定の PC と numpy の実装に依存した結果であり、他の環境では異なる可能性があります。

```python
import numpy as np, time
a = np.ones((5000, 5000), dtype=np.int32)
def best(f):
    r = []
    for _ in range(5):
        t = time.perf_counter(); f(); r.append(time.perf_counter() - t)
    return min(r)
rows = best(lambda: [a[i].sum() for i in range(5000)])
cols = best(lambda: [a[:, j].sum() for j in range(5000)])
print(rows, cols, cols / rows)
```
</details>

## よくある誤解

- キャッシュが大きければ必ず速い：大きくなると検索に時間がかかるため、階層化されているのです。
- キャッシュはプログラマーとは関係ない：ハードウェアが自動的に管理しますが、アクセス順序を変えるだけでヒット率が変化するということは上記で確認しました。
- RAM と仮想メモリのディスクスワップはキャッシュとは別の話です：方向性は同じです。RAM をディスクのキャッシュのように捉える視点も可能であり、ページングポリシーはキャッシュ置換ポリシーと同じ問いかけです。
