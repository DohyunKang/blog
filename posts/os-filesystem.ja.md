[概要](#/post/cs-os) ではプロセスとメモリを中心に解説しましたが、ディスクについてはここで別に扱います。ファイルシステムは、ディスクを名前のついたファイルとディレクトリとして見せる階層です。ディスクは同じサイズのブロックが並んでいるだけなので、どのブロックがどのファイルに属するかは OS が別途記録しておく必要があります。

## ディスクの上には何があるか

OSTEP が説明用に挙げた単純なファイルシステム (vsfs) は、ディスクを 4KB のブロックに分け、役割を以下のように分担しています。

| 領域 | 役割 |
|---|---|
| スーパーブロック | ファイルシステム全体の情報 (inode の数、データブロックの数、inode テーブルの開始位置など) |
| inode ビットマップ・データビットマップ | inode とデータブロックのうち、どのものが空いているかを示す |
| inode テーブル | 各ファイルごとに一つずつあるメタデータ |
| データブロック | ファイルの内容 |

実際のファイルシステムはこれより複雑ですが、骨格は似ているそうです。ここで重要なのは inode です。

## inode

inode (index node) は、一つのファイルのメタデータを格納した構造体です。サイズ、所有者、権限、時刻、そしてデータブロックがどこにあるかを示すポインターが含まれています。ファイル名は inode 内にはありません。名前を保持しているのはディレクトリです。

inode 番号 (i-number) があれば、inode がディスクのどこにあるかを計算で求めることができます。inode が 256 バイトで inode テーブルが 12KB の地点から開始する場合、32 番目の inode はテーブルの開始位置から 32 × 256 = 8192 バイト後にあります。ディスクはセクター（通常 512 バイト）単位で読み取るので、そのアドレスをセクター番号に変換して読みます。

### ブロックポインタと大きなファイル

inode にポインタをいくつかしか入れなければ大きなファイルを格納できません。そのため、直接ポインタ（データブロックを直接指すもの）の他にも、ポインタが入っているブロックを介してアクセスする間接ポインタを設けます。さらに必要であれば、間接ブロックを指す二重間接、三重間接へと拡張します。

OSTEP の例示数値（ブロック 4KB、ポインタ 4 バイト、直接ポインタ 12 個）を用いて実際に計算してみました。

```python
B = 4096; P = 4
n = B // P
print("블록당 포인터", n)
print("직접 12개:", 12 * B)
print("+단일 간접:", (12 + n) * B)
print("+이중 간접:", (12 + n + n * n) * B)
print("+삼중 간접:", (12 + n + n * n + n ** 3) * B)
```

```
블록당 포인터 1024
직접 12개: 49152
+단일 간접: 4243456
+이중 간접: 4299210752
+삼중 간접: 4402345721856
```

直接 12 個は 48KB、単一間接までで約 4MB、二重間接までで約 4GB、三重間接までで約 4TB です。ポインタを一つ追うごとにディスク読み込みが一回増えるため、大きなファイルの後半を読むほどコストが増加します。

## ディレクトリとパス

ディレクトリもファイルです。内容は「名前 → inode 番号」のリストだけなので、ファイルを探すとは、パスを辿りながらディレクトリを一つずつ読み、番号を取得することです。

`/foo/bar` を開く過程は、OSTEP の説明では以下の通りです。

1. ルートディレクトリの inode 番号は事前に知られており（Unix 系ファイルシステムでは通常 2 番）、その inode を読みます。
2. その inode が指し示すルートディレクトリデータブロックから `foo` を探し、inode 番号を取得します。
3. `foo` の inode を読み、そのデータブロックから `bar` を探します。
4. `bar` の inode を読み、権限を確認し、プロセスのオープンファイルテーブルにエントリを作成してファイルディスクリプターを返します。

パスが一つ深くなるごとに、inode の読み込みとディレクトリデータの読み込みが一回ずつ増えます。読み込み (read) 時はビットマップを見ません。ブロックを新規割り当てする時だけビットマップを確認します。閉じ (close) はディスク I/O を行わずにディスクリプターだけを解放します。

## ハードリンクとシンボリックリンク

名前と inode が分離しているため、同じ inode に複数の名前を付けることができます。それがハードリンクです。inode にはリンク数があり、名前が一つ消えるたびに減り、0 になるとファイルが実際に削除されます。実際に確認しました (Windows NTFS で実行)。

```python
import os, tempfile
d = tempfile.mkdtemp()
p = os.path.join(d, "a.txt")
open(p, "w").write("hello world\n")
l = os.path.join(d, "b.txt")
os.link(p, l)
s1, s2 = os.stat(p), os.stat(l)
print("same ino", s1.st_ino == s2.st_ino, "nlink", s1.st_nlink)
os.remove(p)
print("nlink", os.stat(l).st_nlink, "content", open(l).read().strip())
```

```
same ino True nlink 2
nlink 1 content hello world
```

元の名前を削除しても内容は残りました。シンボリックリンクは別のパス文字列を含む独立したファイルなので、元がなくなると途切れます。

## システムコールの観点：ファイルディスクリプター

プロセスは `open` でファイルをオープンし、一つの整数（ファイルディスクリプター）を受け取ります。man ページによると返される番号は、そのプロセスで未使用の最小番号です。0, 1, 2 は通常標準入力・出力・エラーなので、最初のファイルは 3 番になります。

ディスクリプターが指し示すのはシステム全体のテーブルにあるオープンファイル記録 (open file description) で、ここに読み書き位置 (offset) があります。そのため同じファイルを二回 `open` すると offset が別々になり、`dup` や `fork` で複製したディスクリプターは offset を共有します。

```python
import os
fd1 = os.open(p, os.O_RDONLY)
fd2 = os.open(p, os.O_RDONLY)
print("fds", fd1, fd2)
os.read(fd1, 5)
print("fd1", os.lseek(fd1, 0, os.SEEK_CUR), "fd2", os.lseek(fd2, 0, os.SEEK_CUR))
fd3 = os.dup(fd1)
print("dup", os.lseek(fd3, 0, os.SEEK_CUR))
os.read(fd3, 1)
print("fd1 after dup read", os.lseek(fd1, 0, os.SEEK_CUR))
```

```
fds 3 4
fd1 5 fd2 0
dup 5
fd1 after dup read 6
```

fd1 から 5 バイト読み込んだとすると fd1 の位置だけが 5 になり、`dup` で作成した fd3 は同じ 5 から始まり、fd3 で読み込んだ分だけ fd1 の位置も動きました。すべて閉じて再度開いた時に 3 番が再び返ることも確認しました（最小番号の再利用）。

`fork` で作成された子プロセスも、親と同じオープンファイル記述を共有する ([プロセスとスレッド](#/post/os-process-thread) を参照)。`O_APPEND` は書き込み直前にオフセットをファイル末尾に移動する動作と書き込みを 1 ステップにまとめることで、複数のプロセスが同じログファイルの末尾に追加する際に互いに上書きしないようにする。複数のプロセスが同じリソースを扱う問題は [同期とデッドロック](#/post/os-sync-deadlock) と同根である。

<details>
<summary>O_SYNC とデータがディスクに到達するタイミング</summary>

`write` が完了したからといって、データがディスクにあるわけではない。man ページによると `O_SYNC` は各 `write` の後に `fsync` を行ったことと同程度の完了を保証し、`O_DSYNC` は `fdatasync` のようにデータを再読み込みに必要なメタデータ（ファイルサイズなど）のみを保証する。更新時刻などは含まれない。データベースがコミット時に `fsync` を呼ぶ理由はこれであり、[トランザクションと隔離レベル](#/post/db-transaction) の耐久性 (D) と繋がっている。
</details>

## ディスクアクセス時間とスケジューリング

ハードディスクは 1 回の読み取りに時間を 3 つの要素に分けてかかる。ヘッドを目標トラックへ移動させるセーク、必要なセクターがヘッドの下に戻ってくるのを待つ回転遅延、そして実際の転送である。このうちセークと回転遅延が大きく、転送は相対的に小さい。OSTEP は平均セーク距離が全距離の 3 分の 1 であるという計算も示している。

したがって、複数のリクエストが蓄積した際に順序を変えてヘッド移動を減らすことがディスクスケジューリングである。

| 方式 | アイデア | 問題 |
|---|---|---|
| FCFS | 到着順に処理 | ヘッドが大きく動き回る |
| SSTF | 現在の位置から最も近いトラックから | 遠いトラックのリクエストがずっと待たされる飢餓 (starvation) |
| SCAN(エレベータ) | 一方方向にスキャンして処理し、最後に戻ってくる | 戻り際に中央トラックを 2 回通るため中央に有利 |
| C-SCAN | 一方方向のみスキャンし、端に達すると最初に戻って再度スキャン | |

OSTEP は SCAN の変形で F-SCAN（スキャン中に到着したリクエストをキューに保持する方式）も紹介している。小さなシミュレーションで移動距離を比較した。教科書でよく使われるリクエスト列 [98, 183, 37, 122, 14, 124, 65, 67]、開始位置は 53 である。

```python
def fcfs(h, q):
    t = 0
    for r in q:
        t += abs(r - h); h = r
    return t

def sstf(h, q):
    q = list(q); t = 0; order = []
    while q:
        r = min(q, key=lambda x: abs(x - h))
        q.remove(r); order.append(r); t += abs(r - h); h = r
    return t, order

def scan(h, q):  # 위쪽으로 먼저, 마지막 요청에서 방향 전환
    up = sorted(r for r in q if r >= h)
    dn = sorted((r for r in q if r < h), reverse=True)
    t = 0
    for r in up + dn:
        t += abs(r - h); h = r
    return t

q = [98, 183, 37, 122, 14, 124, 65, 67]
print(fcfs(53, q)); print(sstf(53, q)); print(scan(53, q))
```

```
640
(236, [65, 67, 37, 14, 98, 122, 124, 183])
299
```

FCFS は 640、SSTF は 236、SCAN は 299 が得られた。SSTF が最も短いのはこのキューが固定されているためであり、リクエストが連続して到着すると片方が飢餓する可能性がある。前述の SCAN はディスクの端まで行かず最後のリクエストから戻ってくる形式なので、厳密には LOOK と呼ばれる変形に近い。

SSD はヘッドがないためこの計算はそのまま当てはまらない。この記事のシミュレーションは回転式ディスクを基準としている。

## よくある誤解

- ファイルを削除するとデータが即座に消える：リンク数が 0 になり、参照する場所がなくなったときに実際に解放される。単に名前だけを削除したに過ぎない場合もある。
- ファイル名はファイルの中に含まれている：名前はディレクトリエントにあり、inode にはない。
- `write` が成功すればディスクに保存されたことになる：ディスクへの反映タイミングは `fsync` などの呼び出しやフラグに依存する。
- ファイルを 1 つ開くことは 1 回の読み取りである：パスの深さ分だけ inode とディレクトリブロックを追う。
- ディスクスケジューリングは常に SSTF が最適である：距離は短いものの飢餓問題がある。

Windows で開いているファイルを Python の `os.remove` で削除しようとすると「別のプロセスで使用されています」というエラー (WinError 32) が発生した。開いているファイルの削除可否は OS によって動作が異なる。

## さらに読む

名前 → inode → データブロックへと続く間接参照がファイルシステムの骨格であり、ファイルディスクリプターとオープンファイルテーブルはその上にプロセスごとの使用状態を重ねている。ディスクは遅いためスケジューリングとキャッシュでアクセスを減らす方向に設計が進み、同じ考え方は [メモリ管理と仮想メモリ](#/post/os-memory) のページングや [CDN とキャッシュ戦略](#/post/infra-cdn-cache) にも現れる。
