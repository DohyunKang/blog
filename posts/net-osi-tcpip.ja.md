階層モデルは、通信を「層」に分け、各層が自らのヘッダーのみを担当し、他のことは無視させる構造です。送信時には上から下へヘッダーが一枚ずつ追加され、受信時には下から上へ一枚ずつ剥がされます。

[概要](#/post/cs-network)で表を使って概観した内容をここではさらに深掘りします。各層が具体的に何を行うのか、ヘッダーがどのように付加されるのか、そしてなぜこの 2 つのモデルが併存しているのかを解説します。

## なぜ層に分けるのか

ネットワーク通信には、信号を線に載せること、隣接機器へ送ること、複数のネットワークを跨いで経路を見つけること、プロセスへ届けること、アプリ同士のやり取りを合わせる事が一度に行われます。これを一つの塊としてしまうと、Wi-Fi を有線に変更する際に Web ブラウザまで修正しなければなりません。層に分ければ、ある層全体を書き換えても上下はそのまま利用できます。

各層は、下位層が提供するサービスのみを使用し、相手側の同じ層と合意された規則（プロトコル）で対話します。実際のデータは下層へ降りて上へ上がりますが、論理的には同じ層同士が直接会話していることになります。

## OSI 7 階層

OSI は ISO が作成した参照モデルであり、1984 年に ISO 7498 として発表されたと言われています。層は 7 つあります。

| 階層 | 名前 | データ単位 (PDU) | 役割 |
|---|---|---|---|
| 7 | アプリケーション | データ | ユーザーと接するプロトコル (HTTP など) |
| 6 | プレゼンテーション | データ | 形式変換、暗号化、圧縮 |
| 5 | セッション | データ | 対話の開始・管理・終了 |
| 4 | トランスポート | セグメント | エンドポイント間の伝送、分割・確認応答・多重化 |
| 3 | ネットワーク | パケット | アドレス指定、複数のネットワークを跨ぐ経路選択 |
| 2 | データリンク | フレーム | 隣接する 2 つのノード間の伝送、エラー検出 |
| 1 | 物理 | ビット | 電気・電波・光信号によるビット転送 |

データ単位の名称が層ごとに異なる点は試験問題でよく問われますが、概念としては「その層が扱う塊の名前」に過ぎません。トランスポート層の塊はセグメント (TCP) またはデータグラム (UDP) と呼び、ネットワーク層の塊はパケットと呼びます。

[詳細 → TCP と UDP](#/post/net-tcp-udp)では、4 層が具体的にどのように信頼性を確保しているかを別記事で扱っています。

## TCP/IP 4 階層

実際のインターネットで使用されているのは TCP/IP です。RFC 1122 の 1.1.3 節では、プロトコルグループを上からアプリケーション、トランスポート、インターネット、リンクの 4 つの層として説明しています。インターネット層には IP・ICMP・IGMPがあり、トランスポート層には TCP・UDP があり、リンク層は直結されたネットワークとのインターフェースを担当します。

対応関係はおよそ以下の通りです。TCP/IP のアプリケーション層が OSI 5〜7 層を、トランスポートが 4 層を、インターネットが 3 層を、リンクが 1〜2 層をカバーしています。完全に一致しないため「およそ」とする必要があります。

| OSI | TCP/IP | 代表プロトコル |
|---|---|---|
| 5・6・7 | アプリケーション | HTTP, DNS, SMTP |
| 4 | トランスポート | TCP, UDP |
| 3 | インターネット | IP, ICMP |
| 1・2 | リンク | イーサネット、Wi-Fi |

OSI 側は当初から層の役割を厳密に定義しようとした参照モデルであり、TCP/IP は米国防省の支援によりほぼ同時期に作成されたより緩やかな構造であると言われています。その結果として OSI プロトコルは広く採用されず、インターネットは TCP/IP の上に構築されました。そのため、7 階層は名称と概念を説明するための共通語として残り、4 階層は実際の実装の形態として残りました。

RFC 1122 1.3.1 節には、厳密な階層化がプロトコルグループにも推奨実装方法にも「不完全なモデル」という言葉が使われています。実際の実装では層境界を破ってデータ構造を共有するケースも多いと記されています。層モデルを守らなければならない法則のように暗記する必要はありません。

## 封じ込め：ヘッダーが一枚ずつ付く

送信時には、各層は上位から受け取った塊の前に自らのヘッダーを追加して下へ渡します。これがカプセル化です。受信側は逆に最も外側のヘッダーから読み込んで剥がし、上へ戻します。

```
응용 데이터
[UDP 헤더 | 응용 데이터]                       전송 계층
[IP 헤더 | UDP 헤더 | 응용 데이터]              인터넷 계층
[이더넷 헤더 | IP 헤더 | UDP 헤더 | 데이터]      링크 계층
```

文字だけではイメージが湧きにくいため、実際にヘッダーを作成してみました。イーサネット 14 バイト、IPv4 20 バイト、UDP 8 バイトを `struct` で埋め込み、チェックサムも計算した後、受信側のように一枚ずつ剥がしました。アドレスとポート番号は適当に設定した例です。

```python
import struct, socket

def checksum(b):
    if len(b) % 2: b += b'\x00'
    s = sum(struct.unpack('!%dH' % (len(b)//2), b))
    while s >> 16: s = (s & 0xffff) + (s >> 16)
    return ~s & 0xffff

payload = b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'   # 응용 데이터

# 전송 계층: UDP 헤더 8바이트 (포트, 길이, 체크섬)
src_ip, dst_ip = socket.inet_aton('192.168.0.10'), socket.inet_aton('93.184.216.34')
udp_len = 8 + len(payload)
pseudo = src_ip + dst_ip + struct.pack('!BBH', 0, 17, udp_len)
hdr0 = struct.pack('!HHHH', 50000, 53, udp_len, 0)
udp = struct.pack('!HHHH', 50000, 53, udp_len, checksum(pseudo + hdr0 + payload)) + payload

# 인터넷 계층: IPv4 헤더 20바이트
ip0 = struct.pack('!BBHHHBBH4s4s', 0x45, 0, 20 + len(udp), 1, 0, 64, 17, 0, src_ip, dst_ip)
ip = ip0[:10] + struct.pack('!H', checksum(ip0)) + ip0[12:] + udp

# 링크 계층: 이더넷 헤더 14바이트
frame = bytes.fromhex('aabbccddeeff') + bytes.fromhex('112233445566') + struct.pack('!H', 0x0800) + ip
print('앱 데이터', len(payload), '| UDP', len(udp), '| IP', len(ip), '| 프레임', len(frame))

# 받는 쪽: 한 겹씩 벗긴다
dst, src, et = struct.unpack('!6s6sH', frame[:14]); body = frame[14:]
print('이더넷 type=0x%04x' % et)
vihl, _, tot, _, _, ttl, proto, ck, s, d = struct.unpack('!BBHHHBBH4s4s', body[:20])
print('IP ihl=%d ttl=%d proto=%d %s -> %s' % (vihl & 15, ttl, proto, socket.inet_ntoa(s), socket.inet_ntoa(d)))
print('IP 헤더 체크섬 검증(0이면 정상):', checksum(body[:20]))
sp, dp, ln, _ = struct.unpack('!HHHH', body[20:28])
print('UDP %d -> %d len=%d' % (sp, dp, ln))
print(body[28:])
```

実行すると以下のような結果になりました。

```
앱 데이터 37 | UDP 45 | IP 65 | 프레임 79
이더넷 type=0x0800
IP ihl=5 ttl=64 proto=17 192.168.0.10 -> 93.184.216.34
IP 헤더 체크섬 검증(0이면 정상): 0
UDP 50000 -> 53 len=45
b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'
```

37 バイトのデータが UDP を通ると 45 バイト、IP を通ると 65 バイト、イーサネットを通ると 79 バイトになりました。層を下るごとにヘッダーサイズ分だけ大きくなるのです。

数字が層間の接続点としての役割も確認できます。イーサネットヘッダーの type `0x0800` は「中に含まれているのは IPv4」という意味であり、IP ヘッダーの proto `17` は「中に含まれているのは UDP」という意味です。受信側はこの値を見て、次にどのパーサーへ渡すかを決定します。上へ送り返す際、誰に渡すかについては各ヘッダーが自ら書き留ける構造になっています。

<details>
<summary>ヘッダーフィールドをさらに詳しく解説すると</summary>

- イーサネット: 宛先 MAC アドレス 6 バイト、送信元 MAC アドレス 6 バイト、タイプ 2 バイト。MAC アドレスは同じリンク内でのみ意味を持ちます。ルーターを一つ通過するたびにこのヘッダーは新たに作成され、IP ヘッダーはそのまま進みます。
- IPv4: 最初のバイト `0x45` はバージョン 4、ヘッダー長 5（×4 バイト = 20 バイト）。TTL はルーターを通過するたびに減らされ、無限にループする経路を防ぎます。ヘッダーチェックサムはヘッダーのみを検証します。上記のコードで検証結果が 0 になったのは、ヘッダー全体を再計算した際に正しいチェックサムであれば 0 になるためです。
- UDP: 送信元・宛先ポート、長さ、チェックサム。チェックサムは IP アドレスなどを含まれる仮想的なヘッダーも含めて計算され、宛先アドレスが間違えて別の場所へ到達したことを検出します。

</details>

## アドレスは階層ごとに異なる

各階層で「誰に」を指す方法が違う点が、最初は最も混乱しました。

| 階層 | アドレス | 指し示す対象 | 範囲 |
|---|---|---|---|
| リンク | MAC | ネットワークカード | 同じリンク内 |
| インターネット | IP | ホスト（のインターフェース） | ネットワーク間 |
| 転送 | ポート | プロセス | 一つのホスト内 |

パケットがルーターを通過する間、IP アドレスは変わらず、MAC アドレスはホップごとに変わります。経路を選ぶ方法は [詳しく → DNS と IP ルーティング](#/post/net-dns-routing) で続きます。

## 階層とコードの距離

私が書くアプリではこれらの階層はほとんど見えません。ソケットを開くと転送階層以下はオペレーティングシステムが担当します。[詳しく → ソケットとサーバープログラミング](#/post/net-socket) でその境界をコードで見てみましょう。ソケット API を応用と転送の間のインターフェースと考えればよいでしょう。応用階層上のリクエスト・レスポンスルールは [詳しく → HTTP と HTTPS](#/post/net-http) で扱います。オペレーティングシステム内でのネットワークスタックがどこに住んでいるかは、[概要](#/post/cs-os) のカーネル話と続きます。

## よくある誤解

- "7 階層を暗記すればネットワークを理解する": 7 階層は説明用の用語に近いものです。実際のプロトコルは一つの階層に収まらないものが多くあります。TLS が 5 階層か 6 階層か、転送と応用の間にあるかは図によって異なります。
- "OSI モデル通りにインターネットが動いている": インターネットで使われているのは TCP/IP です。OSI プロトコルスイートは広く採用されませんでした。
- "階層間は厳密に区切られている": RFC 1122 でも厳密な階層化は不完全なモデルであると述べています。実装では性能のために境界を越えて動作します。
- "MAC アドレスは宛先ホストのアドレスである": MAC は次のホップのアドレスです。最終宛先は IP ヘッダーが持っています。
