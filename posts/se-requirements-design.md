[개요](#/post/cs-sw-engineering)에서 요구사항, UML, 설계를 한 줄씩만 훑었다. 여기서는 그 셋이 어떻게 이어지는지를 조금 더 파고든다. 요구사항은 "무엇을", 설계는 "어떤 모양으로"에 대한 답이고, 설계가 요구사항 쪽으로 거꾸로 확인되지 않으면 둘은 따로 논다.

## 요구사항 분석이 하는 일

요구사항 단계는 받아 적기가 아니라 정리하는 일에 가깝다. 이해관계자마다 말이 다르고, 같은 단어를 다른 뜻으로 쓰고, 말하지 않은 전제가 있다. 그래서 흔히 도출(듣기) → 분석(충돌·빠짐 찾기) → 명세(문서로 적기) → 검증(이해관계자가 확인) 순으로 돌린다.

기능 요구사항과 비기능 요구사항의 구분은 개요에서 다뤘다. 한 가지만 더 보면, 기능은 "시스템이 ~한다", 비기능은 "시스템이 ~하다"의 모양이다. 위키피디아의 설명대로 비기능 요구사항은 품질 속성이라고도 부르고, 구체적이고 측정 가능하게 적어야 한다. 같은 예를 들면, 레코드 수를 보여 주는 건 기능이고 그 수가 얼마나 최신이어야 하는지는 비기능이다.

비기능 요구사항은 아키텍처를 고르는 기준이 된다. 뒤에 나올 아키텍처 스타일을 고를 때도 이 품질 속성의 우선순위부터 정하라고 한다.

### 유스케이스로 기능 요구 적기

유스케이스는 외부 행위자(사람이나 다른 시스템)가 목표를 이루려고 시스템과 주고받는 과정을 적은 것이다. 정해진 하나의 서식은 없고, 많이 쓰이는 모양은 이렇다.

| 항목 | 내용 |
|---|---|
| 이름 | 사용자 목표 하나(예: 상품 주문하기) |
| 행위자 | 주문자, 결제 시스템 |
| 주 성공 시나리오 | 번호 붙인 단계. 한 단계가 한 번의 상호작용 |
| 확장 | 주 경로 3단계에서 갈라지면 3a, 3b로 적음 |

단계에는 "주문 버튼을 누른다"보다 "주문자가 주문을 확정한다"처럼 목표와 응답을 적고 화면 요소는 피한다. 그래야 화면이 바뀌어도 요구사항은 그대로 남는다.

[Fowler식 유스케이스 설명](https://en.wikipedia.org/wiki/Use_case)을 따라 정리했다.

### 요구사항 ID와 추적

요구사항마다 번호를 달아 두면 "이 요구는 어느 설계 요소가 맡고, 어느 테스트가 확인하나"를 표로 이을 수 있다. 이게 추적(traceability)이다. 빠진 칸이 곧 구멍이다. 간단히 돌려 봤다.

```python
reqs = {"R1": "회원은 이메일로 로그인한다", "R2": "로그인 응답은 1초 안에", "R3": "비밀번호는 해시로 저장한다"}
design = {"R1": ["AuthService.login"], "R2": [], "R3": ["UserRepo.save"]}
tests = {"R1": ["test_login_ok"], "R2": ["test_login_latency"], "R3": []}
for r in reqs:
    gaps = [n for n, m in (("설계", design), ("테스트", tests)) if not m[r]]
    print(r, "OK" if not gaps else "빠짐: " + ",".join(gaps))
```

실행 결과는 `R1 OK`, `R2 빠짐: 설계`, `R3 빠짐: 테스트`였다. R2는 시험은 있는데 어디서 1초를 지킬지 설계가 없고, R3은 만들기는 했는데 확인하는 시험이 없다. 문서로만 관리해도 이 표 하나가 하는 일은 같다.

<details>
<summary>좋은 요구사항의 조건</summary>

- 한 문장에 한 요구. "로그인하고 알림을 보낸다"는 둘로 쪼갠다.
- 확인할 수 있어야 한다. "빠르게"는 못 하고 "1초 안에"는 한다.
- 서로 충돌하지 않아야 한다. 분석 단계에서 걸러야 하는 것이 이것이다.
- 해결책이 아니라 필요를 적는다. "Redis를 쓴다"는 설계 결정이지 요구가 아니다.
</details>

## 설계는 두 층으로 나뉜다

설계는 보통 큰 구조를 정하는 아키텍처 설계와, 모듈 안을 정하는 상세 설계로 나눈다. 요구사항이 "무엇"이었다면 아키텍처 설계는 "어떤 덩어리로 나누고 그 덩어리가 어떻게 말하는가"를 정한다. 여기서 비기능 요구사항이 가장 크게 작용한다. 확장성이나 변경 용이성 같은 요구가 구조를 밀어낸다.

## UML 기초

UML은 OMG가 관리하는 표기법으로, 소개 페이지에서는 분산 객체 시스템의 산출물을 시각화하고 명세하고 구성하고 문서화하는 그래픽 언어라고 설명한다. 다이어그램은 구조를 보여 주는 것과 동작을 보여 주는 것으로 나눠 이해하면 덜 헷갈린다. 클래스·컴포넌트·배치가 구조 쪽이고, 유스케이스·시퀀스·상태·액티비티가 동작 쪽이다. 어느 쪽이 어느 쪽인지는 표준 분류를 따른 것이다.

개요에서 표로 나열했으니 여기서는 읽는 법만 적는다.

- 클래스 다이어그램: 상자 하나가 클래스. 선은 관계(연관, 상속, 집합, 합성, 의존). 상속은 속이 빈 삼각형 화살표라는 식의 모양은 한 번 외워 두면 된다.
- 시퀀스 다이어그램: 위에서 아래로 시간이 흐르고, 가로 화살표가 메시지다. 유스케이스 하나의 주 성공 시나리오를 그대로 시퀀스로 옮길 수 있다.
- 상태 다이어그램: 주문이 "접수 → 결제됨 → 배송 중 → 완료"처럼 상태가 있는 것에 쓴다. 어떤 이벤트에서 어떤 상태로 가는지를 적는다.

유스케이스 → 시퀀스 → 클래스 순으로 내려가면, 시나리오의 각 단계가 메시지가 되고 메시지를 받는 쪽이 클래스의 메서드가 된다. 이 흐름으로 보면 UML 종류를 따로 외울 때보다 서로의 관계가 보인다.

## 아키텍처 스타일

아키텍처 스타일은 같은 특징을 공유하는 아키텍처의 묶음이다. 특정 기술을 요구하지 않는다. 마이크로서비스에 컨테이너가 잘 맞는 정도의 궁합은 있다. 스타일의 본질은 제약이다. 어떤 요소가 있을 수 있고 요소끼리 어떻게 연결될 수 있는지를 제한하고, 그 제약을 지키면 바라는 성질이 따라온다.

마이크로서비스를 예로 들면 제약은 이렇다. 서비스 하나는 하나의 책임을 맡는다, 서비스끼리 독립적이다, 데이터는 소유한 서비스만 가진다. 이걸 지키면 따로 배포하고, 장애를 가두고, 업데이트를 자주 하기 쉬워진다.

| 스타일 | 의존을 다루는 방식 | 어울리는 영역 |
|---|---|---|
| N-tier(계층형) | 위 층이 아래 층만 호출 | 전통적 업무 시스템, 변경이 잦지 않은 곳 |
| Web-Queue-Worker | 웹과 작업자를 큐로 분리 | 단순한 도메인에 무거운 처리가 일부 있는 곳 |
| 마이크로서비스 | 기능별로 세로로 쪼개고 API로 호출 | 복잡한 도메인, 잦은 변경 |
| 이벤트 기반 | 발행자와 구독자를 이벤트로 분리 | IoT, 실시간 처리 |

위 표는 [Azure Architecture Center의 스타일 안내](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/)에서 가져온 분류다. 여기에는 빅데이터, 빅컴퓨트도 있는데 소프트웨어 공학 수업 범위를 넘으니 뺐다.

문서에서 반복해서 강조하는 점은 이렇다. 복잡도가 도메인에 맞아야 한다. 너무 단순하게 짜면 의존이 관리되지 않는 "큰 진흙 덩어리"가 된다. 반대로 마이크로서비스는 서비스 탐색, 데이터 일관성, 분산 시스템 관리 같은 복잡함을 데려오고, 문서는 성숙한 개발·운영 역량이 있는 조직에 더 맞는다고 쓴다. 비동기 메시징은 결합을 풀어 주는 대신 최종적 일관성과 중복 메시지 문제를 만든다.

### 직접 호출과 이벤트, 코드로 비교

계층형은 호출이 직접적이고, 이벤트 기반은 호출하는 쪽이 받는 쪽을 모른다. 같은 주문 기능을 두 방식으로 짜서 돌렸다.

```python
class Inventory:
    def reduce(self, item): print("재고 감소:", item)
class Mail:
    def send(self, item): print("메일 발송:", item)

class OrderLayered:               # 주문이 두 모듈을 직접 안다
    def __init__(self): self.inv, self.mail = Inventory(), Mail()
    def place(self, item):
        self.inv.reduce(item); self.mail.send(item)

class Bus:
    def __init__(self): self.subs = {}
    def subscribe(self, ev, fn): self.subs.setdefault(ev, []).append(fn)
    def publish(self, ev, data):
        for fn in self.subs.get(ev, []): fn(data)

class OrderEvent:                 # 주문은 이벤트만 낸다
    def __init__(self, bus): self.bus = bus
    def place(self, item): self.bus.publish("order_placed", item)

OrderLayered().place("책")
bus = Bus(); bus.subscribe("order_placed", Inventory().reduce); bus.subscribe("order_placed", Mail().send)
OrderEvent(bus).place("책")
bus.subscribe("order_placed", lambda i: print("포인트 적립:", i))  # 주문 코드는 그대로
OrderEvent(bus).place("펜")
```

실행하면 "책" 주문은 두 방식 모두 재고 감소와 메일 발송이 찍히고, 구독을 하나 더 붙인 뒤 "펜" 주문에는 포인트 적립이 추가로 찍힌다. 계층형으로 같은 걸 하려면 `OrderLayered.place`를 고쳐야 한다. 대신 이벤트 방식은 호출 순서가 코드에 안 보여서, 누가 이 이벤트를 받는지 따라가야 한다. 위에서 말한 비동기·이벤트의 대가가 이 작은 예에도 있다.

## 요구사항에서 스타일 고르기

스타일을 먼저 고르고 요구사항을 끼워 맞추면 거꾸로다. 문서가 권하는 순서는 문제의 성격을 보고, 핵심 비즈니스 동인과 거기서 나오는 비기능 요구사항(아키텍처 특성)을 정하고, 우선순위를 매긴 뒤 고르는 것이다. 출시 시간이 급하면 유지보수성·테스트 용이성·신뢰성을, 예산이 빠듯하면 단순함을 앞세우는 식이다. 스타일을 한번 고르면 바꾸는 데 비용이 크니 초반에 더 들여다볼 가치가 있다고 한다.

## 흔한 오해

- 요구사항은 처음에 다 확정한다? 폭포수 쪽 이야기이고, 애자일에서는 바뀌는 것을 전제로 짧게 돌린다. 어느 쪽이든 추적할 수 있게 적어 두는 일은 같다.
- 마이크로서비스가 최신이니 항상 낫다? 제약이 있고 대가도 크다. 도메인이 단순하면 계층형이나 Web-Queue-Worker가 맞다.
- UML은 모든 걸 그려야 한다? 말로 설명하기 어려운 부분만 그린다.
- 비기능 요구사항은 나중에 챙긴다? 구조를 정하는 힘이 되기 때문에 설계 전에 정해야 한다.
