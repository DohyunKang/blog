# 트렌드 수집을 자동화한다는 게 뭔지 정리

한 줄 요약: 트렌드 수집은 "소스 고르기 → 가져오기 → 중복 제거 → 요약 → 사람이 고르기" 순서인데, 어려운 건 요약이 아니라 가져오는 단계의 한도와 약관이었다.

공부 노트라 직접 서비스에 돌려 본 건 아니고, 공식 문서를 읽고 작은 예제만 돌려 봤다. 회사 일과는 무관한 일반론이다.

## 트렌드 수집이 뭔가

마케팅에서 트렌드 수집은 "요즘 사람들이 뭘 많이 찾고 얘기하나"를 매일 모으는 일이다. 사람이 하면 아침마다 커뮤니티, 뉴스, 검색어를 돌아다니는 시간이 든다. 이걸 스크립트가 대신 모아서 한 장으로 보여 주게 하는 게 자동화다.

자동화한다고 해서 "무엇이 뜰지" 맞혀 주는 건 아니다. 이미 올라온 신호를 모아 줄 뿐이고, 그걸 콘텐츠 주제로 삼을지는 사람이 정한다. 주제 풀과 이어지는 얘기는 [자세히 → 콘텐츠 캘린더 자동화](#/post/mk-content-calendar)에 있다.

## 전체 흐름

```
[소스 목록] → [가져오기] → [정리·중복 제거] → [점수·요약] → [사람이 선택] → [주제 풀]
 RSS·API·검색어   스케줄러    URL 정규화      빈도·LLM       후보 5~10개
```

한 단계씩 보면 이렇다.

1. 소스 목록: 어디서 가져올지 정한 파일 하나.
2. 가져오기: 정해진 시각에 돌아가는 스케줄러(cron 같은 것).
3. 정리: 같은 글이 여러 곳에 올라오니 URL을 정규화해서 중복을 뺀다.
4. 점수·요약: 단어 빈도처럼 단순한 계산 먼저, 요약은 LLM.
5. 선택: 사람이 훑고 쓸 것만 주제 풀로 옮긴다.

## 소스는 크게 세 종류

| 종류 | 예 | 장점 | 한계 |
|---|---|---|---|
| 피드(RSS) | 블로그, 뉴스 사이트 | 형식이 정해져 있고 가볍다 | 제공하는 사이트만 됨 |
| 공식 API | YouTube Data API, 구글 트렌드 API 등 | 약관상 안전, 구조화된 데이터 | 한도·승인 절차 |
| 웹 페이지 긁기 | 검색 결과, 커뮤니티 목록 | 뭐든 가능 | 약관·차단·구조 변경 |

처음엔 RSS와 공식 API만으로 시작하는 게 맞아 보인다. 긁기는 마지막 수단으로 두는 게 낫다고 생각했다.

**RSS.** RSS 2.0 명세를 보면 글 하나가 `item`이고, 안에 `title`, `link`, `description`, `pubDate`, `guid`가 들어 있다. 요소는 전부 선택이고 title이나 description 중 하나만 있으면 된다. `guid`는 글을 고유하게 식별하는 문자열이라서 "이미 본 글인지" 판단하는 데 쓰라고 명세에 돼 있다. 중복 제거에 딱 맞는 필드인데, 사이트에 따라 guid를 안 채우는 경우가 있을 것 같아서 링크도 같이 쓰는 편이 안전해 보였다.

**YouTube.** Data API의 `search.list`는 호출당 1유닛이지만, 공식 문서에는 하루 100회까지로 별도 버킷이 잡혀 있다. 그 밖의 메서드는 기본 하루 10,000유닛이고 태평양 시간 자정에 초기화된다. `videos.list`는 호출당 1유닛이다. 그래서 "검색은 아끼고, 이미 아는 영상 ID는 `videos.list`로 조회수를 가져오는" 식의 설계가 된다. (참고로 같은 문서를 나중에 다시 보면 숫자가 바뀌어 있을 수 있어서, 구현할 때 다시 봐야 한다.)

**구글 트렌드.** 공식 API가 Search Central 문서에 소개돼 있지만 지금은 알파 단계다. 문서에 "아직 모두에게 열 수 없다"는 문장이 있고, 알파 테스터 신청 양식으로 지원해야 한다. 최근 5년 데이터를 일·주·월·연 단위로 주고, 값이 0~100으로 다시 맞춰지지 않는 일관된 척도라서 여러 요청을 이어 붙일 수 있다고 한다. 웹 화면은 한 번에 8개 검색어까지만 비교되는데 API는 수십 개를 지원한다고 적혀 있다. 일반 개발자가 지금 바로 쓸 수 있는 건 아니라서, 쓰려면 신청부터 해야 한다.

## 약관과 한계

가져오는 방법이 기술적으로 되느냐와 해도 되느냐는 별개였다.

- robots.txt는 크롤러에게 "여기는 와도 된다/안 된다"를 알리는 규칙이다. RFC 9309는 이게 접근을 허용하거나 막는 권한이 아니고, 실제 접근 통제는 HTTP 인증 같은 다른 수단으로 해야 한다고 적는다. 즉 robots.txt에서 허용돼 있다고 약관상 괜찮다는 뜻은 아니다. 반대로 막혀 있으면 따르는 게 예의다.
- 사이트마다 이용약관에 자동 수집을 금지하는 문구가 있을 수 있다. 이건 사이트별로 읽어 봐야 하는데, 내가 모든 사이트를 확인한 건 아니다.
- 로그인이 필요한 영역, 개인 정보가 섞인 데이터는 트렌드 수집 범위 밖으로 두는 게 맞다.
- 공식 API는 한도가 있다. 한도를 우회하려고 키를 여러 개 돌리는 건 약관 위반이 되기 쉽다고 한다. 이것도 서비스마다 다를 테니 확인이 필요하다.
- 커뮤니티 API(예: Reddit)는 가격·한도 정책이 자주 바뀌었다고 알려져 있는데.

## 직접 돌려 본 작은 예제

아래는 RSS 아이템 몇 개로 중복을 빼고 단어 빈도를 세는 코드다. 외부 라이브러리 없이 표준 라이브러리만 썼고, 인터넷 없이 샘플 XML로 돌렸다. 같은 글인데 `utm_source`가 붙은 링크가 중복으로 걸러지는지 보려고 넣었다.

```python
import xml.etree.ElementTree as ET, hashlib, re
from collections import Counter

SAMPLE = """<rss version="2.0"><channel>
<item><title>New video model released</title><link>https://a.example/1?utm_source=x</link><guid>a1</guid></item>
<item><title>New video model released</title><link>https://a.example/1</link><guid>a1</guid></item>
<item><title>Short video ads: what works</title><link>https://b.example/2</link><guid>b2</guid></item>
<item><title>Video model pricing cut</title><link>https://c.example/3</link><guid>c3</guid></item>
</channel></rss>"""

def norm(u):                       # 쿼리·해시 제거
    return re.sub(r'[?#].*$', '', u)

seen, titles = set(), []
for it in ET.fromstring(SAMPLE).iter('item'):
    key = hashlib.sha1(norm(it.findtext('link')).encode()).hexdigest()
    if key in seen:
        continue
    seen.add(key)
    titles.append(it.findtext('title'))

stop = {'a', 'the', 'what', 'new'}
words = Counter(w for t in titles for w in re.findall(r'[a-z]+', t.lower())
                if w not in stop and len(w) > 2)
print(len(titles), words.most_common(3))
```

실행하면 `3 [('video', 3), ('model', 2), ('released', 1)]`이 나왔다. 4개 중 중복 1개가 빠졌고, "video"와 "model"이 상위로 잡혔다. 실제 피드를 가져오는 부분(네트워크 호출)은 이 예제에 넣지 않았다.

<details>
<summary>자세한 풀이: 실제로 만든다면 붙일 것들</summary>

- 요청 간격: 같은 사이트에 짧은 시간에 몰아서 요청하지 않는다. 피드는 하루 몇 번이면 충분하다.
- 조건부 요청: 서버가 `ETag`나 `Last-Modified`를 주면 다음 요청에 같이 보내서 바뀐 게 없으면 본문을 안 받는 방식이 있다. 사이트가 지원하는지는 사이트마다 다르다.
- 저장: 가져온 원문은 오래 쌓지 않고 제목·링크·날짜·요약 정도만 저장하는 편이 저작권 면에서 가볍다. 본문 전체를 저장·재배포하는 건 별개 문제다.
- 점수: 처음엔 "여러 소스에 동시에 나온 단어"에 가산점을 주는 정도면 된다. 같은 날 세 군데에서 나온 키워드가 한 군데에서만 나온 것보다 신호가 강하다고 보는 식이다.
- 요약: LLM에 제목 20~30개를 한꺼번에 넣고 "묶음 5개와 대표 제목"을 요청한다. 제목만 넣으면 토큰이 적게 든다. 요약이 사실과 다를 수 있어서 링크를 같이 남겨 두고 사람이 원문을 열어 볼 수 있게 한다.
- 실패 처리: 소스 하나가 안 열려도 전체가 멈추지 않게 소스별로 예외를 잡고 로그만 남긴다.

## 비용 추정

가정은 하루 1회 수집, 소스 20개, 제목 약 200개, LLM 요약 1회. 제목 하나를 평균 20토큰으로 잡으면 입력이 4,000토큰 안팎이다. 요약 한 번에 출력 500토큰쯤이라고 하면 하루 한 번 호출로 끝난다. 모델 단가는 바뀌니 숫자를 못 박진 않겠지만, 이 정도 양이면 한 달 몇 백 원에서 많아야 몇 천 원 수준이라는 계산이 나온다.

| 항목 | 방식 | 비용 |
|---|---|---|
| RSS 수집 | 스크립트 | 0원 |
| YouTube Data API | 기본 할당량 안 | 0원 |
| 구글 트렌드 API | 알파, 신청 필요 | - |
| 요약 | LLM 하루 1회 | 월 수백~수천 원 추정 |
| 서버 | 내 PC 또는 이미 있는 서버 | 0원 (전기) |

돈보다 시간이 든다. 소스 목록을 관리하고, 깨진 피드를 고치고, 약관을 읽는 시간이다.

## 직접 만든다면

1. 소스 목록 파일을 만든다. 처음엔 RSS 10개와 YouTube 채널 몇 개.
2. 하루 한 번 도는 스크립트로 제목·링크·날짜를 JSON에 쌓는다.
3. URL 정규화로 중복을 빼고, 최근 24시간치만 남긴다.
4. 단어 빈도 상위와 LLM 묶음 요약을 한 장짜리 문서로 만든다.
5. 사람이 훑고 쓸 것만 주제 풀에 옮긴다.
6. 이 결과가 어떤 성과로 이어졌는지는 [자세히 → 성과 대시보드 만들기](#/post/mk-dashboard)처럼 따로 재야 한다. 어떤 주제가 반응이 좋았는지 모르면 수집이 맞게 되고 있는지도 알 수 없다.

수집한 트렌드로 글이나 영상을 만들 때 하나씩 비교 실험을 하는 쪽은 [자세히 → 썸네일·카피 A/B 시험](#/post/mk-ab-test)에, 숏폼으로 이어 붙이는 쪽은 [자세히 → 숏폼 자동화 파이프라인](#/post/mk-shortform-pipeline)에 정리해 두었다. 댓글에서 나오는 반응을 트렌드로 쓰는 얘기는 [자세히 → 댓글·DM 응대 자동화](#/post/mk-comment-bot)와 이어진다.

## 흔한 오해

- 트렌드를 모으면 뭐가 뜰지 알 수 있다 → 이미 뜬 걸 모은 것이라 늦을 수 있다. 다른 사람들이 같은 목록을 보고 있다면 더 그렇다.
- 긁을 수 있으면 써도 된다 → 기술적으로 되는 것과 약관·저작권상 되는 것은 별개다.
- LLM이 요약해 주니 사람이 안 봐도 된다 → 요약은 틀릴 수 있어서 후보를 고르는 칸은 사람이 맡는 게 안전해 보인다.
