큰 모델을 내 PC에서 돌리려면 먼저 메모리에 올라가야 한다. 그래서 줄이는 방법이 두 가지 나온다. 양자화는 같은 모델의 숫자를 더 적은 비트로 저장하는 것이고, 증류는 큰 모델의 행동을 작은 모델에게 가르치는 것이다. 이름이 비슷하게 들려서 자꾸 헷갈렸는데 줄이는 대상이 다르다.

## 모델은 메모리를 얼마나 먹나

[LLM](#/post/ai-llm)의 크기는 파라미터(가중치) 개수로 말한다. 8B면 80억 개다. 이 숫자 하나하나가 메모리에서 차지하는 크기가 정밀도에 따라 달라진다.

```
가중치 메모리 ≈ 파라미터 수 × 숫자 하나의 바이트 수
```

| 정밀도 | 숫자 하나 | 8B 모델 | 70B 모델 |
|---|---|---|---|
| FP16 / bf16 | 2바이트 | 약 16GB | 약 140GB |
| 8비트 | 1바이트 | 약 8GB | 약 70GB |
| 4비트 | 0.5바이트 | 약 4GB | 약 35GB |

Hugging Face 양자화 문서도 8B 모델이 bf16에서 약 16GB, 8비트에서 약 8GB, 4비트에서 4~5GB라고 적는다. 4비트가 정확히 4GB가 아니라 4~5GB인 건 스케일 값 같은 부가 정보가 따로 붙기 때문으로 보인다(표의 70B 칸은 위 계산식을 그대로 곱한 값이다).

## 양자화: 숫자를 거칠게 저장한다

양자화는 가중치를 적은 비트로 저장해서 메모리를 줄이는 방법이다. 문서 설명으로는 가중치, 경우에 따라 활성값까지 적은 비트로 저장해서 모델이 필요로 하는 메모리를 줄인다. 대신 비트가 줄면 정확도가 조금 떨어지고, 방법마다 메모리·속도·정확도의 균형이 다르다.

쉽게 비유하면 사진 용량을 줄이는 것과 비슷하다. 원본의 세밀한 값을 가까운 눈금으로 반올림해서 저장하면 용량이 줄고, 눈금이 성글수록 원본과 차이가 커진다. 그 차이가 품질 손실이다.

<details>
<summary>자세한 풀이: 반올림 눈금 예시 (직접 만든 단순 예)</summary>

가중치 하나가 0.37이라고 하자. 8비트로 저장하면 256개의 눈금 중 가까운 곳에 저장한다. 4비트면 눈금이 16개뿐이라서 더 멀리 있는 눈금으로 반올림될 수 있다. 실제 방식은 값 묶음마다 스케일(눈금 간격)을 따로 두는 식이라 이 예시보다 정교하다. 어떤 묶음 크기로 스케일을 붙이느냐 같은 구분은 Hugging Face의 양자화 개념 가이드에 나온다.

</details>

### 이름이 뭘 뜻하나

양자화 얘기를 읽다 보면 GGUF, GPTQ, AWQ 같은 이름이 쏟아진다. 같은 층위의 이름이 아니라 섞여 있다.

| 이름 | 정체 |
|---|---|
| GGUF | 파일 형식. 가중치·설정·토크나이저를 한 파일에 담는다(HF 문서). llama.cpp 계열에서 쓴다 |
| GPTQ | 양자화 방법(논문). 2차 정보를 근사해서 정확도를 지키며 한 번에 양자화한다 |
| AWQ | 양자화 방법(논문). 가중치만 줄이는 저비트 방식이고, 중요한 가중치 약 1%를 보호한다 |
| bitsandbytes | 로드할 때 4비트·8비트로 바꿔 주는 라이브러리. HF 문서 예시에 나온다 |
| Q4_K_M 같은 이름 | GGUF 파일 이름에 붙는 양자화 종류 표시. HF 문서 예시 파일명에 나온다 |

그러니까 "GGUF냐 GPTQ냐"는 완전히 같은 선택지는 아니다. GGUF는 담는 그릇이고, GPTQ·AWQ는 줄이는 알고리즘 이름이다.

### GPTQ와 AWQ가 한 일

GPTQ 논문(Frantar 등, 2022, arXiv 2210.17323)은 GPT 계열 모델을 한 번에 양자화하는 방법이다. 초록에 따르면 가중치를 3~4비트로 줄여도 원본 대비 정확도 저하가 거의 없었고, 1750억 파라미터 모델을 약 4 GPU 시간에 양자화했으며, 그 모델을 GPU 한 장에서 생성 추론할 수 있게 됐다. FP16 대비 속도 향상은 A100에서 약 3.25배, A6000에서 약 4.5배라고 한다.

AWQ 논문(Lin 등, 2023, arXiv 2306.00978)의 관찰은 가중치가 전부 똑같이 중요하지 않다는 것이다. 중요한 채널 약 1%를 지키면 양자화 오차가 크게 줄고, 어느 채널이 중요한지는 가중치 크기가 아니라 활성값 통계로 찾는다. 역전파나 재구성이 필요 없다는 점도 초록에 있다.

두 방법 모두 "어떻게 반올림해야 손실이 덜하냐"를 푸는 쪽이다. HF 문서에는 GPTQ만 로드 중에 보정용 데이터셋이 필요하고, 다른 대부분은 필요 없다고 나온다.

### 품질 손실은 얼마나

방법·모델·비트에 따라 다르다. GPTQ 논문은 3~4비트에서 저하가 거의 없다고 했고 2비트나 3진 수준에서도 쓸 만한 정확도를 보고했지만, 이게 모든 모델에서 그렇다는 뜻은 아니다. 쓸 모델이 정해졌다면 내 작업으로 직접 비교해 보는 게 맞다. 성능 비교의 기준은 [AI 모델 지도](#/post/ai-models)와 같은 곳에서 먼저 볼 수 있다.

## 증류: 큰 모델이 작은 모델을 가르친다

증류는 크기를 줄이는 방식이 다르다. 숫자를 거칠게 저장하는 게 아니라, 작은 모델을 새로 학습시키되 큰 모델의 출력을 보고 배우게 한다. 큰 쪽을 선생(teacher), 작은 쪽을 학생(student)이라고 부른다.

Hinton 등의 논문 "Distilling the Knowledge in a Neural Network"(2015, arXiv 1503.02531) 초록은 이렇게 시작한다. 같은 데이터로 여러 모델을 학습해 예측을 평균 내는 앙상블은 성능을 올리는 쉬운 방법이지만 배포하기엔 무겁고 비싸다. 그 앙상블의 지식을 모델 하나로 압축하는 방법을 발전시켰다는 내용이다. 선생·학생이라는 단어는 초록에는 나오지 않고, 이 글에서 쓰는 용어다.

결과물은 파라미터가 처음부터 적은 별도의 모델이다. 그래서 원래 모델과 가중치가 다르고, 이름도 따로 붙는다. 큰 모델과 작은 모델 계열이 함께 나오는 걸 보면 그런 방식으로 만든 것도 있겠다 싶지만, 어떤 모델이 증류로 만들어졌는지는 각 모델의 공개 자료를 봐야 한다.

## 양자화 vs 증류

| | 양자화 | 증류 |
|---|---|---|
| 하는 일 | 같은 모델의 숫자를 적은 비트로 저장 | 큰 모델의 출력으로 작은 모델을 학습 |
| 모델 구조 | 그대로 | 작은 구조를 새로 만듦 |
| 추가 학습 | 거의 없음(GPTQ는 보정 데이터 사용) | 필요함 |
| 줄어드는 것 | 숫자당 비트 수 | 파라미터 개수 |
| 손실 | 반올림 오차 | 학생이 못 따라가는 부분 |
| 내가 하기 | 이미 양자화된 파일을 받아 쓰는 경우가 많음 | 보통 모델 제작사가 함 |

둘은 같이 쓸 수도 있다. 증류로 작게 만든 모델을 다시 4비트로 양자화하면 두 효과가 겹친다.

LoRA 같은 [파인튜닝](#/post/ai-finetuning)과도 다르다. 파인튜닝은 행동을 바꾸는 쪽이고, 양자화·증류는 크기를 줄이는 쪽이다.

## 로컬에서 돌리는 도구

- llama.cpp: C/C++로 만든 오픈소스 추론 프로젝트다. README에 1.5비트에서 8비트까지 정수 양자화를 지원하고, CPU와 GPU를 섞어서 VRAM보다 큰 모델을 일부 가속할 수 있다고 적혀 있다. CUDA, Metal, Vulkan, HIP 등 여러 백엔드를 지원한다. Hugging Face 모델을 `-hf` 옵션으로 바로 받아 실행하고, OpenAI 호환 API 서버도 띄울 수 있다고 한다.
- Ollama: 명령 한 줄(`ollama run <모델>`)로 모델을 받아 대화하게 해 주고 `localhost:11434`에 REST API도 열어 준다. llama.cpp를 지원 백엔드로 쓴다.
- Hugging Face Transformers: `from_pretrained`에 양자화 설정을 넘기면 로드할 때 양자화하고, 이미 양자화된 체크포인트는 설정에서 방법을 읽어 자동으로 로드한다. 이 문서 기준으로 20가지가 넘는 방법을 같은 코드로 다룬다. 다만 GGUF는 대부분 로드 중에 원래 정밀도로 풀려서 메모리 이득이 없다고 문서에 적혀 있으니, GGUF는 llama.cpp 계열에서 쓰는 쪽이 자연스럽다.

<details>
<summary>자세한 풀이: Transformers 로드 예시 (문서 예시를 옮김)</summary>

실행해 본 코드가 아니라 Hugging Face 문서의 예시를 옮긴 것이다. 8B 모델을 bitsandbytes로 4비트 로드하는 형태다.

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=quantization_config,
    device_map="auto",
)
```

</details>

## 내 GPU에 들어가나 가늠하기

순서는 간단하다.

1. 모델 파라미터 수를 확인한다(이름에 8B, 70B처럼 붙어 있다).
2. 비트 수에 맞춰 곱한다. 4비트면 파라미터(B) × 0.5GB쯤, 8비트면 × 1GB, FP16이면 × 2GB.
3. 이 값이 내 VRAM보다 충분히 작은지 본다.

8B를 4비트로 하면 약 4~5GB니까 VRAM 8GB 카드에서도 후보가 된다. 70B는 4비트여도 약 35GB라서 24GB 카드 한 장으로는 가중치만으로도 모자란다. 이럴 때 llama.cpp의 CPU+GPU 혼합 실행이 선택지가 되는데, 문서에는 이게 일부를 가속해 준다고만 나와 있고 속도는 적혀 있지 않다.

여유를 남겨야 하는 이유는 가중치 말고도 메모리를 쓰는 게 있어서다. HF 문서는 긴 생성에서 KV 캐시 메모리를 아끼는 양자화 캐시 옵션을 따로 언급한다. 대화가 길어질수록 [컨텍스트 윈도](#/post/ai-context-window)만큼 캐시가 커진다는 얘기다. 그래서 가중치가 VRAM에 딱 맞는 크기보다는 한 단계 작은 모델·비트를 고르는 편이 안전하다. 같은 문서에는 하드웨어 메모리에 모델이 정밀도별로 들어가는지 보는 양자화 선택 Space도 링크돼 있다.

## 흔한 오해

- 양자화하면 모델이 똑똑해진다: 아니고, 정확도는 조금 떨어지는 쪽이다. 문서도 비트가 줄면 정확도 비용이 있다고 쓴다.
- 4비트면 품질이 반토막이다: GPTQ 논문 초록은 3~4비트에서 저하가 거의 없다고 한다. 모델과 작업에 따라 다르니 직접 재 보는 게 맞다.
- GGUF는 양자화 방법이다: 파일 형식이다. 파일 이름의 Q4_K_M 같은 부분이 양자화 종류를 나타낸다.
- 양자화와 증류는 같은 말이다: 위 표처럼 줄이는 대상이 다르다.
- 양자화된 모델은 파인튜닝을 못 한다: HF 문서에는 방법별로 파인튜닝 지원 여부를 비교하는 표가 있다고 나온다. 방법마다 다르다.
- 로컬에서 큰 모델은 무조건 느리다: 속도는 하드웨어와 양자화 방식에 따라 다르다. GPTQ 논문은 FP16 대비 3배 이상 빨라진 경우를 보고했고, 다만 이건 GPU 환경의 결과다.
