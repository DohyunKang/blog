计算机中只有 0 和 1。无论是数字、字母还是图片，本质上都是比特（bit）的组合。同样的比特组合，根据“按整数读”、“按小数读”或“按字符读”等不同的约定，会呈现出不同的值。本文将通过 Python 验证其中三种约定：整数（2 的补码）、实数（浮点数）和字符（Unicode 与 UTF-8）。关于 CPU 如何提取并计算比特组合的内容，将在 [CPU 与指令](#/post/ca-cpu) 中继续探讨。

## 比特组合与约定

8 个比特可以组成 256 种模式。为这些模式赋予意义的方式即为数据表示。相同的 `11111011`，作为无符号整数是 251，而作为有符号整数（2 的补码）则是 -5。比特本身未变，改变的只是解读方式。

| 解读约定 | `11111011` 的值 |
|---|---|
| 无符号整数 | 251 |
| 2 的补码整数 | -5 |
| 字符编码（如 Latin-1 等） | 根据代码表显示不同的字符 |

因此，打开文件时出现乱码的情况，往往不是比特损坏，而是解读约定不一致所致。在后续的字符编码部分将亲手实现验证。

## 整数：2 的补码

表达负数的方法中，目前几乎所有 CPU 都采用的是 2 的补码。在 n 位系统中，负数 -x 以 $2^n - x$ 的比特模式存储。例如在 8 位中，-5 等于 $256 - 5 = 251$，二进制表示为 `11111011`。在 Python 中使用 `n & 0xFF` 即可验证此结果。

```python
for n in (5, -5, -1, 127):
    print(n, format(n & 0xFF, '08b'))
# 5 00000101
# -5 11111011
# -1 11111111
# 127 01111111
print(int('11111011', 2) - 256)   # -5
```

虽然最高位为 1 代表负数，但这并非简单的符号位。可以将最高位的权重视为 -128。因此 `11111011` 等于 $-128 + 64 + 32 + 16 + 8 + 2 + 1 = -5$。

采用 2 的补码的原因是，仅需一个加法电路即可同时处理有符号和无符号数的运算。减法可转化为加上相反数。0 的表达也仅有一种（`00000000`）。n 位所能表示的范围是从 $-2^{(n-1)}$ 到 $2^{(n-1)} - 1$，因此负数多出一个。8 位数的范围是 -128 到 127。

超出范围则发生溢出。在 8 位中，给 127 加 1 会得到 `10000000`，这代表 -128。由于 Python 的整数没有长度限制，若要模拟此行为需手动应用掩码。

```python
x = (127 + 1) & 0xFF
print(x, x - 256 if x > 127 else x)   # 128 -128
```

C 或 Java 等语言中固定长度整数的溢出即为此类情况：数值绕了一圈后跳转到了另一端。

<details>
<summary>字节顺序（端序）</summary>

当整数由多个字节组成时，哪个字节先存放也是一种约定。例如 258 的十六进制为 `0x00000102`，大端序（Big Endian）从高位字节开始存放，而小端序（Little Endian）则从低位字节开始存放。

```python
print((258).to_bytes(4, 'big').hex())      # 00000102
print((258).to_bytes(4, 'little').hex())   # 02010000
```

在通过文件或网络传输数字时，双方必须约定相同的读取顺序。关于网络中发送比特的规则，可参考 [网络基础](#/post/cs-network) 继续了解。
</details>

## 实数：浮点数

小数比整数更复杂。由于需要在有限的比特中表示极大值和极小值，因此需像科学计数法一样将其分为符号、指数和尾数（有效数字）三部分存储。Python 的 `float` 遵循 IEEE 754 binary64（双精度），使用 64 位进行表示。

| 符号 | 指数 | 尾数 |
|---|---|---|
| 1 位 | 11 位 | 52 位 |

数值形式为 $(-1)^{\text{符号}} \times 1.\text{尾数} \times 2^{(\text{指数}-1023)}$。提取 1.0 和 -2.5 的比特进行验证，结果完全吻合。

```python
import struct
def bits(f):
    b = struct.unpack('>Q', struct.pack('>d', f))[0]
    s = format(b, '064b')
    return s[0], s[1:12], s[12:]

print(bits(1.0))
# ('0', '01111111111', '000...0')           지수 1023 → 2^0
print(bits(-2.5))
# ('1', '10000000000', '0100...0')          지수 1024 → 2^1, 1.25 × 2 = 2.5
```

1.0 的指数字段为 `01111111111`（即 1023），由此可知偏置值（bias）为 1023。-2.5 的符号位为 1，指数为 1024（即 $2^1$），尾数为 `01`，对应值为 1.25，再乘以 -1（符号反转）得到 -2.5。

### 为何 0.1 不准确

十进制的 0.1 在二进制中表示为 $0.000110011001100\dots$，会无限循环。由于尾数仅有 52 位（含隐含的 1 共 53 位），必须在某处截断并存储最接近的值。根据 Python 官方教程说明，实际存储的值并非 0.1，而是 $3602879701896397 / 2^{55}$，比 $1/10$ 略大。Python 显示为 `0.1` 是因为这是能循环表示的最短十进制形式。

```python
from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False
```

这并非 bug，而是表达方式的必然结果。无论在哪种语言中进行相同计算，只要使用 binary64，结果都会一致。比较时应避免直接使用 `==`，而应允许一定的误差范围。

```python
import math
print(math.isclose(0.1 + 0.2, 0.3))   # True
```

在必须进行精确十进制计算的场合（如货币计算），可采用将 `Decimal` 转换为字符串的方法。官方文档也建议在会计等用途中使用 `decimal` 模块。

### 大数旁消失的小数

由于尾数长度固定，数值越大，可表示值之间的间隔就越宽。从 $2^{53}$（9007199254740992）开始，连整数 1 都无法区分。

```python
print(2**53)                              # 9007199254740992
print(float(2**53) + 1 == float(2**53))   # True
print(1e16 + 1 == 1e16)                   # True
```

因此，大数加小数时，小数会消失。在累加大量数字的求和计算中，顺序之所以会影响结果，原因就在于此。

<details>
<summary>特殊值</summary>

如果指数字段全为 1，则表示无穷大或 NaN。超出范围会变成 `inf`，而像 `inf - inf` 这样的计算则会变成 `nan`。NaN 甚至不等于它自己。

```python
import sys
print(sys.float_info.max * 2)         # inf
print(float('inf') - float('inf'))    # nan
nan = float('nan'); print(nan == nan) # False
print(5e-324, 5e-324 / 2)             # 5e-324 0.0
print(sys.float_info.epsilon)         # 2.220446049250313e-16
```

`5e-324` 是可表示的最小正数，其一半则变为 0。`epsilon` 是 1.0 与下一个更大的 float 之间的差值。
</details>

## 字符：码点与编码

理解字符需要分两步思考，这样才不会混淆。首先，Unicode 为每个字符分配一个编号（码点）。接着，编码规则将这些编号转换为字节序列。码点和字节序列是两回事。

ASCII 是一个将 128 个英文字母和符号放入 7 比特的表。对于像韩语这样字符数量众多的文字，单个字节无法容纳，因此出现了如 EUC-KR 这样的国家专用编码；而将这些不同的编号体系统一起来的正是 Unicode。目前 Web 和 Python 3 的默认编码是 UTF-8。

### UTF-8 的长度是可变的

UTF-8 根据码点的大小使用 1 到 4 个字节。RFC 3629 定义的格式如下：

| 码点范围 | 字节数 | 比特模式 |
|---|---|---|
| U+0000 ~ U+007F | 1 | `0xxxxxxx` |
| U+0080 ~ U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 ~ U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 ~ U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

第一个字节开头的 1 的个数决定了总长度，后续字节总是以 `10` 开头。ASCII 范围只需一个字节即可表示，因此英文文本在 ASCII 和 UTF-8 中是相同的。

让我们用 '가' (U+AC00) 来验证一下。将码点 `1010110000000000` 填入 3 字节的框架中，得到 `1110 1010`, `10 110000`, `10 000000`。

```python
ch = '가'
print(hex(ord(ch)))                                  # 0xac00
print(format(ord(ch), '016b'))                       # 1010110000000000
print([format(b, '08b') for b in ch.encode()])
# ['11101010', '10110000', '10000000']
print(ch.encode('utf-8').hex())                      # eab080
```

十六进制数 `eab080` 等同于上述三个字节 (`ea` `b0` `80`)。'A' 占 1 个字节，'가' 占 3 个字节，而表情符号 (U+1F600) 则占 4 个字节。

```python
for ch in ('A', '가', '\U0001F600'):
    print(hex(ord(ch)), ch.encode('utf-8').hex(), len(ch.encode('utf-8')))
# 0x41 41 1
# 0xac00 eab080 3
# 0x1f600 f09f9880 4
```

### 字符数与字节数不同

```python
s = '한글'
print(len(s))                       # 2   글자(코드 포인트) 수
print(len(s.encode('utf-8')))       # 6   UTF-8 바이트 수
print(len(s.encode('euc-kr')))      # 4   EUC-KR 바이트 수
```

这就是为什么需要确认数据库列长度或 API 正文大小限制是基于字节还是基于字符的原因。UTF-16 将 '가' 存储为 2 个字节，将表情符号存储为 4 个字节（代理对），因此即使是相同的字符串，在不同编码下的长度也不同。

### 字符损坏的时刻

如果读取约定不一致，就会导致乱码。例如用 Latin-1 读取韩语 UTF-8 字节，或用 UTF-8 读取 EUC-KR 字节。

```python
s = '한글'
print(s.encode('utf-8').decode('latin-1').encode('unicode_escape'))
# b'\\xed\\x95\\x9c\\xea\\xb8\\x80'   Latin-1 글자 6개로 읽힘
print(s.encode('euc-kr').decode('utf-8', errors='replace').encode('unicode_escape'))
# b'\\ufffd\\u0471\\ufffd'            대체 문자(U+FFFD)가 섞임
try:
    b'\xea\xb0'.decode('utf-8')       # '가'의 3바이트 중 2바이트만
except Exception as e:
    print(type(e).__name__)           # UnicodeDecodeError
```

在用 UTF-8 读取时遇到不符合规则的字节，会产生错误或插入替代字符 (�)。这通常发生在文件被截断或编码识别错误的情况下。

<details>
<summary>码点不同的相同字符</summary>

'é' 可能是一个码点 (U+00E9)，也可能是由 'e' 后跟随组合重音符号 (U+0301) 的两个码点组成。在屏幕上它们看起来是一样的。

```python
import unicodedata
print(len('é'), len('é'))              # 1 2
print('é' == 'é')                       # False
print(unicodedata.normalize('NFC', 'é') == 'é')   # True
```

这就是为什么在搜索或比较时，有时需要先对字符串进行规范化处理的原因。
</details>

## 接下来看

| 对象 | 约定 | 一句话总结 |
|---|---|---|
| 整数 | 二进制补码 | 单个加法电路即可处理符号，超出范围则回绕 |
| 实数 | IEEE 754 | 由符号、指数和尾数组成，大多数十进制小数是近似值 |
| 字符 | Unicode + UTF-8 | 区分码点和字节，每个字符占用 1~4 个字节 |

由于位数固定而产生的限制（溢出、舍入误差、字节数差异）都源于此。这些值在寄存器、缓存、内存和磁盘之间是如何流转的，请参阅 [内存层次结构与缓存](#/post/ca-memory-hierarchy)。

## 常见误解

- 0.1 + 0.2 不等于 0.3 是 Python 的问题：Python 只是原样展示 binary64 值。如果需要精确的十进制运算，请使用 `decimal`。
- 负数仅是将最高位变为 1：在二进制补码表示中，最高位的权重为 -2^(n-1)，因此其余位也会随之变化。例如，-5 的二进制是 `11111011`，而不是 `10000101`。
- UTF-8 字符均为 3 字节：英文字符占 1 字节，韩文字符大多占 3 字节。UTF-8 混合使用 1 到 4 个字节。
- 字符数等于字节数：仅在纯 ASCII 编码时成立。两个韩文字符在 UTF-8 中占用 6 字节。
- 韩文字符显示乱码意味着数据已损坏：比特位本身未变，问题通常出在读取时的编码方式错误。
