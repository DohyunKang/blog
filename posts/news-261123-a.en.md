It's a bundle of skills that lets coding agents drive Stitch, Google Labs' AI screen design tool. ## What it is
A skill is a set of instructions an agent pulls out when it needs them. [More → Skills](#/post/ai-skills) Every skill here works through the Stitch MCP server. MCP is a connection standard that lets an agent call an outside service's features like tools. [More → MCP](#/post/ai-mcp) So installing the skills isn't enough. You have to set up Stitch's MCP first.

There are three plugins.

1. stitch-design: make and edit screens from text or images, move existing frontend code into a Stitch design, upload a DESIGN.md.
2. stitch-build: turn Stitch screens into React or React Native components, make a walkthrough video of the screens (Remotion).
3. stitch-utilities: polish vague requests into Stitch prompts, write DESIGN.md and SITE.md, and a loop that builds a multi-page site piece by piece.

Install is one `npx plugins add` line in Claude Code or Cursor, or a marketplace entry in Codex. The skills follow an open format (Agent Skills), so for OpenCode you can just copy the folders in.

## DESIGN.md sits in the middle
Almost every skill revolves around one file, DESIGN.md. It spells out design rules in words: colors, fonts, spacing, corner rounding. According to the design-md skill, Stitch understands design through "visual descriptions" backed by specific color values. So each new screen gets this file's content in its prompt, to match the earlier screens.

It goes both ways. Design to code: take a Stitch screen's HTML and split it into components. Code to design: code-to-design pulls a single HTML page from a running web app, pulls a DESIGN.md from the source, and uploads both to Stitch. So you can take something already built back into the design tool and rework it.

## A loop that keeps building the site
stitch-loop works like passing a baton. `.stitch/next-prompt.md` says which page to build next. The agent reads it, builds the page, wires it into the site, updates the site map (SITE.md), then writes the next page's task back into that file and stops. State lives in files, not in chat memory, so the next agent can pick it up even in a new session. If Chrome DevTools MCP is around, there's an optional step that opens the page, takes a screenshot, and compares it with the Stitch original.

## Rules in writing, some enforced by code
The react-components skill is pretty firm. Each phase has a GATE: don't move on until this is satisfied. Split components into files, move logic into hooks, move text and image URLs into mockData, and use theme classes instead of hex colors.

Some of this is actually checked by validate.js. It reads the code as a syntax tree (AST, code broken into structural pieces) and checks whether there's an interface whose name ends in Props, and whether a hex color like `#1a2b3c` is baked into className. The November 20 commits were fixes to this check: catch hex even when className is built from expressions, and reject web-only tags in React Native components. Not every rule is enforced. In the part of validate.js I read, it was those two things, Props interface and hex colors. The rest (splitting files, separating hooks) is a request in the docs.

## From a beginner's view
For a PM or a new developer, the DESIGN.md part is the interesting bit. Write design rules down as plain text, and it becomes the same standard for human designers and agents. It handles agents picking random colors on every screen with a file, not one more line in a prompt. Meta's Astryx, which I looked at earlier, also made agents read the design system docs first. [More → Astryx](#/post/news-261117-a)

That said, it's tied to one service, Stitch. The README ends by saying it's not an officially supported Google product. If you wonder why components get split up, I wrote about that before. [More → Components](#/post/fe-component)
