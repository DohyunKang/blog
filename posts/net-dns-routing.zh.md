网络中的“地址”有两种：人类输入的名称（如 `example.com`）和机器使用的编号（IP 地址）。DNS 负责将名称转换为编号，而路由则根据该编号将数据包转发到下一跳。在 [概述](#/post/cs-network) 中，我们仅将 DNS 简述为“单行翻译”，而在此处我们将深入其内部机制。

## DNS 是一棵树

DNS 的名称空间采用树状结构。基于 RFC 1034，每个节点都带有标签（label），某个节点的名称是由该节点到根节点路径上所有标签连接而成的。`www.example.com` 位于根节点下的 `com` 之下，再下是 `example`，最下层是 `www`。单个标签长度限制为 63 字节以下，整个名称长度限制为 255 字节以下。

这棵树并非由单一服务器完整持有，而是被切割成 **区域（zone）** 并由不同方分别管理。若某个组织声明直接管理其子域名，则该分支即构成一个区域，该区域的名称服务器即为 **权威（authoritative）服务器**。权威服务器仅响应其所属区域的数据。它返回的结果有三种：答案、错误，或是“请查询更近的服务器”的指引（referral）。

## 解析器与权威服务器

我们的 PC 不会直接从根节点开始查询。通常，我们会向 **递归（recursive）解析器** 发起一次询问。解析器会代为遍历并查询，最终仅返回答案或错误，而不会将诸如指引之类的中间结果提供给客户端。

解析器的工作流程大致如下：

| 步骤 | 操作 |
|---|---|
| 1 | 检查缓存。若存在则直接返回答案 |
| 2 | 若不存在，则向已知的服务器中最近的一台询问；若不知晓，则从根服务器开始 |
| 3 | 遵循收到的指引，从 `com` 向下导航至 `example.com` 方向的服务器 |
| 4 | 从权威服务器获取答案，存入缓存并返回给客户端 |
| 5 | 若答案为 CNAME（别名），则以该名称重新开始查询流程 |

缓存有效期由记录上附加的 **TTL**（以秒为单位）决定。TTL 为 0 表示不应缓存。“名称不存在”的答案同样可以被缓存。因此，即使更改了 DNS 记录，也无法立即在全球生效，因为已缓存的解析器在 TTL 过期前仍会持有旧值。

主要记录类型如下（RFC 1035）：

| 类型 | 内容 |
|---|---|
| A | 主机的 IPv4 地址 |
| NS | 该区域的权威名称服务器 |
| CNAME | 别名指向的原始名称 |
| MX | 邮件服务器及其优先级 |
| TXT | 字符串 |

## 手动构建 DNS 查询

DNS 查询本质上是一个小的字节块。在包含 12 字节的头部（ID、标志位、问题/回答/授权/附加计数各占 2 字节）后，只需附加一个问题即可。名称不使用点号，而是采用“长度 + 字符”的组合形式，并以长度为 0 的标记结束。下面使用 Python 构建查询，并通过 UDP 发送至公开解析器（8.8.8.8）的 53 端口。

```python
import struct, socket

def build(name, qtype=1, id=0x1234):
    hdr = struct.pack('!HHHHHH', id, 0x0100, 1, 0, 0, 0)  # 0x0100 = RD(재귀 요청) 비트
    q = b''.join(bytes([len(l)]) + l.encode() for l in name.split('.')) + b'\0'
    return hdr + q + struct.pack('!HH', qtype, 1)          # 타입 A, 클래스 IN

pkt = build('example.com')
print(pkt.hex())
# 123401000001000000000000076578616d706c6503636f6d0000010001
```

输出中 `07 6578616d706c65` 表示长度为 7 的 `example`，`03 636f6d` 表示 `com`，`00` 表示结束。发送此数据包并解析收到的响应后，结果如下：

```
('example.com', A, TTL 300, '104.20.23.154')
('example.com', A, TTL 300, '172.66.147.243')
```

返回了两个地址，TTL 为 300 秒。具体数值可能因执行时间和位置而异。响应解析代码见下方折叠部分。

<details>
<summary>响应解析代码（含压缩指针处理）</summary>

在响应中，若出现重复的名称，则不重复书写，而是使用指向前方位置的 2 字节 **指针**（RFC 1035 中的压缩）。前两位为 `11` 时即表示指针，其余 14 位表示从消息起始处的偏移量。

```python
def name_at(d, o):
    parts, end = [], None
    while True:
        l = d[o]
        if l == 0:
            o += 1; break
        if l & 0xC0 == 0xC0:                    # 압축 포인터
            ptr = ((l & 0x3F) << 8) | d[o+1]
            if end is None: end = o + 2
            o = ptr; continue
        parts.append(d[o+1:o+1+l].decode()); o += 1 + l
    return '.'.join(parts), (end if end is not None else o)

def parse(d):
    id, fl, qd, an, ns, ar = struct.unpack('!HHHHHH', d[:12]); o = 12
    for _ in range(qd):
        n, o = name_at(d, o); o += 4
    out = []
    for _ in range(an):
        n, o = name_at(d, o)
        t, c, ttl, rl = struct.unpack('!HHIH', d[o:o+10]); o += 10
        v = socket.inet_ntoa(d[o:o+4]) if t == 1 else (name_at(d, o)[0] if t == 5 else d[o:o+rl].hex())
        out.append((n, t, ttl, v)); o += rl
    return fl & 0xF, out        # (RCODE, 답 목록)

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.settimeout(3)
s.sendto(pkt, ('8.8.8.8', 53))
print(parse(s.recvfrom(512)[0]))
```

UDP 消息长度限制为 512 字节以下；若超出则会被截断发送，并设置 TC（truncated）标志位，正如 RFC 1035 所述。关于 [UDP 与 TCP 为何分离](#/post/net-tcp-udp) 的内容已另行整理。

</details>

从代码中可直观看出 DNS 运行于 UDP 之上：无需建立连接阶段，仅通过一次 `sendto` 即可发送查询，一次 `recvfrom` 即可接收响应。TCP 中使用相同套接字 API 的情形将在 [套接字编程](#/post/net-socket) 中继续探讨。

## IP 地址与子网

IPv4 地址是 32 位数字。为方便人类阅读，将其每 8 位截断并以 `192.168.10.70` 的形式书写。该地址分为前部分（网络）和后部分（该网络内的主机）。哪一部分属于前段由 **前缀长度** 表示。例如 `192.168.10.0/26` 表示前 26 位为网络部分。这是 RFC 4632 中定义的 CIDR 表示法，不同于旧式的 A、B、C 类那样大小固定，只要块的大小是 2 的幂次方，即可使用任意大小的块。

已通过 Python 标准库 `ipaddress` 进行验证。

```python
import ipaddress
n = ipaddress.ip_network('192.168.10.0/26')
print(n.netmask, n.network_address, n.broadcast_address, n.num_addresses)
# 255.255.255.192 192.168.10.0 192.168.10.63 64
print(list(n.hosts())[0], list(n.hosts())[-1])        # 192.168.10.1 192.168.10.62
print(ipaddress.ip_address('192.168.10.70') in n)     # False
print(list(ipaddress.ip_network('192.168.10.0/24').subnets(new_prefix=26)))
# [192.168.10.0/26, 192.168.10.64/26, 192.168.10.128/26, 192.168.10.192/26]
print(ipaddress.ip_address('10.1.2.3').is_private, ipaddress.ip_address('8.8.8.8').is_private)
# True False
```

- `/26` 是一个包含 $2^6$（即 64）个地址块的 CIDR 表示法。其中，开头（.0）和结尾（.63）分别是网络地址和广播地址，不能用于主机分配，因此可用的主机地址范围是 .1~.62，共 62 个。
- `192.168.10.70` 位于该块之外，属于下一个块 `192.168.10.64/26`。
- 将 `/24` 划分为 `/26` 会得到四个子网。子网划分就是通过增加前缀长度（prefix length）将大地址块拆分为小地址块的过程。
- 像 `10.x.x.x` 这样的私有地址段，其 `is_private` 属性为 True；而公有的 IP 地址如 8.8.8.8 则为 False。

<details>
<summary>"前 26 位"以二进制形式查看</summary>

```python
print(bin(int(ipaddress.ip_address('192.168.10.70'))))
# 0b11000000101010000000101001000110
```

将其调整为 32 位二进制表示为 `11000000 10101000 00001010 01000110`。前 26 位是 `11000000 10101000 00001010 01`，该值与 `192.168.10.64` 的前 26 位相同。因此，70 属于 `.64/26` 这个块。子网掩码 `255.255.255.192` 是将前 26 位全部置为 1 的结果（最后一个字节 `11000000` = 192）。

</details>

## 路由：最长匹配优先

路由器收到数据包后，会根据目的 IP 地址查看**路由表**。路由表列出了“前往该前缀的数据包应转发至何处”的条目。当多个条目同时匹配时，规则是**最长前缀匹配（longest-match）**优先。RFC 4632 也指出，在存在重叠路径时，更具体的路径具有优先级。

我构建了一个简单的路由表并进行了模拟测试。

```python
import ipaddress
table = [('0.0.0.0/0', 'A'), ('10.0.0.0/8', 'B'), ('10.1.0.0/16', 'C'), ('10.1.2.0/24', 'D')]
tbl = [(ipaddress.ip_network(p), h) for p, h in table]

def lookup(ip):
    ip = ipaddress.ip_address(ip)
    c = [(n, h) for n, h in tbl if ip in n]
    return max(c, key=lambda x: x[0].prefixlen)

for ip in ['10.1.2.9', '10.1.9.9', '10.9.9.9', '8.8.8.8']:
    n, h = lookup(ip); print(ip, '->', n, h)
```

```
10.1.2.9 -> 10.1.2.0/24 D
10.1.9.9 -> 10.1.0.0/16 C
10.9.9.9 -> 10.0.0.0/8 B
8.8.8.8 -> 0.0.0.0/0 A
```

`10.1.2.9` 虽然匹配了四项中的三项（/8、/16、/24），但由于 /24 最为具体，因此数据包会被转发至 D。`0.0.0.0/0` 的前缀长度为 0，可以匹配任何地址。当没有其他条目匹配时，最后匹配的这条**默认路由（default route）**就是它。

上述代码为了演示概念，采用了遍历所有条目的方式。

## 为什么要进行前缀聚合

路由器无法存储全球每一个 IP 地址的详细信息。因此，需要将地址按照互联网服务提供商（ISP）的结构进行划分，并由 ISP 将其客户的地址块聚合成一个大的前缀进行通告（aggregation）。RFC 4632 指出，通过这种方式，即使某个 ISP 的客户数量增加，外部路由器也只需知晓一条路由条目即可。文档同时也提到了局限性：对于拥有多线连接或更换了 ISP 但未更改 IP 地址的网站，必须单独发布路由信息，否则会导致聚合失效。

最长匹配原则也存在副作用。由于更长前缀优先，如果有人在他人地址块的基础上虚假通告更具体的路径，流量可能会泄露到该错误路径中。RFC 建议采用路径过滤和前缀数量限制作为应对措施。

## 从名称到数据包

将上述过程串联起来，浏览器地址栏中的一行 URL 解析如下：

1. 浏览器向操作系统中的 DNS 解析器询问 `example.com`。
2. 解析器检查缓存；若未命中，则从根域名服务器开始逐级向下查询至权威服务器，获取 IP 地址。
3. 使用该 IP 建立 TCP 连接。数据包的目的字段填入该 IP 地址。
4. 当数据包离开本机时，会使用本地的路由表。若目的地址位于同一子网则直接发送，否则通过默认路由的网关转发。
5. 路径上的各个路由器均依据最长匹配原则确定下一跳。

从分层角度看，DNS 属于应用层，而 IP 和路由属于网络层（Internet Layer）。这一区分在 [OSI 与 TCP/IP](#/post/net-osi-tcpip) 中有专门讨论。至于 HTTP 如何在上述协议之上进行通信，请参阅 [HTTP](#/post/net-http)。

<details>
<summary>几个常见的误解</summary>

- "DNS 只有一台全球服务器"：DNS 是基于域的分布式结构，每个域名都有各自负责的权威服务器。
- "修改记录后立即生效"：已经缓存的解析器在 TTL（生存时间）过期前仍会使用旧值。
- "IP 地址即地理位置"：前缀是根据 ISP 的结构划分的，路由器仅根据前缀决定下一跳，而非精确的物理位置。
- "子网主机数等于 $2^n$"：必须减去网络地址和广播地址，因此 /26 并非 64 个可用地址，而是 62 个（见上文代码）。
- "路由器知道通往目的地的完整路径"：每个路由器仅决定下一跳。

</details>
