## どういうものか
FFmpeg は動画や音声ファイルを切ったり変換したりする古いコマンドラインのプログラムだ。機能は多いがオプションが複雑で、エージェントが自分でコマンドを組むと間違えやすい。README の「Why」がまさにそこを指している。FFmpeg を「知っている」エージェントでも、フレームレートを推測し、コンテナに入らないコーデックを選び、結果を開きもせずに「できました」と報告する、と。

だからこのリポジトリは、FFmpeg のコマンドをエージェントに組ませない。切り出し(cut)、結合(join)、無音カット(silence)、画面比率合わせ(fit)、字幕(caption)、音量(loudness)、プラットフォーム向け書き出し(export)などを、一つずつ Python スクリプトにしてある。全部で 42 個。エージェントはスクリプト名と決まった引数だけを渡す。シェルは通らないし、呼び出し側が FFmpeg のフィルタ文字列を直接渡すことも受け付けない。Python の標準ライブラリだけで動き、クラウドも API キーもいらない。

スキルはエージェントが必要なときに取り出して読む説明書だ。[詳しく → スキル](#/post/ai-skills) 同じツールを MCP サーバーとしても公開している。MCP はエージェントが外のプログラムの機能をツールのように呼べるようにする接続規格だ。[詳しく → MCP](#/post/ai-mcp)

## 測って、やって、また測る
README が描く流れはこうだ。依頼が来ると、エージェントが SKILL.md を読んで合うスクリプトを選ぶ。スクリプトは実行前に必要な FFmpeg の機能がこのマシンにあるか確かめ、FFmpeg を動かし、書き出したファイルを測り直して JSON で返す。

設計原則の一行目は「Probe first」。probe はファイルを実際に開いて、長さ、フレームレート、解像度、色の情報、音声トラックを測ること。ファイル名で判断するな、という意味だ。全ツールに `--dry-run` もある。実行する FFmpeg コマンドを表示するだけでファイルは書かない。既存ファイルを上書きするには `--overwrite` を明示する必要がある。

面白かったのは結果に付く `unverified` のリストだ。ツールは測れたものだけを「確認済み」とする。長さ、コーデック、音量などは測り直して合っているか見る。逆に、画面に何が映っているか、字幕が読めるか、カットした区間に声があったか、口の動きと音が合っているかは、ファイルを測っても分からない。そういう項目は確認できなかったものとして別に書いて返す。値が読めなければ合格ではなく `not_measured` で失敗にする。画面が変わる作業なら、look.py で数フレームを並べた画像(コンタクトシート)を作って目で見るよう指示する。

## 契約書をコードから作る
`contract --json` を実行すると、42 個のツールそれぞれについて、何を受け取り、何を返し、どの FFmpeg の部品が必要で、結果を何で検証するかを書いた文書が出てくる。README はこれを機械が読む契約書(machine-readable contract)と呼んでいる。人が別に管理するのではなく、各スクリプトの引数定義(argparse)から自動で作る。MCP サーバーのツール一覧もここから出る。だからスクリプトに引数を一つ足せば、MCP 側は触らなくても変わる。テストでそれを確かめていると書いてある。

文書どうしで数字がずれるのもテストで防いでいる。contract.md によると、README、SKILL.md、package.json に書かれた「42」という文字を、毎回 scripts フォルダの実際のツール数と比べる。SKILL.md に「28」という古い数字が、ツールが十二個増える間ずっと残っていたことがあって入れたそうだ。

42 個全部をエージェントに見せるわけではない。MCP の標準リストにはよく使う 12 個だけを出し、残りの 30 個は必要なときに名前で呼ぶ。4.0 からこの 12 個は stable(次のメジャーバージョンまで引数名や出力名を変えない)、残りは beta に分けた。

## なぜ今話題なのか
リポジトリは 9 月初めにできた。新しいものではない。ただ今週ずっとトレンドに載っていて、コミットが毎日積み上がっている。11月22日の一日だけで 4.5.3 から 4.7.0 までバージョンが何度も上がり、私が見た最新は 4.7.1 だった。npm のダウンロードは 11月16〜22日の一週間で 17,832 回。「ffmpeg-skill」に触れた X の投稿(リツイート除く、UTC の一日単位)は 11月17日の 103 件が最多で、その後は一日 28〜50 件。スターが伸び始めたきっかけは確認できていない。Reddit の反応も確認できていない。

README には自前の評価記録が長く載っている。プロンプトを数十個から 100 個まで増やしながらエージェントを動かし、別のモデルに採点させた。1.17.0 時点で 100 個のプロンプトに対し「生の FFmpeg 呼び出し 0 回、偽の成功報告 0 回」とある。点数だけでなく、どこで間違え、次のバージョンで何を直したかまで残している。ただ、これは作者自身が測った数字だ。他の人が再現したかは確認できていない。README も、実機映像の全セットのテストは Windows ではまだ回していないと明かしている。

## 入門者の立場から
動画編集そのものより構造が面白かった。エージェントに「気をつけて」と文章で頼む代わりに、間違えやすい作業はスクリプトが受け持ち、結果は測り直し、測れないものは測れないと書いて返す。前に見たアリババの Open Code Review も、間違えてはいけない段階はコードに任せる方向だった。[詳しく → Open Code Review](#/post/news-261115-a)

PM として使えそうなのは `unverified` のような発想だ。「完了」という報告一つを受け取る代わりに、何を確認して、何を人が見るべきかを一緒に受け取る。エージェントの結果をレビューするときに見る場所が減る。README も、このツールは編集を「実行」するだけで、どこを切るかや結果がいいかどうかは人か別のエージェントが決める、と線を引いている。
