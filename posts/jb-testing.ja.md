ソフトウェアテストの単元は用語が多すぎて覚えたくないが、3 つの軸に分ければ大部分の用語は自ずと位置づけられる。コードの中を見るか（ホワイトボックス・ブラックボックス）、どの段階で行うか（テストレベル）、コードをどれだけ走査したか（カバレッジ）だ。試験日程や受験料は公式サイトで確認し、ここでは概念と問題解き方の整理のみ行う。

## まず全体像

| 軸 | 質問 | 代表的な用語 |
|---|---|---|
| 方式 | コード内部を見て設計するか | ホワイトボックス、ブラックボックス |
| ステージ | どの範囲をまとめて見るか | ユニット、統合、システム、受入 |
| 尺度 | コードをどれだけ実行したか | 文脈、決定、条件、MC/DC カバレッジ |

[要件を先に確認したい場合は → 要件分析](#/post/jb-requirements)

## ブラックボックスとホワイトボックス

ブラックボックステストは実装を知らずに「この入力ならこの出力であるべき」とケースを作成する。仕様に基づくため機能テストがほとんどで、通常ユニットレベルではあまり使わない。ホワイトボックステストは逆に内部構造やコードを見て、コードのパスを通るように入力を選定する。構造ベースであり、グラスボックスとも呼ばれる。仕様にはあるが実装が抜けている機能はホワイトボックスでは捉えにくい。

### ブラックボックス技法

試験でよく問われる技法は、名前と一行の説明をセットにして暗記するタイプだ。

| 技法 | 一行 |
|---|---|
| 同値分割 | 入力を取り扱われる区間に分け、各区間に代表値 1 つだけ使う |
| 境界値分析 | 区間の境界とその直前直後の値を使う |
| 原因 - 結果グラフ | 入力（原因）と出力（結果）の関係をグラフ・決定表で作る |
| エラー予測 | 経験からエラーが起きそうな箇所を指摘する |
| ステート遷移 | ステートとイベントの流れでケースを作成する |
| 比較テスト | 同じ入力を複数の実装に投入して結果を比較する |

点数が 60 以上なら合格というルールで見れば、同値分割は「59 以下の区間」と「60 以上の区間」の 2 つに分け、境界値は 59, 60, 61 を使う。コードで回すとこうなる。

```python
def grade(score, bonus):
    if score >= 60 and bonus:
        return "A"
    if score >= 60:
        return "B"
    return "C"

for s in (59, 60, 61):
    print(s, grade(s, False))
# 59 C
# 60 B
# 61 B
```

境界で結果が変わる点が 60 であることは、59・60 の 2 つの値からすぐに明らかになる。境界値分析が `>=` を `>` と誤ったバグをよく捉える理由はここにある。

### ホワイトボックス技法

ホワイトボックスは「カバレッジ基準」とほぼ同じ意味で読める。どの基準でコードを走査するかが技法名になる。以下のカバレッジ節で続きを見る。技法の中には基本パステストも含まれる。制御フローグラフから独立したパスを取り出してテストし、そのパス数の基準が循環複雑度だ。

<details>
<summary>循環複雑度の計算</summary>

循環複雑度 V は制御フローグラフにおいて V = E - N + 2（辺の数 - ノードの数 + 2）で求める。判断（分岐）ノードを持つ単純な構造であれば、判断文数 + 1 と等しい。上記の `grade` 関数は if が 2 つあるので V = 3 で、独立パスも 3 つある（A で終わるパス、B で終わるパス、C で終わるパス）。問題は通常、グラフを描いて V を問う形式で出題される。

</details>

## テストレベル

開発段階とセットで見ると整理しやすい。

| レベル | 範囲 | キーワード |
|---|---|---|
| ユニット | モジュール・関数 1 つ | ドライバー、スタブ |
| 統合 | モジュール間のインターフェース | 底上げ、トップダウン、ビッグバン |
| システム | 全体システム | 機能・性能・セキュリティ |
| 受入 | ユーザー・顧客基準 | アルファ、ベータ |

ユニットテストは隔離されたコードが期待通りに動作するかを見るため、周辺モジュールがまだなければ代わりに動く偽物が必要だ。呼び出す側を模倣するのがドライバー、呼び出される側を模倣するのがスタブだ。統合テストはトップダウンならスタブが必要で、ボトムアップならドライバーが必要というペアが試験によく出る。この方向性は [アーキテクチャパターン](#/post/jb-architecture-pattern) で見る階層構造を思い浮かべれば混乱しない。

受入テストはユーザーが要件に合致するか確認する段階だ。開発者環境でユーザーが行うアルファと、実際のユーザー環境で行うベータに分けて問われる。

その他、名前だけで登場するものもある。

- 回帰テスト：修正後、既存機能が壊れていないか再確認すること
- スモークテスト：ビルドが基本的に動くかを素早く確認すること
- 性能・負荷・ストレステスト：処理量と限界を見ること

回帰・スモークはビルドが頻繁に行われる環境では自動で回すことが多い。[バージョン管理とビルド・デプロイ](#/post/jb-build-release) とセットで見ると流れが繋がる。

## カバレッジ

カバレッジはテストがコードをどれだけ実行したかの尺度だ。基準が強くなるほどケースが必要になる。

| 기준 | 満たす条件 |
|---|---|
| 文 (Statement) | すべての文を少なくとも一度実行する |
| 決定 (分岐) | 全ての判断の結果が真・偽をそれぞれ少なくとも一度持つ |
| 条件 | 判断内の個々の条件が真・偽をそれぞれ少なくとも一度持つ |
| 条件/決定 | 決定カバレッジと条件カバレッジの両方を満たす |
| 変更条件/決定 (MC/DC) | 各条件が結果を独立して変化させることを示す |
| 多重条件 | 条件の全ての組み合わせ |

MC/DC は、航空のような安全性が重要な分野で要求されることが多いと知られている。パスカバレッジは、可能なすべてのパスを通過する基準である。

### 同じ関数での比較

条件カバレッジと決定カバレッジの違いは、試験で最も混同しやすいポイントなので、`grade` 関数を使って実際に確認してみた。

```python
# 결정 커버리지: 두 if가 각각 참/거짓이 되게
dec = [(70, True), (70, False), (50, False)]
print([grade(*c) for c in dec])   # ['A', 'B', 'C']

# 조건만 맞춘 두 케이스: score>=60 이 T/F, bonus 가 T/F
cond = [(70, False), (50, True)]
print([grade(*c) for c in cond])  # ['B', 'C']
```

2 つ目のケースのグループでは、`score >= 60` と `bonus` がそれぞれ真・偽を一度ずつ経験しているため、条件カバレッジは満たされている。しかし、最初の if の全体条件式 (`score >= 60 and bonus`) は一度も真にならなかった。つまり、「A」が出力されるパスを誰も通っていないのである。条件カバレッジを満たしても決定カバレッジを満たせない可能性があることを意味しており、そのため両者を組み合わせた「条件/決定」基準が別途存在する。

<details>
<summary>解法のポイント</summary>

カバレッジの問題は、通常コードやフローチャートが提示され、「このテストセットがどの基準を満たしているか」、あるいは「文カバレッジに必要な最小ケース数は」のように問われる。手順は以下の通りである。

1. 各判断文について、真・偽になる入力を表にまとめる。
2. 与えられたケースを一つずつ代入し、文・分岐・条件が通ったかを示す。
3. 欠けている欄があれば、その基準は満たされていない。
4. 最小ケース数は、真/偽のパスが重複しないようにまとめて数える。

上記の `grade` では、文カバレッジは `(70, True)` のケース一つで最初の if の A は通るが、B と C の文は通らず、A・B・C をすべて通らせるには 3 つ必要である。このように直接代入して確認する方が、暗記するよりも速い。

</details>

## よくある誤解

- カバレッジが 100% であるからといって、バグがないわけではない。カバレッジは「実行したか」を示すもので、「期待された結果を確認したか」を示すものではない。
- ブラックボックスは、コードを知らないからテストが弱いというわけではなく、仕様基準で見る手法に過ぎない。欠落している機能こそがブラックボックスによって検出される。
- ドライバーとスタブは混同しやすい。上から呼び出すものはドライバー、下から呼び出されるものはスタブとして覚えるとよい。

## まとめ

概念をすべて暗記しようとせず、3 つの表を頭に入れて問題を解けばよい。コードが出たらケースを直接代入して確認する。
