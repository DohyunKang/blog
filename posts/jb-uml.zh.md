UML 是一种用于绘制软件的标准图形化表示法，在信息处理技术员考试中，图表类型的区分、类关系符号以及用例图与序列图的识读是核心章节。本文是为备考整理的资料。需求提取阶段已在 [详细 → 需求确认与分析](#/post/jb-requirements) 中首先讨论过。

## UML 是什么

UML（Unified Modeling Language）是一种用于绘制系统模型的标准语言。OMG 于 1997 年将其采纳为标准并进行管理，ISO/IEC 于 2005 年将其发布为 ISO/IEC 19501。此后正式版本为 2.5.1（2017 年 12 月采纳）。

UML 2 定义了 14 种图表。记忆时将其分为两类较为方便。

| 分类 | 绘制内容 | 7 种图表 |
|---|---|---|
| 结构 (Structure) | 系统由哪些部件组成（静态） | 类、组件、复合结构图、部署图、对象图、包图、配置文件 |
| 行为 (Behavior) | 随时间如何变化（动态） | 用例图、活动图、状态机图、序列图、通信图、交互概览图、时序图 |

行为类中的序列图、通信图、交互概览图和时序图四者常被统称为交互 (interaction) 图表。

考试中常出现“这张图是什么图表”、“属于静态模型还是动态模型”之类的分类题，只需准确掌握上表中左侧和右侧的归属即可。容易混淆的点是：部署图属于结构类，用例图属于行为类。

## 用例图

在一张图上绘制使用系统的人员与系统所提供的工作内容。

- **参与者 (actor)**：用户或外部系统。通常画成火柴人形状。
- **用例**：系统提供的单个功能。用椭圆或圆角矩形绘制。
- **系统边界**：包围用例的矩形框，展示系统的范围。

用例之间的关系通过在虚线箭头上添加标签来表示。

| 关系 | 含义 | 箭头方向 |
|---|---|---|
| include | 基本用例从正常流程中引入公共功能 | 基本 → 被包含方 |
| extend | 当条件满足时，在基本功能上添加可选动作 | 扩展方 → 基本 |
| 泛化 | 子类扩展并重定义父类 | 子类 → 父类（三角形头部） |

记住 include 是像登录验证那样始终经过的部分，extend 是像“密码错误”那样偶尔插入的部分，这样有助于减少方向混淆。注意 extend 的箭头指向基本方。

## 类图

这是结构图中使用最频繁的图表。类由三个区域的框（名称、属性、操作）绘制，并在成员前添加访问修饰符符号。

| 符号 | 访问级别 |
|---|---|
| + | public |
| - | private |
| # | protected |
| ~ | package |

多重性 (multiplicity) 写在关系线的末端。1 表示恰好一个，0..1 表示零个或一个，0..* 或 * 表示零个或多个，1..* 表示一个或多个。紧接着的六种关系是本章节的核心。

| 关系 | 文字描述 | 形状 |
|---|---|---|
| 关联 (association) | 类之间结构上的连接 | 实线 |
| 聚合 (aggregation) | has-a，部分可独立存在 | 整体端为空心菱形 |
| 组合 (composition) | 更强的 has-a，整体消亡则部分随之消失 | 整体端为实心菱形 |
| 泛化 (generalization) | is-a，继承 | 实线 + 指向父类的空心三角形 |
| 实现 (realization) | 实现接口 | 虚线 + 指向接口的空心三角形 |
| 依赖 (dependency) | 一方变化影响另一方的弱关系 | 虚线 + 开放箭头（使用方 → 被使用方） |

容易混淆的是聚合与组合，以及泛化与实现。菱形是空心还是实心取决于生命周期是否一致。三角形均为空心，实线表示继承，虚线表示实现。先确定线条形状，再判断头部形状，这样能减少错误。

不过无论考试中以何种术语出现（英文或中文），只需记住每个定义句子即可。转换为代码的感觉将在 [详细 → 面向对象与语言代码阅读](#/post/jb-oop-lang) 中继续展开。

## 序列图

从上到下按时间顺序绘制对象之间发送消息的顺序。

- 生命线 (Lifeline)：表示对象或过程的垂直线。如果下方有 X，则表示该对象已消失。
- 消息 (Message)：在水平箭头旁标注消息名称。实心箭头头表示同步（调用方需等待直到结束），空心箭头头表示异步（不等待，继续执行），虚线表示响应（返回）。
- 激活条 (Activation bar)：生命线上方细长的矩形框，表示该对象正在处理消息的时段。若对象调用自身，则框体会重叠堆叠。
- 组合片段 (Combined fragment)：用于将并行、条件分支或选择行为等流程组合在一起表示的框体。

题目通常通过观察图形来询问“第几条消息属于何种类型”、“哪个对象接收了调用”等，因此区分箭头形状和虚线响应的练习最为直接有效。

以在线下单为例，相同的内容在三张图中呈现方式各不相同。

- 用例图 (Use Case)：包含“客户”和“支付代理”两个参与者，用例包括“下单”和“支付”。“下单”包含“登录检查”，“应用优惠券”扩展了“支付”。用例位于系统边界内，参与者则置于边界外。
- 类图 (Class)：订单 (Order) 与订单项 (OrderItem) 因订单项若无订单则无意义，故用组合关系表示；订单与客户 (Customer) 之间为关联关系。多重性为客户 1 对应订单 0..*。若卡支付类实现了支付方式接口，则用虚线加空心三角形表示。
- 序列图 (Sequence)：客户 → 订单服务发送“订单请求”（同步），订单服务 → 支付模块发送“支付请求”，随后通过虚线返回“支付结果”响应。若不等待通知而直接发送，则绘制为空心箭头头的异步消息。

同一系统中，“谁做了什么”由用例图负责，“拥有什么”由类图负责，“何时向谁说了什么”由序列图负责。阅读题目时，先判断问题属于这三者中的哪一类，解题速度会更快。

## 面向对象分析中的直觉

面向对象分析是从需求中提取对象候选（名词）及其行为（动词），并将其整理为类的过程。先用用例图确定功能范围，再用类图定义静态结构，最后用序列图验证场景，这一顺序最为自然。在此阶段确定的结构，将成为后续 [深入 → 软件架构](#/post/jb-architecture-pattern) 与 [深入 → 设计模式](#/post/jb-design-pattern) 的材料。

## 常见混淆点

- 聚合与组合的菱形形状相同：空心菱形表示部分可独立存在，实心菱形表示整体消失时部分也随之消失。
- 泛化与实现三角形的形状相同：实线表示继承（泛化），虚线表示实现。
- include 与 extend 的箭头方向相反：include 指向被包含方（从基用例到包含用例），extend 指向被扩展方（从扩展用例到基用例）。
- 部署图与组件图属于行为方面：实际上两者均属于结构方面。
