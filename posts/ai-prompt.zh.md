提示（Prompt）是指传递给模型的全部输入，而提示工程则是调整该输入以引导模型输出期望结果的过程。经过梳理，真正被证实有效的技巧寥寥无几，其余的要么随着模型的迭代而意义淡化，要么已被夸大。

## 什么是提示

人们很容易认为，向聊天机器人提出的那一行问题就是提示。准确地说，提示是模型在生成回答之前接收到的所有文本。[LLM](#/post/ai-llm) 是一种续写下一个 token 的模型，因此前面的内容决定了后续生成的文字。提示工程归根结底就是在思考“前面应该放什么”。

如果使用 API，输入通常分为两层：

| | 系统提示 (System Prompt) | 用户提示 (User Prompt) |
|---|---|---|
| 使用者 | 应用开发者 | 应用使用者（或由代码填充） |
| 内容 | 角色、语气、规则、输出格式 | 本次要处理的提问、文档或数据 |
| 变更频率 | 几乎固定不变 | 每次请求都会变化 |

系统提示是贯穿整个对话的基础设置，而用户提示则是针对具体请求的内容。从模型的角度看，两者最终都是输入文本，但由于 API 会加以区分接收，因此将规则放在系统提示中已成为惯例。

## 经证实有效的技巧

Anthropic 文档中的提示指南反复强调的要点如下：

### 1. 表述清晰，并说明原因

这看似平常，却效果显著。文档中给出的例子很有说服力：与其说“不要使用省略号”，不如说“这个回答将由语音合成器朗读，因为它不懂如何朗读省略号，所以请不要使用”。提供理由能让模型将这种意图应用到其他类似情况。这与向人布置任务时同理。

### 2. 加入示例（Few-shot）

这是一种在提示中直接展示若干输入与输出对的方式。如果不给示例仅给出指令称为 zero-shot，若提供示例则称为 few-shot。GPT-3 论文 (Brown et al., 2020) 表明，只需通过文本提供的示例即可让模型在不调整任何权重的情况下解决新任务，这便是 few-shot 提示的起点。指南认为这是最可靠的方法之一用于统一格式、语气和结构，并建议提供 3~5 个示例。条件是示例应贴近实际使用场景、彼此多样化，并用 `<example>` 标签将其与指令区分开。

有一项有趣的研究：Min 等人 (2022) 发现，即使随机打乱示例中的答案标签，性能也不会大幅下降（测试了 12 个模型，涵盖分类和选择题任务）。他们认为影响性能的并非标签是否正确，而是标签的候选范围、输入文本的分布以及整体格式。因此，示例更接近于“展示回答的格式”，而非“教授正确答案”。不过，这仅限于该论文所研究的任务范围内。

### 3. 明确结构与输出格式

当指令、上下文、示例和输入数据混杂在一个提示中时，模型可能会混淆哪些部分是指令。指南建议使用 `<instructions>`、`<context>`、`<input>` 等标签分别包裹不同类型的内容。对于输出格式，最好直接指定：例如“以 JSON 格式”、“不要加引言”、“用表格形式”等。如果需要通过代码处理格式，指南推荐使用 API 的结构化输出或工具调用功能，而非在提示中请求。

### 4. 长文档放前面，问题放最后

当附加较长文档时，应将文档放在前面，问题置于末尾。指南指出，将问题放在结尾可使响应质量最高提升 30%，但这来自测试结果，尤其适用于包含多个文档的复杂输入场景。由于该数值带有特定条件，不宜直接泛化。

### 5. 引导推理

Wei 等人 (2022) 在 chain-of-thought (CoT) 论文中报告称，若在示例中包含解题过程，可提升算术、常识及符号推理能力。他们指出，仅用 8 个示例即可让 540B 模型在数学基准 GSM8K 上达到当时的最高水平。随后，Kojima 等人 (2022) 发现，即使没有示例，只需添加一行“让我们一步步思考”（Let's think step by step），InstructGPT(text-davinci-002) 在 MultiArith 上的准确率从 17.7% 提升至 78.7%，在 GSM8K 上则从 10.4% 提升至 40.7%。

需要注意的是，这些数字基于 2022 年的模型标准。当前使用的模型往往自带“思考”（thinking）功能，即在生成回答前会进行内部推理；指南也建议在处理复杂任务时利用模型的自适应 thinking 能力。因此，“逐步思考”是否应像习惯一样添加，取决于具体模型，这一点我尚未亲自对比验证。

## 被夸大或实用性较低的技巧

既然已经了解了有效的方法，接下来讨论相反的情况。以下内容基于我的阅读范围整理而成。

| 技巧 | 我读到的依据 | 判断 |
|---|---|---|
| "你是世界顶级专家"这类人设 | Zheng 等 (2023)：在系统提示中加入人设并不能提高事实性问题的准确率，效果几乎等同于随机 | 用于提升准确率时效果不佳 |
| 大写、强调“绝对”、“务必”等词汇 | Anthropic 指南：最新模型对系统提示更敏感，“CRITICAL: You MUST"这类表述反而可能导致过度触发，建议改用普通句子 | 旧模型的遗留习惯 |
| 神奇措辞（如“给你个提示”，“深呼吸一下”等） | - | 无依据，暂不采用 |
| 预填充响应 (prefill) | 指南：Claude 4.6 之后，部分模型不再支持最后一个 assistant 回合的 prefill | 因模型而异 |

这并不意味着角色设定完全无用。指南指出，只需在系统提示中给出一句话的角色描述，就能让语气和行为聚焦。我的理解是：角色用于确立语气、视角和标准，并不指望它能让人知晓未知事实。论文考察的是事实性准确率。

## 提示工程的位置

指南从一开始就划清界限。修改提示之前，应先明确成功标准，并准备好测试方法和首个草案。延迟或成本问题有时通过更换模型比调整提示更容易解决。没有评估而不断改写句子，无法判断是否有所改进。

如今讨论的范围更广了。在类似代理（agent）的结构中，模型反复调用工具，此时比起写好一张提示，更重要的是在每个回合中模型眼前应呈现什么内容。这一领域被称为 [上下文工程](#/post/ai-context)。提示只是其中一部分。撰写指令依然必要，其上层还叠加了对话记录、搜索结果（[RAG](#/post/ai-rag)）、工具定义等内容的选择层。同时，单次可容纳的内容量也受限于 [上下文窗口](#/post/ai-context-window)。

## 常见误解

- 写好提示就能消除 [幻觉](#/post/ai-hallucination)：可以减少但无法彻底消除。最有效的方法之一是提供参考文档并指示“若文档中未提及则如实回答”。这部分我尚未通过具体数值验证。
- 存在万能措辞：在我阅读范围内，未能找到始终有效的特殊句式。真正起作用的是清晰、示例和结构等朴素要素。
- 越长越好：提供必要信息不等于啰嗦冗长。有研究表明，内容过长反而会导致不稳定性（参见上下文窗口相关文章）。
- 一次写好就一劳永逸：模型更新后，相同提示的反应也会发生变化。指南也专门收集了迁移旧代提示时需要修正的要点。

<summary>详细解析：一个示例，同一任务三种写法</summary>

假设任务是判断评论句为正面或负面。

zero-shot:

```text
다음 리뷰가 긍정인지 부정인지 한 단어로 답해.
리뷰: 배송은 빨랐는데 포장이 엉망이었다.
```

few-shot（两个示例，用标签区分）:

```text
다음 리뷰를 긍정/부정/혼합 중 하나로 분류해. 한 단어로만 답해.
<examples>
<example>리뷰: 기대 이상이다. 또 살 것 같다. -> 긍정</example>
<example>리뷰: 사흘 만에 고장 났다. -> 부정</example>
</examples>
리뷰: 배송은 빨랐는데 포장이 엉망이었다.
```

加入示例后，回答格式会固定，甚至包括“混合”这类选项。参考上文 Min 等人的结果，此示例中关键不在于单个标签，而是“从三个标签中选其一并用一个词输出”的框架。

CoT（思维链）类则是先要求写出理由。

```text
먼저 <reasoning> 태그 안에 근거를 쓰고, 그다음 <answer> 태그 안에 결론만 써.
```

这样代码就能分别提取答案和依据。本示例由我撰写，并未进行性能测试。
