フロントエンドの学習を進めると、レンダリング、状態、コンポーネント、アクセシビリティ、パフォーマンスといった用語が一気に飛び出してくる。それぞれ異なる話題のように思えるが、結局は「ブラウザが画面をどのように作り、私たちはそれをどのように構築し、ユーザーにどのように見せるか」という一点に集約される。そのため、この順序で 7 つの記事に分け、まずは一言ずつ記した。さらに詳しく知りたい場合はリンクから進んでほしい。

## 一目でわかる関係図

```
브라우저가 그린다  ←  HTML을 누가·언제 만드나 (CSR·SSR·SSG)
        ↑
만든다: 컴포넌트로 쪼개고, 상태를 어디에 둘지 정한다
        ↑
쓰는 사람 쪽: 쓰기 쉬운가(사용성) · 누구나 쓸 수 있나(접근성) · 빠른가(성능)
```

## 1. 画面はどうやって作られるのか

**ブラウザが画面を描画するプロセス**: HTML と CSS を受け取り、DOM、CSSOM、レンダリングツリー、レイアウト、ペイントの順序で画面を生成する。どの段階で再描画が行われるかによって、画面変更のコストは大きく変わる。
[詳しく → ブラウザが画面を描画するプロセス](#/post/fe-browser-render)

**CSR・SSR・SSG**: 画面の HTML を誰が、いつ作るかを異なる 3 つの方法。どちらが良い悪いという話ではなく、ページごとのデータの更新頻度によって選ぶべきだ。
[詳しく → CSR・SSR・SSG](#/post/fe-rendering-modes)

## 2. どうやって構築するか

**状態管理**: 画面が記憶すべき値をどこに置き、誰が変更するかを決定する作業。ライブラリを選ぶ前に、値の種類を整理することがより重要だ。
[詳しく → 状態管理](#/post/fe-state)

**コンポーネント設計**: データの流れに合わせて画面を分割した部品。どれだけ細かく分割するかよりも、どこで区切り、状態を誰が保持するかの方が設計の大部分を占める。
[詳しく → コンポーネント設計](#/post/fe-component)

## 3. ユーザーにとってどうなのか

**ユーザビリティ原則 (UX)**: 画面を使いやすさのこと。ニールセンの 10 つのヒューリスティックがこれをチェックするための最も一般的なリストだ。
[詳しく → ユーザビリティ原則 (UX)](#/post/fe-usability)

**ウェブアクセシビリティ**: マウスと目で見るユーザーだけを想定して作らないこと。大半は HTML を本来の目的通りに使うことで解決でき、ARIA はそれでも不十分な場合の補完手段となる。
[詳しく → ウェブアクセシビリティ](#/post/fe-accessibility)

**フロントエンドパフォーマンス**: 「速い」という感覚を、ロード時間、応答性、安定性の 3 つの数値に分けて測定するのが Core Web Vitals。数値を知ることで、どこを改善すべきか決めることができる。
[詳しく → フロントエンドパフォーマンス](#/post/fe-performance)

## 読む順序

初めての場合は、描画プロセス → CSR・SSR・SSG → 状態 → コンポーネントの順に読むと流れが理解しやすい。ユーザビリティ・アクセシビリティ・パフォーマンスはどのタイミングで読んでも別々に学べる。画面が遅い理由が気になったら、描画プロセスとパフォーマンスの記事を併せて読むとよい。
