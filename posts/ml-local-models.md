로컬 모델은 내 PC에 모델 파일을 내려받아 직접 돌리는 방식이고, 들어가느냐 마느냐는 대부분 VRAM 계산 하나로 정해졌다.

## 로컬로 돌린다는 게 뭔지

API로 쓰는 모델은 남의 서버에서 돈다. 로컬은 모델 가중치(파일)를 내 컴퓨터에 두고 내 CPU·GPU로 계산한다. 인터넷이 없어도 되고 토큰당 요금이 없다. 대신 PC가 감당할 만한 크기의 모델만 돌릴 수 있다.

모델은 결국 숫자 아주 많은 표(가중치)다. 파라미터가 8B면 숫자가 80억 개다. 이걸 16비트(2바이트)로 저장하면 16GB쯤이고, 계산할 때 GPU 메모리(VRAM)에 올려 둬야 빠르다. 여기서 막힌다. 그래서 숫자를 더 적은 비트로 줄이는 양자화가 로컬의 핵심 기술이 됐다.

관련 개념은 [자세히 → LLM이란 무엇인가](#/post/ai-llm)에 있고, 서버 쪽 최적화는 [자세히 → 추론 최적화](#/post/ml-inference)에서 다룬다.

## 양자화

양자화는 가중치를 16비트 대신 8비트, 4비트처럼 짧은 정수로 바꿔 저장하는 것이다. 크기가 비트 수에 거의 비례해서 줄고, 대신 정확도가 조금 떨어진다.

llama.cpp 저장소는 1.5·2·3·4·5·6·8비트 정수 양자화를 지원한다고 적는다. 같은 문서의 Llama-3.1-8B 예시 표로 보면 이렇다.

| 종류 | 파라미터당 비트 | 파일 크기 |
|---|---|---|
| F16 | 16.00 | 14.96 GiB |
| Q8_0 | 8.50 | 7.95 GiB |
| Q6_K | 6.56 | 6.14 GiB |
| Q5_K_M | 5.70 | 5.33 GiB |
| Q4_K_M | 4.89 | 4.58 GiB |
| Q3_K_M | 4.00 | 3.74 GiB |
| Q2_K | 3.16 | 2.95 GiB |

이름은 읽는 법이 있다. Q 뒤 숫자가 대략 비트 수다. K는 블록 단위로 스케일을 따로 두는 방식(K-quants), 끝의 S/M/L은 작게/중간/크게다. 이름에 4비트가 들어가도 실제로는 4.89비트인 것처럼, 스케일 값 같은 부가 정보 때문에 표기보다 조금 더 쓴다.

품질은 어떨까. llama.cpp 문서는 양자화가 정확도 손실을 줄 수 있고 보통 perplexity나 KL divergence로 잰다고만 쓰고 수치는 싣지 않는다. 그래서 "Q4면 몇 % 떨어진다"는 숫자는 이 글에 쓰지 않는다. 문서가 말하는 주의점은 두 가지다. 이미 양자화된 모델을 다시 양자화하면 품질이 크게 나빠질 수 있다는 것, 그리고 imatrix 파일을 쓰면 손실을 줄일 수 있다는 것이다.

<details>
<summary>양자화가 하는 일을 숫자로 보면</summary>

가장 단순한 형태는 이렇다. 블록(예: 32개 숫자)마다 가장 큰 절댓값을 보고 스케일 s를 정한다. 각 숫자 w는 q = round(w / s)로 4비트 정수에 담고, 계산할 때 q × s로 되돌려 쓴다. 블록마다 스케일 하나가 붙으니 파라미터당 비트가 4보다 조금 커지는 것이다.

K-quants는 이걸 더 영리하게 해서 블록 안에 하위 블록을 두는 식이다. 세부 구조는 문서를 직접 읽어 확인하지 못했다.

## GGUF

GGUF는 llama.cpp 계열이 쓰는 모델 파일 형식이다. GGML 저장소 문서에 따르면 한 파일에 모델을 다 담고, 빨리 읽히고, 새 메타데이터를 넣어도 옛 모델이 안 깨지게 만들었다.

파일 안은 네 부분이다.

1. 헤더: 매직 넘버, 버전, 텐서 개수, 메타데이터 개수
2. 메타데이터: 아키텍처, 컨텍스트 길이, 어텐션·RoPE 설정, 토크나이저, 채팅 템플릿
3. 텐서 정보: 이름, 차원, 타입, 위치
4. 텐서 데이터: 실제 가중치(양자화된 것 포함)

토크나이저와 채팅 템플릿까지 파일에 들어 있어서 파일 하나만 있으면 실행이 된다. 텐서 위치를 정해진 간격(기본 32바이트)에 맞춰 두기 때문에 파일을 메모리에 그대로 매핑(mmap)해서 쓸 수도 있다. 파일 이름은 `모델명-크기-버전-양자화.gguf` 식의 규칙이 있고, 큰 모델은 `00001-of-00003`처럼 쪼개진다.

## VRAM 계산법

VRAM에 올라가는 건 크게 둘이다. 가중치와 KV 캐시. 거기에 런타임이 쓰는 작업 공간이 조금 더 붙는다.

가중치 = 파라미터 수 × 파라미터당 비트 ÷ 8. KV 캐시는 대화가 길어질수록 커지는 메모리로, 컨텍스트 길이에 비례한다. ([자세히 → 컨텍스트 윈도우와 토큰](#/post/ai-context-window))

```python
def weights_gib(params_b, bpw):
    return params_b*1e9*bpw/8/2**30

def kv_gib(layers, kv_heads, head_dim, ctx, bytes_per=2):
    return 2*layers*kv_heads*head_dim*ctx*bytes_per/2**30   # 2 = K와 V
```

Llama 3.1 8B(파라미터 약 8.03B, 32층, KV 헤드 8, 헤드 차원 128이라고 가정)로 돌려 본 결과다. 구조 숫자는 모델 카드를 열어 확인한 게 아니라 내가 알던 값이라 틀릴 수 있는데, 가중치 쪽은 llama.cpp 문서 표(14.96 / 7.95 / 4.58 GiB)와 맞게 나왔다.

| 항목 | 크기 |
|---|---|
| 가중치 F16 | 14.96 GiB |
| 가중치 Q8_0 | 7.95 GiB |
| 가중치 Q4_K_M | 4.57 GiB |
| KV 캐시, 컨텍스트 4,096 (f16) | 0.50 GiB |
| KV 캐시, 컨텍스트 32,768 (f16) | 4.00 GiB |
| KV 캐시, 32,768 (8비트 근사) | 2.12 GiB |

그래서 Q4_K_M에 컨텍스트 4k면 5GiB 안팎이라 8GB 카드에도 들어가고, 컨텍스트를 32k로 올리면 KV 캐시만 4GiB가 붙는다. 모델이 작아도 컨텍스트를 키우면 모자랄 수 있다는 뜻이다. 계산은 파이썬으로 직접 돌려서 위 숫자를 얻었다. 실제 사용량은 런타임 작업 공간 때문에 이보다 조금 더 나온다.

KV 캐시도 양자화할 수 있다. Ollama FAQ에 따르면 `OLLAMA_KV_CACHE_TYPE` 기본은 f16이고, q8_0은 메모리를 반쯤, q4_0은 4분의 1쯤 쓴다. q8_0은 품질 손실이 아주 작고 q4_0은 컨텍스트가 클 때 손실이 눈에 띌 수 있다고 한다. 플래시 어텐션을 켠 상태에서 쓰는 설정이다.

## 모델이 VRAM보다 클 때

llama.cpp는 CPU와 GPU를 섞어 쓰는 하이브리드 추론을 지원한다고 적는다. 일부 층만 GPU에 올리고 나머지는 시스템 메모리에서 CPU가 계산한다. 돌아가기는 하지만 CPU 쪽 층이 병목이라 눈에 띄게 느려진다. Ollama에서는 `ollama ps`의 Processor 열에서 "100% GPU"인지, "48%/52% CPU/GPU"처럼 나뉘었는지 볼 수 있다. 느리다 싶으면 이걸 먼저 확인하면 된다.

## Ollama와 llama.cpp

둘의 관계는 [자세히 → 오픈소스 분석: llama.cpp](#/post/repo-llama-cpp)와 [자세히 → 오픈소스 분석: Ollama](#/post/repo-ollama)에서 따로 본다. 여기서는 쓰는 쪽에서 본 차이만 적는다.

| | llama.cpp | Ollama |
|---|---|---|
| 성격 | C/C++ 추론 엔진 | 모델 받기·실행·서버를 묶어 둔 도구 |
| 지원 하드웨어 | CUDA, Metal, Vulkan, CPU 등 | 백엔드와 장치가 지원하면 GPU 사용 |
| 조정 | 양자화·층 분배·옵션을 직접 지정 | 환경변수·모델 설정으로 조정 |
| 서버 | OpenAI 호환 API 서버 제공 | 로컬 API 서버 |

llama.cpp 저장소는 최소한의 설정으로 어디서나 추론하는 것을 목표로 적고, Apple Silicon을 "first-class citizen"으로 최적화했다고 쓴다. Ollama에서 자주 만지는 설정은 FAQ 기준으로 이렇다.

- `OLLAMA_KEEP_ALIVE`: 모델을 메모리에 두는 시간. 기본 5분, 음수면 계속 유지, 0이면 응답 직후 내림
- `OLLAMA_NUM_PARALLEL`: 모델당 동시 처리 요청 수. 기본 1. 메모리는 이 값 × 컨텍스트 길이에 비례해 늘어난다
- `OLLAMA_CONTEXT_LENGTH`: 기본 컨텍스트 4096 토큰

기본 컨텍스트가 4096이라는 점은 실수하기 쉽다. 긴 문서를 넣었는데 앞부분이 잘리는 이유가 이것일 수 있다. 서비스로 서빙하는 쪽은 [자세히 → AI 서비스 서빙 구조](#/post/infra-ai-serving)에서 이어진다.

## 속도와 품질 트레이드오프

- 비트를 줄이면 파일이 작아지고 메모리가 덜 들고, 대개 속도도 빨라진다. 대신 품질이 깎인다. 어디까지가 괜찮은지는 모델과 용도마다 달라서 직접 써 보고 정해야 한다.
- 같은 VRAM이면 "큰 모델을 낮은 비트로"와 "작은 모델을 높은 비트로" 중에 고르게 된다. 어느 쪽이 낫다는 수치는 이번에 근거를 확인하지 못했다.
- 컨텍스트를 키우면 KV 캐시가 늘고, GPU에서 밀려나면 속도가 크게 떨어진다.
- 층을 CPU로 넘기면 돌아가긴 하지만 느려진다.

모델을 내 데이터에 맞추고 싶으면 양자화 모델 위에 LoRA를 얹는 방법이 있는데, 그건 [자세히 → 파인튜닝](#/post/ml-finetuning)에 있다.

## 흔한 오해

- 양자화하면 모델이 멍청해진다: 줄이는 만큼 손실은 있지만 비트가 높은 구간(8비트 근처)은 작다고 알려져 있다. 문서는 구체적인 수치를 싣지 않아서 여기서도 숫자는 안 쓴다.
- 모델 파일 크기만 VRAM에 맞으면 된다: KV 캐시와 작업 공간이 더 필요하다. 컨텍스트가 길수록 더 그렇다.
- 이미 양자화된 파일을 더 줄이면 되겠지: 문서가 품질이 크게 나빠질 수 있다고 경고한다. 원본 16비트에서 양자화하는 게 맞다.
- GPU에 안 들어가면 못 돌린다: 느릴 뿐 하이브리드로 돌아간다.
