After [Inkling 2 Mini](#/post/news-261127-a), the name I saw most this week on Hugging Face trending, X, and YouTube local-model videos was Ternary Bonsai 2.5 27B. PrismML posted it early on November 25, Korea time. It's based on Qwen3.8-27B and squeezes a 53.8GB model into a single 5.93GB file. I read the Hugging Face model card and two whitepapers (2.5, plus Bonsai 2, which first described the format). I didn't run it. Every benchmark number here is the company's own.

## Only three values
Model weights are usually stored as 16-bit numbers (FP16). Quantization stores them in fewer bits, like 8 or 4. Bonsai goes almost all the way. Each weight is one of -1, 0, or +1. These are called ternary weights. One of three values carries log₂3, about 1.585 bits of information.

Three values alone can't express magnitude, so every group of 128 weights shares one FP16 scale. The real value is "scale × (-1, 0, +1)". Spreading that 16-bit scale over 128 weights adds 0.125 bits each, so you get about 1.71 bits. The shipped file, after packing, is 1.76 bits per weight and 5.93GB. Roughly a ninth of FP16.

The part they left uncompressed was interesting. Only the normalization layers and part of the state path in the linear-attention layers, 26.2M parameters in total (0.0976% of the language model, 52MB), stay at full precision. The previous release ternarized even those. They just didn't bother saving bytes where it barely changes the size.

## Rotate, then round
There's one more step before rounding. Each weight matrix gets a Hadamard rotation in blocks of 1,024, and only then is it turned into three values. A Hadamard matrix is an orthogonal matrix made only of +1 and -1. The usual reason for this kind of rotation is to spread a few unusually large values across many slots so the group scale doesn't get dragged around by them (see work like QuaRot). The Bonsai whitepaper gives the formula but doesn't spend much time on the why.

The rotation is folded into the stored weights ahead of time, so it costs no extra bits. But at inference time the same transform has to be applied to the inputs (activations), so the runtime has to know about it. Stock llama.cpp supports it from build b11556. According to the model card, older builds load the file without any warning and then output garbage. That was the most practical sentence I read.

There are three files. PTQ1_0 (5.93GB, needs PrismML's llama.cpp fork), PQ2_0 (each value in its own 2-bit slot, 7.25GB, fork), and Q2_0 (stock llama.cpp's 2-bit type). All three are the same model.

## What changed in 2.5
The format is identical to Bonsai 2. What changed is agent work. By the company's tables, the five tool-calling benchmarks average 77.7 for the FP16 original and 77.2 for Bonsai 2.5. On three agentic coding benchmarks it went from 63% of the FP16 score to 90%. DeepSWE from 0 to 27.0, SWE-bench Verified from 60.8 to 75.6. How they retrained it isn't in the model card or whitepaper, so I couldn't confirm that.

One comparison stood out. A conventional 2.5-bit GGUF of the same Qwen3.8-27B (GSQ-RCO IQ2_XS) scores 79.5 on τ²-Bench but drops to 46.5 on AppWorld. In about one task in five, it writes a long script guessing every API call before seeing any output and declares the task done. The company's point is that its other scores don't show this failure.

MTP variants came out too. They add one layer that guesses the next few tokens. With speculative decoding, the main model checks those guesses in one pass and keeps only the tokens it would have produced itself. So output stays the same and decoding gets 1.5–1.8× faster on NVIDIA GPUs, they say. Even without MTP, the model card lists 163 tokens/s on an RTX 5090 (PTQ1_0).

## Why people are talking about it
The pitch is "a 27B coding model that fits a 16GB GPU." According to one video description, even the 4-bit version is about 17GB and doesn't fully fit on a 16GB card. This one is 6GB. Over three days YouTube got a run on an RTX 4060 Ti 16GB, a run of 86 coding tasks on an RTX 4090, and a run on an M5 Max Mac.

Not every reaction was positive. The 4090 video is titled "Strong quant; not up to the hype." Its description says it passed fewer tasks than several other models that fit the same card, and that it kept printing zeros on a Python-to-C port. It also notes the setups differ and the numbers are preliminary. I couldn't check view counts or Reddit reactions.

The whitepaper's limitations section says something similar. Terminal-Bench 2.1 is still where it's furthest from FP16, and they haven't measured agent work that runs for hours yet.

## As a beginner
I thought of quantization as "give up a bit of precision to shrink the size." The step that evens out values before rounding was new to me, and so was the fact that it means your runtime version has to match. Downloading the model file isn't the end of it.

As a PM, when I see "close to FP16," I want to check which benchmarks the average covers and whether there are failures the average hides. This company put an example of exactly that in its own table.
