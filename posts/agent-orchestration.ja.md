マルチエージェントオーケストレーションとは、複数の LLM（エージェント）がそれぞれタスクを担い、その順序と結果の統合を誰かが調整する構造のことです。[サブエージェント](#/post/ai-subagent) の記事が「なぜ分割するのか」であったなら、この記事は分割した後に何を決定すべきかについて 5 つのポイントにまとめました。誰が分割するか、並列か順次か、状態はどこに置くか、失敗したらどうするか、コストはどう抑えるかです。

## まず用語：ワークフローとエージェント

Anthropic の "Building effective agents" では、両者を以下のように区別しています。ワークフローとは、LLM とツールが「事前に定められたコード経路」で調整されるシステムであり、エージェントとは LLM が「自らプロセスとツールの使用を指揮する」システムです。オーケストレーションは、この 2 つのいずれかの方式にも登場します。OpenAI Agents SDK のドキュメントも同様の区別を行っています。オーケストレーションを LLM に計画と決定をさせる方式と、コードでフローを定める方式に分け、コードで定めれば速度・コスト・パフォーマンスがより決定的で予測可能になるとのことです。両方を組み合わせて使うこともできるとのことです。

この区別は、後のすべての選択に影響します。フローを事前に人間が把握できる場合はコードで記述し、入力を見て分割すべきかどうか判断する必要がある場合はモデルに委ねます。

## 1. 誰が分割するか：3 つのパターン

| パターン | 分割主体 | 例 |
|---|---|---|
| チェーニング | コード（順序固定） | 調査 → 概要 → 下書き → 批評 → 修正 |
| 並列化 | コード（タスク固定） | セクションごとに同時実行、同じタスクを複数回実行して投票 |
| オーケストレーター - ワーカー | 中央 LLM | 入力を基にサブタスクをその場で決定し、結果を統合 |

Anthropic の記事での定義によれば、オーケストレーター - ワーカーは「中央 LLM がタスクを動的に分割してワーカー LLM に委ね、結果を統合する」ものであり、並列化とは異なりサブタスクが事前に定義されず、入力に応じてオーケストレーターが決定します。チェーニングでは各呼び出しが前回の出力を処理し、遅延を受け入れながら精度向上を選択します。OpenAI ドキュメントのチェーニング例（調査→概要→下書き→批評→修正）も同様の形状です。これ 외에도、評価者が通過させるまで回るフィードバックループもコードパターンとして紹介されています。

## 2. 並列か順次か

独立したタスクは並列実行が速いです。Claude Agent SDK のドキュメントでは、並列サブエージェントは「すべてのタスクの合計時間ではなく、最も遅いものの時間」で完了すると説明しています。Anthropic のマルチエージェントリサーチシステムの記事では、リードエージェントが 3〜5 つのサブエージェントを並列に起動し、各サブエージェントも 3 つ以上のツールを並列で使用することで、複雑なクエリの調査時間を最大 90% 削減したと書かれています。この数値は記事に記載されたものであり、私が再現したものではありません。

逆に、前の結果が次の入力となる場合は順次です。並列実行が可能かどうかは「1 つのタスクが他のタスクの結果を必要とするか」で分かれます。同じ記事では、すべてのエージェントが同じコンテキストを共有する必要があったり、エージェント間で依存関係が多いタスクは現在の構造には適さないと述べており、コーディング作業の大部分はリサーチよりも並列に分割できる部分は少ないとされています。

OpenAI のドキュメントでは、コードによる並列化については `asyncio.gather` などの Python 標準ライブラリを挙げています。追加のフレームワークなしでも独立した呼び出しを同時に実行できるということです。

## 3. 状態はどこに置くか

複数のエージェントが動作する場合、互いの会話を共有しない場合、情報がやり取りされる経路が必要です。方式は主に 2 つあります。

- メッセージのみを伝達：Claude Agent SDK のドキュメントによると、サブエージェントは新しいコンテキストから開始し、親から渡されるのはエージェントツールのプロンプト文字列だけです。サブエージェント内で行われたツール呼び出しとその結果は内部に残り、親には最終メッセージのみが返されます。そのため、必要なファイルパスやエラーメッセージ、決定事項をプロンプトに直接記述する必要があります。
- 共有状態オブジェクト：LangGraph ではノードが読み書きする共有データを State に置き、キーごとに reducer が更新を統合します。デフォルトの reducer は値を上書きし、`Annotated[list[str], operator.add]` のように reducer を指定すると、並列ノードの結果がリストに追加されます。

Anthropic のリサーチシステムの記事では、別の理由で外部ストレージを使用しています。コンテキストウィンドウが 200,000 トークンを超えると切断されるため、リードエージェントは計画を外部メモリに保存し、制限に近づくとクリーンなコンテキストで新しいサブエージェントを起動して、保存されたメモリとハンドオフを続けます。[コンパクション](#/post/ai-compaction) や [セッション](#/post/ai-session) の記事で見た問題をエージェント間に移したようなものです。

LangGraph での並列ファンアウトは `Send` で行います。ランタイムでは項目数を把握し、同じノードをそれぞれ入力として呼び出し、結果は reducer で統合します。

```python
def fan_out(state):
    return [Send("worker", {"task": t}) for t in state["tasks"]]

graph.add_conditional_edges("planner", fan_out)
```

このコードはドキュメントの map-reduce の例を簡略化したものであり、LangGraph をインストールして実行したわけではありません。

## 4. 失敗したらどうするか

エージェントが増えれば、必ずどれかが失敗する。ドキュメントで言及されている対応策は以下の通りである。

| 状況 | 対応 | 出典 |
|---|---|---|
| 一時的なエラー | 再試行、定期的なチェックポイント、中断した地点からの再開 | Anthropic リサーチシステム記事 |
| ノードの再起動 | ノードがチェックポイント・再試行境界にあるため、最初からやり直す。副作用は冪等である | LangGraph ドキュメント |
| サブエージェントの停止 | `maxTurns` に達すると結果を「部分」としてマークし、同じエージェントを再開して続行する | Claude Agent SDK ドキュメント |
| 無限ループ | リカージョン制限（super-step 数の上限）に達し、超過すると `GraphRecursionError` が発生する | LangGraph ドキュメント |

Claude Agent SDK のドキュメントには、「API エラーによりサブエージェントが早期に終了した場合、そのエラーが結果として伝播しない」という記述もある。親プロセスが「成功した空の結果」と誤解しないよう、エラーと結果を区別するための設計であると読んだ。

失敗をコードで扱う場合はこのような形になる。偽のワーカー（LLM 呼び出しではなく、ランダムに失敗する関数）を用いて、並行実行制限、タイムアウト、再試行、トークン予算を一度に実装してみた。

```python
import asyncio, random

random.seed(1)
MAX_TOKENS = 3000
state = {"results": {}, "failed": [], "tokens": 0}   # 오케스트레이터만 쓰는 공유 상태

async def worker(task):
    """LLM 호출 자리. 가짜: 가끔 실패하고 토큰을 쓴다."""
    await asyncio.sleep(0.01)
    if random.random() < 0.3:
        raise RuntimeError("rate limit")
    return f"{task}: summary", 500

async def run_worker(task, sem, retries=2):
    async with sem:                                   # 동시 실행 수 제한
        for attempt in range(retries + 1):
            if state["tokens"] >= MAX_TOKENS:          # 예산 초과면 새 호출 안 함
                state["failed"].append((task, "budget"))
                return
            try:
                text, used = await asyncio.wait_for(worker(task), timeout=5)
                state["tokens"] += used
                state["results"][task] = text
                return
            except Exception as e:
                if attempt == retries:
                    state["failed"].append((task, str(e)))

async def orchestrate(question):
    subtasks = [f"{question}/part{i}" for i in range(1, 7)]   # 실제로는 모델이 쪼갠다
    sem = asyncio.Semaphore(3)
    await asyncio.gather(*(run_worker(t, sem) for t in subtasks))
    return state

s = asyncio.run(orchestrate("q"))
print("done:", len(s["results"]), "failed:", s["failed"], "tokens:", s["tokens"])
```

このコードを実際に Python で実行した。失敗確率が 0.3 の場合、`done: 6 failed: [] tokens: 3000` という結果が出た。確率を 0.5 に上げると `done: 5 failed: [('q/part5', 'rate limit')] tokens: 2500` のように、再試行を使い果たしても失敗した部分だけが `failed` に残り、他の結果は保持された。一つが失敗しても全体を破棄せず、「成功した部分と失敗した部分」を区別して返す仕組みである。実際の API 呼び出しではないため、コストや遅延はこの実行では推測できない。並行呼び出しの間には予算確認と使用量記録の間に隙間があるため、上限をわずかに超える可能性がある。

## 5. コスト：最初に防ぐべきこと

Anthropic の記事によると、エージェントはチャットよりも約 4 倍、マルチエージェントは約 15 倍多くのトークンを消費する。同じ記事で、リードが Claude Opus 4、サブエージェントが Claude Sonnet 4 の構成が、単一の Opus 4 よりも内部リサーチ評価において 90.2% 良いとされているという。性能とコストが同時に増えることを意味する。AI 機能において顧客一人あたりの呼び出しが倍増すれば、[原価](#/post/app-cost) も同様に増える。

ドキュメントで提示されているコスト管理手段は以下の通りである。

- プロンプトに規模を埋め込む：Anthropic は初期エージェントが単純な質問に対してもサブエージェントを過剰に起動し、単純な調査ではエージェント 1 つに対してツール呼び出し 3〜10 回、直接比較ではサブエージェント 2〜4 個、複雑な調査では 10 個以上というルールを導入したと述べている。
- ハード上限：Claude Agent SDK ドキュメントでは、ネスト深度（デフォルト 3 ステップ）、並行サブエージェント数（デフォルト 20）、支出上限（`maxBudgetUsd` / `max_budget_usd`）を設定できるとある。支出上限に達すると新しいサブエージェントを拒否し、進行中のバックグラウンドサブエージェントを停止し、クエリを `error_max_budget_usd` で終了させる。サブエージェントが自身のサブエージェントを作成できるため、一つのプロンプトがエージェントツリーとして拡大する可能性があるという説明がこのオプションの理由である。
- サブエージェントごとにモデルを指定：同じドキュメントの `model` フィールドを用いて、調査のような軽量なタスクは小さなモデルに任せることができる。
- タスク自体を削減する：この制限は安全装置であり、最も安価なのはエージェントを使わないことである。Anthropic は「可能な限り単純な解決策を見つけ、必要に応じて複雑さを高める」と推奨している。フレームワークがプロンプトを隠す追加の抽象層を作成するという警告も記されている。設計順序は [エージェント設計パターン](#/post/app-agent-design) にある。

<details>
<summary>詳細解説：Handoff と agents-as-tools</summary>

OpenAI Agents SDK のドキュメントでは、二つの委譲方式を区別している。agents-as-tools ではマネージャーエージェントが対話の統制権を持ち、専門エージェントは「限定的なサブタスク」を支援するが、ユーザーとの対話を引き継ぐことはない。handoff では選択された専門エージェントがそのターンの残りを「所有」する。両方を組み合わせて、handoff で渡された専門エージェントが狭いサブタスクに対して他のエージェントをツールとして呼び出すことも可能であるという。この区別は「状態を誰が保持しているか」という別の表現に過ぎない。マネージャーが保持すればツール、渡せば handoff である。

</details>

<details>
<summary>詳細解説：サブエージェントに渡すプロンプトが全てである</summary>

Claude Agent SDK のドキュメントの表によると、サブエージェントはシステムプロンプト、エージェントツールのプロンプト、プロジェクトの CLAUDE.md、ツール定義を受け取ります。親の会話履歴やツール結果、親のシステムプロンプトは受け取らないことが明記されています。フォーク（fork）は例外で、これまでの会話をコピーして開始します。結果も最終メッセージのみが返され、親がこれを要約してユーザーに伝えるため、原文のまま渡す場合は指示を入れる必要があるとドキュメントは述べています。そのため、委任プロンプトにおいて目標・出力形式・範囲を正確に記述することは、オーケストレーションの品質における重要な要素です。
</details>

<details>
<summary>詳細な解説：この記事で直接確認したこととできなかったこと</summary>

Python コードは上記の偽のワーカーバージョンを実行しました（結果は本文参照）。LangGraph、OpenAI Agents SDK、Claude Agent SDK のコードはインストール・実行しておらず、公式ドキュメントの説明と例を読み込んでいます。数値（15 倍、90.2%、90% の短縮、デフォルト深さ 3・並列 20）はすべて該当する公式記事・ドキュメントに記載された値であり、私が測定したものではありません。Claude Agent SDK のドキュメントも、ドキュメントバージョンによってデフォルト値が異なる可能性があるとしています。

</details>

## よくある誤解

- エージェントを多く追加すれば良い：コストは約 15 倍に増える可能性があり、依存関係の多いタスクには適さないという Anthropic の記事もあります。
- オーケストレーターはすべてを知っている：サブエージェントは親の会話を閲覧できず、渡されたプロンプトのみを受け取ります。
- 失敗は再試行で解決できる：再試行はコストを再度発生させます。回数と予算上限を同時に設定する必要があります。
- フレームワークを使えばオーケストレーションが解決する：フレームワークは状態管理や再試行の枠組みを提供するだけで、何を分割するかは設計者が決定します。Anthropic はむしろ抽象層がプロンプトを隠蔽する可能性があるとして警告しています。

誰が分割するか、並列/順次、状態、失敗、コストという 5 つの要素について、各フレームワークがどのように扱っているか対応させると、名称は異なりますが質問内容は同じであることが分かりました。モデルを一つ追加する前に、タスクをコードで固定できるかを確認するのが正しい順序のように思えます。
