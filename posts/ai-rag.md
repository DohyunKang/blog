RAG는 질문이 들어오면 관련 문서를 먼저 찾아서 프롬프트에 붙여 주고, 모델이 그걸 보고 답하게 하는 방식이다. 모델을 다시 학습시키지 않고도 모델이 모르는 내용을 답하게 만든다.

## 왜 필요한가

[LLM](#/post/ai-llm)은 학습이 끝난 시점까지의 지식만 가지고 있다. 어제 바뀐 사내 규정이나 우리 회사 문서는 당연히 모른다. 모르면 모른다고 하면 좋은데, 그럴듯하게 지어내는 일이 있다([환각 → 할루시네이션](#/post/ai-hallucination)).

그렇다고 문서를 전부 프롬프트에 넣을 수도 없다. [컨텍스트 윈도우](#/post/ai-context-window)에는 한도가 있고, 길어질수록 비용도 늘고 중간 내용은 잘 안 쓰는 경향도 있다. Lost in the Middle 논문은 관련 정보가 입력의 처음이나 끝에 있을 때 성능이 높고 가운데에 있으면 크게 떨어진다고 보고한다. 긴 문맥을 지원하는 모델도 마찬가지였다고 한다.

그래서 필요한 부분만 골라서 넣자는 게 RAG다. 용어는 2020년 Lewis 등의 논문 "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"에서 왔다. 논문은 모델 가중치에 든 지식을 파라메트릭 메모리, 위키피디아 벡터 인덱스처럼 바깥에 둔 지식을 비파라메트릭 메모리라고 부르고, 둘을 합치는 방식을 제안했다. 내 식으로 줄이면 "외우고 있는 지식 + 펴 볼 수 있는 책"이다.

## 흐름

한 번 훑으면 이렇다.

```
[준비 단계, 미리 한 번]
문서 → 청킹(조각내기) → 임베딩(숫자 벡터로) → 벡터 DB에 저장

[질문이 올 때마다]
질문 → 임베딩 → 비슷한 청크 검색(top-k) → 프롬프트에 붙임 → 모델이 답변
```

| 단계 | 하는 일 | 기억할 점 |
|---|---|---|
| 청킹 | 문서를 적당한 크기로 자른다 | 검색의 단위가 된다 |
| 임베딩 | 청크를 의미가 담긴 벡터로 바꾼다 | [자세히 → 임베딩](#/post/ai-embedding) |
| 검색 | 질문 벡터와 가까운 청크를 찾는다 | 상위 k개만 가져온다 |
| 프롬프트 주입 | "아래 자료만 보고 답해" 식으로 청크를 붙인다 | [자세히 → 프롬프트](#/post/ai-prompt) |
| 답변 | 모델이 자료를 읽고 쓴다 | 출처를 같이 달면 확인이 쉽다 |

프롬프트 주입 부분은 대략 이런 모양이다.

```
다음 자료만 근거로 질문에 답하라. 자료에 없으면 모른다고 답하라.

[자료 1] ...청크...
[자료 2] ...청크...

질문: ...
```

"자료에 없으면 모른다고 하라"는 한 줄이 은근히 중요하다. 이게 없으면 모델이 자료에 없는 부분을 자기 지식으로 메운다.

## 청크 크기

청크를 어떻게 자르느냐가 검색 품질에 직접 영향을 준다. Anthropic의 Contextual Retrieval 글도 청크 크기·경계·겹침(overlap)이 검색 성능에 영향을 준다고 적는다.

- 너무 크면 한 청크에 여러 주제가 섞여서 임베딩이 흐려지고, 프롬프트 자리도 많이 먹는다.
- 너무 작으면 문장이 앞뒤 맥락 없이 잘려서 의미가 사라진다.
- 겹침을 두면 경계에서 잘린 내용을 이웃 청크가 받아 준다. 대신 중복이 늘어난다.

몇 토큰이 정답이라는 숫자는 찾지 못했다. 글에서도 사용 사례마다 실험해 보라고 한다. 문서 종류(규정, 대화, 코드)에 따라 자르는 기준이 다르고, 제목이나 문단 단위로 자르는 쪽이 글자 수로 자르는 쪽보다 낫다는 얘기를 흔히 듣는데 이건 내가 직접 확인한 건 아니다.

## 재순위와 하이브리드 검색

처음 검색에서 나온 상위 k개가 늘 좋은 건 아니다. 그래서 두 가지가 자주 붙는다.

하이브리드 검색은 임베딩 검색(의미 기반)과 BM25(단어 일치 기반)를 같이 쓰는 것이다. 임베딩은 뜻이 비슷하면 잘 찾지만 "TS-999" 같은 오류 코드나 고유 용어의 정확한 일치는 놓칠 수 있다. BM25는 반대다. 두 결과를 순위 융합(rank fusion)으로 합치고 중복을 없앤다.

재순위(reranking)는 일단 넉넉히 찾은 뒤 재순위 모델이 질문과 청크를 함께 보고 점수를 다시 매겨서 위쪽만 남기는 단계다. 처음 검색이 빠르고 대충이라면 재순위는 느리고 정교하다. 대신 지연이 조금 늘어서 몇 개를 재순위할지가 비용·속도 절충이 된다.

Anthropic 글에 숫자가 있다. 상위 20개 청크 안에 정답이 없는 비율(검색 실패율) 기준이다.

| 방식 | 실패율 | 기본 대비 |
|---|---|---|
| 기본 임베딩 | 5.7% | 기준 |
| 청크에 맥락 문장을 붙여 임베딩 | 3.7% | 35% 감소 |
| 위 방식 + 맥락 BM25 | 2.9% | 49% 감소 |
| 위 방식 + 재순위 | 1.9% | 67% 감소 |

이건 그 글의 자체 실험 조건(데이터셋, 재순위 모델은 Cohere)에서 나온 값이다. 내 데이터에서 같은 폭으로 줄어든다는 보장은 없다. 방향은 참고할 만하다.

여기서 나온 맥락 붙이기는, 청크가 "매출이 전 분기보다 3% 늘었다"처럼 회사명과 기간이 빠진 채 잘리는 문제를 막으려고 청크 앞에 짧은 설명 문장을 붙여 두는 방식이다.

## 실패하는 경우

RAG가 틀리는 지점은 대체로 모델이 아니라 앞단이다.

- 필요한 청크가 검색에서 안 나온다. 가장 흔하고, 위 실패율이 바로 이걸 잰 숫자다.
- 청크가 잘려서 맥락이 빠진다. 위의 회사명 예시가 그렇다.
- 찾긴 했는데 가운데에 묻혀서 모델이 안 쓴다. 앞의 Lost in the Middle 얘기가 이쪽이다.
- 질문에 여러 문서를 합쳐야 하는 경우(비교, 집계)엔 상위 몇 개 청크로는 모자란다.
- 문서가 낡았거나 서로 모순된다. 검색은 잘 됐는데 자료가 틀린 경우다. 이건 RAG로 못 고친다.
- 자료를 줘도 모델이 자기 지식으로 답하거나 자료를 잘못 읽는다.

그래서 답이 틀렸을 때 "모델 탓"부터 하지 말고 어떤 청크가 프롬프트에 들어갔는지를 먼저 보는 게 순서 같다.

## 파인튜닝과 뭐가 다른가

둘 다 "모델이 우리 걸 알게 하는 방법"으로 묶이지만 하는 일이 다르다.

| | RAG | 파인튜닝 |
|---|---|---|
| 바뀌는 것 | 모델이 보는 입력 | 모델의 가중치 |
| 잘 맞는 것 | 자주 바뀌는 지식, 사내 문서, 출처 필요 | 말투, 출력 형식, 일관된 행동 |
| 지식 갱신 | 문서를 고치면 끝 | 다시 학습 |
| 출처 표시 | 청크를 그대로 보여 줄 수 있다 | 어렵다 |

검색해서 읽은 실무 글들은 대체로 "지식 문제면 RAG, 행동 문제면 파인튜닝"으로 정리하고, 둘을 섞어 쓰기도 한다고 한다. 다만 이건 업체·개인 블로그가 대부분이라 의견에 가깝고, 같은 과제로 둘을 비교한 통제된 실험은 찾지 못했다.

## 흔한 오해

- RAG를 쓰면 환각이 없어진다: 줄어들 뿐이다. 검색이 틀리거나 모델이 자료를 무시하면 똑같이 지어낸다.
- 파인튜닝하면 문서 내용을 외운다: 사실을 안정적으로 외우게 하는 용도로는 약하다는 게 실무 글들의 공통된 얘기였다. 나도 직접 해 보진 못했다.
- 벡터 DB만 있으면 RAG다: DB는 저장 장치일 뿐이고 품질은 청킹, 검색 방식, 재순위에서 갈린다.
- 컨텍스트가 길어졌으니 RAG는 필요 없다: 지식 베이스가 작으면(Anthropic 글 기준 대략 20만 토큰, 500쪽 미만) 통째로 넣는 게 가장 간단하다고 그 글도 말한다. 그보다 크면 여전히 필요하다.

<details>
<summary>자세한 풀이: 의미 검색이 어떻게 찾는지</summary>

임베딩은 글을 수백~수천 차원의 숫자 목록으로 바꾼 것이다. 뜻이 비슷한 글은 벡터 공간에서 가깝게 놓이도록 학습된 모델이 만든다. 질문도 같은 모델로 벡터로 바꾸고, 저장된 청크 벡터 중 가까운 것(코사인 유사도 등)을 고른다. 청크가 많으면 하나씩 비교하지 않고 근사 최근접 탐색 인덱스를 쓴다.

BM25는 단어가 얼마나 자주, 얼마나 희귀하게 나오는지를 보는 점수 함수다. 흔한 단어가 점수를 독차지하지 않게 빈도에 상한을 두고 문서 길이도 보정한다고 한다. 뜻은 몰라도 같은 글자가 있으면 찾는다는 점이 임베딩과 보완 관계다.
