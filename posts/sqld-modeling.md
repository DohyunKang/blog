SQLD 1과목의 첫 단원은 데이터 모델링이다. 현실의 업무를 데이터 구조로 옮기는 과정을 개념, 논리, 물리 세 단계로 나누고, 그 결과를 ERD라는 그림으로 그린다. 이 글은 시험에서 이 단원이 어떤 식으로 묻는지에 맞춰 정리했다. 시험 일정과 응시료는 공식 사이트에서 확인하면 된다.

## 모델링이 뭔지

모델링은 현실 세계를 단순하게 줄여서 표현하는 일이다. 지도가 실제 땅을 다 그리지 않고 필요한 것만 그리는 것과 비슷하다. 업무에서 필요한 것만 남기고 나머지는 버리는 게 핵심이라, 시험에서는 모델링의 특징을 추상화, 단순화, 명확화로 묻는다.

- 추상화: 현실에서 공통된 특성만 뽑아낸다.
- 단순화: 복잡한 것을 약속된 기호로 간단히 나타낸다.
- 명확화: 누가 봐도 같은 뜻으로 읽히게 모호함을 없앤다.

모델링을 바라보는 관점도 세 가지로 나눈다. 데이터 관점은 업무가 어떤 데이터와 관련되는지, 프로세스 관점은 업무가 실제로 하는 일이 무엇인지, 데이터와 프로세스의 상관 관점은 일이 데이터를 어떻게 바꾸는지를 본다. SQLD에서 다루는 건 주로 데이터 관점이다.

## 개념, 논리, 물리

모델링 단계는 추상적인 것에서 구체적인 것으로 내려간다.

| 단계 | 하는 일 | 대표 산출물 | 시험 포인트 |
|---|---|---|---|
| 개념적 모델링 | 업무에서 핵심 엔터티를 뽑고 관계를 잡는다 | 개념 ERD | 추상화 수준이 가장 높고, 특정 DBMS와 무관 |
| 논리적 모델링 | 테이블, 컬럼, 키로 구조를 구체화한다 | 논리 ERD | 정규화를 이 단계에서 한다, 재사용성이 높다 |
| 물리적 모델링 | 실제 DBMS에 맞게 성능과 저장까지 고려한다 | 물리 ERD, 스키마 | DBMS 종류에 따라 달라진다, 반정규화·인덱스 설계 |

위키피디아의 데이터 모델 문서도 ANSI 관점에서 비슷하게 구분한다. 개념 모델은 영역의 의미를 엔터티 분류와 관계로 설명하고, 논리 모델은 특정 기술(테이블·컬럼 등)로 표현한 의미를 설명하며, 물리 모델은 데이터가 실제로 저장되는 방식(파티션, 테이블스페이스 등)을 다룬다. 이 세 관점은 서로 비교적 독립적이라서, 저장 기술을 바꿔도 위쪽 모델은 영향을 덜 받는다.

시험에서 자주 나오는 건 단계와 설명을 짝짓는 문제다. 외우는 요령은 간단하다. 개념은 "무엇을 관리할지", 논리는 "어떤 테이블 구조로 담을지", 물리는 "DBMS에서 어떻게 빠르게 돌릴지"다. 정규화는 논리, 반정규화와 인덱스는 물리 쪽이라고 연결해 두면 문제가 풀린다. 정규화 자체는 [자세히 → 정규화와 성능 데이터 모델링](#/post/sqld-norm-perf)에서 따로 본다.

<details>
<summary>모델링 단계를 헷갈릴 때 쓰는 예시</summary>

도서관을 예로 들면 이렇다.

- 개념: "회원이 책을 빌린다"까지만 정한다. 엔터티는 회원, 책, 대출 정도고 컬럼은 아직 없다.
- 논리: 회원(회원번호, 이름), 책(책번호, 제목), 대출(회원번호, 책번호, 대출일)처럼 컬럼과 키를 정한다. 중복이 없게 정규화한다.
- 물리: 대출 테이블이 커질 것 같아서 대출일 기준으로 파티션을 나누고, 조회가 많은 컬럼에 인덱스를 건다. 컬럼 타입도 사용하는 DBMS에 맞춘다.

같은 대상을 점점 더 구체적으로 다시 그리는 것뿐이라서, 위 단계가 끝난 뒤에 아래 단계로 가는 순서만 기억하면 된다.
</details>

## ERD

ERD(Entity Relationship Diagram)는 엔터티와 엔터티 사이의 관계를 그림으로 나타낸 것이다. 상자가 엔터티고 선이 관계다. 이 모델은 1976년 Peter Chen이 ACM 논문에서 제안했고, 보통 관계형 DB의 추상 데이터 모델로 쓰인다. 엔터티는 명사, 관계는 동사에 가깝다고 보면 이해가 쉽다.

시험에서는 ERD를 그리는 순서와 구성 요소를 묻는다. 한국 SQLD 교재에서 쓰는 작성 순서는 이렇다.

1. 엔터티를 그린다.
2. 엔터티를 배치한다.
3. 엔터티 사이에 관계를 설정한다.
4. 관계명을 서술한다.
5. 관계의 참여도(차수)를 표시한다.
6. 관계의 필수 여부를 표시한다.

엔터티를 배치할 때는 중요한 엔터티를 왼쪽 위에 둔다고 외우는 경우가 많다. 선 끝에 닭발(crow's foot) 모양이면 "많다"는 뜻이고, 동그라미는 0, 짧은 선은 1을 뜻하는 표기법이 가장 흔하다. 이 표기는 위키피디아 ER 모델 문서에도 나온다. 관계의 차수(1:1, 1:N, M:N)와 선택성은 [자세히 → 관계와 식별자](#/post/sqld-relation-identifier)에서, 엔터티와 속성의 분류는 [자세히 → 엔터티와 속성](#/post/sqld-entity-attr)에서 다룬다.

## 좋은 데이터 모델의 조건

"좋은 모델이 갖춰야 할 요소"도 단골로 나오는 문장형 문제다.

| 조건 | 뜻 |
|---|---|
| 완전성 | 업무에 필요한 데이터를 모두 포함한다 |
| 중복 배제 | 같은 사실을 여러 곳에 저장하지 않는다 |
| 업무 규칙 | 업무 규칙을 모델에 표현하고 모두가 공유한다 |
| 데이터 재사용 | 데이터가 어느 한 프로그램에만 묶이지 않게 독립적으로 설계한다 |
| 의사소통 | 모델 표기법을 이해하는 사람끼리 같은 뜻으로 읽힌다 |
| 통합성 | 같은 데이터는 한 번만 정의하고 다른 곳에서 참조한다 |

보기에 "속도"나 "저장 공간 절약"이 끼어 있으면 의심해 볼 만하다. 이 목록의 중심은 중복 없이 정확하게 담고 같이 읽을 수 있느냐다.

## 3단계 스키마와 데이터 독립성

스키마는 데이터베이스의 구조와 제약을 기술한 것이다. 3단계 스키마(ANSI-SPARC 구조)는 이걸 세 층으로 나눈다. 모델링의 개념·논리·물리와 이름이 비슷해서 헷갈리기 쉬운데, 이쪽은 단계가 아니라 하나의 DB를 보는 세 가지 층이다.

| 스키마 | 누가 보나 | 설명 |
|---|---|---|
| 외부 스키마 | 사용자·응용 프로그램 | 각자가 필요한 부분만 보는 뷰. 여러 개 있을 수 있다 |
| 개념 스키마 | 전체 조직·DBA | 모든 데이터와 관계, 제약을 통합한 구조. DB당 하나 |
| 내부 스키마 | 시스템·저장 관점 | 물리적 저장 방식, 레코드, 인덱스. DB당 하나 |

위키피디아의 ANSI-SPARC 문서도 같은 내용을 쓴다. 외부는 사용자별 뷰이고 여러 개가 가능하며, 개념과 내부는 각각 하나이고, 내부는 하드웨어에 실제 저장되는 표현을 다룬다.

이렇게 층을 나눈 이유가 데이터 독립성이다. 한 층을 바꿔도 다른 층에 영향이 가지 않게 하는 것이다.

- 논리적 독립성: 개념 스키마를 바꿔도 외부 스키마(사용자 뷰, 응용 프로그램)는 바뀌지 않는다.
- 물리적 독립성: 내부 스키마(저장 구조)를 바꿔도 개념 스키마는 바뀌지 않는다.

독립성이 있으면 사용자별 접근을 통제하기 쉽고, 저장 장치를 바꿔도 프로그램을 고치지 않아도 되고, 같은 데이터를 여러 방식으로 보여 줄 수 있다. 문제에서는 "어느 스키마를 변경해도 어느 쪽에 영향이 없는가"를 방향으로 묻는 경우가 많다. 논리는 외부와 개념 사이, 물리는 개념과 내부 사이라고 두 줄로 정리해 두면 된다.

<details>
<summary>모델링 3단계와 3단계 스키마를 구분하는 방법</summary>

두 개념은 이렇게 갈라 놓으면 안 헷갈린다.

- 모델링 3단계(개념·논리·물리)는 설계를 하는 순서다. 시간 축이고, 한 사람이 위에서 아래로 진행한다.
- 3단계 스키마(외부·개념·내부)는 완성된 DB를 어떤 층에서 보느냐다. 구조 축이고, 동시에 존재한다.

그래서 "개념"이라는 단어가 두 군데에서 나오지만 같은 것이 아니다. 문제에서 "설계 순서"나 "DBMS 독립적"이라는 표현이 나오면 모델링 단계, "사용자 뷰"나 "저장 구조"가 나오면 3단계 스키마 쪽이다.
</details>

## 자주 틀리는 부분

- 개념 모델링에서 정규화나 인덱스를 한다고 고르는 보기는 틀리다. 정규화는 논리, 인덱스는 물리 쪽이다.
- 외부 스키마가 하나뿐이라는 보기도 틀리다. 외부는 여러 개, 개념과 내부가 각각 하나다.
- 논리적 독립성과 물리적 독립성을 반대로 설명한 보기가 자주 섞인다. 개념 스키마 변경과 외부 스키마, 내부 스키마 변경과 개념 스키마로 짝지으면 된다.
- 모델링은 "현실을 그대로 복제"하는 게 아니라 필요한 것만 남기는 작업이라서, 현실의 모든 정보를 담는다는 보기는 틀리다.

기출문제는 원문을 옮기지 않고 유형만 적었다. 보기 문장은 위 표의 표현과 거의 같은 말로 바뀌어 나오니, 표를 그대로 외우기보다 이유를 한 줄씩 붙여서 외우는 쪽이 오래 갔다. 다음 단원은 [엔터티와 속성](#/post/sqld-entity-attr)이다.
