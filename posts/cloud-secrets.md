시크릿은 코드가 아니라 실행하는 환경에서 건네줘야 하고, 새더라도 피해가 오래 안 가게 바꿀 수 있는 구조를 만드는 게 관리의 전부에 가까웠다.

## 설정과 시크릿

앱이 돌려면 코드 말고도 필요한 값이 있다. DB 주소, 외부 서비스 API 키, 서버 호스트 이름 같은 것들이다. 12-Factor 앱 문서는 이걸 "설정(config)"이라 부르고, 배포마다 달라질 수 있는 모든 것으로 정의한다. 앱 내부 구조를 잇는 라우팅 설정 같은 건 배포마다 안 바뀌니 여기 안 들어간다.

시크릿은 설정 중에서 새면 곤란한 것이다. 비밀번호, API 키, 토큰, 인증서 개인키가 그렇다. DB 주소는 설정이지만 DB 비밀번호는 시크릿이다. 둘을 같은 방식으로 다루다가 사고가 난다.

문서가 제안하는 기준은 하나다. 지금 이 코드를 아무 때나 공개해도 자격 증명이 안 새나가는가. 안 새나가면 설정이 코드에서 제대로 분리된 것이다.

## 환경변수가 기본인 이유

12-Factor는 설정을 환경변수에 두라고 한다. 이유는 세 가지로 적혀 있다.

- 코드를 안 건드리고 배포마다 값만 바꿀 수 있다.
- 설정 파일과 달리 실수로 저장소에 커밋될 가능성이 낮다.
- 언어와 운영체제에 상관없이 쓸 수 있다.

비교 대상은 코드에 박아 넣은 상수와 커밋하지 않는 설정 파일(Rails의 database.yml 같은)이다. 상수는 분리 원칙을 어기고, 설정 파일은 낫지만 실수로 커밋될 수 있고 형식이 프레임워크마다 흩어진다고 한다.

코드에서 읽는 쪽은 단순하다.

```python
import os

def need(name):
    v = os.environ.get(name)
    if not v:
        raise SystemExit(f"{name} 없음")
    return v

db_url = need("DB_URL")      # 없으면 시작 단계에서 바로 멈춘다
```

값이 없을 때 조용히 기본값으로 넘어가지 않고 시작할 때 멈추게 해 두면, 배포하고 한참 뒤에야 터지는 일을 줄일 수 있다. 위 코드는 값을 넣은 경우와 안 넣은 경우를 둘 다 실행해서 동작을 확인했다.

12-Factor가 피하라는 방식도 있다. `development`, `test`, `production`처럼 이름 붙인 설정 묶음을 코드에 두는 것이다. 문서는 이 방식이 "깔끔하게 확장되지 않는다"고 한다. 스테이징이나 개인 환경이 늘면 조합이 곱으로 늘고 배포가 깨지기 쉬워진다. 환경 이름으로 묶지 말고 변수 하나하나를 배포마다 독립적으로 관리하라는 것이다.

## .env 파일

로컬 개발에서는 환경변수를 매번 터미널에 치기 번거로워서 `.env` 파일에 `KEY=value` 줄로 적어 두고, 도구가 시작할 때 읽어서 환경변수로 올려 준다. 파일 하나일 뿐 마법은 아니다.

지켜야 할 건 두 가지다. 첫째 `.gitignore`에 `.env`를 넣는다. 둘째 저장소에는 값을 비운 `.env.example`만 올려서 어떤 변수가 필요한지만 알려 준다.

[자세히 → CI/CD와 배포 전략](#/post/cloud-cicd)에서 보듯 운영 서버나 CI에서는 `.env` 파일을 쓰기보다 그쪽 플랫폼이 주입하는 방식이 일반적이다. 파일을 서버에 올려 두면 그 파일이 또 하나의 관리 대상이 된다.

## 환경변수만으로 부족한 지점

OWASP의 시크릿 관리 치트시트는 환경변수를 "최후의 수단"에 가깝게 본다. 로그나 크래시 덤프에 딸려 나갈 수 있기 때문이다. 문서는 시크릿을 코드, Dockerfile, 설정 파일에 박지 말고 오케스트레이터가 주입하거나 실행 시점에 가져오라고 한다. [자세히 → Docker](#/post/cloud-docker)에서 이미지에 시크릿을 굽는 실수가 왜 위험한지 이어서 볼 수 있다.

환경변수가 약한 지점을 정리하면 이렇다.

| 걱정 | 환경변수만 쓸 때 |
|---|---|
| 누가 읽었는지 | 기록이 안 남는다 |
| 바꾸기 | 앱을 재시작해야 반영된다 |
| 접근 제한 | 프로세스 안에서는 다 보인다 |
| 새어 나감 | 로그·덤프·디버그 출력에 섞이기 쉽다 |

그래서 규모가 커지면 시크릿 전용 저장소를 쓴다.

## 시크릿 매니저

AWS Secrets Manager 문서는 이 서비스를 DB 자격 증명, 앱 자격 증명, OAuth 토큰, API 키 같은 시크릿을 수명 주기 전체에 걸쳐 관리하고 가져오고 로테이션하는 도구라고 소개한다. 핵심 아이디어는 코드에 박은 자격 증명을 실행 시점의 호출로 바꾸는 것이다. 앱이 필요할 때 서비스에 물어 값을 받아 온다.

이렇게 하면 얻는 게 몇 가지 있다.

- 값이 앱과 함께 저장되지 않아서, 앱을 들여다볼 수 있는 사람이 곧바로 시크릿을 얻지는 못한다.
- 자동 로테이션 일정을 걸 수 있고, 값이 앱에 안 박혀 있으니 바꿔도 앱을 다시 배포할 필요가 없다.
- 누가 언제 꺼냈는지 기록이 남는다. 문서는 CloudTrail을 켜면 API 호출 로그를 얻는다고 적는다.

주의할 점도 문서에 있다. 이 서비스는 쓴 만큼 과금하고, 자기 KMS 키로 암호화하거나 로테이션에 Lambda를 쓰면 그 요금이 따로 붙는다. 그리고 AWS 자격 증명은 IAM, 암호화 키는 KMS, 인증서는 ACM처럼 종류별로 맞는 서비스가 따로 있다고 한다. 시크릿 매니저가 모든 비밀을 넣는 만능 금고는 아니다.

다른 클라우드와 도구(Google Secret Manager, HashiCorp Vault 등)도 같은 역할을 하지만 이번에 문서를 열어 보지는 않았다.

## 로테이션과 최소 권한

OWASP 치트시트의 핵심 권장은 대략 이렇다.

- 중앙화: 코드, 설정 파일, 도구에 흩어 두지 말고 전용 시스템에서 관리한다.
- 로테이션: 정기적으로 바꾸고 가능하면 자동화해서 훔친 자격 증명의 수명을 짧게 만든다.
- 최소 권한: 시크릿마다 읽고 바꿀 수 있는 주체를 좁힌다.
- 동적 시크릿: 세션마다 짧게 쓰고 만료되는 자격 증명을 발급한다. 앱을 재시작해도 훔친 자격 증명이 무효가 되지는 않는다고 문서는 지적한다.
- 감사: 누가 요청했고 승인됐는지, 언제 쓰였는지를 남기고 로그 자체도 변조되지 않게 지킨다.

로테이션을 처음엔 귀찮은 정기 작업으로 이해했는데, 문서가 말하는 건 반대에 가까웠다. 새는 걸 막는 게 목표가 아니라 새도 쓸 수 있는 기간을 줄이는 게 목표다. 한 번 정하면 영영 쓰는 키는 새는 순간부터 계속 위험하고, 며칠짜리 키는 새도 곧 죽는다.

## 유출됐을 때

GitHub 문서 기준으로 시크릿 스캐닝은 모든 브랜치의 전체 Git 히스토리와 이슈, PR, 디스커션, 위키까지 훑어서 노출된 키를 찾고, 찾으면 저장소 보안 탭에 경고를 만든다. 공개 저장소는 무료고, 조직의 비공개 저장소는 별도 제품(GitHub Secret Protection)이 필요하다고 한다. 푸시할 때 막아 주는 기능(push protection)은 이번에 읽은 페이지에 설명이 없어서 확인 못 했다.

유출 대응 순서는 두 문서가 거의 같다.

1. 해당 자격 증명을 바로 폐기하고 새로 발급한다.
2. 코드, 로그 등 노출된 곳에서 지운다.
3. 언제 어떻게 새고 뭘 썼는지 기록한다.

GitHub 문서는 Git 히스토리에서 지우는 건 시간이 많이 들고 이미 폐기했다면 대개 불필요하다고 말한다. 커밋을 지우는 것보다 키를 죽이는 게 먼저다. 이미 누가 복사해 갔을 수 있으니까.

## 흔한 오해

- `.env`를 `.gitignore`에 넣었으니 안전하다: 앞으로 커밋은 막지만 이미 커밋된 건 히스토리에 남는다. 그리고 로그나 이미지로 새는 길은 그대로 있다.
- 저장소가 비공개니까 키를 넣어도 된다: 12-Factor의 기준은 공개해도 되는지다. 비공개는 지금 접근 권한이 좁은 것일 뿐이다.
- 환경변수는 암호화돼 있다: 아니다. 프로세스와 같은 권한이면 읽힌다.
- 시크릿 매니저를 쓰면 끝: 매니저에 접근하는 권한이 넓으면 금고 문을 열어 둔 것과 같다. 최소 권한과 감사가 같이 가야 한다.
- 지우면 없던 일이 된다: 이미 복제됐을 수 있어서 폐기가 먼저다.

5. 로테이션 주기와 유출 대응 절차(누가 폐기하고 누구에게 알리는지)를 문서로 정해 둔다.

작은 개인 프로젝트에서 1~3이면 충분한지, 4부터 가야 하는지는 서비스 성격과 요금에 달렸다. 시크릿 매니저는 쓴 만큼 과금되니 개수가 적으면 비용 대비 효과를 따져 봐야 한다.
