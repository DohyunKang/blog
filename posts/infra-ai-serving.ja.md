LLM API 를 호출하여 답변을 제공하는 서비스는 일반적인 웹 서비스와 달리 한 요청이 수 초씩 걸리고, 간혹 실패하며, 매번 호출할 때마다 비용이 발생합니다. 따라서 요청 처리 과정 중간에 큐 (Queue), 캐시, 스트리밍, 타임아웃, 비용 제한 등을 각 층으로 쌓아 구조를 형성하게 됩니다.

## 일반 API 와 무엇이 다른가

[요청 하나가 거치는 길](#/post/infra-request-journey)에서 본 것처럼 보통 웹 요청은 DNS, CDN, 로드밸런서, 서버, DB 를 지나고 수십 ms 에 끝납니다. LLM 이 개입되면 서버가 외부 API 하나를 더 기다리게 됩니다. 이 대기 시간이 다른 단계보다 훨씬 깁니다. 답변이 한 번에 생성되지 않고 토큰을 하나씩 생성하기 때문입니다.

차이를 표로 정리하면 다음과 같습니다.

| | 보통 API | LLM 호출 |
|---|---|---|
| 걸리는 시간 | 수십 ms | 몇 초에서 길면 몇 분 |
| 응답 크기 | 거의 고정 | 생성하는 만큼 달라짐 |
| 같은 입력 | 같은 출력 | 보통 매번 조금 다름 |
| 호출 비용 | 거의 0 | 입력·출력 토큰만큼 과금 |
| 한도 | 내 서버 사양 | 업체가 정한 분당 요청·토큰 한도 |

[LLM 이란 무엇인가](#/post/ai-llm)에서 다룬 것처럼 모델은 다음 토큰을 계속 이어 붙이는 방식이라, 응답 시간이 출력 길이에 비례하여 늘어납니다. 서버 쪽에서는 연결 하나를 오래 붙잡고 있는 요청으로 보입니다.

## 구조를 한 장으로

서비스 측에서 흔히 사용하는 층을 순서대로 그리면 다음과 같은 모양입니다.

```
사용자
  │  (스트리밍으로 받음)
  ▼
[ 우리 서버 ]
  ├─ 1. 인증·사용자별 한도 확인      ← 내 서비스의 레이트 리밋
  ├─ 2. 캐시 조회                    ← 같은 질문이면 여기서 끝
  ├─ 3. 큐 / 동시 호출 제한          ← 업스트림을 한 번에 너무 못 부르게
  ├─ 4. LLM API 호출                 ← 타임아웃·재시도·스트리밍
  └─ 5. 사용량 기록                  ← 토큰 수, 비용, 요청 ID
```

각 층마다 막아야 할 문제가 다릅니다. 아래에서 하나씩 살펴보겠습니다.

## 1. 한도: 업체 한도와 내 한도

Anthropic 문서 기준 Messages API 한도는 분당 요청 수 (RPM), 분당 입력 토큰 (ITPM), 분당 출력 토큰 (OTPM) 으로 모델별로 설정됩니다. 하나라도 초과하면 429 가 발생하며, 응답에 `retry-after` 헤더가 있으면 해당 초만큼 기다린 후 다시 보내야 합니다. 한도 방식은 토큰 버킷이므로 고정된 구간마다 리셋되는 것이 아니라 용량이 계속 채워집니다. 버킷 알고리즘 자체는 [레이트 리밋과 트래픽 제어](#/post/infra-rate-limit) 항목에 정리해 두었습니다.

몇 가지 눈에 띄었던 점입니다.

- 한도는 조직의 사용 등급 (tier) 에 따라 다릅니다. 문서에는 등급별 표가 있지만 숫자가 모델마다, 시점마다 바뀌어 여기에는 옮기지 않았습니다.
- 대부분의 모델에서 캐시에서 읽은 입력 토큰은 ITPM 에 포함되지 않습니다. 따라서 캐시를 사용하면 같은 한도로 더 많은 처리가 가능합니다.
- 429 가 모두 일시적인 것은 아닙니다. 월 지출 상한에 닿으면 같은 429 `rate_limit_error` 가 발생하지만 `retry-after` 가 없으며 다음 달 초까지 계속 실패합니다. SDK 의 자동 재시도도 효과가 없습니다. `error.details.error_code` 가 `enforced_spend_limit_reached` 인지 여부로 구분한다고 합니다.
- 제가 직접 설정한 지출 상한에 닿으면 429 가 아닌 400 이 발생합니다.

따라서 서비스에는 두 종류의 한도가 필요합니다. 업체가 걸어둔 한도를 넘지 않게 하는 것과, 사용자 한 명이 내 한도를 혼자 다 쓰지 못하게 하는 것입니다. 후자는 업체가 대신 해주지 않습니다.

## 2. 캐시: 같은 질문엔 다시 안 부른다

가장 저렴한 호출은 아예 호출하지 않는 것입니다. 응답 캐시는 질문 (과 모델, 설정) 을 해시하여 키로 사용하고 결과를 저장합니다. [캐시와 Redis](#/post/db-cache-redis) 의 방식을 그대로 가져옵니다. 다만 LLM 에서는 조건이 붙습니다.

- 같은 입력에 매번 다른 답이 나올 수 있으므로, "똑같은 답을 줘도 되는 질문"에만 사용합니다. FAQ 형 질문이나 번역, 분류 등에 해당합니다.
- 사용자 개인 정보가 포함된 응답은 키에 사용자를 넣거나 아예 캐시하지 않습니다.

이것과 이름이 같지만 다른 것이 업체가 제공하는 프롬프트 캐싱입니다. 응답을 저장하는 것이 아니라 긴 프롬프트의 앞부분 처리 결과를 재사용합니다. 문서 기준 기본 수명은 5 분이며 히트할 때마다 갱신됩니다. 읽기 단가는 기본 입력 단가의 0.1 배인 모델이 많고, 쓰기는 5 분짜리가 1.25 배입니다. 접두가 정확히 같아야 히트합니다. 자세한 내용은 [프롬프트 캐싱](#/post/ai-prompt-caching) 항목을 참고하세요.

| | 응답 캐시 (내 서버) | 프롬프트 캐싱 (업체) |
|---|---|---|
| 저장하는 것 | 완성된 답 | 프롬프트 앞부분의 처리 결과 |
| 히트하면 | LLM 을 아예 안 부름 | 호출은 하되 입력 단가·한도가 줄어듦 |
| 조건 | 같은 질문 | 앞부분이 글자 단위로 같음 |

## 3. 큐와 동시성 제한

ユーザーが一度に大量にアクセスすると、リクエストが一気にアップストリームへ送られ、制限に達してしまいます。そのため、サービス側で同時に送出される呼び出し数を制限します。簡単な方法としてはセマフォール、大規模なものとしてはメッセージキューとワーカーです。これは [非同期処理とメッセージキュー](#/post/be-async-queue) で扱われる構造ですが、LLM の場合には理由がさらに一つあります。応答に時間がかかる作業は、リクエスト内で完了させようとせず、作業をキューに入れ、ユーザーには「処理中」と表示する方が接続管理が容易です。

Anthropic 側にもこのような用途の Message Batches API が存在します。ドキュメントでは、長いリクエストで接続が切断されるリスクを減らす方法として紹介されており、結果はポーリングで取得する方式であると説明されています。リアルタイム性が不要な大規模作業に適した方式です。

## 4. ストリーミングとタイムアウト

LLM の応答は長いため、すべて生成されるまで待たせるとユーザーは空白の画面を見続けることになります。そのため、`stream: true` を設定してサーバー送信イベント (SSE) を受け取り、生成される 대로 流し出します。ドキュメントに示されたフローは `message_start`、複数の `content_block_delta`、そして `message_stop` の順で、その間に `ping` が混じることもあります。

ストリーミングは体感速度の問題だけではありません。ドキュメントでは、10 分以上の長いリクエストや `max_tokens` が大きいリクエストをストリーミングなしで送るべきではないと述べています。ネットワークがアイドル接続を切断してしまうためです。公式 SDK では、ストリーミングを使用しないリクエストが 10 分を超える可能性があれば、検証段階でブロックするとのことです。

さらに一つ。ストリーミングは HTTP 200 を受信した後でもエラーが発生する可能性があります。ドキュメントの例では、イベントストリーム内に `overloaded_error` が含まれる場合があります。この場合、ステータスコードで処理する通常のエラーハンドリングは通用しないため、ストリームを読み取るコードが `error` イベントを直接扱う必要があります。

タイムアウトについては、接続確立にかかる時間と、応答がすべて揃うまでの全体的な時間の 2 つに分けて考えるのが適切でしょう。ストリーミングの場合、「次のスライスが来るまでどれくらい待つか」の方がより有用な基準となります。具体的な値はサービスごとに異なるため、ここでは数値を記載しません。

## 5. 再試行とエラー処理

ドキュメントのエラーコードの中で、サーバーが一時的に受け入れられないケースは 429、500、504、529 です。529 は API が全体で過負荷の場合に発生し、500 は Anthropic 内部のエラーのため指数関数的なバックオフ（指数バックオフ）で再試行するよう指示されています。逆に、400、401、403、413 はリクエストそのものが間違っているため、再度送っても同じ結果になります。再試行すべきものとしないものを区別する必要があります。

公式 SDK は、接続エラー、429、5xx を基本 2 回指数バックオフで再試行し、`retry-after` が指定されている場合はその値に従います。`max_retries` で調整します。自分で実装する場合はこのルールに従えばよいですが、SDK を使用しながら自分のコードで再度再試行をラップすると、回数が掛け算されてしまう点に注意が必要です。

<details>
<summary>詳細な解説：同時実行制限 + キャッシュ + 再試行を組み合わせた小さなサンプル</summary>

実際の API の代わりに、40% の確率で過負荷（529 の役割）を返す偽の関数を置き、セマフォールで同時呼び出しを 3 つに制限し、応答キャッシュと指数バックオフ再試行を組み合わせたコードです。実際に実行しました。

```python
import asyncio, random, hashlib

class Busy(Exception): pass

calls = 0
async def fake_llm(prompt):
    """진짜 API 대신 쓰는 가짜. 40%는 과부하, 가끔 느림."""
    global calls
    calls += 1
    await asyncio.sleep(random.choice([0.05, 0.05, 0.05, 0.3]))
    if random.random() < 0.4:
        raise Busy("529")
    return f"answer({prompt})"

cache = {}
sem = asyncio.Semaphore(3)  # 동시에 3개까지만 업스트림으로

async def ask(prompt, retries=4, timeout=0.2):
    key = hashlib.sha256(prompt.encode()).hexdigest()
    if key in cache:
        return cache[key]
    async with sem:
        for n in range(retries + 1):
            try:
                out = await asyncio.wait_for(fake_llm(prompt), timeout)
                cache[key] = out
                return out
            except (Busy, asyncio.TimeoutError):
                if n == retries:
                    return "잠시 후 다시 시도해 주세요"
                await asyncio.sleep(min(2 ** n * 0.05, 1) * random.random())

async def main():
    random.seed(1)
    prompts = ["a", "b", "a", "c", "a", "b"] * 3
    res = await asyncio.gather(*(ask(p) for p in prompts))
    print(len(prompts), "요청 / 업스트림 호출", calls, "/ 캐시 항목", len(cache))
    print(sorted(set(res)))
asyncio.run(main())
```

実行結果は以下の通りでした。

```
18 요청 / 업스트림 호출 40 / 캐시 항목 3
['answer(a)', 'answer(b)', 'answer(c)', '잠시 후 다시 시도해 주세요']
```

リクエストは 18 個ありますが、異なる質問は 3 つしかなく、アップストリームへの呼び出しは 40 回でした。理由は二つあります。偽の関数が頻繁に失敗して再試行が追加されたことと、同じ質問を複数のリクエストで同時に送ると、まだキャッシュに値がないためすべてアップストリームへ送出されたことです。これをキャッシュスタンプede（キャッシュ汚染）と呼びます。このコードはそれを防ぎません。防ぐには、同じキーの進行中の呼び出しを一つにまとめる仕組みが必要です。また、再試行を使い果たしたリクエストには案内文が返されますが、その文が結果集合に混ざって出力されていることも確認できます。実際のサービスではこれをキャッシュに入れるべきではありません（上記コードは成功のみをキャッシュします）。

遅延時間や確率は偽の値であり、実際の API の動作とは無関係です。構造が動作するかを確認するためのものです。

</details>

<details>
<summary>詳細な解説：エラーコード表</summary>

Anthropic のエラードキュメントから転記した要約です。

| コード | 意味 | 再度送信しても |
|---|---|---|
| 400 | リクエスト形式・内容の問題（設定した支出上限に達した場合もこちら） | 無効 |
| 401 / 403 | キーの問題 / 権限不足 | 無効 |
| 413 | リクエストが大きすぎる | 無効 |
| 429 | 制限超過または月間支出上限 | `retry-after` があればその分待つ、なければ無効な場合がある |
| 500 | Anthropic 内部エラー | 指数バックオフで再試行 |
| 504 | 処理中のタイムアウト | ストリーミングの使用を検討 |
| 529 | API の過負荷 | 少し待ってから再試行 |

すべてのレスポンスには `request-id` ヘッダーが含まれており、エラー本文にも `request_id` が含まれています。サポートチームへの問い合わせに使用するよう指示されているため、ログにも併せて残しておくのが望ましいです。

</details>

## 6. コスト制御と記録

リクエストごとにトークンがコストとなるため、サーバーログにリクエスト数だけを記録するだけでは不十分です。レスポンスに含まれる入力・出力トークンの使用量を基に、ユーザーや機能ごとの使用内訳を記録することで、コストの発生箇所を把握できます。キャッシュヒットの有無は、レスポンス内の `cache_creation_input_tokens` および `cache_read_input_tokens` が 0 でないかどうかで確認できると文書に記載されています。

制御手段としては概ね以下のものがあります。

- ユーザー別・プラン別の日次トークン上限をサービス側で直接設定します。
- 簡単な質問には小さなモデル、難しい質問には大きなモデルを使用するように分けます。
- コンソールから支出上限を自分で下げておきます（月間上限を超え前に防ぐための安全装置）。
- リアルタイム性が不要な処理はバッチ処理として実行します。

原価の計算方法は [AI サービスのコスト構造](#/post/app-cost) に別途記載されています。サーバーを増設することで解決可能なボトルネックについては [オートスケーリングと拡張](#/post/infra-autoscaling) を参照してくださいが、LLM の呼び出しはサーバー数を増やしてもベンダー側の制限額が変わらないため、サーバー台数と処理量は比例しません。この点が一般的なサービスとの最大の違いだと感じました。

## よくある誤解

- 429 エラーが発生したら必ず待ってから再試行すればよい：月間支出上限により発生する 429 は `retry-after` ヘッダーが含まれず、継続的に失敗します。
- ストリーミングであればエラーはステータスコードで判別できる：200 を受信した後でも、ストリーム内でエラーイベントが発生する可能性があります。
- プロンプトキャッシングを使用しているためレスポンスキャッシングは不要：両者は異なる仕組みです。一方は入力コストを削減し、他方は呼び出し自体を削減します。
- サーバーを増やすと処理能力が向上する：ボトルネックがベンダー制限であれば、サーバー台数は関係ありません。
- `max_tokens` を大きく設定すると制限額を多く消費する：文書によると OTPM は実際に生成されたトークンのみカウントされます。ただし、大きな値をストリーミングなしで使用すると接続問題が発生する可能性があります。
