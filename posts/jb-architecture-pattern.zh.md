在信息处理技术员考试中，软件架构部分主要分为两大块：一是系统整体如何划分（架构模式），二是划分后的模块质量如何（模块化、耦合度与内聚度）。前半部分是关于名称与特征匹配的章节，后半部分则是需要记忆顺序的章节。针对历年真题，我不做直接搬运，而是整理其出题形式以及解题时的判断依据。

## 什么是架构

架构是指定义系统由哪些要素组成，以及这些要素之间如何相互连接的宏观框架。它必须在编写代码之前确定，且后期修改成本高昂。因此，可以将性能、安全、维护性等非功能性需求视为在此阶段确定的内容。关于如何提取需求，将在 [详细 → 需求确认与分析](#/post/jb-requirements) 中单独讨论。

微软 Azure 架构指南将架构风格描述为“具有特定共同特征的一类架构”。风格会对设计施加约束，即规定可能存在哪些要素以及要素之间允许建立何种关系。遵守这些约束，就能获得该风格所预期的优势。在记忆模式名称时，同时思考“该模式施加了何种约束”，有助于减少混淆。

## 架构模式总结

| 模式 | 核心结构 | 一句话特征 |
|---|---|---|
| 分层 (Layered, N-tier) | 表现层 → 业务逻辑层 → 数据访问层 | 每一层仅调用其下层 |
| MVC | Model / View / Controller | 分离数据、视图与输入处理 |
| 管道 - 过滤器 | 过滤器通过管道连接 | 前一阶段的输出是后一阶段的输入 |
| 客户端 - 服务器 | 请求方与响应方 | 服务器持有资源，客户端发起请求 |
| 事件驱动 | 生产者 → 事件通道/代理 → 消费者 | 生产者和消费者互不相识 |
| 微服务 | 多个小型独立服务 | 每个服务拥有自己的数据并独立部署 |

上表的说明基于各模式在 Wikipedia 条目及 Azure 架构指南中的内容整理而成。下面将逐一进行更深入的探讨。

### 分层架构

以 Azure 指南为标准，N-tier 是将应用程序划分为逻辑层和物理层，且每一层仅调用其下层的传统企业级结构。通常包括表现层、业务逻辑层和数据访问层。已采用分层架构的应用程序在进行迁移时变更较少是其优势；而在同一份文档中也指出，若按水平方向划分，变更可能波及多个部分的劣势。关于在实际代码中如何划分层次，请参考 [详细 → 分层架构](#/post/be-layered-architecture)。

### MVC

根据 Wikipedia 的解释，这是一种用于用户界面的模式，将程序逻辑分为三个部分：

- **Model**：应用程序的数据及其相关规则，与界面无关。
- **View**：负责展示信息的部分，同一份数据可由多个 View 展示。
- **Controller**：接收用户输入，并将其转换为对 Model 或 View 的指令进行传递。

MVC 模式由 Trygve Reenskaug 在 20 世纪 70 年代末于 Xerox PARC 进行 Smalltalk 开发工作时创建。考试中只要准确对应“输入是 Controller、数据是 Model、界面是 View"，大部分题目即可解答。MVP 和 MVVM 被视为从 MVC 衍生出的变体。为应对选项中同时出现这些名称的情况，务必先明确 MVC 的三个角色。

### 管道 - 过滤器

处理阶段按顺序连接，前一阶段的输出作为后一阶段的输入。阶段称为“过滤器”，连接称为“管道”，管道中通常包含一定的缓冲机制。虽然结构简单且成本低廉，但 Wikipedia 评价其弹性、容错性和扩展性有限。联想到 Linux 中使用 `|` 符号连接命令的形式，有助于记忆。

### 客户端 - 服务器

这是一种服务器提供功能或资源，客户端发送请求的结构。Web 浏览器与 Web 服务器是最常见的例子。由于服务器需要应对多个客户端，因此服务器端的负载和故障会对整体产生影响，这一点在叙述型选择题中可作为解题线索。

### 事件驱动

Azure 指南中指出该模式采用发布 - 订阅模型。事件生产者不知道消费者是谁而创建事件，消费者则对自己感兴趣的事件做出响应。两者之间通过事件通道或代理连接。虽然消除了生产者和消费者之间的直接依赖，但保证传递、事件顺序以及最终一致性被视为难点。

### 微服务

将应用程序拆分为小型且独立的服务集合。每个服务负责一个业务功能，并拥有自己的数据存储。它们通过 API 相互通信，并且可以按服务分别进行开发、部署和扩展。然而，Azure 指南指出，服务发现、数据一致性和分布式系统管理会变得复杂。这种架构并非适用于所有小型应用。

## 选择模式的依据

| 情况 | 适合的模式 |
|---|---|
| 迁移已构建为分层结构的业务系统 | 分层架构 (N-tier) |
| 希望将界面与数据逻辑分离 | MVC |
| 分阶段转换数据 | 管道 - 过滤器 (Pipe-Filter) |
| 实时处理、松散耦合 | 事件驱动 |
| 复杂领域且变更频繁 | 微服务 |

Azure 指南的表格中也总结道：N-tier 适用于“传统业务领域、更新频率低”，微服务适用于“复杂领域、频繁更新”，而事件驱动则适合 IoT 和实时系统。同一份文档也指出，与其单纯追求理论结构，不如适当放宽限制以贴合现实更为妥当。

## 模块化与耦合度、内聚度

模块化是将系统按功能单元进行划分的工作。划分的依据是耦合度（Coupling）和内聚度（Cohesion）。耦合度衡量模块之间的相互依赖程度，内聚度则衡量模块内部元素围绕单一功能的聚集程度。良好的设计应追求低耦合和高内聚。Wikipedia 指出，高内聚往往伴随着低耦合的趋势。

概念详解可参考 [详细 → 耦合与内聚](#/post/be-coupling-cohesion)，此处仅固定顺序以供测试使用。

### 耦合度（从高到低）

| 序号 | 类型 | 含义 |
|---|---|---|
| 1 | 内容耦合 (Content) | 直接访问或使用其他模块的内部代码或分支 |
| 2 | 公共耦合 (Common) | 多个模块共享相同的全局数据 |
| 3 | 外部耦合 (External) | 共享由外部定义的格式、通信协议或设备接口 |
| 4 | 控制耦合 (Control) | 传递用于控制其他模块流程的值（如标志位等） |
| 5 | 标记耦合 (Stamp) | 共享复合数据结构，但仅使用其中一部分 |
| 6 | 数据耦合 (Data) | 仅通过参数交换基本数据 |

上述顺序和定义遵循了 Wikipedia "Coupling"条目中按“从高耦合到低耦合”排列的内容。最理想的是数据耦合。

### 内聚度（从高到低）

| 序号 | 类型 | 聚集原因 |
|---|---|---|
| 1 | 功能内聚 (Functional) | 所有元素共同贡献于一个定义良好的任务 |
| 2 | 顺序内聚 (Sequential) | 一个元素的输出是下一个元素的输入 |
| 3 | 通信内聚/信息内聚 (Communicational) | 处理相同的数据 |
| 4 | 过程内聚/逻辑内聚 (Procedural) | 遵循既定的执行顺序 |
| 5 | 时序内聚 (Temporal) | 在程序的同一时间点执行 |
| 6 | 逻辑内聚 (Logical) | 属于同一类别，但执行的任务各不相同 |
| 7 | 偶然内聚 (Coincidental) | 没有任何特殊原因而聚集在一起 |

Wikipedia 的 "Cohesion"条目将功能内聚列为最佳，偶然内聚列为最差。也有观点认为，该列表中的排名并不代表持续改进的阶段。

首字母连起来容易记忆：耦合度为“内·公·外·制·斯·资”，内聚度为“功·顺·通·切·时·论·偶”。由于两张表的顺序方向相反，耦合度是从差到好，而内聚度是从好到差，分别记录一次会减少混淆。

## 常见题型与解析

- **模式名称选择**：选项中会出现如“数据/界面/输入分离”、“前级输出作为后级输入”、“仅调用下层”等特征描述。将其与上方表格中的单行特征对应即可解答。
- **耦合度与内聚度顺序**：询问最低耦合度或最高内聚度是什么。只需记住两端即可解题。最低耦合度是“数据耦合”，最高内聚度是“功能内聚”。
- **根据情境匹配类型**：例如看到“两个模块使用相同的全局变量”对应公共耦合，“一个模块传递标志位以改变另一个模块的行为”对应控制耦合。只需记忆耦合度表中的“含义”栏即可。
- **设计原则配对**：题目会询问为何低耦合和高内聚是好的。若理解为“修改一个模块时，需要同时修改的地方减少了”，则大体正确。

在模式单元中，仅靠死记硬背名称容易混淆，像上面这样将单行特征与名称结合记忆会更高效。

## 常见误解

- 耦合度必须为 0：如果模块之间没有任何交互，系统就无法成立。目标是尽量减少连接强度。
- 微服务总是优于分层架构：Azure 指南也指出，在复杂且频繁变更的领域，需要较高的运维成熟度。
- MVC 仅用于 Web：MVC 被描述为用户界面设计模式，仅在 Web 框架中常见使用。
- 高内聚意味着模块较小：这与规模无关。即使处理单一任务导致分支增多，内聚度依然很高。
