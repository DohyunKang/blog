ローカルモデルとは、モデルファイルを PC にダウンロードして直接実行する方式であり、導入するかしないかは主に VRAM の計算で決まります。

## ローカル実行とは何か

API で利用するモデルは他者のサーバー上で動作しますが、ローカルではモデルの重み（ファイル）を自社のコンピュータに置き、自社の CPU や GPU で計算を行います。インターネット接続が不要であり、トークンあたりの料金はかかりません。その代わり、PC が処理可能なサイズのモデルのみを実行できます。

モデルは結局のところ、非常に多くの数字（重み）からなる表です。パラメータ数が 8B の場合、数字の個数は 80 億個になります。これを 16 ビット（2 バイト）で保存すると約 16GB となり、計算時には GPU メモリ（VRAM）に読み込んでおくことで高速化できます。しかしここでボトルネックが発生します。そのため、数字をより少ないビット数で表現する「量子化」がローカルの核心的な技術となりました。

関連概念は [詳細 → LLM とは何か](#/post/ai-llm) に記載されており、サーバー側の最適化については [詳細 → 推論最適化](#/post/ml-inference) で扱っています。

## 量子化

量子化とは、重みを 16 ビットではなく、8 ビットや 4 ビットといった短い整数に変換して保存する手法です。サイズはビット数にほぼ比例して減少し、代わりに精度が若干低下します。

llama.cpp リポジトリでは、1.5・2・3・4・5・6・8 ビットの整数量子化をサポートしていると記載されています。同じ文書の Llama-3.1-8B の例示表を見ると以下のようになります。

| 種類 | パラメータあたりのビット数 | ファイルサイズ |
|---|---|---|
| F16 | 16.00 | 14.96 GiB |
| Q8_0 | 8.50 | 7.95 GiB |
| Q6_K | 6.56 | 6.14 GiB |
| Q5_K_M | 5.70 | 5.33 GiB |
| Q4_K_M | 4.89 | 4.58 GiB |
| Q3_K_M | 4.00 | 3.74 GiB |
| Q2_K | 3.16 | 2.95 GiB |

名前には読み方のルールがあります。「Q」の後の数字は概ねビット数を表します。「K」はブロック単位でスケールを別途設定する方式（K-quants）を示し、末尾の S/M/L は小さめ/中程度/大きさを意味します。名前に 4 ビットが含まれていても実際には 4.89 ビットのように、スケール値などの付加情報があるため表記よりも少し多くのビットを使用します。

品質はどうでしょうか。llama.cpp の文書では量子化が精度の低下を引き起こす可能性があり、通常は perplexity や KL divergence で測定するとだけ記載されており、具体的な数値は載せていません。そのため、「Q4 なら何％低下するか」といった数字はこの記事には記載しません。文書で言及されている注意点には二つあります。一つは既に量子化されたモデルを再度量子化すると品質が著しく低下する可能性があること、もう一つは imatrix ファイルを使用することで損失を減らせるということです。

<details>
<summary>量子化の仕組みを数字で見ると</summary>

最も単純な形式は以下の通りです。ブロック（例：32 個の数字）ごとに最大の絶対値を見てスケール s を決定します。各数字 w は q = round(w / s) で 4 ビット整数に格納し、計算時には q × s で復元して使用します。ブロックごとにスケールが一つ付くため、パラメータあたりのビット数は 4 よりも少し大きくなります。

K-quants はこれをさらに賢く使い、ブロック内にサブブロックを設けるような方式です。
</details>

## GGUF

GGUF は llama.cpp シリーズで使用するモデルファイル形式です。GGML リポジトリの文書によると、一つのファイルにモデルを全て収め、高速読み込みを実現し、新しいメタデータを追加しても古いモデルが壊れないように設計されています。

ファイル内は以下の 4 つの部分から構成されます。

1. ヘッダー：マジックナンバー、バージョン、テンソルの数、メタデータの数
2. メタデータ：アーキテクチャ、コンテキスト長、アテンション・RoPE 設定、トークナイザー、チャットテンプレート
3. テンソル情報：名前、次元、タイプ、位置
4. テンソルデータ：実際の重み（量子化済みを含む）

トークナイザーやチャットテンプレートもファイルに含まれているため、一つのファイルがあれば実行可能です。テンソルの位置は決まった間隔（デフォルト 32 バイト）に合わせて配置されているため、ファイルをメモリにそのままマッピング（mmap）して使用することもできます。ファイル名には `モデル名-サイズ-バージョン-量子化.gguf` という規則があり、大きなモデルは `00001-of-00003` のように分割されます。

## VRAM 計算方法

VRAM に割り当てられるのは主に二つです。重みと KV キャッシュです。それにランタイムで使用される作業領域が少し加わります。

重み = パラメータ数 × パラメータあたりのビット数 ÷ 8。KV キャッシュは対話が進むほど大きくなるメモリであり、コンテキスト長に比例します。（[詳細 → コンテキストウィンドウとトークン](#/post/ai-context-window)）

```python
def weights_gib(params_b, bpw):
    return params_b*1e9*bpw/8/2**30

def kv_gib(layers, kv_heads, head_dim, ctx, bytes_per=2):
    return 2*layers*kv_heads*head_dim*ctx*bytes_per/2**30   # 2 = K와 V
```

Llama 3.1 8B（パラメータ約 8.03B、32 レイヤー、KV ヘッド 8、ヘッド次元 128 と仮定）で試した結果です。構造に関する数字はモデルカードを開いて確認したものではありませんが、私が知っている値であり誤りがある可能性がありますが、重みについては llama.cpp の文書にある表（14.96 / 7.95 / 4.58 GiB）と一致しています。

| 항목 | 크기 |
|---|---|
| 가중치 F16 | 14.96 GiB |
| 가중치 Q8_0 | 7.95 GiB |
| 가중치 Q4_K_M | 4.57 GiB |
| KV 캐시, 컨텍스트 4,096 (f16) | 0.50 GiB |
| KV 캐시, 컨텍스트 32,768 (f16) | 4.00 GiB |
| KV 캐시, 32,768 (8비트 근사) | 2.12 GiB |

따라서 Q4_K_M 에서 컨텍스트 길이를 4k 로 설정하면 약 5GiB 가 필요해 8GB 카드에도 들어가고, 컨텍스트를 32k 로 늘리면 KV 캐시만 추가로 4GiB 가 필요합니다. 모델이 작아도 컨텍스트 길이를 키우면 메모리가 부족해질 수 있다는 뜻입니다. 위 숫자는 직접 파이썬으로 계산하여 얻은 값이며, 실제 사용량은 런타임 작업 공간 때문에 이보다 조금 더 소요됩니다.

KV 캐시도 양자화가 가능합니다. Ollama FAQ 에 따르면 `OLLAMA_KV_CACHE_TYPE` 의 기본값은 f16 이며, q8_0 은 메모리를 절반, q4_0 은 4 분의 1 정도 사용합니다. q8_0 은 품질 손실이 매우 작고, q4_0 은 컨텍스트가 길어질 때 손실이 눈에 띄게 될 수 있다고 합니다. 이는 플래시 어텐션을 켜고 사용할 때의 설정입니다.

## 모델이 VRAM 보다 클 때

llama.cpp 는 CPU 와 GPU 를 혼용하는 하이브리드 추론을 지원한다고 명시되어 있습니다. 일부 층만 GPU 에 배치하고 나머지는 시스템 메모리에서 CPU 가 계산합니다. 실행은 되지만 CPU 쪽 층이 병목이 되어 눈에 띄게 느려집니다. Ollama 에서는 `ollama ps` 의 Processor 열에서 "100% GPU"인지, 아니면 "48%/52% CPU/GPU"처럼 분산되어 있는지 확인할 수 있습니다. 느리다고 느껴질 때 먼저 이 부분을 확인해 보세요.

## Ollama 와 llama.cpp

두者的인 관계는 [자세히 → 오픈소스 분석: llama.cpp](#/post/repo-llama-cpp) 와 [자세히 → 오픈소스 분석: Ollama](#/post/repo-ollama) 에서 따로 다루고 있습니다. 여기서는 사용자 관점에서의 차이점만 정리합니다.

| | llama.cpp | Ollama |
|---|---|---|
| 성격 | C/C++ 추론 엔진 | 모델 로드, 실행, 서버 기능을 통합한 도구 |
| 지원 하드웨어 | CUDA, Metal, Vulkan, CPU 등 | 백엔드와 장치가 지원하면 GPU 사용 |
| 조정 | 양자화, 층 분배, 옵션 직접 지정 | 환경 변수 및 모델 설정으로 조정 |
| 서버 | OpenAI 호환 API 서버 제공 | 로컬 API 서버 |

llama.cpp 저장소는 최소한의 설정으로 어디서나 추론할 수 있도록 하는 것을 목표로 하며, Apple Silicon 을 "first-class citizen" 으로 최적화했다고 기술합니다. Ollama 에서 자주 다루는 설정은 FAQ 기준 다음과 같습니다.

- `OLLAMA_KEEP_ALIVE`: 모델을 메모리에 유지하는 시간. 기본값 5 분이며, 음수면 계속 유지하고 0 이면 응답 직후 해제됩니다.
- `OLLAMA_NUM_PARALLEL`: 모델당 동시 처리 요청 수. 기본값 1 입니다. 메모리는 이 값 × 컨텍스트 길이에 비례하여 증가합니다.
- `OLLAMA_CONTEXT_LENGTH`: 기본 컨텍스트 길이 4096 토큰

기본 컨텍스트가 4096 인 점은 실수하기 쉽습니다. 긴 문서를 입력했는데 앞부분이 잘리는 이유가 이것일 수 있습니다. 서비스로 서빙하는 구조는 [자세히 → AI 서비스 서빙 구조](#/post/infra-ai-serving) 에서 이어집니다.

## 속도와 품질 트레이드오프

- 비트를 줄이면 파일 크기가 작아지고 메모리 사용량이 줄어들며, 대개 속도도 빨라집니다. 대신 품질이 떨어집니다. 어디까지가 괜찮은지는 모델과 용도에 따라 다르므로 직접 사용해 보고 결정해야 합니다.
- 같은 VRAM 이라면 "큰 모델을 낮은 비트로"와 "작은 모델을 높은 비트로" 중 선택해야 합니다.
- 컨텍스트를 늘리면 KV 캐시가 증가하고, GPU 에서 밀려나면 속도가 크게 저하됩니다.
- 층을 CPU 로 넘기면 실행은 되지만 느려집니다.

모델을 내 데이터에 맞추고 싶다면 양자화 모델 위에 LoRA 를 추가하는 방법이 있는데, 이는 [자세히 → 파인튜닝](#/post/ml-finetuning) 에서 다룹니다.

## 흔한 오해

- 양자화를 하면 모델이 멍청해진다: 줄이는 만큼 손실은 있지만, 비트가 높은 구간 (8 비트 근처) 은 손실이 작다고 알려져 있습니다. 문서에는 구체적인 수치가 명시되지 않아 여기서는 숫자를 사용하지 않습니다.
- 모델 파일 크기만 VRAM 에 맞으면 된다: KV 캐시와 작업 공간도 추가로 필요합니다. 컨텍스트가 길어질수록 더 그렇습니다.
- 이미 양자화된 파일을 더 줄이면 되겠지: 문서의 품질이 크게 나빠질 수 있다고 경고합니다. 원본 16 비트에서 양자화하는 것이 맞습니다.
- GPU 에 안 들어가면 못 돌린다: 느릴 뿐이며 하이브리드 방식으로 실행됩니다.
