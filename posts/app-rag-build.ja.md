[RAG](#/post/ai-rag) は概念だけ読むと簡単そうに見えるが、実際に作ってみると手がかりとなる箇所が決まっている。文書をどう分割するか、何をベクトルにするか、いくつを検索して結合するか、うまくいっているかどうかをどう知るか。この記事は、その 5 つのポイントを順番に追いつつ、外部サービスを使わず動作する最小限のコードを作成した記録である。コードは実際に実行して確認済みだ。

## 作るもの

社内の FAQ などの短い文書 3 つ（返金、配送、アカウント）を用意し、質問が来たら関連する断片を検索してプロンプトにまでつなげる。モデルの呼び出しは意図的に省いた。呼び出し部分はどの API を使おうとも「作成したプロンプトを送信する」1 行で済むため、学ぶべきことはそれ以前にある。

```
문서 → 청킹 → 임베딩 → 저장(벡터 DB 자리) → [질문] → 검색 → 프롬프트 → (모델) → 답
```

| ステップ | この記事のコード | 実際の利用時 |
|---|---|---|
| チャンキング | 段落単位で集めて文字数を超えると分割 | トークン基準、見出し単位など |
| エンベッディング | 文字 2-gram ハッシュ（おもちゃ） | エンベッディングモデル API やローカルモデル |
| ベクトル DB | numpy の行列一つ | 文書が増えたらベクトル DB |
| 検索 | コサイン類似度上位 k 件 | ハイブリッド検索、再順位付け |
| プロンプト | データ + 質問を付与 | 同じ |

エンベッディングがおもちゃになっている理由は一つ。本物のエンベッディングモデルはインストールやキーが必要になるため、この記事のコードをそのまま動かすことができない。代わりに関数一つ（`embed`）だけ変更すれば残りはそのまま使えるようにした。おもちゃのエンベッディングは文字が重なる程度を見るだけなので、意味検索ではない。[エンベッディング](#/post/ai-embedding) が本当にやること（意味が似ているほど近くなる）は、このコードでは起こらない。

## 全体コード

```python
import re, zlib
import numpy as np

DOCS = {
    "refund.md": "환불 규정\n\n구매 후 7일 이내에는 사유와 관계없이 전액 환불된다. 7일이 지나면 환불되지 않는다.\n\n디지털 상품은 다운로드를 시작하면 환불이 어렵다.",
    "shipping.md": "배송 안내\n\n주문 후 평일 기준 2~3일 안에 도착한다. 제주와 도서 지역은 하루가 더 걸린다.\n\n배송 조회는 마이페이지의 주문 내역에서 한다.",
    "account.md": "계정 안내\n\n비밀번호를 잊으면 로그인 화면의 비밀번호 찾기에서 이메일로 재설정 링크를 받는다.\n\n탈퇴하면 주문 내역은 5년간 보관된다.",
}

def chunk(text, size=70, overlap=15):
    paras = [p.strip() for p in text.split("\n\n") if p.strip()]
    out, buf = [], ""
    for p in paras:
        if buf and len(buf) + len(p) > size:
            out.append(buf)
            buf = buf[-overlap:] + "\n" + p
        else:
            buf = (buf + "\n" + p) if buf else p
    if buf:
        out.append(buf)
    return out

DIM = 512
def embed(text):
    # 장난감 임베딩: 글자 2-gram을 해시해서 벡터에 더한다.
    v = np.zeros(DIM)
    t = re.sub(r"\s+", "", text)
    for i in range(len(t) - 1):
        v[zlib.crc32(t[i:i+2].encode()) % DIM] += 1
    n = np.linalg.norm(v)
    return v / n if n else v

index = []  # (출처, 청크, 벡터)
for name, text in DOCS.items():
    for c in chunk(text):
        index.append((name, c, embed(c)))
M = np.stack([v for _, _, v in index])

def search(q, k=2):
    scores = M @ embed(q)
    top = np.argsort(-scores)[:k]
    return [(index[i][0], index[i][1], float(scores[i])) for i in top]

def build_prompt(q, hits):
    ctx = "\n\n".join(f"[자료 {i+1}: {n}] {c}" for i, (n, c, _) in enumerate(hits))
    return f"다음 자료만 근거로 답하라. 자료에 없으면 모른다고 답하라.\n\n{ctx}\n\n질문: {q}"

EVAL = [
    ("환불은 며칠 안에 해야 해?", "refund.md"),
    ("배송은 얼마나 걸려?", "shipping.md"),
    ("비밀번호 까먹었어", "account.md"),
    ("제주도는 배송이 더 느려?", "shipping.md"),
]

if __name__ == "__main__":
    print(len(index), "chunks")
    hit = 0
    for q, gold in EVAL:
        r = search(q, 1)
        ok = gold in [n for n, _, _ in r]
        hit += ok
        print(ok, q, "->", [n for n, _, _ in r])
    print("hit@1 =", hit / len(EVAL))
    print(build_prompt(EVAL[0][0], search(EVAL[0][0], 2)))
```

実行するとチャンク 6 つが生成され、評価質問 4 つすべてに対して正しい文書を最初に見つける（hit@1 = 1.0）。最後にモデルに送るプロンプトが出力される。

## 1. チャンキング

チャンキングとは文書を検索の単位として分割することである。コードでは空行で段落を区切り、段落を集めて `size` を超えると一つのチャンクを分割する。次のチャンクは前のチャンクの最後の `overlap` 文字を引き継いで始まる。

実行するとこの単純な重複の問題がすぐにわかる。チャンクリストの一つが「これ以降は返金されません。」で始まる。文字数で重複させるため、単語の真ん中で切断されている。前の文が「7 日」だったことを知らなければ、この断片だけでは意味が通じない。重複を文字数ではなく文単位で行うとこれがなくなる。Anthropic の Contextual Retrieval という記事でも、チャンクサイズ・境界・重複が検索性能に影響すると書かれており、チャンクは通常数百トークンを越えないとされている。

そして適切な大きさはデータによって異なる。この記事の 70 文字は文書が短すぎるため意図的に小さく設定した値である。

## 2. エンベッディング

`embed` は文章を長さ 512 の数字リストに変換する。おもちゃの方法は文字を二つずつ区切ってハッシュし、その箇所に 1 を加え、最後に長さを 1 に正規化する。長さを 1 に正規化しておくと、二つのベクトルの内積がそのままコサイン類似度になり、検索は行列乗算一回で終わる。

ハッシュに Python 標準の `hash()` を使うと実行するたびに値が変わってしまう（文字列のハッシュがプロセスごとにランダムにシャッフルされるため）。そのため `zlib.crc32` を使った。最初は `hash()` で書いたが、評価数値が揺らぐ可能性があることを知って変更した。

本物のモデルに変える際の注意点は二つある。文書と質問は同じモデルでエンベッディングする必要がある。また、エンベッディングの次元やモデル名を保存しておかないと、後でモデルを変更した際に古いベクトルと新しいベクトルが混ざってしまう。

## 3. 保存

`index` がチャンクリスト、`M` がベクトルを積んだ行列である。チャンクが数千個程度まではこれで十分だ。行列乗算は高速でコードも理解しやすい。数十万を超えたり、サーバーが複数あったり、文書が頻繁に変わったりする場合はその時にベクトル DB を使う。ベクトル DB が行うことは主に三つである。近似最近傍探索によりすべて比較せずに検索し、ディスクに保存し、メタデータでフィルタリングすることだ。今のコードにはこれらはいずれもない。[詳細 → ベクトル DB](#/post/db-vector)

保存時にソース（ファイル名）も一緒に記録したのは、プロンプトにソースを付与するためである。ソースがあることでモデルは答えと一緒に「どの資料から見たか」を言えるし、人間も確認しやすい。

## 4. 検索

`search` は質問をエンベッディングしてすべてのチャンクとの内積を求め、スコアが高い k 件を返す。k をいくつにするかは正解がない。Anthropic の記事ではモデルに 5 件、10 件、20 件を渡して比較したが、20 件が最も良かったという。多く渡すほど正解が含まれる確率は上がるが、多すぎるとモデルが散漫になる可能性があるため、実際に実験してみることを勧める。

意味検索だけでは、エラーコードのような正確な単語を見逃す可能性があることも同記事に書かれています。そのため、単語一致ベースの BM25 を併用し、順位を合成するハイブリッド手法が頻繁に採用されます。この記事のコードには実装していません。これは文書が小さく、差を確認できないためです。

## 5. プロンプト

`build_prompt` は資料を番号と出典を付けて列挙し、質問を最後に配置します。指示は「資料のみを根拠に答えよ、なければ知らないと言う」という 2 つです。この指示がない場合、モデルは資料にない部分を自らの知識で埋めてしまいます（[幻覚](#/post/ai-hallucination)）。プロンプトの作成テクニックについては [プロンプト](#/post/ai-prompt) に別途記載されています。

実際にモデルを接続する際は、この文字列を API のユーザーメッセージとして送信すればよいだけです。資料は [コンテキストウィンドウ](#/post/ai-context-window) 内に収める必要があるため、k とチャンクサイズの積が限度内か確認しておきます。

## 評価

作成した後に最も早く忘れ去ってしまう段階です。コードに `EVAL` として用意した質問と正解文書ペアがこの始まりです。検索で正解文書を上位 k に持ってきたかどうか（hit@k）のみを再計算することで、多くのことがわかります。答えが間違った場合に、原因が検索なのかモデルなのかを区別する最初の基準となるためです。

- 正解チャンクが検索結果に含まれていない → 検索（チャンキング、埋め込み、k）の問題
- 正解チャンクはあるが答えが間違っている → プロンプトまたはモデルの問題

この記事の hit@1 = 1.0 は信じてはいけません。4 つの質問に対して 3 つの文書という非常に簡単な試験であり、質問と文書が同じ単語を使用しているため、文字の重複だけで正解してしまいます。「返金」を「お金を戻すこと」と言い換えても、この玩具のような埋め込みモデルは即座に崩壊するようですが、この記事では検証していません。評価質問には、実際のユーザーが使わないような口調や、文書にない表現を用いることで初めて意味があります。

hit@k は検索のみを測定します。答えの品質も測定したいツールとして Ragas があります。文書リストページで確認した名前は、検索側の Context Precision、Context Recall、生成側の Faithfulness、Response Relevancy です。名前だけ見ると、必要なチャンクを取得したか、答えが取得した資料に忠実か、質問に適した答えかを分けて測定する構成のように見えます。

自分で行う場合は、質問 - 正解ペアを 20〜30 個を手で作成し、変更するたびに（チャンクサイズ、k、埋め込みモデル）hit@k を再計算することから始めればよいです。数字が上がったかどうかで判断し、勘で修正しないことが要点です。

- 埋め込みを真のモデルに交換：`embed` 関数だけを置き換えて、`DIM` をモデルの次元に合わせて調整します。
