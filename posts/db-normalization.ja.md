正規化とは、同じ事実が複数の箇所に重複して書かれるのを防ぐためにテーブルを分割する作業であり、1NF から 3NF はそれを 3 つの段階に分けたルールです。

## なぜ分割するのか

最初は Excel のように 1 つの表にすべて書き込みたいと思うものです。注文 1 つあたりに顧客名、メール、商品、価格、数量を 1 行で書けば見やすいでしょう。問題は、同じ顧客のメールアドレスや同じ商品の価格が各行で繰り返されてしまう点です。

Microsoft のドキュメントも同様の話から始まります。正規化はデータを整理するプロセスであり、重複と整合性のない依存関係を排除するためにテーブルを作成し、それらの関係を結びつける作業です。顧客住所の変更を容易にするためには、住所情報が `Customers` テーブルの 1 か所だけにある必要があるという例が挙げられます。

重複が生じることで起こる問題は通常、3 つに分類されます（Wikipedia のまとめ）。

| 名前 | 何が起きるか |
|---|---|
| 更新異常 | 繰り返される値の一部だけを修正してしまい、同じ事実に対して 2 つの異なる答えが返されてしまう |
| 挿入異常 | 他のデータが存在しない場合、ある事実を挿入できない（授業配当前に新任教員の名前を書けないような状態） |
| 削除異常 | 1 行を削除したことで、他の事実も一緒に消えてしまう |

正規化は、こうした異常が発生する構造を事前に防ぐものです。概念は 1970 年に Codd の関係型モデルとともに登場しました。1NF はその時、2NF と 3NF は 1971 年、BCNF は Codd と Boyce が 1974 年に定義しました。

## 実際に動かしてみた例：すべてを 1 つの表にすると

SQLite で小さな表を作成してみました。注文が 2 件あり、キーボードが 2 回登場しています。

```sql
CREATE TABLE flat(order_id INT, customer TEXT, email TEXT,
                  product TEXT, price INT, qty INT);
INSERT INTO flat VALUES
 (1,'민수','m@x.com','키보드',50000,1),
 (1,'민수','m@x.com','마우스',20000,2),
 (2,'지영','j@x.com','키보드',50000,1);
-- 2번 주문의 키보드 가격만 고쳤다
UPDATE flat SET price=55000 WHERE order_id=2 AND product='키보드';
SELECT DISTINCT price FROM flat WHERE product='키보드';
```

結果は 50000 と 55000 の 2 行でした。キーボードの価格が 2 つになっているのです。これが更新異常です。

## 1NF, 2NF, 3NF

3 つの段階を 1 行にまとめると以下のようになります。

| 段階 | ルール | 破ると現れるもの |
|---|---|---|
| 1NF | 1 つのセルに 1 つの値のみ。繰り返されるセル（Class1, Class2…）を作成しない | 項目が 3 つ目になるとセルを追加する必要がある |
| 2NF | キーが複数ある場合、キーの一部だけに依存する値は別テーブルに移す | 商品価格が注文行ごとに繰り返される |
| 3NF | キーではない値同士が互いに依存しないようにする | 顧客ランクによって割引率が各行で繰り返される |

Microsoft のドキュメントにある学生の例はこの点をよく示しています。最初は `Class1`, `Class2`, `Class3` というセルがある表です。1NF では授業を 1 行ずつ展開します。2NF では学生情報と受講情報を分離します。3NF では `Adv-Room`（指導教員の部屋番号）が学生ではなく教員に依存する値なので、`Faculty` テーブルに移します。

2NF と 3NF を混同しましたが、こうして覚えました。2NF は「キー全体に依存しているか」、3NF は「キーだけに依存しているか（他の一般的なセルを介していないか）」です。Wikipedia の定義では、3NF はキー以外の属性間の移行依存がない状態です。

<details>
<summary>詳しい解説：注文例を 3NF まで分割した結果</summary>

上記のフラットな表を分割すると、顧客、商品、注文、注文項目の 4 つになります。

```sql
CREATE TABLE customer(id INTEGER PRIMARY KEY, name TEXT, email TEXT UNIQUE);
CREATE TABLE product(id INTEGER PRIMARY KEY, name TEXT, price INT);
CREATE TABLE orders(id INTEGER PRIMARY KEY,
                    customer_id INT REFERENCES customer(id));
CREATE TABLE order_item(
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES product(id),
  qty INT, unit_price INT,
  PRIMARY KEY(order_id, product_id));
```

実行して確認したのは以下の 3 点です。

- `product` の 1 か所だけを修正すれば、キーボードの価格は 55000 の 1 つだけになります。
- 存在しない顧客 99 で注文しようとすると、`FOREIGN KEY constraint failed` エラーが発生します（SQLite は `PRAGMA foreign_keys=ON` をオンにする必要があります）。
- JOIN で注文 - 顧客 - 商品を再度結合すると、最初のフラットな表と同じ内容が得られます。

`order_item` に `unit_price` を別途置いたのは意図的です。商品価格が後から変更されても、過去の注文はその時点の価格である必要があるためです。これは重複のように見えますが、「注文時点での事実」であり別の値です。この部分はドキュメントで読んだものではなく、例を作成する過程で決めた設計です。

</details>

## ERD の描画

モデリングとは、表を分割する前に「何があり、それらがどう結びついているか」を先に図示する作業です。その図が ERD（実体 - 関係図）です。順序は以下の通り決めました。

1. 名詞を引き出す：顧客、商品、注文。
2. 各名詞の属性を書く：顧客は名前・メールなど。
3. 関係の数を決める：顧客 1 人に対して注文複数（1:N）、注文と商品は互いに複数（N:M）。
4. N:M は中間テーブルで解決する：そのため `order_item` が生まれます。

テキストで描くとこの程度です。

```
customer 1 ──< orders 1 ──< order_item >── 1 product
```

`──<` は「複数」側を表します。正規化を暗記して行うよりも、ERD で N:M を分解し属性を元の位置に戻すと、ほとんど 3NF に近づくと言われています。これは私が直接検証したわけではなく、手書きで描いて感じた印象に近いものです。

## 逆正規化

正規化するとテーブルが増え、読み込む際に JOIN が多くなります。Microsoft のドキュメントでも、3NF を最後まで守ると都市、郵便番号、担当者などの小さな表が次々と生まれ、パフォーマンスが低下する可能性があるとしています。頻繁に変更されるデータに対してのみ 3NF を適用する方法もそこで提案されています。

したがって、意図的に重複を許容することを「反正規化」と呼ぶ。例えば、以下のようなケースだ。

- 注文テーブルに総額を事前に保存しておき、一覧画面で合計を計算しない。
- 投稿テーブルにコメント数カラムを設ける。

代わりに、値がズレないように更新するコードを自ら担当しなければならない。読み込みが圧倒的に多く、JOIN がボトルネックとなった場合などに採用するものであり、まずは [インデックス](#/post/db-index) で解決するか確認するのが順序だ。読み込み負荷を減らすために値を別に置く方法は、[キャッシュ](#/post/db-cache-redis) に関する記事で続いている。

## よくある誤解

- 正規化は分割するほど良い：ドキュメントでも 3NF がほとんどのアプリケーションで必要な最高水準であるとされ、それより上（4NF・5NF）は実務ではよく考慮しないと書かれている。
- 正規化すると遅くなる：JOIN が増えることで遅くなるのは事実だが、それは測定して確認する必要がある。重複がもたらす不整合コストも同時に検討しなければならない。
- 反正規化は設計ミスだ：知っている上で行う反正規化は選択である。知らずに生じた重複が問題となる。
- NoSQL なら正規化は不要：ドキュメント型 DB は、意図的に束ねて保存するモデリングを採用することが多い。この話題は [NoSQL 記事](#/post/db-nosql) で扱っている。

なお、Microsoft のドキュメントでは 4NF を BCNF と呼んでいるが、Wikipedia では BCNF を 3NF より厳格な別形式として位置づけている。両者の説明が異なるため、ここでは BCNF を Wikipedia 側の説明で理解した。テーブル間の関係を SQL で扱う方法は [関係型 DB と SQL](#/post/db-rdb-sql) に、分割したテーブルを一括で修正する際に必要なものは [トランザクション](#/post/db-transaction) にある。
