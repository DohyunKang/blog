仮想メモリは、アドレス変換表（ページテーブル）の上に構築されたデバイスであり、その表がどれほど大きく、どれほど遅いかを追うと、TLB、多段テーブル、ページ置換、スラッシングが順次現れる。オペレーティングシステム全体の概要は [概要](#/post/cs-os) で見ており、ここではメモリ部分のみを詳しく解説する。

## 変換が行うこと

プロセスが発行するアドレスは仮想アドレスであり、これを物理アドレスに変えることは、すべてのメモリアクセスで発生する。ページングではアドレスを 2 つのパートに分割する。前半部分が仮想ページ番号 (VPN)、後半部分がページ内の位置（オフセット）である。VPN を用いてページテーブルを検索し、物理フレーム番号 (PFN) を得て、オフセットはそのまま付加する。

OSTEP が使用する小さな例（64 バイトのアドレス空間、ページサイズ 16 バイト）をそのまま実装して試みた。ページ 0, 1, 2, 3 がそれぞれフレーム 3, 7, 5, 2 に配置されている場合、以下のようになる。

| 仮想アドレス | VPN | オフセット | PFN | 物理アドレス |
|---|---|---|---|---|
| 0 | 0 | 0 | 3 | 48 |
| 21 | 1 | 5 | 7 | 117 |
| 50 | 3 | 2 | 2 | 34 |

```python
PAGE = 16
pt = {0: 3, 1: 7, 2: 5, 3: 2}
def tr(va):
    vpn, off = divmod(va, PAGE)
    return pt[vpn] * PAGE + off
print(tr(0), tr(21), tr(50))   # 48 117 34
```

ページテーブルはプロセスごとに 1 つずつ存在する。表の 1 つのセル (PTE) には、フレーム番号だけでなくいくつかのビットが含まれる。OSTEP の説明では、以下の項目がある。

- valid: この翻訳が有効か。使わない領域を invalid に設定しておけば、物理フレームを与えなくてもよく、そこにアクセスすると OS への trap が発生する。
- 保護 (read/write/execute): 許可されていない方法でのアクセスもまた trap を引き起こす。
- present: 現在 RAM 上に存在するか、ディスクにスワップアウトされたか。
- dirty: メモリ上に読み込まれた後、修正されたか。
- reference(accessed): 最近アクセスされたか。ページ置換で利用される。

## 表が大きすぎる

32 ビットのアドレス空間でページサイズが 4KB の場合、アドレスは 20 ビットの VPN と 12 ビットのオフセットに分割される。翻訳情報は $2^{20}$ 個、約 100 万個あり、PTE を 4 バイトとすると、プロセス 1 つのページテーブルは 4MB になる。OSTEP は、プロセスが 100 つある場合、翻訳情報のみで 400MB を必要だと指摘している。

```python
print(2**32 // 4096, (2**32 // 4096) * 4)   # 1048576 4194304
```

アドレス空間の大部分は空である。コードとヒープは片方の端に、スタックは反対側の端にあり、中間部分は invalid であっても、線形テーブルはそのセルをすべて保持している。ページサイズを大きくすると表は小さくなるが（4 倍に増やすと正確に 4 分の 1 に減る）、ページ内で使用されずに捨てられる空間、すなわち内部断片化が増大する。そのため、多くのシステムでは 4KB や 8KB のような小さなページを使用している。

この問題を解決する方法（多段テーブル、セグメントとの混合）は、以下の折りたたみ部分に記載した。

<details>
<summary>多段ページテーブル、およびセグメントとの混合方式</summary>

多段テーブルでは、ページテーブル自体をページサイズで区切り、完全に invalid な部分は割り当てしない。どの部分が存在するかはページディレクトリが保持しており、ディレクトリ項目 (PDE) は少なくとも valid ビットとフレーム番号を持つ。PDE が valid であることは、その部分内に有効な PTE が少なくとも 1 つあることを意味する。

利点は、表の空間が実際に使用されているアドレス空間に比例することであり、また表の部分がちょうど 1 ページに収まるため、OS が次の空いているページを使用すればよい点にある。代償もある。TLB ミスが発生すると、ディレクトリと PTE をそれぞれ読み取る必要があるため、メモリを 2 回読む。OSTEP はこれを時間と空間のトレードオフと呼んでいる。

これより先に登場した方式は、セグメントとページングの混合である。アドレスの上ビットでセグメント（コード、ヒープ、スタック）を選択し、各セグメントに対して base と bounds を持たせて、そのセグメント専用の線形テーブルを指す。bounds にはそのセグメントの最大有効ページ数が含まれており、その間の空白領域は表を占めない。しかし、ヒープが大きくなりながら断続的に使用されると無駄が残り、表の長さがバラバラになり、空き空間の検索が困難となる外部断片化が再び発生する。この理由から、多段方式へと発展したという。
</details>

## 遅い：TLB

変換を行うにはページテーブルを読み取る必要があるが、その表もメモリ上に存在する。1 つのアクセスでメモリを 2 回触れることになる。これを減らすために、ハードウェアに最近の変換結果を保持する小さなキャッシュがある。TLB（translation-lookaside buffer）である。

流れは単純だ。アドレスが来ると、まず TLB を VPN で見る。あれば（ヒット）、すぐに物理アドレスを作成する。なければ（ミス）、ページテーブルを読み込んで翻訳を取得し、TLB に格納してから再度試みる。

TLB 가 잘 동작하는 이유는 지역성입니다. 시간적 지역성은 방금 쓴 것을 또 쓴다는 것, 공간적 지역성은 x 근처를 쓰면 그 다음도 근처라는 것입니다. OSTEP 의 예시는 정수 배열 10 개를 차례로 읽는 경우입니다. 원소들이 한 페이지에 촘촘히 박혀 있어서 결과가 miss, hit, hit, miss, hit, hit, hit, miss, hit, hit 이고 히트율이 70% 입니다. 처음 읽는 배열인데도 히트가 나옵니다.

평균 접근 시간은 히트율에 따라 이렇게 움직입니다. 숫자는 설명용 가정입니다 (TLB 조회 1, 메모리 접근 100, 미스 때 테이블 읽기 한 번 더).

```python
mem, tlb = 100, 1
for hr in (0.99, 0.9, 0.5):
    print(hr, tlb + hr * mem + (1 - hr) * 2 * mem)
# 0.99 102.0 / 0.9 111.0 / 0.5 151.0
```

프로세스를 바꿀 때 TLB 가 문제가 됩니다. 앞 프로세스의 번역은 다음 프로세스에게는 의미가 없습니다. 한 방법은 컨텍스트 스위치마다 TLB 를 비우는 것입니다. 안전하지만 프로세스가 다시 돌 때마다 미스를 새로 겪습니다. 그래서 일부 하드웨어는 TLB 항목에 ASID(주소 공간 식별자) 를 붙여 프로세스끼리 TLB 를 같이 쓰게 합니다. ASID 는 PID 처럼 쓰이지만 비트 수가 더 적습니다 (OSTEP 예로 8 비트 대 32 비트). 스위치 자체가 어떻게 일어나는지는 [프로세스와 스레드](#/post/os-process-thread), TLB 가 속한 계층 구조는 [메모리 계층과 캐시](#/post/ca-memory-hierarchy)에서 이어 봅니다.

## 메모리가 모자라면: 교체 정책

present 비트가 0 인 페이지에 접근하면 페이지 폴트가 납니다. OS 가 디스크에서 그 페이지를 가져와야 하는데 빈 프레임이 없으면 하나를 내보내야 합니다. 누굴 내보내느냐가 교체 정책이고, 개요에서 FIFO 와 LRU 를 간단히 비교했으니 여기서는 기준점인 최적 정책과 실제 구현에서 쓰는 근사를 봅니다.

최적 정책은 앞으로 가장 늦게 쓰일 페이지를 내보내는 것입니다. Belady 가 보인 바로는 미스가 가장 적습니다. 미래를 알아야 하니 실제로 만들 수는 없고, 새 정책이 얼마나 좋은지 재는 자 (기준선) 로 쓴다.

OSTEP 이 쓰는 참조열 0,1,2,0,1,3,0,3,1,2,1 을 프레임 3 개로 돌렸습니다.

```python
def opt(refs, f):
    mem = []; h = 0
    for i, r in enumerate(refs):
        if r in mem: h += 1; continue
        if len(mem) == f:
            def nxt(p):
                try: return refs.index(p, i + 1)
                except ValueError: return 10**9
            mem.remove(max(mem, key=nxt))
        mem.append(r)
    return h

def fifo(refs, f):
    mem = []; h = 0
    for r in refs:
        if r in mem: h += 1; continue
        if len(mem) == f: mem.pop(0)
        mem.append(r)
    return h

def lru(refs, f):
    mem = []; h = 0
    for r in refs:
        if r in mem: h += 1; mem.remove(r)
        elif len(mem) == f: mem.pop(0)
        mem.append(r)
    return h

def clock(refs, f):
    fr = [None] * f; use = [0] * f; hand = 0; h = 0
    for r in refs:
        if r in fr: h += 1; use[fr.index(r)] = 1; continue
        while fr[hand] is not None and use[hand]:
            use[hand] = 0; hand = (hand + 1) % f
        fr[hand] = r; use[hand] = 1; hand = (hand + 1) % f
    return h

t = [0,1,2,0,1,3,0,3,1,2,1]
print([fn(t, 3) for fn in (opt, fifo, lru, clock)])   # [6, 4, 6, 4]
```

11 번 접근 중 히트가 최적 6 번 (54.5%), FIFO 4 번 (36.4%), LRU 6 번, 클록 4 번입니다. FIFO 의 36.4% 는 OSTEP 이 같은 예시에서 든 수치와 같습니다. 페이지 0 을 여러 번 썼는데도 FIFO 는 먼저 들어왔다는 이유만으로 내보냅니다.

LRU 는 가장 오래 안 쓴 페이지를 내보냅니다. 접근 기록을 매번 정렬해 두는 건 비싸서 실제 시스템은 근사를 사용합니다. 하드웨어가 페이지에 접근할 때마다 use 비트를 1 로 세우고, 0 으로 내리는 건 OS 몫입니다. 클록 알고리즘은 페이지들을 원형 리스트로 놓고 시계바늘을 돌립니다. 바늘이 가리킨 페이지의 use 가 1 이면 0 으로 내리고 다음으로 넘어가고, 0 이면 그 페이지를 내보냅니다. 전체를 매번 훑지 않아도 되는 게 장점입니다. 위 참조열에서는 클록이 FIFO 와 같은 4 번이었는데, 이 짧은 입력 하나로 우열을 말할 수는 없습니다.

한 가지 더 있습니다. 수정된 (dirty) 페이지는 내보내려면 디스크에 써야 하고 그게 비쌉니다. 안 바뀐 (clean) 페이지는 프레임을 그냥 재사용하면 됩니다. 그래서 일부 VM 시스템은 clean 쪽을 우선 내보냅니다. 이게 dirty 비트가 있는 이유입니다.

## 스래싱

루프를 도는 프로그램에서 정책이 얼마나 극단적으로 갈리는지 돌려 봤습니다. 페이지 5 개를 0,1,2,3,4 순서로 20 번 반복하는 100 번 접근입니다.

```python
loop = list(range(5)) * 20
for f in (3, 4, 5):
    print(f, lru(loop, f), fifo(loop, f), opt(loop, f))
# 3 0 0 48
# 4 0 0 72
# 5 95 95 95
```

프레임이 5 개면 히트가 95 번 (처음 5 번만 미스) 인데, 4 개로 한 칸만 줄여도 LRU 와 FIFO 는 히트가 0 입니다. 매번 바로 다음에 쓸 페이지를 방금 내보낸 셈입니다. 같은 입력에서 최적은 4 개일 때 72 번 히트합니다. 활발히 쓰는 페이지 집합 (워킹 셋) 이 메모리에 안 들어가면 성능이 서서히 나빠지는 게 아니라 벼랑에서 떨어지듯 나빠질 수 있다는 것을 보여 줍니다.

이렇게 메모리 요구가 물리 메모리를 넘어서 계속 페이징만 하는 상태가 스래싱입니다. OSTEP 이 소개하는 대응은 두 가지입니다. 옛 시스템은 일부 프로세스를 아예 돌리지 않아서 남은 프로세스들의 워킹 셋이 메모리에 들어가게 했습니다 (admission control). 요즘 일부 Linux 는 메모리가 넘칠 때 메모리를 많이 쓰는 프로세스를 골라 죽이는 out-of-memory killer 를 돌립니다. 뭐든 한꺼번에 어설프게 하느니 덜 하더라도 제대로 하는 편이 낫다는 쪽의 선택입니다.

## 흔한 오해

- ページサイズを大きくするほど良い：テーブルと TLB の負荷は減るが、内部フラグメンテーションが増大する。必要な領域のみを使用するように大きなページ（例えば 4MB）をサポートする CPU も存在するが、OSTEP はその主な目的はテーブル空間ではなく TLB の負荷軽減であると述べている。
- フレーム数を増やすと常に良いわけではない：概要で述べた Belady の現象のように、FIFO では成り立たない場合がある。
- LRU で十分である：上記のループ例では、LRU はフレームが 1 つ不足した瞬間にヒット率が 0 だった。これはアクセスパターンによって異なる。
- スワッピングは遅いので使わない方が良い：一度ページアウトされたページが再び必要であれば問題ないが、問題は往復するスワッピングである。
