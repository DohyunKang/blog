リクエストを受け取った瞬間にすべてを終わらせようとせず、やるべきことをキューに書き留めて先に応答し、その後にワーカーが裏側で処理するのが非同期処理の基本のパターンです。楽になる代わりに、「再試行」と「重複」という宿題がついて回ります。

## 同期と非同期

会員登録を例にとると、行うべきことは以下の通りです。DB に保存し、歓迎メールを送信し、統計を更新します。これらをすべてリクエスト内で順番に行うのが同期処理です。メールサーバーが 3 秒遅れるとユーザーも 3 秒待たされ、メールサーバーが落ちると会員登録そのものが失敗します。

非同期とは、「DB 保存だけして応答し、メールは後で」と分割するものです。後で行うことはどこかに書き留けておく必要がありますが、その書き留ける場所がキューです。リクエストの流れ自体は [リクエストが処理される流れ](#/post/be-request-flow) で整理しました。

| | 同期 | 非同期 |
|---|---|---|
| 応答のタイミング | 作業がすべて終わった後 | 作業を受付けた後 |
| 遅い外部サービス | ユーザーも一緒に待機 | ワーカーが別で待機 |
| 失敗した場合 | ユーザーは即座にエラーを確認 | ユーザーは気づかず、システムが再試行が必要 |
| 結果の確認 | 応答に含まれている | ステータス照会や通知などで別途知らせる必要がある |

最後の行は結構面倒です。受付だけで終わらせてしまうと、「処理済み？」をユーザーに伝えるための別の手段が必要です。

## メッセージキューとは何か

メッセージキューは、送る側（プロデューサー）と受ける側（コンシューマー、通称ワーカー）を中間でつなぐ紐のようなものです。プロデューサーがキューにメッセージを入れたら終わりであり、ワーカーは自分のペースで取り出して処理します。両者が互いに直接知る必要がないため、[結合度](#/post/be-coupling-cohesion) を低くするのにも使われます。

```
API 서버 --(메시지 넣기)--> [ 큐 ] --(꺼내기)--> 워커 1
                                      └-------> 워커 2
```

- トラフィックが一気に集中してもキューがバッファリングします。ワーカーが追いつけなければキューが長くなるだけで、サーバーは即座に落ちません。
- ワーカーを増やせば処理量が増えます。API サーバーとは別に増やすことができます。
- ワーカーが一時的に落ちてもメッセージはキューに残っています。

代表的な実装には RabbitMQ、Amazon SQS、Kafka などのものがあります。この記事では前述の 2 つのドキュメントで確認した動作を基準として記述しています。Kafka は構造が異なるため（ログベース）ここでは扱いません。

## ワーカーがメッセージを取得する方法

ここが核心です。ワーカーがメッセージを受け取った瞬間にキューから削除してしまうと、処理中にワーカーが落ちた際にメッセージが消えてしまいます。そのため、キューは「受け取り」か「完了」かを区別します。

RabbitMQ は手動 ack モードでは、ワーカーが処理を完了させて `ack` を送らなければメッセージを破棄しません。`nack` や `reject` を送ると `requeue` オプションに応じて再度キューに入れるか、デッドレターエクスチェンジが設定されていればそこに送り、なければ破棄します。ack なしで接続が切れた場合そのメッセージは自動的に再度キューに入り、再配信されたメッセージには `redeliver` のマークが付きます。自動 ack モードでは送信の瞬間に伝達済みとみなすため、処理前に接続が切れるとメッセージを失います。ドキュメントもこのモードを多くの用途で安全ではないと記述しています。

SQS は方式が少し異なります。メッセージを受け取るとキューから削除されず、一定時間他のワーカーには見えないだけです。この時間を可視性タイムアウトと呼び、デフォルトは 30 秒です。その間にワーカーが `DeleteMessage` で削除できなければメッセージが再び見え、同じワーカーでも別のワーカーでも再度受け取ります。処理に時間がかかる場合は `ChangeMessageVisibility` で時間を延長できますが、最大 12 時間の制限があります。

名前こそ違いますが構造は同じです。完了であることを確認するまでキューがメッセージを保持し、確認がないと再度返します。

## そのため重複が発生する

上記の構造では避けられないことが一つあります。ワーカーがメールを送信し、ack を送る直前に落ちたと仮定しましょう。キューの立場では処理済みかどうかの判断材料がないため、再度返します。別のワーカーが同じメールを再度送信します。

SQS のドキュメントは可視性タイムアウトがあっても at-least-once 配信モデルであるため、同じメッセージが 2 回以上来る可能性があることを明確に記述しています。RabbitMQ のドキュメントは「at-least-once」という言葉を使いませんが、再配信が発生するため、消費者は冪等性を持たなければならない旨を記述します。つまり、「正確に一度」をキューに期待するのではなく、「最低でも一度来るから二度来ても問題ないようにしよう」とするのが一般的です。

## 冪等性

冪等性とは、同じリクエストを複数回実行しても一回実行した場合と同じ結果になるという性質です。`balance = 100` は何度行っても 100 ですが、`balance += 100` は毎回値が変わります。後者のような処理をワーカーで行う場合は、一度処理済みであることを記録しておく必要があります。

Stripe API の仕組みはわかりやすかった。クライアントが `Idempotency-Key` を指定して送信すると、サーバーは最初のリクエストのステータスコードと本体を保存し、同じキーでの再試行には保存された応答をそのまま返す。キーの最大長は 255 文字で、UUID v4 などのランダムな文字列の使用が推奨される。v1 の基準では 24 時間経過したキーは削除されることがあり、同じキーに対してパラメータが異なるとエラーが発生する。これは外部 API の話だが、キューワーカー内でもメッセージ ID をキーとして同様の仕組みを採用できる。

[API と REST](#/post/be-api-rest) では GET は元々冪等性を持ち、POST は持たないとまとめられていたが、POST が再試行可能な環境ではこのようなキーが必要になる。

## 再試行とデッドレターキュー

処理中にエラーが発生したら再度試す。ただし、すぐに連続して再試行すると、すでに負荷の高い外部サービスをさらに苦しめることになるため、間隔を徐々に長くする指数関数的なバックオフを採用することが多い。一時的な障害は再試行で解決できるが、メッセージ自体が破損している場合は何度やっても解決しない。

そのため、回数制限を設け、それを超過すると別のキューに移動させる。それがデッドレターキュー（DLQ）である。SQS では redrive policy の `maxReceiveCount` が「消費者がこのメッセージを何回受け取ったら DLQ に移動させるか」を決定する。値を低く設定しすぎると（例：1）、一度の失敗ですぐに DLQ へ移動してしまうため、再試行の余地を残すために高く設定すべきだとドキュメントには書かれている。DLQ に蓄積されたメッセージはログを確認して原因を分析するか、修正後に redrive を使って元のキューに戻す。DLQ の保持期間は元のキューよりも長く設定するのが良いともされている。FIFO キューで DLQ を使うと順序が乱れる可能性がある点にも注意が必要だ。

DLQ があるだけでは不十分であり、蓄積された際に通知を受け取る仕組みも用意しておく必要がある。[エラー処理とロギング](#/post/be-error-logging) に続く部分である。

## 実際に試した例

概念をコードで簡略化した。キューは deque、ワーカーはループ一つ、メール送信は 30% の確率で失敗するように設定した。同じ ID のメッセージ（m3）を意図的に二回投入した。

<details>
<summary>コードと結果 (Python で実行確認)</summary>

```python
import random
from collections import deque

random.seed(1)
queue = deque()
dlq = []
done = set()       # 처리 끝낸 메시지 id (멱등성 키)
sent_mail = []     # 부수효과

def send_mail(msg):
    # 30% 확률로 일시 실패
    if random.random() < 0.3:
        raise RuntimeError("smtp timeout")
    sent_mail.append(msg["to"])

def handle(msg):
    if msg["id"] in done:        # 이미 처리한 id면 건너뜀
        return
    send_mail(msg)
    done.add(msg["id"])

MAX = 3
for i in range(10):
    queue.append({"id": f"m{i}", "to": f"user{i}", "tries": 0})
queue.append({"id": "m3", "to": "user3", "tries": 0})  # 중복 발행

while queue:
    msg = queue.popleft()
    try:
        handle(msg)
    except Exception:
        msg["tries"] += 1
        if msg["tries"] >= MAX:
            dlq.append(msg["id"])
        else:
            queue.append(msg)

print("sent", len(sent_mail), "unique", len(set(sent_mail)))
print("dlq", dlq)
```

実行結果は以下の通りだった。

```
sent 10 unique 10
dlq []
```

メッセージ 11 個（そのうち一个是重複）を投入したが、メールは 10 通、受信者は 10 人である。途中で失敗したメッセージは後ろに移動して再試行され、重複した m3 は `done` に ID が記録されているためスキップされた。シード値の影響で今回は連続して 3 回失敗するメッセージがなかったため、DLQ は空だった。失敗確率を上げれば DLQ に入るものも確認できるはずだが、それは試していない。

このコードは概念を示すためのものだ。`done` がメモリ上にしかないためワーカーが死んだら消えてしまい、「メール送信」と「done に記録」が一つのトランザクションではないため、その間に死んでしまうと依然として重複が発生する可能性がある。実際には `done` を DB に置き、ユニーク制約で防ぐような構成になる。

</details>

## よくある誤解

- キューを使えばメッセージは正確に一度だけ処理される：前述したように少なくとも一度の処理が基本である。
- キューがあれば順序が保証される：SQS の標準キューのように順序を保証しないものもあり、FIFO キューもメッセージグループ ID 単位で順序を保つ。必要に応じてキューの種類を確認する必要がある。
- 非同期に変更すれば必ず高速化する：ユーザーが待つ時間は短くなるが、全体の処理量が向上するわけではない。ワーカーに追いつけないとキューだけが長くなる。
- キューは常に使うべきではない：応答に結果を即座に必要とする作業や単純なサービスには同期の方が良い。再試行、重複処理、状態確認まで自分で担当しなければならないため複雑度が増す。
