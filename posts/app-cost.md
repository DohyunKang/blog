AI 서비스는 사용자가 쓸 때마다 토큰 요금이 나가는 구조라서, 호출 한 번의 값을 먼저 계산하고 거기에 횟수와 사용자 수를 곱하면 원가가 나온다.

## 왜 원가를 따로 계산하나

일반 웹 서비스는 사용자가 늘어도 서버 한 대가 더 버티는 경우가 많다. 사용자 한 명이 더 와도 추가로 드는 돈이 거의 없다. LLM 앱은 다르다. 질문 하나마다 API 요금이 붙는다. 그래서 잘 팔릴수록 비용도 같이 늘고, 받는 가격보다 사용자 1명이 쓰는 원가가 크면 팔수록 손해다.

계산 대상은 한 가지다. 사용자 1명이 한 달에 쓰는 AI 요금.

```
월 원가 = 월 호출 수 × (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가)
```

토큰이 뭔지는 [자세히 → 토큰 아끼기](#/post/claude-tokens)에 따로 있고, 여기서는 단가에 곱하는 숫자로만 쓴다.

## 단가 읽는 법

Anthropic 가격표는 모델마다 100만 토큰(MTok)당 입력·출력 단가를 적는다. 확인한 값 중 일부는 이렇다(2026-11-02 문서 기준).

| 모델 | 입력 | 출력 | 캐시 읽기 |
|---|---|---|---|
| Fable 5.1 | $10 | $50 | $0.25 |
| Opus 5.5 | $4 | $20 | $0.20 |
| Sonnet 5.5 | $2 | $10 | $0.10 |
| Haiku 5.5 (프롬프트 10만 토큰 이하) | $0.10 | $0.50 | $0.01 |

눈에 띄는 점이 몇 개 있다.

- 출력이 입력보다 비싸다. 표의 모델은 전부 출력 단가가 입력의 5배다.
- 큰 모델과 작은 모델의 차이가 크다. Sonnet 5.5와 Haiku 5.5의 입력 단가는 20배 차이다.
- Haiku 5.5는 프롬프트가 10만 토큰을 넘으면 입력 $0.50, 출력 $2.50으로 오른다. 긴 문서를 넣을 땐 이 구간을 따로 봐야 한다.
- Claude 4.7 이후 모델은 새 토크나이저를 쓰고, 같은 글에서 토큰이 약 30% 더 나온다고 문서에 적혀 있다. 단가가 같아도 글자 기준 원가는 달라질 수 있다.

단가는 자주 바뀐다. 계산할 때마다 공식 가격표를 다시 열어야 한다.

## 사용자 1명 한 달 원가 계산

가정을 하나 잡았다. 질문-답변형 앱이고, 사용자가 하루 10번, 한 달 30일 쓴다. 호출 한 번은 입력 3,000토큰(시스템 프롬프트 2,000 + 질문과 자료 1,000), 출력 500토큰이다. 모델은 Sonnet 5.5. 이 숫자들은 계산용 가정이고 실제 서비스 값이 아니다.

- 호출 1번: 3,000 × $2/1M + 500 × $10/1M = $0.006 + $0.005 = $0.011
- 한 달 300번: $3.30

사용자 1명이 $3.30이면 월 구독료가 $5일 때 마진이 얼마 안 남는다. 결제 수수료, 서버, 인건비는 아직 넣지도 않았다. 반대로 사용자가 100명이면 $330이라 별 느낌이 없다. 그런데 5만 명이면 $165,000이다. 규모가 커질 때 원가가 어떻게 크는지는 이렇게 곱해서 봐야 보인다.

| 사용자 수 | 월 AI 요금 (Sonnet 5.5, 위 가정) |
|---|---|
| 1명 | $3.30 |
| 1,000명 | $3,300 |
| 5만 명 | $165,000 |

사용량이 고르지도 않다. 헤비 유저 몇 명이 평균을 끌어올린다. 평균만 보지 말고 상위 사용자가 얼마나 쓰는지도 같이 봐야 한다.

## 줄이는 방법

가격을 내리기 전에 원가부터 줄이는 순서가 맞다. 줄이는 수단은 대략 네 가지다.

**1. 프롬프트 캐싱.** 매번 같은 시스템 프롬프트를 보낸다면 그 부분을 캐시에 둔다. 문서 기준 캐시 읽기는 기본 입력 단가의 0.1배(Opus 5.5·Sonnet 5.5는 0.05배)다. 5분 캐시를 쓰는 쓰기는 1.25배, 1시간 캐시는 2배라서, 한 번 쓰고 끝나는 프롬프트에는 오히려 손해다. 같은 접두부가 정확히 일치해야 하고, 모델별 최소 길이(Sonnet 5.5는 512토큰)가 있다. 자세한 건 [자세히 → 프롬프트 캐싱](#/post/ai-prompt-caching).

위 가정에서 2,000토큰을 캐시 읽기로 바꾸면 호출 1번이 $0.0072로 줄고 한 달 $2.16이다. 쓰기 비용(5분 만료로 20번 다시 쓴다고 가정)을 더해도 약 $2.26이다. 34% 정도 줄었다.

**2. 작은 모델로 보내기.** 분류, 짧은 추출, 단순 질문은 작은 모델로 충분한 경우가 많다. 같은 호출을 Haiku 5.5로 보내면 호출 1번이 $0.00055, 한 달 $0.165다. 20분의 1이다. 그래서 요청마다 어려운 정도를 가려서 80%는 작은 모델, 20%만 Sonnet(캐시 적용)으로 보내면 한 달 약 $0.56이 된다. 처음 $3.30의 6분의 1이다. 다만 작은 모델이 정말 같은 품질인지는 따로 재야 한다. 재는 법은 [자세히 → LLM 앱 평가](#/post/app-eval). 모델 고르는 기준은 [자세히 → AI 모델 지도](#/post/ai-models).

**3. 배치.** 실시간이 필요 없는 일(야간 요약, 대량 분류)은 Batch API로 보낸다. 문서에 입력·출력 모두 50% 할인이라고 나온다. 캐시 배율과도 겹쳐서 적용된다고 한다. 대신 결과가 비동기로 온다.

**4. 호출 자체를 줄이기.** 같은 질문 결과를 저장해서 재사용하고, 입력에 넣는 문서를 필요한 부분만 자르고, 출력 길이를 제한한다. 출력이 입력보다 5배 비싸니 `max_tokens`와 "짧게 답해" 같은 지시가 직접 돈이 된다.

## 에이전트는 계산이 다르다

[자세히 → 에이전트 루프](#/post/ai-agent-loop)처럼 모델이 도구를 부르며 여러 번 도는 앱은 호출이 한 번이 아니다. 매 단계마다 지금까지의 대화를 다시 보내서 입력이 쌓인다([자세히 → 컨텍스트 윈도우](#/post/ai-context-window)).

같은 가정에서 한 작업이 5단계이고 단계마다 기록이 800토큰씩 늘면, 입력 합계가 23,000토큰, 출력이 2,500토큰이다. 캐시 없이 Sonnet 5.5로 $0.071이다. 단순 질문 한 번($0.011)의 6배가 넘는다. 단계 수가 늘면 입력은 단계 수의 제곱에 가깝게 는다. 이럴 땐 캐싱이 선택이 아니라 사실상 필수다. 에이전트 설계 쪽 이야기는 [자세히 → 에이전트 설계](#/post/app-agent-design).

## 흔한 오해

- 단가가 싸졌으니 걱정 없다: 단가가 내려도 사용량이 더 빨리 늘면 총액은 올라간다.
- 캐시를 켜면 무조건 싸진다: 쓰기는 더 비싸고, 접두부가 매번 바뀌거나 5분 안에 재사용이 없으면 이득이 없다.
- 평균 사용량으로 계산하면 된다: 상위 사용자가 평균을 크게 올린다.
- 입력만 보면 된다: 출력이 5배 비싸고, 생각(thinking) 토큰도 출력으로 과금된다.
- 요금만 원가다: 이 글은 API 요금만 다뤘다. 직접 모델을 돌리는 GPU 서버는 계산법이 다르다([자세히 → AI 서빙 인프라](#/post/infra-ai-serving)).

<summary>자세한 풀이: 위 계산 한 줄씩</summary>

Sonnet 5.5 입력 $2/MTok, 출력 $10/MTok, 캐시 읽기 $0.10/MTok, 5분 캐시 쓰기 $2.50/MTok.

- 기본: 3,000×2/1e6 = 0.006, 500×10/1e6 = 0.005, 합 0.011. ×300 = 3.30
- 캐시 읽기: 2,000×0.10/1e6 = 0.0002, 나머지 입력 1,000×2/1e6 = 0.002, 출력 0.005, 합 0.0072. ×300 = 2.16
- 캐시 쓰기: 한 달 20번 × 2,000토큰 × 2.50/1e6 = 0.10. 합계 2.26
- Haiku 5.5: 3,000×0.10/1e6 + 500×0.50/1e6 = 0.00055. ×300 = 0.165
- 라우팅: 0.8×0.00055 + 0.2×0.0072 = 0.00188. ×300 = 0.564
- 에이전트: 입력 = Σ(2,000+1,000+800×k), k=0..4 = 23,000. 23,000×2/1e6 = 0.046, 출력 2,500×10/1e6 = 0.025, 합 0.071

이 계산은 python으로 한 번 더 돌려 값이 맞는 것을 확인했다.

<summary>자세한 풀이: 응답에서 실제 사용량 읽기</summary>

가정 대신 실제 값을 쓰려면 응답의 `usage` 필드를 쌓으면 된다. 캐시 문서 기준으로 `input_tokens`는 마지막 캐시 지점 뒤의 입력, `cache_read_input_tokens`는 캐시에서 읽은 것, `cache_creation_input_tokens`는 캐시에 쓴 것이다. 전체 입력은 세 개의 합이다. 둘 다 0이면 캐시가 안 된 것이고, 가장 흔한 원인은 최소 길이 미달이라고 한다.

호출마다 사용자 ID와 이 세 값, `output_tokens`를 로그에 남겨 두면 사용자별 월 원가를 바로 합산할 수 있다.
