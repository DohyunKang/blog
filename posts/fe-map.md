프론트엔드 공부를 하면 렌더링, 상태, 컴포넌트, 접근성, 성능 같은 말이 한꺼번에 나온다. 서로 다른 얘기 같지만 결국 "브라우저가 화면을 어떻게 만들고, 우리는 그걸 어떻게 짜고, 쓰는 사람에게 어떻게 보이느냐"로 이어진다. 그래서 일곱 개 글을 그 순서로 묶고, 한두 줄씩만 먼저 적었다. 더 알고 싶은 건 링크로 넘어가면 된다.

## 한눈에 보는 관계

```
브라우저가 그린다  ←  HTML을 누가·언제 만드나 (CSR·SSR·SSG)
        ↑
만든다: 컴포넌트로 쪼개고, 상태를 어디에 둘지 정한다
        ↑
쓰는 사람 쪽: 쓰기 쉬운가(사용성) · 누구나 쓸 수 있나(접근성) · 빠른가(성능)
```

## 1. 화면이 어떻게 나오나

**브라우저가 화면을 그리는 과정**: HTML과 CSS를 받아 DOM, CSSOM, 렌더 트리, 레이아웃, 페인트 순서로 화면을 만든다. 어느 단계가 다시 도느냐에 따라 화면 변경의 비용이 갈린다.
[자세히 → 브라우저가 화면을 그리는 과정](#/post/fe-browser-render)

**CSR·SSR·SSG**: 화면의 HTML을 누가, 언제 만드느냐만 다른 세 방식. 어느 쪽이 낫다기보다 페이지마다 데이터가 얼마나 자주 바뀌는지로 고른다.
[자세히 → CSR·SSR·SSG](#/post/fe-rendering-modes)

## 2. 어떻게 짜나

**상태 관리**: 화면이 기억해야 하는 값을 어디에 두고 누가 바꾸게 할지 정하는 일. 라이브러리를 고르기 전에 값의 종류부터 나누는 쪽이 더 중요하다.
[자세히 → 상태 관리](#/post/fe-state)

**컴포넌트 설계**: 화면을 데이터가 흐르는 모양대로 쪼갠 조각. 얼마나 잘게 쪼개느냐보다 어디서 멈추고 상태를 누가 갖느냐가 설계의 대부분이다.
[자세히 → 컴포넌트 설계](#/post/fe-component)

## 3. 쓰는 사람에게 어떤가

**사용성 원칙(UX)**: 화면이 얼마나 쉽게 쓰이느냐. 닐슨의 10가지 휴리스틱이 이걸 점검하는 가장 흔한 목록이다.
[자세히 → 사용성 원칙(UX)](#/post/fe-usability)

**웹 접근성**: 마우스와 눈으로 보는 사람만 가정하지 않고 만드는 일. 대부분은 HTML을 제 용도대로 쓰면 해결되고, ARIA는 그래도 모자랄 때 쓰는 보충이다.
[자세히 → 웹 접근성](#/post/fe-accessibility)

**프론트 성능**: "빠르다"는 느낌을 로딩, 반응, 안정성 세 숫자로 나눠 잰 것이 Core Web Vitals. 숫자를 먼저 알아야 어디를 고칠지 정할 수 있다.
[자세히 → 프론트 성능](#/post/fe-performance)

## 읽는 순서

처음이라면 그리는 과정 → CSR·SSR·SSG → 상태 → 컴포넌트 순으로 읽으면 흐름이 이어진다. 사용성·접근성·성능은 어느 시점에 읽어도 따로 읽힌다. 화면이 느린 이유가 궁금하면 그리는 과정과 성능 글을 붙여 보면 된다.
