エージェントは、モデルがツールを使用し、結果を確認し、次に何をすべきかを決めるというサイクルを完了するまで繰り返される構造です。名前は大げさに見えますが、骨組みは while 文です。

## エージェントとは何か

Anthropic の "Building effective agents" という記事では、この 2 つを以下のように区別しています。ワークフローは LLM とツールを「事前に決められたコードの経路」でつなげたシステムであり、エージェントは LLM が「自ら作業プロセスとツールの使用を指揮する」システムです。同じ記事の中で、実際にエージェントを実装すると大抵は「環境からのフィードバックを受けながらツールを使う LLM がループを回すもの」と説明されています。

簡単に言えばこうなります。次のステップがコードに固定されている場合はワークフローで、次のステップをモデルが選ぶ場合はエージェントです。両者の間にはナイフで切ったような明確な線があるというよりは、モデルにどの程度任せるかという度合いの違いだと読み取れます。ツールとは何かについては [詳しく → ツール呼び出し](#/post/ai-tool-use) に別途記載しています。

| | ワークフロー | エージェント |
|---|---|---|
| 次のステップを決定する側 | コード | モデル |
| ステップ数 | 事前にわかる | 回して初めてわかる |
| 予測可能性 | 高い | 低い |
| コスト・遅延 | 少なく安定している | 増え変動が大きい |

## ループはどのように回るか

Anthropic のドキュメント (How tool use works) が説明する基本的な仕組みは以下の通りです。ツールを自分のコードで実行する場合、自分のアプリ側がループを回す必要があります。モデルが直接コードを実行できないためです。

1. ツールリストとユーザーメッセージを含めてリクエストを送信します。
2. モデルが `stop_reason: "tool_use"` とともにツール呼び出しのリクエスト (`tool_use` ブロック) を返します。
3. 自分のコードがそのツールを実行し、結果を `tool_result` として作成します。
4. これまでの会話、モデルの応答、結果を組み合わせて再度リクエストを送信します。
5. `stop_reason` が `"tool_use"` の間、2 から繰り返し続けます。

`end_turn`, `max_tokens`, `stop_sequence`, `refusal` のいずれかが出力されるとループから抜け出します。モデルが最終的な答えを出したか、あるいは別の理由で停止したことを意味します。ドキュメントの表現では、モデルは「構造化されたリクエストを出力するだけ」であり、実行は自分のコード（または Anthropic サーバー）が行うとされています。

これを観察 (Observation)、思考 (Thought)、行動 (Action) と呼ぶこともあります。ツール結果が観察で、それを見て次のステップを決めるのが思考、ツールを呼び出すのが行動です。この方式の名前は ReAct (Yao ら、2022) です。論文の要約によると、推論 (reasoning) と行動 (acting) を交互に行わせるプロンプト手法であり、HotpotQA や FEVER で chain-of-thought だけを使う場合よりも、幻覚や誤りの伝播が減少したと報告されています。さらに一つ、ALFWorld や WebShop では、模倣学習や強化学習手法に比べて成功率がそれぞれ絶対値で 34%p、10%p 高いとされています。ただしこれは 2022 年の論文の実験条件であり、現在のモデルにはそのまま当てはまる数値ではありません。

## 実際に回してみた最小ループ

モデル呼び出しを規則関数で置き換えて構造のみを確認しました。実際のモデルではないため判断能力を見ることはできず、ループの形状と終了のみ観察します。

```python
def fake_model(messages):
    last = messages[-1]
    if last["role"] == "user":
        return {"stop_reason": "tool_use", "tool": "add", "args": {"a": 2, "b": 3}}
    if last["role"] == "tool":
        return {"stop_reason": "end_turn", "text": f"답은 {last['content']}"}

TOOLS = {"add": lambda a, b: a + b}

def run(task, max_steps=5):
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        r = fake_model(messages)
        if r["stop_reason"] != "tool_use":
            return r["text"], step + 1
        try:
            out = TOOLS[r["tool"]](**r["args"])
        except Exception as e:
            out = f"error: {e}"
        messages.append({"role": "assistant", "content": r})
        messages.append({"role": "tool", "content": out})
    return "중단: 최대 단계 도달", max_steps
```

実行すると `run("2+3 は？")` は 2 段階目で「答えは 5」で終わりました。モデルがツールを呼び続けるように変更した場合 (`max_steps=3`) は 3 段階目で「最大ステップ到達」で止まりました。この上限がない場合、同じコードでも終わらないことがあります。

## いつ終わるか

終了には 2 つのパターンがあります。

- モデルが「終わった」と判断してツール呼び出しなしに答えを出す (`end_turn`)。
- 外部から中断する。最大反復回数、トークン・時間予算、人間の確認などが該当します。

Anthropic の記事も制御を維持する方法として、最大反復回数などの終了条件を挙げています。エージェントが詰まったり重要なポイントでは人間に確認を受けながら進めることもあるようです。前方だけを信じているとモデルが「終わった」と勘違いするケースを防げないため、外部から中断する仕組みが必要だというのが私の理解のポイントです。

サーバーがツールを実行する場合 (web_search などのようなもの) はサーバー内部でループが回り、反復の制限に達すると `pause_turn` に戻ります。この時点では仕事が終了しているわけではないため、その会話をそのまま再送信して続きを続けるようドキュメントに記載されています。

## 計画と文脈

ループが長くなると 2 つの問題が生じます。1 つ目は計画です。一度に決めて追いかける方式と、各ステップごとに確認して再度決める方式もあります。上記の記事ではエージェントが「計画を立てて自律的に動作する」とあり、各ステップで環境から「ground truth」（ツール結果、コード実行結果）を得て進行状況を判断しなければならないとされています。私はこれを「頭の中の計画よりも実際に回してみた結果を信じるべきだ」と理解しました。

もう一つの要素は「コンテキスト」です。各ステップでツールの結果が蓄積されるため、ウィンドウが次第に埋まっていきます。これは [詳細 → コンテキスト](#/post/ai-context) と [詳細 → 圧縮](#/post/ai-compaction) で扱った問題と同じものです。長いタスクを任せる場合、ループの外側でハネスがこの部分を管理する必要があります。ハネスについては [詳細 → ハネス](#/post/ai-harness) にまとめられています。

## 失敗モード

文書や記事で確認した事実と、私が推論した内容を分けて記述します。

確認した事実
- エラーが蓄積する: Anthropic の記事は「自律性とは、より高いコストとエラーの累積の可能性を意味する」と述べています。各ステップで失敗確率がわずかにあれば、ステップ数が増えるほど全体の成功率は低下するという話です。
- コストと遅延: エージェントシステムは、より良い成果を得る代わりに、遅延やコストを負うことが多いようです。
- 推奨事項: サンドボックスで十分にテストし、適切なガードレールを設けるよう勧められています。これは [詳細 → ガードレール](#/post/app-guardrails) とも繋がります。

私が推論した内容
- 同じ引数で同じツールを繰り返し呼び出す無駄なループ。
- ツールのエラーメッセージを見ていても同じミスを繰り返すこと。
- 途中で目標を忘れたり、目標が少しずつ変化したりすること。

上記の 3 つは、実際に再現してみたわけではなく、構造上そうなると考えられたものです。もし正しいなら、解決策は主に反復上限の設定、同一呼び出しの検出、モデルがエラーを容易に読み取れるようにする程度のはずですが、これも確認済みの処方ではありません。

## ワークフローで十分な場合

同じ記事が最も強く伝えているのは、「最も単純な解決策から始め、必要に応じて複雑さを追加せよ」という点です。検索や例示を付加した 1 回の LLM 呼び出しだけで十分なケースが多いようです。基準は概ね以下のように読み取れます。

| 状況 | 正しい方 |
|---|---|
| ステップが決まっており予測が重要 | ワークフロー |
| 何ステップかかるか分からない開かれた問題 | エージェント |
| モデルの判断を信頼できる環境 | エージェント |

ワークフローの代表的なパターンとして記事は 5 つ挙げています。プロンプトチェーン、ルーティング、並列化、オーケストレーター・ワーカー、評価者・最適化です。複数のエージェントに分ける話は [詳細 → サブエージェント](#/post/ai-subagent) に続きます。実際にエージェントアプリを設計する際に考慮すべき点は [詳細 → エージェント設計](#/post/app-agent-design) にあります。

## よくある誤解

- エージェントは別々の特別なモデルである: いいえ。同じ LLM をループ内でツールと併せて使う方式です。ただし、ツールをよく使うように学習されたモデルの方がうまく回ることはあります (Anthropic のドキュメントは trained-in ツールスキーマに触れています)。
- エージェントは常にワークフローより良い: コスト・遅延・エラーの累積があるため、狭く決まった仕事にはワークフローの方が適しています。
- ループを回せばモデルが勝手に終わらせる: 終了条件は外側でも設けておくのが安全です。
- モデルがツールを実行する: モデルはリクエストのみを送信します。実行は私のコードやサーバーが行います。

<details>
<summary>詳細な解説: stop_reason 別の処理</summary>

文書で読んだ範囲のみ記述します。

- `tool_use`: ツールを実行し、結果を付けて続けます。ツール呼び出しが複数ある場合があります（並列呼び出し）。
- `end_turn`: 最終的な答え。ループを終了します。
- `max_tokens`: 答えが切り捨てられました。最終的な答えではないため、私のアプリで処理する必要があります。
- `stop_sequence`, `refusal`: 他の理由で止まったもの。同様にアプリで処理します。
- `pause_turn`: サーバー側のループが反復上限に達しました。応答を含めて再度送信して続行します。

</details>
