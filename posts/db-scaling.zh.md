# 复制与分片

随着服务规模扩大，单台数据库服务器会首先不堪重负。即使修复查询、[添加索引](#/post/db-index)以及[使用缓存](#/post/db-cache-redis)，仍无法满足需求时，最后的解决方案就是增加数据库实例数量。主要分为两大类：将相同数据复制到多台服务器的复制（Replication），以及将数据切分并分布到多台服务器上的分片（Sharding）。

一句话概括如下：

| | 复制 (replication) | 分片 (sharding) |
|---|---|---|
| 每台服务器持有的内容 | 完整数据的副本 | 部分数据 |
| 主要提升的方面 | 读吞吐量、可用性 | 写吞吐量、存储容量 |
| 伴随的问题 | 复制延迟、旧数据 | 分片间的 JOIN/事务、重平衡 |

## 读写复制

结构很简单：有一个接收写操作的服务器（主库 primary，MySQL 文档中称为 source），以及多个接收变更并应用这些变更的服务器（从库 replica，standby）。写操作指向 primary，读操作分散到各个 replica。由于大多数服务的读操作远多于写操作，仅靠这一点就能支撑相当长一段时间。负责分发请求的部分由 [负载均衡器](#/post/infra-load-balancer)或应用程序的连接配置承担。

MySQL 官方文档列举的复制用途除了读扩展（scale-out）外还有：在 replica 上执行备份不会影响 primary；可以在 replica 上运行繁重的分析查询；也可以将副本放置在地理位置较远的地方。如果 primary 宕机，可以将一个 replica 提升为 primary 以继续服务（failover），这也源于相同的架构。

### 同步还是异步

如何将变更传递给 replica，决定了性能与安全性的权衡。

| 方式 | 提交时间点 | 优点 | 缺点 |
|---|---|---|---|
| 异步 | primary 提交后立即结束，传递稍后进行 | 速度快 | failover 时最近的提交可能丢失；replica 可能返回旧值 |
| 半同步 (MySQL) | 至少等待一个 replica 确认接收并记录后才响应 | 保证数据已接收 | 响应变慢 |
| 同步 | 所有服务器必须完成提交才算结束 | 不丢失数据，无论何处读取数据均一致 | 速度慢。PostgreSQL 文档指出，如果网络缓慢，性能可能降至一半以下 |

MySQL 默认使用异步复制，标准复制并不提供完全的同步方式（此类情况建议使用 NDB Cluster）。大多数系统使用异步复制并承担其代价。

### 复制延迟

异步复制的代价就是复制延迟（replication lag）。从 primary 写入数据到 replica 收到该数据，时间从几毫秒到负载高时的数秒不等。在此期间读取 replica 将无法看到刚写入的数据。

最常见的事故流程如下：用户修改个人资料（在 primary 上写），随即打开个人资料页面（从 replica 读），看到的是修改前的旧值。用户误以为保存失败，于是再次点击保存。

常见的应对策略有几种：

- 在写入后的短时间内，将该用户的读请求路由到 primary（read-your-writes）。
- 仅对必须立即显示最新数据的页面从 primary 读取。
- 监控 replica 的延迟时间，若延迟过大则将其从读目标中剔除。

还有一点值得记住：复制并不能增加写吞吐量。由于所有 replica 都必须完整应用 primary 的写操作，因此如果写操作成为瓶颈，无论增加多少 replica 都无法改善。这时才会轮到分片的话题。

## 分区

在讨论分片之前先谈谈分区。术语常混用，通常将“将一个表拆分为多个片段”称为分区（partitioning），而将“将这些片段存储在不同服务器上”称为分片（sharding）。

基于 PostgreSQL 文档标准，分区表本身不占用存储空间，行根据分区键进入各个分区（普通表）。划分方式有三种：

- 范围（range）：按区间切割类似日期的键。按月分区是典型例子。
- 列表（list）：直接列出键值。例如按地区代码划分。
- 哈希（hash）：将键的哈希值对模数取余后分配。

效果是查询只需读取部分分区（pruning），且可以整体删除旧数据，使用 `DROP`或`DETACH PARTITION`命令即可。这比大范围的 `DELETE`快得多，且没有 VACUUM 的压力。不过文档指出，只有当表非常大时（经验法则：超过服务器内存）这些优势才有意义。也存在限制：主键和唯一约束必须包含所有分区键列。

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

(上面的 SQL 只是 PostgreSQL 文档中的示例，并未亲自执行过。)

## 分片 (Sharding)

将分区放置在不同的服务器上，即为分片。由于每台服务器只持有部分数据，因此存储容量和写入吞吐量都能随服务器数量线性增长。代价是应用程序（或路由层）必须知道“这个键位于哪个分片”。

### 分片键就是一切

决定如何划分数据（即选择分片键）是最关键的决策，一旦确定便难以更改。

| 方式 | 优点 | 缺点 |
|---|---|---|
| 范围 | 范围查询可在单个分片内完成 | 写入会集中在最新区间（产生热点） |
| 哈希 | 数据分布均匀 | 范围查询需遍历所有分片 |
| 目录表 (查找表) | 灵活 | 目录表会成为瓶颈或单点故障 |

如果按顺序分配 ID 并按范围划分，新产生的写入请求将全部流向最后一个分片。在下方的实验中，将 ID 1~10000 三等分后，最新的 1000 条记录全部进入了同一个分片（第 2 个）。本想通过分片实现均匀分布，结果却只有一台服务器在干活。

### 服务器数量变化时

使用哈希划分时，常见的初次尝试是 `hash(key) % 服务器数量`。这种方法简单，但当服务器数量改变时，几乎所有键的位置都会发生变化。亲自测试发现，当将 10,000 个键从 3 台服务器扩展到 4 台时，约有 75% 的键需要迁移到其他服务器。

一致性哈希 (consistent hashing) 可减少这一问题。它将服务器和键映射到同一个哈希环上，键被分配给沿顺时针方向遇到的第一个服务器。当增加一台服务器时，只需移动该新服务器与前一个服务器之间的键即可。根据维基百科的解释，添加第 n 台服务器时，大约只需移动 1/n 的数据。如果仅在哈希环上放置单点代表服务器，会导致间隔不均、负载倾斜；因此，应将一台服务器映射为多个点（虚拟节点）以实现均匀分布，并为性能要求较高的服务器分配更多虚拟节点。

<details>
<summary>亲自测试的代码与结果</summary>

```python
import hashlib, bisect
def h(k): return int(hashlib.md5(k.encode()).hexdigest(), 16)
keys = [f"user{i}" for i in range(10000)]

def mod(n): return {k: h(k) % n for k in keys}
a, b = mod(3), mod(4)
print("mod 3->4 moved:", sum(a[k] != b[k] for k in keys) / len(keys))

def ring(nodes, vn=100):
    r = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vn))
    hs = [x[0] for x in r]
    def f(k):
        i = bisect.bisect(hs, h(k)) % len(r)
        return r[i][1]
    return f

f3 = ring(["A", "B", "C"])
f4 = ring(["A", "B", "C", "D"])
print("ring 3->4 moved:", sum(f3(k) != f4(k) for k in keys) / len(keys))
```

运行结果 (Python 3, 在此环境中验证)。

```
mod 3->4 moved: 0.7484
ring 3->4 moved: 0.2392
```

实际迁移比例约为 24%，接近理论值 1/4 (25%)。虚拟节点设置为每台服务器 100 个。

</details>

## 分片带来的复杂性

分片虽然能提升写入能力，但也剥夺了数据库原本免费提供的功能。

- **连接查询 (Join)**：位于不同分片的表无法一次性进行连接查询。需要在应用程序中分别获取数据后再合并，或者通过选择分片键确保经常一起使用的数据位于同一分片。若对已**规范化**的表进行分片且跨越多个分片，负担会显著增加。
- **事务 (Transaction)**：在单个分片内可正常运作，但涉及多个分片的 [事务](#/post/db-transaction) 需要分布式事务（如两阶段提交）或补偿机制处理。速度慢且复杂。因此通常设计为让一个事务在一个分片内完成。
- **唯一约束与自增 ID**：若每个分片独立编号会产生重复，需要使用 UUID 或基于时间的 ID 等外部生成方式。
- **重分布 (Resharding)**：增加分片时需要迁移数据。若要实现零停机，则需进行双写和校验等工作。
- **运维**：备份、模式变更、监控等所有操作的成本都会随分片数量成倍增加。

因此，顺序通常是确定的。应先进行查询优化、索引改进、提升服务器规格 (scale-up)、使用缓存以及设置读副本；只有当写入量或容量仍然不足时，才考虑分片。从一开始就采用分片的方案大多是不必要的。选择内置了分片功能的 [NoSQL](#/post/db-nosql) 数据库也是一种方法。

## 一致性权衡

一旦引入复制和分片，“数据存在于多处”这一事实便随之而来，如何在不同位置保持相同值成为关键问题。PostgreSQL 文档对此总结如下：只读数据只需在每台服务器上存储一次，但写入必须传播到所有服务器以确保后续读取的一致性；因此不存在适用于所有工作负载的单一解决方案。

在实际工作中，通常在这三者之间寻求平衡：

| 提升 | 牺牲 |
|---|---|
| 一致性（无论何处读取均为最新） | 写入速度、单点故障时的可用性 |
| 写入速度与可用性 | 读取时保证最新值的能力 |
| 存储与写入扩展性 (分片) | 连接查询与事务的便利性 |

对于像银行余额这样不允许错误的场景，应偏向一致性；而对于像文章浏览量或信息流等允许几秒延迟的场景，则应偏向速度与扩展性。即使在同一个服务内部，也需针对不同类型的数据做出不同选择。

## 常见误解

- 复制后写入也会变快：不对。写入操作由主节点接收，从节点只是跟随应用这些更改，因此写入吞吐量保持不变。
- 从节点就是备份：不对。如果主节点误删了数据，该删除操作会同样反映到从节点上。需要采用延迟复制（delayed replication）或进行独立备份。
- 分区和分片是同一回事：通常在同一台服务器内划分称为分区，而跨多台服务器划分则称为分片。仅靠分区无法突破单台服务器的性能瓶颈。
- 提前规划分片更好：如果分片键选择不当，后期修改将非常困难，同时会立即增加运维复杂度。通常在确认有需求后再进行分片更为妥当。

## 总结

读多时采用复制，容量或写入遇到瓶颈时采用分片，若要在单台服务器内简化大表的管理则使用分区。无论哪种方式，一旦数据分散到多个位置，就必须明确在多大程度上可以牺牲一致性。
