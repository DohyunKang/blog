CPU가 하는 일은 단순하다. 메모리에서 명령어를 하나 꺼내고, 뭘 하라는 건지 해석하고, 실행한다. 이걸 전원이 꺼질 때까지 반복한다. 레지스터, 명령어 집합, 파이프라인은 이 반복을 어떻게 빠르고 정확하게 돌리느냐에 대한 이야기였다. 운영체제가 이 CPU를 어떻게 나눠 쓰는지는 [운영체제 개요](#/post/cs-os)에 있고, 여기서는 CPU 안쪽만 본다.

## 폰 노이만 구조

프로그램(명령어)과 데이터를 같은 메모리에 같이 넣어 두고, CPU가 거기서 명령어를 하나씩 읽어 실행하는 구조를 폰 노이만 구조라고 한다. 지금 쓰는 컴퓨터 대부분이 이 틀 위에 있다. 명령어도 결국 메모리에 있는 숫자라서, 프로그램을 바꾸는 건 메모리 내용을 바꾸는 일이다. 숫자가 어떻게 비트로 저장되는지는 [데이터 표현](#/post/ca-data-representation)에서 다룬다.

CPU 안에는 크게 세 가지가 있다.

| 구성 | 하는 일 |
|---|---|
| 제어 장치 | 명령어를 해석하고, 다른 장치에 "이제 이거 해"라는 신호를 보낸다 |
| ALU | 덧셈·뺄셈 같은 산술과 AND·OR 같은 논리 연산을 한다 |
| 레지스터 | CPU 안에 있는 아주 작고 빠른 저장 공간 |

메모리는 CPU 밖에 있고 레지스터보다 훨씬 느리다. 그래서 대부분의 연산은 값을 레지스터에 올려 놓고 하고, 결과를 다시 메모리에 내려 놓는다. 이 속도 차이가 [메모리 계층과 캐시](#/post/ca-memory-hierarchy)로 이어진다.

## 명령어 사이클

명령어 하나를 처리하는 과정은 세 단계로 나뉜다.

1. 가져오기(fetch): 프로그램 카운터(PC)가 가리키는 주소의 명령어를 메모리에서 읽어 명령어 레지스터에 넣는다. PC는 다음 명령어 주소로 넘어간다.
2. 해석(decode): 제어 장치가 명령어를 읽고 어떤 연산인지, 피연산자가 뭔지 알아낸다.
3. 실행(execute): ALU가 계산하거나, 메모리를 읽고 쓰거나, 결과를 레지스터에 저장한다.

PC는 보통 한 칸씩 늘어나지만 분기나 점프 명령어가 오면 다른 주소로 바뀐다. if나 반복문이 기계 수준에서는 PC를 바꾸는 명령어다.

작은 가상의 CPU를 파이썬으로 만들어서 이 사이클을 직접 돌려 봤다. 1부터 5까지 더하는 프로그램이다.

<details>
<summary>레지스터 머신 직접 돌려 보기 (실행 확인함)</summary>

```python
prog = [
    ("LOADI", 0, 0),   # r0 = 0 (합)
    ("LOADI", 1, 5),   # r1 = 5 (카운터)
    ("LOADI", 2, 1),   # r2 = 1
    ("ADD", 0, 1),     # r0 += r1
    ("SUB", 1, 2),     # r1 -= r2
    ("JNZ", 1, 3),     # r1 != 0 이면 PC = 3
    ("HALT", 0, 0),
]
reg = [0] * 4
pc = 0
cycles = 0
while True:
    ins = prog[pc]          # fetch
    pc += 1
    op, a, b = ins          # decode
    cycles += 1
    if op == "LOADI": reg[a] = b             # execute
    elif op == "ADD": reg[a] += reg[b]
    elif op == "SUB": reg[a] -= reg[b]
    elif op == "JNZ":
        if reg[a] != 0: pc = b
    elif op == "HALT": break
print(reg[0], cycles)
# 15 19
```

결과는 15이고, 명령어는 19개가 실행됐다. 처음 3개 + 반복 본문 3개를 5번 + HALT 1개다. 반복문이 "PC를 3으로 되돌리는 점프"일 뿐이라는 게 코드에서 그대로 보인다.
</details>

## 명령어는 어떻게 생겼나

실제 명령어도 비트 덩어리다. 보통 어떤 연산인지 알려 주는 연산 코드(opcode)와, 어떤 레지스터나 어떤 상수를 쓸지 알려 주는 피연산자 필드로 나뉜다. 위 예제의 `("ADD", 0, 1)`이 그 모양을 문자로 풀어 쓴 것이다.

이 명령어들의 약속 전체를 명령어 집합 구조(ISA)라고 한다. 어떤 명령어가 있는지, 레지스터가 몇 개인지, 메모리 주소를 어떻게 지정하는지가 ISA에 들어간다. x86, ARM, RISC-V가 ISA의 이름이다. 같은 ISA를 따르면 프로그램이 칩 제조사와 상관없이 돌아가고, 칩 안쪽 설계는 자유롭다. 컴파일러가 소스 코드를 만들어 내는 최종 결과물이 이 ISA의 명령어 열이다.

ISA는 크게 두 갈래로 이야기된다. RISC는 명령어를 단순하고 규칙적으로 만들어서 하드웨어를 빠르게 돌리기 쉽게 하고, CISC는 명령어 하나가 더 많은 일을 하게 한다. 파이프라인 설명에 자주 쓰이는 고전 RISC 파이프라인은 RISC 쪽 구조다.

## 파이프라인

세 단계를 한 명령어씩 끝까지 하고 다음 명령어를 시작하면 가져오기 장치는 실행 중에 놀게 된다. 세탁기와 건조기가 있을 때 첫 빨래가 건조기에 들어가면 세탁기에 다음 빨래를 넣는 것과 같은 생각이다. 명령어 처리를 단계로 쪼개서 서로 다른 명령어가 서로 다른 단계에 동시에 있게 만든 게 파이프라인이다.

고전 RISC 파이프라인은 5단계다.

| 단계 | 하는 일 |
|---|---|
| IF | 명령어를 메모리에서 가져온다 |
| ID | 해석하고 레지스터를 읽는다 |
| EX | ALU가 계산한다(메모리 주소 계산도 여기서) |
| MEM | 데이터 메모리를 읽고 쓴다 |
| WB | 결과를 레지스터에 쓴다 |

파이프라인이 한 번 가득 차면 매 사이클마다 명령어 하나가 끝난다. 명령어 하나의 처리 시간(지연)은 그대로지만 단위 시간당 끝나는 개수(처리량)가 늘어난다.

<details>
<summary>사이클 수 계산해 보기 (실행 확인함)</summary>

명령어 n개, 단계 5개일 때 파이프라인이 없으면 5n 사이클, 있으면 5 + (n-1) 사이클이다. 지연이 생기면 그만큼 더한다.

```python
def cycles(n, stall=0, stages=5):
    return stages + (n - 1) + stall
n = 100
print("파이프라인 없음:", n * 5)        # 500
print("파이프라인:", cycles(n))          # 104
print("load-use 20번:", cycles(n, stall=20))  # 124
print(5 / (cycles(n)/n))                 # 4.80...
```

명령어 100개면 500사이클이 104사이클로 줄어 약 4.8배가 된다. 단계 수 5에 가까워질 뿐 넘지는 못한다. 중간에 멈추는 일이 20번 있으면 124사이클이라 속도 향상이 약 4배로 내려간다.
</details>

## 해저드: 겹쳐 돌리면 생기는 문제

명령어를 겹쳐 실행하면 앞 명령어가 끝나기 전에 뒤 명령어가 시작해서 문제가 생길 수 있다. 이런 상황을 해저드라고 부른다.

- 데이터 해저드: 뒤 명령어가 앞 명령어의 결과가 필요한데 아직 레지스터에 쓰이지 않았다. `ADD r1, r2, r3` 바로 다음에 r1을 쓰는 명령어가 오는 경우다. 해결은 포워딩(바이패스)으로 한다. 결과가 레지스터에 쓰이기를 기다리지 않고 ALU 출력에서 바로 다음 명령어의 입력으로 보내 준다. 다만 메모리에서 읽어 오는 load 명령어는 값이 늦게 나와서 바로 다음 명령어가 쓰면 한 사이클을 비워야(버블, 스톨) 한다.
- 제어 해저드: 분기 명령어가 어디로 갈지 알기 전에 다음 명령어를 이미 가져와 버렸다. 예측이 틀리면 가져온 걸 버리고 다시 가져와야 한다. 분기 예측은 결과를 미리 추측해서 이 낭비를 줄이는 방법이다. 초기 MIPS는 분기 바로 다음 칸(지연 슬롯)을 컴파일러가 채우게 하는 방식도 썼다.
- 구조 해저드: 두 명령어가 같은 하드웨어를 동시에 쓰려는 경우다. 예를 들어 메모리 접근 장치가 하나뿐이면 가져오기와 데이터 접근이 부딪힌다.

## 흔한 오해

- 클럭이 높으면 무조건 빠르다: 사이클당 끝내는 명령어 수(IPC)와 명령어 개수도 속도에 같이 걸린다. 파이프라인이 멈추면 클럭이 같아도 느려진다.
- 파이프라인이 깊을수록 좋다: 단계를 늘리면 한 단계가 짧아져서 클럭을 올릴 수 있지만, 분기 예측이 틀렸을 때 버리는 양도 같이 늘어난다.
- 명령어 하나가 한 사이클에 끝난다: 파이프라인에서는 명령어 하나가 여러 사이클에 걸쳐 지나가고, 여러 개가 겹쳐 있을 뿐이다.
- 메모리 읽기는 CPU 안의 일이다: 메모리는 CPU 밖이라 읽기가 가장 느린 축이다. 장치와 CPU가 어떻게 연결돼 데이터를 주고받는지는 [입출력과 버스](#/post/ca-io-bus)에서 이어진다.
