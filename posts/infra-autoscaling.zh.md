自动伸缩是一种根据负载自动调整服务器数量或规模的机制。要让它运行良好，关键在于选择哪些指标以及服务器是否保持无状态。

## 什么是扩展

当服务用户量增加时，单台服务器将无法满足需求。此时有两种扩容方式：

| | 垂直扩展 (scale up) | 水平扩展 (scale out) |
|---|---|---|
| 方法 | 用更大的服务器替换现有服务器 | 增加相同配置的服务器数量 |
| 优点 | 几乎无需修改代码 | 理论上无上限，单台故障不影响整体 |
| 缺点 | 存在硬件上限，更换时需停机 | 需要负载均衡器，且服务器间需共享状态 |

提到自动伸缩时，通常指水平扩展。增加一台新服务器比替换大尺寸服务器更容易自动化，因为后者涉及重启操作。将请求分发到多台服务器的部分已在 [详见 → 负载均衡器](#/post/infra-load-balancer) 中单独整理。

## “自动扩容”的含义

即由机器代替人工监控仪表盘并添加服务器。流程基本一致：

1. 采集指标（如 CPU、请求数等）。
2. 与目标值进行比较。
3. 若不足则增加服务器，若有余量则减少服务器。

AWS 的 target tracking 文档将此过程比作恒温器：设定目标平均 CPU 为 50%，超过该值时扩容，低于该值时缩容。根据文档，此方式由 CloudWatch 自动创建并管理告警。

Kubernetes 的 HPA（Horizontal Pod Autoscaler）也基于相同思路。官方文档给出的计算公式如下：

```
원하는 개수 = ceil[ 현재 개수 × (현재 지표값 / 목표 지표값) ]
```

当前有 4 个实例，平均 CPU 为 90%，目标值为 50%，则计算结果为 4 × 1.8 = 7.2，向上取整后变为 8 个实例。文档指出 HPA 默认每 15 秒执行一次此计算。

<details>
<summary>详细解析：亲自动手验证计算公式</summary>

由于公式难以直观理解，我用 Python 重新实现并运行了测试。tol 参数表示“接近目标值时保持不动”的容差区间，0.1 是我设定的值。

```python
import math

def desired(cur, metric, target, tol=0.1):
    r = metric / target
    if abs(r - 1) <= tol:      # 목표 근처면 그대로
        return cur
    return math.ceil(cur * r)

print(desired(4, 90, 50))   # 8  (7.2를 올림)
print(desired(4, 52, 50))   # 4  (여유 구간 안이라 유지)
print(desired(10, 20, 50))  # 4  (줄이는 쪽도 같은 식)
print(desired(1, 60, 50))   # 2
```

执行结果为 8、4、4、2。采用向上取整策略后，“略微不足”的情况也会导致实例数增加。这种设计倾向于宁可多配也不愿少配，避免因低估负载导致性能瓶颈。

</details>

## 应该基于什么指标进行扩容

在关于伸缩的文章中，最难的部分往往是指标的选择：

- **CPU 使用率**：最常见。适用于计算密集型服务器；但对于主要等待外部响应的服务器，CPU 可能不高但系统会变慢。
- **请求数（每台服务器）**：对 Web 服务而言非常直观。AWS 负载均衡器也提供每个目标的请求数（`ALBRequestCountPerTarget`）作为默认指标。
- **队列长度**：适用于后台处理任务的 Worker。AWS 文档明确指出，不能直接使用 SQS 队列中累积的消息总数，而应转换为“每台服务器的消息数”。即使增加服务器，队列长度也不会按比例下降，因此需按单机负载计算。相关内容详见 [详见 → 异步处理与消息队列](#/post/be-async-queue)。
- **延迟时间 (latency)**：可直接反映系统变慢的情况，但文档指出不应将其用于 target tracking。因为随着服务器数量增加，延迟不会成比例下降，故不适合作为伸缩依据。

用我的话概括 AWS 的标准：随着服务器数量增加，指标值应成比例下降。因此，负载均衡器的总请求数在扩容后保持不变，不能作为伸缩依据。

在 Kubernetes 中若要以 CPU 使用率为目标进行伸缩，文档要求容器必须设置 `requests`。若未设置请求值，则无法计算使用率，HPA 将不会基于该指标执行任何操作。忽略这一点会导致长时间困惑：“为什么没有自动扩容？”

## 缩容比扩容更需谨慎

新服务器启动需要时间。在此期间，指标仍可能偏高，系统可能再次判断“需要扩容”，从而导致过度配置。

AWS 通过 warmup（预热）时间处理此问题：在新服务器完成预热前，不将其纳入指标统计，同时禁止执行缩容操作。文档表述的目标是：“持续扩容，但避免过度扩容”。

缩容时同样需谨慎。文档指出，target tracking 在缩容时会更加缓慢，并采用保守的舍入策略。例如，减少一台服务器后若负载立即超过目标值，系统将避免频繁伸缩带来的震荡。在小规模集群中，这种影响尤为显著。

<details>
<summary>详细解析：小规模集群为何显得偏离目标</summary>

AWS 文档中提到，如果服务器数量较少，实际利用率与目标值可能会出现较大偏差。因此我进行了数值模拟：假设总负载相当于两台服务器各 60% 的负载（合计 120），并将目标设定为 50%。

- **2 台服务器组**：120 / 50 = 2.4 → 需向上取整至 3 台。若使用 3 台，则每台负载为 40%，与目标相差 10 个百分点。
- **20 台服务器组**：总负载 1200 / 50 = 24 台。此时每台服务器负载恰好为 50%。

由于只能以单台为单位进行调整，因此服务器数量越少，向上取整带来的影响越大；而在大型集群中，单台服务器的占比越小，实际负载越接近目标值。

</details>

## 为什么服务器需要保持无状态（stateless）

这部分是本文的核心内容。若要随意启动或关闭服务器，必须确保无论哪台服务器下线，服务都能持续运行。

假设用户登录信息（会话）存储在服务器内存中：当请求从 A 服务器转发到 B 服务器时，B 无法识别该用户；一旦减少节点导致 A 服务器被移除，该用户即被视为已登出。因此，服务器应设计为无状态（stateless），而将状态信息存储于外部。

| 状态类型       | 外部存储位置         |
|----------------|----------------------|
| 会话、临时数据 | 共享缓存（如 Redis）→ [详情 → 缓存与 Redis](#/post/db-cache-redis) |
| 用户数据       | 数据库               |
| 上传文件       | 对象存储             |
| 待处理任务     | 消息队列             |

如此设计后，所有服务器仅包含代码副本，彼此等价。新增节点可立即工作，移除节点亦无损失。关于在服务器中保留会话还是使用令牌进行认证，将在 [详情 → 认证与授权](#/post/be-auth) 中详细说明。

## 数据库该如何应对

服务器易于扩展，但数据库并非如此。即使将服务器数量扩展到 80 台，若它们全部连接至同一数据库，瓶颈仍会转移至数据库。读写副本、分库分表等方案已在 [详情 → 数据扩展](#/post/db-scaling) 中单独整理。在启用自动扩缩放之前，必须预先计算“新增服务器将建立多少个数据库连接”，这是本次梳理中确定的关键检查项。

## 常见误区

- **开启自动扩缩放即可应对突发流量**：由于服务器启动需要时间，无法即时响应瞬间流量激增。因此需预留充足的最小实例数，或采用提前预热的策略（注：此观点并非直接来自文档，而是基于前文 warmup 说明的延伸思考）。
- **只需增加服务器**：若未配置缩减机制，成本将持续累积。相反，应将最小实例数设为 0，以便在无请求时缩容至零台（AWS 文档明确指出这一点）。
- **仅增加服务器就能提升性能**：若瓶颈在于数据库或外部 API，单纯增加服务器无效。
- **任意指标均可用于扩缩放**：所选指标必须随服务器数量变化而线性变动。
- **高请求量时直接返回 429 即可**：限流与扩容属于不同的防御层级，应协同使用 → [详情 → 速率限制](#/post/infra-rate-limit)
