백엔드는 "요청을 받아서 응답을 돌려주는 서버 쪽 코드"인데, 공부하다 보면 REST, 인증, 큐, 로그, 테스트가 따로따로 튀어나온다. 그래서 요청이 지나가는 순서를 뼈대로 잡고, 각 글이 어디에 붙는지 한 줄씩만 적었다. 더 알고 싶은 건 링크로 넘어가면 된다.

## 한눈에 보는 관계

```
클라이언트 ──요청──▶ [API·REST: 주소+메서드로 말한다]
                         │ 누구냐 / 해도 되냐 → [인증과 인가]
                         ▼
             [요청 흐름: 미들웨어 → 라우터 → 핸들러 → DB]
                         │ 코드는 이렇게 나눈다
                         ▼
             [레이어드 아키텍처] ← 좋은 모듈 기준: [응집도·결합도]
                         │ 오래 걸리는 일은 [비동기·큐]로
                         ▼
                 응답 (실패하면 [에러 처리·로깅])

이 전부를 믿을 수 있게 확인하는 방법 = [백엔드 테스트]
```

## 1. 바깥과 어떻게 말하나

**API와 REST**: 주소로 대상을 가리키고 HTTP 메서드로 동작을 말하는 약속. 같은 요청을 두 번 보내도 되는지(멱등성)가 설계에서 은근히 중요하다.
[자세히 → API와 REST](#/post/be-api-rest)

**인증과 인가**: 로그인(누구냐)과 권한(해도 되냐)은 다른 문제다. 세션·JWT·OAuth·RBAC가 각각 어느 쪽을 맡는지 나눠서 본다.
[자세히 → 인증과 인가](#/post/be-auth)

## 2. 서버 안에서 어떻게 흘러가나

**요청이 처리되는 흐름**: 클라이언트가 보낸 요청이 미들웨어 줄을 지나 라우터에서 핸들러로 가고, DB를 거친 응답이 같은 길로 돌아오는 과정.
[자세히 → 요청이 처리되는 흐름](#/post/be-request-flow)

**레이어드 아키텍처**: 컨트롤러·서비스·리포지토리로 코드를 층층이 나누고 위에서 아래로만 의존하게 하는 방식. 작은 프로젝트엔 과할 수 있다.
[자세히 → 레이어드 아키텍처](#/post/be-layered-architecture)

**모듈 응집도와 결합도**: 한 모듈은 한 가지 일만 하고 다른 모듈과는 가볍게 엮이는 게 좋다는 기준.
[자세히 → 모듈 응집도와 결합도](#/post/be-coupling-cohesion)

## 3. 느리거나 틀어질 때

**비동기 처리와 메시지 큐**: 오래 걸리는 일은 큐에 넣어 두고 워커가 따로 처리한다. 대신 같은 메시지가 두 번 올 수 있다는 걸 각오해야 한다.
[자세히 → 비동기 처리와 메시지 큐](#/post/be-async-queue)

**에러 처리와 로깅**: 에러는 어디서 잡고 뭘 남기느냐가 일이다. 재시도, 타임아웃, 로그 형식과 에러 응답까지 한 묶음.
[자세히 → 에러 처리와 로깅](#/post/be-error-logging)

## 4. 믿을 수 있게 만들기

**백엔드 테스트**: 고쳤을 때 예전에 되던 게 아직 되는지 확인하는 코드. 단위·통합·E2E 중 싸고 빠른 걸 아래에 많이 깔아 두는 게 기본 모양이다.
[자세히 → 백엔드 테스트](#/post/be-testing)
