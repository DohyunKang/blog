技能是将执行特定任务的方法（流程、参考资料、脚本）打包存放在一个文件夹中，仅在模型判断需要时才将其取出读取。始终出现在上下文中的只有名称和一两行描述。

## 什么是技能

Anthropic 的文档将技能介绍为“基于文件系统的可重用资源，由指令、元数据和可选资源（脚本、模板）组成”。在工程文章中，这被比喻为给新员工提供的入职指南。

其结构非常简单：一个文件夹中必须包含 `SKILL.md`，如有需要则在旁边放置参考资料或脚本。

```
pdf-processing/
  SKILL.md        # 메인 지침 (필수)
  FORMS.md        # 양식 채우기 가이드
  REFERENCE.md    # API 상세
  scripts/
    fill_form.py  # 돌려서 쓰는 도구
```

`SKILL.md` 的顶部是 YAML 格式的头部（包含 `name`、`description`），其后是正文内容。简化后的文档示例如下：

```markdown
---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
---

# PDF Processing

## Quick start
(pdfplumber로 텍스트 뽑는 코드)

양식 채우기는 FORMS.md를 본다.
```

## 原理：分步读取

核心在于不会一次性全部上传。文档将此称为“渐进式披露”（progressive disclosure），并将其分为三个阶段：

| 阶段 | 何时加载 | 令牌成本（以文档计） | 内容 |
|---|---|---|---|
| 1. 元数据 | 开始时始终加载 | 每个技能约 100 个令牌 | `name`、`description` |
| 2. 正文 | 使用技能时 | 少于 5k 个令牌 | `SKILL.md` 的正文内容 |
| 3. 资源与代码 | 需要时才加载 | 读取前为 0 | 附带文件、脚本 |

从流程上看，开始时系统提示符中会包含每个技能的名称和描述。当用户提出请求时，模型会根据描述判断是否存在合适的技能。如果存在，则通过 bash 读取 `SKILL.md`，将正文内容传入 [上下文](#/post/ai-context-window)。如果正文中提到“请参见 FORMS.md"，则在需要该文件时才进行读取。在文档示例中，由于是 PDF 文本摘要请求，因此不会读取 `FORMS.md`。

脚本不是被读取而是被执行。根据文档说明，脚本代码不会进入上下文，只有执行结果会被传入。因此，与其每次都重新编写代码来完成相同任务，这样做既能节省令牌又能获得一致的结果。

得益于这种结构，即使安装大量技能也不会造成负担。文档指出：“在技能被使用之前，仅名称和描述会占用上下文空间。”然而，由于模型仅根据描述进行选择，因此描述实际上构成了入口点。

## 与提示词、工具及 MCP 有何不同

| | 功能 | 进入上下文的时机 |
|---|---|---|
| [提示词](#/post/ai-prompt) | 本次对话的指令 | 每次直接编写时 |
| 技能 | 以文件夹形式存储工作流程与知识 | 描述始终加载，正文按需加载 |
| [工具调用](#/post/ai-tool-use) | 模型执行外部功能 | 工具定义被加载，调用时传入结果 |
| [MCP](#/post/ai-mcp) | 通过标准方式将工具连接到外部服务器 | 已连接的工具定义被加载 |

文档指出，技能与“一次性提供的对话级提示词”不同，它是“按需加载的机制，避免重复提供相同的指导”。如果说工具关注的是“能做什么”，那么技能则更接近于“如何做”。不过，这种区分并非文档刻意强调的重点，两者经常结合使用（例如技能正文中会指导调用 MCP 工具）。此外，文档中也提到，在使用 MCP 工具时，需按照 `服务器名称:工具名称` 的格式指定服务器名称。

## 在哪里使用

根据 Anthropic 文档，技能可在多个场景中使用，但方式各异：

- **Claude API**：在 `container` 中传递 `skill_id`，并需要配套的执行代码工具。自行创建的技能需上传至 `/v1/skills`，供整个工作空间使用。无法访问网络，也不能安装新包。
- **claude.ai**：通过设置以 zip 格式上传。仅限个人使用，不支持组织级别的共享与管理。提供用于文档处理的基础技能（如 pptx、xlsx、docx、pdf）。
- **Claude Code**：可放置于 `~/.claude/skills/<名称>/SKILL.md`（个人）或 `.claude/skills/<名称>/SKILL.md`（项目）中。其网络环境与本地计算机相同。

重要的是，这三者之间不会自动同步。在 claude.ai 上上传的技能，不会自动出现在 API 或 Claude Code 中。

Claude Code 的文档中还包含更多内容。在开头部分，使用 `disable-model-invocation: true` 可禁止模型自动调用，仅在通过 `/이름`（此处保留原文占位符格式）手动调用时才生效；反之，若设置 `user-invocable: false`，则会在 `/` 菜单中隐藏该技能，仅允许模型调用。旧的自定义斜杠命令（`.claude/commands/`）已合并为技能，但原有文件仍可继续运行。关于整体如何划分配置手段，已在 [Claude Code 技能与配置](#/post/claude-skills) 文章中另行整理。

## 正确使用指南：文档所述最佳实践

仅从 best practices 文档中提取了包含数字和规则的要点：

- `name`：长度不超过 64 个字符，仅允许使用小写字母、数字和连字符；`anthropic` 与 `claude` 为保留字，不可使用。
- `description`：不得为空，且长度不得超过 1,024 个字符。需同时说明该技能的功能及使用场景，并以第三人称撰写（例如“处理 Excel 文件”，而非“我可以提供帮助”）。该描述将纳入系统提示；若时间视角混乱，可能导致模型决策不稳定。
- `SKILL.md` 正文内容应控制在 500 行以内，超出时需拆分文件。
- 引用关系：在 `SKILL.md` 中最多只允许引用一个其他文件。若在文件内部再链接至另一文件，模型可能仅读取前部内容（类似 `head -100`）便跳过后续部分。
- 指令应简洁明了。默认前提是“模型本身已足够智能”，仅需补充模型未知的信息。
- 若任务风险较高（如数据库迁移），应降低自由度，要求“直接执行此脚本”；而对于需要判断的任务（如代码审查），则应提高自由度。
- 应先构建评估机制。在无需技能的情况下尝试执行，定位受阻环节后，仅补充必要的最小内容。

Claude Code 文档还指出，若描述过长会被截断。`description` 与 `when_to_use` 合并后的总长度超过 1,536 个字符时将被截断，因此建议将核心用途置于开头。

## 常见误解

- 安装过多技能会导致上下文溢出：通常情况下，仅上传每个技能的名称和描述（按文档标准约 100 个 token），正文仅在调用时传入。但若技能数量达到数百个，该描述列表本身也会显著增大，并非完全免费。
- 已调用的技能会持续保留：Claude Code 文档指出，一旦使用某技能，其正文将进入对话上下文，并在后续轮次中持续存在。因此，在长期运行任务中，它将占用相应上下文空间。
- 技能可无条件信任：由于技能同时提供指令与代码，不良技能可能导致模型错误调用工具。文档建议仅使用自行创建或由 Anthropic 提供的技能；对于来源不明的内容，应将其包含的所有文件（含脚本、图像等）视为可疑并谨慎处理。引入外部 URL 的技能风险更高，可类比于软件安装行为对待。
- 有技能则模型必然使用：是否调用由模型根据描述自行决定。因此若描述模糊（如“辅助文档工作”），可能不会被调用。这也是文档特别强调名称与描述的重要原因。
- 技能并非提示词的别名：尽管表面上是一组指令，但其具备文件系统结构、分阶段加载及脚本执行等特性，与普通提示词不同。反过来说，仅将长提示词放入文件夹并不能获得技能的益处。必须将其拆分为可独立阅读的部分。

<summary>详细解析：技能在上下文中累积的顺序</summary>

严格遵循文档中的 PDF 示例进行说明：

1. 初始状态：系统提示中包含一行“pdf-processing - 从 PDF 中提取文本和表格并填写表单……”。
2. 用户请求：“请从此 PDF 中提取文本并进行摘要。”
3. 模型执行 `cat pdf-processing/SKILL.md` 读取正文，此时正文已加入上下文。
4. 因无需填写表单，故不读取 `FORMS.md`。
5. 按照正文中的指令开展工作。

在 Claude Code 中还存在一项额外机制：根据文档说明，当发生自动压缩（compaction）时，会重新附加最近使用的技能，但每个技能仅保留前 5,000 个 token，整体预算上限为 25,000 个 token。上下文预算自最近使用的技能开始填充，较旧的技能可能被剔除。因此，将关键指令置于 `SKILL.md` 前端更为稳妥。（此内容基于对文档的阅读，未经过本人直接实验验证。）关于压缩机制本身，已在 [上下文](#/post/ai-context) 相关文章中整理说明。

</details>

<details>
<summary>详细解析：子代理与 Harness 的关系</summary>

我理解的是，当技能正文进入和离开上下文后，它们将被当作普通的指令来处理。不同之处在于进入之前：何时读取什么、如何执行脚本，这些由包裹模型的 [Harness](#/post/ai-harness) 负责。“技能”这一概念更接近于 Harness 方面的约定，而非模型本身。

Claude Code 文档在引言中提到，添加 `context: fork` 可以在单独的 [子代理](#/post/ai-subagent) 中运行技能。我将其理解为用于独立处理输出较多的任务，并仅接收摘要，但我尚未亲自尝试过。
