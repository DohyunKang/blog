LLM API를 호출해서 답을 주는 서비스는 일반 웹 서비스와 다르게 한 요청이 몇 초씩 걸리고, 가끔 실패하고, 부를 때마다 돈이 나간다. 그래서 요청 길 중간에 큐, 캐시, 스트리밍, 타임아웃, 비용 제한을 한 겹씩 두는 구조가 된다.

## 일반 API와 뭐가 다른가

[요청 하나가 거치는 길](#/post/infra-request-journey)에서 본 것처럼 보통 웹 요청은 DNS, CDN, 로드밸런서, 서버, DB를 지나고 몇십 ms면 끝난다. LLM이 끼면 서버가 외부 API 하나를 더 기다린다. 이 기다림이 다른 단계보다 훨씬 길다. 답이 한 번에 만들어지지 않고 토큰을 하나씩 생성하기 때문이다.

차이를 표로 정리하면 이렇다.

| | 보통 API | LLM 호출 |
|---|---|---|
| 걸리는 시간 | 수십 ms | 몇 초에서 길면 몇 분 |
| 응답 크기 | 거의 고정 | 생성하는 만큼 달라짐 |
| 같은 입력 | 같은 출력 | 보통 매번 조금 다름 |
| 호출 비용 | 거의 0 | 입력·출력 토큰만큼 과금 |
| 한도 | 내 서버 사양 | 업체가 정한 분당 요청·토큰 한도 |

[LLM이란 무엇인가](#/post/ai-llm)에서 다룬 것처럼 모델은 다음 토큰을 계속 이어 붙이는 방식이라, 응답 시간이 출력 길이에 비례해서 늘어난다. 서버 쪽에서 보면 연결 하나를 오래 붙잡고 있는 요청이다.

## 구조를 한 장으로

서비스 쪽에서 흔히 두는 층을 순서대로 그리면 이런 모양이다.

```
사용자
  │  (스트리밍으로 받음)
  ▼
[ 우리 서버 ]
  ├─ 1. 인증·사용자별 한도 확인      ← 내 서비스의 레이트 리밋
  ├─ 2. 캐시 조회                    ← 같은 질문이면 여기서 끝
  ├─ 3. 큐 / 동시 호출 제한          ← 업스트림을 한 번에 너무 못 부르게
  ├─ 4. LLM API 호출                 ← 타임아웃·재시도·스트리밍
  └─ 5. 사용량 기록                  ← 토큰 수, 비용, 요청 ID
```

층마다 막는 문제가 다르다. 아래에서 하나씩 본다.

## 1. 한도: 업체 한도와 내 한도

Anthropic 문서 기준으로 Messages API 한도는 분당 요청 수(RPM), 분당 입력 토큰(ITPM), 분당 출력 토큰(OTPM)으로 모델별로 잡힌다. 하나라도 넘으면 429가 오고, 응답에 `retry-after` 헤더가 있으면 그 초만큼 기다렸다 다시 보내라고 한다. 한도 방식은 토큰 버킷이라 고정 구간마다 리셋되는 게 아니라 용량이 계속 채워진다. 버킷 알고리즘 자체는 [레이트 리밋과 트래픽 제어](#/post/infra-rate-limit)에 정리한다.

몇 가지 눈에 띄었던 점.

- 한도는 조직의 사용 등급(tier)에 따라 다르다. 등급별 표가 문서에 있는데 숫자가 모델마다, 시점마다 바뀌어서 여기에는 옮기지 않는다.
- 대부분의 모델에서 캐시에서 읽은 입력 토큰은 ITPM에 안 센다. 그래서 캐시를 쓰면 같은 한도로 더 많이 처리할 수 있다.
- 429가 전부 일시적인 건 아니다. 월 지출 상한에 닿으면 같은 429 `rate_limit_error`가 오는데 `retry-after`가 없고 다음 달 초까지 계속 실패한다. SDK의 자동 재시도도 소용없다. `error.details.error_code`가 `enforced_spend_limit_reached`인지로 구분한다고 한다.
- 내가 직접 정한 지출 상한에 닿으면 429가 아니라 400이 온다.

그래서 서비스에는 두 종류의 한도가 필요하다. 업체가 걸어 둔 한도를 넘지 않게 하는 것, 그리고 사용자 한 명이 내 한도를 혼자 다 쓰지 못하게 하는 것. 후자는 업체가 대신 해 주지 않는다.

## 2. 캐시: 같은 질문엔 다시 안 부른다

가장 싼 호출은 안 하는 호출이다. 응답 캐시는 질문(과 모델, 설정)을 해시해서 키로 쓰고 결과를 저장한다. [캐시와 Redis](#/post/db-cache-redis)의 방식을 그대로 가져온다. 다만 LLM에서는 조건이 붙는다.

- 같은 입력에 매번 다른 답이 나올 수 있으니, "똑같은 답을 줘도 되는 질문"에만 쓴다. FAQ형 질문이나 번역, 분류처럼.
- 사용자 개인 정보가 들어간 응답은 키에 사용자를 넣거나 아예 캐시하지 않는다.

이것과 이름이 같지만 다른 것이 업체가 제공하는 프롬프트 캐싱이다. 응답을 저장하는 게 아니라 긴 프롬프트의 앞부분 처리 결과를 재사용한다. 문서 기준으로 기본 수명은 5분이고 히트할 때마다 갱신된다. 읽기 단가는 기본 입력 단가의 0.1배인 모델이 많고, 쓰기는 5분짜리가 1.25배다. 접두가 정확히 같아야 히트한다. 자세한 건 [프롬프트 캐싱](#/post/ai-prompt-caching)에 있다.

| | 응답 캐시(내 서버) | 프롬프트 캐싱(업체) |
|---|---|---|
| 저장하는 것 | 완성된 답 | 프롬프트 앞부분의 처리 결과 |
| 히트하면 | LLM을 아예 안 부름 | 호출은 하되 입력 단가·한도가 줄어듦 |
| 조건 | 같은 질문 | 앞부분이 글자 단위로 같음 |

## 3. 큐와 동시성 제한

사용자가 한꺼번에 몰리면 업스트림으로 요청이 한꺼번에 나가서 한도에 걸린다. 그래서 서비스 쪽에서 동시에 나가는 호출 수를 제한한다. 간단하게는 세마포어, 크게는 메시지 큐와 워커다. [비동기 처리와 메시지 큐](#/post/be-async-queue)에서 다루는 구조인데, LLM에서는 이유가 하나 더 있다. 답이 오래 걸리는 작업은 요청 안에서 끝내려 하지 말고, 작업을 큐에 넣고 사용자에겐 "처리 중"을 보여 주는 편이 연결 관리가 쉽다.

Anthropic 쪽에는 이런 용도의 Message Batches API도 있다. 문서에서는 긴 요청에서 연결이 끊길 위험을 줄이는 방법으로 소개하고, 결과를 폴링으로 가져가는 방식이라고 설명한다. 실시간이 필요 없는 대량 작업에 맞는 방식이다.

## 4. 스트리밍과 타임아웃

LLM 응답은 길어서, 다 만들어질 때까지 기다리게 하면 사용자는 빈 화면을 본다. 그래서 `stream: true`로 서버-전송 이벤트(SSE)를 받아서 생성되는 대로 흘려 보낸다. 문서에 나오는 흐름은 `message_start`, 여러 개의 `content_block_delta`, `message_stop` 순이고 중간에 `ping`이 섞일 수 있다.

스트리밍은 체감 속도 때문만이 아니다. 문서는 10분 넘는 긴 요청이나 `max_tokens`가 큰 요청을 스트리밍 없이 보내지 말라고 한다. 네트워크가 유휴 연결을 끊을 수 있기 때문이다. 공식 SDK는 스트리밍이 아닌 요청이 10분을 넘길 것 같으면 검증 단계에서 막는다고 한다.

그리고 하나 더. 스트리밍은 HTTP 200을 받은 뒤에도 오류가 날 수 있다. 문서의 예로는 이벤트 스트림 안에 `overloaded_error`가 들어오는 경우가 있다. 이때는 상태 코드로 처리하는 일반 오류 처리가 통하지 않으니, 스트림을 읽는 코드가 `error` 이벤트를 직접 다뤄야 한다.

타임아웃은 두 가지로 나눠 생각하는 게 맞는 것 같다. 연결을 맺는 데 걸리는 시간과, 응답이 다 올 때까지의 전체 시간이다. 스트리밍이면 "다음 조각이 오기까지 얼마나 기다릴지"가 더 쓸모 있는 기준이 된다. 구체적인 값은 서비스마다 다르게 잡아야 해서 따로 숫자를 적지 않는다.

## 5. 재시도와 실패 처리

문서의 오류 코드 중 서버가 일시적으로 못 받는 경우가 429, 500, 504, 529다. 529는 API가 전체적으로 과부하일 때 나오고, 500은 Anthropic 내부 오류라 지수 백오프로 재시도하라고 한다. 반대로 400, 401, 403, 413은 요청 자체가 잘못된 거라 다시 보내도 같은 결과다. 재시도할 것과 하지 않을 것을 나눠야 한다.

공식 SDK는 연결 오류, 429, 5xx를 기본 2번 지수 백오프로 재시도하고 `retry-after`가 있으면 그 값을 따른다. `max_retries`로 조정한다. 직접 짜면 이 규칙을 따라가면 되고, SDK를 쓰면서 내 코드에서 또 재시도를 감싸면 횟수가 곱해진다는 점을 조심해야 한다.

<details>
<summary>자세한 풀이: 동시성 제한 + 캐시 + 재시도를 합친 작은 예제</summary>

진짜 API 대신 40% 확률로 과부하(529 역할)를 내는 가짜 함수를 두고, 세마포어로 동시 호출을 3개로 묶고, 응답 캐시와 지수 백오프 재시도를 얹은 코드다. 직접 실행했다.

```python
import asyncio, random, hashlib

class Busy(Exception): pass

calls = 0
async def fake_llm(prompt):
    """진짜 API 대신 쓰는 가짜. 40%는 과부하, 가끔 느림."""
    global calls
    calls += 1
    await asyncio.sleep(random.choice([0.05, 0.05, 0.05, 0.3]))
    if random.random() < 0.4:
        raise Busy("529")
    return f"answer({prompt})"

cache = {}
sem = asyncio.Semaphore(3)  # 동시에 3개까지만 업스트림으로

async def ask(prompt, retries=4, timeout=0.2):
    key = hashlib.sha256(prompt.encode()).hexdigest()
    if key in cache:
        return cache[key]
    async with sem:
        for n in range(retries + 1):
            try:
                out = await asyncio.wait_for(fake_llm(prompt), timeout)
                cache[key] = out
                return out
            except (Busy, asyncio.TimeoutError):
                if n == retries:
                    return "잠시 후 다시 시도해 주세요"
                await asyncio.sleep(min(2 ** n * 0.05, 1) * random.random())

async def main():
    random.seed(1)
    prompts = ["a", "b", "a", "c", "a", "b"] * 3
    res = await asyncio.gather(*(ask(p) for p in prompts))
    print(len(prompts), "요청 / 업스트림 호출", calls, "/ 캐시 항목", len(cache))
    print(sorted(set(res)))
asyncio.run(main())
```

실행 결과는 이랬다.

```
18 요청 / 업스트림 호출 40 / 캐시 항목 3
['answer(a)', 'answer(b)', 'answer(c)', '잠시 후 다시 시도해 주세요']
```

요청 18개에 서로 다른 질문은 3개뿐인데 업스트림 호출은 40번이었다. 이유는 두 가지다. 가짜 함수가 자주 실패해서 재시도가 붙었고, 같은 질문 여러 개가 동시에 들어오면 아직 캐시에 값이 없으니 전부 업스트림으로 나갔다. 이걸 캐시 스탬피드라고 부른다. 이 코드는 그걸 막지 않는다. 막으려면 같은 키의 진행 중인 호출을 하나로 합치는 장치가 필요하다. 또 재시도를 다 쓴 요청은 안내 문구를 돌려주는데, 그 문구가 결과 집합에 섞여 나온 것도 보인다. 실제 서비스에서는 이걸 캐시에 넣으면 안 된다(위 코드는 성공만 캐시한다).

지연 시간·확률은 가짜 값이라 실제 API 동작과 무관하다. 구조가 동작하는지 보는 용도다.

</details>

<details>
<summary>자세한 풀이: 오류 코드 표</summary>

Anthropic 오류 문서에서 옮긴 요약이다.

| 코드 | 의미 | 다시 보내면 |
|---|---|---|
| 400 | 요청 형식·내용 문제(내가 정한 지출 상한 도달도 여기) | 소용없음 |
| 401 / 403 | 키 문제 / 권한 없음 | 소용없음 |
| 413 | 요청이 너무 큼 | 소용없음 |
| 429 | 한도 초과 또는 월 지출 상한 | `retry-after` 있으면 그만큼 기다림, 없으면 소용없을 수 있음 |
| 500 | Anthropic 내부 오류 | 지수 백오프로 재시도 |
| 504 | 처리 중 타임아웃 | 스트리밍 사용 검토 |
| 529 | API 과부하 | 잠시 후 재시도 |

모든 응답에는 `request-id` 헤더가 있고, 오류 본문에도 `request_id`가 들어 있다. 지원팀에 문의할 때 쓰라고 하니 로그에 같이 남겨 두는 게 좋다.

## 6. 비용 제어와 기록

요청마다 토큰이 곧 돈이라, 서버 로그에 요청 수만 남기면 부족하다. 응답에 사용된 입력·출력 토큰 수가 오니 그걸 사용자·기능별로 남겨야 비용이 어디서 나가는지 보인다. 캐시 히트 여부는 응답의 `cache_creation_input_tokens`, `cache_read_input_tokens`가 0이 아닌지로 확인한다고 문서에 적혀 있다.

제어 수단은 대략 이런 것들이다.

- 사용자별·요금제별 일일 토큰 상한을 서비스에서 직접 건다.
- 싼 질문에는 작은 모델, 어려운 질문에만 큰 모델을 쓰도록 나눈다.
- 콘솔에서 지출 상한을 내가 직접 낮춰 둔다(월 상한을 넘기 전에 막는 안전장치).
- 실시간이 필요 없는 일은 배치로 돌린다.

원가를 계산하는 법은 [AI 서비스 원가 구조](#/post/app-cost)에 따로 있다. 서버를 늘려서 풀 수 있는 병목은 [오토스케일링과 확장](#/post/infra-autoscaling)에서 볼 수 있지만, LLM 호출은 늘려도 업체 한도가 그대로라서 서버 대수와 처리량이 비례하지 않는다. 이 점이 일반 서비스와 제일 다르다고 느꼈다.

## 흔한 오해

- 429가 오면 무조건 기다렸다 재시도하면 된다: 월 지출 상한 때문에 온 429는 `retry-after`가 없고 계속 실패한다.
- 스트리밍이면 오류는 상태 코드로 알 수 있다: 200을 받은 뒤에도 스트림 안에서 오류 이벤트가 올 수 있다.
- 프롬프트 캐싱을 쓰니 응답 캐시는 필요 없다: 서로 막는 것이 다르다. 하나는 입력 비용을 줄이고 하나는 호출 자체를 줄인다.
- 서버를 늘리면 처리량이 늘어난다: 병목이 업체 한도라면 서버 대수는 상관이 없다.
- `max_tokens`를 크게 잡으면 한도를 많이 먹는다: 문서에 따르면 OTPM은 실제로 생성된 토큰만 센다. 다만 큰 값을 스트리밍 없이 쓰면 연결 문제가 생길 수 있다.

## 확인 못 함

- 실제 서비스에서 응답 캐시 적중률이 얼마나 나오는지, 캐시 키에 뭘 넣는 게 좋은지에 대한 공식 가이드.
- 연결·읽기 타임아웃을 몇 초로 잡아야 하는지 권장값(문서에서 못 찾음).
- 다른 업체(OpenAI, Google 등)의 한도·오류 규칙. 이 글은 Anthropic 문서만 읽었다.
- 위 예제는 가짜 API로 실행했고 실제 API 호출은 해 보지 않았다.
