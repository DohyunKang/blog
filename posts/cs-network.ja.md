ネットワークは層に分けて見ると整理できます。アドレスを IP に変え (DNS)、接続を確立し (TCP)、暗号化を設定し (TLS)、その上で要求と応答のやり取りを行います (HTTP)。この 4 つの段階が順次起こります。

## 層に分けて見る

ネットワークの話で最初に挙がるのが OSI 7 階層モデルと TCP/IP 4 階層モデルです。どちらも「役割ごとに通信を分割した図」であり、実際のインターネットで使用されているのは TCP/IP です。7 階層モデルは説明用としてより頻繁に使用されます。

| TCP/IP | OSI 対応 | 機能 | 例 |
|---|---|---|---|
| アプリケーション | 5~7 | アプリ同士の通信規則 | HTTP, DNS, TLS |
| 転送 | 4 | プロセス (ポート) 間での伝達 | TCP, UDP |
| インターネット | 3 | 宛先 IP までの経路探索 | IP |
| リンク | 1~2 | 隣接機器への伝達 | イーサネット、Wi-Fi |

TLS がどの層にあるかは議論があります。通常は転送層とアプリケーション層の間に描かれるため、表ではアプリケーション側に記載しました。

層を分ける理由は単純です。上位層は下位層がどのように伝達するかを知る必要はありません。HTTP は「信頼できる経路が存在する」と仮定して使用し、その経路が Wi-Fi なのか有線なのかは気にしません。各層のデータは下へ降りるごとにヘッダーが一つずつ追加されます (カプセル化)。

## IP アドレスに変換する DNS

人間は `example.com` と入力しますが、コンピュータは IP で通信するため、その間に翻訳が必要です。MDN によると、DNS はドメイン名や IP などの情報を管理する「階層的で分散型のネーミングシステム」とされています。電話番号帳が一つの場所にしかないのではなく、複数のサーバーで分担して保持しているという意味です。

Python ではこの翻訳は一行で済みます。

```python
import socket
print(socket.getaddrinfo('example.com', 443, proto=socket.IPPROTO_TCP)[0][4])
# ('104.20.23.154', 443)   <- 실행해서 나온 값, 시점·위치마다 다를 수 있다
```

この一行は自分の PC のリゾルバー (オペレーティングシステム) に質問を投げかけるものです。キャッシュにあれば即座に答えを出し、なければ上位の DNS サーバーに問い合わせるという仕組みです。

## 接続を確立する TCP

IP アドレスが分かれば接続を確立します。TCP はデータを送る前に双方で順序番号を合わせるプロセスがあり、これが 3-way handshake です。RFC 9293 を基準にした流れは以下の通りです。

1. クライアントが SYN を送信する (自身の初期順序番号 ISN を含む)。
2. サーバーが自身の SYN とともにクライアントの SYN に対する ACK を送信する (SYN-ACK)。
3. クライアントがサーバーの SYN に対する ACK を送信する。この時点から接続が ESTABLISHED となり、データやり取りが始まります。

```
클라이언트                    서버
   |---- SYN, seq=100 ------->|
   |<--- SYN, seq=300, ACK=101-|
   |---- ACK=301 ------------>|
   |====== 데이터 ============|
```

RFC の図にある数字 (100, 300) をそのまま使用した例です。実際の ISN は時刻と秘密鍵を組み合わせる方式で決定するため、適当に 100 から開始するわけではありません。

なぜ 3 回なのかは最初は不思議ですが、双方が各自の開始番号を伝え合い、相手が受信したことを確認する必要があるためです。2 回ではサーバーの番号がクライアントに届いたかどうかがサーバー側で分からないからです。

信頼性はこれに基づいています。バイト単位に番号があり、ACK は累積的に送信され、失われたパケットは再送されます。チェックサムでエラーを検出し、受信側が通知するウィンドウサイズで速度を調整します (フロー制御)。輻輳制御も必須ですが、定義は別の文書にあるため RFC には記載されていません。終了時には FIN をやり取りし、先に閉じた方は TIME-WAIT に 2×MSL 間留まります。RST で一度に切断する方式もあります。

<details>
<summary>TCP vs UDP の直接比較</summary>

同じ PC 内でソケットの 2 つの種類を使用しました。両方を実行して出力を確認しました。

```python
import socket, threading

# TCP: 연결(handshake)부터 맺고 주고받음
s = socket.socket(); s.bind(('127.0.0.1', 0)); s.listen()
port = s.getsockname()[1]
def srv():
    c, _ = s.accept()
    print('서버 받음:', c.recv(100)); c.sendall(b'pong'); c.close()
threading.Thread(target=srv).start()
c = socket.create_connection(('127.0.0.1', port))
c.sendall(b'ping'); print('클라 받음:', c.recv(100)); c.close()

# UDP: 연결 없이 그냥 던짐
u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u.bind(('127.0.0.1', 0))
t = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
t.sendto(b'hi', ('127.0.0.1', u.getsockname()[1]))
print('UDP:', u.recvfrom(100)[0])
```

出力は `サーバー受信: b'ping'`, `クライアント受信: b'pong'`, `UDP: b'hi'` でした。`create_connection` の呼び出し内部でハンドシェイクが発生し、コードには現れません。UDP は `connect`/`accept` そのものが存在しません。

</details>

## TCP と UDP の違いは何か

| | TCP | UDP |
|---|---|---|
| 接続 | 事前に確立する | なし |
| 順序・再送 | 保証する | なし (アプリが対応) |
| オーバーヘッド | 大きい | 小さい |
| 用途 | ウェブ、メール、ファイル | リアルタイム音声・映像、ゲームなど |

"UDP は速い"という話は半分正解です。再送と順序合わせを行わないため遅延は短くなるだけで、失われたパケットは単に消えてしまいます。リアルタイム通話では遅れて届いた音声を再度受け取る意味がないため UDP が適しています。UDP 上に順序や再送をアプリが直接実装する場合もあります。

## HTTP: 要求一つ、応答一つ

HTTP はアプリケーション層のプロトコルであり、MDN の説明によればクライアント - サーバー構造において要求は常にクライアントから先に行われます。メッセージの形式は以下の通りです。

```
GET / HTTP/1.1
Host: developer.mozilla.org
Accept-Language: fr
```

要求はメソッド、パス、バージョン、ヘッダー、(あれば) ボディで構成されます。応答はバージョン、ステータスコード (`200 OK` など)、ヘッダー、ボディです。[詳細 → API と REST](#/post/be-api-rest) でメソッドとステータスコードの使用方法を続編で見ていきます。

HTTP 自体はステートレスです。前のリクエストを記憶しないため、ログイン保持やカート機能などは、Cookie などのヘッダーを追加して実装します。この「ステートレス」な性質が、サーバーを複数台に拡張しやすくする要因でもあります。

転送方式はバージョンによって異なります。MDN の基準では、1.0 は各リクエストごとに TCP 接続を新規に開くため非効率であり、1.1 では接続を再利用する「持続接続（Keep-Alive）」が導入されました。2.x では 1 つの接続内で複数のメッセージをマルチプレックスします。HTTP/3 は UDP ベースの QUIC プロトコルの上に構築されていることで知られています。

## HTTPS は HTTP に TLS を重ねたもの

MDN は、TLS を「信頼できないネットワーク上で安全に通信するためのプロトコル」と定義しており、HTTP を TLS で保護したものが HTTPS です。提供される機能は主に 3 つに整理できます。

| 属性 | 意味 |
|---|---|
| 暗号化 | 途中で読み取ることができない |
| 完全性 | 途中で勝手に改ざんすることができない |
| 認証 | 接続したサーバーが本当にそのドメインのものか確認する |

ハンドシェイクでは TLS バージョンと暗号スイートを決定し、サーバーを認証するとともに秘密鍵を合意します。その後、HTTP ヘッダーと本文のすべてをその鍵で暗号化します。サーバー認証は証明書を用いて行います。証明書にはサーバー公開鍵が CA（認証局）の電子署名と共に含まれており、ドメインに鍵が紐付けられます。なぜ鍵・署名・ハッシュがそのような動作をするかは、[詳細 → 暗号化・ハッシュ・認証の基礎](#/post/sec-authn-crypto) で別途説明しています。

混乱しやすい点は順序です。接続はまず TCP で確立し（3-way ハンドシェイク）、その上で TLS ハンドシェイクを行い、ようやく暗号化された HTTP リクエストが送信されます。HTTPS と言っても TCP が不要になるわけではありません。

## アドレスバーに入力した後に起こること

これらを順に繋げると以下のようになります。

1. DNS を通じてドメイン名を IP アドレスに変換する。
2. その IP の 443 ポートに対して TCP 接続を確立する。
3. TLS ハンドシェイクを行い暗号化を確立する。
4. HTTP リクエストを送信し、レスポンスを受信する。
5. レスポンスの HTML を受け取り画面に描画する。[詳細 → ブラウザが画面を描画するプロセス](#/post/fe-browser-render)

サーバー側でこのリクエストがどこを通過するかは、[詳細 → リクエストが通る経路](#/post/infra-request-journey) と [詳細 → リクエストの処理フロー](#/post/be-request-flow) を参照してください。

<details>
<summary>よくある誤解</summary>

- "HTTPS ならサーバーは安全": TLS は転送経路を保護するだけで、サーバーコードの脆弱性まで防いでくれるわけではありません。これは一般論であり、別途文書で確認した記述ではありません。
- "HTTP は接続を維持する": HTTP メッセージ自体はステートレスです。接続を再利用すること（持続接続）と状態を記憶すること（セッション）は別の話です。
- "UDP は使えないプロトコル": 用途が異なるだけです。アプリ側で順序や再送を直接扱う方が適している場合があります。
- "3-way はセキュリティ手順": セキュリティではなく、両者のシーケンス番号を合わせるプロセスです。暗号化は TLS が担当します。
- "OSI 7 階層は実際の実装": インターネットは TCP/IP を基準に構築されており、OSI は説明モデルに近いものです。

</details>
