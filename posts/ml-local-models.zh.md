本地模型是指将模型文件下载到个人电脑并直接运行的方式，能否运行通常由显存（VRAM）计算决定。

## 什么是“在本地运行”

通过 API 使用的模型是在他人的服务器上运行。而在本地运行意味着将模型权重（文件）保存在自己的计算机上，并利用本地的 CPU 和 GPU 进行计算。即使没有互联网也能使用，且无需按 token 付费。但代价是只能运行电脑能够承载的模型大小。

模型本质上就是包含大量数字的表格（权重）。如果参数为 8B，则意味着有 80 亿个数字。若以 16 位（2 字节）存储，大约需要 16GB 空间；而在计算时，必须将数据加载到 GPU 显存（VRAM）中才能快速运行，这里便遇到了瓶颈。因此，通过减少数字所占位数来进行的“量化”成为了本地运行的核心技术。

相关概念详见 [LLM 是什么](#/post/ai-llm)，而服务器端的优化则在 [推理优化](#/post/ml-inference) 中讨论。

## 量化

量化是指将权重从 16 位改为 8 位、4 位等更短的整数进行存储。文件大小几乎与位数成正比地减小，但代价是精度略有下降。

llama.cpp 仓库支持 1.5·2·3·4·5·6·8 位整数量化。参考同一文档中 Llama-3.1-8B 的示例表格，情况如下：

| 类型 | 每参数位数 | 文件大小 |
|---|---|---|
| F16 | 16.00 | 14.96 GiB |
| Q8_0 | 8.50 | 7.95 GiB |
| Q6_K | 6.56 | 6.14 GiB |
| Q5_K_M | 5.70 | 5.33 GiB |
| Q4_K_M | 4.89 | 4.58 GiB |
| Q3_K_M | 4.00 | 3.74 GiB |
| Q2_K | 3.16 | 2.95 GiB |

命名规则如下：Q 后面的数字大致代表位数；K 表示使用独立缩放因子的块量化方式（K-quants）；末尾的 S/M/L 分别代表小/中/大。例如名称中包含"4 位”但实际上占用 4.89 位，这是因为包含了如缩放值之类的附加信息，导致实际占用的位数略多于标示值。

质量如何呢？llama.cpp 文档仅提到量化可能导致精度损失，通常使用 perplexity（困惑度）或 KL divergence（KL 散度）来衡量，但未提供具体数值。因此，本文不列出"Q4 会导致性能下降百分之几”这类数据。文档强调的注意点有两点：一是已经量化的模型再次量化会显著降低质量；二是使用 imatrix 文件可以减少损失。

<details>
<summary>用数字看量化做了什么</summary>

最简单的形式如下：对于每个块（例如 32 个数字），根据最大绝对值确定缩放因子 s。每个数字 w 通过 q = round(w / s) 存入 4 位整数中，计算时再乘以 s 还原为 q × s。由于每个块都有一个缩放因子，因此每参数位数会略大于 4 位。

K-quants 则更巧妙地在此基础之上，在块内设置子块。
</details>

## GGUF

GGUF 是 llama.cpp 系列使用的模型文件格式。根据 GGML 仓库文档，该格式将完整模型存入单个文件，实现了快速读取，并在添加新元数据的同时保持旧模型不损坏。

文件内部包含四个部分：

1. **头部**：魔数、版本、张量数量、元数据数量
2. **元数据**：架构、上下文长度、注意力·RoPE 设置、分词器、聊天模板
3. **张量信息**：名称、维度、类型、位置
4. **张量数据**：实际的权重（包含量化后的数据）

由于分词器和聊天模板也包含在文件中，因此只需一个文件即可运行。此外，张量位置按照固定间隔（默认 32 字节）排列，因此可以直接将文件映射到内存（mmap）中使用。文件名遵循 `模型名 - 大小 - 版本 - 量化.gguf` 的规则，大模型则会被分割为如 `00001-of-00003` 的形式。

## VRAM 计算方法

占用显存的主要有两部分：权重和 KV 缓存。此外，运行时还会额外占用一些工作空间。

权重 = 参数数量 × 每参数位数 ÷ 8。KV 缓存是随着对话变长而增大的内存，与上下文长度成正比。（[详见 → 上下文窗口与 token](#/post/ai-context-window)）

```python
def weights_gib(params_b, bpw):
    return params_b*1e9*bpw/8/2**30

def kv_gib(layers, kv_heads, head_dim, ctx, bytes_per=2):
    return 2*layers*kv_heads*head_dim*ctx*bytes_per/2**30   # 2 = K와 V
```

这是使用 Llama 3.1 8B（假设参数约 8.03B，32 层，KV 头数为 8，头维度为 128）运行得出的结果。结构中的数字并非通过打开模型卡片核实，而是基于已知信息估算，可能存在误差；但权重部分与 llama.cpp 文档中的表格（14.96 / 7.95 / 4.58 GiB）相符。

| 项目 | 大小 |
|---|---|
| 权重 F16 | 14.96 GiB |
| 权重 Q8_0 | 7.95 GiB |
| 权重 Q4_K_M | 4.57 GiB |
| KV 缓存，上下文 4,096 (f16) | 0.50 GiB |
| KV 缓存，上下文 32,768 (f16) | 4.00 GiB |
| KV 缓存，32,768 (8 位近似) | 2.12 GiB |

因此，对于 Q4_K_M 权重，4k 上下文大约需要 5GiB，可以放入 8GB 显存的显卡；若将上下文提升至 32k，仅 KV 缓存就会额外增加 4GiB。这意味着即使模型较小，增大上下文也可能导致显存不足。上述数字是通过 Python 直接计算得出的。实际用量会因运行时工作空间而略高于此数值。

KV 缓存也可以进行量化。根据 Ollama FAQ，`OLLAMA_KV_CACHE_TYPE` 的默认值为 f16；q8_0 大约使用一半内存，q4_0 则使用约四分之一。q8_0 的质量损失极小，而 q4_0 在上下文较长时可能会出现明显的质量下降。这些设置是在启用 Flash Attention 的情况下使用的。

## 当模型大于 VRAM 时

llama.cpp 支持混合推理，即结合 CPU 和 GPU 进行计算。部分层部署在 GPU 上，其余层由 CPU 在系统内存中处理。虽然可以运行，但 CPU 侧的层会成为瓶颈，导致速度明显下降。在 Ollama 中，可以通过 `ollama ps` 命令的 Processor 列查看是"100% GPU"还是像"48%/52% CPU/GPU"这样分配的情况。如果觉得慢，应首先检查此项。

## Ollama 与 llama.cpp

两者的关系可参考 [详细 → 开源分析：llama.cpp](#/post/repo-llama-cpp) 和 [详细 → 开源分析：Ollama](#/post/repo-ollama) 中的单独介绍。此处仅从用户角度列出差异。

| | llama.cpp | Ollama |
|---|---|---|
| 性质 | C/C++ 推理引擎 | 集模型加载、运行与服务器于一体的工具 |
| 支持的硬件 | CUDA, Metal, Vulkan, CPU 等 | 只要后端和设备支持即可使用 GPU |
| 配置方式 | 直接指定量化、层分配及选项 | 通过环境变量和模型配置进行调整 |
| 服务器 | 提供 OpenAI 兼容 API 服务器 | 本地 API 服务器 |

llama.cpp 仓库的目标是以最小化配置实现随处推理，并称 Apple Silicon 为"一等公民"进行了优化。Ollama 中常用的配置项根据 FAQ 如下：

- `OLLAMA_KEEP_ALIVE`：模型保留在内存中的时间。默认为 5 分钟；负数表示持续保留；0 表示响应后立即卸载
- `OLLAMA_NUM_PARALLEL`：每个模型可并发的请求数。默认为 1。内存占用与该值乘以上下文长度成正比
- `OLLAMA_CONTEXT_LENGTH`：默认上下文长度为 4096 令牌

默认上下文为 4096 这一点容易出错。如果插入长文档时前部被截断，原因可能就在于此。关于服务化部署的结构，请参见 [详细 → AI 服务架构](#/post/infra-ai-serving)。

## 速度与质量的权衡

- 降低比特数会使文件变小、占用内存更少，通常速度也会更快，但质量会下降。具体到何种程度合适，需根据模型和用途自行测试确定。
- 在显存相同的情况下，需在“大模型低精度”与“小模型高精度”之间做出选择。
- 增大上下文会导致 KV 缓存增加，一旦超出 GPU 容量，速度将显著下降。
- 将层迁移至 CPU 虽可运行，但会变慢。

若希望模型适配自己的数据，可在量化模型之上叠加 LoRA，相关内容见 [详细 → 微调](#/post/ml-finetuning)。

## 常见误解

- 量化会让模型变笨：虽然减少比特会带来一定损失，但在高位数区间（如 8 位附近）的损失已知较小。由于本文档未提供具体数值，此处亦不列举数字。
- 只要模型文件大小适配 VRAM 即可：实际上还需要 KV 缓存和工作空间，且上下文越长需求越大。
- 对已量化的文件进一步压缩也无妨：文档警告这样做可能导致质量大幅下降。正确的做法是从原始 16 位版本进行量化。
- GPU 无法运行就不能执行：并非如此，系统会以较慢的混合模式继续运行。
