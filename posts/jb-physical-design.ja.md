物理設計は、論理設計で確定したテーブルを実際のストレージおよび DBMS 上にどのように配置するかを決定する段階であり、インデックス・パーティション・分散 DB・データウェアハウスはすべて「データが増大しても高速に読み込み・管理するための手法」という一言でまとめられます。

## 設計のどの段階か

DB 設計は、要件分析 → 概念設計 (ER) → 論理設計 (テーブル・キー・正規化) → 物理設計 → 実装という順序で進みます。前述の [正規化とトランザクション](#/post/jb-normalization-transaction) は論理設計の側であり、ここから先は同じテーブルをどのような構造で保存するかという問題です。論理設計は DBMS が異なってもほぼ共通しますが、物理設計は使用する製品とハードウェアを見て決定します。

試験では、物理設計で行う作業に関する問題が出題されます。要約すると以下の通りです。

| 行うこと | 内容 |
|---|---|
| ストレージ構造 | テーブル・インデックスをどのファイルおよびスペースに配置するか |
| インデックス設計 | どのカラムに何种の種類のインデックスを作成するか |
| パーティション設計 | 大きなテーブルをどのような基準で分割するか |
| 非正規化 | 性能のために意図的に重複データを復活させるか |
| トランザクション・容量 | 同時使用量とデータ増加量の予測 |

非正規化とは、正規化で分割したテーブルをクエリ性能のために再度結合したり、カラムの重複を持たせたりする作業です。その代わりとして、入力や更新時に一貫性を自ら管理する必要があります。[SQL アプリケーション](#/post/jb-sql-basic) で見たように、JOIN が多すぎて遅くなる場合に検討する選択肢の一つです。

## インデックス

インデックスとは、テーブルから目的の行を素早く見つけるために別途作成しておくデータ構造です。インデックスがない場合、行を最初から順にスキャンする必要がありますが、ある場合は対数時間程度の時間で検索可能です。その代わりとして、より多くのストレージ空間を使用し、行の追加・修正・削除時にインデックスも同時に更新するため、書き込みが遅くなります。読み取りがメインのテーブルには有利ですが、書き込みが多いテーブルには負担になるというのが基本感覚です。より詳しい動作については [インデックス記事](#/post/db-index) に別途整理しています。

試験でよく出る分類は以下の通りです。

- 構造：B-ツリー（バランスド・ツリー）系が最も一般的であり、ハッシュインデックスもあります。範囲検索が必要な場合はツリー系が適切です。
- クラスター化インデックス：テーブルの行自体をインデックス順に保存します。テーブルあたり 1 つしか作成できず、範囲クエリに適しています。
- ノンクラスター化インデックス：ソートされた別々の構造が行を指し示します。複数作成可能です。
- 複合インデックス：カラムの順序が重要です。(都道府県、姓、名前) の順で作成したインデックスは都道府県で検索する場合は速いですが、姓だけで検索する場合は効率が低下します。条件に最初のカラムが含まれていないと不適切です。
- カバーインデックス：クエリに必要なカラムがすべてインデックスに含まれているため、テーブル行を読む必要がない場合です。

インデックスが効果的でない場合も問題として出ます。`LIKE '%abc'` のように先頭にワイルドカードが付くとインデックスを正しく利用できません。カラム値の重複が少ない場合にツリーインデックスが適しており、値が繰り返されるカラムにはビットマップインデックスが向いているとされています。

<details>
<summary>インデックス設計時の選択順序</summary>

1. 頻繁に使用されるクエリ・JOIN・ソートのカラム候補を選出する。
2. 値の多様性を確認する。ほぼ同じ値しかない場合は効果が小さい。
3. そのテーブルへの書き込み頻度を確認する。頻度が高い場合はインデックス数を減らす。
4. 複合インデックスの場合、条件に頻繁に登場するカラムを前面に置く。
5. 作成後、実行計画で実際に使用されているか確認する。

</details>

## パーティション

パーティションとは、大きなテーブル 1 つを論理的には 1 つとしておき、物理的には複数の断片に分ける手法です。PostgreSQL のドキュメントを基準にすると、分割方法は 3 つあります。

| 方式 | 基準 | 例 |
|---|---|---|
| レンジ (範囲) | 値の区間 | 日付ごとに月単位の断片 |
| リスト | 値を直接列挙 | 地域コード別 |
| ハッシュ | ハッシュ値を断片数で割った剰余 | 顧客番号を均等に分散 |

効果は以下の通りです。WHERE 条件にパーティション基準が含まれている場合、該当する断片のみを読み、残りはスキップします（パーティション・プリューニング）。古いデータは断片ごとに取り外したり削除したりできるため、大量の DELETE よりもはるかに高速です。頻繁に使わない断片は低速で安価なストレージへ移動することも可能です。同じドキュメントが指摘している点は、これらの利点は通常テーブルが非常に大きい場合に価値があり、無意味に多くのパーティションを分割しても良いわけではないということです。

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

上記は PostgreSQL 公式ドキュメントの例を簡略化したものです。構文は DBMS によって異なるため、試験では文法よりも「レンジ・リスト・ハッシュのうちどれで、なぜ使うか」を問うものと考えられます。

## 分散 DB

分散 DB はデータを異なる物理場所に分散して保存しつつ、ユーザーには単一のシステムのように見えるようにするデータベースです。同じデータセンター内にある場合もあれば、ネットワークで接続された離れた場所にある場合もあります。サーバー間で部品を共有しない緩やかな結合が特徴であり、ユーザーに近い場所でトランザクションを処理することで性能を向上できる点が長点として挙げられます。

パーティションとシャディングの違いは、行を分割する場合は水平分割、列を分割する場合は垂直分割と呼ばれる。複数のサーバーにわたって水平分割を行うのがシャディングである。パーティションが通常は 1 つの DB インスタンス内で分割されるものであるのに対し、シャディングはインスタンスを超えて複数のサーバーにデータを分散させる点が異なる。シャディングは複雑度が大きく増えるため、他の最適化手法では不足する際に採用するのが一般的なアドバイスだ。同じデータを複数のサーバーに複製して読み込みを増やす「レプリケーション」との違いについては [レプリケーションとシャディング](#/post/db-scaling) で詳しく説明している。

レプリケーションはコピーを最新の状態に同期させる作業が必要で、複雑かつ多くのリソースを消費する。一方、ある場所をオリジナルとして扱い、決められた時間に他の場所に単純に複製する方法（重複、duplication）もあるが、この場合はオリジナルのみを更新する。

シャディングの欠点は覚えるべきだ。SQL が複雑になりやすく、シャードの一つが故障すると全体のデータ整合性に影響が出る可能性がある。また、バックアップやスキーマの変更もすべてのシャードに合わせて行う必要がある。

## データウェアハウス

データウェアハウス（DW）は、複数の運用システムからのデータを収集し、分析目的のために蓄積しておくストレージである。ビル・インマンがまとめた 4 つの特徴は試験でよく問われる。

| 特徴 | 意味 |
|---|---|
| テーマ指向 | 業務処理単位ではなく、主要なテーマ（顧客・商品など）を中心に整理する |
| 統合 | 複数のシステムの名称・単位・コード表記を統一する |
| 時系列（時間変数） | 長期間の履歴を保存し、分析や予測に利用する |
| 非揮発性 | 一度蓄積したら読み取り専用とし、安易に変更や削除を行わない |

運用 DB（OLTP）と比較すると違いは明確だ。

| | OLTP | OLAP(DW) |
|---|---|---|
| 用途 | 短い入力・修正・削除を多く行う | 集計中心の複雑な照会を少なく行う |
| データ | 現在の詳細データ、通常は第 3 正規形 | 過去の履歴、多次元構造 |
| 性能指標 | 1 秒あたりのトランザクション数 | レスポンスタイム |

データを収集するプロセスが ETL である。ソースシステムから抽出（Extract）し、精製・変換（Transform）して、ウェアハウスに読み込み（Load）る。順序を変えてオリジナルを先に読み込み、ウェアハウス内で変換する方法は ELT と呼ばれる。データマートは、特定の部署やテーマに合わせて作られた小さなウェアハウスである。ソースが少なく作成しやすい。

ウェアハウスでよく使われるモデルがスタースキーマだ。中央にファクトテーブルがあり、周囲にディメンションテーブルが配置された形状をしている。ファクトには注文数量・決済金額などの測定値が入り、合計計算が可能だ。ディメンションは注文日・顧客・商品のようにその値を解釈する基準となる。1 つの注文ファクトに日付・顧客・商品のディメンションが付くように図示すると覚えやすい。

<details>
<summary>スタースキーマを図で表すと</summary>

```
        [날짜 차원]
             |
[고객 차원]--[주문 팩트]--[상품 차원]
             |
        [지점 차원]
```

ファクトにはディメンションを指すキーと数量・金額が入る。ディメンション側のテーブルは半正規化してジョイン回数を減らすことが多い。

</details>

## よくある混同点

- パーティションとシャディング：どちらも水平に分割するが、パーティションは通常 1 つの DBMS 内、シャディングは複数のサーバーにわたる。
- インデックスは多いほど良いと思いがちだが、書き込みが遅くなり、スペースを消費する。
- クラスター化インデックスはテーブルにつき 1 つだけ。行の物理的な順序を決めるため、2 つあることは不可能だ。
- DW は運用 DB をそのままコピーしたわけではない。テーマごとに統合し、履歴を蓄積するという点が異なる。
- 半正規化は設計ミスではなく、正規化を行った後にパフォーマンス向上のために選ぶ選択である。

## 問題解決のヒント

概念定義を問う問題は、上記表のキーワード（テーマ指向・統合・時系列・非揮発性、範囲・リスト・ハッシュ）をそのまま思い浮かべれば解ける。「この状況では何をすべきか」というタイプの問題は以下のように考える。日付基準で古いデータを頻繁に削除する場合は範囲パーティション、特定の列検索が遅い場合はインデックス、ジョインが多すぎて遅い場合は半正規化、分析用の集計が目的の場合はウェアハウスを採用する。試験の日程と形式は公式サイトで確認できる。
