コンテンツカレンダーの自動化は、テーマをストックし、日付に合わせて配置し、時期が来たら投稿するという 3 つの段階に分けられます。その中で人間が必ず見なければならないのは、テーマを選定することと、投稿直前の確認です。

## コンテンツカレンダーとは何か

コンテンツカレンダーとは、「いつ、どのチャンネルに、どんな記事を投稿するか」を事前に記した表のことです。エクセルの 1 つでも構いません。表があれば、当日朝に「今日何を投稿しようか」と悩む必要がなくなります。

自動化とは、この表を手作業で埋めていた部分を一部代替することです。ただし、単一の塊ではなく、分けて考える方が都合が良いのです。

| 段階 | 行うこと | 自動化の難易度 |
|---|---|---|
| 1. テーマプール | 投稿に使える素材をストックする | 収集は容易だが、選定は人間の役割 |
| 2. 配置 | 素材を日付・曜日・チャンネルに合わせて配置する | ルールさえ決めれば容易 |
| 3. 制作 | 記事・画像・動画を制作する | AI で下書きを作成し、人間が確認 |
| 4. 予約・投稿 | 決まった時間に投稿する | プラットフォームのポリシーにより異なる |
| 5. 記録 | 投稿されたか、反応はどうかを記録する | 容易 |

## テーマプール

テーマプールとは、まだ日付が割り当てられていない素材の倉庫です。1 行ずつ書き込み、状態（下書き、確定、公開済み）を付けておきます。素材は、普段自分が受ける質問、過去の記事の反応、シーズンスケジュールから生まれます。トレンドを自動で収集する仕組みについては別途整理しました。[詳細 → トレンド収集自動化](#/post/mk-trend-collect)

プールが空になるとカレンダーも止まってしまうため、プールの容量を「あと何週間分残っているか」で管理するのが実用的です。4 週間分未満に減ったら通知を受け取る程度で十分です。

ここで AI を活用できるのは素材を増やす部分です。1 つのテーマを与えて「そのテーマの変形 10 個」を受け取るようなものです。しかし、こうして得られる素材は似通ってしまう傾向があるため、人間によるフィルタリングの段階を残す必要があります。LLM は次の単語を確率で選ぶ方式であるため、平均的な素材が多く出力されます。[詳細 → LLM とは何か](#/post/ai-llm)

## 配置：ルールで日付に埋め込む

配置には AI は不要で、ルールさえあれば OK です。私が設定したルールは以下の通りです。

- 1 週間に 6 回、曜日ごとにカテゴリを固定する（ヒント、レビュー、製品紹介などの柱）。
- 同じテーマは直近 3 件のリスト内では再度登場させない。
- プールが空になったら再充填するが、最近使用したものは除外する。

これを Python で直接動かしてみました。テーマの例としてコーヒーに関する話題を 8 つ投入しました。

```python
from datetime import date, timedelta
import random

pool = ["커피 원두 고르는 법", "집에서 라테 만들기", "드립 vs 에스프레소", "원두 보관법",
        "디카페인 이야기", "그라인더 청소", "여름 아이스커피", "콜드브루 비율"]
slots = [(0, "팁"), (1, "후기"), (2, "팁"), (3, "제품"), (4, "후기"), (5, "팁")]  # 요일 0=월

def make_calendar(start, weeks, seed=1):
    rnd = random.Random(seed)
    topics = pool[:]
    rnd.shuffle(topics)
    cal, used = [], []
    for w in range(weeks):
        for dow, kind in slots:
            if not topics:                      # 풀이 비면 다시 채우되, 최근 3개는 뺀다
                topics = [x for x in pool if x not in used[-3:]]
                rnd.shuffle(topics)
            t = topics.pop()
            used.append(t)
            d = start + timedelta(days=7 * w + dow)
            cal.append({"date": d.isoformat(), "kind": kind, "topic": t, "status": "draft"})
    return cal

for r in make_calendar(date(2026, 11, 2), 2):
    print(r["date"], r["kind"], r["topic"], r["status"])
```

実行すると、2 週間分の 12 行が出力されました。

```

2026-11-03 후기 디카페인 이야기 draft
2026-11-04 팁 커피 원두 고르는 법 draft
2026-11-05 제품 콜드브루 비율 draft
2026-11-06 후기 그라인더 청소 draft
2026-11-07 팁 집에서 라테 만들기 draft
2026-11-09 팁 여름 아이스커피 draft
2026-11-10 후기 원두 보관법 draft
2026-11-11 팁 그라인더 청소 draft
2026-11-12 제품 콜드브루 비율 draft
2026-11-13 후기 커피 원두 고르는 법 draft

```

最初はプールが空だった時のリストをそのまま再充填してしまい、同じテーマが連続して 2 日目に登場する事態になりました。上記のコードはその問題を修正したものです。こうした些細なルールが一つ欠けても、カレンダーはたちまち不自然になってしまいます。

## 制作：反復可能なフローを作る

カレンダーの各行を「下書き → 確認 → 確定 → 公開済み」という状態遷移にしておけば、制作工程は行単位で流れていきます。制作段階では AI にテーマとカテゴリを与えて下書きを受け取ります。結果を JSON などの決まった形式で受け取っておけば、次の工程（予約）でそのまま利用できます。[詳細 → 構造化出力 (JSON・スキーマ)](#/post/ai-structured-output)

短い動画の場合には別途制作パイプラインが必要です。[詳細 → ショートフォーム自動化パイプライン](#/post/mk-shortform-pipeline)

下書きが蓄積される速度が投稿速度を上回ると、確認工程がボトルネックになります。自動化しても最終確認は人間が行うように設定しました。

## 予約と投稿

時期が来たら投稿する部分は、大きく 2 つに分かれます。プラットフォーム側が予約機能を提供する場合と、自分が時間に合わせて API を呼び出す場合です。

公式ドキュメントを確認した内容のみ記載します。

- Instagram (Meta) コンテンツ投稿 API: プロフェッショナルアカウントである必要があり、2 つのステップで投稿します。まず `/<IG_ID>/media` でコンテナを作成し、次に `/<IG_ID>/media_publish` で投稿します。メディアは投稿時点ですでに公開されたアドレスにある必要があります。1 日 100 個まで API で投稿可能と記載されていますが、同じドキュメントのカラセル部分には 50 個という記述もあり、矛盾しています。
- YouTube Data API `videos.insert`: リクエスト本文の `status.publishAt` で公開予約時刻を指定できます。時刻形式については今回読んだページでは詳しく出てきませんでした。

プラットフォームごとに API の許容範囲や審査が異なるため、カレンダーに「このチャンネルは API 投稿、あのチャンネルは手動投稿」と混在させるのが一般的ではないでしょうか。すべてのチャンネルを完全に自動化しようとする考えは断念し、心が楽になりました。

## 繰り返し実行は何で動かすか

「毎日朝 9 時にその日の行を探して投稿する」という動作を実行する方法は主に 3 つあります。

| 方法 | 特徴（文書で確認した内容） |
|---|---|
| n8n Schedule Trigger | 秒・分・時・日・週・月単位または cron で設定。ワークフローを保存して公開 (publish) しないと起動しない。タイムゾーンはワークフロー設定で指定し、指定がない場合はインスタンスのタイムゾーンを使用する |
| GitHub Actions `schedule` | cron の 5 カラム、最小間隔は 5 分。負荷が高ければ遅延したり一部のタスクが破棄されたりすることがあり、デフォルトのタイムゾーンは UTC。デフォルトブランチでのみ実行され、公開リポジトリは 60 日間活動がないと自動的に停止する |
| ローカル PC のタスクスケジューラー | 無料だが、PC が起動している必要がある |

GitHub Actions の「一部のタスクが破棄される可能性がある」という点が目についた。必ず準時でアップロードが必要な作業の場合、一度見逃した際に再試行する仕組みが必要だ。このような再試行とキューは別途整理した。[詳細 → 非同期処理とメッセージキュー](#/post/be-async-queue)

n8n 側も見逃した実行をどう扱うかを決める設定（スキップがデフォルト）があった。どちらの場合でも「見逃した際にどうするか」を事前に決めておくことが核心だった。

## ツールとコスト

コストは 2 つの箇所から発生する。制作時に使う AI の呼び出し料と、動かすサーバー・ツールの費用だ。

AI の呼び出し料は、文字数 ×（入力トークン + 出力トークン）× 単価で計算する。週に 6 回、1 ヶ月で約 26 回なら呼び出し回数も 26 回前後なので、小さなモデルでも負担は小さい。計算方法は別途ある。[詳細 → AI サービスのコスト構造](#/post/app-cost)

動かす側は規模が小さい場合は無料枠（GitHub Actions のスケジュールやローカル PC）から始めることができる。

## 自作する場合

私が作るならこの順序で始めるだろう。

1. スプレッドシートの 1 つにテーマリスト（テーマ、タイプ、ステータス）を作成する。
2. 上記のようなバッチスクリプトで 2〜4 週分を埋め、人が確認して削除する。
3. 下書きの生成は AI に任せて、結果を同じ表の「下書き」欄に入れる。
4. 公開は最初は手動で行い、1 チャンネルずつ API で移行する。
5. 投稿後にアクセス数や反応を同じ表に記録し、次のバッチに反映する。[詳細 → 成果ダッシュボードの作成](#/post/mk-dashboard)

## よくある誤解

- カレンダーを自動化すればコンテンツも自動的に良くなる：自動化はアップロード作業を減らすだけで、素材の質は変わらない。
- 予約機能があれば完全自動化：審査、トークン切れ、投稿失敗などの例外が残る。
- 多く投稿するほど良い：レビュー時間がボトルネックなら、数を増やすよりも確実に数本上げる方が長続きする。

<details>
<summary>詳細な解説：ステータス値とエラー処理</summary>

カレンダーの 1 行にステータス列を設ければエラー処理が容易になる。例えば `draft → approved → scheduled → posted` のように進み、途中で失敗したら `failed` と失敗理由を記す。朝の実行機は今日の日付で `approved` のものだけを拾って投稿し、成功すると `posted` に変更する。同じ行を 2 回投稿しないよう、投稿前に `scheduled` にしてロックすることで重複を防ぐ。

実行機が 1 日遅れた場合への備えとして、「今日より前の日付だがまだ approved の行」も一緒に探して通知を送ることもできる。自動的に後からでも投稿するかどうかはチャンネルの性質に合わせて決めるのが適切だ。この部分は設計の話であり、実際に動かしてみたわけではない。

</details>
