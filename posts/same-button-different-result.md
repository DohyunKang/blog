오늘도 자동화 앱을 만졌다. 큰 사고는 없었는데, 작은 어긋남이 세 번 있었고 셋 다 이름이 있는 개념이더라.

## 같은 버튼, 다른 결과

먼저 판단을 받고, 그 판단으로 다음 단계를 시작하는 흐름이 있었다. 그런데 두 번째로 눌러도 다음 단계로 안 가고 판단만 다시 하더라. 원인은 캐시 키였다. 앱은 「이 입력으로 이미 판단했나」를 입력값 몇 개를 이어 붙인 키로 확인했는데, 판단할 때 입력과 지금 입력칸의 글자가 조금 달랐다. 사람 눈에는 같은 주제인데, 키로는 다른 요청이었다.

캐시나 메모이제이션을 쓸 때는 키에 뭘 넣을지가 거의 전부인 것 같다. 너무 많이 넣으면 같은 일을 매번 새로 하고, 너무 적게 넣으면 다른 일인데 옛 결과를 돌려준다. 이번에는 「지금 화면에 있는 결과로 진행」을 따로 두어서 키 비교를 건너뛰게 했다.

## 어느 쪽을 먼저 쓸까

음성을 글자로 바꾸는 단계는 로컬 모델과 외부 API 둘 다 쓸 수 있었다. 나는 로컬이 기본이라고 알고 있었는데, 실제 코드는 API를 먼저 쓰고 실패하면 로컬로 내려가고 있었다. 문서와 코드가 서로 다른 말을 하고 있었던 거다.

폴백은 순서가 곧 정책이다. 로컬 먼저면 돈이 안 들고 데이터가 밖으로 안 나가지만 느릴 수 있다. API 먼저면 빠르지만 비용이 생긴다. 어느 쪽이 맞는지는 상황마다 다르고, 정했으면 문서에 적힌 것과 코드가 같은지 한 번은 직접 봐야 한다. 단일 원본이 두 개가 되는 순간이 이런 데서 생긴다.

## 하루에 한 번의 기준

자동 실행 주기도 다시 정했다. 처음엔 「첫 실행 뒤 하루 간격으로」였는데, 이러면 기준점이 첫 실행 시각에 묶여서, 한 번 늦게 돌면 그 뒤가 전부 밀린다. 그래서 「매일 정해진 시각 이후 하루 한 번」으로 바꿨다. 크론처럼 달력 시각에 거는 방식이다.

간격 기준과 달력 기준은 비슷해 보이는데, 밀림을 대하는 방식이 다르다. 달력 기준은 시간대도 같이 정해야 한다. 서버 시계와 내 시계가 다르면 「자정」이 엉뚱한 시각이 된다.

셋 다 코드는 몇 줄이었는데, 찾는 데는 그보다 오래 걸렸다.
