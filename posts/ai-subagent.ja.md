サブエージェントは、メインエージェントが一部のタスクを切り出して別のコンテキストで実行させ、結果の要約のみを受け取る構造ですが、タスクが並列化され、結果が要約で十分である場合にのみメリットがありました。

## まず簡単に言うと

1 つのエージェントが一人で作業すると、読んだファイル、検索結果、ログなどがすべてそのエージェントの会話履歴に蓄積されます。[コンテキスト](#/post/ai-context) がすぐに重くなります。そのため、「この部分は別のエージェントが別途調査して結論だけ教えて」という方式が生まれました。受け持つ方をサブエージェントと呼び、このようなエージェント同士が協力する構造全体をマルチエージェントと呼びます。人間のチームに例えると、リーダーが調査した内容をメンバーに任せてレポート 1 枚だけ受け取るのと似ています。ただしこれは比喩であり、実際にはモデルの呼び出しが 1 つ増えるだけです。

[エージェントループ](#/post/ai-agent-loop) がツールを呼び出して回る構造であれば、サブエージェントはそのループ内で「別のループを開始するツール」として使われることが多いです。ツール呼び出し自体は [ツール使用](#/post/ai-tool-use) の記事で別途整理しています。

## 原理：コンテキストの切り分け

Anthropic のドキュメントが説明するサブエージェントは以下の通りです。

- それぞれ独自のコンテキストウィンドウ、システムプロンプト、ツール権限、権限設定を持ちます。
- メイン対話の履歴を見ることはできません。メインから作業を要約した委譲メッセージを受け取るだけです。
- 完了すると最終結果のみがメインに戻ります。途中で読んだファイルの内容や検索結果はメインには流入しません。
- 使用量制限はメイン対話と共有されます。別途無料枠はありません。

核心となるのは最後の 2 点です。乱雑な中間処理はサブエージェントのウィンドウ内で終了し、メインは結論のみを受けます。そのため [コンテキストウィンドウ](#/post/ai-context-window) が埋まりにくくなります。これは [圧縮](#/post/ai-compaction) と目的は同じですが方法が異なります。圧縮はすでに蓄積されたものを減らすものであり、サブエージェントは最初からメインに蓄積させないという点です。

Anthropic のコンテキストエンジニアリング記事では、サブエージェントの結果を 1,000〜2,000 トークン程度の要約で受け取る旨も書かれており、これも同様の文脈です。この数値は以前の記事から引用したものです。

## 並列化とオーケストレーター・ワーカー

Anthropic の「Building effective agents」では、似ているように見える 2 つのパターンを区別しています。

| | 並列化 | オーケストレーター・ワーカー |
|---|---|---|
| 分割主体 | コードで事前に定義済み | 中央モデルが入力を見てその場で決定 |
| サブタスク | 事前に定義済み（セクション分割、同じ作業を複数回実行して投票など） | 事前に予測が難しい |
| 適した用途 | 独立した断片、速度重視 | 複数のファイルを修正するコーディングのような作業 |

サブエージェントの構造はほとんど右側（オーケストレーター・ワーカー）です。オーケストレーター（リーダー）がタスクを分割し、ワーカー（サブエージェント）に任せています。ワーカー同士を同時に実行すれば並列化効果も同時に得られます。

Anthropic が執筆したマルチエージェントリサーチシステムの記事では具体的な数値が出ています。リードエージェントは Claude Opus 4、サブエージェントは Claude Sonnet 4 で構成され、同じ内部リサーチ評価において Opus 4 単独よりも 90.2% も性能が向上しました。メリットは、多くの分岐を広く探索する必要がある質問（breadth-first）で大きかったです。リードが 3〜5 つのサブエージェントを同時に起動し、各サブエージェントも 3 つ以上のツールを同時に呼び出すことで、複雑なクエリの調査時間が最大 90% 削減されたそうです。どちらも Anthropic 内部の評価であり、私が再現したものではありません。

## コスト：これが最も重要でした

同じ記事のトークン数値は以下の通りです。

| 構造 | チャットとの比較（トークン） |
|---|---|
| エージェント | 約 4 倍 |
| マルチエージェント | 約 15 倍 |

BrowseComp 評価では、トークン使用量が性能差の 80% を説明したそうです。ツール呼び出し数とモデル選択を合わせると 95% です。これを逆説的に読むと、マルチエージェントが良くなる理由の相当部分は「より多くのトークンを消費しているから」と言えるということです。構造が賢いからではなく、より多く読み込み、より多くの試行を行った結果良くなった可能性があります。これは記事の結論ではなく、読みながら浮かんだ推測です。記事も、作業の価値が増えたトークンコストを許容できなければならないと述べています。

[AI コスト](#/post/app-cost) の観点では以下のように整理できます。サブエージェントを 1 つ追加すると、そのサブエージェントの入力・出力トークンのすべてが料金となります。メインコンテキストが減った分を節約するのではなく、新たに書き込むものです。[トークンを節約する方法](#/post/claude-tokens) でもこの点が最初に挙げられます。ただし、各サブエージェントで異なるモデルを指定できるため（Claude Code ドキュメント基準の `model` フィールドに sonnet, opus, haiku, fable、全モデル ID, inherit）、単純な調査は小さなモデルに任せるような節約が可能です。

## 使わないほうがいい場合

Anthropic の記事に合致しない場合は、直接記述します。すべてのエージェントが同じコンテキストを必要とするか、互いに依存関係が強い場合です。コーディングはリサーチよりも並列に分けられる部分が少なく、エージェントがリアルタイムで調整することはまだ未熟だと言われています。

反対側の論文も読みました。Cognition の"Don't Build Multi-Agents"では 2 つの原則を挙げています。

- コンテキストを共有せよ。個別のメッセージではなく、エージェント全体の履歴（trace）を。
- 行動には暗黙的な決定が含まれている。決定が衝突すると結果が悪化する。

例として Flappy Bird の複製があります。サブエージェントの一つはスーパーマリオのような背景を作成し、もう一つはゲームにふさわしくない鳥を作成します。最後のエージェントはこの 2 つを合わせる必要があります。両方に元のタスクの説明を与えても完全に解決しないと言われています。実際の対話は複数のターンであり、ツール呼び出しが解釈を変らせるためです。代替案として単一スレッドのエージェント（コンテキストが継続する）、履歴を削減する別圧縮モデル、そして制限されたサブエージェントが挙げられています。Claude Code のサブエージェントは主に明確な質問に答え、コードを並列で書かないため衝突が少ないとこの論文は評価しています。

2 つの記事が同じことを言っているわけではありません。Anthropic は正しいこと（調査）にはマルチエージェントの方が大幅に優れているとし、Cognition は書き込み・決定が絡むことには注意するよう呼びかけています。私は「読み取り・調査は分割し、書き込み・決定は一元化」という程度に受け入れました。2 つの記事を読み、自分で出した要約です。

文書で整理された選択基準も同様です。

- サブエージェント：出力が長すぎてメインに置きたい場合、ツール権限を制限したい場合、タスクが独立していてサマリーに戻せる場合。
- メイン対話：頻繁にやり取りして調整が必要な場合、複数のステップでコンテキストを多く共有する場合、素早い小さな修正の場合、遅延が重要である場合（サブエージェントは空の状態から開始するため、文脈を集める時間がかかります）。

## 委任時に発生する問題

委任説明が不十分だとタスクが重複します。Anthropic の記事にはこのような事例があります。あるサブエージェントは 2021 年の自動車半導体危機を調査し、他の 2 つは 2025 年のサプライチェーンを同様に調査しました。各サブエージェントに対して目標、出力形式、出典指示、作業範囲を明確に与える必要があるという結論です。これはサブエージェントに渡す [プロンプト](#/post/ai-prompt) がすべてだという意味です。サブエージェントはメインの対話を見ることができないためです。

もう一つは規模調整です。初期バージョンでは単純な質問に対しても 50 つのサブエージェントを起動したと言われています。解決策はルールをプロンプトに埋め込むことでした。単純な事実検索にはエージェント 1 つにツール呼び出し 3〜10 回、直接比較にはサブエージェント 2〜4 つそれぞれ 10〜15 回、複雑な調査には 10 個以上使用できるという具合です。

## よくある誤解

- サブエージェントを使えばトークンが減る：メインコンテキストは減りますが、全体トークンは増えることが多いです。前述の 15 倍という数値はその例です。
- エージェントが多いほど賢い：タスクが依存関係がある場合はむしろ衝突します。
- サブエージェントも私の対話を知っている：通常のサブエージェントは知りません。メイン対話を継承するのはフォーク（fork）方式です。文書にはフォークが親対話を継承するとだけ出ています。
- サブエージェントは無制限にネストする：文書によるとデフォルトはメインの下 3 階までで、環境変数で変更可能です。並列実行のデフォルト上限は 20 です。

<summary>詳細な解説：Claude Code サブエージェントファイル構造</summary>

文書に出てくるサブエージェントは YAML フロントマターが付いたマークダウンファイルであり、本文がシステムプロンプトになります。必須フィールドは `name` と `description` のみです。Claude は `description` を見ていつ委任するかを決定します。名前を直接呼ぶか `@` で言及することもでき、`claude --agent <name>` でセッション全体をそのエージェントで回すこともできます。

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices. Use proactively after code changes.
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

上記の例は文書にあるものをそのまま移したもので、私が実行したものではありません。

ツール制限は `tools`（許可リスト）と `disallowedTools`（禁止リスト）で行います。禁止が先に適用され、両方に記載されたツールは除外されます。内蔵サブエージェントには Explore（読み取り専用、コード検索）、Plan（読み取り専用、計画モード調査）、general-purpose（すべてのツール）があります。保存場所が重複する場合、組織管理設定 > `--agents` フラグ > プロジェクト `.claude/agents/` > ユーザー `~/.claude/agents/` > プラグインの順に優先されます。モデルは呼び出し時に指定した値、ファイルの `model`、環境変数 `CLAUDE_CODE_SUBAGENT_MODEL`、メインモデルの順で決定されます。

サブエージェントごとに新しいインスタンスが作成されます。続行させるには `SendMessage` でエージェント ID または名前を指定して再開します。再開されたエージェントは全体の履歴を保持します。Explore と Plan は一度使えば終わりなので再開できないと文書にあります。

[ハーネス](#/post/ai-harness) の観点から見ると、サブエージェントを起動して結果を受け取り、リミットを守ることはモデルではなく、この外側のコードの役割である。この接続は私が付けた解釈です。
