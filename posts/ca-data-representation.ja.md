コンピュータには 0 と 1 のみがある。数字も文字も画像もすべてビットの束であり、同じビットの束でも「整数として読む」「小数として読む」「文字として読む」という約束によって異なる値となる。この文章では、その約束のうち整数（2 の補数）、実数（浮動小数点）、文字（ユニコードと UTF-8）の 3 つを Python で確認しながら見ていく。ビットの束を CPU がどのように取り出して計算するかは、[CPU と命令語](#/post/ca-cpu) にて続きます。

## ビットの束と約束

8 ビットは 256 パターンの組み合わせを生み出します。このパターンに意味を付与する方法がデータの表現です。同じ `11111011` が符号なし整数では 251 であり、符号付き整数（2 の補数）では -5 です。ビット自体は変わらず、解釈だけが異なります。

| 読み方の約束 | `11111011` の値 |
|---|---|
| 符号なし整数 | 251 |
| 2 の補数整数 | -5 |
| 文字コード (Latin-1 など) | コード表に従って異なる文字 |

したがって、ファイルを開いて文字が崩れるのはビットが壊れたのではなく、読み方の約束がずれているケースが多いのです。後述する文字エンコーディングで実際に作成してみます。

## 整数：2 の補数

負数を表現する方法のうち、現在ほぼすべての CPU が採用しているのが 2 の補数です。n ビットにおいて負の数 -x は、2 の n 乗から x を引いた値のビットパターンとして保存します。8 ビットの場合、-5 は 256 - 5 = 251 であり、2 進数では `11111011` です。Python では `n & 0xFF` で確認するとこのようになります。

```python
for n in (5, -5, -1, 127):
    print(n, format(n & 0xFF, '08b'))
# 5 00000101
# -5 11111011
# -1 11111111
# 127 01111111
print(int('11111011', 2) - 256)   # -5
```

最上位ビットが 1 なら負の数というルールは生じますが、それは単なる符号ビットではありません。最上位ビットの位値を -128 と考えればよいのです。`11111011` は -128 + 64 + 32 + 16 + 8 + 2 + 1 = -5 です。

2 の補数を使用する理由は、加算回路一つで符号付きの数と符号なしの数を同時に計算できるためです。減算は逆符号を加えることに変換されます。0 の表現も一つ (`00000000`) だけです。n ビットで表せる範囲は -2^(n-1) から 2^(n-1)-1 までであり、負の数の方が一つ多いです。8 ビットでは -128〜127 です。

範囲を超えるとオーバーフローが発生します。8 ビットで 127 に 1 を足すと `10000000` となり、これは -128 です。Python の整数は長さ制限がないため、直接マスクを適用して模倣する必要があります。

```python
x = (127 + 1) & 0xFF
print(x, x - 256 if x > 127 else x)   # 128 -128
```

C や Java などの言語の固定長整数で発生するオーバーフローはこの様子です。値が一周して反対側の端へ向かいます。

<details>
<summary>バイト順序（エンディアン）</summary>

整数が複数のバイトにわたる場合、どのバイトを先に配置するかという点も約束です。258 は `0x00000102` ですが、ビッグエンディアンは高位のバイトから、リトルエンディアンは低位のバイトからメモリに配置します。

```python
print((258).to_bytes(4, 'big').hex())      # 00000102
print((258).to_bytes(4, 'little').hex())   # 02010000
```

ファイルやネットワークを通じて数字をやり取りする際、両者が同じ順序で読み取るように合意しておく必要があります。ネットワークでのバイト送信に関するルールは [ネットワーク基礎](#/post/cs-network) にて続けます。
</details>

## 実数：浮動小数点

小数は整数よりも複雑です。限られたビットで非常に大きな数と非常に小さな数をすべて表現するため、科学記法のように符号・指数・仮数に分けて格納します。Python の `float` は IEEE 754 binary64（倍精度）であり、64 ビットをこのように使用します。

| 符号 | 指数 | 仮数 |
|---|---|---|
| 1 ビット | 11 ビット | 52 ビット |

値は `(-1)^符号 × 1.仮数 × 2^(指数-1023)` の形式です。1.0 と -2.5 のビットを抽出すると一致します。

```python
import struct
def bits(f):
    b = struct.unpack('>Q', struct.pack('>d', f))[0]
    s = format(b, '064b')
    return s[0], s[1:12], s[12:]

print(bits(1.0))
# ('0', '01111111111', '000...0')           지수 1023 → 2^0
print(bits(-2.5))
# ('1', '10000000000', '0100...0')          지수 1024 → 2^1, 1.25 × 2 = 2.5
```

1.0 の指数フィールドが `01111111111`(1023) であることから、バイアス (bias) が 1023 であることがわかります。-2.5 は符号 1、指数 1024(2^1)、仮数 `01` で 1.25 となり、1.25 × 2 の符号反転です。

### 0.1 が正確でない理由

10 進数の 0.1 は 2 進数で表現すると 0.000110011001100…のように無限に繰り返されます。仮数が 52 ビット（暗黙的な 1 を含むと 53 ビット）しかないため、どこかで切り捨てて最も近い値を保存します。Python の公式チュートリアルの説明によれば、保存されるのは 0.1 ではなく 3602879701896397 / 2^55 であり、1/10 よりわずかに大きい値です。Python が `0.1` と表示するのは、循環する最も短い 10 進表現だからです。

```python
from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False
```

バグではなく、表現方式の結果です。同じ計算をどの言語で行っても binary64 を使用すれば同じ結果が得られます。比較する際は `==` の代わりに許容誤差を用います。

```python
import math
print(math.isclose(0.1 + 0.2, 0.3))   # True
```

正確な 10 進計算が必要な場所（金銭の計算など）では、`Decimal` を文字列として作成して使用する手法があります。公式ドキュメントも会計などの用途には `decimal` モジュールの使用を推奨しています。

### 大きな数の傍らで消える小さな数

仮数の長さが固定されているため、数が大きくなるほど表現可能な値間の間隔が広がります。2^53(9007199254740992) からでは整数 1 も区別できません。

```python
print(2**53)                              # 9007199254740992
print(float(2**53) + 1 == float(2**53))   # True
print(1e16 + 1 == 1e16)                   # True
```

したがって、大きな数と小さな数を足すと、小さい方が消えてしまいます。多くの数を足す合計計算において順序が結果を変える理由はこれです。

<details>
<summary>特殊な値</summary>

指数フィールドがすべて 1 の場合、無限大または NaN を示します。範囲を超えると `inf` になり、`inf - inf` などの計算は `nan` になります。NaN は自分自身とさえも等しくありません。

```python
import sys
print(sys.float_info.max * 2)         # inf
print(float('inf') - float('inf'))    # nan
nan = float('nan'); print(nan == nan) # False
print(5e-324, 5e-324 / 2)             # 5e-324 0.0
print(sys.float_info.epsilon)         # 2.220446049250313e-16
```

`5e-324` は表現可能な最小の正数であり、その半分は 0 になります。`epsilon` は 1.0 と次に大きい float の差です。
</details>

## 文字：コードポイントとエンコーディング

文字については混乱しないように 2 つの段階に分けて考える必要があります。まずユニコードが各文字に番号（コードポイント）を割り当てます。その後、エンコーディングはその番号をバイトに変換する規則を定めます。番号とバイト列は別物です。

ASCII は英語の文字と記号 128 個を 7 ビットに詰めた表でした。漢字のように文字数が多い文字は 1 バイトでは収まらないため、EUC-KR などの国別のエンコーディングが生まれ、これを一つの番号体系でまとめたのがユニコードです。現在の Web と Python 3 のデフォルトエンコーディングは UTF-8 です。

### UTF-8 は長さが異なります

UTF-8 はコードポイントのサイズに応じて 1〜4 バイトを使用します。RFC 3629 で定義された枠組みは以下の通りです。

| コードポイント範囲 | バイト数 | ビットパターン |
|---|---|---|
| U+0000 ~ U+007F | 1 | `0xxxxxxx` |
| U+0080 ~ U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 ~ U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 ~ U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

最初のバイトの先頭の 1 の数が全体の長さを示し、続くバイトは常に `10` で始まります。ASCII 範囲はそのまま 1 バイトなので、英語テキストでは ASCII と UTF-8 は同じです。

'가'(U+AC00) を確認してみましょう。コードポイント `1010110000000000` を 3 バイトの枠に埋めると `1110 1010`, `10 110000`, `10 000000` になります。

```python
ch = '가'
print(hex(ord(ch)))                                  # 0xac00
print(format(ord(ch), '016b'))                       # 1010110000000000
print([format(b, '08b') for b in ch.encode()])
# ['11101010', '10110000', '10000000']
print(ch.encode('utf-8').hex())                      # eab080
```

`eab080` は上記の 3 バイト (`ea` `b0` `80`) の二進数と等しいです。'A' は 1 バイト、'가' は 3 バイト、イモジ (U+1F600) は 4 バイトです。

```python
for ch in ('A', '가', '\U0001F600'):
    print(hex(ord(ch)), ch.encode('utf-8').hex(), len(ch.encode('utf-8')))
# 0x41 41 1
# 0xac00 eab080 3
# 0x1f600 f09f9880 4
```

### 文字数とバイト数は異なります

```python
s = '한글'
print(len(s))                       # 2   글자(코드 포인트) 수
print(len(s.encode('utf-8')))       # 6   UTF-8 바이트 수
print(len(s.encode('euc-kr')))      # 4   EUC-KR 바이트 수
```

データベースカラムの長さや API ボディサイズ制限がバイト基準か文字数基準かを確認する必要がある理由です。UTF-16 では '가' を 2 バイト、イモジを 4 バイト（サロゲートペア）で保存するため、同じ文字列でもエンコーディングによってサイズが異なります。

### 文字が壊れる瞬間

読み方の約束がずれると壊れます。韓国の UTF-8 バイトを Latin-1 で読むか、EUC-KR バイトを UTF-8 で読んでみます。

```python
s = '한글'
print(s.encode('utf-8').decode('latin-1').encode('unicode_escape'))
# b'\\xed\\x95\\x9c\\xea\\xb8\\x80'   Latin-1 글자 6개로 읽힘
print(s.encode('euc-kr').decode('utf-8', errors='replace').encode('unicode_escape'))
# b'\\ufffd\\u0471\\ufffd'            대체 문자(U+FFFD)가 섞임
try:
    b'\xea\xb0'.decode('utf-8')       # '가'의 3바이트 중 2바이트만
except Exception as e:
    print(type(e).__name__)           # UnicodeDecodeError
```

UTF-8 で読みながら規則に合わないバイトに出会えるとエラーが発生したり、代替文字 (�) が挿入されたりします。ファイルが途中で切断されていたりエンコーディングを間違えていたりすると見られる様子です。

<details>
<summary>同じ文字でもコードポイントが異なる場合</summary>

'é' は一つのコードポイント (U+00E9) であることもあれば、'e' の後に結合アクセント (U+0301) が付いた二つのコードポイントであることもあります。画面では同じように見えます。

```python
import unicodedata
print(len('é'), len('é'))              # 1 2
print('é' == 'é')                       # False
print(unicodedata.normalize('NFC', 'é') == 'é')   # True
```

検索や比較で文字列を正規化してから行う必要があるケースはこれによって生じます。
</details>

## 続けてみましょう

| 対象 | 約束 | 一言まとめ |
|---|---|---|
| 整数 | 2 の補数 | 加算回路一つで符号も処理、範囲を超えると一周する |
| 実数 | IEEE 754 | 符号・指数・仮数、ほとんどの 10 進小数は近似値 |
| 文字 | ユニコード + UTF-8 | 番号とバイトを別々に考える、文字ごとに 1〜4 バイト |

ビット数が決まっているために生じる限界（オーバーフロー、丸め誤差、バイト数の違い）はこの 3 つからすべて出てきます。こうして作られた値がレジスタからキャッシュ、メモリ、ディスクへどう移動するかは [メモリー階層とキャッシュ](#/post/ca-memory-hierarchy) で見てみましょう。

## よくある誤解

- 0.1 + 0.2 가 0.3 이 아닌 것은 파이썬의 문제가 아닙니다: 파이썬은 binary64 값을 그대로 표시할 뿐입니다. 정확한 10 진 연산이 필요하면 `decimal` 을 사용합니다.
- 음수는 맨 앞 비트만 1 로 바꾼 것입니다: 2 의 보수에서는 맨 앞 비트가 -2^(n-1) 의 자리값이라서 나머지 비트도 함께 달라집니다. -5 는 `10000101` 이 아니라 `11111011` 입니다.
- UTF-8 문자는 모두 3 바이트입니다: 영어는 1 바이트이고 한글이 대부분 3 바이트입니다. 1~4 바이트를 섞어 사용합니다.
- 글자 수가 곧 바이트 수입니다: ASCII 만 사용할 때만 같습니다. 한글 두 글자가 UTF-8 로 6 바이트였습니다.
- 한글이 깨지면 데이터가 손상된 것입니다: 비트는 그대로이고 읽는 인코딩만 틀린 경우가 많습니다.
