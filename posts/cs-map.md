CS·설계 기초는 범위가 넓어서 어디서부터 봐야 할지 막막하다. 그래서 일곱 가지 주제를 한 줄씩만 먼저 적고, 더 알고 싶은 건 아래 링크로 넘어가게 했다. 순서는 코드를 어떻게 나눌지(설계) → 코드가 돌아가는 바닥(네트워크, OS) → 만드는 과정(공학, Git) 순이다.

## 한눈에 보는 관계

```
설계(코드를 어떻게 나눌까)
  절차지향 / 객체지향  →  SOLID(바뀔 때 덜 깨지게)  →  디자인 패턴(자주 만나는 문제의 이름표)

바닥(코드가 돌아가는 곳)
  네트워크(DNS → TCP → TLS → HTTP)    운영체제(CPU·메모리를 나눠 쓰게 하는 관리자)

과정(여럿이 만들고 고쳐 나가기)
  소프트웨어 공학(방법론·요구사항·UML·테스트)  →  Git(커밋 스냅샷과 브랜치)
```

## 1. 코드를 어떻게 나눌까

**절차지향과 객체지향**: 같은 문제를 코드로 나누는 기준이 다르다. 절차지향은 함수(할 일)로, 객체지향은 객체(데이터와 그걸 다루는 동작)로 쪼갠다. "무슨 순서로 할까"에서 시작하느냐, "이 데이터를 누가 책임질까"에서 시작하느냐의 차이였다.
[자세히 → 절차지향과 객체지향](#/post/cs-procedural-oop)

**SOLID 원칙**: 객체지향 설계에서 코드가 바뀔 때 덜 깨지게 하는 다섯 가지 기준이다. 규칙집이라기보다 코드가 이상할 때 이유를 찾는 체크리스트로 읽는 게 편했다.
[자세히 → SOLID 원칙](#/post/cs-solid)

**디자인 패턴**: 객체지향 설계에서 자주 만나는 문제와 그 풀이에 이름을 붙여 모아 둔 것이다. 이름과 분류만 보면 헷갈리지만, 어떤 상황에 쓰는지와 같이 보면 덜 헷갈렸다.
[자세히 → 디자인 패턴](#/post/cs-design-patterns)

## 2. 코드가 돌아가는 바닥

**네트워크 기초**: 층을 나눠서 보면 정리된다. 주소를 IP로 바꾸고(DNS), 연결을 맺고(TCP), 암호화를 세우고(TLS), 그 위에서 요청과 응답을 주고받는다(HTTP). 이 네 단계가 순서대로 일어난다.
[자세히 → 네트워크 기초](#/post/cs-network)

**운영체제 기초**: CPU와 메모리 같은 한정된 자원을 여러 프로그램이 나눠 쓰게 해 주는 관리자다. 프로세스, 스케줄링, 가상 메모리, 동기화는 다 이 한 가지 일을 서로 다른 면에서 보는 이름이었다.
[자세히 → 운영체제 기초](#/post/cs-os)

## 3. 만드는 과정

**소프트웨어 공학 기초**: 코드를 잘 짜는 법보다 무엇을 어떤 순서로 만들고, 어떻게 확인하고, 어떻게 고쳐 나갈지를 다루는 분야다. 방법론, 요구사항, UML, 테스트, 형상관리를 큰 줄기만 훑었다.
[자세히 → 소프트웨어 공학 기초](#/post/cs-sw-engineering)

**Git**: 변경 내역을 쌓는 도구라기보다 커밋이라는 스냅샷을 이어 붙이고, 브랜치는 그중 하나를 가리키는 이름표라고 보면 머지, 리베이스, 충돌이 한 그림으로 정리된다.
[자세히 → Git 제대로 알기](#/post/cs-git)
