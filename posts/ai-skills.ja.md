スキルとは、特定の作業をこなすための方法（手順書、参考文献、スクリプトなど）を 1 つのフォルダに束ねておき、モデルが必要と判断した際にのみ読み込ませる仕組みです。常にコンテキストに載るのは名前と説明の数行だけです。

## スキルとは何か

Anthropic のドキュメントでは、スキルを「指示、メタデータ、選択的なリソース（スクリプト・テンプレート）を束ねた、ファイルシステムベースの再利用可能な資源」と紹介しています。エンジニアリング記事では、新人向けオンボーディングガイドを書くことになぞらえられています。

構造は単純です。1 つのフォルダに必ず `SKILL.md` が存在し、必要に応じて参考文献やスクリプトを隣に置きます。

```
pdf-processing/
  SKILL.md        # 메인 지침 (필수)
  FORMS.md        # 양식 채우기 가이드
  REFERENCE.md    # API 상세
  scripts/
    fill_form.py  # 돌려서 쓰는 도구
```

`SKILL.md` の先頭には YAML ヘッダー（`name`、`description`）があり、その下に本文が続きます。ドキュメントの例を簡略化すると以下のようになります。

```markdown
---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
---

# PDF Processing

## Quick start
(pdfplumber로 텍스트 뽑는 코드)

양식 채우기는 FORMS.md를 본다.
```

## 原理：段階的に読み込む

核心は、一度にすべてを読み込ませない点にあります。このアプローチは「プログレッシブ・ディスクロージャー（progressive disclosure）」と呼ばれ、3 つの段階に分けられます。

| 段階 | いつ載るか | トークンコスト（ドキュメント基準） | 内容 |
|---|---|---|---|
| 1. メタデータ | 開始時常に | スキル 1 つあたり約 100 トークン | `name`、`description` |
| 2. 本文 | スキルが使用される際 | 5k トークン未満 | `SKILL.md` の本文 |
| 3. リソース・コード | 必要な場合のみ | 読み込むまで 0 | 添付ファイル、スクリプト |

流れとしては以下のようになります。開始時にシステムプロンプトに各スキルの名前と説明が挿入されます。ユーザーがリクエストすると、モデルは説明を確認して適切なスキルがあるか選択します。あれば bash で `SKILL.md` を読み込み、本文が [コンテキスト](#/post/ai-context-window) に追加されます。本文に「形式は FORMS.md を参照してください」とある場合、その作業を行う際のみそのファイルを読み込みます。ドキュメントの例では PDF テキスト要約のリクエストであり、`FORMS.md` は読み込まれません。

スクリプトは読み込むのではなく実行します。ドキュメントによると、スクリプトコード自体はコンテキストには含まれず、実行結果のみが返されます。そのため、同じ作業を毎回コードで再実装するよりもトークン消費が少なく、かつ結果も一貫性があるとしています。

この構造のおかげで、多数のスキルをインストールしても負担は軽いです。ドキュメントでは「スキルが使用されるまでは名前と説明だけがコンテキストを占有する」と記載されています。一方でモデルは説明のみを見て選択するため、1 行の説明が事実上の入口となります。

## プロンプト・ツール・MCP と何が違うか

| | 役割 | コンテキストに載るタイミング |
|---|---|---|
| [プロンプト](#/post/ai-prompt) | 今回の対話の指示 | 毎回手書きする場合 |
| スキル | 作業手順・知識をフォルダで管理 | 説明は常に、本文は必要な場合のみ |
| [ツール呼び出し](#/post/ai-tool-use) | モデルが外部機能を実行する | ツールの定義が載り、呼び出されると結果が返る |
| [MCP](#/post/ai-mcp) | 標準方式で外部サーバーからツールを接続する | 接続されたツールの定義が載る |

ドキュメントでは、スキルを「対話単位で一度与えるプロンプトとは異なり、必要な時にロードされ、同じ案内を毎回繰り返さないようにするもの」と説明しています。ツールが「何ができるか」であれば、スキルは「その作業をどのように行うか」に近いと理解できます。ただし、この区別をドキュメントが厳格に定めたわけではなく、両方を併用するケースも多々あります（スキル本文で MCP ツールを呼び出すように案内するなど）。また、ドキュメント内でもスキル内で MCP ツールを使用する際は `サーバー名:ツール名` のようにサーバー名まで記載するよう案内されています。

## どこで使うか

Anthropic ドキュメントの基準では、スキルは複数の場所で利用可能ですが、方式が異なります。

- **Claude API**: `container` に `skill_id` を渡す必要があり、コード実行ツールの併用も必須です。自作のスキルは `/v1/skills` にアップロードし、ワークスペース全体で共有します。ネットワーク接続はなく、パッケージを新規インストールできません。
- **claude.ai**: 設定から zip ファイルとしてアップロードします。個人単位であり、組織全体の共有・管理は行えません。ドキュメント作成用の基本スキル（pptx, xlsx, docx, pdf）が用意されています。
- **Claude Code**: `~/.claude/skills/<名前>/SKILL.md`（個人用）または `.claude/skills/<名前>/SKILL.md`（プロジェクト用）に配置します。ネットワーク環境は自分のコンピュータと同じです。

重要な点は、この 3 つが互いに同期しないことです。claude.ai にアップロードしたスキルは、API や Claude Code では自動的に表示されません。

Claude Code のドキュメントには、さらにいくつかの情報が記載されています。序論に `disable-model-invocation: true` を設定すると、モデルが自動的に呼び出されず、私が `/名前` で呼ぶ場合にのみ動作します。逆に `user-invocable: false` にすると、`/` メニューからは隠され、モデルからの呼び出しのみが可能になります。従来のカスタムスラッシュコマンド（`.claude/commands/`）はスキルに統合されましたが、既存のファイルも引き続き動作します。設定手段をどのように全体で使い分けるかは、[Claude Code スキル・設定](#/post/claude-skills) の記事で別途整理されています。

## 正しく使うには：ドキュメントが述べていること

ベストプラクティスのドキュメントから、数値やルールのある項目のみを抽出しました。

- `name`: 64 文字以下で、小文字・数字・ハイフンのみ使用可能です。`anthropic` や `claude` は予約語のため使用できません。
- `description`: 空にはできず、1,024 文字以下に制限されます。何を行うものか、いつ使うのかを両方記載します。三人称で記述してください（「エクセルファイルを処理する」「私が手伝うことができます」などは不可）。説明はシステムプロンプトに含まれるため、時制が混ざると選択が揺らぐ可能性があるとのことです。
- `SKILL.md` の本文は 500 行以内に収め、それを超えたらファイルを分割してください。
- 参照は `SKILL.md` から最大 1 ステップのみに行うようにします。ファイル内で他のファイルに続く場合、モデルは先頭部分だけをスキャンして（`head -100` のような処理）スキップしてしまう可能性があります。
- ガイダンスは簡潔に。「モデルはすでに賢い」という前提とし、モデルが知らないことだけを記載してください。
- 作業が微妙な場合（DB マイグレーションなど）は自由度を下げ、「このスクリプトをそのまま実行」させ、判断が必要な作業（コードレビューなど）は自由度を高めます。
- 評価を先に作成します。スキルなしで試してみて詰まった箇所を見つけ、それを埋める最小限のものだけを記述します。

Claude Code のドキュメントには、説明が長すぎると切り捨てられる旨も記載されています。`description` と `when_to_use` を合わせたリストにおいて 1,536 文字で切り捨てられるため、核心的な用途を先に記載するよう指示されています。

## よくある誤解

- スキルを多くインストールするとコンテキストが溢れる：通常はスキルごとの名前・説明（ドキュメント基準では約 100 トークン）のみがアップロードされます。本文は使用時にのみ読み込まれます。ただし、スキルが数百に増えると、その説明リスト自体も大きくなるため、無料ではありません。
- 一度呼び出したスキルは継続して保持される：Claude Code のドキュメントでは、スキルが使用されると本文が会話に一度読み込まれ、以降のターンにも残ると述べています。そのため、長期的な作業ではそれだけスペースを占めます。
- スキルはすべて信頼して使用してもよい：スキルはガイダンスとコードを同時に提供するため、悪意のあるスキルはモデルがツールを誤って呼び出す原因となります。ドキュメントでは、自分で作成したものか Anthropic から入手したものをのみ使用し、不明な出所の場合は中身にあるファイル（スクリプト、画像を含む）をすべて確認するよう指示しています。外部 URL を取得するスキルはさらに危険であると記載されています。ソフトウェアのインストールと同様の態度で捉えることができます。
- スキルがあればモデルが必ず使用する：使用するかどうかはモデルが説明を見て決定します。そのため、説明が曖昧（「ドキュメントを助ける」など）だと呼び出されない可能性があります。これがドキュメントが名前と説明を特に重要視する理由です。
- スキルはプロンプトの別名である：外見上は指示文の束ですが、ファイルシステム構造、段階的な読み込み、スクリプト実行が付随しているため異なります。逆に言えば、単に長い指示文をフォルダに入れるだけではスキルの利点は生まれないということです。読みやすいように分割しておく必要があります。

<summary>詳細な解説：スキルがコンテキストに蓄積される順序</summary>

ドキュメントの PDF 例をそのまま追います。

1. 開始：システムプロンプトに「pdf-processing - PDF からテキストと表を抽出し、フォームを埋める…」という一行が入ります。
2. リクエスト：「この PDF からテキストを抽出して要約してください。」
3. モデルが `cat pdf-processing/SKILL.md` で本文を読み取ります。これで本文がコンテキストに含まれます。
4. フォームの埋めは不要なので `FORMS.md` は読みません。
5. 本文のガイダンスに従って作業を行います。

Claude Code ではさらに一つ追加があります。ドキュメントによると、自動圧縮（compaction）が発生する際、最も最近使用したスキルを再度追加しますが、各スキルについては先頭 5,000 トークンのみを残し、合計予算は 25,000 トークンとされています。予算は最近使用したスキルから埋められ、古いスキルは除外される可能性があります。そのため、重要なガイダンスは `SKILL.md` の先頭に置くのが安全です。（これはドキュメントの内容を読み取ったもので、私が実際に実験したものではありません。）圧縮自体については [コンテキスト](#/post/ai-context) の記事で整理しています。

</details>

<details>
<summary>詳細な解説：サブエージェント・ハネスとの関係</summary>

スキル本体がコンテキストに投入され、取り出された後は、通常の指示文と同様に扱われると理解しました。異なるのは、投入される前の部分です。何をいつ読み取るのか、スクリプトをどのように実行するのかは、モデルを取り巻く [ハネス](#/post/ai-harness) の役割です。「スキル」という概念は、モデルではなく、ハネスの側での約束事に近いと言えます。

Claude Code のドキュメントでは、冒頭に `context: fork` を設定すると、スキルを別の [サブエージェント](#/post/ai-subagent) で実行できることが記載されています。これは、出力が多いタスクを別途実行し、要約のみを受け取るための用途だと理解していましたが、実際に試したことはありませんでした。

</details>
