MCP 是一项公开标准，它统一了 AI 应用程序连接外部系统（如文件、数据库、搜索等）的方式。官方介绍文档将其比喻为“AI 应用的 USB-C 端口”。由于标准已统一，只需构建一次服务器，多个应用即可以相同方式使用。

## 解决了什么问题

如果没有 MCP，每个 AI 应用都需要单独编写连接外部服务的代码。假设有 N 个应用和 M 个服务，连接数量将达到 N×M。**（注：此计算并非出自官方文档，而是我个人的总结。）**MCP 在此之间引入了一套通用标准，使得应用只需懂得与 MCP 通信，而服务方仅需构建 MCP 服务器即可。

官方文档从用户角度阐述了这些优势：开发者在创建和集成 AI 应用或代理时，时间和复杂度得以降低；AI 应用能够访问数据和工具生态系统；最终用户则能使用功能更强大的应用。文档中提到的支持范围包括 Claude、ChatGPT、Visual Studio Code 和 Cursor。其中还提到了“一次构建，随处连接”的理念。

其适用范围较为有限。架构文档中指出："MCP 仅专注于提供和交换上下文的协议，不规定 AI 应用如何使用 LLM，也不规定如何管理接收到的上下文。”模型何时调用什么属于应用层面的职责。这部分内容也与 [上下文](#/post/ai-context) 相关。

## 结构：主机、客户端与服务器

参与者共有三类：

| 名称 | 职责 | 示例 |
|---|---|---|
| MCP 主机 (Host) | AI 应用。负责创建和管理客户端 | Claude Code, Claude Desktop, VS Code |
| MCP 客户端 (Client) | 维持与单个服务器的连接，接收上下文并传递给主机 | 主机内部的对象 |
| MCP 服务器 (Server) | 提供上下文的程序 | 文件系统服务器、Sentry 服务器 |

核心在于：一个客户端单独连接到一个服务器。文档中的示例易于理解。当 VS Code 连接到 Sentry MCP 服务器时，会创建一个客户端对象；若再连接到本地文件系统服务器，则会额外创建一个客户端对象。

```
호스트(AI 앱)
 ├─ 클라이언트 1 ── 서버 A (로컬: 파일시스템)
 ├─ 클라이언트 2 ── 서버 B (로컬: DB)
 └─ 클라이언트 3 ── 서버 C (원격: Sentry)
```

“服务器”一词可能令人困惑，文档对此进行了专门说明：服务器指的是任何提供上下文的程序，无论其运行在哪里。在本地 PC 上运行的称为本地服务器，在互联网另一端运行的则称为远程服务器。

### 两层架构：数据层与传输层

- **数据层**：基于 JSON-RPC 2.0 定义消息的格式和语义。功能包括服务发现（discovery）、工具/资源/提示词（tools/resources/prompts）以及通知（notifications）。
- **传输层**：实际承载消息的通道，主要有两种：
  - **stdio**：同一 PC 内的进程之间通过标准输入输出进行通信。无网络开销。主要用于本地服务器，通常只与一个客户端交互。
  - **Streamable HTTP**：在 HTTP POST 请求中可选地附加 Server-Sent Events (SSE)。专为远程服务器设计，通常服务于多个客户端。认证可使用 Bearer Token、API Key 等，文档推荐使用 OAuth 获取令牌。

## 服务器提供的三种资源

服务器可提供三类（基础）资源，其中决定由谁使用这些资源的机制各不相同，这一点很有趣：

| 类型 | 定义 | 示例 | 决定使用者 (规范表述) |
|---|---|---|---|
| 工具 (Tools) | 可执行的函数 | 文件操作、API 调用、数据库查询 | model-controlled（由模型自主发现并调用） |
| 资源 (Resources) | 提供上下文的静态数据 | 文件内容、数据库记录、模式定义 | application-driven（由主机应用决定如何读取） |
| 提示词 (Prompts) | 可复用的模板 | 系统提示词、少样本示例 | user-controlled（由用户直接选择） |

结合文档中的示例来看：一个用于数据库的服务器可以同时提供用于查询的工具、包含模式定义的资源，以及使用该工具的 few-shot 示例提示词。

规范中提到了通过斜杠命令暴露提示词的示例。工具由模型调用，但规范指出：“出于安全和信任考虑，应始终存在能够拒绝请求的人 (SHOULD)"。这意味着需要展示哪些工具被暴露、在调用时进行标记，并获取确认。不过，同一份文档也指出，协议并不强制要求这种交互方式。

这三类资源均支持通过 `*/list` 端点获取列表及后续获取详情。具体方法为：资源使用 `resources/read`，提示词使用 `prompts/get`，工具使用 `tools/call`。由于列表是动态的，当工具发生变化时，服务器会发送通知，客户端随后重新获取列表。

<details>
<summary>详细解析：工具调用的交互流程</summary>

以下是架构文档示例的简化版。首先，发送 `tools/list` 后，服务器会返回工具列表。每个工具包含 `name`、`title`、`description` 以及以 JSON Schema 格式描述的输入形式 `inputSchema`。

```json
{ "method": "tools/call",
  "params": { "name": "weather_current",
              "arguments": { "location": "San Francisco", "units": "imperial" } } }
```

响应中的 `content` 数组将包含文本、图像等内容。规范将工具执行错误分为两类：对于请求本身错误的情况（如同调用不存在的工具），返回 JSON-RPC 错误；而对于日期格式错误等输入或逻辑错误，则返回带有 `isError: true` 标记的结果。后者意味着模型读取并修正后重新尝试。

主机端的流程遵循文档的伪代码：当模型表示要使用工具时，应用程序拦截该调用并将其转发至合适的服务器，随后将结果重新插入模型的对话中。

值得注意的是，本次阅读的文档（最新版本标注为 2026-07-28）采用无状态方式，在每次请求中将协议版本和能力封装在 `_meta` 中发送。据称，旧版本中存在连接建立时的协商初始化阶段。

</details>

## 服务器向客户端发起的请求

反向功能同样存在。基于最新文档，服务器可向用户发起额外的输入或确认请求（elicitation）。`sampling`（服务器请求客户端 LLM 完成生成）和 `logging` 在此版本中已被标记为弃用。该部分内容正在随版本更新而变化，使用时需查阅对应版本的文档。

## 通用 function calling 与它有何不同

| | function calling | MCP |
|---|---|---|
| 本质 | 模型 API 表达工具调用的方式 | 应用程序与外部系统之间的连接规范 |
| 工具定义 | 应用程序代码在每次请求中直接提供 | 服务器通过 `tools/list` 告知 |
| 工具执行 | 由应用程序自行实现 | 由服务器执行（若为远程，甚至可跨组织） |
| 范围 | 仅限工具 | 涵盖工具、资源和提示词（prompt） |

两者并非竞争关系，而是处于不同层级。主机将接收到的 MCP 服务器工具列表传递给模型；当模型发出调用时，则通过 `tools/call` 转发给服务器。从模型角度看，这依然是工具调用，区别仅在于工具的来源。文档也指出："MCP 并不规定 AI 应用程序如何使用 LLM"，因此不应触碰模型 API 相关部分。

因此，其优势不在于“在一个应用程序内部如何调用工具”，而在于“即使应用程序与工具开发者互不相识，也能实现连接”。

## 安全注意事项

由于 MCP 服务器可执行代码或读取数据，建立连接即意味着授予权限。以下仅列出在官方安全文档和工具规范中值得注意的内容：

- **本地服务器风险**：配置文件中可能包含恶意启动命令，服务器本身可能存在恶意代码，或者已运行的本地服务器可能遭受 DNS rebinding 攻击。文档要求在连接一次性配置的本地服务器时，必须确保实际执行的命令未被截断（MUST），并明确要求获得显式批准。同时建议在沙箱环境中以最小权限运行。
- **禁止 Token 透传**：MCP 服务器接收非自身颁发的令牌并将其原样转发至下层 API 属于反模式。文档规定服务器只能接收颁发给自己的令牌（MUST NOT 接受其他令牌）。
- **糊涂副手（Confused deputy）**：若为第三方 API 提供连接的 MCP 代理服务器，其固定客户端 ID、动态客户端注册及同意 cookie 发生重叠时，可能在未经用户同意的情况下窃取认证代码。因此，必须针对每个客户端单独获取同意。
- **SSRF**：恶意服务器可能将 OAuth 元数据 URL 填充为内网地址或云元数据地址（如 169.254.169.254），诱导客户端跟随访问。应对措施包括阻止私有 IP 地址并强制使用 HTTPS。
- **最小化权限范围**：若一开始就授予 `files:*`、`admin:*` 等广泛范围的权限，一旦令牌泄露将造成更大损害。建议初始仅授予以读为主的较小范围权限，并在需要时再提升。
- **工具规范的推荐做法**：服务器必须实施输入验证、访问控制、调用次数限制和输出清理（MUST）；客户端应在执行敏感操作前获取用户确认，并在将输入发送给服务器之前向用户展示该输入（SHOULD）。除非来自可信服务器，否则不应信任工具的 annotations（动作描述元数据）（MUST consider untrusted）。

由于服务器返回的工具结果和说明最终会进入模型的上下文，因此基本准则应是仅连接可信的服务器。这一理解并非直接来自文档内容，而是阅读后得出的判断。

## 常见误解

- MCP 是工具吗：MCP 并非工具本身，而是一种连接工具的规范。工具由服务器提供。
- 使用 MCP 会让模型变得更聪明：模型本身并未改变，只是其可接收的上下文范围和可执行的操作增加了。
- 服务器仅存在于远程：通过 stdio 在本地 PC 上运行的本地服务器十分常见。
- 因为有规范所以安全：规范仅包含建议，真正的安全性取决于对服务器的选择以及客户端的批准界面（approval UI）。
- 仅有工具：实际上还包括资源和提示词（prompts）。虽然感觉上似乎较少使用，但这只是主观感受，尚未找到相关统计数据。
