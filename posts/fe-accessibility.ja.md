ウェブアクセシビリティは、マウスを使用し画面を目で見る人だけを想定して作成するものではありません。大半のケースでは HTML を目的に合わせて適切に使用することで解決でき、ARIA はそれでも不足する場合のための補完手段でした。

## アクセシビリティとは何か

MDN は、ウェブサイトを作成することを「可能な限り多くの人が利用できるようにすること」と説明しています。通常は障害と結びつけて話されますが、モバイル端末や低速なネットワークなど状況的な理由で不便に感じている人にも役立つと記されています。MDN が引用した WHO の統計によると、世界の約 15%、つまり 10 億人以上の人が何らかの形で障害を持っています。

対象者は大きく分類できます。

| 種類 | 例 | 必要なもの |
|---|---|---|
| 視覚 | 全盲、低視力、色弱 | スクリーンリーダー、拡大機能、十分な輝度コントラスト |
| 聴覚 | 難聴、ろう | キャプション、台本 |
| 運動 | マウスが使えない、手が不自由 | キーボードのみでの操作 |
| 認知 | 集中・理解が困難 | 簡単な言葉、一貫した配置、明確なエラーメッセージ |

続く話は、ほぼこの表のどのセルを満たすかというものです。

## 基準は WCAG

具体的な基準は W3C の WCAG(Web Content Accessibility Guidelines) です。4 つの原則にまとめられています。

- 認識可能 (Perceivable): 情報を視覚的に見たり、聴覚で聞いたり、他の方法で受け取れるようにする必要がある。
- 操作可能 (Operable): キーボードなどの他の入力手段でも操作できる必要がある。
- 理解可能 (Understandable): コンテンツと動作が予測可能である必要がある。
- 堅牢性 (Robust): マークアップが正確で、補助技術が読み取れるようにする必要がある。

各項目には A、AA、AAA の段階があり、法律や契約で求められるのは通常 AA です。この記事で数字を引用している項目は WCAG 2.2 の基準に基づいています。

[詳細 → ブラウザのレンダリング](#/post/fe-browser-render) で扱ったように、DOM が構築されると、ブラウザはそれに加えてアクセシビリティツリーも別途作成します。スクリーンリーダーなどの補助技術が読み取るのは画面のピクセルではなく、このツリーです。CSS や JavaScript ではなく、要素の役割・名前・状態がこのツリーに記録されます。アクセシビリティ作業とは、結局のところこのツリーが正しく構築されるようにすることです。

## セマンティック HTML が先

同じ外見のボタンを 2 つ作成すると違いが見えてきます。

```html
<!-- 눌러지긴 하지만 접근성 트리에서는 그냥 글자 -->
<div class="btn" onclick="save()">저장</div>

<!-- 포커스, Enter/Space, 역할 이름이 기본으로 따라온다 -->
<button type="button" onclick="save()">저장</button>
```

`div` は Tab キーでフォーカスが当たらず、Enter や Space キーでも押されず、スクリーンリーダーは「ボタン」と読み上げません。これを `div` に一つずつ追加するには、`tabindex`、キーイベント、役割の指定を直接実装する必要があります。一方、`button` は最初からこれらを持っています。

したがって、要素は用途に合わせて選択します。

- 移動には `a`、動作には `button`
- タイトルには `h1`〜`h6` を順番に使用。文字サイズを大きくするために選択しない
- 領域には `header`、`nav`、`main`、`footer` などのランドマークとして分割すると、スクリーンリーダーユーザーが区画単位でスキップできる
- リストには `ul`/`ol`、表には `table` と `th`
- 入力欄には `label` で接続する

```html
<label for="email">이메일</label>
<input id="email" type="email" autocomplete="email">
```

画像は `alt` 属性で代替テキストを記述します。情報を伝える画像には内容を記述し、装飾用であれば `alt=""` にして空にし、スクリーンリーダーがスキップするようにします。空にしておくことと属性を完全に削除することは異なります。削除するとファイル名が読み上げられる場合があります。

[詳細 → コンポーネント](#/post/fe-component) を作成する場合も同様です。コンポーネント内部を `div` で埋め尽くすと、どれだけ再利用してもアクセシビリティの問題も一緒に複製されてしまいます。

## キーボード

マウスなしで使用できる必要があることは、MDN がアクセシビリティテストで最初に推奨する方法でもあります。実際に試してみればわかります。マウスを離して、Tab、Shift+Tab、Enter、Space、Esc、方向キーだけでページ全体を使いこなせるか確認します。

確認すべき点は 3 つあります。

- すべての操作要素に到達できるか
- 現在どこにフォーカスがあるかが表示されているか。`outline: none` でフォーカスリングを消去し、代替手段を用意していないケースが頻繁にあります
- フォーカスの順序が画面の読み上げ順序と合致しているか。`tabindex` に正数を指定すると順序が乱れやすいため、通常は 0 と -1 のみ使用します

モーダルは特に注意が必要です。開くとフォーカスがモーダル内に入り、閉じると開いたボタンに戻らなければなりません。開いている間、フォーカスが後方のページに逸脱してはいけません。最近では `dialog` 要素と `showModal()` がこの部分をかなり処理してくれることが知られています。

## 輝度コントラスト

文字色と背景色の明るさの差を比率で測ったものが輝度コントラストです。WCAG 2.2 の 1.4.3(AA) は以下のように要求しています。

| テキスト | 必要なコントラスト |
|---|---|
| 通常のテキスト | 4.5:1 以上 |
| 大きな文字（18pt 以上、または 14pt の太字以上） | 3:1 以上 |

pt を px に変換すると、18pt は約 24px、14pt は約 18.5px です。比率を四捨五入しないため、4.499:1 は基準を満たしません。非アクティブなボタンの文字、装飾のみ、ロゴの文字は例外です。ボタン枠やアイコンなどのテキスト以外の要素については別基準（1.4.11）が存在します。

<details>
<summary>コントラスト比を計算してみる（Python で実行して確認した値）</summary>

WCAG が定義する相対輝度公式をそのまま移植して計算しました。sRGB 値を 0〜1 に変換した後、0.03928 以下であれば 12.92 で割り、それ以外では `((c+0.055)/1.055)^2.4` を適用します。輝度は `0.2126R + 0.7152G + 0.0722B`、コントラスト比は `(明るい方 + 0.05) / (暗い方 + 0.05)` です。

白い背景（#ffffff）上で計算した結果は以下の通りです。

| 文字色 | コントラスト比 | 一般テキスト AA |
|---|---|---|
| #000000 | 21.0 : 1 | 合格 |
| #767676 | 4.54 : 1 | 合格 |
| #777777 | 4.48 : 1 | 不合格 |
| #949494 | 3.03 : 1 | 大文字のみ合格 |

灰色の 1 ピクセルの違いで合格と不合格が分かれます。肉眼ではほとんど区別できません。デザインツールやブラウザの開発者ツールのコントラストチェッカーを使う理由です。
</details>

色だけで情報を伝えないことも同じ文脈にあります。エラーを赤い枠線だけで示すと、色覚障害のあるユーザーは見逃してしまいます。アイコンやテキストも併記します。

タッチターゲットのサイズも WCAG 2.2 に追加されました。2.5.8(AA) ではポインタで押す対象は 24x24 CSS ピクセル以上である必要があります。ただし、より小さくても周囲の対象との間隔が十分であれば例外として合格する場合があります。

## ARIA はいつ使うか

ARIA（WAI-ARIA）は、HTML だけでは表現できない役割・状態・属性をアクセシビリティツリーに追加するための属性の集まりです。`role`、`aria-label`、`aria-expanded` などです。タブ、コンボボックス、ツリーなどの複合ウィジェットは HTML の基本要素がないため ARIA が必要です。

しかし W3C の文書が繰り返しているのは「使えないなら使わない」という方向性です。整理すると以下のようになります。

- 必要な意味と動作が既に含まれているネイティブ要素があればそれを使います
- ネイティブの意味を変えません。絶対に必要な場合のみ例外です
- ARIA で作成した操作要素はキーボードでも操作可能である必要があります
- フォーカスを受け取る要素に `role="presentation"` や `aria-hidden="true"` を付与しません

ARIA Authoring Practices Guide も「No ARIA is better than Bad ARIA」というタイトルで同じことを述べています。「役割は約束である」という説明がしっくりきました。`role="button"` を付与するとその要素は Enter キーと Space キーに反応するボタンのように振る舞う必要がありますが、ARIA は音声のみを変更し、キーボード動作自体は生成しません。それは JavaScript で直接実装する必要があります。

```html
<!-- 상태를 알려 주는 올바른 사용 예 -->
<button type="button" aria-expanded="false" aria-controls="menu">메뉴</button>
<ul id="menu" hidden>...</ul>
```

開閉時に `aria-expanded` を `true`/`false` に切り替える必要があります。値を変えないと嘘をつく属性になってしまいます。

## 数字で見える現実

WebAIM が毎年上位 100 万のホームページを自動検査している WebAIM Million の 2026 年 2 月の分析によると、ホームページの 95.9% で WCAG 違反が検出されました。ページあたりの平均エラー数は 56.1 です。最も一般的な問題は以下の通りです。

| 問題 | 該当ホームページの割合 |
|---|---|
| 低い明度コントラスト | 83.9% |
| イメージに代替テキストがない | 53.1% |
| 入力欄にラベルがない | 51% |
| 空のリンク | 46.3% |
| 空のボタン | 30.6% |
| ドキュメント言語が指定されていない | 13.5% |

上記で説明した項目がそのままランキングに入っています。さらに目立つのは ARIA です。ARIA を使用したページは平均 59.1 のエラーがあり、使用していないページは 42 のエラーでした。ただし WebAIM も ARIA がエラーを生んだと断定せず、ARIA を使用するページの方が元々複雑である可能性もあるとしています。それでも ARIA を多く付与してもアクセシビリティが向上するわけではないことは明らかです。自動検査で検出されるものだけがカウントされた数字であり、実際の問題はこれよりも多いはずです。

## チェックリスト

作成後に確認する順序を以下のように定めました。

1. マウスを離して Tab キーで最後まで移動させてみます。フォーカスが正しく表示され、順序が正しいか確認します。
2. 見出しレベル、ランドマーク、ボタンとリンクの区別が適切か確認します。
3. 画像ごとに `alt` を確認します。装飾用画像は空文字列にします。
4. 入力欄ごとに `label` が接続されているか、エラーメッセージがテキストで表示されるか確認します。
5. テキストのコントラスト比が 4.5:1（大きな文字では 3:1）を超えているか、検査ツールで測定します。
6. `html` に `lang` が設定されているか確認します。
7. ARIA はネイティブ機能で対応できない部分にのみ使用しているか、状態値を更新しているか確認します。
8. 最後にスクリーンリーダー（Windows は NVDA、Mac は VoiceOver）で一度読み上げてみます。

自動検査ツールは 1〜7 の項目の一部しか検出できません。MDN も自動テストと障害を持つユーザーによる直接テストの両方を行うことを推奨しています。ツールが「問題なし」と表示されていても、フォーカス順序や `alt` テキストが適切かどうかは人間が確認する必要があります。

## よくある誤解

- アクセシビリティは障害者だけが対象である：MDN の説明にあるように、モバイル端末、低速なネットワーク、明るい屋外環境下でも同様の改善が役立ちます。
- ARIA を付けるとアクセシビリティが向上する：上記の W3C ルールと WebAIM の数値は逆方向を示しています。ネイティブ要素を優先すべきです。
- 自動検査スコアが 100 点ならそれで終わりである：ツールが検出できない領域が非常に大きいです。
- 後で修正すればよい：MDN は最初から考慮するよう呼びかけています。後から直すコストが高くなるためです。
- 視覚障害者は画像を見る必要がないので `alt` は適当に書いてもよい：`alt` は画像の役割をテキストで代替するため、ファイル名や「画像」といった記述では実質的に存在しないのと同じです。
