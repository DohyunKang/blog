压缩（Compaction）是将充满对话的窗口转换为摘要，而记忆则是将那些可以舍弃但需要回退的信息写在窗口之外。两者并非相互竞争，而是更倾向于协同工作。

## 什么是压缩

模型一次能处理的内容量是固定的，这就是所谓的 [上下文窗口](#/post/ai-context-window)。然而，由于模型无法记住状态，因此每次请求都需要重新发送迄今为止的对话历史（[详情 → 会话与对话记录](#/post/ai-session)）。随着对话变长，需要发送的数据量也会增加，最终会导致窗口填满。

压缩（compaction）就是在此时将旧的轮次替换为单个摘要，从而腾出窗口的空间。Anthropic 的文件将压缩描述为“用 Claude 在服务器上撰写的摘要替换旧的轮次”。重点在于无需手动编写摘要代码。原因也已说明：随着对话变长，响应质量会下降，因此需要保持活跃上下文较小。关于为何质量会下降的内容已在 [上下文文章](#/post/ai-context) 中整理。

简单来说，这类似于撰写会议纪要。由于无法从头到尾重新阅读三小时的会议记录，因此只将决定事项写在一张纸上，并基于这张纸继续会议。

## 压缩的运行方式

从 Anthropic 的文件中确认了三种方式：

| | 谁决定时机 | 特点 |
|---|---|---|
| 按需压缩 (on demand) | 我的应用在发送请求时 | 接收摘要块并将其插入 `messages` 的最前面。最近的轮次可以保留原文，也可以在后台运行 |
| 令牌阈值压缩 (threshold) | API 在输入令牌达到预设标准时触发 | 只需在普通请求中添加一个参数即可。摘要在该请求内部处理 |
| 自定义摘要器 | 我的代码 | 我负责调用摘要、编写提示词以及重写记录 |

文件建议尽可能使用按需压缩。这两种方式在文件中均以“测试版”标记，且按需压缩使用测试版头 `compact-2026-09-04` 和顶层 `compaction` 参数。这些数字和名称可能会更改，使用时需重新查阅文档。虽然也有提到可以自行编写摘要提示词，但建议仅在默认摘要遗漏后续所需内容时使用。

## 压缩中保留什么

做好压缩的关键不在于写短摘要，而在于选择保留什么。Anthropic 的工程文章是这样写的：

- **保留的内容**：设计决策、未解决的 bug、实现细节。Claude Code 还会一并携带最近打开的五个文件。
- **丢弃的内容**：重复的工具输出和消息。对于很久以前调用的工具，其原始结果几乎不会再被查看。
- **调整顺序**：首先确保没有遗漏任何内容，最大化召回率；然后剔除无用信息以提高精确度。

文章中提到了最轻量级的压缩形式——“清除工具结果（tool result clearing）”。即不生成摘要，而是根据规则直接删除旧的工具结果。文件中将此功能单独列为 [上下文编辑 (context editing)](https://platform.claude.com/docs/en/build-with-claude/context-editing)，并将其与压缩区分开来解释。我们尚未尝试该功能。

## 记忆：写在窗口之外

一旦进行压缩，被舍弃的内容就无法找回。因此，重要的是从一开始就将其写在窗口之外。Anthropic 的文章将这种结构化的笔记（structured note-taking，代理型记忆）称为“结构化笔记”。代理会定期向窗口外的内存写入笔记，并在需要时重新读取。例如：Claude Code 的任务列表、自定义代理的 `NOTES.md`，以及 Claude 在玩宝可梦游戏时即使上下文重置也能延续训练进度和策略记忆的案例。

Anthropic 提供的记忆工具（memory tool）基于文件实现。从文件中确认的结构如下：

- Claude 创建、读取、修改和删除 `/memories` 目录下的文件。命令包括 `view`、`create`、`str_replace`、`insert`、`delete`、`rename`。
- 这是客户端侧的工具，Claude 仅发出请求，实际的文件处理由我的应用完成。存储位置（磁盘、数据库等）和保留策略也由我自行决定。
- 如果存在记忆工具，API 会自动在系统提示词中加入“在执行操作前首先查看记忆目录”、“假设上下文随时可能被重置”等指令。
- 警告称必须自行实现防止路径遍历（如 `../`）的验证逻辑。

建议将内存（Memory）与压缩（Compaction）配合使用。两者的分工在于：压缩旨在无需客户端管理的情况下保持活跃上下文较小，而内存则负责在摘要过程中保留必须保留的信息。

这样写看起来与 [RAG](#/post/ai-rag) 相似，但本质不同。RAG 是从外部文档中检索相关片段并通过 [嵌入搜索](#/post/ai-embedding) 注入；而此处所说的“内存”是指代理（Agent）自行记录其工作内容的机制。虽然也可以将内存存入检索数据库，但本文所读资料仅确认了文件存储方式。

## 权衡取舍

| | 压缩 (Compaction) | 内存 (Memory/Note) |
|---|---|---|
| 适用场景 | 交互频繁的对话任务 | 具有里程碑的迭代开发 |
| 优点 | 保持对话流程连贯 | 以较小代价长期留存信息 |
| 风险 | 若过于激进，看似琐碎的重要上下文会丢失 | 需管理记录什么以及如何清理旧笔记 |

工程文档本身并未单独列出笔记方式的缺点。

在处理长任务时，通常会混合使用这些方法。也可以将狭窄的任务分配给子代理（Sub-agent），仅接收其摘要（[详情 → 子代理](#/post/ai-subagent)）。执行此循环、在压缩时刻点以及进行内存读写操作的实体是 [Harness](#/post/ai-harness)。

## 常见误解

- **压缩后原文会保留在某处**：替换为摘要后，若从本地记录中删除原文，模型仅查看摘要。是否单独存储原文由应用程序决定。
- **内存会自动由模型积累**：内存工具需要客户端实现才能运行；若无存储介质，则无法记忆。
- **上下文很大就不需要压缩**：即使窗口变大，质量和成本问题依然存在。[提示词缓存](#/post/ai-prompt-caching) 仅能降低费用，无法节省空间（参考 [上下文文章](#/post/ai-context)）。
- **压缩与上下文编辑是同一回事**：前者是摘要；后者则是通过规则删除特定的工具结果或思考块。
