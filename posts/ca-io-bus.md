CPU는 명령어를 빠르게 실행하는데, 디스크와 네트워크 카드와 키보드는 그에 비하면 한참 느리다. 입출력(I/O) 이야기는 거의 다 이 속도 차이를 어떻게 숨기느냐로 풀린다. CPU 안쪽 동작은 [CPU와 명령어](#/post/ca-cpu)에, 메모리 쪽 속도 차이는 [메모리 계층과 캐시](#/post/ca-memory-hierarchy)에 있어서, 여기서는 CPU 바깥의 장치와 그 사이의 길만 본다.

## 장치는 레지스터 몇 개로 보인다

OSTEP(교재)은 가상의 표준 장치를 하나 놓고 설명한다. 장치는 두 부분이다. 시스템에 보여 주는 인터페이스와, 그 뒤의 내부 구조. 내부는 칩 하나로 끝나는 단순한 장치도 있고, 작은 CPU와 메모리까지 들어 있어 펌웨어가 도는 복잡한 장치도 있다. 운영체제는 내부를 몰라도 되고 인터페이스만 다루면 된다.

인터페이스는 레지스터 세 개로 단순화된다.

| 레지스터 | 쓰임 |
|---|---|
| 상태(status) | 읽어서 장치가 지금 바쁜지 확인 |
| 명령(command) | 쓰면 장치가 그 일을 시작 |
| 데이터(data) | 장치로 보낼 데이터를 쓰거나 받은 데이터를 읽음 |

기본 절차는 네 단계다. 상태가 바쁨인 동안 기다리고, 데이터 레지스터에 쓰고, 명령 레지스터에 쓰고, 다시 상태가 바쁨인 동안 기다린다. 이렇게 상태를 계속 읽으며 기다리는 걸 폴링(polling)이라 하고, CPU가 직접 데이터를 옮기는 걸 PIO(programmed I/O)라 부른다. 단순하고 동작은 하는데, 장치가 느리면 CPU가 그냥 상태 레지스터만 읽으며 시간을 쓴다.

## 레지스터에 어떻게 닿는가

CPU가 장치 레지스터에 접근하는 방법은 두 가지가 쓰인다. 하나는 전용 입출력 명령어다. x86의 `in`, `out`이 그런 예이고, 포트 번호로 장치를 가리킨다. 이 명령어들은 보통 특권 명령이라 운영체제만 쓸 수 있다. 아무 프로그램이나 디스크를 직접 건드리면 곤란하기 때문이다.

다른 하나는 메모리 맵 I/O다. 장치 레지스터를 메모리 주소처럼 보이게 만들어서, 그 주소에 load/store를 하면 하드웨어가 그것을 메모리가 아니라 장치로 보낸다. 새 명령어가 필요 없다는 게 장점이다. OSTEP은 둘 중 한쪽이 뚜렷하게 낫지는 않고 지금도 둘 다 쓰인다고 쓴다.

장치마다 레지스터와 절차가 다르니 운영체제 전체가 그걸 알 수는 없다. 그래서 장치별 세부는 디바이스 드라이버 안에 가두고, 파일 시스템 같은 윗부분은 "블록 읽기/쓰기" 같은 일반적인 요청만 한다. 파일 시스템 쪽은 [파일 시스템과 입출력](#/post/os-filesystem)에서 다룬다.

## 기다리는 비용: 폴링과 인터럽트

폴링 대신 인터럽트를 쓰면, 운영체제가 요청을 보내 놓고 그 프로세스를 재운 뒤 다른 일을 시킨다. 장치가 끝나면 하드웨어 인터럽트를 걸고, CPU는 정해진 인터럽트 핸들러(ISR)로 뛰어든다. 핸들러는 요청을 끝내고 재워 둔 프로세스를 깨운다. 그 사이 CPU는 다른 프로세스를 실행했으니 계산과 I/O가 겹쳐진다.

그럼 인터럽트가 늘 낫느냐 하면 OSTEP은 아니라고 한다. 인터럽트 처리와 컨텍스트 스위치에도 비용이 든다. 장치가 아주 빠르면 처음 몇 번만 폴링해도 끝나 있어서, 그 경우엔 폴링이 낫다. 그래서 잠깐 폴링하다가 안 끝나면 인터럽트로 넘어가는 혼합 방식도 있다. 네트워크처럼 패킷이 쏟아지면 인터럽트가 너무 많아져 운영체제가 인터럽트 처리만 하다 끝나는 라이브락이 생길 수 있고, 그럴 땐 가끔 폴링으로 흐름을 직접 쥐는 게 낫다고 한다. 인터럽트 여러 개를 모아서 한 번에 알리는 coalescing이라는 최적화도 있다.

<details>
<summary>폴링과 블로킹 대기, CPU를 얼마나 쓰나 (직접 실행함)</summary>

1초 뒤에 "끝났다"고 알려 주는 느린 장치를 스레드로 흉내 냈다. 한쪽은 논블로킹 `recv`를 루프로 계속 호출(폴링)하고, 다른 쪽은 블로킹 `recv`로 커널이 재워 두게 했다. 블로킹이 인터럽트 방식과 완전히 같다는 뜻은 아니고, 운영체제가 프로세스를 재우고 이벤트가 오면 깨운다는 점에서 닮은 구조다.

```python
import socket, time, threading

def device(sock, delay):
    time.sleep(delay)
    sock.send(b"done")

def run(mode, delay=1.0):
    a, b = socket.socketpair()
    threading.Thread(target=device, args=(b, delay), daemon=True).start()
    c0, t0 = time.process_time(), time.perf_counter()
    if mode == "poll":
        a.setblocking(False)
        n = 0
        while True:
            n += 1
            try:
                a.recv(4); break
            except BlockingIOError:
                pass
    else:
        a.recv(4); n = 1
    return mode, n, time.process_time() - c0, time.perf_counter() - t0

for m in ("poll", "block"):
    mode, n, cpu, wall = run(m)
    print(f"{mode:5s} 확인 {n:>9,}회  CPU {cpu:.2f}s  경과 {wall:.2f}s")
```

Windows에서 Python 3.13으로 돌린 결과다. 폴링은 확인을 약 58만 번 하고 CPU를 0.98초 썼고, 블로킹은 한 번 호출에 CPU 0.00초였다. 둘 다 경과 시간은 1.00초라서 기다리는 시간은 같고, 그동안 CPU를 쓰느냐 마느냐가 달랐다. 횟수는 실행마다 달라진다.
</details>

## 데이터 옮기는 일: DMA

인터럽트로 기다림은 줄여도, PIO에서는 데이터를 CPU가 한 단어씩 장치로 복사해야 한다. 큰 블록이면 CPU가 단순한 복사에 시간을 쓴다. 이 일을 떼어 낸 게 DMA(Direct Memory Access)다. DMA 엔진은 메모리와 장치 사이 전송을 CPU 개입 없이 진행하는 전용 장치다.

순서는 이렇다. 운영체제가 DMA 엔진에 데이터가 메모리 어디에 있는지, 얼마나 옮길지, 어느 장치로 보낼지를 알려 준다. 거기까지가 운영체제 일이고, 이후 전송은 엔진이 한다. 끝나면 엔진이 인터럽트를 걸어 알린다. OSTEP의 타임라인으로 보면 PIO에서는 프로세스 1이 복사하는 동안 CPU가 묶이지만, DMA에서는 그 구간에 프로세스 2가 실행된다.

DMA가 공짜는 아니다. 엔진을 설정하고 끝 인터럽트를 처리하는 비용이 있으니 아주 작은 전송에서는 PIO가 더 쌀 수도 있다.

<details>
<summary>PIO와 DMA 손익 분기점 계산 (가정한 숫자, 실행함)</summary>

실제 하드웨어를 측정한 게 아니라, 아래 숫자를 가정하고 계산한 것이다. 한 단어(8바이트)를 옮기는 데 20사이클, DMA 설정과 인터럽트 처리에 2000사이클이 든다고 놓았다.

```python
BLOCK = 4096
WORD = 8
COPY_CYCLES = 20
SETUP_CYCLES = 2000

dma = SETUP_CYCLES
for size in (64, 512, 4096, 65536):
    p = (size // WORD) * COPY_CYCLES
    print(f"{size:>6}B  PIO {p:>7}  DMA {dma}  ->", "PIO가 유리" if p < dma else "DMA가 유리")
```

출력은 64B에서 PIO 160 대 DMA 2000(PIO 유리), 512B에서 1280 대 2000(PIO 유리), 4096B에서 10240 대 2000(DMA 유리), 65536B에서 163840 대 2000(DMA 유리)이었다. 분기점이 어디인지는 숫자를 어떻게 가정하느냐에 달렸고, 실제 값은 장치와 CPU마다 다르다.
</details>

## 버스와 주소

버스는 CPU, 메모리, 장치가 데이터와 신호를 주고받는 연결 통로다. OSTEP의 현대 시스템 그림을 보면 CPU는 메모리와 메모리 인터커넥트로, 그래픽 카드와는 고성능 PCIe로 바로 이어진다. 나머지 장치는 DMI로 연결된 I/O 칩을 거친다. 그 칩 아래로 eSATA로 하드 디스크가, USB로 키보드나 마우스 같은 느린 장치가 붙는다. 네트워크 카드나 NVMe 저장장치 같은 고성능 장치는 PCIe에 붙는 경우가 많다고 한다. 빠른 장치일수록 CPU에 가까운 연결을 쓰고, 느린 장치는 멀리 있는 칩을 거치는 계층 구조다.

DMA를 쓰는 장치는 메모리 주소를 직접 쓰기 때문에 주소 개념이 하나 더 생긴다. 리눅스 커널 문서는 주소를 세 가지로 나눈다. 커널이 쓰는 가상 주소, 장치 레지스터 같은 자원을 관리할 때 쓰는 CPU 물리 주소, 장치가 MMIO와 DMA에 쓰는 버스 주소다. 버스 주소는 호스트 브리지나 IOMMU가 바꿔 줄 수 있어서 CPU 물리 주소와 다를 수 있다. IOMMU는 장치가 보는 주소를 실제 RAM 주소로 번역해 주는 장치다. 간단한 시스템에는 없을 수도 있다.

리눅스의 DMA 매핑은 두 종류로 나뉜다. 코히런트 매핑은 드라이버 초기화 때 만들어 오래 쓰고, 하드웨어가 CPU와 장치가 보는 내용을 맞춰 준다. 장치와 주고받는 디스크립터 링 같은 구조에 어울린다. 스트리밍 매핑은 한 번의 전송을 위해 만들었다가 풀고, 네트워크나 파일 시스템 버퍼에 쓴다. CPU가 중간에 그 버퍼를 만지면 동기화 호출이 필요하다.

## GPU는 어디에 붙나

GPU도 장치처럼 버스에 붙는다. 다만 CUDA 문서의 모델에서는 CPU와 직접 붙은 메모리가 호스트 메모리이고, GPU와 붙은 메모리가 디바이스 메모리다. 프로그램은 CPU에서 시작해, CUDA API로 둘 사이에 데이터를 복사하고 커널(GPU에서 도는 코드)을 실행시키고 끝나길 기다린다. CPU와 GPU는 동시에 돌 수 있다. 지원되는 시스템에서는 통합 가상 주소 공간 덕분에 주소만 보고 GPU 메모리인지 시스템 메모리인지 알 수 있고, Unified Memory를 쓰면 런타임이나 하드웨어가 데이터를 필요에 따라 옮긴다. 문서는 PCIe나 NVLink 너머의 CPU 메모리를 GPU가 그대로 읽는 방식이 데이터를 알맞은 자리에 두는 것의 대체가 되지는 못한다고 적는다.

정리하면 GPU 쓸 때의 "데이터 복사" 비용은 결국 버스를 지나는 비용이다. 모델을 GPU에 올려 두면 매번 복사하지 않아도 되는 이유도 여기서 이어진다. 추론 쪽 이야기는 [추론 최적화](#/post/ml-inference)에 있다.

## 흔한 오해

- DMA를 쓰면 CPU가 전혀 관여하지 않는다: 전송 자체는 엔진이 하지만 시작할 때 설정하고 끝날 때 인터럽트를 처리하는 건 CPU다.
- 인터럽트가 폴링보다 항상 좋다: 빠른 장치나 인터럽트가 몰리는 상황에서는 폴링이 나을 수 있다.
- 장치 주소와 메모리 주소는 별개다: 메모리 맵 I/O에서는 장치 레지스터가 주소 공간에 같이 나타난다.
- CPU가 보는 물리 주소와 장치가 쓰는 주소는 늘 같다: 브리지나 IOMMU가 있으면 다를 수 있다.
