トランザクションは、複数の SQL を「すべて成功するか、すべて失敗するか」でまとめる単位であり、隔離レベル（Isolation Level）は、同時に実行されるトランザクション同士が互いの中間状態をどの程度見せるかを決める設定です。

## トランザクションとは何か

振替取引を考えてみると分かりやすいでしょう。A 口座から 30 円を引いて B 口座に 30 円を加えるには、2 つのクエリが必要です。最初のクエリだけが実行されてサーバーが落ちると、30 円が消えてしまいます。この 2 つのクエリを一つにまとめて「両方反映するか、両方無効化するか」にするのがトランザクションです。

```sql
BEGIN;
UPDATE acc SET bal = bal - 30 WHERE id = 1;
UPDATE acc SET bal = bal + 30 WHERE id = 2;
COMMIT;   -- 문제가 생기면 COMMIT 대신 ROLLBACK
```

`COMMIT` をすると一括処理全体が確定し、`ROLLBACK` をすると `BEGIN` 以降の変更はすべて取り消されます。実際に試してみました。Python の sqlite3 で A から 30 を引いた後に意図的に例外を発生させてロールバックしたところ、残高は `[(1, 100), (2, 0)]` のままでした。途中で落ちても半端な状態は残りません。

## ACID

トランザクションが守る性質の 4 つを頭文字で ACID と呼びます。

| 文字 | 名前 | 一言で言うと |
|---|---|---|
| A | Atomicity (原子性) | すべて成功するか、すべて失敗する |
| C | Consistency (一貫性) | 終了後でも制約条件（PK, FK, CHECK など）は破られない |
| I | Isolation (隔離性) | 同時に走るトランザクションが互いに干渉していないように見える |
| D | Durability (永続性) | コミットされたデータは障害があっても残る |

原子性と永続性は比較的分かりやすいです。混乱しやすいのは一貫性と隔離性です。一貫性が「DB が魔法のようにビジネスルールを守ってくれる」という意味ではありません。「私が宣言した制約条件をトランザクションの最後に破られないように防ぐ」程度に理解しています。隔離性は「完全に干渉しない」から「少し見える」まで段階があり、その段階が隔離レベルです。ここがこの記事の本題です。

## 同時実行時に発生する問題

トランザクションが一つずつしか走らなければ問題は起きません。複数のものが同時に走ると奇妙なことが起こり得ます。PostgreSQL のドキュメントではこれを 4 つに定義しています。

- ディーティリード (dirty read): コミットされていない他のトランザクションの変更を読み取る。
- 反復不可能読み取り (nonrepeatable read): 同じ行を 2 回読んだが、その間に他のトランザクションがコミットして値が変わっている。
- ファン텀読み取り (phantom read): 同じ条件で 2 回照会したが、その間にコミットされた他のトランザクションにより、条件に合致する行の集合自体が変わっている。
- シリアライゼーション異常 (serialization anomaly): 同時にコミットされた結果が、そのトランザクションを並べて一つずつ実行したどの順序とも一致しない。

[詳しく → インデックス](#/post/db-index) が検索速度の話であれば、こちらは「同じデータを同時に触った時に何が映るか」の話です。

## 隔離レベル

SQL 標準は隔離レベルを 4 つの段階に定め、各段階で上記の現象のうち何を許可するかが異なります。標準による基準は以下の通りです。

| 隔離レベル | ディーティリード | 反復不可能読み取り | ファン텀読み取り | シリアライゼーション異常 |
|---|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 | 可能 |
| Read Committed | 不可 | 可能 | 可能 | 可能 |
| Repeatable Read | 不可 | 不可 | 可能 | 可能 |
| Serializable | 不可 | 不可 | 不可 | 不可 |

上に行くほど緩く高速で、下に行くほど厳しく高価です。ただしこれは標準の最低要件であり、実際の DB は実装によって異なります。PostgreSQL のドキュメントの表を見ると以下のようになります。

- Read Uncommitted は名目だけ受け入れており、実際には Read Committed と同様に動作します。そのためディーティリードは発生しません。
- Repeatable Read は標準よりも厳格です。ファン텀読み取りも防ぎます。シリアライゼーション異常は残ります。
- デフォルトは Read Committed です。ドキュメントには「各文が新しいスナップショットを見る」とあります。

MySQL(InnoDB) や他の DB では同じ名前でも動作が異なる場合があります。この記事では確認した PostgreSQL の基準のみ記載しています。

## 各レベルの違い (PostgreSQL)

Read Committed では `SELECT` が「クエリ開始前にコミットされたデータ」のみを見ます。一つのトランザクション内で同じ `SELECT` を 2 回実行した場合、その間に他のトランザクションがコミットすると結果が変わることがあります。

Repeatable Read はトランザクションの最初の文でスナップショットを固定します。以降の `SELECT` は常に同じデータを見ます。ただし、私が修正しようとしている行を他のトランザクションが先に変更してコミットしていた場合、以下のようなエラーが発生します。

```
ERROR:  could not serialize access due to concurrent update
```

ドキュメントではこの場合に「現在のトランザクションを中止し、最初からすべてやり直すこと」と案内しています。

Serializable は Repeatable Read に加えて、順次実行の結果と異なる可能性がある依存関係も検出し、片方をロールバックします。このレベルを使用するとアプリケーションが再試行を準備する必要があり、ドキュメントによればシリアライゼーションの失敗は SQLSTATE `40001` で返されるとのことです。

まとめると、高いレベルほど「失敗してやり直す」ことがアプリケーションの役割に委ねられます。厳格さの値はパフォーマンスだけでなく、再試行コードそのものでもあります。

## 隔離レベルだけでは防げないもの：更新の喪失

隔離レベルの話をする際に見落としがちなのが、更新の喪失（lost update）です。コードが値を読み込んで計算した後に上書きする方式で発生します。Python で再現してみました。残高が 100 の口座から 2 つのトランザクションがそれぞれ 30 と 50 を引こうとしています。期待される結果は 20 です。

```python
x = a.execute("select bal from acc where id=1").fetchone()[0]   # 100
y = b.execute("select bal from acc where id=1").fetchone()[0]   # 100
a.execute("update acc set bal=? where id=1", (x - 30,))
b.execute("update acc set bal=? where id=1", (y - 50,))
# 결과: 50 (기대값 20)
```

どちらも 100 を読み取り、各自計算して上書きしたため、最初の更新 30 が消えてしまいました。この実験は sqlite3 で行いました（PostgreSQL はインストールしていないため試していません）。一般的な「読み込み - 計算 - 書き込み」パターンにおける問題を示すためのものです。解決策は計算を DB に委ねることです。

```python
a.execute("update acc set bal = bal - 30 where id=1")
b.execute("update acc set bal = bal - 50 where id=1")
# 결과: 20
```

`bal = bal - 30` は DB が読み書きを一語句の中で処理するため、上書きが発生しません。

## ロック：懐疑的と楽観的

読み込んだ値に基づいてアプリケーション側で判断が必要な場合はロックを使用します。2 つの方式があります。

懐疑的ロックは「衝突が起きそうなので先にロックしておこう」というアプローチです。PostgreSQL では `SELECT ... FOR UPDATE` を使用します。ドキュメントによれば、読み取った行は現在のトランザクションが終了するまで、他のトランザクションによってロックされたり修正されたり削除されることはなく、そのような試みは終了するまで待たされます。

```sql
BEGIN;
SELECT bal FROM acc WHERE id = 1 FOR UPDATE;   -- 이 행을 잠근다
UPDATE acc SET bal = bal - 30 WHERE id = 1;
COMMIT;
```

楽観的ロックは「大抵の場合は衝突しないので先に実行し、保存時に確認しよう」というアプローチです。通常、行に `version` カラムを置き、読み取り時のバージョンと一致する場合のみ更新を行います。

```python
def save(conn, body, ver):
    return conn.execute(
        "update doc set body=?, ver=ver+1 where id=1 and ver=?", (body, ver)
    ).rowcount

save(a, 'A', 1)   # 1  (성공)
save(b, 'B', 1)   # 0  (이미 ver이 2라서 갱신된 행이 없음 -> 충돌)
```

`rowcount` が 0 の場合は誰かが先に変更したことを意味するため、再度読み取って再試行すればよいです。実際に実行してみると A は 1、B は 0 という結果が得られました。

| | 懐疑的ロック | 楽観的ロック |
|---|---|---|
| 方式 | 読み取り時にロック | 保存時にバージョン確認 |
| 衝突が多い場合 | 待機するため安定 | 再試行が多く無駄 |
| 衝突が稀な場合 | ロックコストのみ発生 | 軽量 |
| 注意点 | 長持ちさせると待ち時間・デッドロック | 再試行コードが必要 |

どちらが良いかという問題よりも、衝突の頻度によって選ぶべき問題だと理解しています。

## デッドロック

ロックを使用するとデッドロック（交着）が発生する可能性があります。トランザクション 1 が口座 11111 を修正した後、22222 を修正しようとし、トランザクション 2 が 22222 を修正した後、11111 を修正しようとすると、互いが保持しているロックを待ちながら永遠に止まってしまいます。

PostgreSQL のドキュメントでは、デッドロックを自動的に検出し、関連するトランザクションのいずれかを中止するとあります。どちらが中止されるかは予測できないとも記されています。予防策として最初に挙げられるのは「複数のオブジェクトへのロックを常に同じ順序で行う」ことです。前述の例でも、2 つのトランザクションが同じ順序で更新を行っていればデッドロックは発生しなかったそうです。順序合わせが難しい場合は、デッドロックにより中止されたトランザクションを再試行する方法もあります。また、ロックを取得したままユーザー入力を待機させ、トランザクションを長く開けておくのは良くないとドキュメントが警告しています。

ここでも結論は再試行です。シリアライゼーションの失敗も、楽観的ロックの衝突も、デッドロックも「最初からやり直す」ことで対処します。

## よくある誤解

- トランザクションでまとめることで並行性の問題は解決する：まとめるのは原子性です。並行性は隔離レベルとロックが担当し、デフォルトの Read Committed では前述の更新の喪失のようなパターンがそのまま発生する可能性があります。
- Serializable だけ使えば全て解決する：確かにブロックしますが、失敗するトランザクションが発生し、再試行コードがない場合エラーはユーザーにそのまま伝わります。
- 隔離レベルの名前は DB ごとに同じ意味を持つ：標準は最低限の要求に過ぎず、実装は異なります。PostgreSQL でも Read Uncommitted が Read Committed のように動作します。
- ロックをかけることで遅くなるので使わない方が良い：衝突が頻繁な場所ではロックがむしろ再試行の暴走を防ぎます。

<details>
<summary>詳しい解説：スナップショットと MVCC がなぜ出てくるのか</summary>

PostgreSQL のドキュメントが Read Uncommitted を Read Committed にマッピングする理由として挙げられたのは、「PostgreSQL のマルチバージョン並行制御（multiversion concurrency control）構造に適合する唯一の合理的な方法」です。行を上書きせずバージョンごとに置き、各トランザクションが自分の基準時点のバージョンを読み取る構造であるため、読み取りが書き込みを妨げません。そのため「汚れた」中間値を読み取る手段はありません。

私が上で sqlite3 で確認したことも同様の文脈にある。書き込み接続をコミットする前に読み取り接続で照会すると 100 がそのまま表示され、コミット後には 999 が表示された。ただし、sqlite の動作方式は PostgreSQL と異なるため、隔離レベルの比較用としては使用しなかった。

</details>

<summary>詳細な解説：用語整理</summary>

- **コミット (commit)**: トランザクションの変更を確定する。
- **ロールバック (rollback)**: トランザクションの変更を取り消す。
- **スナップショット**: 特定の時点に基づいて表示されるデータの姿。
- **シリアライズ (serializable)**: 同時に実行されても、結果は順次実行した場合と同じになる。
