MCP는 AI 앱이 파일, 데이터베이스, 검색 같은 바깥 시스템에 붙는 방식을 하나로 맞춘 공개 규격이다. 공식 소개 문서는 "AI 앱을 위한 USB-C 포트"라고 비유한다. 규격이 통일돼 있으니 서버를 한 번 만들면 여러 앱이 같은 방식으로 쓴다.

## 무엇을 해결하나

MCP가 없으면 AI 앱마다 외부 서비스에 붙는 코드를 따로 짜야 한다. 앱이 N개, 서비스가 M개면 연결이 N×M개다. 이 계산은 공식 문서에 나오는 문장이 아니라 내가 정리한 것이다. MCP는 이 사이에 공통 규격을 하나 두어서, 앱은 MCP를 말할 줄만 알고 서비스는 MCP 서버만 만들면 되게 한다.

공식 문서는 이점을 사용자 쪽별로 적는다. 개발자는 AI 앱이나 에이전트를 만들고 연동할 때 시간과 복잡도가 줄고, AI 앱은 데이터·도구 생태계에 접근하게 되고, 최종 사용자는 더 많은 일을 하는 앱을 쓰게 된다. 지원 범위로는 Claude, ChatGPT, Visual Studio Code, Cursor가 문서에 이름이 올라 있다. "한 번 만들고 어디서나 연결"이라는 표현도 있다.

범위는 좁다. 아키텍처 문서에 "MCP는 컨텍스트를 주고받는 프로토콜에만 집중하고, AI 앱이 LLM을 어떻게 쓰는지, 받은 컨텍스트를 어떻게 관리하는지는 정하지 않는다"고 적혀 있다. 모델이 언제 무엇을 부를지는 앱 쪽 일이다. 이 부분은 [컨텍스트](#/post/ai-context)와도 이어진다.

## 구조: 호스트, 클라이언트, 서버

참여자는 셋이다.

| 이름 | 하는 일 | 예 |
|---|---|---|
| MCP 호스트 | AI 앱. 클라이언트들을 만들고 관리한다 | Claude Code, Claude Desktop, VS Code |
| MCP 클라이언트 | 서버 하나와 연결을 유지하고 컨텍스트를 받아 호스트에 넘긴다 | 호스트 안의 객체 |
| MCP 서버 | 컨텍스트를 제공하는 프로그램 | 파일시스템 서버, Sentry 서버 |

핵심은 서버 하나에 클라이언트 하나가 따로 붙는다는 점이다. 문서의 예시가 이해하기 쉽다. VS Code가 Sentry MCP 서버에 연결하면 클라이언트 객체 하나가 생기고, 로컬 파일시스템 서버에 또 연결하면 클라이언트 객체가 하나 더 생긴다.

```
호스트(AI 앱)
 ├─ 클라이언트 1 ── 서버 A (로컬: 파일시스템)
 ├─ 클라이언트 2 ── 서버 B (로컬: DB)
 └─ 클라이언트 3 ── 서버 C (원격: Sentry)
```

"서버"라는 말이 헷갈렸는데, 문서가 따로 짚는다. 서버는 어디서 돌든 컨텍스트를 내주는 프로그램을 가리킨다. 내 PC에서 돌면 로컬 서버, 인터넷 건너편에서 돌면 원격 서버다.

### 두 겹: 데이터 계층과 전송 계층

- 데이터 계층: JSON-RPC 2.0 기반으로 메시지의 모양과 뜻을 정한다. 기능 탐색(discovery), 도구·리소스·프롬프트, 알림이 여기 있다.
- 전송 계층: 메시지를 실제로 나르는 통로다. 두 가지가 있다.
  - stdio: 같은 PC 안의 프로세스끼리 표준 입출력으로 주고받는다. 네트워크 비용이 없다. 주로 로컬 서버가 쓰고, 보통 클라이언트 하나를 상대한다.
  - Streamable HTTP: HTTP POST에 필요하면 Server-Sent Events를 얹는다. 원격 서버용이고 보통 여러 클라이언트를 상대한다. 인증은 bearer 토큰, API 키 등을 쓰고, 문서는 OAuth로 토큰을 받기를 권장한다.

## 서버가 내놓는 세 가지

서버가 줄 수 있는 것은 세 가지(프리미티브)다. 각각 누가 쓸지 결정하는지가 다르다는 점이 재미있었다.

| 종류 | 무엇 | 예 | 누가 쓸지 정하나 (명세 표현) |
|---|---|---|---|
| 도구(Tools) | 실행할 수 있는 함수 | 파일 작업, API 호출, DB 질의 | model-controlled, 모델이 알아서 찾아 부름 |
| 리소스(Resources) | 맥락이 되는 데이터 | 파일 내용, DB 레코드, 스키마 | application-driven, 호스트 앱이 어떻게 넣을지 결정 |
| 프롬프트(Prompts) | 재사용하는 템플릿 | 시스템 프롬프트, few-shot 예시 | user-controlled, 사용자가 직접 고름 |

문서의 예시로 묶어 보면 이렇다. 데이터베이스용 서버라면 질의하는 도구, 스키마를 담은 리소스, 그 도구를 쓰는 few-shot 예시를 담은 프롬프트를 같이 내놓을 수 있다.

프롬프트는 슬래시 명령으로 노출하는 예가 명세에 나온다. 도구는 모델이 부르지만 명세는 "신뢰와 안전을 위해 거부할 수 있는 사람이 항상 있어야 한다(SHOULD)"고 적는다. 어떤 도구가 노출되는지 보여 주고, 호출될 때 표시를 하고, 확인을 받으라는 권고다. 다만 프로토콜이 이런 상호작용 방식을 강제하지는 않는다고 같은 문서에 있다.

세 가지 모두 `*/list`로 목록을 받고, 가져오는 방식이 있다. 리소스는 `resources/read`, 프롬프트는 `prompts/get`, 도구는 `tools/call`이다. 목록이 동적이어서, 도구가 바뀌면 서버가 알림을 보내 클라이언트가 목록을 다시 받는다.

<details>
<summary>자세한 풀이: 도구 호출이 오가는 모양</summary>

아키텍처 문서의 예시를 줄여 옮기면 이렇다. 먼저 `tools/list`를 보내면 서버가 도구 목록을 돌려준다. 각 도구에는 `name`, `title`, `description`, 입력 형식을 JSON Schema로 적은 `inputSchema`가 있다.

```json
{ "method": "tools/call",
  "params": { "name": "weather_current",
              "arguments": { "location": "San Francisco", "units": "imperial" } } }
```

응답은 `content` 배열에 텍스트나 이미지 등이 담겨 온다. 명세는 도구 실행 오류를 두 가지로 나눈다. 모르는 도구처럼 요청 자체가 잘못된 경우는 JSON-RPC 오류로, 날짜 형식이 틀렸다 같은 입력·로직 오류는 `isError: true`가 붙은 결과로 돌려준다. 뒤쪽은 모델이 읽고 고쳐서 다시 시도하라고 있는 것이다.

호스트 쪽 흐름은 문서의 의사코드대로, 모델이 도구를 쓰겠다고 하면 앱이 그 호출을 가로채 알맞은 서버로 보내고, 결과를 모델 대화에 다시 넣는다.

참고로 이번에 읽은 문서(최신 버전 표기 2026-07-28)는 요청마다 프로토콜 버전과 능력을 `_meta`에 실어 보내는 무상태 방식으로 적혀 있다. 이전 버전에서는 연결 시작 때 협상하는 초기화 단계가 있었던 걸로 기억하는데, 그건 이번에 확인하지 않았다.

</details>

## 서버가 클라이언트에 요청하는 것

반대 방향의 기능도 있다. 최신 문서 기준으로 서버가 사용자에게 추가 입력이나 확인을 요청하는 elicitation이 있다. sampling(서버가 클라이언트의 LLM에 완성을 요청)과 logging은 이 버전부터 deprecated로 표시돼 있다. 이 부분은 버전에 따라 바뀌는 중이라 쓸 때 해당 버전 문서를 다시 봐야 한다.

## 일반 function calling과 뭐가 다른가

여기는 공식 MCP 문서가 직접 비교한 글을 읽은 게 아니라, 읽은 내용으로 내가 정리한 것이다.

| | function calling | MCP |
|---|---|---|
| 정체 | 모델 API가 도구 호출을 표현하는 방식 | 앱과 외부 시스템 사이의 연결 규격 |
| 도구 정의 | 앱 코드가 요청마다 직접 넣는다 | 서버가 `tools/list`로 알려 준다 |
| 도구 실행 | 앱이 직접 구현한다 | 서버가 실행한다(원격이면 다른 조직 것도 가능) |
| 범위 | 도구 | 도구, 리소스, 프롬프트 |

둘은 경쟁 관계가 아니라 층이 다르다. 호스트는 MCP 서버에서 받은 도구 목록을 모델에 넘기고, 모델이 호출을 내놓으면 `tools/call`로 서버에 전달한다. 모델 쪽에서 보면 여전히 도구 호출이고, 그 도구가 어디서 왔는지가 달라진 것이다. 문서도 "MCP는 AI 앱이 LLM을 어떻게 쓰는지는 정하지 않는다"고 하니 모델 API 쪽은 건드리지 않는다.

그래서 이득은 "한 앱 안에서 도구를 부르는 법"이 아니라 "앱과 도구 제작자가 서로 모르고도 연결되는 법"에 있다.

## 보안 주의점

MCP 서버는 코드를 실행하거나 데이터를 읽을 수 있으니 연결은 곧 권한을 내주는 일이다. 공식 보안 문서와 도구 명세에서 눈에 띈 것만 적는다.

- 로컬 서버 위험: 설정에 악성 시작 명령이 들어 있거나, 서버 자체에 악성 코드가 있거나, 켜 둔 로컬 서버를 DNS rebinding으로 건드릴 수 있다. 문서는 한 번에 설정되는 로컬 서버를 연결할 때 실제로 실행될 명령을 잘리지 않게 보여 주고 명시적으로 승인받으라고(MUST) 한다. 샌드박스에서 최소 권한으로 돌리는 것도 권고한다.
- 토큰 패스스루 금지: MCP 서버가 자기를 위해 발급되지 않은 토큰을 받아서 아래쪽 API로 그대로 넘기는 것은 안티패턴이다. 문서는 서버가 자기에게 발급된 토큰만 받아야 한다(MUST NOT 그 외 수락)고 한다.
- Confused deputy: 제3자 API와 연결해 주는 MCP 프록시 서버가 고정 클라이언트 ID, 동적 클라이언트 등록, 동의 쿠키가 겹치면 사용자 동의 없이 인증 코드를 빼앗길 수 있다. 클라이언트별로 동의를 따로 받는 것이 필수 대책이다.
- SSRF: 악성 서버가 OAuth 메타데이터 URL을 내부망이나 클라우드 메타데이터 주소(169.254.169.254)로 채워 클라이언트가 따라가게 만들 수 있다. 사설 IP 차단과 HTTPS 강제 등이 대책이다.
- 권한 범위 최소화: `files:*`, `admin:*` 같은 넓은 scope를 처음부터 받으면 토큰이 새었을 때 피해가 커진다. 처음엔 읽기 위주의 작은 scope로 시작하고 필요할 때 올리라고 한다.
- 도구 명세의 권고: 서버는 입력 검증, 접근 통제, 호출 횟수 제한, 출력 정리를 해야 하고(MUST), 클라이언트는 민감한 동작에 사용자 확인을 받고 서버로 보내기 전 입력을 사용자에게 보여 주라고(SHOULD) 한다. 도구의 annotations(동작 설명 메타데이터)는 신뢰할 수 있는 서버에서 온 게 아니면 믿으면 안 된다(MUST consider untrusted).

내가 직접 확인하지 못한 건 도구 설명에 숨은 지시를 넣는 공격(tool poisoning)이나 외부 문서에 지시를 심는 prompt injection이 이 공식 문서에서 어떻게 다뤄지는지다. 이번에 읽은 보안 문서 본문에서는 그 단어를 따로 찾지 못했다. 다만 서버가 돌려준 도구 결과와 설명도 결국 모델의 컨텍스트에 들어가니, 신뢰할 수 있는 서버만 연결하는 게 기본이라고 이해했다. 이건 내 해석이다.

## 흔한 오해

- MCP가 도구다: MCP는 도구가 아니라 도구를 붙이는 규격이다. 도구는 서버가 내놓는다.
- MCP를 쓰면 모델이 더 똑똑해진다: 모델은 그대로고 받을 수 있는 컨텍스트와 할 수 있는 동작이 늘어날 뿐이다.
- 서버는 원격에만 있다: stdio로 내 PC에서 도는 로컬 서버가 흔하다.
- 규격이 있으니 안전하다: 규격은 권고를 담았을 뿐 실제 안전은 서버를 고르는 일과 클라이언트의 승인 UI에 달렸다.
- 도구만 있다: 리소스와 프롬프트도 있다. 도구 말고는 덜 쓰이는 것 같긴 한데, 그건 체감이고 통계는 못 찾았다.
