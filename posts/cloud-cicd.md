CI/CD는 코드를 합치고 테스트하고 내보내는 과정을 자동으로 돌리는 것이고, 배포 전략은 그 마지막 "내보내는" 단계를 안 터지게 하는 방법이다.

## 먼저 말부터

CI는 Continuous Integration, 지속적 통합이다. 여러 사람이 짠 코드를 자주 합치고, 합칠 때마다 빌드와 테스트를 자동으로 돌려서 깨진 걸 바로 알아내는 쪽이다.

CD는 두 가지로 읽힌다. Continuous Delivery는 테스트까지 통과한 결과물을 언제든 배포할 수 있는 상태로 만들어 두는 것이고, 마지막 배포 버튼은 사람이 누른다. Continuous Deployment는 그 버튼마저 없애서 통과하면 바로 서비스에 나간다. 글마다 CD가 둘 중 어느 쪽인지 다르게 쓰니, 읽을 때 어느 쪽 얘기인지 확인하는 게 낫다.

자동화가 왜 필요하냐면, 손으로 하면 순서를 빼먹기 때문이다. "테스트 돌렸나?", "빌드 환경이 내 PC랑 다른데?" 같은 일이 배포 때 터진다. 한 번 스크립트로 적어 두면 누가 해도 같은 순서로 돈다.

## 파이프라인은 이런 모양이다

파이프라인은 단계가 줄줄이 이어진 길이고, 앞 단계가 실패하면 뒤로 안 간다.

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| 코드 푸시 | 브랜치에 올리거나 PR을 연다 | (시작점) |
| 빌드 | 의존성 설치, 컴파일, 필요하면 [Docker 이미지](#/post/cloud-docker) 만들기 | 여기서 멈춤 |
| 테스트 | 단위·통합 테스트, 린트 ([자세히 → 백엔드 테스트](#/post/be-testing)) | 여기서 멈춤 |
| 산출물 보관 | 이미지·번들에 버전 붙여 저장 | 여기서 멈춤 |
| 배포 | 스테이징 → 운영 순으로 내보내기 | 롤백 |
| 확인 | 헬스체크, 지표 보기 ([자세히 → 모니터링](#/post/cloud-observability)) | 롤백 |

앞쪽 절반(빌드·테스트)이 CI, 뒤쪽 절반(산출물·배포)이 CD라고 보면 된다. 파이프라인이 도는 원동력은 [Git](#/post/cs-git) 이벤트다. 푸시나 PR 같은 일이 생기면 트리거가 되어 자동으로 시작한다.

한 가지 눈여겨볼 점은 한 번 만든 산출물을 환경마다 다시 빌드하지 않고 그대로 옮긴다는 것이다. 스테이징에서 테스트한 이미지와 운영에 나가는 이미지가 같아야 "스테이징에선 됐는데"가 줄어든다. 환경마다 달라지는 건 이미지가 아니라 설정과 [시크릿](#/post/cloud-secrets)이다.

## GitHub Actions는 이렇게 생겼다

GitHub Actions는 GitHub 저장소 안에서 파이프라인을 돌리는 서비스다. 공식 문서는 구성요소를 이렇게 나눈다.

- workflow: 하나 이상의 job을 실행하는 자동화 단위. 저장소의 `.github/workflows` 폴더에 YAML 파일로 둔다.
- event: workflow를 시작시키는 저장소 활동. PR을 열거나 푸시하는 것.
- job: 같은 runner에서 함께 도는 step 묶음.
- step: job 안에서 순서대로 실행되는 하나의 작업. 쉘 스크립트이거나 action이다.
- action: 재사용할 수 있게 만들어 둔 작업. 남이 만든 걸 가져다 쓴다.
- runner: job을 실제로 실행하는 서버.

대충 이런 파일이 된다. 구조를 보여주려고 쓴 예시이고 실행해 본 건 아니다.

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:          # PR이 열리거나 갱신되면
  push:
    branches: [main]     # main에 합쳐지면
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4     # 코드 내려받기
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
  deploy:
    needs: test                        # test가 성공해야 시작
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "여기서 배포 명령"
```

`needs: test`가 파이프라인의 "앞 단계 실패하면 뒤로 안 간다"를 그대로 옮긴 줄이다. 배포에 필요한 키는 YAML에 적지 않고 저장소의 시크릿 설정에서 꺼내 쓴다. 코드에 키를 적어 두면 그대로 유출이다.

<details>
<summary>자세히: job이 병렬로 도는 방식과 흔한 막힘</summary>

job은 기본적으로 서로 독립이라 동시에 돈다. 순서를 잡고 싶을 때만 `needs`를 건다. 그리고 job마다 새 runner에서 시작하기 때문에 앞 job에서 만든 파일이 뒤 job에 자동으로 따라오지 않는다. 넘기려면 산출물(artifact)로 올리고 내려받아야 한다. 이 부분에서 "분명 빌드했는데 파일이 없다" 하고 막히는 경우가 많다고 한다.

의존성 설치가 매번 느리면 캐시를 붙일 수도 있다. 다만 이 글에서 구체적인 캐시 설정은 확인하지 않았다.
</details>

## 배포 전략 세 가지

테스트를 통과해도 운영에서 문제가 생길 수 있다. 그래서 새 버전을 한 번에 갈아끼우지 않고, 문제가 생겨도 피해를 줄이고 빨리 되돌릴 수 있게 내보내는 방법이 따로 있다.

| 방식 | 핵심 | 장점 | 부담 |
|---|---|---|---|
| 롤링 | 인스턴스를 조금씩 새 버전으로 교체 | 추가 자원이 적다 | 교체 중엔 새·옛 버전이 섞인다 |
| 블루그린 | 같은 환경 두 벌, 라우터만 전환 | 되돌리기가 빠르다 | 환경이 두 벌이라 자원이 두 배 |
| 카나리 | 소수 사용자에게만 먼저 노출 | 피해 범위가 작다 | 트래픽 나누는 장치와 지표 보기가 필요 |

### 롤링

옛 인스턴스를 한꺼번에 내리지 않고 하나씩 새 걸로 바꿔 간다. Kubernetes의 Deployment가 기본으로 쓰는 방식이다. 문서 설명으로는 새 Pod가 뜨기를 기다린 다음 옛 Pod를 내리고, Service는 요청을 받을 수 있는 Pod에만 트래픽을 보낸다. 그래서 복제본이 여러 개여야 무중단이 된다.

속도와 안전은 두 값으로 조절한다. `maxUnavailable`은 업데이트 중 동시에 내려가도 되는 Pod 수이고, `maxSurge`는 원하는 개수보다 더 띄워도 되는 Pod 수다. 숫자나 퍼센트로 쓴다. `maxUnavailable: 0`에 `maxSurge: 1`이면 용량이 한 번도 줄지 않는 조심스러운 방식이 된다. 기본값은 튜토리얼 본문엔 1이라고 나오는데 Deployment API는 둘 다 25%라서, 쓰는 버전 문서를 보는 게 맞다.

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # 동시에 최대 1개까지 내려감
      maxSurge: 1         # 최대 1개까지 더 띄움
```

롤백도 같은 도구 안에 있다. 업데이트는 버전으로 기록되고 `kubectl rollout undo deployments/<이름>`이면 이전 상태로 돌아간다. 특정 리비전으로 가려면 `--to-revision=N`을 붙인다. 이 YAML과 명령도 위 문서에서 옮겨 온 것이고 내가 클러스터에서 돌려 보진 않았다.

### 블루그린

운영 환경을 최대한 똑같이 두 벌 만든다. 하나는 지금 손님을 받는 쪽(블루), 다른 하나는 놀고 있는 쪽(그린)이다. 새 버전은 놀고 있는 그린에 올려 최종 테스트하고, 괜찮으면 라우터가 모든 요청을 그린으로 보내게 바꾼다. Martin Fowler의 글은 문제가 생기면 라우터를 도로 돌려서 빠르게 되돌린다고 설명한다. 전환 뒤엔 블루가 다음 릴리스의 대기 환경이 되어 둘이 번갈아 쓰인다. 이 "라우터를 바꾼다"는 부분이 [로드밸런서](#/post/infra-load-balancer)가 하는 일이다.

까다로운 건 DB다. 두 환경이 같은 DB를 쓰면 스키마를 바꿀 때 옛 앱과 새 앱이 둘 다 돌아가야 한다. Fowler의 글은 하위 호환되는 스키마 변경을 먼저 배포하고, 그다음에 새 앱을 올리라고 한다. 전환하는 사이 쌓인 거래를 어떻게 다룰지도 따로 정해야 한다. 이 얘기는 [트랜잭션](#/post/db-transaction)과도 이어진다.

### 카나리

광산의 카나리아에서 따온 이름이다. 새 버전을 일부 인프라에 올리고 처음엔 사용자를 안 보낸다. 그다음 소수만 보낸다. 고르는 방법은 무작위, 사내 직원 먼저, 사용자 특성 기준 등이 있고 규모가 크면 지역이나 브랜드로 나누기도 한다. 문제가 없으면 점점 늘려서 전부 새 버전으로 보내고, 옛 인프라는 내린다. 이상하면 사용자를 옛 버전으로 다시 돌린다.

블루그린이 "한 번에 전부 전환"이라면 카나리는 "조금씩 전환"이다. 중간에 두 버전이 동시에 돌아간다는 점이 다르고, 천천히 부하를 올리면서 운영에서 용량을 시험해 볼 수도 있다. 대신 얼마만큼 보낼지, 언제 늘릴지를 판단하려면 에러율 같은 지표가 있어야 한다. 지표가 없는 카나리는 그냥 느린 배포다.

## 롤백은 계획에 넣어 둔다

세 방식 모두 되돌리는 방법이 달라서, 배포 전에 "이상하면 어떻게 돌아가나"를 정해 두는 게 중요하다.

- 롤링: 이전 리비전으로 되돌리면 다시 롤링으로 교체된다. 되돌리는 데도 시간이 든다.
- 블루그린: 라우터만 다시 돌리면 되니 가장 빠르다.
- 카나리: 보내던 사용자를 옛 버전으로 돌린다. 피해를 본 사용자가 소수라는 게 장점이다.

되돌릴 수 없는 변경이 끼면 이 얘기가 다 어려워진다. DB 컬럼을 지우는 마이그레이션이 대표적이다. 코드는 옛 버전으로 돌아가도 데이터는 안 돌아온다. 그래서 스키마는 "추가 먼저, 삭제는 나중에" 두 번에 나눠서 하는 편이 낫다. 롤백 판단의 근거는 결국 모니터링 지표다. 되돌릴지 말지는 에러율과 응답 시간을 보고 정한다.

## 흔한 오해

- CI/CD가 있으면 배포가 안전해진다: 자동화는 같은 순서를 반복해 줄 뿐이다. 테스트가 부실하면 부실한 코드가 자동으로 운영까지 간다.
- 블루그린이면 DB 걱정이 없다: 환경이 두 벌이어도 DB를 같이 쓰면 스키마 호환 문제가 그대로 남는다.
- 롤링은 무중단이 보장된다: 복제본이 하나뿐이거나 `maxUnavailable` 설정이 용량을 깎으면 끊길 수 있다.
- 카나리와 블루그린은 같은 말이다: 초기에 새 버전을 따로 올린다는 점은 비슷한데, 한 번에 바꾸느냐 비율로 늘리느냐가 다르다.
- 배포와 릴리스는 같다: 코드를 서버에 올리는 것과 사용자에게 보이게 하는 건 따로 할 수 있다. 이 글에선 이 구분을 더 파고들지 않았다.

## 확인 못 함

- GitHub Actions의 최소 YAML 예시는 공식 문서 페이지에서 확인하지 못해 직접 구성했고, 실행해 보지 않았다.
- Kubernetes 롤링 설정과 `kubectl` 명령은 문서 내용을 옮긴 것이고 클러스터에서 실행 확인하지 못했다.
- Actions의 캐시·artifact 세부 설정, 환경(environment) 승인 기능은 읽지 않았다.
