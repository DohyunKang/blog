그리디는 매 단계에서 지금 가장 좋아 보이는 선택을 하고, 한 번 고른 건 되돌리지 않는 방식이다. 코드는 짧은데 이 방식이 정답을 주는지 확인하는 게 문제의 대부분이다.

## 그리디가 뭔지

탐욕 알고리즘이라고도 부른다. 위키피디아 설명으로는 각 단계에서 지역적으로 최적인 선택을 하고 이전 선택을 다시 따지지 않는 알고리즘이다. 같은 글에서 동적 계획법의 극단적인 형태, 즉 부분 해를 하나만 들고 가는 방식이라고도 한다. DP는 여러 후보를 다 들고 가면서 비교하는데, 그리디는 하나만 남기고 나머지는 버린다.

그래서 빠르다. 대신 틀릴 수 있다. 가장 큰 숫자를 따라 올라가는 길이 마지막에 막다른 길일 수도 있다.

## 언제 되는가

두 가지가 맞아야 한다.

| 조건 | 뜻 |
| --- | --- |
| 탐욕 선택 속성 | 지금 제일 좋아 보이는 선택을 해도, 그걸 포함한 최적해가 존재한다 |
| 최적 부분 구조 | 그 선택을 하고 남은 문제도 같은 종류의 문제이고, 그 최적해를 붙이면 전체 최적해가 된다 |

위키피디아 본문은 이 용어를 직접 쓰지 않고 교환 논법(exchange argument)으로 설명한다. 최적해와 그리디 해가 처음 달라지는 지점에서 최적해의 선택을 그리디 선택으로 바꿔 봤을 때 결과가 나빠지지 않으면, 귀납법으로 그리디가 최적이라는 결론이 난다.

코테에서는 증명까지 쓰지는 않는다. 정렬 기준을 하나 정하고, 반례를 몇 개 손으로 찾아보고, 안 나오면 그 기준으로 간다. 반례를 못 찾는 것과 증명한 것은 다르긴 해서, 조금 불안한 채로 제출하게 된다.

## 대표 문제

문제 본문은 옮기지 않고 번호와 이름만 적는다.

- 백준 1931 회의실 배정: 한 회의실에서 겹치지 않게 최대한 많은 회의를 잡는다.
- 백준 11047 동전 0: 동전 종류가 서로 배수 관계일 때 최소 개수로 금액을 만든다.
- 백준 1202 보석 도둑: 가방 용량과 보석 무게·가치가 주어질 때 최대 가치를 담는다. 정렬에 힙을 같이 쓴다.
- 프로그래머스 구명보트: 한 번에 최대 두 명, 무게 제한 안에서 보트를 최소로 쓴다.

## 풀이 생각 순서

1. 최적화 문제인지 본다(최대·최소).
2. 정렬 기준 후보를 몇 개 세운다. 시작 시각, 끝 시각, 길이, 단가 같은 것들.
3. 기준마다 반례를 직접 그려 본다. 작은 입력 3~4개면 대부분 걸러진다.
4. 반례가 안 나오는 기준이 남으면 교환 논법으로 한 번 따져 본다.
5. 끝까지 불안하면 DP나 완전탐색으로 작은 입력을 비교해 본다.

회의실 배정은 가장 일찍 끝나는 회의를 먼저 잡는 게 답이다. 일찍 시작하는 것부터 잡으면 (1,10) 하나가 (2,3), (4,5) 두 개를 막는다. 짧은 것부터 잡는 것도 반례가 있다. 교환 논법은 이렇게 간다. 최적해의 첫 회의를 끝나는 시각이 가장 빠른 회의로 바꿔도 겹치는 게 없고 개수도 같으니, 그리디 선택을 포함한 최적해가 있다. 이 문제는 위키피디아의 activity selection problem 문서에도 같은 방식으로 나온다.

## Python 코드

아래 코드는 모두 실제로 돌려서 값을 확인했다. 회의실 배정은 무작위 소규모 입력 300개로 완전탐색 결과와도 맞춰 봤다.

```python
def max_meetings(iv):
    iv.sort(key=lambda x: (x[1], x[0]))   # 끝나는 시각, 같으면 시작 시각
    cnt, end = 0, -1
    for s, e in iv:
        if s >= end:
            cnt += 1
            end = e
    return cnt

print(max_meetings([(1,4),(3,5),(0,6),(5,7),(3,8),(5,9),(6,10),(8,11),(8,12),(2,13),(12,14)]))  # 4
```

끝나는 시각이 같을 땐 시작 시각으로 정렬해야 시작과 끝이 같은 회의(길이 0)도 안 틀린다. 백준 1931에 그런 입력이 실제로 있다고 알려져 있는데, 이 부분은 직접 확인하지 못했다.

동전 문제는 단위가 배수 관계라 그리디가 된다.

```python
def coin_greedy(coins, k):
    cnt = 0
    for v in sorted(coins, reverse=True):
        cnt += k // v
        k %= v
    return cnt if k == 0 else -1

print(coin_greedy([500, 100, 50, 10], 1260))  # 6
```

힙을 같이 쓰는 형태도 많다. 회의가 몇 개 동시에 겹치는지 세는 회의실 개수 문제다.

```python
import heapq

def min_rooms(iv):
    iv.sort()                      # 시작 시각순
    h = []                         # 쓰고 있는 방들의 끝나는 시각
    for s, e in iv:
        if h and h[0] <= s:
            heapq.heapreplace(h, e)   # 비는 방 재사용
        else:
            heapq.heappush(h, e)      # 새 방
    return len(h)

print(min_rooms([(0, 30), (5, 10), (15, 20)]))  # 2
```

<details>
<summary>허프만 코딩 합치기 비용 (우선순위 큐 그리디)</summary>

가장 작은 두 개를 계속 합치는 방식이다. 허프만 트리가 이렇게 만들어진다고 위키피디아에도 적혀 있다. 합치는 비용의 합을 구하면 다음과 같다.

```python
import heapq

def merge_cost(ws):
    h = list(ws)
    heapq.heapify(h)
    total = 0
    while len(h) > 1:
        a, b = heapq.heappop(h), heapq.heappop(h)
        total += a + b
        heapq.heappush(h, a + b)
    return total

print(merge_cost([10, 20, 30, 40]))  # 190
```

10+20=30, 30+30=60, 40+60=100, 합계 190이다.

## 시간·공간 복잡도

정렬이 지배한다. 회의실 배정은 정렬 O(n log n) + 한 번 훑기 O(n)이라 전체 O(n log n)이고, 공간은 정렬을 제자리에서 하면 O(1)이다(파이썬 `sort`는 내부적으로 보조 공간을 쓰긴 한다). 힙을 쓰는 문제는 푸시·팝이 O(log n)이라 마찬가지로 O(n log n)이다. [시간복잡도 읽는 법 → 시간복잡도와 파이썬 기본](#/post/algo-complexity)

## 흔한 오해와 반례

그리디가 안 되는 대표 예가 동전이다. 동전이 1, 4, 5원이고 8원을 만든다면 그리디는 5+1+1+1로 4개를 쓰지만 답은 4+4로 2개다. 위의 `coin_greedy`는 단위가 배수 관계일 때만 맞고, 이 입력에는 쓰면 안 된다. 이런 문제는 [동적 계획법](#/post/algo-dp)으로 푼다. 아래 DP 코드로 2가 나오는 것을 확인했다.

```python
def coin_dp(coins, k):
    INF = 10**9
    d = [0] + [INF] * k
    for i in range(1, k + 1):
        for v in coins:
            if i >= v:
                d[i] = min(d[i], d[i - v] + 1)
    return d[k] if d[k] < INF else -1

print(coin_dp([1, 4, 5], 8))  # 2
```

배낭도 같은 구조다. 쪼갤 수 있으면(분할 가능 배낭) 단위 무게당 가치가 큰 순으로 담는 그리디가 맞고, 쪼갤 수 없으면(0-1 배낭) 틀린다. 물건이 (무게, 가치) = (10,60), (20,100), (30,120)이고 용량이 50일 때 분할 가능이면 240, 0-1이면 220이다. 0-1 배낭은 NP-hard라고 위키피디아에 적혀 있다. 위의 두 값은 코드로 돌려 확인했다.

또 하나, 가중치가 붙으면 회의실 배정도 그리디가 깨진다. 위키피디아의 activity selection 문서에도 가중치 버전에는 그리디 해법이 없다고 나오고, DP로 푼다고 한다.

자주 하는 착각은 정렬만 하면 그리디라는 생각이다. 정렬은 도구일 뿐이고, 그 정렬 기준이 맞다는 근거가 있어야 그리디다. 문제를 풀 때 그리디가 먼저 떠오르면 DP로 풀 수 있는지, 반례가 없는지를 같이 확인하는 쪽이 낫다.

그리디가 맞게 쓰이는 알고리즘도 많다. 다익스트라(음수 간선 없을 때), 크루스칼·프림의 최소 신장 트리, 허프만 코딩이 위키피디아에 그리디 예로 나온다. 에드먼즈가 매트로이드 구조를 가진 문제에는 그리디가 최적이라는 것을 보였고, 이후 그리도이드로 일반화됐다는 설명도 있다. [다익스트라 → 최단 경로·유니온 파인드·위상 정렬](#/post/algo-shortest-path) / [힙 → 트리·힙·우선순위 큐](#/post/algo-tree-heap) / [정렬 → 정렬과 이분 탐색](#/post/algo-sort-search)
