要在本地 PC 运行大模型，首先必须将其加载到内存中。因此有两种压缩方法：量化（Quantization）是将同一模型的数值以更少的位数存储；蒸馏（Distillation）则是将大模型的行为“教”给小模型。这两个名字听起来很相似，容易混淆，但它们针对的对象不同。

## 模型占用多少内存

[LLM](#/post/ai-llm) 的大小是指参数量（权重）的个数。例如"8B"即代表 80 亿个参数。每个参数在内存中占用的大小取决于其精度。

```
가중치 메모리 ≈ 파라미터 수 × 숫자 하나의 바이트 수
```

| 精度 | 单个数值大小 | 8B 模型 | 70B 模型 |
|---|---|---|---|
| FP16 / bf16 | 2 字节 | 约 16GB | 约 140GB |
| 8 位 (8-bit) | 1 字节 | 约 8GB | 约 70GB |
| 4 位 (4-bit) | 0.5 字节 | 约 4GB | 约 35GB |

Hugging Face 的量化文档也指出，8B 模型在 bf16 下约为 16GB，在 8 位下约为 8GB，在 4 位下为 4~5GB。4 位并非精确等于 4GB 而是 4~5GB，这可能是因为附加了类似缩放因子（scale）的额外信息（表中 70B 列的值是直接套用上述计算公式得出的）。

## 量化：以粗糙的方式存储数值

量化是一种通过用较少的位数存储权重来减少内存占用的方法。根据文档描述，它甚至可以将权重以及某些情况下的激活值（activations）也用较少的位数存储，从而降低模型所需的内存。然而，位数减少会导致精度略有下降，且不同方法在内存、速度和精度之间的权衡各不相同。

打个比方，这就像压缩照片文件容量。如果将原始图像的细微数值四舍五入到较近的刻度进行存储，文件容量就会减小；而刻度间隔越稀疏，存储值与原始值的差异就越大。这种差异就是质量损失。

<details>
<summary>详细解释：四舍五入刻度示例（自制简单示例）</summary>

假设一个权重值为 0.37。如果用 8 位存储，可以在 256 个刻度中选择一个最接近的值进行存储；而如果是 4 位，则只有 16 个刻度，因此可能需要四舍五入到更远的刻度。实际的方法更为精细，通常是针对每组数值单独设置一个缩放因子（即刻度间隔），这比上述示例更复杂。关于分组大小等划分方式，可参考 Hugging Face 的量化概念指南。

### 这些名字是什么意思

阅读关于量化的内容时，经常会看到 GGUF、GPTQ、AWQ 等名称混杂出现。它们并不属于同一层级。

| 名称 | 本质 |
|---|---|
| GGUF | 文件格式。它将权重、配置和分词器打包到一个文件中（HF 文档）。常用于 llama.cpp 系列 |
| GPTQ | 量化方法（论文）。通过近似二阶信息，在保持精度的同时一次性完成量化 |
| AWQ | 量化方法（论文）。这是一种仅降低权位数目的低比特方式，并保护约 1% 的重要权重 |
| bitsandbytes | 一个库，用于在加载时将模型转换为 4 位或 8 位。出现在 HF 文档示例中 |
| Q4_K_M 等名称 | 附加在 GGUF 文件名上的量化类型标识。出现在 HF 文档示例文件名中 |

因此，“是 GGUF 还是 GPTQ"并不是完全相同的选项。GGUF 是容器，而 GPTQ、AWQ 则是压缩算法的名称。

### GPTQ 和 AWQ 做了什么

GPTQ 论文（Frantar 等，2022, arXiv 2210.17323）提出了一种对 GPT 系列模型进行一次性量化的方法。根据摘要，即使将权重压缩到 3~4 位，与原始模型相比精度损失也微乎其微；他们成功将 1750 亿参数的模型在约 4 GPU 小时内完成量化，并使其能够在单张 GPU 上进行生成推理。与 FP16 相比，A100 上的速度提升约为 3.25 倍，A6000 上约为 4.5 倍。

AWQ 论文（Lin 等，2023, arXiv 2306.00978）的观察结果是：并非所有权重都同样重要。如果保护约 1% 的重要通道，量化误差会大幅降低；判断哪个通道重要，依据的是激活值的统计信息而非权重大小。摘要中也提到无需反向传播或重构。

这两种方法都是解决“如何四舍五入才能最小化损失”的问题。HF 文档指出，仅在加载时 GPTQ 需要校正数据集，而大多数其他方法则不需要。

### 质量损失有多大

这取决于具体方法、模型和比特数。GPTQ 论文声称在 3~4 位下精度损失几乎可以忽略，并在 2 位或三进制水平上也报告了可用的精度，但这并不意味着适用于所有模型。一旦确定了要使用的模型，最好通过自己的实验直接进行比较。性能比较的基准可以在 [AI 模型指南](#/post/ai-models) 等地方先查看。

## 蒸馏：大模型教小模型

蒸馏是一种不同的缩小模型尺寸的方法。它不是粗略地存储数字，而是训练一个较小的新模型，使其学习来自大模型的输出。较大的模型被称为“教师”（teacher），较小的模型被称为“学生”（student）。

Hinton 等人的论文《Distilling the Knowledge in a Neural Network》（2015, arXiv 1503.02531）的摘要是这样开头的：“使用相同数据训练多个模型并对预测结果取平均的集成方法虽然能轻松提升性能，但在部署时显得沉重且昂贵。本文提出了一种将集成模型的知識压缩到单个模型中的方法。”摘要中并未出现“教师”和“学生”这两个词，这是本文使用的术语。

最终产物是一个从一开始就参数较少的独立模型。因此，其权重与原模型不同，名称也需单独指定。虽然可以看到大模型和小模型系列有时会一起发布，似乎也是以此方式制作的，但究竟哪些模型是通过蒸馏制作的，仍需查看各模型的公开资料才能确定。

## 量化 vs 蒸馏

| | 量化 | 蒸馏 |
|---|---|---|
| 做的事情 | 用较少的比特存储同一模型的数字 | 利用大模型的输出来训练小模型 |
| 模型结构 | 保持不变 | 构建新的较小结构 |
| 额外训练 | 几乎没有（GPTQ 使用校准数据） | 需要 |
| 减少的内容 | 每个数字的比特数 | 参数数量 |
| 损失来源 | 舍入误差 | 学生无法模仿的部分 |
| 由谁执行 | 常直接接收并使用已量化的文件 | 通常由模型厂商完成 |

两者也可以结合使用。例如，通过蒸馏制作的小模型再被量化为 4 比特，则两种效果会叠加。

这与 LoRA 等 [微调](#/post/ai-finetuning) 不同。微调是改变行为的方式，而量化和蒸馏则是缩小尺寸的方式。

## 本地运行的工具

- **llama.cpp**：这是一个用 C/C++ 编写的开源推理项目。README 中提到它支持从 1.5 比特到 8 比特的整数量化，并指出可以将 CPU 和 GPU 混合使用，从而对超过显存容量的模型进行部分加速。它还支持 CUDA、Metal、Vulkan、HIP 等多种后端。可以通过 `-hf` 选项直接加载 Hugging Face 模型并运行，同时也支持启动 OpenAI 兼容的 API 服务器。
- **Ollama**：只需一条命令（`ollama run <模型>`）即可下载模型并进行对话，同时在 `localhost:11434` 提供 REST API。其支持的 backend 包括 llama.cpp。
- **Hugging Face Transformers**：在 `from_pretrained` 中传入量化设置后，加载时会自动进行量化；对于已量化的检查点，则会从配置中读取方法并自动加载。根据本文档，超过 20 种方法均可通过同一代码处理。不过文档指出，GGUF 格式通常在加载过程中会被还原为原始精度，因此并无显存收益，所以 GGUF 更适合在 llama.cpp 系列中使用。

<details>
<summary>详细解析：Transformers 加载示例（移自文档示例）</summary>

此处并非实际运行过的代码，而是移自 Hugging Face 文档的示例。展示的是使用 bitsandbytes 以 4 比特加载 8B 模型的形式。

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=quantization_config,
    device_map="auto",
)
```

## 如何判断是否适合放入我的 GPU

步骤很简单：

1. 检查模型参数量（通常名称中会标注，如 8B、70B 等）。
2. 根据比特数进行换算：4 比特约为参数数 (B) × 0.5GB，8 比特 × 1GB，FP16 则 × 2GB。
3. 判断该值是否远小于你的显存容量。

例如，将 8B 模型量化为 4 比特后约需 4~5GB，因此即使使用 8GB 显存的显卡也可作为候选。而 70B 模型即便量化为 4 比特仍需约 35GB，单张 24GB 显存的显卡仅靠权重就已不够用。此时 llama.cpp 的 CPU+GPU 混合运行便成为一种选择，但文档仅说明其可加速部分计算，并未给出具体的速度数据。

之所以需要预留余量，是因为除了权重外还需占用其他内存。Hugging Face 文档特别提到，在长生成过程中可使用量化缓存选项来节省 KV 缓存内存。随着对话变长，缓存大小会随 [上下文窗口](#/post/ai-context-window) 增大而增加。因此，选择比刚好适配显存的模型和比特数小一级的配置更为稳妥。同一文档中还链接了一个工具，可用于查看不同精度下模型在硬件内存中的占用情况。

## 常见误解

- 量化会让模型变聪明：并非如此，准确度反而会略有下降。文档中也提到，比特数减少会带来精度损失。
- 4 位时质量减半：GPTQ 论文摘要称，在 3~4 位时性能几乎无下降。具体效果因模型和任务而异，建议自行验证。
- GGUF 是一种量化方法：它实际上是一种文件格式。文件名中的 `Q4_K_M` 等部分表示所使用的量化类型。
- 量化与蒸馏是同一概念：如上表所示，二者缩减的对象不同。
- 量化后的模型无法进行微调：Hugging Face 文档中列出了各方法的微调支持情况对比表。是否支持取决于具体方法。
- 本地运行大模型一定很慢：速度取决于硬件和量化方式。GPTQ 论文曾报道 FP16 加速超过 3 倍的情况，但这是基于 GPU 环境的结果。
