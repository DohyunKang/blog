今朝、GitHub トレンドの週間リストに ag-ui-protocol/ag-ui があった。今週のスター 2,966、リポジトリ全体では 21,562(11月25日午前に確認)。AG-UI は、AI エージェントと人が見るアプリ画面のあいだでやり取りするデータの形を決めた公開仕様だ。README、docs の概念ドキュメント(architecture、tools、state、interrupts)、1.0 の変更点ページ、最近のコミットを読んだ。自分でサーバーを立ててはいない。

## 何を決める仕様か
普通の Web はリクエストを一つ送ってレスポンスを一つ受け取れば終わる。エージェントはそうは終わらない。文字を少しずつ流し、途中でツールを呼び、人の確認を待って止まり、サブエージェントを立ち上げる。README の冒頭がこの話だ。これを画面に出すやり方がフレームワークごとに違って、アプリごとに接続コードを書き直していたという。

AG-UI はこれをひとつのイベントの流れにまとめる。イベントは「今こういうことが起きた」という短いメッセージだ。エージェントは決まった種類のイベントを順番に出し、アプリはそれを受け取って描く。エージェントを LangGraph で作っても CrewAI で作っても、アプリ側のコードはそのままだ。

README の位置づけの図がわかりやすかった。MCP はエージェントにツールとデータをつなぎ、A2A はエージェント同士を協力させ、AG-UI はエージェントをユーザーの前に連れてくる。三つは重ならないという主張だ。MCP はエージェントが外部プログラムの機能をツールとして呼べるようにする接続仕様。[詳しく → MCP](#/post/ai-mcp)

## 構造
始まりは単純だ。アプリが HTTP POST で `RunAgentInput`(スレッド ID、実行 ID、これまでのメッセージ、アプリが提供するツール一覧、共有状態)を送ると、エージェントがイベントをストリームで返す。標準の伝送方式は SSE。SSE(Server-Sent Events)はサーバーが接続を一つ開いたままテキストを送り続ける Web 標準だ。1.0 からは Protobuf を使ったバイナリ伝送も仕様に入った。

イベントはいくつかのグループに分かれる。
- 実行の開始と終了: `RUN_STARTED`、`RUN_FINISHED`、`RUN_ERROR`
- 回答の文字: `TEXT_MESSAGE_START` → `CONTENT`(断片) → `END`
- ツール呼び出し: `TOOL_CALL_START` → `ARGS`(引数 JSON を断片で) → `END` → `RESULT`
- 共有状態: `STATE_SNAPSHOT`(全体)、`STATE_DELTA`(変わった部分だけ)

README の例の Python サーバーは30行ほどで、やっているのは開始イベント、文字イベント3回、終了イベントを順に送ることだけ。仕様が求める最低限がそのくらいということだ。

## ツールの一部は画面側が持つ
読んでいていちばん目についたのは、ツールを二種類に分けるやり方だ。エージェントのサーバーにもともとあるツールはサーバーに置く。それとは別に、アプリが実行のたびに `RunAgentInput.tools` に「今回はこのツールを使っていい」という一覧を載せて送れる。確認ダイアログを出す、画面を移動する、といったものだ。エージェントがこれを呼ぶと、実際の実行はアプリで起きる。

tools ドキュメントが挙げる理由は権限だ。このユーザーにどの機能を開くかはアプリが決め、敏感な操作はエージェントではなくアプリが握る。エージェントは判断だけして、手を動かすのはアプリという構造だ。ツール呼び出し自体が気になるなら [詳しく → ツール呼び出し](#/post/ai-tool-use)

## 状態は JSON 一つを一緒に見る
共有状態はエージェントとアプリが一緒に見る JSON オブジェクト一つだ。最初は `STATE_SNAPSHOT` で丸ごと送り、その後は `STATE_DELTA` で変わった部分だけ送る。デルタは JSON Patch(RFC 6902)形式。「このパスの値をこれに変えろ」といった指示を一覧で書く標準だ。接続が切れてつながり直したら、スナップショットを受け取り直して合わせる。エージェントが表を埋めている最中なら、画面も一緒に表を埋めていける。

## 止まって、また続ける
人の確認が必要なときの扱いがかなり厳密だ。エージェントは実行を開いたまま待たない。続きに必要な状態とメッセージを先にスナップショットで送り、`RUN_FINISHED` に「interrupt」という結果を載せて実行を終える。ユーザーが承認すると、アプリが同じスレッドで新しい実行を始め、`resume` に答えを入れて送る。

ルールもドキュメントに書かれている。開いている interrupt には全部答えなければならず、一部だけ答えることはできない。答え待ちのスレッドに resume なしで新しい入力を送るとエラー。同じ resume を二回送っても安全でなければならず、期限(`expiresAt`)を過ぎた答えは拒否される。承認ボタンを二度押したり、だいぶ後で押したりする場合まで、仕様が先に決めてあるわけだ。

## なぜ今話題なのか
リポジトリは2025年5月に作られた。新しく出たものではない。1.0 も9月に出ている(npm `@ag-ui/core` 1.0.0 が9月17日 UTC)。1.0 の変更点ページによると、0.x のころは動作ルールが実質 TypeScript クライアントのコードの中にしかなく、1.0 で初めてルールをドキュメントと JSON Schema で固めた。TypeScript、Python、.NET の SDK はそのスキーマから生成される。サブエージェントのイベント、推論過程のイベント(旧 THINKING イベントの置き換え)、実行がどう終わったかを知らせる `outcome` もこのとき入った。

今週スターが集まった正確なきっかけは確認できなかった。ただ、コミットは毎日積み上がっている。11月17日に SDK 1.0.5 と Cloudflare Agents 連携 0.1.0 が出て、その後も LangGraph、Google ADK、OpenAI Agents の連携パッケージが次々に上がった。README は Google、Microsoft、Amazon、Oracle が採用したと書いているが、これは README の主張で、各社側の発表は別に確認していない。Microsoft Agent Framework のリリースノートに AG-UI エンドポイントが出てくるのは前に見たことがある。[詳しく → Microsoft Agent Framework](#/post/news-harness-2)

ダウンロード数は大きい。npm `@ag-ui/core` は11月17〜23日の1週間で 8,050,853 回。これは他のパッケージが依存関係として引っ張ってきた分も含むので、直接使っている人数として読んではいけない。X で「AG-UI」に触れた投稿(リツイート除く、UTC 日単位)は11月18日の59件が最多で、ほかの日は14〜25件だった。Reddit の反応は確認できなかった。

## 入門者の立場から
エージェントのデモはたいていチャット欄一つで終わるが、実際のサービスでは承認ボタン、進捗表示、エージェントが埋める表のような画面がつく。AG-UI はその画面とエージェントのあいだの約束を先に決めておいたものだ。フロントエンドとバックエンドがこのイベント一覧さえ合わせれば、別々に作れる。

PM の立場で使えそうなのは interrupt のルールだ。「人が承認したら続けて進める」を企画書に一行で書くのは簡単だが、二度押したら、遅れて押したら、一部だけ承認したらどうなるかまで決めないと実際には作れない。この仕様は、その問いへの答えを一つ書いておいた例として読めた。サブエージェントになじみがなければ [詳しく → サブエージェント](#/post/ai-subagent)
