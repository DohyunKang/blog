물리 설계는 논리 설계로 끝낸 테이블을 실제 저장장치와 DBMS 위에 어떻게 올릴지 정하는 단계이고, 인덱스·파티션·분산 DB·데이터 웨어하우스는 모두 "데이터가 커졌을 때 빠르게 읽고 관리하려는 방법"이라는 한 줄로 묶인다.

## 설계 단계에서 어디쯤인가

DB 설계는 요구 분석 → 개념 설계(ER) → 논리 설계(테이블·키·정규화) → 물리 설계 → 구현 순으로 흐른다. 앞의 [정규화와 트랜잭션](#/post/jb-normalization-transaction)이 논리 설계 쪽이고, 여기서부터는 같은 테이블을 어떤 구조로 저장하느냐의 문제다. 논리 설계는 DBMS가 달라도 거의 같지만, 물리 설계는 쓰는 제품과 하드웨어를 보고 정한다.

시험에서는 물리 설계에서 하는 일을 묻는 문제가 나온다. 정리하면 이렇다.

| 하는 일 | 내용 |
|---|---|
| 저장 구조 | 테이블·인덱스를 어떤 파일과 공간에 둘지 |
| 인덱스 설계 | 어떤 컬럼에 어떤 종류를 만들지 |
| 파티션 설계 | 큰 테이블을 어떤 기준으로 쪼갤지 |
| 반정규화 | 성능 때문에 중복을 일부러 되살릴지 |
| 트랜잭션·용량 | 동시 사용량과 데이터 증가량 예측 |

반정규화는 정규화로 쪼갠 테이블을 조회 성능 때문에 다시 합치거나 컬럼을 중복해 두는 일이다. 대신 입력·수정할 때 일관성을 직접 챙겨야 한다. [SQL 응용](#/post/jb-sql-basic)에서 본 조인이 너무 많이 걸려 느릴 때 고려하는 선택지다.

## 인덱스

인덱스는 테이블에서 원하는 행을 빨리 찾으려고 따로 만들어 두는 자료구조다. 인덱스가 없으면 행을 처음부터 훑어야 하는데, 있으면 로그 시간 정도로 찾을 수 있다. 대신 저장 공간을 더 쓰고, 행을 넣거나 고치거나 지울 때 인덱스도 같이 갱신해야 해서 쓰기가 느려진다. 읽기 위주 테이블엔 유리하고 쓰기가 잦은 테이블엔 부담이 된다는 게 기본 감각이다. 더 자세한 동작은 [인덱스 글](#/post/db-index)에 따로 정리했다.

시험에 자주 나오는 구분은 이렇다.

- 구조: B-트리(균형 트리) 계열이 가장 흔하고, 해시 인덱스도 있다. 범위 검색이 필요하면 트리 쪽이 맞다.
- 클러스터드 인덱스: 테이블의 행 자체를 인덱스 순서대로 저장한다. 테이블당 하나만 만들 수 있고, 범위 조회에 유리하다.
- 논클러스터드 인덱스: 정렬된 별도 구조가 행을 가리킨다. 여러 개 만들 수 있다.
- 결합 인덱스: 컬럼 순서가 중요하다. (도시, 성, 이름) 순으로 만든 인덱스는 도시로 찾을 땐 빠르지만 성만으로 찾을 땐 효율이 떨어진다. 맨 앞 컬럼이 조건에 빠지면 잘 못 쓴다.
- 커버링 인덱스: 쿼리가 필요한 컬럼이 전부 인덱스에 들어 있어서 테이블 행을 읽지 않아도 되는 경우다.

인덱스가 효과 없는 경우도 문제로 나온다. `LIKE '%abc'`처럼 앞에 와일드카드가 붙으면 인덱스를 제대로 못 탄다. 컬럼 값이 거의 안 겹쳐야 트리 인덱스가 잘 맞고, 값이 많이 반복되는 컬럼에는 비트맵 인덱스가 어울린다고 한다.

<details>
<summary>인덱스 설계할 때 고르는 순서</summary>

1. 조회·조인·정렬에 자주 쓰이는 컬럼 후보를 뽑는다.
2. 값이 얼마나 다양한지 본다. 거의 같은 값만 있으면 효과가 작다.
3. 그 테이블에 쓰기가 얼마나 잦은지 본다. 잦으면 인덱스 수를 줄인다.
4. 결합 인덱스면 조건에 자주 등장하는 컬럼을 앞에 둔다.
5. 만든 뒤 실행 계획으로 실제로 쓰이는지 확인한다.

</details>

## 파티션

파티션은 큰 테이블 하나를 논리적으로는 하나로 두고 물리적으로 여러 조각으로 나누는 방법이다. PostgreSQL 문서 기준으로 나누는 방식은 세 가지다.

| 방식 | 기준 | 예 |
|---|---|---|
| 범위(range) | 값의 구간 | 날짜별로 월 단위 조각 |
| 리스트(list) | 값을 직접 나열 | 지역 코드별 |
| 해시(hash) | 해시값을 조각 수로 나눈 나머지 | 고객 번호를 고르게 분산 |

효과는 몇 가지다. 조건절에 파티션 기준이 있으면 해당 조각만 읽고 나머지는 건너뛴다(파티션 프루닝). 오래된 데이터는 조각째 떼어 내거나 지울 수 있어서 대량 DELETE보다 훨씬 빠르다. 자주 안 쓰는 조각은 느리고 싼 저장장치로 옮길 수도 있다. 같은 문서가 짚는 점은, 이런 이득은 보통 테이블이 아주 클 때 값어치가 있고 파티션을 무작정 많이 쪼갠다고 좋은 건 아니라는 것이다.

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

위는 PostgreSQL 공식 문서의 예를 줄인 것이다. 구문은 DBMS마다 다르니 시험에서는 문법보다 "범위·리스트·해시 중 무엇이고 왜 쓰는가"를 묻는다고 보면 된다.

## 분산 DB

분산 DB는 데이터를 서로 다른 물리 위치에 나눠 저장하되 사용자에게는 하나처럼 보이게 하는 DB다. 같은 데이터센터 안일 수도 있고 네트워크로 떨어진 곳일 수도 있다. 서버마다 부품을 공유하지 않는 느슨한 결합이 특징이고, 사용자 가까이에서 트랜잭션을 처리해 성능을 높일 수 있다는 점이 장점으로 꼽힌다.

나누는 방식은 파티션과 같은 말로 설명된다. 행을 나누면 수평 분할, 컬럼을 나누면 수직 분할이다. 수평 분할을 여러 서버에 걸쳐 하는 게 샤딩이다. 파티션이 보통 한 DB 인스턴스 안에서 쪼개는 것이라면, 샤딩은 인스턴스를 넘어 서버 여러 대에 나눈다는 차이가 있다. 샤딩은 복잡도가 크게 늘기 때문에 다른 최적화로 부족할 때 쓰라는 것이 일반적인 조언이다. 읽기를 늘리려고 같은 데이터를 여러 대에 복사해 두는 복제와의 차이는 [복제와 샤딩](#/post/db-scaling)에 따로 적었다.

복제는 사본을 최신으로 맞추는 게 일이라서 복잡하고 자원을 많이 쓴다. 한 곳을 원본으로 두고 정해진 시간에 다른 곳으로 복사하는 단순한 방식(중복, duplication)도 있는데, 이때는 원본에서만 고친다.

샤딩의 단점은 외울 만하다. SQL이 복잡해질 수 있고, 샤드 하나가 깨지면 전체 데이터 정합성에 영향이 갈 수 있고, 백업과 스키마 변경을 샤드 전체에 맞춰 해야 한다.

## 데이터 웨어하우스

데이터 웨어하우스(DW)는 여러 운영 시스템의 데이터를 모아 분석 목적으로 쌓아 두는 저장소다. 빌 인먼이 정리한 특성 네 가지가 시험에 단골이다.

| 특성 | 뜻 |
|---|---|
| 주제 지향 | 업무 처리 단위가 아니라 핵심 주제(고객·상품 등) 중심으로 정리 |
| 통합 | 여러 시스템의 이름·단위·코드 표현을 일관되게 맞춤 |
| 시계열(시간 가변) | 오랜 기간의 이력을 보관해 분석·예측에 씀 |
| 비휘발성 | 한번 쌓으면 읽기 전용으로 두고 함부로 고치거나 지우지 않음 |

운영 DB(OLTP)와 비교하면 차이가 선명하다.

| | OLTP | OLAP(DW) |
|---|---|---|
| 일 | 짧은 입력·수정·삭제를 많이 | 집계 위주의 복잡한 조회를 적게 |
| 데이터 | 현재의 상세 데이터, 보통 3정규형 | 과거 이력, 다차원 구조 |
| 성능 기준 | 초당 트랜잭션 수 | 응답 시간 |

데이터가 들어오는 과정이 ETL이다. 원천 시스템에서 추출(Extract)하고, 정제·변환(Transform)해서, 웨어하우스에 적재(Load)한다. 순서를 바꿔 원본을 먼저 적재하고 웨어하우스 안에서 변환하는 방식은 ELT라고 부른다. 데이터 마트는 한 부서나 한 주제에 맞춘 작은 웨어하우스다. 원천이 적고 만들기 쉽다.

웨어하우스에서 자주 쓰는 모델이 스타 스키마다. 가운데 팩트 테이블이 있고 주변에 차원 테이블이 붙은 모양이다. 팩트는 주문 수량·결제 금액 같은 측정값이고 합계를 낼 수 있다. 차원은 주문일·고객·상품처럼 그 값을 해석하는 기준이다. 주문 팩트 하나에 날짜·고객·상품 차원이 붙는 식으로 그려 보면 기억하기 쉽다.

<details>
<summary>스타 스키마를 글로 그려 보면</summary>

```
        [날짜 차원]
             |
[고객 차원]--[주문 팩트]--[상품 차원]
             |
        [지점 차원]
```

팩트에는 차원들을 가리키는 키와 수량·금액이 들어간다. 차원 쪽 테이블은 반정규화해서 조인을 줄이는 경우가 많다.

</details>

## 흔한 헷갈림

- 파티션과 샤딩: 둘 다 수평으로 나누지만, 파티션은 보통 한 DBMS 안, 샤딩은 서버 여러 대에 걸친다.
- 인덱스는 많을수록 좋다고 생각하기 쉬운데, 쓰기가 느려지고 공간을 먹는다.
- 클러스터드 인덱스는 테이블당 하나다. 행의 물리 순서를 정하는 거라서 둘일 수 없다.
- DW는 운영 DB를 그대로 복사한 게 아니다. 주제별로 통합하고 이력을 쌓는다는 점이 다르다.
- 반정규화는 설계 실수가 아니라 정규화를 거친 뒤 성능 때문에 고르는 선택이다.

## 문제 풀 때

개념 정의를 묻는 문제는 위 표의 키워드(주제 지향·통합·시계열·비휘발성, 범위·리스트·해시)를 그대로 떠올릴 수 있으면 풀린다. "이 상황에서 무엇을 쓰나" 유형은 이렇게 본다. 날짜 기준으로 오래된 데이터를 자주 지운다면 범위 파티션, 특정 컬럼 검색이 느리면 인덱스, 조인이 너무 많아 느리면 반정규화, 분석용 집계가 목적이면 웨어하우스. 시험 일정과 방식은 공식 사이트에서 확인하면 된다.
