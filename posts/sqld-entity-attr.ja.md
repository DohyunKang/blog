SQLD 1 과목에서 엔터티와 속성은 용어와 분류를 묻는 문제가 많은 단원입니다. 외워야 할 것은 엔터티의 특징 다섯 가지, 분류 기준 두 가지, 속성의 분류 두 가지, 그리고 도메인 정의 정도입니다. 큰 흐름은 [데이터 모델링의 이해](#/post/sqld-modeling)에서 먼저 잡고 오면 편합니다.

## 용어부터 정리

엔터티 (Entity) 는 업무에서 관리해야 하는 식별 가능한 대상입니다. 정보를 저장하려고 만듭니다. DB 로 옮기면 엔터티는 테이블, 인스턴스는 행, 속성은 열에 대응합니다.

| 용어 | 뜻 | 테이블로 보면 |
|---|---|---|
| 엔터티 | 관리할 대상의 집합 | 테이블 |
| 인스턴스 | 엔터티에 속한 개별 대상 하나 | 행 (Row) |
| 속성 | 엔터티가 가진 의미 있는 최소 단위 | 열 (Column) |
| 속성값 | 속성에 실제로 들어간 값 | 셀 |

포함 관계는 `속성값 ⊂ 속성 ⊂ 인스턴스 ⊂ 엔터티`로 외웁니다. 엔터티 하나에 인스턴스가 2 개 이상, 인스턴스 하나에 속성이 2 개 이상, 속성 하나에는 속성값이 하나입니다. 이 숫자가 보기 문장에 섞여서 나오는 유형이 있습니다.

```
엔터티: 회원
  인스턴스 1: (m01, 김철수, 010-1111-2222)
  인스턴스 2: (m02, 이영희, 010-3333-4444)
  속성: 회원ID, 이름, 전화번호
  속성값: 'm01', '김철수', ...
```

## 엔터티의 특징 다섯 가지

문제에서는 "엔터티가 될 수 있는 것 / 없는 것"을 고르게 합니다. 아래 다섯 개 중 하나라도 깨지면 엔터티로 보기 어렵습니다.

1. 업무에서 쓰는 정보여야 합니다. 필요 없는 데이터는 엔터티로 만들지 않습니다.
2. 인스턴스를 구별하는 식별자가 있어야 합니다. 식별자는 속성 하나일 수도, 여러 속성의 조합일 수도 있습니다.
3. 인스턴스가 2 개 이상이어야 합니다. 평생 하나만 존재할 대상은 엔터티로 만들 이유가 없습니다.
4. 속성을 가져야 합니다. 속성 없이 이름만 있으면 안 됩니다.
5. 다른 엔터티와 관계가 1 개 이상 있어야 합니다. 관계 없이 혼자 있는 엔터티는 효율이 떨어지는 경우가 대부분입니다.

예를 들어 "회사 이름과 주소는 한 개뿐인데 이걸 엔터티로 만든다"는 보기는 2 번 인스턴스 조건에 걸립니다. 풀 때는 보기가 다섯 개 중 어느 조건을 건드리는지부터 봅니다.

## 엔터티 분류: 기준이 두 개

분류는 기준이 둘이고, 시험에서는 어떤 기준의 어떤 종류인지를 섞어서 냅니다. 기준 이름과 종류 이름을 짝으로 외웁니다.

### 유무형에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 유형 엔터티 | 물리적 형태가 있고 안정적이며 지속적으로 쓰인다 | 상품, 회원, 사원 |
| 개념 엔터티 | 형태는 없고 개념으로 존재한다 | 부서, 학과 |
| 사건 엔터티 | 업무를 하면서 발생하고 빈번하며 통계에 쓰인다 | 주문, 이벤트 응모 |

앞 글자를 따서 "유개사"로 외우는 방법이 흔합니다.

### 발생 시점에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 기본 엔터티 | 업무에 원래 있고 독립적으로 생긴다. 자식 엔터티를 가질 수 있다 | 상품, 회원, 사원, 부서 |
| 중심 엔터티 | 기본 엔터티에서 만들어지고 업무의 중심 역할을 한다. 데이터가 많고 행위 엔터티를 만든다 | 주문, 매출, 계약 |
| 행위 엔터티 | 2 개 이상의 엔터티에서 만들어진다. 데이터가 자주 바뀌거나 계속 늘어난다 | 주문 내역, 이벤트 응모 |

"기중행"으로 외웁니다. 기본에서 중심, 중심에서 행위로 갈수록 파생된다고 생각하면 순서가 안 헷갈립니다.

<details>
<summary>자주 헷갈리는 지점</summary>

- 중심 엔터티와 행위 엔터티의 정의는 자료마다 표현이 조금씩 다릅니다. 중심 엔터티를 기본 엔터티에서 파생된 것으로 설명하는 자료도 있고, 기본·행위 엔터티를 연결하는 역할로 설명하는 자료도 있습니다. 공부할 때 쓰는 교재의 정의를 기준으로 삼는 게 안전합니다.
- 사건 엔터티 (유무형 기준) 와 행위 엔터티 (발생 시점 기준) 는 비슷해 보이지만 기준이 다릅니다. 문제에서 "발생 시점"이라는 말이 있으면 기본·중심·행위, "유형·무형"이라는 말이 있으면 유형·개념·사건에서 고릅니다.
- 같은 대상도 기준이 바뀌면 다른 이름이 붙습니다. '주문'은 유무형 기준으로는 사건, 발생 시점 기준으로는 중심으로 나오는 예시가 있습니다.

</details>

## 엔터티 이름 짓기

명명 규칙도 보기 문장으로 나옵니다. 정리하면 아래와 같습니다.

- 업무에서 실제로 쓰는 용어를 사용합니다.
- 한글은 약어를 쓰지 않고, 영문은 대문자로 씁니다.
- 단수 명사로 쓰고, 띄어쓰기는 허용하지 않습니다.
- 다른 엔터티와 의미가 겹치지 않아야 합니다.
- 그 엔터티가 가진 데이터를 분명하게 드러내는 이름이어야 합니다.

"복수형으로 쓴다", "약어를 적극 사용한다" 같은 보기는 틀린 문장입니다.

## 속성

속성은 엔터티가 가진 의미 있는 가장 작은 단위입니다. 더 쪼개면 의미를 잃는 수준이라고 보면 됩니다. 분류 기준은 두 가지가 나옵니다.

### 특성에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 基本属性 | 業務に本来存在する属性。他の属性から生成されるものではありません | 名前、価格、数量 |
| 設計属性 | 業務には存在しないが、設計時に必要として作成された属性 | 連番などの人工識別子 |
| 派生属性 | 他の属性を計算して作成された属性 | 合計金額、年齢 |

派生属性は計算によって得られる値であるため、保存すると重複し、元データが変更されると整合性が取れなくなります。それでも、照会速度向上のために意図的に保持するケースがあり、これは [正規化とパフォーマンス データ モデリング](#/post/sqld-norm-perf) で再帰的に議論されます。

### 構成方式による分類

| 種類 | 説明 |
|---|---|
| PK 属性 | インスタンスを識別する主鍵を構成する属性 |
| FK 属性 | 他のエンティティとの関係から導かれる外部キー属性 |
| 一般属性 | PK でも FK でもない属性 |

PK と FK は [関係と識別子](#/post/sqld-relation-identifier) で識別子の種類とともに引き続き解説します。ここでは、属性が三つに分類されることだけ覚えておけば十分です。

なお、複数の値を持つマルチバリュー属性については、別のエンティティへ分離する方向で考えます。一つのセルに複数の値を入れる構造は、正規化の問題にもつながります。[正規化の概念](#/post/db-normalization) も併せて読むと理解が深まります。

## ドメイン

ドメインとは、属性が持つことができる値の範囲のことです。各属性に対してドメインが定義され、データ タイプ・長さ・許容値も同時に考慮します。例えば、「性別」属性のドメインが「男、女」であれば、それ以外の値は受け付けることができません。問題では、「属性が持つことができる値の集合」という定義文が正しいかどうかを問うことがあります。

## 解き順

この単元の問題は、選択肢を読み、以下の順序で絞り込みました。

1. エンティティの話か、属性の話かを区別する。
2. 分類問題であれば、基準（有無形 / 発生時点 / 特性 / 構成方式）から確認する。
3. 選択肢に登場する例（注文、部署、合計金額など）を、該当基準の種類のいずれかに当てはめていく。
4. 特徴問題であれば、五つの条件のうちどの条件を満たさない選択肢を探す。
5. 命名規則問題であれば、単数形・略語・スペースの使い方について誤っている文をまず疑う。

<details>
<summary>一人で確認できる質問</summary>

- インスタンスが一つしかない対象がなぜエンティティではないのか。
- 「合計金額」は基本・設計・派生のうちどこに分類されるか。
- 有無形基準と発生時点基準の各々について、それぞれ三つずつ挙げることができるか。
- エンティティ名を複数形で命名しない理由を、選択肢の文で説明できるか。

</details>
