软件工程关注的不是如何写好代码，而是“构建什么、按何种顺序构建、如何验证以及如何修复”。这里仅梳理了主要脉络。

## 什么是软件工程

当程序规模较小时，可以仅靠个人在脑海中管理。但随着人员增加和周期延长，问题也随之变化：大家对要构建的内容理解不一致，修改一处导致另一处崩溃，最终延误交付期限。软件工程正是为了减少这类问题而提出的一系列方法的集合。

大致可分为五个部分：整体推进方式（开发方法论）、确定构建内容（需求）、将内容转化为图纸（设计·UML）、验证是否达标（测试）、管理变更的代码（版本控制）。顺序大体如下所示。

| 阶段 | 工作内容 | 产出物 |
|---|---|---|
| 需求 | 听取并整理要构建的内容 | 需求规格说明书 |
| 设计 | 确定结构、界面与数据 | UML、设计文档 |
| 实现 | 编写代码 | 源代码 |
| 测试 | 验证是否符合需求 | 测试结果 |
| 维护 | 修复问题并添加新功能 | 新版本 |

## 开发方法论：瀑布模型与敏捷

方法论决定了上述各阶段如何推进。

瀑布模型按顺序从上至下依次进行每个阶段：完成需求后进入设计，设计完成后进入实现。必须在前一阶段结束后才能进入下一阶段，文档和计划十分明确，但缺点是若中途需求变更则难以回退，且直到最后阶段才能看到最终成果。

敏捷则相反，主张快速构建、展示并修复。阅读《敏捷宣言》的 12 条原则即可明确方向：欢迎开发后期需求的变更，以数周为单位频繁发布可运行的软件，业务负责人与开发人员每日协作，并将可运行的软件作为进度的衡量标准。这也包括定期回顾并调整工作方式。

| | 瀑布模型 | 敏捷 |
|---|---|---|
| 推进方式 | 按顺序依次进行各阶段 | 重复短周期迭代 |
| 需求变更 | 困难且昂贵 | 以接受变更为前提 |
| 成果验证 | 几乎在末期 | 每个周期结束时 |
| 文档 | 数量多 | 按需编写 |
| 适用场景 | 需求固定的项目 | 需求频繁变化的项目 |

在实际运行敏捷框架中最常见的是 Scrum。依据 [Scrum Guide](https://scrumguides.org/scrum-guide.html) 整理如下：

- **Sprint**：固定周期，通常不超过一个月，所有事件均在此范围内进行。
- **事件**：Sprint 计划、每日站会（15 分钟）、Sprint 评审、回顾会。
- **角色**：产品负责人（管理待办列表，一人）、Scrum Master（移除障碍）、开发团队。
- **产出物**：产品待办列表、Sprint 待办列表、增量（可使用的成果）。

若认为瀑布模型不好而敏捷模型好，在现实中就会出错。对于需求固定且回退成本高昂的项目（如嵌入硬件的固件），采用计划驱动的方式更为合适。其他模型如螺旋模型（重复进行风险分析）、原型法等也存在，只需了解其名称与主要特征即可。

## 需求

需求是指系统必须执行的任务和必须遵守的条件。可分为两类：

- **功能需求**：描述系统应执行的操作，例如“用户应能通过电子邮件登录”。
- **非功能需求**：涉及质量或约束条件，例如“登录响应时间应在 1 秒内”、“个人信息必须加密”。

良好的需求应具备单义性（一句话一个含义）且可验证。“快速”无法验证，“1 秒内”则可以。在需求阶段出现的错误，随着项目推进修复成本会急剧增加，因此在此阶段确保各方对同一内容达成一致最为关键。

<details>
<summary>获取与验证需求的方法</summary>

需求的获取可通过访谈、问卷调查、观察当前工作流程、原型演示等方式进行。接收到的需求需经过分析以剔除冲突项，编写成规格说明书，并在最后由利益相关者审查。为每个需求编号，便于后续在设计、测试阶段进行关联追踪（追溯表）。
</details>

## UML

UML 是用于绘制设计图纸的标准符号集。种类虽多，但常用的是以下几种：

| 图表类型 | 展示内容 | 适用时机 |
|---|---|---|
| 用例图 | 用户与系统的交互行为 | 需求整理阶段 |
| 类图 | 类及其关系 | 结构设计阶段 |
| 序列图 | 对象间消息传递顺序 | 单个功能的流程 |
| 状态图 | 状态变更的条件 | 涉及状态流转的场景（如订单、支付） |
| 活动图 | 工作流 | 业务流程 |

将展示结构的图表（如类图）与展示行为的图表（如序列图、状态图）分开记忆可减少混淆。并非需要绘制所有内容，只需针对难以用语言描述的部分进行绘图即可。

## 测试

测试是验证所构建的系统是否按预期运行，并找出故障发生的位置。测试范围从单位（单个函数或类）、集成（组合多个模块）、系统（整体）到验收（用户或客户可接受的程度），依次扩大。

自动化测试通常用“测试金字塔”来描述其比例关系。以 [Martin Fowler 的文章](https://martinfowler.com/articles/practical-test-pyramid.html) 为基准，单位测试因速度快应最多执行；涉及数据库等外部系统的集成测试应适量进行；遍历整个 UI 的测试则应尽量减少。若将这一结构颠倒，则会变成缓慢且维护成本高昂的“冰淇淋筒”，因此应避免在多层中重复检查相同内容，而尽可能将测试下移至更低的层级。

测试可分为黑盒测试（不查看内部代码，仅关注输入与输出）和白盒测试（基于代码结构验证执行路径）。在黑盒测试中，边界值分析尤为典型，因为错误常发生在 0、1、最大值等边界处。

单位测试大致如下所示：使用 Python `unittest` 编写并手动运行，确认全部四个用例均通过。

```python
import unittest

def discount(price, is_member):
    if price < 0:
        raise ValueError("price")
    return int(price * 0.9) if is_member else price

class T(unittest.TestCase):
    def test_member(self):
        self.assertEqual(discount(10000, True), 9000)
    def test_guest(self):
        self.assertEqual(discount(10000, False), 10000)
    def test_zero(self):          # 경계값
        self.assertEqual(discount(0, True), 0)
    def test_negative(self):      # 예외 경우
        with self.assertRaises(ValueError):
            discount(-1, True)

unittest.main()
```

<details>
<summary>几个测试术语</summary>

- **回归测试**：修复问题后，重新验证此前正常运行的功能是否仍正常工作。
- **桩（Stub）与驱动（Mock）**：在测试中替代真实依赖对象（如数据库、外部 API）的模拟对象。
- **验证（Verification）** 指“是否正确构建了产品”（是否符合规范），而**确认（Validation）** 则指“是否构建了正确的产品”（是否满足用户需求）。
</details>

## 版本控制

代码持续变更，若不知晓谁在何时做了什么修改，一旦出现问题便无法回滚。版本控制（SCM）是对源代码、文档等产出物的变更进行记录与管控的过程，涵盖版本管理（回滚、历史记录）、变更控制（审批流程）以及构建与部署管理。当前 Git 已成为事实上的标准工具。

## 常见误区

- 敏捷开发是否意味着无需文档或计划？并非如此，敏捷同样重视良好的设计与技术卓越性；其目标是减少文档数量，而非完全消除。
- 测试是否应在开发完成后进行？建议在需求阶段就明确“如何验证”，并提前记录下来。
- UML 图是否需要全部绘制？只需绘制必要的部分即可。
