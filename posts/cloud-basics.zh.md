云是一种租用而非购买服务器的模式，根据用户对服务器哪一层的控制权不同，可分为 IaaS、PaaS 和 SaaS。在此基础上，还增加了“区域（Region）”和“可用区（AZ）”等位置概念，以及按使用量付费的成本结构。

## 什么是云

过去若要部署服务，必须购买服务器并安置在机房中：需提前数周下单，并根据预估用量大量采购。而云则将这一模式转变为通过互联网租用资源：按需创建，无需时即可删除。

NIST（美国国家标准与技术研究院）的定义文件将云计算描述为“一种允许用户通过网络随时便捷访问可配置计算资源池的模型”。其核心在于能够快速分配和回收资源，且几乎无需管理投入。该文件列出的五大特征包括：自助服务、资源池化、快速弹性、可计量服务以及宽带网络接入（尽管已知共有五项特征，但本次未在正文中逐一核实）。

AWS 概述文档也表达了类似观点：无需前期巨额投入，而是按使用量支付变动成本；声称可在几分钟内启动数百台服务器。总结如下表所示：

| | 传统方式（本地部署） | 云 |
|---|---|---|
| 准备时间 | 数周至数月 | 数分钟 |
| 付费方式 | 先支付大额采购款 | 按使用量付费 |
| 容量规划 | 预估最大值后购买 | 可随时扩展或缩减 |
| 管理责任 | 自行管理硬件 | 服务商代为处理部分工作 |

## IaaS、PaaS、SaaS

服务架构呈分层结构，包括：硬件、虚拟化、操作系统、运行时环境、应用程序和数据。用户与服务商之间的责任划分决定了这三种模型的区别。

| | 用户负责管理的内容 | 服务商负责管理的内容 | 示例 |
|---|---|---|---|
| IaaS | 操作系统及以上所有层 | 硬件、虚拟化 | 虚拟服务器（VM）、磁盘、网络 |
| PaaS | 用户代码与数据 | 操作系统、运行时、服务器 | 仅上传代码即可运行的托管服务 |
| SaaS | 配置与日常使用 | 几乎全部 | 邮件、协作工具等成品软件 |

上表中的示例与分层划分属于一般性说明。由于不同服务的边界存在差异，某些服务难以明确归入某一特定类别的情况较为常见。

IaaS 自由度较高但用户需承担更多管理工作：需登录服务器执行操作系统更新与安全补丁安装等任务。PaaS 则由服务商代为处理底层运维，但可用的编程语言和配置选项受到限制。SaaS 仅提供现成程序供用户使用。总体而言，层级越低越便捷，层级越高则自由度越大。

## 责任共担模型

AWS 的责任共担模型文档从安全角度阐述了上述边界：服务商负责管理主机操作系统、虚拟化层以及设施的物理安全；客户则需管理访客操作系统（含更新与安全补丁）、上层应用软件及安全组（防火墙）配置。文档还指出，具体服务的责任划分会因所选服务而异，这与前述分层逻辑一致——租用服务器并不意味着同时租用了其安全保障。

值得注意的是，该文档附有说明：“本白皮书仅供历史参考，部分内容可能已过时。”尽管整体架构框架依然适用，但细节部分建议查阅最新官方文档以获取准确信息。

## 区域与可用区

云服务器实际部署于全球各地的物理建筑中。依据 AWS 文档标准，“区域（Region）”代表世界上的物理位置，每个区域内包含多个“可用区（Availability Zone, AZ）”。每个可用区由一个或多个数据中心组成，具备电源、网络及连接的双重冗余，并位于不同的设施中。文档指出，使用多个可用区相较于仅使用单个数据中心，可显著提升高可用性、容错能力及扩展性。

```
리전 (예: 서울)
 ├─ AZ-a  [데이터센터]  ← 서버 1
 ├─ AZ-b  [데이터센터]  ← 서버 2
 └─ AZ-c  [데이터센터]  ← 서버 3
```

实际应用中，若将服务器仅部署于单一可用区，则该所在建筑发生故障时服务也会随之中断；若跨多个可用区部署并通过负载均衡器分发请求，则即使某一方失效，整体服务仍可正常运行。负责分发请求的设备即为 [负载均衡器](#/post/infra-load-balancer)。此外，文档还提到：选择靠近用户的区域可加快响应速度，同时需考虑各国数据存储合规要求，因此初期应谨慎选型——不过本次尚未通过官方文档对此进行直接验证。

## 什么是虚拟机（VM）

虚拟机（VM）是通过软件将一台物理服务器分割成多个独立实例，使其如同多台物理机般运行。在 IaaS 中租用的“服务器”通常指的就是这种 VM。用户可选择核心数、内存和磁盘规格，几分钟内即可获得一台可访问的计算机。由于每台 VM 需独立安装操作系统，因此资源占用较重且启动耗时；相比之下，容器是一种更轻量级的替代方案。相关内容将在 [Docker 与容器](#/post/cloud-docker) 中继续探讨。

## 成本结构

云服务的成本可概括为一句话：“按使用量付费”。AWS 概述文档也突出展示了 on-demand（按需）和 pay-as-you-go（即用即付）定价模式。因此，理解其计费机制需要一定的直觉与经验。

- 只要运行时间就会产生费用。即使虚拟机（VM）没有任何请求，只要处于开启状态就会产生费用。
- 除了服务器本身的费用外，还有其他支出。例如磁盘存储容量、从服务器流出到互联网的数据量，以及许多管理型服务都会额外收费。
- 一旦创建后若忘记关闭，费用会持续累积。据说测试环境中的服务器如果不及时删除，导致费用不断堆积的情况很常见。
- 如果打算长期使用，可以选择签约折扣；如果允许中断服务，则可以利用闲置资源以更低成本使用的方式。

因此，一开始就应该设置通知提醒。通常可以设定预算上限，一旦超出就会收到通知。关于收集日志和指标的分析内容，请参见 [详情 → 监控·日志·告警](#/post/cloud-observability)。

## 无服务器与什么不同

“无服务器”并不意味着没有服务器。实际上是有服务器的，只是由我来创建和管理删除。部署函数后，只有在收到请求时才会执行，并按实际运行时间付费。如果说虚拟机是按“租用时间”计费的话，那么无服务器则是按“实际工作时长”计费。从层级来看，许多人认为它比 PaaS 还要高一个层级。详细内容请参见 [详情 → 无服务器](#/post/cloud-serverless)。

## 常见误解

- 云一定便宜：初期成本可能较低，但长时间运行的大型服务器费用可能高于自建。便宜的真正含义是“无需提前购买”。
- 部署到云就不会宕机：如果只部署在一个可用区（AZ），该区域发生故障时服务也会随之中断。高可用架构需要自行设计。
- 安全由服务商负责：根据责任共担模型，操作系统补丁和防火墙配置通常由客户负责。密码和密钥管理也是如此。相关内容在 [详情 → 环境变量与密钥管理](#/post/cloud-secrets) 中有详细说明。
- 流量增加会自动扩容：虽然具备自动扩展功能，但仍需手动开启并设定阈值。相关内容请参见 [详情 → 自动伸缩与扩展](#/post/infra-autoscaling)。

<summary>详细解析：三种部署模型</summary>

除了服务模型（IaaS/PaaS/SaaS）之外，还有一种用于区分应用部署位置的部署模型。AWS 文档将其分为三类：

- **云**：整个应用程序在云端运行。可以是从头在云上构建的应用，也可以是从现有基础设施迁移过来的应用。既可以由底层组件构建，也可以使用提供管理服务的上层服务。
- **私有（本地）**：利用虚拟化和资源管理工具在自有数据中心内构建。文档指出虽然无法充分利用云的优势，但在需要专用资源时可选择此方式。
- **混合**：结合云端与线下现有设施共同使用。最常见的形式是将原有设施逐步扩展至云端，并实现两者之间的连接。

NIST 文档则将部署模型分为四类，其中包含了社区云的概念。
