采样（Sampling）是指模型在计算出下一个词的概率分布后，从中实际抽取一个词的方法；而温度和 top-p 则是控制这种抽取过程保守程度的参数。不过最近 Claude 系列模型似乎不再支持这些参数了，因此本文将一并梳理相关概念与现状。

## 首先用一句话概括

同一个问题问了两次，却得到了不同的回答。这并非模型出了故障，而是其原本的设计如此。[LLM](#/post/ai-llm) 在生成文本时，会为每个 token 计算“哪个 token 更合理”的得分，将这些得分转换为概率分布，然后依据该概率分布抽取一个 token。这个最后的“抽取”过程就是采样（Sampling）。

因此，温度（temperature）、top-p、top-k 并不是改变模型知识或智能程度的参数，它们只影响如何从已经计算好的概率分布中进行抽取。

## 原理：从得分到生成一个词

模型输出的原始得分称为对数几率（logit），每个词都有一个对应的值，此时还不是概率。将这些值输入 softmax 函数后，就会转化为总和为 1 的概率分布。整个流程如下所示：

| 步骤 | 操作 | 涉及参数 |
|---|---|---|
| 1 | 计算每个词的得分（logit） | 模型本身 |
| 2 | 将得分除以温度 | temperature |
| 3 | 使用 softmax 生成概率分布 | - |
| 4 | 截断低概率候选项 | top-k, top-p |
| 5 | 从剩余候选项中按概率抽取一个词 | - |

注意这里是以 token 为单位而非单个字符，该过程对每个 token 重复执行。由于生成一个完整回答可能需要数百次抽取，中间某一次若抽到不同的结果，后续句子就会完全改变。这就是同一问题出现不同回答的原因。

## 温度

温度是在第 2 步中用于除以得分的参数。温度越低，得分差异被放大，第一名几乎独占概率；温度越高，得分差异缩小，概率分布越均匀。当温度接近 0 时，几乎总是抽取第一名（这种做法称为“贪婪”greedy）。

为了直观验证数值影响，我运行了一段简单的 Python 代码（见下方折叠部分），设定六个候选词的得分为 `[3.0, 2.5, 1.5, 1.0, 0.5, -1.0]`，仅改变温度值。

| 温度 | 第 1 名 | 第 2 名 | 第 3 名 | 其余总和 |
|---|---|---|---|---|
| 0.2 | 92.4% | 7.6% | 0.1% | 0% |
| 1.0 | 48.4% | 29.4% | 10.8% | 11.5% |
| 2.0 | 32.9% | 25.6% | 15.5% | 26.0% |

在温度 0.2 时，结果几乎是确定的；而在温度 2.0 时，连最后一名也有约 4.5% 的概率被选中。通过这张表格可以直观理解：“温度越高越有创意”的说法并非指模型变得更聪明，而是增加了抽取低概率词的机会。

## top-k 与 top-p

提高温度有时会生成不合逻辑的词，因此需要额外的机制进行截断。

- **top-k**：仅保留得分最高的 k 个候选项，其余丢弃。例如 k=2 时，只保留第 1、2 名。这种方法简单，但缺点是固定数量，与具体情境无关。即使第一名概率高达 99%，仍会保留 k 个；而在各候选项水平相当的情况下，则可能过度截断。
- **top-p（核采样 nucleus sampling）**：按得分从高到低累加概率，直到总和达到 p 为止，仅保留这些候选项。候选项数量随情况动态变化。若对第一名非常有把握，则只保留一两个；若情况模糊，则会保留多个。

top-p 由 Holtzman 等人于 2019 年的论文中提出。根据相关研究，若始终选择概率最高的词，生成的文本会显得平淡且重复；为避免此问题，仅在概率分布的“动态核（nucleus）”范围内进行采样，并剪除置信度较低的尾部。该论文还指出，即使是同一模型，仅改变解码方式即可显著影响生成质量。

在上述示例（温度 1.0）中，若将 top-p 设为 0.9，由于前 3 名概率总和为 88.6%，尚未达到 0.9，因此保留至第 4 名，而第 5、6 名被截断。剩余候选项的概率会重新归一化，使其总和为 1。

<details>
<summary>详细解析：亲测运行的代码</summary>

```python
import math, random

def softmax(logits, T=1.0):
    z = [x / T for x in logits]
    m = max(z)                       # 오버플로 방지
    e = [math.exp(x - m) for x in z]
    s = sum(e)
    return [x / s for x in e]

def top_k(p, k):
    keep = set(sorted(range(len(p)), key=lambda i: -p[i])[:k])
    q = [p[i] if i in keep else 0 for i in range(len(p))]
    s = sum(q)
    return [x / s for x in q]

def top_p(p, P):
    order = sorted(range(len(p)), key=lambda i: -p[i])
    keep, c = set(), 0
    for i in order:
        keep.add(i)
        c += p[i]
        if c >= P:
            break
    q = [p[i] if i in keep else 0 for i in range(len(p))]
    s = sum(q)
    return [x / s for x in q]

logits = [3.0, 2.5, 1.5, 1.0, 0.5, -1.0]
p = softmax(logits, 1.0)
print(top_k(p, 2))      # [0.622, 0.378, 0, 0, 0, 0]
print(top_p(p, 0.9))    # [0.509, 0.309, 0.114, 0.069, 0, 0]
```

运行结果显示，不同温度下的概率分布分别为：T=0.2 时为 `[0.924, 0.076, 0.001, 0, 0, 0]`，T=1.0 时为 `[0.484, 0.294, 0.108, 0.066, 0.04, 0.009]`，T=2.0 时为 `[0.329, 0.256, 0.155, 0.121, 0.094, 0.045]`。若先将温度降至 0.7 并应用 top-p=0.9，则得到 `[0.622, 0.305, 0.073, 0, 0, 0]`。由此可见，同时使用温度和 top-p 会产生叠加效果。

上述代码仅为用于演示概念的玩具程序。

## 何时以及如何调整

OpenAI API 参考（Chat Completions）将 temperature 描述为 0 到 2 之间的值。较高的值（如 0.8）会使输出更加随机，而较低的值（如 0.2）则使输出更加集中和确定。top_p 是 temperature 的替代方案，如果设置为 0.1，则表示只考虑概率质量前 10% 的 token。文档建议“两者只改其一，不要同时修改”，因为正如上文所见，它们产生相同方向的效果从而相互叠加（虽然这一解释本身并非出自文档）。

经验法则通常如下所述。这部分内容并非来自官方文档，而是业界通用的做法。

| 目的 | 低值 | 高值 |
|---|---|---|
| 摘要、提取、分类、代码生成 | O | |
| 头脑风暴、命名、写作 | | O |
| 需要相同输入产生相同输出的测试 | O | |

## 常见误解

温度设为 0 是否总能得到相同的答案？几乎如此，但并非绝对保证。这一点我尚未亲自验证。虽然有很多说法认为由于服务器端的计算（如浮点运算顺序、批处理等）可能导致结果不完全一致，但我并未在本文中找到确切的出处来证实这一点。

降低温度能减少 [幻觉](#/post/ai-hallucination) 吗？并非如此。温度仅改变从概率分布中采样的方式，并不能让模型“知道”它原本不知道的内容。如果排名第一的候选答案是错误的，那么较低的温度会更坚定地输出这个错误答案。

提高温度会让模型变得更聪明吗？不是。它只会增加输出的多样性。此外，对于像 [推理模型](#/post/ai-reasoning) 这样需要经历较长思考过程的模型，这些参数的具体作用方式因模型而异。

## Claude 正在移除这些参数

对此我感到惊讶。我一直认为调节采样值是理所当然的，但查看 Anthropic 文档中的模型支持终止页面（API parameter deprecations）后发现，`temperature`、`top_p` 和 `top_k` 将在 API 版本 `2026-10-21` 中被移除。如果在此版本中使用这些参数进行请求，发送瞬间就会返回 400 错误。文档建议的替代方法是“移除它们，并通过提示词引导模型行为”。

总结如下：

| 情况 | 操作（基于文档） |
|---|---|
| API 版本 2026-10-21 | 移除所有三个参数，发送将导致 400 错误 |
| 旧版 API + Claude 4.7 及后续模型 | 发送非默认值将导致 400 错误 |
| 旧版 API + 其他模型 | 文档中未特别说明 |

有一家博客（Enjoy Agentic Industries）指出旧版本仍会继续运行，且尚未公布终止日期。由于这是二手资料，仅供参考。同一家博客还建议，对于像 Claude Sonnet 4.6 这样的旧模型，原本用于通过低温度稳定结果的代码在新版本中将失效，因此建议保留在旧版本中使用。

我的理解是，现在“确保输出相同答案”的需求不应再依赖 temperature，而应转向提示词或 [结构化输出](#/post/ai-structured-output) 来解决。其他提供商（如 OpenAI）目前仍将这些参数保留在文档中。由于各模型和供应商的支持情况不同，使用前请务必查阅对应模型的文档。关于各模型之间的差异，可在 [AI 模型地图](#/post/ai-models) 中继续了解。有关输入消耗等其他限制，请参阅 [上下文窗口](#/post/ai-context-window) 一文。
