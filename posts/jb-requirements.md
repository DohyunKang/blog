요구사항은 "시스템이 무엇을 해야 하고 어떤 품질이어야 하는가"를 적은 것이고, 시험에서는 이 요구사항을 다루는 순서와 개발 모델 이름·특징을 구분하는 문제가 반복해서 나온다.

## 요구사항이 뭔지

요구사항은 사용자와 이해관계자가 소프트웨어에 바라는 것을 말로 정리한 것이다. 코드를 짜기 전에 "뭘 만들지"를 맞추는 단계라서, 여기서 틀리면 뒤에서 고치는 비용이 커진다.

시험에서는 요구사항을 크게 둘로 나눈다.

| 구분 | 말투 | 예 |
|---|---|---|
| 기능 요구사항 | 시스템이 ~을 한다 | 로그인한다, 주문 내역을 보여 준다 |
| 비기능 요구사항 | 시스템이 ~하다 | 응답은 2초 안이다, 비밀번호는 암호화해 저장한다 |

위키백과의 비기능 요구사항 문서도 기능 요구사항은 "system shall do ~", 비기능은 "system shall be ~" 꼴로 쓰는 경향이 있다고 설명한다. 비기능의 대표 항목은 성능, 신뢰성·가용성, 확장성, 보안, 사용성, 유지보수성이다. 기능은 무엇을 하는지, 비기능은 얼마나 잘 하는지로 기억하면 문제에서 헷갈리지 않는다.

여기에 제약사항(예산, 일정, 사용 기술)을 따로 두는 분류도 교재에서 자주 보인다. 보기에 "제약사항"이 섞여 나오면 기능도 비기능도 아닌 쪽으로 고르는 문제가 있다.

## 요구사항 개발 프로세스

요구공학의 활동은 위키백과 기준으로 도출(elicitation), 분석·협상, 모델링, 명세, 검증, 관리로 나온다. 정처기 교재는 이걸 네 단계로 묶어서 가르치는 경우가 많다.

```
도출 → 분석 → 명세 → 확인(검증)
```

| 단계 | 하는 일 | 시험 포인트 |
|---|---|---|
| 도출 | 이해관계자에게서 요구를 모은다 | 기법 이름 구분 |
| 분석 | 모호한 것·충돌을 정리하고 우선순위를 정한다 | 충돌 해결(협상), 모델링 |
| 명세 | 문서로 확정한다(SRS) | 명확성·검증 가능성 |
| 확인 | 명세가 진짜 원하는 것과 맞는지 점검한다 | 검토, 프로토타입 |

위키백과는 이 활동들이 순서대로만 가는 게 아니라 실제로는 "considerable interleaving", 즉 많이 섞여서 돌아간다고 적는다. 시험 문제는 순서를 묻지만 현실은 왔다 갔다 한다는 정도로 알고 있으면 된다. 또 명세서는 검증을 거친 뒤에야 공식 문서가 된다고 한다.

### 도출 기법

도출은 요구를 찾아내는 일이고, 기법 이름과 특징을 짝짓는 문제가 많다.

- 인터뷰: 사람을 직접 만나 묻는다. 깊이 들어가기 좋지만 시간이 든다.
- 설문: 많은 사람에게 같은 질문을 돌린다. 넓게 모으기 좋고 깊이는 얕다.
- 브레인스토밍: 모여서 아이디어를 비판 없이 쏟아 낸다.
- 프로토타이핑: 간단한 시제품을 보여 주고 반응을 받는다. 말로 설명이 안 되는 요구를 끌어낼 때 쓴다.
- 관찰: 사용자가 실제로 일하는 모습을 본다. 본인도 말로 못 하는 요구가 나온다.
- 유스케이스·시나리오: 사용자가 시스템을 쓰는 장면으로 요구를 적는다. UML 쪽 내용은 [자세히 → UML과 객체지향 분석](#/post/jb-uml)에서 다룬다.

### 분석

도출한 요구에는 서로 부딪히는 것이 섞여 있다. 영업팀은 빨리 내라고 하고 개발팀은 안정성을 말하는 식이다. 분석 단계에서는 이걸 정리해 충돌을 협상으로 풀고 우선순위를 매긴다. 모델링은 그림으로 요구를 표현하는 일이고, 데이터 흐름도·유스케이스 다이어그램·클래스 다이어그램 등을 쓴다. 위키백과도 분석에서 유스케이스와 사용자 스토리를 쓰고 UML을 그래픽 도구로 쓴다고 적는다.

### 명세와 확인

명세는 요구를 문서로 남기는 일이다. 대표 문서가 SRS(Software Requirements Specification, 소프트웨어 요구사항 명세서)이다. 좋은 명세서는 모호하지 않고, 서로 모순이 없고, 검증할 수 있어야 한다. "빠르게 응답한다"보다 "95%의 요청이 2초 안에 응답한다"가 검증 가능한 문장이다.

확인(검증)은 적힌 요구가 일관되고 이해관계자의 필요를 만족하는지 보는 일이다. 문서 검토, 프로토타입 시연, 테스트 케이스 작성 같은 방법이 있다. 테스트 쪽은 [자세히 → 소프트웨어 테스트](#/post/jb-testing)에 이어진다.

<details>
<summary>자세한 풀이: 헷갈리기 쉬운 짝</summary>

- 확인(validation)은 "올바른 걸 만들고 있나"를 묻고, 검증(verification)은 "만든 게 명세대로인가"를 묻는다는 식으로 구분해서 외우는 사람이 많다. 교재마다 두 용어를 섞어 쓰기도 해서, 문제 문장의 맥락으로 판단하는 게 안전하다.
- 요구사항 관리는 명세가 끝난 뒤에도 변경을 추적하는 활동이다. 위키백과도 관리를 착수부터 시스템을 쓰는 중의 변경까지 이어지는 활동으로 적는다.
- 도출 기법 문제는 "시제품을 보여 주고 반응을 받는다 → 프로토타이핑"처럼 설명을 주고 이름을 고르는 유형이 많다. 설명의 핵심 동사만 잡으면 된다.

</details>

## 개발 모델

요구사항을 언제 얼마나 확정하느냐에 따라 개발 모델이 갈린다. 시험은 모델 이름과 특징을 짝짓는 문제로 나온다.

| 모델 | 한 줄 특징 | 요구사항 관점 |
|---|---|---|
| 폭포수 | 단계를 순서대로, 되돌아가지 않는 게 원칙 | 처음에 요구를 다 확정 |
| 프로토타입 | 시제품을 먼저 만들어 요구를 확인 | 요구가 불분명할 때 |
| 나선형 | 반복하면서 위험을 분석 | 위험이 큰 대형 프로젝트 |
| 애자일 | 짧은 반복으로 변화에 대응 | 요구는 바뀐다고 가정 |

### 폭포수

위키백과에 따르면 폭포수의 단계는 예비 분석, 시스템 분석과 요구 정의, 설계, 개발, 통합과 테스트, 인수·설치·배포, 유지보수 등으로 나열된다. 교재에서는 보통 계획→요구분석→설계→구현→테스트→유지보수 정도로 줄여 외운다.

재미있는 건 Royce의 1970년 논문이다. 그의 도식이 "waterfall"이라는 이름의 출발이 됐지만, 정작 Royce 본인은 테스트가 맨 끝에만 있는 단순한 형태를 위험하다고 보고 테스트에서 설계로, 설계에서 요구로 되돌아가는 피드백을 더했다고 한다. 시험에서는 단순한 폭포수의 약점으로 다음을 든다. 고객이 동작하는 소프트웨어를 보기 전에는 정확한 요구를 모를 수 있어서, 뒤늦은 변경이 재작업과 비용 증가로 이어진다.

### 프로토타입

요구가 모호하면 먼저 간단한 시제품을 만들어 사용자에게 보여 주고 피드백으로 요구를 다듬는다. 폭포수의 약점인 "늦게 알게 되는 요구"를 앞당겨 푸는 모델이다.

### 나선형

Barry Boehm이 1986년 논문에서 제안했다. 위키백과 설명으로는 모든 주기에서 해야 하는 일이 네 가지다. 핵심 이해관계자의 목표와 제약을 살피고, 목표를 이룰 대안을 찾아 평가하고, 선택한 방식의 위험을 분석해 대응하고, 이해관계자의 승인을 받아 다음 주기로 간다. 위험 분석이 이 모델의 중심이라는 점이 시험 단골이다. 위험 때문에 "위험 분석" 단계를 포함하는 모델은 나선형이라고 바로 연결하면 된다.

### 애자일

2001년의 애자일 선언은 네 가지 가치를 든다.

- 프로세스와 도구보다 개인과 상호작용
- 포괄적인 문서보다 동작하는 소프트웨어
- 계약 협상보다 고객과의 협력
- 계획을 따르는 것보다 변화에 대응

선언 문서는 원칙이 열두 개라고 따로 링크한다. 시험에서 "왼쪽도 가치는 있지만 오른쪽을 더 중시한다"는 구조를 묻기도 하니 네 쌍을 짝으로 기억해 둔다.

애자일의 대표 기법이 스크럼과 XP이다.

스크럼은 스크럼 가이드 기준으로 역할이 개발자, 프로덕트 오너, 스크럼 마스터 셋이다. 이벤트는 스프린트, 스프린트 계획, 데일리 스크럼, 스프린트 리뷰, 스프린트 회고이고, 산출물은 프로덕트 백로그, 스프린트 백로그, 인크리먼트다. 스프린트는 한 달 이하의 고정 길이다.

XP(익스트림 프로그래밍)는 Kent Beck이 Chrysler의 급여 시스템 프로젝트에서 발전시켰다. 가치는 의사소통, 단순성, 피드백, 용기, 존중이고, 대표 실천법은 짝 프로그래밍, 계획 게임, 테스트 주도 개발, 지속적 통합, 리팩터링, 소규모 릴리스, 코딩 표준, 공동 코드 소유, 단순 설계, 지속 가능한 속도 등이다. 시험에는 "짝 프로그래밍, TDD, 리팩터링이 나오면 XP"라는 식으로 나온다.

<details>
<summary>자세한 풀이: 모델 고르기 문제 푸는 순서</summary>

1. 문제에 "위험 분석"이 있으면 나선형.
2. "시제품", "견본"이 있으면 프로토타입.
3. "스프린트", "백로그", "스크럼 마스터"가 있으면 스크럼.
4. "짝 프로그래밍", "리팩터링", "TDD"가 있으면 XP.
5. "단계별로 순차, 이전 단계로 돌아가지 않음"이면 폭포수.

보기가 비슷할 때는 요구가 안정적인지(폭포수), 불분명한지(프로토타입), 위험이 큰지(나선형), 계속 바뀌는지(애자일)로 가른다.

</details>

## 흔한 오해

- 요구사항은 처음에 다 정하면 된다: 폭포수가 그렇게 가정하지만 애자일은 요구가 바뀐다고 가정한다. 모델마다 전제가 다르다.
- 비기능 요구사항은 덜 중요하다: 성능·보안이 빠지면 기능이 다 돼도 쓸 수 없는 시스템이 된다.
- 애자일은 문서를 안 쓴다: 선언은 문서보다 동작하는 소프트웨어를 더 중시한다는 것이고, 문서가 필요 없다는 말은 아니다.
- 나선형은 반복이니 애자일이다: 반복은 닮았지만 나선형은 위험 분석이 중심이고, 애자일은 변화 대응과 협력이 중심이다.

기출문제를 풀 때는 같은 개념이 보기 문장만 바꿔 다시 나오는 경우가 많아서, 위 표를 보고 설명을 이름으로 바꾸는 연습이 도움이 된다. 시험 일정과 응시 조건은 공식 사이트에서 확인하면 된다.
