规范化是为了解决因同一事实被记录在多处而产生的问题，即通过拆分表格来消除冗余；而事务则是将多个操作捆绑在一起，确保它们要么全部成功，要么全部失败。在信息处理技术员考试的数据库单元中，这两个概念几乎每次都会出现。关于考试日程和报名费用，文中未予列出，如有需要可自行访问官方网站查询。

## 为什么需要规范化

假设在一个表中同时包含了学生、课程和负责教授的信息。由于教授的名字会随着学生数量的增加而重复出现，这种冗余会导致异常现象（anomaly）产生。考试中通常会分别考查以下三种情况：

| 异常类型 | 何时发生 | 示例 |
| --- | --- | --- |
| 插入异常 | 必须同时存在不需要的值才能插入数据 | 没有注册学生的新课程无法创建行 |
| 删除异常 | 删除一行导致其他信息也随之丢失 | 删除最后一名学生后，课程信息也消失了 |
| 更新异常 | 仅修改部分重复值导致产生矛盾 | 更改两行教授姓名，导致一门课出现两个名字 |

规范化的目的是以函数依赖为标准来拆分表格，从而避免上述问题。数据库基础概念已在 [详细 → 数据库基础与数据模型](#/post/jb-db-concept) 中单独整理。

## 从函数依赖开始

规范化问题的核心在于能否正确理解函数依赖。当已知 A 就能唯一确定 B 时，称 B 函数依赖于 A，记作 A → B。例如：学号 → 姓名。

- **完全函数依赖**：必须知道整个主键才能确定值。例如在复合键（学号，课程）中，成绩就是如此。
- **部分函数依赖**：仅知道复合键的一部分即可确定值。例如在（学号，课程）中，若仅凭学号就能确定姓名，则姓名为部分依赖。
- **传递函数依赖**：由于 A → B 且 B → C，因此通过路径成立 A → C。例如：学号 → 学院，学院 → 院长，则学号 → 院长为传递依赖。

## 范式顺序

范式是在满足前一阶段条件的基础上，附加下一层条件的结构。

| 范式 | 附加条件 | 消除的内容 |
| --- | --- | --- |
| 第一范式 (1NF) | 所有属性均为原子值 | 单个单元格包含多个值 |
| 第二范式 (2NF) | 消除部分函数依赖 | 依赖于复合键部分的属性 |
| 第三范式 (3NF) | 消除传递函数依赖 | 通过非键属性传递的依赖 |
| BCNF | 所有决定因素均为候选键 | 非候选键的决定因素 |
| 第四范式 (4NF) | 消除多值依赖 | 相互无关的多值属性组合 |
| 第五范式 (5NF) | 消除连接依赖 | 不经过候选键的连接依赖 |

记忆方法如下：1NF 是每个单元格一个值；2NF 是移除依附于部分键的属性；3NF 是移除通过非键属性传递的依赖；BCNF 是所有决定因素必须都是候选键。

<details>
<summary>通过示例观察 2NF 和 3NF 的分解</summary>

假设有一个名为“选课”的表，包含字段（学号，课程，姓名，学院，院长，成绩），主键为（学号，课程）。

1. 成立 学号 → 姓名、学院。这是依赖于部分键的部分依赖。要满足 2NF，需进行分解：
   - 学生（学号，姓名，学院，院长）
   - 选课（学号，课程，成绩）
2. 在学生表中，成立 学院 → 院长。由于 学号 → 学院 → 院长，形成传递依赖。要满足 3NF，需再次分解：
   - 学生（学号，姓名，学院）
   - 学院（学院，院长）

进行分解时，必须确保重新连接后能无损恢复原始数据（无损连接），同时不能丢失函数依赖（依赖保持）。在解题时应养成检查这两个条件的习惯。
</details>

## 反规范化

过度规范化会导致表格被拆分成过多部分，查询时需要频繁执行连接操作，从而影响性能。当性能成为瓶颈时，可故意允许冗余，采用反规范化策略。考试中常考查反规范化与规范化的对立概念，以及在牺牲数据一致性以换取查询性能时的权衡。关于物理设计方面的内容，请参见 [详细 → DB 物理设计与分布式数据库](#/post/jb-physical-design)。

## 事务与 ACID

事务是一个逻辑工作单元。例如转账操作必须同时完成取款和入账才有意义，因此将两条 SQL 语句捆绑为一个事务。该绑定需满足以下四个性质，统称为 ACID：

| 性质 | 含义 | 保障方 |
| --- | --- | --- |
| 原子性 (Atomicity) | 要么全部执行，要么完全不执行 | 恢复机制 |
| 一致性 (Consistency) | 执行前后约束条件必须保持成立 | 完整性约束 |
| 隔离性 (Isolation) | 执行过程中的中间结果对其他事务不可见 | 并发控制 |
| 持久性 (Durability) | 已提交的结果在故障后依然保留 | 日志 |

曾使用 SQLite 亲自验证了原子性：设置余额不能小于零的约束，并在转账过程中违反该约束。

```python
import sqlite3
c = sqlite3.connect(":memory:", isolation_level=None)
c.execute("create table acct(id integer primary key, bal int check(bal>=0))")
c.execute("insert into acct values(1,1000),(2,0)")
try:
    c.execute("begin")
    c.execute("update acct set bal=bal-300 where id=1")
    c.execute("update acct set bal=bal+300 where id=2")
    c.execute("update acct set bal=bal-900 where id=1")  # 700-900 < 0
    c.execute("commit")
except sqlite3.IntegrityError as e:
    c.execute("rollback")
    print("rollback:", e)
print(c.execute("select * from acct").fetchall())
```

执行后会出现 `rollback: CHECK constraint failed: bal>=0` 错误，余额状态保持为 `[(1, 1000), (2, 0)]` 的初始状态。尽管前面的两个 UPDATE 操作已成功，但回滚后它们也随之消失。这就是原子性。该流程中的 SQL 语法（COMMIT、ROLLBACK、SAVEPOINT）将在 [详细 → SQL 应用](#/post/jb-sql-basic) 中继续讲解。

## 并发控制与隔离级别

当多个事务同时运行时，若隔离性被破坏，则会出现以下现象：

- **更新丢失**：两个事务读取了相同的值并各自进行修改，其中一方的结果被另一方覆盖。
- **脏读 (Dirty Read)**：读取了其他未提交事务的值。
- **不可重复读 (Non-repeatable Read)**：两次读取同一行数据时，由于中间有其他事务修改了该行，导致读取到的值不同。
- **幻读 (Phantom Read)**：在相同条件下进行两次查询时，由于其他事务插入了新行，导致结果集的行数发生变化。

PostgreSQL 文档中的表格列出了标准的四种隔离级别及其允许的现象：

| 隔离级别 | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| Read Uncommitted | 允许 | 允许 | 允许 |
| Read Committed | 防止 | 允许 | 允许 |
| Repeatable Read | 防止 | 防止 | 允许 |
| Serializable | 防止 | 防止 | 防止 |

该表基于 SQL 标准，但实际产品的实现可能有所不同。例如，PostgreSQL 即使指定了 `Read Uncommitted`，内部仍按 `Read Committed` 行为执行；即使在 `Repeatable Read` 级别下也不会产生幻读。SQLite 默认将所有事务置于可串行化（SERIALIZABLE）级别。考试答题时以标准表格为准即可。

隔离级别越高越安全，但并发处理能力会相应降低。考试中常涉及这种权衡。

### 并发控制技术

| 技术 | 核心 |
| --- | --- |
| 锁机制 (Locking) | 对数据加锁以控制访问。包括共享锁（读）和独占锁（写）。 |
| 两阶段锁 (2PL) | 分为只增加锁的扩展阶段和只释放锁的收缩阶段，保证可串行化。 |
| 时间戳 (Timestamp) | 根据启动时间的顺序确定作业执行顺序。 |
| 乐观验证 (Optimistic Validation) | 先执行操作，在提交前检查冲突。 |
| 多版本并发控制 (MVCC) | 保留数据的多个版本，使读操作不受写操作影响。 |

<details>
<summary>死锁与 2PL 总结</summary>

两阶段锁（2PL）能保证可串行化，但无法防止死锁（deadlock）。例如，T1 持有 A 资源并等待 B，而 T2 持有 B 资源并等待 A，双方将无限期互相等待。应对策略主要分为三个方向：

- **预防**：一次性请求所需的所有锁，或对资源进行排序以避免循环等待。
- **避免**：每次请求时检查是否会产生死锁，仅在安全时才允许执行。
- **检测与恢复**：当等待图中出现环时判定为死锁，并回滚其中一个牺牲者事务。

SQLite 文档指出，在 WAL 模式下，若读事务试图升级为写操作，而此时其他连接已提交，则会抛出 `SQLITE_BUSY_SNAPSHOT` 错误。因此，若计划进行写入，应使用 `BEGIN IMMEDIATE` 从一开始就获取写锁。虽然这不在考试范围内，但有助于理解锁和快照的实际表现。
</details>

## 恢复

发生故障时，为了保持原子性和持久性，系统会使用日志。日志中包含事务 ID、目标数据、修改前的值（Before Image）和修改后的值（After Image）。

| 技术 | 操作 |
| --- | --- |
| REDO | 根据日志中的后续值重新执行已提交的事务。 |
| UNDO | 根据日志中的先前值撤销未提交的事务。 |
| 即时更新 (Immediate Update) | 在提交前直接将更改写入数据库。发生故障时可能需要同时执行 REDO 和 UNDO。 |
| 延迟更新 (Deferred Update) | 在提交时将更改写入数据库。通常只需 REDO 即可。 |
| 检查点 (Checkpoint) | 确认到特定时点的更改，从而缩小恢复范围。 |
| 影子分页 (Shadow Paging) | 不依赖日志，而是保留页面副本并在提交时进行切换。 |

关于检查点的问题，常见类型是根据日志判断“该事务需要 REDO，那个事务需要 UNDO"。在检查点之前已提交的事务已经反映到数据库中，无需处理；在检查点之后提交的需要 REDO；而在故障发生时未能提交的事务则需要 UNDO。

## 常见题型与解决顺序

- 异常现象区分：通过删除并重新插入行来确认是插入、删除还是更新场景。
- 范式判定：首先确定主键，然后用箭头表示依赖关系，依次观察部分函数依赖 → 传递函数依赖 → 决定因素。
- ACID 属性匹配：原子性对应恢复，隔离性对应并发控制，持久性对应日志，按此记忆。
- 隔离级别表：级别越低，允许的现象越多，像填空一样绘制表格。
- 恢复技术：用线画出检查点和提交点，划分 REDO 和 UNDO。
