子代理是一种结构：主代理将部分任务剥离，在新的上下文中交给子代理执行，并仅接收结果摘要。这种模式仅在任务能够并行化且结果足以通过摘要概括时才带来好处。

## 先说人话

如果一个代理独自工作，它读取的文件、搜索结果和日志都会全部累积在其对话历史中。[上下文](#/post/ai-context) 很快就会变得沉重。因此出现了“这部分由另一个代理单独调查，只告知结论”的方式。接受任务的称为子代理，这种多个代理协作的整体结构被称为多代理系统。用人团队来比喻的话，类似于队长将一项调查任务交给队员，并只接收一份报告。但这仅是比喻，实际上意味着多了一次模型调用。

如果 [代理循环](#/post/ai-agent-loop) 是一种通过调用工具而运转的结构，那么子代理在其中常被用作“在循环内部启动另一个循环的工具”。关于工具调用本身，已在 [工具使用](#/post/ai-tool-use) 文章中单独整理。

## 原理：分割上下文

根据 Claude Code 文档，子代理的定义如下：

- 各自拥有独立的上下文窗口、系统提示词、工具权限及权限设置。
- 无法查看主对话的记录。主代理仅通过撰写对任务的摘要消息进行委派。
- 完成后仅将最终结果返回给主代理。中间读取的文件内容或搜索结果不会进入主代理。
- 使用额度限制与主对话共享，并非额外免费额度。

核心在于最后两点：杂乱的中间过程在子代理的窗口中结束，主代理仅接收结论。因此 [上下文窗口](#/post/ai-context-window) 填充较少。这与 [压缩](#/post/ai-compaction) 目的相同但方式不同：压缩是减少已累积的内容，而子代理则是从一开始就不让内容堆积到主代理中。

Anthropic 的上下文工程文章也提到，接收子代理结果时通常进行 1,000~2,000 个 token 左右的摘要，这与上述逻辑一致。该数字源自前文所述。

## 并行化与编排者 - 工作者模式

Anthropic 的《构建高效代理》一文区分了两种看似相似的模式：

| | 并行化 | 编排者 - 工作者 |
|---|---|---|
| 分割主体 | 代码预先设定 | 中央模型根据输入动态决定 |
| 子任务 | 预先定义（如分块、重复相同任务并投票） | 难以预先预测 |
| 适用场景 | 独立片段、追求速度 | 如修复多个文件的编程任务等 |

子代理结构大多属于右侧模式。编排者（lead）将任务分解并委派给工作者（子代理）。若让多个工作者同时运行，也能获得并行化效果。

在 Anthropic 撰写的多代理研究系统文章中给出了具体数据：引导代理采用 Claude Opus 4，子代理采用 Claude Sonnet 4；在同一内部研究评估中，其表现比仅使用 Opus 4 单独运行高出 90.2%。优势主要体现在需要广泛探索多个分支的问题（广度优先搜索）上。引导代理同时启动 3~5 个子代理，且每个子代理同时调用 3 个以上工具，据称将复杂查询的调查时间最多减少了 90%。由于两者均为 Anthropic 内部评估，本人并未复现。

## 成本：这是最关键的因素

同一文章中的 token 数量统计如下：

| 结构 | 相对于聊天的 token 用量 |
|---|---|
| 代理 | 约 4 倍 |
| 多代理 | 约 15 倍 |

在 BrowseComp 评估中，token 使用量解释了性能差异的 80%。若将工具调用次数和模型选择因素一并考虑，则占比达 95%。反过来解读意味着，多代理系统之所以表现更好，相当一部分原因可能是“因为使用了更多 token"。这并非结构更聪明，而是通过阅读更多内容、尝试更多方案而提升。需注意，这只是我在阅读过程中产生的推测，并非文章本身的结论。文章也指出，只有当 token 成本的增长与任务价值相匹配时，该方案才值得采用。

从 [AI 成本](#/post/app-cost) 角度来看，总结如下：增加一个子代理后，该子代理的输入和输出 token 全部计入费用。节省的并非主上下文减少的部分，而是新增的开销。在 [节省 token 的方法](#/post/claude-tokens) 中讨论时，这一点也是首要考虑因素。不过，由于可以为每个子代理指定不同的模型（依据 Claude Code 文档，`model` 字段可设为 sonnet、opus、haiku、fable、完整模型 ID 或 inherit），因此对于简单调查任务，将其委派给小型模型以节省成本是可行的。

## 何时不应使用

如果 Anthropic 的文章不适用，我会亲自撰写。并非所有代理都需要相同的上下文，或者彼此高度依赖。编程任务相比研究更难并行分割，且让代理实时协调目前尚不成熟。

我也阅读了另一篇文章。Cognition 的"Don't Build Multi-Agents"提出了两项原则：

- **共享上下文**：不是针对单个消息，而是整个代理记录（trace）。
- **行为中包含隐性决策**：如果决策相互冲突，结果会很糟糕。

示例是复刻 Flappy Bird。一个子代理创建类似超级玛丽的背景，另一个则制作与游戏风格不符的鸟。最后一个代理需要将这两者协调一致。据说即使将原始任务说明同时提供给两者也无法完全解决。实际对话涉及多轮交互，且工具调用会改变解释。替代方案包括：单线程代理（上下文连续）、独立的压缩模型以减少历史记录，以及限制性的子代理。这篇文章评价称，Claude Code 的子代理主要用于回答明确问题且不并行编写代码，因此冲突较少。

两篇文章并非在说同样的话。Anthropic 认为对于调查类任务（正确的事情），多代理效果显著更好；而 Cognition 则建议对于涉及编写和决策的任务需谨慎对待。我将此总结为：“阅读与调查可以分工，编写与决策应在同一处进行”。这是我读完两篇文章后得出的个人总结。

文档中整理的选择标准也类似：

- **子代理**：当输出过长而不希望放在主线程时、想要限制工具权限时、任务独立且可以通过摘要返回结果时。
- **主对话**：需要频繁交互并不断打磨时、多个步骤需共享大量上下文时、进行快速的小幅修改时、延迟至关重要时（因为子代理从零状态开始，需要时间收集上下文）。

## 委托时遇到的问题

如果委托说明不充分，工作会出现重叠。Anthropic 的文章中就有此类案例。某个子代理调查了 2021 年的汽车半导体危机，而另外两个则同样调查了 2025 年的供应链。结论是必须向每个子代理明确目标、输出格式、来源指南和工作边界。这意味着传递给子代理的 [提示词](#/post/ai-prompt) 就是全部内容，因为子代理无法看到主对话。

另一个问题是规模调整。早期版本据说对简单问题也启动了 50 个子代理。解决方法是将规则写入提示词。例如：简单事实查找使用 1 个代理调用工具 3~10 次；直接比较使用 2~4 个子代理，每个调用 10~15 次；复杂调查可使用 10 个以上。

## 常见误解

- **使用子代理会减少 token**：虽然主上下文减少了，但整体 token 往往会增加。上述 15 倍的数值就是例子。
- **代理越多越聪明**：如果任务具有依赖性，反而会导致冲突。
- **子代理也知道我的对话**：普通子代理不知道。继承主对话是通过 fork（分支）方式实现的。文档仅提到 fork 会继承父级对话。
- **子代理可以无限嵌套**：根据文档，默认值为主线程下最多 3 层，且可通过环境变量更改。同时执行的默认上限是 20 个。

<details>
<summary>详细解析：Claude Code 子代理文件结构</summary>

文档中提到的子代理是带有 YAML frontmatter 的 Markdown 文件，正文内容作为系统提示词。必需字段仅有 `name`和`description`。Claude 会根据 `description` 判断何时进行委托。可以直接称呼名称或使用 `@` 提及，也可以使用 `claude --agent <name>` 将整个会话切换为该代理。

```markdown
---
name: code-reviewer
description: Reviews code for quality and best practices. Use proactively after code changes.
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

上述示例是直接从文档中复制的，并非我实际运行过的结果。

工具限制通过 `tools`（允许列表）和 `disallowedTools`（禁止列表）进行。禁止列表优先应用，同时出现在两个列表中的工具将被移除。内置子代理包括 Explore（只读，代码搜索）、Plan（只读，计划模式调查）和 general-purpose（所有工具）。如果存储位置重叠，优先级顺序为：组织管理设置 > `--agents` 标志 > 项目 `.claude/agents/` > 用户 `~/.claude/agents/` > 插件。模型确定顺序为：调用时指定的值、文件中的 `model`、环境变量 `CLAUDE_CODE_SUBAGENT_MODEL`、主代理模型。

每个子代理都会创建新实例。若要继续执行，需使用 `SendMessage` 指定代理 ID 或名称以恢复会话。文档指出，恢复后的代理会保留完整记录。Explore 和 Plan 属于一次性使用，无法恢复。

从 [Harness](#/post/ai-harness) 的角度来看，启动子代理、接收结果以及遵守配额并非模型本身的功能，而是外部代码的工作。这种关联是我个人的解读。
