시간복잡도는 입력이 커질 때 연산 횟수가 얼마나 빨리 늘어나는지를 적는 방법이고, 코테에서는 입력 크기만 보고 "이 풀이로 시간 안에 되나"를 미리 가늠하는 데 쓴다.

## 시간복잡도가 뭔지

같은 문제를 풀어도 코드마다 걸리는 시간이 다르다. 초 단위로 재면 컴퓨터마다 달라지니까, 입력 크기 n이 커질 때 연산 횟수가 어떤 식으로 늘어나는지만 본다. 이걸 Big-O로 적는다.

- 배열을 한 번 훑으면 n번 정도 일한다. O(n).
- 이중 반복문이면 n×n번이다. O(n²).
- 매번 절반으로 줄이면 log n번이다. O(log n).

상수배나 낮은 차수는 버린다. 3n+5도, 100n도 O(n)이다. 실제로는 100배 차이가 나지만 n이 커질 때 곡선의 모양이 같다는 얘기라서 그렇게 묶는다. 보통은 최악의 경우를 기준으로 적는다.

## 입력 크기로 어림하기

코테 서버는 대략 1초에 파이썬으로 수천만 번 정도의 단순 연산을 돈다고 잡는다. 이 수치는 채점 환경마다 달라서 정확한 값이 아니라 감이다. 이 감으로 n의 범위를 보면 쓸 수 있는 풀이가 거의 정해진다.

| n의 최대값 | 대략 허용되는 복잡도 | 떠올릴 것 |
|---|---|---|
| 10~20 | O(2ⁿ), O(n!) | 완전 탐색, 백트래킹 |
| 500 | O(n³) | 삼중 반복, 플로이드 워셜 |
| 5,000 | O(n²) | 이중 반복, 간단한 DP |
| 100,000~1,000,000 | O(n log n) | 정렬, 이분 탐색, 힙 |
| 10,000,000 이상 | O(n) 또는 O(log n) | 한 번 훑기, 수식 |

표는 감이라서 정확히 이렇다는 건 아니다. 그래도 n이 10만인데 이중 반복문을 짜고 있으면 10¹⁰번이라 시간 초과가 난다는 걸 바로 알아챌 수 있다. 코드를 짜기 전에 이 계산부터 하는 습관이 제일 값어치가 컸다.

## 자주 보는 복잡도 몇 개

- O(1): 인덱스로 값 꺼내기, 딕셔너리에서 키로 찾기(평균).
- O(log n): 정렬된 배열에서 이분 탐색. [자세히 → 정렬과 이분 탐색](#/post/algo-sort-search)
- O(n): 리스트 한 번 훑기, 합 구하기, 최댓값 찾기.
- O(n log n): 정렬. 파이썬 `sort()`가 여기에 해당한다.
- O(n²): 모든 쌍을 비교하는 이중 반복문.
- O(2ⁿ): 원소마다 "넣는다/안 넣는다"를 고르는 모든 부분집합. [자세히 → 재귀와 백트래킹](#/post/algo-recursion)

공간복잡도도 같은 식으로 적는다. 추가로 쓰는 메모리가 입력 크기에 비례해 늘면 O(n)이다. 코테에서는 시간 쪽이 먼저 문제가 되는 일이 많지만, DP 표를 n×n으로 잡으면 메모리도 같이 본다.

## 예시: 두 수의 합

"배열에서 합이 target인 두 원소의 위치를 찾아라" 같은 문제를 생각해 보자. 이중 반복문으로 모든 쌍을 보면 O(n²)이다. 지나온 값을 딕셔너리에 적어 두고 `target - x`가 이미 있는지만 보면 O(n)이다.

```python
def two_sum_slow(a, t):          # O(n^2)
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):
            if a[i] + a[j] == t:
                return (i, j)

def two_sum_fast(a, t):          # O(n), 공간 O(n)
    seen = {}
    for i, x in enumerate(a):
        if t - x in seen:
            return (seen[t - x], i)
        seen[x] = i
```

직접 돌려 보니 둘 다 `1..3000`에서 같은 답 `(2998, 2999)`를 냈다. 시간은 느린 쪽이 n=5,000에서 0.25초, 빠른 쪽은 n=200,000에서 0.025초였다. 입력이 40배 큰데도 10배 빨랐다. 시간은 내 PC 기준이라 숫자 자체는 의미가 없고, 격차만 보면 된다. 시간을 줄이려고 메모리를 쓴 셈이다. 이런 맞바꿈이 해시를 쓰는 이유다. [자세히 → 배열·문자열·해시](#/post/algo-array-hash)

<details>
<summary>Big-O 정의를 식으로 보면</summary>

f(n)이 O(g(n))이라는 건, 충분히 큰 n부터 f(n) ≤ c·g(n)이 되는 양수 c가 있다는 뜻이다. 예를 들어 f(n) = 3n² + 10n + 7이면 n ≥ 1에서 f(n) ≤ 20n²이라 O(n²)이다.

같은 O(n)이어도 반복 한 번에 하는 일이 다르면 실제 시간은 꽤 차이 난다. 코테에서 상수배는 대개 무시하지만, 한도가 빠듯한 문제에서는 상수가 갈리는 경우가 있다.
</details>

## 파이썬에서 느려지기 쉬운 자리

복잡도는 알고리즘만의 문제가 아니라 쓰는 자료구조 연산에도 붙어 있다. 파이썬에서는 겉보기엔 한 줄인데 안에서 O(n)인 연산이 몇 개 있다.

| 하려는 일 | 느린 쓰기 | 빠른 쓰기 |
|---|---|---|
| 앞에서 꺼내기 | `list.pop(0)` O(n) | `deque.popleft()` O(1) |
| 값이 있는지 확인 | `x in list` O(n) | `x in set` 평균 O(1) |
| 문자열 이어 붙이기 | 반복 `s += t` | 리스트에 모아 `"".join()` |
| 중간 원소 접근 | `deque[i]` O(n) | `list[i]` O(1) |

`collections.deque` 공식 문서에 리스트는 `pop(0)`과 `insert(0, v)`에서 O(n) 메모리 이동 비용이 든다고 적혀 있고, deque는 양 끝에서 넣고 빼는 게 O(1)이라고 나온다. 같은 문서에 deque의 인덱스 접근은 양 끝이 O(1), 가운데는 O(n)이라는 말도 있다. 큐가 필요하면 deque, 인덱스로 자주 뒤지면 리스트다. [자세히 → 스택·큐·덱](#/post/algo-stack-queue)

내 PC에서 재 본 값은 이렇다. 시간은 환경 따라 다르고 비율만 참고한다.

| 실험 | 시간 |
|---|---|
| 10만 개 리스트에서 `pop(0)` 5만 번 | 0.36초 |
| 같은 크기 deque에서 `popleft()` 5만 번 | 0.001초 |
| 2만 개 리스트에서 `in` 2천 번 | 0.12초 |
| 2만 개 set에서 `in` 2천 번 | 0.0001초 |

문자열 쪽은 파이썬 공식 문서(시퀀스 타입)에, 불변 시퀀스를 반복해서 이어 붙이면 전체 길이에 대해 제곱 시간이 든다고 나온다. 문자열은 리스트에 모아 두었다가 `join`으로 한 번에 붙이라는 안내가 같이 있다.

정렬은 `sort()`와 `sorted()`가 안정 정렬이라고 문서에 적혀 있다. 같은 값끼리 원래 순서를 유지한다는 뜻이고, 기준을 두 번에 나눠 정렬할 때 이 성질을 쓴다. 정렬 자체는 O(n log n)으로 알고 있으면 된다.

## 코테용 입출력 기본

입력이 많은 문제에서는 `input()`이 느려서 시간 초과의 원인이 되기도 한다. 그래서 보통 이렇게 시작한다.

```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
arr = list(map(int, input().split()))
print(n, m, arr)
```

`3 5`와 `1 2 3`을 넣어 돌려 보니 `3 5 [1, 2, 3]`이 그대로 나왔다. `readline`은 줄 끝의 개행 문자를 같이 읽어서, 문자열 그대로 쓸 때는 `.rstrip()`을 붙인다. 숫자로 바꿀 때는 상관없다.

재귀를 깊게 쓰는 문제에서는 파이썬 기본 재귀 한도가 낮아서 `sys.setrecursionlimit`을 올리는 경우가 많다. 이 부분은 재귀 글에서 이어서 본다. 이 글에서 직접 돌려 확인한 것은 위 코드들까지다.

출력이 많으면 `print`를 매번 부르지 말고 리스트에 모아서 `"\n".join(...)`으로 한 번에 낸다. 이것도 위 문자열 이어 붙이기와 같은 이유다.

<details>
<summary>입력이 한 줄에 몇 개 오는지 헷갈릴 때</summary>

- 한 줄에 정수 하나: `n = int(input())`
- 한 줄에 정수 여러 개를 변수로: `a, b = map(int, input().split())`
- 한 줄에 정수 여러 개를 리스트로: `arr = list(map(int, input().split()))`
- 여러 줄이 격자로 올 때: `grid = [list(map(int, input().split())) for _ in range(n)]`
- 숫자가 붙어 있는 문자열(예: `10110`): `list(map(int, input().rstrip()))`

위의 `readline` 방식에서는 입력 끝 개행을 `int()`가 알아서 처리해 주고, 문자열 줄은 `rstrip()`이 필요하다.
</details>

## 흔한 오해

- 복잡도가 낮으면 무조건 빠르다: n이 아주 작을 때는 단순한 O(n²)가 복잡한 O(n log n)보다 빠를 수 있다. 어림은 n이 클 때 맞는다.
- 반복문이 중첩되면 무조건 O(n²): 안쪽이 상수번만 돌면 O(n)이다. 안쪽 범위가 무엇에 따라 변하는지를 봐야 한다.
- 파이썬 내장 함수는 다 O(1): `in`, `list.index`, `list.count`, 슬라이싱은 다 길이만큼 든다. 한 줄이라고 가벼운 게 아니다.
- 평균과 최악은 같다: 딕셔너리·set의 O(1)은 평균 얘기라서, 해시가 심하게 겹치면 느려질 수 있다는 점은 알고 있어야 한다.

DB에서 인덱스를 거는 이유도 비슷한 계산이다. 전체를 훑는 O(n) 대신 트리를 타고 O(log n)으로 찾겠다는 것이다. 그쪽은 [자세히 → 인덱스](#/post/db-index)에서 다룬다.

알고리즘 유형이 전체적으로 어떻게 나뉘는지는 지도 글에 모아 둘 예정이다. 자세히 → 알고리즘 유형 지도

대부분의 시간 초과는 코드를 늦게 짜서가 아니라 짜기 전에 n을 안 봐서 났다.

## 확인 못 함

- Python 위키 TimeComplexity 표(딕셔너리·set의 평균 O(1), 리스트 연산별 표)는 리다이렉트 때문에 열지 못했다. 본문의 dict/set 평균 O(1)은 그 표가 아니라 일반적으로 알려진 내용이다.
- "1초에 파이썬으로 수천만 번"이라는 기준과 n 범위 표는 출처 없는 어림이다.
- `sys.setrecursionlimit` 사용법과 `sorted`의 정렬 알고리즘 이름은 문서에서 확인하지 못했다.
- 시간 측정은 내 PC 한 번의 결과다.
