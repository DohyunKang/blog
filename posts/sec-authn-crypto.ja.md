暗号化、ハッシュ、電子署名は似て見えるものの、解読しようとする問題は異なります。暗号化とは隠して後で元に戻すこと、ハッシュとは戻さずに同じかどうかだけ確認すること、署名とは誰が作成したか、改ざんされていないかを確認することです。

## まず 3 つを区別すると

| ツール | 復元可能か | キー | 主な用途 |
|---|---|---|---|
| 対称鍵暗号 | 可能 | 1 つ（同じ鍵） | データを隠す |
| 非対称鍵暗号・署名 | 暗号化は可能 | 公開鍵 + 秘密鍵 | キー交換、署名検証 |
| ハッシュ | 不可能 | なし | 完全性確認、パスワード保存 |

用語が混ざって混乱しましたが、質問を一つ投げると整理できました。原文が必要か（暗号化）、同じかどうかだけ分かればよいのか（ハッシュ）、送信元が正しいかが重要なのか（署名）。

## 対称鍵暗号

同じ鍵でロックし、同じ鍵で解きます。高速です。ファイルや通信など、実際に大量のデータを隠すのはほぼ対称鍵が行っています。現在標準として使われているのが AES で、近年は暗号化と改ざん検知を同時に行う AEAD 方式（AES-GCM、ChaCha20-Poly1305 など）を使います。RFC 8446 によると TLS 1.3 も AEAD ではない暗号を取り除いています。

弱点は一つです。両者が同じ鍵をどのように安全に共有するかという点です。インターネット上で鍵をそのまま送ると、隠す意味がありません。

## 非対称鍵暗号

鍵はペアです。公開鍵は誰にでも渡してもよく、秘密鍵は自分だけが持っています。公開鍵でロックしたものは秘密鍵でのみ解けます。そのため、初めて会う相手とも秘密をやり取りする手段が生まれます。

しかし遅いです。そのため実際には組み合わせて使います。非対称方式で対称鍵を合意し、その後に本文を対称鍵で暗号化します。TLS もこの構造です。RSA、楕円曲線（ECDH、ECDSA など）が代表的です。

<details>
<summary>キー交換が実際どのように行われるか (Diffie-Hellman 系)</summary>

TLS 1.3 では鍵を相手に「送る」のではなく、両者がそれぞれ一時的な鍵ペアを作り、公開値のみをやり取りして同じ秘密値を計算し出します。中間で公開値をすべて見てもその秘密値を計算するのは困難だという数学に頼る方式です。一時的な鍵なのでセッションが終了すると破棄され、後からサーバーの長期鍵が漏れても過去の通信は解読できません。これを順方向秘匿性 (forward secrecy) と言い、RFC 8446 は TLS 1.3 の公開鍵ベースのキー交換がすべてこの性質を持つと記述しています（PSK だけのモードと 0-RTT データは例外）。
</details>

## ハッシュ

入力が何であっても固定長の値を出力する関数です。同じ入力には常に同じ値が返され、値から入力を逆算するのは困難です。1 つの文字が変わるだけで結果が完全に変わります。

```python
import hashlib
hashlib.sha256(b"hello").hexdigest()
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
hashlib.sha256(b"hellp").hexdigest()
# fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7
```

上記 2 つの値は実際に計算して確認しました。ファイルダウンロード後にチェックサムを合わせるのもこの用途です。値が同じであれば変更されていないということです。

さらに一つ。ハッシュは「鍵なし」で誰でも計算できます。そのため改ざんを防ぐには鍵を混ぜた HMAC を使います。鍵を知っている側だけが正しい値を作成できます。

## パスワードは単にハッシュするだけではダメです

SHA-256 は高速に設計されており、パスワード保存においてはその速度が逆に問題になります。データベースが漏洩すると攻撃者が毎秒膨大な数の候補を当てようとして試し、同じパスワードには同じハッシュ値が出るため事前に計算した表（レインボーテーブル）も使われてしまいます。

そのため 2 つの要素を追加します。

- ソルト：ユーザーごとに異なるランダム値を混ぜます。同じパスワードでもハッシュ値が異なり、表は無効になります。ソルトは秘密ではなく、ハッシュの隣に一緒に保存しても構いません。
- 遅いハッシュ：意図的に時間やメモリを多く使う関数を使います。

OWASP パスワード保存チートシートでは優先順位を以下のように記述しています。Argon2id が第一位（最小 m=19456KiB、t=2、p=1）、それができない場合は scrypt、古いシステムの場合は bcrypt（コスト係数 10 以上、パスワード 72 バイト制限）、FIPS 規則を守る必要がある場合は PBKDF2-HMAC-SHA256 60 万回。ソルトはパスワードごとに個別にランダムに生成し、大半のライブラリが自動で行ってくれるため自分で作る必要はないと勧められています。

```python
import hashlib, os, hmac
salt = os.urandom(16)
h = hashlib.pbkdf2_hmac("sha256", b"pw", salt, 600000)
hmac.compare_digest(h, hashlib.pbkdf2_hmac("sha256", b"pw", salt, 600000))  # True
```

実行すると 32 バイトの値が出力され、同じソルト・回数であれば同じ値が得られました。比較時に `compare_digest` を使ったのは、比較時間で値が漏れるのを防ぐためです。実際のサービスでは Argon2id をライブラリで使う方が良いでしょう（このコードは PBKDF2 の例なのでそれを確認したものです）。

<details>
<summary>ペッパー (pepper)</summary>

ソルトとは異なり、すべてのパスワードで共有する秘密値です。データベースの外（シークレットストレージ・HSM）に置きます。OWASP の説明ではそれだけでセキュリティが生まれるわけではなく、データベースのみ漏洩した際の備えとして補助的な装置です。ハッシュ前に混ぜたり、ハッシュ後にその値を鍵として HMAC を適用したりします。ペッパーが漏洩したら変更する必要があり、その場合影響を受けたユーザーはパスワードを再設定する必要があります。
</details>

## 電子署名

ハッシュと非対称鍵を組み合わせたものです。文書をハッシュ化した値を秘密鍵で署名すると、受け手は公開鍵で確認します。承認されれば 2 つのことがわかります。この秘密鍵の所有者が作成したものであり、署名後に文書が改ざんされていないことです。

暗号化と方向性が逆であることを覚えると覚えやすいです。暗号化は公開鍵でロックし、秘密鍵で解き、署名は秘密鍵で押印し、公開鍵で確認します。ソフトウェアの配布、JWT の署名、証明書もすべてこの原理に基づいています。

しかし、公開鍵が本当にその人のものかどうかがわかりません。ここで証明書と認証機関（CA）が登場します。証明書とは「このドメインの公開鍵はこれです」という内容に CA が署名したもので、ブラウザは信頼する CA のリストを辿ってチェーンを検証しながら確認を行います。

## TLS が行うこと

HTTPS の S はこれです。上記のツールを順番に使用します。RFC 8446 にまとめられた TLS 1.3 の流れは概ね以下の通りです。

1. クライアントが ClientHello を送信します。一時的な鍵交換値（key_share）とサポートする署名方式が含まれています。
2. サーバーが ServerHello で自らの key_share を返します。ここで両者が同じ秘密値を計算し、以降のメッセージは暗号化されます。
3. サーバーが証明書と CertificateVerify（秘密鍵による署名）、Finished を送信します。これがサーバーが本物である証明です。
4. クライアントが Finished を送ると、以降のデータは合意した対称鍵でやり取りされます。

基本のハンドシェイクは往復 1 回です。すでに一度接続した相手であれば 0-RTT で最初の送信にデータを載せることもできますが、RFC に記載されている通りこのデータには前向きな秘密性がありません。1.2 と比較すると静的 RSA キー交換、圧縮、古い暗号化方式などがなくなっています。

まとめると、非対称（鍵合意・署名）で身元を確認し鍵を作り、対称（AEAD）で本文を高速に暗号化し、ハッシュおよび HMAC が改ざんを検知します。

## よくある誤解

- ハッシュは暗号化ではありません。復元することが目的ではありません。「パスワードを『暗号化して保存』した」と言うのは復元可能という意味であり、むしろ危険な表現です。
- エンコード（Base64）も暗号化ではありません。誰でも解読できます。
- ソルトは秘密ではありません。同じ値が出力されるのを防ぐためのものです。
- 自分で暗号を作成しません。検証済みのライブラリと標準アルゴリズムを使用します。
- HTTPS の鍵マークはサイトが安全という意味ではありません。通信が途中で読み取られないこと、ドメインが正しいことまでを含みます。
