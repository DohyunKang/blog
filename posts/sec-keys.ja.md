API キーやパスワードなどのシークレットは、完璧に隠すことよりも、漏れた瞬間に即座に廃棄して再発行できる仕組みを構築しておくことが管理の核心でした。

## シークレットとは何か

シークレットとは「これを知らないと認められない」という値です。API キー、アクセストークン、DB パスワード、個人鍵（SSH・TLS）、ウェブフック署名値などがこれに含まれます。ログインパスワードとの違いは、人間ではなくプログラムが使用する点にあります。人間が記憶して入力するのではなく、コードや設定ファイルのどこかに置かれており、そのため漏れる経路が多くなります。

キーが漏れると他者が自分のアカウントに対してリクエストを送ることができます。クラウド上のキーであればサーバーを勝手に起動させて料金が請求されます。AI API キーであれば呼び出し費用が自分のカードから引き落とされます。したがって、キー管理はセキュリティの問題であると同時にコスト問題でもあります。

## どこで漏れるのか

一般的な漏洩経路を集めてみるとほぼ似ています。

| 経路 | どのように漏れるか |
|---|---|
| Git リポジトリ | `.env` や設定ファイルをそのままコミット、コードにキーを直接記述する |
| Git ヒストリ | 後で削除しても以前のコミットにはそのまま残っている |
| ログ | リクエストヘッダーや設定全体を出力した際にキーが一緒に記録される |
| チャット・ドキュメント | Slack や Issue、Wiki に「これ使え」と貼り付ける |
| クライアントコード | フロントエンドバンドルやアプリにキーを入れてデプロイすると誰でも開けて見られる |
| CI/CD | パイプライン変数がログに露出したり、長期間使用される大規模権限のキーをパイプラインに残したりする |

Git は特に注意が必要です。GitHub の secret scanning はすべてのブランチの履歴や Issue・PR 本文、Wiki もすべてスキャンするとドキュメントにあります。言い換えれば、この範囲にキーが残っている可能性があるということです。公開リポジトリにアップロードしたキーは人が見る前に自動的にスクレイピングするツールがあることはよく聞きますが、

## 4 つの原則

OWASP の Secrets Management Cheat Sheet にまとめられた内容の中から核心だけを抽出しました。

1. 中央で管理する。チームごとに方式が異なると事故が起きた際にどこに何が 있는지見つけるのが困難です。保存・認証・監査ログを一元化して標準化するとあります。
2. 最小権限を与える。シークレットごとに誰が読み書きできるかを細かく区別します。エンジニア全員が見られるべきではありません。
3. 定期的にローテーションする（回転）。盗まれたキーの寿命を短くする方法です。可能であれば自動化します。ユーザーパスワードは例外で、侵害が疑われる際に主に変更するとあります。
4. できるだけ短時間で使い捨てられる値（動的シークレット）を使用する。セッションやデプロイごとに新規発行し、貸出時間を短く設定します。アプリを再起動してもすでに盗まれたキーが無効になるわけではなく、無効化は期限切れまたは明示的な廃棄のみで行われます。

この 4 つは互いに連動しています。ローテーションが容易にするにはキーを使用する場所を一元化し、権限を狭くすることで漏洩時の被害も小さくなります。環境変数と `.env`、シークレットマネージャーの連携については [詳細 → 環境変数とシークレット管理](#/post/cloud-secrets) に別途まとめました。

## 保存はどこに

段階を追うと大まかに以下のように上がっていきます。

| 段階 | 方式 | 備考 |
|---|---|---|
| 0 | コードに直接記述 | 使用してはならない |
| 1 | `.env` ファイル + `.gitignore` | 個人開発・小規模プロジェクトの最低ライン |
| 2 | デプロイ環境の環境変数・プラットフォームシークレット | コードと分離される |
| 3 | シークレットマネージャー（クラウド提供サービス、Vault など） | 権限・監査・ローテーションを同時に解決する |

`.env` はローカル開発には便利ですが、ファイル自体が秘密となるため、リポジトリには `.env.example` のように名前だけのファイルをアップロードし、実際の値はアップロードしないように区別します。また、`.gitignore` はまだ追跡されていないファイルのみに対して機能します。すでにコミットされたファイルは `.gitignore` に追加しても引き続き追跡されます。これは一般的なミスであり、以下の誤解項目で再度記載しました。

OWASP は CI/CD にも同様の原則を適用するとあります。パイプラインを運用環境と同じくらい慎重に取り扱い、長期間使用される大規模キーをパイプラインに残さず、可能であればシークレットを使用する側が直接シークレットマネージャーから取得するようにして、パイプラインが値に触れることを完全に防ぐようにとあります。デプロイの流れについては [詳細 → CI/CD](#/post/cloud-cicd) にあります。

## 漏らしてしまった場合

順序が重要です。まず行うべきことは「削除」ではなく「廃棄」です。

OWASP は対応手順を以下のように記載しています。露出されたシークレットを即座に廃棄し、新しい値でローテーションする（可能な限り自動化）、コードやログなどの露出位置から削除し、誰がいつアクセスしたかの記録を残します。GitHub のドキュメントも同様です。まずキーをローテーションし、記録からの削除はオプションです。キーを廃棄した後、記録に残った値はすでに使用できないため、記録を修正する必要がない場合が多いとあります。

それでも記録から削除する必要がある場合は、GitHub ドキュメントの注意点が多くあります。

- 기록을 다시 작성하면 해당 커밋 및 이후 커밋의 해시가 모두 변경됩니다.
- 타인의 로컬 복제본이나 포크는 그대로이므로, 해당 측에서 다시 푸시할 경우 값이 복원될 수 있습니다.
- GitHub 의 캐시된 화면이나 PR 이 이전 커밋의 해시를 계속 표시할 수 있으므로, 이러한 경우에는 GitHub Support 에 정리를 요청해야 합니다.

즉 "지웠으니 괜찮다"는 뜻이 아닙니다. 따라서 키 폐기를 먼저 수행하고, 그 다음에 기록 정리를 진행해야 합니다.

<details>
<summary>자세한 풀이: git-filter-repo 로 기록에서 지울 때</summary>

GitHub 문서 기준으로 정리한 순서입니다.

1. 키를 먼저 폐기·회전합니다.
2. 열린 PR 을 먼저 병합하거나 닫습니다. 닫은 PR 의 diff 화면은 기록 수정 후 사라질 수 있습니다.
3. `git-filter-repo` 2.47 이상에서 `--sensitive-data-removal` 옵션을 사용합니다.
4. 파일 하나를 통째로 지우려면 `--invert-paths --path <경로>`, 문자열만 바꾸려면 `--replace-text <파일>`을 사용합니다. 파일이 이동·이름 변경된 적이 있으면 옛 경로도 함께 적습니다.
5. 도구가 생성하는 `changed-refs` 파일로 영향받는 PR 수를 확인합니다. 이 단계를 넘으면 되돌릴 수 없다고 합니다.
6. `git push --force --mirror origin`으로 올립니다. `refs/pull/` 쪽은 실패하는데, 이는 GitHub Support 가 처리합니다.
7. 공동 작업자는 다시 복제하거나, 옛 기록에서 만든 브랜치를 병합이 아닌 rebase 로 옮겨야 합니다. 병합하면 오염된 기록이 돌아옵니다.

브랜치 보호가 force push 를 막고 있으면 잠깐 풀어야 하며, 커밋 서명은 무효가 됩니다.

</details>

## 차단 장치들

사고 후 대응만 있는 것은 아닙니다. 올리기 전에 막는 장치가 있습니다.

- push protection: GitHub 에서 푸시를 하는 순간 하드코딩된 시크릿이 있는지 검사하여 저장소에 도달하기 전에 차단합니다. 제휴사 패턴, 개인 키나 DB 연결 문자열 같은 일반 패턴, 직접 정의한 정규식, 그리고 비밀번호 같은 비정형 값을 문맥으로 찾는 AI 탐지 (공개 프리뷰) 를 적용합니다. 다만 쓰기 권한이 있으면 사유를 대고 우회할 수 있으며, 우회는 감사 로그에 남습니다. 저장소 단위로 켜는 방식은 기본이 꺼져 있다고 문서에 적혀 있습니다.
- secret scanning: 이미 올라간 것을 전체 기록에서 찾아 알림을 줍니다. 제휴 서비스의 키는 해당 서비스에 바로 알려서, 서비스가 알아서 폐기하기도 합니다.
- 로컬 커밋 전 검사: 도구마다 다르지만 원리는 비슷하게, 커밋 직전에 패턴을 훑습니다. 아래 코드는 그 원리만 보여주는 장난감입니다.

<details>
<summary>코드: 정규식으로 키 모양 찾기 (직접 실행해서 확인함)</summary>

아래 키는 AWS 문서에 나오는 예시 형태와 임의의 더미 문자열입니다. 진짜 키가 아닙니다.

```python
import re

PATTERNS = {
    "AWS 액세스 키 ID": re.compile(r"\bAKIA[0-9A-Z]{16}\b"),
    "개인 키 헤더": re.compile(r"-----BEGIN (?:RSA |EC )?PRIVATE KEY-----"),
    "대입문 속 비밀값": re.compile(
        r"""(?i)(?:api[_-]?key|secret|token|password)\s*[:=]\s*['"][^'"\s]{12,}['"]"""
    ),
}

def scan(text):
    hits = []
    for no, line in enumerate(text.splitlines(), 1):
        for name, pat in PATTERNS.items():
            if pat.search(line):
                hits.append((no, name))
    return hits

FAKE_AWS = "AKIA" + "IOSFODNN7EXAMPLE"  # AWS 문서의 공개 예시값(실제 키 아님)
sample = '''import boto3
AWS_KEY = "{FAKE_AWS}"
api_key = "dummy-not-a-real-key-123456"
url = os.environ["DB_URL"]
timeout = "30"
'''.replace("{FAKE_AWS}", FAKE_AWS)
for no, name in scan(sample):
    print(no, name)
```

실행하면 2 번 줄 (AWS 키 모양) 과 3 번 줄 (대입문 속 비밀값) 만 잡히고, 환경변수에서 읽는 4 번 줄과 짧은 값인 5 번 줄은 잡히지 않았습니다. 이 정규식은 모양만 보기 때문에 놓치는 것도 많고 (모양이 없는 임의의 비밀번호), 아무 문자열이나 잡는 오탐도 발생합니다. 실제 도구는 패턴이 훨씬 많으며, 키가 아직 유효한지 확인하는 기능도 추가됩니다.

</details>

## 흔한 오해

- `.gitignore` 에 넣었으니 안전하다: 아직 추적하지 않은 파일에만 효과가 있습니다. 이미 커밋한 파일은 계속 추적됩니다.
- 커밋을 지웠으니 끝났다: 기록, 포크, 타인의 복제본, 캐시에 남을 수 있습니다. 폐기가 먼저입니다.
- 비공개 저장소니까 괜찮다: 접근 권한이 있는 사람이 늘어나거나 저장소를 공개로 바꾸는 순간 같이 노출됩니다. 코드에 키를 적는 습관 자체가 문제입니다.
- 환경변수면 안전하다: 코드 밖에 둔다는 것뿐입니다. 로그에 찍히거나 프로세스 정보로 새는 것은 별개의 문제입니다. 시크릿 매니저는 권한·감사·회전을 더해 줍니다.
- 프런트 코드에 넣고 난독화하면 된다: 클라이언트에 내려가는 값은 누구나 볼 수 있다고 보는 것이 맞습니다. 서버를 거치게 만들어야 합니다.
- 회전은 귀찮으니 한 번 발급해서 오래 쓴다: 오래 쓸수록 유출 후 피해 기간이 길어집니다. 자동화가 어려우면 최소한 폐기 절차는 미리 정해 둡니다.
