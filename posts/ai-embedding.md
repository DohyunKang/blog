임베딩은 글(또는 이미지)을 숫자 목록으로 바꿔서 "뜻이 비슷하면 숫자도 가깝게" 만들어 둔 것이고, 벡터 검색은 그 숫자들 사이에서 가까운 것을 찾는 일이다.

## 임베딩이 뭔지

OpenAI 문서는 임베딩을 텍스트를 나타내는 부동소수점 숫자의 벡터(리스트)라고 설명한다. 두 벡터 사이의 거리가 텍스트 사이의 관련성을 나타내고, 가까울수록 관련이 높다는 식이다.

지도에 비유하면 이해가 쉬웠다. 서울과 부산은 위도·경도 두 숫자로 위치가 정해지고, 두 좌표가 가까우면 두 도시도 가깝다. 임베딩은 이 좌표를 문장에 붙이는 것이다. 다만 숫자가 2개가 아니라 수백~수천 개다. 문서에 나온 OpenAI 모델 기준으로 text-embedding-3-small은 기본 1536차원, text-embedding-3-large는 3072차원이다. 차원 수는 모델마다 다르다.

이 좌표는 사람이 정하지 않는다. 임베딩 모델이 학습 과정에서 비슷한 맥락에 쓰이는 글을 가까이 놓도록 배운다. 이 발상은 단어 단위로는 2013년 word2vec 논문(Mikolov 등)에서 널리 퍼졌다. 초록 기준으로, 큰 데이터에서 단어의 연속 벡터 표현을 싸게 학습하는 구조 두 가지를 제안하고 단어 유사도 테스트에서 당시 최고 수준을 냈다고 주장한다. 지금의 문장·문서 임베딩은 그 연장선에 있다고 이해했는데, 계보를 정확히 따라가 본 건 아니다.

LLM이 내부에서 단어를 숫자로 다루는 이야기는 [자세히 → LLM](#/post/ai-llm)에 있고, 여기서 말하는 임베딩은 "검색·비교용으로 글 하나를 벡터 하나로 만든 것"에 가깝다.

## 코사인 유사도

벡터 두 개가 얼마나 가까운지 재는 방법이 몇 가지 있는데, 텍스트에서는 코사인 유사도를 가장 많이 쓴다. 두 벡터가 이루는 각도를 본다. 같은 방향이면 1, 직각이면 0, 반대 방향이면 -1이다. 길이는 보지 않고 방향만 본다.

| 값 | 의미 |
|---|---|
| 1에 가까움 | 방향이 거의 같다, 뜻이 비슷하다 |
| 0 근처 | 관련이 별로 없다 |
| 음수 | 반대 방향 (실제 텍스트 임베딩에선 드문 편으로 알려져 있다) |

OpenAI 문서는 코사인 유사도를 권하고, 자기네 임베딩은 길이가 1로 정규화되어 있어서 내적만 계산해도 같은 결과가 나온다고 적는다. 코사인 거리와 유클리드 거리가 같은 순위를 낸다는 말도 있다. 길이가 1인 벡터끼리는 각도 순서와 거리 순서가 같기 때문이다. 그래서 실제 코드에서는 "정규화해 두고 내적"으로 끝내는 일이 많다.

<details>
<summary>자세한 풀이: 코사인 유사도 식</summary>

두 벡터 a, b에 대해 코사인 유사도는 이렇다.

cos(a, b) = (a · b) / (|a| × |b|)

a · b는 각 자리 숫자를 곱해서 다 더한 것(내적)이고, |a|는 벡터의 길이다. 두 벡터를 미리 길이 1로 맞추면 분모가 1이 되어 내적이 곧 코사인 유사도가 된다. 정규화를 저장할 때 한 번만 해 두면 검색할 때 곱셈·덧셈만 남아서 빠르다.

</details>

## 키워드 검색과 뭐가 다른가

키워드 검색은 질문에 들어 있는 단어가 문서에 그대로 있는지를 본다. 정확한 용어, 제품 코드, 에러 메시지를 찾을 땐 잘 맞는다. 다만 단어가 다르면 못 찾는다.

| | 키워드 검색 | 벡터 검색 |
|---|---|---|
| 기준 | 단어가 겹치는가 | 뜻이 가까운가 |
| "환불 방법"으로 "결제 취소 절차" 문서 찾기 | 단어가 달라서 놓치기 쉽다 | 뜻이 비슷하면 잡는다 |
| 에러 코드 `E4012` 찾기 | 정확히 잡는다 | 뜻이 없는 문자열이라 약하다 |
| 결과 이유 | 어떤 단어가 맞았는지 보인다 | 왜 가깝다고 했는지 설명하기 어렵다 |
| 준비물 | 인덱스 | 임베딩 모델 + 벡터 저장소 |

그래서 실무에서는 둘을 섞는 경우가 많다고 한다(하이브리드 검색). 이 부분은 공식 문서를 읽고 확인한 건 아니고 흔히 그렇게 말한다는 정도로 받아들였다. 검색 결과를 LLM에게 붙여서 답하게 하는 방식은 [자세히 → RAG](#/post/ai-rag)에서 이어진다.

## 직접 돌려 본 최소 코드

진짜 임베딩 모델 없이도 "벡터를 만들고, 정규화하고, 가까운 걸 찾는" 뼈대는 numpy만으로 볼 수 있다. 아래는 축을 일부러 3개(동물, 음식, 탈것)로 손으로 만든 장난감이다. 실제 모델은 이 숫자를 직접 만들어 준다는 점만 다르다. 이 코드는 내 PC에서 실행해서 동작을 확인했다(numpy 2.5.4).

```python
import numpy as np

# 손으로 만든 3차원 벡터 (축: 동물, 음식, 탈것)
docs = {
    "고양이가 잔다":     [0.9, 0.1, 0.0],
    "강아지가 뛴다":     [0.8, 0.1, 0.1],
    "김치찌개를 끓인다": [0.1, 0.9, 0.0],
    "자전거를 탄다":     [0.1, 0.0, 0.9],
}
names = list(docs)
M = np.array([docs[n] for n in names], dtype=float)
M /= np.linalg.norm(M, axis=1, keepdims=True)   # 길이 1로 정규화

def search(q, k=2):
    q = np.array(q, dtype=float)
    q /= np.linalg.norm(q)
    scores = M @ q                  # 정규화했으니 내적 = 코사인
    for i in np.argsort(-scores)[:k]:
        print(f"{scores[i]:.3f}  {names[i]}")

search([0.85, 0.15, 0.0])           # "동물 쪽" 질문
```

실행하면 "고양이가 잔다"가 약 0.998, "강아지가 뛴다"가 약 0.991로 위에 나온다. 음식·탈것 문장은 아래로 밀린다.

진짜 모델로 바꾸려면 숫자 만드는 부분만 갈아 끼우면 된다. 아래는 sentence-transformers를 쓰는 형태다.

```python
# pip install sentence-transformers 필요
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("all-MiniLM-L6-v2")   # 모델 이름은 예시
vecs = model.encode(["환불 방법", "결제 취소 절차"], normalize_embeddings=True)
print(vecs @ vecs.T)   # 정규화했으니 내적 = 코사인 유사도 표
```

## 벡터 DB와 ANN

위 코드는 질문 벡터를 문서 전부와 비교한다. 문서가 수백 개면 문제없는데, 수백만 개가 되면 질문마다 전부 비교하는 건 느리다. 그래서 정확히 가장 가까운 것 대신 "거의 가장 가까운 것"을 훨씬 빨리 찾는 방법을 쓴다. 이게 근사 최근접 이웃 탐색(ANN, Approximate Nearest Neighbor)이다. 정확도를 조금 내주고 속도를 얻는다.

벡터 DB는 벡터를 저장하고, ANN 인덱스를 만들어 두고, 가까운 것을 찾아 주는 저장소다. 메타데이터(날짜, 작성자 등)로 거르는 기능도 보통 붙어 있다. 제품 이름은 많은데 이 글에서는 특정 제품을 비교해 보지 않았다.

ANN 알고리즘 중 자주 이름이 나오는 게 HNSW다. 2016년 논문(Malkov & Yashunin) 초록에 따르면 층층이 쌓은 근접 그래프로 구성하고, 위쪽 층에서 크게 훑다가 아래 층에서 좁혀 가는 구조다. 탐색 복잡도가 로그 규모로 늘어난다고 주장한다. 건너뛰기 목록(skip list)과 구조가 비슷하다는 설명도 있다.

비유하자면 전 세계 지도에서 도로를 찾을 때, 먼저 고속도로 지도로 대략 가고 거기서 동네 지도로 바꾸는 식이다. 이 비유는 내가 이해하려고 붙인 거라 논문 표현은 아니다.

<details>
<summary>자세한 풀이: 정확도를 내주는 대가</summary>

ANN은 가장 가까운 것을 놓칠 수 있다. 그래서 재현율(recall)이라는 값으로 "진짜 가까운 상위 k개 중 몇 개를 찾았나"를 잰다. HNSW 초록은 이웃 선택 휴리스틱이 높은 재현율 구간에서 성능을 크게 올려 준다고 말한다. 인덱스 파라미터를 키우면 재현율은 오르고 속도와 메모리는 나빠지는 식의 트레이드오프가 있다.

</details>

## 흔한 오해

- 임베딩이 곧 의미를 이해한 것이다: 학습 데이터에서 비슷한 맥락에 놓이던 글이 가깝게 배치된다는 뜻에 가깝다. "가깝다"의 기준은 모델이 배운 것에 달려 있다.
- 유사도 1에 가까우면 같은 말이다: 반대 의미의 문장도 같은 주제면 가깝게 나올 수 있다고 한다. 직접 실험은 못 했다.
- 벡터 검색이 키워드 검색을 대체한다: 정확한 코드나 이름 검색은 키워드가 낫다. 그래서 섞어 쓴다.
- 차원이 크면 무조건 좋다: OpenAI 문서는 `dimensions`로 차원을 줄여 저장 공간에 맞출 수 있다고 한다. 크면 정보가 많지만 저장 비용도 커진다. 품질 차이가 얼마인지는 문서 말고 내가 잰 게 없다.
- 모델을 바꿔도 기존 벡터를 그대로 쓴다: 모델마다 좌표계가 다르므로 섞어 비교하면 안 된다고 이해했다. 이건 원리상의 추론이고 문서에서 직접 확인하진 못했다.
