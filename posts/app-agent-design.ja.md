エージェント設計の出発点は「エージェントを作ろうか」ではなく、「LLM 呼び出し一回で済むのか、そうでない場合はどこまで定義し、残りはモデルに任せるか」である。

## ワークフローとエージェント

Anthropic の "Building effective agents" では、この二つを以下のように区別している。

- ワークフロー：LLM とツールが事前に定められたコード経路で編まれたもの。次に何をすべきかはコードが決める。
- エージェント：LLM が自らプロセスとツールの使用を決定し、仕事をどのように完了させるかを統制するもの。

この二つを束ねて「エージェントティックシステム」と呼ぶ。単にエージェント一つですべて解決するのではなく、このスペクトルのどこに位置づけるかを選ぶ問題に近い。エージェントループ自体は [詳細 → エージェントとエージェントループ](#/post/ai-agent-loop) に別途記述している。

記事で最初に言及されているのはシンプルさである。最も単純な解決策を探し、結果が確実に良くなる場合のみ複雑度を増やすよう促している。理由はコストである。エージェントティックシステムは遅延とコストを支払って性能を購入する取引であり、その取引に価値がある必要がある。多くの場合、検索や例示を付加した LLM 呼び出し一回で十分であると記されている。

## 基盤となる部品：拡張された LLM

パターン共通の部品は、検索、ツール、メモリが付いた LLM である。モデルが自ら検索クエリを作成し、使用するツールを選び、何を記憶すべきか決める。ツールの接続方式としては MCP が例として挙げられる。ツールを呼び出す側については [詳細 → ツール呼び出し](#/post/ai-tool-use) で扱った。

## ワークフローパターンの 5 つ

一度に眺めると以下のようになる。

| パターン | 一行説明 | 向いている場合 | 代償 |
|---|---|---|---|
| プロンプトチェーニング | ステップを分け、前の出力を次の入力にする | 固定されたサブタスクにきれいに分割できる時 | 遅延が増加する |
| ルーティング | 入力を分類し、専門的なカテゴリへ送る | 入力の種類が明確に分かれ、分類が正確な時 | 分類が間違えば全体が間違ってしまう |
| 並列化 | 同時に複数の呼び出しを行い、コードで統合する | 速度が必要か、複数の視点が求められる時 | 呼び出し数分だけコストがかかる |
| オーケストレーター - ワーカー | 中央 LLM がタスクを分割してワーカーに任せて統合する | サブタスクが事前にわからない時 | コスト・複雑さ |
| 評価 - 改善 | 生成 LLM と評価 LLM が反復する | 評価基準が明確で、修正するほど良くなる時 | 反復回数分だけコストがかかる |

### チェーニング

タスクを順序立てて分割する。概要を書き、基準に合っているか確認し、本文を書く。途中でコードによるゲート（検問所）を設ければ、概要段階で誤った箇所をそこでキャッチできる。文書の例は、マーケティングコピーを作成して翻訳することや、概要を検査した後に本文を書くことである。一度にすべて指示するよりも各呼び出しが容易になるため精度は向上し、代わりに速度が遅くなる。

### ルーティング

入力をまず分類し、カテゴリ別のプロンプトやモデルへ送る。顧客問い合わせを一般・返金・技術サポートに分けるのが文書の例である。簡単な質問は小さなモデル、難しい質問は大きなモデルへ送る用途もある。原価削減の観点から使いやすいため [詳細 → AI サービスのコスト構造](#/post/app-cost) と併せて読む価値がある。

### 並列化

二つのバリエーションがある。セクションニング（区画分割）は互いに独立したサブタスクを同時に実行する。例えば、一つのモデルが回答している間に別のモデルが入力を検閲する。投票（voting）は同じタスクを複数回実行して多数決で決定する。コードの脆弱性を複数のプロンプトで検証し、一度でも検知すれば表示するようなものである。一つの呼び出しに複数の考慮事項を詰め込むよりも、考慮事項ごとに呼び出しを別々に行う方が通常良いとされる。

### オーケストレーター - ワーカー

並列化とは外見は似ているが、サブタスクが入力に応じてその都度決定される点が異なる。複数のファイルを修正するコーディングが代表的な例である。どのファイルに触れるかはリクエストを読むまでわからない。中央モデルが分割し、ワーカーモデルが実行して結果を統合する。複数のモデルが役割分担を行う側については [詳細 → サブエージェントとマルチエージェント](#/post/ai-subagent) で続いている。

### 評価 - 改善

一つのモデルが作成し、別のモデルが評価してフィードバックを与え、通過するまで繰り返す。文学翻訳において評価モデルが見落としたニュアンスを指摘するのが文書の例である。二つの条件が付く。評価基準が明確でなければならず、フィードバックを受けると実際に結果が良くならなければならない。そのどちらかが満たされなければただループし続けるだけで改善しない。評価をどのように設計するかについては [詳細 → LLM アプリの評価](#/post/app-eval) で続いている。

## エージェントはいつ

エージェントはステップ数を予測できないため、経路を事前に固定できない開放的な問題に使用する。人間の指示や対話から始まり計画を立て、各ステップでツール結果やコード実行などの現実の事実（ground truth）を受け取りながら進んでいく。詰まった場合やチェックポイントでは人間に確認する。終了条件とは別に、最大反復回数などの上限を設けることが統制に必要であるという。

実装は意外に単純だ。環境からのフィードバックを受けながらループでツールを使う LLM が全てであり、そのためツールの設計が重要になる。文書ではエージェントに向いている例として 2 つ挙げている。カスタマーサポート（会話と行動が混在し、解決の有無で成功を測れる）、コーディング（テストで結果を検証できる）。共通点は明確な成功基準とフィードバックのループがあることだ。逆にコストが高く、エラーが蓄積する可能性があるため、サンドボックスで十分に試し、ガードレールを設置するよう促している。ガードレールについては [詳細 → ガードレールと安全装置](#/post/app-guardrails) で別途扱っている。

## ツールの設計はプロンプトと同じくらい重要だ

文書の付録部分は意外に長く書かれている。人間向けインターフェース (HCI) に注ぐ努力の量を、エージェント - コンピュータ インターフェース (ACI) にも使うべきだという話だ。

- ツールの説明は、新卒エンジニアへの docstring のように書く。使用例、境界ケース、類似ツールとの違いを入れる。
- モデルが作りにくい形式を避ける。diff は行数を事前に数えねばならず、JSON 内のコードはエスケープの負担がある。
- 実際の入力を多く回して誤りを発見し直す。
- 間違いにくくするために引数を工夫する (poka-yoke)。SWE-bench エージェントはディレクトリを移動した後、相対パスでエラーが多かったが、絶対パスを要求すると消えたという。プロンプトよりもツールの整えることに時間を割いたという箇所もある。

## フレームワークについて

Claude Agent SDK などのフレームワークは呼び出し、ツール定義、チェーンを容易にする。しかし抽象化層がプロンプトとレスポンスを隠してデバッグが難しくなり、不要な複雑さを引き起こしやすい。文書の助言は最初は API を直接使い、フレームワークを使う場合は中身をどうしているか理解するということだ。同じ趣旨で、フレームワーク外のモデル周りのコードを指す言葉は [詳細 → ハネスとハネスエンジニアリング](#/post/ai-harness) である。

## 実際に動かした最小限のコード

5 つの構造がコードではどれだけ小さいかを確認するために、偽の LLM 関数 (`llm`) で骨組みだけ作った。実際のモデル呼び出しはなく、フローを確認するためのものだ。

```python
from concurrent.futures import ThreadPoolExecutor

def llm(prompt: str) -> str:
    """가짜 LLM. 실제로는 API 호출 한 번이 들어갈 자리."""
    if prompt.startswith("분류:"):
        return "환불" if "환불" in prompt else "일반"
    if prompt.startswith("평가:"):
        return "OK" if "근거" in prompt else "근거를 추가해라"
    if prompt.startswith("개선:"):
        return prompt[3:] + " (근거 추가)"
    return f"[{prompt[:20]}...에 대한 답]"

# 1) 체이닝: 앞 출력이 뒤 입력
def chain(topic):
    outline = llm(f"개요: {topic}")
    if len(outline) < 5:            # 게이트
        raise ValueError("개요가 너무 짧다")
    return llm(f"본문: {outline}")

# 2) 라우팅: 분류 후 갈래 선택
HANDLERS = {"환불": lambda q: llm(f"환불 절차 안내: {q}"),
            "일반": lambda q: llm(f"일반 답변: {q}")}
def route(q):
    label = llm(f"분류: {q}")
    return label, HANDLERS[label](q)

# 3) 병렬화(투표): 같은 일을 여러 번
def vote(q, n=3):
    with ThreadPoolExecutor(n) as ex:
        answers = list(ex.map(lambda _: llm(f"검토: {q}"), range(n)))
    return max(set(answers), key=answers.count)

# 4) 평가-개선: 기준 통과까지 반복, 횟수 상한
def refine(draft, max_iter=3):
    for i in range(max_iter):
        verdict = llm(f"평가: {draft}")
        if verdict == "OK":
            return draft, i
        draft = llm(f"개선: {draft}")
    return draft, max_iter

# 5) 에이전트: 다음 행동을 고르는 루프 (여기선 decide 함수로 흉내)
def agent(goal, tools, decide, max_steps=5):
    history = [goal]
    for _ in range(max_steps):
        action, arg = decide(history)
        if action == "finish":
            return arg
        history.append(tools[action](arg))
    return "상한 도달"
```

実際に動かしてみると、ルーティングは「返金してください」を `返金` カテゴリ、「営業時間が…」を `一般` カテゴリに送った。評価 - 改善は案の一つを一度修正して通過させ (`('主張だけの案 (根拠追加)', 1)`)、エージェントは検索ツールを一度使った後に終了した。目についたのは、前述の 4 つはフローがコードで握られている点に対し、エージェントだけが `decide` でフローを握っている点だ。そして `max_iter`, `max_steps` のような上限値は両方に含まれている。

<details>
<summary>詳細な解説：マルチエージェントの価値はいくらか</summary>

Anthropic のマルチエージェント研究システムの論文にはコストの数字が出てくる。エージェントはチャットの約 4 倍のトークンを消費し、マルチエージェントは約 15 倍を消費する。そのため価値の高い作業にのみ経済性があるという。構造はオーケストレーター - ワーカーだ。リードエージェントが質問を分析して計画を立て、サブエージェントたちが並列で検索して結果を返す。内部構成は Claude Opus 4 がリード、Claude Sonnet 4 がサブだったという。

性能は単一エージェントの Claude Opus 4 より 90.2% 高いとされているが、これは Anthropic 内部の研究評価から出た数値だ。BrowseComp では性能差の 95% が 3 つの要因で説明され、そのうちトークン使用量だけで 80% を占めた。並列化により複雑なクエリの調査時間が最大 90% 短縮されたという話もある。

合わない場合も書かれている。すべてのエージェントが同じコンテキストを共有する必要がある場合や、互いに依存関係が多い場合、ほとんどのコーディング作業（並列に分割できる部分は研究よりも少ない）、リアルタイムで調整が必要な場合などだ。当初は単純なクエリでもサブエージェントを 50 つ起動するという過ちがあり、そのためクエリの難易度ごとにエージェント数とツール呼び出し数をプロンプトに記述したという。サブエージェントに作業を任せる際は、目標、出力形式、ツール案内、境界を具体的に与えることで重複作業が減った。

</details>

<details>
<summary>詳細な解説：どのパターンを選ぶか（判断順序）</summary>

文書の内容を順序立てるとこうなる。

1. LLM 呼び出し一回で検索と例示を付加して成立するか。成立すればそこで終了。
2. 成立しない場合、サブタスクが固定されるか。固定されればチェーン、入力種別ごとに分岐すればルーティング。
3. 独立した断片があるか、多数決が必要か。あれば並列化。
4. サブタスクは入力を確認しないとわからないか。そうならオーケストレーター - ワーカー。
5. 評価基準が明確で修正すると良くなる場合、評価 - 改善を追加する。
6. ステップ数を本当に知らず、環境フィードバックで継続的に判断する場合、エージェント。この際上限、人間確認ポイント、サンドボックスを同時に設計する。

パターンは互いに組み合わせられることも文書が述べている。目標はパターンを多用することではなく、測定して改善が見える場合に追加することだ。

</details>

## よくある誤解

- エージェントがワークフローより優れている：文書の基準は「高度か」ではなく「決まった経路が可能か」である。可能であれば、ワークフローの方が予測可能で安価である。
- フレームワークを使えばエージェントになる：フレームワークは単なる利便ツールに過ぎず、誰が流れを決定するかが分かれ目である。
- マルチエージェントならより賢い：研究論文の基準ではトークン消費量が約 15 倍増える。コンテキスト共有が多いタスクはむしろ合わない。
- 評価・改善は回数を重ねるほど良い：基準が曖昧だとただ回るだけになる。回数上限が必要である。
