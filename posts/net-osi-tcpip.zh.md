层次模型将通信分层，每一层只负责自己的头部，对其他层保持透明。发送时，从上层到下层逐层添加头部；接收时，从下层到上层逐层剥离头部。

[概述](#/post/cs-network)中通过表格浏览的内容，这里将进一步深入探讨：每一层具体做什么、头部如何添加、以及为何两种模型都保留至今。

## 为什么要分层

网络通信同时涉及将信号加载到线路上、将数据发送到相邻设备、跨越多个网络寻找路径、将数据传递到进程、以及应用程序之间进行协商等工作。如果将这些功能作为一个整体处理，那么当 Wi-Fi 改为有线连接时，甚至需要修改整个 Web 浏览器。如果采用分层结构，即使完全替换某一层，上下层仍可保持不变。

每一层仅使用下层提供的服务，并与对等层的对方按照约定的规则（协议）进行通信。实际数据虽然从下层传回上层，但在逻辑上等同于同层之间直接对话。

## OSI 7 层模型

OSI 是由 ISO 制定的参考模型，据说于 1984 年以 ISO 7498 标准发布。该模型共有七层。

| 层 | 名称 | 数据单元 (PDU) | 功能 |
|---|---|---|---|
| 7 | 应用层 | 数据 | 与用户交互的协议（如 HTTP） |
| 6 | 表示层 | 数据 | 格式转换、加密、压缩 |
| 5 | 会话层 | 数据 | 对话的建立、管理与终止 |
| 4 | 传输层 | 段 (Segment) | 端到端的数据传递、分段、确认应答、多路复用 |
| 3 | 网络层 | 包 (Packet) | 寻址、跨多个网络的路径选择 |
| 2 | 数据链路层 | 帧 (Frame) | 相邻两个节点之间的传递、错误检测 |
| 1 | 物理层 | 比特 (Bit) | 以电信号、电磁波或光信号传输比特 |

数据单元名称在不同层级有所不同，这常是考试中的考点。但从概念上看，它仅仅是“该层所处理的数据块的名称”。传输层的数据块称为段（TCP）或数据报（UDP），网络层的数据块称为包。

[详细 → TCP 与 UDP](#/post/net-tcp-udp)将单独探讨第 4 层如何具体实现可靠性。

## TCP/IP 4 层模型

实际互联网使用的是 TCP/IP。RFC 1122 的 1.1.3 节将协议栈从上至下分为应用层、传输层、互联网层和链路层四个层次。互联网层包含 IP、ICMP、IGMP；传输层包含 TCP、UDP；链路层负责与直接连接的网络接口交互。

大致对应关系如下：TCP/IP 的应用层覆盖 OSI 的 5~7 层，传输层对应 OSI 的第 4 层，互联网层对应 OSI 的第 3 层，链路层对应 OSI 的第 1~2 层。由于并非完全一一对应，因此只能说是“大致”。

| OSI | TCP/IP | 代表协议 |
|---|---|---|
| 5·6·7 | 应用层 | HTTP, DNS, SMTP |
| 4 | 传输层 | TCP, UDP |
| 3 | 互联网层 | IP, ICMP |
| 1·2 | 链路层 | 以太网，Wi-Fi |

OSI 方面从一开始就试图严格定义各层的作用，属于参考模型；而 TCP/IP 则是在类似时期由美国国防部支持开发的更为宽松的结构。结果导致 OSI 协议未能广泛使用，互联网最终建立在 TCP/IP 之上。因此，7 层模型成为用于解释名称和概念的通用术语，而 4 层模型则作为实际实现的形态被保留下来。

RFC 1122 的 1.3.1 节指出，严格的分层结构对于协议族而言是“不完整的模型”，同时也适用于推荐实现方式。文中还提到，实际实现中经常跨越层边界并共享数据结构。因此，不必将其视为必须遵守的法则来死记硬背。

## 封装：逐层添加头部

发送时，每一层将接收到的数据块在其前面添加自己的头部，然后传递给下一层。这就是封装。接收方则相反，从最外层的头部开始读取并剥离，逐层向上传递。

```
응용 데이터
[UDP 헤더 | 응용 데이터]                       전송 계층
[IP 헤더 | UDP 헤더 | 응용 데이터]              인터넷 계층
[이더넷 헤더 | IP 헤더 | UDP 헤더 | 데이터]      링크 계층
```

仅凭文字描述难以理解，因此我亲自编写了代码来生成头部。使用 `struct` 填充了 14 字节的以太网头、20 字节的 IPv4 头和 8 字节的 UDP 头，并计算了校验和，然后像接收方一样逐层剥离。地址和端口号均为示例中随意设定的数值。

```python
import struct, socket

def checksum(b):
    if len(b) % 2: b += b'\x00'
    s = sum(struct.unpack('!%dH' % (len(b)//2), b))
    while s >> 16: s = (s & 0xffff) + (s >> 16)
    return ~s & 0xffff

payload = b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'   # 응용 데이터

# 전송 계층: UDP 헤더 8바이트 (포트, 길이, 체크섬)
src_ip, dst_ip = socket.inet_aton('192.168.0.10'), socket.inet_aton('93.184.216.34')
udp_len = 8 + len(payload)
pseudo = src_ip + dst_ip + struct.pack('!BBH', 0, 17, udp_len)
hdr0 = struct.pack('!HHHH', 50000, 53, udp_len, 0)
udp = struct.pack('!HHHH', 50000, 53, udp_len, checksum(pseudo + hdr0 + payload)) + payload

# 인터넷 계층: IPv4 헤더 20바이트
ip0 = struct.pack('!BBHHHBBH4s4s', 0x45, 0, 20 + len(udp), 1, 0, 64, 17, 0, src_ip, dst_ip)
ip = ip0[:10] + struct.pack('!H', checksum(ip0)) + ip0[12:] + udp

# 링크 계층: 이더넷 헤더 14바이트
frame = bytes.fromhex('aabbccddeeff') + bytes.fromhex('112233445566') + struct.pack('!H', 0x0800) + ip
print('앱 데이터', len(payload), '| UDP', len(udp), '| IP', len(ip), '| 프레임', len(frame))

# 받는 쪽: 한 겹씩 벗긴다
dst, src, et = struct.unpack('!6s6sH', frame[:14]); body = frame[14:]
print('이더넷 type=0x%04x' % et)
vihl, _, tot, _, _, ttl, proto, ck, s, d = struct.unpack('!BBHHHBBH4s4s', body[:20])
print('IP ihl=%d ttl=%d proto=%d %s -> %s' % (vihl & 15, ttl, proto, socket.inet_ntoa(s), socket.inet_ntoa(d)))
print('IP 헤더 체크섬 검증(0이면 정상):', checksum(body[:20]))
sp, dp, ln, _ = struct.unpack('!HHHH', body[20:28])
print('UDP %d -> %d len=%d' % (sp, dp, ln))
print(body[28:])
```

运行后输出如下：

```
앱 데이터 37 | UDP 45 | IP 65 | 프레임 79
이더넷 type=0x0800
IP ihl=5 ttl=64 proto=17 192.168.0.10 -> 93.184.216.34
IP 헤더 체크섬 검증(0이면 정상): 0
UDP 50000 -> 53 len=45
b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'
```

原本 37 字节的数据，经过 UDP 封装后变为 45 字节，经过 IP 封装后变为 65 字节，再经过以太网封装后变为 79 字节。每向下一层，数据大小就增加相应层级的头部大小。

数字也体现了层间连接的机制。例如，以太网头部的 `type` 字段值为 `0x0800`，表示“内部封装的是 IPv4"；IP 头部的 `proto` 字段值为 `17`，表示“内部封装的是 UDP"。接收方根据这些值决定将数据传递给哪个解析器。而在向上封装发送时，每一层头部都会自行记录应传递给哪一层，形成一种自描述的结构。

<details>
<summary>进一步展开头部字段</summary>

- 以太网：目的 MAC 地址 6 字节，源 MAC 地址 6 字节，类型 2 字节。MAC 地址仅在同一个链路范围内有意义。每经过一个路由器，该头部就会被重新生成，而 IP 头部则保持不变。
- IPv4：第一个字节 `0x45` 表示版本为 4，头部长度为 5（×4 字节 = 20 字节）。TTL 值每经过一个路由器就会减 1，以防止数据包在路径中无限循环。头部校验和仅验证头部部分。上述代码中验证结果为 0，是因为当对整个头部重新计算时，正确的校验和即为 0。
- UDP：源端口、目的端口、长度、校验和。校验和在计算时包含了包含 IP 地址等的伪头部，从而能够检测出因地址错误而发往错误目的地的情形。

</details>

## 各层地址各不相同

最初最令我困惑的是，每一层指代“发送给谁”的方式都不同。

| 层级 | 地址类型 | 指代对象 | 范围 |
|---|---|---|---|
| 链路层 | MAC | 网络接口卡 | 同一链路内 |
| 互联网层 | IP | 主机（的接口） | 网络之间 |
| 传输层 | 端口 | 进程 | 单个主机内 |

数据包在穿越路由器时，IP 地址保持不变，而 MAC 地址会在每一跳中更新。关于如何选择路径的内容将在 [详见 → DNS 与 IP 路由](#/post/net-dns-routing) 中继续展开。

## 层级与代码的距离

在我编写的应用程序中，这些层级几乎不可见。一旦打开套接字，传输层及以下的工作便由操作系统接管。[详见 → 套接字与服务器编程](#/post/net-socket) 将通过代码展示这一边界。可以将套接字 API 视为应用层与传输层之间的接口。位于应用层之上的请求/响应规则将在 [详见 → HTTP 与 HTTPS](#/post/net-http) 中讨论。关于网络栈在操作系统内核中的位置，可参考 [概览](#/post/cs-os) 部分的内核相关内容。

## 常见误解

- “背诵七层模型就懂网络”：七层模型更接近于描述性术语。实际上，许多协议并不完全归属于某一层。例如，TLS 属于第五层还是第六层，以及它是否位于传输层与应用层之间，在不同图示中表现各异。
- “互联网按照 OSI 模型运行”：互联网实际使用的是 TCP/IP 协议族。OSI 协议套件并未被广泛采用。
- “层级之间严格隔离”：RFC 1122 也指出严格的分层是一个不完善的模型。出于性能考虑，实现往往会跨越层级边界。
- "MAC 地址是目的主机的地址”：MAC 地址是下一跳的地址。最终目的地由 IP 头部携带。
