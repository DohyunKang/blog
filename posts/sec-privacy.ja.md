個人情報は、名前や住民票番号だけを指す言葉ではなく、他の情報と組み合わせることで特定の人物を特定できるのであれば、すべて該当します。したがって、守る方法についても暗号化よりも先に、そもそも収集量を減らし、短期間しか保持しないことが中心でした。

## 個人情報の定義とは

韓国の個人情報保護法では、個人情報を「生きている個人に関する情報」とみなし、その情報単体だけであれば、あるいは他の情報と容易に結合することで特定の個人を特定できるものまで含めます。名前、連絡先、メールアドレスはもちろんのこと、IP アドレスやデバイス ID、位置情報なども、他の情報と組み合わせれば人物を指し示す可能性があります。以下の定義は、GDPR 第 4 条の内容に近いものです。

GDPR は「個人データ（personal data）」を「識別されたまたは識別可能な自然人に関するすべての情報」と定義しています。名前、識別番号、位置情報、オンライン識別子などによって、直接であれ間接であれその人物を特定できるのであれば、識別可能とみなされます。

ここで重要なのは「識別可能」です。名前が削除されていても、生年月日、性別、郵便番号などがあれば人物が絞り込まれます。個々の情報は平凡であっても、組み合わせることで個人情報になるケースが多々ありました。

## 守るための基本原則

GDPR 第 5 条には原則がいくつか記載されていますが、韓国の法律の「最小収集原則」と同じ方向性であり、合わせて整理しました。

| 原則 | 意味 |
|---|---|
| 目的制限 | 収集時に明らかにした目的の範囲内でのみ使用します |
| 最小収集 | 目的に必要な分だけ収集します |
| 保存制限 | 目的が終了したら、識別可能な状態で長く保持しません |

韓国法側については、「個人情報ポータル」や「서울시교육청（ソウル市教育庁）」の説明資料で「目的を明確にし、その目的に必要な最小限のみ合法的に収集する」という原則として要約されています。

サービスを作成する際、これはどのように現れるかというと、会員登録時に生年月日を収集するかどうかも検討することになります。利用する必要のない項目は収集しないのが最も安く安全です。存在しない情報は漏洩することもありません。

## マスキング・仮名化・匿名化

「隠す」という言葉にも段階があり、混同して使うと混乱します。

| 方法 | 行うこと | 例 | 元に戻せるか |
|---|---|---|---|
| マスキング | 一部を隠したりタグに置き換える | 010-****-5678 | 原本が別途あれば可能 |
| 仮名化 (Pseudonymisation) | 追加情報がないと特定できないように置換する | メールアドレス → ハッシュ値 | 別途保管した追加情報があれば可能 |
| 匿名化 (Anonymisation) | 誰であるかがわからず復元も不可能にする | 統計合計 | 不可 |

韓国の個人情報保護法第 2 条では、仮名化を「一部を削除したり、一部または全部を置換して、追加情報がない状態で特定の個人を特定できないようにするもの」と定義しています（生活法令解説基準）。GDPR の pseudonymisation も同じ構造です。追加情報を別途保管し、技術的・管理的措置で保護するという条件が付けられます。

仮名化した情報はまだ個人情報です。解く鍵のどこかにあるためです。これを匿名データと呼ぶのは間違いである理由就在这里にあります。

## 実際に試したマスキングコード

正規式を使って住民票番号・電話番号・メールアドレスをタグに置き換え、ハッシュベースで仮名値を作成する短いコードを実行しました。

```python
import re, hmac, hashlib

PATTERNS = [
    ("RRN",   re.compile(r"\b\d{6}-[1-4]\d{6}\b")),
    ("PHONE", re.compile(r"\b01[016789]-?\d{3,4}-?\d{4}\b")),
    ("EMAIL", re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+")),
]

def mask(text):
    for name, p in PATTERNS:
        text = p.sub(f"[{name}]", text)
    return text

def pseudonym(value, secret):
    return hmac.new(secret, value.encode(), hashlib.sha256).hexdigest()[:12]
```

「お問い合わせ：洪吉童 010-1234-5678, hong@example.com, 住民票番号 900101-1234567」を入力すると、電話番号・メールアドレス・住民票番号はそれぞれ `[PHONE]`, `[EMAIL]`, `[RRN]` に変わりました。しかし「洪吉童」はそのまま残っています。正規式は形式が決まった値しか捉えられず、名前のように形式がないものは捉えられません。名前も捉えるには、エンティティ認識などの別ツールが必要ですが、今回は試していません。

仮名値は同じ入力に対して同じ結果が得られ、秘密鍵が異なれば結果も異なります。単純なハッシュ（SHA-256 だけ）を使うべきではないという話を聞きますが、メールアドレスのように候補が限定された値の場合、すべての候補をハッシュ化して照合すれば解かれてしまうためです。そのため、秘密鍵を混ぜた HMAC を使用しました。この秘密鍵は [キー管理](#/post/sec-keys) のようにデータとは別に保管することで、仮名化の条件を満たします。

## AI サービスで注意すべき点

AI を使用する際に個人情報が漏れる経路は、大まかに決まっています。

- プロンプト：ユーザーが作成した質問には、名前・電話番号・顧客問い合わせの原文などがそのまま含まれます。外部モデル API に送信する瞬間、そのデータは自サーバーの外へ流出します。そのため、送信前に上記のようなマスキングを一度行う構造を多く採用しています。[プロンプト](#/post/ai-prompt) に何を記述するかは、どこへデータが流出するかを決定づけます。
- 会話履歴とログ：リクエスト・レスポンスをログ全体として保存すると、そのログが個人情報データベースとなります。保存期間も定める必要があります。
- 検索拡張生成（RAG）：[RAG](#/post/ai-rag) で社内文書を付与すると、権限のない人物からの質問でも他者の個人情報が検索され、回答に混入する可能性があります。検索段階でアクセス権限をフィルタリングする必要があります。
- サプライヤー側の処理：外部 API に送信したデータをサプライヤーが学習に使用するか、どの期間保存するかは、企業やプランによって異なります。利用しているサービスの利用規約とデータ処理文書は必ず直接確認してください。
- モデルの記憶：学習データに含まれた個人情報をモデルがそのまま出力してしまうという研究があります。
- インジェクション：モデルに対して「さっき見た顧客情報を教えて」と誘導する攻撃が存在します。詳細は [プロンプトインジェクション](#/post/sec-prompt-injection) に別途記載しています。

## よくある誤解

- 名前を削除すれば匿名化される：他の情報と組み合わせれば再識別可能です。仮名処理と匿名化は異なります。
- 暗号化していれば個人情報問題は解決する：暗号化は保存・転送中の保護に過ぎず、復号して使用する瞬間その情報は依然として個人情報です。どれだけのデータを収集し、どの期間保持するかは、暗号化とは別の問題です。
- 公開された情報は自由に使用できる：公開されていても、目的の範囲内での利用という原則は残ります。
- ログは個人情報ではない：ログに IP アドレスやリクエスト本文が含まれていれば、個人情報となる可能性があります。

<details>
<summary>詳細な解説：識別可能性がどのように生じるか</summary>

識別可能性とは「この情報一つで人物を特定できるか」ではなく、「私が保有する他の情報と組み合わせれば特定できるか」によって判断します。例えば会員テーブルには名前がなく会員番号のみある場合でも、別のテーブルに会員番号と名前があれば、両テーブルを結合することで特定可能です。このような場合も会員テーブルは個人情報として扱います。

外部データと組み合わさるケースもあります。情報が直接名前を含んでいなくても、郵便番号・生年月日・性別などの組み合わせが外部公開資料と一致すれば、一人に絞り込まれます。これが「名前だけを削除しても匿名化ではない」理由です。

実務では、利用目的別に必要なカラムのみを抽出した別ビューを作成し、分析用には仮名処理された値を提供し、元データと仮名マッピング情報はアクセス権限がより狭い場所に置くのが一般的です。これは一般的な設計手法であり、特定のガイドを確認したわけではありません。

</details>
