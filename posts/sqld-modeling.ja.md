SQLD 1 과목의 첫 번째 단원은 데이터 모델링입니다. 현실의 업무를 데이터 구조로 옮기는 과정을 개념, 논리, 물리 세 단계로 나누고, 그 결과를 ERD라는 도표로 표현합니다. 이 글은 시험에서 이 단원이 어떤 식으로 출제되는지 맞춰 정리했습니다. 시험 일정과 응시료는 공식 사이트에서 확인하시면 됩니다.

## 모델링이란 무엇인가

모델링은 현실 세계를 단순하게 축약하여 표현하는 작업입니다. 지도가 실제 땅을 모두 그리지 않고 필요한 부분만 그리는 것과 비슷합니다. 업무에서 필요한 것만 남기고 나머지는 버리는 것이 핵심이므로, 시험에서는 모델링의 특징인 추상화, 단순화, 명확화를 묻습니다.

- **추상화**: 현실에서 공통된 특성만 추출합니다.
- **단순화**: 복잡한 것을 약속된 기호로 간결하게 나타냅니다.
- **명확화**: 누가 봐도 같은 뜻으로 읽히도록 모호함을 제거합니다.

모델링을 바라보는 관점도 세 가지로 나눕니다. 데이터 관점은 업무가 어떤 데이터와 관련되는지, 프로세스 관점은 업무가 실제로 수행하는 일이 무엇인지, 그리고 데이터와 프로세스의 상관관계를 보는 관점은 일이 데이터를 어떻게 변화시키는지 봅니다. SQLD 에서 다루는 내용은 주로 데이터 관점입니다.

## 개념, 논리, 물리

모델링 단계는 추상적인 것에서 구체적인 것으로 내려갑니다.

| 단계 | 하는 일 | 대표 산출물 | 시험 포인트 |
|---|---|---|---|
| 개념적 모델링 | 업무에서 핵심 엔터티를 추출하고 관계를 설정합니다. | 개념 ERD | 추상화 수준이 가장 높으며, 특정 DBMS 와 무관함 |
| 논리적 모델링 | 테이블, 컬럼, 키로 구조를 구체화합니다. | 논리 ERD | 이 단계에서 정규화를 수행하며 재사용성이 높음 |
| 물리적 모델링 | 실제 DBMS 에 맞게 성능과 저장까지 고려합니다. | 물리 ERD, 스키마 | DBMS 종류에 따라 달라지며, 반정규화와 인덱스 설계가 포함됨 |

위키피디아의 데이터 모델 문서도 ANSI 관점에서 비슷하게 구분합니다. 개념 모델은 영역의 의미를 엔터티 분류와 관계로 설명하고, 논리 모델은 특정 기술 (테이블·컬럼 등) 로 표현한 의미를 설명하며, 물리 모델은 데이터가 실제로 저장되는 방식 (파티션, 테이블스페이스 등) 을 다룹니다. 이 세 관점은 서로 비교적 독립적이어서, 저장 기술을 바꿔도 위쪽 모델은 영향을 덜 받습니다.

시험에서 자주 나오는 문제는 단계와 설명을 짝짓는 것입니다. 외우는 요령은 간단합니다. 개념은 "무엇을 관리할지", 논리는 "어떤 테이블 구조로 담을지", 물리는 "DBMS 에서 어떻게 빠르게 처리할지"입니다. 정규화는 논리, 반정규화와 인덱스는 물리 쪽이라고 연결해 두면 문제가 풀립니다. 정규화 자체는 [자세히 → 정규화와 성능 데이터 모델링](#/post/sqld-norm-perf)에서 따로 봅니다.

<details>
<summary>모델링 단계를 헷갈릴 때 쓰는 예시</summary>

도서관을 예로 들면 다음과 같습니다.

- **개념**: "회원이 책을 빌린다"까지만 정합니다. 엔터티는 회원, 책, 대출 정도이고 컬럼은 아직 없습니다.
- **논리**: 회원 (회원번호, 이름), 책 (책번호, 제목), 대출 (회원번호, 책번호, 대출일) 처럼 컬럼과 키를 정합니다. 중복이 없도록 정규화합니다.
- **물리**: 대출 테이블이 커질 것 같아서 대출일을 기준으로 파티션을 나누고, 조회가 많은 컬럼에 인덱스를 적용합니다. 컬럼 타입도 사용하는 DBMS 에 맞춥니다.

## ERD

ERD (Entity Relationship Diagram) 는 엔터티와 엔터티 사이의 관계를 도표로 나타낸 것입니다. 상자가 엔터티이고 선이 관계입니다. 이 모델은 1976 년 Peter Chen 이 ACM 논문에서 제안했으며, 보통 관계형 DB 의 추상 데이터 모델로 사용됩니다. 엔터티는 명사에, 관계는 동사에 가깝다고 보면 이해하기 쉽습니다.

시험에서는 ERD 를 그리는 순서와 구성 요소를 묻습니다. 한국 SQLD 교재에서 사용하는 작성 순서는 다음과 같습니다.

1. 엔터티를 그립니다.
2. 엔터티를 배치합니다.
3. 엔터티 사이에 관계를 설정합니다.
4. 관계명을 서술합니다.
5. 관계의 참여도 (차수) 를 표시합니다.
6. 관계의 필수 여부를 표시합니다.

엔터티를 배치할 때는 중요한 엔터티를 왼쪽 위에 둔다고 외우는 경우가 많습니다. 선 끝에 닭발 (crow's foot) 모양이면 "많다"는 뜻이고, 동그라미는 0, 짧은 선은 1 을 뜻하는 표기법이 가장 흔합니다. 이 표기는 위키피디아 ER 모델 문서에도 나옵니다. 관계의 차수 (1:1, 1:N, M:N) 와 선택성은 [자세히 → 관계와 식별자](#/post/sqld-relation-identifier)에서, 엔터티와 속성의 분류는 [자세히 → 엔터티와 속성](#/post/sqld-entity-attr)에서 다룹니다.

## 좋은 데이터 모델의 조건

"좋은 모델이 갖춰야 할 요소"도 단골로 나오는 문장형 문제입니다.

| 조건 | 意味 |
|---|---|
| 完全性 | 業務に必要なデータをすべて含んでいる |
| 重複排除 | 同じ事実を複数の場所に保存しない |
| 業務規則 | 業務規則をモデルに表現し、全員が共有する |
| データの再利用 | データが特定のプログラムに縛られず、独立して設計される |
| 通信 | モデル記法を理解する人々が同じ意味で解釈できる |
| 整合性 | 同じデータは一度だけ定義し、他から参照する |

「速度」や「保存スペースの節約」といった要素が含まれていれば疑わしい。このリストの中心は、重複なく正確に含み、かつ共有して読み解けるかどうかである。

## 3 つの階層とスキーマ・データ独立性

スキーマとは、データベースの構造と制約を記述したものである。3 つの階層を持つスキーマ（ANSI-SPARC アーキテクチャ）はこれを 3 つの層に分ける。モデルリングの概念・論理・物理という用語は似ているため混同しやすいが、これは段階ではなく、1 つの DB を見るための 3 つの視点である。

| スキーマ | 誰が見るか | 説明 |
|---|---|---|
| 外部スキーマ | ユーザー・アプリケーションプログラム | 各自が必要な部分のみを見るビュー。複数存在しうる |
| 概念スキーマ | 組織全体・DBA | すべてのデータ、関係、制約を統合した構造。DB につき 1 つ |
| 内部スキーマ | システム・ストレージ視点 | 物理的な保存方式、レコード、インデックス。DB につき 1 つ |

ウィキペディアの ANSI-SPARC ドキュメントも同様の内容を述べている。外部はユーザーごとのビューであり複数存在しうるが、概念と内部はそれぞれ 1 つであり、内部はハードウェア上に実際に保存される表現を扱う。

このように階層に分けた理由はデータ独立性にある。ある層を変更しても他の層に影響を与えないようにするためである。

- 論理的独立性：概念スキーマを変更しても外部スキーマ（ユーザービュー、アプリケーションプログラム）は変わらない。
- 物理的独立性：内部スキーマ（保存構造）を変更しても概念スキーマは変わらない。

独立性があれば、ユーザーごとのアクセスを制御しやすく、保存装置を変更してもプログラムを修正する必要がなく、同じデータを複数の方法で表示できる。問題では「どのスキーマを変更してもどの側に影響がないか」を問う場合が多い。論理は外部と概念の間、物理は概念と内部の関係として 2 つの行に整理しておけばよい。

<details>
<summary>モデルリングの 3 段階と 3 つの階層を持つスキーマを区別する方法</summary>

この 2 つの概念はこのように分けておくと混乱しない。

- モデルリングの 3 段階（概念・論理・物理）は設計を行う順序である。時間軸であり、一人が上から下へ進んでいく。
- 3 つの階層を持つスキーマ（外部・概念・内部）は完成した DB をどの層から見るかである。構造軸であり、同時に存在する。

したがって「概念」という単語が 2 か所で出てくるが、同じものではない。問題で「設計順序」や「DBMS 独立性」といった表現が出ればモデルリングの段階、「ユーザービュー」や「保存構造」が出ていれば 3 つの階層を持つスキーマ側である。
</details>

## よく間違える部分

- 概念モデルリングで正規化やインデックスを言及して選ぶ選択肢は誤り。正規化は論理、インデックスは物理側である。
- 外部スキーマが 1 つだけという選択肢も誤り。外部は複数、概念と内部はそれぞれ 1 つである。
- 論理的独立性と物理的独立性を逆に説明した選択肢がよく混ざっている。概念スキーマの変更と外部スキーマ、内部スキーマの変更と概念スキーマでペアにする。
- モデルリングは「現実をそのまま複製」するのではなく必要なものだけを残す作業なので、現実のすべての情報を含めるといった選択肢は誤り。
