CI/CD 는 코드를 통합하고 테스트하며 배포하는 과정을 자동화하는 것이며, 배포 전략은 마지막 "배포" 단계를 안전하게 수행하는 방법입니다.

## 먼저 기본 개념부터

CI 는 Continuous Integration(지속적 통합) 으로, 여러 사람이 작성한 코드를 자주 통합하고, 매번 통합할 때마다 빌드와 테스트를 자동으로 실행하여 오류를 즉시 발견합니다.

CD 는 두 가지 의미로 읽힙니다. Continuous Delivery 는 테스트를 통과한 결과물을 언제든지 배포할 수 있는 상태로 유지하는 것이며, 마지막 배포 버튼은 사람이 누릅니다. Continuous Deployment 는 그 버튼마저 없애서 테스트 통과 후 바로 서비스에 출시합니다. 글마다 CD 가 어느 쪽을 지칭하는지 달라지므로, 읽을 때 어떤 의미인지 확인하는 것이 좋습니다.

자동화가 필요한 이유는 수동으로 수행할 경우 순서를 놓칠 수 있기 때문입니다. "테스트를 돌렸나?", "빌드 환경이 내 PC 와 다른데?"와 같은 문제가 배포 시 발생합니다. 한 번 스크립트로 기록해 두면 누구라도 동일한 순서로 실행됩니다.

## 파이프라인은 이런 모양입니다

파이프라인은 단계가 연이어 이어진 경로이며, 앞 단계가 실패하면 뒤 단계로 진행되지 않습니다.

| 단계 | 수행 내용 | 실패 시 |
|---|---|---|
| 코드 푸시 | 브랜치에 업로드하거나 PR 을 생성합니다. | (시작점) |
| 빌드 | 의존성 설치, 컴파일, 필요 시 [Docker 이미지](#/post/cloud-docker) 생성 | 여기서 중단 |
| 테스트 | 단위/통합 테스트, 린트 ([자세히 → 백엔드 테스트](#/post/be-testing)) | 여기서 중단 |
| 산출물 보관 | 이미지 및 번들에 버전 부여 후 저장 | 여기서 중단 |
| 배포 | 스테이징 → 운영 순으로 출시 | 롤백 |
| 확인 | 헬스체크, 지표 확인 ([자세히 → 모니터링](#/post/cloud-observability)) | 롤백 |

앞쪽 절반(빌드·테스트)을 CI, 뒤쪽 절반(산출물·배포)을 CD 로 보시면 됩니다. 파이프라인이 작동하는 원동력은 [Git](#/post/cs-git) 이벤트입니다. 푸시나 PR 등의 활동이 발생하면 트리거가 되어 자동으로 시작됩니다.

한 가지 주목할 점은 한 번 생성된 산출물을 환경마다 다시 빌드하지 않고 그대로 이동시킨다는 것입니다. 스테이징에서 테스트한 이미지와 운영에 배포하는 이미지가 같아야 "스테이징에서는 정상인데"라는 문제가 줄어듭니다. 환경마다 달라지는 것은 이미지라기보다 설정과 [시크릿](#/post/cloud-secrets)입니다.

## GitHub Actions 는 이렇게 생겼습니다

GitHub Actions 는 GitHub 저장소 내에서 파이프라인을 실행하는 서비스입니다. 공식 문서는 구성 요소를 다음과 같이 구분합니다.

- workflow: 하나 이상의 job 을 실행하는 자동화 단위. 저장소의 `.github/workflows` 폴더에 YAML 파일로 작성합니다.
- event: workflow 를 시작하는 저장소 활동. PR 생성이나 푸시 등.
- job: 같은 runner 에서 함께 실행되는 step 의 묶음.
- step: job 내에서 순차적으로 실행되는 하나의 작업. 쉘 스크립트 또는 action 입니다.
- action: 재사용 가능한 작업으로, 타인이 만든 것을 활용합니다.
- runner: job 을 실제로 실행하는 서버.

대략 다음과 같은 파일이 생성됩니다. 이는 구조를 보여주는 예시이며 실제로 실행해 본 것은 아닙니다.

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:          # PR이 열리거나 갱신되면
  push:
    branches: [main]     # main에 합쳐지면
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4     # 코드 내려받기
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
  deploy:
    needs: test                        # test가 성공해야 시작
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "여기서 배포 명령"
```

`needs: test` 는 파이프라인의 "앞 단계 실패하면 뒤로 진행되지 않음"을 그대로 표현한 것입니다. 배포에 필요한 키는 YAML 에 직접 적지 않고 저장소의 시크릿 설정에서 가져옵니다. 코드에 키를 명시해 두면 바로 유출됩니다.

<details>
<summary>자세히: job 의 병렬 실행 방식과 흔한 문제점</summary>

job 은 기본적으로 서로 독립적이므로 동시에 실행됩니다. 순서를 지정하고 싶을 때만 `needs` 를 사용합니다. 또한 각 job 이 새 runner 에서 시작하므로 앞 job 에서 생성된 파일이 뒤 job 에 자동으로 전달되지 않습니다. 이를 넘기려면 산출물 (artifact) 로 업로드하고 다운로드해야 합니다. 이 부분에서 "빌드했는데 파일이 없다"며 막히는 경우가 많다고 합니다.

의존성 설치가 매번 느리면 캐시를 활용해도 됩니다.
</details>

## 배포 전략 세 가지

테스트를 통과해도 운영 환경에서 문제가 발생할 수 있습니다. 따라서 새 버전을 한 번에 교체하지 않고, 문제가 발생해도 피해를 최소화하고 빠르게 복구할 수 있도록 출시 방법을 별도로 마련합니다.

| 방식 | 핵심 | 장점 | 부담 |
|---|---|---|---|
| 롤링 | 인스턴스를 조금씩 새 버전으로 교체 | 추가 자원이 적음 | 교체 중에는 새/옛 버전이 혼재됨 |
| 블루그린 | 동일한 환경 두 개 준비, 라우터만 전환 | 복구가 빠름 | 환경이 두 개라 자원이 두 배 필요 |
| 카나리 | 소수 사용자에게 먼저 노출 | 피해 범위가 작음 | 트래픽 분산 장치와 지표 모니터링 필요 |

### 롤링

古いインスタンスを一度に停止せず、一つずつ新しいものに入れ替えていく方式です。Kubernetes の Deployment がデフォルトで採用する手法です。ドキュメントの説明では、新しい Pod が起動するのを待ってから古い Pod を停止し、Service はリクエストを受け付けることができる Pod へのトラフィックのみを送信します。そのため、無中断を実現するには複数のレプリカが必要です。

速度と安全性は以下の 2 つのパラメータで調整します。`maxUnavailable` は更新中に同時に停止してもよい Pod の数であり、`maxSurge` は目標数よりも多く起動してもよい Pod の数です。これらは数字またはパーセンテージで指定します。`maxUnavailable: 0` と `maxSurge: 1` に設定すれば、容量が一度も減少しない慎重な方式になります。デフォルト値はチュートリアル本文では 1 と記載されていますが、Deployment API はどちらも 25% なので、使用するバージョンのドキュメントを確認する必要があります。

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # 동시에 최대 1개까지 내려감
      maxSurge: 1         # 최대 1개까지 더 띄움
```

ロールバックも同じツール内で行えます。更新はバージョンごとに記録され、`kubectl rollout undo deployments/<イネーム>` で以前の状態に戻ります。特定のレビジョンへ戻すには `--to-revision=N` を追加します。この YAML とコマンドは上記のドキュメントから転記したもので、実際にクラスターで試していません。

### ブルーグリーン

運用環境を最大限に同じ 2 つ用意します。片方は現在顧客を受け入れている方（ブルー）、もう片方は待機している方（グリーン）です。新しいバージョンは待機のグリーンにデプロイして最終テストを行い、問題なければルーターがすべてのリクエストをグリーンへ送るように変更します。Martin Fowler の記事では、問題が発生した場合はルーターを元に戻して素早くロールバックできると説明されています。切り替え後はブルーが次のリリースの待機環境となり、両者が交互に使用されます。この「ルーターを変更する」部分は [ロードバランサー](#/post/infra-load-balancer) が行う作業です。

難しいのはデータベース（DB）です。2 つの環境が同じ DB を共有すると、スキーマを変更する際に古いアプリと新しいアプリの両方が動作する必要があります。Fowler の記事では、下位互換性のあるスキーマ変更を先にデプロイし、その後新しいアプリをアップロードするよう推奨しています。切り替えの間、蓄積されたトランザクションをどう扱うかも別途決定する必要があります。これは [トランザクション](#/post/db-transaction) とも関連します。

### カナリア

鉱山のカルアリアから名付けられました。新しいバージョンを一部のインフラにデプロイし、最初はユーザーを送りません。その後、少数のユーザーのみを送信します。選択基準はランダム、社内従業員優先、ユーザー属性基準などがあり、規模が大きい場合は地域やブランドで分割することもあります。問題なければ徐々に増やし、最終的にすべて新しいバージョンへ送るようになり、古いインフラを停止します。異常が発生した場合はユーザーを古いバージョンに戻します。

ブルーグリーンが「一度に全切り替え」であるのに対し、カナリアは「少しずつ切り替え」です。中間で 2 つのバージョンが同時に動作するという点の違いがあり、徐々に負荷をかけながら運用上で容量を試すことも可能です。ただし、どれだけの割合を送るか、いつ増やすかを判断するにはエラーレートなどの指標が必要です。指標がないカナリアは単に遅いデプロイに過ぎません。

## ロールバックは計画に含める

3 つの方式ともロールバックの方法が異なるため、デプロイ前に「異常が発生した場合はどうするか」を事前に決めておくことが重要です。

- **ローリング**: 以前のレビジョンへ戻すと再びローリングで置換されます。ロールバックにも時間がかかります。
- **ブルーグリーン**: ルーターだけを元に戻せばよいので最も速いです。
- **カナリア**: 送信していたユーザーを古いバージョンに戻します。被害を受けたユーザーが少数であることが利点です。

ロールバックできない変更が入ると話はすべて難しくなります。DB カラムを削除するマイグレーションが代表的です。コードは古いバージョンに戻ってもデータは戻ってきません。そのため、スキーマの変更は「追加を先に、削除は後」の 2 段階に分けて行うのが望ましいです。ロールバック判断の根拠は結局モニタリング指標です。ロールバックするか否かはエラーレートと応答時間を観測して決めます。

## よくある誤解

- **CI/CD があればデプロイが安全になる**: 自動化は単に同じ手順を繰り返すだけです。テストが不十分であれば、不十分なコードが自動的に本番環境まで進んでしまいます。
- **ブルーグリーンなら DB の心配はない**: 環境が 2 つあっても DB を共有すればスキーマ互換の問題はそのまま残ります。
- **ローリングは無中断が保証される**: レプリカが 1 つしかない場合や `maxUnavailable` の設定で容量を削ると中断する可能性があります。
- **カナリアとブルーグリーンは同じ意味**: 初期に新しいバージョンを別途デプロイするという点は似ていますが、一度に切り替えるか割合を増やすかが異なります。
- **デプロイとリリースは同じ**: コードをサーバーにアップロードすることとユーザーに見えるようにすることは別に行うことができます。本稿ではこの区別に深く触れていません。
