파인튜닝은 사전학습이 끝난 모델을 내 데이터로 한 번 더 학습시키는 일이고, 모델 전체를 고치느냐 일부만 얹느냐에 따라 필요한 GPU가 크게 달라진다.

## 파인튜닝이 뭔지

[LLM](#/post/ai-llm)은 먼저 방대한 텍스트로 사전학습을 한다. 이 단계에서 언어 전반을 익히고, 여기까지는 개인이 하기 어렵다. [사전학습에서 RLHF까지](#/post/ml-pretraining)에서 정리한 부분이다. 파인튜닝은 그 뒤에 얹는 두 번째 학습이다. 이미 말을 할 줄 아는 모델에게 특정 말투, 특정 형식, 특정 분야의 문제 풀이를 추가로 가르친다.

정리하면 이렇다.

| | 사전학습 | 파인튜닝 |
|---|---|---|
| 데이터 | 방대한 일반 텍스트 | 수백~수만 개 정도의 목적 데이터 |
| 목적 | 언어와 지식의 기반 | 특정 행동·형식·말투 |
| 시작점 | 무작위 가중치 | 이미 학습된 가중치 |
| 비용 | 개인이 하기 어려움 | 모델과 방법에 따라 다름 |

데이터는 보통 "입력과 바람직한 출력" 쌍이다. 질문과 정답 답변, 긴 문서와 요약본 같은 것이다. 이 쌍을 모델에 보여 주면서 가중치를 조금씩 고친다. 학습 방식은 사전학습과 같은 [신경망 학습](#/post/ml-neural-net)이고, 달라진 건 데이터와 시작점뿐이다.

## 전체 파인튜닝은 왜 무거운가

전체 파인튜닝(full fine-tuning)은 모델의 모든 가중치를 갱신한다. 문제는 메모리다. 학습하려면 가중치 말고도 기울기와 옵티마이저 상태를 같이 들고 있어야 한다. Adam 계열 옵티마이저는 파라미터마다 값을 두 개씩 더 저장한다. 그래서 학습에 필요한 메모리는 모델 크기보다 몇 배 크다.

숫자를 하나만 잡아 보면, 파라미터 70억 개 모델을 16비트(2바이트)로 불러오기만 해도 가중치가 약 14GB다. 학습 때는 여기에 기울기와 옵티마이저 상태가 더 붙는다. 정확한 배수는 정밀도와 옵티마이저 설정에 따라 다르다.

또 하나는 사본 문제다. 용도마다 파인튜닝하면 용도마다 모델 전체 사본이 생긴다. 7B 모델 사본 하나가 14GB라면, 용도 열 개는 140GB다.

## LoRA의 아이디어

LoRA(Low-Rank Adaptation)는 2021년 Hu 등의 논문에서 나왔다. 사전학습된 가중치는 얼려 두고(freeze), 각 층에 학습 가능한 작은 행렬을 끼워 넣는 방식이다. 논문 초록은 GPT-3 175B 기준으로 학습해야 하는 파라미터가 약 10,000분의 1로 줄고, GPU 메모리 요구량은 약 3분의 1로 줄었다고 쓴다. 성능은 RoBERTa, DeBERTa, GPT-2, GPT-3에서 전체 파인튜닝과 비슷하거나 더 좋았다고 한다. 추론 때 지연이 늘지 않는다는 점도 초록에 나온다.

원리는 이렇다. 가중치 하나(행렬 W, 크기 d×k)를 직접 고치는 대신, 변화량 ΔW를 작은 행렬 두 개의 곱으로 표현한다.

```
W' = W + (alpha / r) * B @ A
     W: d x k (고정)
     B: d x r, A: r x k (이것만 학습, r은 d, k보다 훨씬 작다)
```

r이 랭크다. d=k=4096이고 r=8이면 W는 약 1,678만 개, A와 B를 합치면 약 6만 5천 개다. 이 한 행렬만 보면 256분의 1이다. PEFT 문서는 학습 파라미터 수가 "랭크 r과 원래 행렬의 모양으로 결정된다"고 설명한다. r이 작을수록 행렬이 작아진다.

초기값도 눈여겨볼 만하다. B는 0으로, A는 무작위로 시작한다. 그래서 학습 시작 시점에는 B@A가 0이고 모델은 원래 모델과 똑같이 움직인다. 거기서 조금씩 벗어난다. 아래 numpy로 직접 확인했다.

<details>
<summary>자세한 풀이: LoRA를 numpy로 확인한 코드</summary>

```python
import numpy as np
rng = np.random.default_rng(0)
d, k, r, alpha = 64, 64, 4, 8
W = rng.normal(size=(d, k))
A = rng.normal(size=(r, k)) * 0.01
B = np.zeros((d, r))
x = rng.normal(size=(k,))

# 1) B가 0이면 LoRA를 붙여도 출력이 그대로
print(np.allclose(W @ x, (W + (alpha / r) * B @ A) @ x))   # True

# 2) 학습 후라고 치고 B를 바꾸면, 따로 계산한 것과 합쳐서 계산한 것이 같다
B = rng.normal(size=(d, r)) * 0.1
y_split  = W @ x + (alpha / r) * (B @ (A @ x))
y_merged = (W + (alpha / r) * B @ A) @ x
print(np.allclose(y_split, y_merged))                       # True
print(W.size, A.size + B.size)                              # 4096 512
```

실행 결과는 True, True, 4096 512였다. 두 번째 확인이 "합쳐도 같다"는 부분이다. 아래 병합 얘기가 여기서 나온다.

</details>

## 어디에 붙이고 뭘 고르나

PEFT 문서에 따르면 LoRA는 어떤 가중치 행렬에도 붙일 수 있고, 트랜스포머에서는 보통 어텐션 블록에만 붙인다. [트랜스포머와 어텐션](#/post/ml-transformer)에서 본 쿼리·키·밸류 투영 행렬이 그 대상이다. 어떤 층에 붙일지는 `target_modules`로 고른다.

자주 만지는 값은 셋이다.

| 설정 | 하는 일 |
|---|---|
| `r` | 랭크. 작으면 파라미터가 적고, 커지면 표현력이 늘어난다 |
| `lora_alpha` | 스케일. 기본은 alpha / r 만큼 곱해진다 |
| `target_modules` | LoRA를 붙일 층 |

어떤 값이 좋은지는 모델과 데이터에 따라 달라지고, 문서도 값을 단정하지 않는다.

## 병합과 어댑터

학습이 끝나면 B와 A는 용량이 작은 별도 파일(어댑터)로 저장된다. 쓰는 방법은 두 가지다.

- 어댑터를 기본 모델 위에 얹어서 쓴다. 기본 모델 하나에 어댑터를 바꿔 끼우면 용도마다 사본이 필요 없다.
- `merge_and_unload()`로 W에 합쳐서 일반 모델 하나로 만든다. 위 numpy 두 번째 확인처럼 결과가 같아서, 합친 뒤에는 추가 지연이 없다. PEFT 문서가 "LoRA는 추론 지연을 더하지 않는다"고 쓰는 이유가 이것이다.

사본 문제도 풀린다. 어댑터 파일은 기본 모델에 비해 훨씬 작고, 정확한 크기는 r과 대상 층에 따라 달라진다.

## QLoRA: 기본 모델까지 줄이기

LoRA는 학습할 파라미터를 줄였지만 기본 모델은 여전히 16비트로 메모리에 올려야 한다. QLoRA(Dettmers 등, 2023)는 기본 모델을 4비트로 양자화해서 올려 두고, 그 위에서 LoRA 어댑터만 학습하는 방식이다. 기울기는 얼린 4비트 모델을 통과해서 어댑터까지 흘러간다.

논문 초록이 드는 기법은 세 가지다.

- 4비트 NormalFloat(NF4): 정규분포를 따르는 가중치에 맞춘 4비트 자료형
- 이중 양자화(double quantization): 양자화에 쓰는 상수까지 다시 양자화해 메모리를 더 줄임
- 페이지드 옵티마이저(paged optimizers): 학습 중 메모리가 튀는 구간을 관리

논문은 650억 파라미터 모델을 48GB GPU 한 장에서 파인튜닝할 수 있고, 16비트 파인튜닝 성능을 유지한다고 주장한다. 이 비교는 저자들의 실험 조건에서 나온 결과다. 이 방식으로 만든 Guanaco 모델 계열은 Vicuna 벤치마크에서 당시 공개 모델 중 가장 좋았고, GPU 한 장에서 24시간 학습으로 ChatGPT 수준의 99.3%에 닿았다고 한다. 벤치마크 하나 기준이라 다른 과제에서도 그런지는 별개 문제다. 4비트로 양자화된 모델은 [로컬 모델 돌리기](#/post/ml-local-models)에서 다루는 것과 같은 계열의 아이디어다.

## 언제 파인튜닝이고 언제 RAG인가

둘은 풀려는 문제가 다르다. [RAG](#/post/ai-rag)는 질문마다 관련 문서를 찾아 [프롬프트](#/post/ai-prompt)에 붙여서 모르는 것을 보충한다. 파인튜닝은 모델의 행동 자체를 바꾼다.

| | RAG | 파인튜닝 |
|---|---|---|
| 잘 맞는 일 | 최신·사내 정보, 출처 제시 | 말투, 출력 형식, 특정 작업 방식 |
| 정보가 바뀌면 | 문서만 고치면 됨 | 다시 학습해야 함 |
| 준비물 | 문서와 검색 환경 | 입출력 쌍 데이터와 GPU |
| 추론 때 | 검색 비용과 긴 프롬프트 | 프롬프트가 짧아질 수 있음 |

지식을 모델에 넣는 용도로 파인튜닝을 쓰려는 경우가 많은데, 그 판단은 신중하게 해야 한다. 학습시킨 내용을 모델이 정확히 기억하리라는 보장이 없고, 어느 문서에서 나온 말인지도 알려 주지 않는다. 틀린 말을 자신 있게 하는 [할루시네이션](#/post/ai-hallucination) 문제도 그대로 남는다.

순서로는 프롬프트를 고치는 것부터 시작하고, 정보가 모자라면 RAG, 그래도 형식이나 말투가 안 잡히면 파인튜닝을 검토하는 흐름이 보통이다. 둘을 같이 쓰는 경우도 많다.

## 흔한 오해

- LoRA는 모델을 작게 만드는 기술이다: 기본 모델 크기는 그대로고, 학습하는 부분만 작다. 추론 때는 기본 모델이 필요하다. 모델 크기를 줄이는 쪽은 양자화다.
- QLoRA는 LoRA보다 성능이 낮다: 논문은 16비트 파인튜닝 성능을 유지한다고 주장하지만 조건부 결과다. 늘 같다는 뜻은 아니다.
- 파인튜닝하면 새 지식이 들어간다: 형식·말투를 가르치는 데는 확실히 쓰이지만, 지식 주입은 RAG가 더 안정적인 경우가 많다.
- 데이터가 많을수록 무조건 좋다: 양보다 품질이 더 자주 거론된다.

[추론 최적화](#/post/ml-inference)는 병합하고 난 모델을 어떻게 빠르게 돌리는지를 다룬다.
