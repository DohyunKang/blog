正規化は、重複によって生じる異常現象を防ぐためにテーブルを分割する作業であり、逆に非正規化やパーティショニング、スーパー/サブタイプは、そのように分割したモデルをパフォーマンス向上のために再調整する方法です。SQLD 1 과목では概念問題だけでなく、状況を提示して「どのように変更するか」を問う問題も出題される単元なので、定義だけを暗記するのではなく、いつ使うのかまでまとめて整理しました。

試験日程と受験料は公式サイトで確認してください。この記事では単元の概念と頻出するパターンのみ扱います。

## 正規化が必要な理由

一つのテーブルに部署名を各社員ごとに記載しておくと、部署名が変更された際に社員の数だけ修正する必要があります。一つでも見逃すと、同じ部署が二つの名前を持つことになります。このような問題を異常 (anomaly) 現象と呼び、通常は三つに分けて説明します。

| 異常 | 状況 |
|---|---|
| 挿入異常 | 社員がいない新しい部署を追加する場所がない |
| 更新異常 | 部署名を変更した際、一部の行だけが変更され不整合が生じる |
| 削除異常 | 最後の社員を削除すると部署情報も消えてしまう |

正規化はこれを防ぐために関数依存に従ってテーブルを分割する作業です。関数依存とは「A の値が決まれば B の値も一意に決まる」という関係 (A → B) です。社員の番号が決まれば社員名も一意に決まるため、社員番号 → 社員名となります。

## 第 1〜3 正規形

ウィキペディアの正規化文書の定義を基準にすると、三つの段階は以下のように解釈できます。

| 正規形 | 条件 | 違反時の対応 |
|---|---|---|
| 第 1 正規形 | すべてのセルが一つの値のみを持つ。反復グループや多値はない | 反復する値を別のテーブルに移動させる |
| 第 2 正規形 | 主キーが複合キーの場合、一般属性はキー全体に依存する (部分依存の除去) | 部分依存する属性を別に移動させる |
| 第 3 正規形 | 一般属性が他の一般属性に依存しない (移行依存の除去) | 移行依存する属性を別に移動させる |

暗記する際は、キーワードを一つずつ付け加えると覚えやすくなります。第 1 正規形は原子値、第 2 正規形は部分依存、第 3 正規形は移行依存です。

受講テーブルで考えると以下のようになります。主キーが (学番、科目コード) ですが、科目名が科目コードにのみ依存すれば部分依存となり第 2 正規形の違反となります。学番 → 学科コード → 学科名のように一般属性が他の一般属性を決定すれば移行依存となり第 3 正規形の違反となります。

<details>
<summary>解き順 (問題が出た場合)</summary>

1. まず主キーを確認する。
2. セルに複数の値が入っている場合は第 1 正規形の違反です。
3. 主キーが複合キーの場合、一般属性ごとに「キーの一部だけで決まるか」を検討します。そうであれば第 2 正規形の違反です。
4. 一般属性同士で「A が B を決定する」関係があれば第 3 正規形の違反です。
5. 違反した属性を決定側 (左側の属性) と一緒に新しいテーブルに移動させます。元のテーブルには決定側を外鍵として残します。

主キーが単一属性であれば部分依存は発生しないため、第 2 正規形は自動的に満たされます。この点は選択肢問題でよく利用されます。
</details>

BCNF、第 4 正規形、第 5 正規形もありますが、この単元では第 3 正規形を中心に理解すればよいとされています。出題範囲については公式サイトの科目案内を確認するのが正確です。

## コードで正規化を確認してみる

社員と部署を分離すると、部署名は一つの場所のみになります。SQLite で実際に動かしてみました。

```sql
CREATE TABLE dept(dept_id INT PRIMARY KEY, dept_name TEXT);
CREATE TABLE emp(emp_id INT PRIMARY KEY, emp_name TEXT,
                 dept_id INT REFERENCES dept);
INSERT INTO dept VALUES (10, '영업');
INSERT INTO emp VALUES (1, '가', 10), (2, '나', 10);

UPDATE dept SET dept_name = '영업1' WHERE dept_id = 10;

SELECT e.emp_name, d.dept_name
FROM emp e JOIN dept d USING (dept_id);
```

結果は `('가', '영업1')`, `('나', '영업1')` でした。一行だけ修正しましたが、両方の社員に反映されます。ただし、社員と部署名を同時に表示するには結合 (JOIN) が必要になります。ここから非正規化の話が始まります。

## 非正規化

正規化するとテーブルが増え、照会時に結合が増加します。結合がパフォーマンスのボトルネックになると意図的に重複を許容するのが非正規化です。ウィキペディアの正規化文書には非正規化という項目は別なく、別の文書へのリンクしかありません。一般的には重複を許容して結合を減らす方式で説明されます。

試験では方法を分類して問われます。

| 区分 | 方法 | 例 |
|---|---|---|
| テーブル | テーブルの統合 | 1:1、1:N 関係のテーブルを一つにまとめる |
| テーブル | テーブルの分割 | カラム基準 (垂直分割)、行基準 (水平分割) |
| テーブル | テーブルの追加 | 集計テーブル、履歴テーブル、部分テーブル |
| カラム | 重複カラムの追加 | 結合せずに表示するために名前カラムをコピーする |
| カラム | 派生カラムの追加 | 合計数や件数を事前に計算して保存する |
| 関係 | 重複関係の追加 | 複数段階の結合を減らすために関係を一つ増やす |

非正規化を行う前にまず検討すべきことも併せて知っておくと良いでしょう。インデックスの調整やビューの使用、クエリの修正などが先で、それでもダメな場合に非正規化に踏み切る順序になることが多いです。

非正規化の代償はデータの一貫性です。コピーしたカラムは元が変更された際にも同時に更新する必要があり、それをアプリケーションやトリガーが担当することになります。そのため読み込みが圧倒的に多い照会系業務で主に検討します。

## スーパータイプとサブタイプ

エンティティが共通属性を持ちながら種類ごとに分かれる場合、共通部分はスーパータイプ、種類別部分はサブタイプとなります。例えば、顧客は個人顧客と法人顧客に分類されます。論理モデルではこれをこのように図示し、物理モデルへ移行する際に 3 つの方式のいずれかを選択します。

| 変換方式 | 形状 | 適した場面 |
|---|---|---|
| 1:1 関係 | スーパーとサブをそれぞれテーブルとして置き、1:1 で接続 | サブタイプごとの属性が多く、個別に照会が多い場合 |
| スーパー + サブ統合（単一テーブル） | 一つのテーブルに区別列とすべての属性を含める | サブタイプの区別なく一緒に照会が多く、処理速度が重要である場合 |
| サブタイプ別分離 | サブタイプごとにテーブルを置き、共通属性を重複させる | サブタイプごとにほぼ個別に使用する場合 |

統合方式はジョインが不要で高速ですが、該当しない列は NULL として残り、テーブルが大きくなります。逆に分離すればテーブルは軽量になりますが、全体を結合して見る場合、ジョインや UNION が必要になります。試験では「照会パターンはこのようである、どの変換が適切か」という出題形式が出ます。長所と短所のペアを覚えておけば解けます。

[詳細 → エンティティと属性](#/post/sqld-entity-attr)でエンティティ分類も併せて確認すれば、スーパー/サブの由来が理解しやすくなります。

## パーティショニング

大きなテーブルを小さな断片に分けて管理する方法です。Oracle のドキュメントでは、パーティショニングをテーブルやインデックスを「パーティション」というより小さな断片に分割することとして説明しており、アプリケーション側ではパーティションテーブルが通常のテーブルのように見え、SQL を変更する必要がないとしています。どの行がどのパーティションに含まれるかは、パーティションキーによって決定されます。

| 方式 | 基準 | 例 |
|---|---|---|
| レンジ (Range) | 値の範囲 | 月別の注文データ |
| リスト (List) | 指定された値のリスト | 地域別のデータ |
| ハッシュ (Hash) | ハッシュ値で均等に分散 | 自然な範囲がないデータ |
| コンポジット (Composite) | 上記方式を重ねて使用 | レンジ内でのハッシュ |

効果はドキュメントによると主に 3 つに分類されます。パフォーマンス面では、必要なパーティションのみを読み取る「パーティション・プリューニング（pruning）」が核心です。ドキュメントの例では、週単位で 2 年間分（104 個）を分割した注文テーブルにおいて、一週間分の照会を行うと 104 個のうち 1 つしか読み込まないとしています。管理面ではパーティション単位でのバックアップやロードが可能であり、可用性面では一つのパーティションがロックされても残りは利用可能です。

試験では「照会条件にパーティションキーが含まれることで初めて効果がある」といった文句が正誤選択問題として出題されることがあります。プリューニングはキー条件で動作する構造であるため、これを理解していれば混乱しません。パーティション方式の名前と基準をペアにして暗記しておけばよいです。

<details>
<summary>水平分割とパーティショニングは同じか</summary>

テーブルの水平分割は行を基準にテーブル自体を複数のものに分けるものであり、パーティショニングは論理的には一つのテーブルを置きながら保存を分けます。水平分割ではアプリケーションがどのテーブルを見るべきかを把握する必要がありますが、パーティショニングでは SQL を変更する必要がない点が異なります。試験では両者を区別して問うよりも、効果を問う方が多いです。
</details>

## インデックス視点からのパフォーマンスモデルリング

インデックスを設計する際、モデルリング段階で考えるべき点はいくつか整理できます。

- 照会条件やジョインに頻繁に使用される列にはインデックスを置きます。外部キー列が代表的です。
- 値の種類が非常に少ない列は効果が小さいです。選択度が高い列の方が優れています。
- インデックスは照会を高速化しますが、代わりに INSERT、UPDATE、DELETE の際にも更新されるため書き込みコストがかかります。
- 複合インデックスでは列の順序が重要です。前方の列が条件に使われないと活用が困難です。

上記の従業員例において `emp(dept_id)` にインデックスを作成し、SQLite の実行計画を確認すると、`SEARCH emp USING INDEX ix_emp_dept (dept_id=?)` となりました。外部キー列の照会がインデックスを使用している様子です。

```sql
CREATE INDEX ix_emp_dept ON emp(dept_id);
EXPLAIN QUERY PLAN SELECT * FROM emp WHERE dept_id = 10;
```

インデックス内部構造については [詳細 → インデックス](#/post/db-index) に、正規化をデータベース一般概念として扱った記事は [詳細 → 正規化](#/post/db-normalization) に別途あります。この記事では試験に出る内容のみを扱います。

## よく出るタイプの整理

| 類型 | 解法 |
|---|---|
| 与えられたテーブルが何の正規形か | 基本キーの確認、部分関数従属 → 完全関数従属の順でチェック |
| 正規化結果のテーブル構成 | 決定者と従属性をペアで分離 |
| 非正規化手法の分類 | テーブル、列、関係のうちどこを変更するかで分類 |
| 照会が遅いという状況 | インデックス、ビュー、非正規化の順に検討 |
| スーパー/サブタイプ変換の選択 | 照会パターン（一緒に見るか個別に見るか）を基準に |
| パーティション効果 | パーティションキー条件、プリューニング、管理単位の分割 |

選択肢で誤りを誘う一般的なパターンは、「正規化を多く行うほど常にパフォーマンスが向上する」といった断定です。正規化は一貫性を保つためのものですが、クエリ性能については結合が増えるためむしろ不利になる可能性があるという点だけ覚えておけば、このような選択肢を見抜くことができます。
