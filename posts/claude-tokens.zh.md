Claude 的使用量主要消耗在每次请求时重新发送的对话记录和工具结果上，而非我亲自撰写的文字；节省成本的方法也大多在于保持上下文轻量。

本文整理了 Anthropic 官方文档中的三处内容（Claude Code 成本管理、Claude Code 的提示词缓存、API 的提示词缓存）。文中未记录我的具体使用方式，仅列出了从文档中确认的信息。

## 令牌从哪里流失

Claude Code 文档是这样解释的：模型在请求之间不会记忆任何内容，因此每次发送消息时，都会系统性地重新发送系统提示符、项目上下文（如 CLAUDE.md 等）、迄今为止的所有消息和工具结果，以及新消息。[详情 → 上下文](#/post/ai-context)

这里有两点值得注意：

- 每使用一次工具就会多产生一个请求，且该请求也会包含迄今为止的完整记录。
- 即使在整个会话中只问了一行字，该会话的全部对话也会被计入使用量。虽然得益于缓存单价较低，但并非为零。

因此，令牌成本更接近于“当前上下文有多大 × 发出了多少次请求”，而非“我写了多少字”。这是综合文档内容后的总结。[详情 → 上下文窗口](#/post/ai-context-window)

若将文档中指出的导致长会话使用量增加的原因用表格表示，如下所示：

| 原因 | 文档说明 |
|---|---|
| 长上下文 | 整个对话会在每次请求中重新发送 |
| 缓存未命中 | 若休息超过缓存寿命，第一条消息会重新处理整个上下文 |
| 预约任务·其他会话消息 | 即使会话处于空闲状态，只要产生新轮次，整个上下文都会被重新发送 |
| 子代理 | 各自单独发送请求，因此会叠加在主对话之上 |
| 压缩 | `/compact` 也需要读取待总结的对话，因此大上下文意味着大请求 |

文档中关于成本的讨论更多转向缓存话题。对于可随请求发送的图像和 PDF 数量及大小有限制，若超出限制，Claude Code 会从旧的文件开始逐批移除并重新发送。移除后需从该消息起重新处理，导致该轮次变慢且成本增加。

## 提示词缓存

缓存功能是指：如果请求的前缀（prefix）与之前的请求完全相同，则无需重新计算该部分，而是以较低的单价读取。根据 API 文档，前缀的顺序为 `tools → system → messages`，匹配度必须达到 100%，包括文字和图像。输出结果无论是否使用缓存均保持不变。

各模型的单价不同，但根据文档表格，大致轮廓如下：

| 项目 | 相对于基本输入 |
|---|---|
| 读取缓存 | 基本为 0.1 倍。其中 Opus 5.5·Sonnet 5.5 为 0.05 倍，Fable 5.1·Mythos 5.1 为 0.025 倍，Haiku 5.5 则在模型表中单独标注了固定单价 |
| 写入 5 分钟缓存 | 1.25 倍 |
| 写入 1 小时缓存 | 2 倍 |

文档指出，此倍数会与类似批量折扣等其他折扣叠加适用。5 分钟缓存每次使用时其寿命可免费延长。因此，在持续工作期间读取成本较低；若离开超过 5 分钟，则需重新以较高成本使用。Claude Code 文档称，订阅套餐中包含的使用量默认对主对话应用 1 小时 TTL，而在使用 API 密钥或云提供商时则默认为 5 分钟。

Claude Code 会自动处理此过程，用户只需了解可能导致缓存失效的操作即可。以下是文档中指出的内容：

- 通过 `/model` 切换模型：各模型拥有独立的缓存，因此下一个请求将无缓存地读取全部内容。
- 更改努力程度（effort）：大多数模型均如此。Opus 5.5、Sonnet 5.5、Haiku 5.5、Fable 5.1 在使用 API 密钥或订阅时文档注明会保持缓存（Bedrock 等部分环境除外）。由于模型列表持续变化，建议在使用前重新查阅文档。
- 连接/断开 MCP 服务器、整体拒绝工具：由于工具定义位于系统层，一旦更改会导致缓存失效。不过，对于默认开启工具搜索（tool search）的模型，因工具为延迟加载，故无影响。
- 压缩：会改变对话层。尽管如此，系统提示符和项目上下文仍可能保留在缓存中。

相反，也有保护缓存的操作。文件修改、权限模式切换、技能调用、`/recap`、`/rewind` 等是在对话末尾追加或返回至已缓存的前缀部分，因此能保持缓存。若在会话期间修改 CLAUDE.md，缓存不会失效但内容也不会被反映；需在下一个 `/clear`、`/compact` 或重启时重新读取。

文档中的一条建议：在会话开始时设定模型和努力程度，并建议在任务之间的自然中断处使用 `/compact`。

## 分模型使用

费用文档指出，Sonet 在大多数编码任务中表现良好且比 Opus 便宜，而 Opus 则应保留用于复杂的设计决策或多步骤推理。对于简单的子代理任务，文档建议指定为 `model: haiku`。文档以“意外高昂支出”为例，其常见原因包括长时间未清理的会话以及将 Opus 设为默认模型。[详情 → 模型映射](#/post/ai-models)

需要注意的是，此处内容与前文存在冲突：更换模型会导致缓存失效，因此与其在任务中途频繁切换，不如为子代理指定特定模型以进行划分，这样对缓存的伤害更小。文档指出，子代理拥有自己独立的对话和缓存，不会影响父级缓存。

此外还有“思考（thinking）”令牌。扩展思考默认开启，按输出令牌计费，每个请求的基本预算可能高达数万令牌。对于简单任务，可通过 `/effort` 降低努力级别或在 `/config` 中禁用。但文档也注明，部分模型（Opus 5.5、Sonnet 5.5、Haiku 5.5、Fable 系列）无法禁用此功能。

## 清理、压缩与会话分割

- `/clear`：用于转向无关任务时。文档表述为：陈旧上下文会在后续所有消息中浪费令牌，但成本为零。若需稍后返回，请在清理前使用 `/rename`，之后使用 `/resume`。
- `/compact`：总结对话以减少上下文。可指示保留内容，例如 `/compact Focus on code samples and API usage`，也可在 CLAUDE.md 中设置“压缩指令”项。但压缩本身是一个较大的请求。当缓存处于温热状态（任务进行中）时，从缓存读取开头部分较为划算；而在长时间休息后继续旧会话并压缩，则因缺乏缓存而最为昂贵。
- `/rewind`（或按两次 Esc）：返回错误路径。文档称其通过截断已缓存的前部分内容来回退，相比压缩对缓存更友好。
- 计划模式（Shift+Tab）：在实现前获得方向批准以减少无用功的方法。

此外，文档建议提出具体的请求。“改进此代码库”会引发广泛的探索，而“为 auth.ts 中的登录函数添加输入验证”则涉及读取的文件较少。若同时提供测试用例或预期输出，可减少需要自我验证并修正的往返次数。

## 缩小大文件与日志

文档给出的示例是包含一万行日志的情况。Claude 不会通读整个文件，而是通过钩子（hook）仅筛选 `ERROR` 行，从而将上下文从数十万令牌减少到数百令牌。文档提供了一个使用 PreToolUse 钩子的示例脚本，命令将其修改为仅保留 `npm test`、`pytest`、`go test` 输出中失败的部分。

另一个方法是利用子代理。对于测试运行、获取文档、处理日志等输出较大的任务，可交由子代理处理，这样杂乱的输出会保留在其上下文中，仅将摘要返回给主进程。但需注意，子代理的请求也会计入您的用量。因此，隔离带来的收益是“使主上下文保持干净”，而非“免费”。指定较小的模型可降低此负担。[详情 → Harness](#/post/ai-harness)

代理团队中每位成员都拥有独立的 Claude Code 实例和上下文。文档指出，当有团队成员处于计划模式时，其令牌消耗约为标准会话的 7 倍。减少方法包括：为团队成员使用 Sonet、保持团队规模较小、缩短启动提示词，并在任务完成后让成员退出。代理团队默认关闭，需通过环境变量开启。我尚未亲自尝试过。

## CLAUDE.md 与 MCP

CLAUDE.md 在会话开始时即载入上下文，因此若其中包含特定工作流程（如 PR 审查、数据库迁移等）的长文本，在执行无关任务时也会携带这些令牌。文档的建议有两点：CLAUDE.md 仅保留必要内容并控制在 200 行以内；将特定任务的指令移至技能（Skills）。技能仅在调用时加载。此外，技能还可预先告知项目结构，帮助 Claude 节省读取多个文件以理解结构的令牌消耗。[详情 → 技能与配置](#/post/claude-skills)

MCP 的工具定义默认采用延迟加载，因此仅将工具名称和服务器指令载入上下文，实际使用时再获取定义。尽管如此，文档仍提出两点建议：

- 若已安装 `gh`、`aws`、`gcloud`、`sentry-cli` 等 CLI 工具，其上下文效率优于 MCP，因为不会为每个工具添加额外列表。
- 对于通过 `/mcp` 配置但未使用的服务器，请将其关闭。可通过 `/context` 查看当前上下文占用情况。

关闭工具同样属于工具定义变更，因此在工具搜索已关闭的环境中会导致缓存失效，正如上文所述。[详情 → MCP](#/post/ai-mcp)

## 常见误区

- **使用缓存即可处理长会话**：这仅降低了单次调用成本（unit cost），但上下文大小保持不变；若休息超过 5 分钟或 1 小时，第一条消息将重新处理整个上下文。
- **压缩就一定便宜**：压缩本身可能构成较大的请求。文档指出，对于处于休息状态的旧会话，其成本尤其高昂。
- **频繁切换模型更省钱**：恰恰相反，不频繁切换反而更节省成本。因为每次切换都会导致缓存失效。模型分配最好在会话启动或子代理处进行。这是综合“成本管理”和“提示词缓存”两篇文档得出的结论。
- **子代理不消耗令牌**：上下文会被分离，但请求仍计入您的用量。
