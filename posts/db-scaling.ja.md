# 복제와 샤딩

서비스가 커지면 DB 서버 한 대가 먼저 버거워진다. 쿼리를 고치고 [인덱스](#/post/db-index)를 달고 [캐시](#/post/db-cache-redis)를 붙여도 모자랄 때, 마지막에 꺼내는 게 DB 를 여러 대로 늘리는 방법이다. 크게 둘로 나뉜다. 같은 데이터를 여러 대에 복사해 두는 복제 (replication), 데이터를 쪼개 여러 대에 나눠 두는 샤딩 (sharding) 이다.

한 줄로 구분하면 이렇다.

| | 복제 (replication) | 샤딩 (sharding) |
|---|---|---|
| 각 서버가 가진 것 | 전체 데이터의 사본 | 데이터의 일부 |
| 주로 늘어나는 것 | 읽기 처리량, 가용성 | 쓰기 처리량, 저장 용량 |
| 따라오는 문제 | 복제 지연, 오래된 데이터 | 샤드 간 조인·트랜잭션, 재분배 |

## 읽기 복제

구조는 단순하다. 쓰기를 받는 서버 하나 (primary, MySQL 문서에선 source) 가 있고, 그 변경 내용을 따라 받아 적용하는 서버 (replica, standby) 가 여러 대 있다. 쓰기는 primary 로, 읽기는 replica 들로 흩뿌린다. 대부분의 서비스는 읽기가 쓰기보다 훨씬 많아서 이것만으로도 꽤 버틴다. 요청을 나눠 보내는 부분은 [로드밸런서](#/post/infra-load-balancer)나 애플리케이션의 연결 설정이 맡는다.

MySQL 공식 문서가 꼽는 복제의 쓰임새는 읽기 분산 (scale-out) 말고도 있다. replica 에서 백업을 돌리면 primary 에 영향이 없고, 무거운 분석 쿼리도 replica 에서 돌릴 수 있고, 멀리 있는 지점에 사본을 둘 수도 있다. primary 가 죽으면 replica 하나를 primary 로 올려 이어가는 것 (failover) 도 같은 구조에서 나온다.

### 동기냐 비동기냐

변경을 replica 에 어떻게 전달하느냐가 성능과 안전을 가른다.

| 방식 | 커밋 시점 | 장점 | 단점 |
|---|---|---|---|
| 비동기 | primary 가 커밋하면 바로 끝, 전달은 나중에 | 빠르다 | failover 때 최근 커밋이 사라질 수 있다. replica 가 낡은 값을 줄 수 있다 |
| 반동기 (MySQL) | 최소 한 replica 가 받아서 기록했다고 응답할 때까지 대기 | 받았다는 보장이 있다 | 응답이 느려진다 |
| 동기 | 모든 서버가 커밋해야 끝 | 데이터를 잃지 않고 어디서 읽어도 같다 | 느리다. 네트워크가 느리면 성능이 절반 아래로 떨어질 수도 있다고 PostgreSQL 문서에 적혀 있다 |

MySQL 은 기본이 비동기이고, 표준 복제는 완전한 동기 방식을 제공하지 않는다 (그런 경우엔 NDB Cluster 를 쓰라고 안내한다). 대부분은 비동기를 쓰고 그 대가를 감수한다.

### 복제 지연

비동기의 대가가 복제 지연 (replication lag) 이다. primary 에 쓴 값이 replica 에 닿기까지 짧게는 몇 밀리초, 부하가 크면 몇 초 이상 걸린다. 그 사이에 replica 를 읽으면 방금 쓴 값이 안 보인다.

가장 흔한 사고는 이런 흐름이다. 사용자가 프로필을 수정한다 (primary 에 쓰기). 곧바로 프로필 화면을 연다 (replica 에서 읽기). 수정 전 값이 보인다. 사용자는 저장이 안 된 줄 알고 다시 누른다.

흔히 쓰는 대응은 몇 가지 있다.

- 쓴 직후 일정 시간은 그 사용자의 읽기를 primary 로 보낸다 (read-your-writes).
- 방금 쓴 데이터를 바로 보여줘야 하는 화면만 primary 에서 읽는다.
- replica 의 지연 시간을 모니터링하고, 지연이 크면 그 replica 를 읽기 대상에서 뺀다.

복제는 쓰기를 늘려 주지 않는다는 점도 기억해 둘 만하다. 모든 replica 가 primary 의 쓰기를 전부 따라 적용해야 하므로, 쓰기가 병목이면 replica 를 아무리 늘려도 그대로다. 그때부터 샤딩 얘기가 나온다.

## 파티셔닝

샤딩 전에 파티셔닝부터 짚는다. 용어가 섞여 쓰이는데, 보통 파티셔닝은 한 테이블을 여러 조각으로 나누는 일이고, 샤딩은 그 조각을 서로 다른 서버에 두는 일로 구분한다.

PostgreSQL 문서 기준으로 파티션된 테이블 자체는 저장 공간이 없고, 행은 파티션 키에 따라 각 파티션 (평범한 테이블) 으로 들어간다. 나누는 방식은 셋이다.

- 범위 (range): 날짜 같은 키를 구간으로 자른다. 월별 파티션이 대표적이다.
- 목록 (list): 키 값을 직접 나열한다. 지역 코드별 같은 경우다.
- 해시 (hash): 키 해시를 modulus 로 나눈 나머지로 보낸다.

효과는 질의가 일부 파티션만 읽으면 되고 (pruning), 오래된 데이터를 `DROP`이나 `DETACH PARTITION` 으로 통째로 버릴 수 있다는 것이다. 큰 `DELETE` 보다 훨씬 빠르고 VACUUM 부담도 없다. 다만 문서는 이 이득이 테이블이 아주 클 때 (경험칙으로 서버 메모리보다 클 때) 의미가 있다고 적는다. 제약도 있다. 기본 키와 유니크 제약에는 파티션 키 컬럼이 모두 들어가야 한다.

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

(上記の SQL は PostgreSQL ドキュメントの例であり、実際に実行していません。)

## シャーディング

パーティションを異なるサーバーに配置することをシャーディングと呼びます。各サーバーはデータの一部分しか保持しないため、保存容量や書き込み処理能力もサーバー数に応じて増えます。その代わり、アプリケーション（またはルーティング層）が「このキーはどのシャードにあるか」を知る必要があります。

### シャードキーが全て

データをどのように分割するか（シャードキー）が決めることが最も重要な選択です。一度決めると変更するのが困難です。

| 方式 | 長所 | 短所 |
|---|---|---|
| レンジ | レンジクエリは一つのシャード内で完了する | 最新の区間に書き込みが集中する（ホットスポット） |
| ハッシュ | 均等に分散する | レンジクエリではすべてのシャードを検索しなければならない |
| ディレクトリ（インデックス） | 柔軟である | インデックスがボトルネックや単一障害点となる |

id を順次発行して範囲で分割すると、新規書き込みはすべて最後のシャードに向かいます。以下の実験でも id 1〜10,000 を 3 等分した場合、最新の 1,000 件はすべて同じシャード（2 番目）に入りました。均等に分散させるためにシャーディングを行いましたが、結局一台だけが稼働している状態です。

### サーバー数が変わる場合

ハッシュで分割する際の一般的な最初の試みは `hash(key) % サーバー数` です。シンプルですが、サーバー数が変わるとほぼすべてのキーの位置が変化します。実際に動かして確認したところ、10,000 キーを 3 サーバーから 4 サーバーに増やした場合、約 75% が別のサーバーへ移動する必要がありました。

一貫性のあるハッシュ（consistent hashing）はこの問題を軽減します。サーバーとキーを同じハッシュ円上に配置し、キーは時計回りに最初に遭遇するサーバーに割り当てます。サーバーが一つ増えると、そのサーバーと前のサーバーの間にあったキーだけを移動させればよいです。ウィキペディアの説明によると、n 番目のサーバーを追加する際、大まかに 1/n だけ移動します。サーバーを円上に一点ずつ配置すると間隔が不規則になり負荷が偏ってしまうため、サーバーの一つを複数の地点（仮想ノード）に置き、均一にし、性能の高いサーバーにはさらに仮想ノードを与えます。

<details>
<summary>実際に動かしたコードと結果</summary>

```python
import hashlib, bisect
def h(k): return int(hashlib.md5(k.encode()).hexdigest(), 16)
keys = [f"user{i}" for i in range(10000)]

def mod(n): return {k: h(k) % n for k in keys}
a, b = mod(3), mod(4)
print("mod 3->4 moved:", sum(a[k] != b[k] for k in keys) / len(keys))

def ring(nodes, vn=100):
    r = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vn))
    hs = [x[0] for x in r]
    def f(k):
        i = bisect.bisect(hs, h(k)) % len(r)
        return r[i][1]
    return f

f3 = ring(["A", "B", "C"])
f4 = ring(["A", "B", "C", "D"])
print("ring 3->4 moved:", sum(f3(k) != f4(k) for k in keys) / len(keys))
```

実行結果（Python 3、この環境で確認）。

```
mod 3->4 moved: 0.7484
ring 3->4 moved: 0.2392
```

理論値の 1/4（25%）に近い約 24% しか移動しません。仮想ノードはサーバーあたり 100 個に設定しました。

</details>

## シャーディングを難しくするもの

シャーディングは書き込みを増やす代わりに、DB が無料で提供していた機能を取り上げてしまいます。

- ジョイン：異なるシャードにあるテーブル同士は一度にジョインできません。アプリで別途取得して結合するか、頻繁に一緒に使用するデータを同じシャードに置くようにシャードキーを設定します。[正規化](#/post/db-normalization) で分割したテーブルがシャードを横断すると負担が大きくなります。
- トランザクション：一つのシャード内では通常通り動作しますが、複数のシャードを操作する [トランザクション](#/post/db-transaction) は分散トランザクション（2 フェーズコミットなど）や補償処理が必要です。遅く複雑です。そのため、通常は一つのトランザクションが一つのシャード内で完了するように設計します。
- ユニーク・自動増分 id：各シャードで個別に番号を振ると重複します。UUID や時刻ベースの id などの別々の発行方式が必要です。
- リバランス（resharding）：シャードを増やすとデータを移動させる必要があります。無停止で行うにはダブルライティングや検証などの作業がかかります。
- 運用：バックアップ、スキーマ変更、モニタリングもすべてシャード数に応じて倍増します。

そのため、順序が決まっているように見えます。クエリやインデックスの改善、サーバー仕様の向上（スケールアップ）、キャッシュ、読み取りレプリケーションを優先し、書き込みや容量がそれでも不足する时才はシャーディングを行います。最初からシャーディングを行うのはほとんど過剰です。シャーディングが基本機能として含まれている [NoSQL](#/post/db-nosql) を選ぶのも一つの手段です。

## 一貫性のトレードオフ

レプリケーションとシャーディングを行うと「データが複数箇所に存在する」という事実が生じ、同じ値を複数の場所でどのように合わせるかが問題となります。PostgreSQL ドキュメントはこれを以下のように整理しています。読み取り専用データは各サーバーに一度置くだけで済みますが、書き込みはすべてのサーバーに伝播させる必要があります（その後の読み取りが一貫性を持つため）、そのためすべてのワークロードに適した単一の解決策はありません。

実務で選ぶのは大抵はこの 3 つのバランスです。

| 向上させる | 低下するもの |
|---|---|
| 一貫性（どこから読んでも最新） | 書き込み速度、サーバーが一つ止まった場合の可用性 |
| 書き込み速度・可用性 | 読み取り時の最新値の保証 |
| 保存・書き込みのスケーラビリティ（シャーディング） | ジョイン・トランザクションの利便性 |

銀行残高のように間違えてはいけない場所は一貫性の側、投稿閲覧数やフィードなど数秒遅れてもよい場所は速度・スケーラビリティの側に傾きます。一つのサービス内でもデータごとに異なります。

- 複製すると書き込みも速くなる：違う。書き込みはプライマリが受け、レプリカはその追従により適用されるため、書き込み処理量は変わらない。
- レプリカはバックアップである：違う。プライマリで誤って削除されたデータはそのままレプリカにも反映される。遅延複製（delayed replication）を使用するか、別途バックアップが必要となる。
- パーティショニングとシャディングは同じもの：同一サーバー内で分割する場合はパーティショニング、サーバーを分ける場合はシャディングとして区別することが多い。パーティショニングだけでは単一サーバーの限界を超えることはできない。
- シャディングは事前にしておくのが良い：シャードキーを不適切に設定すると後から変更が難しく、運用複雑度は即座に増大する。必要性が確認された後に実施するのが一般的である。

## まとめ

読み込みが多い場合は複製、容量や書き込みに限界がある場合はシャディング、一つのサーバー内で大きなテーブルを扱いやすくするにはパーティショニングである。いずれの場合も、データが複数の場所に配置される瞬間には、どの程度の一貫性を許容するかを決定しなければならない。
