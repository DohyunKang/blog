오토스케일링은 부하에 맞춰 서버 수나 크기를 자동으로 바꾸는 장치이고, 잘 돌리려면 지표를 뭘로 잡느냐와 서버가 상태를 들고 있지 않느냐가 먼저였다.

## 확장이 뭔지

서비스에 사람이 몰리면 서버 하나로는 모자란다. 이때 늘리는 방법이 둘이다.

| | 수직 확장(scale up) | 수평 확장(scale out) |
|---|---|---|
| 방법 | 서버 한 대를 더 큰 걸로 교체 | 같은 서버를 여러 대로 늘림 |
| 쉬운 점 | 코드를 거의 안 고쳐도 됨 | 한계가 사실상 없음, 한 대가 죽어도 버팀 |
| 어려운 점 | 올릴 수 있는 크기에 천장이 있음, 교체할 때 멈출 수 있음 | 요청을 나눠 줄 장치가 필요하고, 서버끼리 상태를 맞춰야 함 |

오토스케일링이라고 하면 보통 수평 쪽을 말한다. 서버를 한 대 더 띄우는 건 자동화하기 쉽고, 크기 교체는 재시작이 따라오기 때문이다. 요청을 여러 대에 나눠 주는 부분은 [자세히 → 로드밸런서](#/post/infra-load-balancer)에 따로 정리했다.

## 자동으로 늘린다는 건

사람이 대시보드를 보다가 서버를 추가하는 걸 기계가 대신하는 일이다. 순서는 늘 같다.

1. 지표를 잰다(CPU, 요청 수 같은 것).
2. 목표값과 비교한다.
3. 모자라면 서버를 더 띄우고, 남으면 줄인다.

AWS의 target tracking 문서는 이걸 온도 조절기에 비유한다. 목표 평균 CPU를 50%로 정해 두면 그 위로 올라갈 때 늘리고, 아래로 내려가면 줄인다. 문서 기준으로 이 방식은 CloudWatch 알람을 서비스가 대신 만들고 관리한다.

쿠버네티스의 HPA(Horizontal Pod Autoscaler)도 같은 발상이다. 공식 문서에 나온 계산식은 이렇다.

```
원하는 개수 = ceil[ 현재 개수 × (현재 지표값 / 목표 지표값) ]
```

현재 4개인데 평균 CPU가 90%이고 목표가 50%면 4 × 1.8 = 7.2, 올림해서 8개가 된다. HPA는 기본 15초 간격으로 이 계산을 돈다고 문서에 적혀 있다.

<details>
<summary>자세한 풀이: 계산식을 직접 돌려 본 것</summary>

식이 감이 안 와서 파이썬으로 옮겨 돌려 봤다. tol은 "목표와 거의 같으면 가만히 둔다"는 여유 구간인데, 0.1은 내가 쓴 값이다(아래 확인 못 함 참고).

```python
import math

def desired(cur, metric, target, tol=0.1):
    r = metric / target
    if abs(r - 1) <= tol:      # 목표 근처면 그대로
        return cur
    return math.ceil(cur * r)

print(desired(4, 90, 50))   # 8  (7.2를 올림)
print(desired(4, 52, 50))   # 4  (여유 구간 안이라 유지)
print(desired(10, 20, 50))  # 4  (줄이는 쪽도 같은 식)
print(desired(1, 60, 50))   # 2
```

실행 결과는 8, 4, 4, 2였다. 올림을 쓰니 "조금 모자란 것"도 한 대가 늘어난다. 모자란 쪽으로 틀리는 것보다 남는 쪽으로 틀리는 게 낫다는 방향이다.

</details>

## 뭘 기준으로 늘릴까

스케일링 글에서 제일 많이 막히는 곳이 지표 고르기였다.

- CPU 사용률: 가장 흔하다. 계산이 많은 서버에는 맞고, 대부분 외부 응답을 기다리는 서버에는 CPU가 안 오르는데 느려질 수 있다.
- 요청 수(서버 한 대당): 웹 서비스에서 직관적이다. AWS에도 로드밸런서 타깃당 요청 수(`ALBRequestCountPerTarget`)가 기본 지표로 있다.
- 큐 길이: 일을 뒤에서 처리하는 워커에 맞다. AWS 문서는 SQS 큐에 쌓인 메시지 수를 그대로 쓰면 안 되고, 서버 한 대당 메시지 수로 바꿔 쓰라고 한다. 서버를 늘려도 큐 길이가 그에 비례해 줄지 않기 때문이다. 큐 쪽 얘기는 [자세히 → 비동기 처리와 메시지 큐](#/post/be-async-queue)에 있다.
- 지연 시간(latency): 느려지는 걸 직접 보지만 문서에는 target tracking에 쓰면 안 되는 지표로 나온다. 서버가 바쁠수록 늘기는 해도 서버 수에 비례해서 변하지는 않아서다.

AWS 문서의 기준을 내 말로 줄이면, 서버가 늘수록 지표값이 비례해서 내려가는 것이어야 한다. 그래서 로드밸런서의 전체 요청 수는 서버를 늘려도 그대로라 안 된다.

쿠버네티스에서 CPU 사용률을 목표로 쓰려면 컨테이너에 `requests`가 설정돼 있어야 한다고 문서에 나온다. 요청값이 없으면 사용률을 계산할 수 없어서 HPA가 그 지표로는 아무것도 안 한다. 이거 빠뜨리면 "왜 안 늘지?" 하고 한참 보게 될 것 같다.

## 늘리는 것보다 줄이는 게 더 조심스럽다

서버가 새로 뜨는 데 시간이 걸린다. 그동안 지표는 여전히 높아서 "더 늘려야 한다"고 또 판단할 수 있다. 그러면 필요 이상으로 많이 뜬다.

AWS는 이걸 warmup(예열) 시간으로 다룬다. 새 서버가 예열을 마칠 때까지는 그 서버의 지표를 집계에 넣지 않고, 이 시간 동안은 줄이는 동작도 막는다. 문서 표현으로는 "계속 늘리되 과하게는 안 늘린다"가 목적이다.

줄일 때도 비슷하다. 문서는 target tracking이 줄일 때는 더 천천히 줄인다고 하고, 반올림도 보수적으로 한다고 한다. 서버를 한 대 줄였더니 부하가 바로 목표를 넘어 다시 늘리는 오르락내리락을 피하려는 것이다. 작은 그룹에서는 이 영향이 크다.

<details>
<summary>자세한 풀이: 작은 그룹이 목표에서 멀어 보이는 이유</summary>

AWS 문서에 서버 수가 적으면 실제 사용률이 목표값과 꽤 어긋나 보일 수 있다는 설명이 있어서 숫자로 맞춰 봤다. 총 부하가 서버 한 대 기준 60%짜리 두 대분(합 120)이라고 하고, 목표를 50%로 잡았다.

- 서버 2대 그룹: 120 / 50 = 2.4 → 3대가 된다. 3대로 나누면 서버당 40%. 목표와 10%p 차이.
- 서버 20대 그룹: 부하 합 1200 / 50 = 24대. 서버당 정확히 50%.

한 대 단위로만 움직일 수 있으니, 대수가 적을수록 올림의 영향이 커진다. 큰 그룹에서는 한 대가 차지하는 비율이 작아서 목표에 잘 붙는다.

</details>

## 서버가 상태를 들고 있으면 곤란한 이유

여기가 이 글에서 제일 중요한 부분 같다. 서버를 마음대로 띄우고 없애려면 어느 서버가 사라져도 서비스가 이어져야 한다.

로그인 정보(세션)를 서버 메모리에 들고 있다고 해 보자. 요청이 A서버에서 B서버로 가면 B는 이 사용자를 모른다. 줄이는 순간 A가 사라지면 그 사용자는 로그아웃된다. 그래서 서버는 상태가 없게(stateless) 만들고, 상태는 바깥에 둔다.

| 상태의 종류 | 바깥에 두는 곳 |
|---|---|
| 세션, 임시 값 | 공용 캐시(예: Redis) → [자세히 → 캐시와 Redis](#/post/db-cache-redis) |
| 사용자 데이터 | 데이터베이스 |
| 업로드 파일 | 오브젝트 스토리지 |
| 처리 대기 작업 | 메시지 큐 |

이렇게 하면 서버는 코드만 가진 복제본이라 몇 대가 되든 같다. 새로 뜨면 바로 일하고, 사라져도 잃을 게 없다. 인증을 서버에 세션으로 둘지 토큰으로 둘지는 [자세히 → 인증과 인가](#/post/be-auth)에서 다룬다.

## 서버 말고 DB는 어떻게

서버는 늘리기 쉬운데 데이터베이스는 그렇지 않다. 서버를 열 대로 늘려도 모두 같은 DB를 보니까 병목이 DB로 옮겨 간다. 읽기 복제본, 샤딩 같은 방법은 [자세히 → 데이터 확장](#/post/db-scaling)에 따로 정리했다. 오토스케일링을 걸기 전에 "늘어난 서버가 DB를 몇 개 연결로 때리는지"를 먼저 계산해 봐야 한다는 건 이번에 정리하면서 정한 확인 항목이다.

## 흔한 오해

- 오토스케일링을 켜면 폭주 트래픽도 다 받는다: 서버가 뜨는 시간이 있어서 순간 급증에는 늦다. 그래서 최소 개수를 넉넉히 두거나 미리 예약해 두는 방식을 따로 쓴다. 다만 이 부분은 문서로 직접 확인한 게 아니라 위 warmup 설명에서 이어 생각한 것이다.
- 늘리기만 하면 된다: 줄이는 설정이 없으면 비용이 계속 남는다. 반대로 최소 개수를 0으로 둬야 요청이 없을 때 0까지 내려간다고 AWS 문서에 나온다.
- 서버만 늘리면 빨라진다: 병목이 DB나 외부 API에 있으면 서버를 늘려도 그대로다.
- 지표는 아무거나 괜찮다: 서버 수에 비례해 변하는 지표여야 한다.
- 요청이 많이 오면 429로 막으면 되지: 막는 것과 늘리는 것은 다른 방어선이다. 같이 쓴다. → [자세히 → 레이트 리밋](#/post/infra-rate-limit)

<details>
<summary>자세한 풀이: 확인한 것과 못 한 것</summary>

확인함: 수직·수평 확장의 구분(일반 개념), HPA 계산식, 기본 동기화 주기 15초, 컨테이너 `requests`가 있어야 사용률 목표가 동작한다는 것, Metrics Server가 따로 설치돼야 한다는 것(쿠버네티스 문서), target tracking의 동작과 지표 선택 기준, warmup, 줄일 때의 보수적 동작, 최소 용량 0 조건(AWS 문서). 계산식과 올림 예시는 파이썬으로 실행해 확인했다.

확인 못 함: HPA의 허용 오차 기본값(0.1)과 스케일 다운 안정화 구간 기본 300초는 가져온 문서 일부에서 보이지 않았다. 본문에는 숫자를 쓰지 않았고, 코드의 tol=0.1은 예시용이다. 쿠버네티스 문서 뒷부분(약 3만 자)은 읽지 못했다. 클라우드별 예약·예측 스케일링 기능의 세부는 읽지 않았다.

</details>
