形版本管理是记录和管控软件变更的工作，而构建与部署则是将经过如此管理的源代码转化为可执行成果的过程。在信息处理技术员考试中，大部分题目涉及术语定义与分类，因此本文也按此单位进行划分。考试日程与报名费用请查阅官方网站。

## 什么是形版本管理

形版本（Configuration）是指构成软件的产出物整体。它不仅包括源代码，还包括需求文档、设计说明书、测试用例和配置文件等。其中被确定为变更追踪对象的项目称为形版本项。

形版本管理（SCM）是对这些项目记录“谁在何时因何原因进行了变更”，并在需要时能够恢复到先前状态的活动。开发过程中的变更无法避免，因此目标在于使变更过程井然有序。需求中途发生变更的问题也在 [详见 → 需求确认与分析](#/post/jb-requirements) 中提及。

整理了考试中常出现的术语表：

| 术语 | 含义 |
|---|---|
| 形版本项 | 确定为变更管理对象的产出物 |
| 基线 | 经过正式审查并批准的基准时间点。此后任何变更均需遵循既定流程 |
| 检出（Checkout） | 从存储库中取出文件用于工作 |
| 检入（Check-in/Commit） | 将修改内容提交至存储库 |
| 分支（Branch） | 从主干流分叉出的独立工作线 |
| 合并（Merge） | 将分叉的分支重新汇合 |

## 形版本管理的四种活动

这是考试中最为常见的部分。需记住活动名称及其对应说明：

| 活动 | 工作内容 |
|---|---|
| 形版本标识 | 确定管理对象，并为每个项目命名或编号 |
| 形版本控制 | 接收变更请求并进行审查与批准，仅对获批内容进行实施（由变更控制委员会判定） |
| 形版本审计 | 检查是否按基线构建、变更是否按流程处理 |
| 形版本记录（状态报告） | 记录项目的当前状态及变更历史并予以报告 |

容易混淆的是“控制”与“审计”。控制是允许变更的一方，而审计则是确认变更是否按批准方式执行的一方。

<details>
<summary>实施形版本管理的好处</summary>

- 可将错误修复回退至先前版本。
- 多人修改同一文件时能发现并解决冲突。
- 可追踪已部署版本源自何处。
- 保留变更历史，便于明确责任归属与原因分析。

</details>

## 三类版本控制系统

版本管理系统根据存储库存放位置的不同而分类：

| 方式 | 存储库位置 | 典型工具（考试常见） |
|---|---|---|
| 本地/共享文件夹 | 锁定并修改公用文件夹中的文件 | RCS, SCCS |
| 客户端/服务器 | 存储库位于中央服务器 | CVS, SVN (Subversion) |
| 分布式 | 每位开发者拥有完整存储副本 | Git, Bazaar |

集中式方式若服务器宕机则工作受阻，而分布式方式因每位开发者均持有完整历史，故可在离线状态下进行提交和创建分支。Git 的内部结构已在 [详见 → 彻底理解 Git](#/post/cs-git) 中单独说明。

合并操作在《Pro Git》中有两种情况：若待合并的分支恰好位于当前分支之后，仅需移动指针即可（fast-forward），不会产生新提交；若双方各自积累了提交导致分叉，则需基于两个分支末端与共同祖先的三个快照进行合并，并生成具有双亲节点的合并提交。若同一文件的相同部分在两侧被不同修改，则会产生冲突，需在手动解决冲突后使用 `git add` 标记解决状态并提交，方可完成合并。

<details>
<summary>几个常用的 Git 命令</summary>

| 命令 | 功能 |
|---|---|
| `git add` | 将变更添加到暂存区 |
| `git commit` | 确认暂存区内容为提交 |
| `git branch` | 创建或列出分支 |
| `git merge` | 将其他分支合并到当前分支 |
| `git status` | 查看当前状态及冲突文件 |

</details>

## 构建与构建工具

构建是将源代码编译、链接库文件、运行测试并打包为可执行形式的过程。手动操作易出错，因此需借助工具按固定顺序自动执行。

考试中出现的工具有 Make、Ant、Maven、Gradle 等。可根据其声明方式进行区分：Ant 是显式编写任务顺序的类型，而 Maven 则是遵循预定义生命周期的类型。下载并管理依赖库也是 Maven、Gradle 这类工具的特征，可一并记忆。

从 Maven 文档中查到的基本生命周期阶段如下：

| 步骤 | 阶段 | 含义 |
|---|---|---|
| 1 | validate | 检查项目配置是否正确以及所需信息是否完备 |
| 2 | compile | 源代码编译 |
| 3 | test | 执行单元测试（不应需要打包或部署） |
| 4 | package | 以 JAR 等可部署形式进行打包 |
| 5 | verify | 检查集成测试结果等质量基准 |
| 6 | install | 安装到本地仓库 |
| 7 | deploy | 复制到远程仓库并共享 |

指定一个阶段（如 `mvn verify`）时，其前面的所有阶段会按顺序依次执行。清除先前构建产物的 `clean` 属于独立的生命周期阶段，因此需像 `mvn clean deploy` 这样前置添加。测试阶段包含在构建过程中，这一点与 [详情 → 软件测试](#/post/jb-testing) 相关联。

构建和测试会在代码合并时自动运行，这称为 CI；在此基础上自动完成部署的则称为 CD。流水线配置已在 [详情 → CI/CD 与部署策略](#/post/cloud-cicd) 中讨论。

## 发布与版本号

发布是将构建产物交付给用户或生产环境的过程。在发布前后需要同时关注以下两点：

- **发布说明**：记录本版本新增的功能、修复的问题以及已知问题的文档
- **旧版本归档**：保留部署包和源代码的对应关系，以便在出现问题时能够回滚

版本号最常提及的是语义化版本（SemVer）规则。根据官方文档整理如下：

| 位置 | 提升时机 |
|---|---|
| MAJOR | 破坏性向后兼容的 API 变更 |
| MINOR | 向后兼容的功能新增 |
| PATCH | 向后兼容的缺陷修复 |

数字递增时，其右侧的数字归零（例如从 1.4.2 提升 MINOR 变为 1.5.0）。`0.y.z` 处于早期开发阶段，随时可能变更；而从 `1.0.0` 开始，公开 API 正式确定。类似 `1.0.0-rc.1` 这样在连字符后添加的内容属于预发布版本，优先级低于正式的 `1.0.0`。加号 `+` 后的构建元数据在版本比较中被忽略。已发布的版本内容不得修改，若需更改则必须采用新的版本号。

还需了解开发阶段的命名顺序：Alpha（内部测试）、Beta（部分外部用户测试），随后是正式发布。

## 代码审查

在合并代码之前，由他人阅读并查找缺陷的活动。考试中将重点考察静态技术的特点（即不执行代码、仅通过人工检查）以及形式严格程度的差异。

| 类型 | 感觉 |
|---|---|
| 同行评审 | 作者与同事进行的非正式轻量级审查 |
| 走查 | 作者讲解产出物，参与者提出意见的方式 |
| 检视 | 角色（仲裁者、记录员等）和流程均已确定的最正式方式 |

形式由宽松到严格的顺序为：同行评审、走查、检视。不执行代码而进行的验证属于 [详情 → 软件测试](#/post/jb-testing) 中的静态测试范畴。

## 常见错误点

- 混淆版本控制与版本审计：控制对应审批，审计对应确认。
- 误将基线理解为“最新版本”：基线是正式批准并附带变更流程的参考点。
- 将 Git 按客户端/服务器方式分类：Git 是分布式系统。
- 认为 SemVer 中缺陷修复也应提升 MINOR：缺陷修复应使用 PATCH。
- 混淆 `install` 与 `deploy`：前者安装到本地仓库，后者部署到远程仓库。
