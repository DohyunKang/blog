CPU は命令を高速に実行しますが、ディスクやネットワークカード、キーボードなどはそれに比べて非常に遅いです。入出力（I/O）の話は、ほぼこの速度差をどう隠すかという点で説明できます。CPU 内部の動作については [CPU と命令](#/post/ca-cpu) に、メモリの速度差については [メモリ階層とキャッシュ](#/post/ca-memory-hierarchy) に譲り、ここでは CPU 外部の装置とその間のバス（経路）のみを見ていきます。

## 装置はレジスタ数個に見える

OSTEP（教科書）では、仮想的な標準装置を一つ置き、それを使って説明します。装置は二つの部分から成り立っています。システムに提示されるインターフェースと、その背後にある内部構造です。内部は単一のチップで終わる単純な装置の場合もあれば、小さな CPU やメモリまで含まれてファームウェアが動作する複雑な装置の場合もあります。オペレーティングシステムは内部を知らなくても、インターフェースだけを扱えばよいのです。

インターフェースは三つのレジスタに単純化されます。

| レジスタ | 用途 |
|---|---|
| ステータス (status) | 読み取りして、装置が現在忙しいか確認する |
| コマンド (command) | 書き込むと装置がその作業を開始する |
| データ (data) | 装置に送るデータを記述したり、受け取ったデータを読み取る |

基本的な手順は四段階です。ステータスが「忙」の間待機し、データレジスタに書き込み、コマンドレジスタに書き込み、再びステータスが「忙」の間待機します。このようにステータスを繰り返し読みながら待つことをポーリング (polling) と言い、CPU が直接データを転送するのを PIO (programmed I/O) と呼びます。シンプルで動作しますが、装置が遅いと CPU は単にステータスレジスタを読み続けるだけで時間を浪費してしまいます。

## レジスタにどうアクセスするか

CPU が装置レジスタにアクセスする方法は二つあります。一つは専用の入出力命令です。x86 の `in` や `out` がその例で、ポート番号を使って装置を指し示します。これらの命令は通常特権命令であり、オペレーティングシステムだけが使用できます。なぜなら、任意のプログラムがディスクを直接操作すると困るからです。

もう一つはメモリマップド I/O です。装置レジスタをメモリアドレスのように見せることで、そのアドレスに load/store を行うと、ハードウェアがそれをメモリではなく装置宛てに送ります。新しい命令語が必要ないことが利点です。OSTEP はどちらかが明確に優れているわけではなく、現在も両方が使用されていると述べています。

装置ごとにレジスタや手順が異なるため、オペレーティングシステム全体がそれらを把握することはできません。そのため、装置ごとの詳細はデバイスドライバ内に閉じ込められ、ファイルシステムのような上位層では「ブロック読み取り/書き込み」などの一般的なリクエストのみを行います。ファイルシステム側については [ファイルシステムと入出力](#/post/os-filesystem) で扱います。

## 待機のコスト：ポーリングと割り込み

ポーリングの代わりに割り込みを使用すると、オペレーティングシステムはリクエストを送信してそのプロセスをスリープさせ、他の作業を行わせます。装置が完了するとハードウェア割り込みが発生し、CPU は割り当てられた割り込みハンドラ (ISR) に飛びます。ハンドラはリクエストを終了させ、待機させておいたプロセスを起こさせます。その間 CPU は他のプロセスを実行しているため、計算と I/O が重なります。

では割り込みの方が常に良いのかというと、OSTEP はそうではないと言っています。割り込み処理やコンテキストスイッチにもコストがかかります。装置が非常に速い場合、最初の数回のポーリングですぐ終わるため、その場合はポーリングの方が良いのです。そのため、少しポーリングして終わらないようなら割り込みに切り替えるハイブリッド方式もあります。ネットワークのようにパケットが殺到すると割り込みが多くなりすぎて、オペレーティングシステムが割り込み処理だけで終わってしまうライブロック (livelock) が発生する可能性があり、その場合はたまにポーリングで流れを直接握る方がよいと言います。複数の割り込みを集めて一度に通知する coalescing という最適化もあります。

<details>
<summary>ポーリングとブロッキング待機、CPU をどれくらい使うか（直接実行）</summary>

1 秒後に「完了」と知らせる遅い装置をスレッドで模倣しました。片方は非ブロッキング `recv` をループで継続呼び出し（ポーリング）し、もう片方はブロッキング `recv` でカーネルにスリープさせました。ブロッキングが割り込み方式と完全に同じという意味ではなく、オペレーティングシステムがプロセスをスリープさせてイベントが来たら起こす点で似た構造です。

```python
import socket, time, threading

def device(sock, delay):
    time.sleep(delay)
    sock.send(b"done")

def run(mode, delay=1.0):
    a, b = socket.socketpair()
    threading.Thread(target=device, args=(b, delay), daemon=True).start()
    c0, t0 = time.process_time(), time.perf_counter()
    if mode == "poll":
        a.setblocking(False)
        n = 0
        while True:
            n += 1
            try:
                a.recv(4); break
            except BlockingIOError:
                pass
    else:
        a.recv(4); n = 1
    return mode, n, time.process_time() - c0, time.perf_counter() - t0

for m in ("poll", "block"):
    mode, n, cpu, wall = run(m)
    print(f"{mode:5s} 확인 {n:>9,}회  CPU {cpu:.2f}s  경과 {wall:.2f}s")
```

Windows で Python 3.13 を使って実行した結果です。ポーリングは確認を約 58 万回行い CPU を 0.98 秒使用し、ブロッキングは一回の呼び出しで CPU 0.00 秒でした。どちらも経過時間は 1.00 秒なので待機時間は同じですが、その間 CPU を使うかどうかで差がありました。回数は実行ごとに異なります。
</details>

## データ転送の仕事：DMA

割り込みで待機を減らしても、PIO ではデータを CPU が単語単位で装置にコピーする必要があります。大きなブロックの場合、CPU は単純なコピーに時間を費やします。この仕事を引き受けたのが DMA (Direct Memory Access) です。DMA エンジンとは、CPU の介入なしにメモリと装置間の転送を行う専用装置です。

手順は以下の通りです。オペレーティングシステムは、DMA エンジンに「データがメモリのどこにあるか」「どれだけの量を移動させるか」「どのデバイスに送信するか」を通知します。ここまでの処理がオペレーティングシステムの役割であり、以降の転送はエンジンが行います。完了すると、エンジンが割り込みを発生させて知らせます。OSTEP のタイムラインを見ると、PIO ではプロセス 1 がコピーしている間 CPU は待機しますが、DMA ではその区間にプロセス 2 が実行されます。

DMA は無料ではありません。エンジンの設定と終了時の割り込み処理にかかるコストがあるため、非常に小さな転送では PIO の方が有利になることもあります。

<details>
<summary>PIO と DMA の損益分岐点の計算（仮定した数値、実際に実行済み）</summary>

実際のハードウェアを測定したものではなく、以下の数値を仮定して計算したものです。1 ワード（8 バイト）を移動させるのに 20 サイクル、DMA の設定と割り込み処理に 2000 サイクルかかるものとしています。

```python
BLOCK = 4096
WORD = 8
COPY_CYCLES = 20
SETUP_CYCLES = 2000

dma = SETUP_CYCLES
for size in (64, 512, 4096, 65536):
    p = (size // WORD) * COPY_CYCLES
    print(f"{size:>6}B  PIO {p:>7}  DMA {dma}  ->", "PIO가 유리" if p < dma else "DMA가 유리")
```

出力は、64B では PIO 160 対 DMA 2000（PIO が有利）、512B では 1280 対 2000（PIO が有利）、4096B では 10240 対 2000（DMA が有利）、65536B では 163840 対 2000（DMA が有利）でした。分岐点は仮定する数値によって変わり、実際の値はデバイスや CPU ごとに異なります。
</details>

## バスとアドレス

バスは、CPU、メモリ、デバイスがデータや信号をやり取りするための接続経路です。OSTEP の現代システム図を見ると、CPU はメモリおよびメモリインターコネクトに、グラフィックカードには高性能な PCIe で直接接続されています。残りのデバイスは、DMI に接続された I/O チップを経由します。そのチップの下には eSATA でハードディスクが、USB でキーボードやマウスなどの低速デバイスが接続されます。ネットワークカードや NVMe ストレージなど的高性能デバイスは、多くの場合 PCIe に接続されるとのことです。高速なほど CPU に近い接続を使用し、低速なほど遠いチップを経由する階層構造になっています。

DMA を使用するデバイスはメモリアドレスを直接使用するため、アドレスの概念が一つ増えます。Linux カーネルのドキュメントでは、アドレスを三つに分類しています。カーネルが使用する仮想アドレス、デバイスレジスタなどのリソースを管理する際に使用する CPU 物理アドレス、そしてデバイスが MMIO と DMA で使用するバスアドレスです。バスアドレスはホストブリッジや IOMMU が変換するため、CPU 物理アドレスとは異なる場合があります。IOMMU は、デバイスが見るアドレスを実際の RAM アドレスに変換するデバイスです。単純なシステムには存在しない場合もあります。

Linux の DMA マッピングは二つに分類されます。コヒーレントマッピングはドライバの初期化時に作成され長期間使用され、ハードウェアが CPU とデバイスが見ている内容を一致させます。デバイスとのやり取りを行うディスクリプタリングなどの構造に適しています。ストリーミングマッピングは一度の転送のために作成して解放し、ネットワークやファイルシステムバッファに使用します。CPU がそのバッファを途中でアクセスすると、同期呼び出しが必要です。

## GPU はどこに接続されているか

GPU もデバイスとしてバスに接続されます。ただし、CUDA ドキュメントのモデルでは、CPU に直接接続されたメモリがホストメモリで、GPU に接続されたメモリがデバイスメモリです。プログラムは CPU から始まり、CUDA API を使って両者の間でデータをコピーし、カーネル（GPU で実行されるコード）を実行してから終了を待ちます。CPU と GPU は同時に動作できます。対応するシステムでは、統合仮想アドレス空間のおかげで、アドレスを見るだけで GPU メモリかシステムメモリかが判別でき、Unified Memory を使用するとランタイムやハードウェアが必要に応じてデータを移動させます。ドキュメントには、「PCIe や NVLink の向こう側の CPU メモリを GPU がそのまま読む方式は、データを適切な場所に置くことの代替にはならない」と記載されています。

まとめると、GPU を使用する際の「データコピー」のコストは結局バスを通過するコストです。モデルを GPU に配置しておけば毎回コピーする必要がない理由もここから続きます。推論に関する話は [推論最適化](#/post/ml-inference)にあります。

## よくある誤解

- DMA を使うと CPU が全く関与しない：転送自体はエンジンが行いますが、開始時の設定と終了時の割り込み処理は CPU の役割です。
- 割り込みは常にポーリングより良い：高速なデバイスや割り込みが集中する状況では、ポーリングの方が有利になる場合があります。
- デバイスアドレスとメモリアドレスは別物：メモリマップド I/O ではデバイスレジスタもアドレス空間に現れます。
- CPU が見る物理アドレスとデバイスが使うアドレスは常に同じ：ブリッジや IOMMU がある場合は異なる場合があります。
