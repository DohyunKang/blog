SQLD 모델링 과목에서 관계와 식별자는 거의 매 회차 나오는 단원이고, 용어를 "무엇을 기준으로 나눈 이름인지"로 정리해 두면 보기가 달라져도 풀린다.

## 이 단원에서 나오는 것

엔터티와 속성을 정했으면 그다음은 엔터티끼리 어떻게 이어지는지, 그리고 각 엔터티의 행을 무엇으로 구분하는지다. 앞 단원은 [엔터티와 속성](#/post/sqld-entity-attr)에 있고, 모델링 전체 흐름은 [데이터 모델링의 이해](#/post/sqld-modeling)에 있다.

| 구분 | 기준 | 나오는 용어 |
|---|---|---|
| 관계 | 몇 개가 이어지나 | 1:1, 1:N, M:N (관계 차수) |
| 관계 | 꼭 있어야 하나 | 필수, 선택 (선택성) |
| 관계 | 부모 PK가 자식 PK에 들어가나 | 식별 관계, 비식별 관계 |
| 식별자 | 어떤 역할이냐 | 주식별자, 보조식별자 |
| 식별자 | 어디서 왔냐 | 내부식별자, 외부식별자 |
| 식별자 | 한 컬럼이냐 | 단일, 복합 |
| 식별자 | 원래 있던 거냐 | 본질식별자, 인조식별자 |

시험은 이 표의 각 줄이 "무슨 기준의 분류인지"를 묻는 경우가 많다. 기준만 기억하면 낯선 문장도 풀린다.

## 관계의 기본

관계는 두 엔터티 사이에서 업무상 연결이 있다는 뜻이다. 사원과 부서처럼 "소속된다"는 동사로 읽히면 관계다. 읽는 방향이 둘이라서, 부서 쪽에서는 "부서는 여러 사원을 가진다", 사원 쪽에서는 "사원은 한 부서에 소속된다"로 양쪽에서 문장을 만들어 본다. 한쪽 문장만으로는 차수를 잘못 잡기 쉽다.

### 관계 차수 (몇 개가 이어지나)

- 1:1 : 한쪽 행 하나에 상대 행이 최대 하나
- 1:N : 한쪽 행 하나에 상대 행이 여러 개, 반대로는 최대 하나
- M:N : 양쪽 다 여러 개

ER 도식에서 쓰는 까마귀발 표기는 선 끝에 동그라미는 0, 세로 막대는 1, 갈퀴는 많음을 뜻한다. 각 끝에 기호가 두 개 붙는데 안쪽이 최소, 바깥쪽이 최대다([Wikipedia: Entity–relationship model](https://en.wikipedia.org/wiki/Entity%E2%80%93relationship_model)).

M:N은 물리 테이블로 바로 만들 수 없어서 가운데에 교차(연결) 엔터티를 하나 둬서 1:N 두 개로 푼다. 학생과 수강과목이 M:N이면 "수강" 엔터티를 만들고 학생 PK와 과목 PK를 가져온다. 시험에서 "M:N 관계는 어떻게 해소하나"가 나오면 답은 이 교차 엔터티다.

### 선택성 (꼭 있어야 하나)

차수가 최대 개수라면 선택성은 최소 개수다. 최소가 0이면 선택(optional), 1이면 필수(mandatory)다.

- 사원은 반드시 한 부서에 소속된다 : 사원 쪽 필수
- 부서는 사원이 없어도 만들 수 있다 : 부서 쪽 선택

이 선택성이 나중에 FK 컬럼이 NULL을 허용하느냐로 이어진다. 필수면 FK는 NOT NULL, 선택이면 NULL 허용이다. 아래에서 다시 나온다.

## 관계를 읽는 순서

문제에서 관계 문장이 주어지면 이 순서로 읽는다.

1. 양쪽 방향으로 문장을 만든다.
2. 각 방향의 최대(하나/여러 개)를 적는다 → 차수
3. 각 방향의 최소(없어도 되나/꼭 있나)를 적는다 → 선택성
4. 자식이 부모 없이 존재할 수 있나 → 식별/비식별 판단으로 넘어간다

<details>
<summary>예: 주문과 주문상품</summary>

- 주문 → 주문상품 : 주문은 상품 줄을 여러 개 가진다(최대 N). 줄이 하나도 없는 주문은 없다고 보면 최소 1.
- 주문상품 → 주문 : 상품 줄은 반드시 한 주문에 속한다(최대 1, 최소 1).

그래서 1:N이고 자식 쪽은 필수다. 주문 없이 주문상품 줄만 있을 수는 없으니, 뒤에 나올 식별 관계 후보가 된다. 업무 규칙이 바뀌면 최소 개수도 바뀐다는 점은 기억해 둔다. "주문은 상품 없이도 먼저 만들 수 있다"면 주문 쪽 최소는 0이다.
</details>

## 식별자

식별자는 엔터티 안에서 행 하나를 딱 하나로 가리키는 속성(또는 속성 묶음)이다. 모델링에서는 식별자, 물리 테이블에서는 키라고 부르는 경우가 많고, 시험에서도 이 둘을 같은 흐름으로 다룬다.

### 주식별자의 조건

주식별자가 되려면 보통 다음 네 가지를 만족해야 한다고 정리한다.

| 특성 | 뜻 |
|---|---|
| 유일성 | 행마다 값이 달라야 한다 |
| 최소성 | 꼭 필요한 최소한의 속성만 묶는다 |
| 불변성 | 한 번 정해지면 바뀌지 않는다 |
| 존재성 | NULL이면 안 된다, 반드시 값이 있다 |

특히 불변성이 자주 함정이다. 전화번호나 이메일은 유일해 보여도 바뀔 수 있어서 주식별자 후보로는 불안하다. 최소성은 "이미 유일한데 속성을 더 붙이면 안 된다"로 외운다.

### 분류 기준별로 나눠 보기

- 대표성(주식별자 vs 보조식별자) : 다른 엔터티와 관계를 맺을 때 대표로 쓰이면 주식별자, 행은 구분하지만 대표로는 안 쓰이면 보조식별자다.
- 스스로 생성(내부식별자 vs 외부식별자) : 자기 엔터티 안에서 만들어지면 내부, 다른 엔터티에서 가져온 것이면 외부다.
- 속성 수(단일 vs 복합) : 속성 하나면 단일, 둘 이상이면 복합이다.
- 대체 여부(본질 vs 인조) : 업무에서 원래 쓰이던 것이면 본질, 편의를 위해 새로 만든 것이면 인조다.

<details>
<summary>본질식별자와 인조식별자를 조금 더</summary>

인조식별자는 일련번호처럼 시스템이 만든 값이다. 값이 업무 의미를 갖지 않고 바뀌지 않아서 FK가 한 컬럼으로 끝난다는 장점이 있다. 반면 값에 의미가 없으니 같은 업무 데이터가 중복으로 들어가도 막지 못할 수 있어서, 원래의 업무 키에 유니크 제약을 따로 걸어 두는 경우가 많다. 이 장단점은 surrogate key 설명에서도 같은 방향으로 정리돼 있다([Wikipedia: Surrogate key](https://en.wikipedia.org/wiki/Surrogate_key)).

복합 식별자가 길어지면 자식 테이블로 내려갈수록 PK가 계속 길어진다. 그래서 실무에서는 인조식별자를 두기도 하는데, 시험은 이를 "복합 식별자를 단일 인조식별자로 대체"로 표현한다.
</details>

## 식별 관계와 비식별 관계

이 단원의 핵심이다. 기준은 하나, 부모의 PK가 자식의 PK에 들어가느냐다.

| 구분 | 부모 PK가 자식에서 | 자식의 존재 | ERD 선 |
|---|---|---|---|
| 식별 관계 | 자식 PK의 일부가 된다 | 부모가 있어야 존재 | 실선 |
| 비식별 관계 | 자식의 일반 속성(FK)이 된다 | 부모 없이도 가능 | 점선 |

식별 관계에서는 부모 PK가 자식의 PK 일부로 들어가고, 자식 행은 반드시 부모 하나에 연결된다. 주문과 주문상품이 대표 예시로 쓰인다. 주문상품은 주문번호와 줄번호를 합쳐 PK로 삼고, 주문 없이는 존재할 수 없다([Wikipedia: Weak entity](https://en.wikipedia.org/wiki/Weak_entity)).

```sql
-- 식별 관계: 부모 PK(order_no)가 자식 PK에 포함
CREATE TABLE orders (
  order_no INTEGER PRIMARY KEY,
  memo     TEXT
);
CREATE TABLE order_item (
  order_no INTEGER NOT NULL REFERENCES orders(order_no),
  line_no  INTEGER NOT NULL,
  item     TEXT,
  PRIMARY KEY (order_no, line_no)
);

-- 비식별 관계: 부모 PK(dept_id)는 일반 컬럼으로 FK, NULL 허용 = 선택
CREATE TABLE dept (dept_id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE emp (
  emp_id  INTEGER PRIMARY KEY,
  dept_id INTEGER REFERENCES dept(dept_id),
  name    TEXT
);
```

위 DDL을 SQLite에서 직접 돌려 봤다. 존재하지 않는 주문번호(9)로 `order_item`을 넣으면 외래키 제약 위반으로 막혔고, `dept_id`가 NULL인 사원은 들어갔다. 식별 관계는 부모 없이 자식이 못 생기고, 선택적 비식별 관계는 부모 없는 자식이 가능하다는 말이 그대로 확인된다. (SQLite는 `PRAGMA foreign_keys=ON`을 켜야 외래키를 검사한다.)

### 비식별 관계는 둘로 나뉜다

비식별 관계에서 FK의 NULL 허용 여부로 한 번 더 나눈다.

- 필수적 비식별 : FK가 NOT NULL, 자식은 반드시 부모를 가진다
- 선택적 비식별 : FK가 NULL 허용, 부모 없이도 자식이 있을 수 있다

앞에서 본 선택성이 여기서 FK의 NULL 여부로 바뀐다. 시험에서는 "부모 없이 자식이 생성될 수 있다"는 문장이 나오면 선택적 비식별로 연결하면 된다.

### 어느 쪽으로 정할까

- 부모가 없으면 자식이 의미 없다(주문과 주문상품) : 식별 관계
- 자식이 독립적으로 쓰이고 부모를 참조만 한다(사원과 부서) : 비식별 관계
- 자식이 여러 부모의 PK를 가져오게 되면 PK가 길어지니 비식별로 풀고 인조식별자를 쓰는 선택도 있다

<details>
<summary>식별 관계를 쓸 때 생기는 일</summary>

식별 관계가 여러 단계로 이어지면 맨 아래 엔터티의 PK에 맨 위 부모 PK까지 전부 따라 올라온다. 조인할 때 컬럼을 많이 맞춰야 하고 인덱스도 커진다. 반대로 PK만 봐도 어느 부모 밑의 데이터인지 알 수 있고, 부모 삭제 시 자식이 같이 정리되는 업무에 잘 맞는다. 장단점이 갈리는 지점이라 시험에서는 정답 하나를 묻기보다 "식별 관계의 특징"으로 보기를 구분하게 한다.
</details>

## 자주 나오는 유형

| 유형 | 풀이 방향 |
|---|---|
| 관계 차수 구하기 | 양방향 문장으로 최대 개수를 적는다 |
| M:N 해소 방법 | 교차(연결) 엔터티를 두고 1:N 두 개로 나눈다 |
| 식별자 조건 고르기 | 유일성, 최소성, 불변성, 존재성 네 개와 비교한다 |
| 식별자 분류 구분 | "무슨 기준 분류인지"부터 확인한다(대표성, 생성 위치, 속성 수, 대체 여부) |
| 식별/비식별 판단 | 부모 PK가 자식 PK에 포함되면 식별, 일반 속성이면 비식별 |
| ERD 표기 | 실선/점선, 까마귀발, 동그라미(0)/막대(1) 읽기 |

보기에서 틀린 문장을 고르는 유형은 대체로 용어를 바꿔치기한다. 예를 들면 "비식별 관계에서 부모 PK는 자식 PK의 일부가 된다"처럼 정의를 뒤집는 식이다. 정의를 한 줄씩 말로 외워 두면 걸러진다. 직접 풀어 볼 때는 기출문제 원문을 외우기보다 위 표의 기준을 문장으로 설명해 보는 쪽이 낫다. 시험 일정·응시료는 공식 사이트에서 확인한다.

## 헷갈리기 쉬운 것

- 차수와 선택성은 다르다. 차수는 최대, 선택성은 최소다.
- 식별자와 FK는 다르다. FK는 다른 엔터티를 가리키는 속성이고, 그게 PK의 일부가 되면 식별 관계, 아니면 비식별 관계다.
- 인조식별자를 두면 업무 키는 필요 없다? 아니다. 업무상 유일해야 하는 값은 유니크 제약으로 따로 지킨다.
- 복합 식별자는 속성이 여러 개지만 "최소" 조건은 여전히 적용된다. 빼도 유일하면 불필요한 속성이다.
