LLM は過去の会話を記憶しておらず、まるで記憶しているように見えるのは、アプリが各呼び出しごとにこれまでの履歴をまるごと再送信するためです。

## 簡単な言葉で言うと

ChatGPT や Claude のアプリで続きを話すと、先ほどの話を覚えて答えます。そのため、「モデルの中に会話データが保存されている」と思いがちですが、API ドキュメントを見るとその逆です。Anthropic の Messages API ドキュメントでは、この API を「stateless multi-turn conversations」、つまり状態を保持しない多回対話に使用できると記載されています。OpenAI のドキュメントでも、テキスト生成リクエストはそれぞれ独立しており状態がないと説明しています。

「状態がない」というのは、リクエストが完了するとサーバー側でその会話を保持していないことを意味します。次のリクエストには先頭部分も一緒に送らなければモデルは分かりません。モデルにとっては毎回新しい人であり、先頭に書かれた便箋を受け取って読むのに近いのです。

## 用語から

- **メッセージ**: 1 つの発言。通常 `role`(user, assistant) と内容で構成されます。
- **会話履歴 (history)**: これまでのメッセージのリストです。API では `messages` アレイとして送信します。
- **ターン**: ユーザー 1 回とモデル 1 回を束ねた単位。
- **セッション**: 同じ会話を束ねる一塊のことです。本稿ではアプリが同じ履歴を続けて書き込む範囲として使います。公式な用語で定められた定義ではなく、製品によって意味が少し異なります。
- **コンテキスト**: モデルが一度に確認できる入力全体。履歴はその一部です。[詳しく → コンテキスト](#/post/ai-context)

## 原理：毎回履歴を再送信する

Anthropic ドキュメントにある例は以下の通りです。新しいメッセージを作成する際、以前のターンを `messages` に含めて送ると、モデルが次のメッセージを作成します。

```json
[
  {"role": "user", "content": "Hello there."},
  {"role": "assistant", "content": "Hi, I'm Claude. How can I help you?"},
  {"role": "user", "content": "Can you explain LLMs in plain English?"}
]
```

3 つ目のリクエストを送る際にも、前の 2 つの行も一緒に送られます。モデルが作成した回答 (assistant) もアプリ側で受け取って保存し、再度送信する必要があります。アプリが行う作業を順序立てて書くと以下のようになります。

| 手順 | 行うこと | 誰が |
|---|---|---|
| 1 | ユーザー入力を履歴の末尾に追加する | アプリ |
| 2 | 履歴全体を API に送信する | アプリ |
| 3 | 回答を生成する | モデル |
| 4 | 受信した回答を履歴の末尾に追加して保存する | アプリ |

モデルは手順 3 のみを行います。1、2、4 とどこに保存するかはすべてアプリ側の仕事です。そのため同じモデルであっても、アプリによって記憶の仕方が異なります。

## 実際に動かしてみたもの

本物のモデルではなく、受け取ったメッセージだけを見て回答する偽の関数で構造のみを模倣しました。このコードは Python で直接実行し、以下の結果が得られることを確認しました。

```python
def fake_llm(messages):
    names = [m["content"].split("이름은 ")[1].split("야")[0]
             for m in messages if m["role"] == "user" and "이름은 " in m["content"]]
    last = messages[-1]["content"]
    if "뭐라고" in last:
        return names[-1] if names else "모르겠다"
    return "응"

history = []
def chat(text, keep=True):
    msgs = (history if keep else []) + [{"role": "user", "content": text}]
    reply = fake_llm(msgs)
    if keep:
        history.append({"role": "user", "content": text})
        history.append({"role": "assistant", "content": reply})
    return reply, len(msgs)

print(chat("내 이름은 도현이야"))            # ('응', 1)
print(chat("내 이름 뭐라고 했지?"))          # ('도현이', 3)
print(chat("내 이름 뭐라고 했지?", keep=False))  # ('모르겠다', 1)
```

同じ質問でも履歴を送ると「道賢さん」、送らないと「分からない」と返ってきます。モデルが賢くなったのではなく、入力が異なるだけです。これは構造を示すために作ったおもちゃであり、実際のモデルがどのように回答するかとは無関係です。

## 費用と限界はここから生まれる

毎回すべてを送ることで生じる問題は 2 つあります。

第一に、会話が進むほど 1 つのリクエストの入力トークン数が増加します。OpenAI のドキュメントには、`previous_response_id` で以前のリクエストを接続してもコストが削減されない旨が記載されています。チェーンに含まれる以前の入力トークンはすべて入力で請求されるという説明です。アプリ側で履歴を直接保持するかサーバー側で代わりに保持するかに関わらず、モデルが読み込む量は同じということです。10 番目のターンでのリクエストは、前の 9 つのターンも再度読みます。

第二に、コンテキストウィンドウには上限があります。OpenAI のドキュメントではコンテキストウィンドウを 1 つのリクエストで使用できる最大トークン数としており、入力・出力・推論トークンをすべて合計すると説明しています。これを超えると切断される可能性があります。そのため履歴が長くなると先頭部分を要約したり捨てたりする必要があります。これは次の記事につながります。[詳しく → コンパクションとメモリ](#/post/ai-compaction)

コストを削減する方法として、繰り返される先頭部分のキャッシュがあります。これは別に整理しました。[詳しく → プロンプトキャッシング](#/post/ai-prompt-caching)

## サーバー側で履歴を保持する方式もある

履歴の保管をアプリではなく API 側に任せる選択肢が生まれました。OpenAI ドキュメントを基準にすると 3 つあります。

| 方式 | 履歴を保持する場所 | メモ |
|---|---|---|
| 直接送信 | 自分のアプリ | 最も基本的。何を送るか私が選択します |
| `previous_response_id` | OpenAI サーバー | 以前のリクエスト ID を渡して続けます。デフォルトで 30 日間保持、`store` を false にすると保持しない |
| Conversations API | OpenAI サーバー | 固有 ID を持つ会話オブジェクトとして長期間維持。ドキュメントには 30 日間の制限がないとあります |

サーバー側で持たせてくれるとコードは楽になりますが、モデルに入力されるものが自分で扱うようになり 어려워なります。

## セッションと長期記憶は異なります

履歴は 1 つの会話内でのみ続きます。新しい会話を開くと新しい履歴となり、前の会話は知りません。しかしアプリは時々過去の会話を覚えているように見えます。これは通常、履歴とは異なるストレージを使用しているためです。

Anthropic の Memory Tool ドキュメントが一例です。このツールは、会話間において情報をファイルに保存し、再度読み込むようにします。重要なのは、保存がクライアントサイドで行われることです。ドキュメントの記述によれば、Claude はファイル操作を要求するのみであり、実行は自らのアプリケーションが行い、データは自身が指定したストレージ（ディレクトリ、DB など）に存在します。モデル内に蓄積されるわけではありません。

| | 会話履歴 | 長期記憶 (Memory Tool 等) |
|---|---|---|
| 範囲 | 1 セッション | 複数セッション |
| 場所 | 各リクエストの入力内 | 外部ストレージ、必要な時に読み込んで入力に追加 |
| 送信量 | すべて | 必要なもののみ |
| 管理主体 | アプリ | アプリ (モデルが読み書きするファイル操作を要求) |

ドキュメントで目立ったのは、このツールが有効になっている場合、システムプロンプトに「作業前には常に memory ディレクトリを先に確認せよ」という指示が自動的に付与される点です。コンテキストはいつでも初期化されうることを想定し、進行状況をファイルに記載しておく内容です。セッションが途切れても継続させるための仕組みです。[詳細 → コンテキストウィンドウ](#/post/ai-context-window)

## よくある誤解

- モデルが会話を記憶する: 記憶しているのはアプリから送られた記録です。送らなければ知らないことになります。
- 新しい会話でも私を知っていればモデルが学習した結果: 通常は別ストレージの内容を入力に追加しているものです。製品ごとに方式が異なるため、特定のアプリがどのように動作するかは公開された説明がないと分かりません。
- サーバーが記録を受け取れば無料: 前述の通り、以前のトークンも入力として課金されることは OpenAI のドキュメントにも記載されています。
- 記録が長いほど良い: ウィンドウには上限があり、長ければ必ずしも良く使うわけではありません。
- セッション ID があるからモデルに状態がある: ID はサーバーが記録を探すための鍵に過ぎず、各リクエストでモデルが読むのは結局入力トークンです。

<details>
<summary>詳細な解説：アプリ側でセッションを作成する場合</summary>

直接実装する際に考慮すべき点をまとめると以下のようになります。

- セッション ID を作成し、ID ごとに messages アレイを保存します（メモリ、DB など）。
- 各リクエストでアレイの末尾にユーザー入力を追加し、応答を受け取ったら assistant メッセージも追加します。ツールを使用する場合、ツール要求と結果も一緒に追加されます。
- アレイが長くなると古い部分を要約または切り捨てます。何を残すかは設計次第です。
- ユーザーごとのデータが混ざらないよう、セッション ID とユーザーを紐付けておきます。記録に個人情報が含まれる場合は保存期間も定める必要があります。

OpenAI のドキュメントでは、推論モデルを使用する際、応答の `output` アレイをまるごと再度投入することを推奨しています。推論項目などが途切れないようにするためです。つまり、「assistant の文だけ保存」すればよいケースがあるわけではありません。

</details>
