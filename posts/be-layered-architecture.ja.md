レイヤーアーキテクチャは、コードが担当する役割に応じて層に分け、上位層は下位層のみを呼び出す構造です。バックエンドで最も一般的なコントローラー・サービス・リポジトリの構造がこの形です。

## 何をする構造か

1 つのリクエストが入ってくると、その処理が混在しています。リクエストを読み取り、値が正しいか確認し、ルールを適用し、DB に読み書きを行い、レスポンスを作成します。これを 1 つの関数にすべて詰め込むと最初は速いですが、すぐにぐちゃぐちゃになります。そのため、作業の種類ごとに層に分けます。

| 層 | 担当する仕事 | 一般的な名前 |
|---|---|---|
| プレゼンテーション (Presentation) | HTTP リクエストの受け取り、入力形式の確認、レスポンスの作成 | コントローラー、ルーター、ハンドラー |
| ドメイン (Domain/Business) | ルール・検証・計算、複数の作業を 1 つの単位として束ねる | サービス |
| データアクセス (Data Access) | DB や外部ストレージへの読み書き | リポジトリ、DAO |

Martin Fowler の記事では、これをプレゼンテーション / ドメイン / データアクセスの 3 つの塊に分けています。層は論理的な区別なので、1 つのサーバー内にすべて収めても構いませんし、物理的に分割して動かしても問題ありません。サーバーを分ける話 (tier) とは別の概念です。

## 依存方向が重要である

層に分けたからといってレイヤーになるわけではありません。上から下へしか呼ばないというルールが必要です。

```
컨트롤러 → 서비스 → 리포지토리 → DB
```

コントローラーはサービスを知り、サービスはリポジトリを知ります。逆はできません。リポジトリがコントローラーを呼び出したり、サービスが HTTP リクエストオブジェクトを直接触ったりすると、層に分けた意味がなくなります。サービスに HTTP の概念が混ざると、同じロジックを CLI やバッチ処理では使えなくなります。

Fowler の記事には変形も出てきます。ドメインとデータの間にマッパーを置いて、ドメインがストレージを直接知らないようにする方式で、これがよく「ヘキサゴナルアーキテクチャ」と呼ばれているようです。この記事の図は基本形を中心に説明します。

## なぜ分けるのか

Fowler が挙げる最大の理由は「気にすべき範囲が減る」ことです。ある層を見る際、残りはほぼ無視しても構いません。他にもこのような利点があります。

- テスト: ルールがサービスに集まっていると、HTTP や DB を使わずにルールだけをテストできます。リポジトリの場所に偽装オブジェクトを挿入すると高速です。[詳細 → テスト](#/post/be-testing)
- 置換: 同じサービスを Web、モバイル API、CLI が共同で使用できます。ただし Fowler も実際に DB を差し替えることは稀だと書いています。
- 役割の分離: 入力確認のミス、ルールのミス、クエリのミスをどの層の問題か見つけやすいです。

## サンプルコード

注文を入れる小さな例を Python で書きました。注文合計が限度を超えると拒否するルールです。

```python
import sqlite3
from dataclasses import dataclass

@dataclass
class Order:
    id: int | None
    user_id: int
    amount: int

class OrderRepository:                      # 데이터 접근
    def __init__(self, conn):
        self.conn = conn
    def save(self, o: Order) -> Order:
        cur = self.conn.execute(
            "INSERT INTO orders(user_id, amount) VALUES (?, ?)", (o.user_id, o.amount))
        return Order(cur.lastrowid, o.user_id, o.amount)
    def total_of(self, user_id: int) -> int:
        row = self.conn.execute(
            "SELECT COALESCE(SUM(amount),0) FROM orders WHERE user_id=?", (user_id,)).fetchone()
        return row[0]

class OrderError(Exception):
    pass

class OrderService:                         # 규칙 + 트랜잭션 경계
    LIMIT = 100_000
    def __init__(self, repo, conn):
        self.repo, self.conn = repo, conn
    def place(self, user_id: int, amount: int) -> Order:
        if amount <= 0:
            raise OrderError("amount must be positive")
        with self.conn:                     # 한 트랜잭션
            if self.repo.total_of(user_id) + amount > self.LIMIT:
                raise OrderError("limit exceeded")
            return self.repo.save(Order(None, user_id, amount))

def post_order(service, body: dict):        # 표현: HTTP와 에러 코드만 안다
    try:
        o = service.place(body["user_id"], body["amount"])
        return 201, {"id": o.id}
    except OrderError as e:
        return 400, {"error": str(e)}
```

実際に動かすと、6 万円の注文は `201`、続けて 5 万円の注文は限度超過で `400`、マイナスの金額も `400` が返ってきました。リポジトリの場所にメモリリストで作った偽装オブジェクトを入れてもサービスはそのまま動きました。これが層に分けて得られる利点です。ただし実際の Web フレームワークに付けて動かしたわけではありません。

各層で誰が何を分かっているか整理すると以下のようになります。

| 層 | 知っていること | 知らないこと |
|---|---|---|
| コントローラー | HTTP ステータスコード、リクエスト形式 | SQL、保存方法 |
| サービス | ルール、どのような作業を 1 つの単位として行うか | HTTP、具体的な DB |
| リポジトリ | クエリ、テーブル | なぜこのデータを読むのか |

## トランザクションはどの層に置くか

複数の保存処理を 1 つの単位として処理する必要がある場合、その境界は通常サービスに置きます。リポジトリメソッド 1 つはクエリ 1 つだけを行い、どこまでが 1 つの単位かはルールを知っているサービスが決めるためです。上記例の `with self.conn:` がその場所です。

Spring ドキュメントの例でも `@Transactional` をサービスクラスに付けています。ドキュメントが明示的に「サービス層に置け」と書いているわけではなく、例がそのような形をしているだけです。ドキュメントで明確に書かれているのは、インターフェースではなく具体的なクラスにアノテーションを付けることです。AspectJ モードでは、インターフェースに付けたアノテーションは認識されず、ロールバックテストを行うまで正常に見えていて静かに無視されてしまう可能性があるそうです。

## いつ過剰か

レイヤーが常に良いわけではありません。

- サービスがコントローラーから受け取ったものをリポジトリにそのまま渡すだけの場合があります。ルールがないのに層があるだけでコードが増え、ファイルを行き来するだけになります。小さな CRUD アプリでよく見られるようです。
- 各層ごとに同じデータを格納するオブジェクト (DTO, エンティティ) を別々に作り、毎回転送するとボイラープレートが増えます。
- ルールがすべてサービスに集まり、ドメインオブジェクトはフィールドしか持っていない構造を「貧弱なドメインモデル (anemic domain model)」と呼びます。この用語は Fowler が書いた記事で知られています。

Fowler の記事では過剰な層について直接警告していませんが、成長するシステムでレイヤーを上位分類として使うと問題になるため、ドメインごとに分け、その中で層を置くよう勧められています。また、開発チームを層別に分ける (フロントエンドチーム、バックエンドチーム、DB チーム) のはアンチパターンであると書いています。

基準を一つ定めれば、ルールが何行あってもサービス層を置き、ルールがまったくない読み取り専用 API ならレイヤーを減らしてもよいと考えます。これは私の判断であり、出典のある話ではありません。

## よくある誤解

- レイヤーが多いほど良い: レイヤーは作業が区別される際に意味があります。空のレイヤーはコストです。
- レイヤーはサーバー台数だ: レイヤーはコードの論理的な区切りであり、サーバー台数 (tier) とは別の話です。
- コントローラーにルールを書いても動くので問題ない: 動くのは事実ですが、同じルールを他のエントリーポイント (バッチ処理、キューコンシューマーなど) でも再度書く必要があります。
- リポジトリはテーブルごとに一つだ: よくそう使われますが、それはルールではありません。束単位 (例：注文と注文項目) にすることもあります。

<details>
<summary>詳しい解説: 一回の要求がレイヤーを通過する順序</summary>

1. コントローラーが JSON の本文を読み込み、必須フィールドがあるか、型が正しいかを確認します。間違っていれば 400 です。
2. サービスを呼び出します。サービスは金額が正の数か、限度を超えていないかなどルールの確認を行います。ルール違反は例外として投げます。
3. サービスがトランザクションを開き、リポジトリから合計を読み込み保存します。
4. 例外が発生すればトランザクションがロールバックされ、コントローラーが例外の種類に応じたステータスコードに変換して応答します。

ここで例外を HTTP コードに変換する作業はプレゼンテーション層の役割とします。サービスが `400` を直接言うことで、サービスが HTTP を理解することになります。エラー処理の方法は別途整理します。[詳細 → エラー処理とロギング](#/post/be-error-logging)

</details>
