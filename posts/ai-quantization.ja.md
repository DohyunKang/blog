大きなモデルを自分の PC で動かすには、まずメモリに読み込まなければなりません。そのため、サイズを小さくする方法は主に 2 つあります。量子化とは、同じモデルの重み（パラメータ）をより少ないビットで保存することであり、蒸留とは、大きなモデルの振る舞いを小さなモデルに教えることです。名前が似ているためいつも混同していましたが、削減の対象は異なります。

## モデルはどれだけのメモリを使うのか

[LLM](#/post/ai-llm) のサイズはパラメータ（重み）の数で表されます。「8B」は 80 億個を意味します。この数字のそれぞれがメモリ上で占める大きさは、精度によって異なります。

```
가중치 메모리 ≈ 파라미터 수 × 숫자 하나의 바이트 수
```

| 精度 | 1 つの数字 | 8B モデル | 70B モデル |
|---|---|---|---|
| FP16 / bf16 | 2 バイト | 約 16GB | 約 140GB |
| 8 ビット | 1 バイト | 約 8GB | 約 70GB |
| 4 ビット | 0.5 バイト | 約 4GB | 約 35GB |

Hugging Face の量子化ドキュメントでも、8B モデルが bf16 で約 16GB、8 ビットで約 8GB、4 ビットで 4〜5GB と記載されています。4 ビットが正確に 4GB ではなく 4〜5GB なのは、スケール値などの追加情報が付くためです（表の 70B の欄は上記計算式をそのまま掛けた値です）。

## 量子化：数字を粗く保存する

量子化とは、重みを少ないビットで保存してメモリを削減する方法です。ドキュメントの説明では、重みだけでなく場合によってはアクティブな値（活性化値）も少ないビットで保存し、モデルが必要とするメモリ量を減らします。その代わり、ビット数が少なくなると精度が若干低下し、手法ごとにメモリ・速度・精度のバランスが異なります。

わかりやすい例えをすると、写真の容量を削減することと似ています。元の画像の細かい値に近い目盛りで丸めて保存すると容量が減りますが、目盛りが粗いほど元の画像との差が大きくなります。その差が品質の低下です。

<details>
<summary>詳しい解説：丸める目盛りの例（自作の単純な例）</summary>

重みが 0.37 としましょう。8 ビットで保存すると、256 つの目盛りの中で近いものに保存します。4 ビットでは目盛りが 16 つしかないため、より遠い目盛りへ丸められる可能性があります。実際の方式は、値のグループごとにスケール（目盛りの間隔）を別途設定する仕組みであり、この例よりも洗練されています。どのグループサイズでスケールを設定するかといった区切り方は、Hugging Face の量子化概念ガイドに記載されています。

</details>

### 名前の意味は何なのか

量子化について読むと、GGUF や GPTQ、AWQ などの名前が飛び交います。これらは同じ階層の名前ではなく、混在しています。

| 名前 | 正体 |
|---|---|
| GGUF | ファイル形式。重み・設定・トークナイザーを 1 つのファイルに格納します（HF ドキュメント）。llama.cpp シリーズで使用されます |
| GPTQ | 量子化手法（論文）。2 次情報を近似して精度を保ちながら一度に量子化します |
| AWQ | 量子化手法（論文）。重みだけを削減する低ビット方式であり、重要な重みの約 1% を保護します |
| bitsandbytes | ロード時に 4 ビット・8 ビットに変換してくれるライブラリ。HF ドキュメントの例に出ています |
| Q4_K_M などの名前 | GGUF ファイル名に付く量子化種類の表示。HF ドキュメントの例示ファイル名にあります |

つまり、「GGUF か GPTQ か」は完全に同じ選択肢ではありません。GGUF は入れる容器であり、GPTQ や AWQ は削減するアルゴリズムの名前です。

### GPTQ と AWQ が行ったこと

GPTQ の論文（Frantar ら、2022, arXiv 2210.17323）は、GPT シリーズモデルを一度に量子化する手法です。緑色のテキストによると、重みを 3〜4 ビットに削減しても元のモデルに対する精度低下はほとんどなく、1750 億パラメータのモデルを約 4 GPU 時間で量子化でき、そのモデルを 1 つの GPU で生成推論できるようになりました。FP16  대비 の速度向上は A100 で約 3.25 倍、A6000 で約 4.5 倍であると言われています。

AWQ の論文（Lin ら、2023, arXiv 2306.00978）の観察点は、すべての重みが同じように重要ではないということです。重要なチャンネルの約 1% を守っておけば量子化誤差を大きく減らし、どのチャンネルが重要かは重みの大きさではなくアクティブな値の統計から見出します。逆伝播や再構築が必要ない点も緑色のテキストにあります。

両方の手法とも「どのように丸めれば損失が少ないか」を解く側です。HF ドキュメントには GPTQ のみがロード中に補正用データセットが必要であり、それ以外は不要と記載されています。

### 品質の低下はどれくらいか

手法・モデル・ビット数によって異なります。GPTQ の論文では 3〜4 ビットで低下がほとんどなかったと述べられ、2 ビットや 3 値レベルでも使える程度の精度を示しましたが、これはすべてのモデルでそうであるという意味ではありません。使うモデルが決まっていれば、自分の作業で直接比較するのが適切です。性能比較の基準は [AI モデルマップ](#/post/ai-models) などの場所でまず確認できます。

## 蒸留：大きなモデルが小さなモデルを教える

蒸留は、サイズを縮小する方法が異なります。数字を粗く保存するのではなく、大きなモデルの出力を見て学習し、小さなモデルを新たに訓練します。大きな方を「先生（teacher）」、小さな方を「学生（student）」と呼びます。

Hinton 他による論文 "Distilling the Knowledge in a Neural Network"(2015, arXiv 1503.02531) の要約は次のように始まります。「同じデータで複数のモデルを学習させ、予測結果を平均化するアンサンブルは性能向上の簡単な方法ですが、デプロイには重く高価です。そのアンサンブルの知識を一つのモデルに圧縮する方法を開発した」という内容です。「先生・学生」という用語は要約には出ておらず、この記事で用いる用語です。

結果物は、パラメータ数が最初から少ない別のモデルです。そのため元のモデルとは重みが異なり、名前も別々に付けられます。大きなモデルと小さなモデルのシリーズが同時に登場している様子を見ると、そのような方法で作られたものもあるように思えますが、どのモデルが蒸留によって作られたかは、各モデルの公開資料を確認する必要があります。

## 量子化 vs 蒸留

| | 量子化 | 蒸留 |
|---|---|---|
| やること | 同じモデルの数字を少ないビットで保存 | 大きなモデルの出力を使って小さなモデルを学習 |
| モデル構造 | そのまま | 新しい小さな構造を作成 |
| 追加学習 | ほぼなし (GPTQ は補正データを使用) | 必要 |
| 減らすもの | 数字ごとのビット数 | パラメータ数 |
| 損失 | 丸め誤差 | 学生が追いつけない部分 |
| 私がやること | 既に量子化されたファイルを受け取って使うことが多い | 通常はモデル製作者が行う |

両方を併用することもできます。蒸留によって小さく作ったモデルを再度 4 ビットで量子化すると、両方の効果が重なります。

LoRA などの [ファインチューニング](#/post/ai-finetuning) とは異なります。ファインチューニングは振る舞いを変える方であり、量子化・蒸留はサイズを縮小させる方です。

## ローカルで動かすツール

- llama.cpp: C/C++ で作成されたオープンソースの推論プロジェクトです。README には 1.5 ビットから 8 ビットまでの整数量子化をサポートし、CPU と GPU を組み合わせて VRAM よりも大きなモデルの一部を加速できると記載されています。CUDA、Metal、Vulkan、HIP など複数のバックエンドをサポートします。Hugging Face モデルは `-hf` オプションでそのまま受け取り実行でき、OpenAI 互換 API サーバーも起動できるそうです。
- Ollama: 一行のコマンド (`ollama run <モデル>`) でモデルを受け取り対話させ、`localhost:11434` に REST API も公開します。llama.cpp をサポートするバックエンドとして使用します。
- Hugging Face Transformers: `from_pretrained` に量子化設定を渡すとロード時に量子化され、既に量子化されたチェックポイントは設定から方法を自動的に読み込んでロードします。このドキュメントの基準では 20 種類以上の方法を同じコードで扱います。ただし GGUF はほとんどがロード中に元の精度に解像されるため、メモリ上の利得はないとドキュメントに記載されているので、GGUF は llama.cpp シリーズを使う方が自然です。

<details>
<summary>詳しい解説：Transformers ロードの例（ドキュメントの例を転載）</summary>

実際に実行したコードではなく、Hugging Face ドキュメントの例を転載したものです。8B モデルを bitsandbytes で 4 ビットでロードする形式です。

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=quantization_config,
    device_map="auto",
)
```

</details>

## 自分の GPU に収まるか判断する方法

手順は簡単です。

1. モデルのパラメータ数を確認します（名前などに 8B、70B のように付いています）。
2. ビット数に合わせて掛けます。4 ビットならパラメータ (B) × 約 0.5GB、8 ビットなら × 1GB、FP16 なら × 2GB。
3. この値が自分の VRAM よりも十分に小さいか確認します。

8B を 4 ビットにすると約 4〜5GB なので、VRAM 8GB のカードでも候補になります。70B は 4 ビットでも約 35GB なので、24GB のカード一枚では重みだけでも不足します。このような場合、llama.cpp の CPU+GPU 混合実行が選択肢になりますが、ドキュメントにはこれを一部加速するとしか書かれておらず、速度は記載されていません。

余裕を持たせる必要があるのは、重み以外にもメモリを使うためです。HF ドキュメントでは長い生成において KV キャッシュのメモリを節約する量子化キャッシュオプションについて別に言及しています。対話が進むほど [コンテキストウィンドウ](#/post/ai-context-window) 分だけキャッシュが大きくなるということです。そのため、重みが VRAM にぴったり合うサイズよりも、一段階小さいモデル・ビットを選ぶ方が安全です。同じドキュメントには、ハードウェアメモリにモデルが精度別に入っているか確認できる量子化選択の Space もリンクされています。

## よくある誤解

- 量子化するとモデルが賢くなる：むしろ、精度は若干低下する方向です。ドキュメントでもビット数を減らすと精度コストがある旨が記載されています。
- 4 ビットなら品質が半減する：GPTQ の論文の要約では、3〜4 ビットで劣化はほとんどないとされています。モデルやタスクによって異なるため、実際に確認するのが適切です。
- GGUF は量子化手法である：ファイル形式です。ファイル名の「Q4_K_M」のような部分は量子化の種類を示します。
- 量子化と蒸留は同じ言葉である：上記の表のように、削減対象が異なります。
- 量子化されたモデルではファインチューニングができない：HF のドキュメントには、手法ごとのファインチューニング対応の有無を比較する表があると記載されています。手法によって異なります。
- ローカルで大きなモデルは必ずしも遅いわけではない：速度はハードウェアと量子化方式によって異なります。GPTQ の論文では FP16 に比べて 3 倍以上高速化したケースも報告されており、ただしこれは GPU 環境での結果です。
