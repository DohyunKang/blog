정보처리기사에서 소프트웨어 아키텍처 단원은 크게 두 덩어리다. 시스템 전체를 어떤 모양으로 나눌지(아키텍처 패턴)와 나눈 조각이 얼마나 잘 나뉘었는지(모듈화, 결합도·응집도). 앞쪽은 이름과 특징을 짝지어 두는 단원이고, 뒤쪽은 순서를 외우는 단원이다. 기출 문제는 옮기지 않고, 어떤 형태로 나오는지와 풀 때 보는 기준만 정리한다.

## 아키텍처가 뭔지

아키텍처는 시스템을 어떤 요소로 나누고, 그 요소들이 서로 어떻게 연결되는지를 정한 큰 틀이다. 코드 한 줄보다 먼저 정해지고, 나중에 바꾸기 비싸다. 그래서 요구사항 중 성능·보안·유지보수 같은 비기능 요구가 이 단계에서 정해진다고 보면 된다. 요구사항을 어떻게 뽑는지는 [자세히 → 요구사항 확인과 분석](#/post/jb-requirements)에서 따로 다룬다.

Microsoft의 Azure 아키텍처 가이드는 아키텍처 스타일을 "특정한 특징을 공유하는 아키텍처의 한 계열"이라고 설명한다. 스타일은 설계에 제약을 건다. 어떤 요소가 있을 수 있고 요소끼리 어떤 관계가 허용되는지를 정해 두는 식이다. 제약을 지키면 그 스타일에서 기대하는 장점이 따라온다는 것이다. 패턴 이름을 외울 때도 "이 패턴은 어떤 제약을 거나"를 같이 보면 덜 헷갈린다.

## 아키텍처 패턴 정리

| 패턴 | 핵심 구조 | 한 줄 특징 |
|---|---|---|
| 계층형(Layered, N-tier) | 프레젠테이션 → 비즈니스 → 데이터 접근 | 각 층은 아래 층만 호출한다 |
| MVC | Model / View / Controller | 데이터·화면·입력 처리를 분리한다 |
| 파이프-필터 | 필터가 파이프로 연결 | 앞 단계 출력이 다음 단계 입력이다 |
| 클라이언트-서버 | 요청하는 쪽과 응답하는 쪽 | 서버가 자원을 갖고 클라이언트가 요청한다 |
| 이벤트 기반 | 생산자 → 이벤트 채널·브로커 → 소비자 | 생산자와 소비자가 서로를 모른다 |
| 마이크로서비스 | 작은 독립 서비스 여러 개 | 서비스마다 자기 데이터를 갖고 따로 배포한다 |

표의 설명은 각 패턴의 Wikipedia 항목과 Azure 아키텍처 가이드에서 확인한 내용을 바탕으로 했다. 아래는 하나씩 조금 더 본다.

### 계층형

Azure 가이드 기준으로 N-tier는 애플리케이션을 논리적 계층과 물리적 티어로 나누고, 각 계층은 자기 아래 계층만 호출하는 전통적인 엔터프라이즈 구조다. 보통 프레젠테이션, 비즈니스 로직, 데이터 접근 계층이 나온다. 이미 계층형으로 만든 앱을 옮길 때 변경이 적다는 장점이 있고, 수평으로 나눠서 변경이 여러 부분에 걸치기 쉽다는 단점도 같은 문서에 적혀 있다. 실제 코드에서 계층을 어떻게 나누는지는 [자세히 → 레이어드 아키텍처](#/post/be-layered-architecture)에 있다.

### MVC

Wikipedia 설명으로는 사용자 인터페이스를 위한 패턴이고, 프로그램 논리를 세 부분으로 나눈다.

- Model: 애플리케이션의 데이터와 그에 대한 규칙. 화면과 무관하다.
- View: 정보를 보여 주는 부분. 같은 데이터를 여러 View가 보여 줄 수 있다.
- Controller: 사용자 입력을 받아 Model이나 View에 명령으로 바꿔 전달한다.

MVC는 1970년대 후반 Xerox PARC에서 Trygve Reenskaug가 Smalltalk 작업 중에 만들었다. 시험에서는 "입력은 Controller, 데이터는 Model, 화면은 View" 이 대응만 정확하면 대부분 풀린다. MVP, MVVM은 MVC에서 갈라져 나온 변형으로 알려져 있다. 이름이 선택지에 같이 나오는 경우를 대비해 MVC의 세 역할부터 확실히 해 두면 된다.

### 파이프-필터

처리 단계가 순서대로 이어지고 앞 단계의 출력이 다음 단계의 입력이 되는 구조다. 단계는 필터, 연결은 파이프라고 부르고, 파이프에는 보통 약간의 버퍼링이 들어간다. 단순하고 비용이 적게 들지만 탄력성·장애 허용·확장성은 제한적이라는 평가가 Wikipedia에 있다. 리눅스에서 명령을 `|`로 이어 붙이는 모양을 떠올리면 기억하기 쉽다.

### 클라이언트-서버

서버가 기능이나 자원을 제공하고 클라이언트가 요청을 보내는 구조다. 웹 브라우저와 웹 서버가 가장 흔한 예다. 서버가 여러 클라이언트를 상대하므로, 서버 쪽 부하와 장애가 전체에 영향을 주는 점을 같이 생각해 두면 서술형 선택지에서 도움이 된다.

### 이벤트 기반

Azure 가이드에서는 발행-구독 모델을 쓴다고 설명한다. 이벤트 생산자는 소비자가 누군지 모르고 이벤트를 만들고, 소비자는 자기가 관심 있는 이벤트에 반응한다. 둘 사이는 이벤트 채널이나 브로커가 이어 준다. 생산자와 소비자의 직접 의존이 사라지는 대신 전달 보장, 이벤트 순서, 결과적 일관성이 어려운 점으로 꼽힌다.

### 마이크로서비스

애플리케이션을 작고 독립적인 서비스 모음으로 쪼갠다. 서비스 하나는 하나의 비즈니스 기능을 맡고 자기 데이터 저장소를 갖는다. API로 서로 통신하고, 개발·배포·확장을 서비스별로 따로 할 수 있다. 반면 서비스 탐색, 데이터 일관성, 분산 시스템 관리가 복잡해진다고 Azure 가이드는 짚는다. 작은 앱에 무조건 맞는 방식은 아니다.

## 패턴을 고르는 기준

| 상황 | 어울리는 쪽 |
|---|---|
| 이미 계층형으로 만든 업무 시스템을 옮김 | 계층형 |
| 화면과 데이터 로직을 나누고 싶음 | MVC |
| 데이터를 단계별로 변환 | 파이프-필터 |
| 실시간 처리, 느슨한 연결 | 이벤트 기반 |
| 복잡한 도메인에 변경이 잦음 | 마이크로서비스 |

Azure 가이드 표에서도 N-tier는 "전통적인 비즈니스 도메인, 갱신 빈도 낮음", 마이크로서비스는 "복잡한 도메인, 잦은 갱신", 이벤트 기반은 IoT·실시간 시스템에 맞는 것으로 정리되어 있다. 같은 문서가 순수한 구조를 좇기보다 제약을 조금 풀어 현실에 맞추는 편이 낫다고도 적고 있다.

## 모듈화와 결합도·응집도

모듈화는 시스템을 기능 단위로 나누는 일이다. 나누는 기준이 결합도와 응집도다. 결합도는 모듈 사이가 얼마나 얽혀 있는지, 응집도는 모듈 안의 요소가 얼마나 한 가지 일로 모여 있는지다. 좋은 설계는 결합도는 낮게, 응집도는 높게 가져간다. Wikipedia는 높은 응집도가 느슨한 결합과 같이 가는 경향이 있다고 설명한다.

개념 설명은 [자세히 → 결합도와 응집도](#/post/be-coupling-cohesion)에도 있고, 여기서는 시험용으로 순서만 고정한다.

### 결합도 (높음 → 낮음)

| 순서 | 종류 | 의미 |
|---|---|---|
| 1 | 내용 | 다른 모듈의 내부 코드나 분기를 직접 사용한다 |
| 2 | 공통 | 여러 모듈이 같은 전역 데이터를 쓴다 |
| 3 | 외부 | 외부에서 정해진 데이터 형식·통신 규약·장치 인터페이스를 공유한다 |
| 4 | 제어 | 다른 모듈의 흐름을 제어하는 값(플래그 등)을 넘긴다 |
| 5 | 스탬프 | 복합 자료구조를 공유하지만 일부만 쓴다 |
| 6 | 자료 | 매개변수로 기본 데이터만 주고받는다 |

위 순서와 정의는 Wikipedia의 Coupling 항목에서 "가장 높은 결합부터 낮은 결합까지"로 나열한 것을 따랐다. 가장 바람직한 건 자료 결합이다.

### 응집도 (높음 → 낮음)

| 순서 | 종류 | 묶인 이유 |
|---|---|---|
| 1 | 기능 | 모든 요소가 하나의 잘 정의된 작업에 기여한다 |
| 2 | 순차 | 한 요소의 출력이 다음 요소의 입력이다 |
| 3 | 통신(정보) | 같은 데이터를 다룬다 |
| 4 | 절차 | 정해진 실행 순서를 따른다 |
| 5 | 시간 | 프로그램의 같은 시점에 실행된다 |
| 6 | 논리 | 같은 범주지만 하는 일은 서로 다르다 |
| 7 | 우연 | 특별한 이유 없이 모여 있다 |

Wikipedia의 Cohesion 항목이 기능 응집을 가장 좋은 쪽으로 두고 우연 응집을 가장 낮은 쪽으로 둔다. 같은 항목에 이 순위가 꾸준한 개선 단계를 뜻하지는 않는다는 말도 있다.

<details>
<summary>순서를 외우는 방법</summary>

첫 글자를 이어 붙이면 외우기 쉽다. 결합도는 내·공·외·제·스·자, 응집도는 기·순·통·절·시·논·우 순서다. 두 표는 방향이 반대라서, 결합도는 나쁜 것부터, 응집도는 좋은 것부터 적었다고 따로 한 번 적어 두면 덜 헷갈린다.

</details>

## 자주 나오는 유형과 풀이

- 패턴 이름 고르기: 보기에 "데이터·화면·입력 분리", "앞 출력이 다음 입력", "아래 층만 호출" 같은 특징이 한 줄로 나온다. 위 표의 한 줄 특징과 대응시켜 푼다.
- 결합도·응집도 순서: 가장 낮은 결합도는 무엇인지, 가장 높은 응집도는 무엇인지 묻는다. 양 끝만 정확히 알아도 풀린다. 결합도는 자료, 응집도는 기능이 좋은 쪽이다.
- 상황 보고 종류 맞추기: "두 모듈이 같은 전역 변수를 쓴다"는 공통 결합, "한 모듈이 플래그를 넘겨 다른 모듈의 동작을 바꾼다"는 제어 결합처럼 설명을 보고 이름을 고른다. 결합도 표의 의미 칸을 외우면 된다.
- 설계 원칙 짝짓기: 낮은 결합·높은 응집이 왜 좋은지 묻는 문장이 나온다. 한 모듈을 바꿀 때 같이 고칠 곳이 줄어든다는 쪽으로 읽으면 대체로 맞다.

패턴 단원은 이름만 외우면 헷갈려서, 위처럼 한 줄 특징과 같이 묶어 두는 쪽이 빨랐다.

## 흔한 오해

- 결합도는 무조건 0이어야 한다: 모듈이 서로 아무것도 주고받지 않으면 시스템이 되지 않는다. 약한 연결로 줄이는 것이 목표다.
- 마이크로서비스가 계층형보다 항상 낫다: Azure 가이드도 복잡한 도메인에 잦은 변경이 있을 때 어울리고, 운영 성숙도가 필요하다고 적는다.
- MVC는 웹에서만 쓴다: MVC는 사용자 인터페이스를 위한 패턴으로 설명되고, 웹 프레임워크에서 흔히 쓰일 뿐이다.
- 응집도가 높으면 모듈이 작다: 크기와는 별개다. 한 가지 일을 하면 줄 수가 많아도 응집도가 높다.
