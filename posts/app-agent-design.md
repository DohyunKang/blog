에이전트 설계의 출발점은 "에이전트를 만들까"가 아니라 "LLM 호출 한 번으로 되나, 안 되면 어디까지 정해 두고 어디부터 모델에게 맡기나"였다.

## 워크플로우와 에이전트

Anthropic의 "Building effective agents"는 둘을 이렇게 나눈다.

- 워크플로우: LLM과 도구가 미리 정해진 코드 경로로 엮인 것. 다음에 뭘 할지는 코드가 정한다.
- 에이전트: LLM이 스스로 과정과 도구 사용을 정하고, 일을 어떻게 끝낼지 통제권을 갖는 것.

둘을 묶어 "에이전틱 시스템"이라고 부른다. 에이전트 하나로 다 해결한다기보다, 이 스펙트럼 어디쯤에 놓을지 고르는 문제에 가깝다. 에이전트 루프 자체는 [자세히 → 에이전트와 에이전트 루프](#/post/ai-agent-loop)에 따로 적었다.

글이 제일 먼저 말하는 건 단순함이다. 가장 단순한 해법을 찾고, 결과가 확실히 좋아질 때만 복잡도를 더하라고 한다. 이유는 비용이다. 에이전틱 시스템은 지연과 비용을 내고 성능을 사는 거래라서, 그 거래가 값어치를 해야 한다. 많은 경우 검색과 예시를 붙인 LLM 호출 한 번이면 충분하다고도 적혀 있다.

## 바탕이 되는 부품: 증강된 LLM

패턴들의 공통 부품은 검색, 도구, 메모리가 붙은 LLM이다. 모델이 직접 검색어를 만들고, 쓸 도구를 고르고, 무엇을 기억할지 정한다. 도구 연결 방식으로는 MCP가 예로 나온다. 도구를 부르는 쪽은 [자세히 → 도구 호출](#/post/ai-tool-use)에서 다뤘다.

## 워크플로우 패턴 다섯 가지

한 번에 보면 이렇다.

| 패턴 | 한 줄 설명 | 잘 맞는 경우 | 대가 |
|---|---|---|---|
| 프롬프트 체이닝 | 단계를 나눠 앞 출력을 뒤 입력으로 | 고정된 하위 작업으로 깔끔히 쪼개질 때 | 지연이 늘어남 |
| 라우팅 | 입력을 분류해 전문 갈래로 보냄 | 입력 종류가 뚜렷이 갈리고 분류가 정확할 때 | 분류가 틀리면 전체가 틀어짐 |
| 병렬화 | 동시에 여러 호출하고 코드로 합침 | 속도가 필요하거나 여러 관점이 필요할 때 | 호출 수만큼 비용 |
| 오케스트레이터-워커 | 중앙 LLM이 작업을 쪼개 워커에 맡기고 종합 | 하위 작업을 미리 알 수 없을 때 | 비용·복잡도 |
| 평가-개선 | 생성 LLM과 평가 LLM이 반복 | 평가 기준이 분명하고 고칠수록 좋아질 때 | 반복 횟수만큼 비용 |

### 체이닝

작업을 순서대로 나눈다. 개요를 쓰고, 기준에 맞는지 확인하고, 본문을 쓴다. 중간에 코드로 된 검문소(gate)를 두면 개요 단계에서 틀어진 걸 거기서 잡는다. 문서의 예는 마케팅 문구를 쓰고 번역하는 것, 개요를 검사한 뒤 본문을 쓰는 것이다. 한 번에 다 시키는 것보다 각 호출이 쉬워지니 정확도가 오르고, 대신 느려진다.

### 라우팅

입력을 먼저 분류하고 갈래별 프롬프트나 모델로 보낸다. 고객 문의를 일반·환불·기술로 나누는 게 문서의 예다. 쉬운 질문은 작은 모델, 어려운 질문은 큰 모델로 보내는 용도도 나온다. 원가를 줄이는 쪽으로 쓰기 좋아 보여서 [자세히 → AI 서비스 원가 구조](#/post/app-cost)와 같이 읽을 만하다.

### 병렬화

두 가지 변형이 있다. 구획 나누기(sectioning)는 서로 독립인 하위 작업을 동시에 돌린다. 예컨대 한 모델이 답하는 동안 다른 모델이 입력을 검열한다. 투표(voting)는 같은 일을 여러 번 시켜 다수결로 정한다. 코드 취약점을 여러 프롬프트로 검토해서 한 번이라도 걸리면 표시하는 식이다. 한 호출에 여러 고려 사항을 몰아넣는 것보다 고려 사항마다 호출을 따로 하는 게 보통 낫다고 한다.

### 오케스트레이터-워커

병렬화와 겉모습은 비슷한데, 하위 작업이 입력에 따라 그때그때 정해진다는 점이 다르다. 여러 파일을 고쳐야 하는 코딩이 대표 예다. 어느 파일을 건드릴지는 요청을 읽어야 알 수 있다. 중앙 모델이 쪼개고 워커 모델이 하고 결과를 합친다. 모델 여러 개가 역할을 나눠 갖는 쪽은 [자세히 → 서브에이전트와 멀티에이전트](#/post/ai-subagent)에서 이어진다.

### 평가-개선

한 모델이 쓰고 다른 모델이 평가해서 피드백을 주고, 통과할 때까지 돈다. 문학 번역에서 평가 모델이 놓친 뉘앙스를 지적하는 게 문서의 예다. 조건이 두 개 붙는다. 평가 기준이 분명해야 하고, 피드백을 받으면 실제로 결과가 나아져야 한다. 둘 중 하나가 안 되면 돌기만 하고 좋아지지 않는다. 평가를 어떻게 설계하는지는 [자세히 → LLM 앱 평가](#/post/app-eval)에 이어진다.

## 에이전트는 언제

에이전트는 단계 수를 예측할 수 없어서 경로를 미리 못 박을 수 없는 열린 문제에 쓴다. 사람 명령이나 대화로 시작해서 계획을 세우고, 단계마다 도구 결과나 코드 실행 같은 현실의 사실(ground truth)을 받아 보며 나아간다. 막히거나 체크포인트에서는 사람에게 확인한다. 끝나는 조건과 별개로 최대 반복 횟수 같은 상한을 두는 게 통제에 필요하다고 한다.

구현은 의외로 단순하다. 환경의 피드백을 받으며 도구를 루프로 쓰는 LLM이 전부고, 그래서 도구 설계가 핵심이 된다. 문서는 에이전트가 잘 맞는 곳으로 두 가지를 든다. 고객 지원(대화와 행동이 섞이고, 해결 여부로 성공을 잴 수 있다), 코딩(테스트로 결과를 검증할 수 있다). 공통점은 성공 기준이 분명하고 피드백 고리가 있다는 것이다. 반대로 비용이 높고 오류가 누적될 수 있어서 샌드박스에서 충분히 시험하고 가드레일을 두라고 한다. 가드레일은 [자세히 → 가드레일과 안전장치](#/post/app-guardrails)에서 따로 다룬다.

## 도구 설계가 프롬프트만큼 중요하다

문서의 부록이 의외로 길게 쓴 부분이다. 사람용 인터페이스(HCI)에 쓰는 만큼의 노력을 에이전트-컴퓨터 인터페이스(ACI)에도 쓰라는 얘기다.

- 도구 설명은 신입 개발자에게 주는 docstring처럼 쓴다. 사용 예, 경계 사례, 비슷한 도구와의 차이를 넣는다.
- 모델이 만들기 어려운 형식을 피한다. diff는 줄 수를 미리 세야 하고, JSON 안의 코드는 이스케이프 부담이 있다.
- 실제 입력을 많이 돌려 보고 실수를 찾아 고친다.
- 실수하기 어렵게 인자를 바꾼다(poka-yoke). SWE-bench 에이전트는 디렉터리를 옮긴 뒤 상대 경로에서 실수가 잦았는데, 절대 경로를 요구하자 사라졌다고 한다. 프롬프트보다 도구 다듬는 데 시간을 더 썼다는 대목도 있다.

## 프레임워크에 대해

Claude Agent SDK 같은 프레임워크는 호출, 도구 정의, 체이닝을 편하게 해 준다. 대신 추상화 층이 프롬프트와 응답을 가려 디버깅이 어려워지고, 필요 없는 복잡도를 끌어들이기 쉽다. 문서의 조언은 처음엔 API를 직접 쓰고, 프레임워크를 쓰면 안에서 뭘 하는지 이해하라는 것이다. 같은 취지로 프레임워크 바깥의 모델 둘레 코드를 가리키는 말이 [자세히 → 하네스와 하네스 엔지니어링](#/post/ai-harness)이다.

## 직접 돌려 본 최소 코드

다섯 구조가 코드로는 얼마나 작은지 보려고 가짜 LLM 함수(`llm`)로 뼈대만 짰다. 실제 모델 호출은 없고, 흐름을 확인하는 용도다.

```python
from concurrent.futures import ThreadPoolExecutor

def llm(prompt: str) -> str:
    """가짜 LLM. 실제로는 API 호출 한 번이 들어갈 자리."""
    if prompt.startswith("분류:"):
        return "환불" if "환불" in prompt else "일반"
    if prompt.startswith("평가:"):
        return "OK" if "근거" in prompt else "근거를 추가해라"
    if prompt.startswith("개선:"):
        return prompt[3:] + " (근거 추가)"
    return f"[{prompt[:20]}...에 대한 답]"

# 1) 체이닝: 앞 출력이 뒤 입력
def chain(topic):
    outline = llm(f"개요: {topic}")
    if len(outline) < 5:            # 게이트
        raise ValueError("개요가 너무 짧다")
    return llm(f"본문: {outline}")

# 2) 라우팅: 분류 후 갈래 선택
HANDLERS = {"환불": lambda q: llm(f"환불 절차 안내: {q}"),
            "일반": lambda q: llm(f"일반 답변: {q}")}
def route(q):
    label = llm(f"분류: {q}")
    return label, HANDLERS[label](q)

# 3) 병렬화(투표): 같은 일을 여러 번
def vote(q, n=3):
    with ThreadPoolExecutor(n) as ex:
        answers = list(ex.map(lambda _: llm(f"검토: {q}"), range(n)))
    return max(set(answers), key=answers.count)

# 4) 평가-개선: 기준 통과까지 반복, 횟수 상한
def refine(draft, max_iter=3):
    for i in range(max_iter):
        verdict = llm(f"평가: {draft}")
        if verdict == "OK":
            return draft, i
        draft = llm(f"개선: {draft}")
    return draft, max_iter

# 5) 에이전트: 다음 행동을 고르는 루프 (여기선 decide 함수로 흉내)
def agent(goal, tools, decide, max_steps=5):
    history = [goal]
    for _ in range(max_steps):
        action, arg = decide(history)
        if action == "finish":
            return arg
        history.append(tools[action](arg))
    return "상한 도달"
```

실제로 돌려 보니 라우팅은 "환불해 주세요"를 `환불` 갈래로, "영업시간이…"를 `일반` 갈래로 보냈다. 평가-개선은 초안 하나를 한 번 고쳐서 통과시켰고(`(' 주장만 있는 초안 (근거 추가)', 1)`), 에이전트는 검색 도구를 한 번 쓴 뒤 끝냈다. 눈에 띈 건 앞의 네 개는 흐름을 코드가 쥐고 있는데 에이전트만 `decide`가 흐름을 쥔다는 점이다. 그리고 `max_iter`, `max_steps` 같은 상한이 둘 다에 들어가 있다.

<summary>자세한 풀이: 멀티에이전트의 값은 얼마인가</summary>

Anthropic의 다중 에이전트 연구 시스템 글에는 비용 숫자가 나온다. 에이전트는 채팅의 약 4배 토큰을 쓰고, 멀티에이전트는 약 15배를 쓴다. 그래서 값어치가 큰 작업에만 경제성이 있다고 한다. 구조는 오케스트레이터-워커다. 리드 에이전트가 질문을 분석해 계획을 세우고, 하위 에이전트들이 병렬로 검색해서 결과를 돌려준다. 내부 구성은 Claude Opus 4가 리드, Claude Sonnet 4가 하위였다고 한다.

성능은 단일 에이전트 Claude Opus 4보다 90.2% 높았다고 하는데, 이건 Anthropic 내부 연구 평가에서 나온 수치다. BrowseComp에서는 성능 차이의 95%가 세 요인으로 설명됐고 그중 토큰 사용량만 80%였다. 병렬화로 복잡한 질의의 조사 시간이 최대 90% 줄었다는 말도 있다.

잘 안 맞는 경우도 적혀 있다. 모든 에이전트가 같은 맥락을 공유해야 하거나 서로 의존이 많은 일, 대부분의 코딩 작업(병렬로 쪼갤 부분이 연구보다 적다), 실시간으로 조율해야 하는 일이다. 초기에는 간단한 질의에도 하위 에이전트를 50개 띄운 실수가 있었고, 그래서 질의 난이도별로 에이전트 수와 도구 호출 수를 프롬프트에 적어 줬다고 한다. 하위 에이전트에게 일을 맡길 때는 목표, 출력 형식, 도구 안내, 경계를 구체적으로 줘야 중복 작업이 줄었다.

</details>

<details>
<summary>자세한 풀이: 어떤 패턴을 고르나 (판단 순서)</summary>

문서 내용을 순서로 바꾸면 이렇다.

1. LLM 호출 한 번에 검색과 예시를 붙여서 되는가. 되면 거기서 끝.
2. 안 되면 하위 작업이 고정되는가. 고정되면 체이닝, 입력 종류별로 갈리면 라우팅.
3. 독립인 조각이 있거나 다수결이 필요하면 병렬화.
4. 하위 작업을 입력을 봐야 알 수 있으면 오케스트레이터-워커.
5. 평가 기준이 분명하고 고치면 나아지는 일이면 평가-개선을 덧붙임.
6. 단계 수를 정말 모르고 환경 피드백으로 계속 판단해야 하면 에이전트. 이때 상한, 사람 확인 지점, 샌드박스를 함께 설계.

패턴은 서로 조합할 수 있다는 점도 문서가 말한다. 목표는 패턴을 많이 쓰는 게 아니라 측정해서 나아질 때만 더하는 것이다.

</details>

## 흔한 오해

- 에이전트가 워크플로우보다 고급이다: 문서의 기준은 고급이냐가 아니라 정해진 경로가 가능한지다. 가능하면 워크플로우가 더 예측 가능하고 싸다.
- 프레임워크를 쓰면 에이전트가 된다: 프레임워크는 편의 도구일 뿐이고, 흐름을 누가 정하는지가 갈림길이다.
- 멀티에이전트면 더 똑똑하다: 연구 글 기준으로 토큰이 15배 가까이 든다. 맥락 공유가 많은 일은 오히려 안 맞는다.
- 평가-개선은 많이 돌릴수록 좋다: 기준이 모호하면 돌기만 한다. 횟수 상한이 필요하다.
