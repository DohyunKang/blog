# トレンド収集を自動化することとは何かを整理

一言で言うと：トレンド収集は「ソース選定 → 取得 → 重複削除 → 要約 → 人間による選別」という順序だが、難しいのは要約ではなく、取得段階の制限と利用規約だった。

勉強ノートなので、実際にサービスに適用したわけではなく、公式ドキュメントを読み、小さな例のみを実行してみた。会社業務とは無関係な一般論である。

## テンデント収集とは何か

マーケティングにおけるトレンド収集とは、「今の人々が何を多く検索し、話しているか」を毎日集める作業のことだ。人間が行う場合、毎朝コミュニティやニュース、検索語を巡る時間がかかる。これをスクリプトが代わりに集めて一枚の画面に表示させるのが自動化である。

自動化한다고 해서「何が流行るか」を当ててくれるわけではない。すでに上がっているシグナルを集めるだけで、それをコンテンツのテーマにするかどうかは人間が決める。テーマプールと続く話は [詳細 → コンテンツカレンダーの自動化](#/post/mk-content-calendar) にある。

## 全体の流れ

```
[소스 목록] → [가져오기] → [정리·중복 제거] → [점수·요약] → [사람이 선택] → [주제 풀]
 RSS·API·검색어   스케줄러    URL 정규화      빈도·LLM       후보 5~10개
```

各段階を見ると以下のようになる。

1. ソースリスト：どこから取得するか決めたファイル一つ。
2. 取得：決められた時刻に実行されるスケジューラー（cron など）。
3. 整理：同じ記事が複数の場所にアップロードされているため、URL を正規化して重複を削除する。
4. スコアリング・要約：単語頻度などの単純な計算から始め、要約は LLM を使用。
5. 選別：人間が確認し、採用するものをテーマプールに移動させる。

## ソースは主に三種類

| 種類 | 例 | 長所 | 限界 |
|---|---|---|---|
| フィード (RSS) | ブログ、ニュースサイト | 形式が決まっており軽量 | 提供しているサイトのみ対応可能 |
| 公式 API | YouTube Data API、Google Trends API など | 利用規約上安全、構造化されたデータ | 制限・承認手続きが必要 |
| ウェブページスクレイピング | 検索結果、コミュニティリストなど | 何でも可能 | 利用規約・ブロック・構造変更のリスク |

最初は RSS と公式 API のみで始めるのが適切に見える。スクレイピングは最後の手段としておくのが良いと考えた。

**RSS。** RSS 2.0 スペックを見ると、記事一つが `item` で、中に `title`, `link`, `description`, `pubDate`, `guid` が含まれている。要素はすべてオプションであり、`title` または `description` のどちらか一つがあれば良い。`guid` は記事を一意に識別する文字列なので、「すでに見た記事かどうか」を判断するために使用するように仕様で定められている。重複削除にぴったりのフィールドだが、サイトによっては guid を埋め込まない場合があるため、リンクも併せて使う方が安全だと感じた。

**YouTube。** Data API の `search.list` は 1 回呼び出しあたり 1 ユニットだが、公式ドキュメントには別途バケットが設定され、一日最大 100 回までとされている。それ以外のメソッドは基本一日 10,000 ユニットで、太平洋時間真夜中にリセットされる。`videos.list` も呼び出しあたり 1 ユニットである。そのため「検索は控えめにし、既知の動画 ID の再生数は `videos.list` で取得する」といった設計になる。（参考：同じドキュメントを後から再度見ると数字が変わっている可能性があるため、実装時には必ず再確認が必要だ。）

**Google Trends。** 公式 API は Search Central ドキュメントで紹介されているが、現在はアルファ段階である。ドキュメントに「まだ全員に対して公開できない」という記述があり、アルファテスター申請フォームで申請する必要がある。過去 5 年分のデータを日・週・月・年単位で提供し、0〜100 の範囲に正規化されていない一貫した尺度であるため、複数のリクエストを連結して使用できるとのことだ。Web インターフェースでは一度に 8 つの検索語まで比較できるが、API では数十個をサポートしているという記載がある。一般開発者が今すぐ使えるものではないため、使用する場合は申請から始める必要がある。

## 利用規約と制限

取得方法が技術的に可能かどうかと、許容されるかどうかは別問題である。

- `robots.txt` はクローラーに対して「ここは来ても良い/良くない」を伝えるルールだ。RFC 9309 ではこれがアクセスを許可または禁止する権限ではなく、実際のアクセス制御は HTTP 認証などの他の手段で行う必要があると記している。つまり、`robots.txt` で許可されていても利用規約上問題ないという意味ではない。逆にブロックされている場合は従うのが礼儀である。
- サイトによっては利用規約に自動収集を禁止する文言がある可能性がある。これはサイトごとに確認が必要だが、私はすべてのサイトをチェックしたわけではない。
- ログインが必要な領域や個人情報が混ざったデータは、トレンド収集の範囲外とするのが適切だ。
- 公式 API は制限がある。制限を回避するために複数のキーを回すのは利用規約違反になりやすいとされる。これもサービスごとに異なるため確認が必要だ。
- コミュニティ API（例：Reddit）は価格・制限ポリシーが頻繁に変更されていると知られている。

## 実際に動かした小さな例

以下は、重複を除き単語の頻度をカウントするコードです。外部ライブラリを使用せず標準ライブラリのみを用いており、インターネット接続なしでサンプル XML で動作確認を行いました。同じ記事に対して `utm_source` が付与されたリンクが重複として除外されるかを確認するために追加しています。

```python
import xml.etree.ElementTree as ET, hashlib, re
from collections import Counter

SAMPLE = """<rss version="2.0"><channel>
<item><title>New video model released</title><link>https://a.example/1?utm_source=x</link><guid>a1</guid></item>
<item><title>New video model released</title><link>https://a.example/1</link><guid>a1</guid></item>
<item><title>Short video ads: what works</title><link>https://b.example/2</link><guid>b2</guid></item>
<item><title>Video model pricing cut</title><link>https://c.example/3</link><guid>c3</guid></item>
</channel></rss>"""

def norm(u):                       # 쿼리·해시 제거
    return re.sub(r'[?#].*$', '', u)

seen, titles = set(), []
for it in ET.fromstring(SAMPLE).iter('item'):
    key = hashlib.sha1(norm(it.findtext('link')).encode()).hexdigest()
    if key in seen:
        continue
    seen.add(key)
    titles.append(it.findtext('title'))

stop = {'a', 'the', 'what', 'new'}
words = Counter(w for t in titles for w in re.findall(r'[a-z]+', t.lower())
                if w not in stop and len(w) > 2)
print(len(titles), words.most_common(3))
```

実行すると `3 [('video', 3), ('model', 2), ('released', 1)]` という結果が得られました。4 つのうち重複が 1 つ除去され、「video」と「model」が上位にランクインしました。実際のフィード取得部分（ネットワーク呼び出し）はこの例には含まれていません。

<details>
<summary>詳しい解説：実際に実装する場合に追加すべき項目</summary>

- リクエスト間隔：同じサイトに対して短时间内に集中的にリクエストを送信しないようにします。フィードは 1 日に数回取得すれば十分です。
- 条件付きリクエスト：サーバーが `ETag` や `Last-Modified` を返す場合、次のリクエストに一緒に送信して変更がない場合は本体を取得しない方式があります。サイトごとにサポート状況が異なります。
- 保存：取得した原文を長期間蓄積せず、タイトル・リンク・日付・要約程度のみ保存するのが著作権的な観点から軽いです。本文全体を保存・再配布するのは別の問題です。
- スコアリング：最初は「複数のソースで同時に出現する単語」に加点する程度で十分です。同じ日に 3 つの場所で出たキーワードは、1 つの場所だけで出たものよりも信号が強いとみなすようなものです。
- 要約：LLM にタイトル 20〜30 個を一括投入し、「5 つのグループと代表タイトル」を要求します。タイトルのみを入れるとトークン数が少なくなります。要約は事実と異なる可能性があるため、リンクも残して人間が原文を開けるようにしています。
- エラー処理：ソースの一つが開かなくても全体が止まらないよう、ソースごとに例外をキャッチしログだけ残します。

## 費用見積もり

仮定は 1 日 1 回の収集、ソース 20 件、タイトル約 200 個、LLM 要約 1 回です。タイトル 1 つを平均 20 トークンとすると、入力量は約 4,000 トークン程度です。要約 1 回の出力を 500 トークン程度と仮定すれば、1 日 1 回の呼び出しで済みます。モデル単価は変動するため具体的な数字は示せませんが、この規模であれば月額数百円〜数千円程度の計算になります。

| 項目 | 方式 | 費用 |
|---|---|---|
| RSS 収集 | スクリプト | 0 円 |
| YouTube Data API | 基本割り当て枠内 | 0 円 |
| Google Trends API | アルファ、申請必要 | - |
| 要約 | LLM 1 日 1 回 | 月額数百〜数千円推定 |
| サーバー | 自家用 PC または既存サーバー | 0 円（電気代除く） |

お金よりも時間がかかります。ソースリストの管理、壊れたフィードの修正、利用規約を読む時間です。

## 自作する場合

1. ソースリストファイルを作成します。最初は RSS 10 件と YouTube チャンネル数個から。
2. 1 日 1 回走行するスクリプトでタイトル・リンク・日付を JSON に蓄積します。
3. URL の正規化で重複を除き、直近 24 時間のもののみを残します。
4. 単語頻度上位と LLM グループ要約を 1 ページの文書として作成します。
5. 人間が閲覧して利用するものをテーママップに移動させます。
6. この結果がどのような成果につながったかは、[詳細 → 成果ダッシュボード作成](#/post/mk-dashboard) のように別途行う必要があります。どのテーマが反応が良いか分からないと、収集が適切に行われているかも分かりません。

収集したトレンドに基づいて記事や動画を制作する際、一つずつ比較実験を行うのは [詳細 → サムネイル・コピー A/B テスト](#/post/mk-ab-test) に、ショートフォームに繋げるのは [詳細 → ショートフォーム自動化パイプライン](#/post/mk-shortform-pipeline) に整理しています。コメントから出る反応をトレンドとして活用する話は [詳細 → コメント・DM 対応自動化](#/post/mk-comment-bot) と続きます。

## よくある誤解

- トレンドを知れば何が流行るか分かる → 既に流行っているものを集めているため遅れる可能性があります。他の人が同じリストを見ていれば尚更です。
- スクレイピングできれば使っても良い → 技術的に可能であることと、利用規約・著作権的に許容されることは別問題です。
- LLM が要約してくれるので人間が確認しなくて良い → 要約は間違える可能性があるため、候補を選ぶ段階は人間が行うのが安全に見えます。
