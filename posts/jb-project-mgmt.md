프로젝트 관리 단원은 범위가 넓어 보이지만 시험에서 손이 가는 건 계산 문제 몇 종류다. 일정은 CPM과 PERT, 비용은 COCOMO, 사람은 브룩스의 법칙, 운영은 ITIL 용어다. 시험 일정·응시료는 공식 사이트에서 확인하고, 여기서는 개념과 푸는 순서만 정리한다.

## 먼저 큰 그림

| 질문 | 도구 | 푸는 방식 |
|---|---|---|
| 일정이 얼마나 걸리나 | CPM | 선행 관계를 따라 가장 긴 경로를 찾는다 |
| 활동 시간을 모르겠다 | PERT | 낙관·보통·비관 세 값으로 기댓값을 낸다 |
| 비용(인력)이 얼마나 드나 | COCOMO | 코드 규모(KLOC)를 공식에 넣는다 |
| 사람을 늘리면 빨라지나 | 브룩스의 법칙 | 소통 경로 수가 늘어난다 |
| 서비스를 어떻게 운영하나 | ITIL | 인시던트·문제·변경 같은 관리 활동 |

규모를 재는 입력값(요구사항)이 흔들리면 이 계산들도 같이 흔들린다. 앞 단계는 [요구사항 확인과 분석](#/post/jb-requirements)에서 이어진다.

## 일정: CPM

CPM(임계 경로법)은 활동 사이의 선행 관계를 그래프로 놓고, 가장 긴 경로를 임계 경로로 잡는다. 임계 경로 위 활동은 여유 시간(float, slack)이 0이라 하루만 밀려도 전체 일정이 밀린다. 임계 경로 밖의 활동에는 여유가 있다.

계산은 두 번 훑는다.

1. 앞에서 뒤로(전진): 각 활동의 가장 빠른 시작(ES)과 종료(EF = ES + 기간)를 구한다. 선행이 여러 개면 가장 늦게 끝나는 것에 맞춘다.
2. 뒤에서 앞으로(후진): 전체 종료 시점에서 거슬러 가장 늦은 종료(LF)와 시작(LS = LF - 기간)을 구한다. 후속이 여러 개면 가장 이른 시작에 맞춘다.
3. 여유 = LS - ES. 0이면 임계 활동이다.

예로 활동 6개를 잡고 직접 돌려 봤다. 괄호는 기간(일), 화살표 앞이 선행 활동이다.

| 활동 | 기간 | 선행 |
|---|---|---|
| A | 3 | - |
| B | 4 | A |
| C | 2 | A |
| D | 5 | B, C |
| E | 3 | C |
| F | 2 | D, E |

```python
tasks = {"A": (3, []), "B": (4, ["A"]), "C": (2, ["A"]),
         "D": (5, ["B", "C"]), "E": (3, ["C"]), "F": (2, ["D", "E"])}
es, ef = {}, {}
for t in tasks:                       # 전진
    d, pre = tasks[t]
    es[t] = max([ef[x] for x in pre], default=0)
    ef[t] = es[t] + d
end = max(ef.values())
ls, lf = {}, {}
for t in reversed(list(tasks)):       # 후진
    succ = [s for s in tasks if t in tasks[s][1]]
    lf[t] = min([ls[s] for s in succ], default=end)
    ls[t] = lf[t] - tasks[t][0]
for t in tasks:
    print(t, es[t], ef[t], ls[t], lf[t], "여유", ls[t] - es[t])
print("전체", end)
# A 0 3 0 3 여유 0
# B 3 7 3 7 여유 0
# C 3 5 5 7 여유 2
# D 7 12 7 12 여유 0
# E 5 8 9 12 여유 4
# F 12 14 12 14 여유 0
# 전체 14
```

임계 경로는 A-B-D-F이고 전체 기간은 14일이다. C는 2일, E는 4일까지 늦어져도 전체엔 영향이 없다. 문제는 보통 "임계 경로의 길이" 또는 "특정 활동의 여유"를 묻는다.

<details>
<summary>풀 때 자주 하는 실수</summary>

- 전진 계산에서 선행이 둘 이상이면 합이 아니라 가장 큰 EF를 쓴다. 위에서 D의 시작이 7인 건 B(7)와 C(5) 중 큰 쪽이라서다.
- 후진 계산에서 후속이 둘 이상이면 가장 작은 LS를 쓴다. 위에서 C의 LF가 7인 건 D(LS 7)와 E(LS 9) 중 작은 쪽이라서다.
- 임계 경로가 둘 이상일 수도 있다. 한 줄만 찾고 끝내지 말고 여유 0인 활동을 전부 확인한다.

</details>

## 일정: PERT

PERT는 활동 시간을 확신할 수 없을 때 세 값을 받는다. 낙관값 o, 가장 가능성 높은 값 m, 비관값 p다. 기대 시간은 te = (o + 4m + p) / 6이고, 표준편차는 (p - o) / 6이다. 경로 전체의 기대 시간은 활동 기대 시간의 합이고, 경로의 표준편차는 활동별 표준편차 제곱의 합에 제곱근을 씌운다.

```python
o, m, p = 2, 4, 12
print((o + 4*m + p) / 6)   # 5.0
print((p - o) / 6)         # 1.666...
```

낙관 2, 보통 4, 비관 12면 기대 5일이다. 보통 값보다 크게 나오는 건 비관 쪽 꼬리가 길기 때문이다. CPM은 기간을 하나로 확정해서 보고, PERT는 기간을 확률로 본다고 외우면 구분이 된다.

## 비용: COCOMO

COCOMO는 코드 규모로 노력(인월)을 추정하는 모델이다. 기본(Basic) 모델의 식은 이렇다.

- 노력 E = a × (KLOC)^b (인월)
- 개발 기간 D = 2.5 × E^c (개월)
- 평균 인원 P = E / D

계수는 프로젝트 유형에 따라 다르다.

| 유형 | a | b | c |
|---|---|---|---|
| 조직형(Organic) | 2.4 | 1.05 | 0.38 |
| 반분리형(Semi-detached) | 3.0 | 1.12 | 0.35 |
| 내장형(Embedded) | 3.6 | 1.20 | 0.32 |

같은 10 KLOC라도 유형이 달라지면 결과가 어떻게 달라지는지 돌려 봤다.

```python
for name, a, b, c in (("조직형", 2.4, 1.05, 0.38),
                      ("반분리형", 3.0, 1.12, 0.35),
                      ("내장형", 3.6, 1.20, 0.32)):
    e = a * 10**b
    d = 2.5 * e**c
    print(name, round(e, 1), round(d, 1), round(e / d, 1))
# 조직형 26.9 8.7 3.1
# 반분리형 39.5 9.1 4.4
# 내장형 57.1 9.1 6.3
```

노력은 조직형 26.9인월에서 내장형 57.1인월까지 두 배 넘게 벌어지는데 기간은 9개월 안팎으로 비슷하다. 기간 식의 지수 c가 작아서 노력이 커져도 기간은 천천히 늘기 때문이다. 시험은 보통 "10 KLOC 조직형일 때 노력은" 같은 형태라 계수를 외워 두는 게 우선이다. 계산기가 안 되는 환경이면 b 지수를 어림으로 넘기지 말고 문제에서 주는 값을 그대로 쓴다.

<details>
<summary>기본·중간·상세 모델 구분</summary>

기본 모델은 규모와 유형만 쓰는 가장 단순한 형태다. 중간(Intermediate) 모델은 여기에 비용 요인(제품·인력·환경 등 여러 항목)을 반영한 노력 조정 계수(EAF)를 곱한다. a·b·c의 쓰임은 같다. 상세 모델은 단계별로 세분화한다고 알려져 있지만 시험에서는 기본 모델의 식과 계수가 중심이다.

</details>

비슷한 개념으로 코드 줄 수 대신 기능의 수를 재는 방법(기능점수)도 있다. 규모를 무엇으로 재느냐가 달라질 뿐 "규모 → 노력" 흐름은 같다.

## 사람: 브룩스의 법칙

지연된 소프트웨어 프로젝트에 인력을 더 투입하면 오히려 더 늦어진다는 게 브룩스의 법칙이다. 이유는 세 가지로 설명된다. 일이 완전히 독립된 조각으로 안 나뉜다, 새로 온 사람은 먼저 배워야 하고 그동안 기존 팀원의 시간을 쓴다, 사람이 늘면 소통 경로가 빠르게 늘어난다. n명 사이의 소통 경로는 n(n-1)/2다.

```python
print(10*9//2, 50*49//2)  # 45 1225
```

10명이면 45개, 50명이면 1,225개다. 문제로는 "n명일 때 의사소통 경로 수"가 단골이다.

## 서비스 운영: ITIL

ITIL은 IT 서비스 관리의 모범 사례 모음이다. 3판은 프로세스와 기능을 서비스 수명주기를 중심으로 다섯 권으로 묶었고, 4판(2019)은 애자일·데브옵스·린과 맞추며 IT에만 국한되지 않는 서비스 관리 쪽으로 넓어졌다. 시험에서는 개별 관리 활동의 뜻을 구분하는 문제가 나온다.

| 용어 | 한 줄 |
|---|---|
| 인시던트 관리 | 서비스 장애·중단에서 빨리 정상으로 돌리는 것 |
| 문제 관리 | 인시던트의 근본 원인을 찾아 반복을 막는 것 |
| 변경(Change) 관리 | 변경을 통제해서 서비스에 주는 영향을 관리하는 것. 4판 이름은 change enablement |

인시던트는 "일단 복구", 문제는 "왜 났는지"로 갈라 외운다. 변경 관리는 [형상관리와 빌드·배포](#/post/jb-build-release)의 형상 변경 통제와 이름이 비슷해서 헷갈리는데, ITIL 쪽은 서비스 운영 관점이다.

## 자주 하는 착각

- CPM에서 가장 긴 경로가 임계 경로다. 가장 짧은 경로가 아니다. 가장 긴 경로가 전체 기간을 정해서 그렇다.
- COCOMO의 노력과 기간은 비례하지 않는다. 노력을 두 배로 늘려도 기간은 지수 c 만큼만 늘어난다.
- 사람을 늘리면 일정이 준다는 계산은 일을 독립된 조각으로 나눌 수 있을 때만 맞는다. 소프트웨어는 대체로 그렇지 않다.
- 인시던트와 문제는 다르다. 인시던트는 복구, 문제는 원인 제거다.
