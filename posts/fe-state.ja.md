状態管理とは、画面が保持すべき値をどこに置くか、そして誰が変更するかを決定する作業であり、ライブラリを選ぶ前に値の種類を分類することがはるかに重要です。

## 状態とは何か

状態 (state) は時間とともに変化し、その変化に伴って画面も同時に更新される必要があります。入力欄に入力された文字、メニューが開いているかどうか、ログインしたユーザー、サーバーから取得したリストなど、これらすべてが状態です。画面は状態を受け取って描画される結果物と考えると理解しやすいでしょう。そのため、画面に不具合が生じた場合、大抵は状態に問題があるケースが多いのです。

[詳細 → コンポーネント設計](#/post/fe-component) で扱うように、最近のフロントエンド開発では画面をコンポーネントに分割します。その瞬間、「この値はどのコンポーネントが保持しているか」という問いが生じます。状態管理とは、まさにこの問いに対する答えを集めた名前です。

## 状態を 3 つの種類に分ける

最初はすべて同じ状態だと思っていたのですが、性質が異なるため分類して扱う方が便利でした。

| 種類 | 例 | 通常どこに置くか | 特徴 |
|---|---|---|---|
| ローカル状態 | 入力中の文字、モーダルが開いているかどうか | そのコンポーネント内 | 外部から知る必要がない |
| 共有 (グローバル) 状態 | ログインユーザー、テーマ、カート | 共通の親要素、コンテキスト、ストア | 複数の画面が同時に読み書きする |
| サーバー状態 | 記事リスト、商品情報 | サーバーが元データ、クライアントはコピー | 非同期、他者が変更可能、陳腐化する可能性がある |

基準は「この値を誰が知っておく必要があるか」と「元データの所在はどこか」の 2 つです。元データがサーバーにある場合はサーバー状態であり、サーバーにない場合で一つのコンポーネントだけが使うならローカル状態、複数のコンポーネントが使うなら共有状態となります。

## ローカルから始めて引き上げる

React のドキュメントにおける基本方針は、状態をまず近くに置き、必要であれば引き上げるというものです。2 つのコンポーネントが常に同期して変化しなければならない場合、両者の状態を消去して最も近い共通の親要素へ移動させ、props として渡します。これを「状態を引き上げる (lifting state up)」と呼びます。ドキュメントによれば、React コードで最も頻繁に行われる作業の一つだそうです。

ドキュメントのアクーディオン（アコーディオン）の例は理解しやすかったです。各パネルに個別に `isActive` を持たせておくと、両方が同時に開くことができます。親要素が `activeIndex` という 1 つだけを持っていて、「一つだけ開いている」という状態が構造的に保証されます。ドキュメントによれば、状態を引き上げると保存する値の性質が変わることも多いそうです。

```js
const [activeIndex, setActiveIndex] = useState(0);
<Panel isActive={activeIndex === 0} onShow={() => setActiveIndex(0)} />
```

ここで登場する用語が制御コンポーネントと非制御コンポーネントです。自身の状態だけで動作する場合は非制御で、重要な値を props として受け取って動作する場合は制御となります。非制御は書き込みには便利ですが、他の要素との整合性が取りにくく、制御は柔軟な反面、親要素がすべてを設定する必要があります。ドキュメントによれば、この区別は厳格ではなく、一つのコンポーネントで両方を混合してもよいそうです。

そして一つ目の原則。値ごとにそれを所有するコンポーネントを一つだけ決めます (single source of truth)。すべての状態を一处に集めるという意味ではなく、同じ値を二か所にコピーして置かないという意味です。

## 状態の形状を整える

状態をどこに置くかと同じくらい、どのような形状で置くかもバグの原因となります。React ドキュメントの「状態構造の選び方」では 5 つのポイントが挙げられています。

- 一緒に変化する値は束ねる。`x` と `y` を別々に持たず、`position` という一つで管理する。
- 矛盾が生じる構造を避ける。`isSending` と `isSent` のようなブール値の両方を同時に true にすることはできない。`status` に `'typing' | 'sending' | 'sent'` のいずれか一つの値を持つようにすると、そのような事態を防げる。
- 計算可能な値は保存しない。`fullName` はレンダリング時に `firstName + ' ' + lastName` で生成する。props を state にコピーしておくと、props が変わっても追随しない。
- 同じデータを二か所に置かない。`selectedItem` オブジェクトの代わりに `selectedId` を持っておき、リストから検索する。
- 深くネストさせない。上位段階をすべてコピーして修正しようとすると面倒で間違えやすい。ID で検索できるフラットな構造の方が良い。

これらはすべて同じことを言っています。状態を最小限に抑え、残りは計算させるということです。

## サーバー状態は別に扱う

サーバーから取得したデータをそのままグローバルストアに入れて使う方式は、ある期間多く採用されていました。TanStack Query のドキュメントはこのアプローチと異なる見方を提示しています。サーバー状態とは、私が所有していないリモートデータであり、読み書きするには非同期 API が必要で、知らないうちに他者が変更でき、私のアプリ内で陳腐化するという定義です。そのため、ローカル状態用のライブラリには適さないという立場です。

このライブラリが担う役割をドキュメントから整理すると、フェッチ・キャッシング・同期・更新、同じリクエストの統合（重複排除）、陳腐化の判定とバックグラウンドでの再取得、不要なデータの削除、ページネーションなどがあります。これらを自作するにはかなりの規模の仕事となります。サーバー状態をこのようなツールに任せることで、グローバルストアには本当にクライアント側の値だけが残るため、はるかに小さくなります。これはドキュメントを読み込んで整理した理解であり、実際のプロジェクトでどれだけ削減できるかは直接検証していませんでした。

[詳細へ → CSR・SSR・SSG](#/post/fe-rendering-modes) では示されているように、レンダリング方式によってはサーバーデータが最初から HTML に埋め込まれてくるため、サーバー状態の受け取り場所もそれに伴って変化します。

## 全局状態ライブラリはいつ使うか

ローカルで始めて引き上げる過程では、props を複数の段階を跨いで渡す必要がある時が訪れます。その際の選択肢は概ね以下の通りです。

| 選択肢 | 適切なケース |
|---|---|
| そのまま引き上げる | 2〜3 つの段階以内に収まる場合 |
| Context | テーマやログインユーザーのように頻繁に変化せず、広く利用する値 |
| 外部ストア (Redux, Zustand など) | 多くの場所で頻繁に読み書きし、更新範囲を狭めたい場合 |
| サーバー状態ツール | データの元がサーバーにある場合 |

外部ストアの中核は意外にもシンプルです。単一の値、読み取り関数、変更関数、購読者リストのみです。以下のコードはこの構造を純粋な JS で実装したもので、Node.js で直接動作確認を行いました。

```js
function createStore(init) {
  let s = init; const ls = new Set();
  return {
    get: () => s,
    set: (f) => { const n = f(s); if (Object.is(n, s)) return; s = n; ls.forEach(l => l()); },
    sub: (l) => { ls.add(l); return () => ls.delete(l); },
  };
}
const st = createStore({ count: 0 });
let calls = 0;
const un = st.sub(() => calls++);
st.set(s => ({ count: s.count + 1 }));  // 알림
st.set(s => s);                         // 같은 값이라 알림 없음
un();
st.set(s => ({ count: s.count + 1 }));  // 구독 해제 후라 알림 없음
console.log(st.get(), calls);           // { count: 2 } 1
```

値が変更された場合にのみ購読者に通知することが重要です。ライブラリが不要な再描画を削減する方法は、この部分の発展形と言えます。[詳細へ → フロントエンド性能](#/post/fe-performance) に続く話題です。

## よくある誤解

- 状態はすべて全局に置く方が整理しやすい：ドキュメントの方針は逆です。近くに置き、必要な時に引き上げます。
- サーバーから取得したデータもただの状態である：変更可能であり、元データが別途存在するため管理方法が異なります。
- ライブラリを使えば設計上の問題は解決する：重複や矛盾を含む状態構造は、どのライブラリでも修正できません。
- Redux が標準なので必ず使うべき：選択肢の一つに過ぎず、基準となるのは規模と更新パターンです。

<details>
<summary>詳細な解説：派生値と重複状態の例</summary>

カート（ショッピングカート）を例にとると、`items`(商品配列) だけを状態として保持し、`totalPrice` と `count` はレンダリング時に `items` から計算します。これらの値を別途 state に持っておくと、商品を削除した際に 3 つすべてを更新する必要があり、どれか一つでも見逃すと画面が整合しません。

選択された項目も同様です。`selectedItem` オブジェクトを保存しておくと、`items` の名前を変更した際にも選択されている側は旧来の名前のままになります。一方、`selectedId` だけを保存しておけば常に最新のリストから検索するため、ズレが生じることはありません。この例は、ドキュメントの原則を別の状況に適用したものです。

</details>
