운영체제(OS)는 CPU와 메모리 같은 한정된 자원을 여러 프로그램이 나눠 쓰게 해 주는 관리자다. 프로세스, 스케줄링, 가상 메모리, 동기화는 다 이 한 가지 일을 서로 다른 면에서 보는 이름이었다.

## 정의부터

프로그램은 디스크에 있는 파일이고, 프로세스는 그게 실행 중인 상태다. 프로세스는 자기만의 메모리 공간(코드, 데이터, 힙, 스택)과 열어 둔 파일 같은 자원을 가진다. 한 프로그램을 두 번 실행하면 프로세스가 둘이다.

스레드는 프로세스 안에서 실행 흐름만 따로 갖는 단위다. 같은 프로세스의 스레드들은 힙과 코드를 같이 쓰고, 스택과 레지스터만 각자 가진다. 그래서 스레드끼리는 데이터를 주고받기 쉽지만, 같은 데이터를 동시에 만지다 꼬일 수도 있다. 프로세스끼리는 메모리가 막혀 있어서 하나가 죽어도 다른 쪽이 덜 다친다.

| | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | 각자 따로 | 프로세스 안에서 공유(스택만 따로) |
| 만들고 바꾸는 비용 | 상대적으로 큼 | 상대적으로 작음 |
| 데이터 공유 | 따로 통로가 필요 | 그냥 같은 변수를 봄 |
| 하나가 망가지면 | 다른 프로세스는 보통 무사 | 같은 프로세스의 스레드 전체가 위험 |

## CPU를 나누는 법: 스케줄링

코어보다 프로세스가 훨씬 많으니 OS가 번갈아 CPU를 준다. 누구에게 먼저 줄지 정하는 게 스케줄러다. OSTEP(교재)는 성능 지표로 반환 시간(작업이 도착해서 끝날 때까지)을 먼저 쓰고, 공정성과는 서로 부딪히는 경우가 많다고 한다. 반응 시간(도착해서 처음 실행될 때까지)은 사용자 입장에서 느끼는 속도에 가깝다.

- FIFO: 먼저 온 순서대로. 단순하지만 긴 작업이 앞에 있으면 뒤의 짧은 작업이 오래 기다린다.
- SJF(짧은 작업 먼저): 평균 반환 시간이 좋아진다. 대신 작업 길이를 미리 알아야 한다. 교재는 마트의 "10개 이하 계산대"에 비유한다.
- Round Robin: 시간 조각(quantum)만큼 돌리고 다음 작업으로 넘어간다. 반응 시간이 좋지만 반환 시간은 나빠질 수 있다.

시간 조각을 너무 짧게 잡으면 전환 비용이 커진다. 교재 예시로 조각이 10ms이고 전환 비용이 1ms면 시간의 약 10%를 전환에 쓴다. 조각을 늘리면 그 비용이 덜 드는데(amortization), 그만큼 반응은 느려진다.

<details>
<summary>Round Robin 직접 돌려 보기 (실행 확인함)</summary>

작업 A(5), B(3), C(8)를 조각 2로 돌려 각자 끝나는 시각을 셌다.

```python
from collections import deque

def rr(jobs, q):
    d = deque(jobs); t = 0; done = {}
    while d:
        name, r = d.popleft()
        run = min(q, r); t += run; r -= run
        if r: d.append((name, r))
        else: done[name] = t
    return done

print(rr([("A", 5), ("B", 3), ("C", 8)], 2))
# {'B': 9, 'A': 12, 'C': 16}
```

세 작업이 거의 동시에 진행되는 것처럼 보이지만, 가장 짧은 B도 9에 끝난다. 혼자 돌렸으면 3에 끝났을 일이다. 번갈아 돌리는 대가다.
</details>

## 메모리를 나누는 법: 가상 메모리

프로세스마다 "나는 메모리 전체를 혼자 쓴다"고 믿게 만드는 게 가상 메모리다. 프로세스가 보는 주소는 가상 주소이고, 실제 RAM의 위치(물리 주소)로 바꾸는 일은 OS와 하드웨어가 한다. OSTEP은 가상 메모리의 목표를 세 가지로 정리한다.

- 투명성: 프로그램은 메모리가 가상화됐다는 걸 몰라도 된다.
- 효율성: 시간과 공간 모두에서 낭비가 적어야 한다(하드웨어 도움이 필요하다).
- 보호: 한 프로세스가 다른 프로세스나 OS의 메모리를 건드리지 못한다. 교재는 이걸 프로세스 사이의 격리라고 부른다.

메모리를 같은 크기의 조각(페이지)으로 잘라서 가상 페이지를 물리 프레임에 짝지어 두는 방식이 페이징이다. 짝지은 표가 페이지 테이블이다. 모든 페이지가 RAM에 있을 필요는 없어서, 안 쓰는 페이지는 디스크로 내려 보내고 필요할 때 다시 올린다. 접근했는데 RAM에 없으면 페이지 폴트가 나고, OS가 디스크에서 가져온다. 이때 RAM이 가득 차 있으면 누굴 내보낼지 정해야 하는데, 이게 페이지 교체 정책이다.

<details>
<summary>FIFO vs LRU, 그리고 이상한 결과 (실행 확인함)</summary>

참조 순서 1,2,3,4,1,2,5,1,2,3,4,5 로 프레임 수를 바꿔 가며 폴트 횟수를 셌다.

```python
def fifo(refs, f):
    mem = []; miss = 0
    for r in refs:
        if r not in mem:
            miss += 1
            if len(mem) == f: mem.pop(0)
            mem.append(r)
    return miss

def lru(refs, f):
    mem = []; miss = 0
    for r in refs:
        if r in mem: mem.remove(r)
        else:
            miss += 1
            if len(mem) == f: mem.pop(0)
        mem.append(r)
    return miss

refs = [1,2,3,4,1,2,5,1,2,3,4,5]
print(fifo(refs,3), fifo(refs,4), lru(refs,3), lru(refs,4))
# 9 10 10 8
```

FIFO는 프레임을 3개에서 4개로 늘렸는데 폴트가 9에서 10으로 오히려 늘었다. Belady의 이상 현상이라 불리는 것이다. LRU(가장 오래 안 쓴 걸 내보냄)는 3개에서 10, 4개에서 8로 줄었다. 이 입력에서 LRU가 3개일 때는 FIFO보다 나쁘기도 했으니, "LRU가 항상 낫다"는 식으로 외우면 안 되겠다.
</details>

## 같이 쓰면 생기는 문제: 동기화

스레드 둘이 같은 변수에 `n += 1`을 하면 안에서는 읽기, 더하기, 쓰기 세 단계로 나뉜다. 두 스레드가 같은 값을 읽고 각자 1을 더해 쓰면 하나가 사라진다. 이런 걸 경쟁 상태(race condition)라 한다. 막는 기본 도구는 락(mutex)이다. 락을 잡은 스레드만 그 구간(임계 구역)에 들어가고 나머지는 기다린다. 이 흐름은 데이터베이스의 [트랜잭션과 격리 수준](#/post/db-transaction)에서 다시 나오고, 여러 일을 나눠 맡기는 [비동기 처리와 메시지 큐](#/post/be-async-queue)에서도 같은 고민이 이어진다.

락을 쓰면 새 문제가 생긴다. 스레드 1이 락 a를 잡고 b를 기다리는데, 스레드 2는 b를 잡고 a를 기다리면 둘 다 영영 못 움직인다. 교착 상태(deadlock)다.

<details>
<summary>락 있을 때와 없을 때, 교착 상태 재현 (실행 확인함)</summary>

```python
import threading, time
n = 0
def inc(k):
    global n
    for _ in range(k): n += 1

ts = [threading.Thread(target=inc, args=(100000,)) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print("no lock", n)   # 내 환경(Python 3.13)에서는 400000
```

락 없이 돌려도 내 PC에서는 400000이 나와서 값이 틀어지는 걸 못 봤다. 그래서 이 코드는 경쟁 상태를 "보여 주는" 예시가 못 됐다. CPython 쪽 구현 사정일 수 있다. 경쟁 상태가 있다고 해서 매번 터지는 건 아니라는 점은 확실히 알 수 있었다. 재현이 안 된다고 안전한 코드는 아니다.

교착 상태는 타임아웃을 걸어 둔 두 스레드로 재현했다.

```python
a = threading.Lock(); b = threading.Lock()
def w1():
    with a:
        time.sleep(.1)
        if b.acquire(timeout=1): b.release()
        else: print("t1 stuck")
def w2():
    with b:
        time.sleep(.1)
        if a.acquire(timeout=1): a.release()
        else: print("t2 stuck")
```

실행하니 "t2 stuck"만 한 줄 나왔다. 한쪽이 타임아웃으로 락을 놓으면 다른 쪽이 풀려서, 둘 다 stuck이 안 찍힐 수 있다. 타임아웃 없이 쓰면 둘 다 멈춘다. 이 부분은 타임아웃 없는 버전을 돌려 보지는 않았다.
</details>

## 이어 보면

한 줄로 이으면 이렇다. 프로세스가 실행 단위이고, 스케줄러가 CPU 시간을 쪼개 주고, 가상 메모리가 주소 공간을 나눠 주고, 같은 걸 같이 쓰는 지점에서는 동기화가 필요하다. 컨테이너([Docker와 컨테이너](#/post/cloud-docker))도 결국 OS가 프로세스를 어떻게 나눠 보여 주느냐의 문제로 이어지는 걸로 알고 있는데, 이쪽은 아직 정확히 공부하지 않았다.

## 흔한 오해

- 스레드를 늘리면 무조건 빨라진다: 코어 수보다 많으면 전환 비용이 늘고, 락 경쟁도 생긴다.
- 가상 메모리는 RAM이 늘어나는 것이다: 핵심은 용량 확장보다 프로세스마다 독립된 주소 공간을 주는 것이다(격리). 디스크로 내리는 건 그 위에 얹은 기능이다.
- 락만 쓰면 안전하다: 락이 교착 상태를 만들 수 있다.
- 시간 조각이 짧을수록 좋다: 반응은 좋아지지만 전환 비용이 늘어난다.
