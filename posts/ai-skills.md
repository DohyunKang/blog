스킬은 특정 작업을 잘하는 방법(절차, 참고 자료, 스크립트)을 폴더 하나에 묶어 두고, 모델이 필요하다고 판단할 때만 꺼내 읽게 하는 방식이다. 항상 컨텍스트에 올라가는 건 이름과 설명 한두 줄뿐이다.

## 스킬이 뭔지

Anthropic 문서는 스킬을 "지침, 메타데이터, 선택적 리소스(스크립트·템플릿)를 묶은, 파일시스템 기반의 재사용 가능한 자원"이라고 소개한다. 엔지니어링 글에서는 신입에게 주는 온보딩 가이드를 쓰는 것과 비슷하다고 비유한다.

모양은 단순하다. 폴더 하나에 `SKILL.md`가 반드시 있고, 필요하면 참고 문서나 스크립트를 옆에 둔다.

```
pdf-processing/
  SKILL.md        # 메인 지침 (필수)
  FORMS.md        # 양식 채우기 가이드
  REFERENCE.md    # API 상세
  scripts/
    fill_form.py  # 돌려서 쓰는 도구
```

`SKILL.md`는 맨 위에 YAML 머리말(`name`, `description`)이 있고 그 아래에 본문이 온다. 문서의 예시를 줄여 보면 이렇다.

```markdown
---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
---

# PDF Processing

## Quick start
(pdfplumber로 텍스트 뽑는 코드)

양식 채우기는 FORMS.md를 본다.
```

## 원리: 단계별로 읽는다

핵심은 한꺼번에 다 올리지 않는다는 점이다. 문서는 이걸 점진적 공개(progressive disclosure)라고 부르고 세 단계로 나눈다.

| 단계 | 언제 올라가나 | 토큰 비용(문서 기준) | 내용 |
|---|---|---|---|
| 1. 메타데이터 | 시작할 때 항상 | 스킬 하나당 약 100 토큰 | `name`, `description` |
| 2. 본문 | 스킬이 쓰일 때 | 5k 토큰 미만 | `SKILL.md` 본문 |
| 3. 리소스·코드 | 필요할 때만 | 읽기 전까지 0 | 딸린 파일, 스크립트 |

흐름으로 보면 이렇다. 시작할 때 시스템 프롬프트에 스킬마다 이름과 설명이 들어간다. 사용자가 요청하면 모델이 설명을 보고 맞는 스킬이 있는지 고른다. 있으면 bash로 `SKILL.md`를 읽어 본문이 [컨텍스트](#/post/ai-context-window)에 들어온다. 본문이 "양식은 FORMS.md 참고"라고 하면 그 일이 있을 때만 그 파일을 읽는다. 문서 예시에서는 PDF 텍스트 요약 요청이라 `FORMS.md`는 읽지 않는다.

스크립트는 읽는 게 아니라 실행한다. 문서에 따르면 스크립트 코드는 컨텍스트에 안 들어오고 실행 결과만 들어온다. 그래서 같은 일을 매번 코드로 새로 짜게 하는 것보다 토큰도 덜 들고 결과도 같게 나온다고 한다.

이 구조 덕에 스킬을 많이 깔아도 부담이 작다. 문서는 "스킬이 쓰이기 전까지는 이름과 설명만 컨텍스트를 차지한다"고 적는다. 대신 모델이 설명만 보고 고르니까 설명 한 줄이 사실상 입구다.

## 프롬프트·도구·MCP와 뭐가 다른가

| | 하는 일 | 컨텍스트에 올라가는 시점 |
|---|---|---|
| [프롬프트](#/post/ai-prompt) | 이번 대화의 지시 | 매번 직접 적을 때 |
| 스킬 | 작업 절차·지식을 폴더로 | 설명은 항상, 본문은 필요할 때 |
| [도구 호출](#/post/ai-tool-use) | 모델이 밖의 기능을 실행 | 도구 정의가 올라가고, 부르면 결과가 올라감 |
| [MCP](#/post/ai-mcp) | 도구를 외부 서버에서 표준 방식으로 연결 | 연결한 도구 정의가 올라감 |

문서는 스킬을 "대화 단위로 한 번 주는 프롬프트와 달리, 필요할 때 로드되어 같은 안내를 매번 반복하지 않게 해 주는 것"이라고 설명한다. 도구가 "무엇을 할 수 있나"라면 스킬은 "그 일을 어떻게 하나"에 가깝다고 이해했다. 다만 이 구분을 문서가 이렇게 못 박은 건 아니고, 둘이 같이 쓰이는 경우도 많다(스킬 본문이 MCP 도구를 부르라고 안내하는 식). 문서에도 스킬 안에서 MCP 도구를 쓸 때는 `서버이름:도구이름`처럼 서버 이름까지 적으라는 안내가 있다.

## 어디서 쓰나

Anthropic 문서 기준으로 스킬은 여러 곳에서 되는데, 방식이 다르다.

- Claude API: `container`에 `skill_id`를 넘기고, 코드 실행 도구가 같이 필요하다. 내가 만든 스킬은 `/v1/skills`로 올리고, 워크스페이스 전체가 쓴다. 네트워크가 없고 패키지를 새로 설치할 수 없다.
- claude.ai: 설정에서 zip으로 올린다. 개인별이고 조직 전체 공유·관리는 안 된다. 문서 작업용 기본 스킬(pptx, xlsx, docx, pdf)이 있다.
- Claude Code: `~/.claude/skills/<이름>/SKILL.md`(개인) 또는 `.claude/skills/<이름>/SKILL.md`(프로젝트)에 두면 된다. 네트워크는 내 컴퓨터와 같다.

중요한 점은 이 셋이 서로 동기화되지 않는다는 것이다. claude.ai에 올린 스킬이 API나 Claude Code에서 저절로 보이지 않는다.

Claude Code 쪽 문서에서는 몇 가지가 더 나온다. 머리말에 `disable-model-invocation: true`를 쓰면 모델이 자동으로 못 부르고 내가 `/이름`으로 부를 때만 돈다. 반대로 `user-invocable: false`면 `/` 메뉴에서 숨기고 모델만 부른다. 옛 커스텀 슬래시 명령(`.claude/commands/`)은 스킬로 합쳐졌고 기존 파일도 계속 동작한다. 설정 수단을 전체적으로 어떻게 나눠 쓰는지는 [Claude Code 스킬·설정](#/post/claude-skills) 글에 따로 정리했다.

## 잘 쓰려면: 문서가 말하는 것

best practices 문서에서 숫자와 규칙이 있는 것만 추렸다.

- `name`: 64자 이하, 소문자·숫자·하이픈만, `anthropic`·`claude`는 예약어라 못 쓴다.
- `description`: 비어 있으면 안 되고 1,024자 이하. 무엇을 하는지와 언제 쓰는지를 둘 다 적는다. 3인칭으로 쓴다("엑셀 파일을 처리한다", "내가 도와줄 수 있다"는 안 됨). 설명이 시스템 프롬프트에 들어가는데 시점이 섞이면 선택이 흔들릴 수 있다고 한다.
- `SKILL.md` 본문은 500줄 아래로 두고, 넘어가면 파일을 나눈다.
- 참조는 `SKILL.md`에서 한 단계만 들어가게 한다. 파일 안에서 또 다른 파일로 이어지면 모델이 앞부분만 훑고(`head -100` 같은 식) 넘어갈 수 있다.
- 지침은 짧게. "모델은 이미 똑똑하다"를 기본 전제로 하고, 모델이 모르는 것만 적는다.
- 작업이 아슬아슬하면(DB 마이그레이션 같은) 자유도를 낮춰 "이 스크립트를 그대로 실행"하게 하고, 판단이 필요한 일(코드 리뷰)은 자유도를 높인다.
- 평가를 먼저 만든다. 스킬 없이 시켜 보고 막히는 곳을 찾은 뒤, 그걸 메우는 최소한만 쓴다.

Claude Code 문서에는 설명이 길면 잘린다는 내용도 있다. `description`과 `when_to_use`를 합쳐 목록에서 1,536자에서 잘리니 핵심 용도를 앞에 쓰라고 한다.

## 흔한 오해

- 스킬을 많이 깔면 컨텍스트가 터진다: 평소에는 스킬당 이름·설명(문서 기준 약 100 토큰)만 올라간다. 본문은 쓰일 때만 들어온다. 다만 스킬이 수백 개로 늘면 그 설명 목록 자체도 커질 테니 공짜는 아니다.
- 한 번 불러온 스킬은 계속 유지된다: Claude Code 문서는 스킬이 쓰이면 본문이 대화에 한 번 들어와서 이후 턴에도 남는다고 한다. 그래서 오래 쓰는 작업에서는 그만큼 자리를 차지한다.
- 스킬은 다 믿고 써도 된다: 스킬은 지침과 코드를 같이 주기 때문에 나쁜 스킬은 모델이 도구를 엉뚱하게 부르게 만들 수 있다. 문서는 직접 만들었거나 Anthropic에서 받은 것만 쓰라고 하고, 모르는 출처라면 안에 든 파일(스크립트, 이미지 포함)을 전부 감사하라고 한다. 외부 URL을 가져오는 스킬은 더 위험하다고 적는다. 소프트웨어 설치와 같은 태도로 보면 된다.
- 스킬이 있으면 모델이 반드시 쓴다: 쓸지는 모델이 설명을 보고 정한다. 그래서 설명이 모호하면("문서를 돕는다") 안 불릴 수 있다. 문서가 이름과 설명을 특히 중요하게 꼽는 이유다.
- 스킬은 프롬프트의 다른 이름이다: 겉으로는 지시문 묶음이지만 파일시스템 구조, 단계별 로딩, 스크립트 실행이 붙어 있어서 같지 않다. 반대로 말하면 그냥 긴 지시문 하나를 폴더에 넣는다고 스킬의 이점이 생기는 건 아니다. 나눠 읽을 만큼 나눠 놓아야 한다.

<summary>자세한 풀이: 스킬이 컨텍스트에 쌓이는 순서</summary>

문서의 PDF 예시를 그대로 따라가 본다.

1. 시작: 시스템 프롬프트에 "pdf-processing - PDF에서 텍스트와 표를 뽑고 양식을 채운다..." 한 줄이 들어간다.
2. 요청: "이 PDF에서 텍스트 뽑아서 요약해 줘."
3. 모델이 `cat pdf-processing/SKILL.md`로 본문을 읽는다. 이제 본문이 컨텍스트에 있다.
4. 양식 채우기는 필요 없으니 `FORMS.md`는 읽지 않는다.
5. 본문 지침대로 작업한다.

Claude Code에서는 한 가지가 더 있다. 문서에 따르면 자동 압축(compaction)이 일어날 때 가장 최근에 쓴 스킬을 다시 붙여 주는데, 스킬마다 앞 5,000 토큰까지만 남기고 전체 합계 예산은 25,000 토큰이라고 한다. 예산은 최근에 쓴 스킬부터 채워서 오래된 스킬은 빠질 수 있다. 그래서 중요한 지침은 `SKILL.md` 앞쪽에 두는 게 안전하다. (이건 문서 내용을 읽은 것이고 내가 직접 실험해 본 건 아니다.) 압축 자체는 [컨텍스트](#/post/ai-context) 글 쪽에 정리해 뒀다.

</details>

<details>
<summary>자세한 풀이: 서브에이전트·하네스와의 관계</summary>

스킬 본문이 컨텍스트에 들어오고 나면 그 뒤로는 평범한 지시문과 같이 취급될 거라고 이해했다. 다른 점은 들어오기 전의 일이다. 무엇을 언제 읽을지, 스크립트를 어떻게 실행하는지는 모델을 감싸고 있는 [하네스](#/post/ai-harness)가 맡는다. 스킬이라는 개념은 모델이 아니라 하네스 쪽 약속에 가깝다.

Claude Code 문서에는 머리말에 `context: fork`를 넣으면 스킬을 별도 [서브에이전트](#/post/ai-subagent)에서 돌릴 수 있다고 나온다. 출력이 많은 작업을 따로 돌리고 요약만 받는 용도로 이해했는데, 직접 써 보지는 않았다.

</details>
