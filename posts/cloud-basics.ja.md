クラウドはサーバーを購入するのではなく借りる方式であり、サーバーのどのレイヤーまで自社で管理するかによって IaaS、PaaS、SaaS に分かれます。その上には「リージョン」と「AZ（アベイラビリティゾーン）」という位置概念や、使用量に応じた課金構造が加わります。

## クラウドとは何か

以前はサービスを稼働させるためにサーバーを購入してデータセンターに設置する必要がありました。数週間前に注文し、どれくらい使うか事前に予測して余裕を持って購入しました。クラウドはこの仕組みをインターネット経由で借りる方式に変えました。必要な時に作成し、不要になったら削除します。

NIST（米国標準技術研究所）の定義文書では、クラウドコンピューティングを「ネットワークを通じていつでも容易にアクセス可能な、設定可能なコンピューティングリソースの共有プールを提供するモデル」と述べています。リソースの割り当てと回収が迅速で、管理コストがほとんどかからない点が核心です。同じ文書で挙げられている特徴の名前はオンデマンドセルフサービス、リソースプーリング、高速な弾力性、測定可能なサービスでした（広帯域ネットワークアクセスを含めて 5 つあることは知っていますが、今回は本文中で直接確認できませんでした）。

AWS の概要文書も同様に記述しています。最初に大きな出費をかける代わりに使用量に応じた変動費用を支払い、数百台のサーバーを数分で稼働させられるとあります。まとめると以下のようになります。

| | 旧方式（オンプレミス） | クラウド |
|---|---|---|
| 準備 | 数週間〜数ヶ月 | 数分 |
| 費用の支払い方法 | まず大きな額（購入） | 使用量に応じたもの |
| 容量 | 最大値を予測して購入 | 増減自在 |
| 管理 | ハードウェアまで自社で | 事業者が一部代行 |

## IaaS、PaaS、SaaS

サービスは層状に積み重なっています。ハードウェア、仮想化、オペレーティングシステム、ランタイム、アプリケーション、データ。このうちどこまでを事業者が担当してくれるかが 3 つのモデルを分けます。

| | 自社で管理するもの | 事業者で管理するもの | 例 |
|---|---|---|---|
| IaaS | OS 以上すべて | ハードウェア、仮想化 | 仮想サーバー (VM)、ディスク、ネットワーク |
| PaaS | コードとデータ | OS、ランタイム、サーバー | コードをアップロードするだけで動作させるホスティングサービス |
| SaaS | 設定と運用 | ほぼすべて | メール、コラボレーションツール |

表の例示と層の区分は一般的な説明をまとめたものです。境界線はサービスによって少しずつ異なるため、どのサービスがまさにどのセルに該当するか曖昧な場合が多いです。

IaaS は自由度が高く、担当する作業も多くなります。サーバーにアクセスして OS のアップデートやセキュリティパッチ適用まで自社で行います。PaaS はそれを事業者が行ってくれる代わりに、利用可能な言語や設定が決まっています。SaaS は完成したプログラムをそのまま使います。下に行くほど便利で、上に行くほど自由だと理解しました。

## 責任の分割

AWS の責任共有モデル文書はこの境界線をセキュリティの観点から説明しています。事業者はホスト OS と仮想化レイヤーから施設の物理的セキュリティまで運用・管理します。顧客はゲスト OS（アップデートとセキュリティパッチを含む）、その上のアプリケーションソフトウェア、セキュリティグループ（ファイアウォール）の設定を担当します。文書では利用するサービスによって顧客の責任が異なることも記述しています。上で見た層の区分と同じ話です。サーバーを借りたからといってセキュリティまで借りているわけではありません。

なお、この文書には「本白書は過去の参考資料であり、一部の内容は陳腐化している可能性がある」という注意書きがありました。大きな構造は今でも通用する説明ですが、詳細については最新の文書で再確認するのが適切でしょう。

## リジョンと AZ

クラウドサーバーはどこかの実際の建物内にあります。AWS の文書基準ではリージョンは世界の物理的な位置を指し、一つのリージョン内には複数のアベイラビリティゾーン（Availability Zone, AZ）があります。AZ はデータセンター一つまたは複数で構成され、電源・ネットワーク・接続が冗長化されており、互いに異なる施設に設置されています。文書では AZ を複数使用すると、単一のデータセンターを使用する場合よりも高可用性・障害耐性・拡張性を高められると説明しています。

```
리전 (예: 서울)
 ├─ AZ-a  [데이터센터]  ← 서버 1
 ├─ AZ-b  [데이터센터]  ← 서버 2
 └─ AZ-c  [데이터센터]  ← 서버 3
```

実際には以下のように運用します。サーバーを一つの AZ だけに配置すると、その建物の問題でサービスが同時に停止してしまいます。複数の場所に分散させて前方でリクエストを振り分けると、片方が死んでも全体は生き残ります。振り分ける装置は [詳細 → ロードバランサー](#/post/infra-load-balancer) です。リージョンはユーザーに近いほど応答が速く、国ごとのデータ保存規制とも関連するため最初は慎重に選ぶべきだという説明もありますが、今回は公式文書で確認したわけではありません。

## VM とは何か

仮想マシン（VM）は物理サーバー一台をソフトウェアで分割して複数のもののように使うものです。IaaS で借りる「サーバー」の多くはこの VM です。コア数、メモリ、ディスクを選んで作成すれば、数分でアクセス可能なコンピュータが生まれます。VM ごとに OS を個別にインストールするため重く、起動に時間がかかります。より軽量な方式がコンテナです。[詳細 → Docker とコンテナ](#/post/cloud-docker) で続けます。

## 費用構造

クラウドの費用は一言で言えば「使用量に応じたもの」です。AWS の概要文書でも on-demand や pay-as-you-go の価格を前面に出しています。そのためいくつか感覚が必要でした。

- 가동 시간만큼 요금이 부과됩니다. VM 은 요청이 없더라도 켜져 있으면 비용이 발생합니다.
- 서버 비용 외에도 추가 요금이 발생할 수 있습니다. 디스크 저장 용량, 인터넷으로 나가는 데이터 양, 관리형 서비스 이용료 등이 별도로 청구되는 경우가 많습니다.
- 한번 생성하고 잊어버리면 계속 비용이 쌓입니다. 테스트 목적으로 띄운 서버를 종료하지 않아 요금이 누적되는 일이 흔하다고 합니다.
- 장기적으로 사용할 계획이라면 약정 할인 혜택을 활용하거나, 중단해도 되는 경우 남는 자원을 저렴하게 사용하는 방식이 알려져 있습니다.

따라서 처음에는 알림을 설정해 두는 것이 중요합니다. 예산을 정해두고 이를 초과하면 알림이 오는 기능을 제공하는 경우가 많습니다. 로그와 지표를 모아 확인하는 내용은 [자세히 → 모니터링·로그·알림](#/post/cloud-observability)에서 이어집니다.

## 서버리스와 뭐가 다른가

서버리스는 서버가 없다는 뜻이 아닙니다. 서버는 존재하지만, 사용자가 서버를 생성하거나 삭제하지 않습니다. 함수를 배포해 두면 요청이 들어올 때만 실행되며, 사용한 시간만큼 비용을 지불합니다. VM 이 "빌려 둔 시간"에 요금을 부과하는 반면, 서버리스는 "실제로 일한 시간"에 따라 요금이 부과됩니다. 계층 구조로 보면 PaaS 보다 한 단계 더 위에 위치하는 경우가 많습니다. 자세한 내용은 [자세히 → 서버리스](#/post/cloud-serverless)에서 확인하세요.

## 흔한 오해

- 클라우드는 무조건 저렴하다: 초기 비용은 낮지만, 24 시간 가동되는 대형 서버는 직접 구매하는 것보다 비쌀 수 있습니다. 저렴한 점은 "미리 구매할 필요가 없다"는 것입니다.
- 클라우드에 배포했으니 고장 나지 않는다: 하나의 가용 영역 (AZ) 에만 배포하면 해당 지역이 장애가 발생하면 함께 중단됩니다. 이중화는 사용자가 설계해야 합니다.
- 보안은 사업자가 처리한다: 위의 책임 공유 모델에 따라 OS 패치와 방화벽 설정은 고객 몫인 경우가 많습니다. 비밀번호 및 키 관리도 마찬가지입니다. 이 부분은 [자세히 → 환경변수와 시크릿 관리](#/post/cloud-secrets)에서 정리했습니다.
- 트래픽이 증가하면 자동으로 확장된다: 확장 기능을 제공하지만, 활성화 기준을 설정해야 합니다. [자세히 → 오토스케일링과 확장](#/post/infra-autoscaling)에서 확인하세요.

<details>
<summary>자세한 풀이: 배포 모델 세 가지</summary>

서비스 모델 (IaaS/PaaS/SaaS) 과는 별개로, 애플리케이션을 어디에 배치하는지를 구분하는 배포 모델이 존재합니다. AWS 문서에서는 이를 세 가지로 분류합니다.

- 클라우드: 전체 애플리케이션이 클라우드 환경에서 실행됩니다. 처음부터 클라우드에서 구축한 경우나 기존 인프라에서 이전된 경우를 포함합니다. 낮은 계층의 구성 요소를 직접 만들거나, 관리 기능을 제공하는 높은 계층 서비스를 사용할 수도 있습니다.
- 프라이빗 (온프레미스): 가상화와 자원 관리 도구를 사용하여 자체 시설 내부에 구성하는 방식입니다. 문서는 클라우드의 장점을 충분히 얻지 못하지만 전용 자원이 필요할 때 선택한다고 설명합니다.
- 하이브리드: 클라우드와 기존 온프레미스 설비를 연동하여 사용하는 방식입니다. 가장 일반적인 형태는 기존 설비를 클라우드로 확장하면서 두 환경을 연결하는 것입니다.

NIST 문서에서는 배포 모델을 네 가지로 분류하며, 공동체 클라우드 (Community Cloud) 가 추가된다고 알려져 있습니다.

</details>

<details>
<summary>자세한 풀이: 데이터베이스와 상태는 어떻게 관리하나</summary>

서버는 쉽게 생성하고 삭제할 수 있지만, 데이터는 그렇지 않습니다. VM 을 삭제하면 내부에 저장된 파일도 함께 사라지는 구성이 흔하므로, 중요한 데이터는 서버 외부의 저장소나 관리형 DB 에 보관해야 합니다. 서버 내부에 상태를 유지하지 않는 설계는 오토스케일링 관련 내용에서 다시 다룹니다. DB 를 여러 곳에 배치하는 방법은 [자세히 → 복제와 샤딩](#/post/db-scaling)에서 확인할 수 있습니다. 이 부분은 이번 공식 문서 확인 결과가 아니라 일반적인 설계 원칙으로 작성되었습니다.

</details>
