サーバーレスとは「サーバーがない」という意味ではなく、サーバーの起動・停止・スケーリングをクラウドが代行し、私は関数のコードだけをアップロードする方式のことです。

## サーバーレスとは何か

名前が紛らわしいです。サーバーは当然存在します。ただ、私がサーバーを借りて OS をインストールしプロセスを常時稼働させるのではなく、コード（関数）を配置しておき、リクエストが来るたびにクラウドが自動的に実行環境を作成して処理し、リクエストがない場合は環境を停止させるため、「サーバーの管理が不要」という意味でこの名前が付けられています。

Vercel のドキュメントも同様の説明をしています。リクエストごとに関数の実行（invocation）が発生し、トラフィックがない場合、リソースは 0 にまで削減されるとのことです。AWS Lambda はこの方式の代表的なサービスです。

[サーバー・クラウドの基礎 → クラウド入門](#/post/cloud-basics) を先に読むと、「借りて使うサーバー」と何が違うのか比較しやすいでしょう。

| | サーバーを直接運用 (VM など) | サーバーレス |
|---|---|---|
| 稼働状態 | サーバーは常時稼働中 | リクエストが来る時のみ実行 |
| スケーリング | サーバー数・サイズを自分で設定 | リクエストが増えると環境が自動的に拡張される |
| 料金 | 稼働時間に基づき課金 | 実行回数と実行時間に基づき課金 |
| 状態 | メモリやディスクにデータを保持可能 | 実行終了するとデータが消えるため、コード内で管理する必要がある |

## 関数の実行方式

Lambda のドキュメントで説明されている流れは以下の 3 つの段階です。環境が作成される際の Init、リクエストを処理する際の Invoke、環境を整理する際の Shutdown です。

Init では拡張機能を有効にし、ランタイムを起動し、コード内のハンドラ外にある部分（import、設定、DB 接続など）を実行します。Invoke でハンドラが実行されます。終了しても環境は即座に消えず、凍結（freeze）された状態で保持され、同じ関数への次のリクエストが来ると解凍（thaw）されて再利用されます。ドキュメントによると、数時間ごとに環境が入れ替わるため、永久に維持されていると信じてはいけません。

この再利用性のため、コードの配置位置が意味を持ちます。ハンドラ外にある変数や接続は次のリクエストでも存続する可能性があります。ドキュメントで推奨されている通り、DB 接続などは外側（初期化段階）で作成し再利用するのが一般的です。

実行して確認した小さな例は以下の通りです。ハンドラ外は一度だけ実行され、ハンドラは各リクエストごとに実行されます。

```python
import time

time.sleep(0.2)                    # Init: 라이브러리 로드, 연결 생성 흉내
CONN = {"opened": time.time()}     # 핸들러 바깥: 환경이 살아 있는 동안 재사용
calls = 0

def handler(event, context=None):  # Invoke: 요청마다 실행
    global calls
    calls += 1
    return {"call": calls, "conn_age_ms": round((time.time() - CONN["opened"]) * 1000)}

for _ in range(3):
    print(handler({}))
    time.sleep(0.05)
```

実行結果では call が 1, 2, 3 と増え、conn_age_ms も 0, 50, 101 のように増加しています。接続が各リクエストで新規に作成されるのではなく継続していることを模倣したものです。これは実際の Lambda での実行ではなく、ローカル Python シミュレーションです。

## コールドスタート

リクエストが来たのに利用可能な環境がない場合は新規に作成する必要があります。コードをダウンロードし、環境を起動し、Init コードを実行した後でハンドラが始動します。この前段の時間をコールドスタートと呼びます。既に存在する環境を再利用するとウォームスタートと呼ばれます。

Lambda のドキュメントでは、コールドスタートは通常、呼び出しの 1% 未満で発生し、時間は 100ms 未満から 1 秒を超えるまで多様であると記載されています。呼び出しが少ない開発・テスト用関数でより頻繁に現れるともあります。数字はドキュメントの一般的な説明であり、自分の関数ではどの程度かかるかは別途確認する必要があります。

Init に時間を要するのは結局自分のコードです。ドキュメントではパッケージサイズ（ライブラリ、レイヤー）、初期化作業量、接続設定速度を主要な要因として挙げています。削減方法もその逆です。必要なライブラリだけを取得し、使わないパスのオブジェクトは必要になった時に作成します。

予測可能な起動時間が必須の場合は Provisioned Concurrency というオプションがあります。環境を事前に用意しておくもので、それだけ常時稼働させるコストという概念が再び導入されます。SnapStart は初期化が完了した状態のスナップショットを保存しておき、そこから再開する方式で、サポート範囲は限定されています。

## 制限事項

Lambda の基本割り当て量で目立つ項目です。

| 項目 | 値 |
|---|---|
| 1 回の実行時間 | 最大 900 秒 (15 分) |
| メモリ | 128MB ~ 10,240MB (CPU はメモリに比例) |
| 同期呼び出しのリクエスト・レスポンスサイズ | それぞれ 6MB |
| 同時実行 | デフォルト 1,000（アカウント・リージョン基準、増量申請可能） |
| デプロイパッケージ | zip 解凍後 250MB、コンテナイメージは 10GB |
| /tmp | 512MB ~ 10,240MB |

出典は AWS の割り当て量ドキュメントで、新規アカウントではより低い値から始まると記載されています。この数字は変更される可能性があるため、使用する際は再度確認するのが適切です。

数字よりも重要なのは思考の仕方でした。実行が終了すると環境が消える可能性があるため、状態は関数内ではなく DB やストレージに置きます。15 分を超える処理は分割するか別の方式（コンテナ、ワークフロー）を使用します。リクエストが一気に集中すると同時実行の制限に達し、関数の背後にある DB がその並行性を耐えきれない事態も発生します。[DB のスケーリング](#/post/db-scaling) はこの話と続きます。

## 費用

料金は、リクエスト数と実行時間（割り当てメモリ GB × 秒）の合計で計算されます。AWS の価格ページ（x86、米国東部（バージニア）基準）では、100 万回ごとに 0.20 ドル、GB-sec 当たり 0.0000166667 ドルです。また、月間リクエスト 100 万回と 40 万 GB-sec は無料です。

自分で計算した例です。512MB の関数が 200ms で 100 万回実行されると、100 万 × 0.2 秒 × 0.5GB = 100,000 GB-sec になります。100,000 × 0.0000166667 は約 1.67 ドルで、リクエスト料金の 0.20 ドルを足すと約 1.87 ドルとなります。これは無料枠を引く前の金額であり、上記の無料枠内にあるため実際には 0 円になります。他のサービス料金（API Gateway、データ転送、ログ）は計算に含まれていません。

逆に、一日中継続的にリクエストが来るサービスであれば、サーバーを稼働させておく方が安くなる可能性があります。どちらが有利かはトラフィックや実行時間によって異なるため、一般的な数字を見つけることはできませんでした。

Vercel Functions は計算方式が少し異なります。ドキュメントによると、Active CPU、Provisioned Memory、コール数で課金され、「Fluid compute」という方式では、1 つのインスタンスが同時に複数のリクエストを処理することで、待ち時間（外部 API への応答待ちなど）を活用できると説明されています。そのため、コールドスタートとコストが削減できるとのことです。

## おすすめな場合、そうでない場合

- おすすめ: 間欠的に呼び出される API、Webhook の受信、ファイルアップロード時にサムネイル生成、指定時刻に実行するタスク、トラフィックが変動しやすいサービス
- おすすめでない: 15 分を超える長時間処理、常時稼働が必要な接続（WebSocket サーバーなど）、レイテンシが非常に敏感な場所、ローカルディスクやメモリの状態に依存するプログラム

コンテナと比較すると、[Docker とコンテナ](#/post/cloud-docker) は「環境をすべて自分で管理する」に近いのに対し、サーバーレスは「環境は預けてコードを出すだけ」に近いと言えます。両者が混在することもあり、Lambda もコンテナイメージをアップロードできます。自動的な増減については [オートスケーリング](#/post/infra-autoscaling) の項目で詳しく解説しています。

## よくある誤解

- サーバーがない: あります。私が管理しないだけです。
- いつも安い: リクエストが少なく短いときは安いです。継続的に多く使うと変わることがあります。
- いつも遅い: コールドスタートは一部の呼び出しにしか発生しません。ただし、その一部がユーザーに見える場合は遅く感じられます。
- 状態を変数に保存しても OK: 再利用される間だけ偶然残るものです。信じて使わないでください。
- 無限に増える: 同時実行の制限とバックエンドシステムの制限があります。

<details>
<summary>詳しい解説：1 つのリクエストが通る道</summary>

リクエストが入ると、フロントエンド（API Gateway や CDN など）が受け取り関数を呼び出します。利用可能な環境があればそこに、なければ新しく作成して Init を実行した後にハンドラを実行します。レスポンスが出たら環境は凍結されます。リクエストが一気に来ると複数の環境が同時に作成され、Lambda のドキュメントによると 1 つの関数が 10 秒ごとに増やせる環境数にも制限（1,000 個）があります。

実行中にエラーやタイムアウトが発生すると環境がリセットされ、次の呼び出しでは Init からやり直します。ドキュメントによれば、この場合でも /tmp の内容は消えないと記載されています。全体のリクエストフローは [リクエストの通過経路](#/post/infra-request-journey) で別途解説しています。

ログとメトリクスは、[観測性](#/post/cloud-observability) で扱われるように別途管理する必要があります。Lambda は REPORT ログに Duration、Billed Duration、Init Duration などの値を残すとドキュメントの例で示されています。

</details>
