プロンプトとはモデルに与える入力全体を指し、プロンプトエンジニアリングはその入力を所望の回答が得られるよう調整することです。整理してみると、効果が実証されている手法は少数であり、残りはモデルが変わるにつれて意味が薄れたり、誇張されたりしていました。

## プロンプトとは何か

チャットボットに投げかける質問の一語だけをプロンプトだと考えがちですが、正確にはモデルが回答を作成する前に受け取るテキスト全体です。[LLM](#/post/ai-llm) は次のトークンを連続して生成するモデルなので、前面に何が置かれているかによって続く文章も変わります。つまり、プロンプトエンジニアリングは結局「前面に何を置くか」を考案することなのです。

API を利用する場合、入力は通常 2 つの層に分けられます。

| | システムプロンプト | ユーザープロンプト |
|---|---|---|
| 誰が使うか | アプリを作成した人 | アプリを使う人（またはコードで埋め込まれる） |
| 内容 | ロール、口調、ルール、出力形式 | 今回は処理する質問・ドキュメント・データ |
| 変更頻度 | ほぼ固定 | リクエストごとに変更される |

システムプロンプトは対話全体にわたって敷き詰められた基本設定であり、ユーザープロンプトはその時の要求です。モデルの立場ではどちらも結局入力テキストですが、API が区別して受け付けるため、ルールはシステム側に置くのが慣例です。

## 効果が実証されている手法

Anthropic のドキュメントにあるプロンプトガイドで繰り返し言及されている項目は以下の通りでした。

### 1. 明確に書く、理由も添える

最も平凡な方法ながら、最も効果が高いと言われています。ドキュメントの例が良かった。「省略記号を使わないで」という指示よりも、「この回答は音声合成機が読み上げるため、省略記号の読み方を知らないから使わないで」といった説明の方が良いそうです。理由を伝えると、モデルはその意図を他のケースにも適用する、という説明です。人に仕事を頼むときと同じことです。

### 2. 例示を入れる（few-shot）

入力と正解のペアをいくつかプロンプトに直接提示する方法です。指示のみで例示を与えない場合は zero-shot、例示を与える場合は few-shot と呼ばれます。GPT-3 の論文 (Brown et al., 2020) は、モデルを育てれば重みを一切変更せず、テキストとして与えた例示だけで新しい課題をかなり解き得ることを示しており、これが few-shot プロンプトの出発点です。ガイドは形式・口調・構造を整えるのに最も信頼できる方法の一つだとし、3〜5 つを推奨しています。条件は実際の使用ケースと似ており、互いに多様で、`<example>` タグを使って指示と区別しておくことです。

興味深い研究がありました。Min ら (2022) は、例示の正解ラベルをランダムに変更しても性能が大きく低下しないことを確認しました（12 のモデル、分類・選択式課題）。性能を決定的にしていたのはラベルが正しいかどうかよりも、ラベルの候補範囲、入力テキストの分布、全体の形式だったそうです。例示は「正解を教えてくれるもの」よりも「どのような形式で答えるかを示すもの」に近い、と読みました。ただしこれはその論文の課題範囲内での結果です。

### 3. 構造と出力形式を決める

指示、文脈、例示、入力データが一つのプロンプトに混ざると、モデルがどこまでが指示なのか混乱する可能性があります。ガイドは `<instructions>`, `<context>`, `<input>` のように種類ごとにタグで囲むよう推奨しています。出力形式も望ましいものを直接記述した方が良いでしょう。JSON で、序論なし、表などでといった具合です。形式をコード側で処理する必要があれば、プロンプトで頼むよりも API の構造化出力やツール呼び出し機能を使う方がガイドが推奨します。

### 4. 長いドキュメントは上、質問は下に

ドキュメントを長く付加する場合は、ドキュメントを先に、質問を最後に置くように指示されています。ガイドは質問を最後に置くと応答品質が最大 30% まで向上すると記載していますが、「テストで」得られた値であり、特に複数のドキュメントが混ざった複雑な入力における話です。条件付きの数値なのでそのまま一般化することはできません。

### 5. 推論を誘導する

Wei ら (2022) の chain-of-thought (CoT) の論文では、例示に解法過程も一緒に記述すると算数・常識・記号推論が向上したと報告しています。540B モデルで例示 8 つだけで数学問題ベンチマーク GSM8K で当時最高レベルの成績を収めたそうです。続いて Kojima ら (2022) は、例示もなしに「Let's think step by step」という一行だけ追加するだけで、InstructGPT(text-davinci-002) では MultiArith の精度が 17.7% から 78.7% に、GSM8K は 10.4% から 40.7% に向上したと報告しています。

ここで注意すべき点は、この数値が 2022 年のモデル基準に基づくことです。現在使用されているモデルは回答する前に自ら考える機能 (thinking) を備えていることが多く、ガイドも複雑な作業にはモデルの適応型 thinking を使うよう推奨しています。そのため「段階的に考えて」というフレーズを習慣的に付けるかどうかはモデルによります。直接比較を試みませんでした。

## 誇張されていたりあまり有用でないもの

効果的なものを確認したので、今度は反対側です。これは私が読んだ範囲で整理したものです。

| 技法 | 私が読んだ根拠 | 判断 |
|---|---|---|
| 「君は世界最高峰の専門家だ」といったペルソナ | Zheng 他 (2023): システムプロンプトにペルソナを付与しても、事実質問の精度が向上せず、効果はほぼランダムに近い | 精度向上には弱く |
| 大文字や「絶対」「必ず」などの強調 | Anthropic ガイド: 最新モデルはシステムプロンプトに対してより敏感であるため、「CRITICAL: You MUST」といった表現は逆に過剰に動作しうるため、平穏な文調に抑えるよう推奨されている | 旧世代モデルの癖 |
| 魔法のようなフレーズ（ヒントをあげる、深呼吸する等） | - | 根拠なしで保留 |
| 応答の事前埋め込み (prefill) | ガイド: Claude 4.6 以降の一部モデルは、最後の assistant ターンの prefill をサポートしていないとある | モデルによって異なる |

役割指定が完全に無意味だということではない。ガイドでは、システムプロンプトに役割を単一言語で与えるだけで、口調や行動の焦点が定まると述べている。私が理解したところは以下の通りである。役割は口調・視点・基準を定めるために使用し、未知の事実を知らせる目的には期待しない。論文で示されたのは事実質問の精度であった。

## プロンプトエンジニアリングの位置づけ

ガイドは最初から線を引き始める。プロンプトを修正する前に成功基準を定め、それをテストする方法と最初のドラフトを用意しておく必要がある。遅延やコストの問題については、プロンプトを変更するよりもモデルを変える方が容易な場合もあるという。評価なしに文句だけを繰り返しても良くなったかどうかはわからないのだ。

そして最近では話がさらに広がった。エージェントのようにモデルがツールを呼び出しながら反復する構造においては、一枚のプロンプトをうまく使うことよりも、各ターンでモデルの眼前に何があるかが重要になった。この領域を [コンテキストエンジニアリング](#/post/ai-context) と呼ぶ。プロンプトはその中の一部として残る。指示文を書くことはそのまま必要であり、その上に会話履歴、検索結果 ([RAG](#/post/ai-rag))、ツール定義などの選択の層が加わった。一度に投入できる量には [コンテキストウィンドウ](#/post/ai-context-window) の限界もある。

## よくある誤解

- プロンプトをうまく書けば [幻覚](#/post/ai-hallucination) がなくなる: 減らすことは可能だが、完全に消すことはできない。根拠文書を一緒に与え、「文書にない場合は知らない」と伝えるのがそれなりに効果的である。この部分は直接数値で確認することはできなかった。
- 秘訣フレーズがある: 読んだ範囲で一貫して通じるフレーズは見つからなかった。あるのは明確さ、例示、構造といった平凡なものだ。
- 長く詳細な方がよい: 必要な情報を漏らさないことと、長く書くことは異なる。長くなると逆に不安定になるという研究もある（コンテキスト記事参照）。
- 一度うまく書けば終わり: モデルが変われば同じプロンプトへの反応も変わる。ガイドでも前世代のプロンプトを移行する際に修正すべき点を別にまとめている。

<details>
<summary>詳しい解説：例示一つ、同じ作業を三つに分割</summary>

レビュー文句を肯定/否定に分ける作業としよう。

zero-shot:

```text
다음 리뷰가 긍정인지 부정인지 한 단어로 답해.
리뷰: 배송은 빨랐는데 포장이 엉망이었다.
```

few-shot（例示 2 つ、タグで区別）:

```text
다음 리뷰를 긍정/부정/혼합 중 하나로 분류해. 한 단어로만 답해.
<examples>
<example>리뷰: 기대 이상이다. 또 살 것 같다. -> 긍정</example>
<example>리뷰: 사흘 만에 고장 났다. -> 부정</example>
</examples>
리뷰: 배송은 빨랐는데 포장이 엉망이었다.
```

例示を入れることで、回答形式は「混合」という選択肢も含めて固定される。上で見た Min 他らの結果を借りれば、この例示で重要なのはラベルの一つ一つよりも、「三つのラベルの内の一つを一つの単語で出す」という枠組みである。

CoT 系は理由を先に書かせるようなものである。

```text
먼저 <reasoning> 태그 안에 근거를 쓰고, 그다음 <answer> 태그 안에 결론만 써.
```

これにより、回答と根拠をコードが別々に抽出しやすくなる。この例示は私が書いたものであり、性能を測定したわけではない。
