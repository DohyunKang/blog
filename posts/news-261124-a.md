Claude Code, Cursor, Codex 같은 에이전트가 내 컴퓨터의 FFmpeg로 영상을 자르고 붙이고 자막을 넣은 뒤, 결과 파일을 스스로 다시 재 본다. 나는 README, SKILL.md, docs/contract.md 앞부분, 최근 커밋 목록을 읽었다. 직접 설치해서 영상을 편집해 보지는 않았다.

## 뭐 하는 물건인지
FFmpeg는 영상·음성 파일을 자르고 변환하는 오래된 명령줄 프로그램이다. 기능은 많은데 옵션이 복잡해서, 에이전트가 명령을 직접 짜면 틀리기 쉽다. README의 "Why" 부분이 이걸 콕 집는다. FFmpeg를 "안다"는 에이전트도 프레임 수를 짐작하고, 컨테이너에 안 맞는 코덱을 고르고, 결과 파일을 열어 보지도 않고 "다 됐다"고 보고한다는 것이다.

그래서 이 레포는 FFmpeg 명령을 에이전트가 짜게 두지 않는다. 자르기(cut), 이어 붙이기(join), 무음 구간 빼기(silence), 화면비 맞추기(fit), 자막(caption), 음량 맞추기(loudness), 플랫폼용 내보내기(export) 같은 일을 하나씩 파이썬 스크립트로 만들어 뒀다. 전부 42개다. 에이전트는 스크립트 이름과 정해진 인자만 넘긴다. 셸을 거치지 않고, 호출하는 쪽이 FFmpeg 필터 문자열을 직접 넣는 것도 받지 않는다. 파이썬 표준 라이브러리만 쓰고, 클라우드나 API 키는 필요 없다.

스킬은 에이전트가 필요할 때 꺼내 읽는 설명서다. [자세히 → 스킬](#/post/ai-skills) 같은 도구를 MCP 서버로도 연다. MCP는 에이전트가 바깥 프로그램의 기능을 도구처럼 부르게 하는 연결 규격이다. [자세히 → MCP](#/post/ai-mcp)

## 먼저 재고, 하고, 다시 잰다
README가 그리는 흐름은 이렇다. 요청이 오면 에이전트가 SKILL.md를 읽고 맞는 스크립트를 고른다. 스크립트는 실행 전에 필요한 FFmpeg 기능이 이 컴퓨터에 있는지 확인하고, FFmpeg를 돌리고, 나온 파일을 다시 측정해서 JSON으로 돌려준다.

설계 원칙 첫 줄이 "Probe first"다. probe는 파일을 실제로 열어 길이, 초당 프레임 수, 해상도, 색 정보, 오디오 트랙을 재는 일이다. 파일 이름을 보고 판단하지 말라는 뜻이다. 또 모든 도구에 `--dry-run`이 있다. 실행할 FFmpeg 명령만 보여 주고 파일은 안 쓰는 옵션이다. 이미 있는 파일을 덮어쓰려면 `--overwrite`를 명시해야 한다.

재미있던 건 결과에 붙는 `unverified` 목록이다. 도구는 잴 수 있는 것만 "확인됨"으로 친다. 길이, 코덱, 음량 같은 건 다시 재서 맞는지 본다. 반대로 화면에 뭐가 보이는지, 자막이 읽히는지, 잘라낸 구간에 말소리가 있었는지, 입 모양과 소리가 맞는지는 파일 측정으로 알 수 없다. 그런 항목은 확인 못 한 것으로 따로 적어 돌려준다. 값을 못 읽으면 통과가 아니라 `not_measured`로 실패 처리한다. 화면이 바뀐 작업이면 look.py로 프레임 몇 장을 모은 이미지(contact sheet)를 만들어 눈으로 보라고 한다.

## 계약서를 코드에서 뽑는다
`contract --json`을 돌리면 42개 도구마다 무엇을 받고, 무엇을 내놓고, 어떤 FFmpeg 부품이 필요하고, 결과를 무엇으로 검증하는지 적힌 문서가 나온다. 이걸 README는 기계가 읽는 계약서(machine-readable contract)라고 부른다. 이 문서는 사람이 따로 관리하지 않고, 각 스크립트의 인자 정의(argparse)에서 자동으로 만든다. MCP 서버의 도구 목록도 여기서 나온다. 그래서 스크립트에 인자를 하나 추가하면 MCP 쪽은 손대지 않아도 바뀐다. 테스트가 이걸 확인한다고 적혀 있다.

문서끼리 숫자가 어긋나는 것도 테스트로 막았다. contract.md에 따르면 README, SKILL.md, package.json에 적힌 "42개"라는 글자를 실제 scripts 폴더의 도구 수와 매번 비교한다. SKILL.md에 "28개"라는 옛 숫자가 도구가 열두 개 늘 동안 그대로 있었던 일이 있어서 넣었다고 한다.

42개를 다 에이전트에게 보여 주지는 않는다. MCP 기본 목록에는 자주 쓰는 12개만 올리고, 나머지 30개는 필요할 때 이름으로 부른다. 4.0부터 이 12개는 stable(다음 메이저 버전까지 인자와 출력 이름을 안 바꿈), 나머지는 beta로 나눴다.

## 왜 지금 화제인지
레포는 9월 초에 만들어졌다. 새로 나온 건 아니다. 다만 이번 주 트렌딩에 계속 있었고, 커밋이 매일 쌓인다. 11월 22일 하루에만 4.5.3부터 4.7.0까지 버전이 여러 번 올라갔고, 내가 본 최신은 4.7.1이다. npm 내려받기는 11월 16~22일 한 주에 17,832회였다. "ffmpeg-skill"을 언급한 X 글(리트윗 제외, UTC 하루 단위)은 11월 17일 103건이 가장 많았고 이후 하루 28~50건이었다. 별이 늘기 시작한 계기는 확인 못 함. Reddit 반응도 확인 못 함.

README에는 자체 평가 기록이 길게 있다. 프롬프트를 수십 개에서 100개까지 늘려 가며 에이전트를 돌리고, 다른 모델이 채점하게 했다. 1.17.0 기준 100개 프롬프트에서 "날것 FFmpeg 호출 0회, 거짓 성공 보고 0회"라고 적혀 있다. 점수만 적은 게 아니라 어디서 틀렸고 다음 버전에서 무엇을 고쳤는지까지 남겨 뒀다. 다만 이건 만든 사람이 직접 잰 숫자다. 다른 사람이 재현했는지는 확인 못 함. README도 전체 실제 영상 묶음 테스트는 Windows에서 아직 안 돌렸다고 밝힌다.

## 입문자 입장에서
영상 편집 자체보다 구조가 볼 만했다. 에이전트한테 "조심해서 해"라고 글로 부탁하는 대신, 틀리기 쉬운 일은 스크립트가 맡고, 결과는 다시 재고, 잴 수 없는 건 잴 수 없다고 적어 돌려준다. 예전에 본 알리바바 Open Code Review도 틀리면 안 되는 단계는 코드가 맡게 하는 쪽이었다. [자세히 → Open Code Review](#/post/news-261115-a)

PM 입장에서 쓸 만한 건 `unverified` 같은 발상이다. "완료"라는 보고 하나만 받는 대신, 무엇은 확인했고 무엇은 사람이 봐야 하는지를 같이 받는다. 에이전트 결과를 검토할 때 어디를 봐야 할지가 줄어든다. README도 이 도구는 편집을 "실행"할 뿐, 어디를 자를지나 결과물이 괜찮은지는 사람이나 다른 에이전트가 정한다고 선을 긋는다.
