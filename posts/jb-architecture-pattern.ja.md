情報処理技術者試験におけるソフトウェアアーキテクチャ単元は、大きく 2 つの塊に分けられます。システム全体をどのような形状で分割するか（アーキテクチャパターン）と、その分割された部品がどれだけ適切に分離されているか（モジュール化、結合度・凝集度）です。前者は名前と特徴をセットで覚える単元であり、後者は順序を暗記する単元です。過去問はそのまま移すのではなく、どのような形式で出題されるのか、解答時に見るべき基準のみを整理します。

## アーキテクチャとは何か

アーキテクチャとは、システムをどのような要素に分割し、その要素同士がどのように接続されているかを定めた大きな枠組みです。コードの 1 行よりも先に決定され、後から変更するコストが高くなります。そのため、要件のうちパフォーマンス・セキュリティ・保守性などの非機能要件もこの段階で決定的なものと言えます。要件をどのように抽出するかについては [詳細 → 要件の確認と分析](#/post/jb-requirements) で別途扱います。

Microsoft の Azure アーキテクチャガイドでは、アーキテクチャスタイルを「特定の特性を共有するアーキテクチャの一群」と説明しています。スタイルは設計に制約をかけます。どのような要素が存在し得るか、要素同士の間でどのような関係が許容されるかを定義しておくようなものです。その制約を守れば、そのスタイルから期待される利点が伴うというわけです。パターン名を暗記する際も、「このパターンは何様な制約を課すか」を一緒に見ると混乱しにくくなります。

## アーキテクチャパターンの整理

| パターン | 核心構造 | 一言特徴 |
|---|---|---|
| レイヤー型 (Layered, N-tier) | プレゼンテーション → ビジネス → データアクセス | 各層は下の層のみを呼び出す |
| MVC | Model / View / Controller | データ・画面・入力処理を分離する |
| パイプ-フィルター | フィルターがパイプで接続 | 前段の出力が次段の入力となる |
| クライアント-サーバー | 要求側と応答側 | サーバーがリソースを持ち、クライアントが要求する |
| イベント駆動 | 生産者 → イベントチャンネル・ブローカー → 消費者 | 生産者と消費者は互いに知らない |
| マイクロサービス | 小さな独立したサービスの複数 | サービスごとに自らのデータを保有し、個別にデプロイする |

表の説明は、各パターンの Wikipedia 項目と Azure アーキテクチャガイドで確認した内容に基づいています。以下では一つずつもう少し詳しく見ていきます。

### レイヤー型

Azure ガイドの基準では、N-tier はアプリケーションを論理的な層と物理的なティアに分け、各層は自らの下の層のみを呼び出す伝統的なエンタープライズ構造です。通常、プレゼンテーション、ビジネスロジック、データアクセス層が現れます。レイヤー型で構築したアプリを移行する際に変更が少ないという利点があり、水平方向に分割することで変更が複数の部分に影響しやすくなるという欠点も同じ文書に記載されています。実際のコードで層をどのように分割するかについては [詳細 → レイアー・アーキテクチャ](#/post/be-layered-architecture) にあります。

### MVC

Wikipedia の説明では、ユーザーインターフェース向けのパターンであり、プログラムロジックを 3 つの部分に分割します。

- Model: アプリケーションのデータとそれに関する規則。画面とは無関係です。
- View: 情報を表示する部分。同じデータを複数の View が表示できます。
- Controller: ユーザー入力を受け取り、Model や View に命令として変換して伝達します。

MVC は 1970 年代後半、Xerox PARC で Trygve Reenskaug が Smalltalk の作業中に作成しました。試験では「入力は Controller、データは Model、画面は View」という対応が正確であれば、ほとんど解けます。MVP や MVVM は MVC から派生した変形として知られています。選択肢に名前が一緒に現れる場合を想定して、MVC の 3 つの役割については確実に押さえておきましょう。

### パイプ-フィルター

処理段階が順次続き、前段の出力が次段の入力となる構造です。段階はフィルター、接続はパイプと呼び、パイプには通常、ある程度のバッファリングが入ります。単純でコストは低くとも、弾力性・障害許容性・拡張性は限定的という評価が Wikipedia にあります。Linux でコマンドを `|` で繋げる様子 떠올리면 記憶しやすいです。

### クライアント-サーバー

サーバーが機能やリソースを提供し、クライアントが要求を送る構造です。Web ブラウザと Web サーバーが最も一般的な例です。サーバーは複数のクライアントに対応するため、サーバー側の負荷や障害が全体に影響を与える点を併せて考えれば、記述式選択肢で役立ちます。

### イベント駆動

Azure ガイドでは、パブリッシュ-サブスクライブモデルを使用すると説明しています。イベント生産者は消費者が誰かを知らずにイベントを作成し、消費者は自分が興味を持つイベントに反応します。両者の間にはイベントチャンネルやブローカーが繋ぎを担います。生産者と消費者の直接的な依存関係が消える代わりに、伝達保証、イベント順序、結果的一貫性が困難な点として挙げられます。

### マイクロサービス

アプリケーションを小さく独立したサービスの集まりに分割する。各サービスは単一のビジネス機能を担当し、独自のデータストアを持つ。API を通じて相互通信を行い、開発・デプロイ・スケーリングをサービス単位で個別に行える。一方、Azure ガイドでは、サービスディスカバリー、データ一貫性、分散システム管理が複雑化すると指摘している。小さなアプリケーションに必ずしも適したアプローチではない。

## パターンを選択する基準

| 状況 | 向いている方 |
|---|---|
| 既に階層型で構築された業務システムを移行する場合 | N-tier |
| 画面とデータロジックを分離したい場合 | MVC |
| データを段階的に変換する場合 | Pipe-Filter |
| リアルタイム処理、緩やかな結合が必要な場合 | Event-driven |
| 複雑なドメインで変更が頻繁に発生する場合 | マイクロサービス |

Azure ガイドの表でも、N-tier は「伝統的なビジネスドメイン、更新頻度が低い」、マイクロサービスは「複雑なドメイン、頻繁な更新」、イベント駆動型は IoT やリアルタイムシステムに適しているとして整理されている。同じ文書では、純粋な構造を追うよりも、制約を少し緩めて現実に合わせる方がよいとも記述されている。

## モジュール化と結合度・凝集度

モジュール化とは、システムを機能単位に分割することである。分割の基準は結合度と凝集度だ。結合度はモジュール同士がどの程度絡み合っているかを示し、凝集度はモジュール内の要素が一つの目的のためにどれだけ集まっているかを表す。良い設計では結合度を低く、凝集度を高く保つ。Wikipedia は、高い凝集度が緩やかな結合と連動する傾向があると説明している。

概念の説明は [詳細へ → 結合度と凝集度](#/post/be-coupling-cohesion) でもあり、ここでは試験用として順序のみを固定しておく。

### 結合度（高い → 低い）

| 順序 | 種類 | 意味 |
|---|---|---|
| 1 | コンテンツ (Content) | 他のモジュールの内部コードや分岐を直接使用する |
| 2 | コモン (Common) | 複数のモジュールが同じグローバルデータを共有する |
| 3 | 外部 (External) | 外部で定義されたデータ形式・通信規約・デバイスインターフェースを共有する |
| 4 | コントロール (Control) | 他のモジュールのフローを制御する値（フラグなど）を渡す |
| 5 | スタンプ (Stamp) | 複合データ構造を共有するが、一部のみを使用する |
| 6 | データ (Data) | パラメータとして基本データのみをやり取りする |

上記の順序と定義は、Wikipedia の Coupling 項目で「最も高い結合から低い結合まで」として列挙されたものを踏襲した。最も望ましいのはデータ結合である。

### 凝集度（高い → 低い）

| 順序 | 種類 | 理由 |
|---|---|---|
| 1 | 機能的 (Functional) | すべての要素が一つの明確に定義された作業に貢献する |
| 2 | 順次的 (Sequential) | 一つの要素の出力が次の要素の入力となる |
| 3 | 通信的/情報 (Communicational) | 同じデータを扱う |
| 4 | 手順的 (Procedural) | 定められた実行順序に従う |
| 5 | 時間的 (Temporal) | プログラムの同じ時点で実行される |
| 6 | 論理的 (Logical) | 同じカテゴリーに属するが、行うことは互いに異なる |
| 7 | 偶然的 (Coincidental) | 特別な理由なく集まっている |

Wikipedia の Cohesion 項目では機能的凝集を最も良い方とし、偶然的凝集を最も低い方に置いている。同じ項目でもこの順位が継続的な改善段階を表しているとは限らないとも言われている。

<details>
<summary>順序を覚える方法</summary>

頭文字をつなげると覚えやすい。結合度は「内・共・外・制・ス・資」、凝集度は「機・順・通・節・時・論・偶」の順序だ。両表は方向が逆なので、結合度は悪い方から、凝集度は良い方からと別々に一度書き留めておくと混乱しにくい。

</details>

## よくあるパターンとその解法

- パターン名の選択：選択肢に「データ・画面・入力分離」「前の出力が次の入力」「下の層のみを呼び出す」などの特徴が一行で提示される。上記の表の一行の特徴と対応させて解く。
- 結合度・凝集度の順序：最も低い結合度は何か、最も高い凝集度は何かを問う。両端だけ正確に覚えておけば解ける。結合度はデータ、凝集度は機能が良い方だ。
- 状況から種類を選ぶ：「2 つのモジュールが同じグローバル変数を使用する」は共通結合、「1 つのモジュールがフラグを渡して他のモジュールの動作を変更する」は制御結合のように説明を見て名前を選ぶ。結合度の表の意味欄を覚えればよい。
- 設計原則のペア付け：低い結合・高い凝集がなぜ良いか問う文句が出る。あるモジュールを変更した際に修正すべき箇所が減るという観点で読むと、ほぼ正しい。

パターン単元は名前だけを暗記すると混乱しやすいので、上記のように一行の特徴とセットにしておく方が早い。

## よくある誤解

- 결합도는 0 이어야 한다: 모듈 간에 아무런 데이터나 제어 흐름이 오가지 않으면 시스템이 성립하지 않는다. 따라서 목표는 연결을 최소화하는 것이다.
- 마이크로서비스가 계층형 아키텍처보다 항상 낫다: Azure 가이드에서도 도메인이 복잡하고 잦은 변경이 있을 때 적합하며, 운영 성숙도가 필요하다고 명시한다.
- MVC 는 웹에서만 사용한다: MVC 는 사용자 인터페이스를 위한 패턴으로 설명되며, 웹 프레임워크에서 흔히 활용될 뿐이다.
- 응집도가 높으면 모듈이 작다: 이는 크기와는 별개의 개념이다. 하나의 기능만 담당하더라도 처리할 수 있는 줄 수가 많아도 응집도는 높다.
