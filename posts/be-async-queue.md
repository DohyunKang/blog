요청을 받자마자 모든 걸 끝내려 하지 않고, 할 일을 큐에 적어 두고 먼저 응답한 뒤 워커가 뒤에서 처리하는 게 비동기 처리의 기본 모양이다. 편해지는 대신 재시도와 중복이라는 숙제가 따라온다.

## 동기와 비동기

회원가입을 예로 들면 하는 일이 이렇다. DB에 저장하고, 환영 메일을 보내고, 통계를 갱신한다. 전부 요청 안에서 순서대로 하면 동기 처리다. 메일 서버가 3초 늦으면 사용자도 3초를 기다리고, 메일 서버가 죽으면 가입 자체가 실패한다.

비동기는 "DB 저장만 하고 응답, 메일은 나중에"로 나누는 것이다. 나중에 할 일은 어딘가에 적어 둬야 하는데, 그 적어 두는 곳이 큐다. 요청 흐름 자체는 [요청이 처리되는 흐름](#/post/be-request-flow)에 정리해 뒀다.

| | 동기 | 비동기 |
|---|---|---|
| 응답 시점 | 일이 다 끝난 뒤 | 일을 접수한 뒤 |
| 느린 외부 서비스 | 사용자가 같이 기다림 | 워커가 따로 기다림 |
| 실패했을 때 | 사용자가 바로 에러를 봄 | 사용자는 모르고, 시스템이 재시도해야 함 |
| 결과 확인 | 응답에 들어 있음 | 상태 조회나 알림으로 따로 알려야 함 |

마지막 줄이 은근히 번거롭다. 접수만 하고 끝내면 "처리됐나?"를 사용자에게 알릴 방법이 따로 필요하다.

## 메시지 큐가 뭔가

메시지 큐는 보내는 쪽(프로듀서)과 받는 쪽(컨슈머, 흔히 워커)을 중간에서 이어 주는 줄이다. 프로듀서는 메시지를 큐에 넣으면 끝이고, 워커가 자기 속도로 꺼내 처리한다. 둘이 서로를 직접 알 필요가 없어서 [모듈 결합도](#/post/be-coupling-cohesion)를 낮추는 데도 쓰인다.

```
API 서버 --(메시지 넣기)--> [ 큐 ] --(꺼내기)--> 워커 1
                                      └-------> 워커 2
```

- 트래픽이 한꺼번에 몰려도 큐가 완충한다. 워커가 못 따라가면 큐가 길어질 뿐 서버가 바로 죽지는 않는다.
- 워커를 늘리면 처리량이 늘어난다. API 서버와 따로 늘릴 수 있다.
- 워커가 잠깐 죽어도 메시지는 큐에 남아 있다.

대표적인 구현은 RabbitMQ, Amazon SQS, Kafka 같은 것들이다. 이 글은 앞의 둘 문서에서 확인한 동작을 기준으로 적었다. Kafka는 구조가 달라서(로그 기반) 여기서는 다루지 않는다.

## 워커가 메시지를 가져가는 방식

여기가 핵심이다. 워커가 메시지를 받자마자 큐에서 지워 버리면, 처리 중에 워커가 죽을 때 메시지가 사라진다. 그래서 큐들은 "받았다"와 "끝냈다"를 나눈다.

RabbitMQ는 수동 ack 모드에서 워커가 처리를 끝내고 `ack`를 보내야 메시지를 버린다. `nack`나 `reject`를 보내면 `requeue` 옵션에 따라 다시 큐에 넣거나, 데드 레터 교환기가 설정돼 있으면 거기로 보내고, 없으면 버린다. ack 없이 연결이 끊기면 그 메시지는 자동으로 다시 큐에 들어가고, 재전달된 메시지에는 `redeliver` 표시가 붙는다. 자동 ack 모드는 보내는 순간 전달된 것으로 치기 때문에, 처리 전에 연결이 끊기면 메시지를 잃는다. 문서도 이 모드를 많은 용도에 안전하지 않다고 적는다.

SQS는 방식이 조금 다르다. 메시지를 받으면 큐에서 지워지지 않고 일정 시간 다른 워커에게 보이지 않을 뿐이다. 이 시간이 가시성 타임아웃이고 기본값은 30초다. 그 안에 워커가 `DeleteMessage`로 지우지 못하면 메시지가 다시 보이게 되고, 같은 워커든 다른 워커든 다시 받아 간다. 처리가 오래 걸리면 `ChangeMessageVisibility`로 시간을 늘릴 수 있는데, 최대 12시간이라는 한도가 있다.

이름만 다르지 구조는 같다. 끝났다고 확인해 주기 전까지는 큐가 메시지를 쥐고 있다가, 확인이 없으면 다시 내준다.

## 그래서 중복이 생긴다

위 구조에서 피할 수 없는 일이 하나 있다. 워커가 메일을 보내고, ack를 보내기 직전에 죽었다고 하자. 큐 입장에서는 처리됐는지 알 길이 없으니 다시 내준다. 다른 워커가 같은 메일을 또 보낸다.

SQS 문서는 가시성 타임아웃이 있어도 at-least-once 전달 모델이라서 같은 메시지가 두 번 이상 올 수 있다고 분명히 적는다. RabbitMQ 문서는 "at-least-once"라는 말을 쓰지는 않지만, 재전달이 일어나니 소비자는 멱등해야 한다는 취지로 쓴다. 즉 "정확히 한 번"을 큐에 기대하지 말고 "최소 한 번 오니까 두 번 와도 괜찮게 만들자"로 가는 게 보통이다.

## 멱등성

멱등성은 같은 요청을 여러 번 해도 결과가 한 번 한 것과 같다는 성질이다. `balance = 100`은 몇 번을 해도 100이지만, `balance += 100`은 할 때마다 달라진다. 후자 같은 일을 워커에서 해야 하면 한 번 처리했다는 기록을 따로 남겨야 한다.

Stripe API가 쓰는 방식이 알기 쉬웠다. 클라이언트가 `Idempotency-Key`를 정해서 보내면, 서버는 첫 요청의 상태 코드와 본문을 저장해 두고 같은 키의 재시도에는 저장된 응답을 그대로 돌려준다. 키는 최대 255자이고 UUID v4 같은 랜덤 문자열을 권장한다. v1 기준으로 24시간이 지난 키는 지워질 수 있고, 같은 키에 파라미터가 다르면 에러를 낸다. 외부 API 이야기지만, 큐 워커 안에서도 메시지 id를 키로 삼아 똑같이 할 수 있다.

[API와 REST](#/post/be-api-rest)에서 GET은 원래 멱등이고 POST는 아니라고 정리했는데, POST가 재시도될 수 있는 환경이면 이런 키가 필요해진다.

## 재시도와 데드 레터 큐

처리 중 에러가 나면 다시 시도한다. 다만 바로 계속 재시도하면 이미 힘든 외부 서비스를 더 괴롭히니까 간격을 점점 늘리는 지수 백오프를 쓰는 경우가 많다. 일시적 장애는 재시도로 낫지만, 메시지 자체가 깨진 경우는 몇 번을 해도 안 된다.

그래서 횟수 제한을 두고, 넘으면 별도 큐로 옮긴다. 그게 데드 레터 큐(DLQ)다. SQS에서는 redrive policy의 `maxReceiveCount`가 "소비자가 이 메시지를 몇 번 받으면 DLQ로 옮길지"를 정한다. 값을 너무 낮게(예: 1) 잡으면 한 번 실패로 바로 DLQ에 가니까 재시도할 여지를 줄 만큼은 높여야 한다고 문서가 적는다. DLQ에 쌓인 메시지는 로그를 보며 원인을 분석하거나, 고친 뒤 redrive로 원래 큐로 되돌린다. DLQ 보존 기간은 원래 큐보다 길게 잡는 게 좋다고도 한다. FIFO 큐에서 DLQ를 쓰면 순서가 깨질 수 있다는 주의도 있다.

DLQ는 있는 것만으로는 소용이 없고, 쌓였을 때 알림이 오게 해 둬야 한다. [에러 처리와 로깅](#/post/be-error-logging)과 이어지는 부분이다.

## 직접 돌려 본 예시

개념을 코드로 줄여 봤다. 큐는 deque, 워커는 루프 하나, 메일 전송은 30% 확률로 실패하게 했다. 같은 id의 메시지(m3)를 일부러 두 번 넣었다.

<details>
<summary>코드와 결과 (python으로 실행 확인함)</summary>

```python
import random
from collections import deque

random.seed(1)
queue = deque()
dlq = []
done = set()       # 처리 끝낸 메시지 id (멱등성 키)
sent_mail = []     # 부수효과

def send_mail(msg):
    # 30% 확률로 일시 실패
    if random.random() < 0.3:
        raise RuntimeError("smtp timeout")
    sent_mail.append(msg["to"])

def handle(msg):
    if msg["id"] in done:        # 이미 처리한 id면 건너뜀
        return
    send_mail(msg)
    done.add(msg["id"])

MAX = 3
for i in range(10):
    queue.append({"id": f"m{i}", "to": f"user{i}", "tries": 0})
queue.append({"id": "m3", "to": "user3", "tries": 0})  # 중복 발행

while queue:
    msg = queue.popleft()
    try:
        handle(msg)
    except Exception:
        msg["tries"] += 1
        if msg["tries"] >= MAX:
            dlq.append(msg["id"])
        else:
            queue.append(msg)

print("sent", len(sent_mail), "unique", len(set(sent_mail)))
print("dlq", dlq)
```

실행 결과는 아래와 같았다.

```
sent 10 unique 10
dlq []
```

메시지 11개(그중 하나는 중복)를 넣었는데 메일은 10통, 수신자는 10명이다. 중간에 실패한 메시지는 뒤로 다시 붙어 재시도됐고, 중복 m3은 `done`에 id가 있어서 건너뛰었다. 시드 값 때문에 이번에는 3번 연속 실패한 메시지가 없어 DLQ는 비었다. 실패 확률을 올리면 DLQ에 들어가는 것도 볼 수 있을 텐데, 그건 돌려 보지 않았다.

이 코드는 개념용이다. `done`이 메모리에 있어서 워커가 죽으면 사라지고, "메일 보냄"과 "done에 기록"이 한 트랜잭션이 아니라서 그 사이에 죽으면 여전히 중복이 날 수 있다. 실제로는 done을 DB에 두고 유니크 제약으로 막는 식이 된다.

</details>

## 흔한 오해

- 큐를 쓰면 메시지가 정확히 한 번 처리된다: 위에서 본 것처럼 최소 한 번이 기본이다.
- 큐가 있으면 순서가 보장된다: SQS 표준 큐처럼 순서를 보장하지 않는 것도 있고, FIFO 큐는 메시지 그룹 id 단위로 순서를 지킨다. 필요하면 큐 종류를 확인해야 한다.
- 비동기로 바꾸면 무조건 빨라진다: 사용자가 기다리는 시간은 줄지만 전체 처리량이 느는 건 아니다. 워커가 못 따라가면 큐만 길어진다.
- 큐는 항상 써야 한다: 응답에 결과가 바로 필요한 일이나 단순한 서비스에는 동기가 낫다. 재시도, 중복 처리, 상태 확인까지 직접 감당해야 하니 복잡도가 늘어난다.
