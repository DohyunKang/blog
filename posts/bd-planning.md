빅데이터분석기사 필기 목차에서 데이터분석 계획은 두 덩어리다. 분석방안 수립(분석 로드맵 설정, 분석 문제 정의, 데이터 분석 방안)과 분석 작업 계획(데이터 확보 계획, 분석 절차 및 작업 계획)이다. 분석을 시작하기 전에 무엇을 풀지 고르고, 어떤 순서로 하고, 데이터와 위험을 어떻게 다룰지 정하는 단계라서 계산 문제보다 용어와 순서를 묻는 쪽이다. 시험 일정과 응시료는 공식 사이트에서 확인하면 된다. 이 글은 단원별 핵심 개념, 보기에서 자주 갈리는 지점, 푸는 방식 위주로 정리했다.

ADsP를 먼저 본 사람이면 겹치는 내용이 많다. 과제 발굴과 우선순위는 [자세히 → 분석 과제와 마스터플랜](#/post/adsp-task-masterplan)에, 방법론 전반은 [자세히 → 분석 방법론](#/post/adsp-methodology)에 따로 정리해 두었다. 이 글은 빅데이터분석기사 목차에 맞춰 순서를 다시 잡았다.

| 분석 로드맵 | 어떤 순서로 할 것인가 | 시급성, 난이도, 3단계 이행 |

| 위험 계획 | 문제가 생기면 어떻게 하나 | 식별, 회피·전이·완화·수용 |

## 분석 문제 정의

과제를 찾는 방식은 크게 두 가지다.

| | 하향식 | 상향식 |
|---|---|---|
| 출발점 | 풀어야 할 문제가 이미 있다 | 문제를 모르고 데이터부터 본다 |
| 쓰는 곳 | 분석 대상이 분명할 때 | 새로운 통찰을 찾을 때 |
| 진행 | 문제 탐색 → 문제 정의 → 해결방안 탐색 → 타당성 검토 | 가설 생성 → 실험 → 실제 환경 테스트 → 가설 확인 |

하향식은 문제 탐색을 비즈니스 모델 기반과 외부 참조 모델 기반으로 나눈다. 

분석 기획 단계에서 미리 따져 볼 것은 가용 데이터, 적절한 유스케이스, 장애요소 세 가지로 정리되어 있다. 장애요소에는 비용, 정확도, 조직 역량, 변화 관리가 들어간다.

<details>
<summary>해결방안 네 가지: 기존 시스템과 분석 역량의 조합</summary>

과제를 풀 방법은 기존 시스템이 있는지, 분석 역량이 있는지로 갈린다.

| 기존 시스템 | 분석 역량 | 방향 |
|---|---|---|
| 있음 | 있음 | 기존 시스템과 인력을 활용 |
| 있음 | 없음 | 교육하거나 채용 |
| 없음 | 있음 | 시스템 고도화 |
| 없음 | 없음 | 전문 업체 아웃소싱 |

</details>

## 분석 로드맵: 순서 정하기

찾은 과제를 한꺼번에 할 수는 없어서 우선순위를 정한다. 고려하는 요소는 전략적 중요도, 비즈니스 성과(ROI), 실행 용이성이다. 이걸 두 축으로 줄이면 시급성과 난이도가 된다.

| 축 | 보는 것 | ROI 관점 |
|---|---|---|
| 시급성 | 전략 목표와의 연결, KPI 목표 가치. 지금 필요한가, 나중에 필요한가 | 비즈니스 효과 |
| 난이도 | 데이터 획득·저장·가공 비용, 분석 적용 비용, 분석 수준 | 투자비용 |

두 축을 곱하면 네 칸이 나온다.

| 시급성 | 난이도 | 순서 |
|---|---|---|
| 현재 | 쉬움 | 가장 먼저 |
| 현재 | 어려움 | 시급성 우선이면 두 번째 |
| 미래 | 쉬움 | 난이도 우선이면 두 번째 |
| 미래 | 어려움 | 가장 나중 |

가운데 두 칸의 순서는 시급성을 먼저 보느냐 난이도를 먼저 보느냐에 따라 바뀐다. 사분면 번호(Ⅰ~Ⅳ)는 자료마다 다르게 붙이기 때문에, 번호로 외우기보다 시급성과 난이도라는 속성으로 기억하는 쪽이 안전하다. 현재 필요한데 어려운 과제는 데이터 양이나 분석 범위를 줄여 난이도를 낮춘 뒤 먼저 적용할 수도 있다.

이 순서 규칙을 pandas로 옮겨 보면 이런 모양이다. 시급성 우선 기준이고, 직접 실행해서 확인했다.

```python
import pandas as pd

tasks = pd.DataFrame({
    "과제": ["이탈 예측", "재고 수요 예측", "고객 군집", "챗봇 로그 분석"],
    "시급성": ["미래", "현재", "미래", "현재"],
    "난이도": ["어려움", "어려움", "쉬움", "쉬움"],
})

# 시급성 우선: 현재가 먼저, 같으면 쉬운 것이 먼저
tasks["u"] = tasks["시급성"].map({"현재": 0, "미래": 1})
tasks["d"] = tasks["난이도"].map({"쉬움": 0, "어려움": 1})
tasks = tasks.sort_values(["u", "d"]).drop(columns=["u", "d"]).reset_index(drop=True)
tasks.index += 1
print(tasks)
```

실행 결과는 다음과 같다.

```
         과제 시급성  난이도
1  챗봇 로그 분석  현재   쉬움
2  재고 수요 예측  현재  어려움
3     고객 군집  미래   쉬움
4     이탈 예측  미래  어려움
```

난이도를 먼저 보는 기준으로 바꾸려면 정렬 키에서 u와 d의 위치만 바꾸면 된다. 시험에서는 코드가 나오지 않지만, 두 축의 우선순위가 정렬 키의 순서라고 생각하면 가운데 두 칸이 왜 바뀌는지 쉽게 이해된다.

로드맵은 세 단계로 이행하는 모양으로 정리된다.

| 단계 | 내용 |
|---|---|
| 1. 데이터 분석 체계 도입 | 분석 기회 발굴, 과제 정의, 로드맵 수립 |
| 2. 데이터 분석 유효성 검증 | 분석 알고리즘 설계, 아키텍처 설계, 파일럿 수행 |
| 3. 데이터 분석 확산 및 고도화 | 변화 관리, 시스템 구축, 유관 시스템 고도화 |

적용 범위와 방식을 정할 때는 업무 내재화 수준, 분석 데이터 적용 수준(내부 데이터만 쓸지 외부·비정형 데이터까지 넓힐지), 기술 적용 수준(기존 기술 활용인지 새 기술 도입인지)을 고려한다. 세부 이행 계획은 분석이 반복해서 다듬는 성격이라, 데이터 수집·준비는 순차로 하고 모델링 단계만 반복하는 혼합형이 많이 쓰인다고 한다.

접근 방식도 둘로 나뉜다. 과제 중심은 Speed & Test, Quick-Win, Problem Solving이고, 마스터 플랜은 Accuracy & Deploy, Long Term View, Problem Definition이다. 둘의 키워드가 서로 바뀐 보기가 나오기 쉬워서 왼쪽 세 개는 빠르게, 오른쪽 세 개는 길게 보는 쪽으로 묶어 두면 구분이 된다.

## 분석 절차: 방법론 5단계

분석 작업 계획에서 분석 절차는 방법론의 5단계로 다룬다. 계층은 단계(Phase) → 태스크(Task) → 스텝(Step) 순서다. 단계는 산출물을 만들고, 태스크는 단계를 이루는 단위 활동이고, 스텝은 입력·처리·출력으로 이루어진 단위 프로세스다.

| 순서 | 단계 | 주요 태스크 | 주요 산출물 |
|---|---|---|---|
| 1 | 분석 기획 | 비즈니스 이해 및 범위 설정, 프로젝트 정의 및 계획 수립, 프로젝트 위험 계획 수립 | 프로젝트 범위 정의서(SOW), 프로젝트 계획서 |
| 2 | 데이터 준비 | 필요 데이터 정의, 데이터 스토어 설계, 데이터 수집 및 정합성 점검 | 데이터 정의서, 데이터 스토어 |
| 3 | 데이터 분석 | 분석용 데이터 준비, 텍스트 분석, 탐색적 분석, 모델링, 모델 평가 및 검증 | 분석용 데이터셋, 모델 평가 보고서 |
| 4 | 시스템 구현 | 설계 및 구현, 시스템 테스트 및 운영 | 시스템 설계서, 운영 매뉴얼 |
| 5 | 평가 및 전개 | 모델 발전 계획 수립, 프로젝트 평가 및 보고 | 모델 발전 계획서, 최종 보고서 |

분석 기획이 제일 앞이고 데이터 준비보다 먼저다. 시스템 구현은 평가 및 전개보다 앞선다. 각 단계는 기준선(baseline)으로 잡고 버전 관리로 통제한다. 분석 기획 단계 안의 태스크와 스텝을 따로 보면 이렇다.

| 태스크 | 스텝 |
|---|---|
| 비즈니스 이해 및 범위 설정 | 비즈니스 이해 → 프로젝트 범위 설정(SOW 작성) |
| 프로젝트 정의 및 계획 수립 | 데이터 분석 프로젝트 정의 → 프로젝트 수행 계획 수립 |
| 프로젝트 위험 계획 수립 | 데이터 분석 위험 식별 → 위험 대응 계획 수립 |

CRISP-DM이나 KDD 같은 다른 방법론과 비교하는 보기는 [자세히 → 분석 방법론](#/post/adsp-methodology)을 같이 보면 된다.

## 데이터 확보 계획

목차에서 데이터 확보 계획은 분석 작업 계획 아래에 있고, 필요한 데이터를 어떻게 확보할지 정하는 일이다. 방법론 5단계로 옮기면 2단계 데이터 준비의 태스크인 필요 데이터 정의, 데이터 스토어 설계, 데이터 수집 및 정합성 점검과 이어진다. 그래서 필요 데이터 정의와 데이터 스토어 설계가 분석 기획 단계의 태스크로 나온 보기는 틀린 보기다. 데이터 확보 계획은 분석 기획에서 세우지만, 필요 데이터를 정의하고 스토어를 설계하는 실제 태스크는 데이터 준비 단계에 속한다.

수집 방식(스크래핑, ETL, API, 로그 수집)과 저장소는 다음 단원인 [자세히 → 데이터 수집과 저장](#/post/bd-collection-storage)에서 따로 다룬다.

## 위험 계획

프로젝트 위험 계획 수립 태스크는 두 스텝이다. 먼저 데이터 분석 위험을 식별하고, 그다음 대응 계획을 세운다. 대응 방법은 네 가지다.

| 대응 | 뜻 |
|---|---|
| 회피 (Avoid) | 위험 요인 자체를 제거하거나 피한다 |
| 전이 (Transfer) | 위험에 따른 책임이나 영향을 제3자에게 넘긴다 |
| 완화 (Mitigate) | 위험의 발생 가능성이나 영향을 줄인다 |
| 수용 (Accept) | 위험을 받아들이고 그대로 감수한다 |

관리(Management)는 대응 방법의 종류가 아니다. 보기에 "위험 관리"가 대응 방법으로 끼어 있으면 오답이다.

<details>
<summary>대응 방식 짝짓기 연습: 예시 상황</summary>

상황을 하나 만들어서 네 가지에 대응시켜 보면 구분이 빠르다. 예시일 뿐이고 시험 문제와는 무관하다.

| 위험 | 대응 | 이유 |
|---|---|---|
| 개인정보가 섞인 데이터 | 회피 | 그 데이터를 아예 쓰지 않는다 |
| 데이터 적재가 늦어질 수 있음 | 완화 | 일정에 여유를 두고 일부를 먼저 적재한다 |
| 모델 정확도가 목표에 못 미칠 수 있음 | 수용 | 그대로 진행하고 결과를 보고한다 |
| 분석 인력이 부족함 | 전이 | 외부 업체에 맡긴다 |

</details>

## WBS는 어디서 쓰나

WBS(작업 분할 구조)는 프로젝트 정의 및 계획 수립 태스크의 프로젝트 수행 계획 수립 스텝에서 작성한다. 일정, 인력, 예산 계획과 함께 세운다. 방법론의 스텝은 WBS의 워크 패키지에 해당한다. 분석 주제를 정의하거나 모델링 방안을 세우는 일은 WBS를 작성하는 단계의 일이 아니다.

## 자주 틀리는 부분

- 필요 데이터 정의나 데이터 스토어 설계를 분석 기획 단계의 태스크로 쓴 보기. 데이터 준비 단계다.
- 위험 대응 방법에 관리를 넣은 보기. 회피, 전이, 완화, 수용 네 가지다.
- 과제 중심과 마스터 플랜의 키워드를 서로 바꾼 보기.
- 시급성과 난이도 두 칸의 순서를 사분면 번호로만 외워서 자료마다 달라지는 경우.
- 하향식 4단계의 순서를 섞은 보기. 문제 탐색, 문제 정의, 해결방안 탐색, 타당성 검토 순이다.
- 방법론 5단계의 순서를 바꾼 보기. 분석 기획, 데이터 준비, 데이터 분석, 시스템 구현, 평가 및 전개다.

기출문제는 원문을 옮기지 않고 보기에서 갈리는 지점만 적었다. 푸는 방식은 5단계 표를 먼저 써 놓고, 보기에 나온 태스크가 어느 단계 칸에 들어가는지부터 확인하는 것이다. 위험 대응은 네 단어를 외우면 되는 부분이다.
