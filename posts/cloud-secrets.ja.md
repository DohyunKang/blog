シークレットはコードではなく、実行環境から渡すものであり、たとえ漏洩しても被害が長引かないように構造を変更できる仕組み作りこそが管理のすべてに近い。

## 設定とシークレット

アプリを動かすためにはコード以外にも必要な値がある。DB アドレス、外部サービス API キー、サーバーホスト名などがそれだ。12-Factor アプリメントではこれを「設定 (config)」と呼び、デプロイごとに変わる可能性があるすべてのものを定義する。アプリ内部の構造をつなぐルーティング設定などはデプロイごとに変更されないため、ここには含まれない。

シークレットは設定のうち、漏らしてはいけないものである。パスワード、API キー、トークン、証明書個人鍵などがそれだ。DB アドレスは設定だが、DB パスワードはシークレットである。両者を同じように扱って事故が起きる。

ドキュメントが提案する基準は一つだ。今このコードをいつでも公開しても資格証明が漏れないか。漏れないのであれば、設定がコードから適切に分離されているということだ。

## 環境変数が基本である理由

12-Factor は設定を環境変数に置くよう述べている。理由は三つ記載されている。

- コードを触らずにデプロイごとに値だけ変更できる。
- 設定ファイルとは異なり、誤ってリポジトリにコミットされる可能性が低い。
- 言語やオペレーティングシステムに関係なく使える。

比較対象はコードに埋め込んだ定数と、コミットしない設定ファイル（Rails の database.yml など）である。定数は分離原則を無視し、設定ファイルはマシだが誤ってコミットされてしまう可能性があり、形式がフレームワークごとにばらけているという。

コードから読み取る側は単純だ。

```python
import os

def need(name):
    v = os.environ.get(name)
    if not v:
        raise SystemExit(f"{name} 없음")
    return v

db_url = need("DB_URL")      # 없으면 시작 단계에서 바로 멈춘다
```

値がない場合に静かにデフォルト値に遷移せず、起動時に停止させておけば、デプロイしてからしばらく経ってから発覚する問題を減らせる。上記のコードは値を入れた場合と入れなかった場合の両方を実行して動作を確認した。

12-Factor が避けるべき方法もある。`development`, `test`, `production` のように名付けた設定の束をコードに置くことだ。ドキュメントはこの方法を「きれいに拡張できない」と述べている。ステージングや個人環境が増えると組み合わせが乗法的に増え、デプロイが壊れやすくなる。環境名で束ねず、変数を一つずつデプロイごとに独立して管理するよう促している。

## .env ファイル

ローカル開発では環境変数を毎回ターミナルに入力するのが面倒なため、`.env` ファイルに `KEY=value` の行として記述しておき、ツールが起動した際に読み込んで環境変数として設定する。ファイル一つだけなので魔法ではない。

守るべき点は二つある。第一に `.gitignore` に `.env` を入れること。第二にリポジトリには値を空にした `.env.example` だけをアップロードして、必要な変数のみを知らせることだ。

[詳細 → CI/CD とデプロイ戦略](#/post/cloud-cicd) で見るように、運用サーバーや CI では `.env` ファイルを使うよりも、そのプラットフォームが注入する方式が一般的である。ファイルをサーバーに置くと、そのファイルがまた一つの管理対象になる。

## 環境変数だけでは不足する点

OWASP のシークレット管理チートシートは環境変数を「最後の手段」に近いものとして捉えている。ログやクラッシュダンプに付随して漏れる可能性があるためだ。ドキュメントではシークレットをコード、Dockerfile、設定ファイルに埋め込まず、オーケストレーターが注入するか実行時に取得するよう述べている。[詳細 → Docker](#/post/cloud-docker) ではイメージにシークレットを焼き付ける誤りがなぜ危険か引き続き見ることができる。

環境変数の弱点をまとめると以下の通りだ。

| 懸念点 | 環境変数だけを使う場合 |
|---|---|
| 誰が読んだか | 記録が残らない |
| 変更 | アプリを再起動しないと反映されない |
| アクセス制限 | プロセス内ではすべて見える |
| 漏洩 | ログ・ダンプ・デバッグ出力に混じりやすい |

そのため規模が大きくなるとシークレット専用のストレージを使う。

## シークレットマネージャー

AWS Secrets Manager のドキュメントでは、このサービスを DB 資格証明、アプリ資格証明、OAuth トークン、API キーなどのシークレットをライフサイクル全体を通じて管理し、取得・ローテーションするためのツールとして紹介している。核心となるアイデアは、コードに埋め込んだ資格証明を実行時の呼び出しに変更することだ。アプリが必要とする時にサービスに問い合わせて値を受け取る。

これにより得られる効果はいくつかある。

- 値がアプリと一緒には保存されないため、アプリを覗き見できる人がすぐにシークレットを取得することはできない。
- 自動ローテーションスケジュールを設定でき、値がアプリに埋め込まれていないため変更してもアプリを再デプロイする必要がない。
| 誰がいつ取得したかの記録が残る。ドキュメントでは CloudTrail をオンにすれば API 呼び出しログが得られると記載している。

注意点もドキュメントにある。このサービスは使用量に応じて課金され、独自の KMS キーで暗号化したりローテーションに Lambda を使ったりすると別途費用がかかる。また AWS 資格証明は IAM、暗号化キーは KMS、証明書は ACM のように種類ごとに適切なサービスが別々にあるという。シークレットマネージャーがすべての秘密を入れる万能の金庫ではない。

他のクラウドサービスやツール（Google Secret Manager、HashiCorp Vault など）も同様の役割を果たしますが、今回はこれらのドキュメントは開いていませんでした。

## ロテーションと最小権限

OWASP チートシートの核心となる推奨事項はおよそ以下の通りです。

- **中央集管化**: コード、設定ファイル、ツールに散らばらせるのではなく、専用のシステムで管理する。
- **ロテーション**: 定期的に更新し、可能であれば自動化して盗まれた認証情報の有効期間を短くする。
- **最小権限**: シークレットごとに読み書きできる主体を絞る。
- **動的シークレット**: セッションごとに短期間使用され、期限切れとなる認証情報を発行する。ドキュメントは、アプリを再起動しても盗まれた認証情報が無効化されないことを指摘している。
- **監査**: 誰が要求し承認されたか、いつ使用されたかを記録し、ログ自体も改ざんされないように守る。

ロテーションを当初は面倒な定期作業だと理解していましたが、ドキュメントが示唆するのはその逆でした。漏れを防ぐことが目的ではなく、漏れたとしても利用可能な期間を短くすることが目的です。一度設定すれば永久に使うキーは、更新の瞬間から常に危険であり、数日有効なキーなら更新すればすぐに期限切れになります。

## 流出時の対応

GitHub のドキュメントに基づくと、シークレットスキャンではすべてのブランチの Git ヒストリー、イシュー、PR、ディスカッション、ウィキまでを走査して露出されたキーを検出し、検出するとリポジトリのセキュリティタブに警告を作成します。公開リポジトリは無料ですが、組織の非公開リポジトリについては別途製品（GitHub Secret Protection）が必要とのことです。

流出への対応手順は 2 つのドキュメントがほぼ同じです。

1. その認証情報を即時破棄し、新しいものを発行する。
2. コード、ログなど露出された場所から削除する。
3. いつどのように漏れ、何を使用了かを記録する。

GitHub のドキュメントでは、Git ヒストリーから削除するには時間がかかり、すでに破棄済みであれば通常不要だと言っています。コミットを削除するよりもキーを無効化することが優先です。すでに誰かがコピーして持ち去っている可能性があるためです。

## よくある誤解

- `.env` を `.gitignore` に追加すれば安全である: 将来的なコミットは防げますが、すでにコミットされたものはヒストリーに残ります。また、ログやイメージを通じて漏れる経路もそのまま残っています。
- リポジトリが非公開なのでキーを入れてもよい: 12-Factor の基準は「公開してもよいか」です。非公開は単に現在のアクセス権限が狭いだけのことです。
- 環境変数は暗号化されている: いいえ。プロセスと同じ権限を持つものが読み取ることができます。
- シークレットマネージャーを使えばそれで終わり: マネージャーへのアクセス権限が広ければ、金庫のドアを開けておいたようなものです。最小権限と監査を併せて行う必要があります。
- 削除すれば消える: コピーされている可能性があるため、破棄が先です。

<details>
<summary>詳細な解説: どの段階まで行う必要があるか</summary>

ドキュメント自体が段階を直接分けていないため、以下は読んだ内容を順に並べたものです。

1. コードに埋め込まれた値をすべて環境変数に移します。これだけでコード公開の基準を満たします。
2. ローカル環境では `.env` + `.gitignore` + `.env.example` を採用します。
3. 展開環境ではプラットフォームが注入するようにします（CI シークレット、コンテナオーケストレーターのシークレットなど）。
4. 値が多い場合やチームが大きくなったらシークレットマネージャーに移し、アプリの実行時に取得するようにします。
5. ロテーション周期と流出対応手順（誰が破棄し、誰に通知するか）をドキュメントで定めます。

小さな個人プロジェクトでは 1〜3 で十分か、4 から進めるかはサービスの性質や料金次第です。シークレットマネージャーは使用量に応じて課金されるため、数が少ない場合はコスト対効果を検討する必要があります。

</details>
