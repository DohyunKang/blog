This morning ag-ui-protocol/ag-ui was on GitHub's weekly Trending list: 2,966 stars this week, 21,562 in total (checked the morning of November 25). AG-UI is an open spec for the data that flows between an AI agent and the app screen a person looks at. I read the README, the concept docs (architecture, tools, state, interrupts), the 1.0 changes page, and the recent commits. I didn't run a server myself.

## What it specifies
A normal web request sends one request and gets one response. Agents don't work like that. They stream text bit by bit, call tools halfway, stop to wait for a human, and spawn subagents. The README opens with this: every framework shows that to the UI differently, so every app ended up writing its own wiring.

AG-UI turns all of it into one stream of events. An event is a short message saying "this just happened." The agent emits typed events in order, and the app renders them. Whether the agent was built with LangGraph or CrewAI, the app code stays the same.

The README's diagram of where it sits helped. MCP gives agents tools and data, A2A lets agents work with each other, and AG-UI brings agents to users. The claim is that the three don't overlap. MCP is the spec that lets an agent call outside programs as tools. [More → MCP](#/post/ai-mcp)

## How it's built
The start is simple. The app sends an HTTP POST with a `RunAgentInput` (thread ID, run ID, messages so far, the tools the app offers, shared state), and the agent streams events back. The default transport is SSE, a web standard where the server keeps one connection open and keeps pushing text. Since 1.0 a binary transport using Protobuf is also part of the spec.

Events come in a few groups.
- Run start and end: `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`
- Answer text: `TEXT_MESSAGE_START` → `CONTENT` (chunks) → `END`
- Tool calls: `TOOL_CALL_START` → `ARGS` (argument JSON in chunks) → `END` → `RESULT`
- Shared state: `STATE_SNAPSHOT` (all of it), `STATE_DELTA` (only what changed)

The Python server in the README is about 30 lines, and all it does is send a start event, three text events, and an end event. That's roughly the minimum the spec asks for.

## The app holds some of the tools
The part that stood out most was how tools are split in two. Tools that live in the agent server stay there. Separately, the app can send a list in `RunAgentInput.tools` each run saying "you may use these this time," things like opening a confirm dialog or moving to another screen. When the agent calls one, it actually runs in the app.

The tools doc gives permissions as the reason. The app decides which features this user gets, and sensitive actions are controlled by the app, not the agent. The agent decides, the app does the hands-on part. If tool calling itself is new, [More → tool use](#/post/ai-tool-use)

## State is one shared JSON
Shared state is a single JSON object both sides look at. First it goes over whole as `STATE_SNAPSHOT`, then only the changes as `STATE_DELTA`. Deltas use JSON Patch (RFC 6902), a standard for writing a list of instructions like "set the value at this path to this." After a reconnect, the app gets a fresh snapshot to catch up. If the agent is filling in a table, the screen can fill it in along with it.

## Stopping and picking back up
Waiting for human approval is handled pretty strictly. The agent doesn't keep the run open while it waits. It first sends the state and messages needed to resume as snapshots, then ends the run with an "interrupt" outcome on `RUN_FINISHED`. When the user approves, the app starts a new run on the same thread with the answers in `resume`.

The rules are written down. Every open interrupt has to be answered; partial answers aren't allowed. Sending new input to a thread with pending interrupts and no resume is an error. Sending the same resume twice has to be safe, and answers past the expiry time (`expiresAt`) are rejected. The spec has already decided what happens when someone double-clicks the approve button, or clicks it much later.

## Why it's trending now
The repo was created in May 2025, so it isn't new. 1.0 also came out in September (npm `@ag-ui/core` 1.0.0 on September 17 UTC). The 1.0 changes page says that in 0.x the behavior rules mostly lived inside the TypeScript client code, and 1.0 was the first time they were pinned down in docs and a JSON Schema. The TypeScript, Python, and .NET SDKs are generated from that schema. Subagent events, reasoning events (replacing the old THINKING events), and an `outcome` saying how a run ended came in then too.

## For a beginner
Agent demos usually end with one chat box, but real services add approve buttons, progress indicators, and tables the agent fills in. AG-UI is an agreement between that screen and the agent, written in advance. If frontend and backend agree on this event list, they can be built separately.

For a PM, the interrupt rules are the useful part. "Continue once a human approves" is easy to write as one line in a spec, but to actually build it you also have to decide what happens on a double click, a late click, or a partial approval. This spec reads like one worked answer to those questions. If subagents are new, [More → subagents](#/post/ai-subagent)
