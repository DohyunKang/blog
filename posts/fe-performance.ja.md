フロントエンドのパフォーマンスは、「ページが速い」という感覚を、読み込み時間、応答性、安定性の 3 つの数字で測定するものであり、その 3 つの数字こそが Core Web Vitals です。どこを改善すべきかを決定するには、まずこれらの数字を知る必要があります。

## まず 3 つの数字

Core Web Vitals は現在、LCP、INP、CLS の 3 つです。web.dev を基準として「良好（Good）」とみなされる範囲は以下の通りです。

| 指標 | 測定対象 | 良好基準 |
|---|---|---|
| LCP (Largest Contentful Paint) | 画面で最も大きな要素が描画されるまでの時間 | 2.5 秒以下 |
| INP (Interaction to Next Paint) | クリック・タップ・キー入力後、画面が変わるまでの時間 | 200ms 以下 |
| CLS (Cumulative Layout Shift) | 表示中のコンテンツが突然ずれる度合い | 0.1 以下 |

基準は 75 百分位数です。訪問の 100 回中 75 回がこの基準内に入る必要があります。モバイルとデスクトップを別々に評価します。3 つの指標すべてが基準を満たさなければ、そのページは合格しません。

INP は従来の FID に代わり、2024 年に Core Web Vital の一つとなりました。FID は最初の入力の遅延のみを見ていましたが、INP は訪問中のすべてのクリック・タップ・キー入力を監視し、通常是最も遅かったものの値を採用します。入力を受け取り、ハンドラを実行し、次の画面が描画されるまでのすべてが含まれます。

## LCP：最も大きな要素がいつ表示されるか

LCP 要素は、一般的にヒーロー画像や大きなタイトルです。ブラウザが画面を描画する順序を理解していれば、この時間がどこで発生しているかがわかります。順序については [詳細 → ブラウザの画面描画プロセス](#/post/fe-browser-render) に詳しく記載しています。

web.dev は LCP の時間を 4 つの区間に分割します。

| 区間 | 意味 | 推奨割合 |
|---|---|---|
| TTFB | ページリクエストから HTML の最初のバイトまで | 約 40% |
| リソースロード遅延 | TTFB 以降、LCP リソースの受信を開始するまで | 10% 未満 |
| リソースロード時間 | LCP リソースを受信する時間 | 約 40% |
| 要素レンダリング遅延 | すべて受信した後、実際に描画されるまで | 10% 未満 |

「推奨割合」とは規則ではありません。読みながら思ったのは、遅延の 2 つの区間はゼロに近づけるべき無駄な時間であり、そこから削減すればよいということです。

最も効果的とされているのは、リソースロード遅延をなくすことです。LCP 画像が HTML に直接記述されていれば、ブラウザが早期に発見できます。CSS や JavaScript の中でのみ参照している場合、はるかに後に受信を開始します。そのような場合は `<link rel="preload">` で事前に取得するか、画像に `fetchpriority="high"` を指定します。これは 1〜2 つの要素だけに使用すると推奨されています。

```html
<!-- 첫 화면의 큰 이미지: lazy 금지, 우선순위 높임, 크기 명시 -->
<img src="hero.avif" width="1200" height="600"
     fetchpriority="high" alt="소개 이미지">
```

ある区間の時間を削減しても、時間が他の区間に移動する可能性があります。画像を圧縮してロード時間を短くしても、スクリプトがロードされるまでその要素を非表示にしているページであれば、節約した時間はレンダリング遅延としてそのまま戻ってしまいます。

TTFB はサーバーとレンダリング方式の責任です。HTML をサーバーが生成するか、ビルド時に事前に作成しておくか、ブラウザが生成するかによって最初の画面は異なります。この点は [詳細 → CSR・SSR・SSG](#/post/fe-rendering-modes) で整理されています。

## INP：押したのに反応が遅い場合

INP が悪いということは、入力後、次の画面まで長時間かかることを意味し、原因の多くはメインスレッドが忙しくしていることです。web.dev はこれを 3 つの部分に分けます。

- 入力遅延：他の長いタスク（long task）がメインスレッドを占有しており、ハンドラを開始できません。
- ハンドラの遅さ：イベントハンドラ内で実行する作業が長いです。
- 画面更新の遅さ：複雑なレイアウト、スタイル計算、大きな DOM により次のフレームが遅れます。

JavaScript が相互作用の中心であるため、反応が遅い原因も大半は JavaScript によるものです。そのため、バンドルサイズの削減と INP の改善は連動します。

<details>
<summary>Lighthouse に INP がない理由</summary>

INP は実際のユーザーがいつ何を操作するかを知る必要がある値です。実験室ツールはそのことは知りません。そのため、Lighthouse は INP の代わりに TBT（Total Blocking Time）を代替指標として使用します。Chrome DevTools は 3 つの指標すべてを測定します。正確な値とは一致せず、web.dev も TBT がモバイルビューポートのないページのタップ遅延を見逃すと記載しています。

</details>

## CLS：読みながらずれる場合

CLS は、ボタンを押そうとした瞬間に広告が表示されて押す場所がずれてしまうような経験を数値化したものです。要素がフレーム間で開始位置を変更すると、レイアウトシフトとして計測されます。1 回のスコアは影響割合 × 移動距離割合です。

<details>
<summary>スコア計算例</summary>

画面の要素が画面高さの 25% 移動する場合、占める面積の 75% を考慮すると 0.75 × 0.25 = 0.1875 となります。1 秒以内のシフトは 1 つのグループ（セッションウィンドウ、最大 5 秒）としてまとめられ、CLS はその中で最も大きなグループの合計です。0.1 以下が良く、0.25 を超えると悪いです。ユーザー入力後の 500ms 以内のシフトは計算から除外されます。

</details>

一般的な原因は決まっています。

- サイズが不明な画像・動画
- フォントフォールバックとサイズが異なる Web フォント
- 自らサイズを変更する広告・外部ウィジェット
- 既存コンテンツの上に重ねられる動的コンテンツ

修正方法も単純です。画像には `width` と `height` を指定してスペースを確保し、アニメーションは `width`·`top`·`left` の代わりに `transform` を使用します。ユーザー操作で表示されるコンテンツについては、ローディングインジケーターを表示してから表示させることで予期される変化にします。

## 画像と遅延読み込み

画像はバイト数が最も大きいため、ロード時間を短縮する際に最初に手が掛かります。適切な解像度、AVIF や WebP などの最新形式、圧縮、CDN の順です。

画面外にある画像は `loading="lazy"` を 1 つの行で十分です。ブラウザがビューポートから一定距離以内に入った時点で読み込みます。その距離はブラウザによって設定され、接続速度にも依存します。web.dev の記事によると、Chrome は 4G で 1250px、より遅い接続では 2500px に短縮されたとしています。

注意すべき点があります。

- 初めに表示される画像、特に LCP 画像には lazy を使用してはいけません。意図的に遅らせることになります。
- `width`·`height` が指定されていない場合、サイズが 0 とみなされ、ギャラリー全体が画面内に収まっているように見え、すべて読み込んでしまう可能性があります。遅れて表示された画像も CLS を引き起こします。
- `display: none` の画像は読み込まれませんが、`opacity: 0` の場合は読み込まれます。
- `<img>` タグには適用されますが、CSS の背景画像には適用されません。

```html
<!-- 화면 밖 이미지 -->
<img src="card.webp" width="400" height="300" loading="lazy" alt="">
```

## バンドル削減：コード分割

JavaScript が大きくなると、ダウンロード、パース、実行の時間がすべて INP と LCP に影響を与えます。初期画面で不要なコードは後から読み込むように分割するのがコード分割です。動的 `import()` がその手段であり、React では `React.lazy` がそれをラップします。

```jsx
import { lazy, Suspense } from 'react';

const Chart = lazy(() => import('./Chart'));

function Report() {
  return (
    <Suspense fallback={<p>불러오는 중</p>}>
      <Chart />
    </Suspense>
  );
}
```

web.dev は分割をルート単位から始めるよう推奨しています。次に交互操作後に表示される大きなコンポーネント、そして画面外にある次要的なものが次になります。チャンクが取得できないこともあります。オフラインの場合や、再デプロイで古いファイルのアドレスが消えた場合です。そのため Suspense をエラーバウンダリーで囲むよう推奨されています。コンポーネントをどのように分割するかは [詳細 → コンポーネント設計](#/post/fe-component) も参照してください。

<details>
<summary>Suspense と SSR</summary>

web.dev の記事によると、Suspense はサーバーサイドレンダリング（SSR）をサポートしていないと記載されており、その場合は `loadable-components` を推奨しています。この記事が書かれた時点と現在の React バージョンの差がある可能性があるため、SSR 環境では使用するフレームワークのドキュメントを別途確認する必要があります。

</details>

## 測定：実験室と現場

測定値には 2 つの種類があります。

| | 実験室 (lab) | 現場 (field) |
|---|---|---|
| 出所 | 指定された機器・ネットワークで直接ロード | 実際の訪問者 |
| ツール | Lighthouse, DevTools | CrUX, PageSpeed Insights, Search Console |
| 長所 | 同じ条件下での繰り返し、デバッグ容易 | 真のユーザー体験 |
| 短所 | シナリオが 1 つ | 原因を即座に見つけるのが難しい |

CrUX は Chrome ユーザーから収集した 28 日間のローリングデータセットです。実験室と現場の値が異なるのは珍しいことではありません。LCP 要素は画面サイズ、パーソナライゼーション、A/B テストによって変化し、キャッシュがある場合実際のほうが速いです。INP はユーザーが操作することで発生し、CLS は実験室でロード中の最初の画面のシフトのみを捉えます。web.dev では優先順位は現場データで決定し、デプロイ前の確認とデバッグは実験室で行い、両方を使用するよう推奨しています。

後で見直して整理した順序は以下の通りです。PageSpeed Insights で現場値から見て、不合格の指標を確認し、DevTools や Lighthouse で再現して上記 3 つの区間（LCP なら 4 つの区間、INP なら 3 つの部分）で原因を探ります。

## よくある誤解

- Lighthouse スコアが 100 で終わり：実験室スコアは現場指標と異なる場合があります。前述の lab と field の違いそのものです。
- lazy ロードは画像すべてに適用すれば良い：LCP 画像に適用すると逆に遅くなります。
- 数字を一つ上げれば良い：一つの区間を減らすと時間が他の区間に移ることもあります。
- バンドル削減だけで解決：TTFB とレンダリング方式、画像サイズも同時に確認する必要があります。
