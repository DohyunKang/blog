이번 주 GitHub 트렌딩 목록은 거의 다 에이전트 스킬과 하네스 쪽이었는데, 그 사이에 결이 다른 레포가 하나 있었다. TauricResearch의 TradingAgents다. 트레이딩 회사의 역할 분담을 LLM 에이전트로 옮겨 놓은 프로젝트다.

## 이번 주 트렌딩에서 본 것

주간 트렌딩 상위 15개 중 열세 개가 AI 관련이었다. 대부분은 코딩 에이전트에 붙이는 스킬, CLAUDE.md, 메모리, 하네스 같은 도구들이었다. 그중 에이전트들이 서로 역할을 나눠 일하는 구조 자체가 주제인 건 TradingAgents 쪽이었다.

확인한 시점은 2026년 11월 2일이고, 이때 GitHub 페이지 기준으로 별은 약 11만 9천 개(헤더 표기는 12만), 포크는 2만 2천9백 개였다. 이 수치는 매일 바뀐다. 라이선스는 Apache-2.0, 최신 릴리스 표기는 v0.7.1(2026년 10월)이었다.

## 뭘 하는 프로젝트인가

README는 이걸 LLM과 LangGraph 위에 만든 멀티 에이전트 트레이딩 프레임워크라고 소개한다. 실제 트레이딩 회사의 조직을 흉내 낸다는 게 핵심이다. 에이전트들이 시장 상황을 두고 토론한 뒤에 결정을 내린다.

역할은 이렇게 나뉜다.

| 단계 | 역할 | 하는 일 |
|---|---|---|
| 분석가 팀 | 펀더멘털, 감성(뉴스·StockTwits·Reddit), 뉴스·거시, 기술적 지표(MACD, RSI 등) | 병렬로 각자 자료를 보고 보고서를 만든다 |
| 연구원 팀 | 강세 연구원, 약세 연구원 | 분석가 보고서를 두고 서로 토론한다 |
| 트레이더 | 트레이더 | 보고서를 종합해 매매 시점과 규모를 정한다 |
| 리스크·운용 | 리스크 관리, 포트폴리오 매니저 | 제안을 평가해 승인하거나 거절한다. 승인된 주문은 모의 거래소로 간다 |

한 줄로 줄이면 분석 → 토론 → 결정 → 리스크 검토 → 승인 순서다. 하나의 모델이 한 번에 답하는 대신, 같은 문제를 여러 관점으로 나눠 보고 서로 반박하게 만든 구조다.

이 구조가 에이전트 설계 글에서 말하는 패턴과 많이 겹친다. 분석가들이 동시에 일하는 부분은 병렬화이고, 강세와 약세가 맞붙는 부분은 한 에이전트의 결과를 다른 에이전트가 검토하는 평가 단계에 가깝다. 이런 패턴은 [자세히 → 에이전트 설계 패턴](#/post/app-agent-design)에 따로 정리해 뒀다. 역할마다 맥락을 따로 쓴다는 점은 [자세히 → 서브에이전트와 멀티에이전트](#/post/ai-subagent)와도 이어진다.

## 어떤 모델로 돌릴 수 있나

지원하는 제공자 목록이 길었다. OpenAI, Google, Anthropic, xAI, DeepSeek, Qwen, GLM, MiniMax, OpenRouter, Mistral, Kimi, Groq, NVIDIA NIM, AWS Bedrock, Azure OpenAI가 있고, 로컬 모델은 Ollama로 붙인다. OpenAI 호환 엔드포인트면 아무거나 쓸 수 있고, ChatGPT Plus·Pro 구독으로도 된다고 적혀 있다.

한 레포가 이렇게 많은 제공자를 받는다는 건, 에이전트 구조는 그대로 두고 모델만 갈아 끼우는 게 흔한 사용 방식이 됐다는 뜻으로 읽혔다. 에이전트 하나하나가 [LLM](#/post/ai-llm)을 부르는 얇은 층이라는 얘기이기도 하다.

## 써 보려면

README 기준으로 파이썬 3.11 이상이 필요하고, 예시는 3.13을 쓴다. 레포를 받아서 `pip install .`(또는 `uv pip install .`)로 설치하고, `tradingagents` 또는 `python -m cli.main`으로 CLI를 띄운다. 파이썬 코드에서는 `TradingAgentsGraph`를 불러다 쓸 수도 있다. 도커로 돌리려면 `.env.example`을 `.env`로 복사해 키를 채운 뒤 `docker compose run --rm tradingagents`를 실행한다.

이 외에 영구 메모리 로그, 체크포인트에서 이어 하기, 종목·날짜 격자로 돌리는 백테스트, 포트폴리오를 고려한 실행, 야후 파이낸스 티커를 통한 미국 밖 시장 지원이 기능 목록에 있다.

초록 기준으로 주장하는 건 세 가지다. LLM 에이전트를 실제 트레이딩 회사처럼 조직하는 방식이 아직 덜 탐구된 영역이라는 것, 이 프레임워크가 기준 모델들보다 누적 수익률·샤프 지수·최대 낙폭에서 나은 결과를 냈다는 것, 그래서 멀티 에이전트 구조에 가능성이 있다는 것이다. 이 수치는 논문의 실험 조건에서 나온 결과이고, 실제 돈을 굴린 성과는 아니다.

## 같이 적혀 있는 단서

README는 이 프로젝트가 연구 목적으로 만들어졌고 금융·투자·거래 조언이 아니라고 밝힌다. 성능은 고른 모델, 온도, 데이터 품질, 결과가 매번 달라지는 성질에 따라 달라진다고도 적는다. 같은 입력으로 돌려도 토론 내용이 달라질 수 있으니 한 번 나온 결과를 근거로 삼기는 어렵겠다.

토론 구조를 만든 이유도 이 지점과 닿아 있는 것 같다. 한 번의 호출보다 여러 번 서로 따져 보는 게 덜 흔들릴 거라는 기대다. 그 대신 호출 수가 역할 수만큼 늘어나서 비용도 그만큼 는다. [에이전트 루프](#/post/ai-agent-loop)가 몇 바퀴 도는지에 따라 한 번 돌릴 때의 토큰이 꽤 달라질 구조다.

나는 이 레포를 투자 도구보다는 멀티 에이전트 구조의 예제로 읽었다. 역할을 어떻게 쪼개고 어떤 순서로 부딪히게 하는지 보기에는 좋은 샘플이었다. 직접 돌려 보는 건 모의 거래소 쪽으로만 하는 게 맞겠다.
