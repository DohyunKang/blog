## 뭐 하는 물건인지
회사 데이터베이스 위에 "이 숫자가 무슨 뜻인지"를 적어 두는 층을 자동으로 만들어 주는 파이썬 프레임워크다. 그 층 이름이 온톨로지다. 온톨로지는 개념들과 그 사이 관계를 기계가 읽을 수 있게 정리한 지도 같은 것이다. [자세히 → 온톨로지와 트리플](#/post/ai-ontology-triple)

README 첫 문단이 문제를 잘 요약한다. 에이전트가 DB를 조회할 수는 있는데, 매출 숫자를 빨리 답해도 틀리면 소용없다는 것. 그래서 데이터가 어디 있고, 무슨 뜻이고, 써도 되는지, 어디서 왔는지를 알려 주는 맥락 층이 필요하다고 한다.

쓰는 쪽에서 보면 결국 text-to-SQL 도구다. text-to-SQL은 "지난주 주문 몇 건이야?" 같은 질문을 SQL로 바꿔 실행하는 기능이다. 차이는 모델이 테이블 이름만 보고 SQL을 짐작하지 않고, 사람이 확인한 정의를 먼저 찾아본다는 점이다.

## 어떻게 도는지
온톨로지에 담기는 건 세 가지다.

- 용어(Term): Customer, Invoice Line 같은 업무 개념. 설명과 동의어가 있고, 실제 컬럼에 연결된다.
- SQL 속성: 마진이나 누적 합계처럼 검토를 거친 SQL 식. 에이전트가 이걸 재사용하니 같은 지표를 매번 같은 방식으로 계산한다.
- 관계: 테이블끼리 어떻게 조인되는지. 키와 실제 데이터를 보고 추론한다.

흐름은 생성 → 인증 → 답변 세 단계다. 생성 단계에서는 스키마를 읽고, 컬럼 값을 샘플링하고, 테이블마다 용어를 뽑고, 조인 관계를 추론해서 Postgres에 저장한다. 검색용 임베딩은 pgvector에 넣는다. 임베딩은 글을 숫자 벡터로 바꿔 뜻이 비슷한 걸 찾게 해 주는 방식이다. [자세히 → 임베딩과 벡터 검색](#/post/ai-embedding)

인증 단계가 사람 몫이다. 초안을 실제 질문으로 시험해 보고, 정의를 고친 뒤 "이건 맞다"고 certify 한다. 자동으로 만든 지도를 그대로 믿지 않겠다는 설계라 좋았다.

답변 단계에서는 질문의 의도와 엔티티를 뽑고, 임베딩 검색으로 후보 용어·컬럼·SQL 속성을 찾고, SQL을 쓰고, 필터 값과 쿼리를 DB에 대 보면서 틀리면 고친 다음 실행한다. 답에는 SQL과 거친 단계가 같이 붙는다. README 예시에서는 "2015년 6월 펜실베이니아에서 어떤 상품 매출"을 물으니 테이블 여섯 개를 조인한 SQL과 함께 $588.80이 나왔다.

내가 제일 눈여겨본 건 못 답하는 경우다. 샘플 DB에 광고비 데이터가 없는데 광고 수익률(ROAS)을 물으면, MCP의 `check_answerable` 도구가 "ad spend를 덮는 용어가 없다"고 먼저 알려 주고 에이전트가 되묻는다. 없는 컬럼을 그럴듯하게 지어내는 것보다 훨씬 낫다.

## 붙이는 방법
MCP 서버가 따로 있어서 Cursor나 Claude Desktop에 설정 몇 줄로 붙는다. 도구는 전부 읽기 전용이고 사용자 권한으로 돈다. [자세히 → MCP](#/post/ai-mcp) 코딩 에이전트용 스킬도 세 개(설치, 관리, 질의) 들어 있다. [자세히 → 스킬](#/post/ai-skills) REST API로 질문을 보내면 SSE 스트림으로 답이 온다.

기본 모델은 NVIDIA NIM의 Nemotron 3.5 계열이다. 추론용, 가벼운 단계용, 임베딩, 리랭킹 네 역할로 나뉘고, OpenAI 호환 엔드포인트면 역할별로 다른 모델로 바꿀 수 있다고 한다. 연결되는 DB는 PostgreSQL, MySQL, Snowflake, Databricks, DuckDB 등 10종이다.

## 왜 화제인지
레포는 4월 말에 만들어졌는데 이번 주에 갑자기 떴다. 커밋 기록을 보면 11월 4일에 README를 "왜 필요한지" 중심으로 다시 썼고, 11월 5일 밤에 버전을 1.2.0으로 올렸다. X 언급 수도 그 무렵인 11월 5일(UTC)이 153건으로 가장 많았다. 다만 이게 원인인지는 확인 못 함.

에이전트가 사내 데이터에 붙기 시작하면서 "틀린 숫자"가 진짜 문제가 된 시점이라 그런 것 같기도 하다. 시맨틱 모델 교환 표준인 Apache Ossie와 호환된다는 점도 기업 쪽에서는 반가울 것 같다.

## 입문자 입장에서
PM 입장에서 와닿는 건 "매출"의 정의를 한 곳에 박아 두는 개념이다. 팀마다 매출을 다르게 계산하는 문제는 AI 이전부터 있었는데, 그걸 에이전트가 쓰는 사전으로 만든 셈이다. 개발 입문자라면 Next.js + FastAPI + Postgres/pgvector + MCP로 짠 구성이 RAG를 SQL 쪽에 적용한 예로 공부하기 좋아 보인다. [자세히 → RAG](#/post/ai-rag)

주의할 점도 README에 적혀 있다. 내부 포트 3001·3002는 인증이 없거나 프런트가 넘긴 사용자 헤더를 그대로 믿으니 사설망에 둬야 한다. 기본 설정은 NVIDIA API 카탈로그로 요청을 보낸다. 지금은 외부 기여를 받지 않는다고 한다. BIRD 같은 벤치마크 결과는 별도 레포를 안내하는데 수치는 확인 못 함.
