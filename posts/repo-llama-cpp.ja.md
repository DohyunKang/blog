llama.cpp ソースをダウンロードし（コミット 785322d, 2026-11-01）、モデルファイルが開きトークンが出力されるまでの手順を追ってみました。大きく分けて三つの塊でした。ファイル形式（GGUF）、計算ライブラリ（ggml）、そしてその上でループを回す llama 側のコードです。量子化は別機能として付加されたものではなく、ファイル内のテンサー形式そのものでした。

## リポジトリ構造から

最上位に `src/`, `ggml/`, `include/`, `tools/` があります。

| 位置 | 役割 |
|---|---|
| `include/llama.h` | 外部から呼び出す C API。モデルロード、コンテキスト生成、`llama_decode` など |
| `src/` | モデル・コンテキスト・KV キャッシュ・トークナイザー・サンプラー。`llama-context.cpp` が約 4,800 行 |
| `src/models/` | モデル構造ごとにファイル一つずつ（172 個）。グラフを作成するコード |
| `ggml/src/` | テンサー演算とバックエンド。`ggml-cuda`, `ggml-metal`, `ggml-vulkan`, `ggml-cpu` などフォルダに分かれる |
| `tools/` | `cli`, `server`, `quantize`, `llama-bench`, `perplexity` などの実行ファイル |
| `convert_hf_to_gguf.py` | Hugging Face モデルを GGUF に変換するスクリプト |

README は一行で「LLM inference in C/C++」と紹介しています。学習コードはなく推論が主人公です。モデル構造一つをサポートするには `src/models/` にファイルを一つ追加する仕組みなので、新しいモデルが出るとこのフォルダが増える構造です。[詳細 → 推論](#/post/ml-inference)

## GGUF: 一つのファイルに全て入れた形式

`ggml/include/gguf.h` の先頭コメントにファイル構造がそのまま書かれています。順序は以下の通りです。

1. マジック `"GGUF"` 4 バイト、バージョン（現在 `GGUF_VERSION` 3）
2. テンサー数、キー・バリューペアの数
3. キー・バリューペア们（モデル構造名、層数、トークナイザー語彙などのメタデータ）
4. テンサー情報们（名前、次元、データ型、データ位置）
5. ソートされたテンサーデータの塊

重みだけでなく設定や語彙表も一つのファイルに入ります。そのため `llama-cli -hf ...` 一行でファイル一つだけ受け取って動作します。テンサー情報に「データ位置」がありデータがソートされているため、`llama-model-loader.cpp` がファイルを mmap で開くことができます。mmap を使う側のコードには「GGUF データ領域がソートされていなければ mmap できない」という例外もありました。ファイル全体を読み込んでコピーするのではなく、オペレーティングシステムが必要な分だけをメモリに上げる方式です。

## 量子化はブロック構造体です

`ggml/src/ggml-common.h` に形式ごとのブロックが定義されています。代表例として Q4_0。

```c
#define QK4_0 32
typedef struct {
    ggml_half d;           // delta
    uint8_t qs[QK4_0 / 2]; // nibbles / quants
} block_q4_0;
```

重み 32 個を一つのブロックに束ね、ブロックごとにスケール `d` 一つ（2 バイト）と 4 ビット値 32 個（16 バイト）を置きます。18 バイトに 32 個なので重み一つあたり 4.5 ビットです。もともと 16 ビットなら約 3.5 分の 1 です。同様に計算すると Q8_0 はブロックが 34 バイトで 8.5 ビット、Q4_K は 256 スーパーブロックに 144 バイト（2+2+12+128）なのでやはり 4.5 ビットでした。7B パラメータに 4.5 ビットを掛けると約 3.9GB です。この数字はソースの構造体から私が計算した値で、実際のファイルサイズは 1 次元テンサーなどが別の形式に残っているため少し異なります（`llama.h` でも Q4_0 の説明に「except 1d tensors」と書かれています）。[詳細 → ローカルモデル](#/post/ml-local-models)

`quantize_row_q4_0_ref`（`ggml-quants.c`）を読むと変換過程は短いです。ブロック内で絶対値が最大の値を探して `d = max / -8` と定め、各値を `d` で割って +8.5 してから 0~15 の整数に切り捨てます。上側の 16 個と下側の 16 個を一つのバイトの上位ニブル・下位ニブルに分けて入れます。この関数を Python に移植して 32 個のランダムブロックに当ててみると 18 バイトが得られ、復元した時の最大誤差は 0.147 でした。スケール `d` が 0.2986 なので半分間（d/2 ≈ 0.149）以内に入った値です。丸め誤差がスケールの半分以下という意味です。

<details>
<summary>詳しい解説：ブロック単位の誤差がなぜこれほどになるのか</summary>

ブロック内で最大の値一つがスケールを定めるため、ブロック内に飛び出す値（outlier）が一つあれば残り値の解像度も一緒に粗くなります。ブロックを 32 に小さく分割する理由はこれが理解できました。ブロックが小さいと飛び出す値の影響はそのブロック内に閉じ込められます。代わりにブロックごとにスケールを保存する必要がありビットが増えます（4 ビット値 + スケール商 0.5 ビット = 4.5 ビット）。

Q4_K ブロックは、256 スーパーブロック内に小さなブロックを持ち、そのスケールと最小値（`scales`, 6 ビット）をスーパーブロック単位で再量子化します（`ggml-common.h` のコメント参照: "scales and mins, quantized with 6 bits"）。スケールをさらに一度量子化する構造です。

</details>

## 計算はどのように行うか

量子化された重みと行列乗算を行う際、入力（アクティベーション）側も 8 ビットブロック（`block_q8_0`）に変換して整数同士で乗算します。`ggml-cpu/quants.c` の `ggml_vec_dot_q4_0_q8_0_generic` がその汎用（ジェネリック）実装です。

- ブロックごとに `sumi` を整数として累積します。4 ビット値は `(qs & 0x0F) - 8` で復号し、8 ビット値と乗算します。
- ブロックが終了すると、`sumi × 重みスケール × アクティベーションスケール` を浮動小数点の合計に追加します。

つまり「整数乗算を大きく行い、スケールはブロックごとに一度だけ掛ける」という構造です。ファイル名に `_generic` が付いていることから、CPU 種類別（AVX、NEON など）に高速版があり、これは基準実装であることが伺えます。

演算をどのデバイスで行うかは `ggml-backend` が担当します。`llama_model_params` に `n_gpu_layers`（VRAM にアップロードする層数、負数の場合はすべて）があり、一部の層だけを GPU で、残りは CPU で実行することも可能です。そのため、VRAM が不足している PC でも大きなモデルは遅くても動作します。[詳細 → トラン스포ーマー](#/post/ml-transformer)

## 推論ループ：`llama_decode` の一回で起こること

`llama_context::decode`（`llama-context.cpp`）を上から読みました。流れは以下の通りです。

1. トークンが空であればエラー（-1）を返します。
2. 出力するトークンの数を数えます。埋め込みモードの場合はすべて必要で、通常の生成では最後の位置のみが必要です。
3. `memory->init_batch(...)` でバッチを小さな断片（ubatch）に分割し、KV キャッシュから場所を探します。場所がない場合はキャッシュを整理（`memory_update`）して再度試行し、それでもダメな場合は 1 を返します。
4. ubatch ごとに `process_ubatch` を呼び出します。

`process_ubatch` 内では、前回のグラフを再利用できる場合はそのまま使い、そうでない場合は `model.build_graph` で計算グラフを新たに作成します。その後、入力テンソルに値を設定（`set_inputs`）し、`graph_compute` で実行します。一つの ubatch が失敗した場合、その断片の位置情報をメモリから削除して状態を元に戻すコードもありました。

バッチサイズは 2 つあります。`llama.h` では `n_batch` は `llama_decode` に渡せる論理的な最大値、`n_ubatch` は実際に一度に計算する物理的な最大値と説明されています。プロンプトを長く指定すると、ubatch 単位で分割されて処理されます。

`graph_compute(res->get_gf(), ubatch.n_tokens > 1)` の呼び出しにおいて、2 つ目の引数は「トークンが 2 つ以上か」に渡られます。プロンプト処理（複数のトークン）と生成（一つのトークン）を区別して渡しているようです。

グラフはモデルごとに `src/models/` のコードで作成します。例えば `llama.cpp`（モデルファイル名）では、埋め込み入力 → 各層で `build_norm` → `ggml_rope_ext` で Q・K に位置情報を付与 → `build_attn` → `build_ffn` の順に積み上げます。次のトークンを選ぶのは `llama_sampler`（チェーン方式）で、ロジットからサンプラーチェーンを経て一つのトークンが出力されます。このループを外側から直接回すのは `tools/cli` や `tools/server` などの実行ファイルです。[詳細 → サンプリング](#/post/ai-sampling)

## Ollama・vLLM と比較して見ると

前述の [Ollama](#/post/repo-ollama) を読む際に、推論計算は別プロセス（llama-server）で行うことを知りました。このリポジトリがまさにその計算部分です。Ollama はモデル管理とアップロード・ダウンロードのタイミングを担い、実際のトークン計算はこの側から出力されます。逆に [vLLM](#/post/repo-vllm) は、サーバーや多数のユーザー処理に合わせて同じようなことを実現したもので、PagedAttention などの構造が核心です。llama.cpp は一つの PC で一つのファイルを適切に動かすことに重点があり、複数のリクエストをまとめて処理する部分は今回読みませんでした。[詳細 → AI サービング](#/post/infra-ai-serving)

## よくある誤解

- 量子化するとモデルが別のものになる：これは重みの精度だけを下げることであり、構造は同じである。ただし誤差が蓄積するため、ビット数越低るほど品質が低下する可能性がある。
- GGUF は圧縮ファイルである：zip とは異なる。4 ビットの値がそのままファイルに格納されており、計算もその形式を直接読み込んで行う。
- llama.cpp は Llama モデル専用である：名前から誤解されがちだが、`src/models/` ディレクトリには構造別のファイルが 172 つある。
- GPU がなければ動作しない：CPU バックエンドがデフォルトである。GPU は `ggml-cuda` や `ggml-metal` などのバックエンドを選択して追加する。
