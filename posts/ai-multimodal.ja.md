マルチモーダルとは、モデルがテキストだけでなく、画像や音声といった異なる種類の入力（または出力）も同時に処理することを指します。結局のところ、画像もトークンに変換されて、テキストと同じコンテキストウィンドウに投入されます。

## マルチモーダルとは何か

モダリティ（modality）とは、情報が保持されている形式を指します。テキスト、画像、音声、動画はそれぞれ一つのモダリティです。テキストのみを受け付けるモデルは単一モーダルと呼ばれ、2 つ以上を扱う場合はマルチモーダルと呼びます。

入出力の方向性が 2 つあることを区別すれば、混乱しにくくなります。

| | 入力（理解） | 出力（生成） |
|---|---|---|
| 画像 | 写真を見て説明する、表を読む、スクリーンショットを解析する | 図を描く |
| 音声 | 話した言葉を文字に起こす | 文字を読み上げる |
| 動画 | フレーム単位で見て要約する | 動画を作成する |

[LLM](#/post/ai-llm) が画像を「見る」と言う場合、通常は左側の列つまり入力側を指します。図を描いてくれるのは別の種類のモデルであることが多く、そのほうについては [拡散モデル](#/post/ml-diffusion) と [生成型 AI](#/post/ai-generative) の記事で別途整理しています。一つのモデルが両方の機能を果たすかどうかは製品によって異なります。

## 原理：画像をどのようにモデルに投入するか

テキストはトークンに分割して数値ベクトルに変換します。画像も同様のプロセスを経ます。核心は、画像を小さなパッチ（patch）に切り取ることにあります。

Vision Transformer(ViT) の論文の要約では、「画像パッチのシーケンスに対して純粋なトランスフォーマーをそのまま適用」しても画像分類がうまくいくと述べています。これは畳み込みニューラルネットワークが必ずしも必要ないということです。[トランスフォーマー](#/post/ml-transformer) がテキストトークンを扱う構造と同じように、画像パッチもトークンのように扱われると理解すればよいでしょう。

次の問題は、テキストと画像が同じ空間で出会う必要がある点です。CLIP がその代表的な例です。OpenAI の論文の要約によると、インターネットから収集した 4 億個の（画像、テキスト）ペアを用いて、どのキャプションがどの画像に合致するかを判定する形で学習しました。その結果、事前に設定されたラベルリストなしでテキストの説明だけで新しい分類を行うことが可能となり（ゼロショット）、30 つ以上のデータセットで評価されたとのことです。この「テキストと画像を同じ座標系に置く」という感覚は [埋め込み](#/post/ai-embedding) と繋がります。

ここまでは、画像エンコーダーを別に置き、テキストモデルに接続するタイプの話です。近年の商用モデルの内側構造はほとんど公開されていません。

## 例：Claude は画像をこうして感知する

Anthropic のビジョンドキュメントで確認した内容です。

- 画像は 28×28 ピクセルのパッチに分割され、一つのパッチが一つのビジュアルトークンになります。
- トークンの数は ⌈横/28⌉ × ⌈縦/28⌉ です。
- 大きすぎる画像はアスペクト比を保ったまま縮小してから処理されます。制限はモデルの世代によって異なります。標準的な区間は長辺 1,568px・最大 1,568 トークン、Claude 4.7 以降のモデルの高解像度区間は長辺 2,576px・最大 4,784 トークンです。
- 対応形式は JPEG、PNG、GIF、WebP です。アニメーションはサポートしておらず、最初のフレームのみを使用します。
- リクエストあたりの画像数は API では最大 600 枚（コンテキスト 20 万トークンのモデルでは 100 枚）、claude.ai では 1 ターンに 20 枚です。画像一枚の最大サイズは 8000×8000px です。
- 伝達方法は base64 の直接挿入、URL、Files API の file_id の 3 つです。

ドキュメントに掲載された例示表をいくつか転記すると以下のようになります。

| 画像サイズ | 標準区間トークン数 | 高解像度区間トークン数 |
|---|---|---|
| 200×200 | 64 | 64 |
| 1000×1000 | 1,296 | 1,296 |
| 1920×1080 | 1,560 (1456×819 に縮小) | 2,691 |
| 3840×2160 | 1,560 | 4,784 |

1000×1000 の場合、36×36=1,296 で式と一致します。同じ 4K イメージでも高解像度区間のモデルでは標準区間のおよそ 3 倍のトークン数になります。ドキュメントでも詳細さが不要であれば事前に縮小して送るよう指示しています。

## トークンコストの感覚

画像トークンはテキストトークンと同様に [コンテキストウィンドウ](#/post/ai-context-window) を占め、同じ入力単価で課金されます。ドキュメントの計算例を見ると、1000×1000 の画像は 100 万トークンの入力に対して 1 ドルモデルでは約 1.30 ドル、高解像度モデル（100 万トークンあたり 4 ドル）では約 5.18 ドルです。この価格はドキュメント作成時点のものであり、実際の利用時には価格表を再確認する必要があります。

私の感覚では、一枚の画像がテキスト 1,000 トークン程度に相当するため、スクリーンショットを数枚会話中に常時置いていると、各ターンごとに再度送信する入力がかなり大きくなります。ドキュメントでも base64 で挿入すると対話が長くなるほど、各リクエストで画像バイト数が再び実装されるため、繰り返し使用する画像は Files API を通してアップロードすることを推奨しています。

## よくある誤解

- 「画像を目で見る」：実際には、画像をピースに切り分けてトークンに変換したものを「読み取っている」。小さく、ぼやけたり、回転したりした画像では誤認識しやすい。
- 「画像内の個数を正確に数える」：文書が限界まで直接記述する。対象が多い場合、個数のカウントは不正確になる可能性がある。位置情報や座標も概算値である。
- 「画像は無料で入ってくる」：前述の通り、画像もトークンであり、コストがかかる。
- 「見て話したことは事実」：画像の解釈にも [幻覚](#/post/ai-hallucination) が発生する。文書では人物名の識別を行わず、診断用の CT や MRI などの解釈には使用しない旨を記載している。
- 「マルチモーダルなら音声・動画もすべて可能」：モデルによって異なる。Claude のビジョン機能で扱えるのは画像（および添付文書）であり、GIF は最初のフレームのみを使用する。

<details>
<summary>詳しい解説：なぜ解像度とトークン上限があるのか</summary>

モデルは一度に処理できるトークンの数が決まっている。画像が大きくなると、ピースの数が横・縦ともに増えるため平方比例で増加する。そのため、企業側は長い辺と最大トークン数を上限として設定し、それを超過すると比率を保ちながら縮小する。

一つの実務的な結論：画像を大きく送っても、必ずしもより正確に読み取れるわけではない。上限を超えた部分はいずれ縮小されて入力されるため、事前に上限に合わせて縮小して送信すれば、転送量と遅延を削減できる。文書も同様の趣旨で案内している。
