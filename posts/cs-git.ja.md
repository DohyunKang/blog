Git を「ファイルの変更履歴を蓄積するツール」と捉えるのではなく、「コミットというスナップショットをつなぐもの」であり、ブランチはその中の一つを指すラベルに過ぎないと理解すると、マージ・リベース・衝突が一つの図で整理できます。

## コミットとブランチとは何か

コミットは、その時点でのプロジェクト全体のスナップショットであり、直前のコミット（親）を指すリンクを持っています。各コミットにはハッシュ（長い 16 進数文字列）が付与されます。ブランチは、これらのコミットのいずれかを指すポインタです。新しいブランチを作成することは、ファイルをコピーするのではなく、単にラベルを一つ追加する作業なので、瞬く間に完了します。`HEAD` は、現在自分がどのブランチ（コミット）にいるかを指すポインタです。

作業フローには 3 つの領域があります。

| 領域 | 意味 | 移動させるコマンド |
|---|---|---|
| ワーキングディレクトリ | 現在ファイルを編集している場所 | |
| ステージング（インデックス） | 次のコミットに含めるものを集めた場所 | `git add` |
| リポジトリ | コミットとして確定された記録 | `git commit` |

`git add` を別に置く理由は、修正したものの一部だけをコミットできるようにするためです。

このようなツールが行う作業をバージョン管理と呼びます。誰がいつ何を改めたかを記録し、元に戻せるようにする作業です。[詳しく → ソフトウェア工学の基礎](#/post/cs-sw-engineering)

## マージ

2 つのブランチを統合するのがマージです。ケースは 2 つあります（Pro Git の説明基準）。

- fast-forward: 統合するブランチが現在のブランチの直前の延長線上にある場合、統合する必要がないためポインタだけを前方に移動させます。新しいコミットは生成されません。
- 3-way マージ: 2 つのブランチが共通の祖先から分岐し、それぞれコミットがある場合、2 つの端点と共通の祖先の 3 つのスナップショットを使って新しいスナップショットを作成し、親が 2 つあるマージコミットを作成します。

## 衝突

2 つが同じファイルの同じ部分を互いに異なった形で修正した場合、Git は判断できず停止します。マージコミットはまだ作成されず、`git status` では `both modified` と表示されます。ファイル内にはマーカーが表示されます。

```
<<<<<<< HEAD
main line
=======
feature line
>>>>>>> feature
```

上部（`<<<<<<<`~`=======`）が現在のブランチ、下部が取り込むブランチです。解決手順は 4 つあります。

1. ファイルを開いて片方を選ぶか、両方を混ぜるか、新たに書き直して、マーカーの 3 行を消去します。
2. `git add <ファイル>` で解決済みであることを報告します。
3. `git status` で確認します。
4. `git commit` でマージを完了させます。

最初はマーカーを消さずにコミットしてしまう間違いが起きやすいように見えました。衝突が恐ろしいのは難しいからというより、どこを見ればいいかわからないからではないでしょうか。マーカーがこの形であることがわかれば半分は終わっています。

## リベース

リベースは、自分のブランチのコミットを別のブランチの先頭の上に重ね直すことです。Pro Git の説明によると、共通の祖先を見つけ、自分の各コミットの差分（diff）を保存し、自分のブランチを対象ブランチの先頭に移動させた後、差分を順に再度適用します。結果としてファイルの内容はマージと同じですが、記録の形状だけが異なります。マージコミットが一つにまとまります。

小さなリポジトリで 2 つの方式を実際に試してみました。main と feature が同じ行を修正した状況です。マージはこのように枝が分かれ、統合される形になりました。

```
*   a53bebb merge
|\
| * d6ac9dc feat
* | ffb502f main change
|/
* f1a4288 init
```

同じ状況をリベースで行い、衝突を解決して `git rebase --continue` を実行すると、こうして一つにまとまりました。

```
* 84091ca feat
* ffb502f main change
* f1a4288 init
```

`feat` のハッシュが `d6ac9dc` から `84091ca` に変わったのが目立ちます。リベースはコミットを移動させるのではなく、同じ内容の新しいコミットを作成し、古いコミットを破棄します。この事実が以下の規則につながります。

<details>
<summary>詳しい解説：上記の実習コマンド</summary>

一時フォルダで `git init`、a.txt に 1 行のコミット、`feature` ブランチで 1 行追加、`main` で同じファイルに別の 1 行追加する順で作成しました。`git merge feature` は `CONFLICT (content): Merge conflict in a.txt` で停止し、ファイルを修正して `git add` の後にコミットしました。その後、マージコミットを `git reset --hard HEAD~1` で消去し、`feature` から `git rebase main` を実行すると `Could not apply ... feat` と同じ衝突が発生しました。修正して `git add` の後、`git rebase --continue` で終了させました。環境は git 2.55.0(Windows) です。つまりリベースでも衝突が起きれば同様に解決し、解決する際は `merge --continue` の代わりに `rebase --continue` を使います。

</details>

## マージ vs リベース

Pro Git は、2 つの哲学を提示し、どちらが勝者かを示しません。一方は「記録は実際に起きたことなので変更しない（マージ）」であり、他方は「記録はプロジェクトが作られた物語なので公開前に整理する（リベース）」です。妥協案は「ローカル作業はプッシュ前にリベースで整理し、既にプッシュしたものは決してリベースしない」ことです。

| | マージ | リベース |
|---|---|---|
| 記録の形状 | 分かれて合体する | 1 つの直線 |
| コミットハッシュ | 維持される | 新しく作成される |
| マージコミット | 生成される | 生成されない |
| 既に共有されたコミット | 安全 | 危険 |

核心的なルールは Pro Git にこう書かれています。リポジトリの外にあり、他者がそれを基盤として作業している可能性があるコミットはリベースしないでください。リベースして force push をすると同僚の記録と分岐し、同僚が pull した際に同じ著者・日付・メッセージの重複コミットが発生する可能性があります。

## チームワークフロー

チームで使われる流れはほぼ決まっています。広く知られている方式は 2 つあります。

- ブランチ方式 (feature branch): main から機能ごとにブランチを分岐させ、完了すると pull request でレビューを受け、main にマージします。main は常にデプロイ可能な状態に保ちます。
- Gitflow: main の他に develop, feature, release, hotfix のブランチを役割別に用意します。リリースサイクルが決まっているプロジェクトに適しており、小規模チームには重すぎるという評価があります。

コミットメッセージは 1 行の要約に加え、「何を」「なぜ」変更したかが見えるように書くのが、後で `git log` を読む人（大抵は未来の自分）にとって有益です。

## よくある誤解

- ブランチはフォルダのコピーである: コミットを指すポインタに過ぎません。そのため作成や削除が容易です。
- コミットを消すと永遠に消える: リベースや `reset --hard` で見えなくなったコミットも、一時的には `git reflog` に残ります。上記の実習でも reflog に `rebase (start)`, `rebase (finish)` の記録が刻まれました。ただしデフォルトの整理サイクルが過ぎると消える可能性があるため、永久保存ではありません。
- 衝突は何かを間違えたという意味である: 同じ箇所を二人で修正したというシグナルに過ぎず、チーム作業では珍しくありません。
- git は GitHub である: Git はバージョン管理ツールであり、GitHub は Git リポジトリをホストして pull request を通じて協業するサービスです。

<summary>詳細な解説：よく使うコマンドの整理</summary>
