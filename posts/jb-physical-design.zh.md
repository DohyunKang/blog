物理设计阶段决定了如何将逻辑设计完成的表实际部署到存储设备和数据库管理系统之上。索引、分区、分布式数据库和数据仓库都可以用一句话概括：“当数据量增大时，快速读取和管理数据的方法”。

## 处于设计阶段的哪个环节

数据库设计的流程依次为：需求分析 → 概念设计（ER）→ 逻辑设计（表、键、规范化）→ 物理设计 → 实现。前面的 [规范化与事务](#/post/jb-normalization-transaction) 属于逻辑设计范畴，而从这里开始则是关于以何种结构存储同一表的问题。逻辑设计在不同 DBMS 之间几乎相同，而物理设计则取决于所使用的产品和硬件。

考试中常会涉及物理设计相关的问题。总结如下：

| 工作内容 | 内容说明 |
|---|---|
| 存储结构 | 决定将表和索引放置在哪些文件及空间区域中 |
| 索引设计 | 确定在哪些列上创建何种类型的索引 |
| 分区设计 | 依据什么标准对大表进行拆分 |
| 反规范化 | 因性能考虑，是否故意保留冗余数据 |
| 事务与容量 | 预测并发使用量和数据增长量 |

反规范化是指将经规范化拆分的表，为了查询性能而重新合并或重复存储某些列。但这样做需要在插入和更新时手动维护一致性。这是 [SQL 应用](#/post/jb-sql-basic) 中提到的，当连接操作过多导致性能缓慢时可考虑的一种方案。

## 索引

索引是为快速定位表中所需行而额外构建的数据结构。若无索引，必须从头扫描每一行；若有索引，则可在对数时间内完成查找。但代价是占用更多存储空间，且在插入、更新或删除行时还需同步更新索引，因此写入速度会变慢。基本经验是：以读为主的表适合使用索引，而以写频繁的表则不宜过度依赖索引。更详细的运作机制已在 [索引文章](#/post/db-index) 中单独整理。

考试中常见的分类如下：

- **结构**：B-树（平衡树）系列最常见，也存在哈希索引。若需范围查询，应选择 B-树类索引。
- **聚簇索引（Clustered Index）**：按索引顺序物理存储表的行。每个表只能创建一个，适合范围查询。
- **非聚簇索引（Non-clustered Index）**：通过独立的有序结构指向行。可以创建多个。
- **组合索引**：列的顺序至关重要。（例如按“城市、姓氏、名字”创建的索引，在查找城市时很快，但若仅凭姓氏查找则效率低下。若查询条件未包含最前列的列，则属于误用。）
- **覆盖索引（Covering Index）**：查询所需的所有列都已包含在索引中，因此无需读取表行本身。

某些情况下索引无效也会成为考题。例如 `LIKE '%abc'` 这种前缀带通配符的模式无法有效利用索引。对于 B-树索引，列值应具有较高区分度；而对于重复值较多的列，则适合使用位图索引。

<details>
<summary>设计索引时的选择顺序</summary>

1. 筛选出常用于查询、连接和排序的候选列。
2. 观察值的多样性。若值几乎相同，效果有限。
3. 评估该表的写入频率。若写入频繁，应减少索引数量。
4. 若是组合索引，将常出现在查询条件中的列置于前面。
5. 创建后通过执行计划验证是否实际被使用。

</details>

## 分区

分区是一种逻辑上保持单个表不变、物理上将其划分为多个片段的方法。以 PostgreSQL 文档为例，主要有三种分区方式：

| 方式 | 依据 | 示例 |
|---|---|---|
| 范围（range） | 值的区间 | 按日期每月一个片段 |
| 列表（list） | 直接列出值 | 按地区代码划分 |
| 哈希（hash） | 哈希值对片段数取余 | 均匀分散客户编号 |

其效果主要体现在以下几点：若查询条件中包含分区键，则只需读取对应片段，跳过其余部分（即“分区裁剪”）。旧数据可整片移除或删除，效率远高于大批量 DELETE。不常使用的片段也可迁移至低速且廉价的存储设备。同一文档也指出，这些优势通常在表非常大时才显著体现，盲目过度分区并非总是有益。

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

上述内容简化自 PostgreSQL 官方文档示例。由于语法因 DBMS 而异，考试中应重点关注“范围、列表、哈希三种方式及其适用原因”，而非具体语法细节。

## 分布式数据库

分布式数据库是一种将数据分散存储在不同物理位置，但对用户呈现为单一整体的数据库系统。这些节点可能位于同一数据中心内，也可能通过网络连接分布在异地。其特点是各服务器之间松散耦合，不共享硬件组件；优势在于可在靠近用户的地点处理事务，从而提升性能。

分区的概念通常用“分区”来解释。按行划分称为水平分割，按列划分称为垂直分割。将水平分割分布到多台服务器上，就称为分片（Sharding）。如果分区通常是在单个数据库实例内部进行的拆分，那么分片的区别在于它跨越了多个服务器实例进行数据分配。由于分片的复杂度显著增加，一般建议在其他优化手段不足时才采用。关于为了提升读取性能而在多台机器上复制相同数据的“复制”与“分片”的区别，已在 [复制与分片](#/post/db-scaling) 中专门说明。

复制的主要任务是保持副本的同步，因此较为复杂且消耗大量资源。虽然也存在一种简单的方式：指定一个位置作为源，在固定时间将数据复制到其他地方（即冗余或 duplication），但这种方式仅在源端进行修改。

分片的缺点值得牢记：SQL 语句可能变得复杂；若某个分片损坏，可能会影响整个数据的一致性；备份和模式变更需要针对所有分片统一进行。

## 数据仓库

数据仓库（DW）是一个存储库，用于收集来自多个运营系统的数据并堆积起来以供分析使用。Bill Inmon 总结的四个特性在考试中经常出现。

| 特性 | 含义 |
|---|---|
| 主题导向 | 不以业务处理单元为中心，而是围绕核心主题（如客户、商品等）进行组织 |
| 集成 | 统一多个系统中的名称、单位和代码表示方式 |
| 时变性（时间序列） | 存储长期历史记录，用于分析和预测 |
| 非易失性 | 一旦存入数据，即设置为只读，严禁随意修改或删除 |

与运营数据库（OLTP）相比，其差异十分明显。

| | OLTP | OLAP(DW) |
|---|---|---|
| 用途 | 频繁进行简短的插入、更新和删除操作 | 以聚合为主的复杂查询较少 |
| 数据 | 当前详细数据，通常遵循第三范式 | 历史数据，采用多维结构 |
| 性能指标 | 每秒事务数（TPS） | 响应时间 |

数据进入的过程称为 ETL。即从源系统提取（Extract）、清洗和转换（Transform），最后加载到数据仓库（Load）。若顺序颠倒，先加载原始数据再在数据仓库内部进行转换，这种方式称为 ELT。数据集市是针对某个部门或特定主题的小型数据仓库，其源数据较少且易于构建。

数据仓库中常用的模型是星型模式（Star Schema）。该模式由中心的“事实表”和周围连接的“维度表”组成。事实表中包含诸如订单数量、支付金额等可汇总的度量值；维度表则提供了解释这些度量值的依据，例如订单日期、客户、商品等。想象一个订单事实记录关联了日期、客户和商品维度的场景，这样更容易记忆。

<details>
<summary>用文字描述星型模式</summary>

```
        [날짜 차원]
             |
[고객 차원]--[주문 팩트]--[상품 차원]
             |
        [지점 차원]
```

事实表中包含指向维度表的键以及数量和金额等度量值。维度表通常会进行半规范化处理，以减少连接操作。

</details>

## 常见的混淆点

- **分区与分片**：两者都涉及水平划分，但分区通常在单个数据库管理系统（DBMS）内部进行，而分片则跨越多台服务器。
- **索引并非越多越好**：过多的索引会导致写入变慢并占用更多存储空间。
- **聚簇索引**：每个表只能有一个聚簇索引，因为它决定了行的物理存储顺序，因此不可能存在两个。
- **数据仓库并非运营数据库的简单复制品**：DW 是按主题集成数据并积累历史记录，这与 OLTP 有本质区别。
- **半规范化不是设计错误**：它是经过规范化后，为了性能考量而做出的主动选择。

## 解题思路

涉及概念定义的问题，只需直接回忆上述表格中的关键词（如：主题导向、集成、时变性、非易失性，以及范围、列表、哈希等）即可解答。对于“在此情境下应使用什么”这类问题，可参考以下判断逻辑：若需频繁删除基于日期的旧数据，则使用范围分区；若特定列搜索缓慢，则添加索引；若连接操作过多导致性能下降，则考虑半规范化；若目的是分析性聚合，则使用数据仓库。具体的考试日程和形式可在官方网站查询。
