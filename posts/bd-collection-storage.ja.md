## 収集はどこから、どのような形状でか

まず二つの観点に分けて見ていきます。データがどこから来るのか、そしてどのような形状なのかです。

| 基準 | 区分 | 例 |
| --- | --- | --- |
| 出所 | 内部データ | 社内の DB の注文・顧客テーブル、サービスログ |
| 出所 | 外部データ | 公共データ、ソーシャルメディア、Web ページ |
| 形状 | 構造化（定型） | 行と列が決まったテーブル (RDB, CSV) |
| 形状 | 準構造化（半定型） | 構造はあるが固定された表ではないもの (JSON, XML, ログ) |
| 形状 | 非構造化（非定型） | テキスト本文、画像、動画、音声 |

内部データは入手が容易で品質も一定程度制御できます。外部データは簡単に入手できますが、形式や品質も様々なので整理コストがかかります。試験では「内部か外部か」「構造化か準構造化か」を例題を見て選ぶ問題がよく出ます。JSON が準構造化であることは確実に押さえておけば半分は正解できます。

個人情報が混在したデータを収集する際の注意点は [詳細 → ビッグデータ概要と活用](#/post/bd-overview) で別途整理しました。

## 収集方式：バッチとストリーミング

収集方式は、一度にまとめて取り込むか、流れながら受け取るかで大きく分かれます。

バッチ処理は決まった時間にまとめて取り込みます。1 日に 1 回注文テーブルをまるごとコピーするなどが該当します。実装が単純で大量処理に向いていますが、取り込む間に生じた変化については次のバッチまで把握できません。

ストリーミング処理は発生した瞬間に受け取ります。センサー値やクリックログのように絶えず生成されるデータに使います。この分野の代表的なツールは Apache Kafka です。Kafka の紹介文書では、イベントストリーミングをデータベース・センサー・アプリなどの出所からリアルタイムでデータを収集し、長期間保存し、到着時または後で処理し、他のシステムへ送る作業として説明しています。用語も試験に出る可能性があります。

| 用語 | 意味 |
| --- | --- |
| トピック (topic) | イベントが保管される命名された集合体。フォルダのようなもの |
| プロデューサー (producer) | イベントを出力する側 |
| コンシューマー (consumer) | イベントを読み取る側。必要に応じて再読み込みが可能 |
| パーティション (partition) | トピックを分割した単位。同じキーのイベントは同じパーティションに入り、その中では順序が維持される |
| 保持期間 (retention) | トピックごとに設定する、古いイベントを削除するまでの期間 |

出力側と入力側がトピックを挟んで離れている点が核心です。そのため、収集機が遅くても出力側が詰まらず、読み取る側が複数あっても問題ありません。

[詳細 → 非同期処理とキュー](#/post/be-async-queue) ではバックエンドの観点から同じ構造について記述しています。

## ETL とクロール

ETL は抽出 (Extract)、変換 (Transform)、積載 (Load) の頭文字です。出所から取り出し、利用可能な形状に変換し、目的先に投入します。順序が重要です。順序を変えてまず積載してから後で変換する方法は ELT と呼ばれます。試験では ETL の 3 つの文字がそれぞれ何を指すか、どの段階で重複削除や形式統一が行われるかを問います。答えは変換段階です。

小さな例を直接動かしてみました。CSV を読み込んで重複を除去し、空欄の価格を埋めた後、SQLite に投入して SQL で集計します。

```python
import pandas as pd, sqlite3, io

src = pd.read_csv(io.StringIO("id,name,price\n1,a,1000\n2,b,\n3,a,1000\n3,a,1000\n"))
# Extract: 위에서 읽은 src
# Transform: 중복 제거, 빈 값 처리
t = src.drop_duplicates().assign(price=lambda x: x.price.fillna(0).astype(int))
# Load: DB에 적재
con = sqlite3.connect(":memory:")
t.to_sql("product", con, index=False)
print(pd.read_sql("select name, sum(price) s, count(*) n from product group by name", con).to_dict("records"))
print(len(src), len(t))
```

出力は `[{'name': 'a', 's': 2000, 'n': 2}, {'name': 'b', 's': 0, 'n': 1}]` と `4 3` です。4 行が 3 行になりました。価格が空欄だった b を 0 で埋めたのは例を実際に動かそうとしたためです。実際に空値を 0 で埋めるかは分析目的によって異なり、それは [詳細 → データ前処理](#/post/bd-preprocessing) で扱います。

クロールは Web ページをプログラムで巡回してダウンロードし、必要な部分を抽出する収集方式です。外部データの中で構造化された形式で提供されていないものを入手する際に使います。試験の観点では「Web ドキュメントを自動的に収集」程度の定義と、公開 API があればクロールよりも API を使う方が安定するという常識レベルで理解していれば十分です。サイトごとに利用規約や収集許容範囲が異なるため、実際に実施する場合はその規定をまず確認してください。

## 保存：データ形状に合った容器

保存技術はデータの形状と利用方法に応じて選択します。

| リポジトリ | 適したデータ | 特徴 |
| --- | --- | --- |
| RDB | 構造化された、関係性が明確なデータ | スキーマが先に定義され、SQL で照会する。トランザクション性が強い ([詳細 → 関係型 DB と SQL](#/post/db-rdb-sql)) |
| NoSQL | 半構造化・非構造化、スキーマが頻繁に変化するもの | 種類が多い ([詳細 → NoSQL の種類と選択](#/post/db-nosql)) |
| 分散ファイルシステム (HDFS) | 非常に大きなファイル | 複数のサーバーに分割して保存する |

### HDFS

Hadoop 公式ドキュメントの HDFS 設計説明から、試験で出題されそうな部分のみ抜粋しました。

- メスター役の NameNode がファイル名空間 (namespace) と、どのブロックがどの DataNode にあるかを管理します。
- DataNode は実際のブロックを保存し、読み書きリクエストに応じます。
- ファイルは「一度書き込み、複数回読み取り」(write-once-read-many) のモデルです。閉じた後には追加 (append) と切り捨て (truncate) だけで変更されます。
- 低い遅延よりも高いスループットを優先します。バッチ処理に合わせた設計です。
- ブロックは大きく設定します。ドキュメントでは典型的なサイズとして 128MB を言及しています。ファイルごとに設定可能です。
- レプリカは通常 3 つ置きます。ファイル作成時に指定し、後から変更できます。
- データを計算側へ移動させるよりも、計算をデータのそばで行う方がネットワーク負荷が少なくなります。

「NameNode はメタデータ、DataNode は実際のデータ」という言い換えに騙されないようにします。また、HDFS は小さなファイルを頻繁に修正する用途ではなく、大きなファイルを一度書き込んで読み取る用途である点が誤答排除に使われます。

### NoSQL

NoSQL は単一の技術ではなく、種類の集合体です。キー・バリュー、ドキュメント、カラムファミリー、グラフに分けるのが一般的です。それぞれいつ使うかは上記リンクに記載しているので、ここではドキュメント型のみ触れます。

MongoDB のドキュメントはデータを BSON ドキュメントとして保存し、同じコレクション内のドキュメントでもフィールドやデータ型が一致する必要はないと説明しています。フィールドを追加する際も既存のドキュメントを書き換えるかマイグレーションを回す必要はありません。値の中にドキュメントや配列をネストでき、同時にアクセスするデータは一緒に保存するという原則で設計されています。必要であればスキーマ検証で構造を強制することも可能です。試験では「スキーマが柔軟である」ことが NoSQL の代表的な特徴として出題され、このドキュメントがその根拠となります。

<details>
<summary>RDB と NoSQL、どちらを選ぶか (まとめ)</summary>

- テーブル間の関係性と整合性が重要なら RDB。
- 構造がバラバラだったり頻繁に変化したりするならドキュメント型などの NoSQL。
- どちらか一方だけを使う必要はありません。一つのサービス内で使い分けることもあります。
- 試験は通常「特徴の選択肢から正しいものを選ぶ」形式なので、RDB はスキーマ固定・SQL・トランザクション、NoSQL はスキーマ柔軟・水平スケーリングというようにまとめて覚えると良いでしょう。
</details>

## 品質管理：4 つを確認する

収集・保存したデータは書き込む前に品質をチェックします。概念としては完全性（欠落値がないか）、一意性（重複がないか）、妥当性（許容範囲・形式に合っているか）、一貫性（同じものは同じように記述しているか）といった項目があります。名称は資料によって多少異なりますので、選択肢の意味を見て判断します。

この 4 つがコードではそれぞれ 1 行で済むことを実際に確認しました。

```python
import pandas as pd, io

raw = io.StringIO("""id,age,city,amount,date
1,25,Seoul,1200,2026-01-03
2,,Busan,800,2026-01-04
2,,Busan,800,2026-01-04
3,41,seoul,-50,2026-01-05
4,200,Daegu,3000,2026/01/06
5,33,Incheon,,2026-01-07
""")
df = pd.read_csv(raw)

print(df.isna().mean().round(2).to_dict())          # 완전성: 열별 결측 비율
print(df.duplicated().sum())                         # 유일성: 중복 행 수
print(df['city'].str.lower().str.strip().value_counts().to_dict())  # 일관성: 표기 통일 후 집계
print(((df.age < 0) | (df.age > 120)).sum(), (df.amount < 0).sum())  # 유효성: 범위 밖
d = pd.to_datetime(df['date'], errors='coerce', format='%Y-%m-%d')
print(d.isna().sum())                                # 유효성: 날짜 형식 불일치
```

出力は以下の通りでした。

| チェック | 結果 |
| --- | --- |
| カラムごとの欠損率 | age 0.33, amount 0.17, その他 0 |
| 重複行 | 1 |
| city の表記統一後の集計 | seoul 2, busan 2, daegu 1, incheon 1 |
| 年齢範囲外 / 負の金額 | 1 / 1 |
| 日付形式の不整合 | 1 |

`Seoul` と `seoul` は目で見れば同じ都市ですが、そのまま集計すると異なる値になります。小文字に統一してから初めて seoul が 2 つにまとまりました。これが一貫性の問題です。年齢 200 や負の金額は値自体はあるが意味がないケースなので、完全性ではなく妥当性で引っかかります。日付 `2026/01/06` は他の行と区切り文字が異なるため形式が合っていないと判定されました。

ここで一つ区別しておきます。この段階は問題を発見して数える段階です。見つけた欠損値・異常値をどう処理するかは前処理の段階になります。

## よく出るパターン

- 構造化・半構造化・非構造化の例で分類する。JSON・XML・ログは半構造化。
- ETL の各段階の役割、変換段階で行うこと。
- バッチとストリーミングの違い、ストリーミングツールのトピック・プロデューサー・コンシューマー。
- HDFS における NameNode と DataNode の役割、大きなブロックとレプリカの理由。
- RDB と NoSQL の特徴比較。
- 品質項目の名称と意味を結びつける。

## 解き方

用語の問題は、まず選択肢からキーワードを捉える。"リアルタイム"が見えればストリーミング、「メタデータを管理」が見えれば NameNode、「スキーマ柔軟」が見えれば NoSQL、「同じものを同じように」が見えれば一貫性である。過去問は毎年選択肢が少しずつ変わる場合が多いので、概念ごとに「この言葉が見えたらこれ」という対応を一行ずつ作っておけば時間を節約できる。
