# コンテキストウィンドウとトークン

コンテキストウィンドウは、モデルが回答を生成する際に一度に処理できるテキスト量の上限であり、その量を計測する単位がトークンです。この 2 つを理解しておけば、「なぜ会話が長くなると遅くなり、高くなるのか」という疑問のほとんどが説明できます。

## トークンとは何か

トークンは、モデルが文章を読み書きする際に使用する最小の断片です。文字でも単語でもなく、その間のどこかです。Anthropic の用語集では、トークンが単語、サブワード、文字、さらにはバイトに対応しうる可能性があると記載されています。モデルは文章を受け取ると、まずこれらの断片の列挙に変換して処理します。

頻出する塊は 1 トークンにまとめられ、稀な単語は複数の断片に分割されます。OpenAI の tiktoken の説明にも似た例があります。「encoding」が「encod」と「ing」に分かれるといった具合です。よく使う断片を大きくまとめれば、同じ文章でも少ないトークン数で表現でき効率が良く、分割可能なため初めて見る単語も処理できます。

大まかな感覚はこれくらいです。tiktoken の README では平均的に 1 トークンが約 4 バイトであると記載されています。英語に換算すると 1 トークンが文字で 3〜4 文字程度です。Claude の用語集でも、以前のモデル基準では 1 トークンが英語で約 3.5 文字とあり、4.7 以降のモデルは新しいトークナイザーを使用するため、同じ文章でも約 30% 多くのトークンが必要になると記載されています。モデル世代によって数字が変わるため、正確な値を知るには使用するモデルのトークンカウントツールで計測するのが文書の案内です。

## なぜ韓国語はもっと多いのか

ここで韓国語が不利になります。理由は 2 つに整理できます。

- 韓国語の 1 文字は UTF-8 で 3 バイト、英語のアルファベットは 1 バイトです。バイト単位で分割する方式ではスタートラインから不利です。
- トークナイザーの辞書が英語中心で作られていれば、英語単語は丸ごと 1 トークンになりますが、韓国語は音節単位に細かく分割されます。

前者は一般的な原理であり、どのトークナイザーが具体的にどのように分割するかはモデルによって異なります。測定事例を一つ見つけました。ある開発者が同じブログ記事 285 編を英語・韓国語・日本語・中国語で比較し、トークン数を計測した結果です。

| 英語に対する韓国語のトークン数 | 倍率 |
|---|---|
| o200k (OpenAI の最新トークナイザー) | 1.38 倍 |
| cl100k (OpenAI の以前のトークナイザー) | 1.82 倍 |
| Claude トークナイザー（公開されているもの） | 1.88 倍 |

一文で見てみると、「I refactored the agent loop to cut token usage.」が 12 トークンに対し、韓国語の「토큰 사용량을 줄이려고 에이전트 루프를 다시 짰다.」は o200k で 20 トークン、Claude トークナイザーでは 32 トークンだったそうです。「에이전트」が o200k では 4 トークンに分割される一方、英語の「agent」は 1 トークンです。

この数字は注意深く見る必要があります。著者自身も対象が英語コードや用語が多い技術ブログであるため、一般的な韓国語散文では格差がさらに大きいかもしれないと記載しており、トークン数が即座にコストではないとも述べています。韓国語は同じ意味をより少ない文字で表せるためです。

要約すると「韓国語は英語よりも一般的にトークンが多くかかります。どの程度かはトークナイザーや文章の種類によって 1.4 倍からそれ以上まで幅があります」程度の話です。新しいトークナイザーほど格差が縮まる傾向は上記の表でも見られます（cl100k から o200k へ移行する過程で韓国語が 24.7% 減少したとあります）。

## ウィンドウサイズの意味

ウィンドウとは「1 つのリクエストに含まれるトークンの総量」です。学習データ全体とは別の話であり、Anthropic の文書における表現ではモデルの「ワーキングメモリ」です。モデル内に埋め込まれた知識ではなく、現在のリクエストに載せられるもののみをカウントします。概念自体は [詳細 → コンテキスト](#/post/ai-context) で別に整理しています。

サイズはモデルによって異なります。現在のドキュメント基準では、Claude の最新モデル（Opus 5.5, Sonnet 5.5, Haiku 5.5 など）は 100 万トークンのウィンドウを持ち、1 つのリクエストで生成可能な出力の最大値は 12 万 8 千トークンです。一部の旧モデルでは 20 万トークンです。この数字は頻繁に変更されます。数ヶ月後にこの記事を読む場合は、モデル比較表を再度確認するのが適切です。

## 入力と出力が合算される

最初は混乱した部分ですが、ウィンドウは入力のみをカウントしません。文書には「ウィンドウは『応答自体を含めて』モデルが参照できるテキスト」と記載されています。システムプロンプト、`messages` のすべてのメッセージ（ツール結果・画像・ドキュメントを含む）、ツールの定義もすべて含まれ、モデルが生成した回答と思考（thinking）も含まれます。

そのため、入力でウィンドウがいっぱいになると出力する余地がありません。文書によれば、入力だけでウィンドウを超えると 400 エラー（"prompt is too long"）が発生し、Claude 4.5 以降のモデルは入力 +`max_tokens` を超えてもリクエストは受け付けるが、生成中に限界に達すると `model_context_window_exceeded` で停止します。

```
[ 시스템 프롬프트 | 도구 정의 | 지난 대화 | 이번 질문 | 모델이 쓰는 답 ]
 └──────────────── 전부 합쳐서 윈도우 하나 ────────────────┘
```

## 各呼び出しですべてが再計算される

これがこの記事で最も覚えておくべき点だ。対話は続いて見えるが、API は記憶を持っていない。文書の説明に従えば、各ターン（turn）の入力段階には「前回の対話全体 + 今回のユーザーメッセージ」が入り、モデルが生成した回答は次のターンの入力となる。私が 1 行打ち込むだけで、前の対話がすべて再送信されるのだ。

感覚を掴むために仮定して計算してみた（実際の測定ではなく単純な仮定）。

- 各ターンで対話が 1,000 トークンずつ増え、20 ターン行うとしよう。
- n 番目の呼び出しの入力は、およそ n × 1,000 トークンである。
- 20 番目の呼び出しの入力は約 2 万トークンである。
- 20 回呼び出した入力トークンをすべて足すと 1+2+…+20 = 210 となり、およそ 21 万トークンになる。

対話の長さは 2 万なのに、出力される入力は 21 万だ。ターンが増えるほど合計はターンの数の二乗に近くなる。ターンを 2 倍にすると（40 ターン）、合計は 82 万になり約 4 倍になる。長く引き伸ばすほど「もう一度聞く値」が徐々に大きくなる構造だ。

## 長くなるとコスト・速度・品質

- **コスト**: API は入力トークンと出力トークンで課金する。前述のように入力が毎回蓄積されて再び出力されるため、長くなるほど呼び出しあたりの料金が上がる。プロンプトキャッシングは役立つ。文書によるとキャッシュ読み込みは基本入力単価の 0.1 倍（モデルによっては 0.05 倍、0.025 倍もある）で、書き込みは 5 分キャッシュが 1.25 倍、1 時間キャッシュが 2 倍だ。基本寿命は 5 分なので、しばらく休んで戻ってくるとキャッシュが期限切れになる。
- **速度**: 入力が長くなると最初のトークンが出るまでの時間が伸びやすい。文書ではキャッシングにより長い文書でも最初のトークンまでの時間を通常改善すると記載されている。
- **品質**: 最も見落としがちだ。Anthropic の文書は「より多くのコンテキストが自動的に良いわけではない。トークンが増えるほど精度と再現率が低下し、これを context rot と呼ぶ」と述べている。

品質については 2 つの研究も確認した。

- Liu らの"Lost in the Middle": 関連情報が入力の最初や最後にある場合性能が最も良く、真ん中にあると大きく低下する。長いコンテキスト用のモデルでも同様だった。
- Chroma の"Context Rot": 18 のモデルを比較し、課題の難易度を固定しても入力が長くなるほど性能が低下した。似たような内容だが間違った妨害文節がある場合も、長さが増すほどより大きく揺れた。同じ対話において 300 トークン程度の短い入力と約 11 万 3,000 トークンの全入力を比較したところ、短い方がはるかに良かった。

どちらも特定の実験結果だ。Chroma は原因を説明しないと自ら明かしており、位置効果については両研究で結果が分かれている（Lost in the Middle は位置効果があるとし、Chroma の needle 実験では位置効果が目立たなかった）。そのため「長くなれば必ず悪くなる」のではなく、「長くなるほど不安定になる可能性がある」と受け取った。

## コンパクション（圧縮）

ウィンドウがいっぱいになると選択肢は主に 3 つある。新しい対話に切り替えるか、古い部分を切り捨てるか、要約して続けるか。コンパクションは 3 番目の方法だ。Anthropic の文書での定義は、古いターンを Claude がサーバー上で作成した要約に置き換え、対話をウィンドウ内に維持することである。アクティブなコンテキストを小さく保つ効果もあるという。対話が長くなるほど品質が低下するためだ。

文書で示された方法は大きく 2 つある。

| | リクエストから直接 | トークン制限から自動 |
|---|---|---|
| タイミングの決定者 | アプリケーション側 | API が入力が基準に達した時 |
| 直近ターンの原文保持 | 可能 | 一時停止後に再度投入する方式 |
| バックグラウンド実行 | 可能 | 不可（そのリクエスト内で実行） |

どちらもベータ版とされている。実際に試していないため動作は文書の説明レベルしか知らない。クライアント側で私が作成した要約器を使うこともできる。

原理は単純で代償も明確だ。要約から除外されたものは戻ってこない。そのため文書でも基本要約が後のターンに必要なものを抜かすと、要約プロンプトを直接使うよう案内している。何を残すかが設計そのものだ。このようなことは Harness が担当することが多いが、詳しくは [詳細 → Harness](#/post/ai-harness) にある。

## よくある誤解

- ウィンドウが 100 万だから全部入れられる：入れているからといってうまく使うわけではない。context rot の研究がその違いを示している。
- ウィンドウは入力サイズだ：出力と思考トークンも合わせて含む。
- モデルは前の対話を記憶する：記憶ではなく、前の対話を毎回再受信しているのだ。チャットアプリはその点を隠すだけだ。
- キャッシングすればウィンドウの心配はない：文書ではキャッシュされたプロンプトもウィンドウを占拠するとある。変わるのは支払うお金であり、スペースではない。
- 韓国語は英語より正確に N 倍かかる：トークナイザーによって異なる。私の文章、私のモデルで直接計測するのが正確だ。

<details>
<summary>詳しい解説：思考（thinking）トークンとウィンドウ</summary>

思考トークンは `max_tokens` の一部であり、出力トークンとして課金され、ウィンドウにも含まれます。モデルによっては、前のターンでの思考を次のリクエストに保持するかどうかは異なります。ドキュメントによると、Opus 4.5 以降の Opus、Sonnet 4.6 以降の Sonnet、Haiku 5.5 などでは、以前の思考ブロックをデフォルトで保持し、通常の入力のようにウィンドウを使用するとともに、入力としても再度課金されます。以前の Opus・Sonnet および Haiku 4.5 までは、API が自動的に切り離します。思考トークンは生成時に出力として一度課金され、保持されるモデルについては、その後のリクエストで入力として再度課金されます。

ツールを使用する場合、ツールリクエストと結果も同様に蓄積されます。ツールの定義自体がウィンドウを占有するため、ドキュメントではツールの定義を短縮したり、後から読み込ませたりする方法について別途案内しています。

</details>

<details>
<summary>詳細な解説：残りのトークンをモデルが知っているか</summary>

ドキュメントによると、Sonnet 5、Sonnet 4.6、Haiku 4.5 などには「コンテキスト認識」機能があり、システムプロンプトに全体の予算が注入され、ツール呼び出し後に残った量を通知します。Opus 4.7 以降や Sonnet 5.5 などでは、このタグを受け取らず、代わりに task budget（ベータ）を通じて予算を割り当てるとのことです。
