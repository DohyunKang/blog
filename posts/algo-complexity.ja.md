時間計算量は、入力が大きくなると演算回数がどのくらい速く増加するかを表す方法であり、競技プログラミングでは入力サイズだけを見て「この解法で時間内に通るか」を事前に推測するために使います。

## 時間計算量とは何か

同じ問題を解いても、コードによってかかる時間は異なります。秒単位で計測するとコンピュータごとに変わるため、入力の大きさ n が大きくなったときに演算回数がどのような式で増えるかのみを見ます。これを Big-O で表します。

- 配列を一度走査すると約 n 回の作業を行います。O(n)。
- ネストした繰り返し文であれば n×n 回です。O(n²)。
- 毎回半分ずつ減らせば log n 回です。O(log n)。

定数倍や低い次数は捨てます。3n+5 も、100n も O(n) です。実際には 100 倍の差がありますが、n が大きくなったときに曲線の形が同じであるという意味でそう分類します。通常は最悪の場合を基準にして表します。

## 入力サイズでの推定

競技プログラミングサーバーでは、大まかに Python で 1 秒間に数千万回程度の単純な演算を行うと想定されています。この数値は採点環境によって異なるため正確な値ではなく感覚的なものです。この感覚で n の範囲を見ると、使える解法がほぼ決まります。

| n の最大値 | 概ね許容される計算量 | 思い浮かべるもの |
|---|---|---|
| 10~20 | O(2ⁿ), O(n!) | 完全探索、バックトラック |
| 500 | O(n³) | 三重繰り返し、フロイド・ワーシャル |
| 5,000 | O(n²) | 二重繰り返し、単純な DP |
| 100,000~1,000,000 | O(n log n) | ソート、二分探索、ヒープ |
| 10,000,000 以上 | O(n) または O(log n) | 一度走査する、式計算 |

表は感覚的なものですから、正確にこの通りとは限りません。それでも n が 10 万で二重繰り返し文を書いてしまうと 10¹⁰ 回となり時間超過になることはすぐに気づけます。コードを書く前にこの計算を先にやる習慣が最も価値がありました。

## よく見る計算量はいくつかあるか

- O(1): インデックスで値を取り出す、辞書からキーで検索（平均）。
- O(log n): ソートされた配列での二分探索。[詳細 → ソートと二分探索](#/post/algo-sort-search)
- O(n): リストを一度走査する、合計を求める、最大値を見つける。
- O(n log n): ソート。Python の `sort()` がこれに該当します。
- O(n²): すべてのペアを比較する二重繰り返し文。
- O(2ⁿ): 要素ごとに「入れる/入れない」を選ぶすべての部分集合。[詳細 → 再帰とバックトラック](#/post/algo-recursion)

空間計算量も同じように表します。追加で使うメモリが入力の大きさに比例して増える場合は O(n) です。競技プログラミングでは時間の方がまず問題になることが多いですが、DP テーブルを n×n とするとメモリも同時に考慮します。

## 例：2 つの数の和

「配列から target の和になる 2 つの要素の位置を見つけろ」といった問題を考えましょう。二重繰り返し文ですべてのペアを見れば O(n²) です。通った値を辞書に記録しておき、`target - x` がすでに存在するかどうかだけ見れば O(n) です。

```python
def two_sum_slow(a, t):          # O(n^2)
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):
            if a[i] + a[j] == t:
                return (i, j)

def two_sum_fast(a, t):          # O(n), 공간 O(n)
    seen = {}
    for i, x in enumerate(a):
        if t - x in seen:
            return (seen[t - x], i)
        seen[x] = i
```

実際に動かしてみると、どちらも `1..3000` で同じ答え `(2998, 2999)` を出しました。時間は遅い方が n=5,000 で 0.25 秒、速い方は n=200,000 で 0.025 秒でした。入力が 40 倍大きくなっても 10 倍速かったのです。時間は自分の PC の基準なので数字自体の意味はなく、差だけを見ればよいです。時間を減らすためにメモリを使ったことになります。このようなトレードオフがハッシュを使う理由です。[詳細 → 配列・文字列・ハッシュ](#/post/algo-array-hash)

<details>
<summary>Big-O の定義を式で見る</summary>

f(n) が O(g(n)) というのは、十分大きな n から f(n) ≤ c·g(n) となる正の定数 c が存在することを意味します。例えば f(n) = 3n² + 10n + 7 なら n ≥ 1 で f(n) ≤ 20n² なので O(n²) です。

同じ O(n) でも 1 回の反復でやることが異なれば実際の時間は結構差が出ます。競技プログラミングでは定数倍は通常無視しますが、限界がきつい問題では定数が決定的になる場合があります。
</details>

## Python で遅くなりやすい場所

計算量はアルゴリズムだけの問題ではなく、使用するデータ構造の演算にも付随しています。Python では外見上一行で書けても中身で O(n) の演算がいくつかあります。

| やりたいこと | 遅い書き方 | 速い書き方 |
|---|---|---|
| 先頭から取り出す | `list.pop(0)` O(n) | `deque.popleft()` O(1) |
| 値があるか確認 | `x in list` O(n) | `x in set` 平均 O(1) |
| 文字列の連結 | 繰り返し `s += t` | リストに集めて `"".join()` |
| 中間要素へのアクセス | `deque[i]` O(n) | `list[i]` O(1) |

`collections.deque` の公式ドキュメントには、リストは `pop(0)` と `insert(0, v)` で O(n) のメモリ移動コストがかかること、deque は両端から要素を追加・削除する操作が O(1) であることが記載されています。同じドキュメントには、deque のインデックスアクセスは両端で O(1)、中央では O(n) であるとも書かれています。キューが必要な場合は deque、インデックスによる参照が多い場合はリストです。[詳細 → スタック・キュー・デッキ](#/post/algo-stack-queue)

自分の PC で計測した値は以下の通りです。時間は環境によって異なるため、比率だけ参考にしてください。

| 実験 | 時間 |
|---|---|
| 10 万件のリストで `pop(0)` を 5 万回実行 | 0.36 秒 |
| 同じサイズの deque で `popleft()` を 5 万回実行 | 0.001 秒 |
| 2 万件のリストで `in` を 2 千回実行 | 0.12 秒 |
| 2 万件の set で `in` を 2 千回実行 | 0.0001 秒 |

文字列については、Python の公式ドキュメント（シーケンス型）に、不変シーケンスを繰り返して連結すると全体の長さに対して平方時間がかかる旨が記載されています。文字列はリストにまとめておき、`join` で一度に連結するよう案内されています。

ソートについては、`sort()` と `sorted()` が安定ソートであることがドキュメントに記載されています。同じ値同士で元の順序を維持するという意味であり、基準を 2 回に分けてソートする際にこの性質を使います。ソート自体は O(n log n) であると覚えておけば十分です。

## コードテスト用入出力の基本

入力が多い問題では `input()` が遅く、時間超過の原因になることもあります。そのため、通常は以下のように始めます。

```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
arr = list(map(int, input().split()))
print(n, m, arr)
```

`3 5` と `1 2 3` を入力して実行すると、`3 5 [1, 2, 3]` がそのまま出力されます。`readline` は改行文字も一緒に読み取るため、文字列をそのまま使う場合は `.rstrip()` を追加します。数値に変換する場合は問題ありません。

再帰を深く使う問題では、Python のデフォルトの再帰制限が低いため `sys.setrecursionlimit` を上げるケースが多いです。この部分は再帰に関する記事で続けます。この記事で直接実行して確認したのは上記のコードまでです。

出力が多い場合は、毎回 `print` を呼ぶのではなくリストにまとめて `"\n".join(...)` で一度に出します。これも上記の文字列連結と同じ理由です。

<details>
<summary>1 行にいくつの入力が来るか迷う場合</summary>

- 1 行に整数 1 つ: `n = int(input())`
- 1 行に複数の整数を変数として: `a, b = map(int, input().split())`
- 1 行に複数の整数をリストとして: `arr = list(map(int, input().split()))`
- 複数行がグリッド状にある場合: `grid = [list(map(int, input().split())) for _ in range(n)]`
- 数字がついた文字列（例：`10110`）: `list(map(int, input().rstrip()))`

上記の `readline` 方式では、入力終了時の改行は `int()` が自動的に処理してくれますが、文字列の場合は `rstrip()` の必要があります。
</details>

## よくある誤解

- 複雑度が低ければ必ず速い: n が非常に小さい場合は、単純な O(n²) でも複雑な O(n log n) よりも速くなる可能性があります。概算は n が大きい場合に当てはまります。
- 反復문이がネストしていれば必ず O(n²): 内側が定数回しか回らなければ O(n) です。内側の範囲が何によって変化するかに注意する必要があります。
- Python の組み込み関数はすべて O(1): `in`、`list.index`、`list.count`、スライシングはすべて長さ分かかります。一行で済むからといって軽くはありません。
- 平均と最悪は同じ: ディクショナリや set の O(1) は平均の話であり、ハッシュが激しく衝突すると遅くなることがある点は知っておく必要があります。

データベースでインデックスを使う理由も似たような計算です。全体をスキャンする O(n) の代わりに、木をたどって O(log n) で探すというものです。そのあたりは [詳細 → インデックス](#/post/db-index) で扱います。

アルゴリズムのタイプが全体としてどのように分類されるかは、マップ記事にまとめておきます。[詳細 → アルゴリズムタイプマップ](#/post/algo-map)

時間超過のほとんどはコードが遅いからではなく、書く前に n を見ていないために起こります。
