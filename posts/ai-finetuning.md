파인튜닝은 이미 학습된 모델을 예시 데이터로 한 번 더 학습시켜서 가중치를 조금 바꾸는 방법이다. 프롬프트나 [RAG](#/post/ai-rag)가 모델에게 보여 주는 입력을 바꾸는 것과 달리, 파인튜닝은 모델 자체를 바꾼다. LoRA는 이걸 싸게 하려고 나온 방식 중 하나다.

## 프롬프트, RAG, 파인튜닝 중 뭘 고르나

셋 다 "모델이 내가 원하는 대로 답하게 하는 방법"인데 바뀌는 지점이 다르다.

| | 프롬프트 | RAG | 파인튜닝 |
|---|---|---|---|
| 바뀌는 것 | 지시문 | 모델이 읽는 자료 | 모델 가중치 |
| 준비물 | 글 몇 줄 | 문서 + 검색 시스템 | 예시 데이터 + 학습 환경 |
| 고치는 속도 | 바로 | 문서만 고치면 됨 | 다시 학습해야 함 |
| 잘 맞는 문제 | 지시·형식·역할 | 모르는 지식, 자주 바뀌는 문서 | 일관된 말투·출력 형식·반복되는 행동 |

OpenAI 파인튜닝 문서는 파인튜닝이 예시로 행동을 가르치는 용도라고 설명하고, 잘 맞는 예로 분류, 미묘한 번역, 특정 형식의 출력 생성, 지시를 못 따르는 경우의 교정을 꼽는다. 지식을 넣는 용도는 그 목록에 없다.

고르는 순서는 보통 가벼운 것부터다. [프롬프트](#/post/ai-prompt)를 먼저 다듬어 보고, 모르는 정보가 문제면 RAG, 같은 실수가 계속 반복되는 행동 문제면 파인튜닝을 본다. 문서에도 평가 기준을 먼저 만들어 두고 파인튜닝 결과를 기본 모델과 비교하라는 순서가 나온다. 파인튜닝이 맞는지는 [평가](#/post/ai-evals)로 확인한다는 얘기다.

## 파인튜닝이 하는 일

사전학습된 모델의 가중치는 수십억 개의 숫자다. 파인튜닝은 입력과 원하는 출력이 짝지어진 예시를 보여 주면서 이 숫자들을 조금씩 고친다. 학습이 끝나면 그 변화가 가중치에 들어가 있어서 프롬프트에 예시를 길게 붙이지 않아도 비슷하게 행동한다.

방식은 크게 둘로 나눌 수 있다.

- 전체 파인튜닝: 모든 가중치를 학습한다. 가장 자유롭지만 업데이트할 숫자가 모델 크기와 같아서 메모리와 저장 공간이 많이 든다. LoRA 논문은 GPT-3 175B를 예로, 모델마다 175B짜리 사본을 따로 배포하는 게 큰 부담이라고 문제를 제기한다.
- 파라미터 효율 방식(PEFT): 가중치 대부분은 얼려 두고 일부, 또는 새로 붙인 작은 부분만 학습한다. LoRA가 대표적이다. 어댑터 같은 다른 방식도 있다.

참고로 [LLM](#/post/ai-llm)을 직접 서비스하는 쪽이 아니라 API로 쓰는 쪽이라면, 가중치를 만지는 대신 제공사의 파인튜닝 기능을 쓰게 된다. OpenAI 문서에는 이 플랫폼을 단계적으로 종료 중이라는 안내가 있어서(기존 고객은 2027년 1월 6일까지 작업 생성 가능), 쓰기 전에 현재 가능한지 먼저 보는 게 좋겠다.

## LoRA 원리

논문은 Hu 등이 2021년에 낸 "LoRA: Low-Rank Adaptation of Large Language Models"(arXiv 2106.09685)다. 아이디어는 이렇다. 사전학습된 가중치 행렬 W0는 그대로 두고, 학습으로 생기는 변화량을 작은 행렬 두 개의 곱으로 제한한다.

```
W0: d × k  (얼려 둠, 학습 안 함)
B : d × r  (학습)
A : r × k  (학습)
r : 랭크, d·k보다 훨씬 작은 수

출력 h = W0·x + B·A·x
```

변화량 ΔW 전체를 학습하면 d×k개의 숫자가 필요한데, B와 A로 나누면 r×(d+k)개로 줄어든다. 논문이 이렇게 해도 되는 근거로 드는 건, 모델을 특정 작업에 맞출 때 필요한 변화는 낮은 랭크로도 충분하다는 관찰이다.

초기값이 중요하다. A는 무작위 가우시안으로, B는 0으로 시작한다. 그래서 학습 시작 시점에는 BA가 0이고 모델은 원래 모델과 똑같이 움직인다. 변화량에는 α/r이라는 배율이 곱해지는데, 논문에 따르면 α는 처음 시도한 값으로 고정하고 따로 튜닝하지 않았다. r을 바꿔도 다른 하이퍼파라미터를 다시 맞추는 일이 줄어든다.

적용 위치는 논문 실험 대부분에서 어텐션의 쿼리(Wq)와 값(Wv) 투영 행렬이다. MLP 쪽은 얼려 뒀고, 거기까지 확장하는 건 후속 과제로 남겼다. Hugging Face PEFT 문서도 Transformer에서는 보통 어텐션 블록에만 LoRA를 적용한다고 적는다.

배포할 때는 W = W0 + BA를 미리 계산해 두면 추론 속도가 원래 모델과 같다. 어댑터 층을 끼우는 방식은 층이 하나 더 생겨서 지연이 늘지만 LoRA는 합쳐 버리면 사라진다. PEFT에서는 `merge_and_unload()`가 이 일을 한다.

숫자도 논문에 있다. GPT-3 175B에서 r=4, 쿼리·값 행렬만 적용했을 때 체크포인트가 약 350GB에서 약 35MB로 줄고(약 10,000배), 학습에 필요한 GPU 메모리는 약 1.2TB에서 350GB로 줄었다. 학습 대상이 아닌 파라미터는 옵티마이저 상태를 저장할 필요가 없기 때문이다. 초록에는 RoBERTa, DeBERTa, GPT-2, GPT-3에서 전체 파인튜닝과 같거나 더 나은 품질이 나왔다고 쓰여 있다.

<details>
<summary>자세한 풀이: 파라미터가 얼마나 줄어드나 (직접 계산)</summary>

한 층의 가중치가 4096 × 4096이라고 하자. 전체 학습이면 16,777,216개다. LoRA는 r × (d + k)개다.

| 랭크 r | LoRA 학습 파라미터 | 전체 대비 |
|---|---|---|
| 4 | 32,768 | 약 0.2% |
| 8 | 65,536 | 약 0.4% |
| 16 | 131,072 | 약 0.8% |

위는 행렬 하나 기준의 단순 계산이다. 실제 모델 전체에서의 비율은 어느 행렬에 LoRA를 붙이느냐에 따라 달라진다.

</details>

<details>
<summary>자세한 풀이: PEFT 설정 예시</summary>

Hugging Face PEFT 문서에 나오는 기본 흐름은 네 단계다. 기본 모델을 만들고, `LoraConfig`를 만들고, `get_peft_model()`로 감싸고, 평소처럼 학습한다.

```python
from peft import LoraConfig, get_peft_model

config = LoraConfig(
    r=8,
    lora_alpha=16,
    target_modules=["q_proj", "v_proj"],
    bias="none",
)
peft_model = get_peft_model(base_model, config)
# ... 학습 ...
merged = peft_model.merge_and_unload()
```

`r`은 업데이트 행렬의 랭크로, 낮을수록 학습 파라미터가 적다. `lora_alpha`는 배율이고 기본 배율은 `lora_alpha / r`이다. `target_modules`의 이름은 모델 구조마다 다르다. 위 코드는 PEFT 문서의 예시를 옮긴 것이다.

</details>

## LoRA의 좋은 점과 한계

좋은 점은 기본 모델 하나에 작업별로 가벼운 LoRA 파일을 여러 개 얹을 수 있다는 것이다. PEFT 문서도 얼려 둔 사전학습 가중치 덕분에 다양한 작업용 가볍고 이동 가능한 LoRA 모델을 여러 개 만들 수 있다고 쓴다. 작업을 바꿀 때는 BA를 빼고 다른 B'A'를 더하면 된다.

한계도 논문에 있다. 지연을 없애려고 A, B를 W에 합쳐 버리면, 서로 다른 작업의 입력을 한 배치에 섞어서 처리하기 어려워진다. 지연이 중요하지 않다면 합치지 않고 샘플마다 LoRA 모듈을 고르는 방법이 있다고 한다.

## 데이터 준비 때 필요한 것

OpenAI 문서 기준으로 정리하면 이렇다.

- 형식: JSONL이고 한 줄에 JSON 하나다. 채팅 메시지 형식을 쓴다.
- 양: 최소 10줄이고, 문서는 50~100개 예시에서 개선을 봤다고 하며 잘 만든 예시 50개로 시작해서 결과를 보라고 권한다.
- 평가용 분리: 학습용으로 모은 데이터 일부를 따로 빼 두고 대조군으로 쓰라고 한다. 이 홀드아웃으로 파인튜닝한 모델과 기본 모델을 비교한다.
- 순서: 먼저 "좋은 답"이 뭔지 정의하는 데이터셋과 평가를 만들고, 파일을 올리고, 작업을 만들고, 평가하고 반복한다.

"좋은 답이 뭔지"를 적은 예시가 곧 학습 신호라서, 예시의 품질이 양보다 먼저다. 예시에 틀린 답이나 제각각인 형식이 섞여 있으면 모델이 그걸 그대로 배운다. 학습 데이터에 개인정보나 사내 비밀이 들어가는지도 이 단계에서 걸러야 한다. 모델이 안전하게 답하게 만드는 쪽은 [가드레일](#/post/ai-guardrails)에서 따로 다룬다.

## 흔한 오해

- 파인튜닝하면 우리 문서를 외운다: 문서에 나온 파인튜닝의 용도는 행동을 가르치는 것이다. 지식이 자주 바뀌거나 출처가 필요하면 RAG 쪽이 맞는다.
- 파인튜닝하면 환각이 사라진다: 모델이 지어내는 문제([환각](#/post/ai-hallucination))는 파인튜닝으로 줄 수도 있지만 사라진다고 말할 근거는 없다. 평가로 직접 재는 게 낫다.
- LoRA는 품질이 낮은 대신 싼 방법이다: 논문은 여러 모델에서 전체 파인튜닝과 같거나 더 나은 품질을 보고했다. 모든 작업에서 그렇다는 뜻은 아니다.
- 파인튜닝은 데이터가 아주 많아야 한다: OpenAI 문서는 50~100개 예시에서도 개선을 봤다고 한다. 다만 작업에 따라 다르다.
- LoRA를 쓰면 추론이 느려진다: 합쳐서 배포하면 원래 모델과 속도가 같다.
- 모델을 바꾸면 그대로 쓸 수 있다: LoRA는 특정 기본 모델의 가중치 모양에 맞춰 학습한 것이라 기본 모델이 바뀌면 다시 학습해야 한다. 이 부분은 LoRA 구조(W0에 더하는 행렬)에서 따라오는 얘기다. 모델 선택은 [AI 모델 지도](#/post/ai-models)를 참고한다.
