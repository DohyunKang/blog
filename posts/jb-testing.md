소프트웨어 테스트 단원은 용어가 많아서 외우기 싫은데, 세 가지 축으로 나누면 대부분 제자리를 찾는다. 코드 안을 보느냐(화이트박스·블랙박스), 어느 단계에서 하느냐(테스트 레벨), 코드를 얼마나 훑었냐(커버리지)다. 시험 일정·응시료는 공식 사이트에서 확인하고, 여기서는 개념과 문제 푸는 방식만 정리한다.

## 먼저 큰 그림

| 축 | 질문 | 대표 용어 |
|---|---|---|
| 방식 | 코드 내부를 보고 설계하나 | 화이트박스, 블랙박스 |
| 단계 | 어느 범위를 묶어서 보나 | 단위, 통합, 시스템, 인수 |
| 척도 | 코드를 얼마나 실행했나 | 구문, 결정, 조건, MC/DC 커버리지 |

## 블랙박스와 화이트박스

블랙박스 테스트는 구현을 모른 채 "이 입력이면 이 출력이어야 한다"로 케이스를 만든다. 명세 기반이라 기능 테스트가 대부분이고, 보통 단위 수준에서는 잘 쓰지 않는다. 화이트박스 테스트는 반대로 내부 구조와 코드를 보고, 코드의 경로를 지나가게 입력을 고른다. 구조 기반, 글라스박스라고도 부른다. 명세에 있는데 구현이 빠진 기능은 화이트박스로는 잡기 어렵다.

### 블랙박스 기법

시험에서 자주 묻는 기법은 이름과 한 줄 설명을 짝지어 외우는 쪽이다.

| 기법 | 한 줄 |
|---|---|
| 동치 분할 | 입력을 같이 취급되는 구간으로 나누고 구간마다 대표값 하나만 쓴다 |
| 경계값 분석 | 구간의 경계와 그 바로 앞뒤 값을 쓴다 |
| 원인-결과 그래프 | 입력(원인)과 출력(결과)의 관계를 그래프·결정표로 만든다 |
| 오류 예측 | 경험으로 오류가 날 법한 곳을 짚는다 |
| 상태 전이 | 상태와 이벤트 흐름으로 케이스를 만든다 |
| 비교 테스트 | 같은 입력을 여러 구현에 넣어 결과를 비교한다 |

점수가 60 이상이면 합격이라는 규칙으로 보면 동치 분할은 "59 이하 구간"과 "60 이상 구간" 두 개로 나누고, 경계값은 59, 60, 61을 쓴다. 코드로 돌려 보면 이렇다.

```python
def grade(score, bonus):
    if score >= 60 and bonus:
        return "A"
    if score >= 60:
        return "B"
    return "C"

for s in (59, 60, 61):
    print(s, grade(s, False))
# 59 C
# 60 B
# 61 B
```

경계에서 결과가 바뀌는 지점이 60이라는 게 59·60 두 값에서 바로 드러난다. 경계값 분석이 `>=`를 `>`로 잘못 쓴 버그를 잘 잡는 이유가 이거다.

### 화이트박스 기법

화이트박스는 "커버리지 기준"과 거의 같은 말로 읽힌다. 어떤 기준으로 코드를 훑을지가 기법 이름이 된다. 아래 커버리지 절에서 이어서 본다. 기법 중에는 기초 경로 테스트도 나온다. 제어 흐름 그래프에서 독립적인 경로를 뽑아 테스트하고, 그 경로 수의 기준이 순환 복잡도다.

<details>
<summary>순환 복잡도 계산</summary>

순환 복잡도 V는 제어 흐름 그래프에서 V = E - N + 2(간선 수 - 노드 수 + 2)로 구한다. 판단(분기) 노드가 있는 단순한 구조라면 판단문 수 + 1과 같다. 위 `grade` 함수는 if가 두 개라서 V = 3이고, 독립 경로도 세 개다(A로 끝나는 경로, B로 끝나는 경로, C로 끝나는 경로). 문제는 보통 그래프를 그려 주고 V를 묻는 형태로 나온다.

</details>

## 테스트 레벨

개발 단계와 짝지어 보면 정리가 쉽다.

| 레벨 | 범위 | 키워드 |
|---|---|---|
| 단위 | 모듈·함수 하나 | 드라이버, 스텁 |
| 통합 | 모듈 사이 인터페이스 | 상향식, 하향식, 빅뱅 |
| 시스템 | 전체 시스템 | 기능·성능·보안 |
| 인수 | 사용자·고객 기준 | 알파, 베타 |

단위 테스트는 격리된 코드가 기대대로 동작하는지 보는 것이라, 주변 모듈이 아직 없으면 대신해 주는 가짜가 필요하다. 호출하는 쪽을 흉내 내는 게 드라이버, 호출당하는 쪽을 흉내 내는 게 스텁이다. 통합 테스트는 하향식이면 스텁이 필요하고 상향식이면 드라이버가 필요하다는 짝이 시험에 자주 나온다. 이 방향은 [아키텍처 패턴](#/post/jb-architecture-pattern)에서 보는 계층 구조를 떠올리면 헷갈리지 않는다.

인수 테스트는 사용자가 요구에 맞는지 확인하는 단계다. 개발자 환경에서 사용자가 해 보는 알파와, 실제 사용자 환경에서 해 보는 베타로 나눠 묻는다.

그 밖에 이름으로만 나오는 것들도 있다.

- 회귀 테스트: 수정한 뒤 기존 기능이 안 깨졌는지 다시 보는 것
- 스모크 테스트: 빌드가 기본적으로 돌아가는지 빠르게 보는 것
- 성능·부하·스트레스 테스트: 처리량과 한계를 보는 것

회귀·스모크는 빌드가 자주 나오는 환경에서 자동으로 돌리는 경우가 많다. [형상관리와 빌드·배포](#/post/jb-build-release)와 같이 보면 흐름이 이어진다.

## 커버리지

커버리지는 테스트가 코드를 얼마나 실행했는지의 척도다. 기준이 강해질수록 케이스가 많이 필요하다.

| 기준 | 만족 조건 |
|---|---|
| 구문(문장) | 모든 문장을 한 번 이상 실행 |
| 결정(분기) | 모든 판단의 결과가 참·거짓을 각각 한 번 이상 |
| 조건 | 판단 안의 개별 조건이 참·거짓을 각각 한 번 이상 |
| 조건/결정 | 결정 커버리지와 조건 커버리지를 둘 다 만족 |
| 변경 조건/결정(MC/DC) | 각 조건이 결과를 독립적으로 바꾼다는 걸 보임 |
| 다중 조건 | 조건들의 모든 조합 |

MC/DC는 항공 같은 안전이 중요한 분야에서 요구되는 경우가 많다고 알려져 있다. 경로 커버리지는 가능한 모든 경로를 지나가는 기준이다.

### 같은 함수로 비교해 보기

조건 커버리지와 결정 커버리지가 다르다는 게 시험에서 제일 많이 헷갈리는 지점이라, `grade` 함수로 직접 돌려 봤다.

```python
# 결정 커버리지: 두 if가 각각 참/거짓이 되게
dec = [(70, True), (70, False), (50, False)]
print([grade(*c) for c in dec])   # ['A', 'B', 'C']

# 조건만 맞춘 두 케이스: score>=60 이 T/F, bonus 가 T/F
cond = [(70, False), (50, True)]
print([grade(*c) for c in cond])  # ['B', 'C']
```

두 번째 케이스 묶음은 `score >= 60`과 `bonus`가 각각 참·거짓을 한 번씩 경험했으니 조건 커버리지는 만족한다. 그런데 첫 번째 if의 전체 조건식(`score >= 60 and bonus`)은 한 번도 참이 되지 않았다. 결과 "A"가 나오는 경로를 아무도 지나가지 않은 것이다. 조건 커버리지를 만족해도 결정 커버리지는 못 채울 수 있다는 뜻이고, 그래서 둘을 묶은 조건/결정 기준이 따로 있다.

<details>
<summary>풀이 요령</summary>

커버리지 문제는 보통 코드나 흐름도가 나오고 "이 테스트 세트가 어떤 기준을 만족하는가", 혹은 "구문 커버리지에 필요한 최소 케이스 수는"으로 묻는다. 순서는 이렇게 잡는다.

1. 판단문마다 참·거짓이 되는 입력을 표로 쓴다.
2. 주어진 케이스를 하나씩 대입해서 문장·분기·조건이 지나갔는지 표시한다.
3. 빠진 칸이 있으면 그 기준은 불만족이다.
4. 최소 케이스 수는 참/거짓 경로를 겹치지 않게 묶어서 센다.

위 `grade`에서 구문 커버리지는 `(70, True)` 케이스 하나로 첫 if의 A는 지나가지만 B와 C 문장은 못 지나가서, A·B·C를 모두 지나가려면 3개가 필요하다. 이렇게 직접 대입해 보는 게 외우는 것보다 빠르다.

</details>

## 자주 하는 착각

- 커버리지 100%면 버그가 없다는 말은 아니다. 커버리지는 실행했느냐를 말하지, 기대 결과를 확인했느냐를 말하지 않는다.
- 블랙박스는 코드를 몰라서 약한 테스트가 아니라 명세 기준으로 보는 방식일 뿐이다. 빠진 기능은 오히려 블랙박스가 잡는다.
- 드라이버와 스텁은 헷갈리기 쉽다. 위에서 부르면 드라이버, 아래서 불려 주면 스텁으로 외우면 된다.
