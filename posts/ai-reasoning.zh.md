推理模型是一种在给出答案之前，会先独自撰写思考过程（即“思考令牌”）的模型。即使这些文字不会显示在屏幕上，用户仍需为它们支付输出令牌的費用并等待相应的处理时间。

## 先用通俗的话来说

有些人擅长心算直接得出数学题的答案，而有些人则习惯在纸上写出解题步骤后再作答。普通的 LLM 更接近前者，而推理模型则属于后者。当收到问题时，它会在答案之前“长篇大论”地进行思考，并基于此生成最终答案。这部分解题过程即为“思考令牌（thinking tokens）”（OpenAI 方面称之为 reasoning tokens）。

[LLM](#/post/ai-llm) 原本是一个逐个生成下一个令牌的机制，因此从开始到得出答案所能生成的文本量，实际上就是“可计算的量”。如果让模型写出中间的解题过程，就能更好地解决难题。推理模型就是将这一机制内置于模型之中。

## 原理：为什么让模型“思考”能提升表现

其根源在于 Wei 等人于 2022 年发表的 chain-of-thought（思维链）论文。如果在示例中同时展示中间推理步骤，模型便会模仿这种模式；在足够大的模型上，算术、常识及符号推理性能均有所提升。根据论文摘要，即便是 540B 规模的模型，仅提供 8 个示例即可在 GSM8K（小学数学应用题）测试中达到当时的最高水平。在该研究中，是由人类将解题示例放入提示词中的。

而推理模型则是让模型自行完成这部分解题过程，而非依赖提示词。本文仅讨论其在 API 层面的表现及计费方式。

## API 中的表现

Anthropic 和 OpenAI 的文档中提到的共同点如下：

| | Claude(thinking) | OpenAI(reasoning) |
|---|---|---|
| 名称 | 思考块、thinking tokens | reasoning tokens |
| 是否可见 | 可返回摘要版本或省略（omitted） | API 中不可见 |
| 计费方式 | 按输出令牌计费 | 按输出令牌计费 |
| 占用情况 | 占用（包含在 `max_tokens` 中） | 占用 |
| 深度调节 | effort(low~max) | reasoning.effort(none~max 等，视模型而定) |

Anthropic 文档中值得注意的一点是计费方式。屏幕上显示的是经过摘要的思考内容，但费用却是按照模型实际生成的全部思考令牌计算的。文档中的表述为：计费的输出令牌数与响应中显示的令牌数并不一致。即使将 `display` 设置为 `omitted` 从而完全不接收内容，计费金额依然相同。可以通过响应中的 `usage.output_tokens_details.thinking_tokens` 字段查看实际消耗了多少思考令牌。

OpenAI 的文档也类似。推理令牌在 API 中不可见，但会占用上下文窗口，并按输出令牌计费。此外，他们建议初始启动时预留约 25,000 个令牌用于推理和输出。由于这个数值限制，如果上下文窗口已满，可能导致响应尚未生成任何内容就以 `incomplete` 状态结束。

从 [上下文窗口](#/post/ai-context-window) 的角度来看，思考令牌虽然并非由用户撰写，但仍会占用输入或输出的空间。

## 成本与延迟：为何需要关注

由于思考令牌本质上就是输出令牌，因此两者会同时增加。

- **金钱**：输出令牌的单价通常高于输入令牌（具体单价因模型而异，此处不列数字）。问题本身可能只有一行文字，但思考过程可能长达数千令牌，此时费用主要由思考部分构成。关于功能单元的成本，将在 [AI 服务成本](#/post/app-cost) 中另行讨论。
- **时间**：在答案的首个字符出现之前，模型会先进行思考，因此用户感知到的等待时间会变长。即使通过流式传输接收结果，也必须等到思考阶段结束后才会输出正文内容。

因此，我们需要调节深度的控制手段。

## 深度调节：从 budget 到 effort

Anthropic 文档中展示的变化令人感兴趣。旧有的方式（extended thinking）允许用户直接设定 `budget_tokens` 作为思考预算。该值最小为 1,024 个令牌，且必须小于 `max_tokens`；它只是一个目标值，并非严格的上限。然而，这种方式现已标记为 deprecated，根据文档，Claude 4.7 之后的模型将完全拒绝此方式（返回 400 错误）。

取而代之的是自适应（adaptive）思考模式。模型会根据每次请求自行决定是否进行思考以及思考多少，而用户只需通过 `effort`（low, medium, high, xhigh, max）参数设定其倾向即可。根据文档总结出的特点如下：

- 简单的问题可以不加思考直接回答，因此不能编写假设“每个回合都有思考块”的代码。
- 成本上限由 `max_tokens` 负责，这是思考与回答总用量的硬性限制。如果思考过长导致该限额先被耗尽，回答就会被截断，因此基于无思考的回答设定的值可能过小。
- 若想减少思考，文档建议降低 effort 参数，而不是在提示词中说“少想一点”。部分模型通过提示词无法有效减少思考量。
- 中途更改 effort 会破坏提示词缓存（prompt cache），因此在单次对话中最好固定该值。这与 [提示词缓存](#/post/ai-prompt-caching) 相关。

默认 effort 因模型而异（文档指出某些模型为 high，某些为 medium），使用时需查阅文档中的各模型对照表。

## 何时使用

OpenAI 文档建议对复杂问题求解、编程、科学推理以及多阶段代理任务使用推理模型。[代理循环](#/post/ai-agent-loop) 中指出，每次接收工具结果时进行思考更为有利；Anthropic 文档也描述了在工具调用之间穿插思考（interleaved）的操作方式。相反，对于润色句子、分类或简单提取等能直接得出答案的任务则无需思考。上述判断标准并非来自文档的直接对比，而是基于前述内容自行整理。

## 常见误解

- 推理模型没有幻觉：目前尚无证据表明进行思考就能消除 [幻觉](#/post/ai-hallucination)。
- 可见的摘要等于全部思考过程：这只是摘要版本。计费也是基于整体输出而非仅摘要部分。
- 思考时间越长越好：文档指出预算增加会导致收益边际递减（Anthropic，视任务而定），延迟和成本确实会随之上升。
- 思考令牌是免费附加功能：按输出令牌计费。
- [采样](#/post/ai-sampling) 设置（如 temperature）会被完全采纳：各模型可能存在限制，需查阅文档确认。

<summary>详细解析：Anthropic 计费结构</summary>

根据文档，使用思考功能时将产生三项费用：

1. 思考过程中消耗的令牌（按输出令牌计费）。
2. 保留在上下文中的先前回合思考块（按输入令牌计费）。不同模型可能保留所有回合或仅保留最后一个回合。
3. 普通回答的输出令牌。

据称，生成思考摘要不单独计费。`output_tokens` 为计费总量的总和，而 `thinking_tokens` 是其内部明细（只读）。示例响应中 `output_tokens` 为 348，其中 `thinking_tokens` 为 312。这仅是文档中的示例数值，并非平均值。
