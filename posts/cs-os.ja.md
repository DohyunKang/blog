オペレーティングシステム (OS) は、CPU やメモリといった限られたリソースを複数のプログラムが共有できるように管理するものです。プロセス、スケジューリング、仮想メモリ、同期化は、この一つの機能を異なる側面から見た名称に過ぎません。

## 定義から

プログラムとはディスク上のファイルであり、プロセスはそのファイルを実行中の状態です。プロセスには独自のメモリ空間（コード、データ、ヒープ、スタック）や開いているファイルなどのリソースが割り当てられています。一つのプログラムを二回実行すれば、二つのプロセスが生まれます。

スレッドは、プロセス内で実行フローだけを独立して持つ単位です。同じプロセス内のスレッド同士はヒープとコードを共有し、スタックとレジスタのみを個別に持っています。そのためスレッド間ではデータのやり取りが容易ですが、同時に同じデータに触れることで競合（バグ）を引き起こすこともあります。一方、プロセス間はメモリが隔離されているため、一つがクラッシュしても他のプロセスには影響が少ないという利点があります。

| | プロセス | スレッド |
|---|---|---|
| メモリ | 個別に持つ | プロセス内で共有（スタックのみ個別） |
| 作成・変更のコスト | 比較的大きい | 比較的小さい |
| データ共有 | 専用経路が必要 | 同じ変数を参照するだけ |
| 一つが破損した場合 | 他のプロセスは通常無事 | 同じプロセス内の全スレッドが危険にさらされる |

## CPU を分割する方法：スケジューリング

コア数よりもプロセスの数の方が圧倒的に多いため、OS が順番に CPU を割り当てます。誰に先に与えるかを決定するのがスケジューラです。OSTEP（教科書）では、性能指標として「ターンアラウンド時間」（タスクが到着してから完了するまでの時間）を最初に挙げ、公平性としばしば対立すると述べています。一方、「レスポンスタイム」（到着してから最初の実行されるまでの時間）は、ユーザーが感じる速度に近いものです。

- FIFO: 到着順に処理します。単純ですが、長いタスクが先頭にあると、後ろの短いタスクが長く待たされます。
- SJF（短いタスク優先）: 平均ターンアラウンド時間が改善します。ただし、タスクの長さを事前に知る必要があります。教科書ではスーパーマートの「10 個以下のレジ」に例えています。
- Round Robin: タイムスライス（quantum）だけ実行して次のタスクへ移ります。レスポンスタイムは良いですが、ターンアラウンド時間は悪化する可能性があります。

タイムスライスを短すぎると切り替えコストが大きくなります。教科書の例では、スライスが 10ms で切り替えコストが 1ms の場合、時間の約 10% を切り替えに費やします。スライスを長くするとそのコストは相殺されますが（amortization）、代わりにレスポンスタイムが遅くなります。

<details>
<summary>Round Robin の直接実行確認（動作確認済み）</summary>

タスク A(5)、B(3)、C(8) をスライス 2 で回し、それぞれ終了する時刻を計測しました。

```python
from collections import deque

def rr(jobs, q):
    d = deque(jobs); t = 0; done = {}
    while d:
        name, r = d.popleft()
        run = min(q, r); t += run; r -= run
        if r: d.append((name, r))
        else: done[name] = t
    return done

print(rr([("A", 5), ("B", 3), ("C", 8)], 2))
# {'B': 9, 'A': 12, 'C': 16}
```

三つのタスクがほぼ同時に進行しているように見えますが、最も短い B も 9 に終わります。単独で実行すれば 3 で終わっていたはずです。これが交互に実行する代償です。
</details>

## メモリを分割する方法：仮想メモリ

プロセスごとに「私はメモリの全てを独占して使っている」と信じ込ませるのが仮想メモリです。プロセスが参照するアドレスは仮想アドレスであり、実際の RAM の位置（物理アドレス）に変換するのは OS とハードウェアの仕事です。OSTEP は仮想メモリの目標を三つに整理しています。

- 透明性：プログラムはメモリの仮想化されていることに気づかなくてもよい。
- 効率性：時間と空間の両方で無駄が少ないこと（ハードウェアの助けが必要）。
- 保護：一つのプロセスが他のプロセスや OS のメモリに触れないこと。教科書ではこれをプロセス間の隔離と呼んでいます。

メモリを同じサイズのブロック（ページ）に分割し、仮想ページを物理フレームとペアリングする方式がペーシングです。ペアリングされた表がページテーブルです。すべてのページが RAM にある必要はなく、使われていないページはディスクへ下書き出し、必要な時に再度読み込みます。アクセスしたが RAM になければページフォルトが発生し、OS がディスクから取得します。この際 RAM が満杯であれば誰を追い出すかを決定する必要があり、これがページ置換ポリシーです。

<details>
<summary>FIFO vs LRU、そして奇妙な結果（動作確認済み）</summary>

参照順序 1,2,3,4,1,2,5,1,2,3,4,5 を用いてフレーム数を増減させながらフォルト回数を計測しました。

```python
def fifo(refs, f):
    mem = []; miss = 0
    for r in refs:
        if r not in mem:
            miss += 1
            if len(mem) == f: mem.pop(0)
            mem.append(r)
    return miss

def lru(refs, f):
    mem = []; miss = 0
    for r in refs:
        if r in mem: mem.remove(r)
        else:
            miss += 1
            if len(mem) == f: mem.pop(0)
        mem.append(r)
    return miss

refs = [1,2,3,4,1,2,5,1,2,3,4,5]
print(fifo(refs,3), fifo(refs,4), lru(refs,3), lru(refs,4))
# 9 10 10 8
```

FIFO はフレームを 3 から 4 に増やしたにもかかわらず、フォルトが 9 から 10 に逆に増加しました。これは Belady の異常現象と呼ばれます。LRU（最も久しく使われていないものを追い出す）は、3 から 10、4 から 8 と減少しました。この入力では LRU が 3 フレームの場合には FIFO よりも悪かったため、「LRU は常に良い」と覚えるべきではありません。
</details>

## 共有時に生じる問題：同期化

2 つのスレッドが同じ変数に `n += 1` を適用しようとする場合、これは内部で「読み取り」「加算」「書き込み」の 3 つの段階に分かれます。2 つのスレッドが同じ値を読み取り、それぞれ 1 を加えて書き込むと、結果として 1 つが消えてしまいます。これを競合状態 (race condition) と呼びます。これを防ぐための基本的な手段はロック (mutex) です。ロックを取得したスレッドだけがその区間（クリティカルセクション）に入り、他は待機します。この流れは、データベースの [トランザクションと隔離レベル](#/post/db-transaction) でも再び登場し、複数のタスクを分担して行う [非同期処理とメッセージキュー](#/post/be-async-queue) においても同様の課題が続きます。

ロックを使用すると新たな問題が発生します。スレッド 1 がロック a を取得して b を待機している間に、スレッド 2 が b を取得して a を待機すれば、両者とも永遠に動きません。これをデッドロック (deadlock) と呼びます。

<details>
<summary>ロックありの場合となしの場合、デッドロックの再現（実行確認済み）</summary>

```python
import threading, time
n = 0
def inc(k):
    global n
    for _ in range(k): n += 1

ts = [threading.Thread(target=inc, args=(100000,)) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print("no lock", n)   # 내 환경(Python 3.13)에서는 400000
```

ロックなしで実行しても、私の PC では 400,000 という値が表示されることはなく、値が破損する現象は観測できませんでした。したがって、このコードは競合状態を「示す」例としては不適切でした。これは CPython の実装事情による可能性があります。競合状態が存在しても必ず発生するわけではないことは確かなのですが、再現できないからといって安全なコードとは限りません。

デッドロックは、タイムアウトを設定した 2 つのスレッドで再現しました。

```python
a = threading.Lock(); b = threading.Lock()
def w1():
    with a:
        time.sleep(.1)
        if b.acquire(timeout=1): b.release()
        else: print("t1 stuck")
def w2():
    with b:
        time.sleep(.1)
        if a.acquire(timeout=1): a.release()
        else: print("t2 stuck")
```

実行すると "t2 stuck" という一行だけ出力されました。一方がタイムアウトによってロックを解放すれば、他方も解放され、両者が同時に stuck 状態になることはありません。タイムアウトなしで使用した場合、両方が停止します。この部分は、タイムアウトなしのバージョンを実行していませんでした。
</details>

## 概要図

これを一行でまとめると以下のようになります。プロセスは実行単位であり、スケジューラーが CPU 時間を分割し、仮想メモリがアドレス空間を割り当てます。同じものを共有する箇所では同期が必要です。コンテナ ([Docker とコンテナ](#/post/cloud-docker)) も結局は OS がプロセスをどのように分割して見せるかという問題に帰着すると理解していますが、この点はまだ正確に勉強していません。

## よくある誤解

- スレッドを増やせば必ず高速化する：コア数を超えると切り替えコストが増加し、ロック競合も発生します。
- 仮想メモリは RAM が増えること：本質は容量の拡張ではなく、プロセスごとに独立したアドレス空間を与えることです（隔離）。ディスクへの書き出しはその上に追加された機能です。
- ロックを使えば安全：ロックがデッドロックを引き起こす可能性があります。
- タイムスライスが短いほど良い：応答性は向上しますが、切り替えコストが増加します。
