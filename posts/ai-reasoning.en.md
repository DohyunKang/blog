Inference models are those that write internal monologue (thinking tokens) before generating an answer; even if this text is not displayed on the screen, it still counts toward output token usage and latency.

## In Simple Terms

Some people solve math problems mentally in one go, while others work through them step-by-step on paper. Standard LLMs are closer to the former, whereas inference models resemble the latter. Upon receiving a question, they write out "thinking" extensively before arriving at the final answer. This working-out portion constitutes thinking tokens (reasoning tokens, as termed by OpenAI).

Since LLMs [originally](#/post/ai-llm) generate text token-by-token, the amount of text written to reach an answer equates to the "computational capacity." Allowing for intermediate reasoning steps improves performance on difficult problems. Inference models essentially embed this capability directly within the model architecture.

## The Principle: Why Does Encouraging Thinking Improve Performance?

The foundational paper is Wei et al.'s 2022 "chain-of-thought" study. When examples including intermediate reasoning steps are provided, the model mimics them, leading to improved arithmetic, common sense, and symbolic reasoning performance in sufficiently large models. According to the abstract, providing just 8 examples enabled a 540B model to achieve state-of-the-art results on GSM8K (elementary school math word problems) at the time. In this context, humans inserted reasoning examples into the prompt.

Inference models, however, enable the model to generate these explanations autonomously rather than relying on the prompt. This article focuses solely on how they appear in APIs and how they are billed.

## Appearance in APIs

The commonalities noted in Anthropic and OpenAI documentation are as follows:

| | Claude (thinking) | OpenAI (reasoning) |
|---|---|---|
| Name | Thinking block, thinking tokens | reasoning tokens |
| Visibility | Summary may be returned or omitted | Not visible via API |
| Billing | Output tokens | Output tokens |
| Window Allocation | Included (`max_tokens`) | Included |
| Depth Control | `effort` (low~max) | `reasoning.effort` (none~max, model-specific) |

A notable point in Anthropic's documentation regarding billing is that while the screen displays a summarized version of the thinking, charges are applied based on the total thinking tokens actually generated by the model, not just the summary. As stated in the documentation, the number of billed output tokens does not match the number of tokens visible in the response. Even if you set `display` to `omitted` and receive nothing, the charge remains identical. The actual usage can be viewed via the response's `usage.output_tokens_details.thinking_tokens`.

OpenAI's documentation is similar. Reasoning tokens are not visible via the API but consume context window space and are billed as output tokens. They recommend reserving approximately 25,000 tokens initially for both reasoning and output. Due to this number, if the window fills up completely, the response may end with `incomplete` without generating any answer.

From the perspective of a [context window](#/post/ai-context-window), thinking tokens represent input/output that occupy space despite not being text written by the user.

## Cost & Latency: Why It Matters

Since thinking tokens are essentially output tokens, both increase together.

- **Cost**: Output tokens typically have a higher unit price than input tokens (unit prices vary by model, so specific numbers are omitted). While a question might be a single line, if the thinking process spans thousands of tokens, the cost is dominated by the thinking portion. Unit costs per feature are covered separately in [AI Service Cost](#/post/app-cost).
- **Time**: Since the model writes out its thinking before the answer appears, perceived latency increases. Even when receiving a stream, the content only arrives after the thinking phase concludes.

Therefore, controls exist to adjust depth.

## Adjusting Depth: From Budget to Effort

The change illustrated in Anthropic's documentation is interesting. The previous method (extended thinking) allowed direct setting of a thinking budget via `budget_tokens`. This required a minimum of 1,024 tokens and had to be less than `max_tokens`; it was a target rather than a strict upper limit. However, this method is now deprecated, and models following Claude 4.7 and later will reject this approach entirely (returning error 400).

The alternative is adaptive thinking. The model autonomously decides whether to think and how much for each request, while the user simply sets the `effort` preference (low, medium, high, xhigh, max). Based on features read from the documentation, the characteristics are as follows.

- Easy questions can be answered immediately without thinking. Therefore, you should not write code assuming "there is a thinking block in every turn."
- The cost cap is handled by `max_tokens`, which serves as the hard limit for the total count of thoughts and answers combined. If thoughts become too long and hit this limit first, the answer may be cut off; thus, values based on answers without thinking can be too small.
- To reduce thinking, it is recommended by the documentation to lower `effort` rather than prompting "think less." Some models are noted to not respond well to such prompts.
- Changing `effort` mid-conversation breaks prompt caching. It is better to keep the value fixed within a single conversation, as this relates to [prompt caching](#/post/ai-prompt-caching).

The default `effort` varies by model (the documentation states some models use high while others use medium), so you should consult the model-specific table in the documentation when using them.

## When to Use It

OpenAI's documentation recommends reasoning models for complex problem-solving, coding, scientific reasoning, and multi-step agent tasks. In [agent loops](#/post/ai-agent-loop), it is advantageous to think about the next action each time you receive tool results, and Anthropic's documentation also describes interleaved actions where thinking occurs between tool calls. Conversely, tasks with immediate answers like text refinement, classification, or simple extraction do not require thinking. This criterion was summarized by me based on the above content, rather than being a direct comparison from the documentation.

## Common Misconceptions

- Reasoning models have no hallucinations: There is no known evidence that thinking eliminates [hallucinations](#/post/ai-hallucination).
- Visible summaries represent all actual thinking: These are summaries. Billing is based on the total output, not just the summary.
- Thinking longer is always better: The documentation states that revenue diminishes as budget increases (Anthropic; varies by task). Latency and costs definitely increase.
- Thinking tokens are a free add-on feature: They are billed as output tokens.
- [Sampling](#/post/ai-sampling) settings (e.g., temperature) are fully applied: Model-specific limits may apply, so consult the documentation.

<details>
<summary>Detailed explanation: Anthropic billing structure</summary>

According to the documentation, three components are charged when using thinking:

1. Tokens used during thinking (charged as output tokens).
2. Context remaining from previous turn's thinking blocks (charged as input tokens). Depending on the model, either all turns or only the last turn may be retained in context.
3. General answer output tokens.

It is stated that costs for generating thought summaries are not separately charged. `output_tokens` represents the total sum under the billing standard, while `thinking_tokens` is a read-only detail within it. In the example response, `thinking_tokens` was 312 out of 348 `output_tokens`. These are just example numbers from the documentation and not averages.
