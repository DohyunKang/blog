运营服务时，经常会听到诸如负载均衡器、CDN、缓存、限流、自动扩缩容等术语。这些组件都部署在用户请求到达数据库的路径上，因此我先按这条路径逐一介绍。若想深入了解，可点击下方链接查看。

## 一览全貌关系图

```
사용자 → DNS → CDN(엣지 캐시) → 로드밸런서 → 앱 서버 → 캐시 → DB
                                   ↑               ↑
                          레이트 리밋(문 앞에서 제한)   오토스케일링(서버 수 조절)
앱 서버 → (LLM API를 부르는 서비스라면) 큐·캐시·타임아웃을 한 겹 더
```

## 1. 首先查看完整路径

**单个请求的流转路径**：在地址栏输入网址并按下回车后，请求会经过从 DNS 到数据库等多个环节；其中较慢的环节通常只有一两处，因此需优先排查时间损耗点。
[详情 → 单个请求的流转路径](#/post/infra-request-journey)

## 2. 前端接收与分流

**CDN 与缓存层级**：将源服务器的响应副本存储于靠近用户的节点，即缓存。关键在于通过 `Cache-Control` 头决定应信任该副本多久，这才是实际需关注的重点。
[详情 → CDN 与缓存层级](#/post/infra-cdn-cache)

**负载均衡器**：在多台服务器前分发请求，并防止将流量导向已宕机的服务器。相较于分发策略，快速剔除故障服务器的能力显得更为重要。
[详情 → 负载均衡器](#/post/infra-load-balancer)

## 3. 应对高并发场景

**限流与流量控制**：用于在入口处拒绝超出服务器承载能力的请求。根据所采用的算法不同，系统可能允许突发流量通过，也可能在阈值处直接拦截。
[详情 → 限流与流量控制](#/post/infra-rate-limit)

**自动扩缩容与扩展**：扩展服务器的方式分为垂直扩展和水平扩展两种；若要实现自动扩容，则服务器不应持有状态信息。
[详情 → 自动扩缩容与扩展](#/post/infra-autoscaling)

## 4. 若是 AI 服务

**AI 服务架构**：调用 LLM API 的服务通常响应缓慢、偶尔失败，且每次调用都会产生费用，因此需在请求路径中间叠加队列、缓存和超时机制等层。
[详情 → AI 服务架构](#/post/infra-ai-serving)
