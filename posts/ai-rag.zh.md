RAG 是一种机制：当收到问题时，先检索相关文档并将其附加到提示词（prompt）中，然后让模型基于这些内容进行回答。这种方式可以在不重新训练模型的情况下，使模型能够回答其原本不知道的内容。

## 为什么需要它

[LLM](#/post/ai-llm) 仅拥有截至学习结束时的知识。例如，昨天更新的内部规定或公司文档，它自然无法知晓。如果直接说“不知道”固然好，但模型有时会一本正经地胡编乱造（[幻觉 → Hallucination](#/post/ai-hallucination)）。

然而，也不能将所有文档都塞进提示词中。[上下文窗口](#/post/ai-context-window) 存在容量限制；随着内容变长，成本也会增加，且模型往往忽略中间部分的内容。Lost in the Middle 论文指出，相关信息若位于输入的首尾，模型表现较好；若处于中间，性能则大幅下降。支持长上下文的模型也表现出类似趋势。

因此，RAG 的核心思想是：只选取必要部分进行检索并加入提示词。该术语源自 2020 年 Lewis 等人发表的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》。论文将存储在模型权重中的知识称为“参数化记忆”，而将外部知识库（如维基百科向量索引）称为“非参数化记忆”，并提出了结合两者的方案。用通俗的话说，就是“背诵的知识 + 可随时查阅的书籍”。

## 流程

整体流程如下：

```
[준비 단계, 미리 한 번]
문서 → 청킹(조각내기) → 임베딩(숫자 벡터로) → 벡터 DB에 저장

[질문이 올 때마다]
질문 → 임베딩 → 비슷한 청크 검색(top-k) → 프롬프트에 붙임 → 모델이 답변
```

| 步骤 | 操作内容 | 注意事项 |
|---|---|---|
| 切分 (Chunking) | 将文档切割成合适大小的片段 | 这些片段将成为检索的基本单位 |
| 向量化 (Embedding) | 将每个片段转换为包含语义信息的向量 | [详情 → 向量化](#/post/ai-embedding) |
| 检索 (Retrieval) | 查找与问题向量最接近的片段 | 通常只取前 k 个结果 |
| 提示词注入 (Prompt Injection) | 以“仅参考以下资料作答”的方式将片段附加到提示词中 | [详情 → 提示词](#/post/ai-prompt) |
| 回答 (Answering) | 模型阅读资料并生成回答 | 若同时提供出处，便于验证答案来源 |

提示词注入部分大致如下所示：

```
다음 자료만 근거로 질문에 답하라. 자료에 없으면 모른다고 답하라.

[자료 1] ...청크...
[자료 2] ...청크...

질문: ...
```

“如果资料中没有相关信息，请明确说明不知道”这一行至关重要。若无此约束，模型可能会用自身知识填补资料中的空白。

## 切分大小

如何切分文档直接影响检索质量。Anthropic 在 Contextual Retrieval 文章中提到，切分大小、边界处理及重叠（overlap）都会影响检索性能：

- 切分过大：单个片段可能混杂多个主题，导致向量化模糊，且占用大量提示词空间；
- 切分过小：句子因缺乏前后语境而被割裂，语义丢失；
- 设置重叠：相邻片段可承接边界处被截断的内容，但会增加冗余。

目前尚未找到“最佳 token 数”的确切数值。文章也建议根据具体使用场景自行实验。不同文档类型（如规定、对话、代码）的切分标准各异；虽然常听说按标题或段落切分优于按字符数切分，但我并未亲自验证过这一点。

## 重排序与混合检索

初次检索得到的前 k 个结果未必都是最优的，因此常结合以下两种技术：

**混合检索（Hybrid Search）** 同时使用基于语义的向量化检索和基于词项匹配的 BM25。向量化擅长捕捉语义相似性，但可能遗漏如"TS-999"这类错误代码或专有术语的精确匹配；BM25 则相反，侧重字面匹配。两者结果可通过“秩融合（rank fusion）”合并，并去除重复项。

**重排序（Reranking）** 是在初步检索获取较多候选片段后，由重排序模型综合问题与片段内容重新打分，仅保留高分片段的过程。初次检索速度快但较粗略，而重排序较慢但更精细。由于会引入额外延迟，需权衡重排序数量以平衡成本与速度。

Anthropic 的文章提供了相关数据（基于“正确答案不在前 20 个片段中”的失败率）：

| 方法 | 失败率 | 相比基准 |
|---|---|---|
| 基础向量化检索 | 5.7% | 基准 |
| 在片段前后添加上下文句子后再进行向量化检索 | 3.7% | 降低 35% |
| 上述方法 + 上下文 BM25 | 2.9% | 降低 49% |
| 上述方法 + 重排序 | 1.9% | 降低 67% |

这些数据来自该文章自身的实验条件（数据集及重排序模型为 Cohere），不能保证在我的数据上也能实现同等幅度的提升，但整体方向值得参考。

其中提到的“添加上下文句子”策略，旨在防止类似“销售额较上一季度增长 3%"这类因缺失公司名称和时间范围而导致语义模糊的问题，通过在片段前附加简短说明语句来规避此类风险。

## 失败案例

RAG 出错的地方通常不在模型本身，而在于前端流程（检索与预处理环节）。

- 检索无法找到所需的文本块（Chunk）。这是最常见且导致上述失败率的主要原因。
- 文本块被截断，导致上下文缺失。例如前文提到的公司名称案例。
- 虽然找到了相关内容，但被淹没在中间，模型未能利用。这指的是前文所述的"Lost in the Middle"现象。
- 当问题需要结合多个文档回答时（如比较、聚合），仅靠顶部的几个文本块是不够的。
- 文档已过时或内容相互矛盾。检索虽然成功，但资料本身是错误的。这种情况无法通过 RAG 解决。
- 即使提供了资料，模型仍可能依赖自身知识作答，或者错误地解读资料。

因此，当答案出错时，不要先归咎于“模型”，而应首先检查哪些文本块进入了提示词（Prompt）。

## 微调与它有何不同

两者都被归类为“让模型了解我们内容的方法”，但具体操作不同。

| | RAG | 微调 (Fine-tuning) |
|---|---|---|
| **改变的对象** | 模型看到的输入 | 模型的权重 |
| **适用场景** | 频繁变化的知识、内部文档、需要引用来源 | 语气风格、输出格式、一致的行为模式 |
| **知识更新** | 修改文档即可 | 需要重新训练 |
| **来源标注** | 可以直接展示原始文本块 | 较困难 |

检索并阅读的实践文章大多总结为：“如果是知识问题用 RAG，如果是行为问题用微调”，也有观点认为两者结合使用。不过这些内容主要来自厂商或个人博客，更多是个人见解；我尚未找到针对同一任务比较两者的受控实验。

## 常见误区

- **使用 RAG 就能消除幻觉**：只能减少，无法根除。如果检索出错或模型忽略资料，依然会胡编乱造。
- **微调后模型就会记住文档内容**：实践文章普遍认为，微调在“稳定记忆事实”方面的作用有限。我也尚未亲自尝试过。
- **只要有向量数据库就是 RAG**：数据库只是存储设备，质量取决于分块（Chunking）、检索方式以及重排序等步骤。
- **上下文窗口变大了就不需要 RAG 了**：如果知识库较小（以 Anthropic 文章标准为例，约 20 万 token，即不到 500 页），整篇放入确实最简单；但若超过这个规模，RAG 仍然是必要的。

<details>
<summary>详细解析：语义搜索是如何工作的</summary>

嵌入（Embedding）是将文本转换为数百至数千维的数字向量列表。模型经过训练，使得语义相似的文本在向量空间中彼此靠近。提问时，同样使用模型将问题转化为向量，然后在存储的文本块向量中查找最接近的项（如基于余弦相似度）。当文本块数量较多时，不会逐一比较，而是使用近似最近邻搜索（Approximate Nearest Neighbor）索引。

BM25 是一种评分函数，评估词语出现的频率和稀有度。为了防止常见词垄断高分，会对频率设置上限，并同时对文档长度进行校正。虽然不理解语义，但只要字符相同就能找到，这一点与嵌入方法形成互补关系。
