認証は「誰か」を確認することであり、認可は「その人がそれをしてもよいか」を決定することです。セッションと JWT はログイン状態を維持する方法であり、OAuth は他者のサービスに権限を借りる手順であり、RBAC は権限を整理する方式でした。

## 認証と認可の違いから始める

混乱してしまう理由は、両者が常にセットで動いているからです。順序はいつも同じです。まず認証によってユーザーが誰かを確認し、その人の情報に基づいて認可を判断します。

| | 認証 (Authentication) | 認可 (Authorization) |
|---|---|---|
| 質問 | 誰ですか？ | 何をしてもよいですか？ |
| 例 | パスワード確認、ソーシャルログイン | 管理者のみが会員削除可能 |
| 失敗時の HTTP ステータス | 401 | 403 |
| タイミング | ログイン時および各リクエストごとに身元確認 | リクエストごと |

ログインは一度だけですが、HTTP は各リクエストごとに別々に届きます。サーバーは前のリクエストを記憶しません ([詳細 → リクエストの処理フロー](#/post/be-request-flow))。そのため、「このリクエストを送った人はさっきログインしたその人である」ことを毎回証明する方法が必要であり、その方法はセッションかトークンです。

## セッション方式

サーバーがログインに成功すると、ランダムな ID を作り、サーバー側の保存先に「この ID は 42 番ユーザー」と書いておきます。そしてその ID のみをクッキーとしてブラウザに渡します。以降のリクエストごとにブラウザがクッキーを送ると、サーバーは保存先から ID を探し、ユーザーを知ります。

```
로그인 → 서버: 세션 ID 생성, 저장소에 {ID: 사용자 42} 기록
      ← Set-Cookie: sid=랜덤값
요청   → Cookie: sid=랜덤값 → 서버가 저장소 조회 → 42번으로 처리
로그아웃 → 저장소에서 ID 삭제 (바로 무효)
```

OWASP セッション管理ドキュメントの基準で整理すると以下のようになります。

- ユーザー情報と権限はサーバーに置き、ID には含めません。ID は意味のない乱数です。
- クッキーには `HttpOnly`(JavaScript が読めない)、`Secure`(HTTPS のみ送信)、`SameSite`(Strict または Lax) を設定します。
- ログイン直後はセッション ID を新規発行し、古い ID を破棄します。ログイン前に埋め込まれた ID を使い続ける攻撃 (セッション固定) を防ぐためです。
- 不活性時間制限と絶対有効期限の両方をサーバー側で強制します。

利点はサーバーが自由に切断できることです。ログアウト也罢、強制ログアウト也罢、保存先から消せば即座に完了します。欠点はサーバーが状態を保持しなければならないことです。サーバーが複数ある場合、保存所を共有する必要があり、通常 Redis などを前に置きます ([詳細 → キャッシュと Redis](#/post/db-cache-redis))。

## トークン方式 (JWT)

JWT はサーバーが保存せず、ユーザー情報をトークンの中に埋め込んで署名してクライアントに渡す方式です。形式は点で繋がった三つの塊です。

```
헤더 . 페이로드 . 서명
(알고리즘)  (클레임: 누구, 만료 시각 등)  (위 둘에 대한 HMAC 또는 전자서명)
```

RFC 7519 に登録された主要なクレームは `iss`(発行者)、`sub`(主体)、`aud`(受信者)、`exp`(有効期限)、`nbf`(この時刻以前は無効)、`iat`(発行時刻)、`jti`(トークン固有 ID) です。すべてオプション項目です。

サーバーはトークンが来ると署名を再計算して一致するか、有効期限切れになっていないかを確認すればよいだけです。保存所への照会がありません。そのためサーバーが複数あっても、サービスが複数あっても同じキーを共有すれば検証可能です。

ただし注意すべき点はいくつかあります。

- 署名は偽造を防ぐのみで内容を隠しません。ペイロードは base64url でエンコードされているだけなので誰でも読めます。RFC も署名付きトークンの内容は見られると記述しています。パスワードなどは含めません。
- 一度発行すると有効期限が切れる前にサーバー側でキャンセルするのが困難です。保存所がないため「このトークンを無効」を記憶する場所がないからです。そのためアクセストークンは寿命を短く (分単位) とり、更新用のリフレッシュトークンを別に置きます。キャンセルするには結局ブラックリストのような保存所が必要になります。
- 保存位置が問題です。OWASP は `localStorage` や `sessionStorage` にトークンを置かないと勧めています。XSS が一つでも突破すれば読み取られてしまうからです。クッキー (HttpOnly) に置く方がよいということです。クッキーに置くと CSRF を別途考慮する必要があります。

セッションと JWT を一列ずつ比較すると以下のようになります。

| | セッション | JWT |
|---|---|---|
| 状態保存 | サーバー (保存所) | トークン内 (クライアント) |
| 即時無効化 | 容易 | 困難 |
| サーバー拡張 | 保存所共有が必要 | キーのみ共有 |
| リクエストサイズ | 小さい (ID のみ) | 大きい (情報を含む) |
| 向いている場所 | 一つのサービスの Web アプリ | 複数のサービス・モバイル・API |

どちらが優れているというわけではなく、即時に切断する必要がある場合はセッション側、サービスが分割されている場合は JWT 側の方が適しています。セッションの代わりに JWT を使うと自動的により安全になると誤解されがちですが、上記のようにキャンセルと保存位置の問題が新たに生じます。

<details>
<summary>実際に回したコード: セッション ID, JWT 署名・検証, RBAC (Python 標準ライブラリのみ)</summary>

```python
import base64, hashlib, hmac, json, secrets, time

def b64(b): return base64.urlsafe_b64encode(b).rstrip(b"=").decode()
def unb64(s): return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

SECRET = b"dev-only-secret"   # 실제로는 환경변수·시크릿 저장소에서

def sign(payload, ttl=900):
    head = {"alg": "HS256", "typ": "JWT"}
    payload = {**payload, "exp": int(time.time()) + ttl}
    msg = b64(json.dumps(head).encode()) + "." + b64(json.dumps(payload).encode())
    sig = hmac.new(SECRET, msg.encode(), hashlib.sha256).digest()
    return msg + "." + b64(sig)

def verify(token):
    h, p, s = token.split(".")
    if json.loads(unb64(h)).get("alg") != "HS256":   # 알고리즘을 서버가 고정
        raise ValueError("alg")
    good = hmac.new(SECRET, f"{h}.{p}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(good, unb64(s)):
        raise ValueError("bad signature")
    data = json.loads(unb64(p))
    if data["exp"] < time.time():
        raise ValueError("expired")
    return data

sessions = {}
def login(uid):
    sid = secrets.token_urlsafe(32)   # CSPRNG 난수
    sessions[sid] = {"uid": uid}
    return sid

ROLE_PERMS = {
    "viewer": {"post:read"},
    "editor": {"post:read", "post:write"},
    "admin":  {"post:read", "post:write", "user:delete"},
}
def can(roles, perm):
    return any(perm in ROLE_PERMS.get(r, ()) for r in roles)
```

実行結果 (この環境で直接確認):

```
정상 토큰 검증      → {'sub': '42', 'roles': ['editor'], 'exp': ...}
roles를 admin으로 바꿔 재조립 → tampered: bad signature
만료된 토큰         → old: expired
세션 ID 길이 43, 삭제 후 조회 → False
can(editor, post:write)=True / can(editor, user:delete)=False / can(admin, user:delete)=True
```

検証時にヘッダーの `alg` をそのまま信用してはいけません。サーバーが使用するアルゴリズムを固定して比較する必要があるためです（過去に `alg: none` で署名をスキップさせる攻撃があったとされています。この点は RFC では、単に unsecured JWT が存在することのみを確認しました）。

</details>

## OAuth はログインではなく権限委譲

OAuth を「Google でログイン」といったものと混同しやすいですが、RFC 6749 が扱っているのは委譲です。ユーザー（リソース所有者）が特定のアプリ（クライアント）に対して「私のリソース（リソースサーバーにあるもの）をこの範囲で使ってよい」と承認し、その承認を認証サーバー（authorization server）がトークンに変換する構造です。役割は 4 つあります。

| 役割 | 行うこと |
|---|---|
| リソース所有者 | アクセスを許可できる人（ユーザー） |
| クライアント | ユーザーの代わりにリソースにアクセスしようとするアプリ |
| 認証サーバー | ユーザーを認証し、同意を得てトークンを発行 |
| リソースサーバー | リソースを持つサーバー。アクセストークンを提示してリクエストを受け付ける |

最も一般的な認証コード（authorization code）方式の流れは 5 つの段階です。

1. クライアントがユーザーを認証サーバーに誘導します。クライアント ID、要求範囲（scope）、state 値、戻り先アドレス（redirect URI）を同時に送ります。
2. 認証サーバーがユーザーを認証し、同意の有無を確認します。
3. 同意された場合、有効期限の短い認証コードを redirect URI に返却します。
4. クライアントはそのコードをトークンエンドポイントに送信してトークンを交換します。この際、クライアント自身も認証を行います。
5. アクセストークン（およびオプションのリフレッシュトークン）を受信します。

コードとトークンを分ける理由は、ブラウザのアドレスバーを経由するのは一時的なコードだけであり、本物のトークンはサーバー間でやり取りさせるように設計したためです。リフレッシュトークンは認証サーバーにのみ送信し、リソースサーバーには送信しません。

「Google でログイン」は実際には OAuth の上に構築された OpenID Connect によってユーザー情報も取得できるものですが、OIDC については今回は文書を開示していません。

## 権限モデル：RBAC

認証のルールをどのように記述するかが権限モデルです。最も一般的なものは RBAC（ロールベースアクセス制御）です。ユーザーに個々の権限を付与するのではなく、役割（viewer, editor, admin）を与え、役割が権限の束を持つようにします。上記コードの `ROLE_PERMS` がすべてです。

```
사용자 ──(가진다)──▶ 역할 ──(포함한다)──▶ 권한
 42번                 editor            post:read, post:write
```

人が変わっても役割を変えるだけで済み、「誰が何をできるか」はロールテーブル一つで確認できます。ただし例外が増えるとロールが爆発します。「自分が書いた記事のみ編集可能」といったことはロールでは表現できず、リソースの所有者が誰かといった条件を別途検査する必要があります。そのような条件（部署、時間、所有者など）を属性として一般化したものを ABAC と呼びます。

認証チェックは画面でボタンを非表示にするだけで終わるものではありません。リクエストがサーバーに到達した際、サーバー側が毎回チェックを行う必要があります。ボタンを非表示にしても、直接 API を呼び出せば済んでしまうためです。これを怠ると一般的な脆弱点となります（[詳細 → Web 脆弱性と OWASP](#/post/sec-owasp)）。

## よくある誤解

- パスワードは暗号化して保存する：復号化する必要がないためハッシュ（遅いハッシュ）で保存します（[詳細 → 暗号化・ハッシュ・認証の基礎](#/post/sec-authn-crypto)）。
- JWT は暗号化されている：署名のみされた JWT は誰でも読むことができます。
- ログインしているから権限もある：認証と認証は別物であり、401 と 403 も異なります。
- トークンがあれば CORS や CSRF を気にする必要はない：クッキーに含めて送信すると CSRF が再び問題となり、SameSite は補助的な手段です。
- ログイン試行はそのまま受け付ける：ブルートフォース攻撃を防ぐため、回数制限が必要です（[詳細 → レートリミットとトラフィック制御](#/post/infra-rate-limit)）。署名キーなどの機密値の保管については [詳細 → 環境変数とシークレット管理](#/post/cloud-secrets)。
