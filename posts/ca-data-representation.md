컴퓨터 안에는 0과 1밖에 없다. 숫자도 글자도 사진도 전부 비트 묶음이고, 같은 비트 묶음도 "정수로 읽자", "소수로 읽자", "글자로 읽자"는 약속에 따라 다른 값이 된다. 이 글은 그 약속 중 정수(2의 보수), 실수(부동소수점), 문자(유니코드와 UTF-8) 세 가지를 파이썬으로 확인하면서 본다. 비트 묶음을 CPU가 어떻게 꺼내 계산하는지는 [CPU와 명령어](#/post/ca-cpu)에서 이어진다.

## 비트 묶음과 약속

8비트는 256가지 패턴을 만든다. 이 패턴에 의미를 붙이는 방식이 데이터 표현이다. 같은 `11111011`이 부호 없는 정수로는 251이고, 부호 있는 정수(2의 보수)로는 -5다. 비트는 그대로고 해석만 바뀐다.

| 읽는 약속 | `11111011`의 값 |
|---|---|
| 부호 없는 정수 | 251 |
| 2의 보수 정수 | -5 |
| 문자 코드(Latin-1 등) | 코드 표에 따라 다른 글자 |

그래서 파일을 열었는데 글자가 깨지는 일은 비트가 망가진 게 아니라 읽는 약속이 어긋난 경우가 많다. 뒤의 문자 인코딩에서 직접 만들어 본다.

## 정수: 2의 보수

음수를 표현하는 방법 중 지금 거의 모든 CPU가 쓰는 건 2의 보수다. n비트에서 음수 -x는 2의 n제곱에서 x를 뺀 값의 비트 패턴으로 저장한다. 8비트에서 -5는 256 - 5 = 251이고, 이진수로 `11111011`이다. 파이썬에서 `n & 0xFF`로 확인하면 이렇게 나온다.

```python
for n in (5, -5, -1, 127):
    print(n, format(n & 0xFF, '08b'))
# 5 00000101
# -5 11111011
# -1 11111111
# 127 01111111
print(int('11111011', 2) - 256)   # -5
```

최상위 비트가 1이면 음수라는 규칙이 생기지만, 그게 단순한 부호 비트는 아니다. 최상위 비트의 자리값이 -128이라고 생각하면 된다. `11111011`은 -128 + 64 + 32 + 16 + 8 + 2 + 1 = -5다.

2의 보수를 쓰는 이유는 덧셈 회로 하나로 부호 있는 수와 없는 수를 같이 계산할 수 있어서다. 뺄셈은 반대 부호를 더하는 것으로 바뀐다. 0의 표현도 하나(`00000000`)뿐이다. n비트로 나타내는 범위는 -2^(n-1)부터 2^(n-1)-1까지라서 음수 쪽이 하나 더 많다. 8비트는 -128~127이다.

범위를 넘으면 오버플로가 난다. 8비트에서 127에 1을 더하면 `10000000`이 되고, 이건 -128이다. 파이썬 정수는 길이 제한이 없어서 직접 마스크를 씌워야 흉내 낼 수 있다.

```python
x = (127 + 1) & 0xFF
print(x, x - 256 if x > 127 else x)   # 128 -128
```

C나 Java 같은 언어의 고정 길이 정수에서 일어나는 오버플로가 이 모양이다. 값이 한 바퀴 돌아 반대쪽 끝으로 간다.

<details>
<summary>바이트 순서(엔디언)</summary>

정수가 여러 바이트일 때 어느 바이트를 먼저 놓느냐도 약속이다. 258은 `0x00000102`인데, 빅 엔디언은 높은 자리 바이트부터, 리틀 엔디언은 낮은 자리 바이트부터 메모리에 놓는다.

```python
print((258).to_bytes(4, 'big').hex())      # 00000102
print((258).to_bytes(4, 'little').hex())   # 02010000
```

파일이나 네트워크로 숫자를 주고받을 때 양쪽이 같은 순서로 읽기로 정해 둬야 한다. 네트워크에서 바이트를 보내는 규칙은 [네트워크 기초](#/post/cs-network)와 이어서 볼 수 있다.
</details>

## 실수: 부동소수점

소수는 정수보다 어렵다. 한정된 비트로 아주 큰 수와 아주 작은 수를 다 나타내야 해서, 과학 표기법처럼 부호·지수·가수로 나눠 담는다. 파이썬의 `float`은 IEEE 754 binary64(배정밀도)이고, 64비트를 이렇게 쓴다.

| 부호 | 지수 | 가수 |
|---|---|---|
| 1비트 | 11비트 | 52비트 |

값은 `(-1)^부호 × 1.가수 × 2^(지수-1023)` 꼴이다. 1.0과 -2.5의 비트를 뽑아 보면 맞아떨어진다.

```python
import struct
def bits(f):
    b = struct.unpack('>Q', struct.pack('>d', f))[0]
    s = format(b, '064b')
    return s[0], s[1:12], s[12:]

print(bits(1.0))
# ('0', '01111111111', '000...0')           지수 1023 → 2^0
print(bits(-2.5))
# ('1', '10000000000', '0100...0')          지수 1024 → 2^1, 1.25 × 2 = 2.5
```

1.0의 지수 필드가 `01111111111`(1023)이니 편향(bias)이 1023이라는 게 보인다. -2.5는 부호 1, 지수 1024(2^1), 가수 `01`로 1.25가 되어 1.25 × 2의 부호 반전이다.

### 0.1이 정확하지 않은 이유

10진수 0.1은 2진수로 쓰면 0.000110011001100…처럼 끝없이 반복된다. 가수가 52비트(암묵적 1까지 53비트)뿐이라 어디선가 잘라 가장 가까운 값을 저장한다. 파이썬 공식 튜토리얼 설명으로는 0.1 대신 저장되는 값이 3602879701896397 / 2^55이고, 1/10보다 아주 조금 크다. 파이썬이 `0.1`로 보여 주는 건 왕복이 되는 가장 짧은 10진 표현이라서다.

```python
from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625
print(0.1 + 0.2)           # 0.30000000000000004
print(0.1 + 0.2 == 0.3)    # False
```

버그가 아니라 표현 방식의 결과다. 같은 계산을 어느 언어에서 해도 binary64를 쓰면 같은 결과가 나온다. 비교할 때는 `==` 대신 허용 오차를 둔다.

```python
import math
print(math.isclose(0.1 + 0.2, 0.3))   # True
```

정확한 10진 계산이 꼭 필요한 곳(돈 계산 등)은 `Decimal`을 문자열로 만들어 쓰는 방법이 있다. 공식 문서도 회계 같은 용도에 `decimal` 모듈을 권한다.

### 큰 수 옆에서 사라지는 작은 수

가수 길이가 정해져 있으니 수가 클수록 표현 가능한 값 사이 간격이 벌어진다. 2^53(9007199254740992)부터는 정수 1도 구분하지 못한다.

```python
print(2**53)                              # 9007199254740992
print(float(2**53) + 1 == float(2**53))   # True
print(1e16 + 1 == 1e16)                   # True
```

그래서 큰 수와 작은 수를 더하면 작은 쪽이 사라진다. 많은 수를 더하는 합계 계산에서 순서가 결과를 바꾸는 이유가 이거다.

<details>
<summary>특수한 값들</summary>

지수 필드가 전부 1이면 무한대나 NaN을 나타낸다. 범위를 넘으면 `inf`가 되고, `inf - inf` 같은 계산은 `nan`이 된다. NaN은 자기 자신과도 같지 않다.

```python
import sys
print(sys.float_info.max * 2)         # inf
print(float('inf') - float('inf'))    # nan
nan = float('nan'); print(nan == nan) # False
print(5e-324, 5e-324 / 2)             # 5e-324 0.0
print(sys.float_info.epsilon)         # 2.220446049250313e-16
```

`5e-324`는 표현 가능한 가장 작은 양수이고, 그 절반은 0으로 떨어진다. `epsilon`은 1.0과 그 다음으로 큰 float의 차이다.
</details>

## 문자: 코드 포인트와 인코딩

글자는 두 단계로 나눠 생각해야 헷갈리지 않는다. 먼저 유니코드가 글자마다 번호(코드 포인트)를 준다. 그다음 인코딩이 그 번호를 바이트로 바꾸는 규칙을 정한다. 번호와 바이트 열은 다른 것이다.

ASCII는 영어 글자와 기호 128개를 7비트에 넣은 표였다. 한글처럼 글자 수가 많은 문자는 한 바이트로 안 들어가서 EUC-KR 같은 나라별 인코딩이 따로 생겼고, 이걸 하나의 번호 체계로 묶은 게 유니코드다. 지금 웹과 파이썬 3의 기본 인코딩은 UTF-8이다.

### UTF-8은 길이가 달라진다

UTF-8은 코드 포인트 크기에 따라 1~4바이트를 쓴다. RFC 3629에 정의된 틀은 이렇다.

| 코드 포인트 범위 | 바이트 수 | 비트 패턴 |
|---|---|---|
| U+0000 ~ U+007F | 1 | `0xxxxxxx` |
| U+0080 ~ U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 ~ U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 ~ U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

첫 바이트 앞쪽의 1 개수가 전체 길이를 알려 주고, 뒤따르는 바이트는 항상 `10`으로 시작한다. ASCII 범위는 한 바이트 그대로라서 영어 텍스트는 ASCII와 UTF-8이 같다.

'가'(U+AC00)로 확인해 본다. 코드 포인트 `1010110000000000`을 3바이트 틀에 채우면 `1110 1010`, `10 110000`, `10 000000`이다.

```python
ch = '가'
print(hex(ord(ch)))                                  # 0xac00
print(format(ord(ch), '016b'))                       # 1010110000000000
print([format(b, '08b') for b in ch.encode()])
# ['11101010', '10110000', '10000000']
print(ch.encode('utf-8').hex())                      # eab080
```

`eab080`은 위 이진수 세 바이트(`ea` `b0` `80`)와 같다. 'A'는 1바이트, '가'는 3바이트, 이모지(U+1F600)는 4바이트다.

```python
for ch in ('A', '가', '\U0001F600'):
    print(hex(ord(ch)), ch.encode('utf-8').hex(), len(ch.encode('utf-8')))
# 0x41 41 1
# 0xac00 eab080 3
# 0x1f600 f09f9880 4
```

### 글자 수와 바이트 수는 다르다

```python
s = '한글'
print(len(s))                       # 2   글자(코드 포인트) 수
print(len(s.encode('utf-8')))       # 6   UTF-8 바이트 수
print(len(s.encode('euc-kr')))      # 4   EUC-KR 바이트 수
```

데이터베이스 컬럼 길이나 API 본문 크기 제한이 바이트 기준인지 글자 기준인지 확인해야 하는 이유다. UTF-16은 '가'를 2바이트, 이모지를 4바이트(서로게이트 쌍)로 저장해서 같은 문자열도 인코딩마다 크기가 다르다.

### 글자가 깨지는 순간

읽는 약속이 어긋나면 깨진다. 한글 UTF-8 바이트를 Latin-1로 읽거나, EUC-KR 바이트를 UTF-8로 읽어 본다.

```python
s = '한글'
print(s.encode('utf-8').decode('latin-1').encode('unicode_escape'))
# b'\\xed\\x95\\x9c\\xea\\xb8\\x80'   Latin-1 글자 6개로 읽힘
print(s.encode('euc-kr').decode('utf-8', errors='replace').encode('unicode_escape'))
# b'\\ufffd\\u0471\\ufffd'            대체 문자(U+FFFD)가 섞임
try:
    b'\xea\xb0'.decode('utf-8')       # '가'의 3바이트 중 2바이트만
except Exception as e:
    print(type(e).__name__)           # UnicodeDecodeError
```

UTF-8로 읽다가 규칙에 안 맞는 바이트를 만나면 오류가 나거나 대체 문자(�)가 들어간다. 파일이 중간에 잘렸거나 인코딩을 잘못 짚었을 때 보이는 모습이다.

<details>
<summary>같은 글자인데 코드 포인트가 다른 경우</summary>

'é'는 한 코드 포인트(U+00E9)일 수도 있고, 'e' 뒤에 결합 악센트(U+0301)가 붙은 두 코드 포인트일 수도 있다. 화면에서는 똑같이 보인다.

```python
import unicodedata
print(len('é'), len('é'))              # 1 2
print('é' == 'é')                       # False
print(unicodedata.normalize('NFC', 'é') == 'é')   # True
```

검색이나 비교에서 문자열을 먼저 정규화해야 하는 경우가 이래서 생긴다.
</details>

## 이어 보면

| 대상 | 약속 | 한 줄 요약 |
|---|---|---|
| 정수 | 2의 보수 | 덧셈 회로 하나로 부호까지 처리, 범위를 넘으면 한 바퀴 돎 |
| 실수 | IEEE 754 | 부호·지수·가수, 대부분의 10진 소수는 근삿값 |
| 문자 | 유니코드 + UTF-8 | 번호와 바이트를 나눠서 생각, 글자마다 1~4바이트 |

비트 수가 정해져 있어서 생기는 한계(오버플로, 반올림 오차, 바이트 수 차이)가 이 셋에서 다 나온다. 이렇게 만든 값이 레지스터에서 캐시, 메모리, 디스크로 어떻게 오가는지는 [메모리 계층과 캐시](#/post/ca-memory-hierarchy)에서 본다.

## 흔한 오해

- 0.1 + 0.2가 0.3이 아닌 건 파이썬의 문제다: 파이썬은 binary64 값을 그대로 보여 줄 뿐이다. 정확한 10진 연산이 필요하면 `decimal`을 쓴다.
- 음수는 맨 앞 비트만 1로 바꾼 것이다: 2의 보수에서는 맨 앞 비트가 -2^(n-1)의 자리값이라서 나머지 비트도 같이 달라진다. -5는 `10000101`이 아니라 `11111011`이다.
- UTF-8 문자는 모두 3바이트다: 영어는 1바이트이고 한글이 대부분 3바이트다. 1~4바이트를 섞어 쓴다.
- 글자 수가 곧 바이트 수다: ASCII만 쓸 때만 같다. 한글 두 글자가 UTF-8로 6바이트였다.
- 한글이 깨지면 데이터가 손상된 것이다: 비트는 그대로이고 읽는 인코딩만 틀린 경우가 많다.
