## 这是什么
FFmpeg 是一个用来剪切、转换音视频文件的老牌命令行程序。功能很多，但选项复杂，代理自己拼命令很容易出错。README 的"Why"一节正好点出了这一点:就算是"懂 FFmpeg"的代理，也会去猜帧率，选一个容器装不下的编码，连结果都不打开就报告"完成了"。

所以这个仓库不让代理自己写 FFmpeg 命令。剪切(cut)、拼接(join)、去掉静音段(silence)、适配画面比例(fit)、字幕(caption)、响度(loudness)、按平台导出(export)等等，每件事都做成一个 Python 脚本，一共 42 个。代理只传脚本名和规定好的参数。不经过 shell，也不接受调用方直接传进来的 FFmpeg 滤镜字符串。只用 Python 标准库，不需要云服务，也不需要 API 密钥。

技能是代理需要时拿出来读的说明书。[详细 → 技能](#/post/ai-skills) 同一批工具也以 MCP 服务器的形式提供。MCP 是让代理能像调用工具一样调用外部程序功能的连接规范。[详细 → MCP](#/post/ai-mcp)

## 先测，再做，再测
README 画的流程是这样的:收到请求后，代理读 SKILL.md，挑出合适的脚本。脚本运行前先确认这台机器上有它需要的 FFmpeg 功能，然后运行 FFmpeg，再重新测量写出的文件，用 JSON 返回结果。

设计原则第一条是"Probe first"。probe 就是真的打开文件，测量时长、帧率、分辨率、色彩信息和音轨。意思是不要看文件名下判断。每个工具还都有 `--dry-run`，只显示将要执行的 FFmpeg 命令，不写文件。要覆盖已有文件，必须明确加上 `--overwrite`。

我觉得有意思的是结果里附带的 `unverified` 列表。工具只把能测量的东西算作"已确认"。时长、编码、响度会重新测量对照。反过来，画面里有什么、字幕能不能看清、剪掉的片段里有没有人声、口型和声音对不对得上，这些靠测文件是看不出来的。这类项目会作为未确认的内容单独列出来返回。读不到的值不算通过，而是以 `not_measured` 判为失败。如果画面有变化，它会要求用 look.py 生成一张把几帧拼在一起的图(contact sheet)，用眼睛看。

## 契约从代码里生成
运行 `contract --json`，会得到一份文档，写明 42 个工具各自接收什么、返回什么、需要哪些 FFmpeg 组件、用什么来验证结果。README 把它叫作机器可读的契约(machine-readable contract)。它不靠人手维护，而是从每个脚本的参数定义(argparse)自动生成。MCP 服务器的工具列表也从这里来。所以给脚本加一个参数，MCP 那边不用改也会跟着变。README 说有测试专门检查这一点。

文档之间数字对不上的问题也用测试挡住了。按 contract.md 的说法，README、SKILL.md、package.json 里写的"42"每次都会和 scripts 文件夹里的实际工具数对比。之所以加这个，是因为 SKILL.md 里一个旧的"28"在工具增加了十二个期间一直没改。

42 个工具不会全部展示给代理。MCP 默认列表只放常用的 12 个，其余 30 个需要时按名字调用。从 4.0 开始，这 12 个是 stable(到下一个大版本前不改参数名和输出名)，其余是 beta。

README 里有很长的自评记录。作者把提示词从几十个逐步加到 100 个，让代理去跑，再让另一个模型打分。1.17.0 时在 100 个提示词上写着"原生 FFmpeg 调用 0 次，虚假成功报告 0 次"。它不只写分数，还记下了哪里出错、下个版本修了什么。不过这是作者自己测的数字。有没有别人复现过:未能确认。README 也坦白说，完整的真机素材测试还没在 Windows 上跑过。

## 站在入门者的角度
比起视频剪辑本身，我觉得结构更值得看。不是用文字拜托代理"小心点"，而是把容易出错的活交给脚本，结果重新测量，测不了的就写明测不了再返回。之前看过的阿里巴巴 Open Code Review 也是把不能出错的步骤交给代码。[详细 → Open Code Review](#/post/news-261115-a)

对 PM 来说，可以借鉴的是 `unverified` 这种思路。不是只收到一句"完成"，而是同时知道哪些确认过了、哪些还需要人来看。审查代理的结果时，要看的地方就少了。README 也划了界线:这个工具只负责"执行"剪辑，剪哪里、结果好不好，由人或别的代理来决定。
