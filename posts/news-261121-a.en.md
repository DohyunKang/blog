This morning HKUDS/CLI-Anything was on GitHub Trending (daily). 774 stars today, 61,363 in total (checked the morning of November 21). It comes from the HKUDS lab at the University of Hong Kong. The idea: take desktop programs built for people with a mouse (GIMP, Blender, LibreOffice and so on) and give them a command-line tool an AI agent can use. I read the README, HARNESS.md in the plugin folder, and the SKILL.md of the CLI-Hub meta-skill. I didn't run it myself.

## What it is
A CLI is a way of using a program by typing commands instead of clicking. Agents read and write text, so typing a command suits them far better than hunting for a button. I wrote up how agents pick and call tools before. [More → Tool calling](#/post/ai-tool-use)

CLI-Anything has two parts. One is a Claude Code plugin: point it at a program's source folder, like `/cli-anything ./gimp`, and the agent builds a CLI for that program. The other is CLI-Hub, a collection of CLIs already built. You install one with `pip install cli-anything-hub` and then `cli-hub install gimp`. The two registry files in the repo list 79 and 24 entries.

Using a generated CLI looks like this, straight from the README example: `cli-anything-libreoffice document new -o report.json --type writer` creates a document, more commands add a heading and a table, and `export render output.pdf` runs the real LibreOffice without a screen to produce a PDF. Add `--json` to any command and the result comes back as JSON the agent can read directly. Run it with no command and you get an interactive mode (REPL) where you type one line at a time.

## How it builds one
Calling `/cli-anything` runs seven phases: analyze the source, design the command structure, implement, plan tests, write tests, document, and package for install. At the end it also writes a SKILL.md describing how to use the CLI. A skill is a set of instructions an agent pulls out when it needs it. [More → Skills](#/post/ai-skills)

HARNESS.md is basically the design doc, and the first phase was the interesting part.

1. Find the engine behind the GUI. The screen is a shell; the real work happens in a library underneath. The doc uses MLT, the engine behind the video editor Shotcut, as an example.
2. Match every button click and menu item to the function call it really is.
3. Figure out the project file format (XML, JSON and so on).
4. If the program has undo, that's your unit of command. Undo only works if actions are split into single commands, so those map straight onto CLI commands.

One principle stood out: always call the real program. No faking GIMP with a Python image library. The CLI writes the project file and leaves rendering to the actual app. If the app isn't installed, the tests fail instead of being skipped. There's also a line saying not to trust an export just because it exited with code 0. For a PDF, check that the file starts with `%PDF-`; for audio, check the volume isn't zero. With all of these checks the README claims 2,464 passing tests.

The repo was created in March and the last commit on main is from September 22. It isn't riding a new release either (the latest is v0.4.0, June 25). Still, X posts containing "CLI-Anything" (no retweets) went from 2 on November 17 to 22 on the 18th, 87 on the 19th and 63 on the 20th (UTC days), and it's been on Trending for a few days. What people kept saying on X was mostly one thing: driving an app by taking screenshots and clicking coordinates breaks when a button moves or a popup shows up. agent-desktop, which I looked at earlier, reads screen elements through the accessibility tree. This one skips the screen entirely and hooks into the engine. [More → agent-desktop](#/post/news-261111-a)

## For beginners
For a PM, it's one more question to ask about any program: can an agent use it? If it can be driven by commands and JSON instead of a screen, automation breaks less. The README lists its own limits, though. You need a strong recent model to get a decent CLI, quality drops a lot for programs without source code, and you often have to run `/cli-anything:refine` several times.

For a beginner developer, HARNESS.md reads well as a feature-design exercise. Ordering like "build the inspect commands first, the commands that change things after" holds up even without agents. Comparing it with MCP, the other common way agents use tools, makes the difference clearer. [More → MCP](#/post/ai-mcp)
