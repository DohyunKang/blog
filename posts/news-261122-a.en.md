It's a bundle of Claude Code skills for bug bounties (programs where companies pay you for reporting vulnerabilities within a published scope) and external red-teaming (testing a company from an attacker's point of view, with permission). ## What it is
A skill is a set of instructions an agent pulls out when it needs it. [More → Skills](#/post/ai-skills) This repo bundles 83 of them, plus 15 slash commands. You don't call them by name. You describe what you're doing, like "I'm testing this target", and the matching skills load on their own, according to the README.

The README's breakdown, roughly:

1. 58 hunt-* skills, one per web vulnerability class. They say the patterns came from 681 disclosed reports on HackerOne.
2. 10 skills for enterprise platforms like M365, Okta and VPN appliances.
3. 6 skills for validating findings and writing reports.
4. 5 recon and open-source-intelligence skills, and 4 methodology skills.

Install is two lines inside Claude Code: `/plugin marketplace add` and `/plugin install`. Because the skill format is shared, the skills can also be copied into other agent tools like OpenCode or Codex CLI. The slash commands and the automated engine are Claude Code only.

## How it runs
The flow is scope → recon → rank → hunt → validate → report. Set the scope, survey the target, rank where to look first, hunt, validate, write it up.

What stood out was the split of work. The docstring at the top of engine.py says scope checks, state, dispatch, ranking, dedup and reporting are plain deterministic code, and the model is used only for recon, hunting and validation. Out-of-scope hosts are filtered out of recon results by code, and no agent is ever sent at an out-of-scope target. It's not asking the model nicely to stay in scope. The code just doesn't allow it. State is saved after every step, so a run can be resumed if it stops.

The other piece is the 7-Question Gate. Before writing a report, seven questions are asked in order, and if any one fails, the finding is dropped. The first is "can an attacker use this right now, step by step?" Others ask whether it's in scope and whether the program accepts that kind of impact. The doc lists false positives the gate caught: your input shows up in the response, but only because the page echoes the URL back; or the status code changed while the body stayed byte-identical. It's a guard against the model insisting it found something plausible.

## The measured numbers are still thin
The eval folder has a harness that runs the same tasks with skills on and off. Same idea as SkillEvaluator, which I looked at before. [More → SkillEvaluator](#/post/news-261119-a) But the latest result in BASELINE.md (August 25) covers only three tasks on OWASP Juice Shop, a deliberately vulnerable practice site, and both conditions solved all three. With skills on it actually took a few more turns and a bit more money. The author notes these tasks are easy enough that the model has probably memorized them, so they can't measure skill value. The harder set (PortSwigger labs) hasn't been run yet because of account setup. So "skills make it find more" isn't shown in numbers inside this repo yet.

## For a beginner
First, to be clear: this is meant only for targets you own or have written permission to test. The README says so, and running it against someone else's service without permission is illegal.

Setting that aside, what's worth a PM's look is the structure. The parts where a mistake is costly (scope, state, dedup) go to code, and only the judgment calls go to the model. Then the model's output gets filtered once more by a checklist. That pattern works for automation outside security too. On the defensive side, I looked at a similar kind of tool before, OpenAI's Codex Security. [More → Codex Security](#/post/news-261113-a)
