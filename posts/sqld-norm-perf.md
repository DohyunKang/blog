정규화는 중복 때문에 생기는 이상 현상을 막으려고 테이블을 쪼개는 일이고, 반정규화와 파티셔닝, 슈퍼/서브타입은 그렇게 쪼갠 모델을 성능 때문에 다시 손보는 방법이다. SQLD 1과목에서 개념 문제도 나오고 상황을 주고 "어떻게 바꾸겠나"를 묻는 문제도 나오는 단원이라, 정의만 외우지 않고 어떤 때 쓰는지까지 묶어서 정리했다.

시험 일정과 응시료는 공식 사이트에서 확인하면 된다. 이 글은 단원 개념과 자주 나오는 유형만 다룬다.

## 정규화가 왜 필요한지

한 테이블에 부서 이름을 사원마다 적어 두면, 부서 이름이 바뀔 때 사원 수만큼 고쳐야 한다. 하나라도 빠뜨리면 같은 부서가 두 이름을 갖는다. 이런 문제를 이상(anomaly) 현상이라 부르고 보통 셋으로 나눈다.

| 이상 | 상황 |
|---|---|
| 삽입 이상 | 사원이 없는 새 부서는 넣을 자리가 없다 |
| 갱신 이상 | 부서 이름 변경 시 일부 행만 바뀌어 불일치가 생긴다 |
| 삭제 이상 | 마지막 사원을 지우면 부서 정보까지 사라진다 |

정규화는 이걸 막으려고 함수 종속을 따라 테이블을 나누는 작업이다. 함수 종속은 "A 값이 정해지면 B 값이 하나로 정해진다"는 관계(A → B)다. 사원번호가 정해지면 사원 이름이 하나로 정해지니까 사원번호 → 사원이름이다.

## 1~3정규형

위키백과 정규화 문서의 정의를 기준으로 하면 세 단계는 이렇게 읽힌다.

| 정규형 | 조건 | 위반 시 하는 일 |
|---|---|---|
| 제1정규형 | 모든 칸이 값 하나만 갖는다. 반복 그룹, 다중값이 없다 | 반복되는 값을 별도 테이블로 뺀다 |
| 제2정규형 | 기본키가 복합키일 때, 일반 속성이 키 전체에 종속된다 (부분 종속 제거) | 부분 종속되는 속성을 따로 뺀다 |
| 제3정규형 | 일반 속성이 다른 일반 속성에 종속되지 않는다 (이행 종속 제거) | 이행 종속되는 속성을 따로 뺀다 |

외울 때는 키워드 하나씩 붙이면 편했다. 1정규형은 원자값, 2정규형은 부분 종속, 3정규형은 이행 종속.

수강 테이블로 보면 이렇다. 기본키가 (학번, 과목코드)인데 과목이름이 과목코드에만 종속되면 부분 종속이라 2정규형 위반이다. 학번 → 학과코드 → 학과이름처럼 일반 속성이 일반 속성을 결정하면 이행 종속이라 3정규형 위반이다.

<details>
<summary>풀이 순서 (문제가 나왔을 때)</summary>

1. 기본키를 먼저 확인한다.
2. 칸 하나에 값이 여러 개 들어 있으면 1정규형 위반이다.
3. 기본키가 복합키라면 일반 속성마다 "키 일부만으로 정해지나"를 본다. 그렇다면 2정규형 위반이다.
4. 일반 속성끼리 "A가 B를 정한다"가 있으면 3정규형 위반이다.
5. 위반한 속성을 결정자(왼쪽 속성)와 함께 새 테이블로 뺀다. 원래 테이블에는 결정자를 외래키로 남긴다.

기본키가 단일 속성이면 부분 종속은 생길 수 없어서 2정규형은 자동으로 만족한다. 이 점이 선택지에서 자주 쓰인다.
</details>

BCNF, 4정규형, 5정규형도 있지만 이 단원에서는 제3정규형까지를 중심으로 보면 된다고 알려져 있다. 출제 범위는 공식 사이트의 과목 안내를 확인하는 게 정확하다.

## 정규화를 코드로 확인해 보기

사원과 부서를 분리하면 부서 이름은 한 곳에만 있다. sqlite로 직접 돌려 봤다.

```sql
CREATE TABLE dept(dept_id INT PRIMARY KEY, dept_name TEXT);
CREATE TABLE emp(emp_id INT PRIMARY KEY, emp_name TEXT,
                 dept_id INT REFERENCES dept);
INSERT INTO dept VALUES (10, '영업');
INSERT INTO emp VALUES (1, '가', 10), (2, '나', 10);

UPDATE dept SET dept_name = '영업1' WHERE dept_id = 10;

SELECT e.emp_name, d.dept_name
FROM emp e JOIN dept d USING (dept_id);
```

결과는 `('가', '영업1')`, `('나', '영업1')`이었다. 한 행만 고쳤는데 두 사원에게 다 반영된다. 대신 사원과 부서 이름을 같이 보려면 조인이 필요해졌다. 반정규화 얘기가 여기서 시작된다.

## 반정규화

정규화하면 테이블이 늘고, 조회할 때 조인이 늘어난다. 조인이 성능의 병목이 되면 일부러 중복을 허용하는 게 반정규화다. 위키백과 정규화 문서에는 반정규화 항목이 따로 없고 별도 문서로 연결만 돼 있다. 일반적으로는 중복을 감수하고 조인을 줄이는 방식으로 설명된다.

시험에서는 방법을 분류해서 묻는다.

| 구분 | 방법 | 예 |
|---|---|---|
| 테이블 | 테이블 병합 | 1:1, 1:N 관계 테이블을 하나로 합침 |
| 테이블 | 테이블 분할 | 컬럼 기준(수직 분할), 행 기준(수평 분할) |
| 테이블 | 테이블 추가 | 집계 테이블, 이력 테이블, 부분 테이블 |
| 컬럼 | 중복 컬럼 추가 | 조인 없이 보려고 이름 컬럼을 복사 |
| 컬럼 | 파생 컬럼 추가 | 합계·건수를 미리 계산해 저장 |
| 관계 | 중복 관계 추가 | 여러 단계 조인을 줄이려 관계를 하나 더 둠 |

반정규화 전에 먼저 해 볼 일도 같이 알아 두면 좋다. 인덱스를 조정하거나, 뷰를 쓰거나, 쿼리를 고치는 쪽이 먼저고, 그래도 안 될 때 반정규화로 간다는 순서로 나오는 경우가 많다.

반정규화의 대가는 데이터 일관성이다. 복사해 둔 컬럼은 원본이 바뀔 때 같이 바꿔야 하고, 그걸 애플리케이션이나 트리거가 맡게 된다. 그래서 읽기가 압도적으로 많은 조회성 업무에서 주로 고려한다.

## 슈퍼타입과 서브타입

엔터티가 공통 속성을 가진 채 종류별로 갈릴 때, 공통 부분이 슈퍼타입이고 종류별 부분이 서브타입이다. 예를 들어 고객이 개인고객과 법인고객으로 나뉜다. 논리 모델에서는 이렇게 그리고, 물리 모델로 옮길 때 세 가지 방식 중 하나를 고른다.

| 변환 방식 | 모양 | 어울리는 때 |
|---|---|---|
| 일대일 관계 | 슈퍼와 서브를 각각 테이블로 두고 1:1 연결 | 서브타입별 속성이 많고 따로 조회가 많을 때 |
| 슈퍼+서브 통합 (단일 테이블) | 하나의 테이블에 구분 컬럼과 모든 속성을 넣음 | 서브타입 구분 없이 같이 조회가 많고 처리 속도가 중요할 때 |
| 서브타입별 분리 | 서브타입마다 테이블, 공통 속성 중복 | 서브타입별로 거의 따로 쓸 때 |

통합 방식은 조인이 없어 빠르지만 해당하지 않는 컬럼이 NULL로 남고 테이블이 커진다. 반대로 분리하면 테이블은 가볍지만 전체를 합쳐 볼 때 조인이나 UNION이 필요하다. 시험에서는 "조회 패턴이 이렇다, 어느 변환이 맞나"로 나온다. 장단점을 한 쌍씩 외워 두면 풀린다.

[자세히 → 엔터티와 속성](#/post/sqld-entity-attr)에서 엔터티 분류를 같이 보면 슈퍼/서브가 어디서 나오는지 이해가 쉽다.

## 파티셔닝

큰 테이블을 작은 조각으로 나눠 관리하는 방법이다. Oracle 문서는 파티셔닝을 테이블이나 인덱스를 파티션이라는 더 작은 조각으로 나누는 것으로 설명하고, 애플리케이션에서는 파티션 테이블이 일반 테이블처럼 보여 SQL을 바꿀 필요가 없다고 한다. 어느 행이 어느 파티션에 들어갈지는 파티션 키로 정해진다.

| 방식 | 기준 | 예 |
|---|---|---|
| 범위(Range) | 값의 범위 | 월별 주문 데이터 |
| 목록(List) | 지정한 값 목록 | 지역별 데이터 |
| 해시(Hash) | 해시 값으로 고르게 분산 | 자연스러운 범위가 없는 데이터 |
| 복합(Composite) | 위 방식을 겹쳐서 사용 | 범위 안에서 해시 |

효과는 문서에서 크게 셋으로 나온다. 성능에서는 필요한 파티션만 읽는 파티션 프루닝(pruning)이 핵심이다. 문서 예시는 주 단위로 2년치(104개)를 나눈 주문 테이블에서 한 주를 조회하면 104개 중 1개만 읽는다는 것이다. 관리 쪽에서는 파티션 단위로 백업하거나 적재할 수 있고, 가용성 쪽에서는 한 파티션이 막혀도 나머지는 쓸 수 있다.

시험에서는 "조회 조건에 파티션 키가 들어가야 효과가 있다"는 식의 문장이 옳고 그름 선택지로 나오곤 한다. 프루닝이 키 조건으로 작동하는 구조라서 이해하면 헷갈리지 않는다. 파티션 방식 이름과 기준을 짝지어 외우면 된다.

<details>
<summary>수평 분할과 파티셔닝은 같은 건가</summary>

테이블 수평 분할은 행을 기준으로 테이블 자체를 여러 개로 나누는 것이고, 파티셔닝은 논리적으로는 하나의 테이블을 두고 저장을 나눈다. 수평 분할은 애플리케이션이 어느 테이블을 볼지 알아야 하지만, 파티셔닝은 SQL을 바꿀 필요가 없다는 점이 다르다. 시험에서는 둘을 구분해 묻는 쪽보다 효과를 묻는 쪽이 많다.
</details>

## 인덱스 관점으로 본 성능 모델링

인덱스를 설계할 때 모델링 단계에서 생각할 것은 몇 가지로 정리된다.

- 조회 조건과 조인에 자주 쓰이는 컬럼에 인덱스를 둔다. 외래키 컬럼이 대표적이다.
- 값의 종류가 아주 적은 컬럼은 효과가 작다. 선택도가 높은 컬럼이 낫다.
- 인덱스는 조회를 빠르게 하는 대신 INSERT, UPDATE, DELETE 때 같이 갱신되므로 쓰기 비용이 든다.
- 복합 인덱스는 컬럼 순서가 중요하다. 앞쪽 컬럼이 조건에 쓰이지 않으면 활용이 어렵다.

위의 사원 예에서 `emp(dept_id)`에 인덱스를 만들고 sqlite의 실행 계획을 보니 `SEARCH emp USING INDEX ix_emp_dept (dept_id=?)`로 나왔다. 외래키 컬럼 조회가 인덱스를 타는 모습이다.

```sql
CREATE INDEX ix_emp_dept ON emp(dept_id);
EXPLAIN QUERY PLAN SELECT * FROM emp WHERE dept_id = 10;
```

인덱스 내부 구조는 [자세히 → 인덱스](#/post/db-index)에, 정규화를 데이터베이스 일반 개념으로 다룬 글은 [자세히 → 정규화](#/post/db-normalization)에 따로 있다. 이 글은 시험에 나오는 쪽만 다룬다.

## 자주 나오는 유형 정리

| 유형 | 풀이 방식 |
|---|---|
| 주어진 테이블이 몇 정규형인지 | 기본키 확인, 부분 종속 → 이행 종속 순서로 점검 |
| 정규화 결과 테이블 구성 | 결정자와 종속 속성을 한 쌍으로 분리 |
| 반정규화 기법 분류 | 테이블, 컬럼, 관계 중 어디를 건드리는지로 나눔 |
| 조회가 느리다는 상황 | 인덱스, 뷰, 반정규화 순으로 고려 |
| 슈퍼/서브타입 변환 선택 | 조회 패턴(같이 보나 따로 보나)을 기준으로 |
| 파티션 효과 | 파티션 키 조건, 프루닝, 관리 단위 분할 |

선택지에서 틀리게 만드는 흔한 패턴은 "정규화를 많이 할수록 항상 성능이 좋아진다"는 식의 단정이다. 정규화는 일관성을 지키는 쪽이고 조회 성능은 조인이 늘어서 오히려 불리할 수 있다는 점만 기억하면 이런 선택지를 걸러낼 수 있다.
