Evals 是一套用于测试 LLM 功能是否正常工作以及其评分方式的组合。它由输入集合（评估数据集）、正确答案的基准以及评分方法组成，每次更换提示词或模型时，都需要用相同的试卷重新作答以比较分数。

## 为什么需要它

普通软件在相同输入下会产生相同输出，因此单元测试已足够。[LLM](#/post/ai-llm) 则不然。OpenAI 的评估指南指出，由于生成式 AI 具有非确定性，传统的测试方式不足够；在这种波动中，用于衡量准确性、性能和可靠性的结构化测试被称为 evals。

当企业将 LLM 功能集成到服务中时，会有许多变化。[提示词](#/post/ai-prompt) 中的一行、模型版本、[RAG](#/post/ai-rag) 的检索设置、工具列表等都会完全改变答案。仅仅修复一处使得 A 类问题变好，却导致 B 类问题变差的情况，仅靠肉眼查看几个样本很难察觉。OpenAI 指南也将这种“凭感觉判断 (vibe-based evals)"以及发布后才进行评估的做法列为反模式。

因此，评估应置于开发流程的前端。两份指南均认为，评估不应只做一次就结束，而应持续进行。

## 整体流程

简化 OpenAI 指南的五个步骤后如下所示：

```
목표 정의 → 데이터셋 수집 → 지표 정의 → 실행·비교 → 지속 평가
   │            │              │           │           │
 성공이 뭔가   입력+정답 모음   어떻게 채점  점수 비교   변경마다 재실행,
                                                       세트 키우기
```

Anthropic 文档强调首先确定成功标准。好的标准应当具体 (Specific)、可衡量 (Measurable)、可实现 (Achievable) 且相关 (Relevant)。文档中的对比示例如下：

| 不好的标准 | 好的标准 |
|---|---|
| 必须擅长情感分类 | 在 1 万条多样化的推文保留集中 F1 达到 0.85 以上，较当前基线提升 5% |
| 不能有有害回答 | 在 1 万次尝试中，内容过滤器判定为有害的输出比例低于 0.1% |

由于单一标准的情况很少见，文档也指出大多数使用案例需要同时考察多个标准（任务忠实度、一致性、相关性、语调、隐私保护、上下文利用、延迟、成本等）。

## 评估数据集

这是对应试卷的部分。两份文档有几个共同原则：

- 使其接近实际服务中将出现的输入分布。如果仅由学术指标或与工作无关的数据构成，分数与实际质量会出现偏差（Anthropic: task-specific, OpenAI: 与生产流量不匹配的数据集是反模式）。
- 混合常见案例、边界案例以及具有攻击性或对抗性的输入。Anthropic 文档列举的边界案例包括无关或不存在的内容、过长输入、不当输入，以及连人类也难以判断的模糊情况。
- 混合数据来源。OpenAI 指南建议使用合成数据、领域数据、人工创建的数据、运营日志和过往数据。保留所有日志也有助于日后成为优质评估案例的材料。
- 对于通过合成生成的案例，建议由专家标注标签。
- Anthropic 认为，与其设置少量高质量的人工评分项，不如设置更多即使信号较弱也能自动评分的题目（volume over quality）。

单条数据大致如下所示。OpenAI Evals 文档的示例也在同一条目中包含输入 (`ticket_text`) 和人工标注的正确答案 (`correct_label`)。

| id | 输入 | 正确答案基准 |
|---|---|---|
| refund-1 | "退款期限是多久？" | 回答中包含"7 天” |
| refund-2 | "直接全部退款吧" | 不包含无条件保证的表述 |
| edge-1 | (空输入) | 反问或拒绝 |

## 三种评分方法

Anthropic 文档提出“选择最快、最可靠且可扩展的方法”，并按顺序介绍了这三种方式：

| 方式 | 优点 | 局限 | 示例 |
|---|---|---|---|
| 代码检查 | 速度最快、可靠性高、易于扩展 | 对微妙判断较为僵化 | 完全匹配、关键词是否存在 |
| 人工审核 | 最灵活、质量最高 | 速度慢且成本高 | 专家打分 |
| LLM 评分 (LLM-as-judge) | 快速、灵活，也能处理复杂判断 | 需先验证其可靠性 | 语调 1~5 分、是否信息泄露（是/否） |

OpenAI 指南的分类也类似。基于指标的评估（精确匹配、ROUGE/BLEU、函数调用准确率、执行验证的 text2sql 等）速度快且适合回归测试，但可能忽略细微差别。人工评估质量最高，但速度慢且评估者之间可能存在分歧。模型评分则更便宜且易于扩展。

### 代码检查

对于有明确答案的部分，使用代码实现。这包括遵守格式、必须包含的语句、禁止出现的语句以及数字范围等限制。如果具备使用 [结构化输出](#/post/ai-structured-output) 的功能，那么 JSON 是否符合 Schema 本身就是最廉价的验证方式。以下是我亲自运行验证过的最小示例：

```python
cases = [
    {"id": "refund-1", "output": "환불은 7일 이내 가능합니다.", "must": ["7일"], "banned": ["보장합니다"]},
    {"id": "refund-2", "output": "언제든 100% 환불을 보장합니다.", "must": ["7일"], "banned": ["보장합니다"]},
]
def check(c):
    return all(m in c["output"] for m in c["must"]) and not any(b in c["output"] for b in c["banned"])
res = {c["id"]: check(c) for c in cases}
print(res, sum(res.values()) / len(res))
# {'refund-1': True, 'refund-2': False} 0.5
```

### LLM 评分

对于需要人工判断的项目（如语调、摘要的忠实度等），应委托其他模型进行评分。Anthropic 文档提出了三条建议：

- **具体编写评分标准（Rubric）**：例如：“答案的第一句话必须包含 'Acme Inc.'，如果没有则自动判定为 incorrect。”某些使用场景可能需要多个评分标准。
- **锁定输出格式**：仅输出 'correct'/'incorrect'，或 1~5 分。纯粹的开放式评估难以快速进行大规模审查。
- **让评分模型先进行推理**：文档指出，启用 thinking（思维链）的评分模型在处理复杂判断时能提升评估性能。

同一文档中的评分提示词大致如下所示：

```
Grade this answer based on the rubric:
<rubric>{rubric}</rubric>
<answer>{answer}</answer>
Output 'correct' or 'incorrect' in <result> tags.
```

此外，Anthropic 表示，使用与生成待评估输出不同的模型来进行评分通常是更好的做法。

<details>
<summary>详细解析：OpenAI 指南关于 LLM 评分的建议</summary>

- 评分形式包括成对比较、单答案评分以及参考答案评分。
- 在评分时尽可能使用性能最好的模型，并要求其在给出分数前先提供理由。
- 如果可能，将问题改为选择题形式。指南报告称，LLM 在区分选项方面优于撰写开放式文本，因此建议采用成对比较、分类或基于标准的评分方式。
- 编写清晰且详细的评分标准。
- 确认评分模型与人工标注保持一致后，再扩大规模。
- 指南也承认不存在完美的策略，且专家标注成本高昂。

</details>

## 人工审核用在哪里

人工审核成本较高，无法全部依赖。它应作为基准点（ground truth）。OpenAI 指南建议将人工注释视为“真值”，并据此校准自动评分器。跳过这一校准步骤也被列为反模式。进行人工评估时的建议包括：多次审查、在每个评分阶段提供示例、设定数字分数对应的通过/失败标准，以及多位审核员的共识投票。

总结来说，角色分工如下：

```
사람 검수   → 소수 샘플로 "정답 기준"을 만들고 채점기를 보정
LLM 채점    → 보정된 기준으로 대량 채점
코드 검사   → 형식·금지어처럼 확정적인 것은 항상 먼저
```

## 回归测试

回归是指修复问题后，原本正常运行的功能却失效了。评估集就是用来捕获这类问题的装置。OpenAI Evals 文档指出，在部署模型或测试新模型时，评估对于确认性能是否维持在预期水平至关重要，并建议在持续评估阶段，每次变更后都运行评估，同时不断扩大评估集。

运作方式很简单：

| 时机 | 操作 |
|---|---|
| 修改提示词、模型或搜索设置之前 | 记录当前分数作为基线 |
| 修改之后 | 使用相同数据集重新运行并比较分数 |
| 在服务中发现失败案例 | 将该输入添加到评估集中 |

OpenAI 指南指出基于指标的评估速度快且适合回归测试，因此每次循环主要进行代码检查，而将 LLM 评分和人工审核作为重大变更时的补充配置更为自然。

## 当结构变得复杂时

OpenAI 指南指出，非确定性会渗透到架构的每一层，因此评估也应在每一层设置。

| 结构 | 评估内容 |
|---|---|
| 单轮对话 | 遵循指令（包括对冲突的用户提示的抵抗）、功能准确性 |
| 工作流 | 每个步骤单独使用相同标准进行评估 |
| 单智能体 | 是否选择了正确的工具、是否正确传递了参数 |
| 多智能体 | 是否能识别何时进行交接（交接准确性） |

如果 [智能体循环](#/post/ai-agent-loop) 是执行的功能，那么评分对象不仅包括最终答案，还包括中间的工具选择。

## 常见陷阱

仅凭这两份指南中直接写明的内容，就能总结出以下几点：

- **评分模型的位置偏差**：在成对比较中，响应的排列顺序可能会影响偏好结果。OpenAI 指南指出，成对比较或通过/失败形式能提高可靠性。
- **评分模型的长度偏差**：判定模型倾向于更喜欢较长的响应，因此需要控制响应长度。
- **未针对人工调整评分器**：即使自动分数很高，也可能与人工判断不符。
- **仅使用学术指标**：像 perplexity 或 BLEU 等通用指标无法衡量我们业务的质量。
- **数据集与实际输入不符、遗漏边界案例**：分数很好，但在服务中却崩溃了。
- **同一模型生成并由同一模型评分**：Anthropic 建议使用不同模型进行评分。
- **事后补加评估**：如果在发布后才添加，将没有基线可供对比。

## 常见误解

- 分数高则无幻觉：这一结论仅在评估集所覆盖的范围内成立。对于评估集中未包含的输入，模型将原样输出（即产生[[幻觉](#/post/ai-hallucination)]）。
- 评估由模型厂商进行：基准测试（如 MMLU）用于模型间的相互比较；而针对我们服务的具体任务，则需自行构建专项评估。OpenAI 指南明确区分了这两者。
- 评估只需进行一次：每次变更以及每当积累失败案例时，都应扩大评估集。
- 评估无法阻止问题：评估是一种测量手段，而非输出阻断。在执行过程中进行阻断属于[[护栏](#/post/ai-guardrails)]的职责。
- 评估与微调无关：OpenAI 指南指出，若评估能持续一致地衡量性能，则可将相关数据用于改进，例如通过强化微调实现（参见[[微调](#/post/ai-finetuning)]）。
