상태 관리는 화면이 기억해야 하는 값을 어디에 두고 누가 바꾸게 할지 정하는 일이고, 라이브러리보다 값의 종류를 먼저 나누는 쪽이 훨씬 중요했다.

## 상태가 뭔지

상태(state)는 시간이 지나면서 바뀌고, 바뀌면 화면도 같이 바뀌어야 하는 값이다. 입력창에 친 글자, 메뉴가 열렸는지, 로그인한 사용자, 서버에서 받아 온 목록이 다 상태다. 화면은 상태를 받아서 그려지는 결과물이라고 보면 쉽다. 그래서 화면이 이상하면 대개 상태가 이상한 거다.

[자세히 → 컴포넌트 설계](#/post/fe-component)에서 다루겠지만, 요즘 프런트엔드는 화면을 컴포넌트로 쪼갠다. 쪼개는 순간 "이 값은 어느 컴포넌트가 들고 있나"라는 질문이 생긴다. 상태 관리는 이 질문의 답을 모아 둔 이름이다.

## 상태를 세 종류로 나누기

처음엔 다 같은 상태라고 생각했는데, 성격이 달라서 나눠 보는 게 편했다.

| 종류 | 예 | 보통 어디에 | 특징 |
|---|---|---|---|
| 로컬 상태 | 입력 중인 글자, 모달 열림 여부 | 그 컴포넌트 안 | 다른 곳에서 알 필요 없음 |
| 공유(전역) 상태 | 로그인 사용자, 테마, 장바구니 | 공통 부모, 컨텍스트, 스토어 | 여러 화면이 같이 읽고 바꿈 |
| 서버 상태 | 게시글 목록, 상품 정보 | 서버가 원본, 클라이언트는 사본 | 비동기, 남이 바꿀 수 있음, 낡을 수 있음 |

기준은 "이 값을 누가 알아야 하나"와 "원본이 어디 있나" 두 가지다. 원본이 서버에 있으면 서버 상태고, 없으면서 한 컴포넌트만 쓰면 로컬이고, 여럿이 쓰면 공유다.

## 로컬에서 시작해서 끌어올리기

React 문서의 기본 방침은 상태를 일단 가까이 두고, 필요해지면 올리는 것이다. 두 컴포넌트가 항상 같이 바뀌어야 하면 둘의 상태를 지우고 가장 가까운 공통 부모로 옮긴 뒤 props로 내려준다. 이걸 상태 끌어올리기(lifting state up)라고 부른다. 문서는 React 코드에서 가장 흔히 하게 되는 일 중 하나라고 한다.

문서의 아코디언 예제가 이해하기 좋았다. 패널마다 `isActive`를 따로 가지고 있으면 둘이 동시에 열릴 수 있다. 부모가 `activeIndex` 하나만 들고 있으면 "하나만 열림"이 구조상 보장된다. 문서도 끌어올리면 저장하는 값의 성격이 바뀌는 일이 많다고 적는다.

```js
const [activeIndex, setActiveIndex] = useState(0);
<Panel isActive={activeIndex === 0} onShow={() => setActiveIndex(0)} />
```

여기서 나오는 용어가 제어 컴포넌트와 비제어 컴포넌트다. 자기 상태로 움직이면 비제어, 중요한 값을 props로 받아 움직이면 제어다. 비제어는 쓰기 편하지만 다른 것과 맞추기 어렵고, 제어는 유연한 대신 부모가 다 설정해 줘야 한다. 문서는 이 구분이 엄격한 건 아니고 한 컴포넌트가 둘을 섞어도 된다고 한다.

그리고 원칙 하나. 값마다 그걸 소유하는 컴포넌트를 하나 정한다(single source of truth). 모든 상태를 한곳에 모으라는 뜻이 아니고, 같은 값을 두 군데 복사해 두지 말라는 뜻이다.

## 상태 모양 잡기

상태를 어디에 두는지만큼 어떤 모양으로 두는지도 버그를 가른다. React 문서의 "상태 구조 고르기"가 다섯 가지를 든다.

- 같이 바뀌는 값은 묶는다. `x`, `y`를 따로 두지 말고 `position` 하나로.
- 모순이 생기는 구조를 피한다. `isSending`, `isSent` 불리언 둘은 동시에 true가 될 수 있다. `status`에 `'typing' | 'sending' | 'sent'` 하나를 두면 그럴 수 없다.
- 계산할 수 있는 값은 저장하지 않는다. `fullName`은 `firstName + ' ' + lastName`으로 렌더링 때 만든다. props를 state로 복사해 두면 props가 바뀌어도 따라가지 않는다.
- 같은 데이터를 두 곳에 두지 않는다. `selectedItem` 객체 대신 `selectedId`를 두고 목록에서 찾는다.
- 깊게 중첩하지 않는다. 한 단계 고치려고 위 단계를 전부 복사해야 해서 번거롭고 틀리기 쉽다. id로 찾는 평평한 구조가 낫다.

다 같은 얘기를 한다. 상태를 최소로 두고 나머지는 계산하라는 것.

## 서버 상태는 따로 본다

서버에서 받아 온 데이터를 그냥 전역 스토어에 넣고 쓰는 방식을 한동안 많이 썼다. TanStack Query 문서는 이걸 다르게 본다. 서버 상태는 내가 소유하지 않는 원격 데이터이고, 읽고 쓰려면 비동기 API가 필요하고, 모르는 사이에 남이 바꿀 수 있고, 내 앱에서 낡을 수 있다고 정의한다. 그래서 로컬 상태용 라이브러리로는 맞지 않는다는 입장이다.

이 라이브러리가 맡는 일을 문서에서 옮기면 가져오기·캐싱·동기화·갱신, 같은 요청 합치기(중복 제거), 낡았는지 판단하고 백그라운드에서 다시 받기, 안 쓰는 데이터 정리, 페이지네이션이다. 직접 만들려면 꽤 큰 일들이다. 서버 상태를 이런 도구에 맡기면 전역 스토어에는 정말 클라이언트 쪽 값만 남아서 훨씬 작아진다. 이건 문서 내용을 읽고 정리한 이해이고, 실제 프로젝트에서 얼마나 줄어드는지는 직접 재 보지 못했다.

[자세히 → CSR·SSR·SSG](#/post/fe-rendering-modes)에서 보듯 렌더링 방식에 따라 서버 데이터가 처음부터 HTML에 실려 오기도 해서, 서버 상태를 어디서 받느냐도 같이 달라진다.

## 전역 상태 라이브러리는 언제

로컬에서 시작해 끌어올리다 보면 props를 여러 단계 넘겨야 하는 때가 온다. 그때 선택지는 대략 이렇다.

| 선택지 | 맞는 경우 |
|---|---|
| 그대로 끌어올리기 | 두세 단계 안에서 끝날 때 |
| Context | 테마·로그인 사용자처럼 자주 안 바뀌고 넓게 쓰는 값 |
| 외부 스토어(Redux, Zustand 등) | 많은 곳에서 자주 읽고 바꾸고, 갱신 범위를 좁히고 싶을 때 |
| 서버 상태 도구 | 원본이 서버에 있는 데이터 |

외부 스토어의 핵심은 의외로 작다. 값 하나, 읽는 함수, 바꾸는 함수, 구독자 목록이다. 아래 코드는 이 구조를 순수 JS로 만든 것이고 node로 직접 돌려 봤다.

```js
function createStore(init) {
  let s = init; const ls = new Set();
  return {
    get: () => s,
    set: (f) => { const n = f(s); if (Object.is(n, s)) return; s = n; ls.forEach(l => l()); },
    sub: (l) => { ls.add(l); return () => ls.delete(l); },
  };
}
const st = createStore({ count: 0 });
let calls = 0;
const un = st.sub(() => calls++);
st.set(s => ({ count: s.count + 1 }));  // 알림
st.set(s => s);                         // 같은 값이라 알림 없음
un();
st.set(s => ({ count: s.count + 1 }));  // 구독 해제 후라 알림 없음
console.log(st.get(), calls);           // { count: 2 } 1
```

값이 바뀌었을 때만 구독자에게 알리는 점이 중요하다. 라이브러리들이 불필요한 다시 그리기를 줄이는 방법이 이 부분의 발전형이다. [자세히 → 프런트엔드 성능](#/post/fe-performance)과 이어지는 얘기다.

## 흔한 오해

- 상태는 전부 전역에 두는 게 정리가 잘 된다: 문서의 방침은 반대다. 가까이 두고, 필요할 때 올린다.
- 서버에서 받은 데이터도 그냥 상태다: 낡을 수 있고 원본이 따로 있어서 관리 방식이 다르다.
- 라이브러리를 쓰면 설계가 해결된다: 중복·모순 있는 상태 모양은 어떤 라이브러리로도 안 고쳐진다.
- Redux가 표준이라 무조건 써야 한다: 선택지 중 하나일 뿐이고, 기준은 규모와 갱신 패턴이다.
