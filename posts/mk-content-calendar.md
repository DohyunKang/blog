콘텐츠 캘린더 자동화는 주제를 쌓아 두고, 날짜에 끼워 넣고, 때가 되면 올리는 세 단계로 나뉘었다. 이 중 사람이 꼭 봐야 하는 건 주제를 고르는 일과 올리기 직전의 확인이었다.

## 콘텐츠 캘린더가 뭔지

콘텐츠 캘린더는 "어느 날, 어느 채널에, 무슨 글을 올릴지"를 미리 적어 둔 표다. 엑셀 한 장이어도 된다. 표가 있으면 당일 아침에 "오늘 뭐 올리지" 하고 고민하는 일이 없어진다.

자동화는 이 표를 사람이 채우던 걸 일부 대신하는 것이다. 다만 한 덩어리가 아니라서, 나눠서 생각하는 게 편했다.

| 단계 | 하는 일 | 자동화 난이도 |
|---|---|---|
| 1. 주제 풀 | 올릴 만한 소재를 쌓아 둔다 | 모으기는 쉬움, 고르기는 사람 몫 |
| 2. 배치 | 소재를 날짜·요일·채널에 끼운다 | 규칙만 정하면 쉬움 |
| 3. 제작 | 글·이미지·영상을 만든다 | AI가 초안, 사람이 확인 |
| 4. 예약·게시 | 정해진 시간에 올린다 | 플랫폼 정책에 따라 다름 |
| 5. 기록 | 올렸는지, 반응이 어땠는지 적는다 | 쉬움 |

## 주제 풀

주제 풀은 아직 날짜가 안 붙은 소재 창고다. 한 줄씩 적고 상태(초안, 확정, 게시됨)를 붙여 둔다. 소재는 내가 평소 받는 질문, 지난 글의 반응, 시즌 일정에서 나온다. 트렌드를 자동으로 긁어 오는 건 따로 정리했다. [자세히 → 트렌드 수집 자동화](#/post/mk-trend-collect)

풀이 비면 캘린더가 멈추니까, 풀의 크기를 "앞으로 몇 주치가 남았나"로 재 두는 게 실용적이다. 4주치 밑으로 내려가면 알림을 받는 정도면 된다.

여기서 AI를 쓸 수 있는 곳은 소재를 늘리는 쪽이다. 주제 하나를 주고 "이 주제의 변형 10개"를 받는 식이다. 그런데 이렇게 나온 소재는 비슷비슷해지기 쉬워서, 내가 거르는 단계는 남겨야 한다. LLM이 다음 단어를 확률로 고르는 방식이라 평균적인 소재가 많이 나온다. [자세히 → LLM이란 무엇인가](#/post/ai-llm)

## 배치: 규칙으로 날짜에 끼우기

배치는 AI가 필요 없고 규칙이면 된다. 내가 쓴 규칙은 이 정도다.

- 일주일에 6개, 요일마다 유형을 고정한다(팁, 후기, 제품 소개 같은 기둥).
- 같은 주제는 최근 3개 안에 다시 안 나오게 한다.
- 풀이 다 떨어지면 다시 채우되 최근에 쓴 건 뺀다.

이걸 파이썬으로 직접 돌려 봤다. 주제는 예시로 커피 얘기 8개를 넣었다.

```python
from datetime import date, timedelta
import random

pool = ["커피 원두 고르는 법", "집에서 라테 만들기", "드립 vs 에스프레소", "원두 보관법",
        "디카페인 이야기", "그라인더 청소", "여름 아이스커피", "콜드브루 비율"]
slots = [(0, "팁"), (1, "후기"), (2, "팁"), (3, "제품"), (4, "후기"), (5, "팁")]  # 요일 0=월

def make_calendar(start, weeks, seed=1):
    rnd = random.Random(seed)
    topics = pool[:]
    rnd.shuffle(topics)
    cal, used = [], []
    for w in range(weeks):
        for dow, kind in slots:
            if not topics:                      # 풀이 비면 다시 채우되, 최근 3개는 뺀다
                topics = [x for x in pool if x not in used[-3:]]
                rnd.shuffle(topics)
            t = topics.pop()
            used.append(t)
            d = start + timedelta(days=7 * w + dow)
            cal.append({"date": d.isoformat(), "kind": kind, "topic": t, "status": "draft"})
    return cal

for r in make_calendar(date(2026, 11, 2), 2):
    print(r["date"], r["kind"], r["topic"], r["status"])
```

실행하면 2주치 12줄이 나왔다.

```

2026-11-03 후기 디카페인 이야기 draft
2026-11-04 팁 커피 원두 고르는 법 draft
2026-11-05 제품 콜드브루 비율 draft
2026-11-06 후기 그라인더 청소 draft
2026-11-07 팁 집에서 라테 만들기 draft
2026-11-09 팁 여름 아이스커피 draft
2026-11-10 후기 원두 보관법 draft
2026-11-11 팁 그라인더 청소 draft
2026-11-12 제품 콜드브루 비율 draft
2026-11-13 후기 커피 원두 고르는 법 draft

```

처음엔 풀이 비었을 때 쓴 목록을 그대로 다시 채웠더니 같은 주제가 이틀 연달아 나왔다. 위 코드는 그걸 고친 것이다. 이런 사소한 규칙 하나가 빠지면 캘린더가 바로 어색해졌다.

## 제작: 반복되는 흐름 만들기

캘린더의 각 줄이 "초안 → 검토 → 확정 → 게시됨"으로 상태가 바뀌게 두면 제작이 한 줄씩 흘러간다. 제작 단계에서는 AI에게 주제와 유형을 주고 초안을 받는다. 결과를 JSON 같은 정해진 모양으로 받으면 다음 단계(예약)에서 그대로 쓸 수 있다. [자세히 → 구조화 출력(JSON·스키마)](#/post/ai-structured-output)

짧은 영상이면 제작 파이프라인이 따로 있다. [자세히 → 숏폼 자동화 파이프라인](#/post/mk-shortform-pipeline)

초안이 쌓이는 속도가 올리는 속도보다 빠르면 검토가 병목이 된다. 자동화해도 마지막 확인은 사람이 맡는 걸로 잡았다.

## 예약과 게시

때가 되면 올리는 부분은 두 가지로 갈린다. 플랫폼이 예약 기능을 주는 경우와, 내가 시간에 맞춰 API를 호출하는 경우다.

공식 문서를 열어서 확인한 것만 적는다.

- Instagram(Meta) 콘텐츠 게시 API: 프로페셔널 계정이어야 하고, 두 단계로 올린다. 먼저 `/<IG_ID>/media`로 컨테이너를 만들고, 그다음 `/<IG_ID>/media_publish`로 게시한다. 미디어는 게시 시점에 공개된 주소에 있어야 한다. 24시간 동안 API로 올릴 수 있는 수는 100개라고 적혀 있는데, 같은 문서의 캐러셀 부분에는 50개라는 문장도 있어서 서로 어긋난다.
- YouTube Data API `videos.insert`: 요청 본문의 `status.publishAt`으로 공개 예약 시각을 줄 수 있다. 시각 형식은 이번에 읽은 페이지에 자세히 안 나왔다.

플랫폼마다 API의 허용 범위와 심사가 달라서, 캘린더에 "이 채널은 API 게시, 저 채널은 수동 게시"를 섞어 두는 경우가 흔할 것 같다. 모든 채널을 완전 자동으로 만들겠다는 생각은 접는 게 속 편했다.

## 반복 실행은 뭘로 돌리나

"매일 아침 9시에 그날 줄을 찾아서 올린다"를 돌리는 방법은 크게 세 가지다.

| 방법 | 특징 (문서에서 확인한 것) |
|---|---|
| n8n Schedule Trigger | 초·분·시·일·주·월 단위나 cron으로 설정. 워크플로를 저장하고 게시(publish)해야 켜진다. 시간대는 워크플로 설정, 없으면 인스턴스 시간대를 쓴다 |
| GitHub Actions `schedule` | cron 5칸, 최소 5분 간격. 부하가 크면 지연되거나 일부 작업이 버려질 수 있고, 기본 시간대는 UTC. 기본 브랜치에서만 돌고, 공개 저장소는 60일 동안 활동이 없으면 자동으로 꺼진다 |
| 내 컴퓨터의 작업 스케줄러 | 공짜지만 컴퓨터가 켜져 있어야 함 |

GitHub Actions의 "일부 작업이 버려질 수 있다"는 점이 눈에 띄었다. 정시에 꼭 올라가야 하는 일이라면 한 번 놓쳤을 때 다시 시도하는 장치가 있어야 한다. 이런 재시도와 대기열은 따로 정리했다. [자세히 → 비동기 처리와 메시지 큐](#/post/be-async-queue)

n8n 쪽도 놓친 실행을 어떻게 다룰지 정하는 설정(건너뛰기가 기본)이 있었다. 어느 쪽이든 "놓쳤을 때 어떻게 할지"를 미리 정해 두는 게 핵심이었다.

## 도구와 비용

비용은 두 군데서 난다. 제작할 때 쓰는 AI 호출비와, 돌리는 서버·도구 비용이다.

AI 호출비는 글 수 × (입력 토큰 + 출력 토큰) × 단가로 계산한다. 주 6개, 한 달 약 26개면 호출도 26번 안팎이라 작은 모델이어도 부담이 작다. 계산법은 따로 있다. [자세히 → AI 서비스 원가 구조](#/post/app-cost)

돌리는 쪽은 규모가 작으면 무료 구간(GitHub Actions의 스케줄이나 내 컴퓨터)으로 시작할 수 있다.

## 직접 만든다면

내가 만든다면 이 순서로 시작할 것 같다.

1. 스프레드시트 한 장에 주제 풀(주제, 유형, 상태)을 만든다.
2. 위 같은 배치 스크립트로 2~4주치를 채운다. 사람이 훑어보고 지운다.
3. 초안 생성은 AI에게 맡기고, 결과를 같은 표의 "초안" 칸에 넣는다.
4. 게시는 처음엔 수동으로 하고, 한 채널씩 API로 옮긴다.
5. 올린 뒤 조회·반응을 같은 표에 적어서, 다음 배치에 반영한다. [자세히 → 성과 대시보드 만들기](#/post/mk-dashboard)

## 흔한 오해

- 캘린더를 자동화하면 콘텐츠도 저절로 좋아진다: 자동화는 올리는 일을 줄여 줄 뿐, 소재의 질은 그대로다.
- 예약 기능이 있으면 완전 자동이다: 심사, 토큰 만료, 게시 실패 같은 예외가 남는다.
- 많이 올릴수록 좋다: 검토 시간이 병목이면 양을 늘리는 것보다 주 몇 개를 확실히 올리는 쪽이 오래 간다.

<details>
<summary>자세한 풀이: 상태 값과 실패 처리</summary>

캘린더 한 줄에 상태 열을 두면 실패 처리가 쉬워진다. 예를 들어 `draft → approved → scheduled → posted`로 가고, 중간에 실패하면 `failed`와 실패 이유를 적는다. 아침 실행기는 오늘 날짜이면서 `approved`인 줄만 가져와 올리고, 성공하면 `posted`로 바꾼다. 같은 줄을 두 번 올리지 않으려면 올리기 전에 `scheduled`로 바꿔 잠그는 식으로 중복을 막는다.

실행기가 하루 놓쳤을 때를 대비하려면 "오늘 이전 날짜인데 아직 approved인 줄"도 같이 찾아서 알림을 보내면 된다. 자동으로 늦게라도 올릴지는 채널 성격에 따라 정하는 게 맞다. 이 부분은 설계 이야기고, 실제로 돌려 보지는 않았다.
