オートスケーリングは、負荷に合わせてサーバーの数やサイズを自動的に変更する仕組みであり、それを適切に運用するためには「何を指標にするか」と「サーバーがステート（状態）を保持していないか」がまず重要でした。

## 拡張とは何か

サービスに人が集まってくると、一台のサーバーでは足りなくなります。この際、増やす方法は二つあります。

| | 垂直スケーリング (scale up) | 水平スケーリング (scale out) |
|---|---|---|
| 方法 | サーバーをより大きなものに取り替える | 同じサーバーを複数台増やす |
| 利点 | コードをほとんど修正しなくて済む | 限界は事実上なく、一台が落ちても耐えられる |
| 欠点 | 上げられるサイズに天井があり、取り替え時に停止が必要になる | リクエストを分担する仕組みが必要で、サーバー間でステートを同期させる必要がある |

「オートスケーリング」と言った場合、通常は水平方向を指します。サーバーを一台増やすのは自動化が容易であり、サイズ変更は再起動が伴うためです。リクエストを複数台に分担する部分は [詳細 → ロードバランサー](#/post/infra-load-balancer) に別途まとめました。

## 「自動で増やす」とは何か

人がダッシュボードを見てサーバーを追加することを機械が代行することです。手順はいつも同じです。

1. 指標を計測する（CPU、リクエスト数など）。
2. 目標値と比較する。
3. 不足していればサーバーを増やし、余っていれば減らす。

AWS の target tracking ドキュメントでは、これを温度調節器に例えています。目標平均 CPU を 50% に設定しておき、それを超えたら増やし、下がったら減らします。ドキュメントの基準では、この方式は CloudWatch アラームをサービスが代わりに作成・管理します。

Kubernetes の HPA (Horizontal Pod Autoscaler) も同じ発想です。公式ドキュメントにある計算式は以下の通りです。

```
원하는 개수 = ceil[ 현재 개수 × (현재 지표값 / 목표 지표값) ]
```

現在 4 つありますが、平均 CPU が 90% で目標が 50% なら 4 × 1.8 = 7.2 となり、切り上げて 8 つになります。HPA は基本的な間隔として 15 秒ごとにこの計算を行うとドキュメントに書かれています。

<details>
<summary>詳しい解説：計算式を自分で動かしてみた</summary>

式の感覚が掴めず、Python に移植して動かしてみました。tol は「目標とほぼ同じならそのままにする」という余裕の区間であり、0.1 は私が設定した値です。

```python
import math

def desired(cur, metric, target, tol=0.1):
    r = metric / target
    if abs(r - 1) <= tol:      # 목표 근처면 그대로
        return cur
    return math.ceil(cur * r)

print(desired(4, 90, 50))   # 8  (7.2를 올림)
print(desired(4, 52, 50))   # 4  (여유 구간 안이라 유지)
print(desired(10, 20, 50))  # 4  (줄이는 쪽도 같은 식)
print(desired(1, 60, 50))   # 2
```

実行結果は 8, 4, 4, 2 でした。切り上げを使うため、「少し不足している」場合でも一台増えます。不足する方向に誤るよりも、余っている方向に誤る方がよいという方針です。

</details>

## 何を基準にして増やすか

スケーリングに関する記事で最も詰まりやすいのが指標の選び方でした。

- CPU 使用率：最も一般的です。計算が多いサーバーには適していますが、大半は外部応答を待っているサーバーでは CPU が上がらずに遅くなることがあります。
- リクエスト数（一台あたり）：Web サービスでは直感的です。AWS にもロードバランサーターゲットあたりのリクエスト数 (`ALBRequestCountPerTarget`) という基本指標があります。
- キューの長さ：バックグラウンドで処理を行うワーカーに適しています。AWS ドキュメントでは SQS キューに蓄積されたメッセージ数をそのまま使うのではなく、サーバー一台あたりのメッセージ数に変えて使うよう指示しています。サーバーを増やしてもキューの長さがそれに比例して減るわけではないためです。キューに関する話は [詳細 → 非同期処理とメッセージキュー](#/post/be-async-queue) にあります。
- レイテンシ（遅延時間）：遅くなることを直接見ることができますが、ドキュメントでは target tracking で使うべきではない指標として挙げられています。サーバーが忙しくなるほど増えますが、サーバー数に比例して変化しないためです。

AWS ドキュメントの基準を私の言葉でまとめると、「サーバーが増えるにつれて指標値が比例して下がる必要があります」となります。そのため、ロードバランサーの全体的なリクエスト数はサーバーを増やしても変わらないため不適切です。

Kubernetes で CPU 使用率を目標として使うには、コンテナに `requests` が設定されている必要があるとドキュメントにあります。リクエスト値がないと使用率を計算できず、HPA はその指標では何も行いません。これを忘れると「なぜ増えないのか？」としばらく悩むことになるでしょう。

## 増やすことよりも減らす方が注意が必要です

サーバーが起動するには時間がかかります。その間、指標は依然として高く、「もっと増やさなければならない」と判断されてしまう可能性があります。すると必要以上に多く立ち上がってしまいます。

AWS はこれを warmup（予熱）時間として扱います。新しいサーバーが予熱を完了するまで、そのサーバーの指標を集計に含めず、この期間中は減らす動作も禁止します。ドキュメントの表現では、「増え続けるが過剰には増やさない」ことが目的です。

減らす際も同様です。ドキュメントでは target tracking が減らす際はよりゆっくり行い、切り上げも保守的に行うと述べています。サーバーを一台減らしたら負荷がすぐに目標を超えて再び増えるような上下動を避けるためです。小さなグループではこの影響が大きいです。

<details>
<summary>詳しい解説：小さなグループが目標から遠く見える理由</summary>

AWS のドキュメントには、「サーバー数が少ない場合、実際の使用率が目標値とかなり乖離して見える」という記述があり、数値を調整してみました。総負荷を「1 サーバー基準の 60% を持つ 2 台分（合計 120）」とし、目標を 50% と設定しました。

- サーバー 2 台グループ：120 / 50 = 2.4 → 3 台になります。3 台に分割するとサーバーあたり 40% となり、目標と 10%p の差があります。
- サーバー 20 台グループ：負荷合計 1200 / 50 = 24 台。サーバーあたり正確に 50% です。

1 台単位でのみ動作させる必要があるため、サーバー数が少ないほど丸め上げの影響が大きくなります。大きなグループでは 1 台が占める割合が小さいため、目標値によく沿います。

</details>

## サーバーの状態を保持すると困る理由

ここがこの記事で最も重要な部分です。サーバーを適当に起動・停止する際、どのサーバーが消えてもサービスは継続する必要があります。

ログイン情報（セッション）をサーバーのメモリに保持していると仮定しましょう。リクエストが A サーバーから B サーバーへ移動すると、B はそのユーザーを認識しません。削減操作の瞬間に A が消えると、そのユーザーはログアウトされます。そのため、サーバーは状態を持たない（stateless）ように作り、状態は外部に置きます。

| 状態の種類 | 外部に置く場所 |
|---|---|
| セッション、一時値 | 共有キャッシュ（例：Redis）→ [詳細 → キャッシュと Redis](#/post/db-cache-redis) |
| ユーザーデータ | データベース |
| アップロードファイル | オブジェクトストレージ |
| 処理待ちタスク | メッセージキュー |

このようにすることで、サーバーはコードのみを持つ複製機となり、何台になっても同じです。新規起動すれば即座に作業を開始し、消えても損失はありません。認証をサーバー上のセッションにするかトークンにするかは、[詳細 → 認証と認可](#/post/be-auth) で扱います。

## サーバー以外で DB はどうするか

サーバーは容易に拡張できますが、データベースはそうではありません。サーバーを 8 台増やしてもすべて同じ DB を参照するため、ボトルネックは DB に移ります。読み取りレプリカ、シャッディングなどの方法は、[詳細 → データベースのスケーリング](#/post/db-scaling) で別途整理しています。オートスケーリングを適用する前に、「拡張されたサーバーが DB を何個の接続で叩くか」を事前に計算しておく必要があることは、今回の整理で確定した確認項目です。

## よくある誤解

- オートスケーリングを有効にすれば暴走トラフィックもすべて受けられる：サーバー起動に時間がかかるため、急激な増加には遅れます。そのため、最小台数を十分に設定するか、事前に予約しておく方式を別途採用します。ただしこの点は、ドキュメントで直接確認したわけではなく、前述の warmup 説明から連想して考えたものです。
- 増やすだけならよい：削減設定がないとコストが継続して発生します。逆に、最小台数を 0 に設定すれば、リクエストがない場合のみ 0 まで低下するという記述は AWS ドキュメントにあります。
- サーバーを増やせば速くなる：ボトルネックが DB や外部 API にある場合、サーバーを増やしても改善しません。
- 指標は何でもよい：サーバー数に比例して変化する指標である必要があります。
- リクエストが多くなれば 429 で遮断すればよい：遮断と拡張は別の防御ラインです。併用します。→ [詳細 → レートリミット](#/post/infra-rate-limit)
