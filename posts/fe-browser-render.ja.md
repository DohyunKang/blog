ブラウザは HTML と CSS を受け取り、DOM、CSSOM、レンダリングツリー、レイアウト、ペイントの順序で画面を構築します。このプロセスのうちどの段階が再計算されるかが、画面変更のコストを決定づけます。

## アドレスを入力した後

画面を描画する前にまず HTML を受け取る必要があります。MDN ドキュメントを基準にすると、手順は以下の通りです。ホスト名を IP へ変換するため DNS を経由し、TCP 接続を確立（3-way handshake）、HTTPS の場合は TLS 交渉を行います。次に HTTP GET を送信し、最初の HTML フラグメントが到着した時点から解析を開始します。最初のパケットが到着するまでの時間を TTFB と呼びます。この前半部分はネットワークの話であり、[詳細 → ネットワーク](#/post/cs-network) に別途記載されています。ここでは HTML の最初のフラグメントが到着した後から見ていきます。

## 全体の流れ

| ステップ | 行うこと | 結果物 |
|---|---|---|
| 解析 (HTML) | テキストをトークンに分割しノードツリーを作成する | DOM |
| 解析 (CSS) | ルールを一般→具体的の順に積み重ねてツリーを作成する | CSSOM |
| スタイル合成 | DOM と CSSOM を組み合わせ、表示されるノードのみを選択する | レンダリングツリー |
| レイアウト | 各ボックスの位置と大きさを計算する | ボックスモデル |
| ペイント | ボックスをピクセルとして描画する（文字、色、枠線、影） | レイヤーごとのビットマップ |
| 合成 | レイヤーを重ねて画面に配置する | 画面 |

このうち最初の 5 つのステップがいわゆるクリティカル・レンダリング・パスです。web.dev のドキュメントでは、この経路の最適化について「これらの段階で消費する時間を減らすこと」と説明しています。

## DOM と CSSOM

HTML はトークンに分割され、`<html>` をルートとするノードツリーとなります。これが DOM です。CSS も独立したツリーになりますが、これを CSSOM といいます。ブラウザのデフォルトスタイルシートから始まり、一般的なルールから具体的なルールへと上書きされていく構造であるため「ツリー」と呼ばれます。

両者は別々のオブジェクトです。DOM はコンテンツが何なのかを、CSSOM はそのコンテンツにどのようなスタイルルールが適用されるかを保持します。そのため HTML だけであれば DOM を作成できますが、画面に描画するには両者が合流する必要があります。

解析中に `<script>` に遭遇すると事情が変わります。MDN ドキュメントによると、`async` または `defer` が指定されていないスクリプトはダウンロードおよび実行の間、HTML の解析を停止します。CSS は HTML の解析を停止させませんが、計算されたスタイルを読み取る JavaScript はブロックされます。そのためスクリプトには通常 `defer` を付与するか、ドキュメントの末尾に配置します。

```html
<!-- 파싱을 멈추고 내려받아 실행 -->
<script src="a.js"></script>
<!-- 병렬로 내려받고, 끝나는 대로 실행(순서 보장 없음) -->
<script src="b.js" async></script>
<!-- 병렬로 내려받고, 파싱이 끝난 뒤 문서 순서대로 실행 -->
<script src="c.js" defer></script>
```

なお、パサーの後方ではプリロード・スキャナーが先行して動き、CSS、JS、フォント、画像を事前に読み込んでおきます。解析がスクリプトによって止まってもダウンロードはそれ以前から開始されます。

## レンダリングツリー

DOM と CSSOM を合成するとレンダリングツリーとなります。ルートから始めて画面に表示されるノードのみを訪問し、適用する CSS ルールを付与して、計算されたスタイルを持つノードとして出力します。

表示されないノードは除外されます。<head>、<script>、<meta> などの要素や `display: none` の属性を持つ要素が該当します。ここでよく混同されるのが `visibility: hidden` です。これはレンダリングツリーに残ります。スペースを占有するだけで非表示に過ぎません。一方 `display: none` はレンダリングツリーから除外されるため、レイアウトにも参加しません。

## レイアウト

レンダリングツリーをルートから巡回しながら、各要素の正確な位置と大きさをビューポート基準で計算します。パーセントなどの相対値がピクセルに変換される段階です。web.dev の例示は直感的に理解しやすいものです。親がビューポートの 50% で、その中の子が親の 50% なら、子はビューポート幅の 25% となります。

最初に行う計算をレイアウトと呼び、その後再び計算を行うことをリフローと呼びます（MDN）。同じ計算ですが、タイミングによって名称が異なります。

## ペイントと合成

レイアウトが終わるとボックスをピクセルに変換します。文字、色、枠線、影、画像がこの時点で描画されます。スタイルによってコストは異なります。web.dev では単色は安価だがドロップシャドウは計算が高価であると記載しています。

その後、合成の段階があります。`opacity`、3D `transform`、`will-change` が適用された要素や `<video>`、`<canvas>` は独立したレイヤーとして昇格し、GPU で合成可能です。レイヤーを分割しておけば 1 つのレイヤーのみを再描画できますが、レイヤーはメモリを使用するため乱用すべきではないと MDN は述べています。スタイル、レイアウト、ペイントを含めたメインスレッドでの作業が 16.67ms 以内で完了することが、スクロールやアニメーションが滑らかになる基準として同じドキュメントに登場します。

## リフローとリペイント

DOM や CSSOM が変更されると、ブラウザはこのプロセスの一部を再度実行し、どのピクセルを再描画すべきか決定します。この 2 つの用語を分けてみると以下のようになります。

| | Reflow | Repaint |
|---|---|---|
| 뜻 | 크기와 위치를 다시 계산 | 모양만 다시 그림 |
| 지오메트리 | 바뀜 | 안 바뀜 |
| 뒤따르는 단계 | 리페인트와 합성까지 | 해당 레이어의 페인트·합성 |
| 예 | 요소 추가·삭제, 너비·글자 크기 변경 | 배경색, 글자색 변경 |

MDN によると、リフローが発生するとリペイントと再合成が引き起こされるとのことです。そのため、リフローの方がコストが高いのです。上記の表の例は、「ジオメトリが変わるか」という定義から導き出されたものであり、どの属性が正確にどちらに該当するかという全体的なリストについては、MDN もこの文書では提示していません。リストが必要な場合は別途調べる必要があります。

MDN が挙げる実際の事例の一つに画像があります。<img> タグを `width` と `height` を指定せずに配置すると、まず画像なしでレイアウトが行われ、画像が読み込まれて実際のサイズが判明した時点でレイアウトからやり直す必要があります。属性で事前にサイズを指定しておけば位置が確定するため、リフローは不要です。

```html
<!-- 크기 없음: 로딩되면 리플로우 -->
<img src="a.jpg" alt="설명">
<!-- 크기 있음: 자리가 미리 잡힘 -->
<img src="a.jpg" alt="설명" width="800" height="600">
```

## よくある誤解

- レンダーツリーとは DOM と同じだ: 違う。レンダーツリーは DOM から非表示のものを取り除き、計算されたスタイルを付与したものです。
- `display: none` と `visibility: hidden` は同じだ: 前者はレンダーツリーから除外され、後者は位置を保ったまま残ります。
- CSS はパースとは無関係だ: HTML のパースを防ぐわけではありませんが、スタイルを読み取るスクリプトはブロックし、レンダーツリー自体の作成には CSSOM が必要です。
- 画面が表示されたらすべて完了だ: MDN によると、画面がロードされたように見えてもメインスレッドが大きなスクリプトで忙殺されていれば、スクロールやタブへの反応がない場合があります。これを表す指標が TTI です。
- サイズを変えなければコストはゼロだ: 色を変えるだけでもリペイントは発生します。ただしリフローよりも安いです。

パフォーマンスに関する話は [詳細 → フロントエンド性能](#/post/fe-performance) で、サーバーで HTML を生成して送信するかブラウザが生成するかの問題は [詳細 → レンダリング方式](#/post/fe-rendering-modes) で続きます。

<details>
<summary>詳しい解説：JS で回す場合をコードで見る</summary>

概念として知っているのと違い、コードでは読み書きが混ざると同じことが複数回発生する可能性があります。この部分は一般的に知られているパターンです。

```js
const items = document.querySelectorAll('.item');

// 읽기와 쓰기를 번갈아 하는 경우
items.forEach((el) => {
  const w = el.offsetWidth;      // 레이아웃 값을 읽음
  el.style.width = (w + 10) + 'px'; // 레이아웃이 바뀜
});

// 읽기를 먼저 몰아서 하고, 쓰기를 나중에 하는 경우
const widths = [...items].map((el) => el.offsetWidth);
items.forEach((el, i) => {
  el.style.width = (widths[i] + 10) + 'px';
});
```

最初の方式は値を読み取るたびにブラウザが最新のレイアウトに合わせてくれるため、レイアウトが繰り返される可能性があります。二つ目の方式是読み取りをまとめてその回数を減らす方式です。

</details>
