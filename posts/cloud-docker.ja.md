Docker 는 앱과 그 앱이 실행되는 데 필요한 파일들을 묶어서 "컨테이너"라는 격리된 프로세스로 실행하게 해주는 도구입니다. 내 PC 에서 작동하던 것이 서버에서는 안 되는 문제를 줄이기 위해 사용합니다.

## 먼저 쉬운 말로

앱을 서버에 올리면 자주 이런 일이 발생합니다. 내 컴퓨터는 Python 3.12 인데 서버는 3.8 이거나, 라이브러리 버전이 달라서 작동하지 않습니다. Docker 문서에서는 이를 이렇게 해결합니다. 앱을 "느슨하게 격리된 환경"인 컨테이너에 담아, 앱이 호스트에 어떤 것이 설치되어 있는지에 의존하지 않게 합니다.

비유하자면 이삿짐 컨테이너와 같습니다. 짐 (앱) 과 그 안의 가구 (라이브러리, 런타임) 를 통째로 상자에 넣고 옮기니까, 도착한 곳이 어떤 집이든 상자 안은 그대로입니다. 다만 이는 비유일 뿐, 실제로는 상자가 컴퓨터를 하나 더 흉내 내는 것은 아닙니다. 그 이야기는 아래 가상머신 부분에서 합니다.

## 이미지와 컨테이너

용어가 두 가지 나오다 보니 처음에 가장 헷갈렸습니다.

| | 이미지 (image) | 컨테이너 (container) |
|---|---|---|
| 정체 | 읽기 전용 템플릿 | 이미지를 실제로 실행한 것 |
| 비유 | 레시피, 설치 파일 | 그 레시피로 만든 요리, 실행 중인 프로그램 |
| 바뀌나 | 안 바뀐다 | 돌면서 파일이 바뀔 수 있다 |
| 개수 | 하나 | 한 이미지로 여러 개 |

Docker 문서 표현으로 이미지는 "컨테이너를 만드는 지침이 담긴 읽기 전용 템플릿"이고, 컨테이너는 "이미지의 실행 가능한 인스턴스"입니다. 클래스와 객체 관계로 보면 쉽습니다. 이미지가 클래스고 컨테이너가 인스턴스입니다.

컨테이너 안에서 변경된 내용은 영구 저장소 (볼륨 등) 에 따로 저장하지 않으면 컨테이너를 지울 때 함께 사라집니다. 그래서 DB 같은 것을 컨테이너에 넣을 땐 데이터를 어디에 둘지부터 정해야 합니다.

## 이미지는 층 (layer) 으로 쌓인다

이미지는 한 덩어리가 아니라 여러 층이 겹친 구조입니다. 문서의 예시는 다섯 층입니다. 기본 명령과 패키지 관리자, Python 런타임, 요구사항 파일, 설치한 라이브러리, 마지막으로 내 소스 코드입니다.

- 한 번 만든 층은 바뀌지 않습니다 (immutable).
- 컨테이너가 실행되면서 생기는 변경 사항은 그 컨테이너만의 별도 디렉터리에 쌓여서, 원래 이미지 층은 그대로입니다. 그래서 한 이미지로 여러 개의 컨테이너를 띄울 수 있습니다.
- 층은 이미지끼리 공유됩니다. 같은 Python 베이스 층을 쓰는 앱 두 개는 그 층을 한 번만 받으면 됩니다. 문서에서는 이것이 빌드 속도와 저장 공간, 전송량을 줄여준다고 합니다.

내려받은 각 층은 호스트에서 각각 디렉터리로 풀리고, union 파일시스템이 이를 하나로 겹쳐 보여줍니다. 컨테이너의 루트 디렉터리는 그 겹친 결과를 가리킵니다.

## Dockerfile: 이미지를 만드는 설계도

이미지를 만드는 방법을 적은 텍스트 파일이 Dockerfile 입니다. 직접 만들어서 돌려보았습니다.

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]
```

`app.py` 는 한 줄짜리입니다.

```python
import platform
print("hello from container:", platform.system())
```

각 줄은 이렇게 읽습니다.

- `FROM`: 어떤 이미지 위에서 시작할지. 여기선 공식 Python 이미지 (slim) 를 베이스로 사용합니다.
- `WORKDIR`: 이후 명령이 실행될 작업 폴더.
- `COPY`: 내 PC 의 파일을 이미지 안으로 복사합니다.
- `CMD`: 컨테이너를 켰을 때 기본으로 실행할 명령입니다.

빌드하고 실행하는 명령은 다음과 같습니다.

```bash
docker build -t blog-hello .
docker run --rm blog-hello
```

내 PC(Windows) 에서 돌린 결과입니다.

```
hello from container: Linux
```

Windows PC 에서 실행했는데 컨테이너 안은 Linux 로 나왔습니다. 컨테이너가 자기만의 파일시스템과 환경을 가지고 있다는 것을 눈으로 본 셈입니다. 이유는 아래에서 설명합니다. (이 PC 에서는 Docker Desktop 으로 돌렸습니다.)

`docker image history blog-hello`로 층을 보면 내가 쓴 줄들이 위쪽에 보입니다.

```
CMD ["python" "app.py"]
COPY app.py . # buildkit
WORKDIR /app
CMD ["python3"]
RUN /bin/sh -c set -eux; ...   (베이스 이미지의 층들)
ENV PYTHON_VERSION=3.12.16
```

내 Dockerfile 세 줄 (`WORKDIR`, `COPY`, `CMD`) 아래에 Python 공식 이미지가 쌓아둔 층들이 이어집니다. 내 코드 층만 바뀌면 아래 베이스 층은 다시 받을 필요가 없습니다. 문서도 이미지를 다시 빌드하면 바뀐 층만 새로 만든다고 적습니다.

## 가상머신과 뭐가 다른가

둘 다 "격리된 환경"이라서 같은 것으로 보기 쉽습니다. 차이는 커널입니다.

| | 가상머신 (VM) | 컨테이너 |
|---|---|---|
| 안에 든 것 | 운영체제 전체 (커널·드라이버 포함) + 앱 | 앱에 필요한 파일 |
| 커널 | VM 마다 따로 | 호스트 커널을 같이 씀 |
| 무게 | 무거움 | 가벼움 (프로세스에 가깝다) |
| 같은 서버에 | 적게 | 더 많이 |

Docker 문서는 VM 을 앱 하나를 격리하려고 쓰면 "오버헤드가 크다"고 하고, 컨테이너는 호스트 커널을 공유해서 같은 인프라에 더 많은 앱을 돌릴 수 있다고 설명합니다. 같은 페이지에서, 둘은 같이 쓰이기도 한다고 합니다. 클라우드에서는 VM 위에 컨테이너 런타임을 올려서 여러 개의 컨테이너를 돌리는 식입니다.

したがって、上記の「Windows なのに Linux で動作する」理由もここにある。コンテナはホストカーネルを使用するため、Linux コンテナには Linux カーネルが必要である。Windows や Mac で Docker Desktop を使用する場合、内部に Linux 環境（仮想化）が一つ走り、その上でコンテナが動作すると知られている。

隔離は Linux カーネル機能によって行われる。文書によると、Docker は namespace などの機能を使って各コンテナごとに隔離された作業空間を作成し、コンテナの各側面は別の namespace で動作し、その内部からのみアクセスが可能と制限される。

## Docker の構成

コマンドを実行する際、実際に誰が何をしているかも整理しておく。文書に基づいたものである。

| 構成要素 | 役割 |
|---|---|
| クライアント (`docker`) | 私たちが実行するコマンドラインツール。コマンドをデーモンに送信する |
| デーモン (`dockerd`) | バックグラウンドでイメージ、コンテナ、ネットワーク、ボリュームを実際に管理する |
| レジストリ | イメージを保存しておく場所。デフォルトの公開レジストリは Docker Hub |

`docker run` を実行すると、クライアントがデーモンにリクエストを送り、ローカルにイメージがない場合はレジストリから取得する。クライアントとデーモンは REST API で通信する（UNIX ソケットまたはネットワーク経由）。

## よくある誤解

- コンテナは小さな仮想マシンである：違う。独自のカーネルを持っておらず、ホストカーネルを使用する。プロセスを隔離したものに近い。
- イメージとコンテナは同じ意味：イメージはテンプレートであり、コンテナは実行中の状態である。一つのイメージから複数のコンテナを起動できる。
- コンテナ内に保存したファイルは残る：ボリュームなどの永続化ストレージに置かない場合、コンテナを削除すると消えてしまう。
- Docker ならセキュリティは自動で OK：隔離されるのは正しいが、設定やイメージのソースによって異なる。

<details>
<summary>詳しい解説：層を重ねる様子を手作業で見ると</summary>

Docker の文書の層チュートリアルでは `Dockerfile` を使わずに手動で層を作成する。Ubuntu コンテナに Node.js をインストールし、`docker container commit` で保存すると `node-base` という層になり、そこに `app.js` を入れて再度 commit すると `app` という層になる。`docker image history` を実行すると、各層の commit 時に使ったメモ（"Add node", "Add app"）が表示される。

Dockerfile はこのプロセスを自動化してくれると文書にある。行ごとに層が一つずつ生成されるとの説明は、今回読んだ文書のページには明記されていなかった。ただし上記で `docker image history` を使って自分の Dockerfile の `WORKDIR`、`COPY`、`CMD` がそれぞれ一行ずつ表示されたことは直接確認した（`CMD` や `WORKDIR` などの設定行はサイズ 0 の層として現れると知られているが、実際にはサイズを確認しなかった）。

</details>

<details>
<summary>詳しい解説：この記事で実際に試したもの</summary>

環境は Docker 29.8.2（Windows）。一時フォルダに `app.py` と `Dockerfile` を作成し、`docker build` および `docker run --rm` を実行した。出力は本文の結果と一致する。ベースイメージは `python:3.12-slim` を新規に取得し、イメージ履歴で Python 3.12.16 が表示された。実行後に作成したイメージは削除した。

</details>
