インデックスはテーブルとは独立して値をソートした構造体であるため、条件に一致する行を最初から順にスキャンせず、即座に見つけることができます。その代わり、書き込むたびに更新する必要があり、無料ではありません。

## インデックスとは何か

テーブルで `WHERE email = '...'` といった条件で一行を見つける場合を考えましょう。インデックスがない場合、データベースは最初の行から最後の行まで全て読み取ります。これはフルスキャンです。行数が 10 件であれば問題ありませんが、20 万件や 2,000 万件になると話は変わってきます。

インデックスは本の末尾にある索引（目次）に似ています。単語を五十音順でソートし、隣にページ番号を記しておくものです。SQLite のドキュメントも同様に説明しています。インデックスとは、索引対象の列の値と元の行の rowid をソートされた順序で格納した別々の構造体であり、値が同じ場合は rowid で順序を決定します。ソートされているためバイナリサーチが可能となり、検索時間は行数 N に比例するのではなく log N に比例します。ドキュメントでは 1,000 万行のテーブルにおけるこの差は約 100 万倍であると推計しています。

[詳細 → 関係型 DB と SQL の基礎](#/post/db-rdb-sql) でテーブルやキーの話を読んでおくと、この記事がより理解しやすくなります。主キー（primary key）は多くのデータベースでインデックスが自動的に付与されると知られていますが、実装はデータベースによって異なるため、使用するデータベースのドキュメントを確認する必要があります。

## B-Tree はどのような構造か

インデックス構造として最も一般的なものは B-Tree です。「Use The Index, Luke」はインデックスを「二重連結リスト + 検索ツリー」の組み合わせとして紹介しています。最下層（リーフ）にはソートされたインデックス項目が連続して連結されており、その上に「この範囲はこの方向」と案内する階層が積み重なっています。バランスツリーであるため、どの値を検索しても上から下へ降りる深さは同じです。

直感的なイメージは以下の通りです。

```
        [ 50 | 100 ]              <- 루트: 어느 구간인지만 알려 줌
       /     |     \
 [10|30]  [60|80]  [120|150]      <- 중간층
   |        |         |
 리프: 10 20 30 | 55 60 70 80 | 120 130 150 ...  (정렬된 채로 서로 연결)
```

61 を探す場合、ルートで「50 と 100 の間」、中間層で「60〜80 の範囲」、リーフで「61 の付近」というように降りていきます。3 回降りれば終了です。一つのノードに格納できる項目が多いほど階数は浅くなります。例えば、一つのノードに 100 件とすると、3 階だけで 100 万件のリーフを指し示すことができます（単なる計算であり、実際のデータベースの数字ではありません）。データが 1,000 倍増えたとしても、階数は 1〜2 つ増える程度というのがポイントです。

リーフ同士が連結されておりソートされているため、範囲検索（`BETWEEN`）やソート（`ORDER BY`）にもこの構造が役立ちます。起点を見つけ、その後横に順に読み進められるからです。

<details>
<summary>詳細な解説：1 件を検出するコストと複数件を検出するコスト</summary>

SQLite のドキュメントの説明に従えば、インデックスで一行を見つけるにはバイナリサーチが 2 回必要です。インデックスで rowid を見つけること、そしてその rowid で元のテーブルから行を見つけることです。条件に一致する行が K 件ある場合、コストはおよそ (K+1)·log N です。最初の件は探索で見つけ、残りはインデックスから次の項目へ移動して読み取るためです。

したがって K が大きくなりテーブルの大部分を占めるようになると状況が変わります。インデックスを使って 1 件ずつテーブルを行き来するよりも、まるごとスキャンした方が有利になることもあり、データベースは統計情報を基にその方を選択することもあります。この選択基準の正確な計算式はデータベースによって異なります。

</details>

## 実際に試してみた

SQLite(3.50.4) でユーザーテーブルに 20 万行を挿入し、1 つのエメールアドレスを検索しました。すべてのエメールアドレスは異なり、都市と年齢はランダムです。

```python
import sqlite3, random, time
c = sqlite3.connect(':memory:')
c.execute("create table users(id integer primary key, email text, city text, age int)")
random.seed(1)
cities = ['서울','부산','대구','인천','광주']
c.executemany("insert into users(email,city,age) values(?,?,?)",
    [(f"u{i}@ex.com", random.choice(cities), random.randint(18,70)) for i in range(200000)])

q = "select * from users where email='u123456@ex.com'"
for r in c.execute("explain query plan " + q): print(r[3])
c.execute("create index idx_email on users(email)")
for r in c.execute("explain query plan " + q): print(r[3])
```

結果は以下の通りでした。

| | 実行計画 | 経過時間（1 回測定） |
|---|---|---|
| インデックス前 | `SCAN users` | 約 4.17ms |
| インデックス後 | `SEARCH users USING INDEX idx_email (email=?)` | 約 0.019ms |

一度しか計測していないため正確な倍率は意味がなく、フルスキャンからインデックス探索に変更されたことと、時間が 2 桁以上減少したことを確認すれば十分です。コンピュータによって異なります。

## 実行計画で確認する

上記のコードでは `explain query plan` が実行計画を表示しました。インデックスを作成してもクエリが必ずそれを使うとは限らないため、作成後に計画を確認する癖をつける必要があります。

PostgreSQL のドキュメントを基準にすると、`EXPLAIN` はクエリを実行せず、データベースが選択した計画を表示します。読み取り時に目につく項目は以下の通りです。

- `Seq Scan`: テーブル全体を読み取る（SQLite では `SCAN`）。
- `Index Scan`: インデックスで見つけ、その後テーブルから行を取得する。選択度が高い条件では主に選択されるとドキュメントに記載されています。
- `cost`: 開始コストと全体的なコストで、単位は任意です。時間 (ms) ではありません。
- `rows`: その段階で出力すると推定される行数です。推定であるため誤る可能性があります。

`EXPLAIN ANALYZE` 는 쿼리를 실제로 실행하여 실제 소요 시간과 실제 행 수를 함께 보여줍니다. 추정 행 수와 실제 행 수가 크게 어긋난다면 통계 정보가 낡았다는 신호로 해석된다고 합니다. 실제로 실행해보니 `UPDATE` 나 `DELETE` 를 사용할 때는 `BEGIN`/`ROLLBACK` 으로 감싸야 한다고 문서에 나와 있습니다. 저는 PostgreSQL 을 직접 구동하지는 않았으며, 이 부분은 문서만 참고했습니다.

## 인덱스가 도움이 안 되는 경우

같은 테이블의 여러 쿼리 실행 계획을 확인해 보았습니다. 이메일 인덱스는 이미 존재하는 상태입니다.

| 쿼리 | 실행 계획 |
|---|---|
| `email = 'u123456@ex.com'` | 인덱스 탐색 |
| `email like '%123456@ex.com'` | `SCAN users` (풀 스캔) |
| `lower(email) = '...'` | `SCAN users` (풀 스캔) |

앞에 와일드카드가 있는 `LIKE '%...'` 는 정렬된 순서의 시작점을 알 수 없어 인덱스를 사용할 수 없습니다. 사전에서 "사랑으로 끝나는 단어"를 찾는 것과 같습니다. 컬럼에 함수를 적용한 `lower(email)` 도 인덱스는 원본 값 기준으로 정렬되어 있어 맞지 않습니다. 이는 SQLite 에서 확인한 내용이며, 데이터베이스마다 예외 (함수 기반 인덱스 등) 가 존재합니다.

그 밖에도 일반적으로 알려진 경우가 있습니다. 값의 종류가 적은 컬럼 (성별과 같이) 은 인덱스를 사용해도 조건에 맞는 행이 너무 많아 이득이 작습니다. 테이블이 매우 작으면 단순히 훑는 것이 더 빠릅니다.

## 여러 컬럼 인덱스는 왼쪽부터

`city` 와 `age` 를 동시에 조건으로 사용하는 쿼리가 많다면 두 컬럼을 묶은 인덱스를 만들 수 있습니다.

```python
q4 = "select * from users where city='서울' and age=30"
c.execute("create index idx_city_age on users(city, age)")
```

| 쿼리 | 만들기 전 | 만든 뒤 |
|---|---|---|
| `city='서울' and age=30` | `SCAN users` | `SEARCH ... USING INDEX idx_city_age (city=? AND age=?)` |
| `city='서울'` | `SCAN users` | `SEARCH ... USING INDEX idx_city_age (city=?)` |
| `age=30` | `SCAN users` | `SCAN users` (인덱스 사용 불가) |
| `select city, age ... where city='서울' and age=30` | | `SEARCH ... USING COVERING INDEX idx_city_age` |

두 번째 줄과 세 번째 줄이 규칙을 보여줍니다. 왼쪽 컬럼 (`city`) 만 조건이면 이 인덱스를 사용하지만, 오른쪽 컬럼 (`age`) 만 조건이면 사용할 수 없습니다. 전화번호부가 성, 이름 순으로 정렬되어 있어 이름만으로는 찾을 수 없는 것과 같습니다. SQLite 문서도 가장 왼쪽 컬럼이 가장 큰 정렬 기준이며 다음 컬럼은 동점을 가르는 용도라고 설명합니다. 같은 문서는 "한쪽이 다른 쪽의 앞부분이면 두 인덱스를 모두 만들지 말고 짧은 쪽을 삭제하라"는 팁도 제공합니다. `(city, age)` 가 있으면 `(city)` 인덱스는 필요 없다는 말입니다.

네 번째 줄의 `COVERING INDEX` 는 쿼리가 필요한 컬럼이 모두 인덱스에 포함되어 있어 원래 테이블을 전혀 열지 않는 경우입니다. 문서는 이것이 점근적으로 빨라지는 것이 아니라 상수 배 (약 2 배) 정도의 이득이라고 합니다.

## 읽을 땐 빠르고 쓸 땐 느리다

인덱스는 정렬된 상태를 유지해야 하므로 행을 삽입, 수정, 삭제할 때마다 인덱스도 함께 갱신해야 합니다. 같은 SQLite 로 20 만 행을 삽입하는 시간을 비교해 보았습니다. 테이블 컬럼은 세 개 (a, b, c) 이며, 하나는 인덱스 없이, 다른 하나는 세 컬럼 모두에 인덱스를 둔 경우입니다.

| | 20 만 건 INSERT (1 회 측정) |
|---|---|
| 인덱스 0 개 | 약 120ms |
| 인덱스 3 개 | 약 403ms |

약 세 배 느려졌습니다. 이 또한 한 번 측정한 값이며 환경에 따라 다릅니다. 따라서 "자주 조회하는 컬럼에만" 인덱스를 만듭니다. 인덱스는 별도의 저장 공간을 차지합니다. 쓰기가 매우 많은 테이블에 인덱스를 과도하게 적용하는 것은 손해일 수 있습니다. 쓰기 정합성에 관한 이야기는 [자세히 → 트랜잭션과 격리 수준](#/post/db-transaction) 과도 이어지며, 테이블 설계에 관해서는 [자세히 → 정규화와 모델링](#/post/db-normalization) 에서 다룹니다.

## 흔한 오해

- 인덱스를 만들면 무조건 빨라진다: 위 `LIKE '%...'`나 함수를 씌운 조건처럼 적용되지 않는 경우가 있다. 만든 뒤 계획을 봐야 한다.
- 컬럼마다 인덱스를 걸어 두면 안전하다: 쓰기가 느려지고 공간도 쓴다. 컬럼 세 개에 걸었더니 INSERT가 세 배쯤 걸렸다.
- 여러 컬럼 인덱스는 순서가 상관없다: 왼쪽부터 적용된다. `(city, age)`는 `age`만 조건일 땐 소용이 없었다.
- 인덱스가 있으면 DB 가 반드시 그걸 쓴다: DB 가 통계를 보고 풀 스캔이 낫다고 판단하면 안 쓴다.
- 인덱스는 B-Tree 뿐이다: 아니다. 벡터 검색에 쓰는 HNSW 같은 다른 구조도 있다. [자세히 → 벡터 DB](#/post/db-vector)에서 나온다.
