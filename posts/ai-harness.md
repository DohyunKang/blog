하네스는 모델을 빼고 남는 부분, 즉 모델을 루프에 넣어 돌리고 도구를 연결하고 기록을 관리하는 코드와 환경을 가리키는 말이다. 다만 정의가 하나로 굳어진 용어는 아니라서, 자료마다 범위가 조금씩 다르더라.

## 쉬운 말로 먼저

모델 혼자서는 글을 받아서 글을 돌려주는 것밖에 못 한다. 파일을 열거나 명령을 실행하는 건 모델이 아니라 그 옆에서 대신 해 주는 프로그램이다. 모델이 "이 파일 읽어 줘"라고 쓰면 프로그램이 읽어서 결과를 다시 모델에 넣는다. 이걸 끝날 때까지 반복한다. 이 프로그램이 하네스다.

말 그대로 마구(馬具), 말에 씌우는 장비라는 뜻이다. 말(모델)의 힘은 그대로인데, 어디로 어떻게 달릴지는 장비가 잡아 준다는 비유로 이해했다. 이 비유는 내가 붙인 것이고, 공식 글에서 이렇게 설명하는지는 확인 못 했다.

## 공식 글에서는 어떻게 쓰나

Anthropic 글 세 편을 열어 봤는데 쓰임이 조금씩 달랐다.

- Managed Agents 글: 하네스를 "Claude를 호출하고 Claude의 도구 호출을 해당 인프라로 보내 주는 루프"라고 괄호로 짧게 정의한다. 에이전트를 뇌(Claude와 하네스), 손(샌드박스와 도구), 세션(바깥에 남는 이벤트 기록) 셋으로 나눠 놓은 글이다.
- Effective harnesses for long-running agents: 형식적 정의는 없고, Claude Agent SDK를 "범용 에이전트 하네스"라 부른다. 도구, 컨텍스트 관리(압축 등), 주변 설정을 묶어서 하네스라고 쓰는 느낌이다. 각주에서는 초기화 에이전트와 코딩 에이전트가 시작 프롬프트만 다를 뿐 시스템 프롬프트와 도구를 포함한 하네스는 같다고 한다.
- 장기 앱 개발용 하네스 설계 글: 모델을 둘러싼 오케스트레이션, 역할 분담, 컨텍스트 처리, 프롬프트를 통틀어 하네스라 부르고 "하네스 설계"를 하나의 작업으로 다룬다.

같은 단어인데 첫 글은 "루프와 라우팅"만, 뒤의 둘은 "그 주변 설계 전부"까지 넓게 쓴다. 이게 자료마다 정의가 다르다는 뜻이다. 나는 좁은 의미를 핵심으로, 넓은 의미를 실제로 하는 일로 읽었다.

비교로 Anthropic의 Building effective agents 글도 열어 봤다. 에이전트를 "환경의 피드백을 받으며 도구를 쓰는 LLM이 루프를 도는 것"으로 설명하는데, 이 글에는 하네스라는 단어가 없었다. 용어가 나중에 자리 잡은 것 같지만, 언제부터인지는 확인 못 했다.

## 하네스가 하는 일

세 글에서 겹치는 것만 모으면 이렇다.

| 일 | 내용 |
|---|---|
| 루프 | 모델 호출, 도구 실행, 결과 되먹임을 끝날 때까지 반복. 최대 반복 횟수 같은 멈춤 조건 |
| 도구 | 어떤 도구를 줄지, 설명을 어떻게 쓸지. Anthropic은 이를 agent-computer interface(ACI)라 부르며 사람용 UI만큼 공들이라고 한다 |
| 권한 | 무엇을 실행해도 되는지, 자격 증명을 어디에 두는지. Managed Agents 글은 인증 정보를 샌드박스 밖에 둔다 |
| 컨텍스트 | 기록을 자르고 요약하고, 바깥 파일에 메모를 남기는 일 |
| 검증 | 모델이 "다 했다"고 한 걸 믿지 않고 테스트로 확인하는 일 |
| 복구 | 세션이나 컨테이너가 죽어도 이어서 하게 하는 일 |

권한은 위 세 글 중 Managed Agents 글에서만 구체적으로 확인했다. 나머지 권한 승인 방식 같은 건 제품마다 다를 것 같은데 따로 확인하지 않았다.

## 컨텍스트 엔지니어링, 에이전트 루프와의 관계

세 용어는 한 줄로 이어진다.

- 에이전트 루프: 돌아가는 동작 자체. 모델 호출, 도구 실행, 결과 넣기의 반복.
- 하네스: 그 루프를 실제로 돌리는 코드와 환경.
- 컨텍스트 엔지니어링: 루프의 매 턴마다 모델 눈앞에 뭘 올릴지 고르는 일. 하네스가 하는 일 중 하나다.

[자세히 → 컨텍스트 엔지니어링](#/post/ai-context)에서 나온 압축, 메모, 하위 에이전트 같은 방법은 결국 하네스 코드에 구현된다. 하네스는 컨텍스트만 다루는 게 아니라 도구, 권한, 검증, 복구까지 포함하니 더 넓은 쪽이다. 다만 어떤 글은 컨텍스트 관리를 하네스의 일부로 쓰고 어떤 글은 따로 쓴다. 경계는 글쓴이마다 다르다.

모델이 받는 입력 자체는 [자세히 → 컨텍스트 윈도우](#/post/ai-context-window)와 [자세히 → LLM](#/post/ai-llm)을 보면 되고, 도구 연결 규격은 [자세히 → MCP](#/post/ai-mcp)에서 따로 다룬다.

## 예시: 오래 도는 작업에서의 하네스

Effective harnesses 글의 예가 구체적이었다. 세션이 바뀌면 모델은 이전 일을 기억하지 못한다. 그래서 두 가지를 했다.

첫 세션은 초기화용이다. 사용자 요청을 기능 목록 JSON으로 펼치고, 개발 서버를 띄우는 `init.sh`, 진행 기록 파일, 첫 git 커밋을 만든다. 이후 세션은 한 번에 기능 하나만 구현하고 커밋하고 기록을 남긴다. 새 세션은 시작할 때 git 로그와 기록을 읽고, 기본 동작을 먼저 확인한 뒤 일한다.

기능 목록의 각 항목은 처음엔 모두 실패 상태이고, 코딩 에이전트는 통과 여부 필드만 바꿀 수 있다. JSON을 쓴 이유로 마크다운보다 모델이 함부로 고치거나 덮어쓸 가능성이 낮아서라고 적혀 있었다. 또 단위 테스트나 curl만으로 완료 처리하던 문제는 브라우저 자동화로 사람처럼 테스트하게 해서 크게 나아졌다고 한다.

보면 모델은 그대로고, 바깥 구조만 바꿔서 실패(너무 많이 하려는 것, 일찍 끝났다고 선언하는 것)를 줄인 셈이다. 이게 하네스 설계라는 말이 가리키는 일이다.

## 하네스 엔지니어링

하네스를 설계하고 고치는 일을 하네스 엔지니어링이라 부른다. 이 용어는 OpenAI가 2026년 2월에 낸 글 "Harness engineering: leveraging Codex in an agent-first world"로 널리 쓰인 것 같다. 다만 OpenAI 페이지는 접속이 막혀(403) 본문을 직접 읽지 못했고, 검색 결과의 발췌만 봤다. 발췌 기준으로는 초기 진행이 느렸던 이유가 모델이 아니라 환경이 덜 갖춰져서였고, 그래서 팀의 일이 에이전트가 쓸 수 있는 환경을 만드는 쪽으로 옮겨 갔다고 한다. 2차 자료들은 이를 제약, 도구, 피드백 루프, 문서, 검증 체계를 설계하는 일로 요약하는데, OpenAI 원문의 정의인지는 확인 못 했다.

Anthropic 글에도 같은 감각이 있다. 하네스의 모든 부품은 "모델이 혼자 못 하는 것"에 대한 가정을 담고 있고, 모델이 좋아지면 가정이 낡는다고 한다. 실제 예로 Sonnet 4.5에서 도움이 되던 컨텍스트 리셋이 Opus 4.5에서는 필요 없어졌다고 적었다. 그래서 하네스는 한 번 만들고 끝이 아니라 모델이 바뀔 때마다 덜어 낼 부품을 찾아야 하는 물건으로 보인다.

## 흔한 오해

- 하네스는 프레임워크 이름이다: 특정 라이브러리를 가리키는 말이 아니다. LangChain이든 직접 짠 루프든 모델 바깥에서 루프를 돌리면 하네스다.
- 하네스가 좋으면 모델은 아무래도 된다: 같은 글들이 반대로 말한다. 모델이 좋아지면 하네스가 단순해지는 쪽이다. 다만 복잡한 일의 하네스 필요성이 아주 없어진다고 한 건 아니고, 흥미로운 조합의 공간은 줄지 않는다는 문장도 있었다.
- 하네스는 프롬프트다: 프롬프트는 하네스의 일부일 뿐이다. 도구 실행, 기록 관리, 검증 코드가 따로 있다.
- 정의가 정해져 있다: 위에서 봤듯 좁게도 넓게도 쓴다. 글을 읽을 때 어느 범위인지 먼저 보는 게 좋겠다.

<details>
<summary>자세한 풀이: 뇌, 손, 세션 분리</summary>

Managed Agents 글에서 하네스는 컨테이너 안에 있지 않다. 하네스는 `execute(name, input) → string` 하나의 인터페이스로 샌드박스와 도구를 부른다. 컨테이너가 죽으면 하네스는 그걸 도구 호출 오류로 취급해 Claude에게 돌려주고, Claude가 새 컨테이너를 만들 수 있다. 세션은 하네스와 샌드박스 바깥에 남는 추가 전용 이벤트 기록이라, 하네스가 죽어도 마지막 이벤트부터 재시작할 수 있다. 자격 증명도 샌드박스 밖에 둔다.

하네스를 호스팅 서비스 뒤로 빼 놓은 이유는 하네스 구현이 모델 변화에 따라 바뀔 수 있어서라고 이해했다. 글이 그렇게 직접 말하는지는 요약으로만 확인해서 단정하지 않는다.

</details>

<details>
<summary>자세한 풀이: 계획·생성·평가 세 역할</summary>

장기 앱 개발 글의 구조는 세 역할이다. 계획자는 짧은 요청을 제품 명세로 펼치되 기술 세부는 너무 박지 않는다. 초기 오류가 아래로 번지지 않게 하려는 의도다. 생성자는 기능 하나씩 구현한다. 평가자는 Playwright로 실행 중인 앱을 사용자처럼 눌러 보며 기준과 문턱값으로 채점하고 버그를 적는다. 스프린트 전에 생성자와 테스트 가능한 계약을 맞춘다.

단순화한 버전은 스프린트 구조를 빼고 평가자를 마지막에 한 번만 돌렸다. 평가자는 모델이 혼자 안정적으로 못 하는 범위의 작업에서만 값을 한다고 한다. 오케스트레이션 복잡도, 토큰, 지연이 늘어나는 비용도 글에 적혀 있다. 구체적인 점수나 비용 수치는 읽지 못했다.

</details>

<details>
<summary>자세한 풀이: 확인한 것과 못 한 것</summary>

확인함: Managed Agents 글의 하네스 정의와 뇌/손/세션 구조, 하네스가 가정을 담는다는 문장과 Sonnet 4.5/Opus 4.5 예. Effective harnesses 글의 기능 목록 JSON, 진행 기록, git, 세션 시작 절차, 브라우저 테스트 내용과 Agent SDK를 범용 하네스라 부른 표현. 장기 앱 개발 글의 하네스 설계 용법과 세 역할 구조. Building effective agents 글의 루프 설명, ACI, 하네스 단어 부재. (웹 페치 도구의 요약을 통해 읽었고, 본문 전체를 눈으로 읽은 것은 아님.)

확인 못 함: OpenAI 하네스 엔지니어링 글 원문(403, 검색 발췌만 봄)과 그 글의 공식 정의, 숫자(코드량 등)는 일부러 적지 않음. 2차 자료들의 "2025년 말 등장" 같은 시기 주장. Claude Code, Codex 등 제품별 하네스 내부 구조. "하네스"라는 단어가 업계에 퍼진 정확한 시점.

</details>
