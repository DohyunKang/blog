# 복제와 샤딩

서비스가 커지면 DB 서버 한 대가 먼저 버거워진다. 쿼리를 고치고 [인덱스](#/post/db-index)를 달고 [캐시](#/post/db-cache-redis)를 붙여도 모자랄 때, 마지막에 꺼내는 게 DB를 여러 대로 늘리는 방법이다. 크게 둘로 나뉜다. 같은 데이터를 여러 대에 복사해 두는 복제, 데이터를 쪼개 여러 대에 나눠 두는 샤딩이다.

한 줄로 구분하면 이렇다.

| | 복제(replication) | 샤딩(sharding) |
|---|---|---|
| 각 서버가 가진 것 | 전체 데이터의 사본 | 데이터의 일부 |
| 주로 늘어나는 것 | 읽기 처리량, 가용성 | 쓰기 처리량, 저장 용량 |
| 따라오는 문제 | 복제 지연, 오래된 데이터 | 샤드 간 조인·트랜잭션, 재분배 |

## 읽기 복제

구조는 단순하다. 쓰기를 받는 서버 하나(primary, MySQL 문서에선 source)가 있고, 그 변경 내용을 따라 받아 적용하는 서버(replica, standby)가 여러 대 있다. 쓰기는 primary로, 읽기는 replica들로 흩뿌린다. 대부분의 서비스는 읽기가 쓰기보다 훨씬 많아서 이것만으로도 꽤 버틴다. 요청을 나눠 보내는 부분은 [로드밸런서](#/post/infra-load-balancer)나 애플리케이션의 연결 설정이 맡는다.

MySQL 공식 문서가 꼽는 복제의 쓰임새는 읽기 분산(scale-out) 말고도 있다. replica에서 백업을 돌리면 primary에 영향이 없고, 무거운 분석 쿼리도 replica에서 돌릴 수 있고, 멀리 있는 지점에 사본을 둘 수도 있다. primary가 죽으면 replica 하나를 primary로 올려 이어가는 것(failover)도 같은 구조에서 나온다.

### 동기냐 비동기냐

변경을 replica에 어떻게 전달하느냐가 성능과 안전을 가른다.

| 방식 | 커밋 시점 | 장점 | 단점 |
|---|---|---|---|
| 비동기 | primary가 커밋하면 바로 끝, 전달은 나중에 | 빠르다 | failover 때 최근 커밋이 사라질 수 있다. replica가 낡은 값을 줄 수 있다 |
| 반동기(MySQL) | 최소 한 replica가 받아서 기록했다고 응답할 때까지 대기 | 받았다는 보장이 있다 | 응답이 느려진다 |
| 동기 | 모든 서버가 커밋해야 끝 | 데이터를 잃지 않고 어디서 읽어도 같다 | 느리다. 네트워크가 느리면 성능이 절반 아래로 떨어질 수도 있다고 PostgreSQL 문서에 적혀 있다 |

MySQL은 기본이 비동기이고, 표준 복제는 완전한 동기 방식을 제공하지 않는다(그런 경우엔 NDB Cluster를 쓰라고 안내한다). 대부분은 비동기를 쓰고 그 대가를 감수한다.

### 복제 지연

비동기의 대가가 복제 지연(replication lag)이다. primary에 쓴 값이 replica에 닿기까지 짧게는 몇 밀리초, 부하가 크면 몇 초 이상 걸린다. 그 사이에 replica를 읽으면 방금 쓴 값이 안 보인다.

가장 흔한 사고는 이런 흐름이다. 사용자가 프로필을 수정한다(primary에 쓰기). 곧바로 프로필 화면을 연다(replica에서 읽기). 수정 전 값이 보인다. 사용자는 저장이 안 된 줄 알고 다시 누른다.

흔히 쓰는 대응은 몇 가지 있다.

- 쓴 직후 일정 시간은 그 사용자의 읽기를 primary로 보낸다(read-your-writes).
- 방금 쓴 데이터를 바로 보여줘야 하는 화면만 primary에서 읽는다.
- replica의 지연 시간을 모니터링하고, 지연이 크면 그 replica를 읽기 대상에서 뺀다.

복제는 쓰기를 늘려 주지 않는다는 점도 기억해 둘 만하다. 모든 replica가 primary의 쓰기를 전부 따라 적용해야 하므로, 쓰기가 병목이면 replica를 아무리 늘려도 그대로다. 그때부터 샤딩 얘기가 나온다.

## 파티셔닝

샤딩 전에 파티셔닝부터 짚는다. 용어가 섞여 쓰이는데, 보통 파티셔닝은 한 테이블을 여러 조각으로 나누는 일이고, 샤딩은 그 조각을 서로 다른 서버에 두는 일로 구분한다.

PostgreSQL 문서 기준으로 파티션된 테이블 자체는 저장 공간이 없고, 행은 파티션 키에 따라 각 파티션(평범한 테이블)으로 들어간다. 나누는 방식은 셋이다.

- 범위(range): 날짜 같은 키를 구간으로 자른다. 월별 파티션이 대표적이다.
- 목록(list): 키 값을 직접 나열한다. 지역 코드별 같은 경우다.
- 해시(hash): 키 해시를 modulus로 나눈 나머지로 보낸다.

효과는 질의가 일부 파티션만 읽으면 되고(pruning), 오래된 데이터를 `DROP`이나 `DETACH PARTITION`으로 통째로 버릴 수 있다는 것이다. 큰 `DELETE`보다 훨씬 빠르고 VACUUM 부담도 없다. 다만 문서는 이 이득이 테이블이 아주 클 때(경험칙으로 서버 메모리보다 클 때) 의미가 있다고 적는다. 제약도 있다. 기본 키와 유니크 제약에는 파티션 키 컬럼이 모두 들어가야 한다.

```sql
CREATE TABLE measurement (
    city_id int not null,
    logdate date not null,
    peaktemp int
) PARTITION BY RANGE (logdate);

CREATE TABLE measurement_y2006m02 PARTITION OF measurement
    FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');
```

(위 SQL은 PostgreSQL 문서의 예를 줄인 것이고, 직접 실행해 보지는 않았다.)

## 샤딩

파티션을 서로 다른 서버에 두면 샤딩이다. 서버마다 데이터의 일부만 가지므로 저장 용량도, 쓰기 처리량도 서버 수만큼 늘어난다. 대신 애플리케이션(또는 라우팅 계층)이 "이 키는 어느 샤드에 있나"를 알아야 한다.

### 샤드 키가 전부다

데이터를 무엇을 기준으로 나눌지(샤드 키)가 제일 중요한 결정이다. 한번 정하면 바꾸기 어렵다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 범위 | 범위 조회가 한 샤드에서 끝난다 | 최신 구간에 쓰기가 몰린다(핫스팟) |
| 해시 | 고르게 흩어진다 | 범위 조회는 모든 샤드를 뒤져야 한다 |
| 디렉터리(조회표) | 유연하다 | 조회표가 병목·단일 장애점이 된다 |

id를 순서대로 발급하고 범위로 나누면, 새로 들어오는 쓰기가 전부 마지막 샤드로 간다. 아래 실험에서도 id 1~10000을 3등분하면 최신 1000건은 전부 같은 샤드(2번)에 들어갔다. 고르게 나누려고 샤딩했는데 한 대만 일하는 꼴이다.

### 서버 수가 바뀔 때

해시로 나눌 때 흔한 첫 시도는 `hash(key) % 서버 수`다. 간단하지만 서버 수가 바뀌면 거의 모든 키의 위치가 바뀐다. 직접 돌려 보니 10,000개 키를 서버 3대에서 4대로 늘렸을 때 약 75%가 다른 서버로 옮겨 가야 했다.

일관된 해시(consistent hashing)가 이 문제를 줄인다. 서버와 키를 같은 해시 원 위에 올리고, 키는 시계 방향으로 처음 만나는 서버에 맡긴다. 서버가 하나 늘면 그 서버와 앞 서버 사이에 있던 키만 옮기면 된다. 위키백과 설명으로는 n번째 서버를 더할 때 대략 1/n만 움직인다. 서버를 원 위에 한 점씩만 두면 간격이 들쭉날쭉해 부하가 쏠리므로, 서버 하나를 여러 지점(가상 노드)으로 올려 고르게 만들고, 성능이 큰 서버에는 가상 노드를 더 준다.

<details>
<summary>직접 돌려 본 코드와 결과</summary>

```python
import hashlib, bisect
def h(k): return int(hashlib.md5(k.encode()).hexdigest(), 16)
keys = [f"user{i}" for i in range(10000)]

def mod(n): return {k: h(k) % n for k in keys}
a, b = mod(3), mod(4)
print("mod 3->4 moved:", sum(a[k] != b[k] for k in keys) / len(keys))

def ring(nodes, vn=100):
    r = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vn))
    hs = [x[0] for x in r]
    def f(k):
        i = bisect.bisect(hs, h(k)) % len(r)
        return r[i][1]
    return f

f3 = ring(["A", "B", "C"])
f4 = ring(["A", "B", "C", "D"])
print("ring 3->4 moved:", sum(f3(k) != f4(k) for k in keys) / len(keys))
```

실행 결과(Python 3, 이 환경에서 확인).

```
mod 3->4 moved: 0.7484
ring 3->4 moved: 0.2392
```

이론값 1/4(25%)에 가까운 24% 정도만 옮겨 간다. 가상 노드는 서버당 100개로 했다.

</details>

## 샤딩이 어렵게 만드는 것

샤딩은 쓰기를 늘려 주는 대신 DB가 공짜로 주던 것들을 가져간다.

- 조인: 서로 다른 샤드에 있는 테이블끼리는 한 번에 조인할 수 없다. 앱에서 따로 가져와 합치거나, 자주 같이 쓰는 데이터를 같은 샤드에 두도록 샤드 키를 잡는다. [정규화](#/post/db-normalization)로 쪼갠 테이블이 샤드를 가로지르면 부담이 커진다.
- 트랜잭션: 한 샤드 안에서는 평소처럼 되지만, 여러 샤드를 건드리는 [트랜잭션](#/post/db-transaction)은 분산 트랜잭션(2단계 커밋 등)이나 보상 처리가 필요하다. 느리고 복잡하다. 그래서 보통 한 트랜잭션이 한 샤드에서 끝나게 설계한다.
- 유니크·자동 증가 id: 샤드마다 따로 번호를 매기면 겹친다. UUID나 시간 기반 id 같은 별도 발급 방식이 필요하다.
- 재분배(resharding): 샤드를 늘리면 데이터를 옮겨야 한다. 무중단으로 하려면 이중 쓰기와 검증 같은 작업이 든다.
- 운영: 백업, 스키마 변경, 모니터링이 모두 샤드 수만큼 곱해진다.

그래서 순서가 정해져 있다시피 하다. 쿼리·인덱스 개선, 서버 사양 올리기(scale-up), 캐시, 읽기 복제를 먼저 하고, 쓰기나 용량이 그래도 모자랄 때 샤딩을 한다. 처음부터 샤딩부터 하는 건 대부분 과하다. 샤딩이 기본 기능으로 들어 있는 [NoSQL](#/post/db-nosql)을 고르는 것도 한 방법이다.

## 일관성 트레이드오프

복제와 샤딩을 하는 순간 "데이터가 여러 곳에 있다"는 사실이 생기고, 같은 값을 여러 곳에서 어떻게 맞출지가 문제가 된다. PostgreSQL 문서는 이를 이렇게 정리한다. 읽기 전용 데이터는 각 서버에 한 번만 두면 되지만, 쓰기는 모든 서버에 전파돼야 이후 읽기가 일관되고, 그래서 모든 워크로드에 맞는 단일 해법이 없다.

실무에서 고르는 건 대개 이 세 가지의 균형이다.

| 올리면 | 내려가는 것 |
|---|---|
| 일관성(어디서 읽어도 최신) | 쓰기 속도, 서버 하나 멈췄을 때의 가용성 |
| 쓰기 속도·가용성 | 읽을 때 최신 값 보장 |
| 저장·쓰기 확장성(샤딩) | 조인·트랜잭션의 편의 |

은행 잔액처럼 틀리면 안 되는 곳은 일관성 쪽, 게시글 조회수나 피드처럼 몇 초 늦어도 되는 곳은 속도·확장성 쪽으로 기운다. 한 서비스 안에서도 데이터마다 다르게 고른다.

## 흔한 오해

- 복제하면 쓰기도 빨라진다: 아니다. 쓰기는 primary 한 대가 받고 replica는 그걸 따라 적용하므로 쓰기 처리량은 그대로다.
- replica는 백업이다: 아니다. primary에서 실수로 지운 데이터가 그대로 replica에도 반영된다. 지연 복제(delayed replication)를 쓰거나 별도 백업이 필요하다.
- 파티셔닝과 샤딩은 같다: 같은 서버 안에서 나누면 파티셔닝, 서버를 나누면 샤딩으로 구분하는 경우가 많다. 파티셔닝만으로는 서버 한 대의 한계를 못 넘는다.
- 샤딩은 미리 해 두는 게 낫다: 샤드 키를 잘못 잡으면 나중에 바꾸기가 어렵고, 운영 복잡도는 바로 늘어난다. 필요가 확인된 뒤에 하는 게 보통 낫다.

## 정리

읽기가 많으면 복제, 용량이나 쓰기가 한계면 샤딩, 한 서버 안에서 큰 테이블을 다루기 쉽게 하려면 파티셔닝이다. 어느 쪽이든 데이터가 여러 곳에 놓이는 순간 일관성을 얼마나 양보할지 정해야 한다.
