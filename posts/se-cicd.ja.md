型管理とは、ソフトウェアの特定の時点の状態を基準点（ベースライン）として定め、その基準点が変化する過程を追跡する作業です。ブランチ戦略と CI/CD は、この作業をチーム規模で運用するための仕組みです。

[概要](#/post/cs-sw-engineering) では型管理について一言触れただけでしたが、Git の内部構造については [Git を正しく理解する](#/post/cs-git)、パイプラインとデプロイ方式については [CI/CD とデプロイ戦略](#/post/cloud-cicd) にあります。ここではその中間にある、ツール導入前の概念と選択基準について扱います。

## 形像とは何か、何を管理するか

形像（configuration）は、ソフトウェアを構成するすべてのアウトプットのことです。ソースコードだけでなく、設定ファイル、ビルドスクリプト、依存ライブラリのリスト、ドキュメント、テストコードも含まれます。管理対象として束ねられた個別の項目を「形像アイテム」と呼びます。

「コードはバージョン管理するが、設定はサーバーに直接書き換える」のはよくある誤解です。同じコードでも設定が異なると動作が変わり、再現性が失われます。そのため、型管理ではコードと一緒に動くものをすべて同一の履歴にまとめる方向へ進みます。

## ベースライン

ベースライン（baseline）とは、「この状態を公式とする」と合意して固定した時点のことです。リリースが代表的な例です。ベースラインがあれば以下の 2 つが可能になります。いつでも正確に戻ることができ、ベースライン以降に変更されたものをリストとして提示できます。

ベースラインを極めて単純化すると以下のような仕組みになります。ファイル内容をハッシュ化し、そのリストを再度ハッシュ化することで、状態全体を示す短い ID が得られます。

```python
import hashlib, json

def snapshot(files):
    items = {name: hashlib.sha256(data.encode()).hexdigest()[:8] for name, data in sorted(files.items())}
    bid = hashlib.sha256(json.dumps(items, sort_keys=True).encode()).hexdigest()[:8]
    return bid, items

v1 = {"app.py": "print('hi')", "config.yml": "debug: false", "README": "v1"}
v2 = dict(v1, **{"config.yml": "debug: true"})

b1, i1 = snapshot(v1)
b1b, _ = snapshot(dict(reversed(list(v1.items()))))
b2, i2 = snapshot(v2)
print(b1, b1b, b1 == b1b)
print(b2, b1 != b2)
print([n for n in i1 if i1[n] != i2[n]])
```

```
443516a5 443516a5 True
7d2092ea True
['config.yml']
```

ファイルの順序を入れ替えても ID は同じであり、設定の 1 行だけ変更すれば ID も異なります。これにより何が変更されたかを比較できます。Git のコミットハッシュはこの原理に基づいています。このコードは原理を説明するために簡略化したものであり、実際の Git の方式とは異なります。

## 変更統制

ベースラインがあれば、それを変更する手順も必要です。変更リクエストが来ると影響範囲を確認し、誰が承認するか、どのベースラインに反映させるかを決定します。従来の開発組織ではこの承認を委員会形式で行うこともありました。現代のチームではプルリクエストレビューと必須の状態チェックがその役割を果たすことが多くあります。形態は違っても、「誰がどのような根拠でベースラインを変更したか」が残る点は同じです。

## バージョン番号も型管理の一部である

ベースラインに付ける名前がバージョンです。セマンティックバージョニング（SemVer）は `MAJOR.MINOR.PATCH` の 3 つの数字に意味を与えます。

| 上げる位置 | いつ | 下の位置 |
|---|---|---|
| MAJOR | 公開 API が下位互換性を失って変更される場合 | MINOR, PATCH を 0 に |
| MINOR | 下位互換性のある機能が追加される場合 | PATCH を 0 に |
| PATCH | 下位互換性のあるバグ修正 | - |

他にもいくつかルールがあります。公開されたバージョンを修正せずに変更する場合は新しいバージョンをリリースします。`-rc.1` などのプレリリース表記は、正式バージョンよりも低い優先順位です。`+build7` などのビルドメタデータは優先順位の比較では無視されます。MAJOR が 0 の間は、いつでも変更可能な初期開発段階と見なします。

```python
import re

def parse(v):
    m = re.fullmatch(r"(\d+)\.(\d+)\.(\d+)(?:-([0-9A-Za-z.-]+))?(?:\+[0-9A-Za-z.-]+)?", v)
    major, minor, patch, pre = m.group(1), m.group(2), m.group(3), m.group(4)
    return int(major), int(minor), int(patch), pre.split(".") if pre else None

def pre_key(ident):
    return (0, int(ident), "") if ident.isdigit() else (1, 0, ident)

def sort_key(v):
    major, minor, patch, pre = parse(v)
    if pre is None:
        return (major, minor, patch, 1, ())
    return (major, minor, patch, 0, tuple(pre_key(i) for i in pre))

def bump(v, kind):
    major, minor, patch, _ = parse(v)
    if kind == "major": return f"{major+1}.0.0"
    if kind == "minor": return f"{major}.{minor+1}.0"
    return f"{major}.{minor}.{patch+1}"

versions = ["3.0.0", "3.0.0-rc.1", "3.0.0-beta.11", "3.0.0-beta.2", "1.10.0", "1.9.0", "1.0.0+build7"]
print(sorted(versions, key=sort_key))
print(sort_key("1.0.0+build7") == sort_key("1.0.0+other"))
for k in ("patch", "minor", "major"):
    print(k, bump("1.4.7", k))
```

## ブランチ戦略はデプロイ方式で分岐する

ブランチ戦略とは、「ベースラインをどの経路で作成するか」の選択です。最もよく言及される git-flow は、`master`（リリースごとにタグが付けられる運用コード）と `develop`（次のリリースのための統合ブランチ）を置き、機能は feature、リリース準備は release、運用緊急修正は hotfix ブランチに分けます。

| ブランチ | どこから取るか | どこにマージするか |
|---|---|---|
| feature | develop | develop |
| release | develop | master, develop |
| hotfix | master | master, develop |

git-flow を提案した著者は、2020 年に追加した記事で、Web アプリのように継続的にデプロイするソフトウェアは複数のバージョンを同時に維持する必要がないため、GitHub flow のようなはるかに単純な流れの方が良いと書きました。バージョンが明示的に付けられ、現場で複数のバージョンをサポートしなければならないソフトウェアには git-flow がまだ適しているといいます。どちらが良いかはデプロイ方式によって決まります。

[Git を正しく理解する](#/post/cs-git) のマージ・リベースの話はブランチをどのようにマージするかでしたが、ここではブランチの種類やライフサイクルが争点です。

## CI はツールではなく習慣である

Martin Fowler 氏の記述によれば、継続的統合 (Continuous Integration, CI) は以下のように定義される。チームメンバーが各自で変更したコードを少なくとも毎日一度は共有のコードベースにマージし、そのたびにテストを含む自動ビルドを実行するものである。同記事で挙げられている実践項目のうち、バージョン管理に関連するものは以下の通りである。

- すべてをバージョン管理されたメインブランチに置く。リポジトリを取得したらすぐにビルドして実行可能であるべきだ。
- ビルドは単一のコマンドで自動化し、ビルド内にテストを含めることで、緑の信号灯が点灯すれば重大なバグがないとみなせるようにする。
- メインブランチへのプッシュごとに CI サーバーでビルドを行う。
- 壊れたビルドはすぐに修正する。通常は問題のあるコミットをロールバックしてチームが継続的に作業できるようにし、原因については別途調査する。
- ビルドは速やかに維持する。同記事では XP の「10 分ビルド」を、ほとんどのプロジェクトに適した基準として挙げている。
- 未完成の機能は、機能フラグなどの方法で非表示にする。

最後の項目はブランチ戦略と繋がっている。毎日一度マージするためには、機能が一日以内に完了しなくてもマージ可能である必要があり、そのためブランチを長く維持するのではなく、未完了の機能をコード内で隠しておくのである。ブランチの寿命が長いほど CI の「頻繁にマージする」という前提から遠ざかる。

テストがビルドに含まれているため、「[テストと品質](#/post/se-testing)」における単体・統合テストの構成が CI の時間を左右する。同記事では、高速なコミットビルドを先に実行し、低速なテストは後段で実行するデプロイパイプラインの構成を推奨している。

## CI、デリバリー、デプロイを区別する

| 名称 | 自動で行うこと | 人間が行うこと |
|---|---|---|
| CI | マージ、ビルド、テスト | - |
| 継続的デリバリー | デプロイ可能な状態まで | 運用デプロイボタン |
| 継続的デプロイ | 運用デプロイまで | なし（監視） |

段階別の YAML 例やブルー・グリーン、カナリヤなどのデプロイ手法は、「[CI/CD とデプロイ戦略](#/post/cloud-cicd)」にある。デプロイ後の状態を確認するものは「[監視・ログ・通知](#/post/cloud-observability)"である。

## よくある誤解

- CI サーバーを置けば CI を行う：マージ頻度が低ければ、サーバーがあっても統合問題は遅れて表面化する。
- ブランチは多いほど安全：ブランチが長く存続すればするほど、マージ時の衝突と統合コストが増大する。
- git-flow が標準である：提案者は状況に応じて異なることを直接整理している。
- バージョン番号はマーケティング用の名前である：SemVer では公開 API の変更の性質を示す約束事である。
