MCP は、AI アプリケーションがファイル、データベース、検索などの外部システムに接続する仕方を統一した公開規格です。公式の紹介文書では、「AI アプリのための USB-C ポート」という比喩を用いています。仕様が統一されているため、サーバーを一度作成すれば複数のアプリが同じ方式で利用できます。

## 何を解決するか

MCP がなければ、各 AI アプリごとに外部サービスへの接続コードを個別に記述する必要があります。アプリが N 個、サービスが M 個の場合、接続数は N×M になります。この計算は公式文書にある文章ではなく私が整理したものです。MCP はその間に共通規格を設け、アプリ側は MCP を理解するだけで済み、サービス側は MCP サーバーを作成するだけで済むようにします。

公式文書はこの利点をユーザーの立場から記述しています。開発者は AI アプリやエージェントを作成・連携する際の時間と複雑さを減らせますし、AI アプリはデータやツールのエコシステムにアクセスでき、最終ユーザーはより多くのタスクをこなせるアプリを利用できます。サポート範囲として、Claude、ChatGPT、Visual Studio Code、Cursor が文書に記載されています。「一度作成すればどこでも接続」という表現もあります。

範囲は狭いです。アーキテクチャ文書には「MCP はコンテキストのやり取りに焦点を当てたプロトコルのみを対象とし、AI アプリが LLM をどのように使用するか、受け取ったコンテキストをどのように管理するかについては規定しない」と記載されています。モデルがいつ何を呼び出すかはアプリ側の責任です。この部分は [コンテキスト](#/post/ai-context) とも関連しています。

## 構造：ホスト、クライアント、サーバー

参加者は 3 つあります。

| 名前 | 役割 | 例 |
|---|---|---|
| MCP ホスト | AI アプリ。クライアントを作成・管理する | Claude Code, Claude Desktop, VS Code |
| MCP クライアント | サーバー 1 つと接続を維持し、コンテキストを受け取ってホストに渡す | ホスト内のオブジェクト |
| MCP サーバー | コンテキストを提供するプログラム | ファイルシステムサーバー、Sentry サーバー |

核心は、サーバー 1 つに対してクライアントが個別に接続される点にあります。文書の例は理解しやすいです。VS Code が Sentry MCP サーバーに接続するとクライアントオブジェクトが 1 つ生まれ、ローカルファイルシステムサーバーにも接続すればさらにクライアントオブジェクトが 1 つ増えます。

```
호스트(AI 앱)
 ├─ 클라이언트 1 ── 서버 A (로컬: 파일시스템)
 ├─ 클라이언트 2 ── 서버 B (로컬: DB)
 └─ 클라이언트 3 ── 서버 C (원격: Sentry)
```

「サーバー」という言葉が混乱しましたが、文書で別途指摘されています。サーバーとは、どこで実行されていてもコンテキストを提供するプログラムを指します。自分の PC で実行すればローカルサーバー、インターネットの向こう側で実行すればリモートサーバーです。

### 2 つの層：データ層と転送層

- データ層: JSON-RPC 2.0 をベースにメッセージの形式と意味を定義します。機能探索（discovery）、ツール・リソース・プロンプト、通知が含まれます。
- 転送層: メッセージを実際に運ぶ経路です。2 つあります。
  - stdio: 同じ PC 内のプロセス間で標準入出力を通じてやり取りします。ネットワークコストがありません。主にローカルサーバーで使用され、通常はクライアント 1 つと対話します。
  - Streamable HTTP: HTTP POST に必要に応じて Server-Sent Events を追加します。リモートサーバー用で、通常は複数のクライアントと対話します。認証には Bearer トークンや API キーを使用し、文書では OAuth でトークンを取得することを推奨しています。

## サーバーが提供する 3 つのもの

サーバーが提供できるものは 3 つ（プリミティブ）です。それぞれ誰が使用するかが決まる点が興味深かったです。

| 種類 | 何か | 例 | 誰が決めるか（仕様表現） |
|---|---|---|---|
| ツール (Tools) | 実行可能な関数 | ファイル操作、API 呼び出し、DB クエリ | model-controlled、モデルが自動的に見つけて呼び出す |
| リソース (Resources) | コンテキストとなるデータ | ファイル内容、DB レコード、スキーマ | application-driven、ホストアプリがどのように挿入するかを決定 |
| プロンプト (Prompts) | 再利用可能なテンプレート | システムプロンプト、few-shot 例示 | user-controlled、ユーザーが直接選択する |

文書の例でまとめると以下のようになります。データベース用サーバーの場合なら、クエリを行うツール、スキーマを含むリソース、そのツールを使用する few-shot 例示を含むプロンプトを同時に提供できます。

プロンプトはスラッシュコマンドで公開する例が仕様に登場します。ツールはモデルが呼び出しますが、仕様では「信頼と安全のために拒否できる人が常にいるべきである (SHOULD)」と記載されています。どのツールが公開されているかを示し、呼び出された際に表示し、確認を求める勧告です。ただし、プロトコルがこの相互作用方式を強制しないことは同じ文書にあります。

3 つすべて `*/list` でリストを受け取り、取得する方式があります。リソースは `resources/read`、プロンプトは `prompts/get`、ツールは `tools/call` です。リストが動的であるため、ツールが変わればサーバーから通知を送り、クライアントがリストを再取得します。

アーキテクチャドキュメントの例を簡略化して示すと以下の通りです。まず `tools/list` を送信すると、サーバーがツールリストを返します。各ツールには `name`, `title`, `description` および JSON Schema で記述された入力形式 `inputSchema` が含まれます。

```json
{ "method": "tools/call",
  "params": { "name": "weather_current",
              "arguments": { "location": "San Francisco", "units": "imperial" } } }
```

レスポンスは `content` アレイにテキストや画像などが格納されます。仕様では、ツール実行エラーを 2 つのタイプに分けています。リクエスト自体が間違っている（未知のツールのように）場合は JSON-RPC エラーとし、日付形式の誤りなどの入力・ロジックエラーの場合は `isError: true` が付与された結果として返されます。後者はモデルが読み取り、修正して再試行するよう指示しているものです。

ホスト側のフローはドキュメントの擬似コードに従っており、モデルがツールを使用すると宣言した場合、アプリはその呼び出しをキャッチし、適切なサーバーに転送し、その結果をモデルの対話に戻します。

なお、今回読んだドキュメント（最新バージョン表記 2026-07-28）は、各リクエストごとにプロトコルバージョンと機能を `_meta` に埋め込んで送信するステートレスな方式で記述されています。以前のバージョンでは接続開始時にネゴシエーションを行う初期化段階があったことが知られています。

## サーバーがクライアントに要求すること

逆方向の機能もあります。最新ドキュメント基準では、サーバーがユーザーから追加入力や確認を要求する elicitation があります。sampling（サーバーがクライアントの LLM に完了を要求）と logging はこのバージョンから deprecated と表示されています。この部分はバージョンによって変化しており、使用时には該当バージョンのドキュメントを再確認する必要があります。

## 通常の function calling と何が違うのか

| | function calling | MCP |
|---|---|---|
| 本質 | モデル API がツール呼び出しを表す方式 | アプリと外部システム間の接続規格 |
| ツール定義 | アプリコードが各リクエストで直接設定する | サーバーが `tools/list` で通知する |
| ツール実行 | アプリが直接実装する | サーバーが実行する（リモートの場合、異なる組織のものも可能） |
| 範囲 | ツールのみ | ツール、リソース、プロンプト |

両者は競合関係ではなく層が異なります。ホストは MCP サーバーから取得したツールリストをモデルに渡し、モデルが呼び出しを行うと `tools/call` でサーバーに伝達します。モデル側から見れば依然としてツール呼び出しですが、そのツールの出所が変わったという点です。ドキュメントも「MCP は AI アプリが LLM をどのように使うかを規定しない」と述べているため、モデル API 側には触れません。

したがって利点は「アプリ内でツールを呼ぶ方法」ではなく、「アプリとツール作成者が互いに知らなくても接続する方法」にあります。

## セキュリティ上の注意点

MCP サーバーはコードを実行したりデータを読み取ったりできるため、接続とは権限を与える行為そのものです。公式セキュリティドキュメントやツール仕様に目立ったもののみ記載します。

- ローカルサーバーのリスク：設定に悪意のある起動コマンドが含まれていたり、サーバー自体に悪意のあるコードが含まれていたり、稼働中のローカルサーバーを DNS rebinding で攻撃できる可能性があります。ドキュメントでは、一度設定されたローカルサーバーを接続する際に実際に実行されるコマンドが切り取られないように示し、明示的に承認を受けるよう（MUST）指示しています。サンドボックス内で最小権限で動作させることも推奨されています。
- トークンパススルーの禁止：MCP サーバーが発行されていないトークンを自らのために受け取り、下位の API にそのまま渡すことはアンチパターンです。ドキュメントではサーバーは自らが発行されたトークンのみを受け取るよう（MUST NOT それ以外を受理）指示しています。
- Confused deputy: 第三者 API と接続を提供する MCP プロキシサーバーが、固定クライアント ID、動的クライアント登録、同意クッキーが重複すると、ユーザーの同意なしに認証コードを奪われる可能性があります。クライアントごとに個別に同意を取得することが必須対策です。
- SSRF：悪意のあるサーバーが OAuth メタデータ URL を内部ネットワークまたはクラウドメタデータアドレス（169.254.169.254）で埋め込み、クライアントを追従させる可能性があります。プライベート IP のブロックや HTTPS 強制などが対策となります。
- 権限範囲の最小化：`files:*`, `admin:*` などの広範な scope を最初から受け取ると、トークンが漏れた際に被害が大きくなります。最初は読み取り中心の小さな scope で始め、必要に応じて上げるよう指示されています。
- ツール仕様の推奨：サーバーは入力検証、アクセス制御、呼び出し回数制限、出力整理を行う必要があります（MUST）し、クライアントは機密な動作についてはユーザーの確認を受け、サーバーに送信する前に入力をユーザーに表示する必要があります（SHOULD）。ツールの annotations（動作説明メタデータ）は信頼できるサーバーからのものでない場合は信用してはいけません（MUST consider untrusted）。

サーバーが返したツール結果や説明も結局モデルのコンテキストに入るため、信頼できるサーバーのみを接続するのが基本だと理解しました。これはドキュメントに書かれている内容ではなく、読み込んでからの判断です。

## よくある誤解

- MCP 는 도구이다: MCP 는 도구가 아니라 도구를 연결하는 규격입니다. 도구는 서버가 제공합니다.
- MCP 를 쓰면 모델이 더 똑똑해진다: 모델 자체는 그대로이며, 받을 수 있는 컨텍스트와 수행할 수 있는 동작만 늘어납니다.
- 서버는 원격에만 있다: stdio 로 내 PC 에서 실행되는 로컬 서버도 흔합니다.
- 규격이 있으니 안전하다: 규격에는 권고 사항이 담겨 있을 뿐, 실제 안전성은 서버를 선택하는 일과 클라이언트의 승인 UI 에 달려 있습니다.
- 도구만 있다: 리소스와 프롬프트도 존재합니다. 도구 외에는 덜 쓰이는 것 같긴 한데, 이는 체감일 뿐 통계는 찾지 못했습니다.
