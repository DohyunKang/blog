Serverless 并不意味着没有服务器，而是指由云服务商负责服务器的启动、关闭和伸缩，开发者只需上传函数代码即可。

## 什么是 Serverless

这个名字容易让人困惑。当然有服务器存在。只不过，我们不是租用服务器安装操作系统并常驻进程，而是上传代码（函数），当收到请求时，云服务商会自动创建并运行执行环境；没有请求时则停止运行。因此被称为“无需关心服务器”的架构。

Vercel 文档也表达了类似观点：每次请求都会触发一次函数执行（invocation），若无流量，资源可缩减至零。AWS Lambda 是此类服务的典型代表。

先阅读 [服务器与云基础 → 云基础](#/post/cloud-basics) 有助于理解“租用服务器”与此有何不同。

| | 自行运营服务器（如 VM） | Serverless |
|---|---|---|
| 运行状态 | 服务器持续运行 | 仅在收到请求时执行 |
| 伸缩方式 | 由用户决定服务器数量和大小 | 随请求量自动扩展环境 |
| 计费依据 | 按运行时间计费 | 按执行次数和运行时间计费 |
| 状态管理 | 可将数据存储在内存或磁盘上 | 执行结束后环境即消失，需在代码中处理（如持久化到存储） |

## 函数执行方式

Lambda 文档描述的流程分为三个阶段：创建环境时的 Init、处理请求时的 Invoke、清理环境时的 Shutdown。

在 Init 阶段，会启用扩展功能、启动运行时，并执行代码中位于处理器（handler）外部的部分（如 import、配置、数据库连接等）。Invoke 阶段则运行处理器。执行结束后，环境不会立即销毁，而是被冻结（freeze），待同一函数再次收到请求时再解冻（thaw）复用。根据文档，即使每隔几小时也会替换环境，因此不应认为其能永久维持。

正因存在这种复用机制，代码位置才具有重要意义。置于处理器外部的变量和连接在后续请求中仍可保留。正如文档建议，数据库连接等应在外部（初始化阶段）创建并复用。

以下是运行验证后的小示例：处理器外部部分仅执行一次，而处理器则随每次请求执行。

```python
import time

time.sleep(0.2)                    # Init: 라이브러리 로드, 연결 생성 흉내
CONN = {"opened": time.time()}     # 핸들러 바깥: 환경이 살아 있는 동안 재사용
calls = 0

def handler(event, context=None):  # Invoke: 요청마다 실행
    global calls
    calls += 1
    return {"call": calls, "conn_age_ms": round((time.time() - CONN["opened"]) * 1000)}

for _ in range(3):
    print(handler({}))
    time.sleep(0.05)
```

运行结果显示，call 依次变为 1、2、3，conn_age_ms 也相应增长为 0、50、101，模拟了连接并非每次请求都新建而是持续复用的情况。此处并非在真实 Lambda 上运行，而是本地 Python 模拟。

## 冷启动

若收到请求时无法使用现有环境，则需重新创建：下载代码、启动环境并执行 Init 代码后，处理器才会开始运行。这段前置时间称为冷启动（cold start）。若复用已有环境，则称为温启动（warm start）。

Lambda 文档指出，冷启动通常发生在不到 1% 的调用中，持续时间从不足 100ms 到超过 1 秒不等。在开发或测试用途、调用频率较低的函数中更为常见。这些数字来自文档的一般说明，具体耗时需针对自身函数另行评估。

Init 阶段消耗的时间本质上源于用户代码。文档将包大小（库、层）、初始化工作量、连接配置速度列为主要影响因素；优化方向则相反：仅引入必要的库，按需创建不常用路径中的对象。

若必须保证可预测的启动时间，可使用 Provisioned Concurrency 选项，该功能会预先准备环境，但相应地引入了持续运行的成本概念。SnapStart 则是通过保存已初始化完成的环境快照并从中恢复来支持特定范围的功能。

## 限制

以下是 Lambda 默认配额中值得注意的项目：

| 项目 | 值 |
|---|---|
| 单次执行时间 | 最长 900 秒（15 分钟） |
| 内存 | 128MB ~ 10,240MB（CPU 与内存成正比） |
| 同步调用请求/响应大小 | 各为 6MB |
| 并发执行 | 默认 1,000（按账户和区域，可申请增加） |
| 部署包 | zip 解压后不超过 250MB，容器镜像不超过 10GB |
| /tmp | 512MB ~ 10,240MB |

数据来源为 AWS 配额文档，新账户可能从更低配额开始。这些数值可能会变更，使用时建议再次查阅。

比数字更重要的是思维方式：由于执行结束后环境会消失，状态不应保存在函数内，而应存入数据库或存储系统。超过 15 分钟的任务需拆分或使用其他方式（如容器、工作流）。若请求突然激增，可能触及并发执行上限，也可能导致函数背后的数据库无法承受该并发压力。[数据库扩展](#/post/db-scaling) 与此话题密切相关。

## 成本

费用基于请求数量和运行时间（分配的内存 GB × 秒数）进行计算。以 AWS 价格页面的 x86 架构和美国东部（弗吉尼亚）地区为例，每百万次请求收费 0.20 美元，每 GB-秒运行时间收费 0.0000166667 美元；每月前百万次请求和四十万 GB-秒的运行时间为免费额度。

这是一个自行计算的示例：一个 512MB 的函数每秒运行 200ms（即 0.2 秒），若执行一百万次，则总运行时间为 1,000,000 × 0.2 秒 × 0.5GB = 100,000 GB-秒。运行时间费用为 100,000 × 0.0000166667 ≈ 1.67 美元，加上请求费用 0.20 美元，总计约 1.87 美元。这是扣除免费额度前的金额；由于该用量处于上述免费区间内，实际费用为 0。计算中未包含其他服务费用（如 API Gateway、数据传输和日志）。

反之，如果服务全天持续接收请求，则保持服务器运行可能更为划算。流量与运行时间的临界点各不相同，因此无法给出一个通用的数值。

Vercel Functions 的计算方式略有不同。根据文档，其费用基于活跃 CPU、预留内存和调用次数计算；所谓的"Fluid compute"（流体计算）方式是指单个实例可同时处理多个请求，从而利用等待时间（如外部 API 响应延迟等）。因此，这能减少冷启动并降低成本。

## 适用与不适用的场景

- **适用场景**：偶尔调用的 API、接收 Webhook、文件上传后生成缩略图、定时任务、流量波动较大的服务。
- **不适用场景**：超过 15 分钟的长时任务、必须保持常开的连接（如 WebSocket 服务器）、对延迟极其敏感的应用、依赖本地磁盘或内存状态的程序。

与容器相比，[Docker 和容器](#/post/cloud-docker) 更接近“我完全掌控环境”，而 Serverless 则更接近“托管环境，只需提交代码”。两者也有结合之处，例如 Lambda 也可以上传容器镜像。关于自动伸缩的内容，请参见 [自动伸缩](#/post/infra-autoscaling)。

## 常见误区

- **没有服务器**：并非如此。只是我不需要管理它们而已。
- **总是便宜**：仅在请求量少且短时运行时便宜；若持续大量使用，费用可能会发生变化。
- **总是慢**：冷启动仅发生在部分调用中。不过，如果这部分延迟被用户感知到，就会感觉变慢了。
- **可以将状态保存在变量中**：这仅是可重用期间偶然保留的数据，不可依赖。
- **可以无限扩展**：存在并发执行限制和后端系统限制。

<details>
<summary>详细解析：一个请求的流转路径</summary>

当请求到达时，前端（如 API Gateway 或 CDN）会接收并调用函数。如果可用环境存在，则直接复用；否则将创建新环境、执行初始化（Init），然后运行处理程序（Handler）。响应返回后，该环境会被冻结。若请求突然涌入，则会同时创建多个环境。根据 Lambda 文档，单个函数每 10 秒最多可增加的环境数量也有上限（1,000 个）。

如果在运行过程中发生错误或超时，环境将被重置，下一次调用将从 Init 阶段重新开始。文档指出，此时 `/tmp` 目录的内容不会被清除。完整的请求流转过程请参见 [请求的流转路径](#/post/infra-request-journey)。

日志和指标需要像 [可观测性](#/post/cloud-observability) 中所述那样单独处理。根据 Lambda 文档示例，Lambda 会在 REPORT 日志中记录 Duration、Billed Duration、Init Duration 等值。
