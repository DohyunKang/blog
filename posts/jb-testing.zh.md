软件测试部分术语繁多，令人难以死记硬背。若将其分为三个维度，大部分内容便能各归其位：是否查看代码内部（白盒·黑盒）、在哪个阶段进行（测试级别）、以及覆盖了多少代码（覆盖率）。考试日程和报名费请查阅官方网站，此处仅整理概念与解题思路。

## 先看整体框架

| 维度 | 问题 | 代表术语 |
|---|---|---|
| 方式 | 是否查看代码内部设计？ | 白盒、黑盒 |
| 阶段 | 覆盖哪个范围？ | 单元、集成、系统、验收 |
| 尺度 | 执行了多少代码？ | 语句、判定、条件、MC/DC 覆盖率 |

[若想先了解需求 → [需求分析](#/post/jb-requirements)]

## 黑盒与白盒

黑盒测试是在不了解实现的情况下，基于“给定该输入则应产生该输出”来构造用例。这属于基于规范的测试，因此多为功能测试，通常在单元级别较少使用。白盒测试则相反，通过查看内部结构和代码来选择能遍历代码路径的输入。这也称为结构基础测试或玻璃盒测试（Glassbox）。若规范中存在但实现缺失的功能，仅靠白盒测试难以发现。

### 黑盒技术

考试中常考的技术点在于将名称与单句描述进行配对记忆。

| 技术 | 一句话描述 |
|---|---|
| 等价划分 | 将输入划分为若干等效区间，每个区间仅选取一个代表值 |
| 边界值分析 | 使用区间的边界及其紧邻的前后值 |
| 因果图 | 以图形或判定表形式表达输入（原因）与输出（结果）之间的关系 |
| 错误推测 | 依据经验指出可能出错的位置 |
| 状态迁移 | 基于状态与事件流转构造用例 |
| 比较测试 | 将相同输入应用于多个实现并比较结果 |

若以“分数≥60 即为合格”的规则为例，等价划分可划分为"≤59 区间”和"≥60 区间”两部分；边界值则需使用 59、60、61 这三个值。用代码验证如下：

```python
def grade(score, bonus):
    if score >= 60 and bonus:
        return "A"
    if score >= 60:
        return "B"
    return "C"

for s in (59, 60, 61):
    print(s, grade(s, False))
# 59 C
# 60 B
# 61 B
```

从结果可见，变化点发生在 60，这直接体现在 59 和 60 两个值的对比中。这正是边界值分析能有效捕获将 `>=` 误写为 `>` 这类 bug 的原因。

### 白盒技术

白盒测试几乎等同于“覆盖率标准”这一说法。具体依据何种标准遍历代码，即构成技术名称。下文将在覆盖率部分继续展开。其中还包含基础路径测试：从控制流图中提取独立路径进行测试，其路径数量基准为圈复杂度。

<details>
<summary>圈复杂度计算</summary>

圈复杂度 V 可通过控制流图公式 V = E - N + 2（边数 - 节点数 + 2）计算。对于包含判定（分支）节点的简单结构，其值等于判定语句数 + 1。上述 `grade` 函数包含两个 if 语句，故 V = 3，独立路径亦为三条（分别以 A、B、C 结尾）。题目通常以绘制图形并询问 V 值的形式出现。

</details>

## 测试级别

将其与开发阶段对应理解更为清晰。

| 级别 | 范围 | 关键词 |
|---|---|---|
| 单元 | 单个模块或函数 | 驱动、桩 |
| 集成 | 模块间接口 | 自底向上、自顶向下、大爆炸 |
| 系统 | 整个系统 | 功能、性能、安全 |
| 验收 | 用户/客户视角 | Alpha, Beta |

单元测试旨在验证隔离的代码是否按预期运行，若周围模块尚未就绪，则需使用替代品：模拟调用方的称为驱动（Driver），模拟被调用方的称为桩（Stub）。集成测试中，自顶向下方式需要桩，而自底向上方式则需要驱动，这一搭配在考试中频繁出现。结合 [架构模式](#/post/jb-architecture-pattern) 中的层次结构理解，便不易混淆。

验收测试是确认用户是否满足需求的阶段。通常分为在开发者环境中由用户执行的 Alpha 版，以及在真实用户环境中执行的 Beta 版进行提问。

此外还有一些仅以名称出现的概念：

- 回归测试：修改后重新验证原有功能是否仍正常工作
- 冒烟测试：快速检查构建是否能基本运行
- 性能/负载/压力测试：评估吞吐量与系统极限

回归测试和冒烟测试在频繁构建的环境中常由自动化流程执行。结合 [版本管理与构建/发布](#/post/jb-build-release) 可理解其完整流程。

## 覆盖率

覆盖率是衡量测试执行代码比例的尺度。标准越严格，所需的用例数量越多。

| 标准 | 满足条件 |
|---|---|
| 语句 (Sentence) | 所有语句至少执行一次 |
| 分支 (Decision) | 每个判断的结果（真/假）各至少出现一次 |
| 条件 | 判断内的各个条件，其真/假结果各至少出现一次 |
| 条件/分支 | 同时满足分支覆盖和条件覆盖 |
| 修改条件/决策 (MC/DC) | 证明每个条件都能独立地改变结果 |
| 多条件 | 所有条件的组合情况 |

MC/DC 通常被认为在航空等对安全性要求极高的领域中被广泛采用。路径覆盖是指遍历所有可能路径的标准。

### 用同一个函数进行比较

由于条件覆盖和分支覆盖的区别是考试中最容易混淆的知识点，因此我直接用 `grade` 函数进行了验证。

```python
# 결정 커버리지: 두 if가 각각 참/거짓이 되게
dec = [(70, True), (70, False), (50, False)]
print([grade(*c) for c in dec])   # ['A', 'B', 'C']

# 조건만 맞춘 두 케이스: score>=60 이 T/F, bonus 가 T/F
cond = [(70, False), (50, True)]
print([grade(*c) for c in cond])  # ['B', 'C']
```

第二个测试用例组中，`score >= 60` 和 `bonus` 各自都经历了真和假的情况，因此满足了条件覆盖。然而，第一个 if 语句的整体条件表达式（`score >= 60 and bonus`）从未为真，也就是说，没有任何路径能输出结果 "A"。这说明即使满足了条件覆盖，也可能无法达成分支覆盖，因此需要单独设立“条件/分支”这一标准。

<details>
<summary>解题技巧</summary>

覆盖率问题通常会给出代码或流程图，并询问“该测试集满足哪种标准”，或者“实现语句覆盖所需的最少用例数”。解题步骤如下：

1. 为每个判断列出使其结果为真和假的输入组合表。
2. 逐个代入给定的用例，标记哪些语句、分支和条件已被执行。
3. 若有遗漏项，则对应标准未满足。
4. 计算最少用例数时，将能同时覆盖真/假路径的用例尽可能合并计数。

在上述 `grade` 示例中，仅凭 `(70, True)` 这一个用例虽然能经过第一个 if 中的 A 分支，但无法经过 B 和 C 语句；若要遍历 A、B、C 全部路径，则需要三个用例。直接代入验证比死记硬背更高效。

</details>

## 常见误区

- 覆盖率达到 100% 并不意味着没有 Bug。覆盖率只说明代码是否被执行过，并不表示预期结果是否正确。
- “黑盒测试”并非因为不了解代码而进行的弱测试，而是基于需求规格说明书的测试方式；缺失的功能反而更容易被黑盒测试发现。
- “驱动桩”与“存根”容易混淆：由上层调用的称为驱动（Driver），由下层被调用的称为存根（Stub）。

## 总结

不必死记所有概念，只需记住三个表格来解题即可。当给出代码时，直接代入用例进行验证。
