서버리스는 서버가 없다는 뜻이 아니라, 서버를 켜고 끄고 늘리는 일을 클라우드가 맡아 주고 나는 함수 코드만 올리는 방식이다.

## 서버리스가 뭔지

이름이 헷갈린다. 서버는 당연히 있다. 다만 내가 서버를 빌려서 OS를 깔고 프로세스를 띄워 두는 게 아니라, 코드(함수)를 올려 두면 요청이 올 때 클라우드가 알아서 실행 환경을 만들어 돌려 주고, 요청이 없으면 내려 둔다. 그래서 "서버를 신경 쓰지 않아도 된다"는 뜻으로 부르는 이름이다.

Vercel 문서도 비슷하게 말한다. 요청마다 함수 실행(invocation)이 생기고, 트래픽이 없으면 0까지 줄어든다고 한다. AWS Lambda는 이 방식의 대표 서비스다.

[서버·클라우드 기본 → 클라우드 기초](#/post/cloud-basics)를 먼저 보면 "빌려 쓰는 서버"와 뭐가 다른지 비교하기 쉽다.

| | 서버를 직접 운영(VM 등) | 서버리스 |
|---|---|---|
| 켜 두는 것 | 서버가 계속 켜져 있음 | 요청이 올 때만 실행 |
| 늘리기 | 서버 수·크기를 내가 정함 | 요청이 늘면 환경이 자동으로 늘어남 |
| 요금 | 켜 둔 시간 기준 | 실행 횟수와 실행 시간 기준 |
| 상태 | 메모리·디스크에 둘 수 있음 | 실행이 끝나면 없어진다고 보고 짜야 함 |

## 함수가 실행되는 방식

Lambda 문서가 설명하는 흐름은 세 단계다. 환경 하나가 만들어질 때 Init, 요청을 처리할 때 Invoke, 환경을 정리할 때 Shutdown이다.

Init에서는 확장 기능을 켜고, 런타임을 띄우고, 내 코드에서 핸들러 바깥에 있는 부분(import, 설정, DB 연결 같은 것)을 실행한다. Invoke에서 핸들러가 돈다. 끝나면 환경은 바로 없어지지 않고 얼려 두었다가(freeze), 같은 함수에 요청이 또 오면 녹여서(thaw) 다시 쓴다. 문서에 따르면 몇 시간마다는 어차피 환경을 교체하니 영원히 유지된다고 믿으면 안 된다.

이 재사용 때문에 코드 위치가 의미를 갖는다. 핸들러 바깥에 둔 변수와 연결은 다음 요청에서도 살아 있을 수 있다. 문서가 권하는 대로 DB 연결 같은 건 바깥(초기화 단계)에서 만들고 재사용하는 게 보통이다.

실행해서 확인한 작은 예시는 이렇다. 핸들러 바깥은 한 번만 실행되고, 핸들러는 요청마다 실행된다.

```python
import time

time.sleep(0.2)                    # Init: 라이브러리 로드, 연결 생성 흉내
CONN = {"opened": time.time()}     # 핸들러 바깥: 환경이 살아 있는 동안 재사용
calls = 0

def handler(event, context=None):  # Invoke: 요청마다 실행
    global calls
    calls += 1
    return {"call": calls, "conn_age_ms": round((time.time() - CONN["opened"]) * 1000)}

for _ in range(3):
    print(handler({}))
    time.sleep(0.05)
```

돌려 보면 call이 1, 2, 3으로 늘고 conn_age_ms도 0, 50, 101처럼 늘었다. 연결이 요청마다 새로 만들어지지 않고 이어진다는 걸 흉내 낸 것이다. 실제 Lambda에서 돌린 건 아니고 로컬 Python 시뮬레이션이다.

## 콜드 스타트

요청이 왔는데 쓸 수 있는 환경이 없으면 새로 만들어야 한다. 코드를 내려받고, 환경을 띄우고, Init 코드를 돌린 뒤에야 핸들러가 시작된다. 이 앞쪽 시간이 콜드 스타트다. 이미 있던 환경을 재사용하면 웜 스타트라고 부른다.

Lambda 문서는 콜드 스타트가 보통 호출의 1% 미만에서 일어나고, 길이는 100ms 미만에서 1초 넘게까지 다양하다고 적는다. 호출이 뜸한 개발·테스트용 함수에서 더 자주 보인다고도 한다. 숫자는 문서의 일반 설명이고 내 함수에서 얼마나 걸릴지는 따로 재 봐야 한다.

Init에 시간을 쓰는 건 결국 내 코드다. 문서는 패키지 크기(라이브러리, 레이어), 초기화 작업량, 연결 설정 속도를 주요 요인으로 꼽는다. 줄이는 방법도 그 반대다. 필요한 라이브러리만 가져오고, 안 쓰는 경로의 객체는 필요할 때 만든다.

예측 가능한 시작 시간이 꼭 필요하면 Provisioned Concurrency라는 옵션이 있다. 환경을 미리 만들어 두는 것인데, 그만큼 켜 두는 비용 개념이 다시 들어온다. SnapStart는 초기화가 끝난 상태의 스냅샷을 저장해 두고 거기서 재개하는 방식으로 지원 범위가 정해져 있다.

## 한계

Lambda 기본 할당량에서 눈에 띈 것들이다.

| 항목 | 값 |
|---|---|
| 한 번 실행 시간 | 최대 900초(15분) |
| 메모리 | 128MB ~ 10,240MB (CPU는 메모리에 비례) |
| 동기 호출 요청·응답 크기 | 각각 6MB |
| 동시 실행 | 기본 1,000(계정·리전 기준, 증가 요청 가능) |
| 배포 패키지 | zip 압축 해제 후 250MB, 컨테이너 이미지는 10GB |
| /tmp | 512MB ~ 10,240MB |

출처는 AWS 할당량 문서이고 새 계정은 더 낮은 값으로 시작할 수 있다고 적혀 있다. 이 숫자는 바뀔 수 있어서 쓸 때 다시 보는 게 맞다.

숫자보다 더 중요한 건 사고방식이었다. 실행이 끝나면 환경이 사라질 수 있으니, 상태는 함수 안이 아니라 DB나 저장소에 둔다. 15분을 넘는 일은 쪼개거나 다른 방식(컨테이너, 워크플로)을 쓴다. 요청이 한꺼번에 몰리면 동시 실행 한도에 걸릴 수 있고, 함수 뒤의 DB가 그 동시성을 못 버티는 일도 생긴다. [DB 확장](#/post/db-scaling)이 이 얘기와 이어진다.

## 비용

요금은 요청 수와 실행 시간(할당 메모리 GB x 초)으로 붙는다. AWS 가격 페이지의 x86, 미국 동부(버지니아) 기준으로는 요청 100만 건당 0.20달러, 실행 시간 GB-초당 0.0000166667달러이고, 매달 요청 100만 건과 40만 GB-초는 무료다.

직접 계산해 본 예시다. 512MB 함수가 200ms씩 100만 번 실행되면 100만 x 0.2초 x 0.5GB = 100,000 GB-초다. 100,000 x 0.0000166667은 약 1.67달러, 요청 요금 0.20달러를 더해 약 1.87달러가 나온다. 이건 무료 구간을 빼기 전 금액이고, 위 무료 구간 안이라 실제로는 0이 된다. 다른 서비스 요금(API Gateway, 데이터 전송, 로그)은 계산에 넣지 않았다.

반대로 하루 종일 꾸준히 요청이 들어오는 서비스라면 서버를 켜 두는 쪽이 싸질 수 있다. 어디서 뒤집히는지는 트래픽과 실행 시간마다 달라서 일반 숫자를 찾지 못했다.

Vercel Functions는 계산 방식이 조금 다르다. 문서에 따르면 Active CPU, Provisioned Memory, 호출 수로 요금을 매기고, Fluid compute라는 방식은 한 인스턴스가 동시에 여러 요청을 처리해서 기다리는 시간(외부 API 응답 대기 등)을 활용한다고 한다. 그래서 콜드 스타트와 비용이 줄어든다고 설명한다.

## 쓰기 좋은 경우, 아닌 경우

- 잘 맞는 것: 가끔 호출되는 API, 웹훅 받기, 파일 올라오면 썸네일 만들기, 정해진 시간에 도는 작업, 트래픽이 들쭉날쭉한 서비스
- 덜 맞는 것: 15분 넘는 긴 작업, 항상 켜져 있어야 하는 연결(웹소켓 서버 같은 것), 지연 시간이 아주 예민한 곳, 로컬 디스크·메모리 상태에 기대는 프로그램

컨테이너와 비교하면 [Docker와 컨테이너](#/post/cloud-docker)가 "내가 환경을 통째로 정한다"에 가깝고, 서버리스는 "환경은 맡기고 코드만 낸다"에 가깝다. 둘이 섞이기도 해서 Lambda도 컨테이너 이미지를 올릴 수 있다. 자동으로 늘고 줄어드는 얘기는 [오토스케일링](#/post/infra-autoscaling)에 따로 있다.

## 흔한 오해

- 서버가 없다: 있다. 내가 관리하지 않을 뿐이다.
- 항상 싸다: 요청이 적고 짧을 때 싸다. 꾸준히 많이 쓰면 달라질 수 있다.
- 항상 느리다: 콜드 스타트는 일부 호출에만 생긴다. 다만 그 일부가 사용자에게 보이면 느리게 느껴진다.
- 상태를 변수에 저장해도 된다: 재사용되는 동안만 우연히 남는 것이다. 믿고 쓰면 안 된다.
- 무한히 늘어난다: 동시 실행 한도와 뒤쪽 시스템 한도가 있다.

요청이 들어오면 앞단(API Gateway나 CDN 같은 곳)이 받아서 함수를 호출한다. 쓸 수 있는 환경이 있으면 거기로, 없으면 새로 만들어 Init을 돌린 뒤 핸들러를 실행한다. 응답이 나가면 환경은 얼려진다. 요청이 한꺼번에 오면 환경이 여러 개 동시에 만들어지고, Lambda 문서에 따르면 함수 하나가 10초마다 늘릴 수 있는 환경 수에도 한도(1,000개)가 있다.

실행 중 오류나 타임아웃이 나면 환경이 리셋되고, 다음 호출에서 Init부터 다시 한다. 문서는 이때도 /tmp 내용은 지워지지 않는다고 적는다. 전체 요청 흐름은 [요청이 지나가는 길](#/post/infra-request-journey)에서 따로 본다.
