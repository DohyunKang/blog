バックエンドとは「リクエストを受け取り、レスポンスを返すサーバーサイドのコード」のことですが、学習を進めるにつれて REST、認証、キュー、ログ、テストなどが個別に飛び交うように見えます。そのため、リクエストが流れる順序を骨格とし、各項目がどこに該当するかを一行ずつ記述しました。さらに詳しく知りたい場合はリンクをクリックしてください。

## 関係を一覧

```
클라이언트 ──요청──▶ [API·REST: 주소+메서드로 말한다]
                         │ 누구냐 / 해도 되냐 → [인증과 인가]
                         ▼
             [요청 흐름: 미들웨어 → 라우터 → 핸들러 → DB]
                         │ 코드는 이렇게 나눈다
                         ▼
             [레이어드 아키텍처] ← 좋은 모듈 기준: [응집도·결합도]
                         │ 오래 걸리는 일은 [비동기·큐]로
                         ▼
                 응답 (실패하면 [에러 처리·로깅])

이 전부를 믿을 수 있게 확인하는 방법 = [백엔드 테스트]
```

## 1. 外側とのやり取り

**API と REST**: アドレスで対象を指し示し、HTTP メソッドで動作を伝える合意です。同じリクエストを複数回送信しても問題ないか（冪等性）は設計において非常に重要です。
[詳しく → API と REST](#/post/be-api-rest)

**認証と認可**: ログイン（誰か）と権限（できるか）は別の問題です。セッション、JWT、OAuth、RBAC がそれぞれどちらを担当するかを区別して理解しましょう。
[詳しく → 認証と認可](#/post/be-auth)

## 2. サーバー内部での流れ

**リクエストの処理フロー**: クライアントから送信されたリクエストがミドルウェアの列を通り、ルーターでハンドラへ渡され、DB を経由してレスポンスとして同じ経路を戻ってくる過程です。
[詳しく → リクエストの処理フロー](#/post/be-request-flow)

**レイヤードアーキテクチャ**: コントローラー、サービス、リポジトリでコードを階層化し、上位から下位への依存関係のみを持たせる方式です。小規模プロジェクトでは過剰になる可能性があります。
[詳しく → レイヤードアーキテクチャ](#/post/be-layered-architecture)

**モジュールの結合度と凝集度**: 一つのモジュールは一つの機能に特化し、他のモジュールとは軽く結びつくことが望ましいという基準です。
[詳しく → モジュールの結合度と凝集度](#/post/be-coupling-cohesion)

## 3. 遅くなったり間違ったりしたとき

**非同期処理とメッセージキュー**: 時間がかかる作業はキューに格納しておき、ワーカーが別途処理します。ただし、同じメッセージが複数回送信される可能性があることを覚悟しておく必要があります。
[詳しく → 非同期処理とメッセージキュー](#/post/be-async-queue)

**エラー処理とロギング**: エラーをどこでキャッチし、何を記録するかという作業です。再試行、タイムアウト、ログ形式、エラーレスポンスまで一連のセットとして扱います。
[詳しく → エラー処理とロギング](#/post/be-error-logging)

## 信頼性を高めるために

**バックエンドテスト**: 修正後に以前動作していた機能が引き続き動作するかを確認するコードです。単体テスト、統合テスト、E2E テストのうち、コストが安く高速なものを多く配置するのが基本構成です。
[詳しく → バックエンドテスト](#/post/be-testing)
