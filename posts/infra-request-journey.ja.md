ブラウザで Enter キーを押すと、1 つの要求が DNS、CDN、ロードバランサー、サーバー、キャッシュ、DB を順に通過し、各段階で時間が掛かります。遅い場合は、この経路のうちどこが遅いかを調べるのが順序でした。

## まず 1 ページで全体像を見る

```
브라우저
  │ 1. DNS: 도메인 → IP 주소
  ▼
CDN(엣지)  ── 캐시에 있으면 여기서 응답하고 끝
  │ 2. 없으면 원본 서버 쪽으로
  ▼
로드밸런서 ── 살아 있는 서버 중 하나를 고름
  │
  ▼
앱 서버 ──── 3. 캐시(Redis 등)를 먼저 확인
  │            있으면 바로 응답
  ▼
DB ───────── 4. 캐시에 없을 때만 조회
```

実際のサービスでは、これらの中の一部が抜けている場合があります。CDN が存在しないサービスもあれば、サーバーが 1 つだけなのでロードバランサーがない場所もあります。それでも大きな枠組みは似ているため、この順序で整理しておきます。

## 1. DNS: 名前をアドレスに変換する段階

ブラウザが最初に行うのは、ドメインの IP を調べることです。AWS ドキュメントで説明されている流れは以下の通りです。ブラウザが DNS リゾルバー（通常は通信事業者や企業のネットワークが運用）に問いかけ、リゾルバーがルートネームサーバー、次に .com などの TLD ネームサーバー、最後にそのドメインのオーソリティネームサーバーに順次問いかけます。答えを受けると、リゾルバーはその IP を設定された時間 동안 保存しておき、次の質問にはこのプロセスなしで即座に答えます。

そのため、同じドメインを 2 回目に探すときは速いです。保存する時間が TTL です。TTL を長くすると照会数は減りますが、サーバーの IP を変更しても、以前のアドレスがしばらく残ります。

## 2. 接続確立：TCP と TLS

IP が分かってもすぐにデータをやり取りできるわけではありません。まず TCP 接続（ハンドシェイク）を確立し、HTTPS の場合は TLS 交渉もさらに追加されます。MDN の遅延の説明でも、DNS、接続、TLS 交渉、要求送信、サーバー待機、応答受信を別々に分け、最初の要求が遅い理由はこれらの準備段階が同時に含まれているためだとしています。接続を既に開けておいた後の要求は、このコストを再び支払う必要はありません。

ここでは時間は主に距離から発生します。ハンドシェイクには往復が数回必要で、1 回の往復にかかる時間はサーバーが遠ければ長いほど長くなります。ユーザーに近い場所にサーバーを置く CDN が必要な理由はここにあります。

## 3. CDN: 近場で代わりに答える

MDN の説明によると、CDN は複数の地域に分散したサーバーの集合体であり、各サーバーがデータの複製を持っているため、最も近い場所が要求を受け付けます。画像、CSS、JS など、全員に同じファイルが必要な場合にこの方式は特に適しています。エッジに複製があれば（キャッシュヒット）、そこで処理が終わり、なければ（ミス）オリジンサーバーまで行ってデータを取得し、保存しておきます。これにより、オリジンサーバーへの要求数も同程度減少します。

MDN が付け加えた注意点も覚えておく価値があります。CDN は外部依存関係を 1 つ増やすものであり、新しいドメインに接続するために DNS 照会と接続コストが追加されるため、むしろ遅くなることもあるのだそうです。必ず速くなるわけではありません。

[詳細 → CDN とキャッシュ](#/post/infra-cdn-cache)

## 4. ロードバランサー：どのサーバーに送るか選ぶ

オリジン側へ来た要求はロードバランサーが受け取ります。AWS ドキュメントを基準にすると、ロードバランサーは流入するトラフィックを複数のターゲット（インスタンス、コンテナなど）に分けて送り、ターゲットの状態を継続的に確認して正常な場所へのみ送ります。サーバーを追加したり削除したりしても要求の流れが途切れないようにするのが目的です。暗号化・復号化もロードバランサーに任せることができるとのことです。

そのため、1 つのサーバーが落ちてもユーザーは気づかずに通り過ぎることができます。サーバー台数を増やすときは [自動スケーリング](#/post/infra-autoscaling) と組み合わせ、新しく立ち上がったサーバーが自動的にロードバランサーに登録されます。

[詳細 → ロードバランサー](#/post/infra-load-balancer)

## 5. アプリサーバーとキャッシュ、DB

要求がアプリサーバーに到達するとコードが実行されます。認証を確認し、必要なデータを検索します。この際によく使うデータは Redis などのキャッシュに置いてまず確認します。あればメモリから即座に取り出して応答し、なければ DB を照会した後に結果をキャッシュに入れます。

DB 照会は通常ここで最もコストのかかる作業です。同じ質問に対して毎回ディスクを検索しないようにするためにキャッシュを前面に置きます。照会自体が遅い場合は [インデックス](#/post/db-index) が存在するかから確認します。サーバー内で要求がどのように流れるかは別途整理しました。

[詳細 → キャッシュと Redis](#/post/db-cache-redis) · [詳細 → サーバー内の要求フロー](#/post/be-request-flow)

## 6. 遅延はどこで蓄積するのか

段階ごとに大まかにどこで時間が掛かるかを表にまとめました。数字は意図的に記載していません。環境によって差が大きすぎて、1 つの値で語ることは難しいからです。

| 段階 | 時間が掛かる理由 | 削減方法 |
|---|---|---|
| DNS | リゾルバーが複数のサーバーに順次問いかける | リゾルバーキャッシュ (TTL)、ドメイン数を減らす |
| TCP/TLS | 往復が複数回、距離に比例 | 接続の再利用、ユーザーに近い場所に置く (CDN) |
| CDN | ミス時にオリジンまで往復 | キャッシュ可能な応答にする |
| ロードバランサー | 通常短く、サーバー選択程度 | 正常なサーバーのみ受け付けるようチェック |
| アプリサーバー | コード処理、外部呼び出し | 不要な呼び出しを減らす、キャッシュ |
| DB | ディスク照会、クエリの形状 | インデックス、キャッシュ、クエリ整理 |

web.dev は、TTFB（First Byte Time：最初のバイトが到着するまでの時間）を、リダイレクト、DNS、接続と TLS 交渉、そしてリクエストから最初のバイトの到着までの合計として定義しています。大まかな基準としては 0.8 秒以内であれば良好で、1.8 秒を超えると悪化しているとみなされます。ただし、これは「多くのサイトで使える目安」として記載されています。

## 実際に測定した値

理論だけ見ていたため、自分の PC で実際に測定してみました。Python のソケットを使って example.com に対して DNS 問い合わせ、TCP 接続、HTTP リクエスト（最初のバイト）を段階的に計測しました。HTTPS ではなくポート 80 の平文 HTTP を使用したため、TLS 部分は含まれていません。

```
DNS 11ms / TCP 153ms / 첫 바이트 145ms / 다운로드 2ms / 합계 311ms
DNS 10ms / TCP 113ms / 첫 바이트 120ms / 다운로드 0ms / 합계 243ms
DNS 10ms / TCP 114ms / 첫 바이트 119ms / 다운로드 0ms / 합계 243ms
```

DNS は 10ms 前後で短く、TCP 接続と最初のバイトの待機時間がそれぞれ 110〜150ms で長かったです。ダウンロードは小さなページのためほとんどありませんでした。「サーバーが遠ければ距離のために接続と待機が大半を占める」という言葉が数字として現れました。ただし、これは私の PC の位置やその瞬間のネットワーク状態による値であり、他の場所では全く異なる可能性があります。DNS が速かったのは既にキャッシュに存在していたためかもしれません。

<details>
<summary>詳しい解説：測定コードと読み方</summary>

```python
import socket, time, sys
host = sys.argv[1]
t0 = time.perf_counter()
ip = socket.getaddrinfo(host, 80, socket.AF_INET)[0][4][0]   # DNS
t1 = time.perf_counter()
s = socket.create_connection((ip, 80), timeout=10)           # TCP
t2 = time.perf_counter()
s.sendall(f"GET / HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n\r\n".encode())
s.recv(1)                                                      # 첫 바이트
t3 = time.perf_counter()
while s.recv(65536):                                           # 나머지 다운로드
    pass
t4 = time.perf_counter()
ms = lambda a, b: round((b - a) * 1000)
print(f"DNS {ms(t0,t1)}ms / TCP {ms(t1,t2)}ms / 첫 바이트 {ms(t2,t3)}ms / 다운로드 {ms(t3,t4)}ms / 합계 {ms(t0,t4)}ms")
```

上記のコードを 3 回実行した結果が前述の値です。「最初のバイト」はリクエストを送った後、サーバーが最初の一文字を返すまでの時間であるため、サーバー処理時間と往復遅延（RTT）が共に含まれています。両方を分離するにはサーバー側のログやタイミングヘッダーが必要です。

TLS まで測定しようと HTTPS バージョンも試しましたが、この PC で証明書検証エラーが発生したため TLS 部分は測定しませんでした。検証を無効にする方法は使用していません。

ブラウザでは開発者ツールの Network タブでリクエストの一つをクリックすると、同じ段階（DNS、接続、TLS、待機、ダウンロード）が分かれて表示されます。コードを直接書かなくてもこちらの方が便利です。

## よくある誤解

- サーバー側のコードだけが速ければよい：サーバー処理は経路の一部に過ぎません。前述の DNS や接続、CDN ミス、後続の DB などがより大きな要因となることも多いです。
- CDN を使うと必ず速くなる：キャッシュ可能なレスポンスでなければ効果はなく、上記のようにドメインが一つ増えるだけで逆に遅くなることもあります。
- キャッシュをオンにしておくだけでよい：キャッシュ内の値は陳腐化する可能性があるため、いつ破棄するか（TTL）も同時に設定する必要があります。
- ロードバランサーがあればサーバーは死なない：一台が落ちても他のサーバーが受け付けるのは事実ですが、すべてのサーバーが同じ原因で遅くなればロードバランサーでも解決できません。

遅いサービスに遭遇した場合は、上記の表の順序通りに各段階ごとに時間を計測することが先です。勘で DB だけを疑うと間違った箇所を修正しやすくなります。この段階別の測定は [観測可能性](#/post/cloud-observability) の項目でさらに続きます。
