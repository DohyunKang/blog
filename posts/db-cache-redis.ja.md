キャッシュは、本元のデータから読み取る高価な作業を減らすために、コピーを高速な場所に一時的に保存する仕組みであり、Redis はそのコピーをキーと値として保持しているサーバーです。難しいのはデータを格納することではなく、コピーが本元と異なった場合の処理です。

## まず簡単な話で

机のそばによく見る本を並べておくのと似ています。図書館（DB）まで行く必要がないため高速です。ただし、本の数は限られており、図書館で改訂版が出ても自分の持っているのは古い版になります。そのため、「どれくらい長く置くか」「いつ片付けるか」「場所が満杯になったら何を捨てるか」こそがキャッシュの本質と言えます。

バックエンドでは、[リクエストの処理フロー](#/post/be-request-flow)の中で、ハンドラーが DB を呼び出す前にキャッシュを先に確認するように実装します。DB 側の速度は [インデックス](#/post/db-index)でも向上させることができますが、インデックスは DB 内での検索コストを減らすものであり、キャッシュはそもそも DB にアクセスさせない点で異なります。

## キャッシュの中身は何か

キーを使って値を検出します。値は、DB からの問い合わせ結果を文字列（JSON など）に変換したものが一般的です。キーは `user:1` のように、何を入れたかがわかるように命名します。Azure ドキュメントの例でも `MyEntity:{id}` という形式のキーを使用しています。

読み込み時に起こることは以下の 2 つのうちの一つです。キャッシュがあればヒット（hit）、なければミス（miss）です。効果はヒット率に依存します。Redis は `INFO` コマンドの `keyspace_hits` と `keyspace_misses` を使って比率を計算するよう案内しています。Azure ドキュメントにも、ほとんどのリクエストがミスになる場合、キャッシュを確認して充填する手間の方がむしろ損であるという記述もあります。

## cache-aside

最も一般的な戦略です。キャッシュが自動的に DB からデータを読み取るのではなく、アプリケーションコードが直接キャッシュと DB を往復します。Azure Architecture Center の説明では 3 つのステップに分かれています。

1. キャッシュから読み込む。
2. 存在しない場合（miss）DB から読み込む。
3. 読み込んだ値をキャッシュに格納して返す。

書き込み時には DB を更新し、該当するキャッシュ項目を無効化（invalidate）します。次の読み込みでミスが発生すると、新しい値が充填されます。

似た名前の read-through、write-through、write-behind もあります。これらはキャッシュシステムが DB の読み書きを代行する方式です。ドキュメントによれば、cache-aside はキャッシュがその機能を提供しない場合、アプリケーションがそれを模倣するアプローチです。

### 実際に試してみたもの

Redis をインストールせずに、同じ動作を Python の辞書と偽のタイマーを使って再現しました。TTL 期限切れは「読み込む際に時刻を確認し、過ぎている場合は破棄する」という方式です。

```python
class Clock:
    def __init__(self): self.t = 0
    def now(self): return self.t

class Cache:
    def __init__(self, clock): self.d, self.c = {}, clock
    def get(self, k):
        v = self.d.get(k)
        if v and v[1] > self.c.now(): return v[0]
        self.d.pop(k, None)
        return None
    def set(self, k, val, ttl): self.d[k] = (val, self.c.now() + ttl)
    def delete(self, k): self.d.pop(k, None)

clock = Clock(); db = {1: "kim"}; db_reads = 0; cache = Cache(clock)

def read_user(uid):
    global db_reads
    v = cache.get(f"user:{uid}")
    if v is not None: return v
    db_reads += 1
    v = db[uid]
    cache.set(f"user:{uid}", v, ttl=60)
    return v

def update_user(uid, name):
    db[uid] = name                 # DB 먼저
    cache.delete(f"user:{uid}")    # 그다음 캐시 삭제
```

実行結果は以下の通りでした。

| 状況 | 結果 |
|---|---|
| 同じユーザーを 5 回読み込む | DB 読み込み 1 回 |
| `update_user` で修正した後、読み込む | 新しい値 (lee)、DB 読み込み累積 2 回 |
| キャッシュを介さずに DB を変更し、TTL 内に読み込む | 古い値 (lee) が返る |
| 61 秒後に読み込む | 新しい値 (park)、DB 読み込み累積 3 回 |

3 つ目の行はキャッシュの弱点をそのまま示しています。誰かが DB を直接変更すると、TTL が切れるまで古くさい値が返ってきます。Azure ドキュメントでも、cache-aside は一貫性を保証せず、外部から DB を変更した場合、項目が再ロードされるまで反映されない旨が記載されています。

<details>
<summary>順序を逆にした場合の出来事</summary>

Azure ドキュメントでは「DB を先に修正し、その後にキャッシュを削除する」とあり、順序の重要性について別途記述されています。キャッシュを先に削除するとこのようなことが起こります。

1. 書き込み側がキャッシュ項目を削除する。
2. その隙に別のリクエストが読み込みに来てミスとなり、DB からまだ古い値を読み取る。
3. 書き込み側が DB を新しい値に変更する。
4. 読み込み側が古い値をキャッシュに入れる。

同じ順序でコードを実行すると、キャッシュには `old`、DB には `new` が残りました。その後は TTL が切れるまで古くさい値が続いて返ってきます。これは同時に起こる出来事を一行に並べたシミュレーションであり、実際のサーバーでどれほど頻繁に発生するかはわかりません。順序が重要であることは確認できました。

</details>

## TTL

TTL は「このキーは何秒後に削除するか」という値です。Redis では `EXPIRE key seconds` で設定し、`TTL key` で残りの時間を確認します。公式ドキュメントの例では、`SET mykey "Hello"` の後に `EXPIRE mykey 10` を実行すると、`TTL` が 10 になります。

いくつか注意すべき点があります。

- `SET` 명령어로 동일한 키를 다시 설정하면 TTL이 사라집니다 (TTL 이 -1 로 되어 만료 없음). 값을 갱신하면서 TTL 을 유지하려면 다시 설정해야 합니다.
- `INCR`, `LPUSH`, `HSET` 처럼 값을 변경하되 전체를 교체하지 않는 명령어는 TTL 에 영향을 주지 않습니다.
- 만료 처리는 두 가지 방식으로 나뉩니다. 접근 시점에 시간이 지났으면 삭제하는 방식 (passive) 과, 접근이 없는 키 중 가끔 무작위로 몇 개를 골라 삭제하는 방식 (active) 이 있습니다. 위의 파이썬 코드는 전자의 방식을 흉내 낸 셈입니다.
- 만료 시각은 절대 시간 (유닉스 타임스탬프) 으로 저장되며, 컴퓨터 시계가 갑자기 바뀌면 그에 맞춰 만료 시간이 조정됩니다.

TTL 의 길이는 정해진 답이 없습니다. Azure 문서에서는 너무 짧으면 지속적으로 DB 를 읽게 되고, 너무 길면 낡은 데이터가 남는다고 합니다. 변경 빈도와 낡아도 괜찮은지 여부에 따라 결정합니다. 예제 코드는 기본 5 분을 사용합니다.

## 공간 부족 시 (eviction)

캐시는 메모리가 한정되어 있습니다. Redis 는 `maxmemory` 로 한도를 설정하고, 이를 초과하면 `maxmemory-policy` 에 따라 키를 삭제합니다. 64 비트 환경에서 `maxmemory` 의 기본값은 0 이며, 이는 제한이 없음을 의미합니다.

| 정책 | 동작 |
|---|---|
| `noeviction` | 삭제를 하지 않습니다. 새 데이터를 넣는 명령어에 오류가 발생합니다. 읽기는 가능합니다. |
| `allkeys-lru` | 가장 오랫동안 사용되지 않은 키부터 삭제합니다. |
| `allkeys-lfu` | 가장 적게 사용된 키부터 삭제합니다. |
| `allkeys-random` | 임의의 키를 삭제합니다. |
| `volatile-*` | TTL 이 설정된 키만 대상으로 위 방식을 적용합니다. `volatile-ttl` 은 남은 시간이 짧은 키부터 삭제합니다. |

공식 문서에서는 일부 키가 훨씬 더 자주 읽히는 일반적인 경우라면 `allkeys-lru` 가 무난한 기본값이라고 권장합니다. `volatile-*` 정책은 TTL 이 걸린 키가 하나도 없으면 `noeviction` 과 유사하게 동작합니다. 캐시용 데이터와 삭제해서는 안 되는 데이터를 하나의 인스턴스에 함께 둘 때 사용하는 정책이나, 문서는 가능하면 인스턴스를 분리하라고 합니다.

LRU 는 정확한 계산을 수행하는 것이 아니라, 무작위로 몇 개의 키를 추출하여 그중 가장 오래된 것을 삭제하는 근사 방식입니다. 문서 기준 `maxmemory-samples` 의 기본 예시는 5 이며, 이를 10 로 올리면 실제 LRU 에 더 가까워집니다.

## Redis 자료구조

Redis 는 값에 문자열만 저장하는 저장소가 아니라 자료구조 서버 (data structure server) 로 소개됩니다. 공식 문서에서 꼽는 일반 목적 타입은 다음과 같습니다.

| 타입 | 문서 설명 | 용도 |
|---|---|---|
| String | 바이트 배열. 가장 기본 | 캐시 값, 카운터 |
| Hash | 필드-값 쌍의 집합, 딕셔너리와 유사 | 객체를 필드별로 관리 |
| List | 삽입 순서대로 정렬된 문자열 | 최근 목록, 큐 |
| Set | 중복 없는 문자열 모음. 추가·삭제·확인이 원소 수와 무관하게 O(1) | 중복 제거, 태그 |
| Sorted set | 점수 순으로 정렬되는 중복 없는 문자열 | 순위표 |
| Stream | 추가만 되는 로그처럼 동작 | 이벤트 기록 |

이 외에도 JSON, 지오 (Geo), 비트맵, HyperLogLog 등도 있습니다. 캐시 용도로는 String 하나로 대부분 해결되며, 자료구조가 의미를 갖는 것은 캐시를 넘어 Redis 를 다른 용도로 사용할 때입니다. 예를 들어 EXPIRE 문서에는 사용자 페이지 방문을 List 에 `RPUSH` 하고 `EXPIRE ... 60` 을 적용하는 "탐색 세션" 패턴이 소개되어 있습니다. 60 초 이상 쉬면 키가 사라져 새로운 세션이 됩니다.

DB 종류 속에서 Redis 가 어디쯤인지 는 [NoSQL 종류와 선택](#/post/db-nosql)에서 이어서 봅니다.

## 흔한 오해

캐시를 사용하면 무조건 빨라진다고 생각하기 쉽습니다. hit 비율이 낮으면 이득이 없습니다. 한 번만 읽고 마는 데이터, 계속 바뀌는 데이터는 캐시와 맞지 않습니다.

TTL 이 있으니 일관성 문제는 알아서 해결된다는 생각도 합니다. TTL 은 낡은 값이 영원히 남지 않도록 하는 안전망이며, 그 시간 동안에는 낡은 값이 유효합니다. 수정 직후 바로 최신 값이 필요한 화면이라면 cache-aside 대신 write-through 를 검토하라고 Azure 문서에 적혀 있습니다.

민감한 데이터를 캐시에 둬도 된다는 오해도 있습니다. 여러 사용자나 앱이 캐시를 공유하면 부적절할 수 있으므로, 보안 관련 데이터는 원본에서 직접 가져오라는 것이 같은 문서의 권고입니다.

캐시가 죽으면 서비스도 죽는다고 단정할 수도 없습니다. 캐시를 먼저 확인하고 miss 일 때처럼 DB 로 가는 경로로 짜두면 느려질 뿐 동작은 한다고 문서에 말합니다. 다만 그때 DB 가 몰린 요청을 견디는지 여부는 별도로 확인해야 합니다. DB 자체를 여러 대로 늘리는 이야기는 [복제와 샤딩](#/post/db-scaling)에서 다루고, 웹 앞단의 캐시는 [CDN 과 캐싱 계층](#/post/infra-cdn-cache)에서 다룹니다.
