빅데이터분석기사 필기의 데이터 수집·저장 단원을 정리했다. 분석 계획에서 "어떤 데이터가 필요한가"를 정했다면([자세히 → 분석 과제 정의와 분석 계획](#/post/bd-planning)), 이 단원은 그걸 실제로 가져와서 어디에 쌓느냐를 다룬다. 시험에서는 용어를 보고 개념을 고르는 문제가 많아서, 개념마다 "이게 뭐고 뭐랑 헷갈리는지"를 중심으로 적었다.

시험 일정과 응시료는 공식 사이트에서 확인하면 된다. 이 글은 단원 핵심과 자주 나오는 유형만 다룬다. 전체 흐름은 [자세히 → 빅데이터분석기사 지도](#/post/bd-map)에 있다.

## 수집은 어디서, 어떤 모양으로

먼저 두 가지를 나눠서 본다. 데이터가 어디서 오는가, 그리고 어떤 모양인가.

| 기준 | 구분 | 예 |
| --- | --- | --- |
| 출처 | 내부 데이터 | 회사 DB의 주문·고객 테이블, 서비스 로그 |
| 출처 | 외부 데이터 | 공공 데이터, 소셜 미디어, 웹 페이지 |
| 모양 | 정형 | 행과 열이 정해진 테이블(RDB, CSV) |
| 모양 | 반정형 | 구조는 있는데 고정된 표는 아닌 것(JSON, XML, 로그) |
| 모양 | 비정형 | 텍스트 본문, 이미지, 영상, 음성 |

내부 데이터는 가져오기 쉽고 품질을 어느 정도 통제할 수 있다. 외부 데이터는 쉽게 구하지만 형식도 품질도 제각각이라 정리 비용이 든다. 시험에서 "내부냐 외부냐", "정형이냐 반정형이냐"를 예시 보고 고르라는 유형이 자주 나온다. JSON이 반정형이라는 것만 확실히 잡아 두면 절반은 맞는다.

개인정보가 섞인 데이터를 수집할 때의 주의점은 [자세히 → 빅데이터 개요와 활용](#/post/bd-overview)에서 따로 정리했다.

## 수집 방식: 배치와 스트리밍

수집 방식은 크게 한꺼번에 가져오느냐, 흘러오는 대로 받느냐로 갈린다.

배치는 정해진 시간에 모아서 가져온다. 하루에 한 번 주문 테이블을 통째로 복사하는 식이다. 구현이 단순하고 대량 처리에 좋지만, 가져오는 사이에 생긴 변화는 다음 배치까지 모른다.

스트리밍은 발생하는 즉시 받는다. 센서 값, 클릭 로그처럼 계속 생기는 데이터에 쓴다. 이 쪽의 대표 도구가 Apache Kafka다. Kafka 소개 문서는 이벤트 스트리밍을 데이터베이스·센서·앱 같은 출처에서 실시간으로 데이터를 모으고, 오래 보관하고, 도착하는 대로 또는 나중에 처리하고, 다른 시스템으로 보내는 일로 설명한다. 용어도 시험에 나올 만하다.

| 용어 | 뜻 |
| --- | --- |
| 토픽(topic) | 이벤트가 보관되는 이름 붙은 묶음. 폴더 같은 것 |
| 프로듀서(producer) | 이벤트를 쓰는 쪽 |
| 컨슈머(consumer) | 이벤트를 읽는 쪽. 필요하면 다시 읽을 수 있다 |
| 파티션(partition) | 토픽을 나눈 단위. 같은 키의 이벤트는 같은 파티션에 들어가고, 그 안에서는 순서가 유지된다 |
| 보존(retention) | 토픽마다 정하는, 오래된 이벤트를 지우기까지의 기간 |

쓰는 쪽과 읽는 쪽이 토픽을 사이에 두고 떨어져 있다는 점이 핵심이다. 그래서 수집기가 느려도 쓰는 쪽이 막히지 않고, 읽는 쪽이 여럿이어도 된다.

[자세히 → 비동기 처리와 큐](#/post/be-async-queue)에 같은 구조를 백엔드 관점에서 적어 뒀다.

## ETL과 크롤링

ETL은 추출(Extract), 변환(Transform), 적재(Load)의 약자다. 출처에서 꺼내고, 쓸 수 있는 모양으로 고치고, 목적지에 넣는다. 순서가 중요하다. 순서를 바꿔 먼저 적재하고 나중에 변환하는 방식은 ELT로 따로 부른다. 시험에서 ETL 세 글자가 각각 무엇인지, 어느 단계에서 중복 제거·형식 통일이 일어나는지를 묻는다. 답은 변환 단계다.

작은 예를 직접 돌려 봤다. CSV를 읽어 중복을 지우고 빈 가격을 채운 뒤, SQLite에 넣고 SQL로 집계한다.

```python
import pandas as pd, sqlite3, io

src = pd.read_csv(io.StringIO("id,name,price\n1,a,1000\n2,b,\n3,a,1000\n3,a,1000\n"))
# Extract: 위에서 읽은 src
# Transform: 중복 제거, 빈 값 처리
t = src.drop_duplicates().assign(price=lambda x: x.price.fillna(0).astype(int))
# Load: DB에 적재
con = sqlite3.connect(":memory:")
t.to_sql("product", con, index=False)
print(pd.read_sql("select name, sum(price) s, count(*) n from product group by name", con).to_dict("records"))
print(len(src), len(t))
```

출력은 `[{'name': 'a', 's': 2000, 'n': 2}, {'name': 'b', 's': 0, 'n': 1}]`과 `4 3`이다. 4행이 3행이 됐다. 가격이 비어 있던 b를 0으로 채운 건 예시를 돌리려는 것이다. 실제로 빈 값을 0으로 채울지는 분석 목적에 따라 다르고, 그건 [자세히 → 데이터 전처리](#/post/bd-preprocessing)에서 다룬다.

크롤링은 웹 페이지를 프로그램이 돌며 내려받아 필요한 부분을 뽑아내는 수집 방식이다. 외부 데이터 중 정형 형태로 제공되지 않는 것을 가져올 때 쓴다. 시험 관점에서는 "웹 문서를 자동으로 수집" 정도의 정의와, 공개 API가 있으면 크롤링보다 API를 쓰는 편이 안정적이라는 상식 수준이면 된다. 사이트마다 이용 약관과 수집 허용 범위가 다르니 실제로 할 때는 그쪽 규정을 먼저 본다.

## 저장: 데이터 모양에 맞는 그릇

저장 기술은 데이터 모양과 쓰는 방식에 따라 고른다.

| 저장소 | 어울리는 데이터 | 특징 |
| --- | --- | --- |
| RDB | 정형, 관계가 분명한 것 | 스키마가 먼저 있고 SQL로 조회. 트랜잭션이 강하다([자세히 → 관계형 DB와 SQL](#/post/db-rdb-sql)) |
| NoSQL | 반정형·비정형, 스키마가 자주 변하는 것 | 종류가 여럿([자세히 → NoSQL 종류와 선택](#/post/db-nosql)) |
| 분산 파일 시스템(HDFS) | 아주 큰 파일 | 여러 서버에 쪼개 저장 |

### HDFS

Hadoop 공식 문서의 HDFS 설계 설명에서 시험에 연결되는 부분만 골랐다.

- 마스터 역할의 NameNode가 파일 이름 공간(namespace)과 어느 블록이 어느 DataNode에 있는지를 관리한다.
- DataNode는 실제 블록을 저장하고 읽기·쓰기 요청에 응한다.
- 파일은 한 번 쓰고 여러 번 읽는(write-once-read-many) 모델이다. 닫은 뒤에는 추가(append)와 잘라내기(truncate)로만 바뀐다.
- 낮은 지연보다 높은 처리량을 우선한다. 배치 처리에 맞춘 설계다.
- 블록은 크게 잡는다. 문서는 전형적인 크기로 128MB를 언급한다. 파일마다 설정할 수 있다.
- 복제본은 흔히 3개를 두며, 파일을 만들 때 정하고 나중에 바꿀 수 있다.
- 데이터를 계산 쪽으로 옮기기보다 계산을 데이터 옆에서 돌리는 편이 네트워크 부담이 적다.

"NameNode는 메타데이터, DataNode는 실제 데이터"를 바꿔 쓴 보기에 속지 않으면 된다. 또 HDFS는 작은 파일을 자주 수정하는 용도가 아니라 큰 파일을 한 번 쓰고 읽는 용도라는 점이 오답 소거에 쓰인다.

### NoSQL

NoSQL은 하나의 기술이 아니라 종류 묶음이다. 키-값, 문서, 컬럼 패밀리, 그래프로 나누는 것이 일반적이다. 각각 언제 쓰는지는 위 링크에 적었으니 여기서는 문서형 하나만 짚는다.

MongoDB 문서는 데이터를 BSON 문서로 저장하고, 같은 컬렉션 안의 문서라도 필드나 자료형이 같을 필요가 없다고 설명한다. 필드를 추가할 때 기존 문서를 다시 쓰거나 마이그레이션을 돌리지 않아도 된다. 값 안에 문서나 배열을 중첩할 수 있고, 같이 접근하는 데이터는 같이 저장한다는 원칙으로 설계한다. 필요하면 스키마 검증으로 구조를 강제할 수도 있다. 시험에서 "스키마가 유연하다"는 NoSQL의 대표 특징으로 나오고, 이 문서가 그 근거가 된다.

<details>
<summary>RDB와 NoSQL, 어느 쪽을 고르나 (정리)</summary>

- 테이블 간 관계와 정합성이 중요하면 RDB.
- 구조가 제각각이거나 자주 바뀌면 문서형 같은 NoSQL.
- 둘 중 하나만 써야 하는 것은 아니다. 한 서비스 안에서 나눠 쓰기도 한다.
- 시험은 보통 "특징 보기 중 맞는 것" 형태라서, RDB는 스키마 고정·SQL·트랜잭션, NoSQL은 스키마 유연·수평 확장 쪽으로 묶어 외우면 된다.
</details>

## 품질 관리: 네 가지를 센다

수집하고 저장한 데이터는 쓰기 전에 품질을 본다. 개념으로는 완전성(빠진 값이 없는가), 유일성(중복이 없는가), 유효성(허용 범위·형식 안인가), 일관성(같은 것을 같게 적었는가) 같은 항목이 있다. 이름은 자료마다 조금씩 다르게 부르니 보기에서 뜻을 보고 판단한다.

이 네 가지가 코드로는 각각 한 줄이라는 걸 직접 확인했다.

```python
import pandas as pd, io

raw = io.StringIO("""id,age,city,amount,date
1,25,Seoul,1200,2026-01-03
2,,Busan,800,2026-01-04
2,,Busan,800,2026-01-04
3,41,seoul,-50,2026-01-05
4,200,Daegu,3000,2026/01/06
5,33,Incheon,,2026-01-07
""")
df = pd.read_csv(raw)

print(df.isna().mean().round(2).to_dict())          # 완전성: 열별 결측 비율
print(df.duplicated().sum())                         # 유일성: 중복 행 수
print(df['city'].str.lower().str.strip().value_counts().to_dict())  # 일관성: 표기 통일 후 집계
print(((df.age < 0) | (df.age > 120)).sum(), (df.amount < 0).sum())  # 유효성: 범위 밖
d = pd.to_datetime(df['date'], errors='coerce', format='%Y-%m-%d')
print(d.isna().sum())                                # 유효성: 날짜 형식 불일치
```

출력은 다음과 같았다.

| 점검 | 결과 |
| --- | --- |
| 열별 결측 비율 | age 0.33, amount 0.17, 나머지 0 |
| 중복 행 | 1 |
| city 표기 통일 후 집계 | seoul 2, busan 2, daegu 1, incheon 1 |
| 나이 범위 밖 / 음수 금액 | 1 / 1 |
| 날짜 형식 불일치 | 1 |

`Seoul`과 `seoul`은 눈으로는 같은 도시인데 그대로 집계하면 서로 다른 값이 된다. 소문자로 통일하고 나서야 seoul이 2로 묶였다. 이런 게 일관성 문제다. 나이 200과 음수 금액은 값 자체는 있지만 말이 안 되는 경우라서 완전성이 아니라 유효성에서 걸린다. 날짜 `2026/01/06`은 다른 행과 구분자가 달라서 형식이 맞지 않는 것으로 잡혔다.

여기서 하나 구분해 둔다. 이 단계는 문제를 찾아 세는 단계다. 찾은 결측·이상값을 어떻게 처리할지는 전처리의 일이다.
