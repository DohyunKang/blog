계층 모델은 통신을 층으로 나눠서, 각 층이 자기 헤더만 책임지고 나머지는 모르게 만든 구조다. 보낼 때는 위에서 아래로 헤더가 한 겹씩 붙고, 받을 때는 아래에서 위로 한 겹씩 벗겨진다.

[개요](#/post/cs-network)에서 표로 훑은 내용을 여기서는 한 단계 더 들어가 본다. 층별로 정확히 뭘 하는지, 헤더가 어떻게 붙는지, 두 모델이 왜 둘 다 남았는지를 다룬다.

## 왜 층으로 나누나

네트워크 통신에는 신호를 선에 싣는 일, 옆 기기까지 보내는 일, 여러 네트워크를 건너 길을 찾는 일, 프로세스까지 전달하는 일, 앱끼리 말을 맞추는 일이 한꺼번에 있다. 이걸 한 덩어리로 만들면 Wi-Fi를 유선으로 바꿀 때 웹 브라우저까지 고쳐야 한다. 층으로 나누면 한 층을 통째로 갈아 끼워도 위아래는 그대로 쓴다.

각 층은 자기 아래층이 주는 서비스만 쓰고, 상대편의 같은 층과 약속된 규칙(프로토콜)으로 대화한다. 실제 데이터는 아래층으로 내려갔다가 올라오지만, 논리적으로는 같은 층끼리 직접 말하는 셈이다.

## OSI 7계층

OSI는 ISO가 만든 참조 모델로, 1984년에 ISO 7498로 나왔다고 한다. 층은 일곱 개다.

| 층 | 이름 | 데이터 단위(PDU) | 하는 일 |
|---|---|---|---|
| 7 | 응용 | 데이터 | 사용자와 맞닿은 프로토콜(HTTP 등) |
| 6 | 표현 | 데이터 | 형식 변환, 암호화, 압축 |
| 5 | 세션 | 데이터 | 대화의 시작·관리·종료 |
| 4 | 전송 | 세그먼트 | 끝과 끝 사이 전달, 분할·확인응답·다중화 |
| 3 | 네트워크 | 패킷 | 주소 지정, 여러 네트워크를 건너는 경로 선택 |
| 2 | 데이터 링크 | 프레임 | 바로 이웃한 두 노드 사이 전달, 오류 검출 |
| 1 | 물리 | 비트 | 전기·전파·빛 신호로 비트 전송 |

데이터 단위 이름이 층마다 다르다는 점이 시험 문제로 자주 나오는 부분이지만, 개념으로 보면 "그 층이 다루는 덩어리의 이름"일 뿐이다. 전송 계층의 덩어리를 세그먼트(TCP) 또는 데이터그램(UDP)이라 부르고, 네트워크 계층 덩어리를 패킷이라 부른다.

[자세히 → TCP와 UDP](#/post/net-tcp-udp)는 4층이 구체적으로 어떻게 신뢰성을 만드는지를 따로 다룬다.

## TCP/IP 4계층

실제 인터넷이 쓰는 건 TCP/IP다. RFC 1122의 1.1.3절은 프로토콜 묶음을 위에서부터 응용, 전송, 인터넷, 링크 네 층으로 설명한다. 인터넷 계층에는 IP·ICMP·IGMP가, 전송 계층에는 TCP·UDP가 있고, 링크 계층은 바로 연결된 네트워크와의 인터페이스를 맡는다.

대응은 대략 이렇다. TCP/IP의 응용 계층이 OSI 5~7층을, 전송이 4층을, 인터넷이 3층을, 링크가 1~2층을 덮는다. 딱 맞아떨어지는 건 아니라서 "대략"이라고 해야 한다.

| OSI | TCP/IP | 대표 프로토콜 |
|---|---|---|
| 5·6·7 | 응용 | HTTP, DNS, SMTP |
| 4 | 전송 | TCP, UDP |
| 3 | 인터넷 | IP, ICMP |
| 1·2 | 링크 | 이더넷, Wi-Fi |

OSI 쪽은 처음부터 층의 역할을 엄밀하게 정의하려는 참조 모델이었고, TCP/IP는 미 국방부 지원으로 비슷한 시기에 만들어진 더 느슨한 구조라고 알려져 있다. 결과적으로 OSI 프로토콜은 널리 쓰이지 못했고 인터넷은 TCP/IP 위에 올라갔다. 그래서 7계층은 이름과 개념을 설명하는 공용어로, 4계층은 실제 구현의 모양으로 남았다.

RFC 1122 1.3.1절에는 엄격한 계층화가 프로토콜 묶음에도, 권장 구현 방식에도 "불완전한 모델"이라는 말이 있다. 실제 구현은 층 경계를 깨고 자료구조를 공유하는 경우가 많다고도 적혀 있다. 층 모델을 지키지 않으면 안 되는 법칙처럼 외울 필요는 없다.

## 캡슐화: 헤더가 한 겹씩 붙는다

보낼 때 각 층은 위에서 받은 덩어리 앞에 자기 헤더를 붙여서 아래로 넘긴다. 이게 캡슐화다. 받는 쪽은 반대로 맨 바깥 헤더부터 읽고 벗겨서 위로 올린다.

```
응용 데이터
[UDP 헤더 | 응용 데이터]                       전송 계층
[IP 헤더 | UDP 헤더 | 응용 데이터]              인터넷 계층
[이더넷 헤더 | IP 헤더 | UDP 헤더 | 데이터]      링크 계층
```

글로만 보면 감이 안 와서 헤더를 직접 만들어 봤다. 이더넷 14바이트, IPv4 20바이트, UDP 8바이트를 `struct`로 채우고 체크섬까지 계산한 뒤, 받는 쪽처럼 한 겹씩 벗겼다. 주소와 포트 숫자는 임의로 정한 예시다.

```python
import struct, socket

def checksum(b):
    if len(b) % 2: b += b'\x00'
    s = sum(struct.unpack('!%dH' % (len(b)//2), b))
    while s >> 16: s = (s & 0xffff) + (s >> 16)
    return ~s & 0xffff

payload = b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'   # 응용 데이터

# 전송 계층: UDP 헤더 8바이트 (포트, 길이, 체크섬)
src_ip, dst_ip = socket.inet_aton('192.168.0.10'), socket.inet_aton('93.184.216.34')
udp_len = 8 + len(payload)
pseudo = src_ip + dst_ip + struct.pack('!BBH', 0, 17, udp_len)
hdr0 = struct.pack('!HHHH', 50000, 53, udp_len, 0)
udp = struct.pack('!HHHH', 50000, 53, udp_len, checksum(pseudo + hdr0 + payload)) + payload

# 인터넷 계층: IPv4 헤더 20바이트
ip0 = struct.pack('!BBHHHBBH4s4s', 0x45, 0, 20 + len(udp), 1, 0, 64, 17, 0, src_ip, dst_ip)
ip = ip0[:10] + struct.pack('!H', checksum(ip0)) + ip0[12:] + udp

# 링크 계층: 이더넷 헤더 14바이트
frame = bytes.fromhex('aabbccddeeff') + bytes.fromhex('112233445566') + struct.pack('!H', 0x0800) + ip
print('앱 데이터', len(payload), '| UDP', len(udp), '| IP', len(ip), '| 프레임', len(frame))

# 받는 쪽: 한 겹씩 벗긴다
dst, src, et = struct.unpack('!6s6sH', frame[:14]); body = frame[14:]
print('이더넷 type=0x%04x' % et)
vihl, _, tot, _, _, ttl, proto, ck, s, d = struct.unpack('!BBHHHBBH4s4s', body[:20])
print('IP ihl=%d ttl=%d proto=%d %s -> %s' % (vihl & 15, ttl, proto, socket.inet_ntoa(s), socket.inet_ntoa(d)))
print('IP 헤더 체크섬 검증(0이면 정상):', checksum(body[:20]))
sp, dp, ln, _ = struct.unpack('!HHHH', body[20:28])
print('UDP %d -> %d len=%d' % (sp, dp, ln))
print(body[28:])
```

실행하면 이렇게 나왔다.

```
앱 데이터 37 | UDP 45 | IP 65 | 프레임 79
이더넷 type=0x0800
IP ihl=5 ttl=64 proto=17 192.168.0.10 -> 93.184.216.34
IP 헤더 체크섬 검증(0이면 정상): 0
UDP 50000 -> 53 len=45
b'GET / HTTP/1.1\r\nHost: example.com\r\n\r\n'
```

37바이트짜리 데이터가 UDP를 거치며 45, IP를 거치며 65, 이더넷을 거치며 79바이트가 됐다. 층을 내려갈 때마다 헤더 크기만큼 커진 것이다.

숫자들이 층 사이의 연결고리 역할을 하는 것도 보인다. 이더넷 헤더의 type `0x0800`은 "안에 든 건 IPv4"라는 뜻이고, IP 헤더의 proto `17`은 "안에 든 건 UDP"라는 뜻이다. 받는 쪽은 이 값을 보고 다음에 어떤 파서로 넘길지 정한다. 위로 올려 보낼 때 누구에게 줄지를 각 헤더가 스스로 적어 두는 구조다.

<details>
<summary>헤더 필드를 조금 더 풀어서</summary>

- 이더넷: 목적지 MAC 6바이트, 출발지 MAC 6바이트, 타입 2바이트. MAC 주소는 같은 링크 안에서만 의미가 있다. 라우터를 하나 건널 때마다 이 헤더는 새로 만들어지고, IP 헤더는 그대로 간다.
- IPv4: 첫 바이트 `0x45`는 버전 4, 헤더 길이 5(×4바이트 = 20바이트). TTL은 라우터를 지날 때마다 줄어서 경로가 무한히 도는 걸 막는다. 헤더 체크섬은 헤더만 검증한다. 위 코드에서 검증 결과가 0이 나온 건 헤더 전체를 다시 합쳤을 때 올바른 체크섬이면 0이 되기 때문이다.
- UDP: 출발·도착 포트, 길이, 체크섬. 체크섬은 IP 주소 등을 담은 의사 헤더까지 포함해서 계산해서, 주소가 틀려 엉뚱한 곳에 도착한 걸 잡아낸다.

</details>

## 주소가 층마다 다르다

층마다 "누구에게"를 가리키는 방식이 다르다는 점이 처음에 가장 헷갈렸다.

| 층 | 주소 | 가리키는 대상 | 범위 |
|---|---|---|---|
| 링크 | MAC | 네트워크 카드 | 같은 링크 안 |
| 인터넷 | IP | 호스트(의 인터페이스) | 네트워크 사이 |
| 전송 | 포트 | 프로세스 | 한 호스트 안 |

패킷이 라우터를 건너는 동안 IP 주소는 그대로이고 MAC 주소는 홉마다 바뀐다. 경로를 어떻게 고르는지는 [자세히 → DNS와 IP 라우팅](#/post/net-dns-routing)에서 이어진다.

## 계층과 코드의 거리

내가 짜는 앱에서 이 층들은 거의 안 보인다. 소켓을 열면 전송 계층 이하는 운영체제가 맡는다. [자세히 → 소켓과 서버 프로그래밍](#/post/net-socket)에서 그 경계를 코드로 본다. 소켓 API가 응용과 전송 사이의 문 역할을 한다고 보면 된다. 응용 계층 위에 있는 요청·응답 규칙은 [자세히 → HTTP와 HTTPS](#/post/net-http)에서 다룬다. 운영체제 안에서 네트워크 스택이 어디에 사는지는 [개요](#/post/cs-os) 쪽 커널 이야기와 이어진다.

## 흔한 오해

- "7계층을 외우면 네트워크를 안다": 7계층은 설명용 어휘에 가깝다. 실제 프로토콜은 한 층에 안 들어가는 것이 많다. TLS가 5층인지 6층인지, 전송과 응용 사이인지는 그림마다 다르게 그려진다.
- "OSI 모델대로 인터넷이 돌아간다": 인터넷이 쓰는 건 TCP/IP다. OSI 프로토콜 묶음은 널리 채택되지 못했다.
- "계층 사이는 엄격하게 막혀 있다": RFC 1122도 엄격한 계층화가 불완전한 모델이라고 한다. 구현은 성능 때문에 경계를 넘나든다.
- "MAC 주소는 목적지 호스트의 주소다": MAC은 바로 다음 홉의 주소다. 최종 목적지는 IP 헤더가 들고 있다.
