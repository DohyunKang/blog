SQLD 1과목에서 엔터티와 속성은 용어와 분류를 묻는 문제가 많은 단원이다. 외울 건 엔터티의 특징 다섯 가지, 분류 기준 두 가지, 속성의 분류 두 가지, 도메인 정의 정도다. 큰 흐름은 [데이터 모델링의 이해](#/post/sqld-modeling)에서 먼저 잡고 오면 편하다.

## 용어부터 정리

엔터티(Entity)는 업무에서 관리해야 하는 식별 가능한 대상이다. 정보를 저장하려고 만든다. DB로 옮기면 엔터티는 테이블, 인스턴스는 행, 속성은 열에 대응한다.

| 용어 | 뜻 | 테이블로 보면 |
|---|---|---|
| 엔터티 | 관리할 대상의 집합 | 테이블 |
| 인스턴스 | 엔터티에 속한 개별 대상 하나 | 행(Row) |
| 속성 | 엔터티가 가진 의미 있는 최소 단위 | 열(Column) |
| 속성값 | 속성에 실제로 들어간 값 | 셀 |

포함 관계는 `속성값 ⊂ 속성 ⊂ 인스턴스 ⊂ 엔터티`로 외운다. 엔터티 하나에 인스턴스가 2개 이상, 인스턴스 하나에 속성이 2개 이상, 속성 하나에는 속성값이 하나다. 이 숫자가 보기 문장에 섞여서 나오는 유형이 있다.

```
엔터티: 회원
  인스턴스 1: (m01, 김철수, 010-1111-2222)
  인스턴스 2: (m02, 이영희, 010-3333-4444)
  속성: 회원ID, 이름, 전화번호
  속성값: 'm01', '김철수', ...
```

## 엔터티의 특징 다섯 가지

문제에서는 "엔터티가 될 수 있는 것 / 없는 것"을 고르게 한다. 아래 다섯 개 중 하나라도 깨지면 엔터티로 보기 어렵다.

1. 업무에서 쓰는 정보여야 한다. 필요 없는 데이터는 엔터티로 만들지 않는다.
2. 인스턴스를 구별하는 식별자가 있어야 한다. 식별자는 속성 하나일 수도, 여러 속성의 조합일 수도 있다.
3. 인스턴스가 2개 이상이어야 한다. 평생 하나만 존재할 대상은 엔터티로 만들 이유가 없다.
4. 속성을 가져야 한다. 속성 없이 이름만 있으면 안 된다.
5. 다른 엔터티와 관계가 1개 이상 있어야 한다. 관계 없이 혼자 있는 엔터티는 효율이 떨어지는 경우가 대부분이다.

예를 들어 "회사 이름과 주소는 한 개뿐인데 이걸 엔터티로 만든다"는 보기는 2번 인스턴스 조건에 걸린다. 풀 때는 보기가 다섯 개 중 어느 조건을 건드리는지부터 본다.

## 엔터티 분류: 기준이 두 개

분류는 기준이 둘이고, 시험에서는 어떤 기준의 어떤 종류인지를 섞어서 낸다. 기준 이름과 종류 이름을 짝으로 외운다.

### 유무형에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 유형 엔터티 | 물리적 형태가 있고 안정적이며 지속적으로 쓰인다 | 상품, 회원, 사원 |
| 개념 엔터티 | 형태는 없고 개념으로 존재한다 | 부서, 학과 |
| 사건 엔터티 | 업무를 하면서 발생하고 빈번하며 통계에 쓰인다 | 주문, 이벤트 응모 |

앞 글자를 따서 "유개사"로 외우는 방법이 흔하다.

### 발생 시점에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 기본 엔터티 | 업무에 원래 있고 독립적으로 생긴다. 자식 엔터티를 가질 수 있다 | 상품, 회원, 사원, 부서 |
| 중심 엔터티 | 기본 엔터티에서 만들어지고 업무의 중심 역할을 한다. 데이터가 많고 행위 엔터티를 만든다 | 주문, 매출, 계약 |
| 행위 엔터티 | 2개 이상의 엔터티에서 만들어진다. 데이터가 자주 바뀌거나 계속 늘어난다 | 주문 내역, 이벤트 응모 |

"기중행"으로 외운다. 기본에서 중심, 중심에서 행위로 갈수록 파생된다고 생각하면 순서가 안 헷갈린다.

<details>
<summary>자주 헷갈리는 지점</summary>

- 중심 엔터티와 행위 엔터티의 정의는 자료마다 표현이 조금씩 다르다. 중심 엔터티를 기본 엔터티에서 파생된 것으로 설명하는 자료도 있고, 기본·행위 엔터티를 연결하는 역할로 설명하는 자료도 있다. 공부할 때 쓰는 교재의 정의를 기준으로 삼는 게 안전하다.
- 사건 엔터티(유무형 기준)와 행위 엔터티(발생 시점 기준)는 비슷해 보이지만 기준이 다르다. 문제에서 "발생 시점"이라는 말이 있으면 기본·중심·행위, "유형·무형"이라는 말이 있으면 유형·개념·사건에서 고른다.
- 같은 대상도 기준이 바뀌면 다른 이름이 붙는다. '주문'은 유무형 기준으로는 사건, 발생 시점 기준으로는 중심으로 나오는 예시가 있다.

</details>

## 엔터티 이름 짓기

명명 규칙도 보기 문장으로 나온다. 정리하면 아래와 같다.

- 업무에서 실제로 쓰는 용어를 쓴다.
- 한글은 약어를 쓰지 않고, 영문은 대문자로 쓴다.
- 단수 명사로 쓰고, 띄어쓰기는 허용하지 않는다.
- 다른 엔터티와 의미가 겹치지 않아야 한다.
- 그 엔터티가 가진 데이터를 분명하게 드러내는 이름이어야 한다.

"복수형으로 쓴다", "약어를 적극 사용한다" 같은 보기는 틀린 문장이다.

## 속성

속성은 엔터티가 가진 의미 있는 가장 작은 단위다. 더 쪼개면 의미를 잃는 수준이라고 보면 된다. 분류 기준은 두 가지가 나온다.

### 특성에 따른 분류

| 종류 | 설명 | 예 |
|---|---|---|
| 기본 속성 | 업무에서 원래 있는 속성. 다른 속성에서 만들어지지 않는다 | 이름, 가격, 수량 |
| 설계 속성 | 업무에 없지만 설계하면서 필요해서 만든 속성 | 일련번호 같은 인조 식별자 |
| 파생 속성 | 다른 속성으로 계산해서 만든 속성 | 합계 금액, 나이 |

파생 속성은 계산으로 구할 수 있는 값이라 저장하면 중복이 되고 원본이 바뀔 때 어긋날 수 있다. 그래도 조회 속도 때문에 일부러 두는 경우가 있고, 이건 [정규화와 성능 데이터 모델링](#/post/sqld-norm-perf)에서 반정규화로 다시 나온다.

### 구성 방식에 따른 분류

| 종류 | 설명 |
|---|---|
| PK 속성 | 인스턴스를 식별하는 기본키를 이루는 속성 |
| FK 속성 | 다른 엔터티와의 관계에서 가져온 외래키 속성 |
| 일반 속성 | PK도 FK도 아닌 속성 |

PK와 FK는 [관계와 식별자](#/post/sqld-relation-identifier)에서 식별자 종류와 같이 이어서 본다. 여기서는 속성이 세 갈래로 나뉜다는 것만 알면 된다.

한 가지 더, 값이 여러 개 들어가는 다중값 속성은 별도 엔터티로 분리하는 방향으로 간다. 한 칸에 여러 값을 넣는 구조는 정규화 쪽 문제로도 이어진다. [정규화 개념](#/post/db-normalization)을 같이 보면 이해가 빠르다.

## 도메인

도메인은 속성이 가질 수 있는 값의 범위다. 속성마다 도메인이 정해지고, 데이터 타입·길이·허용 값을 같이 생각한다. 예를 들어 '성별' 속성의 도메인이 '남, 여'라면 그 밖의 값은 들어올 수 없다. 문제에서는 "속성이 가질 수 있는 값의 집합"이라는 정의 문장이 맞는지 묻는다.

## 풀이 순서

이 단원 문제는 보기를 읽고 아래 순서로 걸러냈다.

1. 엔터티 얘기인지 속성 얘기인지 구분한다.
2. 분류 문제면 기준(유무형 / 발생 시점 / 특성 / 구성 방식)부터 확인한다.
3. 보기에 나온 예시(주문, 부서, 합계 금액 등)를 해당 기준의 종류에 하나씩 붙여 본다.
4. 특징 문제면 다섯 가지 중 어느 조건을 깨는 보기인지 찾는다.
5. 명명 규칙 문제면 단수·약어·띄어쓰기에서 틀린 문장을 먼저 의심한다.

<details>
<summary>혼자 점검해 볼 질문</summary>

- 인스턴스가 하나뿐인 대상은 왜 엔터티가 아닌가.
- '합계 금액'은 기본·설계·파생 중 어디에 들어가는가.
- 유무형 기준과 발생 시점 기준의 종류를 각각 세 개씩 말할 수 있는가.
- 엔터티 이름을 복수형으로 짓지 않는 이유를 보기 문장으로 설명할 수 있는가.

</details>
