## 它是什么
一个 Python 框架，能在公司数据库之上自动搭一层"这个数字是什么意思"的说明。这一层叫本体(ontology)，就是把概念和概念之间的关系整理成机器能读的地图。[详细 → 本体与三元组](#/post/ai-ontology-triple)

README 第一段把问题说得很清楚：代理能查数据库，但营收数字答得再快，错了也没用。所以需要一层上下文，告诉它数据在哪、是什么意思、能不能用、从哪来。

从使用者角度看，它就是一个 text-to-SQL 工具。text-to-SQL 是把"上周发了多少单?"这种问题转成 SQL 再执行。不同之处在于，模型不是只看表名去猜 SQL，而是先去查人确认过的定义。

## 怎么运作
本体里放三样东西。

- 术语(Term):Customer、Invoice Line 这类业务概念，带说明和同义词，连到真实的列。
- SQL 属性：毛利、累计值这类审核过的 SQL 表达式。代理会复用它们，所以同一个指标每次都用同样的方式算。
- 关系：表之间怎么 join，根据键和实际数据推断。

流程分三步：生成 → 认证 → 回答。生成阶段读取 schema、抽样列值、按表抽出术语、推断 join 关系，存进 Postgres;检索用的嵌入放进 pgvector。嵌入就是把文字变成数字向量，好找出意思相近的东西。[详细 → 嵌入与向量检索](#/post/ai-embedding)

认证是人的活。用真实问题测试草稿，改定义，把正确的 certify。不直接相信自动生成的地图，这个设计我挺喜欢。

回答阶段会抽出问题的意图和实体，用嵌入检索找候选的术语、列和 SQL 属性，写 SQL，把过滤值和查询拿到数据库里核对，不对就修，然后执行。答案会附上 SQL 和经过的步骤。README 的例子里，问 2015 年 6 月宾夕法尼亚某个商品的营收，返回了 $588.80，以及一条 join 了六张表的 SQL。

最吸引我的是答不了的情况。示例数据库里没有广告费数据，问广告投资回报率(ROAS)时，MCP 的 `check_answerable` 工具会先说"没有术语覆盖 ad spend",代理再反问。比编一个看起来合理的列好多了。

## 怎么接上
有单独的 MCP 服务器，在 Cursor 或 Claude Desktop 里加几行配置就能接。工具全是只读的，按用户自己的权限运行。[详细 → MCP](#/post/ai-mcp) 还带了三个给编码代理用的技能(安装、管理、查询)。[详细 → 技能](#/post/ai-skills) 通过 REST API 发问题，答案以 SSE 流返回。

默认模型是 NVIDIA NIM 的 Nemotron 3.5 系列，分推理、轻量步骤、嵌入、重排序四个角色;据说只要是兼容 OpenAI 的端点，每个角色都能换成别的模型。能连的数据库有 PostgreSQL、MySQL、Snowflake、Databricks、DuckDB 等 10 种。

## 从入门者的角度
对 PM 来说，最有感的是把"营收"的定义钉在一个地方。各团队算营收方法不同，这问题 AI 之前就有，现在等于做成了一本代理会读的词典。对刚入门开发的人，Next.js + FastAPI + Postgres/pgvector + MCP 这套组合，看起来是把 RAG 用在 SQL 上的好例子。[详细 → RAG](#/post/ai-rag)

README 里也写了注意事项。内部端口 3001、3002 要么没有认证，要么直接信任前端转来的用户头，所以要放在私有网络里。默认配置会把请求发到 NVIDIA API 目录。目前不接受外部贡献。BIRD 之类的基准结果指向另一个仓库，数字我没能确认。
