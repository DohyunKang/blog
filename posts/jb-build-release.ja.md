形態管理は、ソフトウェアの変更を記録し制御する作業であり、ビルド・デプロイは、そのように管理されたソースを実行可能な成果物として出力する作業である。情報処理技術者試験では、用語の定義や分類に関する問題が大半を占めるため、本記事もその単位ごとに分けて記述した。試験日程や受験料については公式サイトで確認すること。

## 形態管理とは何か

形態（Configuration）は、ソフトウェアを構成するすべての成果物の総称である。ソースコードだけでなく、要件定義書、設計書、テストケース、設定ファイルなども含まれる。これらの中で変更を追跡対象として指定した項目を「形態項目」と呼ぶ。

形態管理（SCM）は、これらの項目が誰によって、いつ、なぜ変更されたかを記録し、必要に応じて以前の状態に戻せるようにする活動である。開発中の変更を防ぐことはできないため、目的は変更のプロセスを秩序立てることにある。要件が途中で変わる問題は [詳しく → 要件の確認と分析](#/post/jb-requirements) でも扱われている。

試験で頻出の用語を表にまとめた。

| 用語 | 意味 |
|---|---|
| 形態項目 | 変更を管理する対象として指定された成果物 |
| ベースライン | 公式なレビューを経て承認された基準時点。以降の変更は定められた手順を経る必要がある |
| チェックアウト | リポジトリから作業用に取得すること |
| チェックイン（コミット） | 修正内容をリポジトリに反映すること |
| ブランチ | 基準のフローから分岐した別々の作業の枝 |
| マージ | 分岐した枝を再び統合すること |

## 形態管理の 4 つの活動

試験で最も多く問われる部分である。活動名と説明をセットで暗記しよう。

| 活動 | 行うこと |
|---|---|
| 形態識別 | 何を管理するか定め、各項目に名前・番号を付与する |
| 形態統制 | 変更要求を受け、レビュー・承認し、承認されたもののみを反映させる（変更統制委員会が判断） |
| 形態監査 | ベースラインに従って作成されているか、変更が手順通りに処理されたか確認する |
| 形態記録（ステータスレポート） | 項目の現在の状態と変更履歴を記録し報告する |

混同しやすいのは「統制」と「監査」である。統制は変更を許可する側であり、監査は許可された通り進んでいるか確認する側である。

<details>
<summary>形態管理を行うと良くなる点</summary>

- 誤って修正したものを以前のバージョンに戻せる。
- 複数の人が同じファイルを修正する際に衝突を検出し調整できる。
- デプロイされたバージョンがどのソースから派生したかを追跡できる。
- 変更履歴が残るため、責任の所在や原因分析が容易になる。

</details>

## バージョン管理ツールの 3 つの種類

バージョン管理システムは、リポジトリをどこに置くかによって分類される。

| 方式 | リポジトリ | 代表的なツール（試験頻出） |
|---|---|---|
| ローカル・共有フォルダ | 共有フォルダ内のファイルをロックして修正 | RCS, SCCS |
| クライアント・サーバー | 中央サーバーにリポジトリが 1 つ | CVS, SVN(Subversion) |
| 分散型 | 開発者ごとにリポジトリ全体の複製を持つ | Git, Bazaar |

中央集権方式はサーバーがダウンすると作業が止まるが、分散型方式は各自が完全な履歴を保持しているため、オフラインでもコミットやブランチ作成が可能である。Git の内部構造については [詳しく → Git を正しく理解する](#/post/cs-git) に別途記述している。

マージには Pro Git 基準で 2 つのケースがある。統合しようとするブランチが現在のブランチの直後にあれば、ポインタだけを先に移動させる fast-forward であり、新しいコミットは生成されない。両側がそれぞれコミットを積み上げて分岐した場合は、両方のブランチの先頭と共通の祖先のスナップショット 3 つで統合し、親が 2 つあるマージコミットが新生成される。同じファイルの同じ部分を両側で異なって修正した場合に衝突が発生し、衝突表示を手動で修正した後、`git add` で解決表示を行いコミットすることでマージが完了する。

<details>
<summary>Git の基本コマンド数選</summary>

| コマンド | 行うこと |
|---|---|
| `git add` | 変更をステージング領域に追加する |
| `git commit` | ステージされた内容をコミットとして確定する |
| `git branch` | ブランチを作成するかリストを表示する |
| `git merge` | 他のブランチを現在のブランチに統合する |
| `git status` | 現在の状態と衝突ファイルを表示する |

</details>

## ビルドとビルドツール

ビルドは、ソースをコンパイルし、ライブラリをリンクし、テストを実行し、実行可能な形式にまとめるプロセスである。手動で行うとミスが生じるため、ツールが決まった順序で代わりに実行する。

試験に出るツールは Make, Ant, Maven, Gradle 程度である。宣言方式の違いによって分類する。Ant は作業順序を直接記述する方であり、Maven は定められたライフサイクルに合わせて設定する方である。依存ライブラリをダウンロードして管理してくれるのも Maven や Gradle のようなものの特徴としてまとめて暗記しよう。

Maven ドキュメントで確認した基本ライフサイクルの段階は以下の通りである。

| 순서 | 단계 | 뜻 |
|---|---|---|
| 1 | validate | プロジェクト構成が正しく、必要な情報が揃っているか検査 |
| 2 | compile | ソースコードのコンパイル |
| 3 | test | ユニットテストの実行（パッケージング・デプロイは不要） |
| 4 | package | JAR などの配布形式でまとめる |
| 5 | verify | 統合テスト結果など品質基準の確認 |
| 6 | install | ローカルリポジトリにインストール |
| 7 | deploy | リモートリポジトリにコピーして共有 |

`mvn verify`のように 1 つの段階を指定すると、その前の段階が順番にすべて実行される。以前のビルド成果物を削除する `clean` は別々のライフサイクルなので、`mvn clean deploy` のように前に付けて書く。テスト段階がビルドに含まれている点は [詳細 → ソフトウェアテスト](#/post/jb-testing) と続きます。

ビルドとテストをコードが合流するたびに自動的に回すのが CI で、そこにデプロイも自動的に続くのが CD です。パイプライン構成は [詳細 → CI/CD とデプロイ戦略](#/post/cloud-cicd) で扱いました。

## リリースとバージョン番号

リリースとは、ビルドされた成果物をユーザーや運用環境に公開することです。公開の前後で同時に確認すべきことは 2 つあります。

- リリースノート: 今回のバージョンで何が追加され、修正され、既知の問題が何かを記した文書
- 前バージョンの保存: 問題が発生した場合にロールバックできるように、配布物とソースの対応を残す

バージョン番号ではシマンティックバージョニング (SemVer) の規則が最も広く言及されます。公式ドキュメントに基づいて整理すると以下のようになります。

| 位置 | 上げる時 |
|---|---|
| MAJOR | 下位互換性が壊れる API の変更 |
| MINOR | 下位互換性のある機能の追加 |
| PATCH | 下位互換性のあるバグ修正 |

数字を上げるとその右側の数字は 0 にリセットされます (1.4.2 で MINOR を上げると 1.5.0)。0.y.z は初期開発段階なのでいつでも変更されることがあり、1.0.0 から公開 API が確定します。`1.0.0-rc.1` のようにハイフンの後に付けるのはプレリリースであり、正式な `1.0.0` より優先順位が低いです。`+` の後に付けるビルドメタデータはバージョン比較では無視されます。一度配布されたバージョンの内容を変更してはいけず、変更する場合は新しいバージョン番号を受け取る必要があります。

開発段階ごとの名前であるアルファ (内部試験) とベータ (外部一部ユーザーによる試験)、そしてその後の正式リリースの順序も合わせて覚えておいてください。

## コードレビュー

コードをマージする前に、他の人が読み込んで欠陥を見つける活動です。試験では静的な手法であり実行せず人間が確認するという点、そして形式の厳格さの違いについて問われます。

| 種類 | 雰囲気 |
|---|---|
| ピアレビュー | 作成者と同僚が軽く回す非公式なレビュー |
| ワークスルー | 作成者が成果物を説明し、参加者が意見を述べる方式 |
| インスペクション | 役割（仲介者・記録者など）と手順が決まった最も形式的な方式 |

形式が厳格になる順はピアレビュー、ワークスルー、インスペクションです。実行せずにコードを見る検証は [詳細 → ソフトウェアテスト](#/post/jb-testing) の静的テストと同じカテゴリです。

## よく間違える部分

- 形態管理と形態監査を逆にして覚える場合。管理は承認、監査は確認です。
- ベースラインを「最新バージョン」と誤解する場合。公式に承認され変更の手続きが付いた基準点です。
- Git をクライアント・サーバー方式で分類する場合。分散型方式です。
- SemVer でバグ修正まで MINOR を上げると考える場合。バグ修正は PATCH です。
- `install` と `deploy` を同じだと見なす場合。前者はローカルリポジトリ、後者はリモートリポジトリです。

スケジュールやコストなど管理面の概念は [詳細 → プロジェクト管理](#/post/jb-project-mgmt) で続きます。
