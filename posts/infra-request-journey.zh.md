在浏览器中按下回车键后，会产生一个请求，该请求依次经过 DNS、CDN、负载均衡器、服务器、缓存和数据库，每个阶段都会消耗时间。当速度变慢时，首要任务就是找出这条路径中的哪个环节导致了延迟。

## 先通过一张图概览

```
브라우저
  │ 1. DNS: 도메인 → IP 주소
  ▼
CDN(엣지)  ── 캐시에 있으면 여기서 응답하고 끝
  │ 2. 없으면 원본 서버 쪽으로
  ▼
로드밸런서 ── 살아 있는 서버 중 하나를 고름
  │
  ▼
앱 서버 ──── 3. 캐시(Redis 등)를 먼저 확인
  │            있으면 바로 응답
  ▼
DB ───────── 4. 캐시에 없을 때만 조회
```

实际上，不同的服务会省略其中的某些部分。有的服务没有 CDN，有的服务只有一台服务器因此没有负载均衡器。不过整体架构大体相似，因此按此顺序进行整理。

## 1. DNS：将域名转换为 IP 地址的阶段

浏览器首先要做的事情是获取域名的 IP 地址。AWS 文档描述的流程如下：浏览器向 DNS 解析器（通常由电信运营商或公司网络运营）询问，解析器依次查询根域名服务器、接着是 .com 等顶级域名（TLD）的域名服务器，最后是目标域名的权威域名服务器。收到回答后，解析器会将该 IP 地址存储一段时间，对于后续的相同查询则无需再次执行上述过程即可直接回答。

因此，第二次查找同一域名时会更快。存储的时间称为 TTL（生存时间）。将 TTL 设置得较长可以减少查询次数，但如果更改了服务器 IP，旧地址仍会在一段时间内保留在缓存中。

## 2. 建立连接：TCP 与 TLS

即使知道了 IP 地址，也不能立即进行数据交换。首先需要建立 TCP 连接（握手），如果是 HTTPS 则还需额外进行一次 TLS 协商。MDN 关于延迟的解释中也单独列出了 DNS、连接、TLS 协商、请求发送、服务器等待和响应接收等步骤，指出首次请求缓慢的原因在于这些准备步骤共同导致了延迟。如果连接已经保持打开状态，后续请求则无需再次支付这些成本。

这里的延迟主要源于距离。握手需要多次往返，而一次往返的时间随着服务器距离的增加而变长。这就是为什么需要 CDN 将服务器部署在用户附近的原因。

## 3. CDN：从就近位置代为响应

根据 MDN 的解释，CDN 是一组分布在各地的服务器，每个服务器都持有数据的副本，因此由最近的服务器响应用户请求。对于图像、CSS、JS 等所有用户共享的文件，这种方式非常适用。如果边缘节点有缓存副本（缓存命中），请求即在此结束；如果没有（缓存未命中），则需前往源服务器获取数据并存储起来。这样也能相应减少源服务器接收的请求量。

MDN 补充的几点注意事项也值得记住：CDN 引入了额外的外部依赖，将其连接到新域名会增加 DNS 查询和连接成本，反而可能导致速度变慢。因此，CDN 并非总是能加速访问。

[详情 → CDN 与缓存](#/post/infra-cdn-cache)

## 4. 负载均衡器：决定将请求分发至哪台服务器

进入源服务器的请求首先由负载均衡器接收。以 AWS 文档为标准，负载均衡器会将传入的流量分发到多个目标（如实例、容器等），并持续检查目标状态，仅将请求转发至正常的节点。其目的是在添加或移除服务器时保持请求流程不中断。此外，加密与解密工作也可交由负载均衡器处理。

因此，即使单台服务器宕机，用户也可能毫无察觉地继续访问。在增加服务器数量时，可配合 [自动伸缩](#/post/infra-autoscaling) 使用，新创建的服务器会自动注册到负载均衡器中。

[详情 → 负载均衡器](#/post/infra-load-balancer)

## 5. 应用服务器、缓存与数据库

当请求到达应用服务器后，代码开始执行。系统会验证身份认证，并查找所需数据。此时，对于频繁使用的数据，会先查看类似 Redis 的缓存。如果缓存中存在，则直接从内存中取出并响应；只有在缓存未命中时，才会查询数据库并将结果存入缓存。

数据库查询通常是此阶段最耗时的操作。为了避免每次查询都反复扫描磁盘，因此将缓存置于前端。如果查询本身较慢，首先应检查是否存在 [索引](#/post/db-index)。关于请求在服务器内部的流转过程，另有专门整理。

[详情 → 缓存与 Redis](#/post/db-cache-redis) · [详情 → 服务器内的请求流程](#/post/be-request-flow)

## 6. 延迟累积在哪里

下表汇总了各阶段大致耗时原因。表中未填写具体数值，因为不同环境差异巨大，难以用单一数值概括。

| 阶段 | 耗时原因 | 优化方法 |
|---|---|---|
| DNS | 解析器依次向多台服务器查询 | 利用解析器缓存（TTL）、减少域名数量 |
| TCP/TLS | 需要多次往返，时间与距离成正比 | 连接复用、将用户靠近部署（CDN） |
| CDN | 缓存未命中时需往返源服务器 | 构建可被缓存的响应内容 |
| 负载均衡器 | 通常耗时较短，主要用于选择目标服务器 | 确保仅转发至正常运行的服务器 |
| 应用服务器 | 代码处理、外部调用 | 减少不必要的调用、使用缓存 |
| 数据库 | 磁盘查询、查询语句结构 | 建立索引、使用缓存、优化查询语句 |

web.dev 将 TTFB（首字节到达时间）定义为重定向、DNS、连接与 TLS 协商以及从请求发出到首字节到达时间的总和。大致标准为：低于 0.8 秒为良好，超过 1.8 秒则视为较差。不过文中也注明这是“适用于大多数网站的粗略标准”。

## 实测数据

光看理论还不够，我在自己的 PC 上进行了实测。使用 Python socket 对 example.com 分步测量了 DNS 查询、TCP 连接和 HTTP 请求（首字节）。由于使用的是 80 端口的明文 HTTP 而非 HTTPS，因此未包含 TLS 协商环节。

```
DNS 11ms / TCP 153ms / 첫 바이트 145ms / 다운로드 2ms / 합계 311ms
DNS 10ms / TCP 113ms / 첫 바이트 120ms / 다운로드 0ms / 합계 243ms
DNS 10ms / TCP 114ms / 첫 바이트 119ms / 다운로드 0ms / 합계 243ms
```

DNS 耗时约 10ms，而 TCP 连接与首字节等待时间分别约为 110~150ms。由于下载的是小页面，实际下载时间几乎可以忽略不计。服务器距离较远时，连接建立和等待时间确实会占据大部分，数据也印证了这一点。但需注意，这些数值取决于我 PC 的位置及当时的网络状态，在其他地方结果可能完全不同。DNS 响应较快也可能是因为它已存在于本地缓存中。

<details>
<summary>详细解析：测量代码与解读方法</summary>

```python
import socket, time, sys
host = sys.argv[1]
t0 = time.perf_counter()
ip = socket.getaddrinfo(host, 80, socket.AF_INET)[0][4][0]   # DNS
t1 = time.perf_counter()
s = socket.create_connection((ip, 80), timeout=10)           # TCP
t2 = time.perf_counter()
s.sendall(f"GET / HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n\r\n".encode())
s.recv(1)                                                      # 첫 바이트
t3 = time.perf_counter()
while s.recv(65536):                                           # 나머지 다운로드
    pass
t4 = time.perf_counter()
ms = lambda a, b: round((b - a) * 1000)
print(f"DNS {ms(t0,t1)}ms / TCP {ms(t1,t2)}ms / 첫 바이트 {ms(t2,t3)}ms / 다운로드 {ms(t3,t4)}ms / 합계 {ms(t0,t4)}ms")
```

上述结果是运行该代码三次后的汇总数据。“首字节”指的是从发出请求到服务器返回第一个字符之间的时间，因此包含了服务器处理时间和往返延迟（RTT）。若要区分这两部分，需要查看服务器日志或定时头信息。

我也尝试测量包含 TLS 的 HTTPS 版本，但由于本机证书验证失败，未能完成 TLS 阶段的测量。未采用禁用验证的方法。

在浏览器中，只需打开开发者工具的 Network 标签页并点击任意一个请求，即可看到相同的阶段划分（DNS、连接、TLS、等待、下载）。无需自行编写代码，这种方式更为便捷。

## 常见误区

- **仅优化服务器代码就能提速**：服务器处理只是链路中的一个环节。前端的 DNS 和连接问题、CDN 缓存未命中、后端的数据库查询等往往影响更大。
- **使用 CDN 就一定更快**：只有对可缓存的响应才有效；正如上文所见，增加一个域名反而可能导致整体变慢。
- **只需开启缓存即可**：缓存中的数据可能过时，因此还需同时设置过期时间（TTL）。
- **配置了负载均衡器服务器就不会挂掉**：即使某台服务器宕机，其他服务器也能接管请求；但如果所有服务器因相同原因变慢，负载均衡器也无法解决。

遇到性能缓慢的服务时，应首先按照上述表格顺序逐段测量耗时。若凭直觉直接怀疑数据库，很容易误入歧途。这种分段测量将在 [可观测性](#/post/cloud-observability) 相关主题中进一步展开。
