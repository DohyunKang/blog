UML は、ソフトウェアを描画するための標準的な記述法であり、情報処理技術者試験では、図の種類の分類、クラス関係の記号、ユースケース・シーケンス図の読み取りが主要な単元です。本稿は試験対策用のまとめです。要件抽出の段階については [詳細 → 要件の確認と分析](#/post/jb-requirements) で先に扱いました。

## UML とは何か

UML (Unified Modeling Language) は、システムをモデルとして描くための標準言語です。OMG が 1997 年に標準として採用し管理しており、ISO/IEC は 2005 年に ISO/IEC 19501 として発行しました。以降の正式なバージョンは 2.5.1（2017 年 12 月採択）です。

UML 2 では図を 14 種類に定義しています。暗記する際は 2 つに分けるのが便利です。

| 分類 | 何を描くか | 図の 7 種類 |
|---|---|---|
| 構造 (Structure) | システムがどのような部品で構成されているか（静的） | クラス、コンポーネント、複合構造、デプロイメント、オブジェクト、パッケージ、プロファイル |
| 振る舞い (Behavior) | 時間経過とともにどのように動くか（動的） | ユースケース、アクティビティ、状態機械、シーケンス、コミュニケーション、相互作用概要、タイミング |

振る舞い側の「シーケンス」「コミュニケーション」「相互作用概要」「タイミング」の 4 つはまとめて「相互作用 (interaction)」図と呼ぶこともあります。

試験では「この図は何の図か」「静的モデルと動的モデルのどちらか」といった分類問題が出やすいので、上記表の左側・右側の所属を正確に把握しておけば十分です。デプロイメント図が構造側に属すること、ユースケースが振る舞い側に属することが混乱しやすい点です。

## ユースケース図

システムを利用する人と、システムが行う仕事を 1 つの図に描きます。

- アクター (actor): ユーザーや外部システム。通常は棒人間のような形です。
- ユースケース: システムが提供する機能の一つ。円または楕円で描きます。
- システム境界: ユースケースを囲む四角。システムの範囲を示します。

ユースケース間の関係は、破線の矢印にラベルを付けます。

| 関係 | 意味 | 矢印の方向 |
|---|---|---|
| include | 基本ユースケースが共通機能を正常フローから引き継ぐ | 基本 → 含まれる側 |
| extend | 条件が満たされた場合に、基本機能に選択動作を追加する | 拡張される側 → 基本 |
| 一般化 | 子クラスが親クラスを拡張・再定義する | 子 → 親（三角形の頭） |

include はログイン確認のように常に通る部分、extend は「パスワードエラー」のようなたまに発生する部分と覚えると方向が分かりやすくなります。extend の矢印は基本側に向きます。

## クラス図

構造図の中で最もよく使われる図です。クラスは 3 つの区画を持つ箱（名前・属性・演算子）で描き、メンバーの前にはアクセシビリティ記号を付けます。

| 記号 | アクセシビリティ |
|---|---|
| + | public |
| - | private |
| # | protected |
| ~ | package |

多重性 (multiplicity) は関係線の端に記述します。1 は正確に一つ、0..1 はゼロまたは一つ、0..* または * はゼロ以上、1..* は一つ以上です。続いて関係の 6 つがこの単元の中心です。

| 関係 | 言葉で言うと | 形状 |
|---|---|---|
| 関連 (association) | クラス同士が構造的につながっている | 実線 |
| 集約 (aggregation) | has-a、部分が独立して存在可能 | 全体側に空のひし形 |
| 合成 (composition) | より強い has-a、全体が消えると部分も消える | 全体側に塗りつぶしのひし形 |
| 一般化 (generalization) | is-a、継承 | 実線 + 親側への空の三角形 |
| 実体化 (realization) | インターフェースの実装 | 破線 + インターフェース側への空の三角形 |
| 依存 (dependency) | 一方が変わると他方に影響を与える弱い関係 | 破線 + 開いた矢印（使う側 → 使われる側） |

混乱しやすいのは集約と合成、そして一般化と実体化です。ひし形が空か塗りつぶされているかは、ライフサイクルを共にするかどうかが分かれ目です。三角形はどちらも空の三角形であり、線が実線なら継承、破線なら実装を表します。線の形状を先に、次に頭の形状と順序を決めておけば間違いが減ります。

ただし上記の関係は試験問題でどのような用語（英語か日本語か）で出ても、定義文の一つずつだけ暗記しておけば十分です。コードへの書き換え感覚については [詳細 → オブジェクト指向と言語コードの読み方](#/post/jb-oop-lang) と続きます。

## シーケンス図

オブジェクト同士がメッセージをやり取りする順序を上から下へ、時間の流れに合わせて描きます。

- LifeLine: 垂直の線はオブジェクトやプロセスを表す。下に X があれば、そのオブジェクトが消滅したことを意味する。
- Message: 水平な矢印にメッセージ名を記す。塗りつぶされた矢羽根は同期（呼び出し側が完了するまで待機）を、開いた矢羽根は非同期（待機せず継続）を表し、破線は応答（返却）である。
- Activation bar: ライフライン上の細い長方形。そのオブジェクトがメッセージを処理している区間を示す。自身を呼び出すとボックスが重なり合うように積まれる。
- Combined fragment: 並列、条件分岐、選択動作などのフローを束ねて表現するボックスである。

問題は通常、図を見て「何番目のメッセージがどのような種類か」「どのオブジェクトが呼び出しを受けたか」などを問う形式であり、矢羽根の形状と破線の応答を区別する練習が最も直接的だ。

<details>
<summary>詳しい解説：1 つのシーンを 3 つの図に展開してみる</summary>

オンライン注文 1 件を例にとると、同じ内容でも図によって表現は異なる。

- Use Case: アクタ「顧客」と「決済代行会社」があり、ユースケースは「注文する」「決済する」。「注文する」が「ログイン確認」を include し、「クーポン適用」が「決済する」を extend する。システム境界内にはユースケースを入れ、アクタは外に置く。
- Class: 注文 (Order) と注文項目 (OrderItem) は項目が注文なしでは意味がないため合成関係で描き、注文と顧客 (Customer) は関連関係とする。多重性は顧客 1 に注文 0..* である。決済方式インターフェースをカード決済クラスが実装すると破線＋空の三角形になる。
- Sequence: 顧客 → 注文サービスへ「注文リクエスト」（同期）、注文サービス → 決済へ「決済リクエスト」、破線で「決済結果」の応答が返ってくる。通知を待たずに送る場合は、開いた矢羽根の非同期メッセージとして描く。

同じシステムでも、「誰が何をするか」はユースケース、「何が何を持つか」はクラス図、「誰が誰にいつ話すか」はシーケンス図が担当する。問題を読む際に、質問がこの 3 つのうちどこに属するかを先に特定すると解法が早くなる。

## オブジェクト指向分析で使う感覚

オブジェクト指向分析は、要件からオブジェクト候補（名詞）とその動作（動詞）を引き出し、クラスとして整理することである。ユースケースで機能範囲を定め、クラス図で静的構造を決定し、シーケンスでシナリオを検証する順序が自然だ。この段階で決めた構造は、続いて展開される [詳細 → ソフトウェアアーキテクチャ](#/post/jb-architecture-pattern) と [詳細 → デザインパターン](#/post/jb-design-pattern) の材料となる。

## よくある混同点

- 集約と合成はどちらも菱形：空の菱形は部分が独立して存在でき、塗りつぶされた菱形は全体と共に消滅する。
- 一般化と実体化の三角形は同じ：実線なら継承、破線なら実装（インターフェースの実装）である。
- include と extend の矢印方向は逆：include は基本側から含まれる側へ、extend は拡張側から基本側へ向かう。
- 配置図・コンポーネント図は振る舞い側：どちらも構造側である。
- 試験日程や問題出題比率はこの記事では扱わない。日程・受付は公式サイトで確認すること。
