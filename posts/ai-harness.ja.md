ハネスは、モデルを除いた残り部分、つまりモデルをループに組み込んで実行し、ツールを接続して記録を管理するコードと環境を指す言葉です。ただし、定義が一つに定着した用語ではないため、資料によって範囲が少しずつ異なります。

## まず簡単な説明で

モデル単体では、文章を受け取って返すことしかできません。ファイルを開いたりコマンドを実行したりするのは、モデルではなくその横で代わりにやってくれるプログラムです。モデルが「このファイルを読んで」と指示すると、プログラムが読み込んで結果を再びモデルに戻します。これを繰り返して終了するまで続けます。このプログラムがハネスです。

文字通り「馬具（まぐ）」という意味で、馬（モデル）に装着する装備のことです。馬（モデル）の力はそのままですが、「どこへどのように走らせるかは装備が決める」という比喩として理解しました。この比喩は私が付けたものです。

## 公式文書ではどう使われるか

Anthropic の記事 3 篇を開いてみたところ、使い方が少しずつ異なっていました。

- **Managed Agents** の記事：ハネスを「Claude を呼び出し、Claude のツール呼び出しをそのインフラへ送るループ」と括弧で簡潔に定義しています。エージェントを脳（Claude とハネス）、手（サンドボックスとツール）、セッション（外に残るイベント記録）の 3 つに分けた記事です。
- **Effective harnesses for long-running agents**：形式的な定義はなく、Claude Agent SDK を「汎用エージェントハネス」と呼びます。ツール、コンテキスト管理（圧縮など）、周辺設定をまとめてハネスと呼ぶ感じですね。脚注では、初期化エージェントとコーディングエージェントはシステムプロンプトとツールを含むハネスは同じで、ただ開始プロンプトだけが異なるだけだと述べています。
- **Long-app development harness design** の記事：モデルを取り巻くオーケストレーション、役割分担、コンテキスト処理、プロンプトを総称してハネスと呼び、「ハネス設計」を一つの作業として扱っています。

同じ単語ですが、最初のものは「ループとルーティング」のみで、後者の 2 つは「その周辺設計全体」まで広く使います。これが資料によって定義が異なるということです。私は狭い意味を核心とし、広い意味を実際にやることとして読みました。

比較のために Anthropic の **Building effective agents** も開いてみました。エージェントを「環境のフィードバックを受けながらツールを使う LLM がループを回すもの」と説明していますが、この記事にはハネスという単語はありませんでした。用語が後に定着したようです。

## ハネスがやること

3 篇で共通するものをまとめると以下のようになります。

| 項目 | 内容 |
|---|---|
| ループ | モデル呼び出し、ツール実行、結果のフィードバックを繰り返す。最大反復回数などの停止条件 |
| ツール | どんなツールを渡すか、説明はどう書くか。Anthropic はこれを agent-computer interface(ACI) と呼び、人間用 UI と同等に磨いていると言います |
| 権限 | 何を実行してもよいか、認証情報をどこに置くか。Managed Agents の記事では認証情報はサンドボックスの外に置くとあります |
| コンテキスト | 記録を切り出して要約し、外部ファイルにメモを残すこと |
| 検証 | モデルが「終わった」と言ったのを信じず、テストで確認すること |
| 復旧 | セッションやコンテナが死んでも続きをさせること |

権限については上記 3 篇の中で Managed Agents の記事のみ具体的に確認しました。残りの権限承認方式などは製品によって異なるようです。

## コンテキストエンジニアリング、エージェントループとの関係

3 つの用語は一行で繋がっています。

- **エージェントループ**：回っている動作そのもの。モデル呼び出し、ツール実行、結果投入の繰り返し。
- **ハネス**：そのループを実際に回すコードと環境。
- **コンテキストエンジニアリング**：ループの各ターンでモデルの目の前に何を置くかを選ぶこと。ハネスがやることのうちの一つです。

[詳細 → コンテキストエンジニアリング](#/post/ai-context) から出てきた圧縮、メモ、サブエージェントなどの方法は、結局ハネスコードに実装されます。ハネスはコンテキストだけでなくツール、権限、検証、復旧も含むためより広い概念です。ただし、ある記事ではコンテキスト管理をハネスの一部として使い、別の記事では別扱いにするなど、境界線は著者によって異なります。

モデルが入力として受けるもの自体は [詳細 → コンテキストウィンドウ](#/post/ai-context-window) と [詳細 → LLM](#/post/ai-llm) を見ておけばよく、ツール接続規格については [詳細 → MCP](#/post/ai-mcp) で別途扱います。

## 例：長期間走るタスクにおけるハネス

**Effective harnesses** の記事の例が具体的でした。セッションが変わるとモデルは前のことを覚えていません。そのため以下の 2 つを行いました。

最初のセッションは初期化用です。ユーザーリクエストを機能リスト JSON に展開し、開発サーバーを起動する `init.sh`、進行記録ファイル、最初の git コミットを作成します。以降のセッションは一度に一つの機能を実装してコミットし、記録を残します。新しいセッションでは開始時に git ログと記録を読み込み、基本的な動作を確認してから作業を行います。

機能リストの各項目は当初すべて失敗状態であり、コーディングエージェントは「通過/不通過」フィールドのみを変更できる。JSON を使用した理由は、マークダウンよりもモデルが恣意的に修正したり上書きする可能性が低いためと記述されていた。また、単体テストや curl だけで完了処理していた問題は、ブラウザ自動化により人間のようにテストできるようになり、大幅に改善されたという。

見るとモデル自体はそのままであり、外側の構造だけを改変して失敗（やりすぎ、早期終了宣言など）を減らしたことになる。これが「ハネス設計」という言葉が指すことだ。

## ハネスエンジニアリング

ハネスを設計し直すことを「ハネスエンジニアリング」と呼ぶ。この用語は、OpenAI が 2026 年 2 月に発表した記事 "Harness engineering: leveraging Codex in an agent-first world" で広く使われ始めたようだ。検索結果の抜粋から判断すると、初期の進行が遅かったのはモデルではなく環境が未整備だったためであり、チームの役割はエージェントが利用可能な環境を構築することにシフトしたという。二次資料ではこれを「制約、ツール、フィードバックループ、ドキュメント、検証体系」の設計に要約している。

Anthropic の記事にも同様の感覚が見られる。ハネスのすべての部品は、「モデル一人ではできないこと」という仮定を含んでおり、モデルが良くなると仮定も陳腐化すると述べている。実際の例として、Sonnet 4.5 で有効だったコンテキストリセットが Opus 4.5 では不要になったと記している。したがってハネスは一度作って終わりではなく、モデルが変わるたびに削り出す部品を見つける必要があるようなものだ。

## よくある誤解

- ハネスはフレームワークの名前である：特定のライブラリを指す言葉ではない。LangChain であっても自分で書いたループであっても、モデルの外側でループを回せばハネスだ。
- ハネスが良ければモデルはどうでもよい：同じ記事群は逆のことを言っている。モデルが良くなるとハネスは単純化する方向になる。ただし複雑なタスクにおけるハネスの必要性が完全に消えたわけではないし、「興味深い組み合わせの空間が減らない」という記述もあった。
- ハネスはプロンプトである：プロンプトはハネスの一部に過ぎない。ツール実行、記録管理、検証コードは別途存在する。
- 定義が決まっている：前述したように狭義でも広義でも使う。文章を読む際はまずどの範囲を指すかを確認するのがよいだろう。

<details>
<summary>詳細な解説：脳・手・セッションの分離</summary>

Managed Agents の記事によると、ハネスはコンテナ内には存在しない。ハネスは `execute(name, input) → string` という単一のインターフェースでサンドボックスとツールを呼び出す。コンテナが死んでもハネスはそれをツール呼び出しエラーとして扱い Claude に返却し、Claude が新しいコンテナを作成できる。セッションはハネスとサンドボックスの外に残る追加の専用イベント記録であり、ハネスが死んでも最後のイベントから再開できる。資格証明もサンドボックスの外に置く。

ハネスをホスティングサービスの背後に置いた理由は、ハネスの実装がモデルの変化に伴って変わる可能性があるためだと理解した。記事がそれを直接言っているかどうかは要約のみで確認しており、断定はしない。

<summary>詳細な解説：計画・生成・評価の 3 つの役割</summary>

長期アプリ開発記事の構造は 3 つの役割である。プランナーは短いリクエストを製品仕様書に展開するが、技術的詳細は過剰に詰め込まない。初期エラーが下層に波及しないよう意図している。ジェネレーターは機能一つずつを実装する。エバリュエーターは Playwright を用いて実行中のアプリをユーザーのようにクリックし、基準と閾値で採点しバグを記録する。スプリント前にはジェネレーターとテスト可能な契約を結ぶ。

単純化版ではスプリント構造を省略し、エバリュエーターを最後に一度だけ回している。エバリュエーターはモデルが一人で安定して処理できない範囲のタスクのみで価値があるという。オーケストレーションによる複雑さ、トークン数、遅延が増えるコストも記事に記されている。
