서버를 띄우는 것까지는 어떻게든 했는데, 띄운 뒤에 "지금 잘 돌고 있나"를 알려면 따로 준비가 필요했다. 그 준비가 모니터링, 로그, 알림이다.

## 세 가지 신호

운영 중인 시스템에서 꺼내 볼 수 있는 정보는 크게 세 종류로 나눈다. OpenTelemetry 문서도 같은 셋을 신호(signal)라고 부른다.

| 신호 | 한 줄 정의 | 답해 주는 질문 |
|---|---|---|
| 메트릭 | 시간에 따라 찍히는 숫자(요청 수, 에러율, 메모리 사용량) | 지금 상태가 어떤가, 평소와 다른가 |
| 로그 | 일어난 사건 하나하나의 기록 | 그때 무슨 일이 있었나 |
| 트레이스 | 요청 하나가 여러 서비스를 거쳐 간 경로 | 어디서 느려졌나, 어디서 터졌나 |

OpenTelemetry는 트레이스를 "애플리케이션을 지나가는 요청의 경로", 메트릭을 "런타임에 측정한 값", 로그를 "이벤트의 기록"으로 설명한다.

보통 순서는 이렇다. 메트릭 그래프가 먼저 이상하다고 알려 주고, 트레이스로 범위를 좁히고, 로그에서 원인 문장을 찾는다. 숫자는 싸고 빠르지만 이유를 모르고, 로그는 이유가 있지만 양이 많아서 찾기 어렵다. 그래서 하나만 쓰지 않고 셋을 같이 쓴다.

## 메트릭: 무엇을 볼까

볼 게 너무 많으니 기준이 필요한데, Google SRE 책의 "네 가지 골든 시그널"이 가장 많이 인용된다.

| 신호 | 뜻 |
|---|---|
| 지연(latency) | 요청 하나 처리하는 데 걸리는 시간. 성공과 실패를 따로 본다 |
| 트래픽 | 시스템에 들어오는 요청량(초당 요청 수 같은 것) |
| 에러 | 실패한 요청 비율. 500뿐 아니라 200인데 내용이 틀린 경우, 너무 느려서 실패로 치는 경우도 포함 |
| 포화(saturation) | 가장 빡빡한 자원이 얼마나 찼는가 |

실패를 따로 보라는 이유는, 빨리 실패하는 요청이 평균 지연을 낮춰서 상황이 좋아 보이게 만들 수 있기 때문이다. 포화는 100%가 되기 전부터 성능이 떨어지는 시스템이 많아서 목표 사용률을 정해 두라고 한다.

### 평균 말고 백분위

지연은 평균으로 보면 속는다. 아래 코드는 1,000개 요청 중 980개는 100ms 안팎, 20개는 3초 걸린 상황을 흉내 낸 것이다.

```python
import random
lat = sorted([random.gauss(100, 20) for _ in range(980)] + [3000] * 20)
avg = sum(lat) / len(lat)
p50 = lat[len(lat) // 2]
p99 = lat[int(len(lat) * 0.99) - 1]
print(round(avg), round(p50), round(p99))   # 실행 결과 예: 156 99 3000
```

평균은 156ms라서 괜찮아 보이는데 p99는 3,000ms다. 요청 50개 중 1개는 3초를 기다린다는 뜻이다. p50은 중앙값, p99는 99%의 요청이 이 시간 안에 끝난다는 값이다. 지연 알림은 평균이 아니라 p95·p99 같은 꼬리 값에 거는 편이 낫다.

## 로그: 사람이 읽는 것에서 기계가 찾는 것으로

로그를 `print("에러 발생")`처럼 문장으로만 남기면 나중에 검색이 안 된다. 요즘은 JSON 같은 구조화된 형식으로 남기고, 요청마다 ID를 붙인다. 에러를 어떤 계층에서 잡고 무엇을 남길지는 [자세히 → 에러 처리와 로깅](#/post/be-error-logging)에 따로 적었다.

```python
import json, time, uuid

def log(level, msg, **kw):
    print(json.dumps({"ts": round(time.time(), 3), "level": level,
                      "msg": msg, **kw}, ensure_ascii=False))

rid = "req-" + uuid.uuid4().hex[:6]
log("info", "order created", request_id=rid, user_id=42, took_ms=120)
log("error", "payment failed", request_id=rid, upstream="pay-api", took_ms=3000)
```

실행하면 한 줄에 JSON 하나씩 나온다. `request_id`로 검색하면 한 요청이 지나간 흔적만 모아서 볼 수 있다. 서비스가 여러 개로 쪼개져 있으면 이 ID를 서비스끼리 넘겨 줘야 하는데, 그게 트레이스의 기본 발상이다.

로그에서 조심할 것은 세 가지다.

- 비밀번호, 토큰, 키, 개인정보를 남기지 않는다. 한 번 로그에 들어가면 여러 곳에 복사된다. 키 관리는 [자세히 → 시크릿·환경 변수 관리](#/post/cloud-secrets)에서 다뤘다.
- 레벨을 구분한다. 정상 흐름은 info, 사람이 봐야 하는 건 error. 전부 error로 찍으면 진짜 에러가 묻힌다.
- 양을 본다. 로그는 저장 용량과 검색 비용이 그대로 돈이라서, 요청마다 본문 전체를 남기면 청구서가 먼저 알려 준다.

## 트레이스: 요청 하나의 지도

트레이스는 요청 하나를 여러 구간(span)으로 나눠 각각 얼마나 걸렸는지 기록한 것이다. API 서버가 DB를 부르고 외부 결제 API를 부르는 요청이라면 span이 세 개쯤 생기고, 그중 어디가 길었는지가 한눈에 보인다. 서버 하나로 된 서비스에서는 로그와 메트릭만으로도 대부분 해결되고, 서비스가 여러 개이거나 서버리스 함수가 이어질 때 트레이스의 값어치가 커진다. 서버리스 얘기는 [자세히 → 서버리스](#/post/cloud-serverless)에 있다.

OpenTelemetry는 이 세 신호를 수집하는 방법을 벤더 중립적으로 표준화한 프로젝트다. 앱에 한 번 심어 두면 보내는 곳(저장소·대시보드)을 바꿔도 앱 코드를 안 고쳐도 된다는 게 장점이라고 한다.

<details>
<summary>수집하는 방식 두 가지(접어 둠)</summary>

- 끌어오기(pull): 모니터링 서버가 주기적으로 앱의 지표 주소를 찾아가서 읽는다. Prometheus가 대표적이다.
- 밀어 넣기(push): 앱이나 에이전트가 수집 서버로 직접 보낸다. 짧게 사는 작업이나 서버리스에서는 이쪽이 자연스럽다.

어느 쪽이든 앱은 "숫자를 노출한다"까지만 하고, 저장·그래프·알림은 별도 도구가 맡는 구조가 일반적이다.
</details>

## 알림 설계

모니터링에서 제일 어려운 부분은 수집이 아니라 알림이었다. 알림이 너무 많으면 다 무시하게 되고, 너무 적으면 장애를 사용자한테서 듣는다.

Google SRE 책과 Prometheus 문서가 공통으로 하는 말은 비슷하다.

- 원인이 아니라 증상에 알림을 건다. "CPU 90%"보다 "에러율 급증, 응답 느림"이 사용자가 실제로 겪는 문제다. CPU가 높아도 사용자가 못 느끼면 급하게 깨울 일이 아니다.
- 호출(page)은 급하고 사람이 할 일이 있을 때만 한다. 기계적으로 처리하면 되는 일이면 호출이 아니라고 SRE 책은 말한다.
- 이메일 알림은 쌓이면 소음이 되기 쉬워서, 당장 급하지 않은 문제는 대시보드로 보는 쪽을 권한다.
- 알림은 가능하면 적게, 사용자가 아픈 지점에만. 알림에는 관련 대시보드 링크를 달아 어느 구성 요소 탓인지 바로 보게 한다.
- 일시적인 흔들림은 넘어갈 여유를 둔다(조건이 일정 시간 이어질 때만 울리게).
- 용량이 한계에 다가가는 건 지금 사용자 영향이 없어도 알린다. 곧 장애가 될 일이라서다.
- 배치 작업은 실행 주기 두 번 이상의 시간을 기준으로 삼는다. 한 번 실패로는 사람이 할 일이 없으면 더 자주 돌리는 쪽이 낫다.

같은 문서에는 모니터링 시스템 자체도 감시하라는 내용이 있다. 알림 서버가 죽어 있으면 조용한 게 아니라 눈이 먼 것이라서, 외부에서 서비스를 찔러 보는 블랙박스 체크를 따로 두는 걸 권한다.

| 구분 | 화이트박스 | 블랙박스 |
|---|---|---|
| 보는 곳 | 시스템 내부(메트릭, 로그) | 사용자가 보는 바깥 동작 |
| 강점 | 곧 터질 문제, 재시도에 가려진 실패, 디버깅 | 지금 실제로 안 되는 것 |
| 약점 | 내부 지표가 많아 소음이 생김 | 아직 안 일어난 문제는 예측 못 함 |

둘 다 쓰는 게 보통이고, 호출은 블랙박스·증상 쪽에 건다.

## 장애가 났을 때 기본 순서

장애 대응은 원인을 찾는 일보다 피해를 줄이는 일이 먼저다. 여기서부터는 문서에서 읽은 내용이 아니라 일반적인 운영 순서를 적은 것이라, 팀마다 다를 수 있다.

1. 영향 범위 확인: 누가, 얼마나, 언제부터 안 되는가.
2. 최근 변경 확인: 직전 배포나 설정 변경이 있었다면 되돌리기가 가장 빠르다. 배포 쪽은 [자세히 → CI/CD](#/post/cloud-cicd)와 연결된다.
3. 완화: 롤백, 트래픽 줄이기, 인스턴스 늘리기. 원인은 나중에 찾아도 된다.
4. 원인 분석: 메트릭에서 시점을 잡고, 트레이스로 구간을 좁히고, 로그에서 문장을 찾는다.
5. 사후 정리: 같은 일이 반복되지 않게 알림·테스트·문서를 고친다. 사람을 탓하는 글이 아니라 구조를 고치는 글로 쓴다.

인스턴스를 늘리는 쪽은 [자세히 → 오토스케일링](#/post/infra-autoscaling)에서 따로 본다.

## 흔한 오해

- 모니터링과 관측 가능성(observability)은 같은 말이 아니다. 모니터링은 미리 정해 둔 지표를 지켜보는 것이고, 관측 가능성은 처음 보는 문제도 신호를 뒤져서 설명할 수 있는 정도를 말한다. 다만 이 구분은 문서마다 정의가 조금씩 달라서 이 글에서는 그 정도로만 쓴다.
- 지표를 많이 만들수록 좋은 게 아니다. 아무도 안 보는 그래프는 비용만 든다.
- 대시보드가 있으면 알림이 필요 없는 게 아니다. 사람은 24시간 화면을 보지 않는다.
- 평균 지연이 괜찮으면 괜찮은 서비스라는 생각은 위의 코드가 반례다.
- 알림은 많을수록 안전하다는 것도 반대다. 울리는 족족 무시되면 알림이 없는 것과 같다.
