个人信息不仅仅指姓名或身份证号，任何与其他信息结合后能够识别特定个人的数据均属于此类。因此，保护方法的核心在于：在加密之前，首要任务是尽可能少地收集数据，并缩短其持有时间。

## 什么是个人信息

韩国《个人信息保护法》将个人信息定义为“与活着的个人有关的信息”，不仅包括仅凭该信息本身即可识别特定个人的情况，也包括与其他信息结合后容易识别特定个人的情形。姓名、联系方式、电子邮件是显而易见的例子；IP 地址、设备 ID、位置信息等，一旦与其他信息关联，同样可以指向具体个人。下方的定义与 GDPR 第 4 条的内容相近。

GDPR 将“个人信息”（personal data）定义为“所有关于已识别或可识别自然人的信息”。无论是直接还是间接，只要能够通过姓名、身份编号、位置信息、在线标识符等确定某个人，即视为可识别。

这里的重点是“可识别性”。即使删除了姓名，若保留出生日期、性别、邮政编码等信息，仍可将范围缩小至特定个人。单个信息看似普通，但组合后往往就构成了个人信息。

## 保护的基本原则

GDPR 第 5 条列举了几项原则，其方向与韩国法律中的“最小收集原则”一致，因此一并整理如下：

| 原则 | 含义 |
|---|---|
| 目的限制 | 仅用于收集时声明的目的 |
| 最小收集 | 仅收集实现目的所必需的信息 |
| 存储限制 | 目的达成后，不得以可识别形式长期保存 |

韩国法律方面，在个人信息门户网站及首尔市教育厅的解说资料中，将其概括为“明确目的，并合法地仅收集实现该目的所需的最小限度信息”。

在设计服务时，这体现为：例如在用户注册环节，是否收集出生日期就需要慎重考虑。不需要的字段不应收集，因为不存在的信息自然无法泄露。

## 掩码、假名化与匿名化

“隐藏”一词包含不同层级，混用容易混淆。

| 方法 | 操作内容 | 示例 | 是否可还原 |
|---|---|---|---|
| 掩码 (Masking) | 部分隐藏或用标签替换 | 010-****-5678 | 若保留原始数据，则可能还原 |
| 假名化 (Pseudonymisation) | 在缺乏额外信息的情况下无法识别个人 | 电子邮件 → 哈希值 | 若单独保存的附加信息泄露，则可还原 |
| 匿名化 (Anonymisation) | 无法识别个人且不可复原 | 统计汇总数据 | 不可还原 |

韩国《个人信息保护法》第 2 条将假名化处理定义为：通过删除部分信息或部分或全部替换，使得在缺乏额外信息的情况下无法识别特定个人（依据生活法令解释标准）。GDPR 中的 pseudonymisation 也遵循相同结构。但必须附加条件：需单独保管附加信息，并采取技术和组织措施加以保护。

经过假名化处理的信息仍属于个人信息，因为存在某种“解密密钥”。因此不能将其称为匿名数据，原因就在于此。

## 亲自测试的掩码代码

运行了一段简短代码，使用正则表达式将身份证号、电话号码和电子邮件替换为标签，并基于哈希生成假名值。

```python
import re, hmac, hashlib

PATTERNS = [
    ("RRN",   re.compile(r"\b\d{6}-[1-4]\d{6}\b")),
    ("PHONE", re.compile(r"\b01[016789]-?\d{3,4}-?\d{4}\b")),
    ("EMAIL", re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+")),
]

def mask(text):
    for name, p in PATTERNS:
        text = p.sub(f"[{name}]", text)
    return text

def pseudonym(value, secret):
    return hmac.new(secret, value.encode(), hashlib.sha256).hexdigest()[:12]
```

输入 `"咨询：洪吉洞 010-1234-5678, hong@example.com, 身份证号 900101-1234567"` 后，电话号码、电子邮件和身份证号分别被替换为 `[PHONE]`、`[EMAIL]`、`[RRN]`。但“洪吉洞”保持不变。正则表达式只能匹配格式固定的值，无法处理如姓名这类无固定格式的内容。若要同时捕获姓名，则需要实体识别等专用工具，本次未进行尝试。

假名化结果对相同输入产生相同输出，而不同密钥则生成不同结果。有观点认为不应使用简单哈希（仅 SHA-256），因为对于候选项有限的值（如电子邮件），可通过对所有候选项进行哈希并比对来破解。因此采用了混合了密钥的 HMAC。该密钥必须与数据分开保管，才能满足假名化的条件，这一点类似于 [密钥管理](#/post/sec-keys)。

## 使用 AI 服务时的注意事项

在使用 AI 时，个人信息泄露的路径大致已明确。

- 提示词：用户提出的问题中会直接包含姓名、电话号码和原始客户咨询内容。一旦发送给外部模型 API，这些数据就会流出我的服务器。因此，在发送前通常会经过类似的掩码处理结构。[提示词](#/post/ai-prompt)中包含什么内容，决定了数据流向何处。
- 对话记录与日志：如果将请求和响应完整记录到日志中，这些日志就会成为个人信息存储库。还需要规定保留期限。
- 检索增强：通过 [RAG](#/post/ai-rag) 附加公司内部文档时，即使对无权人员的问题，也可能检索到他人的个人信息并将其混入回答中。必须在检索阶段过滤访问权限。
- 供应商侧处理：发送给外部 API 的数据是否被供应商用于学习、保留多久，因厂商和套餐而异。必须直接查看所用服务的条款和数据处理文件。
- 模型记忆的内容：有研究表明，包含在训练数据中的个人信息可能会被模型原样输出。
- 注入攻击：存在诱导模型说出“刚才看到的客户信息”的攻击方式。详细内容已另行记录在 [提示词注入](#/post/sec-prompt-injection) 中。

## 常见误解

- 删除了姓名就是匿名：与其他信息结合后仍可重新识别。假名处理和匿名化处理是不同的。
- 加密了就解决了个人信息问题：加密仅保护存储和传输过程中的数据，一旦解密使用，该信息仍然是个人信息。收集多少、保留多久与加密无关。
- 公开的信息可以随意使用：即使已公开，也必须遵循在目的范围内使用的原则。
- 日志不是个人信息：如果日志中包含 IP 地址或请求正文，则可能属于个人信息。

<details>
<summary>详细解析：如何产生可识别性</summary>

可识别性的判断标准并非“仅凭这一条信息能否识别某人”，而是“与我方持有的其他信息结合后能否识别”。例如，会员表中仅有会员编号而无姓名，但若另一张表包含会员编号和姓名，则可通过合并两张表进行识别。在此情况下，会员表也应视为个人信息。

此外，与外部数据结合的情况也存在。即使信息中未直接包含姓名，若邮编、出生年月日、性别等组合能与外部公开资料匹配，即可锁定到特定个人。这就是“仅删除姓名并不代表匿名”的原因。

在实际工作中，通常会为不同使用目的创建仅提取必要字段的独立视图；分析用途则提供经过假名处理的数据；而原始数据与假名映射信息应限制在更严格的访问范围内。这是一种通用的设计方式，并非基于特定指南的要求。

</details>
