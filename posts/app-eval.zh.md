LLM 应用的评估并非凭感觉判断“这个答案好不好”，而是将其转化为预先设定的问题与评分标准下的数字，以便每次修复时都能用同一把尺子进行比较。

## 为什么需要单独的评估？

普通代码在输入相同的情况下输出也相同，因此只需一行测试即可结束。而 LLM 应用的答案每次都会有所不同，正确与错误的界限也模糊不清。因此，很容易修改一行提示词（prompt），运行几次后觉得“还行”就草草了事。

问题在于：修改后的版本虽然变好了，但另一个版本却在悄然变差。如果没有评估机制，用户会最先察觉到这一点。Hamel Husain 的文章警告称，忽视评估、仅专注于调整提示词和模型的做法，会导致陷入“打地鼠式回归”。评估就是让这只“老鼠”显形的装置。

## 首先明确成功标准

Anthropic 的文档指出，在构建评估体系之前，必须先定义成功标准。一个好的标准应具备具体性、可测量性、可实现性，并与应用目标相匹配。不应使用“性能良好”这类模糊表述，而应像“情感分类准确”这样具体；通常单一指标是不够的，需要结合多个维度。文档中的示例包括：F1 分数不低于 0.85、无害输出占比达 99.5%、95% 的响应在 200ms 内等。

在此阶段确定的内容非常多。如果没有标准，就无法确定要收集哪些问题，也无法选择合适的评分器。

## 黄金测试集（Golden Set）

黄金测试集是将输入与“正确答案或通过条件”配对后整理而成的问题集合。它是评估体系的骨架，其质量在此几乎就已定型。

Anthropic 文档提出的设计原则有三条：

- **贴合任务**：使其接近实际使用分布，并纳入边界案例，如不合常理的输入、过长的输入、模糊的输入以及有害的输入等。
- **尽可能实现自动评分**。
- **重数量轻质量**：即使信号稍弱，拥有更多可自动评分的问题，也比依赖人工少量评分的问题更优。

关于问题来源，Hamel 的文章建议利用 LLM 合成输入并加以使用，同时每当发现新的失败案例时持续追加。从实际日志中提取失败的案例并加入黄金测试集，似乎最具价值。

## 三种评分方法

| 方法 | 如何实现 | 适用场景 | 局限性 |
|---|---|---|---|
| 代码评分 | 字符串匹配、包含检查、正则表达式、嵌入相似度（如 ROUGE）等指标 | 分类任务、数字/格式验证 | 难以处理表述多样的开放式回答 |
| LLM 评分 | 由另一个 LLM 依据标准给出分数或判定是否合格 | 语气、摘要质量、开放式回答 | 评分器本身可能出错 |
| 人工评分 | 由人直接阅读并判断 | 制定标准时、验证评分器 | 速度慢且成本高 |

Anthropic 文档中的五个示例评估完全符合此表：推文情感分类采用归一化后的字符串匹配，FAQ 一致性使用 SBERT 嵌入的余弦相似度，摘要任务采用 ROUGE-L，客服语气由 LLM 给出 1~5 分评分，医疗聊天机器人的个人健康信息探测则由 LLM 以 yes/no 形式作答。

顺序上应从低成本的方法开始。Hamel 也建议先部署类似单元测试的快速且廉价的检查，再将基于模型的评估构建在其之上。若从模型评估入手，不仅更昂贵、更缓慢，而且收益有限。

## 小规模试运行

仅用代码评分，我亲手编写并运行了黄金测试集与回归检测的机制。为控制变量，特意将模型调用替换为模拟函数。此处仅展示评估框架的结构：

```python
golden = [
    {"id": 1, "q": "환불 기한이 며칠이야?", "must": ["7일"], "must_not": ["30일"]},
    {"id": 2, "q": "배송비는 얼마야?", "must": ["3,000원"], "must_not": []},
    {"id": 3, "q": "오늘 날씨 어때?", "must": ["모르"], "must_not": []},
]

def check(case, out):
    return all(m in out for m in case["must"]) and not any(m in out for m in case["must_not"])

def run(app):
    res = {c["id"]: check(c, app(c["q"])) for c in golden}
    return res, sum(res.values()) / len(res)

r1, s1 = run(app_v1)   # 프롬프트 고치기 전
r2, s2 = run(app_v2)   # 고친 뒤
print("회귀:", [i for i in r1 if r1[i] and not r2[i]])
print("개선:", [i for i in r1 if not r1[i] and r2[i]])
```

假应用 v1 对天气问题生成虚构回答（“晴朗”），而 v2 虽表示不知天气，却错误地将退款期限设为 30 天。执行结果如下：

```
v1 {1: True, 2: True, 3: False} 0.67
v2 {1: False, 2: True, 3: True} 0.67
회귀: [1]
개선: [3]
```

两个版本的得分均为 0.67。仅看平均数值会得出“无变化”的结论，但实际上是一个版本改进、另一个版本退化。因此，不能只看单一分数，而应将各问题的结果与前一版本并列展示，单独识别回归现象（即之前正确而现在出错的情况）至关重要。

## LLM-as-judge

对于开放式回答，由于无法通过字符串匹配进行评分，因此采用交由另一个 LLM 进行评分的方法，称为 LLM-as-judge。Zheng 等人的论文（如 MT-Bench、Chatbot Arena）报告称，GPT-4 等强大模型与人类偏好的吻合度超过 80%，且接近人与人之间的共识率。同一篇论文的摘要仅提及局限性：位置偏差、冗长偏好和自强化偏差。

实务指南在各文档中大同小异。

- 使用生成的模型以外的模型进行评分（Anthropic）。
- 限制评分器的输出范围。仅要求输出数字，或仅输出 yes/no，并将待评分的答案包裹在 `<response>` 等标签中（Anthropic）。
- 尽可能选用性能更优的模型作为评分器（Hamel）。
- 将评分器与人工判断进行对比以进行校准，并定期重新检查。评分器本身就是一个需要管理的系统（Hamel）。

<details>
<summary>详细解析：评分提示词的格式</summary>

参考 Anthropic 文档中的示例，大致可以形成如下框架。

```
아래 <response>가 다음 기준을 만족하는지 판단해라.
기준: 환불 기한을 정확히 말하고, 정책에 없는 약속을 하지 않는다.
<response>
{{답변}}
</response>
yes 또는 no만 출력해라.
```

以 yes/no 等二值形式开始较为易于管理。Hamel 也提到，最初应使用简单的“好/坏”标签，处理精细分数较为困难。若采用 5 分制量表，3 分和 4 分的界限容易模糊，导致评分器之间、人工之间产生分歧。

验证评分器是否准确的方法是：让人工对少数标注样本进行评分，然后与评分器的结果进行比较。Hamel 指出，在数据不平衡的情况下，简单的准确率或精确率会掩盖少数类的失败，因此建议关注精确率和召回率。例如，如果错误答案仅占 5%，即使全部标记为“好”，准确率也能达到 95%。

</details>

## 何时运行评估

评估不是一次性构建完成的，而是每次变更时都需要重新运行。当提示词、模型版本、检索设置（如 [自行构建 RAG](#/post/app-rag-build) 时的块大小或 top-k 等参数）、工具定义发生变化时，都需要重新运行。这种重复过程属于回归测试。类似于单元测试，可以将可自动运行的部分（格式检查、违禁词检查）与耗时较长、仅在部署前运行的部分（LLM 评分、人工审核）区分开来，这是务实的做法。

基于模型的评估每次调用都会产生费用，随着黄金集（Golden Set）的扩大，评估成本也将成为应用总成本的一项。这部分内容将在 [AI 服务成本](#/post/app-cost) 中继续探讨。

## 评估什么

| 想要观察的方面 | 评估方法示例 |
|---|---|
| 有标准答案的任务（分类、抽取） | 准确率、F1、完全匹配率 |
| 格式 | JSON 解析成功率、模式通过率（参考 [结构化输出](#/post/ai-structured-output)） |
| 生成内容 | 在依据文档中未出现的陈述比例（参考 [幻觉](#/post/ai-hallucination)） |
| 安全性 | 应拒绝输入的拒绝率、泄露尝试拦截率（参考 [护栏](#/post/app-guardrails)） |
| 响应速度 | 延迟时间分布 |
| 成本 | 每请求令牌数、每请求金额 |

不应将所有指标合并为一个数字，而应按维度分别查看。这是因为像上述实验一样，平均值可能会掩盖某些问题。

## 常见陷阱与误解

- 仅凭感觉进行检查。这是 Hamel 指出的首要陷阱。
- 依赖与我们产品失败模式无关的通用评估工具和分数（同文）。
- 相信自动评分可以替代人工审查。Hamel 对“可以消除人工”的工具主张持怀疑态度，并建议持续阅读数据。他将“不再学到新东西”作为停止学习的标准。
- 认为合格率达到 100% 是目标。允许一定的失败率是产品应负责的部分。
- 黄金集中只包含简单问题。分数很高，但在实际使用中却频频出错。
- 直接将评估问题放入提示词示例中。这样会导致评估泄露（类似考试泄题），使分数失去意义。
- 将评估变成提升指标数字的游戏。如果数字上升但用户不满依旧，说明黄金集未能反映现实情况。

像 [提示注入](#/post/sec-prompt-injection) 这样的攻击案例，若单独收集在评估问题中，可以立即察觉防御是否失效。
