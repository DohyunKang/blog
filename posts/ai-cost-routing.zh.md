LLM API 的费用等于所用 Token 数量乘以单价。因此，降低成本的方法可以归纳为同时调整乘法等式两边的变量：使用单价较低的模型、通过折扣方式调用，或者减少 Token 本身的使用量。

## 费用是如何计算的

[LLM](#/post/ai-llm) API 分别计算输入 Token 和输出 Token。单价通常以 100 万 Token (MTok) 为基准，且输出的价格高于输入。以下是 Anthropic 官方价格页面的标准价格（截至 2026-11-04 的数值，价格可能会变动）。

| 模型 | 输入 | 输出 | 批量输入 | 批量输出 |
|---|---|---|---|---|
| Claude Opus 5.5 | $4 | $20 | $2 | $10 |
| Claude Sonnet 5.5 | $2 | $10 | $1 | $5 |
| Claude Haiku 5.5 (提示词少于 10 万 Token) | $0.10 | $0.50 | $0.05 | $0.25 |

基于同一页面，Opus 与 Haiku 的输入价格相差 40 倍，输出价格也相差 40 倍。仅仅更换一个模型，成本就会发生数量级（从个位数变为两位数）的变化。各模型的详细特征已在 [AI 模型地图](#/post/ai-models) 中另行整理。

为了便于估算成本，我们设定了一个假设场景：每天处理 1,000 次请求，每次请求输入 2,000 Token、输出 500 Token。

```
하루 입력 = 1,000 × 2,000 = 200만 토큰
하루 출력 = 1,000 × 500  =  50만 토큰
```

将上述数据与上表相乘，结果如下：

| 模型 | 每日成本 | 30 天 |
|---|---|---|
| Opus 5.5 | $8 + $10 = $18 | $540 |
| Sonnet 5.5 | $4 + $5 = $9 | $270 |
| Haiku 5.5 | $0.2 + $0.25 = $0.45 | $13.5 |

输入 Token 的数量取决于在提示词中填充了多少 [上下文](#/post/ai-context)。随着对话变长或附加的文档增多，每次请求的输入量会增加。[上下文窗口](#/post/ai-context-window) 大意味着可以容纳更多内容，但这并不意味着免费。

## 模型路由

不同请求的难度各不相同。分类、简短提取、格式转换等任务可以使用小模型完成，而长推理或代码生成则需要大模型。路由是前端部分，负责根据收到的请求决定将其发送给哪个模型。

```
요청 → [라우터: 난이도 판단] ─ 쉬움 → 작은 모델 (Haiku급)
                            └ 어려움 → 큰 모델 (Sonnet·Opus급)
```

在上述假设中，将 80% 的请求发送给 Haiku，20% 发送给 Sonnet，每日成本如下：

```
0.8 × $0.45 + 0.2 × $9 = $0.36 + $1.80 = $2.16
```

如果全部使用 Sonnet，每日成本为 $9，现在降至其四分之一水平。这也表明大模型占据了成本的绝大部分。虽然只发送了 20% 的请求，但其中却产生了 80% 的成本。

构建路由器的方法有几种：

- **规则**：根据输入长度、请求类型（是分类还是创作）、用户等级等进行划分。这是最简单且易于调试的方法。
- **让小型模型进行判断**：指示小模型仅回答“简单/困难”。此调用本身会产生成本，因此必须使用非常廉价的模型。
- **先尝试小模型，失败则转大模型**：让小模型先回答，若未通过格式检查或可信度评估，则重新发送给大模型。缺点是失败的尝试也会产生额外成本。

如果路由器将困难请求错误地发送给简单模型，会导致质量下降。仅凭成本调整无法察觉此问题，因此每次调整后都需要使用 [评估集](#/post/ai-evals) 进行分数对比。

## 缓存

对重复出现的提示词前半部分处理结果进行重用的提示词缓存（Prompt Caching），能大幅降低输入侧的单价。在价格页面的 Sonnet 5.5 行中，缓存命中的价格为 $0.10/MTok，仅为标准输入价格 $2 的五十分之一。不过，使用缓存的请求价格为 $2.50/MTok（基于 5 分钟缓存），略高于标准价格。其原理和用法已在 [提示词缓存](#/post/ai-prompt-caching) 文章中整理，此处仅说明其作为成本优化手段的地位。对于系统提示词或长文档等每次请求都会附加的较大内容块，效果越显著。

如果是完全重复相同问题的服务，也可以直接存储答案本身。这种方式无需调用模型，因此成本为零。但前提是问题必须完全一致，因此在用户表达方式各不相同的服务中，命中率较低。

## 批量 API

对于不需要立即回复的任务，可以提交为批量请求。上表中的“批量”列即为此类，Anthropic 页面指出输入和输出均享有 50% 的折扣。OpenAI 的批量指南也提到相比同步 API 可享受 50% 的成本折扣，并在 24 小时内完成（通常更快），适用于评估运行、大规模数据分类和内容嵌入等任务。

此类任务包括夜间分类、文档批量摘要、评估集遍历等无需人工等待的操作。不能用于需要用户在屏幕前等待的请求。价格页面还提到，此折扣可能会与其他价格调整（如缓存）叠加适用。

Sonnet 5.5 的每日费用为 $9，若使用批处理则降至 $4.5。

## 减少输出量

在 Sonnet 5.5 中，输出的单位成本是输入的 5 倍（从 $10 降至 $2），因此减少一个输出令牌的价值高于减少一个输入令牌。

- 根据业务需求限制最大输出长度 (`max_tokens`)。
- 在提示词中强制规定格式，例如“仅用一个词分类”或“只输出 JSON"。
- 指示不要添加不必要的引言和总结。

仅缩短长度可能导致回答被截断，因此此方法仅适用于允许截断的任务。

## 减少调用次数

不呼叫模型是最便宜的方式。

- 避免将可通过规则或普通代码处理的逻辑（如正则表达式、条件判断、数据库查询）交给模型。
- 存储相同输入的结果以供重用。
- 如果可能，批量处理多项内容。这可以减少系统提示因每次请求而重复计费的情况。
- [代理循环](#/post/ai-agent-loop) 会在单次请求中多次调用模型。如果不限制循环次数，成本可能会超出预期。
- 与其通过 [RAG](#/post/ai-rag) 直接附加整个文档，不如仅附加所需的片段，从而减少输入令牌数量。

## 自行运行开源模型时

在自有 GPU 上运行开源模型可以消除每令牌的费用，但会产生固定的 GPU 成本。云 GPU 按小时计费，而自有设备则涉及购置成本和电费。无论使用与否，这些成本都会产生。

因此，比较方式如下：

```
API 비용      = 월 토큰 수 × 단가            (쓴 만큼 늘어남)
자체 운영 비용 = GPU 월 비용 + 운영 인력·시간   (거의 고정)

손익분기 월 토큰 ≈ 자체 운영 월 비용 ÷ API 토큰당 단가
```

当确定自有运营的月度成本后，可将其除以上述单位价格，计算从每月使用多少令牌开始，自有运营变得更具成本效益。不过，此计算中容易遗漏一些项目：GPU 闲置时间、配置和修复服务软件的时间，以及模型性能可能无法达到大型 API 模型的可能性。对于每日几百次用量的场景，如上表所示，Haiku 级别的月费约为十几美元，往往无法覆盖 GPU 固定成本。相反，如果流量大且稳定，且小模型足以满足需求，则自有运营更为合适。具体的盈亏平衡点需要代入实际的 GPU 费用和处理量进行计算。

假设：每日 1,000 次请求，每次请求输入 2,000 令牌、输出 500 令牌，共 30 天。

| 配置 | 每日 | 30 日 |
|---|---|---|
| 全部使用 Sonnet 5.5 | $9 | $270 |
| 全部使用 Sonnet 5.5 批处理 | $4.5 | $135 |
| 80% Haiku + 20% Sonnet | $2.16 | $64.8 |
| 全部使用 Haiku 5.5 | $0.45 | $13.5 |

路由和批处理可以叠加使用。例如，先进行路由，然后仅对可异步的请求进行批处理。缓存可以降低输入单位成本，因此总成本可能比上表更低。

## 从哪里开始减少

大致顺序如下：首先通过日志识别哪些请求消耗大量令牌；接着减少调用次数和输出长度；如果循环部分较大则使用缓存；对于无需人工等待的任务移至批处理；最后添加路由策略。更换模型对质量影响最大，因此应在拥有评估集时进行。

## 常见误解

- 便宜的模型总是有利可图：小模型出错导致重试或重新请求增加时，节省的费用会消失。
- 缓存总是更便宜：写入缓存的请求比标准请求更贵，如果不再次读取则会造成损失。
- 输入越长费用越相似：输入按令牌数量计费，长度越长费用线性增长。
- 自有 GPU 是免费的：虽然没有每令牌费用，但存在固定成本。
