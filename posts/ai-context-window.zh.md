# 上下文窗口与 Token

上下文窗口（Context Window）是模型在生成一个回答时一次性能够“看到”的内容上限，而衡量这一内容容量的单位是 Token。了解这两个概念，几乎就能解释清楚“为什么对话变长后就会变慢且变贵”。

## Token 是什么

Token 是模型在读写文本时使用的基本单元。它既不是字符也不是单词，而是介于两者之间。Anthropic 的术语表指出，Token 可能对应于单词、子词（subword）、字符，甚至字节。模型接收文本后，首先将其转换为这些片段的序列进行处理。

常见的片段会被组合成一个 Token，而生僻的词则会被拆分成多个片段。OpenAI 关于 tiktoken 的说明中也有类似的例子，例如将 "encoding" 拆分为 "encod" + "ing"。如果将常用的片段组合得更大，就可以用更少的 Token 表达相同的文本，从而提高效率；同时由于可以拆分，也能处理首次出现的生词。

大致情况就是这样。tiktoken 的 README 指出，平均而言一个 Token 约为 4 字节。换算成英文，大约相当于 3~4 个字符。Claude 的术语表也提到，基于旧版模型，一个 Token 约等于 3.5 个英文字符；而从 4.7 版本以后的模型使用了新的分词器（tokenizer），使得相同文本所需的 Token 数量增加了约 30%。由于不同模型代际的数字各不相同，文档建议通过目标模型的 Token 计数工具来获取准确数值。

## 为什么韩语消耗更多 Token

在此背景下，韩语处于劣势。原因可以归纳为两点：

- 在 UTF-8 编码中，一个韩文字符占用 3 字节，而一个英文字母仅占 1 字节。在以字节为单位进行切分的方式下，韩语从一开始就处于不利地位。
- 如果分词器的词典主要以英语为主构建，那么英文单词可以整体作为一个 Token，而韩语则需按音节单位被细碎地拆分。

前者是通用原理，具体某个分词器如何精确切分则因模型而异。我们找到了一个实测案例：一位开发者将同一篇博客文章分别用英语、韩语、日语和中文进行 Token 计数，结果如下。

| 相对于英语的韩语 Token 数量 | 比例 |
|---|---|
| o200k（OpenAI 最新分词器） | 1.38 倍 |
| cl100k（OpenAI 旧版分词器） | 1.82 倍 |
| Claude 分词器（公开版本） | 1.88 倍 |

从单个句子来看，"I refactored the agent loop to cut token usage." 为 12 Tokens；而韩语 "토큰 사용량을 줄이려고 에이전트 루프를 다시 짰다." 在 o200k 下为 20 Tokens，在 Claude 分词器下则为 32 Tokens。值得注意的是，"에이전트"（agent）在 o200k 中被拆分为 4 个 Token，而英文单词 "agent" 仅占 1 个 Token。

这些数字需谨慎看待。作者指出，由于目标对象是包含大量英语代码和术语的技术博客，普通韩语散文的差距可能更大；同时强调 Token 数量并不直接等同于成本，因为韩语可以用更少的字符表达相同含义。

简而言之，“韩语通常比英语消耗更多 Token，具体倍数因分词器和文本类型而异，范围从 1.4 倍到更高”。从上述表格可以看出，随着新分词器的出现，差距呈缩小趋势（从 cl100k 到 o200k，韩语用量减少了约 24.7%）。

## 窗口大小的含义

窗口指的是“单个请求中可以包含的 Token 总量”。这与整个训练数据集无关；用 Anthropic 文档中的说法，这是模型的“工作记忆”（working memory）。模型内部存储的知识不计入其中，只计算当前请求中携带的内容。这一概念本身已在 [详见 → 上下文](#/post/ai-context) 中单独整理。

窗口大小因模型而异。根据本文档，Claude 的最新模型（如 Opus 5.5、Sonnet 5.5、Haiku 5.5 等）拥有 100 万 Token 的上下文窗口，单次请求的最大输出为 128,000 Tokens。部分旧版模型的窗口为 20 万 Token。这些数字经常变化；若几个月后阅读本文，建议重新查阅模型对比表。

## 输入与输出共同占用窗口

起初容易混淆的一点是：窗口不仅计算输入，还包括输出。文档明确指出，窗口包含“模型可参考的文本，包括响应本身”。系统提示（system prompt）、`messages` 中的所有消息（包括工具结果、图像、文档等）、工具定义均被计入，模型生成的回答及其思考过程（thinking）也一并纳入。

因此，当输入填满窗口时，便无空间用于输出。根据文档，若仅输入就超过窗口限制，会返回 400 错误（"prompt is too long"）；而 Claude 4.5 及后续模型即使输入加 `max_tokens` 超限，仍会接受请求，但在生成过程中触及极限时会停止并抛出 `model_context_window_exceeded` 错误。

```
[ 시스템 프롬프트 | 도구 정의 | 지난 대화 | 이번 질문 | 모델이 쓰는 답 ]
 └──────────────── 전부 합쳐서 윈도우 하나 ────────────────┘
```

## 每次调用都会重新计算全部

这是本文中最需要记住的一点：对话看似连续不断，但 API 本身并不具备记忆。按照文档说明，每个回合的输入阶段都包含“之前的完整对话 + 本次用户消息”，而模型生成的回答则成为下一回合的输入。因此，每当我敲下一行字，之前的所有对话都会被重新发送。

为了有个直观概念，我进行了假设性计算（并非实际测量，仅为简单推演）：

- 每个回合对话增加约 1,000 个 token，共进行 20 个回合。
- 第 n 次调用的输入约为 n × 1,000 个 token。
- 第 20 次调用的输入约为 2 万个 token。
- 将 20 次调用中输入的所有 token 累加：1+2+…+20 = 210，即约 21 万个 token。

对话总长度仅为 2 万 token，但实际消耗的输入却达到 21 万 token。随着回合数增加，累计总量几乎呈平方级增长。若将回合数翻倍（40 个回合），累计量将达到约 82 万 token，约为原来的四倍。拖得越长，“多问一次所需的额外成本”就越大。

## 变长后的成本、速度与质量

- **成本**：API 按输入 token 和输出 token 计费。如前所述，每次调用都会累积之前的内容并重新发送，因此对话越长，单次调用的费用越高。使用提示词缓存（prompt caching）可有所帮助。根据文档，读取缓存的费用约为基本输入单价的 0.1 倍（部分模型为 0.05 倍或 0.025 倍），写入缓存方面，5 分钟缓存为 1.25 倍，1 小时缓存为 2 倍。默认缓存有效期为 5 分钟，若长时间未使用则缓存会过期。
- **速度**：输入越长，生成第一个 token 所需时间往往越长。文档指出，对于长文本，使用缓存通常能改善首 token 生成时间。
- **质量**：这是最容易被忽视的方面。Anthropic 文档提到：“更多的上下文并不自动意味着更好。随着 token 数量增加，准确率和召回率会下降，这种现象称为 context rot（上下文腐烂）。”

关于质量影响，已有两项研究可供参考：

- Liu 等人“Lost in the Middle”：当相关信息位于输入开头或结尾时性能最佳，若处于中间则性能显著下降，即使在专为长上下文设计的模型中也观察到类似现象。
- Chroma“Context Rot”：对比了 18 个模型，即使固定任务难度，输入越长性能越差；若存在相似但错误的干扰段落，长度增加会导致性能波动更剧烈。在相同对话中，比较约 300 token 的短输入与约 11.3 万 token 的全量输入时，前者表现明显更好。

这两项均为特定实验。Chroma 自身也承认未解释原因；而位置效应在两项研究中结论不一（“Lost in the Middle”认为存在位置效应，但 Chroma 的 needle 实验中并未观察到明显的位置效应）。因此，不应简单理解为“越长越差”，而应视为“越长可能越不稳定”。

## 压缩（Compaction）

当上下文窗口接近满时，通常有三种选择：开启新对话、截断旧内容，或进行摘要以延续对话。Compaction 即第三种方式。Anthropic 文档将其定义为：将早期回合替换为 Claude 在服务器端生成的摘要，从而将对话保持在当前窗口内。此举也有助于维持较小的活跃上下文。

文档中介绍的方法主要分为两类：

| | 通过请求直接启用 | 基于 token 限制自动触发 |
|---|---|---|
| 由谁决定触发时机 | 应用方（我） | API 在输入达到阈值时自动触发 |
| 是否保留最近回合原文 | 支持 | 暂停后重新注入 |
| 是否可在后台运行 | 支持 | 不支持（需在原请求内执行） |

两者均标注为 beta 功能。由于尚未亲自试用，对其行为仅了解文档描述层面。客户端也可自行实现摘要逻辑。

其原理简单且代价明确：摘要中丢失的信息无法找回。因此文档也建议，若基础摘要策略遗漏后续回合所需内容，应直接编写自定义摘要提示词。保留什么内容本身就是系统设计的关键部分。这类任务常由 Harness 承担，详情可参考 [深入解析 → Harness](#/post/ai-harness)。

## 常见误解

- 窗口大小为 100 万，所以可以全部填入：填入并不等于有效利用。context rot 研究已揭示其中的差异。
- 窗口仅指输入大小：实际包含输出及思考（thinking）token。
- 模型能记住之前的对话：并非真正“记住”，而是每次重新接收前文。聊天应用只是对此进行了视觉上的隐藏处理。
- 使用缓存就不用担心窗口问题：文档指出，已缓存的提示词同样占用窗口空间。变化的是费用而非空间。
- 韩语比英语精确 N 倍：取决于 tokenizer 的实现方式。最准确的方法是亲自用我的文章和我的模型进行测算。

<details>
<summary>详细解析：思考（thinking）token 与上下文窗口</summary>

思考令牌是 `max_tokens` 的一部分，按输出令牌计费并计入窗口。不同模型对是否将上一轮的思考保留到下一请求的处理方式各不相同。根据文档，Opus 4.5 之后的 Opus、Sonnet 4.6 之后的 Sonnet、Haiku 5.5 等模型默认保留之前的思考块，将其作为普通输入使用并再次按输入计费。而此前的 Opus、Sonnet 和 Haiku 4.5 及更早版本，API 会自动剥离思考部分。思考令牌在生成时按输出计费一次；对于保留思考的模型，在后续请求中还会再次按输入计费。

在使用工具的情况下，工具请求与结果也会以相同方式累积。由于工具定义本身会占用窗口空间，文档专门提供了减少工具定义或延迟加载的工具建议。

<summary>详细解析：模型是否知晓剩余令牌</summary>

根据文档，Sonnet 5、Sonnet 4.6、Haiku 4.5 等模型具备“上下文感知”功能，会将完整预算注入系统提示符，并在工具调用后告知剩余量。Opus 4.7 之后及 Sonnet 5.5 等模型则不再接收该标签，而是通过 task budget（beta）来分配预算。
