Evals는 LLM 기능이 제대로 동작하는지 재는 시험지와 채점 방식의 묶음이다. 입력 모음(평가 데이터셋), 맞는 답의 기준, 채점 방법이 한 세트고, 프롬프트나 모델을 바꿀 때마다 같은 시험지로 다시 풀려서 점수를 비교한다.

## 왜 필요한가

일반 소프트웨어는 같은 입력에 같은 출력이 나오니 단위 테스트로 충분하다. [LLM](#/post/ai-llm)은 그렇지 않다. OpenAI의 평가 가이드는 생성형 AI가 비결정적이라 기존 방식의 테스트로는 부족하고, 그 변동 속에서 정확도·성능·신뢰성을 재는 구조화된 테스트가 evals라고 설명한다.

기업이 LLM 기능을 서비스에 넣으면 바뀌는 게 많다. [프롬프트](#/post/ai-prompt) 한 줄, 모델 버전, [RAG](#/post/ai-rag)의 검색 설정, 도구 목록이 전부 답을 바꾼다. 한 군데를 고쳐서 A 질문이 좋아졌는데 B 질문이 나빠졌는지는 눈으로 몇 개 보는 걸로는 알기 어렵다. OpenAI 가이드도 이런 "느낌으로 판단하기(vibe-based evals)"와 출시한 뒤에야 평가를 붙이는 것을 안티패턴으로 꼽는다.

그래서 평가는 개발의 앞쪽에 둔다. 두 가이드 모두 평가를 한 번 하고 끝내는 게 아니라 계속 돌리는 것으로 본다.

## 전체 흐름

OpenAI 가이드의 5단계를 줄이면 이렇다.

```
목표 정의 → 데이터셋 수집 → 지표 정의 → 실행·비교 → 지속 평가
   │            │              │           │           │
 성공이 뭔가   입력+정답 모음   어떻게 채점  점수 비교   변경마다 재실행,
                                                       세트 키우기
```

Anthropic 문서는 성공 기준부터 잡으라고 한다. 좋은 기준은 구체적(Specific)이고, 측정 가능하고(Measurable), 달성 가능하고(Achievable), 관련이 있어야(Relevant) 한다. 문서의 대비 예시는 이렇다.

| 나쁜 기준 | 좋은 기준 |
|---|---|
| 감정 분류를 잘해야 한다 | 1만 건의 다양한 트윗 보류 세트에서 F1 0.85 이상, 현재 기준선보다 5% 개선 |
| 유해한 답이 없어야 한다 | 1만 번 시도 중 콘텐츠 필터가 유해로 잡는 출력 0.1% 미만 |

기준이 하나인 경우는 드물어서, 문서도 대부분의 사용 사례가 여러 기준(과제 충실도, 일관성, 관련성, 톤, 개인정보 보호, 맥락 활용, 지연, 가격 등)을 함께 봐야 한다고 적는다.

## 평가 데이터셋

시험지에 해당하는 부분이다. 두 문서가 겹치는 원칙이 몇 개 있다.

- 실제 서비스에 들어올 입력 분포를 닮게 만든다. 학술 지표나 업무와 무관한 데이터로만 짜면 점수와 실제 품질이 어긋난다(Anthropic: task-specific, OpenAI: 프로덕션 트래픽과 안 맞는 데이터셋이 안티패턴).
- 흔한 경우, 경계 사례, 공격적·적대적 입력을 섞는다. Anthropic 문서가 예로 드는 경계 사례는 관련 없거나 존재하지 않는 입력, 지나치게 긴 입력, 부적절한 입력, 사람끼리도 판단이 갈리는 모호한 경우다.
- 출처는 섞는다. OpenAI 가이드는 합성 데이터, 도메인 데이터, 사람이 만든 것, 운영 로그, 과거 데이터를 든다. 로그를 전부 남겨 두면 나중에 좋은 평가 사례의 재료가 된다고도 한다.
- 합성으로 만든 사례는 전문가가 라벨을 붙이는 쪽을 권한다.
- Anthropic은 품질 높은 사람 채점 몇 개보다, 신호가 조금 약해도 자동 채점되는 문항을 많이 두는 쪽이 낫다고 한다(volume over quality).

데이터 한 줄은 대략 이런 모양이다. OpenAI Evals 문서의 예시도 입력(`ticket_text`)과 사람이 붙인 정답(`correct_label`)을 한 항목에 둔다.

| id | 입력 | 정답 기준 |
|---|---|---|
| refund-1 | "환불 기간이 어떻게 되나요?" | 답에 "7일"이 들어간다 |
| refund-2 | "그냥 다 환불해 주세요" | 무조건 보장한다는 표현이 없다 |
| edge-1 | (빈 입력) | 되묻거나 거절한다 |

## 채점 방법 세 가지

Anthropic 문서는 "가장 빠르고, 믿을 만하고, 확장되는 방법을 고르라"고 하며 세 가지를 순서대로 제시한다.

| 방식 | 장점 | 한계 | 예 |
|---|---|---|---|
| 코드 검사 | 가장 빠르고 신뢰성이 높고 확장이 쉽다 | 미묘한 판단에는 뻣뻣하다 | 정확 일치, 키워드 포함 여부 |
| 사람 검수 | 가장 유연하고 품질이 높다 | 느리고 비싸다 | 전문가 점수 매기기 |
| LLM 채점(LLM-as-judge) | 빠르고 유연하며 복잡한 판단도 가능 | 신뢰성을 먼저 확인해야 한다 | 톤 1~5점, 정보 유출 여부 예/아니오 |

OpenAI 가이드의 구분도 같다. 지표 기반(정확 일치, ROUGE/BLEU, 함수 호출 정확도, 실행해서 확인하는 text2sql 등)은 빠르고 회귀 테스트에 맞지만 뉘앙스를 놓칠 수 있다. 사람 평가는 품질이 가장 높지만 느리고 평가자끼리 의견이 갈릴 수 있다. 모델 채점은 더 싸고 확장된다.

### 코드 검사

정답이 정해진 부분은 코드로 한다. 형식 지키기, 필수 문구, 금지 문구, 숫자 범위 같은 것들이다. [구조화된 출력](#/post/ai-structured-output)을 쓰는 기능이면 JSON이 스키마에 맞는지 자체가 가장 싼 검사가 된다. 아래는 직접 돌려서 확인한 최소 예시다.

```python
cases = [
    {"id": "refund-1", "output": "환불은 7일 이내 가능합니다.", "must": ["7일"], "banned": ["보장합니다"]},
    {"id": "refund-2", "output": "언제든 100% 환불을 보장합니다.", "must": ["7일"], "banned": ["보장합니다"]},
]
def check(c):
    return all(m in c["output"] for m in c["must"]) and not any(b in c["output"] for b in c["banned"])
res = {c["id"]: check(c) for c in cases}
print(res, sum(res.values()) / len(res))
# {'refund-1': True, 'refund-2': False} 0.5
```

### LLM 채점

사람이 읽어야 판단되는 항목(톤, 요약의 충실도 등)은 다른 모델에게 채점을 시킨다. Anthropic 문서의 팁은 세 가지다.

- 루브릭을 구체적으로 쓴다. 예: "답의 첫 문장에 'Acme Inc.'가 들어가야 하고, 없으면 자동으로 incorrect." 한 사용 사례에 루브릭이 여러 개 필요할 수도 있다.
- 출력을 못 박는다. 'correct'/'incorrect'만, 또는 1~5점. 순수한 서술형 평가는 빠르게 대량으로 보기 어렵다.
- 채점 모델이 먼저 추론하게 한다. 문서는 thinking을 켠 채점 모델을 쓰면 특히 복잡한 판단에서 평가 성능이 올라간다고 적는다.

같은 문서의 채점 프롬프트는 이런 모양이다.

```
Grade this answer based on the rubric:
<rubric>{rubric}</rubric>
<answer>{answer}</answer>
Output 'correct' or 'incorrect' in <result> tags.
```

또 Anthropic은 평가 대상 출력을 만든 모델과 다른 모델로 채점하는 것이 일반적으로 좋은 방법이라고 한다.

<details>
<summary>자세한 풀이: OpenAI 가이드의 LLM 채점 권장 사항</summary>

- 채점 형식은 쌍 비교, 단일 답변 채점, 정답 참조 채점이 있다.
- 가능한 가장 성능 좋은 모델을 채점에 쓰고, 점수 전에 근거를 쓰게 한다.
- 질문을 객관식으로 바꿀 수 있으면 바꾼다. 가이드는 LLM이 열린 글을 쓰는 것보다 선택지 사이를 구별하는 데 더 낫다고 보고, 쌍 비교·분류·기준별 채점 쪽을 권한다.
- 명확하고 자세한 루브릭을 쓴다.
- 채점 모델이 사람 라벨과 꾸준히 일치하는 것을 확인한 다음에 규모를 키운다.
- 가이드도 완벽한 전략은 없고 전문가 라벨은 비싸다고 인정한다.

</details>

## 사람 검수는 어디에 쓰나

사람 채점은 비싸서 전부를 맡길 수 없다. 대신 기준점 역할을 한다. OpenAI 가이드는 사람 주석을 정답(ground truth)으로 삼고, 자동 채점기를 거기에 맞춰 검증하고 보정하라고 한다. 이 보정 단계를 건너뛰는 것도 안티패턴으로 적는다. 사람 평가를 할 때의 권장 사항은 여러 차례 검토, 점수 단계마다 예시 제공, 숫자 점수와 함께 통과/실패 기준 두기, 여러 검토자의 합의 투표다.

정리하면 역할이 나뉜다.

```
사람 검수   → 소수 샘플로 "정답 기준"을 만들고 채점기를 보정
LLM 채점    → 보정된 기준으로 대량 채점
코드 검사   → 형식·금지어처럼 확정적인 것은 항상 먼저
```

## 회귀 테스트

회귀는 고쳤더니 예전에 되던 게 안 되는 것이다. 평가 세트가 그걸 잡는 장치가 된다. OpenAI Evals 문서는 모델을 올리거나 새 모델을 시험할 때 성능이 기대 수준을 유지하는지 확인하는 데 평가가 필수적이라고 하고, 지속 평가 단계에서 변경마다 평가를 돌리고 세트를 계속 키우라고 한다.

운영 방식은 단순하다.

| 시점 | 할 일 |
|---|---|
| 프롬프트·모델·검색 설정 변경 직전 | 현재 점수를 기준선으로 기록 |
| 변경 후 | 같은 세트로 재실행해 점수 비교 |
| 서비스에서 실패 사례 발견 | 그 입력을 평가 세트에 추가 |

OpenAI 가이드는 지표 기반 평가가 빠르고 회귀 테스트에 맞는다고 하니, 매번 도는 건 코드 검사 위주로 하고 LLM 채점·사람 검수는 큰 변경 때 얹는 구성이 자연스럽다.

## 구조가 복잡해지면

OpenAI 가이드는 비결정성이 구조의 각 층에 들어오므로 평가도 그 지점마다 둬야 한다고 한다.

| 구조 | 평가할 것 |
|---|---|
| 단일 턴 | 지시 따르기(충돌하는 사용자 프롬프트에 대한 저항 포함), 기능적 정확성 |
| 워크플로 | 각 단계를 따로 같은 기준으로 |
| 단일 에이전트 | 도구를 맞게 골랐는지, 인자를 정확히 넘겼는지 |
| 멀티 에이전트 | 넘겨줄 때를 알아채는지(핸드오프 정확도) |

[에이전트 루프](#/post/ai-agent-loop)가 도는 기능이라면 최종 답만이 아니라 중간의 도구 선택까지 채점 대상이 된다.

## 흔한 함정

두 가이드에 직접 적혀 있는 것만 모으면 이렇다.

- 채점 모델의 위치 편향: 쌍 비교에서 응답이 놓인 순서에 따라 선호가 달라질 수 있다. OpenAI 가이드는 쌍 비교나 통과/실패 형식이 신뢰성을 높인다고 한다.
- 채점 모델의 길이 편향: 판정 모델이 더 긴 응답을 선호하는 경향이 있어서 응답 길이를 통제하라고 한다.
- 채점기를 사람에게 안 맞춰 봄: 자동 점수가 높아도 사람 판단과 어긋날 수 있다.
- 학술 지표만 사용: perplexity나 BLEU 같은 일반 지표만으로는 우리 업무의 품질을 못 잰다.
- 실제 입력과 다른 데이터셋, 경계 사례 누락: 점수는 좋은데 서비스에서 터진다.
- 같은 모델이 만들고 같은 모델이 채점: Anthropic은 다른 모델로 채점하는 것을 권한다.
- 늦게 붙이는 평가: 출시 뒤에 붙이면 기준선이 없다.

## 흔한 오해

- 점수가 높으면 환각이 없다: 평가 세트가 다루는 범위 안에서만 말할 수 있다. 세트에 없는 입력은 그대로 남는다([환각](#/post/ai-hallucination)).
- 평가는 모델 회사가 하는 것이다: 벤치마크(MMLU 같은 것)는 모델끼리 비교하는 데 쓰이고, 우리 서비스에 맞는 건 직접 만든 과제별 평가다. OpenAI 가이드가 이 둘을 구분한다.
- 평가는 한 번 하면 된다: 변경마다, 그리고 실패 사례가 쌓일 때마다 세트를 키운다.
- 평가로 막을 수 있다: 평가는 측정이고 출력 차단은 아니다. 실행 중에 막는 건 [가드레일](#/post/ai-guardrails)의 일이다.
- 평가는 파인튜닝과 별개다: OpenAI 가이드는 평가가 일관되게 성능을 재게 되면 그 데이터를 개선에 쓰라고 하고, 예로 강화 파인튜닝을 든다([파인튜닝](#/post/ai-finetuning)).

<details>
<summary>참고: OpenAI Evals 플랫폼 공지</summary>

OpenAI 문서에는 Evals 플랫폼을 중단한다는 공지가 있다. 기존 사용자에게 2026년 10월 31일부터 읽기 전용이 되고 11월 30일에 종료 예정이며, 대안으로 Datasets를 안내한다. 도구는 바뀌어도 위의 구조(데이터 항목, 채점 기준, 실행 후 비교)는 그대로라서 개념 정리에는 영향이 없다. Evals 문서의 흐름은 데이터 스키마와 testing criteria를 정의하고, 정답 라벨이 든 JSONL을 올리고, 모델과 프롬프트 템플릿으로 run을 만들고, run의 통과/실패 수를 보는 순서다. 예시에 쓰인 채점기는 `string_check`(정확 일치 `eq`, 부분 일치 `like`)다.

</details>
