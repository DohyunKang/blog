推論最適化とは、すでに学習済みのモデルに対して質問を入力し回答を生成するプロセスをより高速かつ低コストにする技術の総称です。整理すると、KV キャッシュ、バッチ処理、ストリーミング、投機的デコーディングはすべて相互に関連した一つの体系でした。

## 定義から

推論 (inference) は学習が完了したモデルを使用する段階です。学習は一度大きく回して終了しますが、推論はユーザーが使用するたびに継続的に実行されます。サービス側にとっては、こちらが継続的に発生するコストとなります。（[詳細 → 事前学習](#/post/ml-pretraining)）

LLM は回答を一度に生成しません。トークンを一つ生成し、そのトークンを入力に追加して再度モデルを実行し、また一つ生成します。このプロセスを最終トークンが出力されるまで繰り返します。遅さやコストの大部分はこの反復構造から生じます。（[詳細 → トランスフォーマー](#/post/ml-transformer)）

## 推論の二つの段階

一つのリクエストの処理は二段階に分かれます。

| 段階 | 行うこと | 性質 |
|---|---|---|
| プリフィル (prefill) | 入力プロンプト全体を一度に処理 | トークンを並列で計算、計算量が大きい |
| デコーディング (decode) | トークンを一つずつ生成 | 一度に一つのトークン、毎回モデルの重みとキャッシュをメモリから読み込む必要がある |

プリフィルはユーザーが最初の文字を表示するまでの時間に、デコーディングはその後の文字が表示される速度に影響を与えます。最適化技術は基本的にどちらか一方、特にデコーディング側のボトルネックを解消することに焦点を当てています。デコーディングは計算よりも、メモリからデータを読み取る時間の方が長い傾向にあります。

## KV キャッシュ

トランスフォーマーの注意機構 (Attention) は、新しいトークンを生成する際に、前のすべてのトークンの key および value を使用します。これらの値は各トークンごとに、各層ごとに決定され、すでに生成されたトークンの値は変化しません。そのため、毎回再計算する必要はなく、保存して再利用します。これが KV キャッシュです。

- キャッシュがない場合、トークンを生成するたびに前面全体を再度計算します。
- キャッシュがある場合、新しいトークン 1 つ分のみを計算し、残りは読み込みます。
- ただし GPU メモリを占有します。対話が長くなるほど、同時リクエストが多くなるほど大きくなります。

（[詳細 → プロンプトキャッシング](#/post/ai-prompt-caching)）は、この KV ステートをリクエスト間でも再利用するサービス側の機能です。

<details>
<summary>KV キャッシュのサイズはいくらか（計算例）</summary>

一つのトークンが占めるサイズは以下の式です。

```text
2(key와 value) x 층 수 x 어텐션 헤드 수 x 헤드 차원 x 자료형 바이트
```

これは実際のモデルではなく、計算用に仮定した値です。32 層、32 ヘッド、ヘッド次元 128、fp16(2 バイト) の場合、一つのトークンで 524,288 バイト (0.5MB) です。4,096 トークンの対話一つが 2GB になります。同時に 10 つのリクエストを受けるとキャッシュだけで 20GB になります。（Python で計算して確認しました。）

最近のモデルの中には、key/value ヘッド数を減らしてこのサイズを削減する構造を採用しているものもあります。
</details>

## バッチ処理と連続バッチ処理

GPU は一つのリクエストしか処理しない場合、多くの部分がアイドル状態になっています。デコーディングは重みをメモリから読み取るコストが大きいため、複数のリクエストを束ねて一度に読み込むことで同時に計算すれば効率が向上します。これがバッチ処理 (batching) です。

問題は各リクエストの回答長が異なることです。固定されたグループで実行すると、先に完了したリクエストは席を空けたまま最も長いリクエストが終了するのを待ち、新しいリクエストはグループが終了するまで待機します。

Orca 論文 (OSDI 2022) はこの問題をイテレーション単位のスケジューリングで解決しました。モデルを一度回すたびにスケジューラーが介入し、完了したリクエストは即座に出力し、待機中の新しいリクエストを空きスペースに入れます。この方式は通常、連続バッチ処理 (continuous batching) と呼ばれます。論文ページにはこの用語はなく、同じ発想であると読みました。論文では GPT-3 175B で同様の遅延レベルの NVIDIA FasterTransformer に比べて処理量が 36.9 倍であるという報告を行っています。

```text
고정 배치:   [요청A ████████████]
             [요청B ████░░░░░░░░]  <- 끝났지만 자리가 빈 채로 대기
연속 배치:   [요청A ████████████]
             [요청B ████][요청C ████████]  <- 빈자리에 바로 새 요청
```

## PagedAttention

バッチサイズを大きくするには多くの KV キャッシュを確保する必要がありますが、リクエストごとにキャッシュがどれほど大きくなるかは事前に知ることはできません。最大長さを想定して事前に確保しておくと使用しない空間の無駄が生じ、サイズがバラバラであるためフラグメンテーションも発生します。

vLLM 論文 (SOSP 2023) の PagedAttention は、オペレーティングシステムの仮想メモリとページングの仕組みを取り入れています。キャッシュを小さなブロックに分割し、必要な時に一つずつ割り当て、ブロックがメモリ上で連続している必要がないようにします。同じプロンプトを使用するリクエスト同士はブロックを共有することも可能です。論文ではこれにより無駄をほぼ排除し、既存システム (FasterTransformer, Orca) と比較して同様の遅延で処理量が 2〜4 倍向上したと報告しています。長いシーケンス、大きなモデル、複雑なデコーディングほど差が大きいそうです。（[詳細 → vLLM](#/post/repo-vllm)）

## ストリーミング

ストリーミングは、総生成時間を短縮する技術ではなく、ユーザーが感じる応答時間を短縮する方法です。回答全体が終わるのを待たずに、トークンが生成される 대로 流し出します。デコーディング自体がトークン単位で行われるため、この構造は自然です。

- ユーザーが体感するのは、最初のトークンまでの時間（TTFT）です。プリフィックス処理が長ければ TTFT は増大します。
- その後のトークン間の間隔はデコーディング速度です。
- 総時間が同じでも、ストリーミングにするとはるかに速く感じられます。

## 投機的デコーディング

デコーディングが遅いのは、一度に一つのトークンしか生成できないためです。投機的デコーディング（speculative decoding）では、小さく高速なモデルが複数のトークンを事前に推測し、大きなモデルがその推測を並列で一度に検証します。正しい分については大きなモデルを一度実行した結果として一括で受け入れ、間違っている箇所からは大きなモデルの結果に置き換えてやり直します。

Leviathan などの論文では、T5-XXL で既存の実装と比較して約 2〜3 倍高速化されたことを報告しており、モデルの再学習や構造変更は不要で、出力分布も変わらないと述べています。つまり、品質を犠牲にする妥協ではなく、同じ答えをより早く得る方法です。

正確に当てさせるには、小さなモデルが大きなモデルと同様に予測する必要があります。簡単な部分（構造化された文書、繰り返されるコードなど）は推測がうまくいき、難しい部分は頻繁に外れます。

<details>
<summary>一度に何個のトークンが出るか（計算例）</summary>

推測が当たる確率がトークンごとに 0.8 で、一度に 4 つを推測すると仮定すると、大きなモデルを一度回った時に得られるトークン数の期待値は 1 + 0.8 + 0.8^2 + 0.8^3 + 0.8^4 = 約 3.36 個です。これは仮定した値であり、小さなモデルを実行する時間は別途かかるため、実際の速度向上はこの値より小さくなります。検証プロセスで正確にどのようなルールで受け入れ・拒絶するかは論文の数式を別途読む必要がありますが、この記事では解きませんでした。
</details>

## サービングで併用される概念

- 量子化：重みをより小さな数値形式で保存し、メモリ使用量と読み込み時間を削減します。代わりに精度が若干低下する可能性があります。（[詳細 → ローカルモデル](#/post/ml-local-models)）
- モデル並列化：一つの GPU に収まらないモデルを複数の GPU に分散して配置します。
- プレフィックスキャッシュ：同じ先頭部分を持つリクエスト同士で KV キャッシュを再利用します。

実際のサービス構成については別の記事で続きます。（[詳細 → AI サービングインフラ](#/post/infra-ai-serving)）

## よくある誤解

- ストリーミングしてもモデルがより速く計算するわけではありません。同じ速度で作られたものを先に表示するだけです。
- 投機的デコーディングは回答品質を損なう近道ではありません。論文によれば出力分布はそのままです。
- バッチサイズを大きくすれば必ずしも良いわけではありません。処理量は増えますが、一つのリクエストの待機時間は長くなる可能性があります。
- KV キャッシュはモデルサイズとは無関係にメモリを消費します。モデルをアップロードしても、長い会話でメモリ不足になる理由です。
