LLM 앱의 평가는 "이 답이 좋은가"를 느낌이 아니라 미리 정해 둔 문제와 채점 기준으로 숫자로 만들어, 고칠 때마다 같은 잣대로 비교하는 일이다.

## 왜 따로 평가가 필요한가

일반 코드는 입력이 같으면 출력이 같아서 테스트 한 줄로 끝난다. LLM 앱은 답이 매번 조금씩 다르고, 맞고 틀리고의 경계도 흐리다. 그래서 프롬프트를 한 줄 고치고 몇 번 돌려 보고 "괜찮네" 하고 넘어가기 쉽다.

문제는 고친 쪽은 좋아졌는데 다른 쪽이 조용히 나빠지는 경우다. 평가가 없으면 그걸 사용자가 먼저 알게 된다. Hamel Husain의 글은 평가를 소홀히 하고 프롬프트와 모델만 만지는 상황을 "두더지 잡기식 회귀"로 이어진다고 경고한다. 평가는 그 두더지를 눈에 보이게 하는 장치다.

## 먼저 성공 기준부터

Anthropic 문서는 평가를 만들기 전에 성공 기준을 정하라고 한다. 좋은 기준의 조건은 구체적이고, 측정 가능하고, 달성 가능하고, 앱의 목적에 맞는 것이다. "성능이 좋다" 대신 "감정 분류가 정확하다"처럼 써야 하고, 보통 한 가지 숫자로는 부족해서 여러 축을 같이 건다. 문서의 예시는 F1 0.85 이상, 무해한 출력 99.5%, 응답의 95%가 200ms 이내 같은 식이다.

이 단계에서 정해지는 게 많다. 기준이 없으면 어떤 질문을 모을지도, 어떤 채점기를 쓸지도 정할 수 없다.

## 골든셋

골든셋은 입력과 "정답 또는 통과 조건"을 짝지어 모아 둔 문제 묶음이다. 평가의 뼈대라서 여기서 품질이 거의 정해진다.

Anthropic 문서가 말하는 설계 원칙은 셋이다.

- 작업에 맞춰라. 실제 사용 분포를 닮게, 그리고 엉뚱한 입력, 너무 긴 입력, 애매한 입력, 해로운 입력 같은 경계 사례도 넣는다.
- 가능하면 자동으로 채점되게 만들어라.
- 질보다 양을 우선하라. 신호가 약간 약해도 자동 채점되는 문제가 많은 쪽이, 사람이 손으로 채점하는 적은 문제보다 낫다는 입장이다.

문제를 어디서 구하느냐에 대해 Hamel의 글은 LLM으로 합성 입력을 만들어 쓰되, 새 실패가 발견될 때마다 계속 추가하라고 한다. 실제 로그에서 실패한 사례를 골든셋으로 옮기는 게 가장 값어치가 클 것 같다.

## 채점 방법 세 가지

| 방법 | 어떻게 | 잘 맞는 곳 | 약한 곳 |
|---|---|---|---|
| 코드로 채점 | 문자열 일치, 포함 여부, 정규식, 임베딩 유사도, ROUGE 같은 지표 | 분류, 숫자·형식 확인 | 표현이 다양한 서술형 답 |
| LLM으로 채점 | 다른 LLM이 기준표대로 점수·합격 여부를 매김 | 어조, 요약 품질, 서술형 | 채점기 자체가 틀릴 수 있음 |
| 사람이 채점 | 사람이 직접 읽고 판단 | 기준을 세울 때, 채점기 검증 | 느리고 비쌈 |

Anthropic 문서의 예시 평가 다섯 개가 이 표에 그대로 걸린다. 트윗 감정 분류는 정규화한 문자열 일치, FAQ 일관성은 SBERT 임베딩의 코사인 유사도, 요약은 ROUGE-L, 고객 응대 어조는 LLM이 1~5점을 매기는 방식, 의료 챗봇의 개인 건강정보 탐지는 LLM이 yes/no로 답하는 방식이다.

순서는 싼 것부터가 맞다. Hamel도 단위 테스트 같은 빠르고 싼 검사를 먼저 두고, 모델 기반 평가는 그 위에 얹으라고 한다. 모델 평가부터 시작하면 더 비싸고 느린데 얻는 것도 적다는 이유다.

## 작게 돌려 보기

코드 채점만으로 골든셋과 회귀 확인이 어떻게 돌아가는지 직접 짜서 돌려 봤다. 모델 호출은 일부러 가짜 함수로 바꿨다. 평가 틀이 어떻게 생겼는지만 보려는 것이다.

```python
golden = [
    {"id": 1, "q": "환불 기한이 며칠이야?", "must": ["7일"], "must_not": ["30일"]},
    {"id": 2, "q": "배송비는 얼마야?", "must": ["3,000원"], "must_not": []},
    {"id": 3, "q": "오늘 날씨 어때?", "must": ["모르"], "must_not": []},
]

def check(case, out):
    return all(m in out for m in case["must"]) and not any(m in out for m in case["must_not"])

def run(app):
    res = {c["id"]: check(c, app(c["q"])) for c in golden}
    return res, sum(res.values()) / len(res)

r1, s1 = run(app_v1)   # 프롬프트 고치기 전
r2, s2 = run(app_v2)   # 고친 뒤
print("회귀:", [i for i in r1 if r1[i] and not r2[i]])
print("개선:", [i for i in r1 if not r1[i] and r2[i]])
```

가짜 앱 v1은 날씨 질문에 지어낸 답("맑습니다")을 하고, v2는 날씨는 모른다고 하지만 환불 기한을 30일로 틀린다. 실행 결과는 이랬다.

```
v1 {1: True, 2: True, 3: False} 0.67
v2 {1: False, 2: True, 3: True} 0.67
회귀: [1]
개선: [3]
```

두 버전의 점수가 똑같이 0.67이다. 평균 숫자만 보면 "변화 없음"인데, 사실은 하나 고치고 하나 망가뜨린 것이다. 그래서 점수 하나만 보지 않고 문제별 결과를 이전 버전과 나란히 놓고 회귀(전에 맞았는데 이제 틀린 것)를 따로 뽑는 게 중요하다고 느꼈다.

## LLM-as-judge

서술형 답은 문자열 일치로 채점이 안 되니 다른 LLM에게 채점을 맡기는 방식이 쓰인다. 이걸 LLM-as-judge라 부른다. Zheng 등의 논문(MT-Bench, Chatbot Arena)은 GPT-4 같은 강한 모델이 사람의 선호와 80% 넘게 일치했고, 이는 사람끼리의 일치율과 비슷하다고 보고한다. 같은 논문 초록은 한계로 위치 편향, 장황함 편향, 자기 강화 편향을 이름만 언급한다.

실무 지침은 문서마다 비슷하게 겹친다.

- 생성한 모델과 다른 모델로 채점한다(Anthropic).
- 채점기의 출력을 좁게 제한한다. 숫자만, 또는 yes/no만 내게 하고, 채점할 답은 `<response>` 같은 태그로 감싸 넣는다(Anthropic).
- 가능한 한 성능 좋은 모델을 채점기로 쓴다(Hamel).
- 채점기를 사람 판단과 대조해서 보정하고, 주기적으로 다시 확인한다. 채점기는 그 자체로 관리해야 하는 시스템이다(Hamel).

<details>
<summary>자세한 풀이: 채점 프롬프트의 모양</summary>

Anthropic 문서의 예시를 따라 쓰면 대략 이런 틀이 된다.

```
아래 <response>가 다음 기준을 만족하는지 판단해라.
기준: 환불 기한을 정확히 말하고, 정책에 없는 약속을 하지 않는다.
<response>
{{답변}}
</response>
yes 또는 no만 출력해라.
```

yes/no처럼 이진으로 시작하는 게 관리하기 쉽다. Hamel도 처음엔 단순한 좋음/나쁨 라벨로 시작하고 세밀한 점수는 다루기 어렵다고 한다. 5점 척도를 쓰면 3점과 4점의 경계가 흔들려 채점기끼리, 사람끼리도 갈린다.

채점기가 맞는지는 사람이 라벨 붙인 소수의 사례에 채점기를 돌려 비교한다. Hamel은 불균형한 데이터에서 단순 일치율이나 정확도는 소수 클래스의 실패를 가리니 정밀도와 재현율을 보라고 한다. 예를 들어 나쁜 답이 5%뿐이면 전부 "좋음"이라고 해도 95% 맞는다.

## 평가를 돌리는 때

평가는 한 번 만드는 게 아니라 바꿀 때마다 돌리는 것이다. 프롬프트, 모델 버전, 검색 설정([RAG를 직접 만들 때](#/post/app-rag-build)의 청크 크기나 top-k 같은 것), 도구 정의가 바뀌면 돌린다. 이 반복이 회귀 테스트다. 단위 테스트처럼 코드 변경마다 자동으로 돌릴 수 있는 부분(형식 검사, 금지어 검사)과, 시간이 걸려서 배포 전에만 돌리는 부분(LLM 채점, 사람 확인)을 나누는 게 현실적이다.

모델 기반 평가는 호출마다 돈이 나가니, 골든셋이 커질수록 평가 비용도 앱 원가의 한 항목이 된다. 이 부분은 [AI 서비스 원가](#/post/app-cost)에서 이어서 본다.

## 무엇을 재나

| 보고 싶은 것 | 재는 방법의 예 |
|---|---|
| 정답이 정해진 작업(분류, 추출) | 정확도, F1, 정확 일치 |
| 형식 | JSON 파싱 성공률, 스키마 통과율([구조화 출력](#/post/ai-structured-output) 참고) |
| 지어내기 | 근거 문서에 없는 주장 비율([환각](#/post/ai-hallucination) 참고) |
| 안전 | 거절해야 할 입력의 거절률, 유출 시도 차단률([가드레일](#/post/app-guardrails) 참고) |
| 응답 속도 | 지연 시간 분포 |
| 비용 | 요청당 토큰, 요청당 금액 |

한 가지 숫자로 합치지 않고 축별로 따로 본다. 위 실험처럼 평균에 가려지는 게 있기 때문이다.

## 흔한 함정과 오해

- 느낌으로만 확인하는 것. Hamel이 첫 번째 함정으로 꼽는 게 이것이다.
- 우리 제품의 실패 양상과 상관없는 범용 평가 도구와 점수에 기대는 것(같은 글).
- 자동 채점이 사람 검토를 대체한다는 믿음. Hamel은 사람을 없앨 수 있다는 도구 주장은 회의적으로 보라고 하고, 데이터를 계속 읽으라고 한다. 더 배울 게 없어질 때까지 읽는 게 멈추는 기준이라고 한다.
- 합격률 100%가 목표라는 믿음. 허용 실패율은 제품이 정할 몫이라는 입장이다.
- 골든셋에 쉬운 문제만 있는 것. 점수는 높은데 실제 사용에서는 계속 틀린다.
- 평가 문제를 프롬프트 예시에 그대로 넣는 것. 이렇게 하면 평가가 시험 유출처럼 돼서 점수가 의미를 잃는다.
- 평가를 지표 숫자 올리기 게임으로 만드는 것. 숫자가 오르는데 사용자 불만이 그대로면 골든셋이 현실을 못 닮은 것이다.

[프롬프트 인젝션](#/post/sec-prompt-injection) 같은 공격 사례는 평가 문제에 따로 모아 두면 방어가 무너졌는지 바로 알 수 있다.
