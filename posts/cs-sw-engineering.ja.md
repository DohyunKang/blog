ソフトウェア工学は、コードをどう書くかという技術よりも、「何を、どのような順序で作成し、どのように検証し、どのように修正していくか」を扱う分野です。ここでは大きな枠組みのみ整理しました。

## ソフトウェア工学とは何か

プログラムが小さければ、一人で頭の中で管理することも可能です。しかし、人員が増えたり期間が長くなったりすると問題の性質も変わります。何をすべきかについて互いの理解が異なり、修正中に別の箇所が壊れたり、納期が遅れたりします。ソフトウェア工学は、こうした問題を減らすために考案された手法の集まりです。

大きく 5 つの要素に分けられます。全体の進行方式（開発方法論）、作るものを定めること（要件定義）、それを図にすること（設計・UML）、正しく動作しているか確認すること（テスト）、変更されるコードを管理すること（バージョン管理）。順序も大まかにこれです。

| 段階 | 行うこと | 成果物 |
|---|---|---|
| 要件定義 | 何を作るかを聞き取り整理 | 要件仕様の書 |
| 設計 | 構造・画面・データを決定 | UML、設計書 |
| 実装 | コードの作成 | ソースコード |
| テスト | 要件通りに動作するか確認 | テスト結果 |
| 保守 | 修正と追加 | 新しいバージョン |

## 開発方法論：ウォーターフォールとアジャイル

方法論とは、上記の工程をどのように進めるかという違いです。

ウォーターフォールモデルは、工程を上から下へ一度ずつ順番に進めます。要件定義を全て終えてから設計、設計を全て終えてから実装。前の工程が終わってから次の工程に移るため、文書や計画が明確な代わりに、途中で要件が変わると戻すのが困難です。成果物が最後になって初めて見えることも弱点です。

アジャイルは逆に、短く作って見せて修正する側面があります。アジャイル宣言の 12 の原則を読み比べると方向性がはっきりします。開発後半で要件が変更されても歓迎し、数週間の周期ごとに動作するソフトウェアを頻繁に提供し、関係者と開発者が毎日一緒に働き、動作するソフトウェアを進捗の基準とします。定期的に振り返って手法を修正することも含まれます。

| | ウォーターフォール | アジャイル |
|---|---|---|
| 進行 | 工程を一度ずつ順番に | 短い周期を繰り返す |
| 要件変更 | 難しく高価 | 受け入れることが前提 |
| 成果物の確認 | ほぼ最後 | 各周期ごと |
| 文書 | 多い | 必要な分だけ |
| 適している場所 | 要件が固定されている場合 | 要件が頻繁に変化する場合 |

アジャイルを実際に運用する枠組みの中で最も一般的なものがスクラムです。[スクラムガイド](https://scrumguides.org/scrum-guide.html) を基準に整理すると以下のようになります。

- スプリント：1 ヶ月未満の固定期間。すべてのイベントはこの中に含まれます。
- イベント：スプリント計画、デイリースクラム（15 分）、スプリントレビュー、リトロスペクティブ。
- ロール：プロダクトオーナー（バックログ管理、1 名）、スクラムマスター（障害の除去）、開発者。
- 成果物：プロダクトバックログ、スプリントバックログ、インクリメント（利用可能な成果物）。

ウォーターフォールが悪くアジャイルが良いといった単純な捉え方では現実とズレが生じます。要件が固定されており戻すコストが高い場合（例：ハードウェアに組み込むファームウェア）は計画中心のアプローチが適していることもあります。残りのモデルにはスパイラル（リスク分析を繰り返す）、プロトタイプなどがありますが、名前と特徴だけ覚えておけば十分です。

## 要件定義

要件とは、システムが果たすべき機能と満たすべき条件のことです。2 つの種類に分けられます。

- 機能要件：「会員はメールアドレスでログインできること」のようにシステムが行う動作。
- 非機能要件：「ログイン応答は 1 秒以内」「個人情報は暗号化」のような品質や制約。

良い要件とは、一文に一つの意味を持ち、検証可能なものです。「速く」は検証できず、「1 秒以内」であれば検証可能です。要件定義段階でのミスは後ほど修正するコストが膨大になるため、この段階で互いに同じ理解をしているかを確認することが最も重要だと言われています。

<details>
<summary>要件を引き出す方法と検証</summary>

引き出しにはインタビュー、アンケート、現在の業務観察、プロトタイプデモなどの手法を用います。受け取った要件を分析して矛盾するものをフィルタリングし、仕様に記述し、最後にステークホルダーがレビューします。各要件に番号を付ければ後で設計やテストと連携して追跡できます（トレーサビリティ表）。
</details>

## UML

UML は設計を図示するための標準的な記法です。種類は多いですがよく使われるのは数種類です。

| ダイアグラム | 示す内容 | 使用時期 |
|---|---|---|
| ユースケース | ユーザーがシステムに対して行う動作 | 要件整理 |
| クラス | クラスと関係性 | 構造設計 |
| シーケンス | オブジェクト間のメッセージ順序 | 機能のフロー |
| ステート | 状態が変わる条件 | 注文・決済など状態を持つもの |
| アクティビティ | 作業の流れ | 業務手順 |

構造を示す図（クラスなど）と動作を示す図（シーケンス、ステートなど）に分けて覚えると混乱しにくいです。すべてを描く必要はなく、言葉で説明が難しい部分だけ描くのが良いです。

## テスト

テストとは、作成したものが要件通りに動作するか、どこで失敗するかを見つけることです。範囲は狭い順に「単体（関数・クラス 1 つ）」「統合（モジュールを束ねて）」「システム（全体）」「受入（ユーザー・顧客が受け入れられるか）」の順に広がります。

自動化テストでは「テストピラミッド」で比率を説明します。[Martin Fowler の記事](https://martinfowler.com/articles/practical-test-pyramid.html) を基準にすると、単体テストは速いので最も多く、データベースなど外部と接続する統合テストは適度に、UI 全体を回るテストは非常に少なくするのが理想です。これを逆転させると、遅く維持コストの高い「アイスクリームコーン」になってしまいます。同じことを複数の層で重複して確認せず、できるだけ低い層に集約すべきです。

テストはブラックボックス（内部コードを見ずに入出力のみ）とホワイトボックス（コード構造を見て経路を確認）の 2 つに分けられます。ブラックボックスでは境界値分析が代表的です。値が 0, 1, 最大などの境界でエラーが発生しやすいためです。

単体テストはこのように見えます。Python の `unittest` で記述し、実際に実行して 4 つすべてが通過することを確認しました。

```python
import unittest

def discount(price, is_member):
    if price < 0:
        raise ValueError("price")
    return int(price * 0.9) if is_member else price

class T(unittest.TestCase):
    def test_member(self):
        self.assertEqual(discount(10000, True), 9000)
    def test_guest(self):
        self.assertEqual(discount(10000, False), 10000)
    def test_zero(self):          # 경계값
        self.assertEqual(discount(0, True), 0)
    def test_negative(self):      # 예외 경우
        with self.assertRaises(ValueError):
            discount(-1, True)

unittest.main()
```

<details>
<summary>テスト用語の数々</summary>

- レグレッションテスト：修正後、以前正常だったものが壊れていないか再確認する。
- ステブ・ダミー：テストで真の依存対象（DB, 外部 API）を代替する偽物。
- 検証 (Verification) は「正しく作ったか」（仕様に合っているか）、確認 (Validation) は「正しいものを作ったか」（ユーザー要件に合っているか）。
</details>

## バージョン管理

コードは常に変化しており、誰がいつ何を改変したかを把握できていないと問題が発生しても元に戻せません。バージョン管理 (SCM) はソースやドキュメントなどの産出物の変更を記録・統制することです。バージョン管理（戻す・履歴）、変更統制（誰が承認したか）、ビルド・デプロイ管理が含まれます。現在は Git が事実上の標準です。

## よくある誤解

- アジャイルは文書や計画なしで行うのか？原則にも良い設計と技術的卓越性が含まれています。文書を減らすのではなく、消すわけではありません。
- テストは開発が終わってから行うのか？要件定義段階ですでに「どのように確認するか」を一緒に記しておくのが望ましいです。
- UML はすべて描く必要があるのか？必要な分だけ描きます。
