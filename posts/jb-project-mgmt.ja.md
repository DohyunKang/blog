プロジェクト管理分野は範囲が広いように見えますが、試験で問われるのは計算問題のいくつかの種類です。スケジュールは CPM と PERT、コストは COCOMO、人間はブックスの法則、運用は ITIL 用語です。試験の日程・受験料は公式サイトで確認し、ここでは概念と解き方を整理します。

## まず全体像

| 質問 | ツール | 解き方 |
|---|---|---|
| スケジュールは何日かかるか | CPM | 先行関係をグラフにして最も長い経路（クリティカルパス）を見つける |
| 活動時間を知らない | PERT | 楽観値・最頻値・悲観値の 3 つから期待値を計算する |
| コスト（人件費）はいくらか | COCOMO | コード規模（KLOC）を式に代入する |
| 人員を増やせば早くなるか | ブックスの法則 | 通信経路の数が増えるため |
| サービスをどう運用するか | ITIL | インシデント・問題・変更などの管理活動 |

規模を測る入力値（要件）が揺れると、これらの計算も一緒に揺れます。前段階は [要件確認と分析](#/post/jb-requirements) で続きます。

## スケジュール：CPM

CPM（クリティカルパス法）は活動間の先行関係をグラフに置き、最も長い経路をクリティカルパスとします。クリティカルパス上の活動は余裕時間（float, slack）が 0 なので、1 日でも遅れると全体のスケジュールも遅れます。クリティカルパス外の活動には余裕があります。

計算は 2 回行います。

1. 前へ後へ（前進）：各活動の最も早い開始（ES）と終了（EF = ES + 期間）を求めます。先行が複数ある場合は、最も遅く終了するものに合わせて設定します。
2. 後へ前へ（後退）：全体の終了時点から遡り、最も遅い終了（LF）と開始（LS = LF - 期間）を求めます。後続が複数ある場合は、最も早い開始に合わせて設定します。
3. 余裕 = LS - ES。0 ならクリティカル活動です。

例として活動 6 つを取り、実際に計算しました。括弧内は期間（日）、矢印の先頭は先行活動です。

| 活動 | 期間 | 先行 |
|---|---|---|
| A | 3 | - |
| B | 4 | A |
| C | 2 | A |
| D | 5 | B, C |
| E | 3 | C |
| F | 2 | D, E |

```python
tasks = {"A": (3, []), "B": (4, ["A"]), "C": (2, ["A"]),
         "D": (5, ["B", "C"]), "E": (3, ["C"]), "F": (2, ["D", "E"])}
es, ef = {}, {}
for t in tasks:                       # 전진
    d, pre = tasks[t]
    es[t] = max([ef[x] for x in pre], default=0)
    ef[t] = es[t] + d
end = max(ef.values())
ls, lf = {}, {}
for t in reversed(list(tasks)):       # 후진
    succ = [s for s in tasks if t in tasks[s][1]]
    lf[t] = min([ls[s] for s in succ], default=end)
    ls[t] = lf[t] - tasks[t][0]
for t in tasks:
    print(t, es[t], ef[t], ls[t], lf[t], "여유", ls[t] - es[t])
print("전체", end)
# A 0 3 0 3 여유 0
# B 3 7 3 7 여유 0
# C 3 5 5 7 여유 2
# D 7 12 7 12 여유 0
# E 5 8 9 12 여유 4
# F 12 14 12 14 여유 0
# 전체 14
```

クリティカルパスは A-B-D-F で、全体の期間は 14 日です。C は 2 日、E は 4 日遅れても全体には影響しません。問題は通常、「クリティカルパスの長さ」または「特定活動の余裕」を問います。

<details>
<summary>解く際によく犯すミス</summary>

- 前進計算で先行が 2 つ以上ある場合は、合計ではなく最大の EF を使います。前述の D の開始が 7 なのは、B(7) と C(5) のうち大きい方だからです。
- 後退計算で後続が 2 つ以上ある場合は、最小の LS を使います。前述の C の LF が 7 なのは、D(LS 7) と E(LS 9) のうち小さい方だからです。
- クリティカルパスが複数あることもあります。1 つだけ見つけて終わらず、余裕が 0 の活動すべてを確認してください。

</details>

## スケジュール：PERT

PERT は活動時間を確信できない場合に 3 つの値を受け取ります。楽観値 o、最も可能性が高い値 m、悲観値 p です。期待時間は te = (o + 4m + p) / 6 で、標準偏差は (p - o) / 6 です。経路全体の期待時間は活動の期待時間の合計で、経路の標準偏差は各活動の標準偏差の二乗和に平方根を掛けます。

```python
o, m, p = 2, 4, 12
print((o + 4*m + p) / 6)   # 5.0
print((p - o) / 6)         # 1.666...
```

楽観 2、最頻 4、悲観 12 の場合、期待値は 5 日です。通常値より大きくなるのは、悲観側の裾が長いからです。CPM は期間を 1 つ確定させて扱い、PERT は期間を確率として扱うと覚えると区別がつきます。

## コスト：COCOMO

COCOMO はコード規模から努力（人月）を推定するモデルです。基本（Basic）モデルの式は以下の通りです。

- 努力 E = a × (KLOC)^b （人月）
- 開発期間 D = 2.5 × E^c （ヶ月）
- 平均人数 P = E / D

係数はプロジェクトの種類によって異なります。

| 種類 | a | b | c |
|---|---|---|---|
| 組織型 (Organic) | 2.4 | 1.05 | 0.38 |
| 半分離型 (Semi-detached) | 3.0 | 1.12 | 0.35 |
| 埋め込み型 (Embedded) | 3.6 | 1.20 | 0.32 |

同じ 10 KLOC でも種類が変わると結果がどう変わるか計算しました。

```python
for name, a, b, c in (("조직형", 2.4, 1.05, 0.38),
                      ("반분리형", 3.0, 1.12, 0.35),
                      ("내장형", 3.6, 1.20, 0.32)):
    e = a * 10**b
    d = 2.5 * e**c
    print(name, round(e, 1), round(d, 1), round(e / d, 1))
# 조직형 26.9 8.7 3.1
# 반분리형 39.5 9.1 4.4
# 내장형 57.1 9.1 6.3
```

努力は組織型で 26.9 人月から、埋め込み型で 57.1 人月まで 2 倍近く開きがありますが、期間は 9 ヶ月前後と似ています。期間式の指数 c が小さいため、努力が増えようと期間はゆっくりしか増えないからです。試験は通常、「10 KLOC の組織型の場合は努力が」のような形式なので、係数を覚えるのが優先です。計算機が使えない環境では b の指数を概算で変えずに、問題で与えた値そのままを使います。

<details>
<summary>基本・中間・詳細モデルの区別</summary>

基本モデルは、規模とタイプのみを用いた最も単純な形式である。中間（Intermediate）モデルでは、これにコスト要因（製品・人材・環境など複数の項目）を反映した努力調整係数（EAF）を掛ける。a·b·c の使い方は同じである。詳細モデルは段階ごとに細分化すると知られているが、試験では基本モデルの式と係数が中心となる。

</details>

似た概念として、コード行数ではなく機能の数で測る方法（機能点）もある。規模を何で測るかによって変わるだけで、「規模 → 努力」という流れは同じである。

## 人：ブックスの法則

遅延したソフトウェアプロジェクトに人員を追加投入しても、かえって遅れるというのがブックスの法則である。理由は 3 つに説明できる。仕事が完全に独立した部品に分けられないこと、新しく来た人はまず学習する必要がありその間既存チームメンバーの時間を奪うこと、人が増えるとコミュニケーション経路が急速に増加することである。n 人間のコミュニケーション経路は n(n-1)/2 である。

```python
print(10*9//2, 50*49//2)  # 45 1225
```

10 人では 45 個、50 人では 1,225 個となる。問題としては「n 人のときのコミュニケーション経路数」が定番である。

## サービス運用：ITIL

ITIL は IT サービス管理のベストプラクティスの集まりである。3 版はプロセスと機能をサービスライフサイクルを中心に 5 つの冊子にまとめ、4 版（2019）ではアジャイル・DevOps・リーンに合わせて IT だけでなくサービス管理全般へと広がった。試験では個別の管理活動の意味を区別する問題が出る。

| 用語 | 一言 |
|---|---|
| インシデント管理 | サービス障害や停止から速やかに正常状態に戻すこと |
| プロblem 管理 | インシデントの根本原因を見つけ、再発を防ぐこと |
| 変更（Change）管理 | 変更を統制してサービスに与える影響を管理すること。4 版の名前は change enablement |

インシデントは「まず復旧」、問題は「なぜ起きたか」で区別して覚える。変更管理は [バージョン管理とビルド・デプロイ](#/post/jb-build-release) のバージョン変更統制と名前が似ていて混乱しやすいが、ITIL 側はサービス運用の視点である。

## よくある勘違い

- CPM で最も長い経路がクリティカルパスである。最も短い経路ではない。最も長い経路が全体の期間を決定するためである。
- COCOMO の努力と期間は比例しない。努力を 2 倍にしても期間は指数 c のみ増える。
- 人員を増やせば工期が短くなるという計算は、仕事を独立した部品に分けられる場合에만正しい。ソフトウェアは概ねそうではない。
- インシデントと問題は異なる。インシデントは復旧、問題は原因除去である。

## おわりに

計算問題の 3 つの種類（CPM の前進・後退、PERT の期待値、COCOMO の式）は一度ずつ手計算で解いておけば試験場で式が覚えられる。残りは表で暗記する。前後の単元は [ソフトウェアテスト](#/post/jb-testing)、[新技術と IT 用語](#/post/jb-it-trend) と合わせて見るとつながる。
