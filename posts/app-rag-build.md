[RAG](#/post/ai-rag)는 개념만 읽으면 간단한데, 직접 만들어 보면 손이 가는 곳이 정해져 있다. 문서를 어떻게 자르는지, 뭘로 벡터를 만드는지, 몇 개를 찾아 붙이는지, 잘 되는지 어떻게 아는지. 이 글은 그 다섯 군데를 순서대로 따라가면서 외부 서비스 없이 돌아가는 최소 코드를 만든 기록이다. 코드는 직접 실행해서 확인했다.

## 만들 것

사내 FAQ 같은 짧은 문서 세 개(환불, 배송, 계정)를 두고, 질문이 오면 관련 조각을 찾아 프롬프트로 만드는 데까지 한다. 모델 호출은 일부러 뺐다. 호출 부분은 어떤 API를 쓰든 "만든 프롬프트를 보낸다" 한 줄이라서, 공부할 거리는 그 앞에 다 있다.

```
문서 → 청킹 → 임베딩 → 저장(벡터 DB 자리) → [질문] → 검색 → 프롬프트 → (모델) → 답
```

| 단계 | 이 글의 코드 | 실제로 쓸 때 |
|---|---|---|
| 청킹 | 문단 단위로 모으다가 글자 수 넘으면 끊기 | 토큰 기준, 제목 단위 등 |
| 임베딩 | 글자 2-gram 해시 (장난감) | 임베딩 모델 API나 로컬 모델 |
| 벡터 DB | numpy 행렬 하나 | 문서가 많아지면 벡터 DB |
| 검색 | 코사인 유사도 상위 k개 | 하이브리드 검색, 재순위 |
| 프롬프트 | 자료 + 질문 붙이기 | 같음 |

임베딩이 장난감인 이유는 하나다. 진짜 임베딩 모델은 설치나 키가 필요해서 이 글의 코드를 그대로 돌릴 수 없게 된다. 대신 함수 하나(`embed`)만 바꾸면 나머지는 그대로 쓰도록 짰다. 장난감 임베딩은 글자가 겹치는 정도만 보기 때문에 의미 검색이 아니다. [임베딩](#/post/ai-embedding)이 진짜로 해 주는 일(뜻이 비슷하면 가깝게)은 이 코드에선 안 일어난다.

## 전체 코드

```python
import re, zlib
import numpy as np

DOCS = {
    "refund.md": "환불 규정\n\n구매 후 7일 이내에는 사유와 관계없이 전액 환불된다. 7일이 지나면 환불되지 않는다.\n\n디지털 상품은 다운로드를 시작하면 환불이 어렵다.",
    "shipping.md": "배송 안내\n\n주문 후 평일 기준 2~3일 안에 도착한다. 제주와 도서 지역은 하루가 더 걸린다.\n\n배송 조회는 마이페이지의 주문 내역에서 한다.",
    "account.md": "계정 안내\n\n비밀번호를 잊으면 로그인 화면의 비밀번호 찾기에서 이메일로 재설정 링크를 받는다.\n\n탈퇴하면 주문 내역은 5년간 보관된다.",
}

def chunk(text, size=70, overlap=15):
    paras = [p.strip() for p in text.split("\n\n") if p.strip()]
    out, buf = [], ""
    for p in paras:
        if buf and len(buf) + len(p) > size:
            out.append(buf)
            buf = buf[-overlap:] + "\n" + p
        else:
            buf = (buf + "\n" + p) if buf else p
    if buf:
        out.append(buf)
    return out

DIM = 512
def embed(text):
    # 장난감 임베딩: 글자 2-gram을 해시해서 벡터에 더한다.
    v = np.zeros(DIM)
    t = re.sub(r"\s+", "", text)
    for i in range(len(t) - 1):
        v[zlib.crc32(t[i:i+2].encode()) % DIM] += 1
    n = np.linalg.norm(v)
    return v / n if n else v

index = []  # (출처, 청크, 벡터)
for name, text in DOCS.items():
    for c in chunk(text):
        index.append((name, c, embed(c)))
M = np.stack([v for _, _, v in index])

def search(q, k=2):
    scores = M @ embed(q)
    top = np.argsort(-scores)[:k]
    return [(index[i][0], index[i][1], float(scores[i])) for i in top]

def build_prompt(q, hits):
    ctx = "\n\n".join(f"[자료 {i+1}: {n}] {c}" for i, (n, c, _) in enumerate(hits))
    return f"다음 자료만 근거로 답하라. 자료에 없으면 모른다고 답하라.\n\n{ctx}\n\n질문: {q}"

EVAL = [
    ("환불은 며칠 안에 해야 해?", "refund.md"),
    ("배송은 얼마나 걸려?", "shipping.md"),
    ("비밀번호 까먹었어", "account.md"),
    ("제주도는 배송이 더 느려?", "shipping.md"),
]

if __name__ == "__main__":
    print(len(index), "chunks")
    hit = 0
    for q, gold in EVAL:
        r = search(q, 1)
        ok = gold in [n for n, _, _ in r]
        hit += ok
        print(ok, q, "->", [n for n, _, _ in r])
    print("hit@1 =", hit / len(EVAL))
    print(build_prompt(EVAL[0][0], search(EVAL[0][0], 2)))
```

실행하면 청크 6개가 만들어지고, 평가 질문 4개가 전부 맞는 문서를 첫 번째로 찾는다(hit@1 = 1.0). 마지막에는 모델에 보낼 프롬프트가 출력된다.

## 1. 청킹

청킹은 문서를 검색의 단위로 쪼개는 일이다. 코드에서는 빈 줄로 문단을 나누고, 문단을 모으다가 `size`를 넘으면 한 청크를 끊는다. 다음 청크는 앞 청크의 마지막 `overlap`글자를 가져와 시작한다.

돌려 보면 이 단순한 겹침의 문제가 바로 보인다. 청크 목록 중 하나가 `이 지나면 환불되지 않는다.`로 시작한다. 글자 수로 겹치니까 단어 한가운데서 잘린 것이다. 앞의 문장이 "7일"이었다는 걸 모르면 이 조각만으로는 뜻이 안 통한다. 겹침을 글자 수 대신 문장 단위로 하면 이게 없어진다. Anthropic의 Contextual Retrieval 글도 청크 크기·경계·겹침이 검색 성능에 영향을 준다고 적고, 청크는 보통 몇백 토큰을 넘지 않는다고 한다.

그리고 적정 크기가 몇인지는 데이터마다 다르다. 이 글의 70글자는 문서가 너무 짧아서 일부러 작게 잡은 값이다.

## 2. 임베딩

`embed`는 글을 길이 512의 숫자 목록으로 바꾼다. 장난감 방식은 글자 두 개씩 끊어서 해시한 칸에 1을 더하고, 마지막에 길이를 1로 맞춘다. 길이를 1로 맞춰 두면 두 벡터의 내적이 곧 코사인 유사도가 되어서 검색이 행렬 곱 한 번으로 끝난다.

해시에 파이썬 내장 `hash()`를 쓰면 실행할 때마다 값이 달라진다(문자열 해시가 프로세스마다 무작위로 섞이기 때문이다). 그래서 `zlib.crc32`를 썼다. 처음에 `hash()`로 짰다가 평가 수치가 흔들릴 수 있다는 걸 알고 바꿨다.

진짜 모델로 바꿀 때 주의할 점이 둘 있다. 문서와 질문은 같은 모델로 임베딩해야 한다. 그리고 임베딩 차원과 모델 이름을 저장해 두지 않으면, 나중에 모델을 바꿨을 때 옛 벡터와 새 벡터가 섞인다.

## 3. 저장

`index`가 청크 목록, `M`이 벡터를 쌓은 행렬이다. 청크가 수천 개까지는 이걸로 충분하다. 행렬 곱은 빠르고 코드가 이해하기 쉽다. 수십만 개를 넘거나, 서버가 여러 대이거나, 문서가 자주 바뀌면 그때 벡터 DB를 쓴다. 벡터 DB가 해 주는 일은 크게 세 가지다. 근사 최근접 탐색으로 전부 비교하지 않고 찾기, 디스크에 저장하기, 메타데이터로 거르기. 지금 코드는 셋 다 없다. [자세히 → 벡터 DB](#/post/db-vector)

저장할 때 출처(파일 이름)를 같이 넣어 둔 건 프롬프트에 출처를 달기 위해서다. 출처가 있어야 모델이 답과 함께 "어느 자료에서 봤는지"를 말할 수 있고, 사람이 확인하기도 쉽다.

## 4. 검색

`search`는 질문을 임베딩해서 모든 청크와 내적을 구하고 점수가 높은 k개를 돌려준다. k를 얼마로 할지는 정답이 없다. Anthropic 글에서는 모델에 5개, 10개, 20개를 넘겨 비교했더니 20개가 가장 좋았다고 한다. 많이 넘길수록 정답이 들어 있을 확률이 오르지만, 너무 많으면 모델이 산만해질 수 있어서 직접 실험해 보라고 권한다.

의미 검색만으로는 오류 코드 같은 정확한 단어를 놓칠 수 있다는 점도 같은 글에 나온다. 그래서 단어 일치 기반의 BM25를 같이 쓰고 순위를 합치는 하이브리드가 자주 붙는다. 이 글의 코드에 넣지는 않았다. 문서가 작아서 차이를 확인할 수 없기 때문이다.

## 5. 프롬프트

`build_prompt`는 자료를 번호와 출처를 달아 나열하고 질문을 마지막에 둔다. 지시문은 "자료만 근거로 답하라, 없으면 모른다고 답하라" 두 가지다. 이 지시가 없으면 모델은 자료에 없는 부분을 자기 지식으로 채운다([환각](#/post/ai-hallucination)). 프롬프트를 짜는 요령은 [프롬프트](#/post/ai-prompt)에 따로 있다.

실제로 모델을 붙일 때는 이 문자열을 API의 사용자 메시지로 보내면 된다. 자료는 [컨텍스트 윈도우](#/post/ai-context-window) 안에 들어가야 하니 k와 청크 크기를 곱한 길이가 한도 안인지 따져 둔다.

## 평가

만들고 나서 가장 빨리 잊는 단계다. 코드에 `EVAL`로 넣어 둔 질문과 정답 문서 쌍이 그 시작이다. 검색이 정답 문서를 상위 k 안에 가져왔는지(hit@k)만 재도 많은 걸 알 수 있다. 답이 틀렸을 때 원인이 검색인지 모델인지 가르는 첫 기준이 되기 때문이다.

- 정답 청크가 검색 결과에 없다 → 검색(청킹, 임베딩, k) 문제
- 정답 청크가 있는데 답이 틀렸다 → 프롬프트나 모델 문제

이 글의 hit@1 = 1.0은 믿으면 안 된다. 질문 4개에 문서 3개짜리 아주 쉬운 시험이고, 질문과 문서가 같은 단어를 쓰고 있어서 글자 겹침만으로도 맞는다. "환불"을 "돈 돌려받기"로 바꿔 물으면 이 장난감 임베딩은 바로 무너질 것 같은데, 그건 이 글에서 돌려 보지 않았다. 평가 질문은 실제 사용자가 쓸 법한 말투와, 문서에 없는 표현으로 만들어야 의미가 있다.

<summary>자세한 풀이: 답까지 재는 지표들</summary>

hit@k는 검색만 잰다. 답의 품질까지 재려는 도구로 Ragas가 있다. 문서 목록 페이지에서 확인한 이름은 검색 쪽 Context Precision, Context Recall, 생성 쪽 Faithfulness, Response Relevancy다. 이름만 보면 검색이 필요한 청크를 가져왔는지, 답이 가져온 자료에 충실한지, 질문에 맞는 답인지를 나눠서 재는 구성으로 보인다.

직접 하려면 질문-정답 쌍 20~30개를 손으로 만들고, 바꿀 때마다(청크 크기, k, 임베딩 모델) hit@k를 다시 재는 것으로 시작하면 된다. 숫자가 올랐는지로 판단하고, 감으로 고치지 않는 게 요점이다.

<summary>자세한 풀이: 여기서 더 붙일 것들</summary>

- 임베딩을 진짜 모델로 교체: `embed` 함수만 바꾸고 `DIM`을 모델 차원에 맞춘다.
- 하이브리드 검색: BM25 점수와 임베딩 점수의 순위를 합쳐서 상위를 고른다. Contextual Retrieval 글은 순위 융합을 쓴다고 한다.
- 재순위: 넉넉히(글에서는 150개) 찾은 뒤 재순위 모델로 줄여서 20개를 넘긴다.
- 청크 앞에 문맥 한 줄 붙이기: 청크에서 회사명·기간이 빠지는 문제를 줄이려는 방식.
- 캐시: 문서가 안 바뀌면 임베딩을 다시 계산하지 않는다. 같은 자료를 반복해서 붙이는 프롬프트는 [프롬프트 캐싱](#/post/ai-prompt-caching)으로 비용을 줄일 수 있다.
