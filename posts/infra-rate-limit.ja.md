レートリミットは、一定時間内に受け入れるリクエスト数に上限を設け、その超過分は処理せず返却する仕組みである。サーバーを守るための目的が第一であり、一つのユーザーが資源を独占できないようにするのが第二の目的だ。

## なぜ必要なのか

サーバーが処理できる量は決まっているのに、リクエストは一気に殺到することがある。バグやスクリプトによって API を無限ループで叩くこともあれば、イベントによって本物のユーザーが殺到することもある。制限がない場合、一人の暴走が他の全ユーザーの応答を遅くしてしまう。

Stripe が 2017 年に書いた記事にはこのような話がある。最も重要な制限はユーザーごとの 1 秒あたりのリクエスト数制限であり、月に数百万件を拒否したが、その大半はテストモードで回っていた暴走スクリプトだったという。悪意のある攻撃よりも、誤って実行されたコードの方が多かったということだ。数字はその記事が書かれた時点の基準である。

リクエストが殺到するのをサーバー台数で解決する方法（[詳細 → オートスケーリング](#/post/infra-autoscaling)）もあるが、サーバーを増やすには時間がかかり、お金もかかる。レートリミットはその間を凌ぐためのものだ。リクエストをどこに振り分けるかは [ロードバランサー](#/post/infra-load-balancer) の記事で別途書かれている。

## どこで数えるのか

通常、基準は以下の三つの中の一つだ。

| 基準 | 数える対象 | 特徴 |
|---|---|---|
| IP | リクエストを送信したアドレス | ログイン前でも使えるが、一つの会社のネットワークが同じ IP から見える場合、不当にブロックされる可能性がある |
| ユーザー/API キー | 認証されたアカウント | 最も公平だ。認証後のみ可能 |
| エンドポイント | 特定のパス | ログインや決済のような重い処理を行う場所だけを厳しく制限する |

RFC 6585 は 429 を定義しながら、サーバーがユーザーをどのように識別し、リクエストをどのように数えるかは定めていないと述べている。認証情報やクッキーで識別でき、リソース別・サーバー全体・複数のサーバーの合計などすべて可能であるとしか書かれていない。つまり基準はサービス側が決めるものだ。

複数のサーバーがある場合、カウンターを各サーバーごとに別々に持てない。3 つのサーバーがそれぞれ「1 秒あたり 10 個」を許可すると、ユーザーは実質的に 30 個を送れることになる。そのため、カウンターは通常、サーバー同士が共有できる場所に置く。Stripe はトークンバケットを Redis の上に実装したと書いている。この部分は [Redis キャッシュ](#/post/db-cache-redis) の記事に続く。

## アルゴリズムの三つ

### 固定ウィンドウ

時間を 10 秒などの区切りで分割し、各区間にカウンターを置く。10 秒間に 5 個まで許可すれば、区間が変わるたびにカウンターを 0 にリセットする。実装が最も簡単だ。

弱点は区間の境界である。9.9 秒に 5 個、10.0 秒に 5 個を送れば各区間の基準ではどちらも許可されるが、実際には 0.1 秒以内に 10 個が入ってくる。後で実際に動かして確認した。

### スライディングウィンドウ

「今から逆算して 10 秒間に何個来たか」を数える。リクエスト時刻をすべて記録しておく方式（スライディングログ）は正確だが、各リクエストごとに記録を持ち続ける必要があるためメモリを使う。境界の問題はない代わりにコストがかかる。

### トークンバケット

最もよく見られる方式だ。バケットにトークンが最大 N 個入っており、一定の速度でトークンが再び補充される。一つのリクエストが来ると一つのトークンを取り出し、バケットが空なら拒否する。ユーザーごとにバケットが一つずつある。

パラメータは二つある。容量（capacity）は一度に受け入れられるバーストの大きさであり、補充速度（refill rate）は長期間続いた場合の平均速度だ。容量 5、1 秒あたり 1 個とすると、普段は 1 秒あたり 1 個ずつだが、しばらく休んでから来れば一度に 5 個まで受け入れる。ユーザーたちは静かに待機した後、一度にまとめて送ることが多いため、この性質が現実とよく合致する。

<details>
<summary>三つの方式を Python で動かしてみたもの</summary>

```python
from collections import deque

class TokenBucket:
    def __init__(self, capacity, refill_per_sec, now=0.0):
        self.capacity, self.rate = capacity, refill_per_sec
        self.tokens, self.last = float(capacity), now
    def allow(self, now, cost=1):
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

class FixedWindow:
    def __init__(self, limit, window):
        self.limit, self.window = limit, window
        self.start, self.count = 0.0, 0
    def allow(self, now):
        if now - self.start >= self.window:
            self.start = now - (now % self.window); self.count = 0
        if self.count < self.limit:
            self.count += 1; return True
        return False

class SlidingLog:
    def __init__(self, limit, window):
        self.limit, self.window, self.log = limit, window, deque()
    def allow(self, now):
        while self.log and self.log[0] <= now - self.window:
            self.log.popleft()
        if len(self.log) < self.limit:
            self.log.append(now); return True
        return False
```

実行結果は以下の通りだった。

- トークンバケット（容量 5、1 秒あたり 1 個）：時刻 0 に 10 個を一気に送ると 5 個のみ通過。3 秒後に 5 個を送ると最初の 3 個のみ通過。
- 10 秒に 5 個制限、9.9 秒に 5 個 + 10.0 秒に 5 個：固定ウィンドウでは 0.1 秒以内に 10 個許可、スライディングログでは 5 個のみ許可。

トークンを時間の経過に伴って「まとめて計算して」補充するという点が実装の要領だ。タイマーで一つずつトークンを投入するのではなく、リクエストが来た際、最後の時刻との差分分だけ追加する。そのため、ユーザー数分だけタイマーを回す必要がない。

</details>

## 429 とクライアントが行うべきこと

拒否する際は HTTP 429 Too Many Requests を返すのが標準だ。MDN は「与えられた時間内にクライアントがリクエストを送りすぎた」という意味だと説明している。レスポンスに `Retry-After` ヘッダーを付ければ、どれくらい後に再度送るか知らせることができる。値は秒単位の数字でも HTTP 日付でもあり、クライアントは両方読む必要がある。RFC 6585 ではこのヘッダーは付けることができるオプション事項である。

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

クライアント側が 429 を受け取ってすぐに再送すると状況はさらに悪化します。そのため、再試行にはルールが必要です。AWS Builders' Library の記事でまとめられている内容は以下の通りです。

- 再試行はもはや厳しいシステムにさらなる負荷をかけます。問題が解決した後でも負荷が高く維持されるため、回復が遅れる可能性があります。
- 各段階で再試行すると負荷は累乗的に増加します。5 つのレイヤーがそれぞれ 3 回ずつ再試行すると、最下層の DB は 243 倍もの負荷を受けることになります。そのため、1 つの地点でのみ再試行を行うことを推奨します。
- 指数関数的なバックオフ（待機時間を徐々に増やす）には上限値と回数制限を設けます。
- ジャッター（乱数による無作為のばらつき）を追加します。同じ瞬間に失敗したクライアントが同じ間隔で後退すると、再び同じ瞬間に集中してしまいます。
- 再試行にもトークンバケット方式を採用します。トークンがある間は再試行を行い、枯渇したら低速でのみ実行します。AWS SDK では 2016 年に導入されたそうです。
- 副作用のある呼び出しは冪等性を持たない場合、再試行が危険です。

ジャッターによる差をシミュレーションしてみました。100 のクライアントが同じ瞬間に失敗し、3 回目の試行（待機時間 4 秒）を行う場合、ジャッターがないと 1 秒間に 100 が集中しましたが、0〜4 秒の間に無作為に行うと 1 秒あたりの最大は 27 でした。これは乱数シードを固定した 1 回の実験結果であり、正確な数字よりも傾向を示すものです。

## 防ぐことではなく整理すること

レートリミットは超過した要求を破棄します。破棄すべきでない事象は別の方法で処理する必要があります。

- キューイング：要求を即座に処理せずキューに入れ、ワーカーが自分のペースで取り出して処理します。ユーザーは受理のみされ、結果は後から受け取ります。この構造は [非同期キュー](#/post/be-async-queue) の記事にあります。
- バックプレッシャー (backpressure)：処理側が遅くなるとその事実を前方に伝え、送信速度を低下させる仕組みです。キューが満杯になると新しい要求を拒否するか、プロデューサーを待機させます。キューが無制限に長くなると遅延のみが増加するため、長さにも上限が必要です。
- 同時要求制限：1 秒あたりの数ではなく、現在処理中の要求数をカウントします。Stripe は CPU を多く消費するエンドポイントで再試行が重なり発生する競合を防ぐためにこれを採用しました。
- ロードシェディング (load shedding)：サーバー全体が限界に近づくと、重要な要求の分を確保し、重要度の低いものを破棄します。Stripe の記事では、決済生成などのコアな呼び出し用に一部容量を別途確保し、リスト取得などの重要度の低い呼び出しは超過すると 503 で返すとしています。

Stripe はこの 4 つ（要求速度、同時要求、サービス全体の負荷シェディング、ワーカー使用率基準のシェディング）を重ねて使用していると記されています。1 つで全てを防ごうとせず、層を分けています。

## よくある誤解

- 429 はサーバー障害ではありません。サーバーは正常であり、クライアントが割り当て量を超過したものです。障害時には 5xx が返されます。ただし、サーバーが自己保護のために意図的に送る 503 は、クライアント側からは似ているように見えます。
- レートリミットがあれば DDoS が防げるという過剰な期待です。アプリサーバーまで到達した要求をカウントするため、その前でネットワーク自体が遮断されてしまう攻撃には効果がなく、そのようなものはより上流で処理します。本稿の範囲外のため詳細は記載できません。
- IP だけでカウントすれば十分というわけではありません。同じネットワークの利用者が 1 つの IP にまとめられ、攻撃者は IP を変更するためです。
- 制限を一度設定して終わりではありません。低すぎると正常なユーザーがブロックされ、高すぎると意味がないため、実際のトラフィックを見ながら調整する必要があります。
- LLM API のようにトークン数で制限をかけるサービスもあります。要求数ではなくトークンをコストとするのは、トークンバケットの `cost` パラメータと同じ考え方です。コストに関する話は [AI アプリのコスト](#/post/app-cost) にあります。
