Secrets 不应通过代码传递，而应在运行环境中提供；即使需要更新，也应构建一种能够最小化损害影响的结构，这几乎涵盖了管理的全部。

## 设置与 Secrets

应用程序运行不仅需要代码，还需要其他值，例如数据库地址、外部服务 API 密钥、服务器主机名等。12-Factor 应用文档将这些称为“设置（config）”，并定义所有可能随部署而变化的内容。像连接应用程序内部结构的路由设置这类内容不会随部署改变，因此不包含在内。

Secrets 是设置中一旦泄露就令人担忧的部分。密码、API 密钥、令牌、证书私钥等都属于此类。数据库地址是设置，但数据库密码则是 Secrets。若以相同方式处理两者，就会引发事故。

文档提出的标准只有一个：如果此刻公开这段代码，凭证是否会泄露？如果不会泄露，说明设置已从代码中正确分离。

## 为什么环境变量是首选

12-Factor 建议将设置放在环境变量中。原因有三点：

- 无需修改代码，只需随部署更改值。
- 与设置文件不同，被意外提交到仓库的可能性较低。
- 不受编程语言和操作系统限制，通用性强。

对比对象是嵌入代码中的常量和不提交的设置文件（如 Rails 的 database.yml）。常量违反了分离原则；设置文件虽好，但可能被意外提交，且格式因框架而异。

从代码读取的值很简单：

```python
import os

def need(name):
    v = os.environ.get(name)
    if not v:
        raise SystemExit(f"{name} 없음")
    return v

db_url = need("DB_URL")      # 없으면 시작 단계에서 바로 멈춘다
```

若配置为在值缺失时静默使用默认值而非启动时停止，可减少部署后很久才爆发的事故。上述代码已分别执行了“填入值”和“未填值”两种情况以验证其行为。

12-Factor 还建议避免的一种做法是：将名为 `development`、`test`、`production` 的设置组嵌入代码中。文档指出这种方式“无法优雅扩展”。随着 staging 或本地环境增多，组合数量呈指数增长，容易导致部署失败。应通过单个变量独立管理每个部署，而非按环境名称分组。

## .env 文件

在本地开发中，每次手动输入环境变量到终端很繁琐，因此会在 `.env` 文件中以 `KEY=value` 的形式记录，工具启动时读取并将其作为环境变量加载。这并非魔法，只是一个普通文件。

需注意两点：首先，将 `.env` 加入 `.gitignore`；其次，仅向仓库提交清空了值的 `.env.example` 文件，以告知所需变量有哪些。

正如 [详见 → CI/CD 与部署策略](#/post/cloud-cicd) 所述，在生产服务器或 CI 环境中，通常采用平台注入方式而非使用 `.env` 文件。若将文件上传至服务器，该文件本身又成为另一个管理对象。

## 环境变量不足之处

OWASP 的 Secrets 管理速查表将环境变量视为“最后手段”，因为其可能随日志或崩溃转储一同泄露。文档建议不要将 Secrets 嵌入代码、Dockerfile 或设置文件中，而应由编排器注入或在运行时获取。[详见 → Docker](#/post/cloud-docker) 可继续了解为何向镜像中写入 Secrets 存在风险。

环境变量的弱点总结如下：

| 担忧 | 仅使用环境变量时 |
|---|---|
| 谁读取过 | 无记录留存 |
| 修改 | 需重启应用才能生效 |
| 访问限制 | 进程内所有人均可见 |
| 泄露风险 | 易混入日志、转储或调试输出中 |

因此，随着规模扩大，应使用专用 Secrets 存储库。

## Secrets 管理器

AWS Secrets Manager 文档介绍该服务可作为工具，在整个生命周期内管理并获取和轮换 Secrets，如数据库凭据、应用凭据、OAuth 令牌、API 密钥等。核心思想是将嵌入代码的凭据替换为运行时调用：应用程序在需要时向服务请求值。

这样做可获得以下好处：

- 值不与应用程序一同存储，因此即使有人能查看应用程序，也无法立即获取 Secrets。
- 可设置自动轮换计划；由于值未嵌入应用，更换时无需重新部署应用。
- 记录谁在何时提取了 Secrets。文档指出启用 CloudTrail 后可获取 API 调用日志。

文档也列出了注意事项：该服务按使用量计费；若使用自有 KMS 密钥进行加密或借助 Lambda 执行轮换，会产生额外费用。此外，AWS 凭据、加密密钥和证书分别对应 IAM、KMS 和 ACM 等专用服务，Secrets Manager 并非存放所有秘密的万能保险箱。

其他云平台和工具（如 Google Secret Manager、HashiCorp Vault 等）也能起到相同的作用，但本次并未查阅相关文档。

## 轮换与最小权限

OWASP 指南的核心建议大致如下：

- **集中管理**：不要将密钥分散在代码、配置文件或各类工具中，而应使用专用系统进行统一管理。
- **轮换**：定期更换密钥，并尽可能实现自动化，以缩短被盗凭据的有效生命周期。
- **最小权限**：限制每个密钥的读取和修改主体范围。
- **动态密钥**：为每次会话颁发短暂有效且会过期的凭据。文档指出，即使应用重启，被盗用的凭据也不会失效。
- **审计**：记录谁请求了访问、获得了批准以及何时使用了密钥，并确保日志本身不被篡改。

起初我认为轮换是一项令人厌烦的定期任务，但文档的观点恰恰相反。其目标并非防止泄露，而是缩短即便发生泄露也能被利用的时间窗口。一旦设定，永久使用的密钥从泄露那一刻起便持续存在风险；而短期有效的密钥即使泄露也会很快失效。

## 泄露应对

以 GitHub 文档为标准，密钥扫描会遍历所有分支的完整 Git 历史、Issue、PR、讨论及 Wiki，以查找已暴露的密钥。一旦发现，将在存储库安全标签页中生成警告。公开仓库可免费使用，而组织内的私有仓库则需要额外产品（GitHub Secret Protection）支持。

泄露应对流程两份文档基本一致：

1. 立即吊销相关凭据并重新颁发新密钥。
2. 从代码、日志等已暴露的位置删除该密钥。
3. 记录泄露发生的时间、方式及使用情况。

GitHub 文档指出，从 Git 历史中彻底删除密钥耗时较长，若已吊销则通常无需操作。与其删除提交记录，不如先使密钥失效，因为对方可能已经复制走了密钥。

## 常见误区

- **将 `.env` 加入 `.gitignore` 就安全了**：这只能防止未来的提交，但历史提交中已存在的密钥仍保留在历史记录中。此外，通过日志或镜像泄露的途径依然存在。
- **存储库私有就可以存放密钥**：12-Factor 应用的核心标准是“是否允许公开”，私有仅表示当前访问权限较窄，并不代表安全。
- **环境变量已加密**：并非如此。若进程拥有相同权限，即可读取这些变量。
- **使用密钥管理器就万事大吉**：若对管理器的访问权限过大，无异于打开了保险库的大门。必须结合最小权限原则和审计机制。
- **删除后问题就解决了**：由于可能已被复制，吊销才是首要步骤。

<summary>详细解析：需要执行到哪个阶段？</summary>

文档本身并未直接划分具体步骤，以下内容是按阅读顺序整理的操作指南：

1. 将代码中硬编码的值全部替换为环境变量。仅此即可满足代码公开的基本合规要求。
2. 本地开发环境使用 `.env` + `.gitignore` + `.env.example` 组合方案。
3. 部署环境由平台自动注入（如 CI 密钥、容器编排系统的密钥等）。
4. 若密钥数量较多或团队规模较大，则迁移至密钥管理器，并在应用启动时动态加载。
5. 制定密钥轮换周期及泄露应对流程（包括谁负责吊销、通知哪些人员），并形成文档规范。

对于小型个人项目，执行前 3 步是否足够，还是必须进入第 4 步，取决于服务性质和成本考量。密钥管理器通常按使用量计费，若密钥数量较少，需权衡其投入产出比。
