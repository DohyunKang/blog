브라우저에서 엔터를 치면 요청 하나가 DNS, CDN, 로드밸런서, 서버, 캐시, DB를 차례로 지나가고, 각 단계마다 시간이 붙는다. 느릴 때는 이 길 중 어디가 늦는지부터 찾는 게 순서였다.

## 한 장으로 먼저 보기

```
브라우저
  │ 1. DNS: 도메인 → IP 주소
  ▼
CDN(엣지)  ── 캐시에 있으면 여기서 응답하고 끝
  │ 2. 없으면 원본 서버 쪽으로
  ▼
로드밸런서 ── 살아 있는 서버 중 하나를 고름
  │
  ▼
앱 서버 ──── 3. 캐시(Redis 등)를 먼저 확인
  │            있으면 바로 응답
  ▼
DB ───────── 4. 캐시에 없을 때만 조회
```

실제 서비스마다 이 중 일부가 빠져 있다. CDN이 없는 서비스도 있고, 서버 한 대라서 로드밸런서가 없는 곳도 있다. 그래도 큰 틀은 비슷해서 이 순서로 정리해 둔다.

## 1. DNS: 이름을 주소로 바꾸는 단계

브라우저가 처음 하는 일은 도메인의 IP를 알아내는 것이다. AWS 문서가 설명하는 흐름은 이렇다. 브라우저가 DNS 리졸버(보통 통신사나 회사 망이 운영)에 묻고, 리졸버가 루트 네임서버, 그다음 .com 같은 TLD 네임서버, 마지막으로 그 도메인의 권한 네임서버에 차례로 묻는다. 답을 받으면 리졸버는 그 IP를 설정된 시간 동안 저장해 두고, 다음 질문에는 위 과정 없이 바로 답한다.

그래서 같은 도메인을 두 번째 찾을 때는 빠르다. 저장하는 시간이 TTL이다. TTL을 길게 잡으면 조회가 줄지만, 서버 IP를 바꿔도 예전 주소가 한동안 남는다.

## 2. 연결 맺기: TCP와 TLS

IP를 알았다고 바로 데이터를 주고받는 건 아니다. 먼저 TCP 연결(핸드셰이크)을 맺고, HTTPS면 TLS 협상이 한 번 더 붙는다. MDN의 지연 설명에서도 DNS, 연결, TLS 협상, 요청 전송, 서버 대기, 응답 수신을 따로 나눠 놓고, 첫 요청이 느린 이유를 이 준비 단계가 같이 들어가서라고 한다. 연결을 이미 열어 둔 다음 요청은 이 비용을 다시 내지 않는다.

여기서 시간은 대부분 거리에서 나온다. 핸드셰이크는 왕복이 몇 번 필요하고, 왕복 한 번의 시간은 서버가 멀수록 길다. 서버를 사용자 가까이에 두는 CDN이 필요한 이유가 이쪽이다.

## 3. CDN: 가까운 곳에서 대신 답하기

MDN 설명으로 CDN은 여러 지역에 흩어진 서버 묶음이고, 각 서버가 데이터 사본을 갖고 있어서 가장 가까운 곳이 요청을 받는다. 이미지, CSS, JS처럼 모두에게 같은 파일이 이 방식에 잘 맞는다. 엣지에 사본이 있으면(캐시 히트) 거기서 끝나고, 없으면(미스) 원본 서버까지 가서 가져온 뒤 저장해 둔다. 원본 서버가 받는 요청도 그만큼 줄어든다.

MDN이 덧붙인 주의점도 기억해 둘 만하다. CDN은 외부 의존이 하나 더 생기는 것이고, 새 도메인에 연결하느라 DNS 조회와 연결 비용이 추가돼서 오히려 느려질 수도 있다고 한다. 무조건 빨라지는 건 아니다.

[자세히 → CDN과 캐시](#/post/infra-cdn-cache)

## 4. 로드밸런서: 어느 서버로 보낼지 고르기

원본 쪽으로 들어온 요청은 로드밸런서가 받는다. AWS 문서 기준으로 로드밸런서는 들어오는 트래픽을 여러 대상(인스턴스, 컨테이너 등)에 나눠 보내고, 대상의 상태를 계속 확인해서 정상인 곳으로만 보낸다. 서버를 붙이고 빼도 요청 흐름이 끊기지 않게 하는 게 목적이다. 암호화·복호화를 로드밸런서가 대신 맡게 할 수도 있다고 한다.

그래서 서버 한 대가 죽어도 사용자는 모르고 지나갈 수 있다. 서버 대수를 늘릴 때는 [자동 확장](#/post/infra-autoscaling)과 같이 붙어서, 새로 뜬 서버가 자동으로 로드밸런서에 등록된다.

[자세히 → 로드밸런서](#/post/infra-load-balancer)

## 5. 앱 서버와 캐시, DB

요청이 앱 서버에 도착하면 코드가 돈다. 인증을 확인하고, 필요한 데이터를 찾는다. 이때 자주 쓰는 데이터는 Redis 같은 캐시에 두고 먼저 본다. 있으면 메모리에서 바로 꺼내 응답하고, 없을 때만 DB를 조회한 뒤 결과를 캐시에 넣는다.

DB 조회는 보통 여기서 가장 비싼 일이다. 같은 질문에 매번 디스크를 뒤지지 않게 하려고 캐시를 앞에 둔다. 조회 자체가 느리면 [인덱스](#/post/db-index)가 있는지부터 본다. 서버 안에서 요청이 어떻게 흘러가는지는 따로 정리했다.

[자세히 → 캐시와 Redis](#/post/db-cache-redis) · [자세히 → 서버 안의 요청 흐름](#/post/be-request-flow)

## 6. 지연은 어디서 쌓이나

단계별로 대략 어디서 시간이 걸리는지 표로 모았다. 숫자는 일부러 적지 않았다. 환경마다 차이가 너무 커서 한 값으로 말하기 어렵다.

| 단계 | 시간이 걸리는 이유 | 줄이는 방법 |
|---|---|---|
| DNS | 리졸버가 여러 서버에 차례로 묻는다 | 리졸버 캐시(TTL), 도메인 수 줄이기 |
| TCP/TLS | 왕복이 여러 번, 거리에 비례 | 연결 재사용, 사용자 가까이 두기(CDN) |
| CDN | 미스일 때 원본까지 왕복 | 캐시 가능한 응답으로 만들기 |
| 로드밸런서 | 보통 짧고, 서버 선택 정도 | 정상 서버만 받게 점검 |
| 앱 서버 | 코드 처리, 외부 호출 | 불필요한 호출 줄이기, 캐시 |
| DB | 디스크 조회, 쿼리 모양 | 인덱스, 캐시, 쿼리 정리 |

web.dev는 TTFB(첫 바이트가 도착하기까지의 시간)를 리다이렉트, DNS, 연결과 TLS 협상, 요청부터 첫 바이트 도착까지의 합으로 정의한다. 대략의 기준으로 0.8초 이하면 좋고 1.8초를 넘으면 나쁜 쪽으로 본다. 다만 이건 "대부분의 사이트에 쓰는 어림 기준"이라고 적혀 있다.

## 직접 재 본 값

이론만 보다가 내 PC에서 한 번 재 봤다. 파이썬 소켓으로 example.com에 DNS 조회, TCP 연결, HTTP 요청(첫 바이트)을 단계별로 쟀다. HTTPS 대신 80번 포트의 평문 HTTP로 한 것이라 TLS 구간은 빠져 있다.

```
DNS 11ms / TCP 153ms / 첫 바이트 145ms / 다운로드 2ms / 합계 311ms
DNS 10ms / TCP 113ms / 첫 바이트 120ms / 다운로드 0ms / 합계 243ms
DNS 10ms / TCP 114ms / 첫 바이트 119ms / 다운로드 0ms / 합계 243ms
```

DNS는 10ms 안팎으로 짧았고, TCP 연결과 첫 바이트 대기가 각각 110~150ms로 컸다. 다운로드는 작은 페이지라 거의 없다. 서버가 멀면 거리 때문에 연결과 대기가 대부분이라는 말이 숫자로 보였다. 다만 내 PC 위치와 그 순간의 망 상태 값이라, 다른 곳에서는 전혀 다를 수 있다. DNS가 빨랐던 건 이미 캐시에 있었기 때문일 수도 있다.

<details>
<summary>자세한 풀이: 측정 코드와 읽는 법</summary>

```python
import socket, time, sys
host = sys.argv[1]
t0 = time.perf_counter()
ip = socket.getaddrinfo(host, 80, socket.AF_INET)[0][4][0]   # DNS
t1 = time.perf_counter()
s = socket.create_connection((ip, 80), timeout=10)           # TCP
t2 = time.perf_counter()
s.sendall(f"GET / HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n\r\n".encode())
s.recv(1)                                                      # 첫 바이트
t3 = time.perf_counter()
while s.recv(65536):                                           # 나머지 다운로드
    pass
t4 = time.perf_counter()
ms = lambda a, b: round((b - a) * 1000)
print(f"DNS {ms(t0,t1)}ms / TCP {ms(t1,t2)}ms / 첫 바이트 {ms(t2,t3)}ms / 다운로드 {ms(t3,t4)}ms / 합계 {ms(t0,t4)}ms")
```

위 코드를 3번 실행한 결과가 앞의 값이다. "첫 바이트"는 요청을 보낸 뒤 서버가 처음 한 글자를 돌려줄 때까지라서, 서버 처리 시간과 왕복 지연이 같이 들어 있다. 둘을 나누려면 서버 쪽 로그나 타이밍 헤더가 필요하다.

TLS까지 재려고 HTTPS 버전도 시도했는데, 이 PC에서 인증서 검증 오류가 나서 TLS 구간은 재지 않았다. 검증을 끄는 방법은 쓰지 않았다.

브라우저에서는 개발자 도구의 Network 탭에서 요청 하나를 누르면 같은 단계(DNS, 연결, TLS, 대기, 다운로드)가 나뉘어 보인다. 직접 코드를 짜지 않아도 이쪽이 더 편하다.

</details>

## 흔한 오해

- 서버 코드만 빠르면 된다: 서버 처리는 길의 한 구간일 뿐이다. 앞쪽의 DNS와 연결, CDN 미스, 뒤쪽의 DB가 더 큰 경우도 많다.
- CDN을 쓰면 무조건 빨라진다: 캐시 가능한 응답이어야 효과가 있고, 위에서 본 것처럼 도메인이 하나 늘면서 오히려 느려질 수도 있다.
- 캐시는 켜 두기만 하면 된다: 캐시에 있는 값이 낡을 수 있어서, 언제 버릴지(TTL)를 같이 정해야 한다.
- 로드밸런서가 있으면 서버는 안 죽는다: 한 대가 죽어도 다른 서버가 받아 주는 것이지, 서버가 전부 같은 원인으로 느려지면 로드밸런서도 해결해 주지 못한다.

느린 서비스를 만나면 위 표 순서대로 한 구간씩 시간을 재 보는 게 먼저였다. 감으로 DB부터 의심하면 엉뚱한 곳을 고치기 쉽다. 이 구간별 측정은 [관측 가능성](#/post/cloud-observability) 쪽에서 더 이어진다.
