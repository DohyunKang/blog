오늘 아침 GitHub 트렌딩 주간 목록에 ag-ui-protocol/ag-ui가 있었다. 이번 주 별 2,966개, 레포 전체 별은 21,562개다(11월 25일 오전 확인). AG-UI는 AI 에이전트와 사람이 보는 앱 화면 사이에서 오가는 데이터를 어떤 모양으로 주고받을지 정한 공개 규격이다. 나는 README, docs의 개념 문서(architecture, tools, state, interrupts), 1.0 변경점 문서, 최근 커밋 목록을 읽었다. 직접 서버를 띄워 보지는 않았다.

## 뭘 정하는 규격인지
보통 웹은 요청 하나 보내면 응답 하나 받고 끝난다. 에이전트는 그렇게 안 끝난다. 글자를 조금씩 흘려보내고, 중간에 도구를 부르고, 사람 확인을 기다리며 멈추고, 서브에이전트를 띄운다. README 첫 부분이 이 얘기다. 이걸 화면에 보여 주는 방식이 프레임워크마다 달라서 앱마다 연결 코드를 새로 짜야 했다는 것이다.

AG-UI는 이걸 이벤트 하나의 흐름으로 통일한다. 이벤트는 "지금 이런 일이 일어났다"는 짧은 메시지다. 에이전트는 정해진 종류의 이벤트를 차례로 내보내고, 앱은 그걸 받아서 그린다. 에이전트를 LangGraph로 만들었든 CrewAI로 만들었든 앱 쪽 코드는 그대로다.

README가 자기 자리를 설명하는 그림이 이해하기 편했다. MCP는 에이전트에게 도구와 데이터를 붙이고, A2A는 에이전트끼리 일하게 하고, AG-UI는 에이전트를 사용자 앞에 데려온다. 셋이 겹치지 않는다는 주장이다. MCP는 에이전트가 바깥 프로그램 기능을 도구처럼 부르게 하는 연결 규격이다. [자세히 → MCP](#/post/ai-mcp)

## 구조
시작은 단순하다. 앱이 HTTP POST로 `RunAgentInput`(스레드 ID, 실행 ID, 지금까지의 메시지, 앱이 내주는 도구 목록, 공유 상태)을 보내면, 에이전트가 이벤트를 스트림으로 돌려준다. 기본 전달 방식은 SSE다. SSE(Server-Sent Events)는 서버가 연결 하나를 열어 둔 채 텍스트를 계속 밀어 보내는 웹 표준이다. 1.0부터는 Protobuf로 묶은 바이너리 전달 방식도 규격에 들어갔다.

이벤트는 몇 무리로 나뉜다.
- 실행 시작과 끝: `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`
- 답변 글자: `TEXT_MESSAGE_START` → `CONTENT`(조각) → `END`
- 도구 호출: `TOOL_CALL_START` → `ARGS`(인자 JSON을 조각으로) → `END` → `RESULT`
- 공유 상태: `STATE_SNAPSHOT`(전체), `STATE_DELTA`(바뀐 부분만)

README 예제의 파이썬 서버가 30줄 남짓인데, 하는 일은 시작 이벤트, 글자 이벤트 세 번, 끝 이벤트를 차례로 보내는 게 전부다. 규격이 요구하는 최소한이 그 정도라는 뜻이다.

## 화면 쪽이 도구를 쥔다
읽으면서 제일 눈에 띈 건 도구를 두 종류로 나누는 방식이다. 에이전트 서버에 원래 있는 도구는 서버에 둔다. 따로, 앱이 실행할 때마다 `RunAgentInput.tools`에 "이번엔 이 도구들을 써도 된다"고 목록을 실어 보낼 수 있다. 확인 창 띄우기, 화면 이동 같은 것들이다. 에이전트가 이걸 부르면 실제 실행은 앱에서 일어난다.

tools 문서가 꼽는 이유는 권한이다. 이 사용자에게 어떤 기능을 열지 앱이 정하고, 민감한 동작은 에이전트가 아니라 앱이 통제한다. 에이전트는 판단만 하고 손은 앱이 쓰는 구조다. 도구 호출 자체가 궁금하면 [자세히 → 도구 호출](#/post/ai-tool-use)

## 상태는 JSON 하나를 같이 본다
공유 상태는 에이전트와 앱이 같이 보는 JSON 객체 하나다. 처음엔 `STATE_SNAPSHOT`으로 통째로 보내고, 그다음엔 `STATE_DELTA`로 바뀐 부분만 보낸다. 델타는 JSON Patch(RFC 6902) 형식이다. "이 경로의 값을 이걸로 바꿔라" 같은 지시를 목록으로 적는 표준이다. 연결이 끊겼다 붙으면 스냅샷을 다시 받아서 맞춘다. 에이전트가 표를 채우는 중이면 화면도 그 표를 같이 채워 갈 수 있다.

## 멈췄다가 다시 이어 가기
사람 확인이 필요할 때 처리가 꽤 엄격하다. 에이전트는 실행을 열어 둔 채 기다리지 않는다. 다시 이어 가는 데 필요한 상태와 메시지를 스냅샷으로 먼저 보내고, `RUN_FINISHED`에 "interrupt" 결과를 실어서 실행을 끝낸다. 사용자가 승인하면 앱이 같은 스레드에 새 실행을 시작하면서 `resume`에 답을 담아 보낸다.

규칙도 문서에 박혀 있다. 열린 interrupt에는 전부 답해야 하고 일부만 답할 수는 없다. 답이 걸린 스레드에 resume 없이 새 입력을 보내면 에러다. 같은 resume을 두 번 보내도 안전해야 하고, 만료 시각(`expiresAt`)이 지난 답은 거절된다. 승인 버튼을 두 번 누르거나 한참 뒤에 누르는 경우까지 규격이 미리 정해 둔 셈이다.

## 왜 지금 화제인지
레포는 2025년 5월에 만들어졌다. 새로 나온 건 아니다. 1.0도 9월에 나왔다(npm `@ag-ui/core` 1.0.0이 9월 17일 UTC). 1.0 변경점 문서를 보면 0.x 때는 동작 규칙이 사실상 TypeScript 클라이언트 코드 안에만 있었고, 1.0에서 처음으로 규칙을 문서와 JSON Schema로 못 박았다. TypeScript, Python, .NET SDK가 그 스키마에서 생성된다. 서브에이전트 이벤트, 추론 과정 이벤트(옛 THINKING 이벤트를 대체), 실행이 어떻게 끝났는지 알리는 `outcome`도 이때 들어갔다.

이번 주에 별이 몰린 정확한 계기는 확인 못 함. 다만 커밋은 매일 쌓이고 있다. 11월 17일에 SDK 1.0.5와 Cloudflare Agents 연동 0.1.0이 나왔고, 그 뒤로도 LangGraph, Google ADK, OpenAI Agents 연동 패키지가 계속 올라갔다. README는 Google, Microsoft, Amazon, Oracle이 채택했다고 적는데, 이건 README의 주장이고 각 회사 쪽 발표를 내가 따로 확인하지는 않았다. Microsoft Agent Framework 릴리스 노트에 AG-UI 엔드포인트가 나오는 건 예전에 본 적이 있다. [자세히 → Microsoft Agent Framework](#/post/news-harness-2)

내려받기 수는 크다. npm `@ag-ui/core`가 11월 17~23일 한 주 8,050,853회였다. 이 숫자는 다른 패키지가 의존성으로 끌어온 것까지 포함이라, 직접 쓰는 사람 수로 읽으면 안 된다. X에서 "AG-UI"를 언급한 글(리트윗 제외, UTC 하루 단위)은 11월 18일 59건이 가장 많았고 나머지 날은 14~25건이었다. Reddit 반응은 확인 못 함.

## 입문자 입장에서
에이전트 데모는 보통 채팅창 하나로 끝나는데, 실제 서비스에선 승인 버튼, 진행 표시, 에이전트가 채우는 표 같은 화면이 붙는다. AG-UI는 그 화면과 에이전트 사이의 약속을 미리 정해 둔 것이다. 프론트엔드와 백엔드가 이 이벤트 목록만 맞추면 서로 따로 만들 수 있다.

PM 입장에서 쓸 만한 건 interrupt 규칙이다. "사람이 승인하면 이어서 진행"을 기획서에 한 줄로 적기는 쉬운데, 두 번 누르면, 늦게 누르면, 일부만 승인하면 어떻게 되는지까지 정해야 실제로 만들 수 있다. 이 규격은 그 질문에 대한 답을 하나 미리 적어 둔 예시로 읽을 만했다. 서브에이전트가 낯설면 [자세히 → 서브에이전트](#/post/ai-subagent)
