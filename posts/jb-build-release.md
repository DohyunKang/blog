형상관리는 소프트웨어가 바뀌는 걸 기록하고 통제하는 일이고, 빌드·배포는 그렇게 관리된 소스를 실행 가능한 결과물로 만들어 내보내는 일이다. 정보처리기사에서는 용어 정의와 분류를 묻는 문제가 대부분이라, 이 글도 그 단위로 나눠 적었다. 시험 일정·응시료는 공식 사이트에서 확인한다.

## 형상관리가 뭔지

형상(Configuration)은 소프트웨어를 이루는 산출물 전체다. 소스 코드만이 아니라 요구사항 문서, 설계서, 테스트 케이스, 설정 파일도 포함한다. 이 중 변경을 추적할 대상으로 정한 항목을 형상 항목이라고 부른다.

형상관리(SCM)는 이 항목들이 누가·언제·왜 바뀌었는지 남기고, 필요하면 이전 상태로 되돌릴 수 있게 하는 활동이다. 개발 중 바뀌는 건 막을 수 없으니, 바뀌는 과정을 질서 있게 만드는 쪽이 목적이다. 요구사항이 중간에 바뀌는 문제는 [자세히 → 요구사항 확인과 분석](#/post/jb-requirements)에서도 나온다.

시험에서 자주 나오는 용어를 표로 모았다.

| 용어 | 뜻 |
|---|---|
| 형상 항목 | 변경을 관리할 대상으로 정한 산출물 |
| 베이스라인 | 공식 검토를 거쳐 승인된 기준 시점. 이후 변경은 정해진 절차를 거쳐야 한다 |
| 체크아웃 | 저장소에서 작업용으로 꺼내 오는 것 |
| 체크인(커밋) | 수정한 내용을 저장소에 반영하는 것 |
| 브랜치 | 기준 흐름에서 갈라져 나온 별도 작업 줄기 |
| 머지 | 갈라진 줄기를 다시 합치는 것 |

## 형상관리 4가지 활동

문제로 가장 많이 나오는 부분이다. 활동 이름과 설명을 짝지어 외운다.

| 활동 | 하는 일 |
|---|---|
| 형상 식별 | 무엇을 관리할지 정하고 항목마다 이름·번호를 붙인다 |
| 형상 통제 | 변경 요청을 받아 검토·승인하고, 승인된 것만 반영한다 (변경통제위원회가 판단) |
| 형상 감사 | 베이스라인대로 만들어졌는지, 변경이 절차대로 처리됐는지 확인한다 |
| 형상 기록(상태 보고) | 항목의 현재 상태와 변경 이력을 기록하고 보고한다 |

헷갈리는 쌍은 통제와 감사다. 통제는 변경을 허락하는 쪽, 감사는 허락대로 됐는지 확인하는 쪽이다.

<details>
<summary>형상관리를 하면 좋아지는 점</summary>

- 잘못 고친 걸 이전 버전으로 되돌릴 수 있다.
- 여러 사람이 같은 파일을 고칠 때 충돌을 발견하고 조정할 수 있다.
- 배포된 버전이 어떤 소스에서 나왔는지 추적된다.
- 변경 이력이 남아 책임 소재와 원인 분석이 쉬워진다.

</details>

## 버전관리 도구 세 갈래

버전관리 시스템은 저장소를 어디에 두느냐에 따라 나뉜다.

| 방식 | 저장소 | 대표 도구(시험 단골) |
|---|---|---|
| 로컬·공유 폴더 | 공용 폴더 한 곳의 파일을 잠그고 수정 | RCS, SCCS |
| 클라이언트·서버 | 중앙 서버에 저장소가 하나 | CVS, SVN(Subversion) |
| 분산 | 개발자마다 저장소 전체 사본을 가진다 | Git, Bazaar |

중앙 방식은 서버가 죽으면 작업이 막히지만, 분산 방식은 각자 전체 이력을 갖고 있어 오프라인에서도 커밋하고 브랜치를 만들 수 있다. Git의 내부 구조는 [자세히 → Git 제대로 알기](#/post/cs-git)에 따로 적었다.

머지는 Pro Git 기준으로 두 경우가 있다. 합치려는 브랜치가 현재 브랜치의 바로 앞에 있으면 포인터만 앞으로 옮기는 fast-forward라서 새 커밋이 안 생긴다. 양쪽이 각자 커밋을 쌓아 갈라졌으면 두 브랜치 끝과 공통 조상 세 스냅샷으로 합치고, 부모가 둘인 머지 커밋이 새로 생긴다. 같은 파일의 같은 부분을 양쪽에서 다르게 고쳤다면 충돌이 나고, 충돌 표시를 직접 고친 뒤 `git add`로 해결 표시를 하고 커밋해야 머지가 끝난다.

<details>
<summary>Git 기본 명령 몇 개</summary>

| 명령 | 하는 일 |
|---|---|
| `git add` | 변경을 스테이징 영역에 올린다 |
| `git commit` | 스테이징된 내용을 커밋으로 확정한다 |
| `git branch` | 브랜치를 만들거나 목록을 본다 |
| `git merge` | 다른 브랜치를 현재 브랜치에 합친다 |
| `git status` | 현재 상태와 충돌 파일을 본다 |

</details>

## 빌드와 빌드 도구

빌드는 소스를 컴파일하고, 라이브러리를 연결하고, 테스트를 돌리고, 실행 가능한 형태로 묶는 과정이다. 손으로 하면 실수가 나니 도구가 정해진 순서로 대신 돌린다.

시험에 나오는 도구는 Make, Ant, Maven, Gradle 정도다. 선언 방식이 다르다는 점으로 구분한다. Ant는 작업 순서를 직접 적는 쪽이고, Maven은 정해진 생명주기에 맞춰 설정하는 쪽이다. 의존 라이브러리를 내려받아 관리해 주는 것도 Maven·Gradle 같은 쪽의 특징으로 묶어 외운다.

Maven 문서에서 확인한 기본 생명주기 단계는 이렇다.

| 순서 | 단계 | 뜻 |
|---|---|---|
| 1 | validate | 프로젝트 구성이 맞고 필요한 정보가 있는지 검사 |
| 2 | compile | 소스 코드 컴파일 |
| 3 | test | 단위 테스트 실행(패키징·배포가 필요 없어야 함) |
| 4 | package | JAR 같은 배포 형태로 묶기 |
| 5 | verify | 통합 테스트 결과 등 품질 기준 점검 |
| 6 | install | 로컬 저장소에 설치 |
| 7 | deploy | 원격 저장소에 복사해 공유 |

`mvn verify`처럼 한 단계를 지정하면 그 앞 단계가 순서대로 전부 실행된다. 이전 빌드 산출물을 지우는 `clean`은 별도 생명주기라서 `mvn clean deploy`처럼 앞에 붙여 쓴다. 테스트 단계가 빌드 안에 들어 있다는 점이 [자세히 → 소프트웨어 테스트](#/post/jb-testing)와 이어진다.

빌드와 테스트를 코드가 합쳐질 때마다 자동으로 돌리는 것이 CI, 거기에 배포까지 자동으로 이어 붙인 것이 CD다. 파이프라인 구성은 [자세히 → CI/CD와 배포 전략](#/post/cloud-cicd)에서 다뤘다.

## 릴리즈와 버전 번호

릴리즈는 빌드된 결과물을 사용자나 운영 환경에 내보내는 일이다. 내보내기 전후로 같이 챙기는 것이 두 가지다.

- 릴리즈 노트: 이번 버전에서 뭐가 추가되고 고쳐졌고, 알려진 문제가 뭔지 적은 문서
- 이전 버전 보관: 문제가 생기면 되돌릴 수 있게 배포본과 소스의 대응을 남겨 둔다

버전 번호는 시맨틱 버저닝(SemVer) 규칙이 가장 널리 언급된다. 공식 문서 기준으로 정리하면 이렇다.

| 자리 | 올리는 때 |
|---|---|
| MAJOR | 하위 호환이 깨지는 API 변경 |
| MINOR | 하위 호환되는 기능 추가 |
| PATCH | 하위 호환되는 버그 수정 |

숫자를 올리면 그 오른쪽 숫자는 0으로 돌아간다(1.4.2에서 MINOR를 올리면 1.5.0). 0.y.z는 초기 개발 단계라 언제든 바뀔 수 있고, 1.0.0부터 공개 API가 정해진다. `1.0.0-rc.1`처럼 하이픈 뒤에 붙이는 건 사전 릴리즈로 정식 `1.0.0`보다 우선순위가 낮다. `+` 뒤에 붙는 빌드 메타데이터는 버전 비교에서 무시된다. 한 번 배포된 버전의 내용은 바꾸면 안 되고, 바뀌면 새 버전 번호를 받아야 한다.

개발 단계별 이름인 알파(내부 시험)와 베타(외부 일부 사용자 시험), 그다음 정식 출시 순서도 같이 알아 둔다.

## 코드 리뷰

코드를 합치기 전에 다른 사람이 읽고 결함을 찾는 활동이다. 시험에서는 정적 기법이라 실행하지 않고 사람이 본다는 점, 그리고 형식의 엄격함 차이를 묻는다.

| 유형 | 느낌 |
|---|---|
| 동료 검토 | 작성자와 동료가 가볍게 돌려 보는 비형식 리뷰 |
| 워크스루 | 작성자가 산출물을 설명하며 참석자들이 의견을 내는 방식 |
| 인스펙션 | 역할(중재자·기록자 등)과 절차가 정해진 가장 형식적인 방식 |

형식이 갈수록 엄격한 순서는 동료 검토, 워크스루, 인스펙션이다. 실행하지 않고 코드를 보는 검증은 [자세히 → 소프트웨어 테스트](#/post/jb-testing)의 정적 테스트와 같은 범주다.

## 자주 틀리는 부분

- 형상 통제와 형상 감사를 반대로 외우는 경우. 통제는 승인, 감사는 확인이다.
- 베이스라인을 "최신 버전"으로 착각하는 경우. 공식적으로 승인돼 변경에 절차가 붙은 기준점이다.
- Git을 클라이언트·서버 방식으로 분류하는 경우. 분산 방식이다.
- SemVer에서 버그 수정까지 MINOR를 올린다고 생각하는 경우. 버그 수정은 PATCH다.
- `install`과 `deploy`를 같게 보는 경우. 앞은 로컬 저장소, 뒤는 원격 저장소다.

일정·비용처럼 관리 쪽 개념은 [자세히 → 프로젝트 관리](#/post/jb-project-mgmt)에서 이어진다.
