时间复杂度描述了当输入增大时，运算次数增长的速度。在编程竞赛中，我们仅凭输入规模就能预先判断“这个解法能否在规定时间内通过”。

## 什么是时间复杂度

即使解决同一个问题，不同代码的运行时间也不同。如果以秒为单位测量，结果会因计算机而异，因此我们只关注当输入大小 $n$ 增大时，运算次数如何增长。这种增长规律用 Big-O 表示。

- 遍历一次数组大约需要 $n$ 次操作，记为 O(n)。
- 双重循环则需要 $n \times n$ 次操作，记为 O(n²)。
- 每次将规模减半则需要 $\log n$ 次操作，记为 O(log n)。

常数倍或低阶项会被忽略。例如 $3n+5$ 和 $100n$ 都记为 O(n)。虽然实际上相差 100 倍，但当 $n$ 很大时，它们的曲线形状相同，因此归为一类。通常我们基于最坏情况来记录。

## 根据输入规模估算

编程竞赛服务器的评测环境大致假设 Python 每秒能执行数千万次简单运算。这个数值因评测环境而异，并非精确值，而是一种经验估计。通过这种估算观察 $n$ 的范围，几乎可以确定可用的解法。

| $n$ 的最大值 | 大致允许的复杂度 | 应想到的算法 |
|---|---|---|
| 10~20 | O(2ⁿ), O(n!) | 暴力搜索、回溯 |
| 500 | O(n³) | 三重循环、Floyd-Warshall 算法 |
| 5,000 | O(n²) | 双重循环、简单动态规划 |
| 100,000~1,000,000 | O(n log n) | 排序、二分查找、堆 |
| 10,000,000 以上 | O(n) 或 O(log n) | 单次遍历、数学公式 |

表格是基于经验估计，并非绝对精确。但即便如此，如果 $n$ 为 10 万却使用了双重循环（约 $10^{10}$ 次操作），能立刻意识到会超时。在写代码前养成先进行此类计算的习惯是最有价值的。

## 常见的时间复杂度

- O(1)：通过索引取值、在字典中通过键查找（平均情况）。
- O(log n)：在已排序数组中进行二分查找。[详情 → 排序与二分查找](#/post/algo-sort-search)
- O(n)：遍历一次列表、求和、寻找最大值。
- O(n log n)：排序。Python 的 `sort()` 函数即属于此类。
- O(n²)：比较所有元素对的双重循环。
- O(2ⁿ)：每个元素选择“放入”或“不放入”的所有子集。[详情 → 递归与回溯](#/post/algo-recursion)

空间复杂度也用同样的方式表示。如果额外使用的内存随输入规模成比例增加，则为 O(n)。在编程竞赛中，时间问题通常更为紧迫，但如果动态规划表的大小设为 $n \times n$，则内存也会成为考量因素。

## 示例：两数之和

考虑“找出数组中和为 target 的两个元素的位置”这类问题。如果使用双重循环检查所有对，复杂度为 O(n²)。如果记录已遍历的值到字典中，只需检查 `target - x` 是否存在，复杂度则为 O(n)。

```python
def two_sum_slow(a, t):          # O(n^2)
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):
            if a[i] + a[j] == t:
                return (i, j)

def two_sum_fast(a, t):          # O(n), 공간 O(n)
    seen = {}
    for i, x in enumerate(a):
        if t - x in seen:
            return (seen[t - x], i)
        seen[x] = i
```

实际运行结果显示，两者在 `1..3000` 范围内都给出了相同的答案 `(2998, 2999)`。较慢的方法在 $n=5,000$ 时耗时 0.25 秒，而较快方法在 $n=200,000$ 时仅耗时 0.025 秒。尽管输入规模大了 40 倍，但速度却快了 10 倍。这里的数字基于我的 PC，具体数值本身意义不大，只需关注差距即可。为了节省时间而牺牲内存的做法正是使用哈希表的原因。[详情 → 数组·字符串·哈希](#/post/algo-array-hash)

<details>
<summary>用公式看 Big-O 定义</summary>

$f(n)$ 是 $O(g(n))$ 意味着存在一个正数 $c$，使得对于足够大的 $n$，有 $f(n) \le c \cdot g(n)$。例如，若 $f(n) = 3n^2 + 10n + 7$，则当 $n \ge 1$ 时，$f(n) \le 20n^2$，因此为 O(n²)。

即使同为 O(n)，如果每次循环执行的操作不同，实际时间也会有很大差异。在编程竞赛中，常数倍通常被忽略，但在时限紧张的问题中，常数项可能会成为关键。
</details>

## Python 中容易变慢的地方

复杂度不仅是算法本身的问题，也取决于所使用的数据结构及其操作。Python 中有些看似只有一行的代码，内部却包含 O(n) 的操作。

| 想要做的事 | 慢的写法 | 快的写法 |
|---|---|---|
| 从开头取出元素 | `list.pop(0)` O(n) | `deque.popleft()` O(1) |
| 检查值是否存在 | `x in list` O(n) | `x in set` 平均 O(1) |
| 字符串拼接 | 重复执行 `s += t` | 收集到列表中再使用 `"".join()` |
| 访问中间元素 | `deque[i]` O(n) | `list[i]` O(1) |

`collections.deque` 官方文档指出，列表在 `pop(0)`和`insert(0, v)`操作中会产生 O(n) 的内存移动开销，而 deque 在两端进行插入和删除操作的时间复杂度为 O(1)。同一文档也提到，deque 的索引访问在两端为 O(1)，而在中间则为 O(n)。如果需要队列功能请使用 deque，如果频繁通过索引访问则使用列表。[详情 → 栈·队列·双端队列](#/post/algo-stack-queue)

我在本地 PC 上重新测试的结果如下。具体时间会随环境不同而变化，仅供参考比例。

| 实验 | 时间 |
|---|---|
| 在 10 万个元素的列表中执行 5 万次 `pop(0)` | 0.36 秒 |
| 在相同大小的 deque 中执行 5 万次 `popleft()` | 0.001 秒 |
| 在 2 万个元素的列表中执行 2 千次 `in` 操作 | 0.12 秒 |
| 在 2 万个 set 中执行 2 千次 `in` 操作 | 0.0001 秒 |

关于字符串部分，Python 官方文档（序列类型）指出，重复拼接不变序列会导致时间与总长度平方成正比。文档还建议将字符串收集到列表中，然后使用 `join` 一次性连接。

排序方面，文档指出 `sort()`和`sorted()`均为稳定排序，即相同元素之间的原始顺序保持不变。这一性质在需要分两次进行排序时会被利用。只需记住排序本身的时间复杂度为 O(n log n)。

## 竞赛编程基础输入输出

在处理大量输入的问题中，`input()` 速度较慢，有时会导致超时。因此通常采用以下方式开始：

```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
arr = list(map(int, input().split()))
print(n, m, arr)
```

将 `3 5`和`1 2 3`作为输入进行测试，输出结果仍为`3 5 [1, 2, 3]`。`readline` 会一并读取行尾的换行符，因此在直接使用时需附加 `.rstrip()`；若转换为数字则无需处理。

在递归深度较深的问题中，由于 Python 默认的递归限制较低，经常需要调用 `sys.setrecursionlimit` 来提高限制。这部分将在递归相关文章中继续讨论。本文直接验证的代码仅限于上述内容。

如果输出量较大，不要每次调用 `print`，而应收集到列表中，然后使用 `"\n".join(...)` 一次性输出。这与前述字符串拼接的原因相同。

<details>
<summary>当不确定一行输入包含多少个数据时</summary>

- 每行一个整数：`n = int(input())`
- 每行多个整数赋值给变量：`a, b = map(int, input().split())`
- 每行多个整数存入列表：`arr = list(map(int, input().split()))`
- 多行以网格形式输入时：`grid = [list(map(int, input().split())) for _ in range(n)]`
- 带有数字的字符串（例如 `10110`）：`list(map(int, input().rstrip()))`

在上述使用 `readline` 的方式中，`int()` 会自动处理输入末尾的换行符，而字符串行则需要手动使用 `rstrip()`。
</details>

## 常见误区

- **复杂度低就一定快**：当 n 非常小时，简单的 O(n²) 可能比复杂的 O(n log n) 更快；估算应在 n 较大时成立。
- **嵌套循环一定导致 O(n²)**：如果内层循环仅执行常数次，则整体为 O(n)。需要观察内层循环的范围受什么影响。
- **Python 内置函数都是 O(1)**：`in`、`list.index`、`list.count`以及切片操作的时间复杂度都与长度相关，并非轻量级操作。
- **平均情况与最坏情况相同**：字典和集合的 O(1) 指的是平均情况，若哈希冲突严重则可能变慢，这一点需要知晓。

在数据库中建立索引的原因也基于类似的计算逻辑：旨在避免遍历整个数据的 O(n)，转而通过树结构以 O(log n) 进行查找。相关内容将在 [详情 → 索引](#/post/db-index) 中讨论。

算法类型的全部分类计划整理在地图文章中。[详情 → 算法类型地图](#/post/algo-map)

大多数超时并非因为代码编写得慢，而是因为编写前没有考虑 n 的大小导致的。
