## What it is
An OpenAI tool that finds security vulnerabilities in code, checks whether they're real, and fixes them. You can use it as a plugin inside Codex, as the `cs` command in a terminal, or automate it with a TypeScript SDK and a GitHub Action. A vulnerability is a gap in code an attacker can abuse, like SQL injection or a missing permission check.

Classic security scanners look for code that matches fixed rules (patterns). This one has a coding agent read and investigate the code. An agent is a program where a model takes several steps on its own, using tools. [More → Agents and the agent loop](#/post/ai-agent-loop)

## How it works
The basic command is `cs scan .`. When it finishes, three files are left in a folder.

- `report.md`: a readable summary of scope and findings
- `findings.json`: source locations and evidence for each finding
- `scan-manifest.json`: what was scanned and what was left out

You pick a scope: the whole repo, certain paths (`--path`), a commit diff (`--diff origin/main`), or uncommitted changes (`--working-tree`). For PR review you'd use a diff scan.

There are two modes, Standard and Deep. Deep repeats Standard scans. Several workers investigate at once and can ask each other to check a location, and each new batch gets the titles and locations of earlier findings so it digs into other paths. It stops after a few scans in a row find nothing new (`--stop-after-no-new`). The docs list `gpt-5.6-sol` with `xhigh` effort as the default, with one parent and up to eight delegated workers. [More → Subagents and multi-agent](#/post/ai-subagent)

The steps after finding something felt like the core of it.

- validate: re-reviews one finding and decides if it's real. The tools can only read code; network and web search are off.
- patch: writes a fix and, if you want, a draft PR. You can add a patch-risk assessment.
- verify-fix: looks again after a fix and answers fixed, still_vulnerable, or inconclusive. Exit codes are 0, 1, 2, so it's easy to hook into CI.

It also records how far it actually looked. The docs say a completed scan means the workflow finished, not that every file or every possible vulnerability was examined. Excluded paths, deferred work, and open questions are written down.

On top of that: drafting `SECURITY.md`, saving threat models, importing results from other scanners like Semgrep, Snyk, and Wiz, sending findings to Linear, Jira, or GitHub, and exporting SARIF, JSON, or CSV. A threat model is a document about who could attack what, and how.

## For beginners
As a PM, I like that "found", "confirmed", and "fixed" are separate steps. It doesn't just trust what the AI says and keeps evidence and scope alongside, which seems easy to get a report from. For someone new to dev, running `cs scan . --diff origin/main` on each PR in a small repo seems like a fine start. The GitHub Action example uses an estimated $5 limit per scan, and notes that in-flight requests can go over it.

Things to watch. You need a login or API key, and model usage costs money. Some security requests and protected findings need OpenAI's Trusted Access for Cyber. Other providers like Bedrock, OpenRouter, and Fireworks AI are supported. I couldn't confirm any detection accuracy numbers. There's an evals folder in the repo, but I didn't read the results.
