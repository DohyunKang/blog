LLM でアプリを開発する際、モデルの呼び出し自体よりもその周辺部分で手がかかることが多いです。構造をどう設計するか、外部ドキュメントをどう付与するか、コストはいくらかかるか、成果をどう評価するか、どこでブロックすべきか、ツールをどう接続するか。このシリーズは、その 6 つのポイントをそれぞれ実際に追ってみた記事であり、この記事はその目次です。用語が馴染めない場合は、まず [AI 概念マップ](#/post/ai-map) をご覧ください。

## 全体の流れ

```
구조를 정한다   → 에이전트 설계 패턴
지식을 붙인다   → RAG 직접 만들기
도구를 붙인다   → MCP 서버 만들어 보기
돈을 계산한다   → AI 서비스 원가 구조
품질을 잰다     → LLM 앱 평가
바깥에서 막는다 → 가드레일과 안전장치
```

## 1. 作成前に決めること

**エージェント設計パターン**: エージェントを作成する前に、各パターンのように事前に決まった順序で書かれたワークフローになるかを確認します。LLM の呼び出し一回だけで完結するか、そうでない場合はどこまでを定義し、どこからモデルに任せるかが出発点です。
[詳細 → エージェント設計パターン](#/post/app-agent-design)

**AI サービスのコスト構造**: ユーザーが使用するたびにトークン料が発生するため、一度の呼び出しのコストを計算し、回数とユーザー数を掛けて月間コストを確認します。
[詳細 → AI サービスのコスト構造](#/post/app-cost)

## 2. 機能を実装する

**RAG を直接実装**: ライブラリを使わずに数十行の Python コードで RAG を構築・実行し、ドキュメントの分割・ベクトル化・検索・評価までの 5 つの手順を追います。概念については [RAG](#/post/ai-rag) の記事をご覧ください。
[詳細 → RAG の直接実装](#/post/app-rag-build)

**MCP サーバーを試す**: 関数に名前と説明を付けて外部に公開する作業であり、Python ファイル一つで 2 つのツールを持つサーバーを実際に動かしてみました。規格については [MCP](#/post/ai-mcp) の記事をご覧ください。
[詳細 → MCP サーバーの実装](#/post/app-mcp-server)

## 3. 成果を確認し守る

**LLM アプリの評価**: プロンプトを修正するたびに感覚で確認すると、どこかが静かに壊れてしまうため、事前に定義した問題セットと採点基準に基づいてスコアを付け、同じ基準で比較します。
[詳細 → LLM アプリの評価](#/post/app-eval)

**ガードレールと安全装置**: モデルに注意するよう頼むだけでは安全装置にはならないため、不適切な入力や行動をアプリ側のコードでブロックする箇所を別途設けます。モデルの口調を直すのではなく、外側に扉をつける作業です。
[詳細 → ガードレールと安全装置](#/post/app-guardrails)

## 読む順序

初めての場合は、設計パターン → コスト → RAG → MCP サーバー → 評価 → ガードレールの順で読むことをお勧めします。すでに実装している場合は、詰まっている箇所だけを選んで読んでください。
