추론 최적화는 이미 학습된 모델에 질문을 넣고 답을 뽑는 과정을 더 빠르고 싸게 만드는 기법 모음이다. 정리해 보니 KV 캐시, 배치, 스트리밍, 투기적 디코딩이 서로 연결된 한 덩어리였다.

## 정의부터

추론(inference)은 학습이 끝난 모델을 쓰는 단계다. 학습은 한 번 크게 돌리고 끝나지만 추론은 사용자가 쓸 때마다 계속 돈다. 서비스 입장에서는 이쪽이 계속 나가는 비용이다. ([자세히 → 사전학습](#/post/ml-pretraining))

LLM은 답을 한 번에 만들지 않는다. 토큰을 하나 만들고, 그 토큰을 입력에 붙여서 다시 모델을 돌리고, 또 하나 만든다. 이걸 끝 토큰이 나올 때까지 반복한다. 느림과 비용의 대부분이 이 반복 구조에서 나온다. ([자세히 → 트랜스포머](#/post/ml-transformer))

## 추론의 두 단계

한 요청의 처리는 두 단계로 나뉜다.

| 단계 | 하는 일 | 성격 |
|---|---|---|
| 프리필(prefill) | 입력 프롬프트 전체를 한 번에 처리 | 토큰을 병렬로 계산, 계산량이 많음 |
| 디코딩(decode) | 토큰을 하나씩 생성 | 한 번에 한 토큰, 매번 모델 가중치와 캐시를 메모리에서 읽어야 함 |

프리필은 사용자가 첫 글자를 보기까지의 시간에, 디코딩은 이후 글자가 나오는 속도에 영향을 준다. 최적화 기법은 대체로 둘 중 하나, 특히 디코딩 쪽의 병목을 건드린다. 디코딩은 계산보다 메모리에서 데이터를 읽어 오는 시간이 더 걸리는 경향이 있다.

## KV 캐시

트랜스포머의 어텐션은 새 토큰을 만들 때 앞의 모든 토큰의 key, value 값을 쓴다. 이 값은 토큰마다, 층마다 정해지고 이미 만든 토큰의 값은 바뀌지 않는다. 그래서 매번 다시 계산하지 않고 저장해 두고 재사용한다. 이게 KV 캐시다.

- 캐시가 없으면 토큰을 만들 때마다 앞 전체를 다시 계산한다.
- 캐시가 있으면 새 토큰 하나분만 계산하고 나머지는 읽어 온다.
- 대신 GPU 메모리를 차지한다. 대화가 길수록, 동시 요청이 많을수록 커진다.

([자세히 → 프롬프트 캐싱](#/post/ai-prompt-caching))은 이 KV 상태를 요청 사이에서도 재사용하는 서비스 쪽 기능이다.

<details>
<summary>KV 캐시가 얼마나 큰가 (계산 예시)</summary>

토큰 하나가 차지하는 크기는 다음 식이다.

```text
2(key와 value) x 층 수 x 어텐션 헤드 수 x 헤드 차원 x 자료형 바이트
```

실제 모델이 아니라 계산용으로 가정한 값이다. 32층, 32헤드, 헤드 차원 128, fp16(2바이트)이면 토큰 하나에 524,288바이트(0.5MB)다. 4,096토큰 대화 하나가 2GB가 된다. 요청 10개를 동시에 받으면 캐시만 20GB다. (python으로 계산해 확인했다.)

최근 모델 중에는 key/value 헤드 수를 줄여 이 크기를 줄이는 구조를 쓰는 것들이 있다.
</details>

## 배치와 연속 배치

GPU는 한 요청만 처리하면 놀고 있는 부분이 많다. 디코딩은 가중치를 메모리에서 읽는 비용이 크니, 요청 여러 개를 묶어 한 번 읽을 때 같이 계산하면 효율이 오른다. 이것이 배치(batching)다.

문제는 요청마다 답 길이가 다르다는 것이다. 고정된 묶음으로 돌리면 먼저 끝난 요청이 자리를 비운 채 가장 긴 요청이 끝나길 기다리고, 새 요청은 묶음이 끝날 때까지 대기한다.

Orca 논문(OSDI 2022)이 이 문제를 반복(iteration) 단위 스케줄링으로 풀었다. 모델을 한 번 돌 때마다 스케줄러가 개입해서, 끝난 요청은 바로 내보내고 대기 중인 새 요청을 빈자리에 넣는다. 이 방식을 보통 연속 배치(continuous batching)라고 부른다. 논문 페이지에는 이 용어가 없고 같은 발상이라고 읽었다. 논문은 GPT-3 175B에서 같은 지연 수준의 NVIDIA FasterTransformer 대비 처리량이 36.9배라고 보고한다.

```text
고정 배치:   [요청A ████████████]
             [요청B ████░░░░░░░░]  <- 끝났지만 자리가 빈 채로 대기
연속 배치:   [요청A ████████████]
             [요청B ████][요청C ████████]  <- 빈자리에 바로 새 요청
```

## PagedAttention

배치를 키우려면 KV 캐시를 많이 담아야 하는데, 요청마다 캐시가 얼마나 커질지 미리 알 수 없다. 최대 길이만큼 미리 잡아 두면 쓰지 않는 공간이 낭비되고, 크기가 제각각이라 조각(fragmentation)도 생긴다.

vLLM 논문(SOSP 2023)의 PagedAttention은 운영체제의 가상 메모리와 페이징을 가져온다. 캐시를 작은 블록으로 쪼개 필요할 때 하나씩 할당하고, 블록이 메모리에서 연속일 필요가 없게 한다. 같은 프롬프트를 쓰는 요청끼리는 블록을 공유할 수도 있다. 논문은 이렇게 해서 낭비를 거의 없애고, 기존 시스템(FasterTransformer, Orca) 대비 같은 지연에서 처리량이 2~4배 늘었다고 보고한다. 긴 시퀀스, 큰 모델, 복잡한 디코딩일수록 차이가 컸다고 한다. ([자세히 → vLLM](#/post/repo-vllm))

## 스트리밍

스트리밍은 총 생성 시간을 줄이는 기법이 아니라 체감 시간을 줄이는 방식이다. 답 전체가 끝날 때까지 기다리지 않고 토큰이 만들어지는 대로 흘려 보낸다. 디코딩이 어차피 한 토큰씩 나오니 구조상 자연스럽다.

- 사용자가 체감하는 건 첫 토큰까지의 시간(TTFT)이다. 프리필이 길면 TTFT가 늘어난다.
- 이후 토큰 사이 간격은 디코딩 속도다.
- 전체 시간이 같아도 스트리밍이 되면 훨씬 빠르게 느껴진다.

## 투기적 디코딩

디코딩이 느린 건 한 번에 한 토큰만 만들기 때문이다. 투기적 디코딩(speculative decoding)은 작고 빠른 모델이 토큰을 여러 개 먼저 추측해 두고, 큰 모델이 그 추측을 한 번에 병렬로 검증한다. 맞은 만큼은 큰 모델을 한 번 돌린 값으로 한꺼번에 받아들이고, 틀린 지점부터는 큰 모델의 값으로 바꿔서 다시 시작한다.

Leviathan 등의 논문은 T5-XXL에서 기존 구현 대비 대략 2~3배 빨라졌다고 보고하고, 모델 재학습이나 구조 변경이 필요 없으며 출력 분포가 바뀌지 않는다고 적는다. 즉 품질을 희생하는 근사가 아니라 같은 답을 더 빨리 얻는 방식이다.

잘 맞으려면 작은 모델이 큰 모델과 비슷하게 예측해야 한다. 쉬운 부분(정형 문장, 반복되는 코드)은 추측이 잘 맞고, 어려운 부분은 자주 틀린다.

<details>
<summary>한 번에 몇 토큰이 나오나 (계산 예시)</summary>

추측이 맞을 확률이 토큰마다 0.8이고 한 번에 4개를 추측한다고 가정하면, 큰 모델을 한 번 돌릴 때 얻는 토큰 수의 기댓값은 1 + 0.8 + 0.8^2 + 0.8^3 + 0.8^4 = 약 3.36개다. 가정한 값이고, 작은 모델을 돌리는 시간은 따로 들기 때문에 실제 속도 향상은 이보다 작다. 검증 과정에서 정확히 어떤 규칙으로 받아들이고 거절하는지는 논문의 수식을 따로 읽어야 하는데 이 글에서는 풀지 않았다.
</details>

## 서빙에서 같이 쓰는 개념

- 양자화: 가중치를 더 작은 숫자 형식으로 저장해 메모리와 읽는 시간을 줄인다. 대신 정밀도가 약간 떨어질 수 있다. ([자세히 → 로컬 모델](#/post/ml-local-models))
- 모델 병렬: 한 GPU에 안 들어가는 모델을 여러 GPU에 나눠 올린다.
- 프리픽스 캐시: 같은 앞부분을 쓰는 요청끼리 KV 캐시를 재사용한다.

실제 서비스 구성은 별도 글에서 이어진다. ([자세히 → AI 서빙 인프라](#/post/infra-ai-serving))

## 흔한 오해

- 스트리밍하면 모델이 더 빨리 계산하는 게 아니다. 같은 속도로 만들어진 걸 먼저 보여 줄 뿐이다.
- 투기적 디코딩은 답 품질을 깎는 지름길이 아니다. 논문에 따르면 출력 분포가 그대로다.
- 배치를 키우면 무조건 좋은 것도 아니다. 처리량은 오르지만 요청 하나가 기다리는 시간은 늘 수 있다.
- KV 캐시는 모델 크기와 별개로 메모리를 먹는다. 모델이 올라갔는데도 긴 대화에서 메모리가 모자랄 수 있는 이유다.
